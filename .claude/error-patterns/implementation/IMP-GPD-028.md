# IMP-GPD-028: 以舊路徑當 pathspec 追 git 歷史，rename 被顯示為刪除

## 基本資訊

| 項目 | 說明 |
|------|------|
| 分類 | Implementation |
| 風險等級 | 中 |
| 來源版本 | v0.6.0 |
| 發現日期 | 2026-11-09 |
| 發現途徑 | 判定文件中失效的舊票號時，第一輪結果把改號判為刪除；改用全 repo rename 對照表後推翻 |

## 症狀

要判定一個舊檔名（例：改號前的票檔）後來去了哪裡，執行：

```bash
git log -M --diff-filter=RD --name-status -- '*/<舊檔名>.md'
```

輸出只有 `D <舊路徑>`，沒有 `R`。據此判定「該檔已刪除」。

實際狀態：該檔是改名，新路徑在另一個檔名下仍存在。一次實測（2026-11-09，票號改號後的文件引用盤點）中，16 個被判為刪除的舊號全部是改名（最長鏈經 5 次改名），沒有一個是真的刪除。

## 根因

git 的 rename 偵測只在 diff 的兩側都在 pathspec 範圍內時才配對。pathspec 只匹配舊檔名時，改名後的新路徑不在範圍內，git 只看得到「舊路徑消失」，於是顯示為 `D`。

`-M` 與 `--diff-filter=R` 都無法補救：它們作用在 pathspec 已過濾後的 diff 上。`--follow` 只能從**現存**路徑往回追，不能從舊路徑往前追，不適用於本情境。

## 解決方案

1. 不帶檔名 pathspec，一次匯出整個 repo（或整個目錄）的 rename 對：

   ```bash
   git log --name-status -M --diff-filter=R --format=@%h > renames.txt
   ```

   要限縮範圍時，pathspec 用目錄層級的萬用字元（例：`'docs/work-logs/**/tickets/*.md'`），讓改名前後兩側都落在範圍內。

2. 由 `renames.txt` 建「舊名 → 新名」映射，從舊名沿映射追到現存檔。改名可能換序號，不可用名稱相似度猜測。
3. 用 `git show <commit>^:<舊路徑>` 讀改名前的內容（如標題），與終點檔比對，確認是同一份內容，不是相似度誤配對。
4. 映射追不到的才判為刪除或從未存在；從未存在的再讀引用上下文分類（外部識別符、範例、打錯字）。

## 預防措施

- 判定「檔案被刪除」之前，先確認判定所用的 pathspec 能涵蓋改名後的新路徑。
- 大量判定時固定採用「先建對照表、再查表」的兩段式流程，不逐一以舊路徑查詢。
- 檢查 rename 偵測是否因上限被截斷：以 `-l0` 重跑並比對 `R` 行數；有差異即代表大批改名被拆成 `D`＋`A`。
