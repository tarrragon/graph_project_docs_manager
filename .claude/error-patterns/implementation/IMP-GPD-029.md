# IMP-GPD-029: 以 null 同時代表「尚未就緒」與「沒有資料」，消費端以預設值續算，結果靜默失真

## 基本資訊

| 項目 | 說明 |
|------|------|
| 分類 | Implementation |
| 風險等級 | 中 |
| 來源版本 | v0.7.0 |
| 發現日期 | 2026-11-10 |
| 發現途徑 | 實機驗證兩度發現事件數不對（一次為 0，一次是篩選旗標從未設上）。兩次的根因同形，第三處同形寫法是讀碼時找到的 |

## 症狀

- 非同步載入的值（Riverpod 的 `AsyncValue.value`、「目前輪次」的結果、尚未完成的快取）在載入中讀到 null，消費端把它當成「沒有這筆資料」，代入空清單、空字串、永不匹配的正規式等預設值，繼續計算。
- 沒有例外，也沒有日誌。產出看起來正常，只是錯了，例如事件數為 0、某個旗標永遠是 false、說明文字裡的鍵名是空的。
- 單元測試全綠：測試直接注入已就緒的值，或覆寫 provider，從來不會走到「載入中」這個時序。
- 只在實機的特定時序下出現。例如使用者進入畫面時，背景重掃剛好把「目前輪次」打回進行中；或首次讀取發生在資產載入完成之前。

## 根因

- 同一個 null 承載兩種語意：「還不知道」（未就緒，應該等待或標記為未知），以及「已知為空」（就緒但沒有值，可以用預設值）。型別系統看不出兩者的差別。
- 消費端為了不讓程式崩潰，寫出 `?? 預設值`、`?.x ?? const []` 這類回落。回落把「還不知道」改寫成「已知為空」，錯誤就此靜默。
- 「目前狀態」型的來源（例如重掃時會先清空再重跑的輪次 provider）有週期性的空窗，消費端看不出自己剛好讀在空窗裡。

## 解決方案

1. **讓未就緒可辨識**：未就緒時用專屬型別或狀態（sealed 狀態、`AsyncLoading`、專屬識別字串）傳給消費端，不和「沒有資料」共用同一個 null。
2. **未就緒時等待或中止，不代入預設值**：需要完整資料才能計算的地方，先等資料就緒；等不到就落到可辨識的失敗狀態，並寫日誌。
3. **改讀「最後一次完成的結果」**：來源有「重掃時先清空」的空窗時，改讀保留上一次完成結果的 provider。只有從未完成過的時候才等待。
4. **快取鍵把未就緒分開**：快取鍵或識別值要讓「未就緒」與任何真實值不同，避免以預設值算出的結果被快取，之後一再命中。
5. **回落必附日誌**：真的需要回落時，依可觀測性規則 1 寫 warning 日誌，日誌中帶原因碼。

## 預防措施

- Code review 時，看到非同步來源的 `.value`、`?? const []`、`?? RegExp('(?!)')`，就問一句：這裡的 null 是「還不知道」還是「已知為空」？
- 測試要涵蓋「載入中進入」的時序：在替身中讓來源停在進行中（hold 或 completer），斷言消費端會等待或標記為未知，不能以預設值得出結果。配合 E2 正向對照：修正前，這個案例必須是紅燈。
- 整合測試不要一律覆寫上游 provider。至少保留一案走實際接線，只替身 I/O 邊界。

## 與相關模式的關係

- `TEST-GPD-1005` 是測試端的同源現象：以 async override 模擬「已載入」，首幀仍是 loading。本模式是產品碼端：在 loading 時把 null 當成已載入的空值。
- 可觀測性規則 1（catch 後回傳預設值必須記錄 warning）在這裡的延伸：沒有 catch 的 `?? 預設值` 回落，同樣會讓錯誤靜默消失。
