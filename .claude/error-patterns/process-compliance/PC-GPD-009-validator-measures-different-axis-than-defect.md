# PC-GPD-009: 驗證器驗的維度與缺陷所在的維度不同軸，每次都是「查了，而且通過了」

## 基本資訊

| 項目 | 值 |
|------|------|
| 編號 | PC-GPD-009 |
| 類別 | process-compliance |
| 風險等級 | 高 |
| 發現日期 | 2026-09-08 |
| 來源版本 | 0.1.0 |

## 症狀

一個名稱宣稱保證性質 P 的檢查，實際量的是一個容易量的代理指標 Q。Q 與 P 之間有縫，缺陷落在縫裡：**檢查跑了、通過了，而缺陷完好無損**。

這不是檢查器壞掉——它正確地量了 Q，回報也誠實。壞的是「通過 Q 即滿足 P」這個從未被寫下來的假設。

**識別特徵**：

- 檢查名稱或訊息用性質的語言（「不溢位」「範圍正確」「條件齊備」），實作用代理指標的語言（不拋例外、檔名相符、條目數 >= N）
- 缺陷被發現時，回顧發現**該檢查當時是綠的**，而且再跑一次還是綠的
- 修正缺陷之後，若不動檢查器，同一形態的下一個缺陷仍會通過

本模式有兩種來源，防護方向不同，須分開處理。

### 來源一：工具的宣稱與量測不符

工具本身宣稱在驗 P（名稱、訊息、`--help` 描述都這樣說），實際量的是 Q。使用者沒有理由懷疑——**橋是工具搭的**。

**單一 session 內的實例**（2026-09-08，同一天由不同活動各自撞上）：

| 檢查 | 宣稱保證（P） | 實際量測（Q） | 縫 |
|------|-------------|-------------|-----|
| 派發前檢查的路徑項 | where.files 指向本票要改的檔案 | 該路徑在檔案系統存在 | 路徑真實存在但與本票無關（寫成 `x_dispatch.py` 而目標在 `x_dispatch_validate.py`），通過只證明不是手誤 |
| 派發前檢查的驗收項 | 本票有可驗收的目標 | acceptance 條目數 >= 門檻 | 未填樣板恰好滿足門檻且句型完整，恆通過（詳見 `PC-GPD-008`） |
| 提交前的範圍核對 | 這次 commit 只含目標檔 | `git diff --cached` 的檔名清單相符 | 檔名對而 index entry 相對新 HEAD 已過期，裸 commit 靜默回滾他人內容 |
| 元件測試的溢位斷言 | 內容沒有超出容器 | 上一次 pump 沒有拋例外 | 固定高度容器對超出的文字是靜默裁切、不拋例外，字形被切而測試全綠 |
| 整套測試綠燈 | 功能在真實環境可用 | 以替身執行的斷言全部通過 | 替身恆可用，掛在服務成功路徑上的回饋因此恆存在（詳見 `ARCH-GPD-001`） |
| worktree 清理守衛的遺失警告 | 強制移除會遺失修改內容 | git status 首欄為 `D` | `D` 是刪除不是修改，且磁碟內容與已合併的主線完全相同，警告的損害不存在 |
| CLI 參數說明 | 這個參數怎麼用 | 這個參數是什麼 | 兩個外觀同構的參數，一個吃逗號分隔一個不吃，說明文字給不出區分依據 |

載體完全不同——票務驗證器、git 工具、測試斷言輔助、整個測試套件、清理守衛、命令列說明——形狀相同。

### 來源二：使用者臨時發明的代理指標

工具從未宣稱它回傳 P，是使用者當下把它當成 P 用。**橋是使用者自己搭的**，沒有人誤導。

**實例**（同日）：以 `ls -t | head -1` 當作「我剛建立的那張票」的識別。並行環境中三個 session 同時在動 ticket 檔案，`ls -t` 量的是最近被修改（Q），不是我剛建立（P）。結果是把一組 acceptance 寫進了另一張票——**而該操作成功執行，因為那張票真實存在**。

**這一類比壞掉的工具更難防**：壞掉的檢查器修一次就不再壞；臨時發明的代理指標每次發明的都不一樣（這次是 `ls -t`，下次可能是序號遞推、或「剛才那個 commit 的檔案清單」），形態不同但都會失敗。防護不能列黑名單，只能禁行為——**用建立動作本身的回傳值，不用代理指標去找剛建立的東西**（該次 `ticket create` 有報 ID，未讀）。

### 兩類共同的危險特徵

**它回傳一個合法值而非錯誤。** 上述所有實例中，整條執行路徑沒有任何一步報錯：`ls -t` 給出真實存在的票號、`set-acceptance` 對該票執行成功、清理守衛的警告內容格式正確。錯誤只在有人閱讀內容時才顯形，而閱讀者往往不是操作者。

## 根因

代理指標之所以被選中，正是因為它**容易量**：檔案存在性是一次 stat，條目數是一次 len，例外有無是一次 takeException。真正的性質（相關、已填、新鮮、沒被裁切、真實邊界可用）都需要更多脈絡或更貴的手段。

寫檢查的人知道自己在量 Q，但檢查一旦被命名為 P，**名稱就成了讀者的認知**。此後每個讀者看到綠燈，得到的是「P 成立」的印象，而不是「Q 成立」。這個落差沒有任何機制會提醒——綠燈的外觀不因為量的是代理指標而有所不同。

由此推出這類缺口最難處理的性質：**同一個驗證器跑第二次永遠揭露不了**。它會再次正確地量 Q，再次通過。發現缺陷的唯一途徑是**換軸重查**——用另一個維度的觀測去撞它。上表實例中，沒有一個是被原檢查器發現的：多數由人工覆核撞到，其餘由實機目視或另一個 session 的獨立查證揭露。

**為何殘留下來的全是這一類**（並行 session 於同日提出）：能被**字面偵測**的缺陷已經有 hook 擋了——規則 8 的專案識別符違反有固定格式，一寫進去就被攔。而「acceptance 是未填樣板」「where.files 指錯檔案」「這個路徑跟本票相關嗎」都需要**語意判斷**，寫不成字面規則。

所以這批缺陷集中在語意判斷區間不是巧合，**是既有防護體系篩選之後的殘留分佈**：字面層已被清空，剩下的必然是需要判斷的那些。這也解釋了為何它們幾乎只能由人（或另一個帶著不同脈絡的 session）發現——目前沒有機械手段能站在那個位置。

## 解決方案

1. **檢查的名稱與訊息說出量的是什麼，不說宣稱保證什麼**。「where.files 路徑全數存在」比「路徑正確」誠實；讀者看到前者會自己補問「存在但相關嗎」，看到後者不會。
2. **為每個檢查寫下 Q 與 P 的差距**，放在檢查的實作註解或文件裡。寫不出差距有兩種可能：Q 確實等於 P（少見），或作者沒想過（常見）。這個問題本身就有診斷價值。
3. **確定性判準該硬、啟發式判準該軟**。Q 與 P 有大縫的檢查不該硬擋（誤報成本高），但也不該讓它的綠燈被當成 P 的保證——分級本身要與縫的寬度對應。
4. **換軸重查是唯一有效的複驗**。同一檢查跑第二次不產生新資訊。複驗要問「有什麼是這個檢查結構上看不到的」，再用另一個維度去看。
5. **縫太寬時補檢查，而不是補提醒**。文件寫「請注意路徑要相關」不會被讀到；把相關性納入檢查（例如比對路徑與 ticket 標題或 how.strategy 的關鍵字）才會生效。
6. **來源二專屬：不用代理指標定位剛建立的東西**。用建立動作本身的回傳值（`create` 回報的 ID、寫入函式回傳的路徑），不用「最近修改的那個」「序號加一」「剛才那批檔案」這類當下推導出來的識別。此條無法以檢查器落實——代理指標是使用者臨場發明的，工具不知道它被發明了；只能作為行為禁令。

## 預防措施

| 時機 | 動作 |
|------|------|
| 設計任何檢查、斷言或守衛時 | 明寫「本檢查量的是 Q」與「Q 與宣稱性質 P 的差距」；差距寫不出來時，先確認是真的沒有還是沒想過 |
| 為檢查命名或撰寫訊息時 | 用量測的語言，不用性質的語言 |
| 檢查通過但仍懷疑時 | 不要重跑同一檢查——問「這個檢查結構上看不到什麼」，換軸觀測 |
| 缺陷修復後 | 追問「原檢查為何沒攔到」；答案是「軸不同」時，缺陷修完仍要處理檢查 |
| 新增檢查以攔某個既有缺陷時 | 驗證新檢查在修復前會失敗——沒有先看它變紅，就不知道它抓不抓得到 |
| 需要指涉「剛剛建立的那個東西」時 | 用建立動作的回傳值，不用「最近修改的」「序號加一」這類臨場推導的識別（來源二） |
| 對某個工具輸出下結論前 | 問「這個管道承載我要的訊號嗎」。輸出缺席只在管道確實承載該訊號時才構成證據 |
| 例外 | 代理指標與性質確實等價的情形（如雜湊比對、二元存在性判定）；此時仍應寫明等價的理由，不預設讀者看得出來 |

## 行為模式分析

綠燈的心理作用是「這件事已經確認過了」，而確認過的事不會被再問一次。檢查器因此不只沒有攔到缺陷——**它主動降低了缺陷被人工發現的機率**，因為它佔據了「這裡已經有人看過」的位置。

這也解釋了為何五個實例都是在做別的事情時撞到的：沒有人是為了驗證那些性質而去看的，是為了別的目的碰巧從另一個軸經過。

最後一個實例（整套測試綠燈 vs 真實環境可用）把這個性質推到極端：一整套測試都是同一個軸上的觀測，數量再多也不會跨出那個軸。
