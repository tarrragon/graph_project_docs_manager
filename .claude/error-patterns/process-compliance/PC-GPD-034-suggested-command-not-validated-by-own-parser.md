# PC-GPD-034: 工具印出的建議指令未經自身參數驗證，照做即被同一工具拒絕

## 基本資訊

| 項目 | 值 |

| 編號 | PC-GPD-034 |
| 類別 | process-compliance |
| 風險等級 | 中 |

## 症狀

CLI 在輸出中印出「下一步可執行的指令」（強制清理、重試、修復建議），使用者或代理人照原文執行，同一個 CLI 回報參數格式錯誤。最小重現：掃描報告對某類對象印出 `<tool> cleanup <target> --force`，其中 `<target>` 填入掃描到的實際識別字串；該子命令的 positional 參數只接受另一種識別格式，回 `INVALID_<X>_FORMAT`。同一工具的另一子命令已有處理該類對象的專用旗標，出錯的子命令沒有對應。

使用者被迫退回底層手動指令，工具的建議路徑成為死路，且該訊息正是在使用者最需要引導時（清理卡住、需要強制）出現。

## 根因

建議訊息與接收它的參數解析各自維護，沒有測試把兩者接起來：

1. 建議訊息是字串模板，變數代入的值來自「掃描／列舉」端，其值域由列舉邏輯決定。
2. 參數解析器的合法值域由驗證邏輯決定，兩個值域無共同定義。
3. 模板撰寫時假設「掃描到的值就是解析器收的值」，新增一類對象（掃描納入、解析器未擴充）後假設即失效。
4. 現有測試分別覆蓋「模板能渲染」與「解析器能解析合法輸入」，沒有「模板渲染的結果餵回解析器」這一條，故雙綠燈下仍然壞。

## 解決方案

- 修建議端或接收端其一，使值域重疊：接收端補對應旗標（參考同工具其他子命令處理同類對象的做法），或建議端依對象類別印出對應的合法指令。
- 不可只改模板文字：模板與解析器仍各自演進，同型缺口會在下次新增對象類別時重現。

## 預防措施

1. **機械驗證（主防線）**：對每個建議指令模板，以掃描實際會產生的值（每個對象類別至少一個代表值）渲染出完整指令，餵回該 CLI 的參數解析函式，斷言不產生格式錯誤。測試輸入必須來自掃描端的真實產出，而非手寫的合法值。
2. 模板與解析器共用同一份識別格式定義（常數或函式），不各自寫一份正規表達式。
3. 新增被掃描／列舉的對象類別時，檢查所有引用該類對象的建議模板，渲染結果能否被解析。
4. 審查含「下一步」「建議指令」「強制執行」類輸出的 CLI 變更時，要求提供一次實際照做的執行結果。

## 通用化檢驗

將工具名、子命令名、識別字格式替換為中性描述後仍成立：工具輸出的建議指令由模板產生，接收端參數解析獨立維護，無測試把兩者接起來，因此建議的可照做性在對象類別擴充時靜默失效。屬跨專案可重現的結構性模式。
