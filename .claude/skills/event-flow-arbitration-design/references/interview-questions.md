# 事件流仲裁設計訪談問題

> 何時讀：執行〈六步流程〉任一步、需要具體問句時。判準本身在事件流負載仲裁方法論，本檔只給問句與「為什麼問」。

## 步驟 1：列通道

| 問題 | 為什麼問 |
|------|---------|
| 系統裡哪些資源「一次只能服務有限請求」，且有「尚未被消費的請求」可言？（連線池、worker pool、單一執行緒的事件迴圈、訊息 partition、畫面提示載體） | 判別對象是否為方法論定義的通道；無佇列的直通型資源（accept backlog 為零）不屬此列，歸入口配額處理 |
| 這個通道的真持有者是誰？多個服務實例各自的連線池，背後是不是同一個資料庫在頂著？ | 分片仲裁的前提是分片對象為真持有者；分片對象非真持有者時，各分片各自不滿而下游已飽和，是自欺 |
| 這個通道目前有沒有仲裁器？如果有，它落在哪一層（通道的持有層，還是某個 domain 內部）？ | 仲裁器落入 domain 內部會產生 N² 協調邊；落在持有層只需 N 條邊 |
| 有沒有互不呼叫的兩個 domain，卻可能同時打這個通道？ | 協調圖與依賴圖正交，只查依賴圖會漏掉這類競爭，且看起來像已確認過 |
| 有沒有請求會在持有這個通道時，又向同一通道要第二份？ | 「持有並等待」計不進佔用量，也是死鎖的經典路徑；答案為是時必須改為一次申請 |

## 步驟 2：標類別與級別

| 問題 | 為什麼問 |
|------|---------|
| 這條事件流的這一次到達，時機是誰決定的？能不能回溯到一個正在等我方回覆的外部發起者？ | 判別等待型／自發型／推送型的第一問；分類對象是「這一次的發生」，不是那段程式碼 |
| 這個事件在到達我方邊界之後，是不是還會轉一手（送達跳、確認收訖後的處理跳）？兩跳的類別一樣嗎？ | 逐跳分類是必要動作——把 webhook 的送達跳歸為推送型會放棄回應碼這個唯一的推回手段 |
| 這個請求被丟棄，後果是不可回復、資訊遺失但可補做、還是重算即得？ | 判別不可棄／須留痕／可棄三級的鍵；鍵是「接收方的丟棄後果」，不是產生方認定的技術嚴重度 |
| 這個請求會不會發出子呼叫？子呼叫的級別有沒有被誤標為比父請求更高？ | 級別傳播只能單調不升；只傳播不降會讓子呼叫以不可棄佔通道，允許升級則任何請求都能自我拔高 |
| 邊界拿不到足夠脈絡標定級別時，退回的靜態預設是什麼？這個「以預設標定」的事件會不會被記錄下來？ | 靜默退回預設會讓「本該不可棄卻被當可棄丟棄」的請求無從追溯 |

## 步驟 3：定佔用量

| 問題 | 為什麼問 |
|------|---------|
| 這個通道能不能讀到佇列深度？讀不到的話，用什麼代理量（事件迴圈 lag、frame 逾時）表示最老未消費請求年齡？ | 卸載判準是佔用量不是到達率；讀不到佇列深度時仍需一個能驅動卸載的輸入 |
| 這個通道上，最貴的請求與最便宜的請求，成本差幾個數量級？ | 成本跨一個數量級以上時，以請求數計的佔用量會讓少數貴請求在指標上隱形，須改分池 |
| 進入卸載狀態與離開卸載狀態，用的是同一個閾值嗎？ | 同一閾值會在臨界點反覆進出（震盪）；離開閾值須低於進入閾值 |
| 暫停這個通道上的工作，是佔用量觸發還是某個不可棄事件觸發？如果是後者，誰負責在恢復點重驗前提？ | 事件觸發的暫停若只看佔用量恢復，會立刻恢復一個前提已失效的工作；判讀前提需要業務知識，須由工作自己驗 |

## 步驟 4：填卸載順序表

| 問題 | 為什麼問 |
|------|---------|
| 三格「不可棄」（自發型／等待型／推送型）各自的處置符合方法論的九格表嗎（等待型不由仲裁器卸載、推送型須落持久佇列）？ | 這三格是與其他六格處置邏輯不同的格，最容易被套用者用「一般 fallback」蓋過 |
| 這個通道上的搶佔，是綁在呼叫路徑上，還是綁在級別上？ | 綁呼叫路徑會讓低級別請求從另一入口進來時繞過搶佔規則，在無人察覺下違反規則 |
| 有序消費的通道（同一 partition 的 FIFO 加 ack）上，是否混流不同級別的事件？ | 有序通道的級別搶佔只在拉取批次內成立，混流須依級別分流至不同通道，這是分池的一種 |
| CPU 通道上，正在跑的工作有沒有提供可中斷點？沒有的話，搶佔的代價是什麼？ | 無中斷點時搶佔退化為終止並重算，重算成本要計入該工作的級別判定 |
| 可棄的推送型緩衝滿時，丟最舊還是丟最新？最新值語意的事件（如心跳）怎麼處理？ | 可棄的定義是「重算即得」，丟最新會留下最無價值的一批；最新值語意事件應先合併再丟棄，保留最新一則並計數 |

## 步驟 5：定 deadline 來源

| 問題 | 為什麼問 |
|------|---------|
| 這條事件流的 deadline 上界，是取自來源自身的有效期，還是另外設了一個常數？ | 另設常數會產生第二個需要與來源同步的數字，兩者必然漂移 |
| 自發型的工作，是狀態驅動（下一輪自動涵蓋本輪範圍）還是窗口驅動（對帳、結算、摘要）？ | 兩者的逾期動作不同：狀態驅動可直接跳過，窗口驅動不留痕就是資料缺口 |
| 錯過的排程，補跑會不會在恢復瞬間堆出一個自製的尖峰？ | 尖峰正好發生在卸載狀態剛離開、最承受不起的時刻 |
| 發起者沒帶 deadline 的請求，邊界指派的預設有沒有標記為「指派」而非「攜帶」？ | 兩者在追溯時意義不同——逾期究竟是發起者的決定還是我方的預設，決定該修哪一邊 |

## 步驟 6：定可觀測事件與最小指標集

| 問題 | 為什麼問 |
|------|---------|
| 每個仲裁決策是否都產生一個可觀測事件，帶滿請求識別、到達類別、級別、通道、決策、佔用量快照、deadline 剩餘七項欄位？ | 被丟棄的請求若沒有這個事件，丟棄與靜默失敗在日誌上同形 |
| 三級留痕粒度（不可棄逐筆、須留痕逐筆但可攢批、可棄只計數加取樣）是否都已定義？ | 全部逐筆留痕會讓留痕本身成為高負載下的新負載 |
| 告警綁的是狀態變遷（進入／離開卸載、卸載計數增量），還是「佔用量高」這種在高負載時恆真的訊號？ | 恆真的訊號輸出恆非空且增量不可見，比沒有偵測更糟——會掩蓋真正的新事件 |
| 這個系統有沒有 structured log 與 request id？沒有的話，本節退化成什麼形態？ | 逐筆留痕以兩者為前提；前提缺席時退化為「計數＋狀態變遷事件」的最小形態，仍須成立 |
