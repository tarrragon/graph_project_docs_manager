# 事件流仲裁設計套用範例

> 何時讀：需要參考已套用過的案例，理解方法論判準如何落地到具體系統時。三個場景取自方法論定稿前的高負載工程視角審查，當時以初稿套用，部分判準當場卡住；卡住處多數已於定稿修入方法論本文，本檔逐項標明現行對應章節。每則範例分三段：**套用結果**（能直接套的部分）、**當時卡住處**（套用時發現初稿沒回答的問題）、**方法論現行對應判準**（定稿後的判準與所在章節）。

## 場景 (a)：HTTP API 共用 DB 連線池，另有 cron 對帳與 webhook 消費

系統的 HTTP API 服務共用一個資料庫連線池；另有排程執行的 cron 對帳任務，與接收外部通知的 webhook 消費者，三者都會向這個池借連線。

### 套用結果

連線池是通道，資料庫是持有層的真持有者，仲裁器掛在「取用連線」這個動作之前。三種到達路徑分屬不同到達類別：HTTP 請求屬等待型（呼叫端在等回應）；cron 對帳屬自發型（開始的決定點在排程本身）；webhook 逐跳分類——送達跳等待型（外部發送方在等 2xx 或非 2xx 的回應）、確認收訖後的處理跳自發型。佔用量以「已借出連線數＋等待者數＋最老等待者年齡」實例化，進入卸載與離開卸載用不同閾值。全表掃描與主鍵查詢的成本差數個數量級，依成本分池後才讓佔用量指標對兩者都有意義。

### 當時卡住處

1. webhook 發送方會在收到非 2xx 時重送；套用初稿時把 webhook 整條歸為推送型，會放棄「回 503 讓對方重試」這個推回手段。
2. cron 對帳屬窗口驅動的工作（本輪要對的帳有固定範圍）；套用初稿的「逾期跳過不補跑」會直接遺漏當日窗口，不是單純的延後。
3. HTTP、cron、webhook 各自是獨立行程、各持一個連線池時，若把每個行程的池各自當通道分片仲裁，會忽略真正的持有者其實是背後同一個資料庫；cron 閒置時它的配額不會流回 HTTP 那一分片。
4. 某個 handler 在同一交易中先借一條連線，交易中途又要借第二條；三參數模型（到達類別、級別、佔用量）把它計為兩個獨立的 in-flight 請求，實際上是「持有並等待」，是連線池死鎖的經典觸發路徑。

### 方法論現行對應判準

1. 〈到達類別〉逐跳分類規則：等待 ack 的 webhook 在送達跳屬等待型（非 2xx 即為推回），確認收訖之後的處理跳屬自發型。
2. 〈Deadline 傳播〉自發型細分：狀態驅動的工作逾期直接跳過，窗口驅動的工作逾期須留痕，留痕由下一次排程消費（窗口併入下一輪）。
3. 〈通道與仲裁器〉分片前提：分片對象須為真持有者；多個連線池背後是同一資料庫時，真持有者是資料庫，仲裁器應落在真持有者處，或明白承認協調配額是刻意新增的單點與其代價。
4. 〈通道與仲裁器〉一次申請原則：同一請求對同一通道的多次佔用必須在首次進入時一次申請完畢，禁止持有並等待。

## 場景 (b)：Flutter 桌面 App，worker isolate 解析大檔、主 isolate 處理操作與提示

worker isolate 負責解析大型檔案，主 isolate 負責處理使用者操作與畫面提示；兩者透過訊息互通。

### 套用結果

三個通道各自一個仲裁器：主 isolate 事件迴圈、worker isolate、畫面提示載體。worker 回傳結果與主 isolate 派工，在接收方依「有沒有人在等回覆」分類——request/reply 形態屬等待型，fire-and-forget 形態屬推送型。解析進度提示屬自發型且可棄（重算即得），使用者觸發的對話框屬等待型且不可棄；兩者的讓步順序依方法論〈讓步與卸載順序〉的三條規則裁決。

### 當時卡住處

1. 主 isolate 的事件迴圈佇列深度不可讀，能觀察到的只有 frame 逾時與迴圈 lag 這類間接訊號，初稿的佔用量定義沒有覆蓋「讀不到佇列」的通道。
2. isolate 內正在跑的計算無法從外部中斷，唯一手段是 kill 該 isolate；kill 等於放棄目前進度、需要重算，初稿沒有把這個代價計入搶佔的判斷。
3. 記憶體本身作為跨 isolate 傳遞的通道時，它的消費形態是 GC 回收，不落在方法論定義的三種消費形態（完成、撤回、逾期）內；且跨 isolate 傳遞時資料會被複製，佔用量在傳遞瞬間翻倍。此項未修入方法論本文，屬已知缺口，需要時另開票承接記憶體通道的實例化條件。

### 方法論現行對應判準

1. 〈競爭與佔用量〉代理量規則：通道不暴露佇列深度時，以最老未消費請求年齡的代理量（事件迴圈 lag、frame 逾時）作輸入，並標明它是佔用量三項組成之一，不是替代物。
2. 〈讓步與卸載順序〉CPU 通道搶佔的實例化條件：搶佔以「工作提供可中斷點」為前提，無中斷點時搶佔退化為終止並重算，重算成本計入該工作的級別判定。
3. 記憶體通道的消費形態與跨 isolate 複製造成的佔用量瞬間翻倍，尚未修入方法論本文——套用本場景時須明確標示此為已知缺口，不可預設方法論已覆蓋。

## 場景 (c)：訊息消費者，付款完成事件與心跳混流

同一個訊息消費者拉取同一個 partition 的事件，其中包含付款完成通知與服務心跳兩種事件。

### 套用結果

拉取式消費在「是否拉取」這個決策點屬自發型（開始的決定點在我方程式碼），拉進來的批次是接收緩衝。付款完成事件依丟棄後果屬不可棄，須落持久佇列；心跳事件屬可棄，且是最新值語意（只關心最新一則）。持久佇列即該通道的 broker，記憶體中的批次即 prefetch 視窗，不可棄事件的 ack 只能在處理完成後發出。

### 當時卡住處

1. 同一 partition 上事件依 FIFO 順序消費並依序 ack，初稿的「高級別可搶佔低級別」規則若直接套用，會誤以為可以讓付款事件插隊到心跳事件之前處理——但這在已拉取的批次之外，搶佔實際上不可能成立，順序早已由 partition 固定。
2. 心跳事件全部丟棄會讓下游的存活偵測誤判服務已離線；初稿的「可棄即可丟」沒有處理「最新值語意」這種特殊的可棄事件。
3. 當 prefetch 視窗被大量不可棄事件填滿、且下游資料庫處理速度跟不上時，消費者唯一能做的動作是停止拉取；初稿沒有把這個狀態明確標記為容量問題，容易被誤判為消費者本身的 bug。

### 方法論現行對應判準

1. 〈讓步與卸載順序〉有序通道的搶佔實例化條件：有序消費的通道上，級別搶佔只在同一次拉取的批次內成立；跨批次的搶佔須改為依級別分流至不同通道（分池的一種）。
2. 〈讓步與卸載順序〉九格表推送型 × 可棄格：緩衝滿時先合併再丟棄，丟最舊；最新值語意的事件保留最新一則並加計數，不整批丟棄。
3. 〈讓步與卸載順序〉九格表推送型 × 不可棄格：不可棄事件不得只存在於記憶體緩衝，必須落持久佇列；仲裁器對它只能延後消費，延後至接收視窗（prefetch 視窗）填滿，即為容量失敗訊號，交由容量維度處理，不屬消費者程式本身的缺陷。

## 延伸裁定

審查過程中另外確認了三則不屬特定場景、但影響套用判斷的裁定：

- **佔用量與延遲型准入控制的相容性**：CoDel、adaptive concurrency limit 這類依到達率調整的演算法，看似與方法論「卸載判準是佔用量、不是到達率」相悖；實際上 CoDel 的 sojourn time 即最老未消費請求年齡，adaptive concurrency limit 的准入決策仍在比較 in-flight 數，兩者的判準變數本就含在佔用量的三項組成內，不衝突。
- **常數時間有界仲裁與分級延遲的相容性**：仲裁器要求每個決策為常數時間、狀態有界（見〈跨執行緒與 isolate〉），與需要分級追蹤延遲的可觀測性需求可同時成立——條件是級別為固定小枚舉、每（類別 × 級別）各自一條 FIFO、deadline 只在出隊時懶檢查（不排序）、延遲統計用固定桶直方圖（不是精算分位數）。
- **高負載除錯的必問兩題**：初稿的最小指標集漏掉兩個問題——「這個通道有沒有在推進」（完成計數，用來區分死鎖／活鎖與單純飽和）與「誰把通道佔滿」（佔用量按到達類別 × 級別分解）。兩者已補入方法論〈可觀測性〉的最小指標集表。
