# 元件語意與版面：切換標籤、可點性、選中態、溢出、版面保障

本 reference 為「審查元件在靜態呈現時的語意標籤、可點性辨識、選中態對比、內容溢出與關鍵回饋文字版面保障」情境。原屬 `interaction-feedback.md`〈按鈕級回饋〉的子節，因補齊範例後超出體量門檻獨立為本檔（同組四檔，逐檔互指）：

| 檔案 | 內容 |
| --- | --- |
| `interaction-feedback.md`（入口） | 核心原則／三層回饋模型／按鈕級回饋（按鈕流程與六種按鈕狀態） |
| `interaction-feedback-waiting-and-notification.md` | 時間門檻與回饋策略／畫面級回饋／Spinner vs Skeleton／結果通知的形式選擇 |
| `interaction-feedback-component-semantics.md`（本檔） | 元件語意與版面檢查 |
| `interaction-feedback-checklist.md` | 反模式速查／檢查清單／參考來源（三份內容檔共用） |

適用：切換元件標籤的現態 / 動作歧義判斷；非互動狀態指示與動作按鈕的形態辨識；選中態底色與文字色的對比設計（含 WCAG AA）；水平清單溢出的捲動 affordance；關鍵回饋文字的版面保障；版面擠壓的診斷分層（換算錯 vs 分配錯）。
不適用：按鈕的時間軸狀態（Default / Hover / Active / Focus / Disabled / Loading，屬按鈕流程範疇，見 `interaction-feedback.md`〈按鈕級回饋〉）；非同步等待期間的指示形式與通知形式選擇（屬 `interaction-feedback-waiting-and-notification.md`）。

> **自包含聲明**：本檔六項判準各自獨立可套用，不需要先讀 `interaction-feedback.md`；判準 1 提及的 Disabled / Loading 狀態語意，其完整定義見該檔〈按鈕級回饋〉六種按鈕狀態表。

---

## 核心原則

**狀態清單之外，標籤、圖示、選中態與版面各自承載語意。** 按鈕的六種時間軸狀態（見 `interaction-feedback.md`〈按鈕級回饋〉）處理的是操作時序，本檔六項判準處理的是同一元件在靜態呈現時容易被誤讀的語意落差。

## 六項判準

1. 切換元件的標籤要能區分「現態」與「動作」— 名詞標籤（「管理模式」）容易被讀成當前狀態指示；消歧做法是狀態顯示與動作按鈕分離（非互動現態文字 +「切換」動作鈕）、改用自帶 on/off 語意的控件（switch / segmented control）、或最低成本把標籤改成動詞句（「切換到 X」— 不動結構、現態仍不可見）。三種做法的選擇順序固定：先看值數，二值狀態（開／關）一律改用 switch 或等義控件（即使切換會連動畫面其他區域增減元素，如「管理模式」開啟後每列多出刪除按鈕，仍先判二值再套用）；三值以上且切換會連動畫面其他區域增減元素時，拆成狀態顯示＋動作鈕；三值以上但沒有連動增減元素、或前兩者暫時受版面限制無法採用時，才用動詞句做最低成本過渡，且動詞句不解決現態不可見的問題，屬權宜而非首選。不幫助消歧的圖示是雜訊、移除。
2. 非互動的狀態指示不與動作按鈕同形混排 — 同列有按鈕時使用者預設整列可點，點到指示的「沒反應」被讀成壞掉；描邊 vs 實心不是可靠的互動性訊號，指示用明顯非按鈕形態（文字 chip、圓點）或移出動作列，同一圖形全畫面只承載一個語意。
3. 選中態是（底色, 文字色）的成對設計 — 單獨覆寫選中底色會脫離主題的成對機制、元件庫不會為自訂底色反推文字色，淺底疊淺字就是「選中後看不到字」；對比方向成對反轉（底淺配深字），逐狀態驗 WCAG AA（一般字級 4.5:1、大字 3:1）。
4. 水平清單溢出要有捲動 affordance（邊緣漸層、下一項半顆露出、箭頭、捲軸指示）— 截斷的預設讀法是「壞了 / 被旁邊的元件遮住」、不是「可以捲」；選項少時優先消除溢出（wrap / 選單），截斷邊緣避免緊貼固定按鈕（視覺歸因會錯）。
5. 關鍵回饋文字要有版面保障 — flex 寬度競爭會把「已選擇: 3/45」壓成「...」（state 正確、使用者零資訊）；ellipsis 對短關鍵資訊是錯誤的降級策略，改縮格式或最小寬度，回饋鏈要驗到像素層、並在窄幕驗收。
6. 版面擠壓先分「換算錯 vs 分配錯」再動手 — 等比縮放（換算類）sizing 套件不驗證空間分配：換算工具工作在常數層（設計稿座標 → 裝置座標、發生在 layout 之前）、空間分配發生在 layout 協商層（有限寬度分給動態內容：計數、i18n 字串、使用者資料），兩層獨立、比例正確不等於空間夠用（隱含假設「實際內容 = 設計稿內容」被動態內容打破）。換算錯查套件用法；分配錯補三層（設計層空間競爭規格：誰讓步怎麼降級；實作層把 flex 組合當顯式優先權決策；驗證層窄幕驗收 / layout test）。設計層的空間競爭規格本 skill 不另立格式與欄位 — 一律路由至 `component-contract-design` skill 的〈空間不足策略〉欄，本 skill 只負責標出「這裡需要一份空間競爭規格」，內容與填寫規則交由該欄位的定義處理，避免兩份 skill 各自定義同一件事。其他響應式方案（constraint-based layout、breakpoint）保證層各異；引入「解決某維度」的套件時，記錄它不保證的層、缺口層掛對應驗證。

### 三段鏈式範例：第 1 項——三值以上且無連動增減元素的邊界情境

情境：一個排序方式切換元件有三個值，切換只改變版面外觀、不增減任何元素，判斷該套用哪種消歧做法。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個排序方式切換元件，有三種值（依時間、依名稱、依大小），切換時畫面
版面外觀會改變（欄位寬度與對齊方式不同），但列表項目本身的數量與內容不會增減
```

【產出】

```
形態：決策表
判斷依據                                     | 結果
值數                                         | 三值以上（依時間／依名稱／依大小）
切換是否連動增減畫面上的元素數量             | 否（只改變版面外觀，如欄位寬度與對齊，
                                                不增加或移除任何元素）
依優先序（先看值數，三值以上依是否連動增減元素分流）判定 | 不屬於「拆狀態顯示＋動作鈕」
                                                （該做法針對連動增減元素的情境）
結論                                         | 三值以上但無連動增減元素，優先評估是否有
                                                自帶語意的控件（如 segmented control 呈現
                                                三個選項本身即為現態），僅在無合適控件時
                                                才退回動詞句過渡
```

【驗證】

```
檢驗問句
Q 三值以上但沒有連動增減元素的情境，是否直接套用「拆狀態顯示＋動作鈕」？
  預期：否——該做法設計目的是處理「切換會連動增減元素」的情境；本情境只改變版面
  外觀，不增減元素，應先考慮 segmented control 等自帶現態語意的控件

Q 若元件目前找不到合適的自帶語意控件、暫時只能用動詞句過渡，是否代表現態不可見
  的問題已解決？
  預期：否——動詞句「不解決現態不可見的問題，屬權宜而非首選」，選用動詞句過渡時
  仍須記錄為技術債，待有合適控件時替換
```

### 三段鏈式範例：第 2 項——非互動指示與按鈕形態的判斷

情境：一個狀態指示與一個真實按鈕同列，判斷該狀態指示目前的視覺樣式是否會被誤認為可點。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個清單項目同一列同時有一個「已同步」狀態指示與一個「刪除」按鈕；
狀態指示目前的視覺樣式是無邊框文字包在一個有圓角的淺色底色區塊裡（chip 樣式）
```

【產出】

```
形態：決策表
判斷依據                                     | 結果
狀態指示目前的視覺形態                       | 無邊框文字包在圓角淺色底色區塊（文字 chip）
是否屬於條文列舉的明顯非按鈕形態之一         | 是（條文明列「文字 chip、圓點」為明顯非
（文字 chip、圓點）                            按鈕形態，本情境即為典型文字 chip）
結論                                         | 合格，不需改為其他形態；「無邊框」不是判斷
                                                依據——描邊 vs 實心不是可靠的互動性訊號，
                                                判準是形態類別（文字 chip／圓點 vs 按鈕），
                                                不是外觀圓角與否
```

【驗證】

```
檢驗問句
Q 「無邊框文字包在圓角淺色底色區塊」是否等同於條文所稱的「文字 chip」？
  預期：是——條文明列「文字 chip」為明顯非按鈕形態之一，本情境的視覺樣式即為
  典型文字 chip，不需要另外改成純文字或加圖示才算合格

Q 同列已有真實按鈕，是否代表所有圓角色塊都會被誤認為可點、因此都不合格？
  預期：否——條文排除的是「同形混排」且描邊/實心等外觀差異不足以區分的情況；
  文字 chip 與圓點是條文明列的合格形態，與同列有無按鈕無關
```

### 三段鏈式範例：第 5 項——窄幕下關鍵回饋文字的處理順序

情境：一個計數文字在窄螢幕下與旁邊的操作按鈕共用同一列空間，判斷該不該被壓成省略號。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個顯示「已選擇: 3/45」的計數文字，元件所在容器在窄螢幕下寬度不足，
與旁邊的操作按鈕共用同一列空間
```

【產出】

```
形態：決策表
判斷依據                               | 結果
「已選擇: 3/45」是否為關鍵回饋文字      | 是（讓使用者知道目前選取進度，缺這則資訊
                                          使用者無法判斷操作是否符合預期）
空間不足時是否應該讓此文字被壓成省略號 | 否（省略號會讓使用者拿到零資訊）
應該怎麼處理                           | 優先縮短格式（如「3/45」不含「已選擇: 」前綴）；
                                          仍不足則設定最小寬度，改由旁邊的操作按鈕
                                          讓步（縮小或換行）
```

【驗證】

```
檢驗問句
Q 窄幕下空間不足時，是否應該讓「已選擇: 3/45」被壓縮成「...」？
  預期：否——關鍵回饋文字要有版面保障，ellipsis 對短關鍵資訊是錯誤的降級策略

Q 「縮格式」與「設最小寬度改由旁邊元件讓步」兩個做法的優先順序為何？
  預期：先嘗試縮格式（去掉非必要前綴），仍不足才設最小寬度並要求旁邊元件讓步——
  縮格式的代價較低（不影響其他元件版面），應優先嘗試
```
