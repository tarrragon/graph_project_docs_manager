## 核心原則

**狀態清單之外，標籤、圖示、選中態與版面各自承載語意。** 按鈕的六種時間軸狀態（見 `interaction-feedback.md`〈按鈕級回饋〉）處理的是操作時序，本檔八項判準處理的是同一元件在靜態呈現時容易被誤讀的語意落差。

## 八項判準

1. 切換元件的標籤要能區分「現態」與「動作」— 名詞標籤（「管理模式」）容易被讀成當前狀態指示；消歧做法是狀態顯示與動作按鈕分離（非互動現態文字 +「切換」動作鈕）、改用自帶 on/off 語意的控件（switch / segmented control）、或最低成本把標籤改成動詞句（「切換到 X」— 不動結構、現態仍不可見）。三種做法的選擇順序固定：先看值數，二值狀態（開／關）一律改用 switch 或等義控件（即使切換會連動畫面其他區域增減元素，如「管理模式」開啟後每列多出刪除按鈕，仍先判二值再套用）；三值以上且切換會連動畫面其他區域增減元素時，拆成狀態顯示＋動作鈕；三值以上但沒有連動增減元素時，先看全部選項能否在一列內完整並排顯示而不截斷：能 → 改用 segmented control（選中的分段即為現態）；不能，或前述做法暫時受版面限制無法採用時，才用動詞句做最低成本過渡，且動詞句不解決現態不可見的問題，屬權宜而非首選。不幫助消歧的圖示是雜訊、移除。
2. 非互動的狀態指示不與可點元素同形混排（子項見 2.1～2.10）

### 2.1 前提

- (1) 本項的「指示」指畫面上不可點的狀態指示，也就是按下去沒有任何反應的元素。
- (2) 指示符合下列任一形態即合格，(a)(b) 各自獨立判定、可同時成立：
  - (a) 明顯非可點元素形態，依 2.2～2.7 判定；
  - (b) 移出動作列，依 2.8 判定。
- (3) (a) 的判定與指示是否和可點元素排在同一列無關：同列的指示只要屬 (a) 即合格；指示屬 (b) 也不影響 (a) 是否成立，(a) 仍依 2.2～2.7 判定。
- (4) 畫面上沒有可點元素時，本項不適用。「不適用」只用於整項。2.3 每一軸的結果只有「不同」與「相同」兩種。

### 2.2 比較對象

- (1) 可點元素指同一畫面上所有按下去會有反應的元素，含按鈕、可點 chip、文字連結，非窮舉。比較範圍是整個畫面，不限指示所在的列；此全畫面比較範圍只屬於 (a)，(b) 的比較範圍見 2.8(1)。
- (2) 執行順序：① 先列出畫面上所有可點元素；② 對每一個可點元素填 2.3 的兩軸；③ 只要有一個可點元素兩軸皆「相同」，即判指示不屬 (a)，此時才可停止；否則須填完全部可點元素，且逐一皆至少一軸「不同」才屬 (a)。
- (3) 只要對某一個可點元素兩軸都「相同」，指示就不屬 (a)（即 (2)③ 的停止條件）。

### 2.3 兩軸

- (1) 構成要素軸。構成要素有兩項：文字或圖示（文字與圖示算同一項；純幾何形狀不算圖示，界線見 (3)）、區塊（底色或外框圍住文字或圖示的範圍）。有區塊必定有文字或圖示，所以一方不會同時缺少又多出。判定方式：先分別列出雙方（指示、對方）具備的項目再比對，再依下表判定：

  | 比對結果 | 判定 |
  | --- | --- |
  | 指示缺少對方具備的一項 | 不同 |
  | 指示多出對方沒有的一項 | 依 2.4 |
  | 兩者具備的項目相同 | 相同 |
- (2) 區塊高度軸。指示與對方都有區塊時才比較，達到 2.6 的門檻記為不同；以下情況記為相同：任一方沒有區塊（不比較）、專案沒有尺寸 token（不成立）、未達 2.6 的門檻。這裡的「相同」表示此軸不提供差異，判定只剩構成要素軸。
- (3) 圖示與純幾何形狀的界線：純幾何形狀只有以下幾類：點、直線或直條、圓環、內部不含文字或圖示的純色圓形或方形。其他圖形一律算圖示，含勾號、箭頭、三角形。

### 2.4 多出規則

- (1) 指示多出對方沒有的一項時，須同時滿足以下兩點，這一項才算不同；不滿足時，構成要素軸記為相同：畫面上另有一個可點元素具備該項；指示與那個可點元素至少在一軸上不同。
- (2) (1) 的第二點依 2.3 判定，可以是任一軸。2.2(2) 本來就要求指示與每一個可點元素比較，讀者須把那一次比較的結果取回這裡用——那次比較兩軸皆為「相同」時，第二點即不成立，不是系統自動處理，須讀者自行取回核對。

### 2.5 徽章

附在可點元素熱區內、按下去觸發該可點元素本身的徽章，不是本項的指示，不做比較。

### 2.6 門檻與量測

- (1) 區塊高度軸記為不同的門檻：在專案尺寸 token 階梯上，指示的區塊高度比對方至少低一階。
- (2) 專案沒有尺寸 token 時，區塊高度軸不成立，記為相同，只看構成要素軸。
- (3) 比較須在專案支援的所有字級、斷點、密度下都達到門檻；任一條件下未達門檻，此軸記為相同。
- (4) 指示或可點元素的高度不在專案尺寸 token 階梯上時，視同專案沒有尺寸 token，此軸不成立，記為相同。

### 2.7 不可靠訊號

描邊或實心、圓角或直角、底色深淺，都不是可靠的可點性訊號，不作為比較依據。比較依據只有構成要素與區塊高度兩軸。

### 2.8 (b) 移出動作列

- (1) 動作列指排有可點元素的列。移出動作列，指指示所在的列上沒有任何可點元素。
- (2) (b) 只看指示所在的列，不與畫面其他位置的可點元素比較。

### 2.9 例示

同一種指示形態，換了畫面上的可點元素，結果可能相反。以下例示須連同比較對象一起讀，不可單獨當成合格形態：

- (1) 不加底色與外框的純文字：畫面上的可點元素全都帶區塊時，指示對每一個可點元素都缺少區塊，屬 (a)。畫面上只要有一個不帶區塊的可點元素，指示對它構成要素相同，區塊高度軸不比較、記為相同，不屬 (a)。
- (2) 圓點：畫面上有一排可點的純色圓形色票（例如顏色選擇器）時，圓點與色票都沒有文字、圖示與區塊，構成要素相同；區塊高度軸不比較、記為相同，不屬 (a)。

### 2.10 理由

本條只適用於 (a)(b) 都沒有達成的指示：同列有可點元素時，使用者預設整列可點，按到指示時「沒反應」會被讀成壞掉。

3. 選中態是（底色, 文字色）的成對設計 — 單獨覆寫選中底色會脫離主題的成對機制、元件庫不會為自訂底色反推文字色，淺底疊淺字就是「選中後看不到字」；對比方向成對反轉（底淺配深字），逐狀態驗 WCAG AA（一般字級 4.5:1、大字 3:1）。
4. 水平清單溢出要有捲動 affordance（邊緣漸層、下一項半顆露出、箭頭、捲軸指示）— 截斷的預設讀法是「壞了 / 被旁邊的元件遮住」、不是「可以捲」；選項少時優先消除溢出（wrap / 選單），截斷邊緣避免緊貼固定按鈕（視覺歸因會錯）。
5. 關鍵回饋文字要有版面保障 — flex 寬度競爭會把「已選擇: 3/45」壓成「...」（state 正確、使用者零資訊）；ellipsis 對短關鍵資訊是錯誤的降級策略，改縮格式或最小寬度。兩者順序固定：先縮短格式（去除不影響理解的前綴或單位），仍不足才設定最小寬度並由鄰近元件讓步；讓步規則（誰讓步、怎麼降級）路由至 `component-contract-design` skill 的〈空間不足策略〉欄，本項只決定先後。回饋鏈要驗到像素層、並在窄幕驗收。
6. 版面擠壓先分「換算錯 vs 分配錯」再動手 — 等比縮放（換算類）sizing 套件不驗證空間分配：換算工具工作在常數層（設計稿座標 → 裝置座標、發生在 layout 之前）、空間分配發生在 layout 協商層（有限寬度分給動態內容：計數、i18n 字串、使用者資料），兩層獨立、比例正確不等於空間夠用（隱含假設「實際內容 = 設計稿內容」被動態內容打破）。換算錯查套件用法；分配錯補三層（設計層空間競爭規格：誰讓步怎麼降級；實作層把 flex 組合當顯式優先權決策；驗證層窄幕驗收 / layout test）。設計層的空間競爭規格本 skill 不另立格式與欄位 — 一律路由至 `component-contract-design` skill 的〈空間不足策略〉欄，本 skill 只負責標出「這裡需要一份空間競爭規格」，內容與填寫規則交由該欄位的定義處理，避免兩份 skill 各自定義同一件事。其他響應式方案（constraint-based layout、breakpoint）保證層各異；引入「解決某維度」的套件時，記錄它不保證的層、缺口層掛對應驗證。
7. 同一圖形只承載一個語意（子項見 7.1～7.4）

### 7.1 前提

- (1) 本項的「圖形」範圍同 2.3(3) 所指的圖示與純幾何形狀（2.3(3)：「其他圖形一律算圖示」）：涵蓋 2.3(3) 的兩類——圖示與純幾何形狀，二者皆在本項射程內。
- (2) 本項不受 2.1(4) 限制：畫面上沒有可點元素時，本項仍適用。

### 7.2 判定

- (1) 同一圖形在全畫面只承載一個語意。
- (2) 比較對象是畫面上所有圖形，不限指示與可點元素之間；兩個可點元素用同一圖形表達不同語意，也違反 (1)。
- (3) 「語意」指圖形代表的事物或動作，不含可點與否：同一圖形只差可點與否、代表的事物相同時，不違反 (1)。描邊與實心變體算同一圖形。
- (4) 本項與第 2 項各自判定，第 2 項的結論不改變本項的結論。

### 7.3 處置

違反 (1) 時，處置是更換其中一方的圖形；不是改指示形態或移出動作列（那是第 2 項的處置）。

### 7.4 例示

- (1) 違反：畫面上兩顆可點按鈕都使用旗子圖示，一顆用於切換語言至英文版、另一顆用於檢舉此則留言；兩者代表的語意不同（語言選擇 vs 檢舉），違反 (1)，此結果與畫面上有沒有指示無關。
- (2) 不違反：畫面上兩顆可點按鈕都使用分享圖示，一顆用於分享文章、另一顆用於分享相簿；兩者代表的動作相同（分享），只是操作對象不同，依 7.2(3) 語意相同，不違反 (1)。

8. 顏色不作為唯一區分依據（子項見 8.1～8.5）

### 8.1 前提

- (1) 本項的「區分」指使用者要分辨兩個以上不同語意時所依據的視覺差異。「語意」指該元素代表的事物、狀態或類別。
- (2) 畫面上不存在兩個以上靠視覺差異分辨的語意時，本項不適用。「不適用」只用於整項。
- (3) 本項不限載體：圖示、純幾何形狀、文字顏色、底色、邊框色、線條顏色皆在射程內。

### 8.2 判定

- (1) 兩個以上語意之間，使用者可依據的視覺差異只有顏色時，違反本項。
- (2) 「只有顏色」依序判兩點，兩點都成立才算：把畫面轉為灰階後，這些語意的呈現無法區分；且各自旁邊沒有文字標明它代表什麼。**第一點不成立即結束判定，判不違反，不進第二點。**無法實際轉灰階時，改問「把這些元素的顏色全換成同一個顏色後，還分得出哪個是哪個嗎」。
- (3) 灰階後仍可區分者不違反 (1)。可區分的差異有：形狀、大小、位置、圖示、存在與否、填滿與否、線條樣式、文字內容。
- (4) 各自旁邊有文字標明語意者不違反 (1)，即使灰階後不可區分。該文字須與所標語意同時可見；須先觸發才出現者（tooltip、長按提示、說明彈窗）不算。
- (5) 顏色搭配其他差異時不違反 (1)：顏色可以承載語意，本項要求的是它不獨自承載。

### 8.3 射程與交界

- (1) 比較對象是畫面上承載語意的所有元素，不限元件邊界。同一個元件的兩個實例分別用兩種顏色代表兩個語意，也在射程內。
- (2) 本項與第 7 項各自判定。第 7 項治同一圖形承載兩個語意，本項治兩個語意只靠顏色區分；同一組元素兩項都命中時記一項缺口，以本項為準——本項的處置涵蓋第 7 項的處置（換形狀是 8.2(3) 的一種），反之不成立。
- (3) 底色與文字色的成對設計與 WCAG AA 比值屬第 3 項，不在本項。第 3 項問顏色看不看得見，本項問顏色以外還有沒有訊號，兩項對同一組顏色可以一過一不過。
- (4) 可點性的判定屬第 2 項。2.7 已規定底色深淺不作為可點性的比較依據，本項不改變該條。

### 8.4 處置

違反 8.2(1) 時，為每個語意補一項 8.2(3) 所列的差異，或補一則符合 8.2(4) 的文字。**改變顏色本身不構成處置**——換成對比更強的色相、拉開明度差、改用色盲友善色票，都仍是「只有顏色」。

### 8.5 例示

- (1) 表單畫面：必填欄位的標籤以橘色顯示、選填欄位的標籤以一般文字色顯示，兩者旁邊都沒有星號或「必填」字樣。違反 8.2(1)：灰階後兩種標籤只剩明度差而無法區分，且旁邊沒有文字標明（8.2(2) 兩點皆成立）。處置是為必填欄位補星號或「必填」字樣。
- (2) 同一份表單改為必填欄位標籤後加一個橘色星號、選填欄位無星號。不違反：使用者區分兩類欄位所依據的差異是星號的存在與否，屬 8.2(3) 的「存在與否」，灰階後仍可區分。**星號本身是橘色不構成違反**——8.2(1) 問的是使用者可依據的差異是不是只有顏色，此處的差異不是顏色。

### 三段鏈式範例：第 1 項——三值以上且無連動增減元素的邊界情境

情境：一個排序方式切換元件有三個值，切換只改變版面外觀、不增減任何元素，判斷該套用哪種消歧做法。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個排序方式切換元件，有三種值（依時間、依名稱、依大小），切換時畫面
版面外觀會改變（欄位寬度與對齊方式不同），但列表項目本身的數量與內容不會增減
```

【產出】

```
形態：決策表
判斷依據                                     | 結果
值數                                         | 三值以上（依時間／依名稱／依大小）
切換是否連動增減畫面上的元素數量             | 否（只改變版面外觀，如欄位寬度與對齊，
                                                不增加或移除任何元素）
依優先序（先看值數，三值以上依是否連動增減元素分流）判定 | 不屬於「拆狀態顯示＋動作鈕」
                                                （該做法針對連動增減元素的情境）
三個選項標籤是否能在一列內完整並排顯示而不截斷 | 是（「依時間」「依名稱」「依大小」三個標籤
                                                皆短，可完整並排）
結論                                         | 三值以上但無連動增減元素，且選項能在一列內
                                                完整並排不截斷，改用 segmented control（選中
                                                的分段即為現態）；若選項無法完整並排或暫時
                                                受版面限制無法採用，才退回動詞句過渡
```

【驗證】

```
檢驗問句
Q 三值以上但沒有連動增減元素的情境，是否直接套用「拆狀態顯示＋動作鈕」？
  預期：否——該做法設計目的是處理「切換會連動增減元素」的情境；本情境只改變版面
  外觀，不增減元素，應先看選項能否在一列內完整並排顯示而不截斷，能則用 segmented control

Q 若元件目前找不到合適的自帶語意控件、暫時只能用動詞句過渡，是否代表現態不可見

  預期：否——動詞句「不解決現態不可見的問題，屬權宜而非首選」，選用動詞句過渡時

```

### 三段鏈式範例：第 2 項——非互動指示與可點元素形態的判斷

情境：一個狀態指示與一個可點元素同列，判斷該狀態指示目前的視覺樣式是否會被誤認為可點。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個清單項目同一列同時有一個「已同步」狀態指示與一個「刪除」按鈕；
「刪除」按鈕為填色圓角矩形（有文字＋底色區塊），高度 40；狀態指示目前的視覺
樣式是無邊框文字包在一個有圓角的淺色底色區塊裡（有文字＋底色區塊），高度 28，
比「刪除」按鈕低一個專案尺寸 token 階
```

【產出】

```
形態：決策表
判斷依據                                     | 結果
畫面上的可點元素                             | 「刪除」按鈕（填色圓角矩形，有文字＋
                                                底色區塊，高度 40）
狀態指示的構成要素                           | 文字＋底色區塊
與「刪除」按鈕比較構成要素軸（2.3(1)）        | 相同（兩者皆有文字與區塊，指示未缺少
                                                也未多出任何一項）
與「刪除」按鈕比較區塊高度軸（2.3(2)、2.6(1)）| 不同（指示 28 低於按鈕 40，達專案尺寸
                                                token 階梯的至少一階）
逐一比較結果（2.2(2)）                        | 對唯一的可點元素「刪除」按鈕已在區塊
                                                高度軸不同，滿足「對每一個可點元素
                                                都至少一軸不同」

                                                改為其他形態；「無邊框」與圓角深淺

                                                構成要素與區塊高度（2.3）
```

【驗證】

```
檢驗問句
Q 「無邊框文字包在圓角淺色底色區塊」是否因為外觀像 chip 而自動合格？
  預期：否——條文不再以外觀類名作為判斷依據，需逐一與畫面上的可點元素比較
  構成要素與區塊高度兩軸（2.3）；本情境合格的依據是指示的區塊高度低於
  「刪除」按鈕，達尺寸 token 階梯的至少一階（2.6(1)）

Q 若把狀態指示的高度改成與「刪除」按鈕相同（40），是否仍合格？
  預期：否——構成要素軸相同（皆為文字＋區塊，2.3(1)），區塊高度軸也相同
  （未低於按鈕，2.3(2)），兩軸皆同即不屬 (a)（2.2(3)），須移出動作列（2.8）
  或改為其他形態；同色同高只差圓角或描邊不足以構成合格（2.7）
```

### 三段鏈式範例：第 5 項——窄幕下關鍵回饋文字的處理順序

情境：一個計數文字在窄螢幕下與旁邊的操作按鈕共用同一列空間，判斷該不該被壓成省略號。驗證段的判定屬「設計產出物」。

【輸入】

```
SPEC 片段：一個顯示「已選擇: 3/45」的計數文字，元件所在容器在窄螢幕下寬度不足，
與旁邊的操作按鈕共用同一列空間
```

【產出】

```
形態：決策表
判斷依據                               | 結果
「已選擇: 3/45」是否為關鍵回饋文字      | 是（讓使用者知道目前選取進度，缺這則資訊
                                          使用者無法判斷操作是否符合預期）
空間不足時是否應該讓此文字被壓成省略號 | 否（省略號會讓使用者拿到零資訊）
應該怎麼處理                           | 優先縮短格式（如「3/45」不含「已選擇: 」前綴）；
                                          仍不足則設定最小寬度，改由旁邊的操作按鈕
                                          讓步（縮小或換行）
```

【驗證】

```
檢驗問句
Q 窄幕下空間不足時，是否應該讓「已選擇: 3/45」被壓縮成「...」？
  預期：否——關鍵回饋文字要有版面保障，ellipsis 對短關鍵資訊是錯誤的降級策略

Q 「縮格式」與「設最小寬度改由旁邊元件讓步」兩個做法的優先順序為何？
  預期：先嘗試縮格式（去掉非必要前綴），仍不足才設最小寬度並要求旁邊元件讓步——
  縮格式的代價較低（不影響其他元件版面），應優先嘗試
```
