## 問作用不問存在：查重粒度不足導致的兩次反向錯誤

【輸入】

```
盤點某維度時，讀者看到一份文件的章節標題涵蓋該維度的關鍵詞（如「UI」），或看到一個檔名看起來像承接該產物（如某設定檔檔名對應「seed 資料」）。讀者尚未逐字搜尋文件內文。
```

【產出】

```
形態：決策表
  判斷方式             | 過程與結果
  甲：讀標題／檔名下結論 | 「UI 的 token 與元件庫沒有承接者」（未搜尋內文）；「seed 由某設定檔承接」（未搜尋內文）
  乙：逐字搜尋原文確認作用 | 對候選權威文件執行關鍵詞搜尋，確認是否真的涵蓋該產物

實測結果：甲的兩次判斷皆與實測相反——第一次「UI 的 token 與元件庫沒有承接者」，實測既有文件對「i18n」「UX 審查」兩詞皆 0 命中（四塊只涵蓋兩塊，另兩塊確實有承接卻被判無）；第二次「seed 由某設定檔承接」，實測該檔對「seed」一詞 0 命中（無承接卻被判有）。
```

【驗證】檢驗問句

```
Q 只讀章節標題或檔名，能否判斷一份文件對本維度「有沒有作用」？
  預期：否——依據句「本 skill 的每一條判準都問『它對本專案有沒有作用』，不問『它存不存在』」（〈判準的通用形式：問作用，不問存在〉），標題與檔名只證明文件存在，不證明內容真的涵蓋該產物。

Q 「錯誤的缺口宣告」（判有為無）與「錯誤的承接宣告」（判無為有）哪一種更難被後續發現？
  預期：錯誤的承接宣告——盤點表看起來已結案，不會被要求重新建置而暴露；缺口宣告至少會被要求重新盤點。
```

## 萃取揭露規格漂移

【輸入】

```
規格散文記載「圓角 10/12、字級 12–22」；量測設計畫布得到的實際值為圓角 5/7/8、字級 10–19。兩邊數值不同，且沒有任何機制會發現兩者已經漂移。
```

【產出】

```
形態：決策表
  候選處置           | 內容                                             | 結論
  甲：以規格散文為準 | 保留規格記載的 10/12、12–22，畫布數值視為誤差    | 不合格，見驗證段
  乙：以畫布實測值建 token | 建立圓角 token（5/7/8）與字級 token（10–19 區間離散化），規格改為指向 token 不再複述數值 | 合格
```

【驗證】檢驗問句

```
Q 規格散文的手寫數值與畫布實測值不一致時，哪一方為準？
  預期：畫布實測值——依據句「萃取自程式碼的值每一步可 grep 驗證」（`handoff-mode.md`〈為什麼這個順序比直接補文件更可靠〉：憑印象寫的文件會與現況漂移且無機制發現，此原則同樣適用於規格散文與設計來源之間的漂移）。

Q 規格改寫後是否還應複述具體數值？
  預期：否——複述數值會讓規格與 token 表各寫各的，重新製造同一種漂移。
```

## 萃取不等於照抄

【輸入】

```
量測同一份設計畫布，間距實測出七種值：4、6、9、13、15、20、23（彼此相近、看不出明確尺度規則）。這份畫布尚無任何程式碼綁定這些值。
```

【產出】

```
形態：決策表
  候選處置       | 內容                                                                          | 結論
  甲：逐值命名   | 七個值各自建一個具名 token                                                   | 不合格，見驗證段
  乙：歸納為離散具名階 | 判斷七個值屬同一組尺度的雜訊，歸納為 3–4 個離散階（如 small／medium／large／xlarge）並記錄映射（例：4、6 對映 small；9、13 對映 medium；15 對映 large；20、23 對映 xlarge） | 合格
```

【驗證】檢驗問句

```
Q 本例是否適用「萃取當下即歸納為離散階」？
  預期：是——依據句「來源若是設計畫布而非既有實作（尚無程式碼綁定這些值），沒有需要保持中立的行為，萃取當下即歸納為離散具名階」（`handoff-mode.md`〈命名與收斂分兩步〉）。

Q 若這七個值已被既有程式碼引用（不是畫布），處置是否相同？
  預期：否——改採命名與收斂分兩步：第 2 步逐值命名、值不變，把疑為雜訊的值與候選映射記入決策文件，收斂另開一張票、與命名同批建立，見 `handoff-mode.md`〈命名與收斂分兩步〉。
```

## 權威形態不符時的正確取用

【輸入】

```
一個單機資料收集工具（無伺服器、無多租戶）的資料庫維度，權威來源是以 SaaS 為預設形態的技術選型訪談框架。該 repo 逐字搜尋「租戶」相關字樣為 0 命中。現況的建表邏輯採「若不存在則建立」寫法，沒有任何 schema 版本標記。
```

【產出】

```
形態：決策表
  候選判定             | 內容                                                                   | 結論
  甲：權威整條不適用   | 找不到多租戶的對應現況，判定整個資料庫維度形態不符、直接跳過            | 不合格，見驗證段
  乙：改寫產物         | migration 版本化紀律段落適用（本專案仍需要 schema 版本管理），多租戶隔離段落不適用；產物填「改寫產物：migration baseline，不含租戶隔離」 | 合格，對得上真缺口：現況無 schema 版本標記
```

【驗證】檢驗問句

```
Q 「多租戶隔離不適用」是否等於「整個資料庫維度都不適用」？
  預期：否——依據句「只取權威中與形態無關的部分，記錄不適用的範圍」（〈權威缺席時〉「權威存在但形態不符」），須逐段判斷而非整條放棄。

Q 產物欄「改寫產物」是否對應到現況的真實缺口？
  預期：是——現況「若不存在則建立」的建表方式沒有 schema 版本標記，對應 migration baseline 這個缺口。
```

## 產物有而判準無

【輸入】

```
一個服務端專案已有完整的資料填充腳本與對應的工廠函式，並有整合測試覆蓋這些填充邏輯。資料庫維度盤點問「seed 判準是否已被框架承接」。
```

【產出】

```
形態：決策表
  層級   | 候選判定                                                                        | 結論
  產物層 | 已存在於資料填充模組（含測試覆蓋）                                              | 合格——盤點的是本專案有沒有這個產物，答案是有
  判準層 | 甲：無判準即代表產物不合格，標「待定：缺口」／乙：無判準只影響判準層，產物層仍照實填「已存在」，判準層另標「無判準」並建框架缺口票 | 採乙，見驗證段
```

【驗證】檢驗問句

```
Q 判準層缺口是否會推翻產物層「已存在」的判定？
  預期：否——依據句「兩者獨立，『產物有、判準無』是常見狀態」（〈權威缺席時〉「框架內確實無承接者」）。

Q 若把判準缺口與產物層合併填「待定：缺口」，會有什麼問題？
  預期：對一個已完成的東西標成未結案，讀者可能誤以為這個維度還沒人做而重複建置。
```

## UI 維度適用條件不限時的處置

【輸入】

```
一個純 CLI 工具，只在終端輸出文字報表，沒有圖形介面、沒有網頁前端。盤點 UI 維度時問「這個維度是否成立」。
```

【產出】

```
形態：決策表
  候選判定 | 內容                                                                                     | 結論
  甲：無   | UI 維度不適用，填「無」，理由是沒有圖形介面框架可用                                     | 不合格，見驗證段
  乙：改寫產物 | 依〈維度與產物〉表 UI 列「適用條件：不限」，維度仍成立；答〈改寫產物是主路徑〉推導問句「這個維度要防的失效在本專案長成什麼樣子」——UI 防的是「同一概念長出多種樣子」，在純文字輸出上長成「欄位順序與色碼語意不一致」；產物填「改寫產物：輸出格式契約」 | 合格
```

【驗證】檢驗問句

```
Q 「甲：無」是否合格？
  預期：否——依據句「適用條件：不限（權威非 SaaS 特定）」（〈維度與產物〉表 UI 列），UI 維度對任何專案形態皆成立，不因無圖形介面框架就判「無」；「無」只用於「該維度判定後不產出」，本例維度仍成立。

Q 「乙：改寫產物」的產出是否有依據句？
  預期：有——推導問句「這個維度要防的失效，在本專案會長成什麼樣子」見 `dimension-product-notes.md`〈改寫產物是主路徑〉；「UI 防的是同一概念長出多種樣子」一句的權威原句與出處見該檔〈各維度要防的失效（權威出處）〉表「UI」列。
```

## 產物欄「無」與「待定」的拆兩問判斷

【輸入】

```
一個純函式庫專案（無執行進入點、不提供伺服器模式、僅供其他專案 import），盤點 DevOps 維度（CI gate 構成與部署還原）。
```

【產出】

```
形態：決策表
  步驟                      | 結果
  1 答推導問句「這個維度要防的失效，在本專案會長成什麼樣子」 | DevOps 防的是「部署後才發現壞掉、或壞掉後救不回來」；本專案沒有獨立部署動作，該失效在本專案不存在
  2 產物層判定              | 失效不存在 → 填「無」＋理由「無獨立部署動作，不存在部署失敗待救援的情境」＋重評條件「新增可獨立執行的伺服器模式時重評」
  3 判準層檢查              | 與此無關——判準層檢查的是框架有沒有辦法判斷既有產物是否合格，本例產物層已判「無」，不需要再檢查判準層
  候選錯誤答案 | 甲：直接標「待定」（誤把「形態不符」當「該判而未能判」）／乙：標「無」但不附理由與重評條件（漏必須附帶欄位）
```

【驗證】檢驗問句

```
Q 「無」與「待定」的區分軸是什麼？
  預期：是否已完成判斷——依據句「『無』的語意是判完了、結案；『待定』的語意是還沒判完」（〈產物欄的五種合法答案〉表下強調段）。

Q 本例填「無」是否需要附帶理由與重評條件？
  預期：需要——依據句「無」列「必須附帶」欄「理由（失效為何不存在）+ 重評條件」。

Q 若框架本身沒有判斷 CI gate 合格與否的判準，是否也要在產物欄標「待定」？
  預期：否——判準缺席屬判準層，另標「無判準」，不影響產物層已判「無」的結論；依據句「權威存在但無可用部分屬判準層，另標『無判準』，單獨不構成填『待定』的理由」。

Q 步驟 1「DevOps 防的是……」是否有可溯的依據句？
  預期：有——依據句「壞的版本怎麼在使用者看到之前被攔下、依賴失敗時系統怎麼不跟著一起死」，出處見 `dimension-product-notes.md`〈各維度要防的失效（權威出處）〉表「DevOps」列（`saas-tech-selection` skill `references/dimensions/reliability.md` 開頭段）。
```

## 權威缺席的查證對象：session 端還是被盤點 repo

【輸入】

```
執行本流程的 AI session 已安裝某維度的權威 skill；被盤點的目標 repo 本身沒有任何框架資產目錄，是一個純粹的第三方程式碼庫。盤點該維度時要判「權威是否缺席」。
```

【產出】

```
形態：決策表
  候選判定 | 依據                                     | 結論
  甲：待定 | 被盤點 repo 沒有框架資產目錄，判權威缺席 | 不合格，見驗證段
  乙：非待定（權威存在） | 執行本流程的 session 有安裝該權威，判權威存在 | 合格
  產物欄   | 依權威（session 端）判定的結果照常填入產物欄，該產物落在被盤點 repo 的 ticket 系統 | 兩個查證對象各自對應各自的判定面，不可混用
```

【驗證】檢驗問句

```
Q 判斷「權威是否存在」該查哪一端？
  預期：執行本流程的 session 的框架資產目錄——依據句「權威是否存在，看的是執行本流程的 session 的 `.claude/`，不是被盤點的 repo」（〈權威缺席時〉「先定相對於誰」）。

Q 被盤點 repo 沒有框架資產目錄是否構成權威缺席？
  預期：否——依據句同上，被盤點的 repo 不需要安裝框架。
```

## 已驗證與未驗證的專案形態

已實跑驗證的形態：Flutter 桌面應用、Go CLI 單檔工具、多語言 SDK monorepo、前後端分離的 PHP 服務（真 PostgreSQL）、瀏覽器擴充套件（非 Flutter 的 GUI，四塊全部成立）、多人協作的既有 Flutter 專案（本機使用者零 commit）。

**未經實跑驗證**：單體遺留系統（十萬行以上、無模組邊界）、非 Web 非 Flutter 的桌面框架、需要合規稽核的受管制系統。

`references/dimension-product-notes.md`〈改寫產物是主路徑〉已針對其推導問句補上三段鏈式範例；範例本身是特定形態下的具體示範，推導問句才是可套用到其他形態的部分。
