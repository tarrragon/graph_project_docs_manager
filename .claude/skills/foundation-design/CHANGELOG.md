# foundation-design 版本紀錄

新到舊。版號規則與兩個住址（本檔與 `SKILL.md` frontmatter 的 `metadata.version`）見專案的 skill 同步規範。

**Version**: 6.5.3 — 補六處缺引導（既有審查確認 agent 依此文件執行時被迫自行發明規則，皆判定不改變既有判定者，直接寫入）。**〈權威缺席時〉形態 2「權威存在但形態不符」**：改寫後產物的合格判準改為回答 `dimension-product-notes.md`〈改寫產物是主路徑〉推導問句，答得出具體形狀即完成；同步移除〈工作流〉步驟 3 與本形態互指卻各自無終止條件的循環引用，步驟 3 改為單向指向本形態、本形態明寫「不需再回頭比對步驟 3」。**形態 4「工作流自身引用的 skill 缺席」**：決策記錄補四欄定義（維度清單、已產出產物內容、缺席 skill 名稱、重排觸發條件），觸發條件固定為該 skill 出現在執行 session 的 `.claude/skills/`。**步驟 5 人工複核**：補驗收條件須寫的三項（複核者、複核依據、複核產出），機械檢查形態仍留給各維度權威自行設計。**baseline 表達形式**：補違規計數上限／檔案清單白名單兩種形態的擇一依據，`handoff-mode.md` 規模閘門段落改指回本定義避免兩處各說一次。**`handoff-mode.md` 步驟 1 盤點表欄位**：補值／位置／是否被斷言涵蓋三欄定義。**`handoff-mode.md` 末段三種情形抽取**：由僅列舉情形改為各自附處置（共用可變實例改抽不可變值或工廠函式、編譯期常數位置抽取後仍須維持編譯期常數形式、平台設定檔或行內樣式改指單一事實來源或由建置產生）。

**Version**: 6.5.2 — 依獨立評估者 WRAP 裁決落地兩則原文矛盾修法（起草草稿未採用，改採 WRAP 定稿）。**命名時值變不變**：`handoff-mode.md` 新增〈命名與收斂分兩步〉——第 2 步仍逐值命名、值不變，疑為雜訊的值記入決策文件、收斂另開票與命名同批建立（安全性掛在行為中立，命名與改值同步發生會使畫面變化無法歸因）；來源為設計畫布尚無程式碼綁定時例外，萃取當下即可歸納，`examples.md`〈萃取不等於照抄〉補一句範圍界定並指回新段落。**填「無」或「待定」**：改用產物層／判準層兩問取代「能否具體說出理由」的自評式判準——`dimension-product-notes.md`〈非 SaaS 專案的形態轉換〉改為先答〈改寫產物是主路徑〉推導問句（失效在本專案長成什麼樣子），失效不存在才標「無」，權威無可用判準另標「無判準」建框架缺口票；`SKILL.md`〈產物欄的五種合法答案〉表「無」「待定」兩列同步改寫，移除「待定」列原「判準缺席」括注的舊語意（單獨的判準缺席不再是填待定的充分條件）。

**Version**: 6.5.1 — 修正兩處文字不一致：`dimension-product-notes.md` 引用錨點「產物欄的四種合法答案」改為現行標題「產物欄的五種合法答案」；`troubleshooting.md` 末列「不在五個維度內」與 `SKILL.md`〈本 skill 不做什麼〉節「五個維度全部已有既有權威」皆改為引用〈維度與產物〉表而非寫死數字（維度表現為六列；依〈集合命名用角色、不內嵌數量〉同一判準，與 6.4.0/6.3.1 兩筆同類）。另有兩處原文矛盾（handoff-mode「值不變」vs examples.md「萃取不等於照抄」；dimension-product-notes「無可用部分標無」vs SKILL.md「判不出來一律待定」）待獨立評估者裁決後另筆記錄，本次未落地改文。

**Version**: 6.5.0 — 依一輪低階 model 讀者探針（同一份 SKILL.md 派 3 個實例，指令逐字相同、無審查框架、禁臆測填補）處置四項。**「權威缺席時填『待定』不得填『無』」由 0/3 帶走改為進主路徑**：〈產物欄的四種合法答案〉擴為五種，「待定」成為表列答案形態之一，原本置於〈權威缺席時〉之後的獨立說明段併入表下並移除，避免兩處各說一次；工作流步驟 2 的括號同步列入「待定」。探針顯示原文對該規則已用粗體兩次加一整段專講而三份無一帶走——歸因為位置而非強調密度，處置因此是移位不是再加強調。**新增〈按需讀取〉表**（四份 reference 各自何時讀），原本三份 reference 散在三個章節內文提及，讀到其中一節的人不知道另兩份存在。**新增〈與相鄰資產的交界〉表**並首次指名 `dart-style-guardian`——原文載體表列「執法工具」一類、工作流步驟 5 要求「接入執法載體」、Common Issues 有一列專講執法載體失效，三處皆用類別名從未指名實例，探針 Q5 三份無一提及它。交界表刻意不列 `tdd`／`saas-tech-selection`／`design-decision-framework`／`project-init`：維度表與開頭已逐列指名並給判別句，重列只會讓讀者多讀一次而不多知道一件事。**體量**：`Common Issues` 外移至新建的 `references/troubleshooting.md`，〈已知的證據基礎限制〉併入 `references/examples.md` 並更名〈已驗證與未驗證的專案形態〉，共外移 773 tokens；淨增 27 tokens，SKILL.md 4872 tokens。

**Version**: 6.4.0 — 維度表新增一列「事件流仲裁」：權威為事件流負載仲裁方法論（判準在此，本 skill 不複述），預設產物為通道清單＋每通道的仲裁器落層＋九格卸載順序表，適用條件為有兩條以上事件流的專案（不限 SaaS）。`references/dimension-product-notes.md` 補該維度的四種答案形態範例，改寫產物的典型為單線程桌面 App 只有注意力通道。frontmatter description 同步補列；「本表列的是五個常見維度」改為不寫死數字（新增一列後原數字即失真，依〈集合命名用角色、不內嵌數量〉同一判準）；移植前置條件的權威清點勾選項同理改為不寫死 skill／方法論數量。動因：事件流負載仲裁方法論定稿後，地基盤點原無一格問「多條事件流搶同一通道時誰裁決」。

**Version**: 6.2.0 — 維度與產物表補「適用條件」欄；資料庫／DevOps／可觀測性三列的權威 `saas-tech-selection` 明示為 SaaS/伺服器端專案預設形態，非 SaaS 專案（CLI 工具、函式庫、單機 app）改依既有「改寫產物」機制取可用部分，無可用部分則改指專案自身 CLAUDE.md 技術選型記錄或標「無」+ 理由；不新增第二套權威。實測依據：非 SaaS 專案（如 Go CLI 工具）走此路由會被引導至 managed database／k8s 等不適用選型。本筆原編為 6.1.0，與 canonical 上另一筆獨立的 6.1.0 撞號——兩者由不同 consumer 各自從 6.0.0 前進一步，版本號是單調計數器不表達分叉，合併時以 canonical 為共用時間軸故本筆順延為 6.2.0。

**Version**: 6.1.0 — UI 列補反向路由：元件庫那塊實作前的契約程序指名 `component-contract-design` skill，預設產物的元件庫依賴補「契約齊全」。動因：多輪審查發現本 skill 自稱地基單一入口，UI 列卻零次指向契約程序，即本檔 Examples 自述的「錯誤的承接宣告誘發漏做」形態

**Version**: 6.0.0 — 引用形式由檔案路徑改為指名身分（skill 用名字、方法論與規則用標題）。路徑是「它現在放在哪」會隨改版移動，名字是「它是什麼」不會；且 skill 在本系統以名字載入，寫路徑等於繞過既有載入機制。實測依據：框架改版移動 hook 位置使註冊失效、可攜性閘門把 25 處路徑判為指名他專案檔案而擋下推送。
