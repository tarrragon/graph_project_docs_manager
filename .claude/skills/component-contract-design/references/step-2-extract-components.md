## 這一步在解什麼

把手上的材料變成兩張表：**元件候選表**與**容器候選表**。三條路徑的輸入不同、步驟不同，產出的表格形態相同，step 3 一律拿這兩張表去填契約。

三條路徑的差別只在怎麼取得事實：

| 路徑 | 事實從哪來 | 這條路徑特有的難處 |
|------|-----------|------------------|
| A 規格推導 | 逐畫面狀態表的「顯示」與「可用操作」兩欄 | 只在單一狀態出現的元件容易漏抽；頁面框架不在任何顯示欄裡 |
| B 畫布拆解 | 畫布上的視覺單元 | 畫布上只有畫素沒有語意，要先命名；且畫布不是檔案系統可及物 |
| C 程式碼萃取 | 既有元件目錄與頁面 | 事實散在呼叫端；存量的不一致是漂移而非設計 |

## 中間產出物的形態與落點（三條路徑共用）

**這三張表不是草稿。** step 4 的齊全判準要拿容器候選表當分母，形態未定該判準即無法機械執行。三者一律寫入**本規格票的 Problem Analysis**，不寫暫存檔——跨 session 會遺失。

| 產出物 | 由哪一步產生 | 欄位 |
|--------|------------|------|
| 元件候選表 | 路徑 A 步驟 2 | 候選名 / 來源（狀態表哪一列的哪一欄、或畫面清單、或畫布）/ 出現的畫面與狀態 / 是否與他候選總是共現。**存在必要性檢視於本表追加「判定」與「理由」兩欄**（合併或不合併、依據哪個語意或行為差異） |
| 容器候選表 | 路徑 A 步驟 4、路徑 C 步驟 4 | 容器候選名 / 所在畫面 / 佈局結構 / 全部子件 / 排列方向 / 空間不足策略（step 3 填定前留空） |
| 排列關係表 | 路徑 B 步驟 4 | 畫面 / 區塊 A / 區塊 B / 排列（並排／堆疊／格線）/ 間距的 token 名 |
| 三態盤點表 | 路徑 C 步驟 1 | 元件名 / 欄位 / 問句 / 三態（已定義於程式碼／隱含於呼叫端／空白）/ 證據（檔案與行，或呼叫端位置） |

三態盤點表另有量級要注意：元件契約欄位表逐欄展開的填寫問句遠多於欄位本身的數量，元件數乘以問句數即本表列數，中型專案的元件數即可讓列數達到另立子節的規模。它與路徑 C 步驟 2 的回收提案值放在一起，使核定者一次看到證據與提案。

## 路徑 A：規格推導

狀態表的「顯示」欄是元件的主要書面來源，因此**先從它抽元件候選、再盤容器**。順序反過來（先想元件再對表）會漏掉只在某一個狀態出現的元件。不在任何顯示欄的頁面框架（導覽、專案切換）從畫面清單與畫布補入。

```
1 收集輸入   逐畫面狀態表、畫面清單、畫布、token 表、互動反應規格（UX 審查產出）。
             畫布缺就只用狀態表與畫面清單。互動反應規格的 UX 審查票已開但產出未落檔時，
             暫以狀態表的退出路徑欄代之並標待決；票未開者回 SKILL.md〈起手〉走前置出口

2 元件候選   三處來源：狀態表每列「顯示」欄的視覺單元；「可用操作」欄有視覺承載的控制項
             （搜尋、篩選、取消）；畫面清單與畫布中的頁面框架（導覽項、切換觸發器）。
             跨畫面跨狀態總是一起出現的單元合為一個元件；有時一起出現的單元是該元件的可選 slot；
             只在單一畫面內共現、各自也能獨立出現的單元不是一個元件，是容器的子件，走步驟 4

3 存在必要性 每個候選問「通用元件加變體能否涵蓋」——判準見本檔〈共用規則一：存在必要性檢視〉。
             排列型候選（格線、表格、樹、列表、雙欄）不做此檢視，逕移步驟 4

4 容器盤點   逐畫面列出每一個佈局結構及其全部子件（含框架層：側欄／主區、工具列／內容），
             每個佈局結構一個容器候選。「一組」指同一佈局結構下的全部子件，不是兩兩相鄰對。
             判準是方法論〈容器亦為元件〉的判別問句「任兩個元件的相對位置是誰決定的」；
             路徑 A 尚無頁面，答案恆為「尚未有人決定」，所以這裡做的是**列舉不是判定**。
             單一子件的包裝（Padding／Align／Center 包一個元件）無排列關係，不是容器候選，
             其內距屬子件的組合規則或所屬容器的格位。
             容器的子件可以是容器；巢狀容器依同一歸併鍵跨層歸併，殼層（側欄／主區）
             以一個框架容器承載，不再往上遞迴。
             由路徑 B 進入者，本步驟以路徑 B 的排列關係表代替，不重列

5 同型歸併   規則見本檔〈共用規則二：同型歸併〉。本步驟只做第一次歸併（依「子件類型加排列方向」）
             並暫記空間不足策略的假設；**第二次歸併要等 step 3 填定策略之後才做，屆時回到本節**
```

**元件候選（步驟 2）的常見遺漏**：狀態表的「顯示」欄常寫成句子（「顯示訊息與一顆前進按鈕」），名詞抽取要抽到能對應一個視覺單元為止——「訊息加前進動作」跨六個畫面總是一起出現，是一個空狀態元件，不是「文字」與「按鈕」兩個。判斷粒度問「這組單元跨畫面、跨狀態會不會總是一起出現」。

**走完之後**：帶著元件候選表與容器候選表進 `step-3-fill-contract.md`。

## 路徑 B：畫布拆解

畫布上只有畫素，沒有語意。本路徑的核心工作是把視覺單元**命名成語意**，命名完就接回路徑 A。

**輸入形態（本路徑獨有的前置）**：三條路徑中只有 B 的第一手輸入不是檔案系統可及物——執行者開不了設計工具的原生檔。可接受的交付物三選一：

| 交付物 | 附帶要求 |
|--------|---------|
| 逐畫面的點陣圖或向量圖匯出檔 | 放進專案可讀路徑；**須另附間距實測清單或標註座標**——步驟 4 要的是間距實測值，圖檔本身量不出來，只給圖檔者視同交付不完整 |
| 設計工具的結構化匯出 | 含區塊名稱與座標的 JSON／CSV |
| 人工撰寫的逐畫面區塊描述 | 每畫面列出區塊、相對位置、間距實測值 |

三者皆無時走前置出口：建畫布交付票並設為本規格票的 blockedBy，**不在本規格票內以想像補畫布**。step 1 判定起點時同此——`SKILL.md` 起點表 B 列的訊號（如設計工具自動命名視同未命名）須在上述交付物上可觀察，觀察不到就不是路徑 B 的合格起點。

```
1 視覺單元盤點  逐畫面框出每個可獨立辨識的區塊；相同外觀的區塊先各自列，不預設同型

2 語意問句      每個區塊問：使用者看到它預期能做什麼？
                它承載標題／內文／標籤／數值／動作哪一種？

3 同型歸併      語意相同者歸併為一個元件，外觀差異降為變體；語意不同而外觀相同者不歸併

4 排列關係盤點  逐畫面記錄區塊之間的排列（並排、堆疊、格線）與間距實測值，產出排列關係表
                （欄位見本檔〈中間產出物的形態與落點〉）

5 接回路徑 A    專案另有狀態表者，先補跑路徑 A 步驟 2 的「顯示」欄與「可用操作」欄兩處候選來源
                （避免漏掉只在單一狀態出現、畫布未畫出的元件），再自路徑 A 步驟 3 起；
                無狀態表者直接自路徑 A 步驟 3 起。路徑 A 步驟 4 以本路徑步驟 4 的排列關係表代替
```

**同型歸併（步驟 3）的反向陷阱**：畫布產生器常給語意不同的單元相同外觀（同一個圓角卡片放專案摘要也放錯誤訊息）。以外觀歸併會把兩種語意塞進一個元件，之後靠參數分岔。判斷用語意問句（步驟 2）的答案，不用畫素。

**排列關係盤點（步驟 4）與 token 的關係**：間距實測值歸納為 token 階屬 token 萃取（`foundation-design` skill 接手模式的「盤點 → 命名」與其「萃取不等於照抄」案例），本步驟只記錄「哪兩個區塊之間有間距」，值引用已萃取的 token 名；token 未萃取時停下走前置。

**畫布漂移**：畫布為準**只限視覺值**（圓角、間距、字級、顏色）——規格寫圓角 10、畫布量到 7，以畫布為準並更新規格，畫布是視覺決策的產物。行為、狀態、退出路徑的差異（規格有「切換專案」動作而畫布沒畫）以**規格**為準，標漂移待決送 PM，不從規格刪除。契約填寫時引用 token 名而非數值，視覺漂移只需改 token 表一處。

**走完之後**：路徑 B 不直接進 step 3，它在步驟 5 接回路徑 A，走完路徑 A 步驟 3 到 5 才進 `step-3-fill-contract.md`。

## 路徑 C：程式碼萃取（接手既有專案）

接手的元件庫常見兩種病：**有元件無契約**（行為散在各呼叫端），與**有元件無容器**（頁面用原生佈局排列元件，違反方法論工程端的「禁自製元件」判準）。本路徑先盤點事實再補契約，順序與 `foundation-design` skill 的接手模式一致：盤點 → 命名 → 固化 → 補文件。

```
1 元件盤點     列出元件目錄的每個 public widget（一檔多 class 各算一個；非 widget 的 helper
               不算元件，誤入匯出入口者記為清理項），與 spec 元件清單對帳：
               目錄有而清單無者補入清單，清單有而目錄無者標「待實作」或刪除（PM 核定）。
               每個元件對照 step 3 的**每一個填寫問句**（不是每一欄）標三態：
               已定義於程式碼／隱含於呼叫端／空白；一欄內混合三態屬正常。
               回饋契約欄位的證據常散在動畫 controller、觸覺 API 呼叫、通知服務程式碼，
               而非 widget 宣告本身；找不到對應呼叫標空白，**不可只因缺席就填「不可用加替代」**
               ——替代方案須有實際程式碼佐證才算已定義。
               零呼叫端的元件仍屬本路徑的元件，標「待接線」，其「隱含於呼叫端」態不成立

2 呼叫端回收   「隱含於呼叫端」的欄位（如 maxLines、overflow 在頁面設定）回收進元件契約；
               呼叫端的設定值不一致時填提案值附各處證據並標「待核定」，
               PM 核定前視同待決，不另建決策票。
               另三種形態：呼叫端繞過 slot 自組內容（在 child 裡自己排 icon 與文字）
               → 記為 slot 契約缺口，提案新 slot 或收窄型別；
               spec 有而程式碼無（spec 的變體多於實作）→ 反向漂移，標「待核定」由 PM 裁定
               補實作或刪 spec；元件與呼叫端都沒設（雙空）→ 標空白，留給 step 3 處理

3 原生佈局掃描 grep 頁面層的佈局原語（依框架：水平／垂直堆疊、彈性盒、格線），
               只算包兩個以上元件庫元件的位置；中間只隔佈局輔助
               （Expanded／Flexible／Padding／SizedBox／Align）仍算直接包，
               中間隔另一個元件庫元件則不算。
               頁面層含 feature 目錄下的 sheet／dialog／card 等區域 widget
               （不在統一匯出入口即頁面層）；每頁的根堆疊也算，同型歸併為
               「頁面區塊堆疊」框架容器。每處問判別問句

4 容器候選     判別問句答「頁面」處即容器候選；依本檔〈共用規則二：同型歸併〉歸併，
               但**存量的策略不一致要收斂不要拆**，理由見該節。
               資料驅動 N 列的堆疊（列表、明細）是容器候選，
               只在 `appendix-examples.md`〈Troubleshooting：卡住時的症狀處置〉的計數門檻中排除

5 事故對照     既有的重疊、截斷、點不到事故逐一對應到缺哪個容器或哪個空白欄位。
               來源三選一：issue tracker 既有紀錄、ticket 描述提及的缺陷、用戶口述提供的清單，
               逐一標明取自何處；對不上的事故是新發現，另建分析票（不建元件票）。
               三者皆查無時視同零事故，本步驟為空——**零事故是關機判定**，
               要記下查過哪些來源、各自為空。零事故的專案，
               step 5 的容器優先序改依呼叫處數量（出現最多的排列關係先建）
```

**呼叫端回收（步驟 2）的判準**：呼叫端設定值不一致是契約缺內容政策的訊號。同一個元件在三個頁面被設成三種 `maxLines` 時，執行者選一個值作提案並附三處證據，PM 於契約票驗收核定後其餘兩處改為引用元件預設；差異若是語意的（標題一行、內文三行），那是**兩個內容角色，拆元件**。

**原生佈局掃描（步驟 3）的框架對應**：Flutter 找 `Row` / `Column` / `Wrap` / `Flex` 直接包兩個以上元件庫元件的位置；Web 框架找頁面元件內的 flex / grid 容器。原生佈局出現在元件庫內部（統一匯出入口涵蓋的目錄）屬正常——容器元件自己就是用它實作的；入口外的 feature 目錄下的自製 widget 屬頁面層，一併掃。

**特徵測試閘門（掛在步驟 2）**：回收呼叫端設定進元件會改變頁面行為。覆蓋不足時先補特徵測試（不驗「應該是什麼」，只把現況行為原樣鎖住，改動一旦改變行為就紅燈）鎖住現況。規模補不補得起來由 PM 於票面裁定，**執行者只提報覆蓋數字、不自行裁定**；裁定為補不起時只在有覆蓋的模組內回收，其餘標「只擋新增」——這也是關機判定，要記下覆蓋數字與門檻值。判準與規模閘門見 `foundation-design` skill 的接手模式；本步驟的裁定結果會成為 step 5 遷移票的 blockedBy。

**走完之後**：帶著三態盤點表、回收提案值、容器候選表與事故對照進 `step-3-fill-contract.md`——那裡有**路徑 C 專屬的證據順序與漂移判定**，其他兩條路徑不需要那一節。

## 共用規則一：存在必要性檢視

路徑 A 步驟 3 消費本節；路徑 B 經步驟 5 接回路徑 A 後同樣消費它；路徑 C 用它推得語意與內容角色、變體、反例三欄（這三欄不需程式碼證據）。

**方向是先假設能併，找不到併不進去的理由才立特化元件。** 判準是方法論〈命名與通用元件判準〉的「能否命出設計目的」：理由須為**語意或行為差異**（內容角色不同、退出路徑不同），外觀差異不構成理由。

| 差異類型 | 構成拆分理由嗎 | 說明 |
|---------|--------------|------|
| 退出路徑不同 | 是 | 指離開的層級（留在畫面內／離開畫面／離開專案）。只是目的地不同者為 slot，不拆 |
| 內容角色不同 | 是 | 標題一行與內文三行是兩個角色 |
| 外觀不同 | 否 | 降為變體 |
| 語氣不同 | 否 | primary／confirm／danger 是同一語意的不同語氣，變體欄已明訂此命名法。語氣不改變內容角色與退出路徑，據它拆會使每個按鈕語氣各成一個元件 |

實測案例：空狀態與阻擋狀態外觀相近，但空狀態說「這裡目前沒有內容」、阻擋狀態說「這個專案不適用」，退出路徑不同，因此是兩個元件。完整的判斷過程對照見 `appendix-examples.md`〈正例〉。

判定結果寫回元件候選表的「判定」與「理由」兩欄。與 spec 既有清單衝突時以本檢視為準，回填時標「提案」，PM 核定後去標。

## 共用規則二：同型歸併

**歸併鍵是「子件類型加排列方向加空間不足策略」，不是出現的畫面。** 一個按鈕列在七個畫面出現七次仍是一個容器元件；子件從按鈕變成徽章時，若排列方向與空間不足策略相同，仍是同一個容器，slot 的具名子件清單加一項。

歸併分兩次：第一次在 step 2（依子件類型加排列方向，並暫記空間不足策略的假設），第二次在 step 3 填定策略之後（策略相同者再併一次）。

**歸併過頭的訊號**：排列不變式填不出單一值，或 slot 子件清單長到只能寫「任意」。容器的 slot 子件類型須為具名元件清單——填「任意元件」視同原生佈局，一個接受任意子件的水平堆疊等於加了 token 間距的原生列，判別問句形式上滿足但無約束力。

### 策略不一致時，路徑 A 拆、路徑 C 併

兩邊的規則都對，差別在同一組事實的語意不同：

| | 路徑 A（新建） | 路徑 C（存量） |
|---|---|---|
| 策略不一致是什麼 | 執行者當場決定的設計 | 既有程式碼在無契約狀態下各自演化的漂移 |
| 是誰決定的 | 有人決定 | 沒人決定，長出來的 |
| 處置 | **拆**：兩個排列關係選了不同策略，代表設計上就是兩個容器 | **併**：收斂為一個容器候選，策略欄填提案值附各處證據標「待核定」，PM 選定單一策略後回填各處 |

**新建與存量問句**：這個差異是有人決定的，還是沒人決定而長出來的？前者拆，後者併。

> 這個問句與路徑 A 步驟 4、路徑 C 步驟 3 消費的方法論〈容器亦為元件〉判別問句（「任兩個元件的相對位置是誰決定的」）**不是同一個，兩者不可互代**。前者判要不要歸併，後者判是不是容器。
