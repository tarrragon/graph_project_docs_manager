# Step 3：填契約

> **你在 step 3。** 上一步：`step-2-extract-components.md`，你帶著元件候選表與容器候選表過來（路徑 C 另帶三態盤點表與回收提案值）。下一步：`step-4-verify-completeness.md`。全程表在 `SKILL.md`〈全程〉。
>
> **本步結束前要回頭一次**：空間不足策略在本步填定，而 step 2〈共用規則二：同型歸併〉的**第二次歸併**要等這個值——填完策略後回 step 2 那一節，把策略相同的容器再併一次，再進 step 4。
>
> **簡稱查地址**：本檔出現的方法論、範本、L2、本規格票，地址一律查 `addresses.md`。

## 這一步在解什麼

拿 step 2 的兩張表，對每個元件與每個容器逐欄填出契約值。**每欄一個問句，答不出來的欄位就是空格。空格的處置是找來源，不是猜。**

來源不可得（決策者不可得、前置資源未產出、合併與否無人拍板）時三條路徑共用同一出口：該欄標「待決」並建決策票或前置票，設為元件票的 blockedBy；存在必要性檢視的合併結論由 PM 於契約票驗收核定。

## 空格的處置：「待決」與「不適用」

**合法的佔位值只有兩個，且不可互代**：「待決」是**缺答案**，「不適用」是**答案**。

「不適用」限該欄對此元件結構上不存在時使用（無變體、狀態集只有 enabled、無 slot、無文字、純顯示且無資料態變更），須附一句理由，且只允許於下表第一組：

| 分組 | 欄位 |
|------|------|
| 可填「不適用」的欄位 | 變體、狀態集、slot 契約、內容政策、反例、操作機制（純顯示且無任何互動的元件）、回饋契約（限純顯示且無資料態變更者） |
| 不得填「不適用」的欄位 | 語意與內容角色、尺寸契約、組合規則、測試契約、無障礙 |

第二組不得填的理由：語意與內容角色填不適用等同宣告該元件不該存在；純顯示元件的無障礙至少有朗讀標籤與焦點路徑。

兩組合計即元件契約欄位表全部欄位，無欄位落在兩組之外——step 4 第一條的機械檢查因此對每一欄都有唯一解。

> 空間不足策略不是元件契約欄位表的欄位之一，它是容器的排列不變式；其合法替代值「不觸發加公式」見本檔〈容器元件另答排列不變式三項〉。

**誤填「不適用」的代價**：它是齊全檢查唯一的假陽性入口。

| | 誤填「待決」 | 誤填「不適用」 |
|---|---|---|
| 齊全檢查怎麼看它 | 視同空白，該元件不得被畫面票引用 | 視為落成值，全數通過 |
| 後果 | 流程被擋住，多一次往返 | 元件票取得可被畫面票引用的資格，缺料到實作期才暴露，而該處已無契約可回溯 |

**判定不確定時填「待決」不填「不適用」。**「見設計稿」「同上」「TBD」等未落成值的寫法一律視同空白。

i18n key 已宣告而譯文未到者，內容政策填 key 即齊全，測試契約以當時資源檔的值執行；譯文更新後的重測屬 i18n 票驗收，不回退契約狀態。

方法論〈分層架構〉最小適用集生效的小型專案，元件契約欄位表縮至語意與內容角色／尺寸契約／內容政策（**回饋契約不在最小適用集**），排列不變式仍須填，不隨欄位一併縮減。

## 元件契約欄位填寫問句

| 欄位 | 填寫問句 | 常見空格與來源 |
|------|---------|--------------|
| 語意與內容角色 | 使用者看到它預期能做什麼？它放的是標題／內文／標籤／數值／動作？什麼情境不該用它？ | 「何時不用」常空白；來源是相鄰元件的語意差異。複合角色（內文加動作）並列寫出，每個角色對應一個 slot |
| 變體 | 同一語意有幾種行為不同的形態？各自的外觀與行為差在哪？ | 常以外觀值命名（藍色版）；改以語意命名（primary／confirm／danger） |
| 狀態集 | 它自身可以處於哪些狀態？每個狀態怎麼顯示、能做什麼、怎麼進、怎麼出？此狀態的來源是互動瞬態、資料態、還是無（—）？同步策略是本地即時、樂觀更新後確認、還是等確認才顯示？ | 只列元件自身的狀態（enabled／loading／error 等），畫面級的進出由呼叫端的畫面狀態表承載；退出路徑空白即死胡同；來源與同步策略常空白，兩者不分會讓互動瞬態與資料態混在同一張矩陣，實作者不知哪個狀態要接 provider、哪個只是本地事件；四欄填法見 `ux-design-evaluation` skill 的狀態矩陣 |
| 操作機制 | 這個形態的使用者用什麼動作完成它的任務？任務要多精確？該形態的輸入做得到嗎？做不到時給什麼替代機制？按下後走哪個回饋通道？ | 常直接沿用畫布的手勢（桌機拖動滑桿搬到手機）；每形態各答一次，精度不足時填替代機制（步進按鈕、輸入彈窗）；回饋通道引用形態因素矩陣（手機須觸覺或聲音，手指會遮住按鈕）；輸入形式判準見 `ux-design-evaluation` skill 的輸入機制 reference |
| 尺寸契約 | 它自己決定大小還是填滿父容器？最小多小、最大多大？可點元件的最小尺寸有沒有達到該形態的最小命中區？每個形態各一份，同形態內每種測試尺寸下怎麼變？ | 「每種測試尺寸」常只填預設尺寸；最小命中區常沿用桌機值搬到手機；形態、測試尺寸集合與命中區 token 的來源是範本第 1 章形態因素矩陣（判準見方法論〈形態因素先決〉） |
| 內容政策 | 每個文字位置可不可以換行？最多幾行？超出時截斷／淡出／縮放／換行？最長的測試文案是什麼？ | 最長測試文案常空白；來源是專案 i18n 資源檔（Flutter 為 ARB）中該 key 各語言的最長值，排除未翻譯的 fallback（與來源語系字串相同者）；語系少於三種時另加一條人工的長文案。無文字 slot 的元件填「不適用」 |
| slot 契約 | 呼叫端能放什麼進來？每個位置接受什麼型別？文字從哪來？ | 文字來源常寫死；規則見方法論〈元件文字歸屬〉。容器的子件 slot 須寫具名元件清單與數量上限，策略欄只引用此處的上限 |
| 組合規則 | 它可以放進哪些容器？哪些區域不得放它（該形態的禁放區）？對齊基準是什麼？當它是表格或列表的一欄時佔多寬、內距多少？ | 「可放入的容器」填「任何地方」即等於允許頁面原生佈局；須列具名容器。可點元件的禁放區引用形態因素矩陣（手機四角、系統手勢區）。根層框架容器填「根：無父容器」並承載該形態的安全區 |
| 無障礙 | 輔助技術會把它唸成什麼？值或狀態變了怎麼播報？不靠顏色能不能分辨？鍵盤或輔助技術怎麼走到它、怎麼操作它？ | 常空白或只填對比；朗讀標籤與播報跨形態共用，操作路徑每形態各一份；不得填「不適用」 |
| 回饋契約 | **本欄是一套有序程序，不是一個問句**——見下方〈回饋契約的填寫順序〉整節，依序作答完才回來填格子 | 見該節末的漏答樣態表 |
| 測試契約 | 一支測試能不能一次看到全部變體與狀態？每種尺寸都不溢位？最長文案照內容政策處置？ | 常只測預設尺寸與短文案；測試形態（golden / widget）定於 L2，L2 無此條時以範本測試點的 widget test 為預設並建 L2 補條目票。測試基座（讓元件在各視窗尺寸下可渲染與斷言的測試工具與 fixture）由 `foundation-design` skill 的測試維度承接 |
| 反例 | 什麼情境會有人誤拿它來用？該改用哪個相鄰元件？ | 常空白；來源是存在必要性檢視時被否決的合併理由 |

範本子節與元件契約欄位表不同名者：狀態集即範本的「狀態矩陣」、測試契約即「測試點」、語意與內容角色即條目標頭三行；完整對應表在範本檔頭註解。

一份填好的逐欄正例（清單卡）見 `appendix-examples.md`〈正例〉，它逐欄呼應上表的「常見空格與來源」。

## 回饋契約的填寫順序

**適用前提**：元件判定為可互動（操作機制非「不適用」）或有資料態變更。純顯示且無資料態變更者本欄填「不適用」，不跑本節。

本節是五個關卡，**依序通過才填得出通道格**。順序不可調換的地方各自標明了理由。

### 關卡一：掛載點判準

填「按下確認」與「等待與結果」兩格之前先答：

> **把這個元件背後的服務整個拔掉，使用者按下去還看得到反應嗎？**

答**否**即掛載點錯誤。該事件要改掛在**互動事件與待回應狀態**上，不得只掛在服務回應之後。判準見方法論〈掛載點〉。

改對掛載點才進關卡二。

### 關卡二：通道大類四問

**依序作答，先命中先決定，此序不可調換。**

| # | 問句 | 命中（答是／答否如括號所示）時怎麼辦 |
|---|------|--------------------------------|
| 1 | **可見性**——事件抵達時，觸發它的畫面是否為使用者當前可見、且視窗在前景？ | 答**否**：不用暫態提示。改走升級通道，或延後至該畫面再度可見時處理；兩者皆不可行時進關卡四 |
| 2 | **狀態轉換**——事件是否已在該可見畫面上產生可見的狀態轉換？ | 答**是**：不用暫態提示，狀態轉換本身即結果 |
| 3 | **保留需求**——訊息內容是否需要使用者保留、抄錄或逐項閱讀（路徑、明細、需比對的清單）？ | 答**是**：不用會自動消失的暫態提示，改由畫面承載 |
| 4 | **附隨操作**——是否附帶使用者必須執行才能取得結果的動作？ | 答**是**：列為不可被靜默取代或截斷級。答**否**：可截斷級 |

**第 2 問必須排在第 1 問之後。** 同一事件可能已產生狀態轉換，但轉換發生於使用者當前不可見的畫面——此時仍須先被第 1 問擋下，**不得因「有狀態轉換」就逕自判定不需要任何回饋**。

第 4 問只定等級。爭用時的排序或優先序處置留給容器層或元件層決定，不在本欄回答。

四問全數作答完成、且結論為需要暫態提示，才進關卡三。

### 關卡三：類型分化

> 本元件庫現有的暫態提示元件是否只有一種？此事件依關卡二的結論（尤其第 3、4 問判定的等級）該用哪一種？

**即使目前只有一種可選、答案因此唯一，本問句仍不得省略**，且須註明判定來源。例：

> 目前只有一種載體，故所有等級皆落在同一元件；是否分化取決於同類事件的顯示位爭用是否實際發生及其後果分級，未經實測不得逕行分化，亦不得逕行斷定不需要分化。

分化與否是**待決策的設計判斷，不是不存在的問題**。日後新增第二種暫態提示元件時，本問句即為既有事件重新歸類的入口——省略它，那一天就沒有回頭套用的著力點。

### 關卡四：不顯示時的日誌承接

依關卡二判定為**不使用**暫態提示時，該事件的可觀測性由誰記錄？

| 情形 | 誰記錄 |
|------|-------|
| 已改走升級通道 | 由該通道自身既有的日誌承接，本問不重複規定 |
| 無任何升級通道（第 1 問判否且無替代） | **判斷當下必須記錄一則「因判準而未顯示提示」事件，並標明命中的是哪一問** |

第二列不做的後果：程式主動決定不告知使用者這件事，完全不可稽核。

判定為**使用**暫態提示者，其顯示、靜默早退、使用者互動三類時刻的日誌由方法論〈元件層回饋日誌（觀測對偶）〉承接，本問不重複規定。

### 關卡五：填通道與四段結局

四個關卡都過了才填格子：

- 使用者接近／按下／被程式定位／資料態變更時，此形態的使用者從哪個通道得知？
- 元件不在視野時要不要升級為系統通知？
- 每條狀態邊的提示是元件自播還是呼叫端觸發？
- **「等待與結果」須在同一格回答成功／失敗／逾時／服務不可用四種結局**，不接受「不會發生」（方法論〈失敗路徑覆蓋〉）。某結局收斂為某個狀態值時，該狀態的可見表現須同時寫明（方法論〈降級不解除回饋義務〉）

### 本欄的漏答樣態

| 常見漏答 | 造成什麼 |
|---------|---------|
| 定位提示（locate）與狀態變更提示（state-change）留空 | 來源是範本第 1 章回饋通道子表與第 2 章過渡提示觸發點，查得到卻沒查 |
| 跳過關卡一 | 按下確認與等待與結果的內容只在服務回應之後才成立 |
| 等待與結果只填成功結局 | 漏答失敗／逾時／服務不可用 |
| 跳過關卡二四問，逕自預設用暫態提示 | 可見性與狀態轉換兩問未經檢查 |
| 關卡三因「目前只有一種」而整段省略 | 日後新增第二種載體時無從回頭套用 |
| 誤以為升級通道會自動記下「為何選它」 | 升級通道的既有日誌只記自己的顯示，不記判準命中的理由 |

## 容器元件另答排列不變式三項

容器除了元件契約欄位表之外，另填三項各一問：

| 項目 | 問句 |
|------|------|
| 不重疊 | 子件邊界盒在每種尺寸與數量上限下是否兩兩不相交？ |
| 最小間距 | 相鄰子件的最小間距是哪個 token？ |
| 空間不足策略 | 空間不足時換行、捲動、收合選哪一個？什麼條件觸發？ |

子件有數量上限（上限先寫進 slot 契約）且最小視窗保證放得下者，策略填：

> 不觸發：上限 N，最小視窗下 N × 子件最小尺寸 + (N−1) × 最小間距 ≤ 可用空間

**這個公式即不重疊的測試斷言。** 填「不觸發」是關機判定，要記下代入值與比較結果。一則完整代入的容器條目見 `appendix-examples.md`〈正例〉。

填完策略後回 `step-2-extract-components.md`〈共用規則二：同型歸併〉做第二次歸併。

## 路徑 C 專屬：證據順序與漂移判定

**只有 step 2 走路徑 C（程式碼萃取）的讀者需要本節**，路徑 A 與 B 跳過。

行為類欄位（狀態集、內容政策、尺寸契約、組合規則）的值以既有測試與呼叫端行為為證據，無證據者標「待決」並建決策票，不猜。語意與內容角色、變體、反例三欄由存在必要性檢視推得，不需程式碼證據。

**證據順序**（衝突時取序位在前者）：

> 既有測試 ＞ 元件自身實作 ＞ 呼叫端一致的設定 ＞ spec 的結構化表格 ＞ 畫布 ＞ 規格散文

既有測試常是原作者意圖唯一的書面殘留；規格散文最容易與程式碼漂移。

**元件實作與 spec 表格衝突時**（程式碼尺寸 64 而 spec 寫 36）：

| 情形 | 怎麼填 |
|------|-------|
| 一般情形 | 行為類欄位以實作加測試為準填入，標「spec 漂移」 |
| spec 為近期且有決策記錄 | 反過來標「實作漂移」 |

兩者都由 PM 於驗收核定，**執行者不自行選邊**。

**契約值不變的實作偏離不走漂移判定**：型別撞名改名、套件版本限制的規避、等價轉換這三類，改的是實作方式而不是契約值，填範本的〈實作註記〉即可。

> 判別問句：**改完之後，元件契約欄位表有任何一欄的值不同了嗎？** 沒有就是實作註記，有就走漂移判定。

沒有這一條時，本步只有「待決」與「漂移」兩態，這類偏離無處可歸而被歸入漂移，會為一個沒有分歧的情況觸發 PM 裁定。

## 多形態專案

支援多個形態時，畫布拆解與容器盤點按形態分別進行（每形態一套 artboard、一份排列關係表），元件候選與存在必要性檢視跨形態合一；畫面票的 how 帶形態前綴。

**元件契約欄位跨形態的共用範圍**：

| 分組 | 欄位 |
|------|------|
| 跨形態共用 | 語意與內容角色、變體、狀態集、slot 契約、反例、無障礙（朗讀標籤）、回饋契約（事件與對應狀態邊） |
| 每形態各一份 | 操作機制、尺寸契約、內容政策、組合規則、測試契約、無障礙（操作路徑）、回饋契約（通道）、容器條目 |

**形態因素矩陣的每形態填一次維度**（填欄位時引用）：

| 維度 | 內容 |
|------|------|
| 覆蓋表面對映 | bottom sheet、drawer、dialog、popover 等覆蓋表面依此對映選件，元件的組合規則引用該對映 |
| 回饋通道 | 手機按鈕被手指遮住，須震動或音效；桌機視覺即可 |
| 最小命中區 token | 可點元件的最小命中尺寸依此 token |
| 禁放區與安全區 | 手機四角與系統手勢區不放可點元件，SafeArea 由框架容器承載 |

同一語意可落在不同容器與不同操作機制：導覽項共用，承載它的容器在手機是收合抽屜、在平板與桌機是常駐側欄；數值調整在桌機是拖動滑桿、在手機是步進或輸入彈窗。

**同形態內不依寬度自動切版**：桌機常駐側欄的版型靠視窗尺寸下界與比例約束維持。設計上刻意給使用者選版型（雙欄／單欄）時，那是設定項不是斷點。同形態內的視窗或螢幕尺寸差異不是新形態，由容器的排列不變式承載——把它判為「不是新形態」也是關機判定，要記下該差異的尺寸範圍。
