## 這一步在解什麼

手上有什麼材料，決定 step 2 走哪一條路徑。三條路徑的步驟不同，判準相同，而且互斥——判定完就只走一條。

## 為什麼值得慢慢判

這是全程第一個分岔，而且**判錯了不會有人告訴你**。

| 判錯方向 | 會產生什麼 | 什麼時候才發現 |
|---------|-----------|--------------|
| 該走 C（有存量程式碼）而走了 A | 契約與存量對不上；既有的重疊與截斷事故對應不到任何缺件；遷移票整批缺失 | 實作期。規格本身讀起來完好，格式齊全、判準全過，缺的是它描述的東西跟程式碼裡的東西不是同一批 |
| 該走 B（畫布是主要來源）而走了 A | 元件候選只來自狀態表的顯示欄，畫布上有而狀態表沒寫的視覺單元整批漏抽 | 填契約時發現候選表湊不出畫面，或更晚 |
| 該走 A 而走了 C | 對著 scaffold 產生的佔位元件盤點，得到一份反映鷹架而非需求的元件清單 | step 2 路徑 C 的呼叫端回收與原生佈局掃描全空時 |

三種都不會在中間步驟翻紅。排除理由紀錄之所以要留在這一步，原因就在這裡：事後要回溯「當初為什麼這樣判」，只剩這則紀錄可查。

## 判定

`SKILL.md`〈判定起點〉的速查表給三個起點各自的訊號。訊號清楚時照那張表走即可，本節處理它處理不了的三種情況。

### 情況一：多個訊號同時命中

以「**哪個來源最接近使用者實際看到的畫面**」為準，**不看新舊**：

- 有可跑、且有頁面呼叫元件的程式碼 → 一律走 C。畫布較新也一樣——畫布上的差異在 step 2 路徑 C 的填契約步驟當作漂移處理，不是改判起點的理由
- 無程式碼、有畫布 → 走 B
- 只有規格 → 走 A

原則是**先萃取事實，再對照規格找漂移**。反過來（先照規格寫契約，再看程式碼對不對）會把存量的既有行為當成偏差刪掉。

### 情況二：A 與 C 之間猶豫

逐一核對 C 的三訊號，**任一命中即為 C**：

- [ ] 元件目錄非空，且其中的元件有呼叫端
- [ ] 頁面直接用原生佈局排列元件
- [ ] 曾發生重疊、截斷、功能補做

三項全否才是 A。

### 情況三：A 與 B 之間猶豫

C 的三訊號在這裡判不了（兩者都沒有程式碼）。改用**來源就近原則**：有畫布、且畫布是主要來源 → B；只有規格 → A。

一律不以「哪個來源比較新」替代上述任一種判法。

## 三個不照表判的例外

上表的訊號在下列三種情形下會給出錯的答案，各有指定的處置：

| 情形 | 訊號會怎麼騙你 | 實際走哪條 |
|------|--------------|-----------|
| 專案只有路由殼與佔位元件，頁面尚未呼叫任何元件 | 「元件目錄非空」命中，看起來像 C | 走 A 或 B。路徑 C 的呼叫端回收與原生佈局掃描會全空，跑了也沒有產出 |
| 已決議整體換版，且該決策有記錄 | 存量程式碼命中 C 的三訊號 | 走 B。舊碼只供路徑 C 的事故對照與呼叫端回收當**反例**來源，契約值以畫布為準 |
| 程式碼標記為 spike 且不合入生產 | 元件目錄非空且有呼叫端，命中 C | **都不走**——依方法論的原型豁免，整個 skill 對它不適用，本規格票不存在。該原型轉正時再走 C。此時的關機判定紀錄落在做出豁免判定的那張票，不落在本規格票（本規格票還不存在） |

第三列是三者中唯一會讓本步驟終止的：前兩列改的是走哪條路徑，第三列的結論是現在不做這件事。
