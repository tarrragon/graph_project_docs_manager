# 元件庫規格範本 缺範例位置 三段鏈式範例集

> 何時讀：填寫 `templates/component-library-spec-template.md` 時，遇到範本內「範例：見本檔〈...〉」路由句，跳轉本檔對應條目。本檔依
> `.claude/skills/skill-design-guide/references/chained-examples.md` 的三段鏈式格式撰寫，服務範本中「讀者依文字約束推導可能分歧」
> 的決策點——約束本身不重述，只補校準範例。
>
> 範例採外置而非內嵌於範本，理由：範本供複製後填寫，多個決策點若逐一內嵌三段範例，複製出的規格檔會夾帶大量
> 與該專案元件無關的示範內容，須逐一手動刪除；外置後範本維持精簡，讀者按需跳轉查閱。
>
> 條目標題取自範本的位置錨點（章節與欄位名），依範本章節順序排列，供雙向對照。

## §1 形態因素矩陣

### 支援的形態：操作方式整體改變才算獨立形態

【輸入】

```
SPEC 片段（形態列）：
  支援平板（觸控或筆）與桌機（指標 + 鍵盤）兩形態；
  使用者可能為平板外接實體鍵盤
```

【產出】

```
形態：決策表

情境                                             | 操作方式是否整體改變 | 判定
平板外接鍵盤，仍以觸控為主要操作，鍵盤僅輔助      | 否                   | 仍屬平板形態
平板外接鍵盤且鍵盤成為主要輸入（如常駐鍵盤座）    | 是                   | 獨立形態
```

【驗證】

```
檢驗問句
Q 判定依據是否為「操作方式是否整體改變」而非「外接裝置是否存在」？
  預期：是——僅存在外接裝置不足以判定，須操作方式主導權轉移
Q 觸控與鍵盤同時可用但使用比例不定時如何處理？
  預期：以目前主要操作方式為準，並在形態列註記判定依據，不得留白不判定
```

### 多形態時「每形態各一份」的展開粒度

【輸入】

```
SPEC 片段：
  本專案支援桌機與手機兩形態
```

【產出】

```
形態：決策表

子節類型                                   | 展開處置
第 4 章尺寸契約／內容政策／組合規則／測試點 | 同一子節內以形態為維度新增一欄或一列，維持表格結構不變
第 5 章容器條目                             | 每形態各自一份完整容器條目（排列不變式公式本身依形態不同）
```

【驗證】

```
檢驗問句
Q 第 4 章子節是否允許整節複製成兩份平行子節？
  預期：否——範本引言「每形態各一份」指向表格內增列或增欄，非重複整節標題，
  否則每個元件的子節數會隨支援形態數等比膨脹
Q 第 5 章容器條目的展開方式與第 4 章是否相同？
  預期：不同——容器條目整份依形態各自複製，第 4 章其餘子節僅新增維度欄／列
```

### 尺寸適應策略與「換版型」是否違反禁自動切版

【輸入】

```
SPEC 片段：
  尺寸適應策略選 (b) 使用者可選版型；
  小視窗下按鈕列排列由兩欄改一欄
```

【產出】

```
形態：決策表

觸發來源                             | 是否違反 §1 禁自動切版 | §4 視窗尺寸下的行為填法
使用者於設定項手動切換版型           | 否                     | 填「換版型」，並註記依據為設定項而非視窗寬度
程式依偵測到的視窗寬度自動切換版型   | 是                     | 禁止；改填「維持」，交由容器空間不足策略（換行／捲動／收合）承接
```

【驗證】

```
檢驗問句
Q「換版型」是否只在觸發來源為使用者顯式設定時合法？
  預期：是——§4〈尺寸契約〉「{視窗尺寸 N} 下的行為」條文明寫「換版型」僅限第 1 章策略
  (b) 使用者可選版型觸發，依視窗寬度自動觸發一律違規
Q 判斷合法性時是否需回頭核對 §1「同形態內的尺寸適應策略」欄位選了哪個選項？
  預期：是，兩處必須一致——選 (a) 約束視窗尺寸者不得在 §4 填「換版型」，此為 §4 條文與 §1
  選項互相對照後的結果，非獨立判準
```

### 回饋通道子表：可用通道判定與播報替代的必填性

【輸入】

```
SPEC 片段（回饋通道子表桌機列 affordance 格待填）：
  桌機游標移到可互動元件上方會變形
```

【產出】

```
形態：決策表

通道判斷                                             | 該格填法
該形態原生具備此回饋管道                             | 填具體通道（如「游標變手形」）
該形態不具備此回饋管道但有等價替代                   | 填「不可用 + 替代：{通道}」
該形態對此回饋管道完全無等價替代                     | 不得留空；填「不可用，無替代（風險：{影響}）」
```

【驗證】

```
檢驗問句
Q 桌機是否可因具備滑鼠游標而只填「視覺」兩字了事？
  預期：否——須具體到通道形式（游標變手形／顏色變化），籠統詞不構成校準
Q 桌機是否因非觸控裝置而豁免填寫播報替代通道？
  預期：否——播報替代服務的是視覺障礙使用者而非觸控與否，桌機同樣需要填寫（範本引言已明定）
```

> 範本〈回饋通道子表〉CLI 欄現有的預填值（如「終端機回聲」「游標跳行」）為 CLI 這個固定形態的合法示範答案，
> 本條目校準的是「桌機／手機／平板」等仍需規格撰寫者自行判斷的欄位該怎麼推導，兩者不衝突。

## §2 狀態綁定模式

### 樂觀更新政策「低風險、可逆」判準

【輸入】

```
SPEC 片段（候選操作）：
  操作 A：加入購物車
  操作 B：送出訂單並扣減庫存
```

【產出】

```
形態：決策表

操作         | 是否可逆           | 是否低風險                     | 樂觀更新
加入購物車   | 可逆（隨時移除）   | 低風險（僅 UI 狀態，不扣庫存） | 允許
送出訂單     | 不易逆轉           | 高風險（涉及庫存與金流）       | 不允許，等伺服器確認
```

【驗證】

```
檢驗問句
Q 判準是否為「操作本身影響誰的資料」而非「操作發生的畫面位置」？
  預期：是——同一畫面內加入購物車與送出訂單風險等級不同
Q「低風險」與「可逆」兩條件是否須同時成立？
  預期：是，缺一即不允許樂觀更新
```

## §3 元件清單總表

### 元件與容器的「層級」（L2／L3）判定

【輸入】

```
SPEC 片段：
  元件 A 在畫面一、畫面二、畫面三各出現一次
  元件 B 只在畫面四出現，且是該業務流程的一次性排版
```

【產出】

```
形態：決策表

元件   | 出現次數     | 判定               | 層級
元件 A | 3 個畫面複用 | 通用可複用元件     | L2
元件 B | 1 個畫面單次 | 業務流程專屬排版   | L3
```

【驗證】

```
檢驗問句
Q 判準是否為「專案內複用次數」而非「是否由框架或第三方套件提供」？
  預期：是——本專案自製但被 2 個以上畫面複用者仍歸 L2
Q 只出現 1 次但預期未來會複用的元件是否可先歸 L2？
  預期：否，以目前實際複用次數判定；「預期」非機械可驗證依據，未來複用時再升級並記入變更歷史
```

## §4 逐元件規格

### 內容角色的複合角色粒度

【輸入】

```
SPEC 片段：
  情境甲：按鈕含一個垃圾桶圖示與「刪除」文字，拿掉任一個仍是同一個「刪除」動作
  情境乙：卡片同時有狀態圖示與標題文字，各自獨立傳遞不同資訊
```

【產出】

```
形態：決策表

情境                                       | 角色／slot 判定
甲：圖示與文字共同表達同一語意             | 內容角色填「動作」一項，圖示與文字為同一 slot 的複合內容
乙：圖示與文字表達不同語意                 | 內容角色填「標籤 + 動作」兩項，各自一個 slot
```

【驗證】

```
檢驗問句
Q 判準是否為「拿掉其中一半，剩下的是否仍完整表達原語意」？
  預期：是——仍完整即同一角色複合內容，不完整即兩個獨立角色
Q「動作」角色底下能否同時含圖示與文字兩個 slot？
  預期：能，複合角色的一個角色仍可對應多個實體元素，只要語意上是單一角色
```

### 變體與狀態（disabled）的分界

【輸入】

```
SPEC 片段：
  按鈕有「主要」「次要」兩種視覺樣式；
  按鈕在表單未通過驗證時會變灰且不可點擊
```

【產出】

```
形態：決策表

項目                 | 是否隨操作或資料變化而切換             | 判定
主要／次要視覺樣式   | 否，由呼叫端建立時選定，執行期不變     | 變體
變灰不可點擊         | 是，隨表單驗證結果變化                 | 狀態矩陣 disabled 狀態，非變體
```

【驗證】

```
檢驗問句
Q 變體與狀態的分界依據是否為「執行期是否會自動切換」？
  預期：是——變體建立時決定且執行期不變，狀態依條件於執行期轉換
Q「停用樣式」能否同時列為變體又列為 disabled 狀態？
  預期：否，二擇一；本例會依表單驗證結果變化，判定為狀態非變體
```

```
SPEC 片段：
  pressed 狀態，使用者放開按鍵後回到 default
```

【產出】

```
形態：契約表

狀態    | 退出路徑
pressed | 使用者放開按鍵 → default
```

【驗證】

```
檢驗問句
Q 退出路徑欄是否須同時含觸發事件與目標狀態兩部分？
  預期：是——只寫觸發事件不知道去哪，只寫目標狀態不知道被什麼觸發，缺一不完整
Q 格式是否固定為「{觸發事件} → {目標狀態}」，全表一致？
  預期：是，讀者不需要為不同列重新判讀格式
```

### 狀態矩陣「來源」欄：互動瞬態與資料態的分界（含推導值）

【輸入】

```
SPEC 片段：
  表單有三個必填欄位，未全部填寫時送出按鈕 disabled；
  前提 A：表單欄位與送出按鈕分屬不同元件，驗證結果由 store 計算並保存，供送出按鈕元件跨元件讀取
  前提 B（前提相反）：表單欄位與送出按鈕同屬一個複合元件，驗證結果只存在該元件內部、不對外暴露
```

【產出】

```
形態：決策表

情境                                                                        | 判定
disabled 直接綁定「目前是否正在按壓其他互動元件」等本地暫態                 | 互動瞬態
（前提 A）disabled 綁定「表單驗證結果」，此值由 store 計算並保存，供送出按鈕跨元件讀取 | 資料態：{表單驗證結果}
（前提 B）disabled 綁定「表單驗證結果」，但此值只存在於欄位與按鈕同屬的複合元件內部、不對外暴露 | 互動瞬態
```

【驗證】

```
檢驗問句
Q 判準是否為「值存於元件之外、可被其他元件讀取，還是僅存在於觸發它的元件內部」？
  預期：是——依範本〈狀態矩陣〉「來源」欄條文，判準看的是值的儲存位置與可讀取範圍
Q 由使用者輸入直接觸發、但透過 store 計算才回饋到 disabled 的情況（前提 A），算互動瞬態還是資料態？
  預期：資料態——依條文「推導值依其推導結果的儲存位置判定，不看最初觸發者」，此值寫入具名欄位
  供送出按鈕跨元件讀取，即使最初觸發者是使用者輸入
Q 同一題若驗證結果只存在複合元件內部、不對外暴露（前提 B），判定是否改變？
  預期：改為互動瞬態——依同一條文，此值不可被其他元件讀取，儲存位置屬元件本地
```

### 狀態矩陣「同步策略」欄判定

【輸入】

```
SPEC 片段：
  error 狀態定義為「伺服器回傳驗證失敗，欄位顯示紅框與錯誤文字」
```

【產出】

```
形態：決策表

情境                                                       | 同步策略判定
畫面先樂觀顯示成功，再收到失敗才轉為 error（回滾）         | 樂觀更新後確認
error 只在等到伺服器明確回應失敗後才顯示，過程中維持 loading | 等確認才顯示
```

【驗證】

```
檢驗問句
Q 同步策略欄的三個選項（本地即時／樂觀更新後確認／等確認才顯示）是否互斥？
  預期：是，每個狀態列只能選一個
Q 若某狀態本地生成、不涉及伺服器（如純本地格式驗證錯誤），同步策略該填哪個？
  預期：本地即時——依實際狀態來源判斷，不得機械照抄 error 列的示範值
```

【輸入】

```
  狀態矩陣已定義 disabled／loading／error／default 四狀態
```

【產出】

```
形態：契約表

事件                       | 對應狀態邊
狀態變更提示 state-change  | loading → default（成功）；loading → error（失敗）
```

【驗證】

```
檢驗問句
Q 邊的兩端狀態名是否必須逐字取自上方狀態矩陣的狀態集？
  預期：是——引用未定義的狀態名（狀態矩陣沒有的列）即違規

  預期：可以，同一事件在不同結果下可能導向不同狀態，逐條列出
```

### 回饋契約「等待與結果」四段格式：離線與服務不可用的歸類

【輸入】

```
SPEC 片段：
  情境甲：使用者送出表單時裝置離線
  情境乙：使用者送出表單時伺服器回應 500
```

【產出】

```
形態：契約表

結局             | 反應
離線（無網路連線）| 服務不可用：顯示「目前無法連線，請檢查網路後重試」，保留已輸入內容
伺服器 500       | 服務不可用：顯示「伺服器發生問題，請稍後再試」，保留已輸入內容
逾時（有連線無回應）| 逾時：顯示「回應逾時，請重試」，允許重新送出
```

【驗證】

```
檢驗問句
Q 離線是否歸類為「失敗」而非「服務不可用」？
  預期：否——判準為「問題出在使用者這端連線還是伺服器那端」，離線歸服務不可用；
  「失敗」保留給伺服器已回應且明確拒絕的情境（如驗證錯誤）
Q 成功／失敗／逾時／服務不可用四段是否必須在同一格內全部出現？
  預期：是，缺一段即視為未覆蓋失敗路徑
```

### 回饋契約「降級不解除回饋義務」的前提判定

【輸入】

```
SPEC 片段：
  網路不穩時，即時同步降級為每 30 秒批次同步一次
```

【產出】

```
形態：決策表

前提                                   | 不成立時的替代表現
資料來源（伺服器）可用但通道（即時連線）不穩 | 畫面顯示「離線暫存中，將於恢復連線後同步」標記，不佯裝即時
```

【驗證】

```
檢驗問句
Q「前提」在此指的是通道可用性還是資料來源可用性？
  預期：通道可用性——降級的對象是「同步方式」而非「資料本身是否存在」
Q 降級後的可見表現是否可以完全等同原本即時同步的畫面（讓使用者無感）？
  預期：否，必須明確標記已降級，否則使用者無法得知資料可能不是最新
```

### 回饋契約「三層回饋模型」承載層填法

【輸入】

```
SPEC 片段（三層回饋模型：第 1 層 < 100ms 動畫過渡、第 2 層 100ms-10s 進度提示、
第 3 層 > 10s 可取消或背景執行）：
  某清單載入平均耗時 3 秒
```

【產出】

```
形態：契約表

項目   | 值
承載層 | 第 2 層
反應   | 顯示載入中骨架畫面；成功：淡入內容；失敗／逾時／服務不可用：依上方四段格式
```

【驗證】

```
檢驗問句
Q 該欄是否只填「第 2 層」三個字就算完整？
  預期：否，須同時填該層對應的具體行為描述（骨架畫面等），單填層名讀者不知道該呈現什麼
Q 3 秒的耗時判定落在哪一層是否需要引用外部模型的時間門檻？
  預期：是，須對照三層回饋模型的時間帶，不可自行估計層級
```

## §7 豁免清單

### 條件 1「結構性無法收斂」的判準

【輸入】

```
SPEC 片段：
  第三方套件 A 的元件無法自訂內距，只能整體置換或不用
```

```

  預期：是，理由欄須包含已嘗試的封裝路徑，不可只寫「套件限制」帶過
```
