# skill-design-guide 版本紀錄

新到舊。版號規則與兩個住址（本檔與 `SKILL.md` frontmatter 的 `metadata.version`）見專案的 skill 同步規範。

**Version**: 1.4.0 — 新增 §6.5「拆分既有 skill」與 `references/splitting-an-existing-skill.md`。§1.2 原本只說「超標就外移」，沒說怎麼外移才不會壞——本次補上該程序，並在 §1.2 的 Action 加一句路由。

**動因是一次實測**：一份 15,015 字元的 skill 拆為八份，拆分經驗證行覆蓋 245/245、各新檔與原區間位元相同、無重複無遺漏，**而該次拆分仍引入四項嚴重缺陷**。壞掉的不是位元，是位元之間的關係——節界（`##` 是語意結構，把粗體段附到別節尾巴位元全對而少一層）、跨檔指涉（原本同檔的〈章節名〉互指變成跨檔）、共置關係（兩處矛盾的判準原本相鄰、拆後分居兩檔而可發現性下降）、外部引用（路徑級引用會斷，指名式不會）。逐行比對對這四類全部無鑑別力。

reference 另收兩類拆分特有的高頻缺陷。**內嵌計數**（「六檔」「五條」「三則」「共用兩節」）在檔數或條數改動時不會跟上，修法一律是改成不自帶計數而非把數字改對——改對的數字下次還會漂；該次實測中此類每一輪都出現。**位置性指涉**同型缺陷出現四次（末段／下段／上節／下方），其中三次由修法自身引入，最後一次寫在專為定址而設的表格裡；但同批留下的四處位置指涉全部正確且比具名好讀，故判準卡在失效條件（跨檔即失效、目標可能移動即失效）而非形態。

另收檔頭三段式（何時讀 → 同目錄 → 溯源，且「何時讀」須另列橫向入口）、路由表的「涵蓋章節」欄（文件以章節名互指而路由表以情境索引，兩軸不接時外部引用者站不到落點）、以及收尾兩步（修完掃該類不掃該處且逐條列出、整體通讀抓合成缺陷）。

**本節條文寫成後隨即套回本文件自身**（沿用 §6.4 的作法），抓到兩處：新寫的路由句自帶「四類必查、兩類缺陷、兩步收尾」等計數而 reference 內容會增減，已改為不帶計數；§13 延伸閱讀表列了另外兩份 reference 而漏第三份，已補。**寫完條文與用條文掃過自己是兩個動作**，這次的違規正是新條文本身。

**Version**: 1.3.0 — §1.2 第 2 層體量判準由行數改為字元數。原表列兩個判準「< 5k tokens（< 500 行）」而 Action 只綁行數，於是實際生效的是括號裡那個代理指標。查證官方 spec：Level 2 逐字為 "Under 5k tokens"，全篇未給任何行數限制——「< 500 行」是本地自創且未標出處的代理指標。行數對繁中散文失效，因每行字元數無上界：一份實測 skill 為 245 行（通過行數門檻）但 15,015 字元（超標 2.31 倍），最長單行 548 字。新門檻 6,500 字元 = 5k tokens × 框架既有校準係數 1.3 chars/token（`file-size-guardian-hook.py` 的 `CHARS_PER_TOKEN`，2026-06-12 以 `/context` 實測校準，非自創公式）。條文另載明本層零執法的事實（`SCAN_CONFIG` 涵蓋 pm-rules / rules / references，不含 skills；`skill-description-length-check-hook.py` 只查第 1 層 description），執法層建置與存量收斂已於消費端各建票承接。以新門檻量測一個 58 檔的 skill 庫：29 檔超標，本檔自身 15,237 字元亦在其中（2.34 倍）
