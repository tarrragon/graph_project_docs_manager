**類 1 條文未套回自身**：〈外部引用〉起手句原寫「三類例外」而底下實列四項，導致 `SKILL.md` 檢查清單「須屬三類例外之一，說不出屬於哪一類就是該改」把合規的第 4 類（hook/script 溯源）判為該改——依本 skill 自訂的「改成不自帶計數」改寫，並補「同時命中多類時取義務較嚴者」。〈拆分特有的必查項〉補第 5 列 H1 與檔名（走查判定表本就驗五項，其結論句「四個必查項就命中三個」在必查項＝4 的讀法下不自洽），表前加範圍界定（只收檔內關係，新生的檔頭與路由歸〈結構約定〉）。節界必查項的 `grep -c '^## '` 在含 fenced markdown 範例的檔上實測高估至 2.7 倍（writing-the-body 9 vs 4），且拆分前後被同等高估、前後比對仍相符使節界遺失可能通過檢查——改為排除 fenced block 的 awk 版並載明差異。「亦由此進入」補查法（線索全在別的檔案裡，從本檔內部看不到跡象）。四份 100+ 行 reference 全部補上章節清單（該要求是本 skill 自己的檢查清單第 15 項）。內嵌計數移除：「四個核心心法」、「建立流程六步」×3、測試方法三個並列類型的序號。

**兩項對外查證推翻了既有寫法，其中一項是 v1.3.0 自己寫錯的**：

其一，v1.3.0 寫「官方全篇未給任何行數限制——行數門檻是本地代理指標，已於下方廢止」。**此句為誤**。官方文件有兩頁，v1.3.0 只讀了 overview（該頁確實只有 "Under 5k tokens"），而 best-practices 頁三處寫「Keep SKILL.md body under 500 lines」（Progressive disclosure patterns、Token budgets、Checklist）。**兩個門檻都是官方值**，互補而非互相取代：tokens 是真正成本，行數是它在英文內容下的可靠代理。已改為兩者皆量、任一超標即外移。此錯誤與本框架記錄過的「截斷後下全稱結論」同型——從部分來源推出「官方全篇」，而截斷至少留下線索，「只讀了兩頁中的一頁」沒有。

其二，§1.2 的 6,500 字元門檻沿用 `CHARS_PER_TOKEN = 1.3`，而該常數的原始碼註解逐字寫「**繁中為主集合**」。v1.3.0 引用它作為「不自創公式」的依據卻未問適用條件。實測一份 100% ASCII、7,584 字元的 skill 依此判超標，實際約 1,896 tokens ＝ 官方預算的 38%。已改為附語言換算表（繁中 1.3／英文約 4），並明令不可無條件套用。

**§3.1 的額外檔案禁令查證後大幅收窄**：官方 best-practices **未禁止**任何額外檔案，且立場相反——「Reference files, data, or documentation don't consume context tokens until actually read」「no context penalty until accessed」，其示範目錄即為 SKILL.md 與多份 md 平鋪。原條給的理由「每多一個檔案就增加 Claude 讀檔判斷成本」是本地發明且與官方明文相反。已改寫為本地判斷、理由改為目錄辨識成本、適用範圍收窄至「AI 不會讀到的檔案」，並把 `CHANGELOG.md` 移出禁止之列——本專案的 skill 走 git 同步且有跨 consumer 版號協定，它是該協定的載體（全庫 59 個 skill 有 58 個帶著它）。§12 檢查清單同步。

**其餘嚴重項**：§1.1 的 Why 有半個機制不成立（原寫「body 排擠其他 skill 的 description budget」，而 body 只在觸發後載入，不影響他人），已改為兩層各自的成本機制；§6.4 列三類例外而 §12 檢查清單寫「兩類」，已對齊並改為指名而非 §編號；§6.4 的示範引用「`tdd` skill 的分層測試策略」在對方 SKILL.md 查無路由，已換為可達者並補一句「指到某一節時該節須在對方路由中可找到」；§6.4 補第四類例外——hook 與 script 無法以名字載入，路徑是唯一可行的指名方式，原三類例外未涵蓋；本檔 description 382 字元違反自訂的 250 上限，已壓至 237，並統一「字／字元」單位、補量測指令與執法 hook 名；§13 末列「Skill Marketplace 標準」為死名，已改為實際標題；`patterns-and-troubleshooting.md` 的「低於 5,000 字」與 §1.2 衝突，已改為指向門檻節。

**補三節範例**（reviewer 判定為純判準零樣本，且是判斷難度最高、後果最不可逆的三處）：§1.3 補「同一任務寫成三種自由度」的並列對照並補上中自由度的判準（原判準二分而表格三列，中層不可達）；§1.4 補一則完整走查，對象取本 skill 自己的 §1.2 門檻缺陷；§6.5 的範例放進 `splitting-an-existing-skill.md`，為一則十行的最小走查——兩節、一次搬移，四個必查項命中三個，而行覆蓋與位元比對對這三項全部回報通過。

**動因是一次實測**：一份 15,015 字元的 skill 拆為八份，拆分經驗證行覆蓋 245/245、各新檔與原區間位元相同、無重複無遺漏，**而該次拆分仍引入四項嚴重缺陷**。壞掉的不是位元，是位元之間的關係——節界（`##` 是語意結構，把粗體段附到別節尾巴位元全對而少一層）、跨檔指涉（原本同檔的〈章節名〉互指變成跨檔）、共置關係（兩處矛盾的判準原本相鄰、拆後分居兩檔而可發現性下降）、外部引用（路徑級引用會斷，指名式不會）。逐行比對對這四類全部無鑑別力。

reference 另收兩類拆分特有的高頻缺陷。**內嵌計數**（「六檔」「五條」「三則」「共用兩節」）在檔數或條數改動時不會跟上，修法一律是改成不自帶計數而非把數字改對——改對的數字下次還會漂；該次實測中此類每一輪都出現。**位置性指涉**同型缺陷出現四次（末段／下段／上節／下方），其中三次由修法自身引入，最後一次寫在專為定址而設的表格裡；但同批留下的四處位置指涉全部正確且比具名好讀，故判準卡在失效條件（跨檔即失效、目標可能移動即失效）而非形態。

另收檔頭三段式（何時讀 → 同目錄 → 溯源，且「何時讀」須另列橫向入口）、路由表的「涵蓋章節」欄（文件以章節名互指而路由表以情境索引，兩軸不接時外部引用者站不到落點）、以及收尾兩步（修完掃該類不掃該處且逐條列出、整體通讀抓合成缺陷）。
