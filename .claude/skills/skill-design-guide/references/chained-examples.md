# Chained Examples 三段鏈式範例規格

> 何時讀：`SKILL.md`〈按需讀取〉路由表對應列——設計某個 skill 的範例、或判斷某處文字約束是否需要配範例時。本檔定義固定的三段範例格式與「何處需要範例」的機械判準，供多份審查／走查子票共用同一套格式，避免各自發明。

本檔章節：〈三段鏈式格式〉〈各段允許與禁止內容〉〈「何處需要範例」判準〉〈「缺範例」與「缺引導」的分界〉〈完整示範〉〈語言專屬 skill 的例外：違規／修正程式碼對照〉〈與既有範例規格的相容判定〉。

> 補範例後若使該檔超出體量門檻，處置見 `splitting-an-existing-skill.md`〈補範例後超標：觸發條件與處置順序〉——門檻是為了避免認知超載，不得以刪範例或壓縮規則文字達標。

## 三段鏈式格式

範例固定分三段，段名與標記固定，三段皆不可省略：

| 段 | 標記 | 回答的問題 |
|----|------|-----------|
| 輸入 | 【輸入】 | 讀者手上拿到的原始素材是什麼 |
| 產出 | 【產出】 | 依文字約束應產出的具體形態是什麼 |
| 驗證 | 【驗證】 | 怎麼判斷產出是對的 |

**Why**：範例形態若不先固定，各審查者會各自發明格式，產出物彼此無法比對、也無法彙整成單一報告。三段對應校準三個獨立面向——輸入決定範例起點是否語言中立、產出決定讀者要交付的形態、驗證決定怎麼判斷交付物合格；三者混寫會讓某一面向的違規被另外兩面向的正確內容掩蓋，讀者看不出問題出在哪一段。

**Consequence**：省略任一段，範例就只校準了部分行為——只給輸入與產出而無驗證，讀者知道要交付什麼形態卻不知道怎麼判斷自己做對了；只給產出與驗證而無輸入，讀者不知道這個產出物對應的原始情境，無法類推到自己手上的其他情境。

**Action**：任何需要範例的位置，三段都要寫全，順序固定為輸入先於產出、產出先於驗證。

**跨技術中立性**：本格式服務的 skill 涵蓋任何能建構畫面的技術（如以標記語言與樣式表建構的頁面、或以宣告式 UI 框架建構的頁面），三段皆不得預設讀者使用哪一種技術。判斷方法見下節。

## 各段允許與禁止內容

**判準只有一條，三段共用**：把段落內容換成另一種建構畫面的技術時，這段文字要不要跟著改？要改，即代表混入了技術相依內容，違規。

### 【輸入】段

| 允許 | 禁止 |
|------|------|
| 自然語言描述的 spec 片段（需求文字、規格表格的一列或數列） | 任何程式碼片段或程式語法（條件式、迴圈、宣告） |
| 抽象化的資料事實（如「清單來源回傳的項目數為零」） | 具體 UI 框架的元件類別名或屬性名 |
| 狀態、數量、條件等語言中立的描述詞 | 已預設實作路徑的敘述（如「呼叫某函式後」「掛載某元件後」） |

**Consequence**：輸入段一旦混入框架相依內容，讀者會誤以為範例只適用某一種建構畫面的技術，該範例對使用其餘技術的讀者即失去校準作用。

### 【產出】段

產出物只能是下列三種形態之一：

| 形態 | 內容 |
|------|------|
| 契約表 | 欄位名加值的表格，欄位名取自受管詞彙（如語意、變體、狀態集），不得是框架 API 名 |
| ASCII 線框 | 純文字字元組成的版面示意圖，不含任何框架特定標記；只需表達選件與排位時可用組合樹記法 `容器[子件, 子件]`，名稱取規格內的元件名 |
| 決策表 | 條件欄加動作欄的對照表 |

| 允許 | 禁止 |
|------|------|
| 中性名詞描述畫面元素（如「按鈕」「訊息文字」「圖示」） | 框架特定的元件寫法（如標記語言的元素標籤、宣告式框架的元件建構式） |
| 欄位表述用受管詞彙（尺寸、內容政策、狀態集等） | 框架特定屬性或參數名稱（如事件處理器的具體命名、樣式屬性的框架寫法） |
| 決策表的條件欄用可觀測事實 | 任何一種程式語言的語法片段，含標記語言 |

**Consequence**：產出段寫入框架特定寫法，等於把「校準文字約束」的範例做成了另一種技術的實作規格，使用其他技術的讀者需自行翻譯，違背本格式跨技術中立的目的。

### 【驗證】段

已知風險：驗證段最容易滑向框架測試 API。

**驗證段依【產出】段的產出類型分兩種形態**，先判定屬哪一種，再套用對應格式。兩種形態皆不得出現框架 API、選擇器語法或任何程式語言的程式碼寫法；元件的測試驗證仍以 Given/When/Then 為主形態（多數元件產出屬執行期行為）。

**判定規則**：看【產出】段的產出物是否會在執行期被實際渲染或操作——讀者能不能「啟動它、看它動」。

| 產出類型 | 判定依據 | 驗證段形態 |
|---|---|---|
| 執行期行為 | 產出物是元件在畫面上的實際表現、狀態轉換或操作結果 | Given/When/Then |
| 設計產出物 | 產出物是契約表、候選判定、起點判定、token 表等靜態文件，不存在「啟動它」這個動作 | 檢驗問句 + 預期答案 |

**執行期行為形態**：

| 允許 | 禁止 |
|------|------|
| Given/When/Then 三段式描述 | 框架測試 API 的具體方法名或選擇器語法 |
| 使用者可觀測的事實（畫面顯示了什麼、可操作什麼） | 程式語法（賦值、條件式、迴圈的程式碼寫法） |
| 直接引用【產出】段契約表已定義的欄位名（如「狀態」「內容政策」） | 框架事件 handler 的具體命名 |

範例：

```
Given 清單來源查詢逾時
When  畫面渲染完成
Then  主區只含逾時提示，不含清單容器
```

**設計產出物形態**：「檢驗問句」逐條列出，每條問句對應一個【產出】段已寫出的判定或欄位，並附「預期答案」；預期答案錯誤即代表產出物不合格。

| 允許 | 禁止 |
|------|------|
| 檢驗問句直接引用【產出】段已定義的欄位名或判定結果 | 框架 API、任何程式語言的程式語法 |
| 預期答案為封閉選項（是／否、欄位值本身） | 需要讀者再次主觀判讀的開放式預期答案 |
| 問句含反向檢查（如「理由欄是否引用了不該引用的依據」） | 對執行期行為的描述（此形態的產出物不會被渲染） |

範例：

```
【輸入】狀態表：空狀態 6 列、阻擋狀態 3 列，外觀相近
【產出】元件候選表
  候選名   | 判定         | 理由
  空狀態   | 不與阻擋合併 | 退出路徑層級：留在畫面內（開啟新增）
  阻擋狀態 | 不與空合併   | 退出路徑層級：離開專案（切換專案）
【驗證】檢驗問句
  Q 兩個候選的退出路徑層級是否相同？   預期：不同 → 不合併
  Q 理由欄是否以層級而非目的地表述？   預期：是（只寫目的地即判錯；層級相同而目的地不同者為 slot，不拆）
  Q 理由欄是否引用外觀？               預期：否（引用外觀即判錯）
```

**Action**：驗證段寫完後自我檢查一次——先確認本段產出物屬執行期行為或設計產出物，再依對應表逐句核對；出現任何工具或框架的專有名詞，一律改寫成該形態允許的等價敘述。

## 「何處需要範例」判準

**核心判準**：讀者只讀文字約束（不看任何範例）時，針對同一份輸入，是否可能產出兩種以上不同的結果。是，即需要範例；否，不需要。核心判準的執行方式是**模擬分歧**——設想兩位讀者各自依文字約束推導結果，比對兩人的產出是否可能不同；判準檢驗的是「推導結果會不會分岔」，不是「文字裡有沒有特定詞彙」。

**機械套用步驟**：

1. 取出該處要驗收的文字（規則句、schema 欄位定義句、判準描述句）。
2. 設想兩位讀者，兩人皆已讀過該文字約束、皆未讀過任何範例，面對同一份輸入各自產出結果。
3. 分別寫出兩位讀者各自的推導過程與結果，逐項比對是否可能不同。
4. 可能不同 → 命中，需要範例。
5. 無論怎麼推導兩人結果必然一致（已是封閉列舉、固定公式、唯一映射）→ 未命中，不需要範例。

**輔助訊號（用於快速篩查，不是判準本身）**：文字含「相近」「合理」「必要」「一致」「適當」等需主觀判讀而未配機械公式或封閉列舉的詞，是分歧的常見來源之一。**但分歧不限於此**——下列類型常無任何模糊詞仍會命中，只查詞彙表會系統性漏掉它們：

| 分歧來源類型 | 說明 |
|---|---|
| 粒度 | 表格該分幾列、切分深淺無共識 |
| 方向 | 誰依附誰、誰優先於誰，文字只給規則沒給方向基準 |
| 規則交界 | 兩條規則同時成立時何者優先，文字未言明 |
| 術語定義在別處 | 文字用了一個關鍵詞但定義不在同一段落，兩讀者各自代入不同定義 |
| 空間排列 | 版面元素的相對位置文字只描述功能不描述位置 |

遇到上述類型，詞彙表篩查會判「未命中」，此時仍須執行機械套用步驟第 2–3 步（模擬兩位讀者的實際推導），不可因詞彙表未命中就直接判定不需要範例。

| | 正例一（命中，含模糊詞） | 正例二（命中，無模糊詞——規則交界類型） | 反例（未命中，不需要範例） |
|---|---|---|---|
| 判準文字 | 「兩個候選是否算同一元件，由使用者預期能做什麼決定；外觀相近不構成合併理由」 | 「當清單同時符合兩條篩選規則時，以規則定義順序在後者為準」 | 「欄位若標記為必填，呼叫端必須提供值；未標記則為選填」 |
| 判讀空間 | 「使用者預期能做什麼」需要讀者對輸入情境做主觀解讀，兩人對同一輸入可能讀出不同的使用者預期 | 文字本身無模糊詞，但「規則定義順序」的依據未言明（文件章節順序？規則建立時間？），兩位讀者各自代入不同基準 | 必填／選填是二元列舉，值只有兩種、對應動作固定，讀者不需要解讀 |
| 結論 | 命中：兩讀者可能一個判定歸併、一個判定不歸併，產出分岔，需要範例校準判讀 | 命中：兩讀者依不同基準排序，結果分岔；詞彙表在此無效，唯有模擬分歧才能查出 | 未命中：兩讀者的產出必然一致，範例不會改變任何人的行為 |

**Consequence**：判準若不機械化，「需要範例」會退化為審查者的個人品味，等於繞回本規格原本要解決的問題；而若機械化退化為只查模糊詞，會系統性低報「粒度」「方向」「規則交界」「術語定義在別處」「空間排列」這五類無模糊詞仍分歧的判準——它們往往涉及多個決策點交互，範例校準的價值最高卻最容易被詞彙表漏掉。

## 「缺範例」與「缺引導」的分界

審查子票在應用上一節判準時，若命中「兩位讀者可能分歧」，還須進一步分辨分歧的成因，因為兩種成因的處置方式不同：

| 成因 | 判定方式 | 處置 |
|---|---|---|
| 缺範例 | 該決策點**已有**文字約束（規則句、schema 欄位定義句），但約束本身允許分歧 | 依本規格補三段鏈式範例 |
| 缺引導 | 該決策點**根本沒有**任何文字約束——讀者必須自行發明規則才能產出結果 | 範例補不了，須先補文字約束，再視新約束是否仍命中判準決定要不要配範例 |

**判定順序**：先問「這個決策點有沒有文字約束存在」，答「沒有」直接判為缺引導，不需再跑〈「何處需要範例」判準〉的機械步驟（判準的前提是「讀者已讀過文字約束」，約束不存在時判準無對象可套用）。答「有」才進入判準機械步驟，判準命中即為缺範例。

**Consequence**：若不分界，審查子票會把「缺引導」誤判為「缺範例」而只補了範例——範例是校準既有文字約束的工具，沒有約束可校準時，補的範例只是審查者自己發明的規則，換一個審查者會發明另一套，問題原封不動。

**Action**：審查報告中，每一個命中位置須先標「缺範例」或「缺引導」；缺引導的位置額外附上建議的文字約束草稿供 PM 裁決，不可直接以範例代替文字約束。

## 完整示範

情境：一個清單頁，依資料來源狀態呈現不同畫面樣貌。以下只示範其中一種狀態（清單來源逾時無法讀取），驗證段的判定屬「執行期行為」（見〈各段允許與禁止內容〉【驗證】段的判定規則）。

【輸入】

```
SPEC 片段（狀態表一列）：
  清單來源逾時 | 顯示逾時提示 | 可操作：重新查詢
```

【產出】

```
形態：契約表 + ASCII 線框

元件：逾時提示
  欄位     | 值
  ---------|--------------------------------------------
  語意     | 告知使用者清單來源逾時無法讀取
  變體     | default
  狀態     | 逾時
  尺寸     | 依容器寬度延展，最小寬度 240px
  內容政策 | 訊息文字 可換行=是 最大2行；按鈕文字不換行

+--------------------------+
|  (icon)                  |
|  查詢逾時，請重新嘗試    |
|  [ 重新查詢 ]            |
+--------------------------+
```

【驗證】

```
Given 清單來源查詢逾時
When  畫面渲染完成
Then  主區只含逾時提示，不含清單容器
And   最長文案下訊息文字最多 2 行、按鈕文字不換行，且兩者皆不超出元件邊界
```

**逐段核對**（示範如何用上一節的允許／禁止表自我檢查）：

| 段 | 是否符合本規格 | 理由 |
|----|--------------|------|
| 輸入 | 符合 | 只有規格文字與抽象狀態，未指名任何框架；標籤與【產出】段元件名一致（逾時提示），無命名漂移 |
| 產出 | 符合 | 契約表為多欄位表格（語意、變體、狀態、尺寸、內容政策），欄位名皆受管詞彙，非單一行內容政策；ASCII 線框不含框架標記 |
| 驗證 | 符合 | 全句使用者可觀測事實加上【產出】段既有欄位名（內容政策），未引入輸入未定義的狀態轉換；訊息與按鈕各自對照契約表內容政策欄的對應值（訊息最大 2 行、按鈕文字不換行），不把按鈕溢位錯掛到訊息文字的換行政策，也不驗證契約表未定義的屬性 |

## 語言專屬 skill 的例外：違規／修正程式碼對照

〈各段允許與禁止內容〉的程式碼語法禁令，服務的是「同一份規格文字要能套用到任何建構畫面技術」這個情境（見〈三段鏈式格式〉「跨技術中立性」）。有一類 skill 從一開始就不追求這個中立——它只服務單一程式語言或框架，內含的「違規程式碼／修正程式碼」對照，功能是讓讀者拿自己手上的程式碼去比對是否命中某條靜態掃描規則，並查出對應修正寫法。這類對照不是三段鏈式格式要校準的「規格範例」，而是查表工具本身；查表工具的比對對象就是程式碼語法，禁止程式碼語法會讓查表功能失效。

**判定條件（三項全部成立才適用本例外，缺一即不適用，仍須完整套用三段鏈式格式與程式碼語法禁令）**：

| 條件 | 說明 |
|------|------|
| 1. 單一技術定位 | 該 skill 的 SKILL.md 開頭定位句或 frontmatter description 明確宣告只服務單一程式語言或單一框架，不含「涵蓋任何建構畫面的技術」一類跨技術中立聲明 |
| 2. 查表用途 | 該處對照的作用是讀者拿具體程式碼比對是否命中某條既有的靜態掃描規則、並查出對應修正寫法，不是在教讀者從語言中立的規格描述推導產出物 |
| 3. 語言一致 | 對照中的違規碼與修正碼使用同一種語言／框架語法，且與條件 1 宣告服務的語言／框架一致，不得夾雜其他技術寫法 |

**Consequence**：不區分會導致兩種相反的損害——對語言專屬 skill 的查表對照硬套語言中立禁令，查表工具會被拆成讀者無法比對自身程式碼的抽象描述，查表功能失效；反之若放寬本例外時不附判定條件，任何 skill（包含本應保持跨技術中立者）都能援引它夾帶框架特定寫法混入範例，使該範例對其他技術的讀者失效，回到本規格原本要防止的問題。

**Action**：三項條件同時成立時，該 skill 內的違規／修正程式碼對照可用「Violation／Fix」或等義的兩欄對照呈現，跳過【輸入】【產出】【驗證】三段鏈式格式與各段程式碼語法禁令；缺任一條件則仍需完整套用本規格。

## 與既有範例規格的相容判定

`component-contract-design` skill 的既有範例附錄已有三類既有內容：〈Examples〉〈正例〉〈Troubleshooting〉，用途分別是：

| 既有類別 | 用途 |
|---------|------|
| Examples | 校準單一步驟產出物的粒度（輸入到該步驟產出物的兩欄對照，不含獨立驗證段） |
| 正例 | 貫穿情境示範元件契約欄位填滿的樣子（含測試契約欄，以「填寫格式」而非 Given/When/Then 呈現） |
| Troubleshooting | 症狀對成因對處置的表格 |

**本規格不預先豁免任何既有範例。** 上述三類既有內容現況皆不含本規格要求的三段鏈式格式（尤其欠缺獨立【驗證】段）——依〈三段鏈式格式〉「三段皆不可省略」的要求，三類既有內容現況皆不合規；但是否需要改寫、改寫到什麼程度、或維持現狀，屬於個別 skill 依其自身讀者情境的範疇判斷，本規格不代為預先下結論。

**處置移交審查子票**：`component-contract-design` 既有範例的處置（合格／需改寫／應刪除）由該 skill 的審查子票依本規格逐則判定，判定時須說明理由（例如：該範例的讀者情境是否確實不需要獨立驗證段、或只是尚未補上）。本規格不代審查子票下結論，避免與該 skill 審查子票的 acceptance 產生相反指示。
