# Chained Examples 三段鏈式範例規格

> 何時讀：`SKILL.md`〈按需讀取〉路由表對應列——設計某個 skill 的範例、或判斷某處文字約束是否需要配範例時。本檔定義固定的三段範例格式與「何處需要範例」的機械判準，供多份審查／走查子票共用同一套格式，避免各自發明。

本檔章節：〈三段鏈式格式〉〈各段允許與禁止內容〉〈「何處需要範例」判準〉〈完整示範〉〈與既有範例規格的相容判定〉。

## 三段鏈式格式

範例固定分三段，段名與標記固定，三段皆不可省略：

| 段 | 標記 | 回答的問題 |
|----|------|-----------|
| 輸入 | 【輸入】 | 讀者手上拿到的原始素材是什麼 |
| 產出 | 【產出】 | 依文字約束應產出的具體形態是什麼 |
| 驗證 | 【驗證】 | 怎麼判斷產出是對的 |

**Why**：範例形態若不先固定，各審查者會各自發明格式，產出物彼此無法比對、也無法彙整成單一報告。三段對應校準三個獨立面向——輸入決定範例起點是否語言中立、產出決定讀者要交付的形態、驗證決定怎麼判斷交付物合格；三者混寫會讓某一面向的違規被另外兩面向的正確內容掩蓋，讀者看不出問題出在哪一段。

**Consequence**：省略任一段，範例就只校準了部分行為——只給輸入與產出而無驗證，讀者知道要交付什麼形態卻不知道怎麼判斷自己做對了；只給產出與驗證而無輸入，讀者不知道這個產出物對應的原始情境，無法類推到自己手上的其他情境。

**Action**：任何需要範例的位置，三段都要寫全，順序固定為輸入先於產出、產出先於驗證。

**跨技術中立性**：本格式服務的 skill 涵蓋任何能建構畫面的技術（如以標記語言與樣式表建構的頁面、或以宣告式 UI 框架建構的頁面），三段皆不得預設讀者使用哪一種技術。判斷方法見下節。

## 各段允許與禁止內容

**判準只有一條，三段共用**：把段落內容換成另一種建構畫面的技術時，這段文字要不要跟著改？要改，即代表混入了技術相依內容，違規。

### 【輸入】段

| 允許 | 禁止 |
|------|------|
| 自然語言描述的 spec 片段（需求文字、規格表格的一列或數列） | 任何程式碼片段或程式語法（條件式、迴圈、宣告） |
| 抽象化的資料事實（如「清單來源回傳的項目數為零」） | 具體 UI 框架的元件類別名或屬性名 |
| 狀態、數量、條件等語言中立的描述詞 | 已預設實作路徑的敘述（如「呼叫某函式後」「掛載某元件後」） |

**Consequence**：輸入段一旦混入框架相依內容，讀者會誤以為範例只適用某一種建構畫面的技術，該範例對使用其餘技術的讀者即失去校準作用。

### 【產出】段

產出物只能是下列三種形態之一：

| 形態 | 內容 |
|------|------|
| 契約表 | 欄位名加值的表格，欄位名取自受管詞彙（如語意、變體、狀態集），不得是框架 API 名 |
| ASCII 線框 | 純文字字元組成的版面示意圖，不含任何框架特定標記 |
| 決策表 | 條件欄加動作欄的對照表 |

| 允許 | 禁止 |
|------|------|
| 中性名詞描述畫面元素（如「按鈕」「訊息文字」「圖示」） | 框架特定的元件寫法（如標記語言的元素標籤、宣告式框架的元件建構式） |
| 欄位表述用受管詞彙（尺寸、內容政策、狀態集等） | 框架特定屬性或參數名稱（如事件處理器的具體命名、樣式屬性的框架寫法） |
| 決策表的條件欄用可觀測事實 | 任何一種程式語言的語法片段，含標記語言 |

**Consequence**：產出段寫入框架特定寫法，等於把「校準文字約束」的範例做成了另一種技術的實作規格，使用其他技術的讀者需自行翻譯，違背本格式跨技術中立的目的。

### 【驗證】段

已知風險（Context Bundle 標記）：驗證段最容易滑向框架測試 API。

| 允許 | 禁止 |
|------|------|
| Given/When/Then 三段式描述 | 框架測試 API 的具體方法名或選擇器語法 |
| 使用者可觀測的事實（畫面顯示了什麼、可操作什麼） | 程式語法（賦值、條件式、迴圈的程式碼寫法） |
| 直接引用【產出】段契約表已定義的欄位名（如「狀態」「內容政策」） | 框架事件 handler 的具體命名 |

**Action**：驗證段寫完後自我檢查一次——每一句是否只用了「使用者看到／能做什麼」與【產出】段既有的欄位名；出現任何工具或框架的專有名詞，一律改寫成使用者可觀測的等價敘述。

## 「何處需要範例」判準

**核心判準**：讀者只讀文字約束（不看任何範例）時，針對同一份輸入，是否可能產出兩種以上不同的結果。是，即需要範例；否，不需要。

**機械套用步驟**：

1. 取出該處要驗收的文字（規則句、schema 欄位定義句、判準描述句）。
2. 設想兩位讀者，兩人皆已讀過該文字約束、皆未讀過任何範例，面對同一份輸入各自產出結果。
3. 檢查文字裡是否含有需要主觀判讀而未配上機械公式或封閉列舉的詞（如「相近」「合理」「必要」「一致」「適當」）。
4. 含有這類詞 → 兩位讀者的產出可能分歧 → 命中，需要範例。
5. 不含（已是封閉列舉、固定公式、唯一映射）→ 未命中，不需要範例。

| | 正例（命中，需要範例） | 反例（未命中，不需要範例） |
|---|----------------------|--------------------------|
| 判準文字 | 「兩個候選是否算同一元件，由使用者預期能做什麼決定；外觀相近不構成合併理由」 | 「欄位若標記為必填，呼叫端必須提供值；未標記則為選填」 |
| 判讀空間 | 「使用者預期能做什麼」需要讀者對輸入情境做主觀解讀，兩人對同一輸入可能讀出不同的使用者預期 | 必填／選填是二元列舉，值只有兩種、對應動作固定，讀者不需要解讀 |
| 結論 | 命中：兩讀者可能一個判定歸併、一個判定不歸併，產出分岔，需要範例校準判讀 | 未命中：兩讀者的產出必然一致，範例不會改變任何人的行為 |

**Consequence**：判準若不機械化，「需要範例」會退化為審查者的個人品味——同一份文字，甲審查者覺得夠清楚不需範例，乙審查者覺得模糊而各自產出不同格式的補充說明，等於繞回本規格原本要解決的問題。

## 完整示範

情境：一個清單頁，依資料來源狀態呈現不同畫面樣貌。以下只示範其中一種狀態（清單來源逾時無法讀取）。

【輸入】

```
SPEC 片段（狀態表一列）：
  清單來源逾時 | 顯示重試提示 | 可操作：重新查詢
```

【產出】

```
形態：契約表 + ASCII 線框

元件：逾時提示 variant=default
+--------------------------+
|  (icon)                  |
|  查詢逾時，請重新嘗試    |
|  [ 重新查詢 ]            |
+--------------------------+
內容政策：訊息 可換行=是 最大2行
```

【驗證】

```
Given 清單來源查詢逾時
When  畫面渲染完成
Then  主區只含逾時提示，不含清單容器
And   點擊「重新查詢」後，畫面回到載入中狀態
And   最長文案下按鈕不被擠出容器（內容政策：可換行）
```

**逐段核對**（示範如何用上一節的允許／禁止表自我檢查）：

| 段 | 是否符合本規格 | 理由 |
|----|--------------|------|
| 輸入 | 符合 | 只有規格文字與抽象狀態，未指名任何框架 |
| 產出 | 符合 | 契約表欄位（元件、變體、內容政策）皆受管詞彙；ASCII 線框不含框架標記 |
| 驗證 | 符合 | 全句使用者可觀測事實加上【產出】段既有欄位名（內容政策），未出現任何測試 API 或程式語法 |

## 與既有範例規格的相容判定

`component-contract-design` skill 的既有範例附錄已有三類既有內容：〈Examples〉〈正例〉〈Troubleshooting〉。判定如下：

| 既有類別 | 用途 | 與本規格的關係 |
|---------|------|--------------|
| Examples | 校準單一步驟產出物的粒度（輸入到該步驟產出物的兩欄對照，不含獨立驗證段） | 範疇不重疊：服務單一 skill 內部的步驟粒度校準，不含【驗證】層 |
| 正例 | 貫穿情境示範元件契約欄位填滿的樣子（含測試契約欄，以「填寫格式」而非 Given/When/Then 呈現） | 範疇不重疊：驗收依據是契約欄位是否填滿，不是使用者可觀測行為的三段式驗證 |
| Troubleshooting | 症狀對成因對處置的表格 | 與範例格式無關 |

**判定：相容並存，不遷移。** 既有範例附錄服務 `component-contract-design` 這一個 skill 的步驟型工作流校準，讀者是正在填寫元件契約表的人；本規格服務多個 skill 共用的「文字約束是否需要範例」判準與呈現格式，讀者是需要為審查／走查子票配範例的任何人。兩者的產出物形態與驗收依據都不同，不構成同一件事的兩種寫法，不需互相取代或遷移，既有範例附錄維持現狀不變。
