# 命名是分類的驗證程序

> **角色**：methodology。適用於任何「先有一批觀察值、要凍結成一套分類」的工作。
>
> **何時讀**：把一組觀察到的值整理成分類之前（design token、enum、error code、event 型別、欄位群、目錄結構、標籤體系）；或手上已經有一份分類、要判斷它可不可信。

## 核心主張

一份分類可不可信，取決於它有沒有經過一道**錯的時候會長得不一樣**的程序。

分類寫在規格裡的時候，對的版本跟錯的版本外觀相同——都是一列標著角色的表格。沒有任何東西會因為它錯了而改變外觀，所以它不會被發現。逐一命名改變這件事：它把「這四個值屬於同一個序列」這種看不出對錯的宣稱，改寫成四個各自可被指認為錯的斷言。

這條主張同時給出這套方法的適用邊界跟它的失效點。往下三節談命名怎麼做到，第六節談它做不到的部分。

## 命名能驗證分類的條件

### 個別化：移除集合標籤的遮蔽

規格裡可以寫「表面層次」而不必知道它是什麼。給四個值各取一個名字則做不到——取名的人必須先查每個值實際承擔什麼角色。

集合標籤把 N 個宣稱壓成一個，而那一個宣稱的真值條件模糊到無法解決。個別化把它還原成 N 個各自要面對的問題。

### 語意內容：名字要能被指認為錯

`surfaceSegmentTrack` 斷言「這個色是分段控制元件的軌道底」，讀者拿著畫面就能判定它對不對。`surface4` 只斷言「它是清單裡第四個」，而這件事由列舉這個動作本身保證為真。

序號式命名完成了個別化，卻沒有可否證的內容，驗證力歸零。判斷標準是一句話：**一個讀者只拿著這個名字跟成品，看不看得出它錯了。** 看不出來的話，命名這一步只是儀式。

### 對照來源：真值條件要能在規格之外解決

名字的對錯回設計檔判定，不回規格判定——規格是衍生物，也正是待驗的對象。規格與設計檔不符時以設計檔為準，並回頭更新規格。

這一條解釋了為什麼命名比審查規格有效：審查規格的人手上只有規格，而規格的每一列都自洽。

## 帶順序詞的集合標籤會規定下一個成員怎麼命名

「表面層次」這個標籤裡的「層次」斷言了一個順序。四個值加一個順序詞等於一個隱含宣稱：它們構成一道明度階。

這個宣稱會外溢到三個地方——API 的形狀（`surface1` 到 `surface4`）、擴充規則（下一個淺灰綠色自動變成 `surface5`）、以及任何據此推理對比度的人。假分類不只是錯的，它還規定了後續成員該怎麼被命名，於是每個新成員都繼承同一個錯誤。

所以在命名這一步攔下它的收益高於表面看起來的樣子：攔下的是一列表格，避免的是一整條擴充路徑。

## 三層結構：每層記錄什麼，就是那層的憑證

| 層       | 回答             | 可見性   | 記錄什麼            | 憑證                   |
| -------- | ---------------- | -------- | ------------------- | ---------------------- |
| 原始值層 | 這個值是多少     | 私有     | 值 + 出現次數       | 次數是它作為觀察的憑證 |
| 語意層   | 這個值代表什麼   | 公開     | 語意名 → 原始值名   | 對照設計檔的實際用途   |
| 元件層   | 這個元件用哪個   | 元件檔內 | 元件角色 → 語意名   | 元件自身               |

語意層不記出現次數，因為次數不會讓一個定義為真。把次數帶進語意層等於把觀察混進定義——而「四個色出現次數相近、外觀也相近，所以是同一組」正是假分類的成因。

三條配套約束讓分層有效：畫面只引用語意層與元件層；原始值層是全專案唯一允許出現裸值的位置；每個語意名可回溯到原始值層的某個名字，映射逐條列在檔頭。

## 讓規則執行，而不是請求遵守

那份規格在同一張表裡寫了自我警告（角色欄是觀察不是定義、命名時須確認每個值實際承擔的語意），然後在那張表裡犯了它警告的錯。

對照這次真正攔下違規的三個機制：

| 規則                     | 載體                        | 執行者               |
| ------------------------ | --------------------------- | -------------------- |
| 畫面不得引用原始值層     | `private` 修飾字            | 編譯器               |
| 裸值只准出現在原始值層   | 行內豁免標記 + linter       | 工具                 |
| 每個值要有自己的語意     | 逐一命名這個動作            | 程序（做完就查過了） |
| 角色欄要查證、不要推定   | 規格裡的一段話              | 無                   |

行內豁免標記的做法是在唯一允許出現裸值的每一行標上一個固定字串，於是「其他位置出現裸值即違規」成為 linter 讀得懂的檢查。**例外能被機械辨識，禁令才有辦法自動執行**；例外只寫在文件裡的話，禁令也只能停在文件裡。

## 邊界：可回溯不等於已驗證

三層結構提供一條從語意名回到原始值的路徑。路徑存在不代表路徑的終點正確。

同一批工作裡，字級檔的檔頭宣稱記錄了各階吸收哪些原始值，記的是 9、10、11、12、13、14、15、19。用容許小數的方式重新量測：9 出現 0 次（不存在，而規格與實作者都記了它）、10.5 出現 58 次（全設計最高頻字級，兩邊都漏）、11.5 出現 55 次（次高頻，兩邊都漏）。根因是雙方都用只抓整數的字元類，`10.5` 被切成 `10` 與 `5`、`9.5` 被切出一個看似合理的 `9`，切出來的數字全部落在既有值域，所以輸出端毫無異狀。

階值本身沒錯（半像素落在既有分階區間內），錯的是那張宣稱記錄來源的映射表。三個推論：

- **兩個獨立來源共享同一個抽取方法時，一致性不是證據。** 獨立性指方法的獨立，不指人的獨立。
- **儀器的錯誤若產出落在合法值域內的讀數，輸出端沒有訊號。** 這種錯誤靠換一把儀器重測才會現形，檢查輸出看不出來。
- **映射表本身是未經驗證的資料。** 它的外觀像稽核紀錄，於是沒有人稽核它。

核心主張在這裡也成立，而且是它自己失效的說明：那張來源表錯的時候跟對的時候外觀相同，所以沒有被檢查。命名把分類改寫成了錯會顯現的形式，卻沒有對來源表做同樣的事。要讓來源表也被檢查，需要的改寫是換一個抽取方法重測、比對兩次讀數的差。

## 操作程序

1. **量測，並把量測方法連同結果一起寫下來**——下一步要挑戰它，方法沒寫下來就挑戰不了
2. **換一個抽取方法重量一次**，兩次讀數不一致的位置就是要查的位置。特別注意會被第一種方法切開或吞掉的形態：小數、負值、帶單位、大小寫差異、全形字元
3. **把候選分類逐一展開成個別名字**，每個名字回設計檔（或其他非規格的來源）查它實際承擔什麼
4. **檢查每個名字能不能被指認為錯**。出現序號式名字，代表這一步還沒做完
5. **分不進任何序列的成員直接記為獨立角色**，不編進階梯
6. **把唯一允許的例外位置做成機器讀得到的標記**，其餘位置交給工具檢查
7. **規格與來源不符時以來源為準**，回頭更新規格

## 判讀徵兆

分類可能是假的，訊號有這幾種：

- 成員靠**值本身的相似**被歸在一起（顏色相近、數字接近、命名前綴相同），而不是靠用途
- 集合標籤帶順序詞（層次、階、level、scale、tier），而相鄰兩階的差別代表什麼指不出來
- 規格裡有一欄放著角色或語意，而那一欄是看著值填的
- 文件裡有一段話警告不要做某件事，而那件事沒有任何機制檢查
- 一份宣稱記錄來源的表，從來沒有被第二種方法重算過
- **一份宣稱有了第一個執行者之後，就沒有人再問還有沒有第二層**——查到執行者這個動作讓人以為已經查完，而它只回答了「這一層覆蓋誰」

## 適用範圍與失效條件

適用於任何「先有一批觀察值、要凍結成分類」的工作：design token、enum、error code、event 型別、DB 欄位群、目錄結構、標籤體系。

失效條件：

- **分類來自外部凍結規格時**（RFC、法規、第三方 API），命名否證不了它，只能記錄落差
- **成員數只有一兩個時**，個別化沒有東西可分離，驗證力全部來自語意內容那一條
- **名字的真值條件無法在規格之外解決時**（沒有設計檔、沒有可查的實際用途），命名退化成儀式

## 素材出處與驗證程度

本文的推導材料來自一次 Flutter 桌面專案的 design token 萃取（三層命名、17 個顏色、6 階尺寸、4 階字級）與同批的一則覆核紀錄（字級來源表的抽取方法缺陷，另記為 error-pattern `PC-GPD-002`）。

推導者未讀取該專案的規格全文與 `lib/tokens/` 原始檔，材料取自實作者與覆核者的敘述。本文的**推導**（命名的三個條件、順序詞的外溢、每層的憑證、規則載體對照、可回溯的邊界）由推導者負責；本文引用的**數字與事實**沿用該敘述，未獨立複驗。

### 落地時的事實層複驗（2026-08-28，接收端補）

上節聲明數字未複驗，接收端於併入框架前逐項查證原始檔，四項全部成立：

| 宣稱 | 查證方式 | 結果 |
|------|---------|------|
| 17 個顏色、三層可回溯 | 解析 `colors.dart` 的兩個 class，比對語意名是否皆引用原始值層成員 | 17 / 17，無未引用者、無指向不存在者 |
| 6 階尺寸 | 讀 `spacing.dart` | `Space` 六階（xxs/xs/sm/md/lg/xl），另 `Radius` 三階 |
| 4 階字級 | 讀 `typography.dart` | `AppFontSize` 四階 |
| 字級來源表的缺陷數字 | 兩種抽取方法各量一次（regex 取值 + 逐值計數） | `9` 出現 0 次、`10.5` 58 次、`11.5` 55 次，與上文一致 |

**一項須加註的限定**：規則載體對照表把「裸值只准出現在原始值層」的執行者記為「工具」。該執行者不是單一機制，而是兩層，且兩層都有各自的邊界：

| 層 | 機制 | 覆蓋 | 不覆蓋 |
|----|------|------|--------|
| 寫入時 | `presence-detection-hook.py`（`PreToolUse`，`matcher` 為 `Edit` 與 `Write`，`L124` 判裸 `Color` 並認 `color-exempt`） | 經這兩個工具的寫入 | 經 Bash 寫入（heredoc／`sed -i`／內嵌腳本） |
| commit 時 | `commit-stage-guard-gate-hook.py` 第 8 項 `_check_presence_detection`，轉呼同一組判斷函式、掃描對象改為本次 commit 的新增行 | 真實 `git commit` 呼叫，補上 Bash 寫入的缺口 | 不經 `git commit` 而寫入 ref 的路徑（`commit-tree` + `update-ref` 的隔離索引提交、`git merge --continue`） |

所以正確的讀法既不是「這條規則已被機械保證」，也不是「只在受監控的寫入管道上被保證」——**是「兩層各自覆蓋一個管道集合，聯集大於任一層，但仍非全集」**。

**由此得一條可操作的推論**（來自另一專案的獨立驗證，該處同型 hook 兩處，其中一處有 commit 層補網、一處沒有）：**要讓規則覆蓋檔案而非覆蓋管道，不能靠再加一個 `PreToolUse` matcher。加 matcher 只是把管道從一條擴成兩條，而管道是開放集合。**

但「落點是 commit 層」這個第一版答案不夠——**git 原生的 `pre-commit` 綁的也是命令，只是命令換了一層**。本機實測（git 2.50.1）：

| 路徑 | `pre-commit` | `reference-transaction` |
|------|:---:|:---:|
| `git commit` | 觸發 | 觸發 |
| `git commit --no-verify` | **不觸發** | **觸發** |
| `commit-tree` + `update-ref` | **不觸發** | **觸發** |
| `git checkout -b`（僅建 ref，無內容變更） | 不觸發 | 觸發 |

`reference-transaction`（git 2.28 起）綁的是 ref transaction 本身而非任何命令，是本機唯一能綁到「ref 被改變」這個事件的落點。四項另需知道的性質，皆為實測所得：

- **每次交易觸發兩次**（`prepared` 與 `committed` 兩個狀態，以第一個參數區分），naive 計數會重複計算
- **內部 ref 也會觸發**（如合併期間的 `AUTO_MERGE`），且有 `aborted` 狀態
- **非零離開碼會中止 ref 更新**（實測誤寫路徑導致失敗時，git 回報 `fatal: ref updates aborted by hook`）——它是實質閘門，不只是通知
- **stdin 收到的是 `<old> <new> <ref>` 三元組而非 diff**，內容檢查須自行從 new-oid 走訪 tree

最後一項決定了它的定位：**它是「ref 變了」的偵測點，不是內容檢查的好住處**——它對 fetch 與 reset 也會叫，觸發頻率與所需的走訪成本都不對。

**所以兩者兼得的位置在伺服器端**（`pre-receive`，或 push 觸發的 CI）：那裡「ref 變了」是事件本身，而且換一個本機命令繞不過去——繞過本機不改變推上來的東西。本專案的 commit 層補網做對了方向，但它綁定在 `git commit` 這個命令上；要覆蓋檔案而非管道，最終落點在推送之後。

本專案的 commit 層補網正是這個做法，且它的存在理由逐字寫在該 hook 的檔頭——「13 個僅註冊於 Edit/Write/MultiEdit 的 PreToolUse guard 對 Bash 寫入全數繞過」。它做對了方向，剩下的缺口不在方向而在完整性：**commit 層要真的覆蓋檔案，前提是它攔得到所有寫入 ref 的路徑**，而目前它綁定在 `git commit` 這個命令上，不是綁定在「ref 被改變」這個事件上。

該限定本身正是本文核心主張的又一個實例——「已有 linter 執法」這句宣稱，對的時候與錯的時候在文件上長得一樣，要看出差別必須去查 hook 的註冊 matcher。**推導者不可能知道這一點，因為它不在敘述材料裡，只在註冊設定裡。**

（本節首版只寫了第一層並斷言「經 Bash 寫入不觸發」，漏掉 commit 層補網。該漏失同樣命中核心主張：查了註冊 matcher 就以為查完了，而 matcher 只回答「這一層覆蓋誰」，不回答「還有沒有別層」——**問對了一個問題，仍可能沒問完所有問題**。）
