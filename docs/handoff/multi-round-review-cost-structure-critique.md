# 多輪審查的成本結構問題：一次發散案例的檢討

> **交付對象**：blog repo（多輪審查與寫作技能 skill 的上游維護者）
> **來源專案**：`graph_project_docs_manager`，ticket `0.1.0-W3-417` 及其衍生票（W3-530～611）
> **狀態**：本檔放在來源專案的 `docs/handoff/`，因 blog repo 當前在保護分支 main、跨專案守衛擋下直接寫入。請由 blog 端取用。

## 交付說明

這項工作的形態是多輪審查的一個極端版本：用探針（haiku agent）讀 skill 條文、作答，由兩名獨立判定者判讀，據以判斷條文是否寫得夠明確。它產出了大量真實缺陷，但**沒有收斂**——單一 session 內新建 82 張票、關閉 35 張、淨增 41 張待辦，且新增速度持續高於關閉速度。

用戶的診斷：「目的跟手段是對的，但是做法錯了——每新增一小段就要完整重新檢驗排查，這樣子永遠不會收斂。」

---

## 一、成本結構：為什麼必然發散

每改一句條文，驗證成本是：

```
O(全部既有題目) × O(全部既有答案鍵) × O(全部既有節錄檔)
```

而**每次改動的價值是固定的**（修好一個缺陷）。題庫從第 6 批長到第 21 批：261 個題目區塊、140 個題目檔、118 份答案鍵。分母持續成長，分子不變。**這個比值只會越來越差，不存在收斂點。**

更關鍵的是題庫是**累積資產**。每出一題，它的答案鍵、餵入節錄、字面通路狀態、歷輪讀數對照就永久進入維護面。發現的七項器材缺陷中，五項的本質都是「舊批次的東西沒跟上」：

| 缺陷 | 形態 |
|---|---|
| 隔離檢查單向自查 | 擋得住新批次撞既有詞，擋不住既有詞日後被撞 |
| 引文驗證固定比對 HEAD | 凍結批次的「條文已改、引文仍是當時事實」與「器材被誤改」輸出同形 |
| 節錄檔同名覆蓋 | 早期批次的餵入材料已遺失，讀數無法重現 |
| 歷輪對照欄落後一批 | 查歷史讀數最自然的位置，落後而無訊號 |
| 自檢對「前寫」與「損壞」同形 | 答案鍵已寫下批生效的引文，節錄檔還是這批的 |

**共同根因**：器材的每一項設計都預設「只有當前這一批」，而累積下來器材有一大半是凍結的歷史。這些工具都是在只有一個批次時寫的，那時「當前」等於「全部」——固定檔名、固定比對 HEAD、單向自查全都是對的。批次累積之後這個等式失效，而工具不會告訴你。

## 二、核心錯誤：用歸因級標準做及格級的事

> 我們一直在問「**這一句改動有沒有效**」，但需要知道的只是「**這份條文現在讀得懂嗎**」。

問前者需要**單變數實驗**：改一句、量一次、排除所有混淆因子。而單變數實驗的定義就是一次只准動一個變數——於是 N 次改動要 N 次全量驗證。「每新增一小段就要完整重新檢驗排查」不是執行不當，是單變數歸因這個目標的**直接推論**。

約一半的工作花在**讓歸因成立**，不是花在改條文上：字面通路盤點、涵蓋數守恆對帳、帶入判準拆訊號、計量口徑並列、基線重建、不可判讀定義、雙臂派發設計。

而其中最後一項做完之後否定了自己的前提——設計者誠實寫下：「兩臂測的是兩個不同的量，相減等於把兩個不同問題的答案相減。」付了七倍成本，做一件做完才發現測不到的事。

**對多輪審查 skill 的直接意涵**：審查輪次設計必須先問「這一輪要產出的是判定還是歸因」。判定只需要通過／不通過，歸因需要排除混淆因子，而排除混淆因子的成本在累積式產物上是超線性的。**預設應為判定，歸因是需要特別授權的昂貴動作。**

## 三、可推廣的失敗形態

### 3.1 通過率不等於機制有效

探針 3/3 全對，可能來自三種成因：

| 成因 | 可觀測面 |
|---|---|
| 讀者確實執行了判定步驟 | 依據句引條文、有中間推導 |
| **字面對應**（把題幹字串對上條文字串） | 依據句也引條文，**外觀完全相同** |
| **前提自備**（讀者補上條文沒給的前提，且補對了） | 依據句正常，缺的那一步不在那裡 |

最惡劣的一例：一組六輪的否決依據句全部是新增條文句，看似修法生效的鐵證。獨立覆核後判定為「字面對應 2、分不出來 4、走了判定步驟 0」——因為新增條文句與題幹共用字串，**「依據句是新款次」正是字面查表的預期輸出**。

另有一次量到「通過，但產出與條文主張相反」：判定值正確，而寫出的結論正是該節首段明文禁止的狀態。三輪全對，扣不到分。

### 3.2 規範文字的效力取決於它在讀者的行走路徑上

五次同型：

1. 一款處置側的涵蓋關係陳述，十五輪合計**零引用**——不是措辭壞，是讀者在前一步就收斂了。
2. 判定表外的診斷句：讀者在表內取到可填的值就停止，表外段落不被當作取值來源。
3. 排除句寫在清單引言，六輪零引用；而**同段落僅相距兩句**的另一句被六輪全引。「寫在同一段落」已量過讀數為零。
4. 一款被六輪全文引用，讀完仍判它「無作用」——**讀到了不綁定**，因為它在判定程序的結尾而非開頭。
5. 一款的排除條件邏輯上成立，但**排除點位於讀者做選擇之後**。

位置判準（經一次可證偽檢驗，證偽條件未觸發）：

> **讀者取用的單位是程序中的一個步驟與有編號的款次，不是段落中的一句。**

射程有限：同一編號單位內**末句仍會掉**（該款 6/6 被引，其末句僅 1/6 抄出）。

### 3.3 零觀測有兩種成因，而紀錄上同形

| 成因 | 處置 |
|---|---|
| 沒測到（樣本不足） | 補測即可 |
| **測不到**（設計上同形） | 補測無用，再測七批還是零 |

實例：一項風險記為「跨七批零觀測、屬推論風險」，後查明是**不可觀測**——兩條路徑指向同一輸出值，以輸出值計分時同形。每多測一批，都會讓人更相信它不存在。

三個同形變體：「零新增命中」不等於「零通路」；「讀者沒做出誤指派」可能是條文擋住了他也可能是他沒往那想；「不可判讀」是器材看不到不是讀者沒做。

### 3.4 判準若與被測量相關，會在最需要讀數時宣告無法測量

一項污染判準的候選訊號「兩題輸出分支是否相同」被明文否決，理由是：以它作判準會讓被測失分形態的每一輪自動不可判讀——**判準吃掉被測量**。

### 3.5 否決是判準的一部分

> **未明文否決等於留給判定者自行決定。**

兩名獨立判定者在同一組資料上得出不重疊的有效樣本，成因正是判準只寫了「什麼算命中」，沒寫「什麼不算，以及為什麼」。

### 3.6 最省力的路徑決定實際行為——對每一種讀者都成立

- 探針：一句字面可對、一條抽象規則要先分類，取前者。
- 代理人：答案鍵裡有一欄歷史讀數（一行看到），判定報告要另開檔案（正確但費事）——取前者，而前者落後一批。
- PM 本人：同一組讀數有兩個計量口徑，引用了方便的那個，沒標明。

### 3.7 修正動作本身製造新缺陷

一次改文新增「並指出條文**哪一句**寫出了這項差異」。而「依據哪一句？」是題庫**每個子問的結尾**——20 個射程內題目中 17 題含之。該詞成為那款的獨佔詞，對題目結尾三個字做字面比對即唯一選到它。**這是廣度最大的一條字面通路，由修正動作開出。**

同型另有兩例：補句使某題通過率由 2/3 降為 1/3；補句與另一款的問法衝突而被移除。

### 3.8 差集法只抓得到新開的問題

一次盤點以「本次改動的新增字面」為差集基準，漏掉三題——那三題的來源條文句從未改過，**差集下為零**。「本次變更掃描」與「全量掃描」不可互相替代；前者會隱含假設「存量沒問題」。

### 3.9 過濾條件不在任何檢查的射程內

一具工具以「餵入欄含某字串」過濾，部分題目沿用上一題的寫法不含該字串——**被靜默丟棄**，分母跟著少。工具報出的每個數字都正確，只是都建立在沒人檢查過的子集上。

修正的第二項才是根治：**被排除者一律寫入 `dropped` 欄附原因**——關掉的是「靜默」本身。

驗證用守恆式：把全部區塊分類到互斥的格，**加總必須等於總數**。抽樣比對做不到，因為被丟棄的東西不會出現在樣本裡。

該類問題出現三次（過濾條件、丟棄規則、抽取 span 定義），每次都在「處理」之前發生，因此不在任何檢查的射程內。

### 3.10 順序會改變掃描結果

同一份比對，先極大化再交集、與先交集再極大化，結果不同：先極大化會使短詞被長串吸收而消失，而讀者用的正是短詞。兩步驟對調，多找到三條廣度 9 以上的通路。工具做了、也沒做錯，只是順序讓它看不見。

## 四、重設計方向（該專案採取的處置）

1. **題庫由累積資產改為拋棄式**。每輪現出題、驗完即棄，只保留出題規格。規格是恆定大小，題庫不是。跨批可比性、歷輪對照、節錄同步的維護成本會歸零——它們全是「舊題目還在」造成的。
2. **放棄逐項歸因，改為整體通過**。失敗時才定位，定位可用二分，只在失敗時付成本。
3. **改動批次化**。所有待修條文一次改完再驗一次。
4. **停損**：發現不再逐項開票，只有會使判定翻面的才開票。

三項的共同點是**放棄「每一步都可解釋」，換取「整體可完成」**。

須強調：建立的每個防護機制單獨看都是對的——守恆式對帳、正向對照輸入、以不變量排除混淆因子、計量口徑並列、空窗期警語。沒有一個多餘。**問題是它們全部為了讓單變數歸因成立而存在**，而那個目標本身選錯了。拿掉它，七項器材缺陷中至少五項當場消失。

## 五、對 skill 設計的具體建議

| 建議 | 對應形態 |
|---|---|
| 審查輪次先宣告產出是判定還是歸因，預設判定 | 第二節 |
| 通過標準須含依據，且檢查依據與輸入是否共用字串 | 3.1 |
| 審查意見必須落在被審查者的執行路徑上，不寫旁註 | 3.2 |
| 「未發現 X」須同時說明本次審查看不看得到 X | 3.3 |
| 排除規則須與被審查對象正交 | 3.4 |
| 審查清單須同時列「什麼不算問題」 | 3.5 |
| 正確來源要放在比錯誤來源更省力的位置 | 3.6 |
| 區分「只審不改」與「允許改」，後者帶回歸檢查 | 3.7 |
| 變更掃描與全量掃描不可互相替代 | 3.8 |
| 工具的輸入範圍界定本身需要對照輸入 | 3.9 |
| 掃描步驟的順序要寫進規格，不可由實作者自選 | 3.10 |
