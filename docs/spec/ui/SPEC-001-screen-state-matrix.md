# 畫面狀態矩陣與 gate 退出路徑

## 概述

界定六個畫面與專案切換浮層的**每一個狀態**，各以四欄描述：
顯示／可用操作／進入條件／退出路徑。

核心判準：**退出路徑欄為空即 UX 死胡同**，須在實作前修正。
每個 gate 的三問（成功／失敗／不確定）皆須有對應的行——gate 的「失敗」
欄為空代表使用者被擋住且無法繼續。

本規格是 0.1 整合測試的斷言來源：該版本無資料可串，驗證對象正是
「每個狀態都畫得出來、且都走得出去」。

## 1. Domain 視圖（矩陣／泳道雙模式）

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 未選專案 | 空畫面 + 選擇資料夾引導 | 開啟切換浮層、選擇資料夾 | App 首次啟動，無已存路徑 | 選擇資料夾 → 載入中 |
| 載入中 | 骨架版面 + 進度 | **取消載入**、開啟切換浮層 | 已選專案，節點解析未完成 | 取消 → 未選專案；完成 → 正常／空圖 |
| 正常 · 矩陣 | domain × UC 交叉表 | 點格子→泳道、選 domain、切模式 | 節點解析成功且有節點 | 導覽至其他畫面、切換專案 |
| 正常 · 泳道 | flow 橫向穿過 domain 泳道 | 選 domain、切模式、捲動 | 同上，且已選定一條 UC | 切回矩陣、導覽、切換專案 |
| 空圖 | 「此專案尚無圖譜節點」+ 說明 | 開啟 `docs/` 目錄（**僅在該目錄存在時提供**）、切換專案 | `docs/` 存在、解析成功、節點數為 0 | 切換專案、導覽至破洞報告 |
| **不是框架專案** | 「此資料夾沒有 `docs/`，不是使用本框架的專案」+ 說明本 App 需要什麼 | 切換專案、選擇其他資料夾 | 資料夾可讀但無 `docs/` 目錄 | 切換專案（浮層維持可用） |
| **無可消費的型別表** | 版本值 + 「此專案的框架版本早於圖譜型別表的機器可讀匯出」+ 可否降級檢視 | 切換專案、（若支援降級）以純檔案模式檢視 | `.claude/VERSION` 存在，但 `tracking_schema.json` **檔案不存在** | 切換專案 |
| schema 不相容 | 版本不符說明 + 兩個版本值 | 檢視詳情、切換專案 | 框架版本超出 App 已知範圍 | 切換專案（浮層維持可用） |

## 2. UC Flow 視圖

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 無 UC | 「此專案尚無 UC 節點」 | 導覽至破洞報告 | 專案無 UC 型別節點 | 導覽、切換專案 |
| **flow 未結構化** | UC 基本資訊 + 「尚未填寫結構化 flow」 | 開啟原始檔、檢視關聯 | UC 存在但無 FlowStep | 開啟原始檔、返回 Domain 視圖 |
| 正常 | 垂直步驟表，domain 與事件成欄 | 點步驟→節點詳情、點 domain→Domain 視圖 | UC 含結構化 flow 區塊 | 導覽、切換專案 |

> **`flow 未結構化` 必須是一級狀態。** `FlowStep` 屬 `proposed` layer，
> 其升級判準有兩條且須同時成立：(1) 兩個以上互相獨立的 consumer 專案語料
> 中有實例；(2) doc CLI 對該型別有建立與驗證支援。
>
> 現況：條件 1 為 flutter_balance 1/1、本專案 6/6，跨專案的真實覆蓋率未知；
> **條件 2 尚未滿足**——沒有任何 CLI 驗證器檢查 flow 區塊。該缺口已實際發作：
> 本專案六份 UC 首次填寫時，39 個步驟中有 37 個缺必填欄位（`emits`／
> `consumes`）而無任何機制察覺，於 2026-08-27 的多輪審查中才被發現並補齊。
>
> 因此不論出現率如何，此狀態的視覺與引導品質決定這個畫面在真實專案上
> 是可用還是空殼——**結論不依賴出現率**。

## 4. Ticket 清單（列表／主題雙模式）

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 未載入 | 「載入 N 張 ticket」+ 預估耗時（N 為該專案實際票數） | **開始載入**、返回 | 首次進入此畫面（依視圖惰性） | 返回上一畫面、切換專案 |
| 載入中 | 進度條 + 已解析筆數 | **取消載入**、切換至其他畫面 | 使用者觸發載入 | 取消 → 未載入；完成 → 正常 |
| 正常 · 列表 | 密集表格 + 虛擬捲動 | 搜尋、篩選、排序、切模式、開票 | 載入完成且票數 > 0 | 導覽、切換專案 |
| 正常 · 主題 | 主題節 + 未歸屬節 | 展開收合、切模式、開票 | 同上 | 同上 |
| 無 ticket | 「此專案尚無 ticket」 | 導覽至破洞報告 | 載入完成但票數為 0 | 導覽、切換專案 |
| 含損壞 | 正常視圖 + 損壞徽章與計數 | 同正常 + 跳轉破洞報告 | 存在解析失敗的票 | 同正常 |

## 5. 破洞報告

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 掃描中 | 骨架 + 進度 | 取消 | 進入畫面且圖已建立 | 取消 → 返回；完成 → 有／無破洞 |
| 無破洞 | 「未偵測到破洞」+ 掃描範圍說明 | 重新掃描、導覽 | 掃描完成且破洞數為 0 | 導覽、切換專案 |
| 有破洞 | 依類別分節，各項帶檔案與行號 | 點項→開啟原始檔並定位、重新掃描 | 破洞數 > 0 | 導覽、切換專案 |

## 6. 節點詳情

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 正常 | 全頁內容 + 關聯右欄 | 開啟原始檔、點關聯→跳轉 | 節點存在且解析完整 | 返回來源畫面、點關聯跳轉 |
| 部分損壞 | 可讀欄位 + 損失欄位標示「因檔案損壞而無法讀取」 | 同正常 + 跳轉破洞報告 | 該節點解析時發生斷點 | 同正常 |
| 原始檔已消失 | 「原始檔已不存在」+ 最後已知路徑 | 重新整理、返回 | 外部刪除且尚未重新載入 | 返回、重新整理 |

## 7. 專案切換浮層（非獨立畫面）

| 狀態 | 顯示 | 可用操作 | 進入條件 | 退出路徑 |
|------|------|---------|---------|---------|
| 收合 | 側欄頂端顯示目前專案名 | 點擊展開 | 常態 | —（此為靜止態，非阻擋態） |
| 展開 | 最近專案清單 + 健康徽章 + 選擇其他 | 選專案、選資料夾、點外部收合 | 使用者點擊 | 選取 → 收合並重載；Esc／點外部 → 收合 |
| 無最近專案 | 僅「選擇資料夾…」 | 選擇資料夾 | 首次使用 | 選取 → 收合並載入；Esc → 收合 |

## Gate 三問對照

| Gate | 成功 | 失敗 | 不確定 |
|------|------|------|--------|
| **資料夾可用性** | Domain 視圖 · 載入中 → 正常 | 切換浮層顯示該項不可用 + 原因，其餘項仍可選 | 探測逾時 → 視為不可用，訊息註明「可能是磁碟未掛載」 |
| **schema 版本相容** | JSON 存在且版本在範圍內 → 型別表載入，進入正常 | 版本**超出**已知範圍 → schema 不相容；**JSON 檔案不存在** → 無可消費的型別表 | `.claude/VERSION` 缺失但 JSON 存在 → 以 JSON 內的產生版本推定並標示；兩者皆缺 → 視為非框架專案 |
| **文件解析** | 正常 | 單檔失敗不中止整輪；該節點標記損壞並列入破洞報告 | 斷點救援後欄位不完整 → 依 `severity` 分級標記（邊損壞／詳情損壞） |

三個 gate 皆無「失敗欄為空」的情形。

> **schema gate 的三路判定只用兩個訊號：`.claude/VERSION` 的值，與
> `tracking_schema.json` 檔案是否存在。** 不讀 `tracking_schema.py` 的內容
> ——PROP-002 §被否決的方案已否決 Dart 側解析 `.py`（`ast.literal_eval` 對
> `GRAPH_NODE_TYPES` 與 `GRAPH_EDGE_TYPES` 皆失敗，因兩者引用具名常數）。
>
> 實測本機 10 個樣本，這兩個訊號足以正確分出三類，無需第三個訊號。

## 功能需求

### FR-01: 所有狀態皆有非空退出路徑

| 項目 | 值 |
|------|-----|
| 優先級 | P0 |
| 驗收 | 本規格 §1–7 的每一列，退出路徑欄非空；唯一例外是浮層收合態（靜止態，非阻擋態） |

### FR-02: 長時操作可取消

| 項目 | 值 |
|------|-----|
| 優先級 | P0 |
| 驗收 | Ticket 載入與破洞掃描期間，取消操作恆可用且可離開該畫面（與規模無關） |

理由：惰性載入把整批解析的成本集中在單次觸發。若載入期間無法取消或離開，
該狀態即為死胡同——專案越大越嚴重。佐證：`flutter_balance` 於 2026-08-26
以 Python + PyYAML 量得約 1.9 秒（1300 檔、17.26 MB，粗略上界）。該數字只作
理由，不進驗收條件——換一個十倍大的專案時它無法重算。

### FR-03: 空狀態必須提供前進動作

| 項目 | 值 |
|------|-----|
| 優先級 | P1 |
| 驗收 | 所有「無 UC／無 ticket／無提案／空圖」狀態皆提供至少一個非「返回」的動作 |

### FR-04: 版本不符時拒絕渲染，不靜默降級

| 項目 | 值 |
|------|-----|
| 優先級 | P0 |
| 驗收 | schema 版本超出已知範圍時顯示兩個版本值與說明，不繪製圖譜 |

理由見 `EVT-SCHEMA-002`：渲染可能錯誤的圖比明確拒絕更糟，使用者無從
分辨圖是對的還是壞的。

### FR-05: 損壞資料依嚴重度分級標記

| 項目 | 值 |
|------|-----|
| 優先級 | P1 |
| 驗收 | 邊損壞以視覺差異呈現（虛線框／降低不透明度），詳情損壞以圖示加計數徽章呈現 |

### FR-06: `flow 未結構化` 為一級狀態

| 項目 | 值 |
|------|-----|
| 優先級 | P1 |
| 驗收 | UC 無 FlowStep 時，顯示 UC 基本資訊與明確說明，並提供開啟原始檔的動作，而非空白或錯誤 |

理由：`FlowStep` 屬 `proposed` layer 且無 CLI 驗證器（升級判準第 2 條未滿足），
因此各專案的填寫率與符合率皆不可預期。將此狀態視為例外會使該畫面在
未填寫的專案上成為空殼；而它是否為多數，本規格不作宣稱。

### FR-07: 型別表不可消費或非框架專案時，明確說明而非空白

| 項目 | 值 |
|------|-----|
| 優先級 | P0 |
| 驗收 | `tracking_schema.json` 不存在時進入「無可消費的型別表」狀態並顯示框架版本值；`.claude/VERSION` 與 JSON 皆缺時進入「不是框架專案」狀態並說明本 App 需要什麼。兩者皆不得顯示空白或泛用錯誤，且皆須提供切換專案的出口 |

理由：實測本機 17 個有 `.claude/` 的專案，可正常載入者僅 1 個（5.9%）。
FR-04 只涵蓋「版本超出已知範圍」這一路，而實際輸入 94% 落在另外兩路。
一個對 94% 的輸入沒有定義行為的規格，在真實使用中就是空白畫面。

> 本 FR 由 2026-08-27 的 frame 3-H 個案實跑產生——四個個案的停頓點並排後
> 指向同一個缺席變數（被觀察專案的框架版本），詳見 `docs/domain-map.md` §9。

## 設計約束

- 本規格描述狀態與轉換，不描述視覺細節；版型見 PROP-004 與 `design/`
- 0.1 版本不串接真實資料，所有狀態以假資料驅動
- 假資料須涵蓋四種極端：真實規模（不低於 1300 筆，取下界因語料持續成長）、
  空狀態、異常長內容、損壞資料（舊框架版本缺欄位、斷邊、不合法 ID）
- 假資料的產生方式尚未決定（生成器 vs 指向真實 repo）。指向真實 repo 的路徑
  在 CI 上不存在，列為待決
