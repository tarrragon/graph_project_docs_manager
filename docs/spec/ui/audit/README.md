# SPEC 同步稽核腳本

本目錄存放 SPEC-001／SPEC-003／SPEC-004（與 UC 文件）之間集合同步稽核用的
唯讀腳本，來源為 `0.1.0-W3-335.54`（首次窮舉式核對）。腳本僅讀取
`docs/spec/ui/*.md` 與 `docs/usecases/*.md`，不修改任何檔案。

## 用途

三份 SPEC 之間存在多處「同一集合、多處列舉」的結構：狀態總數（SPEC-001 定義，
SPEC-003／SPEC-004 各自複述引用）、SnackBar i18n key（SPEC-003 定義觸發時機，
SPEC-004 定義元件層 slot／i18n）、可點擊錨點（testKey，三份文件與 UC 皆可能
引用）。每輪修補若只憑人工抽樣核對，容易在改一處時漏改另一處引用同一集合的
位置（`0.1.0-W3-335.54` Problem Analysis 記錄的三輪 V4 重複缺漏即為此類）。
兩支腳本把「這個集合在各章節位置是否出現」機械列成矩陣，取代人工抽樣。

## 執行指令

於專案根目錄執行（腳本以 `Path(__file__).resolve().parents[4]` 定位專案根，
與目前工作目錄無關，但仍建議在根目錄執行以符合下方相對路徑輸出範例）：

```bash
python3 docs/spec/ui/audit/matrix.py > /tmp/spec-audit-matrix.md; echo "exit=$?"
python3 docs/spec/ui/audit/counts.py > /tmp/spec-audit-counts.txt
```

| 集合 | 權威表位置（本腳本內） | 上游權威來源 |
|------|----------------------|-------------|
| 狀態（節、狀態名、狀態錨點） | `matrix.py` 模組層級 `STATES` list | SPEC-001 §1–§7 逐節表列序；新增或移除狀態須同步改 `STATES`（腳本的狀態集合相等檢查會報出 `STATES` 與 SPEC-001 的差異） |
| SnackBar key | `matrix.py` 模組層級 `SNACK_KEYS` list（與規格推導聯集比對，見下） | SPEC-003 §2.13〈判準與既有條文的對照〉與 SPEC-004 §4.0.6 新 key 總表；新增或移除 key 須同步改 `SNACK_KEYS`，差異由權威表推導差報出 |
| 可點擊錨點（testKey） | `matrix.py` 模組層級 `ANCHOR` 正則（前綴白名單） | 三份 SPEC 與 UC 文件內以 backtick 包裹的 `state-` / `action-` / `mode-` / `scroll-` / `drag-` / `badge-` / `panel-` / `menu-` / `option-` / `card-` / `cell-` / `expander-` / `input-` / `nav-` / `project-` 開頭字串；矩陣為全集聯集（`S3任一` / `S4任一` / `S1任一` 三欄），非白名單式列舉 |
| 疑似寫死計數 | `counts.py` 模組層級 `NUM` / `P` 正則 | `document-format-rules.md` 規則 10〈可變計數不實例化〉；正則為啟發式樣式，非精確語意判斷 |

**權威表維護**：三份 SPEC 或 UC 文件新增／移除狀態、SnackBar key 或錨點時，
上述對應 list／正則須同批更新，否則矩陣會漏掉新集合成員（矩陣只核對「清單內
成員是否出現於各章節」，不會自動發現清單外的新成員）。

## 如何判讀輸出

### `matrix.py`（三張矩陣 A 狀態、B SnackBar key、C 錨點，加 D 狀態集合相等檢查）

- 格值三態：`Y` = 該成員字面出現於該欄對應章節區段；`~<id>` = 未出現但屬合理不出現
  （id 指向腳本內 `MASKS`，每項附出處與理由）；`X` = 未出現且無遮罩，即真缺漏候選。
- 遮罩來源兩類：`R1`–`R12` 取自 `0.1.0-W3-335.54` Solution〈4. 合理不出現〉；`N1`–`N3`
  為 `0.3.3-W3-375` 新判定；`N4`、`N5` 為 `0.3.3-W3-404` 依 `0.3.3-W3-392` 遮罩複核新增；`N6`–`N12` 為 `0.3.3-W3-407` 由原 baseline 47 列依判準改寫（`N3` 同時擴及 S3任一／S4任一欄）。**遮罩只收有理由的項目，
  不得為了讓缺漏歸零而擴大**；新增遮罩須附出處或判定理由，並列入所屬 ticket 供核對。
  `N1`（子集欄）已依欄收窄：S3§1.1 只對 `scroll-` 錨點檢查、S3§4 改為「S3 §3.x〈導航跳轉與退出〉出現的錨點須在 §4」
  （排除殼層 `nav-item-`／`nav-page-` 與 `action-*-open-*` 外部動作）、S4§4.26 變體欄只對 `*Action` 檢查；
  S3§1.4 的 `expander-`／`menu-` 缺漏為警告等級（列出但不計入合計）；S1任一欄改 `N4`（SPEC-001 不承載錨點）；
  新增 S4§4.26 一致欄（key 於變體表被具名處須與 §2.13 判準結論一致，無可比者 `N5`）；S4§4.0.6 欄改為
  與 S3§2.2 與 ARB 的聯集。仍套 `N1` 的欄，其副作用不變：漏列新成員不會被本腳本發現。
- `X` 只是候選：是否真為缺漏須對照上游 SPEC 條文語意，判定結果記錄於對應 ticket，
  本目錄不記錄判定結論。矩陣 A 與 C 對同一狀態錨點可能重複列出同一發現。
- **D 狀態集合相等檢查**：SPEC-001 §1–§7 各表狀態集合、SPEC-003 §4 的（畫面, 狀態）集合、
  `STATES` 三者兩兩比對（狀態名去除 `**` 與全形括號疊加註記後比對）；有對稱差時逐項列出
  缺漏方向與名稱。
- 結尾輸出 `真缺漏數；狀態集合對稱差；合計`。

**exit code 語意（三值）**：

| exit | 條件 | 處置 |
|------|------|------|
| `0` | 基線外真缺漏 0、狀態集合差 0、權威表推導差 0，且基線無過期列、無欄位不全列 | 乾淨 |
| `1` | 有基線外的真缺漏，或狀態集合差／權威表推導差大於 0 | 讀「真缺漏清單」「集合差」「權威表差」逐項判讀；新缺漏建追修票 |
| `2` | 只有基線問題：過期列（key 已不在輸出，通常代表追修已完成）或欄位不全（ticket 欄空） | 刪除過期列或補齊欄位；與 `1` 並存時取 `1` |

腳本讀檔失敗等例外由 Python 直接以非零結束（Python 例外為 `1`，與 exit 1 同碼；讀 stderr 區分）。

**基線 `baseline.tsv`**（與 `matrix.py` 同目錄，TAB 分隔，首列為表頭 `key`／`ticket`／`note`）：

- `key`：真缺漏清單輸出行字面（去除行首 `- `），逐字比對。
- `ticket`：**必填**，收錄判讀的出處或追修票號。
- `note`：選填，一行說明。
- 只收「已判定且有追修票」的真缺漏。基線只記指標（比對鍵加票號），判讀理由留在該票面，本目錄不記錄判定結論。
- 「合理不出現」**不進基線**，一律寫成帶判準與出處的遮罩規則（`MASKS`）；逐格白名單會遮住同欄新成員，
  重演 `N1` 的失效模式（`0.3.3-W3-392` 基線機制定案；`0.3.3-W3-407` 已把原 47 列改寫為 `N6`–`N12` 與 `N3` 擴充）。
- 現況：基線只有表頭（無列）。`scanCompleteUndeterminableSnackbarMessage` 四欄由 `0.3.3-W3-405` 登記（追修票 `0.6.0-W1-025`）。
- 維護：發現票加列（必帶票號）；追修票在同一 commit 修規格並刪除該列；過期列由腳本以 exit 2 提示。

**權威表推導差**：`SNACK_KEYS`、`R10_ANCHORS` 兩份寫死清單由規格推導聯集（SnackBar key：SPEC-003 §2.13 對照表首欄、
§2.2 i18n 表的 `*SnackbarMessage`／`*Action`、SPEC-004 4.26 變體的 `*Action`；R10 非互動錨點：規格內非狀態錨點的
`badge-`／`panel-`），輸出 `[權威表差]` 逐項並計入合計。推導多出的 key 也會在矩陣 B 逐列核對。差異的處置是人工判定後更新寫死清單，
或（確為缺漏時）修規格。

作為追修票驗收閘門時，以 exit code 與「基線外真缺漏數」判定：exit 0 才是乾淨；合理不出現項由遮罩承載，
已判定且有追修票的真缺漏才登記於基線，不依賴「修改前後的真缺漏數」比較。

### `counts.py`（疑似寫死計數片段清單）

- 輸出格式：`檔名<TAB>行號<TAB>片段`，每行是一處疑似寫死集合大小的文字片段。
- **正則為啟發式，非精確判斷**：常見的假陽性來源——
  - 契約編號誤觸發（如 `C1–C8`、`L1–L2` 這類固定契約代號本身就含數字，屬正常引用非缺漏）
  - 版本號或票號被截斷後誤判為計數（如 `SPEC-003 條文` 中的 `003` 被前一字元
    的正則片段誤配對成「003 條」）
  - 日期片段（如 `2026-09-02`）中的數字後接其他中文字時偶發誤配
- 每一筆命中都需要人工核對是否真為「集合大小寫死」（`document-format-rules.md`
  規則 10 判準：欄位數／檔案數／條文數／步驟數等會演進的集合大小才算，凍結承諾
  數字與規則 9 實測記錄兩類例外不算）。
- 契約代號範圍（`C1–C8`、`L1–L2`、`F1–F7`、`S1–S8`、`M1–M5`）是識別碼而非集合大小，已自樣式排除；
  契約集合的大小敘述（如「共 10 條」）仍會被擷取。
- **exit code 語意**：恆為 `0`（本檔只列疑似片段，不自動判定）；stderr 印命中筆數，
  可用「修改前後筆數差」確認新增的寫死計數會被擷取。
- 判定結果記錄於對應 ticket，不在本目錄留存。

## 已知侷限

- 章節切段依標題文字比對（`section()` 函式），若標題文字改寫、章節層級調整，
  切段範圍會跟著改變，屬正常行為非 bug。
- 三個權威表（`STATES` / `SNACK_KEYS` / `ANCHOR` 白名單前綴）需人工維護，不會
  自動偵測「新集合成員被加入卻忘記登記」——此為窮舉式核對的已知代價，取代的是
  「連清單本身都沒有」的抽樣核對，不是全自動化。
