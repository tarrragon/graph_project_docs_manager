# PROP-004: 展示介面與 Domain 視圖版型

> **狀態說明**：版型已全數定案（見 §「版型定案」）。畫面狀態矩陣（Stage 1.5）
> 已展開為 `SPEC-001`。

## 需求來源

核心使用場景：需求變更時的雙向**穿透**（兩視圖間的雙向導覽操作；
與「貫穿」的區別見 `docs/domain-map.md` §2.5）——

- **domain → UC**：找出負責的 domain，檢視有哪些 UC flow 貫穿它
- **UC → domain**：自 UC 頭尾檢視該 flow 貫穿哪些 domain

這是需要圖形介面而非文字介面的理由。改功能／加功能／改介面 model 時，
在對應的 SPEC / UC / EVT 對應的測試掛上 ticket，依 BDD / TDD 先開紅燈。

## 問題描述

需確定畫面清單與各畫面的版型，作為後續 UI/UX 規格與整合測試的依據。

依專案方法論，**展示先於邏輯** —— 先確認怎麼操作、怎麼查看、怎麼展示，
才討論 data flow。因此本提案是資料層設計的上游而非下游。

## 影響範圍

| 影響項目 | 說明 |
|---------|------|
| 模組 | 全部展示層 |
| 檔案 | `lib/` 之下尚未建立的畫面模組 |
| 用例 | UC-02、UC-03、UC-04、UC-05、UC-06 |

## 範圍界定

### 本提案要做的（In Scope）

畫面清單（**六個**，非原本的七個——見下方專案切換的決定）：

| 畫面 | 回答的問題 | 版型 |
|------|-----------|------|
| Domain 視圖 | 哪些 UC flow 貫穿這個 domain | 矩陣 + 泳道雙模式 |
| UC Flow 視圖 | 這個 flow 貫穿哪些 domain | 垂直步驟，domain 與事件成欄 |
| 追溯視圖 | 需求長出什麼／為什麼存在 | 樹狀展開 |
| Ticket 清單 | 什麼卡住了 | 列表 + 主題雙模式 |
| 破洞報告 | 哪裡有破洞 | 依類別分節 |
| 節點詳情 | —— | 全頁內容，關聯收右欄 |

**專案切換不是獨立畫面**，收為側欄浮層。導覽列因此為六項，側欄頂端的專案名
本身即切換入口。

  > 方法論（所有應做的功能先討論清楚再排順序，不預先劃分 v1／v2）衝突。
  > 票 `0.0.3-W1-002` 已定案編輯模型（本 App 直接改檔、CLI 僅作驗證器），
  > 但該決策尚未落為提案與規格——列為待決。
- 搜尋與全域導覽 → 尚未確認是否納入，待訪談補完
- 圖譜總覽（鳥瞰起手畫面） → 同上

## 提案方案

### Domain 視圖：泳道 + 矩陣雙模式

| 模式 | 認知任務 | 形態 |
|------|---------|------|
| 矩陣 | **發現** —— 哪裡有關係 | domain × UC 交叉表，密度最高，一眼看完全貌 |
| 泳道 | **理解** —— 關係長什麼樣 | flow 橫向穿過 domain 泳道 |

點矩陣格子自動切換至泳道並定位。兩者服務不同的認知任務，
以單一視圖同時承擔會兩邊都不好。

### Ticket 清單的分組軸：主題，而非波次

`ticket track board --group-by topic`。原先設計的波次（wave）分組不採用。

理由是波次分的軸壞了：波次是**時間軸**分組，而在版本遲遲無法結束、
波次與待辦持續累加的情況下，時間軸只會單向增長，分組因此失去區分力。
主題是**內容**分組，不隨時間膨脹。

依框架規格呈現：

| 規則 | 行為 |
|------|------|
| 節標題 | `<主題名> (N tasks, 最高優先級=PX)` |
| 排序 | 最高優先級（P0 最前，無有效 priority 排最後）→ 票數降冪 |
| 票行 | `short_id [priority] title`，沿用樹狀縮排 |
| 未歸屬票 | 獨立一節置於全部主題節之後，不與任一主題混列 |

框架文件載明此視圖存在的理由：`track topics` 只給票數與 status 分佈、
`track topic` 只給單一主題的鏈，兩者皆無法一次看到所有主題的內容，
而**票數相同的兩個主題正是內容決定該先做哪個**。

**對 Corpus domain 的影響**：主題是 ticket 的 side-channel 資訊，
**全程不寫入 ticket frontmatter**。解析 frontmatter 取不到 topic，
須另讀被觀察專案的**兩個**純文字檔：

| 檔案 | 格式 | 語意 |
|------|------|------|
| `docs/work-logs/topic-assignments.txt` | 每行 `ticket_id \t topic`（tab 分隔） | ticket → 主題的 append-only 映射 |
| `docs/work-logs/topics-registry.txt` | 每行一個主題名 | 主題名的去重清單 |

**不變式**：任何出現在 assignments 的主題名必已存在於 registry——框架的
寫入路徑先呼叫 `append_topic()` 註冊主題名，再寫 assignment log
（`lib/topic_assignments.py:_append_line`）。本 App 若讀到 assignments
中有而 registry 中無的主題，屬破洞而非正常狀態。

**解析寬容度比照框架**：跳過空行與不含 `\t` 的行；容忍檔尾缺換行
（外部手動編輯所致，框架自身亦有此防護）。

> 框架另有同名的 Python 實作模組
> `.claude/skills/ticket/ticket_system/lib/topic_assignments.py`，
> 那是 CLI 的讀寫程式而非資料檔。本 App 以 Dart 撰寫、無法 import Python
> 模組（同 PROP-002 對 schema 消費的論證），只能讀 `.txt` 資料檔。

### 已否決：獨立的 ticket 進入點畫面

**問題**：維護者接到 ticket 後從哪裡開始查程式脈絡？

**反向框架**：反面是「ticket 應自帶足夠脈絡，使維護者不需要查」。

**基本率**（`flutter_balance` 全量 1295 張 ticket 實測）：

| 欄位 | 填寫率 |
|------|--------|
| `where.files` | 99.9% |
| `why` | 99.9% |
| `how.strategy` | 99.8% |
| `acceptance` | 99.9% |
| `source_ticket` | 70.1% |
| `blockedBy` | 18.0% |
| **`where.layer`** | **16.1%（資訊率）／99.9%（填寫率）** |
| `relatedTo` | 13.6% |

> 分母為可解析 ticket N=1299（總檔 1300，1 檔無 frontmatter），
> 重測於 2026-08-27。
>
> `where.layer` 須分兩層看：**填寫率 99.9%**（1298 張有值），
> 但 **資訊率 16.1%** —— 有值的票中 1089 張是 CLI 的預設佔位字串 `待定義`。
> 該欄位的合法值域僅載於 docstring、無任何強制，實際出現 **32 種**相異值
> （含自創詞如「工具層」「架構層」，以及與 `--where` 參數錯置而貼入的檔案路徑）。
>
> **先前版本的數字已作廢**：`acceptance` 89.8%、`where.files` / `why` 99.5%、
> `how.strategy` 98.1%、資訊率 14% 皆偏低，成因是量測腳本用
> `content.split("---")` 解析 frontmatter，被引號字串內的 markdown 表格
> 分隔線截斷而產生 130 筆假損壞。詳見 `docs/domain-map.md` §7。

「從哪裡開始」在 99.9% 的情況下已由 ticket 的 5W1H 結構回答，
獨立畫面是在解 0.5% 的問題。Premortem：該畫面會因「僅將同一份 YAML
換個字體顯示」而在使用兩次後被棄用。

**但資料同時暴露真正的缺口**：`where.layer` 的資訊率僅 16.1%。ticket 記錄了
「要改 `lib/domain`」，卻未記錄那屬於哪個 DDD domain、被哪些 UC flow 貫穿。
這條 ticket → domain 的邊在 83.9% 的票上是斷的。

> 本節一律採資訊率口徑（分母為可解析 ticket N=1299）。先前版本混用了
> 15.4%／84.6% 與 14%／85.6% 兩組數字，兩者分母不同且皆受量測 artifact 污染。

**採用方案**：於既有 Domain / UC Flow 視圖加入「以 ticket 切入」模式，
以 **`where.files`** 反查涵蓋的 domain 並高亮。

定位機制刻意**不使用 `where.layer`**：該欄位資訊率僅約 14% 且值域未受強制，
不足以承擔定位職責。`where.files` 的填寫率為 99.9%，且其值是實際路徑，
原則上可對照 `domain-map.md` 推導所屬 domain。

> **但被對照的那一側目前不存在。** `domain-map.md` 全篇以「唯一變更理由」
> 定義 domain，**沒有任何一個 domain 標註它涵蓋哪些路徑**（該檔 `lib/`
> 路徑出現次數為 0）。實作者拿到一張 `where.files: [lib/workspace/foo.dart]`
> 的票，無從判定它屬不屬於 Workspace。
>
> 這條推導成立的前提是先建立「路徑模式 → domain」對照表。該表尚未建立，
> 且它本身是設計決策（本專案的 `lib/` 目前只有 `main.dart`、`l10n/`、
> `workspace/`，分層命名未定）。列入 `domain-map.md` §9 待決。

無法自 `where.files` 對應到任何 domain 的票，顯示為「無法定位」，
該狀態本身即為破洞報告的一項。

## 首個整合測試的契約

依專案的雙迴圈測試理念，首版（展示介面，不串資料）的核心整合測試須斷言：

- 每個畫面皆能渲染且無版面溢位
- 應可捲動處能捲動、應可換頁處能換頁、應可拖拉處能拖拉
- 假資料涵蓋四種極端：真實規模（不低於 1300 張 ticket——`flutter_balance`
  於 2026-08-26 量得 1295、2026-08-27 量得 1300，口徑為
  `docs/work-logs/**/tickets/*.md`；該數字持續成長，驗收取下界不取定值）、空狀態、
  異常長內容、損壞資料（舊框架版本缺欄位、斷邊、不合法 ID）

此測試與資料正確性解耦，因此在後續每次加入邏輯時持續有效。

## 風險與 Tripwire

**風險：ticket → domain 的邊在上游尚無定案來源。** 上游已建
`0.2.1-W3-1115`（ANA）評估三個選項：強制 `where.layer` 值域並回填 /
廢除該欄位改由 `where.files` 對照 domain-map 推導 / 明示為選填。

本提案採用的 `where.files` 推導路徑與其中第二個選項一致，但**上游尚未定案**。
若最終採「推導」，該推導的計算方式歸屬（上游提供或本 App 自行實作）需另行協調。

先前曾假設 `where.layer` 的低資訊率是「刻意留白、由 domain-map 推導」，
上游查證後表示**無任何證據支持**——沒有任何地方載明它是推導而非填寫。
該假設已撤回。

**Tripwire**：`0.2.1-W3-1115` 定案 → 回頭確認本提案的定位機制是否需要調整。

## 版型定案

設計畫布：`design/`（原始 artboard 與產生器；已發布為 Artifact 供比較）。

各畫面提供 2–4 種版型方案比較後定案。被否決的方案已自畫布移除，
其存在與理由記於此：

| 畫面 | 採用 | 否決的方案 |
|------|------|-----------|
| 專案切換 | **側欄浮層**（非獨立畫面） | 清單+預覽、卡片格狀、單一動作優先 |
| UC Flow | **垂直步驟表** | 水平時間軸、事件匯流排、多 UC 疊合熱點 |
| 追溯 | **樹狀展開** | 四欄漏斗 |
| 破洞報告 | **依類別分節** | 指標卡片+鑽取 |
| 節點詳情 | **全頁+關聯右欄** | 右側抽屜 |
| Domain 視圖 | **矩陣+泳道雙模式** | （雙模式，非二擇一） |
| Ticket 清單 | **列表+主題雙模式** | 波次分組（軸已失效，見上） |

視覺基礎：seed `#2E6F6A`、Material 3、設計基準 1280×800、macOS 系統字。

> **具體數值以 artboard 為準，不以本段為準。** 本段原記「圓角 10/12、
> 字級 12–22」，實測 `design/` 的九份 artboard（皆 1280×800 且無縮放）
> 為圓角 5/7/8、字級 10–19，兩者不符。
>
> 成因是這些值沒有單一住址——規格散文與 artboard 各寫各的，必然漂移。
> 已於 2026-08-27 立 `SPEC-002` 為 design token 的唯一權威，本段不再
> 複述數值。

## 0.1 的設計流程

依 Stage 4 的 `verification-surface` 決策，0.1 階段不以「手動開啟 App 觀察」
作為驗證手段——該階段無資料可看，App 本身即展示殼。

改採**以設計技能生成多種版型配置並比較**：先產出設計稿層級的版型選項，
比較後定版，再進入實作。手動觀察留待有真實資料的階段。

這也是 §「首個整合測試的契約」的上游——版型定案後，該測試才知道要斷言
哪些畫面、哪些互動。
