# PROP-004: 展示介面與 Domain 視圖版型

> **狀態說明**：本提案為 `draft`。畫面清單與版型的上游（核心使用場景）已封閉，
> 但 domain / event 切分尚未執行，可能影響各畫面的資料需求。
> 待 `saas-tech-selection` Stage 2 完成後轉 `discussing`。

## 需求來源

核心使用場景：需求變更時的雙向穿透 ——

- **domain → UC**：找出負責的 domain，檢視有哪些 UC flow 貫穿它
- **UC → domain**：自 UC 頭尾檢視該 flow 貫穿哪些 domain

這是需要圖形介面而非文字介面的理由。改功能／加功能／改介面 model 時，
在對應的 SPEC / UC / EVT 對應的測試掛上 ticket，依 BDD / TDD 先開紅燈。

## 問題描述

需確定畫面清單與各畫面的版型，作為後續 UI/UX 規格與整合測試的依據。

依專案方法論，**展示先於邏輯** —— 先確認怎麼操作、怎麼查看、怎麼展示，
才討論 data flow。因此本提案是資料層設計的上游而非下游。

## 範圍界定

### 本提案要做的（In Scope）

畫面清單：

| 畫面 | 回答的問題 |
|------|-----------|
| 專案選擇／切換 | —— |
| Domain 視圖 | 哪些 UC flow 貫穿這個 domain |
| UC Flow 視圖 | 這個 flow 貫穿哪些 domain |
| 追溯視圖 | 需求長出什麼／為什麼存在 |
| Ticket 清單 | 什麼卡住了 |
| 破洞報告 | 哪裡有破洞 |
| 節點詳情 | —— |

### 本提案不做的（Out of Scope）

- **獨立的 ticket 進入點畫面** → 經 WRAP 分析否決，理由見下
- 編輯能力 → 首版唯讀，另立提案
- 搜尋與全域導覽 → 尚未確認是否納入，待訪談補完
- 圖譜總覽（鳥瞰起手畫面） → 同上

## 提案方案

### Domain 視圖：泳道 + 矩陣雙模式

| 模式 | 認知任務 | 形態 |
|------|---------|------|
| 矩陣 | **發現** —— 哪裡有關係 | domain × UC 交叉表，密度最高，一眼看完全貌 |
| 泳道 | **理解** —— 關係長什麼樣 | flow 橫向穿過 domain 泳道 |

點矩陣格子自動切換至泳道並定位。兩者服務不同的認知任務，
以單一視圖同時承擔會兩邊都不好。

### 已否決：獨立的 ticket 進入點畫面

**問題**：維護者接到 ticket 後從哪裡開始查程式脈絡？

**反向框架**：反面是「ticket 應自帶足夠脈絡，使維護者不需要查」。

**基本率**（`flutter_balance` 全量 1295 張 ticket 實測）：

| 欄位 | 填寫率 |
|------|--------|
| `where.files` | 99.5% |
| `why` | 99.5% |
| `how.strategy` | 98.1% |
| `acceptance` | 89.8% |
| `source_ticket` | 70.3% |
| `blockedBy` | 18.1% |
| **`where.layer`** | **14~15%（資訊率）** |
| `relatedTo` | 13.4% |

> `where.layer` 須分兩層看：**填寫率 99.9%**（欄位幾乎都有值），
> 但 **資訊率僅約 14%** —— 1164 張有值的票中 996 張是 CLI 的預設佔位字串
> `待定義`。上游複驗另發現該欄位的合法值域僅載於 docstring、無任何強制，
> 實際出現 20 種以上變體（含自創詞、與 `--where` 參數錯置而貼入的檔案路徑）。

「從哪裡開始」在 99.5% 的情況下已由 ticket 的 5W1H 結構回答，
獨立畫面是在解 0.5% 的問題。Premortem：該畫面會因「僅將同一份 YAML
換個字體顯示」而在使用兩次後被棄用。

**但資料同時暴露真正的缺口**：`where.layer` 僅 15.4%。ticket 記錄了
「要改 `lib/domain`」，卻未記錄那屬於哪個 DDD domain、被哪些 UC flow 貫穿。
這條 ticket → domain 的邊在 84.6% 的票上是斷的。

**採用方案**：於既有 Domain / UC Flow 視圖加入「以 ticket 切入」模式，
以 **`where.files`** 反查涵蓋的 domain 並高亮。

定位機制刻意**不使用 `where.layer`**：該欄位資訊率僅約 14% 且值域未受強制，
不足以承擔定位職責。`where.files` 的填寫率為 99.5%，且其值是實際路徑，
可對照 `domain-map.md` 推導所屬 domain。

無法自 `where.files` 對應到任何 domain 的票，顯示為「無法定位」，
該狀態本身即為破洞報告的一項。

## 首個整合測試的契約

依專案的雙迴圈測試理念，首版（展示介面，不串資料）的核心整合測試須斷言：

- 每個畫面皆能渲染且無版面溢位
- 應可捲動處能捲動、應可換頁處能換頁、應可拖拉處能拖拉
- 假資料涵蓋四種極端：真實規模（1295 張 ticket）、空狀態、
  異常長內容、損壞資料（舊框架版本缺欄位、斷邊、不合法 ID）

此測試與資料正確性解耦，因此在後續每次加入邏輯時持續有效。

## 驗收條件

- [ ] 七個畫面的狀態矩陣完成（顯示／可用操作／進入條件／退出路徑）
- [ ] 每個畫面的退出路徑欄非空（空欄位 = UX 死胡同）
- [ ] Domain 視圖雙模式可切換，點矩陣格子能定位至對應泳道
- [ ] 首個整合測試涵蓋四種極端假資料

## 風險與 Tripwire

**風險：ticket → domain 的邊在上游尚無定案來源。** 上游已建
`0.2.1-W3-1115`（ANA）評估三個選項：強制 `where.layer` 值域並回填 /
廢除該欄位改由 `where.files` 對照 domain-map 推導 / 明示為選填。

本提案採用的 `where.files` 推導路徑與其中第二個選項一致，但**上游尚未定案**。
若最終採「推導」，該推導的計算方式歸屬（上游提供或本 App 自行實作）需另行協調。

先前曾假設 `where.layer` 的低資訊率是「刻意留白、由 domain-map 推導」，
上游查證後表示**無任何證據支持**——沒有任何地方載明它是推導而非填寫。
該假設已撤回。

**Tripwire**：`0.2.1-W3-1115` 定案 → 回頭確認本提案的定位機制是否需要調整。

## 0.1 的設計流程

依 Stage 4 的 `verification-surface` 決策，0.1 階段不以「手動開啟 App 觀察」
作為驗證手段——該階段無資料可看，App 本身即展示殼。

改採**以設計技能生成多種版型配置並比較**：先產出設計稿層級的版型選項，
比較後定版，再進入實作。手動觀察留待有真實資料的階段。

這也是 §「首個整合測試的契約」的上游——版型定案後，該測試才知道要斷言
哪些畫面、哪些互動。
