# PROP-005: 版本序列：依資料管線切分，每版一個整合測試

## 需求來源

三輪文件審查（2026-08-27）的收束產物。審查把待決事項從 5 項擴為 19 項，
而那 19 項的價值不在清單本身——**每一項對應一個必須先綠燈的能力，
它們之間的依賴就是整合測試的順序**。

本提案把那個順序寫下來。

## 問題描述

專案方法論規定「每個版本基於一個整合測試，該測試全綠才推進下一個」，
但 0.1 之後沒有任何一份文件列出「還有哪些整合測試」。排順序的對象本身
不存在。

同時，19 項待決散在 `docs/system-layer.md` §6、各 domain map §6 與 `CLAUDE.md` §6 兩份清單裡，
**沒有一項綁定 ticket ID、承擔者或檢查點**。依專案的
`decision-trigger-binding` 規則 2，合法 trigger 限 ticket ID；
現況等於一份沒有觀察者的清單。

## 切分軸的選擇

依**資料管線**切，不依畫面、不依 UC。

| 軸 | 為何不採用 |
|----|-----------|
| 依畫面 | 每個畫面都要各自把整條管線帶起來，前幾個版本會重複建同樣的地基 |
| 依 UC | UC 之間共用大量基礎設施，切分邊界會反覆重疊 |

管線軸與 `docs/system-layer.md` §2 的依賴圖同構——前一段綠了，下一段才有輸入。
這使「這個版本能不能開始」有客觀答案，而非判斷題。

## 序列是順序，不是閘門

**本序列規定的是先後，不是「每個版本要先想清楚所有情況才能開始」。**

下方各版本列的「阻擋」是**已知的未知**，不是開工前必須全部消滅的清單。
處理方式：

| 情況 | 做法 |
|------|------|
| 阻擋確實使該版本的整合測試無法定義 | 該項先做，這是真阻擋（例如 0.5 的 step → domain） |
| 實作中撞到未預期的文件變體或情況 | **開該版本的小版本票修正**（0.1.1、0.1.2…），不回頭改版本規劃 |
| 阻擋在實作後才看得出真正的形狀 | 讓它留在清單上，做到那裡再開票 |

理由：本輪審查已證明**在沒有實作經驗前定案的判準會錯**——「130 個 YAML
錯誤」的整套容錯策略、`FLOWSTEP_REQUIRED_FIELDS` 讀成必填、carrier 讀成
目錄，三者都是在沒有跑過真實資料前推導出來的。把所有情況一次想完不會
更準，只會更晚發現錯的那些。

**任務切細、隨時可調整**，是本專案文件分這麼多層的理由：PROP 定方向、
SPEC 定狀態、UC 定流程、ticket 承載開發資訊。改一層不必動其他層。

## 版本序列

**0.x 的 minor 清單已固定**（2026-09-29，`0.4.0-W1-040`，用戶裁決）：0.1～0.3（已發布）、
0.4 Graph、0.5 Layout、0.6 其餘畫面接真資料、0.7 History，0.x 到此結束；編輯能力改變
系統基本能力（唯讀 → 可寫），劃為 1.0。不在上列任一 minor 範圍內的項目不另開 0.x minor，
經討論後停放至下一個 major（規則見 `docs/tech-decisions.md` 2026-09-29 補記）。

該換頁處能換頁、該拖拉處能拖拉。

**阻擋**：無。兩項待決已於 2026-08-27 定案——假資料採真實 repo 快照、

**0.1.x 吸收的是什麼**：實作版型時必然會撞到 `SPEC-001` 沒有預估到的

## 範圍界定

### 本提案要做的（In Scope）

- 定義整合測試的順序與各自的斷言來源
- 為每項待決指名它擋住哪一個版本
- 建立 ticket 並以 `blockedBy` 綁定，使每項待決有觀察者

### 本提案不做的（Out of Scope）

- ~~預先登記版本到 `docs/todolist.yaml` → 該檔只登記已發生與進行中的版本；
  各版本待範圍定案後才登記~~ **已廢除**（2026-09-29，`docs/tech-decisions.md`
  〈廢除「不預先登記尚未定案範圍的未來版本」〉）：0.6、0.7、1.0 已以 planned 登記
- 決定各項待決的**內容** → 那是各自 ticket 的工作，本提案只定順序與依賴
- 搜尋與全域導覽、圖譜總覽 → 是否納入尚未確認，不在本序列內

## 風險與 Tripwire

**風險**：上游的三張票（`1119` / `1121` / `1131`）不在本專案的控制範圍內。
0.3 與 0.4 會被它們擋住，而它們的排程由上游決定。

**緩解**：0.1 與 0.2 完全不依賴上游，可先做；0.6+ 的四個畫面中有三個
無阻擋，必要時可與 0.5 換序。

**Tripwire**：上游三票任一定案 → 回頭確認對應版本的阻擋是否解除，
以及定案內容是否改變本序列的順序。

> 以上三段為 2026-08-27 提案當時的敘述。2026-10-12 現況：0.3、0.4 的上游阻擋皆已解除
> （見〈失敗防護〉情境 1）；「0.6+ 的四個畫面」已收斂並部分前移（情境 6）；仍有效的
> 上游依賴只剩 §1.0 所列的 `0.2.1-W3-1119`／`1120`。

## 分階段實施計畫

階段即〈版本序列〉的各 minor，每階段的完成判準是該版的整合測試全綠。

| 階段 | 版本 | 完成判準 | 現況（2026-10-12，以 `docs/todolist.yaml` 為準） |
|------|------|---------|------|
| 1 | 0.1 展示殼 | 七個畫面與浮層全部狀態可渲染、不溢位 | completed |
| 2 | 0.2 Workspace＋Schema | 本機專案各自進入正確的 gate 分支 | completed |
| 3 | 0.3 Corpus | 逐行 frontmatter 語意與框架一致；破洞與合法非節點分類正確 | completed |
| 4 | 0.4 Graph | 對稱聯集正確、斷邊交給 Diagnostics、輕節點與全文分離 | completed |
| 5 | 0.5 Layout | 矩陣的列與格由真實資料驅動；點交叉格定位至泳道。2026-10-09 起另含破洞報告整頁與 UC Flow 接真資料 | active |
| 6 | 0.6 其餘畫面接真資料 | 於該版規劃波定義；範圍已縮為 Ticket 清單、節點詳情、追溯視圖 | planned |
| 7 | 0.7 History | `git log -p` 單次掃描與三種降級可辨識 | planned |
| 8 | 1.0 編輯 | 寫入後呼叫唯讀驗證器，索引不同步成為可偵測的紅燈 | planned |

推進條件分兩種。階段 2～5 是依賴鏈：前一段的整合測試全綠是後一段的輸入。階段 6、7
與階段 5 沒有依賴關係（`docs/system-layer.md` §2 中 Diagnostics、TicketDetail、History
皆不經 Layout），其先後是排程決定，可經裁決換序或前移；已發生者為 2026-10-09 的兩次前移。

階段內撞到的情況，承接方式也分兩種：

| 時點 | 作法 | 實例 |
|------|------|------|
| minor 開放期間 | 在該 minor 內開票修正，同時回填規格 | 0.5 規劃波的各輪裁決 |
| minor 完成後 | 分診一次，依 topic 定固定數量的 patch；topic 不契合者停放；契約行為或資料錯誤走例外閥（2026-09-29 起） | 0.3.1～0.3.3、0.4.1、0.4.2（0.4.2 為框架修復） |

分診模型之前的 0.1.1 是承接失敗的例子：零交付結案、不打 tag，42 張票前移 0.3.0。
上述情況皆不改階段順序；範圍變動記於本表與〈討論記錄〉。
