# PROP-005: 版本序列：依資料管線切分，每版一個整合測試

## 需求來源

三輪文件審查（2026-08-27）的收束產物。審查把待決事項從 5 項擴為 19 項，
而那 19 項的價值不在清單本身——**每一項對應一個必須先綠燈的能力，
它們之間的依賴就是整合測試的順序**。

本提案把那個順序寫下來。

## 問題描述

專案方法論規定「每個版本基於一個整合測試，該測試全綠才推進下一個」，
但 0.1 之後沒有任何一份文件列出「還有哪些整合測試」。排順序的對象本身
不存在。

同時，19 項待決散在 `domain-map.md` §9 與 `CLAUDE.md` §6 兩份清單裡，
**沒有一項綁定 ticket ID、承擔者或檢查點**。依專案的
`decision-trigger-binding` 規則 2，合法 trigger 限 ticket ID；
現況等於一份沒有觀察者的清單。

## 切分軸的選擇

依**資料管線**切，不依畫面、不依 UC。

| 軸 | 為何不採用 |
|----|-----------|
| 依畫面 | 每個畫面都要各自把整條管線帶起來，前幾個版本會重複建同樣的地基 |
| 依 UC | UC 之間共用大量基礎設施，切分邊界會反覆重疊 |

管線軸與 `domain-map.md` §2 的依賴圖同構——前一段綠了，下一段才有輸入。
這使「這個版本能不能開始」有客觀答案，而非判斷題。

## 序列是順序，不是閘門

**本序列規定的是先後，不是「每個版本要先想清楚所有情況才能開始」。**

下方各版本列的「阻擋」是**已知的未知**，不是開工前必須全部消滅的清單。
處理方式：

| 情況 | 做法 |
|------|------|
| 阻擋確實使該版本的整合測試無法定義 | 該項先做，這是真阻擋（例如 0.5 的 step → domain） |
| 實作中撞到未預期的文件變體或情況 | **開該版本的小版本票修正**（0.1.1、0.1.2…），不回頭改版本規劃 |
| 阻擋在實作後才看得出真正的形狀 | 讓它留在清單上，做到那裡再開票 |

理由：本輪審查已證明**在沒有實作經驗前定案的判準會錯**——「130 個 YAML
錯誤」的整套容錯策略、`FLOWSTEP_REQUIRED_FIELDS` 讀成必填、carrier 讀成
目錄，三者都是在沒有跑過真實資料前推導出來的。把所有情況一次想完不會
更準，只會更晚發現錯的那些。

**任務切細、隨時可調整**，是本專案文件分這麼多層的理由：PROP 定方向、
SPEC 定狀態、UC 定流程、ticket 承載開發資訊。改一層不必動其他層。

## 版本序列

### 0.1 — 展示殼（無資料）

**整合測試**：七個畫面與浮層的全部狀態皆能渲染、不溢位；該捲動處能捲動、
該換頁處能換頁、該拖拉處能拖拉。

**斷言來源**：`SPEC-001` §1–§7。

**阻擋**：無。兩項待決已於 2026-08-27 定案——假資料採真實 repo 快照、
泳道只做靜態版型。**可立即開始。**

> 此測試與資料正確性解耦，因此在後續每次加入邏輯時持續有效。

**0.1.x 吸收的是什麼**：實作版型時必然會撞到 `SPEC-001` 沒有預估到的
文件變體與畫面情況——那不是規劃失誤，是只有跑過才看得到的東西。
撞到就開 0.1.x 的票修正，同時回填 `SPEC-001` 的狀態表。
不要為了「一次想完」而延後開工。

### 0.2 — Workspace + Schema：三路 gate

**整合測試**：本機 17 個有 `.claude/` 的專案，各自進入正確的 gate 分支。

| 分支 | 預期數量 | 判定訊號 |
|------|:---:|---------|
| 不是框架專案 | 6 | 無 `.claude/VERSION` 且無 `docs/` |
| 無可消費的型別表 | 10 | `VERSION` 存在但 `tracking_schema.json` 不存在 |
| 可載入 | 1 | 兩者皆存在且版本在範圍內 |

**斷言來源**：`SPEC-001` FR-04、FR-07、Gate 三問對照。

**阻擋**：無。

> **這是本 App 最有價值的一個整合測試。** 測資是真實專案、答案由實測得出、
> 涵蓋 94% 過去沒有定義行為的輸入，且沒有省力路徑可走——它指名的是外部
> 固定值，改錯即紅。

### 0.3 — Corpus：解析與破洞判定

**整合測試**：
1. 以框架的逐行 frontmatter 語意解析既有語料，失敗數為 **0**；
   改用 `split("---")` 得 **130**，兩者的差即為本測試的鑑別力
2. 五個語料專案 7106 份文件中，真破洞 **47** 件、合法非節點 **1243** 件，
   分類正確

**斷言來源**：`domain-map.md` §7、`EVT-CORPUS-001`、`EVT-CORPUS-003`。

**阻擋**：
- 【上游 `0.2.1-W3-1131`】`*_REQUIRED_FIELDS` 的語意裁決——
  裁決前不得實作「缺欄位即破洞」，否則每個不分支的 FlowStep 都會誤報
- 【本地】檔案級 carrier 的破洞判定（`DomainBundle` 的 carrier 是單一檔案）

### 0.4 — Graph：建圖

**整合測試**：`relatedTo` 的 1-hop symmetric union 正確（只讀單向會漏一半）；
斷邊不丟棄而交給 Diagnostics；輕節點與 5W1H 全文分離。

**斷言來源**：`EVT-GRAPH-001`、`domain-map.md` §4.1。

**阻擋**：【上游 `0.2.1-W3-1121`】反向邊該存還是該推導。

### 0.5 — Layout：Domain 視圖接真資料

**整合測試**：矩陣的列與格皆由真實資料驅動；點交叉格定位至泳道且正確。

**阻擋**：
- 【本地】「路徑模式 → domain」對照表不存在
- 【上游】`FlowStep` 無 `domain` 欄位，step → domain 的推導方式未定
- 【本地】泳道布局演算法（自 0.1 後推至此）
- 【本地】「間接依賴」的計算路徑與跳數上限

### 0.6+ — 其餘畫面接真資料

UC Flow、Ticket 清單、破洞報告、節點詳情、追溯視圖。各自的阻擋：

| 畫面 | 阻擋 |
|------|------|
| Ticket 清單 | 無（`topic-assignments.txt` 與 `topics-registry.txt` 的格式與不變式已定，見 PROP-004） |
| 破洞報告 | 【本地】破洞各類別下的具體項目與嚴重度未列舉 |
| 節點詳情 | 無 |
| 追溯視圖 | 【上游】UC → Ticket 在 16 條語意邊中無對應邊；【本地】四層樹第二跳的欄位未明訂 |
| UC Flow | 無 |

### 0.x — History：git 邊層級變更記錄

**整合測試**：單次 `git log -p` 掃描 9409 commits 為 2.28 秒量級；
非 git 目錄、git 不在 PATH、淺層 clone 三種降級可辨識。

**阻擋**：無（票 `0.0.3-W1-003` 已實測定案）。**尚未落為提案與規格。**

### 0.x — 編輯：直接改檔 + CLI 驗證

**整合測試**：寫入後呼叫唯讀驗證器，索引不同步由靜默錯誤變為可偵測的紅燈。

**阻擋**：
- 【本地】tripwire「加入編輯能力」的四項重評（備份／衝突／還原／PII）
  —— 該 tripwire 觸發條件已於票 `0.0.3-W1-002` 定案時成立，action 未執行
- 【上游 `0.2.1-W3-1119` / `1120`】驗證器繞過 `id_pattern`、
  `uc verify` 無法區分提及與使用——驗證器誤報會使這條紅燈失去訊噪比

## 範圍界定

### 本提案要做的（In Scope）

- 定義整合測試的順序與各自的斷言來源
- 為每項待決指名它擋住哪一個版本
- 建立 ticket 並以 `blockedBy` 綁定，使每項待決有觀察者

### 本提案不做的（Out of Scope）

- 預先登記版本到 `docs/todolist.yaml` → 該檔只登記已發生與進行中的版本；
  各版本待範圍定案後才登記
- 決定各項待決的**內容** → 那是各自 ticket 的工作，本提案只定順序與依賴
- 搜尋與全域導覽、圖譜總覽 → 是否納入尚未確認，不在本序列內

## 驗收條件

- [ ] 每個版本皆有一個明確的整合測試與斷言來源文件
- [ ] 19 項待決皆綁定到它擋住的版本，並有對應 ticket
- [ ] 上游依賴（`1119` / `1121` / `1131`）標為外部 blocker 而非本地待辦
- [ ] 0.1 與 0.2 的 ticket 可立即開始，無未定案前置

## 風險與 Tripwire

**風險**：上游的三張票（`1119` / `1121` / `1131`）不在本專案的控制範圍內。
0.3 與 0.4 會被它們擋住，而它們的排程由上游決定。

**緩解**：0.1 與 0.2 完全不依賴上游，可先做；0.6+ 的四個畫面中有三個
無阻擋，必要時可與 0.5 換序。

**Tripwire**：上游三票任一定案 → 回頭確認對應版本的阻擋是否解除，
以及定案內容是否改變本序列的順序。

## Reality Test / 觸發案例實證

### 觸發案例

三輪審查的 frame 3-H（個案實跑）拿四個真實專案把全部判準走一遍，
四個停頓點並排後指向同一個缺席變數：**被觀察專案的框架版本只在
schema gate 是變數，其餘判準都不是**。

該發現直接產生本序列的形狀——若不先把 0.2（三路 gate）做出來，
0.3 之後的每一段都會在 94% 的真實輸入上停住。

### 假設列舉

- 假設 1：管線的前一段綠燈是後一段的必要條件
- 假設 2：0.1 與 0.2 不依賴任何上游未定案項
- 假設 3：本機 17 個專案足以涵蓋 0.2 的輸入分佈

### 實驗驗證

| 假設 | 驗證方式 | 執行的觀察 | 結果 |
|------|---------|-----------|------|
| 1 | 對照 `domain-map.md` §2 的 8 條依賴邊 | 管線軸與依賴圖同構 | 成立 |
| 2 | 逐項檢查 19 項待決的阻擋對象 | 0.1 兩項已定案；0.2 由 FR-07 完整定義 | 成立 |
| 3 | 掃描 `~/project/` 下全部有 `.claude/` 的專案 | 17 個，分五類，三路 gate 皆有實例 | 成立 |

### 已驗證 vs 未驗證

| 類別 | 內容 |
|------|------|
| 已驗證 | 17 個專案的分類與數量；逐行語意 0 vs 天真語意 130；47 真破洞 vs 1243 合法非節點；`git log -p` 2.28 秒 |
| 未驗證 | 0.5 之後各版本的阻擋是否窮盡——它們距離較遠，可能在前面版本實作時浮現新的依賴 |

## 討論記錄

### 2026-08-27

切分軸經三選一確認採資料管線；待決處理時機經三選一確認為「各自綁到它
擋住的那個版本」，理由是避免它們變成沒有 trigger 的永久清單——那正是
本輪審查在 tripwire 上抓到的同一個問題。

0.1 的兩項阻擋同日定案：假資料採真實 repo 快照（生成器產的損壞形態是
想像的，而本輪已證明想像的損壞形態可能整批是假的）、泳道只做靜態版型
（在沒有真實 flow 資料可看時設計布局演算法，很可能設完又改）。
