# PROP-006: History：期間內全專案的關係變動

> **分級理由**：heavy。本提案新增一條 domain 依賴邊（History → Schema），屬架構層級改動。

## 需求來源

PROP-005 §0.7 把 History（git 邊層級變更記錄）排為 0.7 的主軸，但只定了整合測試，沒有產品規格。
架構已在 0.0.3 定案（`docs/tech-decisions.md`〈git 變更記錄：邊層級〉、`docs/system-layer.md` §4.3、
`docs/spec/history/domain-map.md` §4.1），本提案不重議架構，只定產品面：放在哪個畫面、回答什麼問題、
一列代表什麼。產品面由 `0.7.0-W1-012` 的訪談裁定（2026-11-09，三輪 AskUserQuestion，其中兩題由用戶要求
以 WRAP 分析後裁定）。

## 問題描述

App 目前呈現的是「現在」的圖：關聯右欄、追溯視圖、Domain 視圖都只看得到最後一輪掃描的邊。使用者要回顧
「這一版改了哪些關係」時，只能自己讀 `git log -p`，並在 frontmatter diff 裡辨認哪些行是邊——這正是本專案
定位要取代的 grep 與人工追溯。被移除的邊只存在於 git 歷史，現有畫面沒有任何地方看得到。

## 影響範圍

| 影響項目 | 說明 |
|---------|------|
| Domain | History（新增 History → Schema 出邊，層級仍為 L1，見〈提案方案〉第 4 點） |
| 規格 | 新增 SPEC-008（History domain）；SPEC-001 新增第七畫面一節；SPEC-003 互動與 SPEC-004 元件由執行期 DOC 票補齊 |
| 畫面 | 新增第七個導覽目的地「變更記錄」；其他六個畫面不動 |
| 用例 | 新增 UC-07 |

## 範圍界定

### 本提案要做的（In Scope）

1. History domain：單次 `git log -p` 掃描、frontmatter 邊事件解析、三種降級判定
2. 第七畫面「變更記錄」：一列一個邊事件，依時間新到舊排列
3. 期間篩選：預設「最近一個版本 tag 至今」，無版本 tag 的專案預設最近 30 天；另可選最近 30 天、全部歷史
4. 「ticket 建檔事件」篩選：預設排除，可切換為包含
5. 事件列的對端節點可跳至節點詳情（沿用既有 jump 與「節點不在目前的圖上」狀態）
6. PROP-005 §0.7 的整合測試：單次掃描的成本量級，以及三種降級可辨識

### 本提案不做的（Out of Scope）

- 節點詳情的變更記錄區段（單一節點的「何時由誰建立」「曾被移除哪些關聯」）→ 訪談未選入，登記為下一個 minor 的候選（票號見〈轉化記錄〉）
- 依 commit 反查（點 commit 看該 commit 的全部邊變動）→ 同上
- 邊型篩選、節點型別篩選、自訂日期區間 → 同上；本版以期間與 ticket 建檔兩項篩選驗證可用性
- 增量掃描 → 架構定案不做（全量重掃已夠快，增量需維護狀態且正確性風險高）
- 分支內個別 commit 的歸屬 → 用戶裁定採主線歸屬，見〈提案方案〉第 2 點

## 提案方案

1. **一列一個邊事件**（用戶裁定）。事件欄位：類型（新增／移除）、邊型、宣告端節點、對端節點、commit（短 hash）、
   日期、作者、commit 訊息首行。
2. **事件歸屬到主線 commit**（用戶裁定）。掃描指令為
   `git log -p --first-parent --diff-merges=first-parent`，分支上完成的工作顯示為 merge commit。理由：
   邊事件的解析必須追蹤每個檔案的 frontmatter 狀態（約 36% 的 block 清單列項，所屬欄位名不在 hunk 上下文內），
   而平行分支會讓按時間重放失準；主線使歷史成為線性，仍是單次 `git log -p`。
3. **邊的身分沿用 SPEC-007**。有反向欄位的邊取兩側聯集（SPEC-007 D1）。事件定義為「宣告來源集合在某個
   主線 commit 由空變非空（新增）或由非空變空（移除）」；只改變宣告側而邊仍存在，不產生事件。
4. **History 依賴 Schema**（`0.7.0-W1-012` 規劃線的設計選擇，主控授權規劃期設計選擇由規劃線判斷）。History 需要邊型表（正向與反向欄位）判定 diff 行是否為邊，
   也需要路徑對型別查詢判定節點是否為 ticket；兩者都在 Schema 公開面。改由呼叫端傳入，等於把同一條依賴藏到
   組裝根。型別表缺席時的內建表降級沿用 Schema 既有行為。
5. **惰性載入與快取**。進入第七畫面才掃描；結果以（工作區根、HEAD commit、型別表識別）為鍵快取（以 SPEC-008 FR-09 為準），
   鍵未變時再次進入不重掃，鍵改變或使用者按重新整理時全量重掃。掃描可取消。
6. **版本 tag 由前置檢查取得**。以 tag 清單與主線清單判定基準 tag，不依賴掃描輸出：`-- docs/` 會剪掉未觸及 `docs/`
   的 commit，打在這類 commit 上的 tag 不會出現在掃描輸出中（多視角審查 linux 第 5 項）。判定規則在 SPEC-008 FR-06。
7. **解析追蹤每個檔案的全文**。frontmatter 範圍在每個 commit 結束時重新計算；只追蹤 frontmatter 會在 frontmatter
   邊界移動時失準（多視角審查 linux 第 1 項）。本專案 HEAD 時 `docs/**/*.md` 全文約 40 MB。

## 失敗防護

| 失敗情境 | 早期警訊 | 防護 |
|------|------|------|
| diff 輸出隨 repo 規模成長，掃描變慢、記憶體上升 | 輸出位元組數超過 tripwire 閾值（SPEC-008 定義） | 超過閾值記日誌；緩解手段為 `--since` 或路徑範圍收窄（定案沿用） |
| frontmatter 狀態追蹤使解析成本高於原型（0.18 秒） | 實作票的兩語料實測超出秒級 | 實作票 acceptance 含兩語料實測；超出量級時停手回報，不自行改架構 |
| 節點改過 ID，事件斷成兩條 | 同一路徑出現 `id` 欄位變更 | 以 ID 比對，不追蹤改名，SPEC-008 列為已知限制 |
| 淺層 clone 使「首次出現」時點錯誤 | `git rev-parse --is-shallow-repository` 為 true | 畫面標示歷史不完整（定案的三種降級之一） |
| 預設篩選後仍為空，使用者以為功能壞了 | 期間內無事件 | 空狀態提供擴大期間的動作（SPEC-001 FR-03） |

## 機會成本

- 0.7.0 的非維護工作只有 001 與 History。History 範圍越小，維護工作佔比越高；比例按票數計，不足時由主控退回維護工作，不為比例拆票（主控回覆，2026-11-09）。
- 選第七畫面而不選節點詳情區段，代價是新增導覽項與一整節狀態矩陣；換來的是直接回答用戶選定的問題。節點詳情區段延到下一個 minor，延後期間單一節點的「曾被移除哪些關聯」仍看不到。
- 編輯能力（1.0）不受影響：History 為唯讀，與 1.0 寫入路徑無共用元件。

## Reality Test / 觸發案例實證

### 觸發案例

PROP-005 §0.7 排定 History 為 0.7 主軸；訪談中用戶選定的問題是「某段期間全專案的關係變動」。

### 假設列舉

- 假設 1：單次 `git log -p` 的成本在使用者專案上仍是秒級
- 假設 2：全專案事件在預設篩選下可讀
- 假設 3：主線模式不改變成本量級

### 實驗驗證（量測環境：作者本機 macOS，2026-11-09，本專案 repo，非淺層 clone）

| 假設 | 驗證方式 | 結果 |
|------|---------|------|
| 1 | `git log -p --no-color -- docs/` | 30354 commits、83 MB、6.1 秒；比定案參考值（31.2 MB／2.28 秒）大，仍是秒級，但載入中、可取消與 tripwire 閾值必須寫進規格 |
| 2 | 以 awk 分類最近兩週邊欄位的 `+`／`-` 行（近似值） | 約 3,000 列，其中九成是 ticket 建檔；排除後約 300 列；只看非 ticket 節點約 40 列 |
| 3 | `git log -p --first-parent --diff-merges=first-parent -- docs/` | 26212 commits、82 MB、5.6 秒 |

### 已驗證 vs 未驗證

| 類別 | 內容 |
|------|------|
| 已驗證 | 上表三項；block 清單列項約 36% 欄位名不在 hunk 內；本 repo 有 1165 個 merge commit |
| 未驗證 | 實作解析器的耗時（原型 0.18 秒是否涵蓋 frontmatter 狀態追蹤）；精確事件數；flutter_balance 在主線模式下的量測 |
