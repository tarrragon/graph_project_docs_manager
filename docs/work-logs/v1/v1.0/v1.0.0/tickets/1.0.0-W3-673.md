## Task Summary

## Problem Analysis
### 問題根因

`nodeDetailBodyProvider`（`lib/screens/node_detail/node_detail_providers.dart`）在 fixture 內文為空時，以 `File(path).readAsStringSync()` 讀取**整個檔案**，原樣傳給 `DocumentBody.markdown`，沒有切掉 frontmatter。能進入圖譜的節點都有可用的 frontmatter（SPEC-001 §6〈部分損壞在 0.x 不可達〉），所以**每一種節點型別**的詳情內文開頭都會出現 frontmatter，不只 ticket。

### 影響範圍

已驗證的事實：
- 規格的組成要求內文不含 frontmatter：SPEC-004 §2 NodeDetailB 的拆解為 `Panel`[`ListRow.meta`, `AppText.title`, `BadgeRow`, `Divider`, `DocumentBody`]，frontmatter 欄位由分隔線以上的三個元件承載；§4.20 `DocumentBody`〈何時不用〉明寫「frontmatter 欄位（`ListRow.meta` / `BadgeRow`）」。畫面程式的類別註解也寫「主欄 meta + 標題 + 徽章 + 分隔線 + 內文」。
- 但規格措辭沒有寫死這個切分：SPEC-001 §6「正常」列只寫「全頁內容」；SPEC-004 §4.20 slot 表的 `markdown` 來源寫「呼叫端（檔案內容）」，狀態矩陣的來源欄寫「內容為解析完成後的檔案內容」。只讀 slot 表的實作者會把整檔傳進去。
- 切分函式已存在：Corpus 公開的 `bodyLinesAfterFrontmatter`（`lib/corpus/frontmatter_classifier.dart`，SPEC-006 FR-09），與 `classifyFrontmatter` 用同一套規則，UC flow 擷取已在使用。
- 測試缺口：`test/` 與 `integration_test/` 中引用 `nodeDetailBodyProvider` 或 `panel-nodeDetail-document-body` 的檔案為 0 個。fixture 的兩個內文樣本都不含 frontmatter，就算有測試也測不到這條路徑。

未驗證的假設：
- 渲染形態：依 CommonMark，第一個 `---` 渲染為分隔線，結尾的 `---` 緊接在連續的 YAML 行之後，會讓整段 YAML 成為一個 setext 二級標題，而不只是一般段落。本票未實機截圖確認，不影響判定。

**與 1.0 編輯的關係**：節點詳情是 1.0 的編輯入口。frontmatter 欄位在 1.0 以表單編輯（SPEC-009 FR-09），內文編輯要到 1.3。內文若繼續含 frontmatter，使用者會在表單下方看到同一組欄位的原始 YAML，而且表單寫入後兩處會不一致。

### 相關 Error Pattern

`/error-pattern query` 未命中同型案例。形態上接近「規格以元件組成表達約束，slot 表卻沒有寫明，實作者只讀 slot 表」，屬本專案規格措辭問題，不是框架層的可攜模式，不另立 error-pattern。

## 重現實驗結果
### 實驗方法

靜態重現：讀內文的取得路徑，比對規格組成。fixture 是否涵蓋這條路徑以 grep 驗證。

### 實驗執行

1. `nodeDetailBodyProvider`：`node.markdown` 為空（`projectNodeDetails` 一律給 `''`）→ 解析路徑 → `readAsStringSync()` 回傳整檔。
2. 來源票的觀察對象 `0.7.0-W1-007.10.md`，第一行為 `---`、第二行為 `id: 0.7.0-W1-007.10`，所以傳進 `DocumentBody` 的字串以 frontmatter 開頭。
3. `DocumentBody`（`lib/components/document_body.dart`）把 `markdown` 直接交給 `flutter_markdown_plus`，不做任何切分。
4. `grep -rn "nodeDetailBodyProvider\|panel-nodeDetail-document-body" test integration_test`：0 筆。

### 實驗發現

- 已驗證：內文字串含 frontmatter，元件不切分，也沒有測試涵蓋。與 012.14 實機觀察 F-4 一致。
- 已驗證：切分函式 `bodyLinesAfterFrontmatter` 已是 Corpus 的公開面。
- 未驗證：setext 標題的確切渲染形態（見 Problem Analysis），不影響結論。

## Solution
multi_view_status: skipped
reason: 結論由規格條文與程式路徑的逐字比對得出：SPEC-004 §2 NodeDetailB 組成、§4.20〈何時不用〉，對照 provider 的 readAsStringSync。修法沿用 Corpus 既有的公開函式，不引入新設計。設計選擇只有「在哪一層切分」一項，以下以候選方案比較；實作票的 Phase 4 會再做審查。

### 判定：缺陷，附帶規格措辭缺口與測試缺口

| 面向 | 判定 | 依據 |
|---|---|---|
| 實作 | **缺陷** | 規格的元件組成要求 frontmatter 由分隔線以上的元件承載、`DocumentBody` 不承載 frontmatter（SPEC-004 §2 NodeDetailB、§4.20〈何時不用〉）；provider 卻傳入整檔 |
| 規格 | **措辭缺口** | SPEC-004 §4.20 slot 來源寫「檔案內容」、SPEC-001 §6 寫「全頁內容」，沒有寫死切分；只讀 slot 表就會實作出現況 |
| 測試 | **零覆蓋** | provider 與內文錨點都沒有測試；fixture 內文不含 frontmatter |

影響所有節點型別，不只 ticket。

### 候選方案：在哪一層切掉 frontmatter

| 方案 | 做法 | 利 | 弊 |
|---|---|---|---|
| A（採用） | provider 讀檔後呼叫 Corpus 公開的 `bodyLinesAfterFrontmatter` | 與圖譜解析用同一套切分規則（BOM、`\r\n`、第一個結尾 `---`），符合「Corpus 是唯一的解析者」（系統層 §2）；UC flow 擷取已有先例 | 畫面狀態層的 provider 依賴 Corpus 的一個函式（依賴方向本來就允許） |
| B | 在 `DocumentBody` 內部切 | 所有使用者自動受益 | 純顯示元件開始理解文件格式，元件契約「呼叫端傳值、元件不解析」被打破；也形成第二套切分規則 |
| C | 擴充 markdown 渲染器，加入 frontmatter 語法並忽略它 | 不改資料流 | 第三套解析，規則可能與 Corpus 不一致（例如 BOM、未閉合的處理） |

### 與 1.0 編輯的接點（已通知主控，供 1.0.0-W3-553.3 參考）

- 編輯表單屬於分隔線以上（frontmatter 欄位）的區域，內文區只顯示 frontmatter 之後的本文。不修的話，表單下方會出現同一組欄位的原始 YAML，寫入後兩處各自顯示，內容可能不一致。
- 1.3 的內文編輯（`re_editor`）範圍，與本票定義的「本文」同一個切分。
