# Execution Log

## Task Summary

設計全 domain 的 structured log 與錯誤分類：記錄格式與欄位、錯誤分類軸、落地位置（檔案路徑、輪替、保留期）、與既有 developer.log 的關係、與 C-2「只記識別不記內容」的界線、規格歸屬（橫切，現有 8 個 domain 無一以此為變更理由）；產出設計結論與實作票

---

## Problem Analysis
### 問題根因

〈2026-11-10〉子決策 3 解除 structured log 延後，但現況沒有任何「記錄載體」：所有日誌只經 `developer.log`（DevTools／終端），App 關閉即消失；`reportFatalError`（`lib/main.dart`）註解明寫「未預期例外不寫入 log 檔」。各 driven port 的 LogSink 由各票各自宣告，形狀未統一（W3-549 併入的問題）。

### 影響範圍

已驗證（2026-11-10，main HEAD 47a57fa6eb）：
- `developer.log` 呼叫 123 處、分布 43 檔；其中帶 `level: 900/1000` 86 處。
- LogSink typedef 8 個，形狀 4 種：
  - (event enum, Map fields, {level})：AttentionArbiter、AppSnackBar
  - (message, {event, payload Map, level})：Graph、History
  - (message, {event, level, error})：Workspace
  - 純字串：DomainView `(message,{level})`、StaleOpen `(name,message)`、Parse `(ParseLogLevel,message)`
- LogEvent enum 5 個：AttentionArbiter、Workspace、Graph、AppSnackBar、History。後三形狀中純字串三個無事件碼。
- 規格內有日誌事件契約者：SPEC-001、SPEC-003、SPEC-005、SPEC-007、graph domain-map。事件契約目前分散在各 SPEC。
- 全域三層攔截已建（〈2026-08-27〉裁決二），匯流至 `reportFatalError` 單一出口。

未驗證：Parse 路徑的診斷訊息是否夾帶原文行（C-2 風險來源 2）；本次未逐一讀 43 檔的訊息內容。

### 相關 Error Pattern

無直接對應。C-2 的兩個風險來源（手寫錯誤處理接入內容、解析器診斷引用原文）見〈2026-09-10〉C-2。

## 重現實驗結果
### 實驗方法

本票為設計票，無缺陷可重現；以唯讀盤點取代：`grep -rn "typedef .*LogSink\|enum .*LogEvent" lib`、`grep -rn "developer.log" lib | wc -l`、讀 `lib/main.dart` 全域攔截出口、讀 Parse 路徑兩處日誌呼叫。

### 實驗執行

main HEAD 47a57fa6eb，2026-11-10。數字見 Problem Analysis。

### 實驗發現

- Parse 路徑兩處（desync、unparsable）只記 `path` 與 `commit` SHA，已符合 C-2；形態為 logfmt 風格字串（`history.scan.desync path=... commit=...`）。
- 事件碼已是「測試斷言綁定的穩定契約、message 為可改寫文案」（`graph_log_event.dart` 檔頭），此慣例可直接延伸為 structured record 的 `event` 欄位。
- 現況無任何落檔路徑；落檔是新增能力，不是改寫既有呼叫。

## Solution
### 狀態：候選已列，待用戶裁決（經主控 AUQ 轉達）

前提（不變）：〈2026-08-27〉裁決二、三、四；C-1 不新增使用者內容的持有者；C-2 只記識別。structured log 是畫面之外新增的載體，不取代畫面錯誤態。

### Q1 記錄格式

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| F-A JSON Lines | 每行一筆 `{ts, level, domain, event, fields, error_class}` | `jq` 可查；巢狀 fields 無轉義問題；欄位可由測試直接 decode 斷言 | 人眼直讀較吃力 |
| F-B logfmt | 每行 `ts=… level=… event=history.scan.desync path=…` | 與 Parse 路徑現況同形；人眼可讀、grep 友善 | 值含空白或等號時要自定轉義；巢狀 fields 須攤平 |

### Q2 錯誤分類軸

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| E-A 依來源 | platform_io／external_process（git、doc CLI）／parse／gate_blocked／internal | 對應「誰該處理」，與 driven port 邊界一致 | 與畫面錯誤態的「使用者能做什麼」需另一層對應 |
| E-B 依可恢復性 | user_fixable／retryable／bug | 直接對應畫面錯誤態的行動（修設定、重試、回報） | 同一來源可跨類（IO 失敗可能是權限也可能是暫時性），分類需在發生點判定 |
| E-C 兩軸並記 | `source` + `recoverability` 兩欄 | 兩種查詢都可做 | 每個發生點要判兩次，實作成本最高 |

### Q3 落地位置

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| L-A App 自管檔案 | `~/Library/Logs/<bundle id>/`（沙盒已關閉可寫） | macOS 慣例位置，Console.app 可瀏覽；純 Dart 可寫，不需原生橋接 | 輪替、保留、清除全由 App 負責 |
| L-B 系統 unified logging | 經 platform channel 寫 `os_log` | 保留與清除由系統管；不新增 App 持有的檔案 | 需原生橋接；使用者匯出要 `log show` 指令；Dart 端測試只能測到 channel 邊界 |

排除：寫入工作區內（會出現在使用者的 `git status`，且讓使用者 repo 成為 log 持有者）。

### Q4 保留策略（Q3 選 L-A 才需裁；L-B 由系統管）

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| R-A 依大小輪替 | 單檔上限 N MB、保留 K 檔 | 磁碟上限固定 | 高頻事件（監看、掃描）可能把幾天前的崩潰前紀錄擠掉 |
| R-B 依日期分檔 | 每日一檔、啟動時刪除超過 N 天者 | 「哪天出事」直接對應檔名 | 單日爆量時無上限，需另加單檔上限 |

### Q5 C-2 界線的強制方式

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| C-A 型別層白名單 | fields 值只收 enum、數字、布林、工作區相對路徑、欄位名、SHA 等包裝型別，不收任意 String；錯誤只記 `runtimeType` 與分類，不記 `toString()` | 內容在編譯期就進不來，對應 C-2「約束位置在寫入層」 | 既有 43 檔的呼叫點需改寫；新事件要先定型別 |
| C-B 約定加測試 | fields 仍為 `Map<String, Object?>`；以規格條文、code review 與每個事件的測試斷言把關 | 遷移成本低 | 自由字串欄位是 C-2 指名的風險來源 1，靠審查會漏 |

附帶子題（兩候選皆需裁）：路徑記絕對路徑或工作區相對路徑。絕對路徑含 `/Users/<name>/`，使用者貼 log 求助時會外洩帳號名稱。

### Q6 規格歸屬

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| S-A 系統層章節 + 各 SPEC 事件表 | `docs/system-layer.md` 新增一節定格式、分類、落地、C-2；事件碼仍留在各 SPEC（SPEC-001/003/005/007 現已如此） | 符合「橫切、8 個 domain 無一以此為變更理由」；不新增 domain | system-layer 不是圖節點，無 SPEC 編號可被 traceability 引用 |
| S-B 新建橫切 SPEC | 獨立 SPEC（例：observability）定共用契約，各 SPEC 引用 | 可被追溯矩陣與票引用；有版本號 | 需決定放哪個 `docs/spec/{domain}/`，或新增不屬任何 domain 的位置，與「每個 domain 一份 domain-map」的結構不一致 |

### Q7 LogSink 統一（併入的 W3-549）

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| U-A 單一泛型 typedef | `LogSink<E extends Enum> = void Function(E event, Fields fields, {Level level, ErrorClass? error})`；事件 enum 仍各 domain 自有 | 4 種形狀收斂為 1；保留事件碼窮舉檢查；與 Q5 C-A 天然契合 | 8 個 port 與其測試全改；純字串三個需新增事件 enum |
| U-B 各 port 保留、統一 writer | 各 typedef 不動，生產預設實作改為轉呼共用 structured writer | 改動集中在 adapter 預設值，測試不動 | 4 種形狀並存；純字串三個仍無事件碼，落檔後只能全文搜尋 |

### Q8 與 developer.log 的關係

| 候選 | 內容 | 利 | 弊 |
|---|---|---|---|
| D-A 並寫 | structured writer 同時轉呼 `developer.log` | 開發時 DevTools 照舊可見 | 兩處輸出，等級對應要維護 |
| D-B 取代 | 生產只落檔，`developer.log` 只在 debug build | 單一出口 | 開發時要另開 log 檔觀察 |

### 後續（裁決後）

- 規格修改票（依 Q6）與實作票（writer、sink 統一、`reportFatalError` 落檔、既有呼叫遷移）建於 1.0.0（版本描述已列 structured log）或 1.x minor。
- 規格定稿前把變更摘要傳主控審查，再 commit。

裁決前不建票；裁決後逐項建立，本節屆時更新。
