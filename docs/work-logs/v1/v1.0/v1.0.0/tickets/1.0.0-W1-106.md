## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 框架問題兩條 AND 判準（escalation-flow）

1. **抽象可攜**：成立。抽換專案名稱與路徑後敘述仍成立：「doc skill 的 schema 只定義節點必填欄位與邊，未定義欄位值域；需要渲染表單或驗證欄位值的消費端拿不到機器可讀值域」。任何採用 doc skill、要編輯或驗證 frontmatter 的 consumer 都會遇到。
2. **根源在 `.claude/` 通用資產**：成立。值域散落在三處框架資產：`tracking_schema.py`（只有 EVT_CATEGORIES）、`doc_system/commands/update.py`（PROP 的 VALID_STATUSES）、`doc/templates/*.md` 的註解（SPEC／UC／EVT status、source、priority、platform 等）；沒有一處是全部欄位的權威。

### 實查（2026-11-10）

- 掃本專案 41 份節點 frontmatter（PROP 6、SPEC 8、UC 7、DomainBundle 8、EVT 12）。
- 機器定義的列舉：PROP status 5 值（`update.py` 的 `VALID_STATUSES`，`create.py` 另有一份 `VALID_PROPOSAL_STATUSES` 相同內容）、EVT category 2 值（`tracking_schema.EVT_CATEGORIES`）。
- 只在範本註解：SPEC／UC／EVT status（draft／review／approved／deprecated）、PROP source（5 值）、PROP priority（P0／P1／P2）、UC platform（3）、extension_status（3）、runtime_surface（2）。
- 無任何定義：PROP evaluation_level（語料 6 份皆為 heavy）。
- 附帶：doc validate 不檢查 SPEC／UC／EVT status 的值，寫錯值不會報錯。

### 查重紀錄

`gh issue list -R tarrragon/claude --state all --search` 關鍵字「值域」「允許值」「enum」「tracking_schema 欄位」「status 值」。
- #99（doc 文件圖譜 schema 的四項定義缺口，含「where.layer 值域無強制」）：同主題，本發現是 schema 定義缺口的另一項（節點欄位值域），判定為**引用並補觀測**，不另開 issue。
- #98（doc skill 建立端與驗證端各自實作契約）：相關（PROP status 在 update.py 與 create.py 各有一份），不重複。

### 拖慢專案

是。1.0 表單的下拉與單選以 schema 值域為來源（用戶裁定）；上游補上之前，無機器定義的欄位只能用單行文字輸入。

### 補充實測：CLI 與範本的值域互相矛盾（2026-11-10）

- `doc update SPEC-005 --status approved` → 「無效狀態: approved／有效值: draft, discussing, confirmed, implemented, withdrawn」，結束碼非 0，工作區無變更。`update.py` 的 `VALID_STATUSES` 不分型別，套用到全部文件。
- SPEC、UC、EVT 範本註解列的合法值是 draft／review／approved／deprecated。依範本把 SPEC 推進到 approved，CLI 會拒絕。
- 正向對照：同一 grep 在 `update.py` 命中 `draft`；`review|approved|deprecated` 在 doc CLI 的 Python 原始碼命中 0 次，`commands/validate.py` 不含任何 status 字樣，doc validate 不檢查 status 值。
