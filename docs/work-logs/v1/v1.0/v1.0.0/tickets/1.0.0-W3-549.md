### Task Reference
- 0.3.1-W3-132 what: 改為 日誌事件識別碼，使斷言脫離中文散文字面

### Rationale Chain
- 0.3.1-W3-132 why: Phase 4a 有三個視角獨立指出同一問題（linux 範本適用性、Coupling 耦合量測、basil 措辭一致性）：

`WorkspaceLogSink` 的簽章是 `(String message, {int? level, Object? error})`，**沒有獨立於文案的事件識別欄位**。訊息字串同時扮演「人類可讀文案」與「測試用事件識別碼」兩個角色。

Coupling 的實測：`workspace_repository.dart` 有 16 個 `_log()` 呼叫點，`workspace_repository_test.dart` 的 27 個測試中有 15 個綁在日誌文字上。改一句文案的連鎖：

- `'開啟資料夾選取面板'` → 打破 4 個測試（G1-1／G1-2／G1-3／G2-1）
- `'偏好設定儲存已就緒'` → 打破 3 個測試（G2-1／G3-1／G4-1）

矛盾在於穩定性宣告：這些字串在產品端標 `i18n-exempt: 開發者 debug log`（可自由改寫的內部文案），測試卻把它們當穩定契約比對。**同一個字串被兩份文件宣告成相反的穩定性等級。**

`'偏好設定儲存已就緒'` 另有獨立成因：`chooseFolder()` 與 `restore()` 各持一份相同字面值，只改其中一處會產生不對稱紅燈，看起來像「chooseFolder 的受理事件壞了」而非措辭不一致——假紅燈把診斷引向錯的方向。

basil 另指出五則「呼叫發出」事件用了三種句型（只有一則帶「準備」前綴），日誌讀者無法用單一措辭特徵撈出所有呼叫發出點。

範本效應：本檔形態將被複製到 `0.1.0-W1-068`（ExternalOpener）、`0.1.0-W3-112`、`0.1.0-W1-014` 三個 driven port。不先修，四個 port 會各自累積掛在中文字面上的斷言。
