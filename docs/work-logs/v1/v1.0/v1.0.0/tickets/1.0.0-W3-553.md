### WRAP：domain 數量上限是否合理

**錨點**：要決定的是編輯能力的規格與職責放在哪個 domain；「domain 已 8 個、觸及上限」被當成反對新建 edit domain 的理由，需先判定這個上限能不能當理由。

**Step 0 資料**：上限出處為 `.claude/skills/saas-tech-selection/references/domain-event-modeling.md`〈切太粗與切太細的訊號〉末句：「MVP 階段的 domain 數量參考：3-6 個是常態（帳號／核心業務一到兩個／計費／通知）。超過 8 個先懷疑切太細」。同段的判準本體是 SRP 三問與兩個訊號（兩個 domain 永遠在同一個 PR 裡一起改；event 來回打乒乓）。數量句的語意是「先懷疑」，作用是提醒去跑訊號檢查，不是上限；其基準為 SaaS MVP 的典型組成，本專案是桌面文件工具，組成不同。

**W 選項**：
- a 數量當上限：維持 8 個，編輯併入 corpus。
- b 數量只當檢查觸發：每新增一個 domain，對最近鄰 domain 跑 SRP 三問與共現檢查，通過即可新增。
- c 完全不看數量：只看 SRP 三問。
- 反向檢查：若「8 個太多」為真，應能觀測到某些 domain 對永遠一起改。

**R 實測（2026-11-10，`git log --no-merges -- lib/`，463 個 commit）**：
- 各 domain 觸及 commit 數：graph 49、corpus 37、workspace 34、schema 32、diagnostics 25、history 8、ticket_detail 5、layout 5。
- 共現率（同時觸及兩者的 commit 數 ÷ 兩者中較少的那個）最高五組：graph×ticket_detail 0.40（2 筆，樣本小）、diagnostics×graph 0.24、graph×schema 0.22、corpus×diagnostics 0.20、corpus×ticket_detail 0.20。
- 沒有任何一對接近「永遠一起改」。依同一份參考的訊號本體，8 個 domain 沒有切太細的證據。

**編輯能力的 SRP 三問（對最近鄰 corpus）**：
1. 同一個變更理由？corpus 因文件格式與解析語意而改；寫入路徑因資料安全政策（三平面閘門、快照、變更記錄）、git 互動與 CLI 驗證介面而改。理由不同。共用處只有 frontmatter 的序列化格式，可由單向依賴的共用編解碼承接。
2. 誰說了算（一人專案改問交接邊界）？寫入安全與解析器可分開交接。
3. 同詞異義？「文件」在 corpus 是解析後的節點與破洞，在寫入路徑是磁碟上的位元組與三個平面（HEAD、工作目錄、App 記憶體）。
- 依賴面：寫入路徑依賴 git（快照、HEAD 比對、commit）與 doc CLI，corpus 兩者皆不依賴。檔案監看已活躍，寫入後由監看事件觸發 corpus 重掃，寫入路徑不必直接呼叫 corpus。

**A 拉開距離**：1.x 會擴充可編輯的對象；寫入路徑放在 corpus，corpus 會同時承載讀與寫兩個變更理由，之後再拆的成本隨功能累積上升。新建 domain 的代價是多一份 domain-map 與系統層通道登記。

**P 失敗預想**：
- 編輯與 corpus 因 frontmatter 格式在多數 PR 共現。早期訊號：前 10 個觸及寫入路徑的 commit 中，同時觸及 lib/corpus/ 的過半。處置：依 §4.5 合併。
- edit domain 退化成資料表式的 CRUD 管理者。早期訊號：domain-map 的 command 清單出現 Create／Update／Delete 而非業務操作。

**結論**：數量句是 SaaS MVP 情境的先驗提醒，不能當上限；本專案的可操作判準是 SRP 三問與共現訊號，實測不支持「8 個太多」。PM 建議：系統層 §4.5 改寫為「數量只觸發檢查」，並附本次實測；編輯能力依 SRP 三問新建 edit domain。
