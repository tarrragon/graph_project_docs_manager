### 問題根因

PROP-005 §1.0 已定 1.0 為編輯能力 major，巨觀形態為「本 App 直接改檔、CLI 僅作驗證器」（`docs/system-layer.md` §4.4）；寫入前閘門與寫入後義務的五項結論已在 `docs/tech-decisions.md`〈2026-09-10：加入編輯能力 tripwire 的重評〉。落為規格前尚缺四項子決策，現住 `docs/system-layer.md` §6〈編輯能力四項架構決策與規格前置未完成〉。SPEC-004 §2 樂觀更新政策列、系統層 §6、CLAUDE.md §6 三處 trigger 指向本票。

### 影響範圍（2026-11-10 實查）

- where.files 的 `docs/domain-map.md` 已不存在（`0.5.0-W1-070.3` 拆檔），四項知識現住 `docs/system-layer.md` §6。
- 前提變動一：實作層已有寫入，但不是使用者內容。`lib/services/file_watch_canary_io.dart` 在 `docs/` 第一層寫入並刪除空的金絲雀檔（SPEC-006 FR-11 規則 10）。覆寫使用者檔案的路徑仍為 0。
- 前提變動二：檔案監看已活躍（`lib/corpus/corpus_watch.dart`，SPEC-006 FR-11）。2026-09-10 A-2 寫明「監看轉為活躍時本項應一併重評」：外部改動的發現時點可提前到修改當下；寫入當下的比對仍要保留，因為監看事件有延遲，且有漏事件的實例（system-misjudgment FS 系列）。
- CLI 驗證延遲實測（本機，經 shim）：`doc validate SPEC-006` 0.35 秒、`doc uc verify` 0.52 秒。
- PROP-005 §1.0 的上游阻擋 `0.2.1-W3-1119`／`1120`（驗證器繞過 id_pattern、uc verify 分不出提及與使用）：本專案票庫與 llm-dev docs 皆查無這兩個票號，現況待查，列入規劃波待辦。

### 四項子決策的分析

1. **規格檔路徑**：寫入責任屬 Corpus（系統層 §4.4）。domain 已 8 個，系統層 §4.5 記為觸及上限；新開 edit domain 會超過。SPEC-006 已承載解析、破洞分類與監看，再加寫入會讓一份規格承載三種職責。承接關係：樂觀更新政策列屬 UI 元件層，留在 SPEC-004 §2；三個可觀測時刻與寫入結果型別寫進編輯規格，SPEC-004 該列改引編輯規格。
2. **寫入前閘門判準**：2026-09-10 A-1 表依 git 狀態分三列（已追蹤無變更、已追蹤有未提交變更、非 git 工作區），git 工作區內的未追蹤檔不在表內，屬未定義行為。三平面單一述詞：寫入前讀工作目錄內容 W，與 App 記憶體 M、HEAD 內容 H 比較。W 不等於 M 時，判定外部已改，阻擋（A-2）。W 不等於 H 時（含檔案未追蹤、H 不存在），先 `git hash-object -w` 快照 W 再寫入；快照失敗時退回阻擋（A-1）。未追蹤檔因 H 不存在，自動落入快照分支。
3. **structured log 延後**：W1-013 的三個理由中，「不擁有資料」與「唯讀」已隨編輯能力失效，只剩「單機無伺服器可收 log」。寫入路徑的事後追溯已有兩個載體：B 組由 App 產生的 commit message，以及 A-1 的快照 SHA。錯誤的載體是畫面（2026-08-27 裁決三）。
4. **樂觀更新的可觀測時刻**：寫入是本機寫檔；CLI 驗證實測約 0.35～0.5 秒。三個時刻：發出（閘門通過、寫入呼叫發出）、受理（寫入呼叫回傳、位元組已落檔）、結果（驗證器判定）。寫入 port 回傳型別化結果（成功、閘門阻擋附原因、IO 失敗），呼叫端據此區分「寫入成功」與「失敗被降級」，不以日誌抵扣。
