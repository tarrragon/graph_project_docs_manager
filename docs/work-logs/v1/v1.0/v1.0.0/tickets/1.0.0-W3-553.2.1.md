## Problem Analysis
### 問題根因

1.0.0-W3-553.2 的裁決把 structured log 規格歸屬定為新建 observability domain。依 tech-decisions〈domain 數量：只觸發檢查，不是上限〉，新增前須先對最近鄰 domain 做 SRP 三問與共現檢查。本節是這道閘門。

### 影響範圍

最近鄰：diagnostics。理由：兩者都處理「出了問題」，且〈2026-08-27〉裁決三已劃分「文件層問題進破洞報告、App 層失敗進畫面錯誤態」，最容易被認為是同一職責。

**共現實測**（main f7b0e9ec0c，2026-11-10）：observability 尚無 `lib/` 目錄，以現有 8 個宣告 LogSink／LogEvent 的檔案代理（`grep -rlE "typedef .*LogSink|enum .*LogEvent" lib`），對 `lib/diagnostics/` 計算 `git log --no-merges`。

| 集合 | commit 數 |
|---|---|
| 觸及 LogSink／LogEvent 檔 | 51 |
| 觸及 lib/diagnostics/ | 25 |
| 兩者同時 | 1（3db34b43aa，只改註解中的舊路徑引用） |

共現率 1 ÷ 25 = 0.04，低於 2026-11-10 實測 8 domain 的最高值 0.40。代理集合的限制：只量到既有日誌宣告，量不到落檔後的 writer。

**SRP 三問（對 diagnostics）**：
1. 同一個變更理由？diagnostics 的唯一變更理由是「什麼算破洞」的定義改變（domain-map §1）。observability 因記錄格式、錯誤來源分類、落地與保留政策、C-2 白名單型別而改。理由不同。
2. 交接邊界？破洞判定與日誌記錄可以分開交接：前者要懂文件 schema，後者要懂平台 IO 與保留政策。
3. 同詞異義？「錯誤」在 diagnostics 是文件內容的缺陷（破洞，使用者要修文件）；在 observability 是 App 執行期的失敗（error_source，給開發者與求助時用）。

**邊界風險**（寫進 SPEC）：解析失敗同時落在兩邊。文件內容造成的解析失敗是破洞，log 只記識別（路徑、事件碼）；解析器本身拋出未預期例外歸 `internal`。若同一個解析失敗在兩邊各寫一套判定，即為職責重疊的早期訊號。

**判定**：通過，可新建 observability domain。
