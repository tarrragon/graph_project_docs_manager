## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

框架〈實機驗證票〉（`.claude/pm-rules/verification-framework.md`）只規定「誰驗」「何時開票」與「名額閘門」，沒有規定「驗的是哪個程序」與「驗完如何收尾」。共用一台機器時，有三個缺口：

1. **截圖前沒有辨識實例**：截圖前沒有用前景 pid（`lsappinfo front`）確認截到的是自己啟動的實例。0.7.0-W1-007.5 上午的英文選單截圖，實際前景很可能是另一個 session 留下的同 bundle id 實例（PID 51632）。當時拿「結束 59780 後選單列改變」當作歸屬證據，但結束任何 App 都會讓前景重排，這不能證明歸屬。
2. **驗完沒有結束自己的實例**：殘留的實例會讓後續驗證者截錯畫面。PID 51632 就是這類殘留。
3. **驗證前沒有確認閘門是否正在跑 macOS integration**：合併閘門的 integration_test 會啟動同 bundle id 的 App 並把它帶到前景。驗證者若在這時啟動同 bundle id 的實例，兩邊會搶前景。時序證據（0.7.0-W1-007.10 Problem Analysis）：閘門測試 App（PID 44685）12:15:34 啟動；L53 12:16:14 以 Contents/MacOS 執行檔啟動同 bundle id 實例（PID 46787），12:16:2x 以 open 帶到前景，數秒後結束；該次閘門的 flutter-integration 900 秒逾時，log 有「Failed to foreground app; open returned 1」。**因果未定**：該訊息在 log 中位於 L53 啟動之前，故只當作時序證據，不當作已證實的干擾。

三點同根：驗證者以推定（記錄平面）判定程序歸屬，沒有查程序清單或前景 pid（世界平面）；後果由並行的其他驗證者或閘門承擔。

### 影響範圍

- 已驗證：007.5 誤判延誤約兩小時，並觸發一次不必要的在地化假設排查；以前景 pid 重驗後確認在地化已生效。
- 已驗證：同機曾同時存在至少兩個同 bundle id 的實例（51632 與受測實例）。
- 未驗證：L53 啟動的實例是否造成 007.10 第一次閘門逾時（見第 3 點的因果未定）。
