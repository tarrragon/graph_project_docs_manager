### 實驗發現

已驗證：
1. 7 份 test-design 中有 5 份落後，落後最多 55 個版本。只比對版本號，會對 5 份同時報警。
2. 落後區間的變更多數不影響測試。四種情形：〈概述〉補一段（SPEC-006 1.42、SPEC-007 1.43、SPEC-008 1.3，自述「不改契約」）、票號更正、時效註記、引用字面更正。只比對 spec_version 的偵測，雜訊遠多於訊號。
3. 「含驗收」字面也不是可靠訊號。SPEC-001 是狀態矩陣，測試由矩陣列推導，不以「驗收」一詞表述，55 列中只命中 5 列。字面分類兩個方向都會錯。
4. 測試來源不只 test-design 一處。SPEC-003 的測試設計寫在規格本身（§2.17、§4 testKey），且 SPEC-002～005 沒有 test-design。以 test-design 為唯一測試來源的偵測，對這些 SPEC 沒有射程。
5. 現行 `spec_version` 的語意是「test-design 內容已同步到的版本」。審視過、確認無測試影響的版本，沒有地方留紀錄。因此「已審、無影響」與「未審」在 frontmatter 上同形。這是無聲缺漏的根因：不是缺檢查，而是欄位裝不下「已審」這個事實。

未驗證：SPEC-006／007／001 落後區間的「含驗收」列，test-design 是否實際缺案例。這需要逐列對照，量大，不在本票範圍；見 Solution 的 spawn 規劃。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論（2026-11-11，用戶裁定採 A，經主控 AUQ；排進 1.1）

1. **spec_version 語意改為「已審視到的版本」**：test-design 的 `spec_version` 記的是「來源 SPEC 已被審視到哪一版」，不再是「內容已同步到哪一版」。審視後確認無測試影響時，同樣把它改成新版號，並在 test-design 的變更記錄寫一句「v1.x 已審，無測試影響」。這樣「已審無影響」就與「未審」區分得開，這正是無聲缺漏的根因（見〈實驗發現〉第 5 點）。
2. **偵測：Dart 契約測試**：要求每份 test-design 的 `spec_version` 等於 `source_spec` 現行的 `version`，不等即紅燈。放在 `test/unit/`，比照 `spec004_key_table_contract_test.dart` 這個讀 docs 的先例。`doc validate` 屬框架資產，不擴充。
3. **流程**：改 SPEC 的票同批審視對應的 test-design；票的 where.files 含該 test-design。
4. **同批落地**：偵測機制與 5 份落後文件的回填須同批進 main，否則新測試一上線就紅燈。兩張票互設依賴。
