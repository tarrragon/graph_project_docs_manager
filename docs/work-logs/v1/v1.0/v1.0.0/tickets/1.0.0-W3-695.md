### 問題根因

直接原因無法以重現確認（10/10 綠燈）。結構性原因已確認：O3-1 setUpAll（test/observability_contract_test.dart 的 analyzeFixture）只保留 stdout+stderr 中以 `ERROR|` 開頭的行，不檢查 `exitCode`、不保留原始輸出。analyzer 只要沒有以正常 machine 格式結束（崩潰、被系統殺掉、啟動失敗、輸出非 machine 格式），negative 就得到 `[]`，positive 同時假綠。閘門 log 中 positive 綠、negative 為 `[]`，與「analyzer 這次沒正常產出」相符，與「守衛本身失效」不可區分。

### 影響範圍

- 已驗證：test/observability_contract_test.dart O3-1；test/edit_contract_test.dart P-9 的 `_analyze` 同樣只看輸出字串（`contains('error')`），positive 在 analyzer 異常時同樣假綠。
- 已驗證：兩檔暫存目錄不同（.dart_tool/observability_whitelist_guard、.dart_tool/p9_negative），tearDown 互不刪除對方檔案。
- 未驗證假設：閘門那次 analyzer 異常的具體形態（崩潰／記憶體／被殺／輸出格式）。閘門 log 顯示 setUpAll 自 09:16 持續到 11:44（約 2.5 分鐘），當時全套件並行，負載高於本次取樣。

### 判定

- 並行干擾（O3-1 與 P-9 互擾）：不支持。兩檔暫存目錄不同，b 組 5/5 綠，三個 analyze 同時跑皆正常。
- 輸出格式：正常情況下格式穩定；異常情況下的格式無法取得（閘門未保留原始輸出）。
- 負載：單跑在 load 45 下仍綠；閘門那次 setUpAll 長約 2.5 分鐘，屬全套件並行下的更高壓力，無法排除。
- 其他／結構性成因（確認）：守衛不檢查 exitCode 也不保留原始輸出，analyzer 任何非正常結束都被判成「0 個 error」。本次紅燈的直接觸發無法以目前證據定案，下次重現時能否定案，取決於守衛是否帶出 exitCode 與原始輸出。

### 處置建議

1. 承接票 `1.0.0-W3-695.1`（scope_blocker，P1）：O3-1 與 P-9 斷言 exitCode（negative=3、positive=0），失敗訊息帶出 exitCode 與原始 stdout/stderr。效果：analyzer 異常時兩個案例都紅且訊息可判讀，不再出現 positive 假綠、negative 空清單。
2. 下次閘門重現時，依失敗訊息中的 exitCode 與原始輸出回到本票判定（崩潰／被殺／格式），再決定是否需要序列化或加重試。
