## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

前移目標由 `compute_overflow_target_version`（version-release）計算，規則兩段：先 `find_open_successor`
取「todolist 中排在凍結版本之後、status 為 planned/active、未凍結的最小版本」，命中即回傳、**不看票型與動詞**；
未命中才走動詞分類（IMP + 新功能動詞 → minor+1，其餘 → patch+1）。

分歧來自兩段規則的切換由 todolist 登記狀態決定，而登記本身是 finish 要求的前置：

1. dry-run 當下 todolist 無 0.3.1、0.4.0 → successor 為 None → 動詞分類 → 7 張新功能票算到 0.4.0、其餘 0.3.1。
2. `migrate_overflow_tickets` 的前置檢查要求「前移目標版本須已在 todolist 登記」，擋下並列出 0.3.1、0.4.0。
3. 依提示登記兩者（`4aa6b281e`，14:44）後，successor = 0.3.1（最小開放後繼）→ 70 張全部路由至 0.3.1（`4cd0db798`，14:48）。

即：預覽算出的目標集合要求被登記，登記後規則切換到不分票型的第一段，推翻了預覽本身。dry-run 失去鑑別力不是
dry-run 與實際走不同程式碼，而是同一函式在輸入狀態改變後給出不同結果，且狀態改變由工具自己要求。

### 影響範圍

- 已驗證：`.claude/skills/version-release/scripts/version_release.py` 的 `compute_overflow_target_version`；
  ticket skill `ticket_system/lib/version.py` 的 `suggest_overflow_version` 為同一規則的鏡射（兩段順序相同），
  建票凍結閘門的「建議去處」同樣不分票型。
- 已驗證：只要凍結版本之後同時登記了 patch 與 minor 後繼，新功能票一律落入 patch，minor 後繼永遠不可達。
- 未驗證：其他 consumer 是否已因此把新功能票發進 patch 版本（本 consumer 之外無資料）。

### 相關 Error Pattern

以 `dry-run|預覽` 與 `successor|開放後繼|前移` 掃 `.claude/error-patterns/`：最近者為 PC-152（migrate 撞號，
dry-run 與實際行為落差），機制不同——PC-152 是包裝層未轉達警告，本案是預覽要求的前置步驟改寫了預覽的輸入。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 分析結論

分歧位置為 `compute_overflow_target_version` 的「後繼優先」段不分票型（見 Problem Analysis）；dry-run 與實際
走同一函式，差別在 finish 的前置檢查要求登記目標版本，登記後輸入改變。

### 框架問題兩條 AND 判準（逐條）

| 判準 | 判定 | 依據 |
|---|---|---|
| 抽象可攜：替換本專案名稱與路徑後仍成立 | 成立 | 任何 consumer 在凍結版本後同時登記 patch 與 minor 後繼，新功能票即落入 patch；與本專案內容無關 |
| 根源在 `.claude/` 通用資產 | 成立 | `version-release` 的 `compute_overflow_target_version` 與 ticket skill 的 `suggest_overflow_version` 皆屬框架 skill |

兩條皆成立 → 框架問題，依 framework-issue 流程登記，不在本地修（本地修會被下次 sync-pull 覆蓋）。

### 查重與關係判定

- `dedup --keywords "find_open_successor overflow 前移 開放後繼 finish"`：命中 #55、#101、#16、#92 等。
- #55（ticket CLI 契約缺口叢集）：「後繼優先」規則出自其 WRAP 結論，且已累積 finish 前移的多則觀測
  （收尾提交範圍、index.lock、撞號）；以「開放後繼／最近的」掃其全部 comment，無票型不分或預覽自我推翻的記錄。
  關係 = **同領域新觀測**，以 `observe` 附加至 #55，不另開 issue。
- #16（版本生命週期推進）：引用關係，不重複。#101、#92：命中詞在無關段落，無關係。

### 候選修法（交 canonical 裁決）

| 方案 | 做法 | 利 | 弊 |
|---|---|---|---|
| A 分類後繼 | 先依票型分類，再在對應類別內找最小開放後繼：新功能找 minor 大於凍結版本且 patch 為 0 者，其餘找同 minor 的 patch 後繼；找不到才走動詞計算 | 保留「只建議已登記版本」的原意，同時修正票型不分；預覽與實際在登記前後結果一致 | 兩個 skill 需同步改（既有鏡射漂移風險，#55 已記錄） |
| B 預覽對齊 | finish 先檢查並要求登記，再印前移預覽 | 消除自我推翻 | 不修票型不分：預覽會如實顯示全部進 patch，錯誤仍在 |
| C 移除後繼優先 | 只用動詞計算 + 目標須已登記 | 最簡單 | 回退 #55 採後繼優先的理由（凍結版本後已有非相鄰後繼時建議落空） |

傾向 A：B 只讓錯誤變得可見，C 回退既有決策。
