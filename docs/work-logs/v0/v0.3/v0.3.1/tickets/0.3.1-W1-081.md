### 實驗方法

以 `tracking_schema.py` 的 `GRAPH_NODE_TYPES` 取各型 `carrier_path_patterns` 與 `id_pattern`，對五個語料專案的 `docs/**/*.md` 執行判定鏈：列舉 → 逐行語意解析 frontmatter（禁 `split("---")`）→ carrier 比對 → id 比對。目標集合 = frontmatter 可用 AND 位於某型 carrier 內 AND（id 缺席 OR 不命中任何 id_pattern）。

### 實驗發現

1. **壓倒性主因是子票 dot 後綴**（85.8%）：`id_pattern` 為 `^[\w.]+-W\d+-\d+$`，末段只允許純數字（`\d+`），但語料中大量子票使用 `NNN.M` 形態（如 `623.2`、`1192.11`、`795.2.1`），這不是「舊格式」而是**現行框架的子票命名慣例未被 id_pattern 收納**。
2. **id 缺席集中於 book_overview_app**（179/183）：該專案早期版本的 ticket 檔 frontmatter 無 `id` key。
3. **少量邊緣成因**（SIM 前綴、phase companion、大小寫、SPEC 後綴字母）合計 25 筆，佔 1.7%，各為獨立的歷史慣例殘留。
4. **與 SPEC-006 FR-03 的偏差**：FR-03 將此類檔案描述為「有 frontmatter 的非節點，本版不列」，但實測顯示 85.8% 其實**意圖成為合法節點**（子票），只是 id_pattern 未涵蓋其命名形態——這不是「非節點」而是「pattern 缺口」。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 候選方案比較

三個候選方案逐項利弊，對照實測分布（目標集合 1465 筆，子票 dot 後綴佔 85.8%）：

#### (a) parseFailure 新原因碼

為 `parseFailure` 新增原因碼（如 `id_pattern_mismatch`），將這類檔案歸入「解析可達但 id 不合法」的破洞。

| 面向 | 評估 |
|------|------|
| 利 | 語意精確：區分「frontmatter 解析失敗」與「frontmatter 正常但 id 不合法」；App 可呈現修復建議（如「id 格式應為 X」） |
| 利 | 實測分布支持：85.8% 是子票 dot 後綴，確實是「可修復的 id 格式問題」，歸 parseFailure 語意合理 |
| 弊 | parseFailure 原定義是「frontmatter 解析本身的失敗」，id 格式不符嚴格說是「驗證失敗」非「解析失敗」，概念混用風險 |
| 弊 | 新增原因碼需修 tracking_schema 的 parseFailure 定義 |

#### (b) 另立破洞類別

新增獨立破洞類別（如 `idMismatch`），與 parseFailure 平行。

| 面向 | 評估 |
|------|------|
| 利 | 語意最乾淨：解析失敗（parseFailure）vs id 驗證失敗（idMismatch）各自獨立 |
| 利 | 擴充性佳：日後 id 格式演進，此類別自然承接 |
| 弊 | schema 新增一個 gap 類別的成本較高（需同步 SPEC-006、App 渲染、gap report） |
| 弊 | 實測 1465 筆中 85.8% 可透過擴充 id_pattern 消除（`\d+` → `\d+(\.\d+)*`），若 pattern 修正後此類別可能近乎空集 |

#### (c) 不報（維持 FR-03 現行）

維持 SPEC-006 FR-03「有 frontmatter 的非節點，本版不列節點也不列破洞」。

| 面向 | 評估 |
|------|------|
| 利 | 零成本，無需改動 |
| 弊 | FR-03 的前提假設（「這些是非節點」）與實測不符——85.8% 意圖為合法子票節點，只是 id_pattern 未收納 |
| 弊 | 靜默丟棄 1257 筆子票，gap report 的「完整性」承諾打折 |

### 補充觀察：根因可能不在歸類而在 id_pattern

實測最關鍵的分布特徵：**85.8% 的目標集合並非「非節點誤放」或「舊格式殘留」，而是現行框架的子票命名慣例（`NNN.M`）未被 Ticket 型的 `id_pattern`（`^[\w.]+-W\d+-\d+$`）收納**。若將 id_pattern 修正為 `^[\w.]+-W\d+-\d+(\.\d+)*$`，這 1257 筆立即變為合法節點，目標集合縮至 208 筆（id 缺席 183 + 邊緣成因 25）。

此時三案的利弊天平大幅傾斜：目標集合縮至 208 筆後，(c) 不報的「丟棄量」可接受度提高；(a)(b) 的投入產出比下降。但 pattern 修正本身是否該做、是否屬本版範圍，需用戶裁決。

**結論待用戶裁決**。

### 用戶裁決（2026-09-29）

1. **破洞歸類**：修正 pattern 後剩餘的 208 筆（id 缺席 183、歷史格式 25）歸 `parseFailure` 新原因碼（`idMissing`／`idPatternMismatch`）。理由：與現行「carrier 內缺 frontmatter」歸 `parseFailure` 同構（皆為「位於 carrier、應為節點而成不了節點」），破洞類別數不變，原因碼為資料值（SPEC-006 FR-08）。否決：另立類別（成本高、需同步畫面分節）、不報（208 筆靜默消失）。
2. **id_pattern 缺陷**：本專案直接修，但先寫 framework issue 再修。
