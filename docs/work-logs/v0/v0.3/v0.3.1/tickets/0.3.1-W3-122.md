### 排序約束：本票應在 `0.1.0-W3-078` 實機驗證之後（PM，2026-09-08）

**本票會關上 `0.1.0-W3-078` 目前開著的觀測窗口，因此順序不可顛倒。**

現況（本票要修的缺陷）意外地讓通知路徑**容易觸達**：掃描在 App 啟動當下完成，那一刻 `destination` 是 `domain` 而非 `gaps`，SPEC-003 §2.2 觸發條件 (b) 成立，通知因此會發送。`0.1.0-W3-078` 要驗的四項平台事實（`UNUserNotificationCenter` 可用性、未簽章 build 的授權回應、撤回 API 效果）都需要通知真的送出才觀測得到——**現在啟動 App 就會發生**。

本票修好之後，觸發點移至首次可見 `nav-page-gaps`。屆時使用者正看著該頁，條件 (b) 不成立；條件 (a)（視窗非前景）則因掃描仍是零耗時（`0.1.0-W3-096` 的 D2，屬階段落差、不在本票範圍）而來不及讓使用者切換視窗。**通知將重新變得難以觸達**，直到真實掃描接上資料源為止。

因此正確順序是：先跑 `0.1.0-W3-078` 的實機驗證取得四項平台事實，再修本票。倒過來做會把一個現成的觀測機會關掉，而其中「未簽章 debug build 的授權請求回應」是**一個 build 只有一次**的觀測（授權一旦授予不可逆）。

本節不改變本票的技術內容，只約束執行時機。`0.1.0-W3-078` 完成後本節即失效，屆時可直接派發。

### 退回修正（PM 合併後全套測試 35 個失敗，pumpAndSettle timed out）

**根因**（依 PM 提供固定值重現確認）：`GapReportNotifier.build()` 在「圖已建立但尚未首次可見 gaps 頁」時回傳 `const GapReportScanning()` 作為佔位，但 `AppShell` 以 `IndexedStack` 一次建構六頁（`lib/app/router.dart` 註解「SPEC-003 §2.8：IndexedStack 一次建構六頁」），gaps 頁即使未被選取仍持續存在於 widget tree。`_ScanningView`（`gap_report_screen.dart`）使用 `LoadingState.skeleton`，其 shimmer 用 `AnimationController..repeat(reverse: true)` 無限循環（`lib/components/loading_state.dart`）。修復前掃描在 App 啟動的 build() 內立即完成（`Motion.spinnerMinVisible` 後轉 Found/NoGaps），骨架動畫短暫存在後即被真實內容取代；修復後掃描永不觸發（因目的地非 gaps），骨架狀態與其無限動畫永久停留，任何經 `pumpApp`（完整 App）呼叫 `pumpAndSettle` 的測試皆逾時（`project_switcher_test.dart`／`domain_view_test.dart`／`ticket_list_test.dart`／`node_detail_test.dart`／`test/widget/app/shell_test.dart` 等）。

**修法**：`build()` 的「圖已建立但尚未首次可見」分支改回傳 `const GapReportProjectUnready()`（既有狀態，`EmptyState` 靜態渲染，無動畫）取代原本誤用的 `GapReportScanning()`。理由：
1. 使用者尚未選取本頁時，此佔位內容不會被實際看見（IndexedStack 非選取分頁的畫面內容對使用者不可見，只是仍存在於 widget tree）。
2. 選取 gaps 頁當下，`firstVisibleProvider(gaps)` 已於同一次 provider 重算中同步翻為 `true`（Riverpod 狀態變更的依賴傳播是同步的），故不會有「先閃一下 ProjectUnready 文字才轉 Scanning」的可觀察殘影。
3. `GapReportHeaderTrailing`（重新掃描鈕）對 `!NoGaps && !Found` 一律渲染 `SizedBox.shrink()`，`ProjectUnready` 與原本的 `Scanning` 佔位在此處行為一致，不受影響。

**新增邊界處理**：`!graphBuiltProvider` 分支（原有，因圖未建立而非因未首次可見）刻意**不寫入 `_lastResult`**——`IndexedStack` 使圖建立狀態可能在已觸發過掃描後又反覆變化（例如切換專案）；若在此覆寫 `_lastResult`，圖重新建立後會誤判為「首次進入」的佔位態，而非恢復已完成的掃描結果。修正後：已觸發過掃描時，圖狀態的 true→false→true 往返會先渲染 `ProjectUnready`（圖未建立期間），圖重建後立即恢復 `_lastResult`（已完成的掃描結果），不重新掃描、不卡在佔位態。

### 補充情境測試（要求 3）

`gap_report_provider_test.dart` 新增兩則：
1. `graphBuiltProvider` 由 true→false→true 往返：驗證已觸發過掃描的結果在圖重建後正確恢復（不覆寫 `_lastResult`、不卡在 `ProjectUnready`、不重新掃描）。
2. 首次可見時圖尚未建立、之後圖才建立：驗證 `!graphBuilt` 早退分支不建立 `firstVisibleProvider` 依賴時，圖建立後仍能正確重新判定 `isFirstVisible` 並觸發首次掃描（不因未建立期間被視為已訪問而卡住——因為 `firstVisibleProvider` 從未在該期間被 watch，其副作用寫回也從未執行）。

兩則測試皆使用可動態切換的 `_graphBuiltState`（`StateProvider<bool>`）間接覆寫 `graphBuiltProvider`（原生為不可變 `Provider<bool>`），並在狀態切換後手動 `container.read(gapReportProvider.notifier)` 強制建構——因 riverpod 對無活躍監聽者的 provider 採惰性重算，狀態變更不會立即觸發 rebuild。

### Rationale Chain

機制（PM 已讀原始碼確認）：`gap_report_provider.dart` 的 `_scheduleScan()` 是 `Future.microtask(_completeScan)`——掃描在**同一幀的 microtask 內完成**。由此推出兩件事：

1. **`state-gaps-scanning` 骨架存在時間短於一幀**，畫面上不可能看到。SPEC-003 §3.5 明訂「重新掃描時現有結果立即被骨架取代」，該骨架實際從未被繪出。
2. **系統通知的觸發條件結構性不可達**。SPEC-003 §2.2 的觸發條件是「完成當下視窗非前景，或可見頁非 `nav-page-gaps`」。完成發生在按鈕點擊的同一個 microtask 內，而按鈕點擊必然發生在視窗前景且使用者正看著破洞報告頁——**兩個條件都不可能為真**。授權因此永不請求（`notDetermined` 僅於首次觸發時請求），通知永不發送。

後果分三層：

- `0.1.0-W3-078` 要驗的四項平台事實中，至少三項（授權可用性、未簽章 build 的授權回應、撤回 API 效果）**在此實作下無法以任何操作觸達**，實機驗證無從進行。
- SPEC-003 §2.2 整節（觸發條件、不發送情境、權限 gate 三路徑、撤回三時機）與 §3.5 的骨架列，在現行實作下皆為**描述了一個不會發生的情境**的規格。
- `test/` 的 fake 直接設定狀態與 provider 值，繞過真實的完成時機，因此沒有任何測試會察覺這件事——與 `0.1.0-W3-094`（固定高度裁切）同屬「測試綠燈但實機不成立」。

**這不是說掃描應該變慢**。真實掃描（讀取檔案、解析 frontmatter）本來就需要時間；問題在於現行實作以 fixture 常數取代掃描，把耗時降為零，順帶讓所有依賴「掃描期間」的規格行為失去存在空間。（來源已完成，結論見 Solution）
