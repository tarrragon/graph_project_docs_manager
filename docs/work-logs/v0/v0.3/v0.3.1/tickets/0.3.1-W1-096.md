### Rationale Chain
- 0.3.1-W1-028 why: W3-064 acceptance 2、3 承接，平台事實只有實機能驗
- 0.3.1-W3-113 why: `0.1.0-W3-103` 盤點頁面層接線時的附帶發現：`ScanNotificationController.show()` 失敗時**沒有 SnackBar fallback**——`MacosScanNotifier` 內部 catch 之後靜默回傳，controller 不知道發送失敗，使用者在非 `nav-page-gaps` 頁面因此不會收到掃描完成的任何通知。

SPEC-003 §2.2 為權限 `denied` 定義了 fallback（`AppSnackBar.withAction` + `viewGapsAction`，非前景時延後至 `resumed`），但那是**授權被拒**的路徑。**發送本身失敗**（授權已 granted 但 `show` 拋例外或平台回錯）沒有對應條文，實作也沒有處置。

這是 `ARCH-GPD-001` 的第三層（event 效果）在失敗時消失的實例：成功時有系統通知，失敗時什麼都沒有——回饋與服務可用性正相關。且失敗被 `MacosScanNotifier` 的 catch 收斂為靜默回傳，符合〈降級不解除回饋義務〉所述「收斂到一個沒有表現的狀態，等同銷毀證據」。

**blockedBy `0.1.0-W3-097`** 的理由：目前 `MethodChannel` 原生端未註冊，`show` 必然失敗。在那個狀態下修 fallback 無法區分「fallback 生效」與「fallback 沒生效但反正也沒通知」——修好註冊之後才有可驗證的成功基準線。（來源已完成，結論見 Solution）
