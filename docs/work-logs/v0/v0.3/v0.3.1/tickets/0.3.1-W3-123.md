### 調查結果

四處固定高度容器逐一新增 `expectNoVerticalClip` 斷言後，實測皆為 GREEN（無裁切）：

| 元件 | Finder | 測試檔案位置 |
|------|--------|-------------|
| SearchField | `find.descendant(of: find.byKey(testKey), matching: find.byType(Row))` | empty/filled 兩態 |
| SegmentedControl | `find.descendant(of: find.byKey(matrixKey), matching: find.byType(Text))` | 「高等於 hitTargetMin」測試 |
| FilterDropdown | `find.descendant(of: find.byKey(testKey), matching: find.byType(Row))` | default/active 兩態 |
| Toolbar | `find.descendant(of: find.byKey(Key('toolbar-search')), matching: find.byType(Row))` | 新增「固定高度容器不裁切內容」group |

### Toolbar 的技術限制

Toolbar 自身的 Row 直接子樹含 FilterDropdown（內部用 `LayoutBuilder` 解析觸發器寬度），
Flutter intrinsic 查詢不支援跨越含 `LayoutBuilder` 的祖先節點（拋
`LayoutBuilder does not support returning intrinsic dimensions`），故無法對 Toolbar
整條 Row 直接呼叫 `expectNoVerticalClip`。改為測 SearchField 巢狀於 Toolbar 固定高度
容器下是否被壓縮——Toolbar 高度公式（`hitTargetMin + 2 * Space.xs`）扣除自身垂直
內距後恆等於 `hitTargetMin`，與 SearchField 自身容器高度相同，此斷言足以攔截
「Toolbar 外層再壓一層」的裁切風險。

### 斷言鑑別力驗證（每個新斷言先確認修復前紅燈）

由於實際內容（icon iconMd=15、AppFontSize.body=12 文字）皆小於 hitTargetMin=28，
四處在現行 token 值下皆不觸發裁切，非 SizedBox → ConstrainedBox(minHeight) 意義上的
「修復前紅燈」。改以人工暫時將對應 SizedBox/Container 的 `height:` 改為 `5`（明顯
小於任何內容），逐一確認新斷言翻紅（結果：四處皆成功攔截），驗證 finder 位置正確、
斷言具備鑑別力後，逐一復原為原始 token 值。復原後 `git status` 確認 `lib/` 無變更。

### 判定：四處皆非缺陷，未修改 lib/ 元件

與 W3-094 的 NavItem 情況不同（NavItem 用 `iconLg`=17 + 雙倍 `Space.sm` 內距，
內容固有高度恆超過 hitTargetMin=28，屬真缺陷）；本票四處元件的圖示尺寸
（iconMd/iconSm）與文字字級（AppFontSize.body=12）皆明顯小於 hitTargetMin，
內容固有高度不超過容器高度，無需修改為 ConstrainedBox(minHeight)。維持現行
SizedBox/Container 固定高度不變；本票僅新增測試斷言作為未來回歸防護——若後續
字級 token 或圖示尺寸調大導致內容超過 hitTargetMin，這批新斷言會攔截。

四處皆非「SPEC 明訂上界」豁免（無對應 SPEC 條文佐證），而是「實測確認現行
token 值下無裁切」，兩者性質不同但同屬「記錄豁免理由」的精神：已逐一驗證、
記錄鑑別力證據，本票不強制修改 lib/。
