### Context Bundle（PM 2026-09-29，派發前寫入）

**呼叫點實測（grep `ProcessRunnerProvider`）：共 5 處，不是 4 處**——Domain 視圖有兩個入口共用同一 provider。

| 入口 | 位置（符號） | 現行傳入路徑 | SPEC-003 對應列 |
|---|---|---|---|
| 開啟 docs 目錄 | `domain_view_screen.dart` `_openDocsFolder` | 相對 `'docs'` | §3.1「開啟 docs 目錄」三列：opened→`openedExternallyMessage`；notFound／failed→`externalOpenFailedMessage` |
| 泳道開啟原始檔 | `domain_view_screen.dart` `_openSource` | fixture 相對 `docs/usecases/<uc>.md` | §3.1「泳道開啟原始檔」：opened→opened；notFound→`sourceFileNotFoundSnackbarMessage`；failed→failed |
| UC Flow 開啟原始檔 | `uc_flow_screen.dart` | fixture 相對 `uc.filePath` | §3.2 |
| 節點詳情開啟原始檔 | `node_detail_screen.dart` `_openSource` | fixture 相對 `node.filePath` | §3.6：notFound→轉 `NodeDetailMissing`（不出 SnackBar） |
| 破洞項開啟原始檔 | `gap_report_screen.dart` `_openExternally`／`_runOpen` | fixture 相對 `item.filePath` | §3.5：notFound→`sourceFileNotFoundSnackbarMessage` + 重新掃描動作 |

**現況**：五處各自 `File(path).existsSync()` 前置檢查 + `ref.read(*ProcessRunnerProvider)('open', [path])` + 自寫 try/catch。`ExternalOpener`（`lib/workspace/external_opener.dart`）已內含前置檢查、ProcessException 攔截與結果日誌（`已開啟／路徑不存在／開啟失敗／呼叫失敗：<path>`），這些是版本契約第 5 欄「ExternalOpener 結果事件」的來源。

**改法**：五處移除自身存在檢查與 try/catch，改 `await ref.read(externalOpenerProvider).open(path)`，依 `ExternalOpenResult` 三值 switch 到上表既有回饋；移除四個 `*ProcessRunnerProvider` 宣告。docs 目錄路徑改為 `currentWorkspaceStateProvider` 的 `WorkspaceReady.path` 組出的絕對路徑。

**範圍界線（PM 裁定）**：其餘四入口的 fixture 相對路徑**本票不改**——版本契約第 2 欄「預期改變的值」只列 docs 目錄。四入口的行為不變（原本 `File.existsSync` 與 `FileSystemEntity.type` 對相對路徑同樣以程序 cwd 解析）。此事違反 `ExternalOpener.open` 的「絕對路徑」介面前提，已另報 e1 決定落點。
