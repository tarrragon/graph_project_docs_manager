### Context Bundle（PM 2026-09-29）

**四個入口**（W1-004 合併後，main `9943feeb5`）都已經走 `ref.read(externalOpenerProvider).open(path)`，現在傳入的是 fixture 相對路徑：
- `domain_view_screen.dart` `_openSource`：`docs/usecases/<uc>.md`
- `uc_flow_screen.dart`：`uc.filePath`
- `node_detail_screen.dart` `_openSource`：`node.filePath`
- `gap_report_screen.dart` `_openExternally`：`item.filePath`

**路徑組合方式**：沿用 W1-004 docs 目錄的做法，也就是 `WorkspaceReady.path` 加上 `/`，再接相對路徑。建議抽成一個共用的純函式，放在 `lib/workspace/`，輸入是 `WorkspaceState` 與路徑，輸出是 `String?`。

**PM 裁定的規則**：
1. 已是絕對路徑（以 `/` 開頭）：原樣回傳，不論 workspace 狀態。gap_report_test 用暫存檔絕對路徑的 3 則測試仍依賴這條規則。
2. 相對路徑且 workspace 是 `WorkspaceReady`：組合成絕對路徑。
3. 相對路徑且 workspace 不是 Ready：無法解析。記一筆 warning 日誌，內容含 workspace 型別與原始路徑；**不呼叫 opener**，走該入口既有的 notFound 回饋。理由：找不到可解析的目標，對使用者來說就是找不到檔案。

### 預期與實際不符的說明：預期紅 8 則、實際紅 6 則（PM 2026-09-29，合併前）

**結論：預測有誤，是計數單位混用造成的，不是斷言缺乏鑑別力。**

- 實作前的預期表寫「opened／failed 6 則 + 2 則路徑斷言」，把**斷言**和**測試**放在同一個計數裡。
- 那 2 則路徑斷言 `expect(fake.calls, ['docs/usecases/UC-06.md'])`，分別是「Domain 泳道」與「UC Flow」兩個群組 `opened` 測試的**第一行 expect**，本身就屬於那 6 則紅燈測試，不是另外 2 則測試。
- 以 main 的原檔核對：泳道 `testWidgets('opened')` 的第一行即 `expect(fake.calls, ['docs/usecases/UC-06.md'])`，UC Flow 群組相同。

**這 2 則斷言在改動後確實紅了，而且紅的就是它們本身**：非 Ready 時依規則 3 不呼叫 opener，`fake.calls` 為 `[]`，與 `['docs/usecases/UC-06.md']` 不相等，因此在這一行失敗，後面的 SnackBar 斷言沒有執行到。

**改後斷言的鑑別力**：
- 泳道、UC Flow：`expect(fake.calls, ['/ws/proj/docs/usecases/UC-06.md'])` 是完整字串的相等比對。路徑若仍是相對路徑，比對必然失敗，所以有鑑別力。
- 節點詳情：原測試只有 `hasLength(1)`，**對路徑沒有鑑別力**，路徑相對或絕對都會綠。本票已補 `expect(fake.calls.single, startsWith('/ws/proj/'))`，相對路徑會讓它失敗。

**後續預測的做法**：預期紅燈一律以測試（`testWidgets`）為單位計數。同一則測試裡的多個斷言，以括號註明是哪一個斷言翻紅，不另外計數。
## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
新增 `lib/workspace/open_path_resolver.dart`：`String? resolveOpenPath(WorkspaceState workspace, String path, {log})`，規則如下。
1. 絕對路徑：原樣回傳。
2. 相對路徑且 workspace 為 Ready：回傳 `<root>/<path>`。
3. 其他情況：記 warning（level 900，內容含 workspace 型別與原始路徑），回傳 null。

四個入口改為先解析路徑。解析結果為 null 時，不呼叫 opener，直接走該入口原有的 notFound 回饋。fixture 路徑內容沒有改。

### Phase 4 評估

- 重構需要：否
- 技術債務：有一項，記錄如下，不另開票。
  - 「非 Ready 走 notFound」這一支只在破洞項入口有專屬測試，其餘三個入口靠共用函式的單元測試加上相同的呼叫形態來保證。
  - 不另開票的理由：四個入口對 null 的處理都是同一句 `result = ExternalOpenResult.notFound`，分支邏輯已經收斂在共用函式裡，逐入口重測只是在驗證同一行賦值。
- 程式碼品質：A。路徑解析從四處收斂成一個純函式，日誌透過注入點驗證。
- 結論：無需重構。
