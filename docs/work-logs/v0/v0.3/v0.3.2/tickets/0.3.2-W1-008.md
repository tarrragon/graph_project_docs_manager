### Context Bundle（PM 2026-09-29）

**規格**：SPEC-003 v1.42 §2.2
- 「不重複發送」列的時刻 (ii)
- 「可觀測性」列的撤回觸發條件與剩餘通知數
- 測試斷言表新增的兩列：非前景且可見頁為 gaps → resumed → withdraw 恰一次，日誌記 `lifecycle`；可見頁為 tickets → resumed → withdraw 為 0

**現況**（`scan_notification_controller.dart`）：
- `_withdraw()` 的呼叫點共 2 處：`_onGapReportStateChange`（新一輪掃描開始，即 rescan）與 `_onDestinationChange`（destination）。
- 切換專案的撤回是否經由這個 controller，請實作時以 grep 確認，並對應到 `projectSwitch`。
- `_onLifecycleChange` 目前只處理 denied fallback 延後顯示的 SnackBar。

**改法**：
- `_onLifecycleChange` 在 `next == resumed`、`selectedDestinationProvider == gaps` 且 `_pendingWithdrawableState != null` 時呼叫撤回。
- `_withdraw` 改為接收觸發條件參數，並以 `developer.log` 記錄。

**原生端**（`macos/Runner/AppDelegate.swift` 的 withdraw handler）：
- `removeDeliveredNotifications` 之後，在 `getDeliveredNotifications` 的 completion 裡，以 NSLog 記錄本 App 剩餘的通知數。這是結果值，不是請求。
- Dart 介面 `ScanNotifier.withdraw()` 維持 `Future<void>`。

**機械驗證（驗收第 3 項）**：
- 前置檢查依版本契約第 4 欄：實例數為 1、同一 bundle id 只登記一份現存 .app、log 已接上、終端機的輔助使用權限已允許。
- 以腳本讓另一個 App 在前景，再用 Cmd+Tab 經過本 App 但不停留，讀取 Shell 生命週期日誌，確認有沒有 `-> resumed`。
- 這一項由 PM 在合併後執行；代理人只需確保 lifecycle 日誌存在。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
- `_onLifecycleChange` 加入條件：`next == resumed`、`selectedDestinationProvider == gaps`，且 `_pendingWithdrawableState != null` 時撤回通知。這個分支放在 denied SnackBar 分支之前。
- `_withdraw(WithdrawTrigger)` 一開始先記 `withdraw-trigger:<name>`，並提供可注入的 `withdrawLogSink`。
- 原生端 withdraw handler：在 `removeDeliveredNotifications` 之後，於 `getDeliveredNotifications` 的 completion 裡以 NSLog 記錄 `withdraw-result: remaining=%d`。
- `ScanNotifier.withdraw()` 的簽章維持 `Future<void>`。

觸發條件與呼叫點：

| 觸發條件 | 呼叫點 |
|---|---|
| destination | `_onDestinationChange` |
| lifecycle | `_onLifecycleChange` |
| rescan | `_onGapReportStateChange` 轉入 Scanning |

- `projectSwitch` 保留在列舉中，但目前沒有呼叫點。
- 依 e1 裁定 B：`graphBuiltProvider` 固定為 true，原本以 ProjectUnready 代表切換專案的分支在執行期到不了。這項由 `0.3.2-W1-010` 承接，改為監聽 `currentWorkspaceStateProvider`。

**量測環境**：macOS 26.5（Darwin 25.5.0，arm64），main `fbec9c9ce` 的 debug build，以 `flutter run -d macos` 啟動。

**前置檢查**（版本契約第 4 欄）：

**觀測通道**：用 Node 22 內建的 WebSocket 連上 VM service 的 `Logging` stream（`streamListen`），把 `developer.log` 全部寫入檔案。沒有用 DevTools，也不靠人看畫面。

**觸發與結果**（時間為 UTC）：

| 步驟 | 動作 | 生命週期日誌 | 前景 App |
|---|---|---|---|
| R1 06:22:03 | osascript 把本 App 設為前景 | `hidden -> inactive`、`inactive -> resumed` | 本 App |
| R2 06:22:05 | Finder 設為前景 | `resumed -> inactive`（06:22:05.537） | Finder |
| R3 06:22:07 | CGEvent：按住 Cmd，連按兩次 Tab，放開。此時 MRU 順序為 Finder、本 App、第三個 App，所以會經過本 App、停在第三個 App | 06:22:07 到 06:22:11 之間**沒有任何 `-> resumed`**；06:22:09.564 出現 `inactive -> hidden`，推定是落點 App 遮住了視窗 | Google Chrome |

**結論**：用 Cmd+Tab 經過本 App 但不停留，**不會產生 resumed**。所以 W1-005 候選 B 列出的缺點「短暫掠過也會撤回」，在 App 切換器這條路徑上不會發生。裁決不變。

**排除的無效量測**：第一輪 S3 用 System Events 的 `key down command`，App 切換器沒有把它當成持續按住的 Cmd，實際效果等於單按一次 Cmd+Tab，落點是本 App（前景顯示為 graph_project_docs_manager），所以不算「經過」測試，改用 CGEvent 重做為 R3。這一輪 S1 與 S2 的 resumed／inactive 日誌，證明觀測通道本身能正確記錄轉換。

**未涵蓋**：真實撤回的端到端流程（送出通知、回到前景、原生端 `withdraw-result: remaining=`）沒有在本次實機執行。驗收第 2 項的 NSLog 由 build rc=0 加上程式碼審查確認。
