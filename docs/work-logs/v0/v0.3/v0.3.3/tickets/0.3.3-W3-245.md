### Rationale Chain
- 0.1.0-W3-176 why: `0.1.0-W3-167` 的確定性重現實驗（四組，`fvm flutter test`）證實 `0.1.0-W3-165` 落地後仍有三項可稽核缺口，使「程式主動決定不告知使用者」這件事無法被事後追究：

| 缺口 | 現況 | 後果 |
|------|------|------|
| G1 訊息識別 | `closed` 事件的 `fields` 只有 `reason`，無 message 或關聯識別 | 無法回答「被截斷的是哪一則」。只能靠 `shown`／`closed` 的 FIFO 順序推斷，與其他 tag 的日誌交錯時不可靠 |
| G2 實際可見時長 | `closed` 不帶「這則實際被看到多久」 | 實驗 F4：「一幀都沒顯示」與「顯示滿 1 秒後被截斷」的日誌逐字相同，而兩者對使用者的嚴重度不同 |
| G3 未顯示的決定 | 因判準而不顯示的事件完全無事件 | 程式決定不告知使用者時零痕跡，該決定不可稽核 |

實驗同時確立判別式：全 repo 呼叫 `hideCurrentSnackBar` 只有兩處（`app_snack_bar.dart:121` 取預設 `reason: hide`、`:166` 明確 `reason: action`），故 `closed{reason=hide}` 恆等於「被後續一次 `show` 截斷」。G1／G2 補齊後，此判別式才足以支撐 `0.1.0-W3-167` 規劃的頻率量測協定——否則量測拿不到「被截斷的是不是 withAction」與「使用者實際看到多久」兩項指標。（來源已完成，結論見 Solution）
- 0.1.0-W3-205 why: `AppSnackBar.show` 無條件呼叫 `hideCurrentSnackBar()`，因此**任何一則新訊息都會截斷正在顯示的那一則，不分級別**——一則 L3 完成通知會殺掉正在顯示的 L2 失敗訊息，違反 `0.1.0-W3-184` 截斷規則第三條（低級別不得截斷任何東西）。

**且干擾是跨路徑且不對稱的。** `hideCurrentSnackBar()` 作用於 `_snackBars.first`，**不分那一則是誰放進去的**；而 `lib/main.dart:219` 直接呼叫 `ScaffoldMessenger.of(context).showSnackBar(...)` 繞過元件層，走排隊語意。結果是元件路徑殺得掉原生路徑的訊息、反之不行，且被殺的那則**零日誌**（不經過元件層，`0.1.0-W3-165` 的四個事件對它全不適用）。

**使用者可觀察到的徵狀**：訊息閃一下就不見了，而沒有任何紀錄能回答哪一則被殺、被誰殺。（來源已完成，結論見 Solution）
