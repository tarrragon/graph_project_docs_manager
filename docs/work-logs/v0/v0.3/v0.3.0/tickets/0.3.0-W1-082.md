### 設計方向（PM 派發前寫入，依 SPEC-001 既有先例）

來源：SPEC-006 v1.4 FR-06 規則 7、FR-08、〈錯誤處理〉最後兩列；UC-06 v1.3〈無法判定破洞〉〈破洞歸屬型別不明〉。

| 需求 | 建模方式 | 先例 |
|------|---------|------|
| 專案 JSON 缺 carrier 路徑模式、版本不高於內建版本，路徑模式由內建表補 | **常駐徽章**，不另立狀態：破洞報告顯示「路徑模式取自 App 內建型別表」，比照 SPEC-001 §1「推定版本」徽章的位置與渲染方式；與「無可消費的型別表」顯式關卡區分（本情境自動生效、不需使用者按鈕，因為只補一個欄位，其餘仍讀專案 JSON） | §1「VERSION 缺 + JSON 有」推定版本徽章 |
| 專案 JSON 與內建表都取不到路徑模式 | §5 破洞報告**新增狀態列**「無法判定破洞」：顯示原因說明；可用操作至少含切換專案與導覽；畫面須與「無破洞」明顯不同（UC-06 驗收） | §5「無破洞」列的欄位形態 |
| 破洞歸屬型別不明（schema 歧義） | 不是新狀態：「有破洞」列的破洞項帶候選型別與歧義標記，指向欄視為「無法指向任何節點」（點擊開啟原始檔） | §5 破洞項主操作表 |
