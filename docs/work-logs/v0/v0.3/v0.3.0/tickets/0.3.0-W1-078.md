### WRAP 摘要

- R1：`tracking_schema.json` 沒有匯出完整性集合。R2：框架內四個 REQUIRED 常數有三個沒有消費端，`validate.py` 另有一份 EVT 集合，採「值不能為空」判定。R3：FlowStep 空值有兩種形式，清單寫 `[]`，單一值寫 `null`（branch_from 28、return_to 35）。R4：JSON Schema 的 `required` 只管鍵存在，值不可為空另用 minLength／minItems 表達。R5：doc 範本的欄位比舊語料多（PROP 範本 12 鍵，100% 出現的只有 3 鍵）
- 排除的選項：A（null 與漏寫不可區分）、B+C（C 無消費需求）、D（退化為 B）、E（違反 R1）；Q2 的 b（違反 R5，且觸及 ticket skill 權威）、a（本 App 的需求用 c 可滿足，且不誤報）
- 預想失敗：consumer 照常數名字面實作成「值不能為空」→ 防護為改名或在 JSON 加 `empty_allowed`；只改 `.py` 沒有匯出 → 0.3.0 Step 2 寫 spec 時會找不到 JSON 鍵
- 絆腳索：任一 consumer 回報完整性誤報超過 10% → 回 #99 重評語意
- 盲點：R3 的 `null` 寫法只有兩個 consumer 樣本

### 裁決

| 項 | 裁決 |
|----|------|
| 語意 | **欄位必須存在；值可為 `null` 或空清單，代表「明確沒有」**。對應 JSON Schema 的 `required`（只管鍵存在）。`id` 另由 `id_pattern` 約束；更嚴格的值規則（例如 EVT 的 producers／consumers 不得為空）屬各型別 validator 的職責，不放進本集合 |
| 五個未定義型別 | **識別與顯示最小集**：PROP／SPEC／UC = {id, title, status}；DomainBundle = {id, domain}；Ticket 不在圖譜 schema 設集合，欄位權威在 ticket skill |
| FlowStep | 現行七欄加 `traverses`（domain 名清單，0..n，空清單合法） |
| 匯出 | 集合與「空值合法」語意一併匯出到 `tracking_schema.json`；現行 JSON 沒有任何完整性鍵，讀 JSON 的 consumer 無從取得 |
| 命名 | 常數名或 JSON 鍵須明示「空值合法」，避免 consumer 照 `REQUIRED` 字面實作成「值不能為空」 |

### 依據

- 兩個有 FlowStep 的 consumer 共 48 步，鍵存在率 100%。空值形式有兩種：清單寫 `[]`，單一值寫 `null`（branch_from 28、return_to 35）。若採「值不能為空」，41/48 步會誤報；採本裁決，48/48 合規
- 五型最小集在現有 PROP 53、SPEC 67、UC 45、DomainBundle 25 個節點上全數成立。集合由語意推導（識別、顯示、生命週期），出現率只用來確認不會誤報
- 不採用 doc 範本的全部欄位作為集合：範本的欄位比舊語料多（PROP 範本 12 鍵，每份都有的只有 3 鍵），舊檔會被大量報缺；這是框架版本差異，不是檔案缺陷
- 不另設「已知欄位」集合（用來判定未預期欄位）：目前沒有消費需求。語料中出現集合外的鍵 `implements`（16 步），另記入欄位文件即可

### 落地影響

- `FLOWSTEP_REQUIRED_FIELDS` 加入 `traverses` 後，flutter_balance 的 9 個 FlowStep 須回填 `traverses`（空清單亦可）
- doc skill 的 usecase 欄位表把 next／branch_from／return_to／emits／consumes 標為選填，須改寫為「欄位必須存在、值可為空」
- `validate.py` 另有一份 `EVENT_REQUIRED_FIELDS`（值不能為空），與 schema 的 EVT 集合是兩份定義。實作時應把完整性判定改為讀 schema 集合，「值不能為空」保留為該型別 validator 的附加規則
- 實作票由 graph-project-docs-manager 承接，完成後 sync-push

### 絆腳索

任一 consumer 回報完整性誤報超過 10%，回到本項重新評估語意。
