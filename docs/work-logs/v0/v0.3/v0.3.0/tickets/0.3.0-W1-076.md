## Solution
### 分析結論

本項裁決只阻擋 0.3.0 的欄位層完整性回報（`lostFields`／診斷「缺欄位」類），不阻擋兩項整合測試。語料實測顯示第三項列的兩種語意之外存在第三種「鍵必須存在、值可為空」，且為兩個有 FlowStep 的 consumer 實際採用的填法。本票不替上游裁決，產出為附加觀測（下方全文），把裁決所需的消費需求與實測交給 owner。

### 候選方案（供上游裁決，非本票決定）

| 方案 | 利 | 弊 |
|------|----|----|
| A 必填（值須非空），集合收窄至 id、name | 語意最嚴、lostFields 最有鑑別力 | 其餘五欄降為選填後，「明確為空」與「漏填」不可區分 |
| B 鍵必須存在（值可為空） | 與兩 consumer 現行填法一致，48/48 合規；可區分漏填與明確為無 | 需在常數名或註解寫明「空值合法」，否則消費端易照字面實作為非空 |
| C 已知欄位（判未預期欄位） | 可偵測拼錯的鍵 | 方向與 lostFields 相反，不能單獨滿足消費端；現行集合漏 `implements` |

### 語料實測

以框架既有函式 `parse_frontmatter` 與 `_extract_structured_flow_steps` 量測六個 consumer 專案 `docs/` 全量（2026-09-24），依各型別 `id_pattern` 判型。

**FlowStep**：共 48 步，只出現在兩個 consumer（9 步、39 步），其餘四個 consumer 為 0。

| 欄位 | 鍵存在 | 值非空 |
|------|:---:|:---:|
| id | 48 | 48 |
| name | 48 | 48 |
| next | 48 | 24 |
| branch_from | 48 | 20 |

兩個 consumer 都以「鍵存在、值可為空清單」填寫，所以鍵存在率 100%，值非空率 15%～50%。現行集合的三種讀法結果不同：當「值必須非空」實作，48 步中 41 步至少報一項缺漏；當「鍵必須存在」實作，48 步全數合規；當「已知欄位」實作，16 步的 `implements` 被報為未預期，表示現行集合作為已知欄位也不完整。

**五個未定義型別**，鍵出現率 100% 的欄位（n 為節點數）：

| 型別 | n | 100% 出現的鍵 |
|------|:---:|------|
| PROP | 53 | id, title, status |
| SPEC | 67 | id, title, status, created, version, domain, related_specs |
| UC | 45 | id, title, status, created, updated, primary_actor, platform |
| DomainBundle | 25 | id, domain, source_specs, related_usecases, created, updated |
| EVT | 14 | 現行 `EVT_REQUIRED_FIELDS` 四鍵皆 100%；status, created, updated, payload, producers, consumers 亦 100% |

此表是觀察值，不主張這些鍵是必填——用出現率推導必填，正是第三項指出的同型錯誤。它的用途是：裁決採必填語意時，候選集合先從語意推導，再用此表確認不會對既有語料全面誤報。

### 三種語意對消費端的差異

第三項列了兩種語意；實測顯示還有第三種，而且是兩個 consumer 都已在用的那一種：

| 語意 | lostFields 的算法 | 對現行語料的效果 |
|------|------------------|----------------|
| 必填（值須非空） | 必填集合 − 救回欄位 | 現行 FlowStep 集合下 41/48 誤報；集合須收窄至 id、name |
| 鍵必須存在（值可為空，空即「明確為無」） | 集合 − 救回的鍵 | 48/48 合規；與兩個 consumer 的填法一致 |
| 已知欄位（判未預期欄位） | 不適用於 lostFields（方向相反） | `implements` 16 步被報未預期 |

消費端需要的最小裁決：**每個型別給出「缺了算缺陷」的鍵集合，並寫明值為空是否算缺**。前兩種語意只差在後半句；第三種是另一個集合，可與前者並存，但不應共用同一個常數名。
