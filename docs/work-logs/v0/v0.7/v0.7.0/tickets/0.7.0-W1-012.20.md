### 根因（摘自 0.7.0-W1-012.14〈F-3 根因〉，已實測）
- `_inputsFromSchemaState` 只在 `scanRoundProvider` 為 `ScanRoundCompleted` 時取型別表與 edgeResolution，其他狀態給 null。table 為 null 時 Ticket 的 id_pattern 退回永不匹配，isTicketCreation 恆為 false，closed_by 略過規則也失效。
- 檔案監看的重掃走 `ScanRoundNotifier.rescan()`，會先 `discard` 把狀態打回 Idle 再進 Running（`corpus_watch_provider.dart` 的 `_obtainRound`）。所以只要其他線一提交，`scanRoundProvider` 就有一段非 Completed 的窗口，即使該工作區早已完成過輪次。vm5.log：History 掃描開始於 +13.94s，輪次 generation 6 在 +12.71s 至 +15.31s。
- 替身 `fakeRound`（`test/helpers/gap_round_fakes.dart`）的型別表是空的 `TypeTable({})`，edgeResolution 為 null。既有測試無法覆蓋 id_pattern 路徑。

### 修法（用戶裁定 (a)：輪次未完成時等它完成再掃描）
1. 型別表與 edgeResolution 改取 `lastCompletedRoundProvider`。它是同一工作區最後一次完成的輪次，重掃、取消、失敗時都保留上一輪，切換專案時清除，Domain 矩陣、泳道與節點詳情已經讀這個來源。裁定 (a) 的「等待」只在 `lastCompletedRoundProvider` 為 null 時發生，也就是本工作區還沒有任何完成的輪次。已有完成輪次時不等待，直接使用上一輪的型別表。PM 判斷這與裁定意圖一致：避免用 null 表掃描。這個解讀已回報主控。
2. 等待的做法是呼叫 `scanRoundProvider.notifier.ensureRound()`。回傳 null 時，若輪次狀態是 Running（等待中的輪次被重掃取代），就接續等待新的輪次；若不是 Running（輪次失敗，或被取消且沒有後續輪次），結果落「讀取失敗」，原因碼新增 `GitFailureReason.scanRoundUnavailable`，可重試。
3. 等待邏輯經 `HistoryScanInputs` 注入，例如新增一個 `Future<bool> Function()` 欄位，預設值為立即完成的頂層函式，維持 const。`HistoryNotifier` 不直接依賴 `scanRoundProvider`，所以覆寫 inputs 的既有測試（history_cache_provider_test、history_screen_fixtures、uc07_history_test）不必修改。
4. `HistoryNotifier._load` 的順序：先檢查 blocked，再等待（畫面為讀取中，可取消），等待後重新 `ref.read(historyScanInputsProvider)`，再檢查一次 blocked，最後做前置檢查與掃描。等待期間 cancel 會遞增 `_generation`；等待結束後若 token 不符就停止，不啟動掃描。
5. `_tableIdentityOf` 在 table 為 null 時回傳專用識別（例如 `none`），不與空邊型表的 `project:<hash>` 相同，避免快取命中以 null 表算出的結果。
6. 日誌（observability 規則 4）：等待開始、等待結束（含毫秒數與結果）、沿用上一輪，各寫一筆 developer.log。

### 012.19 內建表 fallback 的評估：移除
- SPEC-008 FR-08 規則 6 規定，只有 Schema 以內建型別表降級時才使用內建表，而且畫面要帶降級徽章。`_fallbackResolution` 是在非降級狀態下、沒有徽章時，用內建表決議邊型，違反這一條。
- 修法 1、2 之後，正式路徑上的 builder 一定有完成的輪次，edgeResolution 由 `_runRound` 寫入；降級時輪次以內建表作為專案表，自然沿用。所以 fallback 在正式路徑上不再被走到，只剩替身輪次會用到。
- 移除後，edgeResolution 為 null 時使用中邊型為空，並沿用既有的 level 900 日誌。WR-6 改由替身輪次提供 edgeResolution。`fakeRound` 新增可選參數 typeTable 與 edgeResolution，預設值維持不變，其他呼叫端不受影響。
- 附帶效果：fallback 移除後，實機上事件數大於 0 就能證明 `_runRound` 寫入 edgeResolution 的路徑可用，補上 012.19〈更正 2026-11-10〉列出的未驗證缺口。

### 輪次被頻繁提交一再重跑時的等待時間
- 等待只發生在本工作區第一次完成輪次之前。第一次完成之後，`lastCompletedRoundProvider` 在每次重掃期間都保留上一輪，History 不再等待，所以頻繁提交不會讓已完成過輪次的工作區等待變長。
- 第一次完成之前，若重掃一再在輪次完成前到來，等待會延長。這個情況下 Domain 視圖等所有讀輪次的畫面同樣拿不到結果，History 沒有額外暴露。等待期間畫面為讀取中且可取消，不會卡住。
- 本票不證明首輪前不會飢餓。實機驗證時記錄等待毫秒數（修法 6）。若出現首輪前等待超過一次輪次耗時的實例，另建票評估重掃的節流。
