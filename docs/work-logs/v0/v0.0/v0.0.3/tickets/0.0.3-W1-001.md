# Execution Log

## Task Summary

評估 markdown 渲染套件：flutter_markdown_plus 與 gpt_markdown 以真實語料實測比較

---

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
完整 WRAP 四階段：

【W 擴增選項】候選在前一輪對話已擴增至四項：flutter_markdown_plus、markdown_widget、gpt_markdown、以及「先不決定，實測後再選」。使用者選定實測路徑並指定比較第一與第三項。三類涵蓋檢查：新增工具（引入套件）、改造既有（自建渲染器）、零工具（不渲染 markdown，僅顯示原始文字）。後兩者未列入實測，理由記於 A 階段。

【R 現實檢驗】基本率查證推翻了預設：flutter_markdown 已被 Flutter 官方標記 discontinued，pub.dev metadata 指定接替者為 flutter_markdown_plus。若未查證而沿用「官方套件較安全」的直覺，會選到已停止維護的套件。

近距離檢視以真實語料實測，非閱讀套件描述。首次目視比較誤判 gpt_markdown 標題階層有缺陷，隔離測試後發現相反。此為 R 階段「清單類答案需逐項核對」的實例——單一混合文件的觀察不足以支撐逐項結論。

【A 拉開距離】自建渲染器與不渲染兩個選項的機會成本過高：前者排擠核心的 domain↔UC 穿透功能，後者使節點詳情畫面失去價值（該畫面的存在理由就是可讀地呈現文件內容）。10 個月後的影響：套件的維護狀態比當下的渲染品質重要，因為渲染缺陷可用樣式表修，停止維護不能。

【P 準備好犯錯】premortem——這個選擇會怎麼死：(1) flutter_markdown_plus 作為社群 fork 亦停止維護；(2) 樣式表的 27 個欄位不足以達成設計稿要求；(3) 效能在長文件上不足。早期警訊分別為：pub.dev 出現 discontinued 標記、實作節點詳情時發現需要 builders 而非 styleSheet、渲染長文件時出現掉幀。

回退計畫：兩者 API 表面差異不大且皆以 markdown 字串為輸入，替換成本侷限於節點詳情畫面的渲染層，不擴散至 domain 層。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
採用 flutter_markdown_plus ^1.0.12。

判準：不比「現在誰看起來好」，比「誰的缺點改得動」。flutter_markdown_plus 的兩個缺點（標題階層 H3/H4/H5 差異小、行內程式碼無底色）落在其 27 個樣式欄位的可修範圍；gpt_markdown 的缺點（8 個 transitive 依賴，含本專案用不到的 flutter_math_fork 與 flutter_svg）不可修。

另一項差異：文字可選取性。flutter_markdown_plus 內建 selectable 參數；gpt_markdown 需自行包 SelectionArea。節點詳情畫面需要可複製內容，前者成本較低。

gpt_markdown 已自 pubspec 移除，spike 程式碼已刪除。結論寫入 docs/tech-decisions.md。
