## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
完整 WRAP 四階段：

【W 擴增選項】原本框成三條路（呼叫 CLI／結構化表單加純文字／WYSIWYG 套件）。反向框架檢查後發現框窄了——真正的問題不是「選哪個編輯器」而是「編輯的寫入責任歸誰」。補上第四個選項：寫入自己做、驗證交給 CLI。

【R 現實檢驗】三項實測，其中第一項推翻了 CLI 路徑的可行性。

CLI 編輯覆蓋率量化：doc CLI 僅 3 個變更型指令，且 update 只能改 status；ticket track 有 32 個變更型子命令。對照 schema 的 16 條邊，僅 4 條（parent_id／source_ticket／blockedBy／relatedTo，皆在 Ticket 上）可經 CLI 編輯，其餘 12 條需直接改檔。圖譜節點（PROP／SPEC／UC／EVT／DomainBundle）經 CLI 只能改 status。

降級行為：移除 PATH 中的 uv 後為 FileNotFoundError（Dart 端 ProcessException），可辨識。但更關鍵的是系統內建 python3 為 3.9.6，執行 doc CLI 直接 TypeError——該 CLI 使用 PEP 604 的 X | None 語法，需 3.10 以上。CLI 路徑硬性依賴使用者裝有 uv。

編輯器實測（re_editor 0.10.0）：首次渲染 744 ms，8000 行大檔換入 122 ms，中文插入 108 ms。虛擬化渲染有效。但 re_highlight 的 markdown mode 將 snake_case 識別符中的底線誤判為強調標記，導致大段內文錯誤斜體化。關閉語法高亮的對照組全部正確，確認缺陷在高亮模式而非編輯器本身。本專案語料充斥 snake_case（source_proposal、where.files、tracking_schema.py），該缺陷會普遍發作。

【A 拉開距離】CLI 寫入路徑的機會成本最高：即使投入實作，也只覆蓋 25% 的邊與圖譜節點的一個欄位，其餘仍須直接改檔——等於同時維護兩套寫入路徑。10 個月後的影響：兩套寫入路徑會分歧，而分歧的形態正是本專案已撞到六次的索引不同步。

【P 準備好犯錯】premortem——這個選擇會怎麼死：(1) 直接改檔造成索引不同步，重蹈框架六個缺陷的覆轍；(2) 結構化表單的欄位定義與 schema 漂移；(3) 關閉語法高亮後編輯體驗過於原始。

早期警訊分別為：doc validate 或 uc verify 出現本 App 寫入後才有的違規、schema 契約測試紅燈、使用者回報找不到區塊邊界。

第一項的緩解手段即本票的核心結論：寫入後立即呼叫 CLI 的唯讀驗證器（doc validate／uc verify／validate-filenames），把索引不同步變成可偵測的紅燈而非靜默錯誤。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
採用：直接改檔為寫入路徑，CLI 僅作為驗證器。

編輯模型分兩層：
- frontmatter 與結構化區塊（flow block）以結構化表單編輯，欄位定義取自 tracking_schema.json，型別安全
- markdown 內文以 re_editor 純文字編輯，關閉 markdown 語法高亮

不採 CLI 作為寫入路徑，理由是覆蓋率不足：16 條邊僅 4 條可改，圖譜節點僅 status 可改，其餘仍須直接改檔。若同時維護兩套寫入路徑，兩者必然分歧，而分歧形態正是本專案已撞到六次的索引不同步。

CLI 仍有不可取代的價值，但職責是驗證而非寫入：doc validate、uc verify、validate-filenames 皆為唯讀。寫入後立即呼叫，把索引不同步從靜默錯誤變成可偵測的紅燈。

語法高亮關閉的理由：re_highlight 的 markdown mode 將 snake_case 中的底線誤判為強調標記，在本專案語料上普遍發作。對照組確認缺陷在高亮模式而非編輯器。後續可評估針對 frontmatter 區域套用 YAML mode、內文區域維持純文字的分區高亮。
