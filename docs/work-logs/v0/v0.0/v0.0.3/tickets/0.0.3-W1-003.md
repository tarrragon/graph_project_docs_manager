## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
完整 WRAP 四階段：

【W 擴增選項】層級選項三項（文件層級／停滯偵測／邊層級）之外，三類涵蓋補上：新增工具（引入 git 函式庫綁定）、改造既有（歷史併入 Corpus domain）、零工具（不做 git 記錄，僅顯示檔案 mtime）。

【R 現實檢驗】基本率查證推翻了自己的推估兩次，且錯法相同——把天真實作的成本當成問題的固有成本。

文件層級：原估 O(commits × files) 昂貴，實測單次 git log --name-only 掃描 9409 commits 為 1.04 秒。
邊層級：原估昂貴，逐 commit 啟動 git show 實測 52000 對耗時 18.3 分鐘，但改為單次 git log -p 僅 2.10 秒加解析 0.18 秒，合計 2.28 秒。差距 523 倍，而問題本身未變。

【A 拉開距離】2.28 秒的成本落在與 ticket 載入（1.9 秒）相同的量級，因此適用同一個策略：依視圖惰性載入，開啟歷史視圖才付這個成本，不在啟動時付。零工具選項（僅顯示 mtime）的機會成本是失去「這條邊何時被加上」的追溯能力，而該能力正是本 App 相對於 grep 的差異化之一。

【P 準備好犯錯】premortem——這個選擇會怎麼死：(1) 更大的 repo 使 diff 輸出膨脹至記憶體不可承受，本次 9409 commits 產生 31.2 MB，十倍規模即 312 MB；(2) 使用者的專案不是 git repo；(3) 淺層 clone 使歷史不完整而顯示錯誤的「首次出現」時點。

早期警訊分別為：diff 輸出位元組數超過閾值、git 回傳 exit 128、git rev-parse --is-shallow-repository 回傳 true。

降級行為已實測：非 git 目錄 exit=128 且 stderr 明確；git 不在 PATH 為 ProcessException，與解析失敗等其他形態可區分，可分別給出對應訊息。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
採用邊層級，實作方式為單次 git log -p 掃描後解析，非逐 commit 查詢。

實測數據：

| 做法 | 耗時 |
|------|------|
| 文件層級（git log --name-only 單次） | 1.04 秒 |
| 邊層級（逐 commit git show，天真實作） | 18.3 分鐘 |
| 邊層級（單次 git log -p + 解析） | 2.28 秒 |

載入策略沿用依視圖惰性——開啟歷史視圖才掃描，不在啟動時付這個成本。
全量重掃 2.28 秒已足夠快，不實作增量更新邏輯：增量需維護狀態且正確性風險高，而省下的時間有限。

Domain 職責歸屬：獨立為 History domain，不併入 Corpus。理由是變更理由不同——Corpus 的變更來源是文件格式或解析寬容度，History 的變更來源是 git 查詢方式或歷史語意；兩者資料來源不同（工作目錄檔案 vs git 物件庫）、失敗形態不同（解析失敗 vs 非 repo／git 缺失）、依賴不同。兩者不會出現在同一個 PR 裡。

此決定使 domain 數達 8，觸及協議建議上限。已檢查切太細的訊號：History 與任何既有 domain 皆無「永遠一起改」的關係。
