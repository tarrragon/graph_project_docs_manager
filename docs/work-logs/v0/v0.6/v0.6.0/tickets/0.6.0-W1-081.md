# Execution Log

## Task Summary

commands/validate.py 的 EVT 檢查不分 category 一律要求 consumers 非空；tracking_schema.py EVT_CATEGORIES 註解寫 process_event 允許無 consumer。判定何者為準，並套框架問題兩條 AND 判準決定是否觀測 canonical issue

## Problem Analysis
### 問題根因

同一條規則在 doc skill 內有兩個互斥的寫法，且兩者在上游同一個版本（v2.40.0）一起出現：

- 建立端：tracking_schema.py 的 EVT_CATEGORIES 上方註解定義兩個 category 的差異——domain_event「必有 consumer」，process_event「允許無 consumer」。這是框架內唯一一處說明兩個 category 行為差異的地方。
- 驗證端：validate.py 的 _validate_event 對 consumers 的檢查沒有 category 條件，process_event 空 consumers 一樣被拒。

驗證端的寫法不是對 process_event 做過決定的結果，而是沒有分流：test_validate_event.py 的所有 fixture 都是 category: domain_event，沒有任何一個 process_event 案例，該行為從未被測試覆蓋；validate.py 也沒有 import EVT_CATEGORIES，而是自持一份 EVENT_VALID_CATEGORIES 值域，與建立端沒有程式上的連結。

載體是成因之一：建立端把「是否需要 consumer」寫在註解裡，不是機器可讀的欄位，驗證端沒有東西可以引用。

### 影響範圍

已驗證的事實：

- 框架內寫著「EVT 的 consumers 一律非空」的位置：validate.py（程式與 docstring）、test_validate_event.py 檔頭、SKILL.md 的 Event 列、event-template.md 註解、tracking_schema.py 完整性語意註解（2026-09-24，#99 第三項裁決時加入）、tracking_schema.json 的 completeness_semantics、CHANGELOG 1.22.4。後兩處是把既有 validator 行為舉為「型別附加規則」的例子，不是對 category 重新裁決。
- 框架內寫著「process_event 允許無 consumer」的位置：只有 tracking_schema.py 的 EVT_CATEGORIES 註解。
- 本專案已有兩份規格依建立端的定義寫成：SPEC-001 §5 與 SPEC-003 §3.5 的「有發出無消費」破洞判準排除 category: process_event（0.1.0-W3-345）。App 端尚未實作該排除（lib／test／integration_test／assets 對 process_event 零命中）。
- 本專案 docs/events 下 11 份 EVT 全為 domain_event，consumers 皆非空，所以目前沒有任何文件被誤拒，這個矛盾是潛伏的。
- event-template.md 對 category 的說明（process_event＝流程/系統事件）與 EVT_CATEGORIES 註解（步驟進行中標記）用詞不同，屬同一批定義分散的徵狀。

未驗證的假設：

- 其他 consumer 專案是否有 process_event 實例、是否有流程依賴「空 consumers 被拒」，未查（不在本專案可讀範圍）。
- 上游兩處在 v2.40.0 內的先後順序無法得知（上游以版本為單位壓成單一 commit）。

對 0.5.0-W1-095 的影響：三份 consumers 列 presentation 的 EVT 都是 domain_event，在兩種讀法下都必須有 consumer，所以「允許無 consumer」不能當作刪掉 presentation 後留空的出路，W1-095 的值域裁決不受本票結論改變。

## 重現實驗結果
### 實驗方法

根因假設：_validate_event 對 consumers 的檢查不看 category。以最小輸入直接呼叫該函式驗證，不經檔案系統：固定 id／name／canonical_name／producers，只變動 category 與 consumers 兩個欄位，共 5 例。腳本放在 session scratchpad，未寫入專案。

```python
from doc_system.commands.validate import _validate_event
base = dict(id="EVT-X-001", name="n", canonical_name="A.B.C", producers=["corpus"])
# 各例以 dict(base, category=..., consumers=...) 組成後呼叫 _validate_event
```

### 實驗執行

| 例 | category | consumers | 回傳 |
|----|----------|-----------|------|
| A | domain_event | [graph] | 通過 |
| B | domain_event | [] | 缺少 consumer：EVT 必須至少一個 consumer |
| C | process_event | [graph] | 通過 |
| D | process_event | [] | 缺少 consumer：EVT 必須至少一個 consumer |

B 與 D 的輸入只差 category，回傳完全相同。

來源追溯：

- 本專案 git blame：兩處皆來自框架導入 commit cffdda1df（2026-08-26，拉取上游 v2.40.2），不是本專案的本地修改。
- 上游 tarrragon/claude：tracking_schema.py 在 v2.20.12（d4c112c42）不含「允許無 consumer」、v2.40.0（341b4e062）含；validate.py 在 v2.24.1（2c488f543）不含「EVT 必須至少一個 consumer」、v2.40.0 含。兩者同版出現。
- 驗證端的來源票為上游 consumer 的 0.2.1-W3-1060（見 test_validate_event.py 檔頭），動機案例是「有 consumer 無 producer」，consumers 檢查是它的鏡像，動機敘述未涉及 category。

### 實驗發現

已驗證：

- 假設成立。驗證端對 process_event 空 consumers 一律拒絕（例 D、E），與建立端定義相反。
- 驗證端沒有任何 process_event 測試案例，現行行為未經測試確認。
- 兩處同源同版，矛盾自上游建立時即存在，不是同步落差造成。

未驗證：

- 上游作者當時是否有意讓驗證端比註解更嚴格。現有證據（零測試、未引用常數、動機案例不涉及 category）都指向沒有分流，但無法從 commit 歷史直接證明。

## Solution
### 判定

process_event 是否需要 consumer，以建立端（tracking_schema.py 的 EVT_CATEGORIES 定義）為準。驗證端應修正為分 category 檢查。

依據：

1. 兩個 category 的語意差異只在建立端定義過，那是該欄位存在的理由。驗證端一律非空的話，category 在框架內沒有任何行為差異。
2. 驗證端自己寫明的理由是「缺一端代表事件的接收方未被記錄」，這個前提對 domain_event 依定義成立，對 process_event 依定義不成立。套到 process_event 上，檢查攔下的不是缺口。
3. 驗證端對 process_event 的行為沒有測試、沒有引用建立端常數、來源票的動機不涉及 category，屬於沒有分流，不是另一個決定。
4. 框架內其餘重述「consumers 不得為空」的位置都是轉述驗證端行為，不構成獨立依據；依 tool-output-trust 規則 6，不以出現次數反推建立端有誤。
5. 本專案兩份規格（SPEC-001 §5、SPEC-003 §3.5）已依建立端定義寫成，改採驗證端為準需要回頭改規格。

判定的限度：建立端的載體是註解，不是 canonical 常數，所以這不是規則 6 字面上的「常數優於清單」，而是依欄位語意與產生機制判定。上游作者的原意無法從歷史直接證明（見重現實驗「未驗證」）。

### 候選方案

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（建議） | 驗證端跟建立端：process_event 不要求 consumers 非空，producers 仍必填；validate.py 改引用 EVT_CATEGORIES；同步各處敘述 | 純放寬，不會讓任何現有文件由綠轉紅；本專案規格不用改；順手消除值域重複定義 | 規則仍寫在註解裡，下次新增 category 時同樣的落差可能重現 |
| B | 建立端跟驗證端：改寫 EVT_CATEGORIES 註解，刪去「允許無 consumer」 | 改動最小，只動註解 | category 失去行為差異；本專案 SPEC-001 §5 與 SPEC-003 §3.5 的排除條款失去依據，須回寫；真正沒有接收方的進行中標記事件只能填假的 consumer 才能通過 |
| C | 把「是否需要 consumer」升為型別表的機器可讀欄位，驗證端讀它 | 根除註解當載體的成因 | 型別表形狀變動，tracking_schema.json 要重產，本專案 App 內嵌副本與凍結測資要跟著重產；屬 #98 機制層修法的範圍，不宜在單一 consumer 先行 |

建議採 A。C 的方向寫進給 #98 的觀測內容，由上游在機制層一併處理。
