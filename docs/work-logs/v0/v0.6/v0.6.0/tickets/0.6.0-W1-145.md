## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### Context Bundle（PM 盤點與裁定，2026-11-04）

**現況（main 實測）**
- `WorkspaceSelectionNotifier.select`（`lib/app/workspace_selection.dart`）：`detect(path)` 之後才 `_persistRecentProjectSelection` → `addRecentProject`
- `recentProjectCountsWriterProvider`（`lib/app/recent_project_counts_writer.dart`）：監聽 `scanRoundProvider` 進入 `ScanRoundCompleted` 時呼叫 `saveRecentProjectCounts(workspacePath, counts)`；首次開啟的專案此時清單尚無同 path 項，回 false，快照落空
- 兩者先後是競態：首輪若在 `addRecentProject` 之後才完成，快照會寫入；若先完成就落空

**PM 裁定：採候選 B（加入清單後補寫最近完成輪次），不採 A**
- A（`addRecentProject` 移到 `detect` 之前）會讓載入失敗的專案也進最近清單，違反 SPEC-005 §2.4〈寫入時機〉「成功載入後」
- B：`_persistRecentProjectSelection` 在 `addRecentProject` 成功、更新 `recentProjectsProvider` 之後，讀 `lastCompletedRoundProvider`（`lib/app/scan_round.dart`）；若有輪次且 `workspacePath == path`，以 `recentProjectCountsOf` 補寫快照並同步 provider。補寫邏輯放在 writer 檔、以一個公開函式供 selection 呼叫，避免兩處各寫一份 save + sync
- 競態另一側（首輪在 add 之後完成）由既有 writer 監聽照常寫入，兩條路徑都以同一輪結果寫入，結果相同

**規格同批修改**：SPEC-005 §2.4〈計數快照〉表的「寫入時機」列句尾補一句：「另於 `addRecentProject` 成功後，若最近完成輪次的 `workspacePath` 與該項相同，立即以該輪補寫（首次開啟的專案首輪可能先於加入清單完成）」；版本歷史加一列。SPEC-005 不屬 SPEC-004 與綁定 ARB 的段落，不需跑規格閘門

**紅燈步驟**
1. `test/unit/app/recent_project_counts_writer_test.dart` 新增測試：清單初始為空，首輪先完成（save 回 false）→ 再 select 同 path → 斷言 `recentProjectsProvider` 該項帶 counts、repository 有收到補寫。先跑確認紅燈
2. 對照（E1）：最近完成輪次的 `workspacePath` 不同時不補寫
3. 實作補寫函式與呼叫點，轉綠
4. 跑 `test/unit/app/`、`test/unit/screens/`（切換器相關）、`test/unit/workspace/`、`test/unit/architecture/` 全綠
