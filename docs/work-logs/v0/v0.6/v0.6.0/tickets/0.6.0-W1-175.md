## Problem Analysis
### 問題根因

`source_specs` 的「只收有 FR 落在本 bundle 公開面的 spec」判準不是 schema 定義，是 `0.6.0-W1-168` 從各 bundle 現況歸納出來的寫法，從來沒有成文。

- schema 權威 `tracking_schema.py` 的 `domain_coverage` 邊（forward_field `source_specs`，class containment）與 `doc` skill 範本 `domain-map-template.md` 都只寫「本 map 覆蓋的 spec」，沒有 FR 條件。
- `docs/system-layer.md` §8 的歸屬判準是「FR → Bundle」，本來就只回答 FR 怎麼歸屬，從來沒有規定 `source_specs` 怎麼填。168 把它借來當 `source_specs` 的判準。
- 這套歸納已經有一個例外：workspace 的 SPEC-005 沒有 FR 編號，照樣列入 `source_specs`。

所以 layout 的 `source_specs: []` 照 168 的歸納判準算是正確，照 schema 的字面定義（覆蓋）算是缺漏。兩種讀法不一致才是根因；SPEC-001 §1 有沒有 FR 只是表面現象。

### 影響範圍

已驗證事實：
- SPEC-001 §1〈泳道布局規則〉是逐值可比對的判定式表（列集合與列序、列鍵比對、主線、欄序、節點所屬列、邊的來源／形狀／端點、欄序無法輸出、`traverses` 異常），每一項都附 UC-02 期望值。性質上就是驗收條文，只是沒有 FR 編號。SPEC-001 功能需求只有 FR-01～FR-08，都不涵蓋布局。
- `docs/spec/layout/domain-map.md` §3 公開面明文引用 SPEC-001 §1；§7 只寫「SPEC-006、SPEC-007 無 FR 歸屬」，沒有提到 SPEC-001。
- layout 測試（`test/unit/layout/lane_order_test.dart`、`column_order_test.dart`、`node_placement_test.dart`、`edge_shape_test.dart`）已登錄在 `docs/traceability.yaml` mappings 的 `spec: SPEC-001 / usecase: UC-02` 列。因此能追溯到 SPEC-001 與 UC-02，只是追不到 FR，也追不到 DomainBundle → Spec 的 `domain_coverage` 邊。票面 why 寫「無法回溯 FR」是對的，但測試並不是完全沒有追溯。
- 8 個 domain map 中，`source_specs` 為空的只有 layout 與 history 兩個。

未驗證假設：
- history 為空的原因是否與 layout 同型（有非 FR 條文覆蓋其公開面）：本票未盤點。
- App 端是否有畫面或破洞判準依賴 `domain_coverage` 出邊數（例如把出邊為 0 標成缺口）：本票未查 `lib/`。

### 相關 Error Pattern

沒有直接對應的已知模式。性質接近「歸納出來的慣例被當成權威判準」，與 tool-output-trust 規則 6「建立端定義優先於下游判準」同一家族：建立端是 schema，FR 判準是下游歸納。
