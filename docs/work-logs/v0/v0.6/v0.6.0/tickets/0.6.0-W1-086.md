盤點 SPEC-003 以外 6 份 SPEC 內文的依賴型票號引用

## Problem Analysis
### 問題根因

0.5.0-W1-524 只逐處分類 SPEC-003；其餘 6 份 SPEC（001、002、004、005、006、007）內文的票號引用未經規則 7〈出處型與依賴型的判準〉判讀，依賴型可能殘留。

### 影響範圍

- 範圍：6 份 SPEC 的內文（`## 變更歷史` 章節以外）。
- 實測（2026-11-05，本 session 腳本計數）：內文票號共 535 處，依份為 004 209、001 148、007 101、006 53、005 23、002 1。票面 Why 記的 554 是 0.5.0-W1-524 當時的計數，差值來自之後的 SPEC 改版，不影響本票結論。
- 讀取 SPEC 的測試：`test/unit/l10n/spec004_key_table_contract_test.dart` 讀 SPEC-004 §4.0.6 key 表；改動 §4.0.6 時須依 PC-GPD-075 與測試同一 commit。

### 相關 Error Pattern

PC-GPD-075（SPEC 改動與讀取它的測試同 commit）。規則 7 判準本身在 `.claude/references/reference-stability-rules.md`。

## 重現實驗結果
### 實驗方法

1. 腳本逐檔掃描 6 份 SPEC，遇 `## 變更歷史` 起跳過至下一個 `##`；以 `\d+\.\d+\.\d+-W\d+-\d+(\.\d+)*` 抽出票號，記錄行號與是否位於括號內（全形或半形）。
2. 初篩：括號外的 78 處全數人工判讀；括號內的 457 處以關鍵字（詳見／見／參考／依／待／承接／NeedsContext／上報／Solution／量測表）篩出 43 處人工判讀，其餘視為括號附在完整條文後的出處型。
3. 判讀：依規則 7，把票號連同所屬括號或子句拿掉後重讀條文；缺結論、缺範圍或只剩指向詞者為依賴型。

### 實驗執行

- 括號外 78 處多為「依據：`<票號>` 用戶裁決」「來源：`<票號>`」接在已完整陳述的條文之後，屬句子層級的出處標注，拿掉後條文完整。
- SPEC-007 FR-02／FR-04 驗收條件中的票號（如 `closed_by: 0.6.0-W1-010`）是測資字面值，不是引用。
- 括號內篩出的 43 處，「依 `<票號>` 用戶裁決」類為出處型；「見 `<票號>`」「待 `<票號>`」「NeedsContext 上報」類逐處讀上下文判讀。

### 實驗發現

- 依賴型 8 處（4 份 SPEC），清單見 Solution〈依賴型清單〉。SPEC-001、SPEC-002 無依賴型。
- 另有一類時效型進度註記（「由 `<票號>` 承接」「ARB 待建，`<票號>`」「依賴宣告待 `<票號>`」）：拿掉票號後條文完整，不屬規則 7 違規，但進度可能已過時。其中 SPEC-004 4.35〈尺寸契約〉的「待裁決」已被同檔 4.25〈內容政策〉定案，同時屬依賴型，列入依賴型清單。
- 未驗證：時效型註記所指的票目前是否已完成（不在本票範圍，見 Spawn 規劃）。
