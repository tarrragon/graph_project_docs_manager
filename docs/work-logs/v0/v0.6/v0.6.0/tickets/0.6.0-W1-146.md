## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### Context Bundle（PM 盤點與裁定，2026-11-04）

**現況（main 實測）**
- `WorkspaceRepository._parseRecentProjects(String raw)` 回 `List<RecentProject>?`（null＝整份損壞），逐元素呼叫 `_parseCounts(item['counts'], index)`
- `_parseCounts` 格式不符時直接 `_log(..., event: WorkspaceLogEvent.recentProjectCountsInvalid, level: 900)` 後回 null：日誌副作用在解析鏈內
- `_parseRecentProjects` 有 3 個呼叫端（讀清單、寫入前讀基底、計數寫入前讀基底）

**PM 裁定的形狀**
- 解析改為純函式：回傳私有值物件（例：`_ParsedRecentProjects`，含 `projects` 與 `invalidCountsIndexes`），整份損壞仍以 null 表示；`_parseCounts` 只回值不記日誌
- 新增一個薄包裝（例：`_decodeRecentProjects(raw)`）呼叫純解析、對每個 index 記一筆既有的 level 900 日誌（event、文字、level 不變），3 個呼叫端改呼叫包裝，日誌點只有一處；不要在 3 個呼叫端各寫一份記錄迴圈
- 不改公開 API、不改 `WorkspaceLogEvent` 列舉、不改 SPEC-005

**紅燈步驟**
1. `test/unit/workspace/workspace_repository_test.dart` 新增：直接驗證純解析對「counts 格式不符」的元素回 counts 為 null 且 `invalidCountsIndexes` 含該 index（需讓純解析可測：以 `@visibleForTesting` 的頂層或靜態函式暴露），先跑確認紅燈
2. 實作純解析與包裝，轉綠
3. 既有「格式不符記 level 900」的日誌斷言維持綠（證明呼叫端仍記錄）
4. 跑 `test/unit/workspace/`、`test/unit/app/`、`test/unit/architecture/` 全綠
