## Task Summary

裁決 SPEC-004 4.36–4.38 容器『ConsumerWidget 以 select 自行訂閱』與實作傳值不一致

---

## Problem Analysis
### 問題根因

SPEC-004 對三個資料視圖容器寫了兩組契約，實作兩組都沒有照做。

| 契約 | 規格出處 | 實作現況 |
|---|---|---|
| 容器為 `ConsumerWidget`，以 `select` 自行訂閱資料 provider，以 `ref.listen` 重建 | §2〈容器元件的例外〉；4.36 default 列與 state-change 列；4.37、4.38 state-change 列 | `MatrixGrid`：`StatelessWidget`；`SwimlaneGrid`：`StatefulWidget`；`AppDataTable`：`StatelessWidget`。三者都不 import riverpod，資料由建構參數傳入 |
| 捲動 offset 由頁面層持有的 `ScrollController` 承載，元件庫元件不得持有畫面級狀態 | 4.36 default 列〈offset 由頁面層持有的 `ScrollController` 承載〉；§2〈頁面狀態保留〉 | offset 都存在元件內部：`AppDataTable` 的 `ListView` 沒有 controller，offset 存在它自己的 `ScrollPosition`；`MatrixGrid` 的 `TableView.builder` 也沒有 controller；`SwimlaneGrid` 在自己的 `State` 建立 `_hController`、`_vController` 兩顆 |

訂閱在畫面層：`domain_view_screen` watch `domainMatrixProvider`、`domainSwimlaneProvider`；`ticket_list_screen` watch `ticketListStateProvider`；`uc_flow_screen` watch `ucFlowUcListProvider`。三個畫面都 watch 整個 provider，沒有用 `select`。

### 影響範圍

- 已驗證：規格 4.36 的「頁面層 ScrollController」在程式碼中不存在。`lib/` 中只有 `swimlane_grid.dart` 與 `two_column_layout.dart` 用到 `ScrollController`。
- 已驗證：規格 4.36 press-ack 列要求「排序後經 controller 將 offset 歸零」（SPEC-003 §3.4），`lib/screens/ticket_list/` 中沒有任何歸零程式碼；`test/` 與 `integration_test/` 對 `scroll-tickets-list` 只測「drag 至末端 offset 改變」，沒有測排序後歸零。
- 推論，未實測：切換導覽項時 offset 保留，靠的是 `IndexedStack` 讓元素存活，與規格要的結果一致，載體不同。切換專案時 offset 重置（SPEC-003 §3.4、§3.1 生命週期），若元件 key 不變，內部的 `ScrollPosition` 不會被丟棄，可能不重置。
- 規模：Ticket 清單在 1313 列下渲染（`app_data_table_test.dart`〈virtual 渲染 1313 列假資料不溢位〉），畫面層 watch 整個 provider，每次變更都重建整個子樹，正是 §2 例外想避免的情形。實際重繪成本沒有量測。

### 相關 Error Pattern

無直接對應。規格與實作都標為「提案」，同一條契約（§3.7 核定記錄第 19 列）核定後沒有回頭驗證實作。屬設計問題（品質基線規則 3），改哪一邊是設計決策。

### 實驗發現

- 已驗證：三個容器都是傳值元件，與 §2 一般元件的規則一致，與 §2 容器例外不一致。
- 已驗證：offset 由元件內部承載，與 4.36「頁面層 ScrollController」以及 §2「元件不持有畫面級狀態」不一致。
- 已驗證：4.36 的「排序後 offset 歸零」既沒有實作，也沒有測試。
- 未驗證：切換專案時 offset 是否重置；整頁 watch 在 1313 列下的實際重繪成本。

## Solution
### 分析結論（待裁決）

這是兩個獨立的不一致：訂閱位置（容器自行 `select`，還是畫面傳值）與 offset 載體（頁面層 controller，還是元件內部）。兩者可以分開裁決，但改實作的方案會一起動到。

### 方案一：改規格，認可傳值形態

把 §2 容器例外收窄或刪除，4.36–4.38 改寫成「畫面層 watch，以參數傳值」；offset 載體改寫成元件內部的 `ScrollPosition`／`State`，畫面級狀態的保留由 `IndexedStack` 承擔。

| 面向 | 現況的實際輸出（不改程式碼） |
|---|---|
| 訂閱 | 畫面 watch 整個 provider（`domainMatrixProvider`、`ticketListStateProvider` 等），任一欄位變更都會重建整個容器子樹 |
| offset：切換導覽項 | 保留（`IndexedStack` 不 dispose） |
| offset：排序後 | 不歸零。沒有實作，也沒有測試，與 SPEC-003 §3.4 不一致 |
| offset：切換專案 | 未驗證，推論可能不重置 |

- 利：程式碼不用改，元件維持純傳值，widget test 不需要 ProviderScope。
- 弊：§2「元件不得持有畫面級狀態」須開例外給 offset。「排序歸零」「切換專案重置」沒有頁面層 controller 可以呼叫，須另定機制，例如換 key 強制重建，或由元件接收 reset 訊號。§2 例外原本的效能理由（1300 筆規模下的整樹重建）會變成接受成本。這項成本沒有量測過。

### 方案二：改實作，照現行規格

三個容器改為 `ConsumerWidget`，以 `select` 訂閱；頁面層建立 `ScrollController` 並傳入容器（SwimlaneGrid 的兩顆 controller 上移到頁面層）。

| 面向 | 改完後的預期輸出 |
|---|---|
| 訂閱 | 容器只在 select 的欄位改變時重建，畫面層不再持有整份清單 |
| offset | 頁面層的 controller 可以 `jumpTo(0)`，排序後歸零與切換專案重置都有了明確的呼叫點 |

- 利：與 §2、4.36–4.38、§3.7 第 19 列核定的設計一致；歸零與重置有明確載體。
- 弊：要改三個元件檔、三個畫面檔，以及元件 widget test（須補 ProviderScope 與 override）。元件和 provider 綁在一起，降低了元件庫的可重用性。SwimlaneGrid 的 `jumpTo` 定位（4.38 locate，套件已知限制，見實作註記）須隨 controller 上移重新驗證。

### 4.36 offset 載體（acceptance 第 2 項）

已查明：`AppDataTable` 的 `ListView` 不掛 controller，offset 存在該 `ListView` 自己的 `ScrollPosition`。規格寫的「頁面層持有的 `ScrollController`」在 `lib/` 中不存在。
