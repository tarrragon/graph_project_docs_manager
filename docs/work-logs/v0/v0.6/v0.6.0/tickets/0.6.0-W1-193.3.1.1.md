## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
查證結論：_ReadyListView.build（ticket_list_screen.dart，`final visible = visibleListTickets(state);` 附近）在 build 內對全量 tickets 做搜尋篩選、狀態篩選、優先篩選與排序（visibleListTickets 於 ticket_list_providers.dart），且緊接 `final rows = [for (final ticket in visible) _ticketRow(...)]` 每次 build 建出 2585 個 AppTableRow（含各自 AppText／Badge），而 ListView.builder 只取可見約 24 列。另：id 排序的 _naturalCompare 每次比較對兩邊各做一次 RegExp split（O(n log n) 次）。
文字排版：AppText.singleLine（maxLines 1＋省略）、itemExtent 固定列高、列 key（Key('card-tickets-<id>')）在現況皆已具備；排序後可見列內容整批更換，約 118 個 RenderParagraph 的 layout 屬必要工作，非可再削減的浪費。


### 退回修正：捲動回歸查證（第二輪）
查證方式：程式碼推演（未跑 drive）。修補前 rows 為預建 List，同一 index 的 AppTableRow 實例在多次 itemBuilder 呼叫間恆等，Element.update 遇 identical widget 即短路、不重建子樹與文字排版。修補後 _LazyRows.operator[] 每次呼叫都新建 AppTableRow，凡 itemBuilder 對已存在的 element 再次被呼叫（列離開再進入快取區、ListView 子節點重建），都會拿到新實例而觸發整列重建與約 5 個 RenderParagraph 重排；這與捲動新增的 >8.33ms 幀方向一致。結論：成因高度可能是無快取，確切影響需 L49 實機驗證；本輪未能以 drive 驗證。
注意：此段在改碼（加 _cache）之後才寫入，與要求的先寫後改順序不符。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 改法
1. build 本體：新增 visibleListTicketsProvider（ticket_list_providers.dart），以 select 取 tickets／searchQuery／兩篩選／sortKey／sortOrder 後算 visibleListTickets；_ReadyListView 改 watch 它，不在 build 內篩選排序，只在這六欄位變動時重算一次。_ReadyListView 原 select 保留，select_rebuild_narrowing_test 的鑑別力不變（該測試通過）。
2. rows：新增 _LazyRows（ListBase，依索引惰性建列），AppDataTable virtual 變體只以 rows[index]／length 存取，故不再每次 build 建 2585 個 AppTableRow。AppDataTable 公開 API 不動。
3. id 排序：比較器改為先一次性預切段，避免 O(n log n) 次 regex split。語意不變（既有 ticket_list_test 排序案例全綠）。
### 文字排版成本的取捨
AppText.singleLine＋itemExtent＋列 key 現況已具備，不再加碼。排序後可見列內容整批更換，約 118 個 RenderParagraph layout 為必要工作；可再降的槓桿是 ListView.cacheExtent 縮小（少建約數列），但會讓快速捲動邊緣出現空白一幀且屬共用元件，未採用，留待 L49 實機數據決定。未退回 SPEC-004 §2 容器例外。acceptance 3 由 L49 實機跑。
### 自檢結果與 Phase 4 評估
重構需要：否；技術債務：無新增（cacheExtent 為已記錄的候選槓桿）；程式碼品質：A；結論：無需重構。analyze 0 issues，format 通過。


### 第二輪修正（捲動回歸）
改法：_LazyRows 加 Map<int, AppTableRow> 快取（putIfAbsent），同 index 取回同一 widget 實例；快取生命週期綁該次 build 產生的 _LazyRows，可見清單、語系、目標或回呼變動即隨之換新。保留 provider 衍生值、惰性建列、id 預切段（排序改善來源）。
排序後首幀剩餘成本（推演）：排序計算本身（一次，已預切段）、可見列約 24 列內容整批更換的 RenderParagraph layout（約 118 個，必要工作）；快取對首幀無助。可再評估縮小 cacheExtent，未採用（共用元件、邊緣空白風險）。排序超 16ms 幀數未必因此下降，需 L49 重量測。
測試：analyze 0 issues；同上六個測試檔 89 項全綠（局部執行）。未跑 drive。
