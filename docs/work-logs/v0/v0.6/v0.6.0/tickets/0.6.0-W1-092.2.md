## 重現實驗結果
### 實驗方法

- 對象：`git -C <repo> archive HEAD .claude/skills/line-board`（HEAD `c805f26e71`）解到 scratchpad `0922/`，插樁只做在副本，repo 內未改任何檔。執行指令 `claude plugin test <副本>`
- 插樁三處（皆在副本）：
  - `tests/paneHarness.ts` 的 `startBoard`：以 `performance.now()` 切出 setup／`$.session.start`／`clock.advance(1)`／`ui.mount` 四段；把傳入的 `on` 包一層，記錄每次 test 端 hook 被呼叫的事件名與時刻（即 engine→hook 往返次數）
  - `hooks/register.tsx`：模組頂層記載入時刻；`session.start` handler 進入時刻；`openIfConfigured` 與 `refresh` 內每個 `read*`／`findCheckouts`／`update` 各包一層計時。plugin 程式碼跑在獨立 realm，`console.log` 與 `globalThis` 都到不了測試端，所以改以帶 `@@R` 前綴的 `$.ui.log` 回送，harness 攔下這類行、不轉給原 handler、不計入往返次數
  - 第二輪起另在 `hooks/` 其餘 27 個模組頂層記最早的求值時刻，把「session.start 到 register 載入完成」再拆成「求值前（建 realm、讀檔、轉譯、連結）」與「模組求值」兩段
- 欄位定義（每次 `startBoard` 一筆）：
  - boot：harness 呼叫 `$.session.start` → plugin 的 register 模組求值完成
  - start.handler：register 載入 → `$.session.start` 回到 harness（handler 本體：command.register、tool.register、發出 `openIfConfigured`）
  - advance：`clock.advance(1)` 的耗時；`openIfConfigured` 與第一輪 `refresh` 以 `void` 發出、不在 session.start 內等待，實際在這一段跑完
  - mount：`ui.mount` 的耗時
  - 首測：每個 Pane 測試檔（6 檔）第一次呼叫 `startBoard`；其餘為非首測
- 分組（每組 N=5 輪，每輪 73 次 startBoard，其中首測 6 次）：baseline（不加壓）、加壓 16 個 `yes`、加壓 48 個 `yes`（見實驗執行的加壓紀錄）
- 補充對照：在 register 多 import 27 個極小模組（v1），或多 import 1 個約 215 KB 的模組（v2），各 N=5，看 boot 隨模組數與原始碼量的變化；兩者結束後還原，再跑 N=5 對照組（m2）

- 插樁開銷：未插樁的副本整套 4.84 s（12:16:23），插樁後 baseline 4.66–6.55 s，差異落在輪間變異內
- baseline：12:19:16–12:19:43，load1 5.05→6.27，5/5 綠

- 模組求值拆分（m）：12:27:19–12:27:47，load1 11.23→16.60，5/5 綠
- v1：12:28:20–12:28:41，load1 11.5–12.1；v2：12:28:59–12:29:31，load1 10.2–12.3；m2 對照：12:29:36–12:29:56，load1 12.6–13.4；皆 5/5 綠
- 全部 35 輪無任何 fail

### 實驗發現

已驗證：

1. **每個 Pane 測試的主成本是 plugin 冷啟動，不是 refresh 的往返**。boot 在非首測占 startBoard 的 73–77%，首測占 62–69%；refresh 各 read* 合計（advance 段）只占 14–20%，mount 4–7%（量測表見 Test Results）
2. **每個 test 都重新建一份 plugin realm、重新載入全部模組**：每筆 startBoard 的 register 載入計數皆為 1、27 個 hooks 模組計數皆為 27，同一檔內的 harness 模組則只載入一次。這是 `claude plugin test` 對每個 test 給新 engine 的行為，plugin 程式碼無法讓兩個 test 共用同一份已載入的 plugin
3. **boot 幾乎全在模組求值之前**：非首測 boot 109.3 ms 中求值 0.1 ms，首測 370.5 ms 中求值 2.0 ms。成本在建 realm、讀檔、轉譯 TS／TSX 與連結
4. **boot 隨原始碼量成長**：多 import 27 個極小模組，非首測 boot 108.8→120.1 ms（+10%）、首測 312.2→443.1 ms；多 import 約 215 KB 程式碼（現有 hooks 約 175 KB，總量成為約 2.2 倍），非首測 boot 108.8→192.4 ms（+77%）、首測 312.2→1045.2 ms（3.3 倍）。看板每長一份程式碼，每個 Pane 測試都會變慢
5. **首測與非首測的差值主要也在 boot**：差值 baseline 378.6 ms（boot 占 66%）、加壓 16 時 590.6 ms（57%）、加壓 48 時 1233.7 ms（60%），其餘差值在 advance（refresh 程式碼第一次執行）。首測較慢應是子行程內轉譯快取與 JIT 都還是冷的；每個測試檔各付一次
6. **refresh 的往返**：每次 startBoard 平均 43.5 次（非首測）／52.7 次（首測）test 端 hook 往返，組成為 fs.read 24.6、ui.log 8.5（全是讀不到檔時記的 debug 行）、process.run 7.6、session.root 1.8、fs.list 1.7，其餘各 1。最貴的兩步是 `readTicketStatus*`（baseline 8.8 ms，加壓 48 時 49.3 ms）與 `readSessions`（7.1／38.2 ms）；平均每次往返約 0.4 ms（baseline）到約 3 ms（加壓 48）
7. 加壓下各段大致等比例放大（boot 占比 73%→72%→73%），沒有某一段對負載特別敏感

未驗證：

- boot 在「建 realm」「讀檔」「轉譯」「連結」之間怎麼分配：插樁點最早只到模組頂層，求值前的細分要 engine 端才量得到
- `claude-code/testing` 是否有讓多個 test 共用同一個 engine 的 API：本機只有 `claude-code` 執行期型別，沒有 testing kit 的型別或文件可查；已觀察到的 test callback 形如 `($, on)`，每個 test 各給一個新的 `$`
- 改用 dynamic import 延後載入不常用模組是否真能降低 boot：要看 engine 對 dynamic import 的處理，且 Pane 測試多數會用到畫面相關模組，可延後的部分有限
