## Problem Analysis

## 重現實驗結果
### 實驗方法

主 checkout（HEAD 432119e3e 時點），設定 `multi-session.json` = `{"coordinationTicket": "0.5.0-W1-349"}` 原樣不動，對兩個 Python 消費者直接餵 stdin，比對 349 與 099 兩張票的結果。

### 實驗執行

1. hook：`coordination-queue-line-check-hook.py` 餵 PostToolUse Edit `0.6.0-W1-099.md` 的 payload，結果 rc=0、stdout 空。
2. statusline：`statusline_lane.py --inner true`，stdin `session_name=協調票解析`：
   - `--coord-ticket .../0.5.0-W1-349.md` 輸出 `協調票解析`
   - `--coord-ticket .../0.6.0-W1-099.md` 輸出 `L50 │ 協調票解析`

### 實驗發現

已驗證：設定停在舊票時，hook 對現行協調票靜默不檢查、statusline 掉線號；兩者都無錯誤輸出，換版遺漏只能靠人發現。看板與 line_status 走同一個 `readProjectConfig`，讀到的是同一張舊票（未另行實機驗證畫面，依程式路徑推定）。

## Solution
### 結論

移除「協調票是誰」這份手寫狀態，改由票面自帶標記推導：協調票在 frontmatter 加 `coordination: true`，消費者一律呼叫同一支解析函式，找出「active 版本中 `coordination: true` 且 `status: in_progress` 的票」。`multi-session.json` 與 `--coord-ticket` 降為選用覆寫。

### 候選方案

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 標記 + 一支 Python 解析模組 `multi-session-orchestration/scripts/coordination_ticket.py`（可 import，也有 `--json` CLI）；Python 消費者 import，line-board 以 `$.process.run` 呼叫 CLI | 真正單一實作，規則只寫一次 | 看板每 30 秒多一次 python 行程；需處理 python3 不可用的退路 |
| B | 同標記，TS 與 Python 各寫一份，共用 fixture 做契約測試 | 看板不起子行程 | 兩份實作，line-board 已有多處「與 X 同一規則」註解，漂移風險同型 |
| C | 保留設定檔，版本開工時由工具自動改寫 `multi-session.json` | 消費者不動 | 狀態仍是兩份；`.claude/project-integration/` 寫入受白名單擋（0.5.0 收尾實例），自動化本身會撞同一道牆 |

選 A 的理由：本票的根因是同一事實存兩份，B 在程式層重演這件事，C 在資料層重演。

### 解析規則

1. 讀 `docs/todolist.yaml` 中 `status: active` 的版本（與 `ticket_system/lib/version.py` `get_active_versions` 同源）；對每個版本掃票目錄，取 frontmatter `coordination: true` 且 `status: in_progress` 的票。
2. 覆寫：`multi-session.json` 的 `coordinationTicket`（或 statusline 的 `--coord-ticket`）存在時，先讀該票狀態。未結案就採用，結果標 `source: override`。已結案（completed／closed）就不採用，附一則警告「覆寫的協調票 <id> 已結案，改用自動解析」，再走規則 1。
3. 回傳型別：`ok`（票號、票檔路徑、source、warnings）、`none`、`multiple`（候選清單）、`error`（todolist 讀不到等原因）。不靜默。

| 結果 | 看板 | line_status | statusline | 主控接續提示 | 佇列行 hook |
|------|------|-------------|------------|--------------|-------------|
| 1 張 | 照常 | 照常；警告列於輸出 | 照常 | 指名該票 | 見下 |
| 0 張 | 不自動開 Pane（沒用多 session 的專案不受影響）；`/board` 顯示「active 版本沒有標記 `coordination: true` 的進行中票」與補法 | 同訊息 | 省略線號，stderr 一行 | 第 2 步改為「找不到協調票，請用戶確認」 | 不需解析 |
| 多張 | `/board` 列出候選，不自行擇一 | 列候選 | 省略線號，stderr 列候選 | 列候選，請用戶裁定 | 不需解析 |

hook 不走解析：寫入的票本身 frontmatter 有 `coordination: true` 就檢查。檢查對象本就是「被寫的那張」，不需要先知道「現行那張」。

### 換版不需改設定檔

- 新版本的協調票建立時帶標記（子票 100.4：`ticket create --coordination`），開工即生效。
- 舊票 complete 後自然退出候選。
- 用戶動作（不由本線代改，屬用戶設定檔）：子票 100.2 合併後，從 `.claude/settings.local.json` 的 statusline 命令刪去 `--coord-ticket ...`；不刪也不會壞，因為覆寫的 349 已結案，會走警告後退回自動解析。
- `multi-session.json` 在 100.3 刪除（主線程寫入該路徑受白名單擋，交由 worktree 代理人處理；刪不掉時一樣走「已結案覆寫」退路）。
