## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 取證方式（L50，2026-11-04）

本票需要一次失敗的完整輸出才能判定成因，現在無法主動重現。之後任何一條線執行 push 時，改用下列命令保留全文：

```bash
out=$(git push origin main 2>&1); rc=$?; echo "rc=$rc"; echo "$out"
```

- 不接 `| tail`，也不加 `-q`。拒絕原因（`[rejected]`、`remote:` 行、hook 訊息）可能在輸出的頭或中段，`tail -1` 只留得下最後一行的 `failed to push some refs`（依 bash-tool-usage-rules 規則二：過濾方向）。
- 失敗時另外記錄：失敗當下的 `git rev-parse HEAD origin/main`；重試前跑 `git fetch` 後的 `git rev-list --left-right --count main...origin/main`；同一時間是否有其他線在推送（看 099 協調票當時的 log）。
- L50 本 session 推送多次（次數未逐筆記錄），事後比對 origin/main 都已含推送內容，但用的是 `-q ... | tail`，失敗訊息即使出現也會被截掉，所以不能當作「沒有失敗過」的證據。

### 2026-11-05 L50 補充證據（0.6.0-W1-181／182／184 收尾期間）

- 本 session 推送三次（1149ab28cc、9b528e5002、b7c6482107），皆以 `out=$(git push origin main 2>&1); rc=$?` 保留全文，三次 rc=0，未取得失敗樣本。
- 已排除本機 ref 守衛拒絕：`.git/hooks/reference-transaction` shim 在 prepared 階段呼叫 `git-ref-transaction-content-guard.py`，判定阻擋時回 87 轉 exit 1，且必先寫 `logger.warning("ref transaction 被阻擋：...")`。`.claude/hook-logs/git-ref-transaction-content-guard/` 的 20261104 與 20261105 日誌只有 DEBUG／INFO 兩級（共 2498 行），無 WARNING，所以 L49 那三次失敗不是守衛 deny。shim 的 uv 啟動失敗路徑是 fail-open（exit 0 加 stderr），不會造成 push 失敗。
- 未驗證的候選成因：共用 checkout 的多條線共用同一個本機 main，兩條線幾乎同時推送同一個 main 時，後到者在遠端 ref 已前進的瞬間被拒（`[rejected]`／`cannot lock ref`），重試時遠端已含相同 commit，結果為成功或 up-to-date，fetch 後 0 0。與三項觀測一致，但需失敗當下的完整 stderr 與同時段 099 協調票 log 才能確認。

### 觀測（2026-11-09，L50 session）

兩次 `git push origin main` 第一次就成功，沒有重現失敗：`959ba1040b..cef4a3da9e`、`aeaa9632be..d6927e3ec1`。第二次推送時 main 領先 origin 9 個 commit，且有一個 locked 的 agent worktree 尚未合併。成功的樣本不能用來分析成因，觸發條件（下次失敗時保留完整輸出）仍未發生。
