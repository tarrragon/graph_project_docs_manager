### 實驗發現

已驗證：
1. 逾時的成因是負載：Pane 單測平均耗時從 baseline 約 375 ms（非首測）上升到加壓二的約 1231 ms，約 3 倍；最大值從約 1.6–3.3 s 升到 4–5.2 s。只有加壓二重現逾時，與 10-28 觀測（load 約 60 時 5 輪中 3 輪紅）的方向一致

4. 主要耗時步驟：每個 Pane 測試都呼叫一次 `startBoard`，依序執行 `session.start`、`clock.advance(1)` 觸發第一次 refresh，再 `ui.mount` 渲染。refresh 期間走 test 端 hook 的 `process.run`（git worktree list、協調票 CLI、每個 pid 一次 `ps`）與 `fs.list`／`fs.read`（7 個狀態檔、票檔），每一次都是 engine 與 hook 的往返。harness 沒有自訂等待條件，`ui.find` 直接查描述樹。所以耗時隨往返次數與 CPU 排程延遲成正比。帶 `sessionStub` 的測試（約 1 s 起跳）明顯比不掛狀態檔的專案設定測試（約 140–180 ms）慢

未驗證：

- 逾時的確切 load 門檻：介於 48（無逾時）與 88（重現）之間，沒有更細的取樣


## Solution
### 結論

根因判定：**機器負載**，屬 `test-assertion-design-rules.md` D1 的「機器負載」類不可靠斷言。信心度：中高（N=30，in／out 各 15，對調順序，在 load 33–119 區間重現）。

- 斷言本身沒有計時，但每個 Pane 測試的 pass／fail 取決於整體執行時間是否在 `claude plugin test` 預設的 5000 ms 內，等同一個隱含的計時門檻。程式碼不變、只改變 load，就能讓結果翻轉，符合 D1 的判定流程
- 不是程式缺陷：30 輪中 29 輪全綠，唯一紅輪的兩個測試都只有逾時，沒有任何斷言失敗
- 冷啟動是加乘因子，不是獨立的根因：首測的冷啟動成本約為非首測的 2–3 倍，讓首測最先撞線，但負載夠高時非首測也會逾時（10-28 觀測）
- 不是位置問題（見 Problem Analysis）
- 對照閘門：閘門內 3 次皆綠，與合併當下 load 較低一致；閘門在 load 約 60 以上時有誤紅風險

### 候選方案

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| A 放寬 Pane 測試逾時並寫明依據 | 給 Pane 測試（或 6 個 board*.test.ts）設定明確逾時，例如 15000 ms，依據為本次 load 約 119 時的實測最大值 5157 ms，留約 3 倍餘裕 | 改動最小；閘門誤紅大幅下降；保留端到端測試在主套件內 | 仍是計時門檻，只是移遠；load 再更高仍可能誤紅；真實的效能退化要到 3 倍才會被看見 |
| B 降低 Pane 測試的單測開銷 | 減少 `startBoard` 的 hook 往返（例如用不帶 `sessionStub` 的精簡 fixture 處理不需要 session 的斷言），或在 describe 層共用冷啟動 | 治本：降低對負載的敏感度，整套變快 | 需要改 harness 與多個測試；改 fixture 有降低涵蓋度的風險；冷啟動構成尚未量測，需要先做一次剖析 |
| C 把 Pane 端到端測試移出閘門套件（tag 或獨立指令） | 主套件只留純函式測試，Pane 測試獨立執行 | 閘門結果不再受負載影響 | Pane 行為失去合併前的保護，這正是最常改動的區域；需要另外安排執行時機 |
| D 閘門只對 `timed out` 的失敗自動重跑一次 | 在合併閘門判讀時，只把逾時類失敗重跑 | 不動測試 | 掩蓋真正的效能退化；屬框架閘門的改動，範圍超出本票 |

建議：**A 先落地**（低成本，立刻消除閘門誤紅），**B 列為後續**改善。C、D 不採：C 犧牲最常改區域的合併前保護；D 讓逾時失去訊號，並且動到框架閘門。
