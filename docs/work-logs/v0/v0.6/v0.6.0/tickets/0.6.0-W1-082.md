## Solution
### 結論

根因分兩層：

1. **可判定的部分（staleness）**：測試自身的計時假設。阻擋斷言依賴 hook 內 5 秒與 30 秒兩個牆鐘逾時，逾時即 fail-open 回 0；屬 D1 同軸，應移出主套件（wallclock）。純 CPU 負載下無法觸發，觸發條件推測為 I/O 等待或 uv 冷啟動延遲，未在失敗當下取證。
2. **無法判定的部分（flat-gate 四項）**：無逾時，失敗發生在 hook 啟動或輸出層面；現有證據無法區分成因。
3. **主要障礙**：閘門日誌不保留失敗細節，間歇紅燈事後無法取證。此項優先於前兩項處理。

名額外負載：6 次取樣中的重負載皆為平台常駐（視訊會議與編碼、WindowServer、OrbStack、Prowl、動態桌布、Spotlight）與每次工具呼叫的短命 hook 程序。依派發分類屬「平台常駐，改讓測試承受」，不建 231 系列擴大名額票。唯一可疑項是一筆 xcodebuild（pid 51984），取樣時已結束，無法確認是否經 run-with-timeout，不據此建票。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 閘門保留失敗細節（314.1）+ staleness 生產啟動測試標 wallclock（314.2）+ 取得細節後判定 flat-gate（314.3） | 先取證再修；staleness 牆鐘依賴立即移出閘門 | flat-gate 在 314.3 前仍可能間歇紅燈 |
| B | 閘門紅燈自動重跑失敗項一次 | 立即止血 | 掩蓋真實缺陷（PC-168 幸運連勝的反向），閘門語意變成「兩次中一次綠」 |
| C | 拉長 hook 內逾時 | 改動小 | 逾時是 hook 在生產環境的保護，為測試拉長影響生產行為；不處理 flat-gate |
