## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 結論

值域沒有送達的環節是**寫入時點**。代理人寫 Solution 時能看到的載體有：新 ANA 票的 placeholder、Schema 註解、派發骨架、代理人定義、append-log 的回饋。這些載體都沒有 `reviewed／skipped／n_a`。值域第一次主動出現是在 complete gate，而 092／092.2 的 complete 是 PM 執行的，所以代理人從頭到尾沒收到值域。

修正路徑則是**送達了但不完整**。gate 的非法值訊息附有 `fix-multi-view-status` 指令，但少了多行情境需要的 `--match`；fix 的多行拒寫訊息和 references 也都沒提。〈補充觀測〉說「只能在 1 行時用」是誤讀，實驗 b2 證實帶 `--match` 一次就能修好。另外發現兩點：gate 只讀第一行，合法值在前、非法值在後時會靜默通過（a2）；fix 的 `--reason` help 與實際行為不符。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A：placeholder 前移 | `ticket_builder.py` 的 ANA Solution placeholder 直接寫出 `multi_view_status: <reviewed|skipped|n_a>` 與子欄位要求，並指明用 `fix-multi-view-status`（遇到 0 行即新增）寫入 | 建票時就送達，每位讀票的代理人都看得到，不依賴每次派發的 prompt；只改一處 | 只影響新票；值仍然可能手寫錯，屬於引導，不是強制 |
| B：錯誤訊息揭露 `--match` | gate 的非法值提示在偵測到多行時附上 `--match <非法值子字串>`；fix 的多行拒寫訊息附 `--match` 用法；references 補記載；同時修正 `--reason` help | 讓修正路徑可以被發現，改動小，直接消除 092 收尾時的手改票檔 | 只改善事後修正，不減少寫錯 |
| C：gate 讀全部行 | checker 改為掃描 Solution 的所有 `multi_view_status:` 行，任一非法就擋下並列出全部 | 消除 a2 的靜默通過，判定不再取決於行序 | 改變既有判定語意，存量票可能被新擋下，代價未量 |
| D：寫入時驗值 | append-log 在 Solution 內容出現 `multi_view_status:` 時驗值，非法就警告並指向 fix 命令 | 在寫入當下送達，代理人當場就看得到 | append-log 是通用寫入命令，加入欄位特例會讓職責混雜 |

建議組合：A + B 是最小可行組合，一個解決送達、一個解決可發現性。C 與 D 留給清理線一併評估代價。與 #55 既有三個方向的對應：方向 1 與 A 同向，但載體建議從派發骨架改為 template；方向 2 即 B；方向 3 已由現有的 `--match` 涵蓋，縮減後併入 B。
