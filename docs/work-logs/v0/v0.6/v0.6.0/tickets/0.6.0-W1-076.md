### 分析結論（saffron-system-analyst，2026-10-12，HEAD fc20421f4）

#### 問題根因

`navigateTo(read, target, intent)`（`lib/app/router.dart`）只有三個參數，不帶 payload。跳轉目的畫面顯示什麼，完全由目的畫面自己的 provider 預設值決定。Ticket 清單、節點詳情、追溯視圖三個畫面的 provider 預設值皆為 fixture，且三者對共用掃描輪次（`scanRoundProvider`）零引用。因此凡是自已接真資料畫面 jump 進這三個畫面，落點一律是與來源項目無關的 fixture。這與 2026-10-09 J2（破洞報告 flow 類 → UC Flow）的成因相同。

#### 影響範圍

已驗證的事實：

| 畫面 | 資料來源（lib 現況） | 依據符號 |
|------|--------------------|---------|
| Domain 視圖 | 狀態推導已接共用輪次；`DomainReady.matrix` 為 null 時內容仍取 `DomainViewFixtures` | `domain_view_loader.dart`、`domainSwimlaneProvider`、`DomainReady.matrix` |
| 破洞報告 | 真資料（已接） | `GapReportNotifier` 監聽 `scanRoundProvider`；`detectGraphDefectGaps` 由 `gap_report_round_state.dart` 呼叫 |
| UC Flow | fixture（現在）；0.5 完成時會接（`0.5.0-W1-114.18`，pending） | `ucFlowUcListProvider` 回傳 `UcFlowFixtures.ucList`；畫面另有兩處直讀 |
| Ticket 清單 | fixture | `ticketListStateProvider` 預設 `TicketsUnloaded(count: TicketListFixtures.all.length)` |
| 節點詳情 | fixture | `nodeDetailStateProvider` 預設 `NodeDetailReady(nodeId: NodeDetailFixtures.normalNodeId)`；`_ReadyView` 直讀 `NodeDetailFixtures.nodes` |

- 破洞項的指向節點 ID（`GapReportItem.pointerNodeId`）在投影層已算出，但 `_openItem` 的 ticket／otherNode 分支未使用它；`TicketsReady.targetTicketId` 欄位存在但 lib 內無任何寫入端

### 實驗記錄（2026-10-12，HEAD fc20421f4，唯讀；未跑 flutter test、未啟動 App）

#### 實驗方法

靜態查證。跳轉的唯一入口是 `navigateTo`（`router.dart` 註解明訂畫面不得直接寫 `selectedDestinationProvider`），故列舉其全部呼叫點即為全量跳轉清單；再逐一讀各目的畫面的 provider 定義判定資料來源。

#### 實驗執行

| 指令 | 結果 |
|------|------|
| `grep -rn "navigateTo(" lib --include='*.dart'`，排除 `router.dart` 定義 | 26 個呼叫點，分佈：shell 1、project_unready_view 1、ticket_list 5、trace 4、scan_notification_controller 2、gap_report_screen 5、gap_report_provider 1、domain_view 1、node_detail 2、uc_flow 4 |
| `grep -rn "selectedDestinationProvider.notifier" lib` | 只在 `router.dart` 的 `navigateTo` 與 `consumeReturnTo` 內，無畫面繞過 |
| `grep -rc -E "scanRound\|ScanRound" lib/screens/ticket_list lib/screens/node_detail lib/screens/trace lib/screens/uc_flow` | 16 個檔全為 0 |
| `grep -c "pointerNodeId" lib/screens/gap_report/gap_report_screen.dart` | 0 |
| `grep -rn "targetTicketId:" lib`，排除 `ticket_list_state.dart` | 0 列 |
| `grep -rln -F "AdjacencyQuery" lib`、`-F "TicketDetail"` | 各只命中自身定義檔，無呼叫端 |
| `grep -rln -F "buildGraph(" lib`、`-F "detectGraphDefectGaps("` | 定義檔之外各有一個呼叫端（`scan_round.dart`、`gap_report_round_state.dart`） |

#### 實驗發現

已驗證：

1. 26 個呼叫點中，rail 意圖 4 個（側欄、通知點擊 2、破洞報告取消掃描回 Domain），jump 意圖 22 個
2. 三個畫面的資料來源皆為 fixture，無一接共用輪次
3. 自已接真資料畫面 jump 進三個畫面的呼叫點：破洞報告 3 個（ticket、otherNode、事件類無 UC 引用時的後備）、UC Flow 2 個（步驟列、檢視關聯）；Domain 視圖 0 個
4. 三個畫面 jump 出去到已接真資料畫面者，落點皆為破洞報告（真資料）
5. `0.6.0-W1-073` 驗收 1「production 編排層呼叫 buildGraph 與 detectGraphDefectGaps」在 lib 現況已成立；`AdjacencyQuery`、`TicketDetail` 仍無呼叫端

未驗證：真實語料下各分支的實際觸發數量；`0.5.0-W1-114.18` 合併後 UC Flow 兩條 jump 是否改帶節點 ID（該票 how 段只提到選定 UC、step、事件定位，未提節點詳情）。

**範圍驗證方法**：rg regex 法（單一入口函式的全呼叫點列舉）加逐檔讀取
**驗證指令**：見上表
**已知盲區**：(1) 不經 `navigateTo`、直接改畫面狀態 provider 的同畫面轉換不在清單內（如節點詳情關聯項點擊，屬畫面內切換非跨畫面）；(2) 經函式參考或變數間接呼叫 `navigateTo` 的寫法 grep 抓不到；(3) 系統通知點擊屬 rail 意圖，落點為破洞報告
**盲區影響評估**：(1) 不是跨畫面跳轉，不在本票範圍；(2) 以 `selectedDestinationProvider.notifier` 寫入點只有 `router.dart` 兩處交叉確認，任何切換畫面的路徑都必經這兩個函式，而 `navigateTo` 字面在 lib 內除 26 個呼叫點與定義外無其他出現形式；(3) 落點已接真資料，不影響結論
