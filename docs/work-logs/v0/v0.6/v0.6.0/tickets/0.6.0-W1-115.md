### PM 盤點（2026-11-03，L48）

現況：P7「SPEC-004 表中的 gap* key 全數存在於 zh／en ARB 且文案逐字相同」先以前綴與白名單篩出子集，再以 `expect(keys, hasLength(35))` 寫死數量。113.2 加了 3 個 key，所以 32 改成 35；之後每加一個 key 都要手改一次。

實測集合（main 6ba3580daa，python 對 ARB 與 SPEC-004 掃描）：
- SPEC-004 表中符合 `^| \`gap[A-Za-z]+\` |` 的列：47 個，zh／en 文案逐字一致 47／47。
- zh ARB 的 gap* key：49 個。不在規格表的只有 `gapReportScanning`、`gapsScanningProcessedCount`，這兩個屬掃描中畫面，不在 SPEC-004 gap 表。
- 規格表有、ARB 沒有：0 個。

設計（取代寫死計數，鑑別力不降）：
1. 移除前綴篩選、白名單與 `hasLength(35)`，改為比對規格表抽到的全部 gap* 列。
2. 正向：規格表每個 key 都要在 zh／en ARB 存在，且文案逐字相同（沿用既有迴圈）。
3. 反向：ARB 的 gap* key，扣掉具名豁免集合 {gapReportScanning, gapsScanningProcessedCount}（註明豁免理由：不屬 SPEC-004 gap 表），要全數出現在規格表。這是集合相等，不是數量相等。漏一列時，失敗訊息會列出缺哪一個 key。
4. 下界：keys 不可為空，且包含 gapCategoryOrphanEvent、gapCategoryEventDeclarationMismatch（沿用既有兩條 contains）。這兩條防止解析器抽到 0 列時空轉通過。
5. E2 對照輸入：把比對邏輯抽成測試檔內的函式 `missingInArb(rows, zh, en)`（或同等）。另以合成規格行 `| \`gapSyntheticOnlyInSpec\` | 甲 | A |` 餵入，斷言回傳含該 key（應紅的輸入確實被抓到）。

紅燈步驟（PC-GPD-079）：
- 先寫第 5 點的對照測試：函式尚未抽出，編譯失敗即為紅燈。
- 執行 `fvm flutter test test/unit/screens/gap_report/gap_report_projection_test.dart`，貼出失敗輸出。
- 之後才改 P7 本體。
