### 實驗執行

`wc -l lib/workspace/*.dart`（本檔 1006；同目錄其他檔 12-190）；`grep -nE "^(class|enum|typedef|const|final)"` 取區段；`grep -rhoE "<九個公開符號>" lib test integration_test | sort | uniq -c` 取引用數；`grep -rln workspace_repository.dart lib test integration_test` 取 import 檔清單。

### 實驗發現

- 全檔僅一個 domain：工作資料夾的選取、持久化與探測（workspace）。port／adapter／log 契約都是 WorkspaceRepository 自身的接縫，不是其他 domain 的概念，未觸及「> 2 domain 必須拆分」。
- 1006 行中約 165 行是 enum doc comment，約 605 行是 repository 類別本體。把 port／adapter／log／純解析搬出只會把檔案降到約 610 行，仍超過 300；行數真正集中於類別本體。
- 類別本體內可辨識的次職責是 recent projects 讀寫（loadRecentProjects、addRecentProject、saveRecentProjectCounts 及其 _read*/_write*/_encode*/_parse* helpers，約 712-962，約 250 行），與「資料夾選取與 restore」共用同一個 preferences handle 與 log sink。
- 預設 adapter 為 library-private，搬到別檔須改公開或改 `part`，會擴大公開面或引入 part 機制。

## Solution
### 結論：維持單檔，本票不拆分

理由：
1. 單一 domain，未達強制拆分條件；行數閾值為「考慮」級，已依其要求做 domain 邊界分析。
2. 機械式抽出 port／adapter／log 契約／純解析只降到約 610 行，仍超閾值，卻要把 private adapter 改公開或引入 `part`，並讓 22 個 import 檔面臨 import 變更（或須加 re-export 維持）——成本實、收益低。
3. 唯一有意義的切點是 recent projects 讀寫次職責（約 250 行），但那是類別拆分（抽出獨立 store 並共享 handle／log sink），屬設計變更而非拆檔，P3 技術債評估不足以支撐；且同一 preferences schema migration 與 recent projects 寫入有耦合，需先有實際觸發（新功能落在此區）再談。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A 維持（採用） | 不動 | 零風險，接縫集中、易追 | 檔案仍 1006 行 |
| B 機械抽檔 | ports+log 契約 → workspace_ports.dart，純解析 → recent_projects_codec.dart，原檔 re-export | 公開 import 不變 | 仍約 610 行；private adapter 須公開或 part；enum 註解引用 `[_persistAndInspect]` 等私有符號會跨檔失效 |
| C 抽 RecentProjectsStore 類別 | recent projects 讀寫獨立成類別 | 真正降低類別認知負擔 | 設計變更，影響 provider 與多數測試 stub（test/helpers/stub_workspace_repository.dart） |
