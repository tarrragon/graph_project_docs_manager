## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
遷移結果：flutter_riverpod ^2.6.1 -> ^3.0.0（lock 解析 3.4.3，riverpod 同為 3.4.3）。commit a62203a2d（分支 worktree-agent-ad905a033475d6dc5）。

修改範圍（37 檔）：
- StateProvider／StateNotifier／StateNotifierProvider／StateController：加 import package:flutter_riverpod/legacy.dart，未改寫為 Notifier。
- Override／ProviderListenable：3.x 不再由 flutter_riverpod.dart 導出，改 import package:flutter_riverpod/misc.dart（lib 1、test／integration_test 多檔）。
- AsyncValue.valueOrNull 改 value（gap_report_provider.dart 1 處；3.x value 回傳 T?）。
- 不再使用的 flutter_riverpod.dart import 移除（9 檔）。
- test/helpers/pump_harness.dart 新增 lastWinsByProvider，pumpHarness／pumpApp 與 shell_test 的 ProviderScope 使用：3.x 於同一容器重複 override 同一 provider 會 assert，本專案測試倚賴 2.x「後者取代」語意（明示預設 + 呼叫端覆寫）。

三項行為變更逐項評估：
1. 失敗自動重試：影響。lib 有 FutureProvider 2 個（builtinTrackingSchemaJsonProvider、builtinSchemaVersionProvider，載入內嵌資產）及 5 個 NotifierProvider；內嵌資產失敗屬確定性失敗，重試只延後降級路徑（SPEC-001 §1）出現。處置：根 ProviderScope（lib/main.dart）以 retry 回傳 null 關閉，維持 2.x「失敗即錯誤態」；測試各自的 ProviderScope 未設，不影響結果。
2. 通知以 == 過濾：Notifier 類 provider（5 個）狀態改以 == 比較；StateProvider／StateNotifier 走 legacy 路徑維持原行為。狀態型別若覆寫 == 且更新值相等，原本的重複通知會被抑制，屬預期且無害。受影響測試（254 個）全過，未見行為差異；接受新行為。
3. 不可見時暫停監聽：影響面為 ref.listen（lib 13 處）與離屏畫面對 provider 的監聽。單元／widget 測試環境無法重現實際視窗可見性，無法由自動化確認；處置為接受預設，交由 PM 合併後 macOS 實機 integration_test 與跨畫面（SPEC-003 §3.5 再次可見重掃、firstVisibleProvider）手動驗證。

Phase 4 評估：重構需要＝否；技術債務＝有（StateProvider 等 legacy API 28 檔仍在 legacy.dart，後續改寫 Notifier 另票；本票未建 spawn，因屬票面既定範圍外決策）；程式碼品質＝A；結論：最小遷移完成，無需重構。

PM 收尾：Phase 4 技術債務（14 個 lib 檔仍 import legacy.dart，合併後實測）建 0.6.0-W1-106；行為變更第 3 項實機驗證建 0.6.0-W1-107。
