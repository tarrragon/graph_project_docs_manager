L49（2026-11-03，sumac 分析，PM 以固定值複核）：
- 根因（中高信心）：宿主機 fseventsd（PID 427，已執行 20 天 11 小時）持續約 100% CPU，只回應歷史查詢，不推送即時事件。PM 用 ps 三次採樣複核：101.8／99.7／100.6%。App、package:watcher 與 SPEC-006 FR-11 都沒有可證的缺陷。
- 驗證過程：Swift 探針經對照確認寫法正確（歷史重播可收到 23934 筆，即時 0 筆）；node fs.watch、Dart Directory.watch、由 launchd 啟動的 Probe.app，即時事件全部是 0 筆；sandbox 內外結果相同。
- 觀測管道：VM service 新連線會重送完整歷史（各 78 筆，seq 連續，兩次比對相同）。140 寫的「只到首輪完成」與「時間戳是連線當下」都是 vmlog 腳本的誤讀。可靠讀法是 vm3.mjs：直接寫檔、不經 grep、以 sequenceNumber 連續性判讀。即時串流漏行無法重現，推測與多層 grep 加 Monitor 的管線有關（低信心）。
- B10 build 重做驗證：新建、追加、刪除探針檔，DirectoryWatchSource 一筆事件都沒有，與即時 0 筆一致。
- 未證實：fseventsd 高 CPU 與「不推送事件」是因果，還是同一故障的兩個症狀。在健康環境下 App 會收到事件，目前仍是推論。
- 待用戶在 Claude Code 外執行：Terminal.app 跑金絲雀探針、看 fseventsd CPU，必要時重啟 fseventsd 後重測（PM 轉達）。
- 後續：驗證配方腳本化（含前置健康閘門與金絲雀正向對照）另開 IMP；監看存活檢查（ready 完成但監看實際無效）屬產品決策，登記 spawn request。
