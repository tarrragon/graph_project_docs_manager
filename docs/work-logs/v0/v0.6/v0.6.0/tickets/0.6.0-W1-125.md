### 建票時的觀察（L50，2026-11-03，供接手者不必重建 context）

| 票 | 代理人寫入 how.strategy 的形態 | gate 的判定 | PM 的修法 |
|----|-------------------------------|------------|----------|
| 0.6.0-W1-101.2 | 散文（產生路徑以頓號列舉，無表格） | 缺「產生路徑盤點結果」，也缺 Solution 的 fail-open 段 | 重寫為三欄表格，另補 fail-open 段 |
| 0.6.0-W1-101.3 | 散文「產生路徑共三條，皆已涵蓋」 | 合併後 PM 先改寫，未實際被擋 | 改寫為三欄表格 |
| 0.6.0-W1-120 | 四欄表格「產生點｜入口｜輸出管道｜是否改動」，且缺分隔列 | 缺「產生路徑盤點結果」 | 改寫為「產生路徑｜是否覆蓋｜未覆蓋原因」 |

- gate 要求的格式（擋下時的錯誤訊息原文）：markdown 表格，一條產生路徑一列，「是否覆蓋」欄只接受「是」或「否」；how.strategy 非空時，gate 只讀 how.strategy、不讀 Solution。
- 對照實驗：0.6.0-W1-123 的派發 prompt 寫明了三欄欄位名稱與「是／否」限制，代理人第一次就寫對（合併後再確認）。這支持「格式未傳達」的假設，但只有一個樣本。

第四次實例（2026-11-03，L50）：0.6.0-W1-126.1 的代理人把盤點表寫成單行「產生路徑｜是否覆蓋｜未覆蓋原因」分隔文字，complete 時 gate 判缺「產生路徑盤點結果」。誘因之一在 PM 端：L50 的派發 prompt 與 --note 以「欄位「產生路徑｜是否覆蓋｜未覆蓋原因」」描述格式，全形直線被照抄成分隔符，而沒有寫明須為 markdown 表格。gate 的阻擋訊息本身有完整表格範例，但只在 complete 時才出現。修法評估時納入：派發骨架直接嵌入表格範例，而不是只列欄位名。
L50 實例（2026-11-03，129）：建票時 acceptance 要求新增 --parent deny/allow 測試，但 where.files 只列 hook 檔，代理人依派發指令停手；PM 以 set-where 補入 .claude/hooks/tests/test_acceptance_gate_batch_wave_coordination.py（f9b89656af）。附帶觀測：停手時代理人未改檔，worktree 被自動清理；以 SendMessage 恢復同一代理人後 worktree 已不存在，只能重新派發。兩者都是 hook 類要求在建票與派發之間的傳遞缺口。
第二個對照樣本（2026-11-03，L50，129）：派發 --note 與 prompt 明寫「markdown 表格（| 產生路徑 | 是否覆蓋 | 未覆蓋原因 |）寫進 how.strategy，單行「｜」分隔 gate 認不出」，代理人第一次就寫對，gate 的盤點判定日誌為「盤點 4 條、覆蓋 3 條、未覆蓋 1 條」（.claude/hook-logs/acceptance-gate/acceptance-gate-20261103.log 17:59:18）。另：ticket track dispatch 產生的骨架已有一行「產生路徑盤點表寫入 how.strategy，格式見 ticket-body-schema.md「防護類 ticket」節」，只給路由不給範例；126.1 的失敗發生在這行存在的情況下。
