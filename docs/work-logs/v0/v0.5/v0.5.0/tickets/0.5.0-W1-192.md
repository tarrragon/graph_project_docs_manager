## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 第二次重現（2026-10-13，0.5.0-W1-187.7 驗收稽核）

對已完成的票派發 acceptance-auditor 後，該票的 who.current 再次被改寫，這次變為 acceptance-auditor，history 仍為空。稽核者回報它未變更任何欄位，改寫發生在派發當下。與第一次的差異：這次票的狀態是 completed。兩次皆以 set-who 改回。

由此可知：改寫不區分票的狀態，也不區分被派發者是執行者還是唯讀的審查或稽核角色。

### 問題根因

寫入點是 `.claude/hooks/dispatch-identity-bind-hook.py` 的 `bind_dispatch_identity`。觸發條件為 PostToolUse(Agent)、非 worktree 派發、prompt 首行可解析出 Ticket ID，且 who.current 屬於 `UNBOUND_WHO_VALUES`；條件成立時，以 `ticket track set-who <id> <subagent_type>` 把 who 改為派發的代理人。`UNBOUND_WHO_VALUES` 刻意把 PM 名稱（rosemary-project-manager）視為無主態，原意是「PM 暫代管、等派發後改綁給實作者」。但 PM 自己執行的票一派發唯讀審查者（linux、basil-writing-critic、acceptance-auditor 等），審查者的名稱就被當成執行者寫進去。

history 沒有留下原執行者，原因有兩層：
- set-who 本身從不追加 history。
- 此 hook 用的是位置參數形式（整體覆寫 who 欄位），不是 `--current`。

全專案沒有任何程式碼追加 history，已另由 0.5.0-W1-214.1.3 承接。

身份守衛（`identity_guard`，complete／finish 強制）不符時印出的範例是 `--as <who.current>`，也就是審查者的名字。執行者照範例操作，就成了不實申報。

### 影響範圍

- 已驗證：凡是 PM 持有、在共用 checkout 派發多視角審查的票，who 都會被改寫成最後一位被派發的審查者。
- 已驗證：who 已指派給具名代理人（非 PM）時不會改寫，worktree 派發也一律跳過。
- 查重：#55 的留言有 who.current 相關的兩條範疇（claim 未帶 --as 不覆寫預填值；析取值比對失敗），#47 處理的是派發寫入 who 弄髒工作區。兩者皆未記錄「PM 持有的票被審查者覆寫」，原查重結論成立，關係為引用 #55。

### 相關 Error Pattern

PC-V1-002（錯誤指派保護）是身份守衛存在的理由；本現象是守衛自己的提示繞過了該保護。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

覆寫來自 `dispatch-identity-bind-hook` 把 PM 名稱列為無主態。PM 自己執行的票，在共用 checkout 一派發唯讀審查者，who 就被改成審查者。history 不留原值，是因為 set-who 從不追加，且此 hook 以整體覆寫的形式呼叫。身份守衛的範例 `--as <who.current>` 會引導執行者照抄審查者的名字。

### 修法候選與代價

| 案 | 作法 | 代價 |
|----|------|------|
| A 依寫入能力判斷 | 讀 agent 定義的 tools，不含 Edit 或 Write 者不綁定 | 依賴 agent 定義格式；`general-purpose` 等代理人的 tools 為全部，仍會被綁 |
| B 移除 PM 的無主態身分 | 只在 pending／待派發／?／空時綁定；PM 持有改由既有的 complete 前置讓出交接 | 讓出目前只在 complete／finish 生效，代理人在 check-acceptance 時會撞上身份不符，須把讓出延伸到其他身份檢查命令 |
| C 綁定改用 --current | 保留 history 欄位（與 214.1.3 的追加邏輯相接） | 無；與 A、B 皆可併用 |
| D 守衛訊息不給以他人名義申報的範例 | 改為提示回報 PM 以 set-who 改派 | 執行者多一步回報 |

建議：C＋D 必做；A 與 B 二擇一，由實作者讀碼評估連帶修改範圍後在 Solution 定案。落地為 children 0.5.0-W1-192.1，與 0.5.0-W1-214.1.3（who.history 追加）標記為相關。
