### 平台事件查證（acceptance：C 是否成立）— 成立

來源：Claude Code hooks 官方文件 https://code.claude.com/docs/en/hooks（claude-code-guide 擷取，2026-10-14）。
- 事件表：「`PostToolUseFailure` | After a tool call fails」。
- PostToolUse 段：「Runs immediately after a tool completes successfully.」「For tool calls that fail, add the same hook under PostToolUseFailure.」
- PostToolUseFailure 頂層欄位 `error`（字串）、`is_interrupt`（可選）、`duration_ms`（可選），無 `tool_response`。Bash 的 `error` 第一行為「Exit code N」；文件：「Key your hook on `tool_name`, `is_interrupt`, and the `Exit code N` first line; treat the rest of the string as display text, not a stable format.」
- Bash tool_response 文件列出 stdout、stderr、interrupted、isImage；exit_code 文件未提及（實機另有 noOutputExpected）。

### 實機驗證（PM，2026-10-14 17:35）

- 17:35:03 執行 `ls /nonexistent_probe_279_2`（Exit code 1，未經管線）：session-context-guard、handoff-cleanup、worktree-merge-reminder 三支 PostToolUse hook 日誌於該秒 0 筆。
- 正向對照：前後兩條成功命令（17:35:02、17:35:08）session-context-guard 皆有紀錄。
- `.claude/settings.json` 無 PostToolUseFailure 註冊（grep 0 筆）。

結論：PostToolUse 收到的 Bash 命令，shell 層結束碼必為 0；失敗走 PostToolUseFailure，本專案未註冊。

### 對本票的影響

1. helper 判定改以事件為準：在 PostToolUse 內，exit_code 缺席即代表 shell 層成功；保留命令自身成功回音的檢查，只為涵蓋複合命令中被管線或分號遮蔽的失敗（如 `ticket ... | tail` 整體回 0），docstring 寫明此依據與遮蔽情境。`interrupted` 檢查保留為防禦。
2. 結束碼 75（auto-commit 失敗）屬非零，走 PostToolUseFailure，PostToolUse hook 永遠看不到；各 hook 內「75 視為成功」的分支在 PostToolUse 上為死碼。
3. 掛在 PostToolUse 上、目的為觀察失敗的 hook（cli-error-feedback、parallel-claim-audit 的失敗判讀等）只收得到被遮蔽的失敗。此影響超出本票，另建 ANA（0.5.0-W1-281）。
後續（bb，2026-10-14）：0.5.0-W1-281 若決定把成功／失敗判定改掛 PostToolUseFailure，`.claude/lib/bash_tool_response.py` 的 docstring 須同步更新判定依據；此同步列為 281 落地 children 的驗收項。
