## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 設計分析（basil-hook-architect 產出；它在 worktree 內寫票時被 runtime 的隔離檢查拒絕，依指示停手，由 PM 代為寫入。PM 已抽查 TTL 常數與 turn_ended_at 標記式清理兩項事實）

#### 從實際程式碼確認的事實

- active-dispatch-tracker-hook（PostToolUse(Agent)）寫入 dispatch-active.json，每筆含 branch_name（isolation=worktree 時字面為 worktree）、agent_id、agent_handle（Agent 的 name 參數）、turn_ended_at
- 派發當下的 tool_response.agentId 有 68% 缺值，且命名空間與 SubagentStop 回報的 id 不同。可靠的比對鍵是 agent_handle，以正規式 ^a<handle>-[0-9a-f]+$ 比對 SubagentStop 的 agent_id
- #89 的前提在本 repo 已部分過時：subagent-stop-dispatch-cleanup-hook 現在只標記 turn_ended_at 而不刪除 entry，保留 24 小時（.claude/lib/dispatch_tracker.py 的 TURN_ENDED_MAX_AGE_HOURS = 24，PM 已核對）。映射只會在 TTL 過期、id 與 handle 都比對不上、或檔案缺席時遺失
- 子代理人的 hook payload 帶非空的 agent_id（is_subagent_environment 依此判斷），與 SubagentStop 屬同一命名空間
- payload 沒有 isolation 欄位，isolation 只出現在派發時 Agent 的 tool_input，所以一定要查映射
- CLAUDE_PROJECT_DIR 恆指主 repo，get_project_root() 無法分辨子代理人是否在自己的 worktree。Edit／Write 改用 tool_input.file_path（在主 repo 根目錄下、且不在 .claude/worktrees/ 下，即寫入 main）；Bash 改用 payload 的 cwd（merge-staged-index-guard、workspace-wipe-guard 已在使用）
- 未驗證：payload 的 cwd 是否等於子代理人實際的 shell cwd（這是改為 deny 前必須先做的實驗）；named agent 的 worktree 目錄名是 agent-<hex> 還是含 handle（只影響 D）

#### C 與 D 比較

| 面向 | C：子代理人端寫入守衛 | D：PM 端 PreToolUse(SendMessage) 警告 |
|------|----------------------|--------------------------------------|
| 攔截點 | 子代理人 PreToolUse：Edit／Write，以及 Bash 的 git add／mv／rm／commit | PM 送出 SendMessage 時 |
| 涵蓋範圍 | 所有隔離失效路徑，包括未知的路徑；補上 branch-verify 的兩個缺口（豁免 .claude/ 與 docs/；Bash 只擋 commit）；機械判定 | 只涵蓋 SendMessage 恢復這一條路徑；時點最早，但 PM 忽略警告時代理人就沒有防護 |
| 映射來源 | payload agent_id → dispatch-active.json（agent_id 精確比對或 agent_handle 正規式）→ branch_name == worktree；24 小時內可用，不需新增持久化檔案 | 收件者 handle → 同一檔案 → 再以 git worktree list 確認；目錄命名未驗證 |
| 誤報情境 | 映射命中且寫入落在 main，幾乎必為真實失效；風險只在 payload cwd 與實際 cwd 不一致（僅 Bash 路徑）；非隔離派發不會命中映射 | 非隔離收件者、worktree 名稱比對錯誤、agent team 訊息（teammate、shutdown_request）若未排除 |
| fail-open | 沒有 agent_id、映射缺或過期、讀檔錯誤、缺 cwd：放行並以 logger.info 記錄 | 同上：沒有映射就不警告 |
| 成本 | 中：新增一支 PreToolUse hook（兩個 matcher），重用 dispatch_tracker 的查詢 | 中低，但多一個前提未驗證的 worktree 存在性比對 |

#### E2 正向對照測試設計

- C：(a) 該紅：agent_id 命中 isolation=worktree 的 entry，且 Edit 的 file_path 在主 repo 根目錄下、不在 worktrees/ 下，斷言警告或阻擋；Bash 以 cwd=main 執行 git add 同理。(b) 該綠：同一代理人，寫入自己 worktree 內的路徑。(c) 該綠：同樣的寫入，但 entry 的 branch_name 為空。(d) 該綠：沒有 agent_id（PM）。(e) 該綠：映射缺失，並斷言有 info 日誌。E1 對照：拿掉映射命中後，(a) 必須翻為放行，證明守衛確實依賴 isolation。另以重播 2026-10-08 實測事件序列的 fixture 做 dogfood
- D：(a) 該警告：收件者有 worktree entry，但 git worktree list 沒有對應的 worktree。(b) 該綠：worktree 存在。(c) 該綠：收件者是非隔離代理人。(d) 該綠：shutdown_request 與 teammate 訊息

#### 推薦

採 C，先以 warn 上線，第二階段再改 deny。理由：C 是唯一在寫入前攔截、而且不依賴 PM 記性的選項；D 在 PM 忽略警告時失效，而 PM 端的判斷已由 0.5.0-W1-111.1（選項 A）的指引涵蓋。C 需要的映射資料已經存在，不需新增持久化檔案。D 的 worktree 名稱比對前提未驗證，日後可以低成本補上。warn 透過 additionalContext 送到子代理人，要求它停手、寫 NeedsContext、交回 PM 重派。驗證 payload cwd 之後才改為 deny。

#### 交用戶裁決的問題（附建議答案）

1. 是否新增一層強制機制（新 hook）？屬規則語意變更，需 WRAP 與用戶裁決。建議：是，新增一支 PreToolUse hook（選項 C）
2. deny 還是 warn？建議：先 warn。驗證 payload cwd 並確認 Bash 路徑後，Edit／Write 改為 deny。只在映射命中時 deny，映射缺失時永遠不 deny
3. 映射缺失或過期（超過 24 小時 TTL）時是否 fail-open？建議：是，一律放行並記 info 日誌，不為此延長 TTL
4. 是否同時做 D？建議：否，等 C 運作一段時間後再決定
5. 實作前的驗證：建議做一次實驗確認子代理人 PreToolUse 的 payload cwd，並以重播 fixture 作為 E2 正向對照

#### 框架 issue 處置（定案）

在 #89 observe，不新開 issue。兩條判準成立（抽象可攜；根源在 .claude/hooks），父票 dedup 判定與 #89 為引用關係。觀測內容：#89 的「idle 時刪除」前提在本 repo 已改為標記加 24 小時 TTL，映射遺失改由 TTL 過期或 handle 比對失敗造成，並說明守衛 C 依賴這份映射。指向 subagent-stop-dispatch-cleanup-hook.py 與 dispatch_tracker.py 的模組 docstring。時序：先讀 #89 原文確認其描述的是舊行為，等用戶裁決 C 之後再 observe，好讓觀測內容一併寫入裁決結果。observe 屬既有授權範圍。
