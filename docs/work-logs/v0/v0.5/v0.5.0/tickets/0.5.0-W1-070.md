# Execution Log

## Task Summary

現行框架規定一個 domain 一份 domain-map（DomainBundle 節點），但沒有載體承接跨 domain 內容（domain 間分層與依賴方向、通道、邊界決策、容錯策略、待決事項），schema 也沒有 domain → domain 的依賴邊；設計上游載體與（如需要）邊型，供本專案拆檔

---

## Problem Analysis
### 問題根因

框架對多 domain 專案只定義了「單一 domain」這一層的載體，沒有定義「domain 之間」這一層：

| 上游資產 | 現況（已讀原文） | 缺口 |
|---------|----------------|------|
| `domain-map-template.md` §2 | 只畫單一 domain 內的 bundle 分層 DAG（單／多 aggregate 兩形態） | 沒有 domain 間 DAG 的位置 |
| `domain-map-template.md` §2.5 | 通道表含「涉及 domain」欄、協調圖畫多個 domain | 這一節本身是跨 domain 內容，卻放在 per-domain 模板；拆檔後沒有單一歸處 |
| `domain-bundle-mapping-methodology.md` §3 | DAG 規則只管 domain 內 bundle | 沒有 domain 間依賴規則 |
| `tracking_schema.py` 邊型 `domain_dependency` | 正向欄位 `depends_on_domains`，class `ordering`、directed、手動、established | 欄位寫在 **SPEC** frontmatter（`spec-template.md` 宣告；本專案 7 份 SPEC 皆用），值是 domain 名字串不是節點 ID：它是「SPEC → 名稱」，不是「domain → domain」 |
| `tracking_schema.py` EVT | carrier `docs/events/{domain}/...` | 只表達事件歸屬，推不出依賴方向 |
| `tracking_schema.py` DomainBundle | carrier 接受 `docs/spec/{domain}/domain-map.md` 與根層 `docs/domain-map.md` 兩形態；`DOMAINBUNDLE_REQUIRED_FIELDS = {id, domain}`，註解明寫「僅描述單一 bundle 的識別欄位，不含 domain-map 全域結構」 | 全域結構沒有承擔者；根層形態若改放系統層內容，會被判成一個 DomainBundle 節點 |

**票面 why 的一處更正**：why 寫「schema 的 domain 間關係只有 UC 層 depends_on_domains」。實查為 SPEC 層（`grep -rn depends_on_domains docs/usecases` 零命中；`docs/spec/*/*.md` 7 份皆命中）。結論方向不變：仍無 domain → domain 邊。

**本專案的結構性錯位**（盤點時發現）：`docs/domain-map.md` 的 frontmatter 是 `id: DOMAIN-MAP-docs-graph`、`domain: "docs-graph"`。對 schema 而言它是**一個** domain 的 map，8 個「domain」落在模板 §3 的 bundle 層。用戶 2026-10-06 裁決把 8 個視為 domain、要求拆檔；本票依該前提分析，另將「維持單 domain、8 個為 bundle」列為候選 D 供對照，不推翻裁決。

**比對結論**：domain 間關係在現行 schema 只有兩條間接線索——SPEC 層 `depends_on_domains`（SPEC → 名稱字串）與 EVT 目錄歸屬。兩者都回答不了「domain A 是否依賴 domain B」：一個 domain 目錄可有多份 SPEC（`ui` 下 4 份）；沒有 SPEC 目錄的 domain（schema、diagnostics、layout、history、ticketdetail）沒有出邊；值是字串，與 DomainBundle `id`（`DOMAIN-MAP-*`）無法 join，大小寫權威亦未定（§9）。舊版多檔專案的做法僅引用票面 why：以 schema 外的自由文件承接，不進圖譜。

## Solution
### 分析結論

跨 domain 內容佔本專案 domain-map 的多數（27 單位中 19 跨、6 單一、2 混合），拆檔後的主體需要一個系統層載體；上游目前沒有。domain → domain 依賴在 schema 不存在：`depends_on_domains` 是 SPEC → 名稱字串。下表候選交用戶裁決，本票不選定。

### 候選載體方案比較

共通前提：任何改 `tracking_schema.py` 並重新產生 JSON 的方案，都會使 `schema_generated_at_framework_version` 升至產生當下的框架版本（現 JSON 與本 App 內建皆 `2.60.13`，框架 `2.76.0`）。依「App 已知範圍」判準，以內建版本為閘門的 consumer 在更新內建副本前，會把新 JSON 判為超出已知範圍。只改模板與方法論不需重新產生 JSON。

| 候選 | 內容 | schema 相容代價（含升版對既有 consumer） | 本專案拆檔工作量 | 主要風險 |
|------|------|----------------------------------------|----------------|---------|
| A 新增系統層模板，不改 schema | doc skill 新增 `system-map-template.md`（domain 間分層、依賴表、通道、邊界決策、容錯、待決），路徑避開根層 `docs/domain-map.md`（例 `docs/architecture/system-map.md`）；系統層文件不是圖節點；方法論補一條「domain 間依賴以系統層表格為權威」 | 零：不動型別表、不重新產生 JSON、不升版 | 新建 5 個 domain 目錄 + 8 份 per-domain map + 1 份系統層；更新 78 個引用檔中帶節號者；`traceability.yaml` domain_bundle_tests 改指各 domain map | 依賴方向仍是散文表格，不可機器消費——矩陣「間接依賴」判定式（§9）無資料來源；系統層與各 domain map 的依賴陳述可能漂移，無 validator |
| B DomainBundle 新增出邊欄位 + 系統層模板 | 各 per-domain map frontmatter 加 `depends_on_bundles: [DOMAIN-MAP-x]`，新增邊型（DomainBundle → DomainBundle，`ordering`，手動，初為 `proposed`）；系統層模板只承載理由、通道與跨 domain 決策 | 中：型別表加一條邊型與一個選填欄位；JSON 重新產生、版本升；舊 consumer 不讀新邊時行為不變（加法），但版本閘門 consumer 需更新內建副本；新邊依型別分層判準須兩個獨立 consumer 實例才能升 established | A 的全部 + 8 份 frontmatter 填出邊（7 條，來自現 §2）+ App 內建型別表副本與 K4 契約測試同步 | 與既有 `depends_on_domains`（SPEC 層、字串）並存兩套依賴表達，需裁決是否淘汰或重定義後者；`proposed` 期間形狀可能變動 |
| C 只改方法論與模板：根層 domain-map 在多 domain 專案改作系統層 | 方法論規定：多 domain 專案的 `docs/domain-map.md` 承載系統層內容，frontmatter 以標記（例 `scope: system`）區分；模板加系統層變體 | 零 schema 代價、不升版；但根層檔仍命中 DomainBundle carrier 與 id_pattern，被判為一個 DomainBundle 節點 | 本專案根層檔可原地瘦身保留（引用路徑不變，只有搬出段落的節號錨點失效），新建 8 份 per-domain map | 同一型別承載「一個 domain」與「整個系統」兩種語意；以 DomainBundle 為矩陣列的消費端必須額外過濾，否則多出一列 |
| D 不拆檔：8 個維持為單 domain `docs-graph` 的 bundle | 依現行 frontmatter（`domain: "docs-graph"`）原樣保留；矩陣列改取 bundle，需 schema 讓 bundle 可被消費（DomainBundle 加結構化 `bundles` 清單欄位，或新增 Bundle 節點型別） | 中至高：加欄位升版；新增節點型別另需 id_pattern 與既有七型兩兩互斥 | 最低：不拆檔，只補 frontmatter 結構化清單 | 與 2026-10-06 用戶裁決前提（8 個為 domain、須拆檔）衝突，列出僅供對照；框架 domain／bundle 兩層的分級在本專案被壓成一層 |
| E 新增系統層節點型別 + domain → domain 邊型 | `SystemMap` 節點（carrier 例 `docs/architecture/system-map.md`），新增邊型 DomainBundle → DomainBundle，系統層節點以 containment 邊列出所屬 DomainBundle | 最高：新節點型別與新邊型；id_pattern 須與七型互斥、carrier 具體度須避免平手、需 conformance 測試；JSON 升版；新型別依分層判準起始為 `proposed` | A 的全部 + 系統層 frontmatter + 內建型別表副本與 Schema domain 判型邏輯更新（`lib/schema/`、`lib/corpus/node_typer.dart`） | 改動面最大；型別升 established 需兩個獨立 consumer 語料，期間消費端只能把它當 proposed |

### 框架問題兩條 AND 判準（逐條套用）

| 判準 | 套用 | 結論 |
|------|------|------|
| 抽象可攜性 | 敘述去掉專案名與路徑後為「多 domain 專案依框架一 domain 一份 domain-map 拆檔時，跨 domain 內容（分層、依賴方向、通道、邊界決策）無模板載體，schema 無 domain → domain 邊，`depends_on_domains` 實為 SPEC → 名稱字串」，對任何多 domain consumer 皆成立 | 成立 |
