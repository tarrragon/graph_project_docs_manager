### 資料來源與格式提案（2026-10-31，L39；動手前回報主控核可）

**兩種來源**，都從票面讀出，不經 LLM 生成：

| 來源 | 讀什麼 | 寫入方 | 解除 |
|------|--------|--------|------|
| U1 主控待辦行 | 協調票 `## Solution` 段，行首為 `**用戶待辦**：<事項>` 或 `**用戶待辦**（<鍵>）：<事項>` 的行 | 主控 | 同一個鍵的 `**用戶待辦完成**（<鍵>）：<結果>`；沒寫鍵的行以事項全文當鍵，完成行須逐字相同 |
| U2 各線等用戶 | 沿用 580 的 S1／S2／S3（`line_status` 的「等用戶」段同一份判定） | 各線、Claude Code、主控 | 依 580 的解除規則 |

**格式細節**：
- 鍵可省略，相容主控現行的 6 行暫定寫法（57851b056）。建議有對應票號時以票號當鍵，例如 `**用戶待辦**（560）：裁定 SPEC 內文的出處型票號標注`；完成時寫 `**用戶待辦完成**（560）：<結果>`。這樣改寫事項文字也不會配對失敗
- 同一個鍵以最後一行為準：完成後再寫一次待辦行，就重新列出
- 「用戶要做的動作」不另設欄位，事項以動詞開頭（開、裁定、授權、核可、實測）。待開 session 的指令直接寫在事項裡，例如 `開 L44 session（claude -n 派發格式檢查）`，不另立來源
- 只讀行首（不容前導空白）、略過 fenced code block，與 580 的 S1 同一套規則，避免說明段裡的格式範例被列出

**顯示**：
- Pane 最上方新增可收合群組「用戶待辦（N）」，預設展開，位置在各線群組之上。沒有待辦時顯示「用戶待辦：無」
- 每項一行：
  - U1：`<事項>｜<鍵或「主控」>`
  - U2：`<事項>｜L<n> <票號>（S1／S2／S3）`
- U1 在前、U2 在後；U2 中 S2（session 等待中，用戶要到該 session 處理）上洋紅色，沿用「要人處理」的配色

**實作要點**：
- `continuity.ts` 匯出各線等用戶的判定，供看板呼叫，`line_status` 與看板共用同一份實作
- 待辦行的解析放在 `lanes.ts` 旁的純函式
- 看板不讀 SessionStart 來源紀錄，U2 只需要協調票、session 檔、佇列票，看板既有的讀取已涵蓋

**不採用**：
- 從主控回覆或訊息擷取：不是票面，session 結束後讀不到，也違反「不經 LLM 生成」
- `line_status` 輸出也加 U1：主控自己寫的待辦主控本來就知道。若要加，另開票

**E2**：
- 正向對照：有鍵、無鍵的待辦行必列；S1、S2、S3 各一，經看板列出
- 負向對照（不得列出）：
  - 同鍵已有完成行
  - 無鍵待辦配上逐字相同的完成行
  - 縮排行、fence 內的範例
  - Solution 段以外的待辦行
