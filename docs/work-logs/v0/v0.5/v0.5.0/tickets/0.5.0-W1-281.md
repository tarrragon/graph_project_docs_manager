## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

PostToolUse 只在工具成功時觸發（官方文件與 17:35／17:38 兩組實測一致）。本專案未註冊 PostToolUseFailure，所以以 PostToolUse 觀察失敗的 hook 只收得到被遮蔽（`| tail`、`; echo $?`、`> log`）而整體回 0 的失敗。今日 post-test-hook 能報 TEST FAILURE，完全依賴呼叫端遮蔽結束碼的習慣；直接失敗的測試它看不到。

### 候選比較

| 候選 | 做法 | 優點 | 缺點 |
|------|------|------|------|
| A 同一 hook 加註 PostToolUseFailure | 分派器新增 PostToolUseFailure:Bash 群組，失敗類 hook 同時掛兩個事件，內部依 hook_event_name 分流解析（成功讀 tool_response，失敗讀 error） | 一支 hook 一套邏輯，失敗與遮蔽失敗都看得到 | hook 內需處理兩種 payload 形狀 |
| B 拆出失敗專用 hook | 每支失敗類 hook 拆一支只掛 PostToolUseFailure | 單一事件、單一形狀 | 支數倍增，成功與失敗判讀邏輯分散兩處，易漂移 |
| C 維持現狀並文件化 | docstring 註明只見遮蔽失敗，要求呼叫端遮蔽 | 零改動 | 把正確性押在呼叫端習慣上；直接失敗的測試與 CLI 錯誤永遠沒有回饋 |

### 選定

失敗類 hook 採 A（post-test-hook、cli-error-feedback）；cli-failure-help-reminder 先釐清與 cli-error-feedback 的重複再定；parallel-claim-audit 採 C（claim 失敗呼叫端已可見，docstring 註明）；wrap-decision-tripwire 先實測 Agent 失敗事件再定。註冊與分派器支援交 E 線（settings.json 與 hook-dispatcher 屬 E 線，bb 2026-10-14 分派）。
