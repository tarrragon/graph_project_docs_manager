### 派發背景（PM，2026-10-30，主控核准條件已併入）

- 現行做法：`node_detail_screen.dart` 的 `_refresh` 只呼叫 `File(lastKnownPath).existsSync()`，檔案存在就直接設成 `NodeDetailReady`。
- 解析入口：改用既有的 `classifyFrontmatter(Uint8List bytes)`（`lib/corpus/frontmatter_classifier.dart`）。它回傳 sealed `ParseOutcome`（`lib/corpus/parse_outcome.dart`）：
  - `Available`：解析完整，轉成 `NodeDetailReady`。
  - `NoFrontmatter`、`Unclosed`、`EmptyOrNotMap`、`YamlSyntaxError`、`Unreadable`：都屬於「存在但解析失敗」。狀態維持 missing，並以 SnackBar 顯示 `sourceFileUnparsableMessage`。
  - screens 已經在其他地方 import `lib/corpus/`（例如 `node_detail_state.dart`），這次不算新增分層方向。
- 預期文字的來源（TEST-GPD-1006）：
  - zh 文案取自 SPEC-003 §3.6〈重新整理的三分支〉：「檔案存在但無法解析，詳見破洞報告」。
  - SnackBar 形態取自 §2.13 第 19 列與 §2.14 第 19 列：`AppSnackBar.plain`，可棄，`userInitiated`。
  - en 文案沿用 `sourceFileStillMissingMessage` 的語氣自行翻譯，並在 Solution 註明。
- 測試：三種輸入（檔案不存在、frontmatter 完整、frontmatter 未閉合）各寫一個行為層紅燈，以 E1 對照，斷言三者產物互不相同：

  - 完整：轉成 normal。
  - 解析失敗：missing，SnackBar 顯示 unparsable 文案，而且沒有 stillMissing 文案。
- l10n：新增 `sourceFileUnparsableMessage`，刪除 `fieldCorruptedMessage`。只用 `fvm flutter gen-l10n` 產生，不用全域版，因為全域版會少一個空行。

- 可觀測性（規則 5）：`_refresh` 觸發處用 `developer.log` 記錄入口與結果分支。
## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
