### 四支辨識者盤點

| hook | 辨識對象 | lib 函式 | 事件 | 型別 | 判決條件 | 失效方向 |
|---|---|---|---|---|---|---|
| global-pkill-guard | 命令位置的 pkill、killall；orphan-test-procs.py --kill 搭配 --root | parse_command_statements、skip_prefix_wrapper_count（預設非 extended） | PreToolUse | 阻擋，無條件 DENY | 辨識即擋，沒有狀態條件可緩衝 | 漏判=放行全機終止；誤判=無條件擋下正當命令 |
| acceptance-gate | ticket track complete、finish、batch-complete | 同上，另有自寫的 _statement_complete_verb；has_force_flag_on_complete 已是視窗掃描 | PreToolUse | 阻擋，狀態條件 | 辨識為完成命令後，ticket 實有未達成 acceptance 或 children 才擋 | 漏判=不經 hook 檢查；但 ticket CLI 的 complete 自身亦驗 acceptance（lifecycle.py validate_acceptance_criteria），hook 為第二道 |
| phase4-decision-enforcement | ticket track phase <id> phase4（main_gate，PostToolUse）與完成類（residual_gate，PreToolUse） | 同上，另用 lib/ticket_command_parse.complete_statement_args | 兩者 | residual 阻擋，main 為事後回饋 | ticket md 實含 MUST-block 用語才擋 | 漏判=少一次用語掃描；誤判=須命令含字面 ticket ID 且該票含違規用語才有效果 |
| needs-context-listener | ticket track append-log <id> --section NeedsContext | parse_command_statements 加自寫視窗比對 | PostToolUse | 提示 | 成功回音含已追加日誌到 才提醒 | 漏判=少一則提醒；誤判=多一則提醒 |

### 結構性觀察

1. needs-context-listener 的實作已是任意位置視窗掃描，沒有前綴白名單；檔頭卻稱「比對命令位置」，說明與實作不符（建 DOC 子票）。它事實上已是掃描模型，本票只需判斷是否維持。
2. acceptance-gate 內部不一致：is_complete_command 用命令位置加前綴白名單，同檔 has_force_flag_on_complete 用視窗掃描。同一支 hook 對「這是不是 complete」有兩種答案。
3. phase4 與 acceptance-gate 對完成類動詞各自實作比對（phase4 用 lib 的 complete_statement_args，acceptance-gate 用自寫 _statement_complete_verb），是重複實作。
4. pkill 與 git 阻擋型守衛的關鍵差異：git 守衛的並行期以外多為狀態條件或僅 WARN，誤判有緩衝；pkill 守衛辨識即 DENY，誤判無緩衝，120.7.9 的「誤判有上限」論證不能直接搬過來。
5. 兩種白名單方向相反：前綴包裝白名單（現行）漏收一項=放行；非執行者例外清單（grep、rg、man 等）漏收一項=多擋。前者開放集合的失效方向是放行，後者是擋下，對阻擋型是安全側。
