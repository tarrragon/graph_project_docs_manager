## Problem Analysis
### 問題根因

`dispatch_skeleton.py` 的 `WORKTREE_HEREDOC_LINE`（355.1 加入）要求 worktree 代理人「多行內容以 heredoc 傳給 append-log」。這個寫法撞上已知的拒收條件：PC-GPD-003 記載，worktree 隔離守衛以「參數含字面換行，過於複雜無法驗證」拒收 Bash 呼叫。heredoc 展開後，換行仍在命令列參數裡，所以骨架指定的寫法正好落在拒收條件內。

`tool-selection-details.md` 的 too complex 例外只教「拆成單一命令」。直傳 heredoc 的 append-log 本身已是單一命令，拆不下去，依該例外步驟 4 應停手。例外的邊界表允許「前一條以可見寫入把中間結果放到 scratchpad 檔，下一條以單一命令讀取」，355.2 的 `--content-file` 正是這個形狀，但骨架與例外都沒有把兩者連起來。337.11 的代理人只好自行摸索。

### 影響範圍

- 範圍：所有 `isolation=worktree` 派發（每條線共用此骨架）。
- 已驗證：骨架最長組合（hook_scope、worktree、測試入口、紅燈句、commit policy agent）為 22 行，等於 `SKELETON_MAX_LINES`（30 − 8）。新增任何一行都會使 `test_every_skeleton_variant_leaves_room_for_pm` 紅燈，修法只能原行改寫。
- 已驗證：`_resolve_content_file` 以 `newline=""` 逐字讀入，多行與 `###` 行首保留；位置參數與 `--content-file` 二擇一。
- 已驗證：PC-GPD-003 處置表與 `agent-dispatch-closeout.md`〈append-log 收尾持久化驗證〉給的替代是「分次單行 append」，兩者都寫於 355.2 之前，沒有提到 `--content-file`。
- 未驗證：平台拒收 heredoc 的確切條件。337.8 直傳 heredoc 通過、337.11 直傳 heredoc 被拒，同形狀在兩次派發結果不同。結論不依賴這個條件：`--content-file` 的命令列不含換行，兩種情況都不會撞上。

## 重現實驗結果
### 實驗方法

1. 窮舉 `build_skeleton` 全部 normal 組合（hook_scope × isolation × 測試入口 0/1/2 × 紅燈句 × commit policy），以 hook 同款算法 `len(s.strip().splitlines())` 量行數，判斷還剩多少行可用。
2. 讀 `_resolve_content_file` 原始碼，確認多行內容的讀入方式。
3. 主線程（非 worktree）以 heredoc 直傳多行內容執行 `append-log --replace`，取一個非 worktree 環境的對照點。
4. 對照 PC-GPD-003 與 `agent-dispatch-closeout.md` 的既有替代路徑。

代理人端（worktree）的拒收不重現：拒收屬平台判定，本 session 不在 worktree 隔離下，重現不了；且結論不依賴拒收條件（見實驗發現）。

### 實驗執行

- 行數：最長兩組（hook_scope=True、worktree、測試入口 1 或 2、紅燈句=True、agent）為 22 行；次長 21 行。上限 `SKELETON_MAX_LINES` = 30 − 8 = 22。
- `_resolve_content_file`：`open(content_file, encoding="utf-8", newline="")` 讀入後寫回 `args.content`，之後與位置參數同一路徑。
- 主線程 heredoc 直傳：本票 Problem Analysis 以 `--replace "$(cat <<'EOF' ... EOF)"` 寫入，rc=0，`[verify] ticket md: 195 lines after write`。

### 實驗發現

- 已驗證：骨架已達行數上限，修法只能原行改寫 `WORKTREE_HEREDOC_LINE`。
- 已驗證：`--content-file` 保留換行與 `###` 行首，命令列本身不含換行。
- 已驗證：主線程直傳 heredoc 可行。拒收只出現在 worktree 代理人端，與 PC-GPD-003 記載的守衛判準一致。
- 未驗證：worktree 守衛對 heredoc 的確切判準（337.8 通過、337.11 被拒）。改用 `--content-file` 後命令列不含換行，結論不受這個判準影響。

## Solution
### 結論

骨架要補替代路徑，而且應把 `--content-file` 改為 worktree 多行內容的**首選**，不只是被拒時的退路。理由：

1. heredoc 的換行仍在命令列參數裡，撞上 worktree 守衛的拒收判準（PC-GPD-003）。現有 4 個觀測點中 3 次被拒（PC-GPD-003 原案、337.8 的 `out=$(...)`、337.11 直傳），只有 337.8 直傳 1 次通過，代理人無法事先判斷這次會不會過。
2. 先試 heredoc 再退，每次被拒都要多一輪呼叫；而且依 too complex 例外步驟 4，單一命令被拒應停手，代理人照例外會停下來，而不是改走 `--content-file`。
3. `--content-file` 的命令列不含換行，與拒收判準無關；`newline=""` 逐字讀入，`###` 行首保留，PC-GPD-003 的壓平失效也一併消除。
4. 這個形狀已在 too complex 例外的邊界表內（可見寫入 scratchpad 檔，下一條單一命令讀取），不新增例外，只是把例外接到骨架上。

### 與 Edit/Write 範圍約束的關係

- 骨架既有的 `WORKTREE_CLI_REJECT_LINE` 禁的是「以 Edit／Write 改 worktree 內**票檔**」。scratchpad 內容檔只放暫存的票面文字，不是票檔，也不會被提交，兩句不衝突。新句要明寫「（非票檔）」，讓代理人不必自己推論。
- 337.11 衝突的是 PM 在 prompt 補述的「Edit/Write 只用於產品檔與測試檔」。骨架句落地後，同一份 prompt 裡兩句互相矛盾，代理人依骨架「prompt 與正本衝突停手」會停下來。PM 補述這類範圍約束時，要寫成「Edit/Write 只用於產品檔、測試檔與 scratchpad 內容檔」。這句寫法交主控（-d7）轉知各線，不改框架文件，因為補述是 PM 每次派發自寫的文字，沒有框架正本。
- PC-087（禁止 PM 以 /tmp 中介檔繞路）射程是主線程：主線程能直傳 heredoc，多走一步沒有理由。worktree 代理人的命令列不能帶換行，前提不同，不適用。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 原行改寫：多行內容一律 Write 到 scratchpad 內容檔，再以 `--content-file` 傳入 | 單一路徑、命令列無換行，不受守衛判準影響；行數不變 | 每次多一個 Write；需同步三份文件中「分次 append」的替代寫法 |
| B | heredoc 維持首選，被拒時改 `--content-file` | 與 bash 規則五（長文字用 heredoc）字面一致 | 被拒一次就浪費一輪；與 too complex 例外步驟 4 的「停手」衝突，句子要多交代一層；句長逼近一行的容量 |
| C | 被拒時分次單行 append（PC-GPD-003 現行處置） | 不新增寫入路徑 | 呼叫次數隨段落數成長，壓平風險仍在；355.2 已提供更好的工具 |

骨架最長組合已達 `SKELETON_MAX_LINES`（22），三案都只能原行改寫。

放寬型：骨架新增一條允許的寫入路徑（Write 到 scratchpad 內容檔）。依主控規定，412.1 進合併閘門前回報主控（-d7）。
