## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 預估方法

- 記錄：排隊檔與 holder 檔新增 estimate（秒）；holder 另記 started_epoch。acquire_slot 新增 estimate_seconds 參數，未傳用 default_estimate_seconds(command)。舊格式檔案（無欄位）同樣以命令預設值計。
- 預估等待 = 持有者剩餘 + 前方各存活排隊者 estimate。持有者剩餘 = max(holder.estimate - (now - started_epoch), 0)；持有者 pid 已不存在或 holder 檔不可讀計 0。holder 逾預估仍在跑時剩餘計 0（不外推，避免無依據的猜測；等待上限逾時仍保護）。
- 進入排隊（建立排隊檔後）計算一次：預估 > 等待上限（CLAUDE_SLOT_WAIT_LIMIT，預設 3600）即 exit 125 立即結束，訊息含順位、前方筆數、預估秒數，並移除自己的排隊檔。未超過照常排隊，每次等待提示附預估剩餘秒數。
- 合併閘門：MergeGate.hold 以 merge-base..branch 的改動路徑跑 select_suites，各套件取 worktree-merge.log 尾段（256KB）最近 5 筆綠燈耗時的中位數加總，傳給 acquire_slot。紅燈、逾時、中斷不計入樣本。
- 預設值（無歷史）：flutter 600、hooks 230、scripts 60、skill:ticket 580、其他 skill 120；slot_gate 命令預設：merge-gate 900、含 flutter 600、含 pytest 300、其他 600。依據父票實測（hooks 160-230、ticket 520-580、動到 lib 的合併約 915 秒），保守取偏高值。
- 已知限制：預估是估算不是保證。同進程多執行緒共用 os.environ 時，持有期間被降為 30 秒的子程序上限會被同進程排隊者讀到（僅測試場景，真實排隊者為獨立進程），測試已以 monkeypatch 隔離。
