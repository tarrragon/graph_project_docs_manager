## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 結論

兩題皆可落地，但都不能沿用 SPEC-007 的泛用「frontmatter 欄位值＝節點 ID」管線原樣啟用：FlowStep 缺 `next` 邊型且載體不在 frontmatter；`depends_on_domains` 的值是名稱，需一層名稱→DomainBundle 解析。以下列候選，不選定（用戶裁決）。

### 1. FlowStep 節點化與分支邊

共同前提：`next` 無邊型，任一候選都要先決定 `next` 的來源——(a) 上游 tracking_schema 新增 FlowStep 的 sequence 邊型（框架 issue，跨專案）；(b) Graph 以本地常數建邊（新增 D6 鍵名例外）。branching／returning 為 proposed，啟用亦需「使用中邊型」改為 established ＋ 指定 proposed（再一個例外）或上游升級 layer。

| 項目 | A：FlowStep 作為合成 RawNode（裸 id） | B：合成 RawNode（UC 限定 id） | C：FlowStep 子圖掛在 UC，不進主圖 |
|------|------|------|------|
| Corpus 解析範圍 | 讀 UC 本文的 `flow:` yaml 區塊，每步產一個 RawNode（typeName=FlowStep，path=UC 路徑，frontmatter=步驟 map ＋ 所屬 UC） | 同 A；id 改寫為 `<UC id>/<step id>`，並把 next／branch_from／return_to 值改寫為同 UC 限定形 | 讀同一區塊，掛到 UC RawNode 新欄位（如 `flowSteps`），不另產節點 |
| Graph 節點 | +40（本專案）／+9（flutter_balance） | 同 A | 主圖不變；Graph 公開面另提供 `flowOf(ucId)` 子圖 |
| Graph 邊 | branching 17、returning 9、next 20（依共同前提選 a/b），經泛用分類管線 | 同 A，邊端點為限定 id | 子圖內 17／9／20，不進 `GraphBuiltEvent.edges` |
| FlowStep id 規則 | 沿用 schema kebab，**要求跨 UC 全域唯一**（現況 0 重複）；重複時依 D3 兩節點皆不建 | 圖上 id＝`UC-xx/<kebab>`，與 schema id_pattern 不符，需上游放寬或 Graph 繞過 pattern 檢查；跨 UC 同名安全 | 只需 UC 內唯一；不受 D3 影響 |
| 對凍結值 | IT 不變（manifest 無 flow）；S6-2／IT-3 若改使用中邊型集合需改寫 | 同 A | IT 不變；S6／IT-3 不受影響（若 `next` 不進邊型表） |
| G9 | 不變；且新邊走 `_lookupId`，正比性質自然涵蓋 | 同 A | 不變；子圖解析不經 `_lookupId`，正比性質不涵蓋 flow，需另加案例 |
| 優點 | 與 schema 的 GRAPH_NODE_TYPES 一致；未來 emits／consumes 直接沿用 | 對跨 UC 同名有韌性 | 改動最小、凍結面零變動；泳道只需單 UC 子圖 |
| 缺點 | 依賴「資料剛好全域唯一」；破洞面多出 FlowStep 類斷邊／重複 | 與上游 id_pattern 衝突，屬 schema 層變更 | FlowStep 非一級節點，鄰接查詢、Diagnostics 破洞、emits／consumes 之後須重做 |

### 2. domain_dependency 與 bundle_dependency

| | domain_dependency | bundle_dependency |
|---|---|---|
| 欄位／載體 | `depends_on_domains`，現只在 SPEC frontmatter | `depends_on_bundles`，在 DomainBundle frontmatter |
| 起點→終點 | SPEC（任何帶欄位的節點）→ domain（以名稱指涉） | DomainBundle → DomainBundle（以節點 ID） |
| 語意 | 「這份規格依賴哪些 domain 的公開面」，規格對 domain 的覆蓋／依賴 | bundle 之間的架構依賴 DAG（間接依賴的來源） |
| layer | established | proposed |
| 值形 | 名稱（`corpus`） | ID（`DOMAIN-MAP-corpus`） |

兩者起點型別不同、語意不同，不可合併（與背景更新一致）。

**前者能否落地：能**，21 個值全數可解析。候選：

| | D1：Graph 以 `domain` 欄解析名稱 | D2：資料改寫為 DomainBundle ID | D3：維持排除 |
|---|---|---|---|
| 作法 | LightNode（或 Graph 內索引）帶 DomainBundle 的 `domain`；`depends_on_domains` 值先查名稱索引再建邊，未命中歸新的斷邊子類 | SPEC frontmatter 改寫為 `DOMAIN-MAP-*`，泛用管線原樣處理 | 不建邊，矩陣只用 bundle_dependency ＋ traverses |
| Graph 邊 | +21 條 SPEC→DomainBundle | +21 | 0 |
| 程式例外 | 移除 D6 排除鍵；新增「名稱型邊」處理（需型別表表達或另一鍵名例外） | 移除 D6 排除鍵即可 | 不變 |
| 凍結值 | IT 不變；S6-2、S6 降級案例、IT-3 `_activeEdgeFieldNames` 改寫 | 同 D1；另需上游 schema 文件與 doc CLI 驗證同步改寫，跨 consumer 影響 | 無 |
| 附帶 | 同一名稱解析器可供 `traverses`（FlowStep→DomainBundle，矩陣格）共用 | `traverses` 仍是名稱，問題沒解掉 | 矩陣格仍需另外處理 traverses |

注意：`DOMAIN-MAP-<domain>` 對兩語料目前都成立，但這是命名慣例而非 schema 保證，D1 不應以字串拼接代替 `domain` 欄查詢。
