### 分析結果（incident-responder，2026-10-12）

#### 問題根因

該測試沒有注入任何時鐘。_fake_run_with_timing 的假 subprocess.run 只做兩件事：取一次真實 time.time() 當基準，把 configure／unconfigure／atexit 寫成「基準 + 固定偏移」；然後真實 time.sleep(0.05)。票面所稱「注入假計時」實際是「以真實牆鐘為錨的固定偏移」，五個時刻與 total 全部取自真實時鐘。

| 量 | 取樣位置 | 時鐘 | 是否受負載影響 |
|----|---------|------|---------------|
| spawn_wall | 產品碼 _run_pytest，subprocess.run 之前 | 真實牆鐘（_wall_clock = time.time） | 是 |
| started | 產品碼 _run_pytest，緊接 spawn_wall 之後 | 真實 time.monotonic | 是 |
| configure／unconfigure／atexit | 測試的假 run 內 | 真實 time.time() + 0.01／0.03／0.04 | 錨點是，間距否 |
| total | 產品碼 _run_pytest，subprocess.run 返回後 | 真實 time.monotonic 差 | 是 |
| return_wall | 產品碼 _run_pytest，緊接 total 之後 | 真實牆鐘 | 是 |

四段由 _compute_segments 對 [spawn_wall, configure, unconfigure, atexit, return_wall] 取相鄰差：

| 段 | 算式 | 性質 |
|----|------|------|
| spawn_to_configure | (now+0.01) - spawn_wall | 0.01 + 真實耗時（spawn_wall 到假 run 取 now） |
| configure_to_summary | 0.03 - 0.01 | 常數 0.02 |
| summary_to_pyexit | 0.04 - 0.03 | 常數 0.01 |
| pyexit_to_uvexit | return_wall - (now+0.04) | 真實耗時（假 run 取 now 到 return_wall）- 0.04 |

第四段取得真實耗時的原因：它的右端點 return_wall 是產品碼在真實牆鐘上的讀值，左端點是假 run 進入時的真實牆鐘加 0.04。兩者之間的真實耗時包含寫計時檔、time.sleep(0.05) 的實際睡眠（高負載下超睡）、subprocess.run 返回後到 return_wall 取樣的排程等待。紅燈那次第四段 0.14 = 名目 0.01 + 額外 0.13。

紅燈成因：sum(parts) 恆等於 return_wall - spawn_wall（牆鐘窗），total 是 monotonic 窗。牆鐘窗的兩個端點都在 monotonic 窗之外（spawn_wall 先於 started、return_wall 後於 total），因此

    sum(parts) - total = 空隙1（spawn_wall 到 started）+ 空隙2（total 到 return_wall）+ 兩時鐘源漂移 + 格式化四捨五入

兩個空隙各是相鄰兩行 Python 之間的排程等待，是機器負載的函數，無上界。紅燈那次：第四段的額外 0.13 中，0.08 落在 monotonic 窗內（total 由名目 0.05 變 0.13），剩 0.05 落在窗外；第一段為 0.01 未膨脹，故空隙在 total 與 return_wall 之間。0.05000000000000002 是 0.18 - 0.13 的浮點表示，斷言比較的是日誌中兩位小數的值，差值只會是 0.01 的整數倍，門檻 < 0.05 等同「至多 0.04」；五個值各自四捨五入最多再貢獻約 0.025，真實空隙約 25 至 75 毫秒即可觸發。

#### 判定：測試設計問題，非產品碼缺陷

依據：
1. 產品碼的 sum_residual 欄位設計目的即為揭露這個差值，它是純觀測日誌（_log_segment_timing_safely 註明不影響判定）。兩個時鐘的讀值無法原子取樣，調換取樣順序只會移動空隙位置，不會消除。計時邏輯無誤。
2. 測試對一個「機器負載的函數」設固定上界，屬 test-assertion-design 規則 D1（主套件絕對計時門檻）與不可靠斷言判準的「機器負載」列。同檔已有先例把同性質測試移出主套件（wallclock 標記，理由原文為逾時上界是機器負載的函數）。
3. 同一測試內另一條斷言（sum_residual 絕對值 < 0.05）是同一個量的另一個讀法，同樣不可靠；注入實驗中兩者同時越界。

附帶發現（產品碼文件，非邏輯缺陷）：_compute_segments 的 docstring 稱 sum_residual「來自兩個時鐘源的差異，正常 <10ms」。實際主要來源是取樣點非原子的排程空隙，且高負載下不成立。讀日誌的人會把大的 sum_residual 誤讀為校時事件。已併入子票 0.5.0-W1-155.1 的驗收條件。

## Solution
### 分析結論

事件類型：測試失敗，分類為「測試本身問題」（斷言設計），非產品碼缺陷。

test_segments_logged_sum_equals_total 未注入時鐘，斷言比較真實牆鐘窗與真實 monotonic 窗的長度差並設固定上界 0.05 秒。該差值等於兩個取樣空隙的排程等待，是機器負載的函數。完整推導與時鐘來源表見 Problem Analysis，注入實驗見重現實驗結果。

### 欄位格式追蹤

| 欄位 | 生產者函式 | 完整格式 | 範例值 |
|------|-----------|---------|-------|
| 四段（spawn_to_configure 等，名稱清單為 _SEGMENT_FIELDS） | _compute_segments 計算，_segment_detail 經 _fmt_seconds 格式化 | 名稱=兩位小數加 s；任一端點缺漏時為 n/a；值可為負 | pyexit_to_uvexit=0.14s |
| total | _run_pytest 以 time.monotonic 差計算，_log_segment_timing 格式化 | total=兩位小數加 s | total=0.13s |
| segment_sum | _segment_detail | 兩位小數加 s；任一段缺漏時與 sum_residual 合併輸出為 segment_sum=n/a sum_residual=n/a | segment_sum=0.18s |
| sum_residual | _segment_detail，算式為 total - segment_sum（未四捨五入的原值相減） | 三位小數加 s，可為負 | sum_residual=-0.067s |
| 計時檔 configure／unconfigure／atexit | 正式環境由 conftest 計時外掛寫入；本測試由假 subprocess.run 寫入 | JSON 浮點，epoch 秒（牆鐘） | 假 run 取 time.time() 加 0.01 |
| 計時檔 load1_start／load1_end | 同上 | JSON 浮點，load average，非時刻 | 1.5 |

修法須注意：測試的正則以「名稱=可選負號、數字、小數點、數字、s」擷取，n/a 不匹配；四段與 total 為兩位小數、sum_residual 為三位小數，以確定值斷言時容許值須依各欄位的格式化位數設定。

### 候選方案

| 案 | 做法 | 利 | 弊 | 結論 |
|----|------|----|----|------|
| A 全注入時鐘 | 測試以共用假時鐘同時替換 _wall_clock 與 hook 模組的 monotonic，假 run 以推進假時鐘取代 time.sleep；斷言改確定值 | 斷言結果只由程式決定；留在主套件；可加一個對照測試證明 sum_residual 對取樣空隙有鑑別力（E 系列）；測試不再睡眠 | 需改寫 _fake_run_with_timing 與斷言；同檔已有替換 monotonic 的先例，替換面小 | 採用 |
| B 移入 wallclock 標記 | 測試原樣加標記，由 pyproject 的 addopts 排出主套件 | 改動一行 | 斷言仍不可靠，只是換地方紅：wallclock 套件的固定執行點是 commit 觸及 gate 本體時由 gate 加跑，偶發紅燈會擋下無關的 commit；四段算術本可確定性驗證，移出後主套件失去這段覆蓋 | 不採 |
