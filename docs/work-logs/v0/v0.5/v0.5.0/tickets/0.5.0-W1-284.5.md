## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
改寫 boundary-guard 命令解析為單趟字元走訪（O(n)），移除所有以正則抽取 sed／cp／mv／tee／重導向路徑的做法。

做法：_parse_statements 單趟切出陳述與 token（引號內文字併入單一 token，不再被當命令；heredoc 正文讀入陳述的 bodies，不進 token 走訪；以分號、管線、and、括號、換行切陳述；重導向目標與 fd 重導向在走訪時分流）。_scan_sed／_scan_cp_mv／_scan_tee 各對 token 走一次。python 陳述才對原文與 heredoc 正文掃 open()；sh／bash／zsh 的 heredoc 正文會被執行，遞迴解析（深度上限 2）。bash -c 字串內寫入維持不在範圍。

長度上限：不加。解析為線性，上限只增加誤擋面（大型 heredoc 正文合法存在，例如長 append-log），不增加防護。誤擋面為零。

失敗語意：hook 非 fail_closed。解析為純字串走訪，無外部呼叫、無回溯，不會逾時；200KB 級輸入耗時為毫秒到數十毫秒。未預期例外由 run_hook_safely 記錄並回傳非零（非阻擋碼），行為同修正前。無法辨識的語法一律放行（fail-open，既有保守白名單策略不變）。

產生路徑表：單一 sed 接長串選項、大量 sed 字樣墊長、heredoc 正文含寫入描述、引號內含寫入描述、真實 sed／cp／mv／tee／重導向寫入皆覆蓋（測試對應）；bash -c 字串內寫入未覆蓋（屬 284.1）。

### 自檢結果
- Phase 4 評估：重構需要：否；技術債務：無新增（舊的七個正則常數已移除，認知負擔由集中在一支走訪函式承擔）；程式碼品質：A；結論：無需重構。
- 已知行為差異：sed -i 現在收集所有位置檔案（原只取第一個）；cp／mv 取最後一個位置參數為目的地（原取第二個）；tee 收集全部位置參數；註解（井字號開頭 token）不再解析。皆朝更少漏放方向，或與 shell 語意一致。
- 修正前紅燈證據：舊實作跑新增的 n／4n 效能測試，單一 sed 接長串選項形態使測試在 300 秒逾時內未完成（平方級）。

追加修正：19 個 n／4n 比值測試加 wallclock 標記（主套件排除，手動 -m wallclock 執行）；主套件改留 4 個約 200KB 最壞形態的 5 秒粗門檻測試（線性實測約 0.05 秒，平方級需數十秒）。
恢復執行（計數斷言）：主套件不再有任何 time 斷言（time 僅存在於 wallclock 標記的測試與其量測輔助）。
計數方法：work = sys.setprofile 觀測到的函式呼叫事件（Python 與 C 的 call）+ 交給 _scan_sed 的 token 走訪數；對每個 _PERF_SHAPES 形態以 n=500 與 4n 量測，斷言 work(4n) <= 4 * work(n) + 100。確定性，不受負載影響。
正向對照：以 patch 把 _scan_sed 改為每次只前進一格（模擬每個 sed 重掃後段 token 的平方級回退），在 sed 字樣墊長兩形態上，同一個計數斷言必須翻紅。鑑別力來源：重掃使 token 走訪數與 sed 個數乘積成正比，4n 時趨近 16 倍而非 4 倍，遠超 4 倍加常數的門檻，且與機器負載無關。
計時測試（padded 3 筆、200KB 最壞 4 筆、n/4n 比值 19 筆）全數標 wallclock；另加不計時的正確性斷言留在主套件。
