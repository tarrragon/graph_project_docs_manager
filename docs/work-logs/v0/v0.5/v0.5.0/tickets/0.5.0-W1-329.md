## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因
狀態檔路徑來自 config.state_file（預設 .claude/hook-state/wrap-tripwire-state.json），main() 以 project_root 拼出單一路徑，load_state、apply_ticket_switch_reset、_process_signals、save_state_atomic 全程不帶任何 session 維度。state 內只有 current_ticket 與 signals 兩個頂層鍵，無分區。

### 寫入者與讀取時機（程式碼位置：wrap-decision-tripwire-hook.py）
- 註冊三處（settings.json）：PostToolUseFailure(Agent)、PostToolUse(無 matcher，含 Agent 與 Bash)、UserPromptSubmit。每個事件都是 load -> 改 -> save 的整檔讀改寫，save_state_atomic 用 tmp+os.replace，只保證檔案不破損，不防 lost update。
- apply_ticket_switch_reset：current_ticket 與 state 內值不同即 signals={}。derive_ticket 的票號來源只有 Agent 事件 prompt 首行、環境變數 TICKET_ID、git branch feat/*；UserPromptSubmit 與 Bash 事件在主 checkout 通常導不出票號（返回 None 時不重置）。故重置幾乎只由 Agent 事件觸發。
- is_manual_wrap_invocation 命中時 reset_all_signals，同樣清全部。

### 干擾情境盤點（S1~S4 x 共用狀態）
| 訊號 | 共用狀態下的干擾 | 嚴重度 | 依據 |
|------|----------------|--------|------|
| S1 consecutive_failures | (a) 他 session 的 Agent 換票 -> signals 清空 -> 本 session 累積中的連續失敗計數歸零，警告延後或永不觸發；(b) 他 session 任一成功的 Agent PostToolUse 走 reset=True，把 count 寫成 0，即使票號不變；(c) 兩 session 的失敗被加總，可能在本 session 只失敗一次時即達閾值 2 而誤報 | 中（S1 的語意是單一執行緒的連續性，共用即失去意義；但 advisory 非阻擋） | ConsecutiveFailuresStrategy.detect/apply 讀寫 state.signals；實測見下 |
| S2 restrictive_keywords | cooldown(last_warned_at) 全域共用：A 剛警告，B 300 秒內命中同訊號被壓制（漏報）；換票重置又清掉 cooldown（重複警告） | 低 | in_cooldown/mark_warned 以 signal_id 為鍵，無 session 維度 |
| S3 ana_claim | 同 S2 的 cooldown 共用；last_claimed_ticket 只寫不讀（不影響判斷）；判斷本身依 ticket 檔而非 state，故無誤判 | 低 | AnaClaimStrategy.apply 只寫 last_claimed_ticket |
| S4 reflection_depth_challenge | 同 S2，signal_id 獨立不跨訊號，但跨 session 共用 | 低 | SIGNAL_STRATEGIES 與 RestrictiveKeywordsStrategy 共用類別 |
| 全體 | 無鎖的 load-modify-write：兩 hook 行程並行時後寫者覆蓋先寫者（今日日誌同一秒內多次 state loaded/saved 交錯可見）；手動 /wrap-decision 清全部 session | 低~中 | main() 流程；wrap-decision-tripwire-20261015.log 同秒多筆 |

### 影響範圍
僅 advisory 提示的漏報、誤報與重複，不阻擋任何操作（exit 0）。已驗證：S1 跨 session 互相歸零（重播）。未驗證：lost update 的實際發生率（只有日誌交錯的間接證據）。
