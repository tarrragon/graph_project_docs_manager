### WRAP 評估（2026-10-08）

範圍：NeedsContext 3 的四項邊界（SPEC-006 FR-09 規則 3b）。程式識別名（NeedsContext 1、2）已由 PM 判定為實作細節，交 001.3／001.4。不選定方案。

**事證**
- 兩份語料 7 個 UC 各只有 1 個 fenced yaml 區塊，且都以 `flow:` 開頭；現況 0 筆解析失敗。
- 框架 `usecase-template.md` 有 2 個 yaml 區塊（骨架與範例），兩者皆以 `flow:` 開頭；照模板複製的 UC 會有兩個 flow 區塊，規則 1 取第一個合法者。
- 框架 `_extract_structured_flow_steps` 與上游 `doc validate`（`_find_flow_order_problems` 等三處）都以 `... or []` 吞掉解析失敗，上游同樣把「壞掉」當「沒有」。
- EVT-CORPUS-003 的「事實」段寫明「該文件未進入圖譜」；flow 壞掉的 UC 仍是節點，與此事實矛盾。
- FR-08「破洞數等於命中 carrier 數」是 IT-2 守恆式的一環；flow 失敗在兩語料 0 筆，IT-2 凍結值不受影響。

**A＋B（建議合併裁決）：壞區塊的判定與後方有合法區塊時**

| 候選 | 作法 | 代價 |
|---|---|---|
| AB1 | 判定：fenced yaml 區塊內有頂層 `flow:` 行（文字層判定，不需解析）。只要有任一此類區塊解析失敗就產生破洞；步驟仍取第一個合法區塊 | 文字判定可能被縮排錯誤騙過；模板骨架壞掉但範例合法時也會報（這正是要暴露的情形） |
| AB2 | 判定同 AB1；只在找不到任何合法區塊時才報 | 骨架壞、範例合法時靜默採用範例步驟 |
| AB3 | UC 本文任何 yaml 區塊解析失敗都算 | 若 UC 未來放入非 flow 的 yaml 範例，會誤報 |
| AB4 | 規格不定義 | 001.3 寫不出 E2 對照 |

**C＋D（建議合併裁決）：破洞由哪個事件承載、與 FR-08 守恆式**

| 候選 | 作法 | 代價 |
|---|---|---|
| CD1 | 新增事件 EVT-CORPUS-004（FlowBlockRejected，producers corpus、consumers diagnostics）；FR-08 改為「破洞數 = 命中 carrier 數 + flow 區塊失敗 UC 數」，FR-07 統計另立計數 | 多一份 EVT 文件與一條通道；003 的「未進入圖譜」維持成立 |
| CD2 | 擴充 EVT-CORPUS-003 加原因碼，改寫其事實段 | 一個事件承載「檔案被拒」與「檔案入圖但區塊壞」兩種事實，語意變寬 |
| CD3 | 不另發事件：rawNode 帶 flow 區塊狀態，經 EVT-CORPUS-001 交出，Diagnostics 由此推導 | 最省；但破洞來源從「錯誤事件」變為「掃描結果欄位」，與 FR-08 現行模型不同 |
| CD4 | 規格不定義 | 實作自行選通道 |

**傾向**：AB1＋CD1。理由是 3b 裁決的目的是讓壞掉的 flow 可見，AB2 在模板情境下仍會靜默；CD1 保住 EVT-CORPUS-003 的事實語意。
**盲點**：
- 沒有實測縮排錯誤的 YAML 是否仍保有頂層 `flow:` 行。
- CD1 新增 EVT 是否要走 `doc` 的 EVT 建立流程與 W1-091／W1-095 的 domain 值檢查，沒有查。

### 用戶裁決（第二輪，2026-10-08）

- AB1：區塊內有頂層 `flow:` 行即判為 flow 區塊；任一此類區塊解析失敗即報，步驟仍取第一個合法區塊。
- CD1：新增 EVT-CORPUS-004 承載 flow 解析失敗（UC 仍為節點）；破洞數公式改為「命中 carrier 數＋flow 失敗的 UC 數」。
