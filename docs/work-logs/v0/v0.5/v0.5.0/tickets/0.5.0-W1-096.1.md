### WRAP 評估（2026-10-07）

錨點：App 觀測的是其他專案，非 domain 清單必須能由被觀測專案（含單 domain、舊框架專案）自行宣告；評估單位是「宣告載體」，判定規則（字面前綴、最長前綴、W1-096.2 定義）各候選相同。

#### R：事證（2026-10-07 實測）

1. `system-layer-template.md` frontmatter 只有 `title`／`bundles`／`created`／`updated`；doc skill 程式碼對 system-layer frontmatter **零讀取點**（`bundles` 無消費端），tracking_schema 無 system-layer carrier；App 的 lib 只在註解提到 system-layer，Corpus 不讀它。→ 83 所說「不需新建 carrier」只在模板層成立，doc 與 App 兩端都要新增讀取路徑，與獨立檔同量。
2. 模板自己的分流判準：「移除其他 domain 後決策仍成立 → 寫在 domain-map；涉及兩個以上 domain → 本文件」。非 domain 路徑清單在只剩一個 domain 時仍成立，依此判準**不屬 system-layer**。
3. 模板與 SKILL 定義 system-layer 為多 domain 專案「整個專案一份」；單 domain 專案（退化 `docs/domain-map.md`）沒有系統層。flutter_balance：單一 `docs/domain-map.md`（DOMAIN-MAP-balance-sheet）、無 system-layer、lib 依層切 core/data/domain/presentation——它的非 domain 路徑（presentation/、core/）若走 S1，得為單 domain 專案新建一份跨 domain 文件。
4. 可定位率（本專案 263 張帶 lib 路徑票、554 筆引用；規則＝6 個 domain 目錄 ＋ 非 domain：screens/components/app/l10n/tokens/services/main.dart；裸目錄補尾斜線）：

| 宣告狀況 | 命中 domain | 非 domain | 無法定位 |
|---|---|---|---|
| 兩者皆有 | 票 78 | 票 182 | 票 3（1.1%；皆為裸 `lib/`） |
| 只有 path_patterns | 78 | 0 | 185（70.3%） |
| 只有非 domain 清單 | 0 | 199 | 64（24.3%） |

各載體候選表達同一份規則，宣告齊全時可定位率相同（1.1%）；差異只在「哪些專案寫得出這份宣告」與缺席語意。

#### 缺席語意三情形（對照 P2+）

| 情形 | 83 的「退回 P1」 | P2+ 字面 | 判定 |
|---|---|---|---|
| 有 path_patterns、無非 domain 清單 | 未命中 → 無法定位（70%） | P2+ 只定義「完全沒有路徑宣告」→ 未宣告；此情形未涵蓋 | **與 P2+ 意圖衝突**：P2+ 的動機正是把 70% 的非 domain 從無法定位拿出來；退回 P1 讓半套宣告的專案重現該雜訊。替代：未命中者歸「非 domain 層未宣告」，不計入無法定位 |
| 兩者皆無 | 若同樣讀成退回 P1 → flutter_balance 1762 筆假破洞 | 整體顯示「未宣告路徑」 | 83 的退回若涵蓋此情形即衝突；應限定 83 的敘述只指第一情形 |
| 有非 domain 清單、無 path_patterns | 未定義 | 未涵蓋 | domain 側未宣告：其餘路徑應歸「domain 未宣告」而非無法定位 |

結論：三分類＋未宣告實際要擴成「domain 側」「非 domain 側」各自有無宣告的 2×2，缺席語意需用戶補裁。

#### W：候選

| 候選 | 載體 | 擁有者 | Graph 讀取 | 缺席降級 | 主要代價 |
|---|---|---|---|---|---|

選項品質檢查：S2 與 S6 可退化 → 實質 S1／S2／S3／S5 四個；涵蓋改造既有（S1、S3）、新增（S2）、零清單（S5）三類。

#### A：機會成本

0.5.0 目標是矩陣 ticket 高亮與 UC-02 判定可用。S1／S2 的 App 端工作量相同（新讀取路徑一條）；S3 免新讀取路徑但要改矩陣列過濾與 DomainBundle 語意；S5 免清單維護但把錯分隱藏起來，與 P2+「讓無法定位有鑑別力」同向卻犧牲「非 domain」的正確性。上游代價：S1 改模板＋validate，S2 新增 carrier＋validate，S3 改 DomainBundle 型別語意（跨 consumer），S5 新增一個旗標。

#### P：失敗預想

| 候選 | 3 個最可能失敗原因 | 早期警訊 |
|---|---|---|
| S1 | 單 domain 專案不建 system-layer → 永遠「非 domain 未宣告」；system-layer 被當散文檔不維護 frontmatter；未來多份系統層文件無合併規則 | 第一個單 domain consumer 升版後非 domain 側仍未宣告；validate 對 system-layer 零檢查 |
| S2 | 新檔被遺忘（不在任何模板流程內）；與 system-layer §2 L4 定義漂移；上游拒絕再加 carrier | 新 lib 頂層目錄出現而清單未增；version-bootstrap 步驟未列此檔 |
| S3 | 矩陣誤把 layer 列成一列；Diagnostics 把 layer 當 domain 報依賴違規；其他 consumer 不理解 kind | 矩陣列數 ≠ domain 數；depends_on_bundles 指向 layer |
| S5 | 新 domain 目錄未補 path_patterns 被靜默歸非 domain；旗標被無條件設 true；錯分只在人工比對時才發現 | domain 目錄數 > 宣告數；某 domain 的命中票數長期為 0 |

回退成本：S1／S2／S5 都只是新增選填欄位或檔案，移除即回到「非 domain 未宣告」；S3 涉及型別語意，回退要改 consumer 資料。

#### 傾向與盲點

傾向：S2（獨立小設定檔），理由是事證 2、3——非 domain 清單是「每個專案一份、與 domain 數量無關」的屬性，system-layer 依模板自身判準只收跨 domain 的事，也不存在於單 domain 專案；S1 與 S2 的 App 端成本相同。次選 S1 若用戶接受「單 domain 專案也建 system-layer」。S5 有吸引力但把錯分變成不可見，不傾向。
盲點：只看了本專案與 flutter_balance；不確定上游是否已有規劃中的專案設定檔（W1-096.2 之外）；第一情形的「非 domain 未宣告」顯示方式屬 UC-02 文案，未評估 UI 成本。

#### 需用戶裁決

1. 載體：S1／S2／S3／S5？

3. 若取 S1：是否要求單 domain 專案也建立 system-layer？
