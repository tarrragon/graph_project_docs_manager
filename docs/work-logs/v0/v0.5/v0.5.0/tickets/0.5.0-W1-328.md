### 實地觸發時點（2026-10-15，派發方提醒）

本票修改的是 merge_gate 本身。閘門程序在送出當下就從主 checkout 載入程式，所以本票所在的批次是用舊閘門驗證新閘門。本票的實地觸發，是本票寫入 main 之後的下一筆合併：須記錄那一筆的閘門輸出，包括預檢是否執行、有衝突時是否在進入排隊前就回報，作為驗收證據。

### 派發 context（2026-10-19，257 合併後）

- 0.5.0-W1-257 已把 CAS 引擎搬到 `scripts/merge_cas.py`（合併 `da6c9c1a9`）。預檢要用的 `_resolve_commit`、`_compute_merge_tree` 都在 merge_cas
- 建議掛點：`worktree_manager._merge_through_gate`，在 `record("開始", ...)` 之後、呼叫 `merge_branch_cas(..., hold=gate.hold(...))` 之前。這裡是唯一經過名額佇列的入口；`--skip-gate` 路徑不排隊，不需要預檢
- 建議形狀：merge_cas 新增一個公開函式，給定 branch／base／repo，回傳空字串（可合併）或中止說明（文字衝突、ref 解析失敗）。內部沿用 `_resolve_commit` 與 `_compute_merge_tree`。`_prepare_candidate` 前半段的相同判斷改為呼叫它，避免兩份邏輯各自演進（同型缺口見 `file-split-by-contention.md` §3.1 第 5 步）
- 預檢衝突時：記一行「[合併閘門] 結束」，結果分類新增一個標籤（與 `merge_gate.py` 既有的 GATE_WRITTEN 等並列，例如「預檢衝突」），以非 0 結束，不進入排隊
- 「已合併」與「空合併」不屬於衝突，預檢放行，維持由取得名額後的既有路徑判定
- 實地觸發驗收：本票寫入 main 之後，下一筆經閘門的合併（預定為 0.5.0-W1-351）的閘門輸出記入本票 Test Results，再 complete 本票
- 與 0.5.0-W1-351 同改 merge_gate.py：351 排在本票之後，blockedBy 本票不需要另設，由 L7 佇列依序執行
