## Solution
### 修法

- 送訊號函式（_signal_group）除 ProcessLookupError 外一併忽略 PermissionError。EPERM 表示群組內沒有本程序可送訊號的成員；已知成因是 macOS 上群組只剩未回收的殭屍。存活判定函式（_group_alive）先前已處理同一例外，本次未改其行為，補了測試。
- 命令無法啟動時攔截整類 OSError：找不到命令或其直譯器（FileNotFoundError）輸出單行訊息並回 127；其餘啟動失敗（無執行權限、執行格式錯誤、路徑中段不是目錄等）回 126，訊息附系統錯誤說明。
- 秒數不是數字時輸出用法訊息並回 2。
- 命令自身也可能回 126 或 127，結束碼無法區分兩者；包裝層的訊息一律以「run-with-timeout:」開頭，以此區分。
- 模組說明改為逐列結束碼，補上用法錯誤與本腳本被訊號終止兩種既有結束碼，並寫明：命令在期限內結束後，同群組內仍存活的程序立即以 KILL 終止、無寬限，已脫離群組的程序不在此列。

提交：4091260ff（初版）、962bf22d6（審查後修正）。初版提交訊息宣稱「無法啟動即回 127 或 126」，當時實作只涵蓋兩種例外；該宣稱在 962bf22d6 才成立。

### 已知限制

- PATH 中某個目錄不可搜尋且命令不存在時，系統回報權限不足，本腳本會回 126 而非 127。訊息附有系統錯誤說明。無需建 ticket：成因在作業系統回報的錯誤碼，本腳本無從分辨。
- 在非 macOS 平台上，對殭屍群組送訊號不回 EPERM，「不拋例外」與「存活判定」兩項測試照常執行且恆綠，對 PermissionError 分支沒有鑑別力；對照測試在該平台略過。無需建 ticket：該分支在這些平台上不會被執行，沒有可測的行為。

### 殭屍群組 fixture 的判定方式

輪詢 ps 的狀態欄直到以 Z 開頭，期限 10 秒，逾期以斷言失敗收場，訊息含 PID 與最後觀測狀態。採輪詢是因為 os.waitid 在 macOS 的 Python 不提供。

### 對照的兩種形態

- 常駐測試：對同一個殭屍群組不經保護直接呼叫 killpg（訊號 0 與 KILL），斷言拋出 PermissionError。作用是證明 fixture 造出的群組確實會觸發例外。
- 變異實測（一次性，未留檔）：在記憶體內分別移除兩個函式的 PermissionError 處理後，對殭屍群組呼叫。結果：_signal_group 原版不拋例外、變異版拋 PermissionError；_group_alive 原版回傳 True、變異版拋 PermissionError。量測環境 macOS（Darwin 25.5.0），2026-10-13。
