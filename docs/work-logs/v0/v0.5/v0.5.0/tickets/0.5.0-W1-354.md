## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 第二次實例（2026-10-19）

主控 PM 建 0.5.0-W1-360 時再次未跑 dedup 即填 none，事後補跑（結論恰為 none）。同一執行者在已建本票、知道缺口的情況下仍重犯，支持「文字提醒不足、需由閘門承擔」的方向（opinionated-default-design 主張 3）

## 重現實驗結果
### 實驗方法

1. 讀閘門實作：`validate_portable_issue_gate`（ticket_system/lib/field_validators.py）與 create.py 呼叫點
2. 讀 `section_comment.py` 的 `cmd_dedup`，確認查重是否留下任何可查紀錄
3. `ticket create --dry-run`，where.files 全在 `.claude/` 下，三種輸入對照：不帶旗標／未跑 dedup 直接 `--dedup-checked none`／`--dedup-checked "隨便"`

### 實驗執行（2026-10-19，本機）

- 閘門判定只有一行：`if dedup_checked: return True`——任何非空字串都放行
- `cmd_dedup` 只 `sys.stdout.write(render_dedup_report(...))`，不寫檔、不留時間戳或關鍵字紀錄
- 對照結果：不帶旗標 → `errno: PORTABLE_ISSUE_UNDEDUPED`（擋下）；`none` 與 `"隨便"` → 皆通過查重閘門，續行至後段 `enforce_checklist`（errno 改為 CHECKLIST_VALIDATION_FAILED，缺 when／how_strategy，與查重無關）

### 實驗發現

- 已驗證：閘門無法區分「已查重得到 none」「未查重填 none」「填任意字串」；查重本身不留紀錄，事後也無從覆核
- 已驗證（實例）：主控建 0.5.0-W1-353、0.5.0-W1-360 兩次未跑 dedup 即填 none，第二次發生在已建本票、已知缺口之後
- 未驗證：B' 方案中 create 呼叫 dedup 的耗時與離線時的錯誤形態（留給實作票量測）
