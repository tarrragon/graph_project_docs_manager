### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` fails or is
unavailable) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
resolve_lock_path 以 rev-parse --git-path index.lock 解析（失敗退回 <root>/.git/index.lock）；刪除須 0 位元組 + 鎖齡 > 5s + lsof 無持有，lsof 缺席/逾時視為持有（fail-safe）；每次刪除/拒刪寫 stderr 與日誌。產生路徑盤點：僅 hook main -> check_and_cleanup_index_lock 一條刪除路徑。

### 自檢結果
- 三項條件各有拒刪測試；現存 .git/worktrees 鎖檔未觸碰（測試僅用 tmp_path）。
- Python 3.9 相容：用 Optional，無 PEP604。

### 合併前審查與追修清單（PM，2026-10-12；本票分支尚未合併）

**Phase 4 審查**（linux 唯讀審查，提交快照與暫存 repo 及其 linked worktree 於 scratch 實測，load 68 至 211）：重構需要 是（小範圍）；技術債務 發現；程式碼品質 B；可否合併 修正後可。

**已確認**：lsof 對「git 正持有、0 位元組」的鎖檔可靠（12/12 次回報持有者，hook 對其 5/5 次拒刪）；lsof 缺席、逾時、rc=2 皆不刪且逾時有記錄；本提交新增的子程序（rev-parse --git-path 與 lsof）不取 index.lock，未引入父票分析的同型問題；七項變異六項翻紅。

**合併前必修**：
1. 目標解析：hook 以 lib.git_utils.get_project_root() 決定目錄，其第一優先為 CLAUDE_PROJECT_DIR。實測 env 為主 repo、cwd 為 worktree、命令為 git add 時，被清的是主 repo 的 .git/index.lock，worktree 的鎖原封不動——即本票要解的那一個。實作者的實地觸發係手動把 env 設為 worktree，未走到此路徑；所有單元測試皆 patch get_project_root，解析層零覆蓋。改用 payload 的 cwd。
2. 刪除前複核：stat、lsof、os.remove 之間無任何複核。實測（注入交錯）：lsof 執行期間舊鎖被移除、git 取得新鎖（新 inode、0 位元組、持有中），hook 照刪並回報無行程持有。空檔長度等於 lsof 耗時，實測 0.85 至 2.65 秒；修改前無 lsof，空檔為微秒級。刪除前重新 os.stat，st_ino、st_mtime_ns、st_size 任一不同即不刪並留記錄。
3. 為上列兩項各補測試：不 patch get_project_root 的真實 stdin 測試（env 為主 repo、cwd 為 worktree，斷言 worktree 鎖被清、主 repo 鎖不動）；lsof 期間換 inode 的測試。

**同批處理**（PM 裁決：皆在刪除路徑的安全性上，不延後）：
4. lsof rc=1 且 stdout 為空一律視為未持有，而 lsof 自身出錯亦回 rc=1（以 shim 模擬 rc=1 加 stderr 有錯誤時鎖被刪）。未持有的判定加上 stderr 為空的條件，其餘視為無法判定而不刪。補「異常 rc」的測試（該變異目前存活）與獨立的逾時測試。
5. rev-parse 逾時或失敗時靜默退回 <root>/.git/index.lock，於 worktree 內該路徑不存在而無聲漏清。退回時留記錄；worktree 內無法解析時明示為無法解析。
6. 鎖齡未達閾值分支的訊息仍寫死 .git/index.lock 與 rm .git/index.lock，於 worktree 情境會指示使用者刪錯檔，且該分支不寫 stderr。訊息改用解析出的實際路徑。

**PM 確認的行為變更**：主 repo 的非 0 位元組舊鎖於修改前會被自動移除，本票之後不會（寫入途中被終止的殘留須人工處理）。此為預期：非 0 位元組的鎖檔可能含寫到一半的索引，自動刪除的風險高於保留；須於 hook 檔頭 docstring 與提交訊息載明。

**可延後**（另票）：hook 的觸發判定為命令字串含 git add 或 git commit 的子字串比對，git -C <path> add／commit 與 ticket track commit 皆不觸發，而兩者為框架推薦的寫法。

**PM 覆核補記**：分支上該 hook 的測試檔 11 passed；本專案 .git/worktrees 下兩個證物鎖檔於實作與審查後皆未被觸碰。產生路徑盤點表寫於 Solution 而未併入 how.strategy，且只盤了刪除路徑；決定 hook 清得到誰的觸發與解析路徑未被盤點，與必修第 1 項為同一缺口，追修時一併補齊並併入 how.strategy。
