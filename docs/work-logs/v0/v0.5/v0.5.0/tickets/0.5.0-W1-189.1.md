## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 設計段

**1. 函式入口形式**：不改 43 支既有 hook。分派器以 `runpy.run_path(<hook>, run_name="__main__")` 在同一程序內執行每支 hook 的原檔，hook 自身的 `if __name__ == "__main__"` 區塊照常執行（含 `run_hook_safely(main, name, fail_closed=...)`、hook 名稱、liveness 進入紀錄），因此各支的 fail_closed 設定、日誌名稱、單獨執行入口全數保留，零檔案改動。每支執行時：stdin 換成載有原始 payload 的 StringIO、stdout/stderr 換成各自的緩衝、捕捉 SystemExit 取得 exit code；結束後還原 sys.argv、sys.path、os.environ、cwd。`lib` 等已匯入模組在程序內共用，這就是消去固定成本的來源。

**2. 逐支例外與逾時隔離**：每支獨立 try/except，捕 Exception 與 SystemExit；逾時用 `signal.setitimer(ITIMER_REAL)`，每支逾時取自 registry 的 `timeout`（缺省 30 秒，沿用 settings.json 原有的 120／595 等值）。例外或逾時只影響該支：記入分派器日誌、在合併後的 stderr 以 `[hook名]` 前綴留下可見紀錄，其他支照常執行。

**3. 合併規則**：
- exit code：任一支 2 即整體 2；否則任一支非 0 則整體 1（非阻擋錯誤，與原本單支行為一致）；否則 0。
- stdout 的 JSON：`permissionDecision` 取最嚴格者（deny > ask > allow）；只有一支給出該層級時，decision 與 reason 原樣傳出，多支同層級時 reason 以 `[hook名] ` 前綴逐行相接；`additionalContext`、`systemMessage` 以換行相接並加前綴；非 JSON 的 stdout 以前綴相接。
- stderr：逐支加 `[hook名] ` 前綴後相接，exit 2 時整段作為回饋。
- 所有支都跑完才合併（原本 CC 並行執行，本來就沒有短路，副作用維持一致）。

**4. 分派器自身失敗**：
- 單支 hook 例外／逾時：fail-open 但可見（stderr 前綴 + 日誌），與原本單支被 CC 逾時終止或崩潰的語意相同；fail_closed 的守衛（例：workspace-wipe-guard）由其自身 `run_hook_safely(fail_closed=True)` 在 hook 內回 2，照常生效。
- 分派機制本身失敗（registry 讀不到、runpy／串流替換出錯）：逐支退回以子程序執行（`sys.executable <hook>`，與原本等價），守衛不因分派器壞掉而消失；連退回都失敗則 exit 1 並寫 stderr 與日誌。選 fail-open 可見、不選 fail-closed 的理由：fail-closed 會讓所有 Bash 命令（含修復用的）被擋，退回子程序已保住守衛。
- 判斷依據是「原本應被擋下的命令是否仍被擋下」，詳見 how.strategy 盤點表。

**5. 新增 hook 如何掛進分派程序（含 231.2 的 PreToolUse(Bash) 封堵）**：
- 註冊位置：`.claude/hooks/hook-dispatch-registry.json`，鍵為 `<event>:<matcher>`（`PreToolUse:Bash`、`PostToolUse:Bash`），值為有序清單，項目 `{"path": "<自專案根的相對路徑>", "timeout": <秒，選填>}`。新增 Bash 的 PreToolUse／PostToolUse hook 時在清單加一項，不再動 settings.json。
- 入口形式：hook 維持原本的腳本（PEP 723 標頭、`main() -> int`、`__main__` 區塊），分派器以 runpy 執行，不需任何改寫。
- 單獨執行入口：保留。pre-test-hook 在 `mcp__dart__run_tests` 的 matcher 仍由 settings.json 直接以 uv 啟動，同一檔案同時服務兩種註冊。
- 231.2 的封堵判定在既有 pre-test-hook 的 `build_block_reason`，已列於 registry，deny 的 permissionDecision 與 reason 由合併規則原樣傳出（有對應測試）。
- PEP 723 依賴：分派器標頭宣告各 hook 依賴的聯集（pyyaml），所以在 uv 環境下 hook 內 `import yaml` 照常可用。
- 分派器命令：settings.json 每個 matcher 一筆 `uv run --quiet $CLAUDE_PROJECT_DIR/.claude/hooks/hook-dispatcher.py --group PreToolUse:Bash`。

**範圍外**：wrap-decision-tripwire（PostToolUse 不帶 matcher，全工具觸發）不在 Bash 段，維持原註冊。

### 設計段修正與補充（以本節為準，覆蓋上方同題敘述）

**輸出前綴**：additionalContext 與 systemMessage 不加前綴（各 hook 自帶標籤，例如 `[Bash Edit Guard]`），多支以空行相接；stderr 與多來源 permissionDecision reason 才加 `[hook名] ` 前綴；單一來源的 deny reason 原樣傳出。上方設計段寫「additionalContext 加前綴」的部分作廢。

**逾時推算與卡住時的最長等待**：
- 每支上限 = min(registry 的 timeout（缺省 30 秒；hooks-test-gate 120、tracking-schema-json-staleness-guard 595、其餘沿用原 settings 值），群組剩餘預算)，由 `setitimer` 強制截斷，超時只影響該支並可見。
- 群組預算（budget）是實際執行上限，不是各支加總：PreToolUse:Bash 600 秒、PostToolUse:Bash 120 秒。預算用盡後的後續 hook 不執行並在 stderr 標示。
- settings.json 逾時 = budget + 20 秒餘裕：Pre 620、Post 140。
- 一支卡住時最久等到該支上限（多數 30 秒）；多支同時卡住也不超過 budget，Pre 最壞 620 秒（重型 hook 排最後，最壞情形是前面的卡住把預算耗盡），Post 最壞 140 秒。原本各支獨立並行、各自 30 秒，改為序列後最壞值變大，這是序列執行的代價。
- 分派器序列執行：wall 由並行的最慢一支變成各支加總，實測仍較快（見量測）。

**實作清單**：`.claude/hooks/hook-dispatcher.py`、`.claude/hooks/hook-dispatch-registry.json`、settings.json 的 Bash matcher 各剩一筆（Pre 原兩筆併一）、`hook-liveness-summary-hook.py` 新增 `_merge_dispatch_registry`（第 12 條）、兩支既有測試改為同時讀 registry（test_hooks_test_gate_hook、test_phase4_decision_enforcement_hook 的 settings 契約案例）。
