## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修法

- `commit_files_isolated`：在 `rev-parse HEAD` 之後、`git add`（讀工作區）之前，快照整檔路徑（deduped，不含 append 路徑）的共用 index entry，作為 `pre_commit_entries` 傳給收尾同步。
- `_sync_shared_index_after_commit`：新增選用參數 `pre_commit_entries`；新函式 `_is_superseded_pre_commit_stage` 在三條件同時成立時判為己方：(1) 路徑在快照內（整檔提交）(2) 本次 tree 與 parent 對該路徑不同（本次確實改動）(3) entry 自快照後未變動，且不是 conflict。
- 既有判準（HEAD／tree／parent／路徑歷史）不變；三參數呼叫形態不變。

### 對照規則七〈隔離索引 CAS 的時間維度要件〉要件 B

三平面判準把「index 與 $OLD_HEAD、新 HEAD 皆不同」判為他人在途。本修法加入第四平面「提交前共用 index」，用來辨認被本次提交取代的狀態：整檔提交讀工作區全文，快照時已在 index 的 stage 若保留下來，下一次裸 commit 會把該路徑回滾到 stage 版本，等於回滾本次提交。所以同步這類 entry 的方向是保護 HEAD，不是清除他人工作。

仍判為他人在途、不清理的情形（各有測試）：
- 快照後才出現的 stage（提交期間他方 stage）
- 路徑列在本次提交但本次未改動（快照的 stage 沒有被取代）
- append-only 路徑（只提交 HEAD 加上本次行，他方 stage 的行沒有被取代）

已知邊界：快照時他方已 stage、且本次整檔提交改動了同一路徑時，這個 entry 會被同步。這時他方的工作區內容已整檔進入本次提交，被丟掉的只是 stage 那一刻的版本。這個情形本身就屬於檔案級共用（PC-BAL-008），收尾同步不是它的防線。
