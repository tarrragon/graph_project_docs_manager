## Task Summary

SPEC-007 使用中邊型＝established 扣 domain_dependency；阻擋 4 的 bundle_dependency 與 FlowStep branching/returning 皆為 proposed，需 Graph 能啟用指定 proposed 邊型，現無票承接

## Problem Analysis
### 問題根因

SPEC-007 的「使用中邊型」＝型別表 `layer` 為 established 的邊型扣除 `domain_dependency`（〈用詞〉、D2、D6；`lib/schema/edge_type.dart` `activeEdgeTypes`）。proposed 邊型一律不進建圖，契約測試 S6-9（`edge_type_decoding_test`）與 K5（`tracking_schema_contract_test`，W1-070.2）釘住「`bundle_dependency` 為 proposed 且不進使用中」。但 0.5.0 已裁決的兩個消費者需要 `bundle_dependency`：

1. 矩陣「間接依賴」判定式（SPEC-001〈間接依賴判定式〉第 2 列，W1-093.1）：沿 `bundle_dependency` 往下游可達。
2. 泳道列序（SPEC-001〈泳道布局規則〉，W1-092.2）：由 `bundle_dependency` 推導層序。

兩者都在 Layout／矩陣側，而 Layout 只依賴 Graph（layout domain-map §2），Graph 公開面目前沒有任何管道提供 `depends_on_bundles`：`LightNode` 只有 id／typeName／status／title／path，不帶 frontmatter；SPEC-007 全文沒有 `bundle_dependency`。

### 影響範圍

- 已驗證：範圍收窄為 `bundle_dependency` 一個邊型。FlowStep 已裁決 C（子圖掛 UC、不進主圖），branching／returning 不再需要進主圖邊；emission／consumption 本版無消費者。
- 已驗證：本專案 8 份 DomainBundle 共 7 條 `depends_on_bundles` 值，全為 `DOMAIN-MAP-*` 節點 ID（可走既有 `_lookupId`）。flutter_balance 0 條（單一 domain-map，無此欄）。
- 受影響：SPEC-007（〈用詞〉、D2、D6、FR-01 驗收）、`lib/schema/edge_type.dart`、`lib/graph/`、契約測試 S6-9／K5、SPEC-001 兩段的資料來源描述。
- 未驗證：Layout 現行程式是否已以 fixture 實作列序（本票不讀 lib/layout）。

### 相關 Error Pattern

無直接匹配。相關：W1-083（產生版本與內建副本漂移），本票候選若改型別表欄位需同步內建副本（W1-096.8 前例）。

### 實驗與 WRAP 評估（2026-10-08）

**錨點**：0.5.0 目標是矩陣與泳道可用；消費者只有兩個（間接格、泳道層序），都在 Layout 側。App 觀測其他專案，做法須對沒有 `depends_on_bundles` 的語料（flutter_balance）也成立。

**範圍**：收窄為 `bundle_dependency`（FlowStep 取 C 後 branching／returning 不進主圖；emission／consumption 本版無消費者）。

**W：候選**

| 候選 | 作法 | 對 D6／測試 | 無此欄語料 |
|------|------|------------|-----------|
| P1 本地允許清單 | 使用中邊型＝established 扣 `domain_dependency` 加 `bundle_dependency`（D6 第三個鍵名例外）；7 條邊進主圖，走既有 `_lookupId`，鄰接查詢與破洞（目標不存在）自動涵蓋 | D6 例外 2→3；K5 改寫；S6-9 不變 | 0 條邊，層序全 L0、間接格全空 |
| P2 型別表新增欄位 | 上游為邊型加「消費端可依賴」之類旗標，App 依旗標決定使用中 | 移除鍵名例外的方向，但語意與 `layer` 重疊（layer 本身就是穩定性承諾）；框架變更、需 83 協調與推送授權、內建副本再同步 | 同 P1 |
| P3 上游升 established | 改 `layer` | 違反上游自身升級判準條件 (1)（只有本專案有實例）；影響所有 consumer 的 conformance 預期集合 | 同 P1 |
| P4a 不進主圖，Graph 公開面另給 | Graph 自 DomainBundle 的 RawNode frontmatter 讀正向欄位（欄位名取自型別表，不寫死），提供 bundle 依賴查詢（同 `flowOf` 形態的旁路） | 不改使用中邊型、K5／S6-9 不變；D6 不增例外，但 SPEC-007 多一個非邊管道 | 回空 |
| P4b Layout 直讀 Corpus | 跳過 Graph | 違反 Layout 只依賴 Graph 的分層（layout domain-map §2），淘汰 | — |
| P5（反向框架）App 自宣「消費的 proposed 邊型清單」 | 以 App 常數列出本版消費的 proposed 邊型（目前只有 `bundle_dependency`），寫為獨立設計約束而非 D6 例外 | 實質與 P1 相同，差在命名與文件位置 → 退化為 P1，不單列 | 同 P1 |
| P6（反向框架）不做 | 間接格與層序先用寫死常數或 fixture | 違反 1c 裁決「做法須對其他專案成立」，淘汰 | — |

三類涵蓋：改造既有（P1、P4a）、零工具（P6，淘汰）、新增工具／欄位（P2、P3）。可退化檢查：P5≡P1；P1 與 P4a 差在「邊是否進主圖」，非同一方案。

**R：事證**
- 上游升級判準：兩條件 AND；條件 (1) 不成立 → P3 與上游規則衝突。
- 形狀變動風險：`bundle_dependency` 2026-10-07 才新增，proposed 的承諾即「形狀可能變」。P1／P4a 若欄位名取自型別表，改名可吸收；若改為 directed→其他或加反向欄位，P1 由泛用管線自動吸收，P4a 的旁路需跟改。
- IT／G9：所有候選都不改凍結值與計數（manifest 無該欄、G9 無 DomainBundle）；新邊 IT 零覆蓋，是否重凍結已由 W1-001.6 承接評估。
- 共同前提：D4 名稱解析器（W1-001.5）與間接格都需要 DomainBundle 的 `domain`，`LightNode` 目前不帶；兩者可同批決定 Graph 暴露 DomainBundle 屬性的方式。

**A：機會成本**
- P1：最少新程式（泛用管線現成），代價是 D6 例外再加一個，而 D6 原意是例外收斂（現有兩個都標「由 W1-001 移除」，實際 domain_dependency 已裁決保留）。
- P4a：例外不增，但 Graph 公開面多一種「非邊」查詢，鄰接查詢、破洞分類不自動涵蓋 bundle 依賴（指向不存在的 bundle 要另寫）。
- P2：根治例外累積，但 0.5.0 內要再走一輪上游→canonical→內建副本同步（W1-096.8 剛示範此鏈會造成 main 短暫紅燈）。

**P：失敗預想**

| 候選 | 可能失敗 | 早期警訊 | 回退成本 |
|------|---------|---------|---------|
| P1 | 上游改 `bundle_dependency` 形狀；他 proposed 邊型陸續被要求加入，例外清單膨脹；proposed 邊混入一般鄰接查詢使詳情卡顯示未承諾穩定的關係 | D6 例外數 >3；SPEC-007 出現第二個「加入使用中」的 proposed 邊 | 低：移除清單一項＋還原 K5 |
| P2 | 上游拒絕新增語意重疊的欄位；內建副本未同步造成紅燈 | 83 協調意見反對；`test/unit/schema` 翻紅 | 中：框架欄位已推出則要走 deprecation |
| P3 | 其他 consumer 的 conformance 測試失敗；日後形狀要改卻已承諾 established | 他 consumer 回報 conformance 紅 | 高：established 降級屬破壞性變更 |
| P4a | 旁路與泛用管線各自演進而漂移；破洞（指向未宣告 bundle）被漏報 | SPEC-007 兩處描述同一欄位；Diagnostics 沒有對應類別 | 低：旁路改為 P1 是加法 |

**我的傾向**：P1，理由：消費者需要的正是「沿邊可達」，泛用管線已含目標解析與破洞，旁路要重做這兩件事；回退成本最低。附帶條件：使用中的 proposed 邊在畫面上須標示為 proposed（W1-070.2 策略「proposed 邊型不進入 established 渲染」的延伸），避免把未承諾穩定的關係與 established 混同。次選 P4a（若用戶要求 D6 例外不再增加）。

**盲點**：沒有讀 lib/layout 是否已有列序實作；未查證其他 consumer 是否已有多份 domain-map；P1「proposed 邊在畫面上標示」的成本未估。

**需用戶裁決**
1. P1／P2／P4a（P3 違反上游判準、P4b／P6 淘汰）？
2. 若 P1：使用中的 proposed 邊在詳情卡／鄰接查詢是否標示 proposed？
3. Graph 暴露 DomainBundle `domain` 的方式是否與 W1-001.5 同批定案？

### 用戶裁決（2026-10-08）

- P1：使用中邊型加入 `bundle_dependency`（D6 第三個例外），7 條邊進主圖、走現成目標解析與破洞判定；K5 契約測試同批改寫。
- 使用中的 proposed 邊在詳情卡與鄰接查詢標示 proposed（layer 為穩定性承諾）。
- Graph 對外提供 DomainBundle `domain` 的方式，與 0.5.0-W1-001.5（名稱解析器）同批決定，以 0.5.0-W1-001.2 寫定的解析器條文為準，不另行設計。
- 落地：0.5.0-W1-103.1（規格）、0.5.0-W1-103.2（實作）。
