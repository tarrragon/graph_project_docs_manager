### PM 方案判定（2026-10-20，待主控裁決）：建議採次選方案「pubspec.lock 入庫」，不採「worktree 建立流程複製 lock」。理由：本日五個案例全為 CC runtime 的 agent worktree，不經 worktree_manager；lock 入庫同時涵蓋 agent worktree、/worktree create 與 CI（231.6），也符合 Dart 對應用程式的建議（.gitignore 第 7 行註解）。lock 以哪一份解析入庫（主 checkout 的 9/24 版或重新解析）、生成檔與 l10n 產物是否隨之重生，須一併裁決。合併前須回報主控。where.files 已改為逐檔列出。
### 用戶裁定（2026-10-20，經 WRAP）：兩步，先鎖現狀，升級另立票

- **背景**：這是現實開發的常見問題，不是 AI 特有。lock 未入庫時，每份 checkout 各自解析，AI 並行開發只是放大了發生頻率。正規做法有兩項：應用程式的 lock 入庫；「採用 lock」與「升級依賴」分成兩次變更。
- **以主 checkout 的 lock 為準**：今天 macOS 實機的 integration_test 與 App 都在主 checkout 跑，用的是 9/24 的 lock（shared_preferences_android 2.4.27，無 jni）。在目標平台上實際驗過的是這一份。閘門快照用的重新解析版只驗過單元與 widget 層。
- **本票步驟**：
  1. 在主 checkout 執行 `fvm flutter pub get`，不可用 upgrade。pub get 會保留已鎖版本，只補上 9/24 之後 pubspec 變動的部分。若這次改動超過少數套件，停手回報主控。
  2. 移除 .gitignore 對 pubspec.lock 的排除，並把該 lock 原樣入庫。
  3. 生成檔與 l10n 產物不改，維持 main 的現狀。
- **合併注意**：合併後，主 checkout 原本未追蹤的 pubspec.lock 會變成已追蹤檔，git 可能以「untracked working tree file would be overwritten」拒絕同步。合併前先確認入庫內容與主 checkout 的檔案逐位元組一致，必要時暫時移開本機檔，合併後再核對。
- **231.6**：CI 的 pub get 加 `--enforce-lockfile`，由 L20 補進 231.6 的 acceptance。
- **依賴升級**：另立 449（P3，blockedBy 本票）。審過 pub outdated 的清單後才升級，並同批重生生成檔與 l10n。
主控補充：本裁定屬專案技術決策，與 CLAUDE.md §6 的 FVM 釘選屬同一類可重現性決策。446.1 合併時，同批在 docs/tech-decisions.md 追加補記段：lock 入庫、採用 lock 與升級依賴分開進行、CI 使用 --enforce-lockfile，以及理由（多份 checkout 各自解析造成版本不一致；AI 並行 worktree 會放大這個問題）。where.files 一併加入 docs/tech-decisions.md。
