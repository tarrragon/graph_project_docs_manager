## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

`lib/hook_io.is_handoff_recovery_mode` 只判斷 `.claude/handoff/pending/*.json` 是否非空（process 級快取），不讀檔內的 `ticket_id` / `target_ticket_id`，也不看檔齡。兩支派發守衛命中後整體略過檢查。殘留檔的兩個成因：

1. `ticket migrate` 不處理 `.claude/handoff/pending/`（`migrate.py` 中 handoff 字樣命中 0），舊 ID 的 pending 檔原地殘留。
2. `ticket handoff --gc` 對查無來源票的檔不判 stale：`handoff_utils.is_ticket_completed` 查不到票回 False（「保守策略」），`is_handoff_stale` 情境 2/3 因此不成立；`--force` 路徑同樣走 `is_ticket_completed`，也不清理。實測 clone 內 `--gc --dry-run` 與 `--dry-run --force` 皆回「無 stale handoff」。

#45 的 2026-09-23 觀測已記錄成因 1 與 2 的機制（候選 a/b/c）；本票新增的是殘留檔的下游爆炸半徑。

### 影響範圍

| 守衛 | 位置 | 恢復模式下放行什麼 | 範圍 |
|------|------|------------------|------|
| agent-ticket-validation-hook | `.claude/skills/ticket/hooks/`，步驟 0 | 略過「Ticket 引用 / 存在 / 決策樹欄位 / 嵌套深度」全部驗證 | 全域（任何派發、任何 prompt） |
| task-dispatch-readiness-check | `.claude/hooks/`，主流程 | `sys.exit(0)` 略過代理人分派檢查 | 全域 |
| ticket-file-access-guard-hook | `.claude/skills/ticket/hooks/` | 不呼叫共用函式；已本地改用 `get_handoff_recovery_ticket_ids`，只放行 pending 檔指向的 ticket（來源與目標） | 限縮（既有先例） |

- 殘留檔產生條件：(1) migrate 改 ID 後舊 ID 檔留存；(2) 票被刪除或原 ID 消失；(3) gc 對 (1)(2) 皆不處理；(4) 一般 handoff 在 target 尚 pending 時也合法存在，故「檔存在」不等於「有人在恢復」。
- 已驗證：兩支守衛皆呼叫共用函式（grep 全 `.claude/` 非測試碼僅此三處 import 加 `lib/__init__` re-export）；agent-ticket-validation 的放行有 E2 實測；task-dispatch-readiness 的放行由程式碼路徑確認（payload 未驗證其放行差異，見實驗發現）。
- 未驗證假設：派發守衛放行 45 次中有多少是真恢復、多少是殘留造成（log 無法區分，這正是缺可見訊號的後果）。
- handoff 目錄被 gitignore（`.gitignore:86`），殘留檔不隨 clone 傳播，影響限於產生它的工作區。

### 實驗發現

未驗證：task-dispatch-readiness 放行差異需另造「會被分派檢查擋下」的 payload 才能對照（程式碼路徑已確認放行點）；真實恢復流程（Stop hook 提示 resume 後的派發）是否總是引用 handoff 指向的票未實測，方案 A 的前提即此。

## Solution

multi_view_status: skipped
reason: 單一 hook 範圍的分析，修法方向由實測與既有先例（file-access-guard 本地限縮）支撐；多視角審查留給 children 實作票的 Phase 4

### 結論

採 A（限縮）為主、C（可見訊號）為輔、D+E（清除殘留，即 #45 候選 b、a）為並行。三者處理不同層：A 使殘留檔無法放大成全域放行（與成因無關），C 使任何放行可被觀測，D+E 縮小殘留產生與停留。B（有效期）不單獨採用。

### 方案比較

| 方案 | agent-ticket-validation | task-dispatch-readiness | file-access-guard | 可攜性與風險 |
|------|------|------|------|------|
| A 限縮至 handoff 指向的票 | 僅 prompt 引用的票 ∈ 集合時放行，其餘走正常驗證 | 同左；readiness 無票引用語意，可改為放行條件加同一集合判斷或移除恢復分支 | 已是此做法，改引用共用實作 | 高：純 lib 函式，無專案特定常數。風險：真恢復流程若不引用指向的票會被擋（未驗證，列為實作票的先決實測）。與成因無關，殘留檔危害歸零 |
| B pending 檔有效期（mtime TTL） | 檔齡超限者不計 | 同左 | 不受影響 | 中：TTL 數值是專案特定猜測；合法 handoff 可跨日，TTL 內殘留仍全域放行，爆炸半徑未縮 |
| C 恢復模式放行改為可見警告 | 放行不變，加一行訊息列出 pending 檔與指向 | 同左 | 不受影響 | 高；單獨不夠：仍放行，只把 45 次靜默變為 45 次可見（規則 4）。stderr 會顯示為 hook error，需用 additionalContext 或日誌 + 摘要 |
| D gc 把查無票的檔判 stale（#45 b） | 清除後恢復模式自然結束 | 同左 | 同左 | 高；僅清理已存在之殘留，不改守衛對「非空即恢復」的信任；須區分「查無」與「查詢例外」，跨 worktree 以 `get_ticket_state_root` 為準，否則真 handoff 被誤歸檔 |
| E migrate 改寫 pending（#45 a） | 同 D | 同 D | 同 D | 高；僅治成因 1，成因 2（票被刪）不覆蓋 |
