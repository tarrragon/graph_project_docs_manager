# Execution Log

## Task Summary

分析 Domain 泳道在已選定 UC 而投影為 null 時顯示「需先選定 UC」，以及矩陣快照與泳道即時衍生的生命週期分歧

---

## Problem Analysis
### 問題根因

已驗證（讀碼）：
- `domainSwimlaneProvider`（domain_view_providers.dart）watch `selectedUcProvider` 與 `scanRoundProvider`；`round is! ScanRoundCompleted` 或建圖不可用即回 `null`。
- `_SwimlaneBody`（domain_view_screen.dart）以 `selectedUcId == null || swimlane == null` 共用一個分支，渲染 `swimlaneUcUnsetPrompt`（「需先選定 UC」）與 `state-domain-swimlane-uc-unset`。該分支註解寫「選定 UC 尚無投影（輪次未完成）」並掛在 SPEC-001 §1「泳道 · 尚未選定 UC」名下，但 SPEC 該列進入條件只有「選定 UC 為空」。
- `DomainReady.matrix` 是 `DomainViewLoader._stateOfRound` 在載入當下寫入的快照；`DomainViewLoader` 只在 `load()` 期間 listen 輪次（僅更新 Loading 進度），完成後不再監聽。
- `ScanRoundNotifier.rescan()` 先 `discard`（state → `ScanRoundIdle`）再 `_startRound`（state → `ScanRoundRunning`），整段重掃期間輪次不是 Completed。
- `GateDetectionNotifier.detect` 的呼叫點只有兩處：`shell.dart` 啟動還原、`workspace_selection.dart` 選專案。導覽切換目的地**不會**重新觸發 gate 或 loader，Domain 的 `DomainReady` 原樣保留。

根因：同一畫面消費兩個生命週期不同的來源——矩陣（載入時快照，不隨輪次失效）與泳道（隨輪次即時衍生）——而畫面把「投影暫不可得」誤歸入「未選定 UC」的呈現。

### 影響範圍

- 檔案：lib/screens/domain_view/domain_view_screen.dart（`_SwimlaneBody`、`_emptyLanes`、`_ucTitleOf`、`_highlightName`）、domain_view_providers.dart（`domainSwimlaneProvider`）、lib/app/domain_view_loader.dart（不監聽輪次）。
- 規格：SPEC-001 §1 缺「已選定 UC、投影暫不可得」一列（規格缺口）。
- 同型風險：`firstNodeInLaneQueryProvider` 同樣以 `ref.read(scanRoundProvider)` 取當下輪次，與快照矩陣可錯位（「在泳道中檢視」定位欄可能取自新輪、矩陣卻是舊輪）。
- 未驗證：UC Flow／節點詳情 provider 亦 watch 輪次，是否有同型「未選定」誤呈現不在本票範圍，未查。

### 相關 Error Pattern

## 重現實驗結果
### 實驗方法

讀碼追蹤 provider 依賴圖（未跑實機、未新增 widget 測試；本代理人不寫測試）。追蹤對象：`scanRoundProvider` 狀態轉移（scan_round.dart `rescan`／`discard`／`_runGuarded`）、`domainSwimlaneProvider`、`DomainViewLoader`、`GateDetectionNotifier.detect` 全部呼叫點（grep `gateDetectionNotifierProvider`、`domainViewLoaderProvider`、`.discard(` 於 lib/）、破洞報告 `rescan`／`cancelScan`。可執行的 widget 重現測試已登記 spawn request（見 Spawn Requests）。

### 實驗執行

路徑 A（重掃後返回泳道）步驟：
1. 開專案 → gate → loader 寫 `DomainReady(matrix=輪次 R1)`；選 UC-01、切泳道 → 正常 · 泳道。
2. 至破洞報告按 `action-gaps-rescan` → `rescan()` → R1 discard（Idle）→ R2 Running。
3. 回 Domain（導覽不觸發 gate/loader，`DomainReady` 保留，mode 仍 swimlane）→ `domainSwimlaneProvider` 因非 Completed 回 null → 顯示「需先選定 UC」，selectedUcId 仍為 UC-01。
4. R2 完成 → provider 重算 → 泳道取 R2，面板標題（`_ucTitleOf`）與高亮名（`_highlightName`）仍取 R1 矩陣。

路徑 A'（取消重掃）：步驟 2 後按 `action-gaps-cancel-scan` → `discard('gap-report-cancel')`（Idle）→ 自動導覽回 Domain。Domain 不呼叫 `ensureRound`，輪次停在 Idle，泳道持續顯示「需先選定 UC」，直到使用者回破洞報告觸發掃描、或重選專案。輪次失敗（`_runGuarded` catch → Idle）同此。

路徑 B（詳情卡「在泳道中檢視」）：`action-domain-cell-goto-swimlane` 寫 `selectedUcProvider` 再切 mode swimlane。一般情形輪次即矩陣來源 R1、為 Completed，投影非 null，**無症狀**。僅當進入前輪次已被路徑 A／A' 置為 Running／Idle（矩陣仍顯示舊快照可點）時出現同一症狀；另 `firstNodeInLaneQueryProvider` 回 null 使定位欄失效。

### 實驗發現

已驗證（讀碼，狀態轉移確定）：
- 切換目的地**不會**重新觸發載入（gate 只在啟動還原與選專案時執行）。
- 路徑 A 症狀存在，窗口＝重掃耗時。
- 路徑 A'／輪次失敗：窗口**無上界**（Idle 無人重啟），比票面推測嚴重。
- 路徑 B 單獨進入無症狀；與 A／A' 疊加時症狀同 A。
- 新輪完成後矩陣與泳道來自不同輪次（標題、高亮、依賴路徑、定位欄可錯位；新輪刪除 UC 時標題退為裸 id）。

推測（未以執行驗證）：實際窗口秒數依專案大小而定，未量測；widget 測試重現待 spawn request 落地。

## Solution
### 結論

1. 症狀存在（路徑 A 窗口＝重掃耗時；A'／輪次失敗窗口無上界；B 只在疊加時出現）。
2. 生命週期分歧**需要結構性修正**：單靠畫面拆分支只能修正文案，無法消除矩陣與泳道跨輪錯位，也無法處理 Idle 無人重啟。
3. 「已選定 UC 而投影為 null」的呈現屬規格缺口，列為待用戶裁決（下方），不自行定案。

### 候選比較

| 候選 | 做法 | 利 | 弊 |
|------|------|----|----|
| 1 loader 監聽輪次 | `DomainViewLoader` 常駐 listen `scanRoundProvider`：離開 Completed 時回 `DomainLoading`（保留 mode／選取）、新輪 Completed 時重算矩陣；Idle 時呼叫 `ensureRound` | 矩陣與泳道同輪；沿用既有載入中列（SPEC 已定義），不需新狀態；A' 無上界窗口一併修正 | 重掃期間整個 Domain（含矩陣模式）回載入中，取消載入語意需重審（`cancelLoading` 會 discard 他頁發起的輪次）；`DomainReady` 帶 UI 選取欄位，回 Loading 再回 Ready 須保留 mode/selectedCell/swimlaneFocus |
| 2 矩陣改由輪次衍生 | 新增 `domainMatrixProvider`（同 `domainSwimlaneProvider` 由輪次衍生），`DomainReady` 不再帶 matrix；loader 只負責 gate／進入判定 | 單一資料源、結構上不可能錯位；`firstNodeInLaneQueryProvider` 同步受益 | 改動面大（DomainReady 契約、114.14／114.21 測試、空圖判定改由衍生值觸發）；輪次非 Completed 時矩陣也為 null，仍需定義呈現（與候選 3 共存）；Idle 仍需有人 `ensureRound` |
| 3 畫面拆分支 | `_SwimlaneBody` 拆出「已選定 UC 且投影為 null」分支，顯示「投影準備中」（或沿用載入中元件），不顯示「需先選定 UC」 | 改動最小、直接消除錯誤文案；不動 provider 結構 | 不解決跨輪錯位；A' 情境會永遠停在「準備中」；需新增 SPEC 列 |

建議：候選 2 加候選 3 的「準備中」呈現（或候選 1，若用戶傾向沿用既有載入中列），並補「Domain 可見時輪次為 Idle 則 `ensureRound`」。純候選 3 不足以滿足 acceptance 3。

### `_emptyLanes` 是否移入投影層

建議移入。理由：它以矩陣列推導泳道列結構，屬投影邏輯（SPEC-001 §1「同正常 · 泳道的列結構」），目前與 `projectDomainSwimlane` 的列序推導分離，兩者可能不一致（矩陣列序 vs 泳道依 bundle_dependency 層序加未定位列）。移入後空泳道與正常泳道共用同一列序函式，並由同一輪次衍生。採候選 2 時順勢完成；採候選 3 時可獨立成小改動。

### 待用戶裁決（SPEC-001 §1 規格缺口）

Q1：已選定 UC、投影暫不可得（輪次 Running／Idle）時泳道呈現為何？
- (a) 沿用 Domain「載入中」列（整個畫面，含進度與取消），對應候選 1
- (b) 新增「泳道 · 投影準備中」列：保留面板標題 `<UC id> <UC 標題>`、列結構不含步驟、顯示準備中提示，對應候選 2/3
- (c) 保持現狀並修 SPEC 進入條件涵蓋此情形（不建議：文案「需先選定 UC」與事實矛盾）

Q2：重掃完成後矩陣是否須隨新輪更新（是 → 候選 1 或 2；否 → 須在 SPEC 明定矩陣為進入當下快照並接受錯位）。
