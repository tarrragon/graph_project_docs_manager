## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 盤點（PM，2026-10-14）

**判定依據**：代理人能否寫檔，以 runtime 實際授予的工具為準，不看定義檔字面。Agent 工具的代理人清單（runtime 產出）是權威來源。frontmatter 只寫 `allowed-tools:` 的代理人（basil-event-architect、bay、clove、coriander、ginger、thyme-extension-engineer），runtime 都顯示為「All tools」。可見 `allowed-tools` 不是 subagent 的工具欄位，runtime 會忽略它，等同未宣告、繼承全部工具。

**寫檔能力**：只要有 Bash 就能寫檔，Write/Edit 不是必要條件。.claude/agents/ 的代理人中，只有 oregano-data-miner（Grep、LS、Read）完全無法寫檔；其餘都有 Bash 或全部工具。外掛代理人 general-purpose 與 claude 也是全部工具；Explore 和 Plan 不含 Edit/Write，但含 Bash。

| 代理人類別 | 例子 | 在 IMPLEMENTATION_AGENTS 內 | 名單外時被略過的檢查 |
|-----------|------|---------------------------|--------------------|
| 語言實作 | parsley、fennel、thyme-python、cinnamon、pepper、mint | 是（6 名） | — |
| 會寫產品檔／測試檔 | sage-test-architect（Edit/Write）、lavender、star-anise、project-compliance-agent、impeccable-manual-edit-applier | 否 | worktree 強制（第 4 支阻擋）、廣域 staging 警告、隔離派發收尾提示 |
| 會寫 .claude/ | basil-hook-architect、thyme-documentation-integrator（全部工具）、framework-issue-curator | 否 | 同上（但只碰 .claude/ 時，ARCH-015 本來就豁免 worktree，實際只損失收尾提示與 staging 警告） |
| 審查／分析（runtime 全部工具或有 Bash） | linux、basil-writing-critic、incident-responder、saffron、bay、clove、ginger、acceptance-auditor | 否 | 同上；唯讀派發另有 `Dispatch-Mode: readonly` 首行豁免 |
| 外掛 | general-purpose、claude、Explore、Plan、claude-code-guide | 否 | 同上 |

**名單外被略過的範圍**（main()）：關鍵字衝突掃描在名單判斷之前，不受影響；名單判斷之後的全部邏輯都被略過，包括 (1) 外部 .claude/ 阻擋、廣域 staging 警告、(2) worktree 放行時的 `_emit_worktree_complete_warning`、(4) 未用 worktree 時的阻擋。

**實際影響**：
- 287：basil 只碰 .claude/，worktree 本就不強制，實際損失只有收尾提示。
- 本專案是 Flutter 專案：sage-test-architect 寫 `test/` 時若沒用 worktree 不會被擋。這是真實缺口。
- 外部 .claude/ 路徑的阻擋（runtime 必定拒絕）對名單外代理人無效，只會延後到 runtime 才失敗。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 修法比較

| 方案 | 做法 | 新增代理人時的漂移 | 誤擋方向 | 評估 |
|------|------|------------------|---------|------|
| (1) 補入名單 | 把 sage、basil、lavender 等加入 IMPLEMENTATION_AGENTS | 新代理人預設在名單外，被靜默放行，不會有人察覺 | 不誤擋 | 漂移方向不可見，等於重演 287 |
| (2) 由 tools 推導 | 讀代理人定義，含 Write/Edit/Bash 或未宣告就納入 | 自動跟上 | 只有 oregano 例外，其餘全納入；`allowed-tools` 被 runtime 忽略，字面推導會判錯 | 判準以 Bash 為界，幾乎等於全收；外掛代理人沒有定義檔，推導不到 |
| (3) 排除式名單 | 列出唯讀代理人（Explore、Plan、claude-code-guide、oregano 等），其餘一律強制 | 新代理人預設被強制；誤擋時阻擋訊息可見，且可用首行宣告豁免 | 名單外的審查派發若未宣告 readonly、prompt 又沒寫路徑，第 4 支會阻擋 | 漂移方向可見，但審查與研究派發的誤擋量大 |
| (4) 依目標路徑判定（選定） | 名單只決定「沒寫路徑時要不要擋」；有具體非 .claude/ 目標（prompt 或票的 where）時，不論代理人類型都要求 worktree。收尾提示與外部 .claude/ 阻擋移到名單判斷之前 | 不依賴名單完整性，新代理人寫產品檔時自動受管 | 只有寫了非 .claude/ 路徑且沒用 worktree 時才擋，研究或審查派發通常不帶這類路徑 | 選定 |

### 選定 (4) 的理由

- 寫入風險來自「要改的檔在共用 checkout 的哪裡」，不是代理人的名字。用身分做判準時，名單一漂移，防護就靜默失效（287 的實例）。用路徑做判準，判定依據就是寫入目標本身。
- 同 hook 已有 `_resolve_path_classification`（prompt 路徑加上票的 where，L1–L3），不必新增推導來源。
- 現行 6 名實作代理人保留「沒寫路徑也要 worktree」的嚴格行為，既有測試的語意不變。
- 收尾提示（270.3.4）和外部 .claude/ 阻擋都與代理人類型無關，搬到名單判斷之前即可涵蓋 287 的情境。

**排除**：(1) 的漂移方向不可見；(2) 的判準以 Bash 為界，失去鑑別力，且 `allowed-tools` 會導致字面誤判；(3) 的誤擋成本落在高頻的審查派發上。
