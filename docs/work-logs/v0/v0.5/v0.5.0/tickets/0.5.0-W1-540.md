## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

畫面逐一從假資料接到真實資料（0.5.0-W1-114.18 UC Flow、114.25 節點詳情、Domain 視圖）的過程中，寫成「待真實資料整合後再處理」的註解沒有綁定承接票。真實資料接上之後，這些延後條件已經成立，但無人回頭處理。後果分兩種：

- 功能缺口靜默存在：規格定義的狀態在真實資料下不可達。
- 註解誤導讀者：註解宣稱畫面仍讀假資料。

### 影響範圍

範圍是 lib/screens 的 node_detail、uc_flow、gap_report 與 lib/components/swimlane_grid。逐處結論見 Solution。

- 已驗證：節點詳情的部分損壞態與重新整理的 partial 分支，在真實資料下不可達。
- 未驗證：斷點資料要由哪一層產出，交給 0.5.0-W1-540.1 分析。

### 相關 Error Pattern

IMP-GPD-020（本票 why 所引）：domain_view 以慣例組路徑，註解寫「待真實資料整合後才會走到」卻沒有承接票，接上真實資料後靜默失效。本票的節點詳情兩處是同型的新實例，不另建 error-pattern。

### 實驗方法

在 main（2026-10-30）上全庫搜尋，排除 lib/l10n：

```bash
grep -rnE "真實資料|真資料|假資料|fixture 時代|fixture 期|接上真|real data|fixture-driven|尚未接|待.*整合|不可達|走不到|才會走到" lib --include='*.dart' | grep -v "^lib/l10n/"
```

命中 34 處。對每一處：

1. 查該畫面的 provider 預設讀假資料還是讀 `scanRoundProvider`。
2. 讀註解描述的前提，在現行程式碼中是否還成立。
3. 查承接票：todolist 的 0.6.0 條目、open 票、已完成票的 acceptance。

### 實驗執行

各畫面的資料來源：

| 畫面 | 現況資料來源 | 依據 |
|------|------------|------|
| node_detail | `scanRoundProvider` 投影，fixture 只供測試注入 | `node_detail_providers.dart` 檔頭；0.5.0-W1-114.25 已完成 |
| uc_flow | `scanRoundProvider` 加上 `flowOf` | `uc_flow_providers.dart` 檔頭；0.5.0-W1-114.18 |

| ticket_list | `TicketListFixtures.all` | `ticket_list_providers.dart` 第 28 行 |

關鍵觀察：

- `projectNodeDetails` 建 `NodeDetailFixture` 時沒有傳 `damagedFields`。lib 內唯一讀取它的地方是 `node_detail_screen.dart` 的 `isPartial`，所以真實資料下 `isPartial` 恆為 false。
- `node_detail_screen.dart` 的 `_refresh` 只做 `File.existsSync()`，存在就設為 `NodeDetailReady`，沒有重新解析。SPEC-003 §3.6〈重新整理的三分支〉的「檔案存在但解析有斷點 → partial」分支因此不可達。
- `test/` 內沒有任何測試引用 `eventOutsideUc`。
- `gap_report_screen.dart` 的 flow 類已透過 `ucFlowFocusProvider` 交出 stepId，`uc_flow_screen.dart` 依 `focus.stepId` 定位步驟。
- `swim_lane_layout.dart` 把同一步驟放在同一欄、各泳道最多一個節點，所以「每欄至多一節點」由結構保證。
