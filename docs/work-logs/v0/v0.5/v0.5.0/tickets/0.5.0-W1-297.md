### 問題根因

`ticket track commit` 的拒絕訊息與文件把所有拒絕當成同一類「命令失敗」。`track-command.md`〈Fallback 條件〉寫「僅當本命令因故失敗或不可用時，才降級為精確 git add + 核對 + 裸 git commit」，`bash-tool-usage-rules.md` 規則七的預設關係段與 `agent-dispatch-template.md` 的 STAGING_PHRASE_AGENT 用同一句（"only if `ticket track commit` fails or is unavailable"）。三處都沒有分開「環境性失敗」與「判準性拒絕」。判準性拒絕是命令在執行它的保護職責，走 fallback 就等於繞過。fallback 端的守衛 `bare-commit-guard-hook.py` 只在並行期比對 staged 內容與**其他活躍派發**的 files，不比對本票 where.files；所以只要超出範圍的檔案不在別人的宣告裡，就照樣放行。非並行期則只有 WARN。

### 拒絕類型盤點（`track_commit.py` 的 `execute_commit`；lib 層在 `git_ops.py` 的 `commit_files_isolated`）

| # | 拒絕類型 | 位置 | 訊息原文（節錄） | 性質 | 可否走 fallback | 理由 |
|---|---------|------|----------------|------|----------------|------|
| R1 | ticket 不存在 | execute_commit 開頭 `load_ticket` | `ErrorMessages.TICKET_NOT_FOUND` | 輸入錯誤 | 否，先修正 ID | fallback 不需要 ticket，走了等於提交一筆無歸屬的 commit |
| R2 | --worktree 不是合法 git 目錄 | `_resolve_repo_root` 回 None | `--worktree {worktree} 不是合法的 git 目錄（git rev-parse --show-toplevel 失敗），拒絕提交` | 輸入錯誤 | 否，先修正路徑 | 路徑錯誤時，fallback 一樣會提交到錯的地方 |
| R3 | worktree 內提交票面 | `if worktree and own_md_inputs` | `的票面不可在 worktree 提交：票面由主 repo CLI 寫入並自動提交，worktree 內的副本是舊版本……請從輸入移除票面，只提交產品檔。` | 判準（防票面倒退） | **禁止** | 用 fallback 在 worktree 裡 add 舊票面，正好造成這道拒絕要防的倒退 |
| R4 | where.files 沒有宣告寫入路徑（ANA 另附 NOTE） | `if not normalized_declared and non_own_inputs` | `的 where.files 未宣告任何寫入路徑，無法判斷提交範圍是否合法，拒絕提交`（ANA 另附 `::write` NOTE） | 判準（範圍未宣告） | **禁止**，停手回報 PM 補 where | 屬範圍檢查。程式註解記錄過「本 session 已有兩個代理人各自誤判並繞道」 |
| R5 | 範圍外 | `_out_of_scope_files` 非空 | `以下檔案不在 ticket where.files 宣告的寫入範圍內，拒絕提交：` + 範圍外清單 + 宣告範圍 | 判準（越界寫入） | **禁止**，停手回報 PM 補 where 或移除檔案 | 281.5 實例就是這一類。這道檢查本來就是用來攔越界寫入的 |
| R6 | 目錄展開後沒有變更 | `_expand_directories` 為空 | `宣告範圍內的目錄底下無任何變更檔案，無可提交內容，拒絕提交` | 無內容 | 不適用 | 沒有東西可提交，走 fallback 也一樣是空的 |
| R7 | 只提交共用檔的本票行，但缺主路徑 | `if not normalized_input` 分支兩則 | `worktree 模式下只提交共用檔的本票行需要主路徑……` / `……票面 {own_md} 不存在於 {repo_root}` | 判準＋輸入 | 否，依訊息改用連同產品檔一起提交，或回主 repo 執行 | fallback 會整檔 add 共用 append 檔，正是 `_split_shared_append_files` 要避免的夾帶 |
| R8a | 隔離索引的 git 步驟失敗（rev-parse／read-tree／add／write-tree／commit-tree） | `commit_files_isolated` 各步 `return {"status":"failed"...}` → `提交失敗：{error}` | git stderr 原文 | 環境 | **可以**（lock 類先短暫重試） | 這是 fallback 的本意：工具壞掉，範圍判準本身已經通過 |
| R8b | 提交範圍自我驗證失敗 | `out_of_scope = changed - set(expected_changes)` | `提交範圍自我驗證失敗，預期 [...] 實得 [...]（範圍外 [...]）` | 判準（實得 diff 越界） | **禁止**，停手回報 | 這代表工具內部的不變式被打破，可能是 CLI 缺陷，fallback 會把異常掩蓋掉 |
| R8c | update-ref CAS 被拒或撞鎖 | `_describe_update_ref_failure` | 依該函式描述（HEAD 被他方前進或鎖殘留） | 環境（並行競爭） | **先重跑本命令**，持續失敗才走 fallback | HEAD 前進後重跑通常就能成功；fallback 在同一個視窗內會遇到規則七的過期 index 風險 |
| R9 | empty（rc=0） | status=="empty" | `檔案內容與 HEAD 相同，無需提交（空 tree 短路）。若變更實際發生在 linked worktree 但未帶 --worktree……` | 非拒絕 | 不適用 | 應補 --worktree 重跑，不是走 fallback |

歸納：能走 fallback 的只有 R8a，以及持續失敗的 R8c，兩者都是隔離索引機制本身的環境故障，範圍判準已經通過。判準性拒絕（R3、R4、R5、R8b）一律停手回報。輸入錯誤（R1、R2、R7）修正輸入後重跑本命令。

### 對照：prompt 約束當下有效，但是靠記憶維持的防線

今天 0.5.0-W1-282 與 0.5.0-W1-276.2 的派發 prompt 明寫「範圍拒絕即停手回報」。兩位代理人遇到 R5 後都停手回報，由 PM 補 where 後提交，沒有繞過。281.5 的 prompt 沒有這句，代理人就走了 fallback。兩相對照，決定代理人行為的是 PM 這次有沒有在 prompt 寫上那句話，命令輸出與文件都沒有給出這個界線。這種防線靠 PM 每次記得寫，強度和 PM 的記憶一樣。

## 重現實驗結果
### 實驗方法

用唯讀的方式觸發兩類判準性拒絕，命令會在 commit 之前就拒絕。目標是不在任一票寫入範圍內的 `README.md`，所以不會真的產生 commit。前後比對 `git rev-parse HEAD`，確認沒有提交。fallback 守衛端只讀 `bare-commit-guard-hook.py` 的程式碼與 docstring，沒有實際執行 git commit。

### 實驗執行

命令一：`ticket track commit 0.5.0-W1-297 -m probe -- README.md`（ANA 票，where.files 全為唯讀）

```
[ERROR] Ticket 0.5.0-W1-297 的 where.files 未宣告任何寫入路徑，無法判斷提交範圍是否合法，拒絕提交
[NOTE] 本票為 ANA 型，where.files 預設唯讀（用於標記影響面，非寫入意圖）；若確有寫入需求，請於該路徑後加 ::write 標記，例如：path/to/file.py::write
rc=1
```

命令二：`ticket track commit 0.5.0-W1-281.5 -m probe -- README.md`（281.5 補 where 後的狀態）

```
[ERROR] 以下檔案不在 ticket where.files 宣告的寫入範圍內，拒絕提交：
  - README.md
宣告範圍：
  - .claude/hooks/hook-dispatch-registry.json
  - .claude/hooks/parallel-claim-audit-hook.py
  - .claude/hooks/session-context-guard-hook.py
  - .claude/hooks/tests/test_completion_hooks_exit75_failure_event.py
  - .claude/lib/bash_tool_response.py
  - .claude/skills/ticket/hooks/handoff-cleanup-hook.py
  - .claude/skills/ticket/hooks/post-ticket-lifecycle-hook.py
rc=1
```

實驗後 `git rev-parse HEAD` = `2f8d9e04bc37ac00b7b6d6584aa30009112183c5`，與 session 起點的 HEAD（2f8d9e04b）相同，確認沒有提交。

守衛端（閱讀程式碼）：bare-commit-guard 的 docstring 寫「並行條件觸發（.claude/dispatch-active.json 有活躍派發才啟用）」、「並行期 DENY + 非並行期 WARN」。放行判準 `_staged_scope_is_safe_for_bare_commit` 驗證的是 staged 內容與**有宣告範圍的活躍派發**之間不相交，沒有任何一處讀取「本次提交所屬 ticket」的 where.files。

### 實驗發現

- 已驗證：R4、R5 的訊息只說「拒絕提交」，沒有指示下一步。R5 會列出宣告範圍，但沒有寫「不得改走 fallback」或「請回報 PM 以 set-where 補宣告」。讀者只拿到「命令失敗」這個訊號，與文件裡的 fallback 條件「本命令因故失敗」字面吻合。
- 已驗證：fallback 路徑上沒有任何機制比對本票 where。範圍外的檔案只要不在其他派發的宣告內，並行期一樣放行；非並行期只有 WARN。
- 未驗證：R8c 的訊息字面。這不影響結論，因為 R8c 本來就歸在可以 fallback 的那一側（重跑後仍失敗才走）。
