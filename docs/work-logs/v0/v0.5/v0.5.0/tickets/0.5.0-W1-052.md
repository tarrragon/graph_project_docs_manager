# Execution Log

## Task Summary

分析 PreToolUse 守衛 deny 路徑本身拋例外時經 run_hook_safely 以 exit 1 放行的失敗語意

---

## Problem Analysis
### 問題根因

`run_hook_safely`（`.claude/lib/hook_logging.py`）捕獲 main 的任何 Exception，回傳 `EXIT_DENY if fail_closed else EXIT_ERROR`，預設 `fail_closed=False` 即 exit 1。CC runtime 的 PreToolUse 只有 exit 2 觸發阻擋，exit 1 是非阻塞錯誤、工具照常執行。多數守衛的 deny 決定以「print 一段 permissionDecision=deny 的 JSON 再 return 0（或 EXIT_BLOCK）」表達；決定本身是記憶體中的值，輸出動作（`emit_hook_output` 內的 `print(json.dumps(...))`）才是讓 runtime 看見 deny 的唯一管道。輸出動作拋例外時，deny 決定尚未送達即被丟棄，例外上浮到 `run_hook_safely` 轉成 exit 1，結果是放行，且與「守衛判定無需攔」在 runtime 端同形（#97 的 fail-open 無訊號特徵）。

次要根因：部分守衛（如 `bash-edit-guard-hook.py`）在 main 內自帶 `except Exception: return 0`，例外根本到不了 `run_hook_safely`，同樣放行（exit 0）。因此單改 `run_hook_safely` 涵蓋不到這類守衛。

### 影響範圍

已驗證事實（本 session 實測）：
- `.claude/hooks` 下 `run_hook_safely(` 使用檔 114，`fail_closed=True` 檔 3（`bash-git-protected-branch-guard`、`branch-verify`、`workspace-wipe-guard`），與票面查證一致。
- 以 settings.json 註冊的 PreToolUse 腳本為準，守衛的 deny 輸出路徑見 Solution 盤點表；JSON-deny 且經 `emit_hook_output` 者 9 支、直接 print JSON deny 者至少 2 支（presence-detection、proposal-evaluation-gate）加 ticket 系統下 3 支（acceptance-gate、agent-ticket-validation、ticket-path-guard，路徑在 `.claude/skills/ticket/`）；其餘為純 exit 2 + stderr。
- 失效必須是輸出動作拋 Exception。實測 stdout 關閉（`>&-`）時 `sys.stdout` 為 None，print 為 no-op 而不拋例外，ascii 編碼因 `json.dumps` 預設 ensure_ascii 亦不拋；故自然觸發面是 BrokenPipe / ENOSPC 類 OSError，頻率低，嚴重度為「守衛靜默失效」。

未驗證假設：BrokenPipe 在真實 CC runtime 下是否會發生（runtime 是讀端，讀端先關閉才會發生）；`/dev/full` 實測被沙盒拒絕（Operation not permitted），故 OSError 以 monkeypatch 重現，非真實 OS 故障。盤點表以腳本啟發式 + 逐檔 grep 產生，直接 print 守衛清單為候選，須由 .3 實作時重跑確認。

### 相關 Error Pattern

- #97（框架 issue：hook 執行前提不成立與正常執行同形，含 fail-open 放行無訊號）：本項為其 deny 路徑實例，關係＝引用。
- PC-V1 系列與 IMP-048（stderr 顯示為 hook error）：兜底寫 stderr 為預期行為，與 IMP-048 的「已處理路徑勿寫 stderr」不衝突——deny 輸出失敗屬未處理的真失敗。
- 本地 error-patterns 無對應 deny-output-failure 條目；是否升級為 error-pattern 由 .2（DOC）的規範段承接，不另建。

## 重現實驗結果
### 實驗方法

`git clone --no-hardlinks` 主 repo 到 scratchpad（`<scratchpad>/clone`），`CLAUDE_PROJECT_DIR` 指向 clone，對 hook 腳本餵 PreToolUse stdin JSON，量 exit code 與 stdout。靶：`mcp-write-tool-on-text-file-guard-hook.py`（deny 後 `return EXIT_BLOCK`，無內層 except）。失效注入：包裝腳本於 `runpy` 前把 `lib.hook_io.emit_hook_output` 換成拋 `OSError("synthetic: stdout pipe broken")` 的函式。對照：同 hook 無注入（baseline）、`bash-edit-guard-hook.py`（內層 except-all）、`workspace-wipe-guard-hook.py`（fail_closed=True）。不改主 repo 的 `.claude/` 產品檔。

### 實驗執行

~~~text
--- A baseline (mcp-write-tool-on-text-file-guard)
exit=2   permissionDecision=deny
--- D emit_hook_output monkeypatched to raise
exit=1   stdout_bytes=0
[Hook Error] mcp-write-tool-on-text-file-guard failed unexpectedly. Check hook logs for details.
log: OSError: synthetic: stdout pipe broken
--- bash-edit-guard (bare cd deny, inner except-all), same injection
exit=0   stdout_bytes=0     (例外被內層 except 吞掉，連 run_hook_safely 都沒經過)
--- 非注入的自然輸出故障嘗試
stdout 關閉(>&-): exit=2（sys.stdout=None，print 無例外，deny 未送達但 exit 2 兜住）
PYTHONIOENCODING=ascii:strict: exit=2（ensure_ascii 預設，無例外）
--- 失效路徑的爆炸半徑對照（main 內注入 RuntimeError，指令為無害的 ls）
fail_closed=True 的 workspace-wipe-guard: exit=2（無害指令被擋）
預設 bash-edit-guard: exit=0（放行）
~~~

判讀：A 與 D 的唯一差異是輸出動作拋例外，結果由 exit 2（deny）變 exit 1（放行，工具照跑），此為 E2 正向對照：守衛在正常輸入下確實會 deny（A），失效注入下確實放行（D）。

### 實驗發現

已驗證：(1) deny 決定後輸出失敗，經 `run_hook_safely` 預設語意為 exit 1 = 放行，與票面主張一致；(2) 內層 except-all 守衛放行路徑更早（exit 0）；(3) `fail_closed=True` 會把守衛自身任何缺陷轉為擋下所有（含無害）工具呼叫，不可全域套用；(4) 純 exit 2 守衛（`return 2` / `sys.exit(2)` + stderr）在輸出前沒有 JSON print 步驟，只剩 stderr 寫入失敗的極低機率面。
未驗證：真實 CC runtime 下 stdout 管線中斷的實際發生率；`/dev/full` 實測被沙盒擋下（改用 monkeypatch）。

### 三案比較

| 維度 | 案 A：各守衛 deny 失效時自行 exit 2 兜底 | 案 B：lib 層 deny-in-flight（emit_hook_output 於 deny 輸出失敗時 stderr 寫 reason + SystemExit(2)；或 run_hook_safely 旗標變體） | 案 C：維持現狀 |
|------|------|------|------|
| 影響面 | 約 14 支 deny 守衛逐支改，每支 try/except | 1 個函式（hook_io.emit_hook_output）；114 支 hook 零改動，含未來新守衛 | 0 |
| 直接 print 的守衛 | 逐支改 | 需先遷移到 emit_hook_output（.3）；run_hook_safely 旗標變體可由 helper 標記，但仍要改呼叫 | 不涉及 |
| 內層 except-all 守衛 | 要逐支改 | SystemExit 不被 `except Exception` 攔截，天然涵蓋；旗標變體涵蓋不到 | 放行 |
| consumer 可攜性 | 各 consumer 自帶複本，sync 後漂移 | 改動在 .claude/lib，隨 sync-pull 擴散，consumer 無需動作 | 無 |
| hook 自身缺陷時是否擋全部呼叫 | 否（僅 deny 路徑） | 否：只在已決定 deny 之後才觸發；未決定前的缺陷維持現行 exit 1，不擴大 fail_closed | 否 |
| 副作用 | 重複樣板，易漏（同 E 類盲點） | emit 內 raise SystemExit：呼叫端若在 emit 後有必須執行的清理需用 finally；allow 路徑不受影響 | 靜默失效維持 |
| 對照：全域 fail_closed 預設翻 True | （非本三案）實測 F 對照：缺陷即擋無害 `ls`，爆炸半徑為全部工具呼叫，不採 | | |

結論：採案 B 的 emit 邊界變體（SystemExit(2)）。理由：根因是「deny 決定與其輸出之間沒有原子性」，在輸出函式邊界補原子語意即可，不必動 114 支 hook；且不碰 fail_closed 預設，故 hook 自身缺陷時不會擋下無害呼叫。案 A 用於直接 print 且無法遷移的少數例外。案 C 不採：靜默失效且與 #97 同形，成本僅一個函式。

限制：本案只治 deny 輸出失敗，守衛邏輯自身缺陷的 fail-open 仍屬 #97 共同面（由各守衛是否設 fail_closed 的既有政策決定），不在本票範圍。
