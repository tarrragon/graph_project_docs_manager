## Task Summary

分析 version-release finish dry-run 遇前移目標 ID 撞號即中止、不預覽改號，dry-run 與正式執行的行為差異

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

同一撞號輸入（0.5.0 前移票 0.5.0-W1-002，目標 0.6.0 已有 0.6.0-W1-002），dry-run 與正式執行走不同分支，兩者在 `migrate.py` 的 `_migrate_single_ticket` 內分叉：

- dry-run 分支（預覽區塊，collision 且非 force_overwrite）：呼叫 `_resolve_available_target_id` 算出改號預覽 0.6.0-W1-003，但以 `format_error(DRY_RUN_COLLISION_FAIL)` 輸出並 `return 1, None`。`version_release.py` 的 `migrate_overflow_tickets` 見 returncode 非 0 即 `print_error("前移失敗，中止")` 並 return False，finish 在 Step 0 中止，後續 preflight、文件更新、git 步驟的預覽全部看不到。
- 正式分支（collision 且非 force_overwrite）：同一 `_resolve_available_target_id` 取下一可用序號，`ticket["migrated_from"]` 記原目標，previous_ids 追加來源 ID，續行。
- 子樹分支（來源票有非終態子孫，先於上兩分支 return）：`_migrate_subtree` 的 `_subtree_preflight` 對 `collision and not force_overwrite` 一律加入 failures，無改號邏輯；dry-run 與正式皆零寫入中止。

該 FAIL 語意是 #55 comment 觀測（「finish --dry-run 不偵測碰撞、逐張印 OK」）的修法：碰撞列為 FAIL 而非 OK。修法同時加了正式執行的自動改號，兩者合起來使 dry-run 預告「失敗」而正式執行實際成功（單票）。ticket 描述中「正式執行行為未經觀測」已由本票實測補上。

### 影響範圍

已驗證（clone 實測，見重現實驗結果）：
- 單票前移撞號：dry-run rc=1 中止、無寫入；正式 Step 0 自動改號 rc=0 續行。
- 帶非終態子孫的父票前移撞號：dry-run 與正式皆 preflight 失敗 rc=1、零寫入，無改號路徑。
- 影響檔案：`.claude/skills/ticket/ticket_system/commands/migrate.py`（分支所在）、`.claude/skills/version-release/scripts/version_release.py`（`migrate_overflow_tickets` 對 rc 的處理，原樣轉印 child stdout）。
- 單票正式改號時 previous_ids 只含來源 ID（0.5.0-W1-002），migrated_from 為原目標 0.6.0-W1-002，外部引用經交叉引用改寫（輸出「已更新 1 個 Ticket 的交叉引用」）。

未驗證的假設：
- 批次內多票撞號時，dry-run 因零寫入，各票的改號預覽可能算出同一候選（未實測，列為 E2 要求）。
- finish 後續（preflight 之後）步驟在 dry-run 被中止時是否另有撞號以外的問題，因被截斷而不可見。

### 相關 Error Pattern

PC-152（ticket migrate 撞號）同族。#55 comment 觀測（finish 前移保留原序號致撞號且 dry-run 不偵測）為現行行為的來源修法；本票結論是該修法的後續缺口（dry-run 預告與正式結果不一致、子樹路徑未對等），非回歸。

### 實驗發現

已驗證：
1. 單票路徑 dry-run 預告失敗、正式實際成功續行，兩者結果相反，dry-run 無法預告正式執行。
2. 子樹路徑兩個模式都中止且無改號，與單票路徑不對等；dry-run 連預覽都不給。
3. 中止點在 Step 0，dry-run 因此看不到後續步驟。
4. 單票改號後 previous_ids 只記來源 ID，migrated_from 記原目標，不覆寫既有票。

未驗證：批次內連環撞號的 dry-run 預覽是否重複（零寫入使候選計算不看見同批前一筆預留）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 三案比較

| 案 | 內容 | dry-run 結果 | 對 previous_ids 的影響 | 對 parent／外部引用改寫的影響 | 評估 |
|----|------|-------------|----------------------|----------------------------|------|
| A | dry-run 預覽改號並 rc=0（標示將改號與預覽目標），正式自動改號並於結尾列對照；子樹路徑補改號 | 與正式一致，finish dry-run 可續行 | 不變：改號後 previous_ids=[來源 ID]，migrated_from 記原目標 | 單票沿用現行交叉引用改寫；子樹須對映射的根與子孫前綴一併用新根（mapping 以新根為前綴），子票 parent_id 指新根，外部引用依同一映射改寫；dry-run 零寫入不改任何引用，但預覽須列出將改寫的映射 | 建議。dry-run 預告等於正式結果；需補批次內預留集合避免兩票預覽同目標 |
| B | 維持現況：dry-run FAIL+預覽、正式自動改號 | 預告失敗但正式成功，且中止後續預覽 | 同 A | 單票同 A；子樹無改號故無改寫 | 預覽與結果相反，PM 仍須手動排除撞號才能走完 dry-run；不建議 |
| C | 兩者都中止並指引 `ticket migrate` 手動改號 | 與正式一致（皆中止） | 手動 migrate 才產生 previous_ids，行為取決於操作者 | 手動 migrate 逐票處理，批次與子樹的引用改寫依賴操作者順序 | 一致性佳但退回 #55 修法之前的人工流程，並廢除已實作的自動改號；不建議 |
| D | dry-run rc=0 但只 WARN（不給預覽目標） | 與正式一致但資訊少 | 同 A | 同 B（預覽不含映射） | 不能預告改號後 ID，PM 無法預先檢查引用；劣於 A |

結論：採 A，分兩張 IMP（先子樹對等，再 dry-run 預覽與結尾對照），因 dry-run 預覽依賴子樹也能算出改號映射。
