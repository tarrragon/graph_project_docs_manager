### 根因定位（讀碼，2026-10-28，框架線 511）

- **10 秒逾時**：`worktree_manager.py` 的 `_cleanup_execute` 以 `run_git_command(["worktree", "remove", path])` 呼叫，未傳 timeout，落到 `.claude/lib/git_utils.py` `run_git_command` 的預設 `timeout=10`。`subprocess.run` 逾時即殺掉 git，`git worktree remove` 正在逐檔刪除工作樹時被中斷，管理目錄（`.git/worktrees/<name>`）與 `.git` 指標檔仍在，故 `git status` 呈現全量 ` D`。同檔 `worktree add` 早已改用 `WORKTREE_ADD_TIMEOUT_SECONDS = 120`，remove 未比照。逾時與工作樹檔數（3318～6629）及本機負載（39～42）同向，10 秒不是可靠上限。
- **半刪後雙重阻擋**：(a) Guard C 是 PreToolUse Bash hook，只看「有未提交變更」，不分辨「變更全為 tracked 刪除且 HEAD 已併入 main」的半刪狀態；(b) `workspace-wipe-guard-hook.py` `_resolve_target_is_other_repo` 刻意把主 repo 的 linked worktree 視為主 repo（共用 git common dir），故 `git -C <wt> restore .` 在有活躍派發時一律被擋。linked worktree 的 index 與工作樹各自獨立，`restore .` 只動該 worktree；守衛的真正風險對象是「正被代理人使用的 worktree」，而非所有 linked worktree。
- **鎖**：cleanup 全程無 lock 處理；`git worktree remove` 遇鎖直接失敗。鎖由 Claude Code 平台以「claude agent」原因加上，TaskStop 後不釋放屬平台行為，框架只能偵測與回報。
- **rc 不一致**：第一例 rc=0、第三例 rc=1。`_cleanup_single` 路徑回傳 `0 if success else 1`，rc=0 需另查路徑（待重現確認）。

## Solution
### 結論

半刪 worktree 的成因是 cleanup 的 `worktree remove` 繼承了 `run_git_command` 的 10 秒預設逾時；半刪後重跑被 Level 1、Guard C、workspace-wipe-guard 三道擋住，所以沒有合法的清理路徑。修法以 cleanup 工具自身處理，不放寬兩道 Bash 守衛：收尾在 Python subprocess 內執行，不經 hook。主控於 2026-10-28 裁定採候選 A，並已實作、合併、實機驗證（0.5.0-W1-499.1）。
