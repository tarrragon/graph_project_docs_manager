### 主控指示（2026-10-28）

- 先分清兩種成因：(a) 平台於 session.start 不受理 `$.ui.open`；(b) `openIfConfigured` 吞例外。
- 若為 (b)：例外只寫 `$.ui.log(..., { to: 'debug' })` 違反品質基線規則 4（失敗須可見），修法須一併規劃可見性修正。
- 實機現象與可疑點見 0.5.0-W1-485.6 Test Results〈實機第 1 處〉。
### 主控提示（2026-10-28）

先區分兩種成因：(1) 平台在 session.start 不受理 ui.open；(2) openIfConfigured 吞掉例外、只寫 debug log。若是 (2)，失敗對用戶不可見，違反品質基線規則 4（Hook 失敗必須可見），候選方案須一併規劃讓失敗可見。用戶可選擇用 `claude --debug` 提供 log。
### 線索（485.6 實機第 2 處）

專案內 detached worktree（讀主 checkout 設定）啟動時看板有自動開出，主 checkout 啟動卻沒有。這表示成因 (a)「平台一律不受理」不成立，或至少不是在每個 session 都成立，所以重點轉向 (b) 或主 checkout 特有條件。主 checkout 特有的條件包括：git worktree list 多筆且含 locked 代理人 worktree、並行 session 多、load 高。詳見 485.6 Test Results〈實機第 2 處〉。
### 用戶回覆（2026-10-28）

- 第 1 處判定「沒開」前等了多久：不記得
- 第 1 處的終端機寬度：和 debug 那次差不多寬，所以 (d) 放置判定的可能性降低

### 時序細拆（debug log）

`git worktree list` 在 03:28:01.846 結束，ui.open 在 03:28:10.869 placed，中間約 9 秒只做了 `readProjectConfig`（一次 `$.fs.read`）。負載高時，worker 的檔案讀取與排程延遲占了主要耗時，再加上 git 的 5.5 秒；從 session 啟動到 Pane 出現，延遲都落在 `openIfConfigured` 的前置讀取上。
## 重現實驗結果
### 實驗：主 checkout 以 `claude --debug` 啟動（2026-10-28 03:27，用戶操作）

結果：看板**有自動開出**。debug log（`~/.claude/debug/e4d5b9bc-….txt`）的時序：

| 時刻 | 事件 |
|------|------|
| 03:27:52.872 | plugin.register line-board admitted |
| 03:27:54.164 | /board listed |
| 03:27:54.623 | session.start settled in 1034ms（`openIfConfigured` 以 void 背景執行，不在這段耗時內） |
| 03:27:56.496 → 03:28:01.846 | `git worktree list` 耗時 **5474ms**（之後輪詢為 0.2–2.7s） |
| 03:28:10.869 | `ui.open line-board (unasked, 116 columns): placed` |

- 從 session.start 到 Pane 出現共約 **16 秒**。全檔沒有「line-board 啟動檢查失敗」，也沒有其他 ui.open 結果（只有這一筆 placed）
- 平台會對「unasked」（非使用者要求）的 ui.open 做放置判定，並記錄欄寬

### 發現

- 已驗證：設定成立時，主 checkout 可以自動開出 Pane；成因 (a)「平台在 session.start 不受理」不成立
- 已驗證：本次沒有吞例外的紀錄，所以第 1 處失敗未必是成因 (b)
- 未驗證，兩個候選：
  - (c) **延遲**：`openIfConfigured` 要等 `git worktree list`（高負載下 5s 以上）與設定讀取完成，才呼叫 ui.open，本次延遲 16 秒。第 1 處若是在 Pane 出現前就判定「沒開」，會被記成失敗
  - (d) **放置判定**：ui.open 屬 unasked，平台依欄寬判定是否放置；第 1 處的終端機若較窄，可能被拒絕放置，而本次 116 欄被接受
- 不論哪一個：`openIfConfigured` 的例外只寫 debug log 仍違反品質基線規則 4（主控指示），修法須一併處理

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

- 排除 (a) 平台不受理：實證為主 checkout 曾 placed
- 排除 (d) 欄寬放置判定：用戶確認兩次寬度相近；這只是旁證，未做窄視窗實驗
- 成因最可能是 (c) 延遲：`openIfConfigured` 要等 `git worktree list` 與 `$.fs.read` 完成，才呼叫 `ui.open`，高負載下實測要 16 秒；第 1 處無法確認等了多久，所以與 (c) 相容
- (b) 吞例外本次未發生；但例外只寫 debug log，畫面上看不到，違反品質基線規則 4，須修

### 修法（spawn IMP，--parent 本票）

1. 縮短延遲：session.start 先以 `$.session.root()` 讀設定（主 checkout 的 root 就是 mainPath，不需要 git），設定成立就立刻 `ui.open`；只有在 root 讀不到設定時，才走 `findCheckouts` 取主 checkout 再讀一次（worktree session 情境）
2. 失敗可見：`openIfConfigured` 的 catch 改為使用者可見的管道（`$.ui.log` 送 transcript，或 `/board` 開啟時顯示上次啟動檢查失敗的原因），不只寫 debug
3. 測試：補「root 有設定時，不呼叫 git 就先開 Pane」的鑑別測試（規則 E1／E2：比對有設定與無設定的呼叫序）；補「啟動檢查失敗時有可見輸出」的正向對照測試
4. 實機：修完後重驗 485.6 AC1，以 `claude --debug` 確認 ui.open 的時刻接近 session.start

### Spawn 落地確認

- 修法 1–4 合為一張 IMP（同檔 register.tsx／readers.ts，職責單一：啟動開 Pane 路徑）
