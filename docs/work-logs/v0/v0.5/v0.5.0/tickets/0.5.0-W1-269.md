### 實測（2026-10-14，HEAD f24f6f47d 之後）

1. pre-test-hook（stdin 餵入）：`uv --directory .claude/skills/worktree run pytest tests/a.py`、兩檔、加 `-q 2>&1 | tail -5` 皆 deny；同形改為 `tests/test_a.py` 皆 allow。
2. pytest 收集行為：`/tmp/pyexplicit/a.py`（內含一個 `test_one`，檔名不符 test_*.py）以命令列明確指定執行 → `1 passed in 0.05s`。確認 pytest 對明確指定的檔案不套 python_files 樣式。
3. 閘門端：同一 argv 經 `run-with-timeout.py 120 --` 執行時被判 heavy，排在他方 hooks 全套件（holder pid 89722，15:36:49 開始）之後，超過 Bash 前景 120 秒轉為背景，最終完成。單檔執行因此多排隊一輪全套件時間。

結論：誤判方向為多擋（封堵端 deny、閘門端排隊），不會漏擋；影響限於非 test_ 命名的明確測試檔。

### 實地紀錄：他方全套件被本缺陷佔用名額（2026-10-14，派發方回報）

派發方快照輪（HEAD f24f6f47d）跑 worktree 全套件時被名額閘門排隊，log 原文：

    run-with-timeout: 等待名額：持有者 pid=91926 cwd=/Users/mac-eric/project/graph_project_docs_manager 命令=uv run --quiet --with pytest pytest /tmp/pyexplicit/a.py -q -p no:cacheprovider 開始=2026-10-14 15:42:57 load=47.91/40.19/36.60；已等待 0 秒
    run-with-timeout: 取得名額，已等待 3.0 秒

持有者是本票實測用的單檔探測命令（明確指定、檔名不符 test_*.py）。多擋的代價不只落在單檔執行者，也會讓他方真正的 heavy 命令排隊。本例只等 3 秒，因為單檔很快結束；若該檔本身耗時，他方的等待時間會等同於它的執行時間。
