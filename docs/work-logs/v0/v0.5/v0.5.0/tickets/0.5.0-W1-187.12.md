## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 處置（九項發現）
1. 零終止斷言涵蓋範圍：攔截器清單改為 _SPIED_ROUTES（subprocess.run/Popen/call/check_call/check_output、os.system/popen/kill/killpg），逐項參數化對照 test_interceptor_catches_route。
2. 常數 AUTO_KILL_THRESHOLD 改名 LIMIT_THRESHOLD，hook 與測試同批改。
3. 上限警告改寫：含上限分鐘數（LIMIT_THRESHOLD // 60 換算）、不自動終止理由、開頭標籤「[已達上限]」與 15 分鐘一級不同。
4. 兩條指令各佔一行、絕對路徑（project_dir 推得，shlex.quote）、第二條的執行判準寫成一句。
5. 門檻分支改為 _classify_duration 由高到低回傳 (level, action, message)，共同出口只記錄一次（limit 用 warning，其餘 info）；stderr 輸出仍僅 limit。
6. 對照測試直接對攔截器做，不複製原始碼、不以註解為錨點；舊的 mutated-source 測試已刪除。
7. 測試檔新區段註解不含票號。
8. 註解與警告改寫為波及其他 session 與其他專案。
9. action 讀取端查核：見下。

### action 值讀取端查核
查法：在專案根（排除 .git、worktrees、hook-logs、node_modules）grep -rnI "limit_warning|auto_kill|test-duration-history|test-monitor"；另 grep auto_killed（舊值）。結果：test-monitor.json 與 test-duration-history.jsonl 僅有寫入端（test-timeout-pre.py 寫開始時間、post-test-hook.py 寫結果與 action）；無任何程式讀取 action 欄位。舊值 auto_killed 與 limit_warning 僅出現在 .claude-backup-20260903-122115 備份、本票 187.2 的 md 與 PC-BAL-002 路徑表（只列檔名）。現有 history 檔 21 筆 action 僅 normal 20、warning 1。結論：無讀取端，改名無下游影響。限制：只搜了本 repo，未搜其他 consumer 專案。

### 自檢結果
- 本 session 未實地觸發 PostToolUse hook 的 30 分鐘上限路徑（不可能等 30 分鐘）；以單元測試呼叫 check_test_timeout 代替，監控檔時間戳為人工構造。liveness（hook 在真實 session 中被呼叫）與失敗語意（真實 stderr 在 Claude Code 中的呈現）均未驗證。
- 紅燈說明：四條新途徑的對照紅，是暫時從 _SPIED_ROUTES 移除這四項後，測試的成員檢查斷言失敗（斷言在實際呼叫前停下，避免真的呼叫 os.kill）；並非觀察到呼叫未被記錄。
- 測試中保留字串 AUTO_KILL 僅在 test_no_obsolete_constant_name 的反向斷言。
