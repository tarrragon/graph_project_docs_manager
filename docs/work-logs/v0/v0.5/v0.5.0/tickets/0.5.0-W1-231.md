### 實機驗證票（驗收第 4 項）

**開票條件**（任一成立即由 PM 開一張）：

1. 一批合併中有任一票的 `where.files` 觸及 runtime surface（verification-framework 既有判準：`lib/presentation/`、`lib/main.dart`、平台整合層）——該批合併後開一張，取代每張開發票各自執行的實機驗收
2. 版本發布前固定一張（承接 version-release 的 on-device 套件要求）
3. CI 的 integration_test 紅燈且歸因於 runner 環境而非程式時

**執行方式**：PM 以 `/verify`、`/run` 驅動 app 觀察 runtime 行為（實機驗證屬 PM 職責）；需要編譯或執行 integration_test 時經 `run-with-timeout.py`，該類命令判為 heavy，自動排入名額閘門，同一時間全機只有一份編譯。

**與 CI 的分工**：可自動化的 integration_test 由 CI macOS runner 承接（以驗收第 3 項實測結論為準）；實機驗證票承擔 CI 無法覆蓋的部分——人眼觀察、平台權限與檔案系統互動、需用戶環境的流程。

條文落地於 0.5.0-W1-231.4。
