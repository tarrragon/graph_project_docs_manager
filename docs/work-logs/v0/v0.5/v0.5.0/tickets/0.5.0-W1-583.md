### 判準與實作方案（2026-10-31，L39；待主控核可後建 IMP 子票）

**判準**：只用兩個程式可讀的輸入，不依賴 AI 判斷或回報。

1. 用量：M6 的 `percent`（`tokens / window`），由該 session 自己的 line-board plugin 量測。
2. 持有狀態：看板已讀到的票狀態。該線現行佇列中有沒有 `in_progress` 的票。

| 狀態 | 條件 | 依據 |
|------|------|------|
| 待 compact | 用量 ≥ T_compact，且該線持有 `in_progress` 的票 | 票做到一半，還需要脈絡。compact 保留摘要，清除就要重讀票面 |
| 待 clear | 用量 ≥ T_clear，且該線沒有 `in_progress` 的票（目前的票已 completed、下一張還沒 claim） | 位在票與票之間，接手點已在票面，清空的成本最低。compact 要花時間，實測 44–57 秒 |
| （不標） | 用量低於門檻；或線已收線（收線走既有的「請用戶關閉」） | — |

- 主控不標「待 clear」，只會標「待 compact」，因為主控長駐（multi-session-orchestration 1.15.0）。
- 門檻初值：T_clear = 40%，T_compact = 60%，兩者都是常數。依據是本 session 兩次手動 compact 前的量：446,269 與 330,894 tokens，compact 後回到 31k–33k。第一張 IMP 實測 `window` 後再校準（N ≥ 5 筆，記錄分布）。T_clear 定得比較低，是因為在票與票之間清除幾乎沒有損失。
- compact 剛完成時，`tokens` 會消失，直到下一次回應才回來。這段期間不標，避免把「剛壓縮」誤判成低用量。

**寫入與讀取**：

- 寫入：每個 session 的 line-board plugin 掛 `session.measure` hook。`changed` 含 `context` 時，寫入 `<主 checkout>/.claude/hook-logs/line-board/context/<sessionId>.json`，內容為 `{ sessionId, tokens, window, percent, measuredAt }`。
- 讀取：看板 refresh 時讀這些檔，以 sessionId 對上存活的 session，pid 已結束的檔略過。
  - 「各 session」列加上 `｜ctx 62%`。
  - 線群組標題的 session 狀態加上 `待 compact` 或 `待 clear`，用要人處理的洋紅色。
- `line_status` 每條線補一個用量欄位。

**IMP 子票規劃**（主控核可後以 `--parent` 建立）：

| 子票 | 內容 |
|------|------|
| IMP-1 | plugin 掛 `session.measure` 寫用量檔；實測 `window`、`percent`，以及 compact 後 `tokens` 消失的行為（N ≥ 5），校準門檻 |
| IMP-2 | 看板讀用量檔，判定待 clear／待 compact 並顯示（各 session 列、線標題）；含 E2 正向與反向對照 |
| IMP-3 | `line_status` 補用量欄位；line-continuity.md 補判讀與接續動作 |

585 的「compact 完成」與「已恢復開工」也用同一個用量檔與 `session.measure`，設計見 585 票面。
