## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
修改：lib/git_command_parse.py 新增 classify_parse_cause（None=tokenize 失敗、全 via_scan=僅掃描命中）、explain_parse_cause 與兩段說明文字（單一來源，與 details 〈scan 的誤判情境與改寫方式〉一致：加引號，或把 git 放命令位置）；_Unparseable 路徑的 command cannot be parsed safely 由 warning 降為 debug。四支守衛（bare-commit、tracking-schema-json-staleness、domain-import-lint、workspace-wipe）的阻擋與提醒訊息依成因附說明；staleness 與 domain-import 新增 classify_commit_command（is_commit_command 簽章不變）；workspace-wipe 僅在阻擋路徑重解析一次以補理由行。判定邏輯與擋或提醒處置不變。

不違反 quality-baseline 規則 4：無法解析是判定結果（find_git_invocations 回傳 None 由呼叫端處置），不是 hook 失敗；會阻擋的守衛自有 stderr 訊息，且 lib 仍寫 debug 日誌檔。

實地觸發（本 session，scratchpad 暫存 repo，HEAD 版 before 與工作樹版 after，經 hook-dispatcher --group PreToolUse:Bash 餵 payload，CLAUDE_PROJECT_DIR 指向暫存 repo，非並行期）：
- 輸入 `git commit -m "unclosed`：before 提醒文案為「因未閉合引號等原因無法安全解析」；after 附「原因：未閉合引號，或命令結構…無法解析；請檢查命令引號是否配對…」。
- 輸入 `find . -exec git commit -m x \;`：before 仍寫「未閉合引號等原因…請檢查引號是否配對」（找錯方向）；after 三支各附「git 出現在非命令位置…改寫方式：把 git 字樣加上引號…或把 git 放在命令位置直接呼叫」。
- 輸入 `git commit -m x | bash`（觸發 lib _Unparseable）：before stderr 有 11 行「command cannot be parsed safely: pipe into shell」（9 支 hook 各一至二次）；after 為 0 行，只剩各守衛自己的提醒。
liveness：兩輪輸出皆來自真實 dispatcher 子行程 stderr，before 與 after 內容不同，證明是被測程式碼產生。失敗語意：不變（bare-commit 並行期 fail-closed 阻擋，非並行期放行並提醒；staleness 與 domain-import 同；workspace-wipe fail-closed）。
環境註記：暫存 repo 缺 skills 目錄，dispatcher 對 skills 下 hook 印「hook 檔案不存在」，與本票無關。
