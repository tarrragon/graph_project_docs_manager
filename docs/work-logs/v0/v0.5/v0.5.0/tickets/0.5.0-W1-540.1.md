## 重現實驗結果

### 實驗方法

1. 在 lib/corpus 找出所有「欄位缺失或損壞」的資料：`lost_fields.dart`、`parse_outcome.dart`、`parse_failure_event.dart`，並查 `lostFields` 在 lib 內的呼叫端。
2. 對照四份規格：SPEC-001 §6〈部分損壞〉的進入條件、SPEC-003 §3.6〈重新整理的三分支〉、SPEC-006 FR-04（含〈範圍外〉表與 D5）。
3. 查破洞報告中 `parse-failure` 類破洞項的指向型別，確認使用者能不能從破洞報告進入節點詳情。

### 實驗執行

- `lostFields(...)` 在 lib 內只有一個呼叫端：`parse_failure_event_builder.dart`。也就是說，只有解析失敗、沒拿到可用 frontmatter 的檔案會算 `lostFields`。有可用 frontmatter 的節點，不會計算缺少哪些完整性集合的鍵。
- `ParseFailureEvent`（EVT-CORPUS-003）描述的是「未進入圖譜」的檔案（parse_failure_event.dart 的 `FlowParseFailedEvent` 文件說明「UC 仍是節點，與 ParseFailureEvent 的『未進入圖譜』事實分立」）。節點 id 取自 frontmatter，所以解析失敗的檔案沒有 id，不在 `GraphBuiltEvent.nodes` 裡。
- SPEC-006 FR-04 規定 `salvagedFields` 本版一律為空清單，不做部分救回。〈範圍外〉表寫明「YAML 損壞檔的部分欄位救回」不做，理由是語料中只有一件 YAML 錯誤，演算法沒有樣本可以校準。
- `gap_report_projection.dart` 的 `_carrierItem` 沒有設定 `pointerType`，預設為 `none`，主操作是開啟原始檔。所以使用者無法從 `parse-failure` 破洞項進入節點詳情。
- SPEC-001 §6 的「部分損壞」：
  - 進入條件寫「該節點解析時發生斷點」。
  - 顯示「可讀欄位 + 損失欄位標示『因檔案損壞而無法讀取』」。
  - 操作含「跳轉破洞報告（欄位級損壞標記）」。

### 實驗發現

已驗證：

- 在真實資料下，圖譜中的節點都有可用 frontmatter，沒有任何一層產出這些節點的欄位級損壞資料。部分損壞態的資料來源不存在。這不是投影漏接，而是上游沒有產出。
- 有欄位損失資料（`lostFields`）的對象是解析失敗的檔案。但這些檔案不在圖譜中，沒有節點 id，破洞報告也不會帶使用者進入節點詳情。而且依 FR-04，它們的「可讀欄位」恆為空，因為不救回任何欄位。
- 結論：SPEC-001 §6〈部分損壞〉與 SPEC-003 §3.6 的 partial 分支，和 SPEC-006 FR-04「不做部分救回」在現行規格下互相牴觸。0.1 的 fixture 示範了一個真實資料產生不出來的狀態。

未驗證：

- 完整性集合缺鍵的節點（有 frontmatter 但缺欄位）在五個語料專案中有多少，沒有量測。若選下方方案 B，需要先量測。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 分析結論

斷點資料不是由投影漏接，而是上游根本不產生。部分損壞態牽涉規格語意：「斷點」指什麼、由哪一層判定。這需要用戶裁決，依主控指示，選項交主控轉達。

`_refresh` 的三分支中，「檔案存在且解析完整 → 正常」與「檔案仍不存在 → 維持」兩支與 partial 的定義無關，但重新整理必須真的重新解析，才能分辨三支。所以 partial 的定義先決定，重新整理的實作票再依定義建立。

### 候選方案（待用戶裁決）

| 方案 | 「部分損壞」的定義 | 資料由誰產出 | 要改的規格 | 利 | 弊 |
|------|------------------|------------|-----------|----|----|
| A：解析失敗的 carrier 檔 | EVT-CORPUS-003 的對象：落在 carrier 內但 frontmatter 解析失敗的檔案 | 已存在（`ParseFailureEvent` 帶 `lostFields`、`nodeType`） | SPEC-001 §6：「可讀欄位」改為路徑與推定型別。`parse-failure` 破洞項要能進入節點詳情（新增指向型別）。節點詳情的定位方式要能用路徑，因為這些檔案沒有 id | 資料現成；「因檔案損壞而無法讀取」與「跳轉破洞報告」的文字和行為都對得上 | 可讀欄位幾乎是空的（FR-04 不救回）。節點詳情要接受「不在圖譜中的節點」，要動定位模型與 SPEC-003 §3.4 跳轉 |
| B：缺完整性集合鍵的節點 | 有可用 frontmatter，但缺少該型別完整性集合中的鍵 | Corpus 對可用檔也計算 `lostFields`，經 Graph 帶到 `LightNode` | SPEC-006 新增可用檔的 `lostFields` 產出。SPEC-001 §6 文案「因檔案損壞而無法讀取」改為「缺少欄位」一類。若要保留「跳轉破洞報告」，SPEC-007 需新增對應的破洞類別 | 節點仍在圖譜中，定位模型不變；可讀欄位是真的有內容 | 語意從「損壞」變成「不完整」；要動 Corpus、Graph、Diagnostics 三層與三份規格；語料中的實例數未量測 |
| C：0.x 移除部分損壞態 | 部分損壞態與重新整理的 partial 分支標為不可達，等 FR-04 部分救回實作時再啟用 | 不需要 | SPEC-001 §6 與 SPEC-003 §3.6 註明不可達，並綁定觸發票（承接 FR-04 部分救回的票） | 改動最小，規格與實作一致；不為沒有樣本的狀態建資料管線 | 損失一個使用者可見的狀態；畫面上的 partial 分支與 fixture 測試要退場或改標不可達 |

### 建議

C。理由：

- FR-04 不做部分救回，是 2026 年對五個語料專案量測後的決定（YAML 錯誤僅一件）。A 的「可讀欄位」在這個決定下恆為空，B 則把語意改成另一件事。
- C 讓規格和實作一致，等救回真的實作時再啟用 partial。

C 與另外兩案無論選哪一個，重新整理都要改成真正重新解析，至少要能分辨「仍不存在」與「存在且解析完整」兩支。
