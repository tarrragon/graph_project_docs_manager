## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### S1 失敗判定來源

- `.claude/skills/wrap-decision/hooks/wrap-decision-tripwire-hook.py` 的 ConsecutiveFailures 偵測器：`detect()` 先比對 `event["tool_name"] == sd.tool_matcher or "Task"`；`_is_failure()` 讀 tool_response，status 為 failed 或 error，或 tool_response 的 JSON 字串含關鍵字（error、exception、failed、timeout）即判為失敗。
- `.claude/config/wrap-triggers.yaml` 的 consecutive_failures：`tool_matcher: "Task"`、threshold 2。
- settings.json：tripwire 註冊於 PostToolUse（無 matcher，全工具）與 UserPromptSubmit；沒有註冊 PostToolUseFailure。

### 實測（本 session，2026-10-15 04:03）

- 以不存在的 subagent_type 發出一次 Agent 派發，平台回 `Agent type ... not found`。
- 時間窗：Bash A 於 04:03:56.908 記下 T0，接著派發，再以 Bash B 查 liveness。
- PreToolUse 的 Agent 類 hook（agent-dispatch-validation、agent-prompt-length-guard、agent-ticket-validation、dispatch-staging-phrase-guard、worktree-commit-before-dispatch 等）在 T0 後各有 1 筆，表示這次呼叫有走到 hook 流程。
- PostToolUse 的 Agent 類 hook（dispatch-count-guard、agent-dispatch-logger、active-dispatch-tracker、dispatch-identity-bind）在 T0 後 0 筆；tripwire 在 Bash B 執行當下只有 1 筆，即 Bash A 自己的 PostToolUse。
- 結論：失敗的 Agent 呼叫不觸發 PostToolUse，與 Bash 一致，應走 PostToolUseFailure；因 PostToolUseFailure 目前只註冊 matcher Bash，本次無法直接觀察。
- 平台實際的工具名為 Agent：settings.json 中派發相關 matcher 皆為 "Agent"，hook 日誌也記到 `"tool_name":"Agent"`。

### 判定：S1 已失效，原因有兩個，彼此獨立

1. tool_matcher 為 Task，平台送來的是 Agent，所以 detect() 永遠在第一行返回，任何派發都不會計入。這屬於 IMP-V1-004 的同類問題：hook 內部的工具名守衛因平台改名而靜默早退。
2. 即使改成 Agent，派發失敗也不會送到 PostToolUse，失敗事件根本到不了 S1。

另一個風險：如果只把 tool_matcher 改成 Agent，前景代理人的 tool_response 是完整報告，報告中常出現 error、failed 等字樣，會被關鍵字比對誤判為失敗，S1 因此誤報。背景派發的 tool_response 只是「已啟動」訊息，不會反映代理人之後的成敗。

### 修法方向（落地為 0.5.0-W1-281.4.1）

- tool_matcher 改為 Agent，並相容 Task。
- 失敗來源改為 PostToolUseFailure：在 settings.json 為 tripwire 加 PostToolUseFailure、matcher Agent 的註冊；收到失敗事件即計為一次失敗。PostToolUse 的成功派發則重置計數。
- 移除對報告全文的關鍵字比對，或只在結構化 status 欄位存在時才採用，避免誤報。

### Spawn 落地確認

| 規劃項目 | 落地 |
|---------|------|
| S1 改認 Agent、改以 PostToolUseFailure 為失敗來源、移除報告全文關鍵字比對 | 0.5.0-W1-281.4.1（--parent） |

### 自檢結果

- 實測以時間窗加 liveness 判讀，並列出 Pre 與 Post 兩側的 hook 作對照，排除「呼叫根本沒進 hook 流程」的可能。
- Bash B 之後的 liveness 會被後續命令汙染，結論只採用 Bash B 執行當下的觀測。
