## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
實作：record_dispatch 增 run_in_background 欄位（True/False/None）；active-dispatch-tracker-hook 由 PostToolUse(Agent) tool_input 擷取（bool 才採用，缺席記 None）；dispatch_tracker 新增 is_fifo_fallback_candidate（null、未結束、run_in_background 非 False），hook 候選計數與 mark_oldest_active_null_agent_id_entry_turn_ended 共用；無候選時既有路徑落入墓碑。舊記錄/None 按背景處理。
限制：背景 null 記錄與同步 Stop 在狀態檔中無法區分（同步自身記錄 Stop 時未寫入），故「僅有一筆運行中背景 null 記錄 + 同步 Stop」仍會 FIFO 標記；本修正消除的是候選為同步記錄的誤標（ANA 重現情境）。

Phase 4：重構需要 否；技術債務 無（上述限制為案 C 固有）；品質 A；結論：無需重構。

- **缺失項**：修法未涵蓋 ANA 重現的情境。069 Problem Analysis 的重現是「狀態檔只有一筆運行中的 null 記錄（他人的背景派發），送入無匹配的同步派發 Stop，該筆被誤標」。被誤標的是背景記錄；本分支把同步記錄排除出候選，背景記錄仍是候選，該情境照舊誤標。執行者回報的「已知限制」即此情境。
- **觸發位置**：`is_fifo_fallback_candidate` 的過濾對象是記錄而非 Stop。同步派發的記錄在 PostToolUse 才寫入（晚於自身 Stop，且寫入時即消費墓碑），運行中的同步 null 記錄在實務上幾乎不存在，新增的正向對照測試構造的是一個不會出現的狀態。另一點：省略 `run_in_background` 的同步派發記為 None，按背景處理。
