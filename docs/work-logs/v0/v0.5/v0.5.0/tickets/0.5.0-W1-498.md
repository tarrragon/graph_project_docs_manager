## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 發現者更正與證據（L18，2026-10-27，以 git log 核對）

更正 why 欄「兩次撞上」的第一次：479.1／479.2 那次的 W3-007 警告，指的並**不是** dispatch-log commit。實際情形如下：

- 479.x 兩筆 dispatch-log（7f698427f、168076c0b）在派發前已一起推送（3a1f1f70b..168076c0b）。
- 警告中落後的 2 個 commit 是 3dcd94911「479.1 claim status」（479.1 代理人派發後執行 claim 產生）和 e6c279c30「349 append-log Solution」（主控寫入）。這兩筆都發生在派發 479.1 之後、派發 479.2 之前。
- 所以第一次屬於另一種形態：前一張票的代理人 claim，或並行 session 的寫入，讓 origin 落後；它只觸發 W3-007 警告，沒有被硬擋。

本機制的實例目前只有一次（486.1）：

- PM 推送到 746dfcbca 後執行 `ticket track dispatch 0.5.0-W1-486.1`，產生 6a6605638「486.1 dispatch dispatch-log」。
- 派發被 worktree-commit-before-dispatch-hook 擋下，訊息為「目標票 0.5.0-W1-486.1 的 md 尚未同步至 origin/main」。
- 再推送一次（746dfcbca..f0ec1080a，其中含並行 session 的 f0ec1080a）後派發成功。
- 疑點：這次 dispatch 前已推送過一次，而 479.x 兩張是「dispatch → 推送 → 派發」，並沒有被擋。差別在 486.1 的順序是「推送 → dispatch → 派發」，dispatch 放在推送之後。因此本缺陷的觸發條件應寫成「推送之後才跑 dispatch」，而不是「每次 worktree 派發」。

### 主控重判（2026-10-27，依 L18 更正）

- L18 以 git log 核對後更正：同機制實例只有 486.1 一次，順序是「推送 → dispatch → 派發」；479.x 的順序是「dispatch → 推送 → 派發」，未被擋，當時的 W3-007 警告來自派發後才產生的 commit，與 dispatch-log 無關。
- 重判：守衛的攔截是正確行為（dispatch 寫入的票面變更確實尚未推送）。框架問題第二條判準「根源在 .claude/ 通用資產」不成立為缺陷，至多是預設行為可改善：dispatch 成功輸出沒有提示「接著推送再派發」（opinionated-default 規則的信號）。
- 範圍收窄：本票只評估 dispatch 成功輸出與 worktree 派發守衛的阻擋訊息是否指出正確順序；兩者皆已指出則以「非缺陷」關閉，未指出則 observe 進 #54 或 dedup 判定的 issue 後關閉。#47 回歸的假設撤除。優先級維持 P3。
