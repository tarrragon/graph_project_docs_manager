## Solution

### 結論

主案採 PostToolUse hook，事件掛兩處：Bash 經 `hook-dispatch-registry.json` 的 `PostToolUse:Bash` 群組，Edit／Write／MultiEdit 註冊在 settings.json。比對規則與 lanes.ts、sessions.ts 共用一份 JSON 測試案例。

### 決策 1：hook 事件選 PostToolUse，不選 commit 前

| 候選 | 涵蓋 ticket CLI 寫入 | 涵蓋 Edit 寫入 | 提示時機 |
|------|------|------|------|
| PostToolUse（Bash + Edit/Write/MultiEdit） | 是：比對 command 含 `ticket track` 且帶協調票號 | 是：比對 tool_input.file_path | 寫入當下，模型還在同一個動作的脈絡裡 |
| commit 前（PreToolUse `git commit`） | 否：ticket CLI 以隔離索引自行提交（`ticket track commit`／auto-commit hook），不經過 `git commit` 的 Bash 呼叫 | 是 | 晚，而且可能根本不觸發 |

判定協調票的方式與看板相同：讀 `.claude/project-integration/multi-session.json` 的 `coordinationTicket`，不另以「含〈看板讀取約定〉」判定，避免 hook 與看板認定不同的票。設定檔不存在或不成立時，hook 不輸出任何內容（沒有使用多 session 協調的專案不受影響）。

內容一律在工具執行後**從磁碟重讀票檔**，不解析 tool_input 的字串，這樣 append-log、Edit、Write 三種路徑的處理方式一致。

### 決策 2：兩項檢查的範圍（依實驗修正主控方向）

| 檢查 | 範圍 | 提示文字 |
|------|------|------|
| 1 括號名稱 | 只檢查最後一行票序不是 `（無）`、且有括號的線。比對對象是 cwd 在本 repo checkout 路徑（`git worktree list`）下的狀態檔 name，精確相等 | 「L<n> 括號內『<原文>』目前沒有同名 session：若是附註，請移到票序；若 session 已結束而線仍在，可忽略」 |
| 2 線結束未標記 | 最後一行票序中的票號全部解析得到、且狀態都是 completed／closed，票序不是 `（無）` | 「L<n> 佇列票皆已終態，若線已結束請寫（無）」 |

實驗證實狀態檔只存在於存活的 session，所以檢查 1 不檢查已結束的線；提示寫兩種可能原因，因為交接中的線比對不到名稱是合法的。檢查 2 中有任何票號查不到票檔時，該線不提示（無法判定）。

輸出：受眾是模型，經 `emit_hook_output("PostToolUse", additional_context=...)`；一律 exit 0、不阻擋（規則 4）。異常寫 stderr 與日誌檔。

### 決策 3：Python hook 與 lanes.ts 共用測試案例

- 測試案例的唯一來源：`.claude/skills/line-board/tests/queue-line-cases.json`。每筆包含 `text`（協調票全文片段）、`prefix`、預期 `lanes`（線號、session、票序是否為 `（無）`、票號清單）。
- TS 端：lanes.test.ts 新增一組測試，逐筆以 `parseLanes` 跑並斷言與預期相同。claude-code/testing 能否 import JSON 尚未驗證；不能的話，改用 fixtures.ts 匯出相同內容，並由 Python 測試斷言 fixtures 匯出的內容與 JSON 一致（漂移守衛）。實作票自行實測後擇一，記錄在 Solution。
- Python 端：hook 的解析函式以同一份 JSON 跑相同斷言。
- E2：案例中包含正向對照輸入（括號帶附註、全終態未寫 `（無）`），斷言會提示；正常寫法則斷言不提示。
