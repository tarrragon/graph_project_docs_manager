# Execution Log

## Task Summary

分析 hook 於每次工具呼叫啟動大量 uv 程序的累計負擔與降低方式

---

## Problem Analysis
### 問題根因

每支 hook 是一個獨立的 `uv run --quiet <hook>.py` 程序（uv 父程序 + Python 子程序），單支約 0.1 CPU 秒，其中約 0.086 秒是每支都重複支付的固定成本：直譯器啟動約 30ms、`lib` 套件匯入約 45～65ms（`lib/__init__.py` 一次匯入 hook_base／git_utils／hook_logging／hook_io／config_loader，含 yaml、subprocess、logging、json、dataclasses）、`git rev-parse --git-dir --git-common-dir` 約 13ms。hook 本體邏輯平均僅約 0.013 秒。單次工具呼叫觸發的支數乘上這段固定成本，就是累計負擔：一次 Bash 呼叫觸發 43 支，合計約 4.2 CPU 秒。

`uv` 本身不是成本來源：同一個帶 PEP 723 依賴的空腳本，`uv run` 為 28ms CPU、直接 `python3` 為 31ms，差距在量測解析度以內。uv 的代價在別處：每支 hook 多一個 13 條執行緒的父程序常駐到 hook 結束，RSS 約 12～18MB，所以 `ps` 看起來是「大量 uv 程序」。

228.1（`_find_project_root` 行程內快取，已在量測 HEAD 內）只消除同一程序內的重複 rev-parse。實測每支 hook 仍各自呼叫 1 次（PreToolUse/Bash 27 支共 27 次 git，其中 26 次是同一條 rev-parse），跨程序的重複不在 228.1 的射程內。

### 影響範圍

- 已驗證：一次 Bash 呼叫 PreToolUse 27 支、PostToolUse 16 支（含不帶 matcher 的 1 支）；一次 Edit 約 30 支；settings.json 註冊的 hook 全部經 `uv run` 啟動
- 已驗證：多 session 下 hook 平均吃掉約 0.8 個 CPU 核心，約占 8 核整機的 10%；尖峰時一秒觸發 48～52 次，瞬間約 5 個核心
- 已驗證：hook 不是 load 35～45 的主因。同時段整機 CPU 使用率 75～100%（sys 27～37%），長駐的非 hook 程序在 5 秒區間內合計約 300%（kernel_task 57%、WindowServer 33%、VS Code 30%、Chrome 約 50%、avconferenced + VTEncoder 約 30%、OrbStack 16%、Prowl 17%），另有他線在 worktree 跑 pytest 單程序 63%。hook 並行程序數的時間平均約 2.6～4.8，對 load average 的貢獻上限約 4～5
- 未驗證：sys% 偏高與 trustd（8%）／opendirectoryd 有多少來自 hook 程序的 fork/exec 與簽章檢查；本次的逐支 rusage 不含這部分，實際負擔比估計值略高
- 未驗證：liveness 紀錄只涵蓋有呼叫 `mark_hook_entry` 的 hook，觸發率是下界

### 實驗發現

已驗證：

1. 累計負擔約為「每秒觸發數 × 0.1 CPU 秒」，多 session 下約 0.8 核心，約占整機 10%；尖峰一秒內約 5 核心，同時有 30～40 個程序、RSS 約 0.5～1GB
2. 單支成本的八成以上是每支重複支付的固定成本（直譯器 + lib 匯入 + rev-parse），本體邏輯平均約 0.013 秒
3. `uv` 不增加可量測的 CPU，只多出一個 13 條執行緒、約 12～18MB 的父程序
4. 延遲匯入 `lib` 的收益有限：多數 hook 需要 hook_logging（liveness 進入點）與 hook_io，那幾個模組加起來已和現行相當
5. hook 不是 load 35～45 的主因，而是排在多個長駐程序之後的一個貢獻者

未驗證：fork/exec 帶來的核心與 trustd 成本占比；不在 liveness 涵蓋範圍內的 hook 觸發數。

## Solution
### 分析結論

累計負擔來自「支數 × 每支重複支付的固定啟動成本」，不是 uv，也沒有單一熱點 hook。能有效降低的只有把同一事件的多支 hook 放進同一個程序執行，讓固定成本只付一次。其他候選要嘛量到的收益接近零，要嘛會被合併方案涵蓋。

用戶裁定的前提「hook 是 load 一直卡在 35 左右的主因」與實測不符：hook 約占整機 CPU 10%、對 load 的貢獻上限約 4～5，其餘來自長駐程序與他線的測試執行。合併方案仍值得做，因為一次 Bash 呼叫要 4.2 CPU 秒、尖峰會瞬間拉起 30～40 個程序，這會隨 session 數線性放大；但它不會單獨把 load 降到 8 核以下。
