### 問題根因

（實驗票，本欄記錄待驗證的假設與實驗設計；主控於 2026-10-21 與用戶討論後寫定）

**用戶的假設**：Haiku 對小字、細微對齊、相近顏色的辨識比高階模型差。這個弱點反而能當成 UX 的壓力測試：Haiku 一眼找不到主要操作、讀不出目前狀態，就表示對比、尺寸或層級設計可能不足。做法類似設計上的「瞇眼測試」與低視力的無障礙檢查。

**和 465 的差別**：

| 票 | Haiku 的弱點代表什麼 | 正解 |
|---|---|---|
| 465 | 漏判，是缺點 | 畫面有沒有渲染缺陷 |
| 466 | 訊號，是想要的效果 | 人一眼能不能找到、讀懂 |

兩者方向相反，所以分成兩張票。

**成立條件**：要先驗證「代理效度」，也就是 Haiku 的失敗和人的失敗是不是同一回事。主控提出三個疑慮：

1. **失敗機制不同**：
   - 模型看圖會先縮圖，再切成區塊編碼，看不清是因為解析度。
   - 人看不清的原因不同，主要是視覺層級、格式塔分組、注意力分配。
   - 因此 Haiku 可能在人很容易看懂的密集文字上失敗；反過來，它會平均讀過所有文字，不會像人一樣忽略橫幅，也就可能在人會漏看的地方成功。
2. **送圖解析度會改變結果**：圖送進 API 後可能被縮圖。尺寸不固定的話，量到的會是傳送流程的差異，而不是 UX 的好壞。
3. **觀察者較弱 vs 資訊較少**：Haiku 失敗，可能是模型能力較弱，也可能只是圖被縮小、資訊變少。要把兩者分開，需加一組確定性降質對照：把同一張圖模糊、縮小或轉灰階後交給 Opus 作答。

**提問形式**：一律用任務式提問，而不是問「畫面對不對」。例如：「要開啟專案，該點哪個編號？」「目前的掃描狀態是什麼？」「錯誤訊息在哪裡？」選項用 Set-of-Mark 編號，做法與 465 相同，並附「找不到」一個選項。

### 用戶補充裁示：Haiku 是反指標（2026-10-21）

用戶原話：「把 Haiku 當成反指標去檢驗，我期望他犯錯，而不是期望他做對」。

**由此推得的設計要求**：反指標有沒有用，不取決於它錯得多不多，而取決於它錯的地方是否落在真正的問題上。如果錯誤是隨機雜訊，好畫面和壞畫面上錯得一樣多，這個指標就沒有鑑別力。因此要做三件事：

1. **成對變體**：每題同時準備兩個版本。一個是原設計，一個是刻意把 UX 做差的版本，例如字縮小、對比降低、主要操作埋進次要位置。分別量 Haiku 在兩個版本上的失敗率。壞版本的失敗率要明顯高於原設計，Haiku 的錯誤才算有資訊量。這和規則 E1 的「傳與不傳的產物必須不同」是同一個結構。
2. **雜訊底線**：已知良好的畫面上，Haiku 的失敗率要夠低。否則所有畫面都會被標記，指標失去用處。
3. **一致才算失敗**：同一題在多次取樣、選項順序打亂之後都失敗，才算 Haiku 判定失敗。偶發的一次失敗屬於取樣雜訊。

**同一框架可延伸到 464**：Haiku 在 C1 條件下的單 token 選擇，就是「自動駕駛式的直覺答案」。如果 464 量到 Haiku 的選擇和用戶否決的選項高度重合，就可以把它當作 WRAP 反向框架檢查的輸入，標出「這是直覺答案，要特別質疑」。是否成立要看 464 的結果，本票不處理。

### WRAP 完整模式評估（主控，2026-10-21，用戶要求）

**錨點**
- 客戶：本 App 的使用者，也就是在 macOS 桌面管理專案文件的開發者。用戶本人既是設計者，也是主要使用者。
- 核心目標：0.5 的產品進度（畫面接真資料、破洞報告）。466 屬研究線，不能擠壓產品線。
- 評估單位：跨畫面的模式，不針對單一畫面下結論。

**Step 0 資料充足度**：判定「不足，中風險」。缺口有兩項：
1. 用戶最在意的 UX 性質尚未指明，例如可找到性、可讀性、層級、資訊密度。
2. 正解來源有結構性偏差，詳見下方 R 第 1 點。

處置方式：不阻擋，在實驗設計中補對照（見下方「補充設計」）。

**W 擴增選項**：先寫下底層假設，再列方案。

假設 X：Haiku 的失敗與人的辨識困難相關。

除了真實的 UX 顯著性不足，Haiku 失敗還可能來自另外四個原因，實驗必須能把它們分開：

| 替代原因 | 機制 | 分離方式 |
|---|---|---|
| 送圖縮放 | API 端縮圖使小字消失，與設計無關 | 固定像素尺寸，並記錄實際送出尺寸 |
| CJK 字形 | 繁體中文小字在縮圖後比拉丁字母更快糊掉 | 同一畫面切 zh 與 en 兩種語系各跑一次（`lib/l10n/` 已有 `app_zh.arb`、`app_en.arb`） |
| 標記遮蔽 | Set-of-Mark 的編號框蓋住文字 | 編號放在元件外緣，並加一組無標記的對照，改問「描述位置」 |
| 提問措辭 | 失敗來自問句不清，不是畫面本身 | 每題用兩種等價問法 |

方案三類涵蓋：

| 類別 | 方案 | 能量測什麼 |
|---|---|---|
| 改造既有 | flutter_test 內建的 `meetsGuideline`：`textContrastGuideline`、`androidTapTargetGuideline`、`iOSTapTargetGuideline`、`labeledTapTargetGuideline`（SDK `flutter_test/lib/src/accessibility.dart` 已有，本專案測試目前沒有使用） | 確定性量測文字對比、點擊目標尺寸、標籤，成本為零，可放進 CI |
| 零工具 | 用戶自己做瞇眼／模糊測試，或請一位沒看過畫面的人做走廊測試 | 人的真實辨識，但成本高、不可重複 |
| 新增工具 | Haiku 弱觀察者（本票）、確定性降質後交 Opus 作答 | 語意層的可找到性：哪個是主要操作、層級是否清楚、標籤是否看得懂 |

**反向思考**：「Haiku 看不清小字與低對比」這項訊號，大部分已能由 `textContrastGuideline` 確定性量到，而且量得更準、成本為零。所以 Haiku 獨有的價值不在對比與尺寸，而在準則量不到的語意層，例如：主要操作是否突出、狀態是否一眼可讀、相似元件是否容易混淆。結論：本票先跑內建準則；Haiku 的評估範圍限定在準則量不到的項目。

**R 現實檢驗**
1. **設計者的知識詛咒**：用戶是設計者，早就知道每個東西在哪裡，判定「人一眼能否找到」時會偏向「容易」。這會汙染代理效度的校準基準。處置：正解改以「構造」為主，成對變體中的壞版本本來就比較差；用戶判定只用在真實畫面，並在報告中註明偏差方向。
2. **基本率**：據主控所知，視覺語言模型做 UI 啟發式評估的研究，結論大致是與專家中等一致、誤報偏多。具體數字未經查證，不作為判讀門檻。
3. **試水溫**：先做 3 個畫面的成對變體，每個條件取樣 5 次，看壞版本的失敗率是否高於原設計。沒有差異就停下並結案，不擴大到 15 題。

**A 拉開距離**
- 機會成本：研究線佔 1 條框架線，不阻擋產品線。先做試水溫，可以把投入限在小範圍。
- 悖論檢查（Goodhart 效應）：如果把它當成合併閘門，設計會往「讓 Haiku 通過」的方向調整，例如到處加大標籤、增加視覺雜訊，反而傷害真正的使用者。處置：只產出候選問題，不作為閘門，最後由人判定。

**試水溫規格**（取代上文〈補充設計〉第 2、3 點與〈用戶補充裁示〉中無數值的描述）：

1. **變體目錄先凍結再取樣**：3 個畫面 × 3 種壞版本類型，共 9 組成對題。目錄寫入本票並提交後，才能開始任何 Haiku 取樣。試水溫不通過時，依絆腳索結案，**不得修改變體後重跑**。Alternatives 視角指出，否則會一路調到出現差異為止。
2. **壞版本只動語意層**：壞版本必須仍通過 0.5.0-W1-466.1 的準則，也就是對比與點擊尺寸都合格，不准縮字、不准降低對比。三種類型取自外部分類，每個變體標注它破壞了哪一項：
   - 主次操作的視覺權重相同
   - 狀態只靠顏色表達
   - 相關元件失去鄰近分組（違反格式塔鄰近原則）
3. **設計約束**（防止交互作用，不增加格數）：
   - **無標記為主**：可找到性題以無標記圖為主條件，模型回答區域。原因是 Set-of-Mark 的編號框本身就把元件標出來，會抵銷「主要操作被埋起來」這類壞版本的效果。
   - **問句避開標籤字面**：每題問句不得與畫面上的標籤文字共用詞。否則模型只要比對字串就能答對，層級好壞都答得出來。
   - **編號每次重新隨機**：使用編號版時，每次取樣都重新隨機分配編號並重新繪製。編號是畫在圖上的，只打亂文字選項沒有作用。
   - **單 token 代碼**：所有選項用單一 token 的代碼表示，「找不到」固定為代碼 0；無法解析的回覆另外計數，不算失敗。

4. **固定條件**：1280×800、zh、送圖前在本地縮到固定像素；記錄實際回傳的模型 ID 與 temperature（固定 1.0）。開工前查證並記錄 Haiku 與 Opus 的圖片解析度上限，兩者不同時取較小值。
5. **題級失敗**：每題每版本取樣 K=5 次，至少 4 次失敗才算題級失敗。答錯與選「找不到」都算失敗，兩者分開記錄。

6. **通過條件**（以下全部成立）：
   - (a) 「壞版本失敗、原版本通過」的成對題至少 4/9，且反向的成對題為 0。
   - (b) 有差異的題涵蓋至少 2 種壞版本類型。

7. **製作者隔離**：變體目錄由主控依上述分類撰寫，再由 0.5.0-W1-466.2 的執行者產生。凍結之前，兩者都看不到任何 Haiku 輸出。
