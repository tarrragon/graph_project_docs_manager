# Execution Log

## Task Summary

評估兩個無產品讀取方的掃描結果欄位應保留、接上讀取方或移除

---

## Problem Analysis
### 問題根因

462 對齊 EVT-CORPUS-001 負載段時，以 lib 呼叫點查讀取方，發現 `CorpusScanResult.parseErrors` 與 `CorpusScanResult.schemaAmbiguousNodes` 沒有產品層的消費方。破洞已改由 EVT-CORPUS-003／004／005 產生，兩欄位是否仍需保留沒有人判斷過。

### 查證結果（2026-10-21，main 6dc6c9be2 之後）

**寫入點**（皆在 `lib/corpus/corpus_scanner.dart`）

| 欄位 | 型別 | 寫入點 |
|------|------|--------|
| `parseErrors` | `List<ParseError>`（`path`、`outcome: ParseOutcome`，`reasonText` 與 `parseOutcomeReasonText` 共用對照） | 掃描迴圈的 `addFailure`：結果不是「可用」的檔案**一律**加入，之後才依 carrier 命中分流，命中者另組 EVT-CORPUS-003 |
| `schemaAmbiguousNodes` | `List<SchemaAmbiguousNode>`（`path`、`candidateTypes`） | 節點判型時 `id` 互斥被打破的可用檔案（0.3.0-W3-534 加入） |

**lib 內讀取方**

- `parseErrors`：只有掃描器自己的掃描完成日誌讀 `result.parseErrors.length`（`failureCount`，debug log）。Graph、Diagnostics、畫面都不讀
- `schemaAmbiguousNodes`：lib 內沒有任何讀取方

**更正 462 的寫法**：EVT-CORPUS-001 負載表把 `parseErrors` 寫成「目前沒有產品程式讀取（只有測試）」，漏了掃描器自身日誌這個讀取方。已在 0.5.0-W1-459 順帶更正為「只有掃描器自身的完成日誌讀取筆數」。

**測試讀取方**

| 測試 | 用途 |
|------|------|
| `test/unit/corpus/corpus_scanner_test.dart` | C5／C9 系列斷言失敗檔記入 `parseErrors`（含 carrier 外不發事件的 C5-2、C5-6、C9-2）；FR-03 歧義檔以路徑與候選型別出現在 `schemaAmbiguousNodes` |
| `test/unit/corpus/uc_flow_block_test.dart` | flow 區塊失敗不進 `parseErrors`、不改變 `schemaAmbiguousNodes` 筆數 |
| `test/integration/corpus_it2_gap_classification_test.dart` | IT-2 以 `parseErrors` 減去已成破洞的路徑，算出「失敗但未命中 carrier」的檔案集合 |
| `test/unit/app/scan_round_test.dart`、`test/unit/screens/project_switcher_test.dart`、`test/helpers/gap_round_fakes.dart` | 只在建構 `CorpusScanResult` 時填空清單 |

**關鍵事實**：carrier 外的失敗檔（例：沒有 frontmatter 的工作日誌）不發 EVT-CORPUS-003（SPEC-006 FR-04），`parseErrors` 是這些檔案在掃描結果裡**唯一的逐檔紀錄**；守恆式只有計數，沒有路徑。`schemaAmbiguousNodes` 同理，是 FR-03「須出現在掃描結果中，不得只計數後丟棄」的唯一載體。

### 三個方向各自牽動的 SPEC-006 條文

| 方向 | 牽動條文 | 說明 |
|------|---------|------|
| 保留（寫明用途） | FR-07 描述句、FR-04 描述與驗收 #1、#3 | 規格不改；在 FR-07 或 EVT-CORPUS-001 寫明兩欄位的用途是「可追溯性與測試觀測點」，不是破洞來源。成本最低，但仍留下「無產品消費方的負載」 |
| 接上讀取方 | FR-08（破洞產生）或 SPEC-001 §5 | 例：carrier 外失敗檔、schema 歧義檔顯示在破洞報告。這會改變 FR-04 刻意的設計（carrier 外不進破洞，以免九成雜訊），屬用戶裁決範圍；歧義檔目前也沒有破洞類別 |
| 移除 | FR-04 描述與驗收 #1、#3（「記入 parseErrors」）、FR-07 描述句、FR-03 互斥被打破規則（「須出現在掃描結果中」）、EVT-CORPUS-001 負載段、`docs/spec/corpus/domain-map.md` §3 不變式（「未命中者只記入 parseErrors」）、SPEC-006 test-design C5、C9 系列 | 移除 `parseErrors` 會讓 carrier 外失敗檔完全無逐檔紀錄，IT-2 的未命中集合也算不出來；移除 `schemaAmbiguousNodes` 直接違反 FR-03 現行條文，需先改 FR-03 |

### 執行提示

結論若是「保留」以外的方向，牽涉 FR-04 的雜訊取捨或 FR-03 條文，依主控指示用 AskUserQuestion 交用戶裁決。

## 重現實驗結果
### 實驗方法

在 main（2026-10-21，ef0ca519b 之後）以 `grep -rn 'parseErrors\|schemaAmbiguousNodes' lib` 與 `grep -rln ... test integration_test` 重查兩欄位的寫入點與讀取方，並對照 SPEC-006 FR-03、FR-04、FR-07 與 EVT-CORPUS-001 負載段條文。

### 實驗執行

- lib：寫入點只在 `lib/corpus/corpus_scanner.dart`（`addFailure` 與判型的互斥檢查）；讀取方只有同檔掃描完成日誌的 `result.parseErrors.length`。`schemaAmbiguousNodes` 在 lib 內零讀取方
- test：讀取方為 corpus_scanner_test、uc_flow_block_test、corpus_it2_gap_classification_test；scan_round_test、project_switcher_test、gap_round_fakes 只建構空清單
- 規格：FR-03「這些檔案須出現在掃描結果中（相對路徑與候選型別），不得只計數後丟棄」；FR-04 驗收「不命中任何 carrier 的失敗檔，記入 `parseErrors`，但不發出 EVT-CORPUS-003」；FR-07 描述句只列 `rawNodes`、`parseErrors`

### 實驗發現

已驗證：
- 兩欄位的現況與 Problem Analysis〈查證結果〉一致，無新增讀取方
- `parseErrors` 是 carrier 外失敗檔在掃描結果中唯一的逐檔紀錄（003 不涵蓋、守恆式只有計數）；IT-2 以它算出「失敗但未命中 carrier」集合
- `schemaAmbiguousNodes` 是 FR-03 現行條文要求的唯一載體，移除即違反 FR-03

未驗證：無。是否要讓 carrier 外失敗檔或歧義檔進破洞報告（接上讀取方）屬產品取捨，本票不主張。

## Solution
### 結論：保留（並寫明用途）

兩欄位都保留。判斷依據是條文要求與逐檔可追溯性，不是「目前有沒有畫面讀它」（DOC-GPD-005）。

### 候選方案比較

| 方案 | 利 | 弊 | 判定 |
|------|----|----|------|
| 保留並寫明用途 | 不改程式與條文語意；carrier 外失敗檔與歧義檔仍可逐檔追溯；IT-2 未命中集合照常可算 | 負載中留著無產品消費方的欄位，需靠文件說明用途 | **採用** |
| 接上讀取方（例：進破洞報告） | 欄位有產品消費方 | 推翻 FR-04 刻意的「carrier 外不進破洞」以免雜訊的取捨；歧義檔目前無破洞類別，需新設計 | 不採用：無產品需求驅動，屬用戶裁決範圍，本票不主張 |
| 移除 | 負載變小 | 違反 FR-03 現行條文；carrier 外失敗檔失去唯一逐檔紀錄；IT-2 未命中集合算不出；需改 FR-03／FR-04／FR-07、domain-map 不變式與 C5、C9 測試設計 | 不採用 |

結論為「保留」，依主控指示不需交用戶裁決。
