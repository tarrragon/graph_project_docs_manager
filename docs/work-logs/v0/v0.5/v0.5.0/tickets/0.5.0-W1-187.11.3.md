## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修法
- orphan-test-procs.py：terminate_registered 在已驗證身份並送 TERM 後，領頭查無而群組仍有成員 -> 繼續送 KILL；領頭存在但啟動時間不符 -> 不送，回傳 changed_after_term，登記回報「未能終止」並計入失敗（結束碼 1）。KILL 前另驗包裝腳本未存活。清理開始時領頭不在而群組有成員者仍只列出（judge_entry 未改）。
- 登記 pgid 須為大於 1 的整數（布林、浮點、字串不接受）且不等於 os.getpgrp()，否則在 read_registry 視為損壞登記、不送訊號。killpg 的 ProcessLookupError/PermissionError 以外之 OSError 攔截並回報未能終止。
- process_start 區分「程序不存在」（None）與「查詢失敗」（CommandError）；單筆登記查詢失敗只回報該筆、保留登記並計入失敗，其餘登記與既有類別照常處理。
- 兩支腳本的 process_start 固定 TZ=UTC。登記檔名改為 wrapper-<PID>-<啟動時間>.json；暫存檔於寫入/改名失敗時清除；群組已無成員且包裝腳本未存活的登記不論範圍皆移除。
- 測試註：macOS 的 ps 對超過 PID 上限（99999）的值回錯誤而非「不存在」，測試改用已回收的真實 PID 表示不存在。

### 自檢結果
- 8 項驗收皆有對應測試且通過；修法未改 is_runner、run-with-timeout.py 既有結束碼、「疑似殘留」只顯示。
- 範圍：僅改 where.files 四個檔。

### 主線程覆核（完成後，2026-10-14）

- 群組編號驗證（實測）：於暫存目錄建立 12 種不合格的登記（0、1、負數、布林、浮點、字串、空值、自身群組編號、串列、字典）與 1 個損壞檔，直接呼叫 read_registry：有效 1 筆（合格的對照），判為無法讀取 13 筆。
- 終止函式（讀碼）：TERM 前比對領頭啟動時間；KILL 前僅在領頭存在且啟動時間不符時放棄；KILL 前重驗包裝腳本；對群組送訊號只經單一輔助函式，全檔 os.killpg 出現一處。與票面裁決一致。
- 執行者另加的保護（KILL 前包裝腳本若存活則不送）：採納。與「只終止包裝腳本已不在的群組」的保證方向一致。
- 機器狀態：覆核當下無任何測試相關程序，清理指令列出模式輸出「符合 0 略過 0 疑似殘留 0」，登記目錄為空。

未做：主線程未重跑測試檔。覆核當下 1 分鐘平均負載約 190（來源為容器服務與檔案系統事件服務，非本線程序），執行者已於負載 35 至 72 間取樣 5 次全數通過。

已知並維持：KILL 前包裝腳本存活的路徑僅有以替換查詢函式的單元測試；清理開始時即發現領頭不在而群組有成員者只列出不終止。
