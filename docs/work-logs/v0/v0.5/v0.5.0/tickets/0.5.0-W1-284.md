### SA 分析（saffron，2026-10-15）

#### 1. 實際涉及的兩支 hook 與現行判定

票面 where 只列 `bash-edit-guard-hook.py`，實際有兩支 Bash PreToolUse hook 與本議題相關（皆登記於 `.claude/hooks/hook-dispatch-registry.json`）：

| Hook | 判定邏輯（程式位置） | 對 Bash 寫檔的處置 |
|------|------|------|
| `.claude/hooks/bash-edit-guard-hook.py` | `_detect_bash_edit_patterns()`：只比對 `sed -i`／`sed --in-place`／`perl -pi`／`perl -i.bak`；`main()` 命中時 `permission_decision="allow"` + additionalContext 警告。輸出重導向、awk 重導向等 pattern 已於 W10-047.3 降級移除（函式 docstring「移除模式」段） | 只警告，不阻擋；不偵測 `cat >>`、heredoc、`printf >>`、`tee`、python `open()` |
| 同上 | `_find_bare_cd_target()` + `main()` 的 deny 分支 | 裸 cd／pushd 一律 deny（主線程與 subagent 皆然） |
| `.claude/hooks/bash-write-boundary-guard-hook.py` | `_extract_candidate_paths()` 以正則抽取 `>`/`>>`、`tee`、`sed -i`、`cp`/`mv`、`open('...')` 目標；`_find_boundary_violation()` 只在正規化後命中 `test/`、`lib/`、`*.dart` 時轉呼 `check_file_permission` | 主線程：deny。subagent：`main()` 中 `is_subagent_environment()` 為真即直接 allow；開發分支（feat/*、fix/*）亦直接 allow |

結論：對 subagent 而言，**沒有任何 hook 會阻擋 Bash 寫檔**；唯一訊號是 bash-edit-guard 對 `sed -i`／`perl -i` 的警告。

### 實驗方法

```bash

CLAUDE_PROJECT_DIR=$PWD uv run --quiet --script .claude/hooks/<hook>-hook.py < $S/p.json
```

### 實驗發現

已驗證事實：

1. `cat >>` + heredoc、python heredoc `open()`：bash-edit-guard 無輸出（直接放行、無警告）；bash-write-boundary-guard 對主線程且目標在 test/、lib/、*.dart 時 deny，對 subagent 一律 allow。
2. 目標在 `.claude/` 下（本專案 Python hook 測試所在）時，即使主線程也放行——boundary-guard 範圍只含 test/、lib/、*.dart。
3. `sed -i lib/a.dart`：bash-edit-guard 警告但 allow；boundary-guard 對主線程亦 allow——`_SED_I_PATTERN` 遇 macOS 形式 `sed -i "" expr file` 時把 `""` 後的 expr 當成路徑之前的 token，路徑抽取失準（漏放）。
4. 裸 cd 對主線程與 subagent 皆 deny。這是現行唯一會擋 subagent Bash 的路徑，270.7 的「被擋」最可能是此路徑。

未驗證假設：270.7 當次的確切命令與 deny 來源（裸 cd 或 harness auto mode classifier），票面與已查 log 無逐筆對應。

## Solution
### 結論

現行強制層對 subagent 的 Bash 寫檔完全放行：bash-edit-guard 只對 `sed -i`／`perl -i` 警告，bash-write-boundary-guard 的 `is_subagent_environment()` 分支直接 allow，且範圍只含 test/、lib/、*.dart，漏掉本專案 Python 測試所在的 `.claude/`。四個實例中三例無任何訊號，第四例（270.7）的「被擋」推定來自裸 cd 分支而非寫檔偵測。prompt 層禁令已逐字寫到 `cat >>`，仍發生 2 次，證據指向需要強制層。

### 候選比較

| 方案 | 內容 | 誤擋方向 | 繞過成本 |
|------|------|------|------|
| A 全面阻擋（路徑限定） | 擴充 bash-write-boundary-guard：移除 subagent 一律放行，改為主線程與 subagent 皆檢查；目標路徑落在 repo（或 worktree）內的追蹤原始碼區（`lib/`、`test/`、`integration_test/`、`.claude/**`、`docs/**` 中非 ticket CLI 管轄者）即 deny，`/dev/null`、`/tmp`、`/private/tmp`、`$TMPDIR`、scratchpad、`.git/` 放行 | 主要誤擋：(1) `mv`／`cp` 改名追蹤檔（需改用 `git mv`，git 命令不經重導向偵測，或以 Edit／Write 重建）；(2) scratchpad 以變數表達（`> $S/x`）——正則看到未展開的 `$S/x`，正規化後不在 repo 原始碼區前綴，不會誤擋；(3) 寫 `docs/**` 的合法 Bash 重導向極少，ticket／doc CLI 不經重導向。誤擋可觀測（立即 deny 有訊息），符合 bash-edit-guard 檔頭「可觀測性不對稱」論述 | 正則啟發式仍可被 `bash -c`、`eval`、變數路徑（`f=lib/a.dart; cat >> $f`）、python 以字串拼接路徑繞過；但四個實例全是字面路徑，皆會被擋。繞過需刻意構造，與現況「零成本」相比成本明顯上升 |

### 選定：方案 A

理由：B 的覆蓋缺口正好落在已發生的 E 線實例，C 已被四個實例反證；A 的誤擋集中在 `mv`/`cp` 改名一類，有 `git mv` 與 Edit／Write 兩條低成本替代，且誤擋是可觀測方向。

實作要點（交 children 承接）：

1. bash-write-boundary-guard：移除 subagent 一律放行；主線程沿用既有 `check_file_permission` 判定（職責邊界），subagent 改用路徑範圍判定（工具選擇邊界），兩者 deny reason 分開，subagent 的 reason 指向 Edit／Write 與 `git mv`。開發分支跳過條件是否對 subagent 保留，於實作票決定並記錄理由。
2. 範圍擴充至 `.claude/**`（306.1 實例）與 `integration_test/`；放行清單含 `/dev/null`、暫存區前綴、`.git/`。
3. 修正 `_SED_I_PATTERN` 對 macOS `sed -i "" expr file` 的路徑抽取失準（實驗發現 3）。
4. bash-edit-guard 模式 A 的 `sed -i`／`perl -i` 警告保留不變（避免兩支 hook 雙重 deny 同一命令）。
5. 測試依 `test-assertion-design-rules` E2：每種寫法（`cat >>` heredoc、`printf >>`、`tee -a`、python `open()`、`sed -i ""`）各一個應 deny 的正向對照輸入，另含 scratchpad、`/dev/null`、`git mv` 應 allow 的對照。
