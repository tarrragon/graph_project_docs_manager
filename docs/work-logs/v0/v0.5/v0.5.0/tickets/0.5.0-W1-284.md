### 補記實例（2026-10-14，0.5.0-W1-285）

basil-hook-architect（worktree 隔離派發）以 Bash 的 python heredoc 改寫測試檔，代理人回報中自述違反 PC-GPD-031。與 270.3.2 不同處：本次派發 prompt 已明寫「改檔用 Edit/Write，不用 Bash 寫檔（PC-GPD-031）」，代理人仍違反，事後才自述。顯示 prompt 層與 error-pattern 層的約束不足以阻止此行為，支持本票評估把 Bash 寫檔守衛由提示改為阻擋。內容經 PM 核對 diff 無誤，產出保留（規則 6）。

### 第三例：270.9 thyme-python-developer（2026-10-14 20:3x）

- prompt 首次明寫「程式碼修改用 Edit/Write。禁止 Bash heredoc、sed、python -c 改檔（PC-GPD-031）」（依 bb 指示，比先前只寫「禁止 python -c」更具體）。
- 代理人仍用 `cat >> <測試檔> <<EOF` 在兩個測試檔尾端附加測試，並在回報中自承違規。
- 代理人自述原因：附加前沒有先 Read 該檔，而 Edit 要求先 Read。也就是說，選 Bash 的理由是省掉 Edit 的前置條件，而不是 Edit 被拒。
- 寫入時沒有任何 hook 攔截。對照 270.7 的 thyme：當時的 Bash 改檔被 hook 擋下，代表現行攔截只涵蓋部分寫法，`cat >>` 附加不在內。
- 對 284 分析的意義：prompt 措辭從籠統改為具體之後，違規依然發生，可見只靠 prompt 約束不足；強制層的攔截範圍（是否涵蓋 `>>` 附加）應列入比較。
第四例：276.1 thyme-python-developer（2026-10-15）。prompt 逐字禁止「Bash heredoc、cat >>、sed、python -c 改檔」，代理人補端到端測試時仍以 Bash heredoc 追加內容到測試檔。這次代理人自行發現，用 git checkout 還原後改用 Edit，並在回報中自承。與第三例（270.9，cat >> 附加）同型：附加到檔尾時繞過「Edit 須先 Read」的前置條件。差別在於本例代理人有自我修正。寫入時沒有 hook 攔截。
E 線補充實例（2026-10-15）：兩次代理人在派發 prompt 已明寫「修改一律用 Edit／Write，禁止 python -c、sed、heredoc 改檔」的情況下仍以 Bash 寫檔，Bash Edit Guard 皆只警告：(1) 0.5.0-W1-314.1 代理人執行 no-op 的 sed -i（未改到檔案）；(2) 0.5.0-W1-306.1 代理人以 printf >> 追加 .claude/error-patterns/ 下的 md。第 (2) 例落在 .claude/ 框架檔，不在本票原定的產品檔與測試檔範圍內；評估阻擋範圍時建議一併納入。prompt 層的明文禁令對此類寫法沒有鑑別力，證據指向需要強制層。
### SA 分析（saffron，2026-10-15）

#### 1. 實際涉及的兩支 hook 與現行判定

票面 where 只列 `bash-edit-guard-hook.py`，實際有兩支 Bash PreToolUse hook 與本議題相關（皆登記於 `.claude/hooks/hook-dispatch-registry.json`）：

| Hook | 判定邏輯（程式位置） | 對 Bash 寫檔的處置 |
|------|------|------|
| `.claude/hooks/bash-edit-guard-hook.py` | `_detect_bash_edit_patterns()`：只比對 `sed -i`／`sed --in-place`／`perl -pi`／`perl -i.bak`；`main()` 命中時 `permission_decision="allow"` + additionalContext 警告。輸出重導向、awk 重導向等 pattern 已於 W10-047.3 降級移除（函式 docstring「移除模式」段） | 只警告，不阻擋；不偵測 `cat >>`、heredoc、`printf >>`、`tee`、python `open()` |
| 同上 | `_find_bare_cd_target()` + `main()` 的 deny 分支 | 裸 cd／pushd 一律 deny（主線程與 subagent 皆然） |
| `.claude/hooks/bash-write-boundary-guard-hook.py` | `_extract_candidate_paths()` 以正則抽取 `>`/`>>`、`tee`、`sed -i`、`cp`/`mv`、`open('...')` 目標；`_find_boundary_violation()` 只在正規化後命中 `test/`、`lib/`、`*.dart` 時轉呼 `check_file_permission` | 主線程：deny。subagent：`main()` 中 `is_subagent_environment()` 為真即直接 allow；開發分支（feat/*、fix/*）亦直接 allow |

結論：對 subagent 而言，**沒有任何 hook 會阻擋 Bash 寫檔**；唯一訊號是 bash-edit-guard 對 `sed -i`／`perl -i` 的警告。

#### 2. 四個實例為何被擋／沒被擋

| 實例 | 寫法 | 判定 | 原因 |
|------|------|------|------|
| 270.7 thyme（被擋） | 不在票面記錄；推定為 `cd <dir> && python3 - <<EOF` 類 | deny 來自裸 cd 分支，不是寫檔偵測 | 兩支 hook 對 subagent 的寫檔皆放行（見〈重現實驗結果〉）。`.claude/hook-logs/bash-edit-guard` 於 2026-10-14 有多筆 `cd .../.claude/scripts/tests && python3 - <<` 裸 cd 命中，與此推定吻合。另一可能來源是 harness auto mode classifier（非專案 hook）。兩者皆非「寫檔被識別」。此點為推定，未取得 270.7 當次 log 對應行 |
| 270.9 thyme `cat >>` | `cat >> <測試檔> <<EOF` | allow，無訊息 | bash-edit-guard 不偵測重導向；boundary-guard 對 subagent 直接放行，且 thyme 的測試檔位於 `.claude/` 下，也不在 test/、lib/、*.dart 範圍 |
| 276.1 thyme heredoc 追加 | heredoc 追加至測試檔 | allow，無訊息 | 同上 |
| 285 basil python heredoc | `python3 - <<EOF` 內 `open(...)` 改測試檔 | allow，無訊息 | 同上（`open()` 偵測只在 boundary-guard，且 subagent 跳過） |
| E 線 314.1 `sed -i` | no-op sed -i | allow + 警告 | bash-edit-guard 模式 A |
| E 線 306.1 `printf >>` | 追加 `.claude/error-patterns/*.md` | allow，無訊息 | 兩支皆不涵蓋 |

#### 3. 合法 Bash 寫檔情境清單（阻擋設計不可誤擋）

| 類別 | 範例 | 寫入目標 | 能否由命令字面辨識 |
|------|------|------|------|
| scratchpad／暫存 | `> $S/p.json`、`tee /tmp/task.log`、`mkdir -p $S` | `/private/tmp/claude-*`、`/tmp`、`$TMPDIR` | 可；但目標常以變數表達（`$S/x`），正則看到的是未展開字串 |
| 丟棄輸出 | `> /dev/null`、`2>&1` | `/dev/null`、fd | 可（boundary-guard 已排除 fd） |
| 日誌 | `PYTHONUNBUFFERED=1 pytest ... \| tee /tmp/x.log`（bash 規則六） | 暫存區 | 可 |
| git 產物 | `git commit`、`git apply`、`git checkout -- <path>`（276.1 自行還原所用） | `.git/`、工作樹 | 不經 shell 重導向，偵測天然不命中 |
| ticket／doc CLI | `ticket track append-log`、`doc validate` | `docs/work-logs/**`、`docs/**` | 不經重導向，天然不命中 |
| uv／pytest／flutter 產物 | `.venv`、`.pytest_cache`、`__pycache__`、`build/`、`flutter gen-l10n` 寫 `lib/l10n/*.dart` | 含 `lib/` | 由工具內部寫入，非 shell 字面，天然不命中 |
| hook 測試的 fixture | 測試程式在 tmp_path 建檔 | pytest tmp | 天然不命中 |
| 刻意 Bash 寫入 | `git mv`／`mv` 改名追蹤檔、`cp` 產生器輸出到 lib/ | 工作樹 | 可辨識，但屬真實寫入，需豁免通道 |

要點：合法寫入的大多數由工具內部完成、不經 shell 重導向，對「以命令字面偵測寫入目標」的阻擋天然免疫；真正會撞上的合法情境集中在「重導向到 repo 內路徑」，主要是 scratchpad 被誤寫成 repo 相對路徑、以及 `mv`/`cp` 檔案改名。
