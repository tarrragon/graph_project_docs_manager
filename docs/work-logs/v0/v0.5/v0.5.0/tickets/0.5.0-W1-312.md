## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 四層推導失敗原因
- 層1 環境變數 TICKET_ID：PM 主 checkout 與 hook 子程序皆未設定。
- 層2 dispatch-active.json：實檔為 {"dispatches": [...]} 物件，程式碼卻要求 list（isinstance(data, list)），形狀不符必落空；即使修形狀，取「最新 dispatched_at」是全域最近派發，並行派發或已結束派發時會誤判成別張票，故不修此層。
- 層3 git 分支：PM 在 main，且只認 feat/<id>，worktree 分支名為 worktree-agent-*，皆不匹配。
- 層4：以上皆失敗，日誌記 unable to derive。

### 選定修法與理由
補一層（層0）：Agent/Task 事件 tool_input.prompt 首行以 lib.ticket_id_pattern.extract_ticket_id_anchored 取票號（與 active-dispatch-tracker-hook 讀同一欄位，PostToolUse 與 PostToolUseFailure 皆帶 tool_input）。UserPromptSubmit 無此欄位，不使用。置於最前，因為它是該次事件自身的資料，比全域狀態準確。
另在 render_message 於票號為空時移除「（Ticket: ）」片段（yaml 不在 where.files，故在程式端處理），滿足 acceptance「推不出時不顯示空欄位」。這是任務所述二擇一之外的補強：層0只覆蓋 Agent 事件，S2/UserPromptSubmit 仍會推不出，故兩者並用。
apply_ticket_switch_reset 本身未改；因 Agent 事件現可推出票號，重置在該事件上開始生效。推不出時維持原行為（None 不動）。fail-open 沿用既有 main/run_hook_safely，未新增阻擋路徑。

### 自檢結果
- hook 主體只加層0與 render 清理，restrictive_keywords 未動。
- Python 3.9 相容（Optional，無 PEP 604）。
- 程式修改全用 Edit/Write。

### Phase 4 評估
重構需要：否；技術債務：發現 1 項（層2 dict 形狀不符，屬既有，未修，需 PM 決定是否建票）；程式碼品質：A；結論：無需重構。

PM 審查（2026-10-15）：通過。行為變更須知：apply_ticket_switch_reset 過去因推不出票號從未生效；本票後 Agent 事件換票時會清空 signals，不同票上的兩次代理人失敗不再累計為「連續 2 次」。此即該函式的設計意圖（不同票的失敗不屬同一卡關），接受。層 2 dispatch-active.json 形狀不符（程式要求 list、實檔為 {dispatches: [...]}）另建票追蹤。
