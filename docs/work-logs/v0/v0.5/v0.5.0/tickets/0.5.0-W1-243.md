### 交接給 0.5.0-W1-187.13.1：本票對計時與監控檔寫入點的改動

- 改動點：post-test-hook.py 的 main()，在 ticket body 寫入 gate 之後新增 gate；tool_input.run_in_background 為 True（`is True`）時 return EXIT_SUCCESS，不呼叫 check_test_timeout 與 evaluate_test_failure，只記一行 debug 日誌
- 欄位缺失或為 False：視為前景，行為不變
- 未動的寫入點：check_test_timeout 內對 test-monitor.json 的寫入（end_time、duration_seconds、status、action，以及 history 寫入）、_classify_duration；test-timeout-pre.py（開始時間寫入端）
- 未覆蓋：背景命令實際結束時的計時（無 hook 事件），由 187.13.1 或閘門承接
- 失敗語意：欄位缺失視為前景；liveness 以 PostToolUse 輸出確認
- 測試：test_foreground_command_is_timed_and_evaluated、test_background_command_skips_timing_and_evaluation、test_background_false_treated_as_foreground


### 交接補充（Phase 4 審查指出，給 0.5.0-W1-187.13.1）

- 背景命令啟動時 test-timeout-pre 仍寫入開始時間，post-test 跳過收尾，監控檔的 status 會停在 running。目前 hooks 內只有 post-test-hook 讀此檔且不讀 status，暫無實際影響；分檔設計時需決定 running 狀態由誰收尾
- 交錯情境（建議作為 187.13.1 的測試案例）：同一則訊息並行發出前景測試與背景測試，若背景命令的 pre 寫入落在前景命令的 pre 與 post 之間，前景的開始時間被覆寫，量到的時長偏短。屬每專案一份監控檔的並行覆寫問題

### Phase 4 結論（linux 審查，2026-10-14）

重構需要＝否；技術債務＝發現（上述兩項，歸 0.5.0-W1-187.13.1）；品質 A。`is True` 判斷遇非布林值時退回前景行為，屬安全退路，維持現狀；背景命令回傳只有啟動回條、無測試輸出可評估，背景測試結果經 TaskOutput 等非 Bash 工具取得，原本即不觸發本 hook，此缺口非本票引入。
