## 重現實驗結果
### 實驗方法
全部在 scratchpad 拋棄式 repo（已刪除），git 2.50.1（Apple Git-155），macOS。持鎖：git add／update-index 搭配 clean filter（filter 內 sleep 60），git 先取 index.lock 再跑 filter。終止前確認 index.lock 已存在，對 git 本身 PID 送訊號；終止後等 0.5 秒檢查鎖是否殘留、大小、lsof 持有者、index 與 HEAD 是否變動。以 PID 指名清理 filter 子行程，未用 pkill／killall。每組前 load 最高 30（首組前，低於 45），swap free 約 1.0G（高於 500M）。

|----|-----------|---|------|--------|
| A 正向對照 | git add（filter 持鎖）SIGKILL | 6 | 6 | 0 位元組、lsof 無持有者、index 與 HEAD 未變 |
| A2 | git update-index --add SIGKILL | 5 | 5 | 同上 |

### 實驗發現
已驗證：
1. 正向對照成立：寫入類 git 於持鎖時被 SIGKILL 必留 0 位元組、無持有者、index 與 HEAD 皆未變的鎖，與 164.5 兩個殘留鎖實例形態完全吻合（SIGTERM 則不留）。
2. 推翻 164.6 的「讀取路徑不留鎖」：status 預設與不帶設定的工作樹 diff，在 index 因 stat-dirty 而回寫的窗口內被 SIGKILL，8/8 留下同形的 0 位元組鎖；164.6 的 42 次為 0 是因為沒打中回寫窗口（其 fixture 未製造 stat-dirty）。
3. 抑制旗標有效：--no-optional-locks（status）與 diff.autoRefreshIndex=false（diff）皆使鎖不出現，各 8/8 為 0，故 164.6.1 補旗標方向正確。
4. uv 鏈：對外層 uv 送 SIGTERM，uv 與 python 退出，但 git 及其 filter 子行程不死，成為孤兒續持鎖；訊號不傳到 git。
未驗證：
- hook／CLI 載入來源：未現場量測。既有文件（agent-isolation-worktree.md、PC-GPD-030）記載 CLAUDE_PROJECT_DIR 恆指向主 repo，settings 的 hook 指令用 $CLAUDE_PROJECT_DIR，故 hook 載入自主 checkout；ticket CLI 的 get_project_root 在 linked worktree 內解析為該 worktree。此為文件依據，非本次實測。
- 實際 harness 逾時的訊號送法（是否為 process group、是否對 uv 之外送訊號）。
- Bash 工具逾時／使用者中斷對 git 的影響（PM 推測項，未測）。

## Solution
### 判定：縮小範圍（尚未識別單一成因）
已識別的機制：任何在持鎖窗口（寫入類 git 的整段執行；status／工作樹 diff 的 index 回寫瞬間）被 SIGKILL 的 git，必留 0 位元組、無持有者、index 與 HEAD 不變的鎖，與 164.5 殘留鎖形態吻合。SIGTERM 不留鎖。
縮小：(1) 讀取路徑並非不留鎖（推翻 164.6 結論；164.6 全為 0 的原因為推測其 fixture 未造成 stat-dirty、沒打中回寫窗口，未驗證）；(2) uv 鏈使 git 於外層被終止後成為孤兒，之後被另行 SIGKILL 的路徑存在，但「誰送出 SIGKILL」未識別；(3) 164.6.1 的旗標補強對 status 與 diff 的鎖抑制有效。
仍未識別：164.5 兩個鎖當時是哪個行程被誰以 SIGKILL 終止（Bash 逾時、使用者中斷、session 結束為候選，未測）。
下一步：觀測而非再實驗——讓 git-index-lock-cleanup 類 hook 發現殘留鎖時記錄當下的 cwd、鎖 mtime 與近期被終止行程線索（併入 164.4.1），累積真實發生的樣本。

### 候選處置
| 方案 | 利 | 弊 |
|------|----|----|
| 1 所有 hook 內 git 呼叫優先帶抑制旗標，寫入類改以「先 SIGTERM 並等待，逾時才 SIGKILL」（164.6.2 範圍） | 直接消除可控路徑的殘留；SIGTERM 實測不留鎖 | 無法涵蓋 harness 外部送的 SIGKILL |
| 2 每次 Bash 呼叫前檢查並清理 0 位元組無持有者的殘留鎖（164.4.1 範圍） | 涵蓋所有成因，含未識別者 | 是事後補救；須確認清理判準（0 位元組、lsof 無持有者、mtime 夠舊）不誤刪活鎖 |
| 3 uv 鏈改為 exec 直啟或讓 hook 用 process group 終止 | 避免孤兒 git | 逾時送法屬 harness 行為，專案端可控範圍有限 |
建議：方案 1 與 2 已各有票，並行；方案 3 暫不實作（harness 端訊號送法未驗證）。
