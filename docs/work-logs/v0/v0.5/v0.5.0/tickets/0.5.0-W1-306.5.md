## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
PM 派發前判斷（2026-10-15）：PostToolUse 只在 shell 層結束碼 0 時觸發（bash_tool_response 模組說明），失敗命令走 PostToolUseFailure、帶 error 欄位；cli-error-feedback 的 skill-cli 分支已處理失敗事件（286.3）。因此 general-cli 分支在 PostToolUse 上「改以 stdout 內容判斷」等於把成功命令的輸出（含引用的錯誤字樣）當成失敗，會重現 286.3 剛修掉的誤報方向。評估方向優先序：(a) 移除 PostToolUse 上的 general-cli 分支；(b) 若其回饋內容仍有價值，改由 PostToolUseFailure 的 error 欄位觸發。acceptance 第 1 條的「改以 stdout 判斷」若採用，須在 Solution 說明如何避免上述誤報。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
選擇理由：採 PM 優先序 (a)+(b) 組合。PostToolUse 的 stderr 判斷移除（恆空、為死分支）；失敗回饋保留在 PostToolUseFailure（error 欄位）；PostToolUse 僅保留 286.3/295 既有的「遮蔽路徑 stdout 行首 [Error]」前綴偵測。不採「以 stdout 內容判斷」：成功命令 stdout 引述錯誤字樣會誤報。
修改：cli-error-feedback-hook.py 的 check_general_cli_failure 非失敗事件分支不再讀 stderr；bash_tool_response.py 文件字串補記 stderr 恆空實測（2026-10）；測試改 test_skill_cli_error_feedback_hook.py。

### 自檢結果
- 成功命令 stdout 含錯誤字樣 -> 不回饋（E1 對照）；PostToolUse 塞 stderr 值 -> 不觸發
- PostToolUseFailure Exit code 1 -> 回饋 CLI_FAILURE_HELP_REMINDER（E2 正向對照）；error 格式無法解析 -> fail-open None
- 認知負擔：函式更短，分支減少

### Phase 4 評估
重構需要：否；技術債務：無；程式碼品質：A；結論：無需重構。
