### 問題根因
bare-commit-guard 的放行判定（_staged_scope_is_safe_for_bare_commit）只驗 staged 檔案集合與派發宣告的集合關係，兩條路徑（子集 / 不相交）皆不讀 MERGE_HEAD、不比對提交者身分（函式 docstring 自述「不依賴呼叫者身份比對」）。git 自身對 commit 的語意是：MERGE_HEAD 存在即為 merge commit，不論誰下 commit、index 內含什麼。

### 影響範圍
已驗證：main() 全檔無 MERGE_HEAD 讀取（grep 無命中）；MERGE_HEAD 檔內容僅為目標 SHA，無發起者資訊；.git 下 MERGE_MODE / MERGE_MSG / AUTO_MERGE 同樣無 session 欄位。未驗證：實機 PreToolUse payload 的 session_id 是否在所有 session 型態皆非空（resolve_session_id 有 env fallback 且可回空字串，表示存在缺失情形）。

### 相關 Error Pattern
PC-BAL-008（共用 index 吸入他方 staged）變體；MERGE_HEAD 唯一命中 canonical #101（引用關係，見票 why）。
## 重現實驗結果
### 實驗方法
scratch 暫存 repo（scratchpad/repro120，非共用主工作樹）。A：feat 分支含 f1.md f2.md，於 main 執行 git merge --no-ff --no-commit feat。B：另改 doc.md，git add doc.md，裸 git commit -m "docs: one line"。

### 實驗執行
A 後：.git/MERGE_HEAD=238e707...，另有 MERGE_MODE / MERGE_MSG / AUTO_MERGE。B 後：rc=0，HEAD 有兩個 parent（3df434a 238e707），stat 為 doc.md f1.md f2.md 共 3 檔，訊息為 B 的 "docs: one line"，MERGE_HEAD 已清除。

### 實驗發現
已驗證：裸 commit 必然收尾他方 MERGE_HEAD，且歸屬於提交者的訊息；git 層無任何阻擋。已驗證：守衛現行碼無 MERGE_HEAD 判斷，故事件中 staged=4 檔（皆落在 113.1 宣告內）走子集路徑放行。已驗證：現有 merge-staged-index-guard-hook 只攔 merge 起手（index != HEAD），不涵蓋 merge 與 commit 之間的空窗。已驗證：同專案 commit-stage-guard-gate-hook 已有 MERGE_HEAD 可解析的偵測（rev-parse -q --verify MERGE_HEAD），可重用；但其語意是「把 MERGE_HEAD 當合併豁免」，與本案方向相反。
身分可行性：PreToolUse payload 含 session_id（resolve_session_id 已被 5+ hook 使用）與 subagent 的 agent_id。MERGE_HEAD 本身不攜發起者，故「事後從 git 狀態辨識發起者」不可行；只能「事前記錄」：在 git merge --no-commit 的 PreToolUse 由既有 merge-staged-index-guard 寫 marker（session_id + MERGE 目標 SHA），commit 時比對。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論
裸 commit 收尾他方 MERGE_HEAD 已在 scratch repo 最小重現（見重現實驗結果）。根因是守衛只驗檔案範圍、不讀 MERGE_HEAD、不比對提交者。

### 候選方案
| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A 發起者 marker | merge-staged-index-guard 於 git merge --no-commit 的 PreToolUse 寫 marker（session_id + 目標 SHA），commit 時比對 | 精準：只擋非發起者 | 兩支 hook 耦合 + 狀態檔；CLI subprocess 合併與 session_id 缺失時無 marker，仍須 fallback；清理時機（abort / 崩潰）增加殘留風險 |
| B MERGE_HEAD 存在即擋裸 commit（採用） | commit 守衛偵測 MERGE_HEAD，一律 deny，訊息指向 git merge --continue / --abort | 零身分依賴、無狀態、實作面小；強迫收尾走語意明確的 merge --continue（守衛不攔） | 發起者誤用 git commit 也被擋（改下 merge --continue 即解，成本低）；旁觀者仍可手動 merge --continue，但需有意識動作 |
| C 範圍判定改以提交者本人派發為準 | 比對 payload session_id/agent_id 與派發記錄 | 理論上補子集路徑缺口 | PM 主線程無派發記錄，無法表示；docstring 記載 PreToolUse 拿不到可靠身分；不解決本案（PM 自己的 merge 無派發） |
| D 規則七明文禁兩段式 | 共用 checkout 一步合併，禁跨呼叫留 MERGE_HEAD | 消除事故前提；PM 已採行 | 純自律，無強制力，須搭配 B |

### 決策
採 B + D。A 因耦合與殘留風險不採（若 B 誤報率日後證明高再評估）；C 不可行（PM 無派發記錄）。身分可行性：session_id / agent_id 在 payload 可得，但 MERGE_HEAD 不攜發起者，事後辨識不可行，只能事前記錄（即 A）。
