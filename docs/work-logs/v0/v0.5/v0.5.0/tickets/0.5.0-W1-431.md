## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`dart-style-guardian.json` 是專案專屬的校準檔（token 類別名、i18n 存取形態），卻放在 `.claude/config/`。該目錄屬框架層，sync 不排除，所以各 consumer 的校準會隨 push 進入 canonical，再隨 pull 互相覆寫：base 是 A 的值，B 推送自己的值後，A 在本地未改的情況下 pull，三方合併會採用 B 的值。

### 影響範圍

- 已驗證：`.claude/config/` 下 10 個檔中，只有這一檔自述為專案專屬（見重現實驗結果）。
- 已驗證：flutter_balance 的校準已被覆寫。它的 design system 類別是 `AppPalette`／`AppSpacing`／`AppTypography`／`AppRadius`，現行校準卻是本專案的 `AppColors`／`Space`／`AppFontSize`／`Radius`，這些類別在它的程式碼中不存在。style_checker 會建議改用不存在的類別，正是該 skill 自述要避免的情形。
- 讀取端：`style_checker.py` 的 `CONFIG_RELATIVE_PATH`，以及 `.claude/hooks/tests/test_dart_style_guardian_hook.py`、SKILL.md、`references/i18n-guidelines.md`。

### 相關 Error Pattern

無直接對應。屬 #50 的「名稱式排除使 consumer 專屬層無法標記」一族。

## 重現實驗結果
### 實驗方法

1. 以 `python3 -I` 直接呼叫 `sync_exclude_manifest.should_exclude`，逐一檢查 `.claude/config/` 下每個檔。
2. 用 `rg` 搜尋 `.claude/` 下自述為專案專屬（「專案專屬」「per-project」「專案校準」等字樣）的 json／yaml／toml 檔，排除 project-integration 與 runtime 目錄。
3. 用 `gh api repos/tarrragon/claude/contents/config/<檔>` 取得 blob sha，與本地 `git hash-object` 比對。
4. 唯讀查證本機其他 consumer（flutter_balance、book_overview_app、book_overview_v1）：比對校準值、`git log` 該檔的來源 commit、grep 各自 `lib/` 實際定義的類別。

### 實驗執行

- `should_exclude`：config/ 下 10 個檔全部回 False（`__pycache__` 除外）。
- 自述為專案專屬的檔：只有 `.claude/config/dart-style-guardian.json`。`wrap-triggers.yaml` 是框架 hook 的設定，它的專案對應表已放在 `skills/wrap-decision/references/project-integration/`，判定不屬於專案專屬。
- canonical 比對：config/ 下 10 個檔都與 canonical 相同，canonical 收的正是本專案的校準值。
- flutter_balance 的時序：
  - `b7aba25ca`（feat 0.2.1-W3-361.1）以 `AppPalette`／`AppSpacing` 建立校準。
  - `c5a3f3346`（chore(sync): pull，2026-09-24）把四個值改寫為 `AppColors`／`Space`／`AppFontSize`／`Radius`。
- 類別定義：`AppColors`／`Space` 只出現在本專案 `lib/tokens/`；`AppPalette` 等四類只出現在 flutter_balance 的 `lib/core/design_system/`。
- book_overview_app／v1 現行仍是 `AppPalette` 系列。

### 實驗發現

已驗證的事實：
1. 外洩已經造成覆寫：flutter_balance 現行的校準指向它不存在的類別。
2. 外洩路徑是「放在框架目錄」本身，而不是少登記一條排除規則：config/ 是框架層，名稱式排除要逐檔登記，漏一檔就外洩。
3. 本專案範圍內只有這一檔。

尚未驗證的假設：
- book_overview_* 下次 pull 時也會被覆寫（推論自三方合併規則，未實測）。
- 本機之外是否還有其他 consumer。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

校準檔遷到 `.claude/project-integration/dart-style-guardian.json`，style_checker 改讀新位置，並保留一段讀舊位置加遷移提示的過渡；canonical 端的舊檔另行移除。根因是把專案專屬檔放在框架目錄，修法是改放置位置，不是補一條排除規則。

### 修法比較

| 案 | 做法 | 利 | 弊 |
|---|---|---|---|
| **A（採用）遷入 project-integration** | 檔搬到 `.claude/project-integration/`，style_checker 改路徑；只有舊位置有檔時沿用舊檔並提示遷移 | 與 410.3 的專案宣告載體一致；之後的專案宣告都放這裡，不必逐檔登記排除；`config/` 回到純框架層 | 要改讀取端與文件；各 consumer 要自行搬檔（過渡提示會指出要搬到哪裡） |
| B 名稱登記排除 | 把 `dart-style-guardian.json` 加入 `PER_PROJECT_PATTERNS`，位置不變 | 只改 manifest 一行 | 根因不變，下一個專案專屬檔放進 `config/` 時同樣會外洩；`config/` 繼續混放框架與專案檔 |

### canonical 移除路徑

431.1 合併後，canonical 的 `config/dart-style-guardian.json` 要以 sync-push 刪除，這不在常駐授權內。依主控指示，回報主控，由主控向用戶取得授權，本 session 不自行推送。推送前提：431.1 的過渡讀取已上線；否則 consumer pull 到刪除後，校準會直接退回中性預設，不會看到遷移提示。

### 框架問題判定（兩條 AND 判準）

| 判準 | 判定 | 依據 |
|---|---|---|
| 抽象可攜性 | 成立 | 去掉專案名後，敘述為「專案專屬校準檔放在 sync 不排除的框架目錄，各 consumer 的校準經 canonical 互相覆寫」，任何有兩個以上 consumer 使用該 skill 時都成立 |
| 資產範圍 | 成立 | 根源在 `.claude/skills/dart-style-guardian/scripts/style_checker.py` 的 `CONFIG_RELATIVE_PATH`，以及 `.claude/config/` 的放置慣例 |
