### 對照實例（2026-10-14）

- 285：`ticket track finish ... > log 2>&1; echo rc=$?`，parallel-dispatch-verification 日誌 18:17:52「非 ticket track complete 成功，靜默結束」，dispatch-cleanup 等完成類提示亦未出現在 PM context。

同一命令、同一 session，差別只在 stdout 是否被導向檔案。

### 盤點（PM，2026-10-15）

**以 stdout 成功標記判定成敗的 hook（排除 git commit 類）**

| hook | 判定方式 | 成功標記 | 對應命令 | 輸出被吸走時的行為 |
|------|---------|---------|---------|-----------------|
| .claude/hooks/parallel-dispatch-verification-hook.py | is_bash_success | "已完成"、"成功" | complete、finish | 判為非成功，靜默結束，驗證不執行（285 實例） |
| .claude/hooks/session-context-guard-hook.py | 自行比對 | "已完成" | complete、finish、batch-complete | 不計數，不提醒 handoff |
| .claude/skills/ticket/hooks/post-ticket-lifecycle-hook.py | 自行比對 | 含 "已完成" 等 | complete | 不跑完成後檢查點 |
| .claude/skills/ticket/hooks/handoff-cleanup-hook.py | is_bash_success（忽略大小寫） | "[OK]"、"已完成"、"completed" | handoff 相關 | 不清理 |
| .claude/hooks/parallel-claim-audit-hook.py | is_bash_success | "[OK] 已接手" | claim | 不記錄 claim 快照 |
| .claude/skills/ticket/hooks/needs-context-listener-hook.py | is_bash_success | "已追加日誌到" | append-log NeedsContext | 不通知 PM |
| .claude/skills/ticket/hooks/cli-error-feedback-hook.py | is_bash_success（反向：非成功才給回饋） | "[OK]" | ticket CLI 全部 | 誤判為失敗並給回饋，或因 stdout 沒有錯誤文字而什麼都不做 |

**「輸出被吸走」的三種形態**（都會讓 stdout 不含標記）

1. 重導向到檔案：`ticket ... > log 2>&1`。結束碼沒有被遮蔽。
2. 以分號接其他命令：`ticket ... > log 2>&1; echo rc=$?`（285 實例）。結束碼被遮蔽。
3. 命令替換：`out=$(ticket ... 2>&1); rc=$?`。結束碼被遮蔽。**這是 `.claude/rules/core/bash-tool-usage-rules.md` 統一檢查清單要求寫入類 CLI 使用的寫法**（判成敗讀 rc，不讀輸出外觀）。所以現行規則與標記判定在設計上互相衝突：遵守規則的呼叫，正好會讓完成類 hook 靜默略過。本 session 大量使用此寫法執行 append-log，needs-context-listener 對這些呼叫都不會觸發。

**結束碼是否被遮蔽**（PostToolUse 只在 shell 層結束碼為 0 時觸發，見 .claude/lib/bash_tool_response.py 模組說明）

- 單一命令，或以 `&&` 串接、且 ticket 呼叫失敗時後續不執行：沒有遮蔽。收到 PostToolUse 就代表 ticket 呼叫成功（75 走 PostToolUseFailure，已由 auto_commit_failure_as_success 處理）。
- `;`、`|`（未設 pipefail）、`||`，或命令替換後接其他陳述：遮蔽。收到 PostToolUse 不能推得 ticket 呼叫成功。
- `.claude/lib/ticket_command_parse.py` 能找出呼叫（含 `$( )` 內的呼叫，實測 5 種形態皆可），但目前不回報遮蔽與否。
更正：上段「本 session 大量使用此寫法執行 append-log，needs-context-listener 對這些呼叫都不會觸發」不準確。needs-context-listener 只處理寫入 NeedsContext 章節的 append-log，本 session 的 append-log 都不是寫這個章節。正確的說法是：若以 out=$(...) 的寫法向 NeedsContext 追加，listener 會因 stdout 沒有標記而不通知 PM。本 session 沒有實際發生過。
## 重現實驗結果
### 實驗方法

同一 session、同一完成命令，只改變 stdout 去向與結束碼是否被遮蔽，比對完成類 hook 的日誌與 PM context 是否出現完成後提示；子票合併後以相同手法實地觸發。

### 實驗執行

- 2026-10-14 對照：285 以「finish ... > log 2>&1; echo rc=$?」執行，parallel-dispatch-verification 日誌 18:17:52 記「非 ticket track complete 成功，靜默結束」；270.3.3 以「finish ... 2>&1 | head -30」執行，18:25:05 進入驗證並記 PASS，完成後提示皆出現。
- 2026-10-15（286.2 合併後）：對已完成的票再 complete，session 完成計數不增加；以「complete ... > log 2>&1」完成新票，計數 22 → 23。
- 2026-10-15（286.3 合併後）：重複 claim 已認領的票（rc=1）→ parallel-claim-audit 讀票面 started_at 為舊值，記「未成功，不記錄快照」；成功 query 輸出重導向 → cli-error-feedback 不回饋；多陳述命令第二陳述失敗 → 回饋標示「無法判定出錯的陳述」；append-log NeedsContext 未遮蔽重導向 → 通知送達；帶尾端 echo rc 的遮蔽形態 → 依設計退回標記而漏判；complete 286.3 以重導向執行 → 計數 25 → 26、Checkpoint 提示與 handoff-cleanup 清理報告皆出現。

### 實驗發現

- 已驗證：漏判由「stdout 不含成功標記」造成，與命令本身成敗無關；分層判定上線後，未遮蔽重導向形態四類 hook 均判成功，遮蔽形態由票面驗證器判定。
- 已驗證：CLI 對無狀態轉換的重複 complete 回結束碼 0，所以在乎狀態轉換的 hook 必須用票面驗證器，第 1 層不夠。
- 已知接受的殘餘：needs-context-listener 在遮蔽且輸出被吸走時仍漏判（無票面狀態可驗證）；重複 claim 本次實測結束碼為 1，與 2026-10-15 11:59 實測的 0 不同，驗證器判定不依賴結束碼，故不影響結論。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 修法候選比較

| 候選 | 做法 | 誤報（判成功但其實失敗） | 漏報（判失敗但其實成功） | 其他代價 |
|------|------|----------------------|----------------------|---------|
| (1) 依遮蔽與否分流 | 呼叫沒有被遮蔽時，收到 PostToolUse 即判成功；被遮蔽時才看標記 | 只在解析器誤判「沒有遮蔽」時發生 | 遮蔽且輸出被吸走時仍會漏報（285 實例與 `out=$(...); rc=$?` 都屬此類） | 解析器需新增遮蔽判斷 |
| (2) 規範收尾命令不得重導向，由守衛提示 | 守衛擋下或提醒 `> log`、`out=$(...)` 形態 | 無 | 守衛覆蓋不到的形態仍會漏報 | **與 bash-tool-usage-rules 要求的 `out=$(...); rc=$?` 直接衝突**；要嘛改規則，要嘛守衛自相矛盾 |
| (3) 讀票面狀態 | 命令執行後讀票面：complete 看 status 為 completed 且 completed_at 在近期內；claim 看 in_progress 且 started_at 在近期內 | 只在時間窗內另有他方對同票做同一動作時發生 | 讀票失敗時才發生 | 每次觸發多一次讀檔；只適用有對應票面欄位的命令 |

### 選定：分層判定，(1) 為主、(3) 補遮蔽情形、標記作最後退路

判定順序（落實在 .claude/lib/bash_tool_response.py，由各 hook 呼叫）：

1. 解析器判定呼叫**沒有被遮蔽** → 收到 PostToolUse 即判成功，不看 stdout。涵蓋單一命令與純重導向（`> log 2>&1`）。
2. 呼叫**被遮蔽**，且呼叫端提供票面狀態驗證器 → 以票面狀態判定。涵蓋 285 實例與 `out=$(...); rc=$?`。
3. 其餘情形（無法解析、或呼叫端沒有狀態驗證器）→ 沿用現行的標記判定。

理由：

- (2) 與現行 Bash 規則衝突，不採用。
- 只用 (1) 解決不了 285 實例；只用 (3) 則每次都要讀檔，且 append-log 這類命令沒有可比對的狀態欄位。分層後，每一層只處理上一層判不了的情形，最差也只會退回現行行為。
- 誤報方向最安全：第 1 層的誤報只在解析器出錯時發生；第 2 層靠時間窗限制，避免把「重新 complete 已完成的票」誤判為成功。
- cli-error-feedback 的方向相反（非成功才給回饋），它在第 3 層退路下維持現行行為即可，不需要狀態驗證器。
