## Problem Analysis

### 同類實例（D 線回報，2026-10-14）

- worktree 內的 acceptance-gate 讀取 worktree 內的舊票面副本，ticket CLI 則寫入主倉庫；代理人在 worktree 內 complete 時必被錯擋（實例：0.5.0-W1-120.7.1，主倉庫驗收 5/5 勾選，worktree 副本 0 勾選）。D 線改由 PM 於主倉庫結案並記錄原因。
- 與本票平台拒絕案例（231.2.1）共同指向：worktree 隔離派發下，「代理人自行收尾」的路徑同時受平台限制與票面副本分歧兩層阻礙。D 線已將此發現併入 0.5.0-W1-264。

### 盤點：要求或指引隔離代理人執行 ticket 寫入命令的位置（acceptance 1）

| 位置（檔案〈章節〉） | 指示內容 | 是否區分 worktree |
|------|------|------|

| `.claude/agents/AGENT_PRELOAD.md`〈worktree 隔離派發時必須 commit 產品碼進 worktree 分支〉 | `ticket track commit --worktree <path> -- <files>` | 是 |

**矛盾一**：AGENT_PRELOAD 的 append-log 替代做法是「Edit worktree 內的 ticket md」，與 worktree SKILL「恆落主倉庫」、dispatch 骨架「禁止複製或提交票面副本」方向相反；照 AGENT_PRELOAD 做，寫進去的是舊副本，主倉庫看不到。
**矛盾二**：AGENT_PRELOAD 與 agent-definition-standard-details 對所有代理人只寫 `complete`。worktree 的 `finish` 別名只寫在 dispatch 範本與骨架；代理人若沒有拿到骨架的收尾句，就會照 AGENT_PRELOAD 執行 `complete`。

### 231.2.1 拒絕的成因比對

票面 log 記錄代理人執行的是 `ticket track complete ... --as basil-hook-architect`，不是 `finish`。平台訊息「runs a string through complete」與 dispatch 範本記載的既有成因一致：隔離守衛以 argv token 的 basename 比對 shell 命令清單，`complete` 撞到 bash builtin。是否只要改用 `finish` 就能放行，需要實測（框架既有紀錄為五次兩擋三過，屬條件性）。

### 120.7.1 票面副本分歧的成因（第二層，與平台無關）

`.claude/skills/ticket/hooks/acceptance-gate-hook.py` 以 `get_project_root()` 取 project_dir（`.claude/lib/hook_base.py`）。其優先序第 1 項是「位於 git linked worktree 時，用該 worktree 根目錄」。ticket CLI 依設計恆寫主倉庫，所以在隔離代理人中 gate 讀到的是 worktree 內建立時的舊副本：`set-acceptance`／`check-acceptance` 勾選寫進主倉庫，gate 讀副本為 0 勾選。即使平台放行 `finish`，這一層仍會錯擋。hook_base.py 與 gate 屬 D 線範圍，本票只分析、不修改。
### 與 0.5.0-W1-264 的分工

264（D 線）已以暫存 repo 重現 gate 讀舊副本，根因定位為 hook_base 的 worktree 優先根被用來讀共用狀態，CLI 端的 `get_ticket_state_root` 已回推主倉庫而 hook 缺對應函式。第二層的技術修法屬 264，本票不重複，候選方案以「264 修好之後仍需解決什麼」為前提比較：即平台層與收尾責任的歸屬。

#### 實驗發現（實填）

已驗證：
1. 隔離代理人可執行 query、append-log（含 heredoc）、set-acceptance、check-acceptance、finish，寫入皆落主倉庫。平台只擋 `complete`，本次 5/5 穩定被擋（框架既有紀錄為五次兩擋三過，本次未見放行）。
2. acceptance-gate 在真實 worktree 內讀舊副本（日誌路徑為證），與 264 的暫存 repo 重現一致。
3. **新發現（高）**：`is_complete_command()` 只比對字面 `ticket track complete`／`batch-complete`，`finish` 別名不被辨識，gate 的全部阻擋檢查（驗收、自檢、Phase 4、spawn 落地、子任務）被整個略過。此缺口不限 worktree：主 checkout 執行 `finish` 同樣繞過。框架文件卻指示 worktree 收尾一律用 `finish`。其他以字面 `complete` 判定的 hook（phase4-decision-enforcement、phase-completion-gate、sibling-blockedby-validator 等）可能同型，需逐一盤點。
4. 本次實驗票為 DOC，gate 對 DOC 本來豁免驗收檢查，故未能直接觀察到「讀副本導致 IMP 被錯擋」；該現象以 120.7.1 實例與 264 的重現為據。

未驗證：`finish` 在平台層是否永遠放行（只取樣 1 次即完成，無法重複）。
