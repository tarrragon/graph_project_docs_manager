### 實作摘要

- `hooks/register.tsx` `openIfConfigured`：先 `readProjectConfig($, root)`，成立即 `openConfiguredPane`（不呼叫 git）；不成立才 `findCheckouts` 取 `checkoutPaths[0]`，mainPath 與 root 相同時沿用 root 的結果不重讀，不同時（worktree session）再讀一次；兩次都不成立寫 unconfiguredSnapshot，`configPath` 指向 mainPath（同現行）
- 新增 `openConfiguredPane`：`startTimer` → 先發出 `$.ui.open` → `void refresh` → `await` 開 Pane 的 promise。先發出開 Pane 再啟動第一輪讀取，Pane 不排在 refresh 的 git 與讀檔之後；開 Pane 失敗由 openIfConfigured 的 catch 收
- catch 改 `$.ui.log(..., { to: 'transcript' })`
- `hooks/readers.ts` 未改：root 讀不到設定時的 debug log 屬正常路徑（Context Bundle 已排除）
- `/board`、`refresh`、各 View 未改
- 測試：`tests/paneHarness.ts` 的 Stub 增 `sessionRoot`、`rootError`，回傳增 `logs`（ui.log 的 text/to）與 `callOrder`（git 呼叫與 ui.open 的順序）；`tests/board.test.ts`〈專案設定〉增 5 個測試（E1 主 checkout／worktree 呼叫序對照、主 checkout 無設定對照、E2 例外／無例外對照）

### 既有測試斷言的調整（需 PM 知悉）

「對照：同一批 fixture 沒有設定檔時…」原斷言 readPaths 全為 `/repo/<設定檔>`。新流程先讀 session root（`/wt`）的設定檔，該斷言改為「全為 `/repo` 或 `/wt` 的設定檔」。斷言意圖（不讀協調票、不定時讀其他檔）不變，只是多容許 root 的設定檔這一條路徑。

### 失敗可見管道的選擇：`$.ui.log` 送 transcript

- 選 transcript 而非寫入 `$.state` 由 `/board` 顯示：失敗發生在 session 啟動時，此時 Pane 沒開；寫入 `$.state` 要等使用者主動執行 `/board` 才看得到，而使用者正是因為沒看到 Pane 才不知道要去查，可見性仍依賴使用者先懷疑
- transcript 一行在啟動當下就出現在畫面，且同時進 debug log（UiLogSink 型別定義：transcript 也寫 debug log），原有除錯管道不丟失
- 與本檔既有慣例一致：群組切換失敗已以 transcript 送出（「$.ui.log 無級別，送 transcript 使畫面可見」）
- 不寫 `$.state` 也避免與 refresh 的 snapshot 寫入競爭、改動 View（範圍限制：不改 View）
