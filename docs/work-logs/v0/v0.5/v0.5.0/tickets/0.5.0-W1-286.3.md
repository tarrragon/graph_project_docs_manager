## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
PM 附帶觀察（2026-10-15）：cli-error-feedback 對多陳述命令的失敗歸因不準確。實例：命令為「ticket track set-who ... > /dev/null 2>&1; ticket track check-acceptance <id> 2 3 ...」，實際出錯的是第二個陳述（check-acceptance 不接受兩個索引），但回饋把「失敗命令」標為第一個陳述 set-who。改接分層判定時，順便讓失敗歸因指向實際出錯的陳述，或在無法判定時不指名具體陳述。

PM 審查 286.2 時的實測（2026-10-15）：對已完成的票再執行 complete（未遮蔽），CLI 輸出「已完成於 …」且結束碼為 0，舊版 session-context-guard 因此誤加計數。所以「未遮蔽且收到 PostToolUse 即成功」只代表命令成功，不代表發生了狀態轉換。本票的 claim、handoff 等 hook 若在乎的是狀態轉換，同樣要以狀態驗證器確認，不能只靠第 1 層；派發前先實測 claim 已認領的票時 CLI 的結束碼。
PM 實測（2026-10-15 11:59）：對已認領的 0.5.0-W1-286.3 再執行 claim（未遮蔽），CLI 輸出「[Warning] 0.5.0-W1-286.3 已被接手」且結束碼為 0。現行標記判定不含「[OK] 已接手」所以不誤判，但若只接分層判定第 1 層（未遮蔽即成功）就會誤判為新的 claim。parallel-claim-audit 須比照 286.2 的 is_complete_transition_success 做法：不論是否遮蔽都以 claim 驗證器確認（status 為 in_progress 且 started_at 在時間窗內；重複認領時 started_at 保持舊值）。
