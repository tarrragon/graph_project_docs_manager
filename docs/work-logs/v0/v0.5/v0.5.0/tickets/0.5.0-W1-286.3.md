## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
PM 附帶觀察（2026-10-15）：cli-error-feedback 對多陳述命令的失敗歸因不準確。實例：命令為「ticket track set-who ... > /dev/null 2>&1; ticket track check-acceptance <id> 2 3 ...」，實際出錯的是第二個陳述（check-acceptance 不接受兩個索引），但回饋把「失敗命令」標為第一個陳述 set-who。改接分層判定時，順便讓失敗歸因指向實際出錯的陳述，或在無法判定時不指名具體陳述。

PM 審查 286.2 時的實測（2026-10-15）：對已完成的票再執行 complete（未遮蔽），CLI 輸出「已完成於 …」且結束碼為 0，舊版 session-context-guard 因此誤加計數。所以「未遮蔽且收到 PostToolUse 即成功」只代表命令成功，不代表發生了狀態轉換。本票的 claim、handoff 等 hook 若在乎的是狀態轉換，同樣要以狀態驗證器確認，不能只靠第 1 層；派發前先實測 claim 已認領的票時 CLI 的結束碼。
PM 實測（2026-10-15 11:59）：對已認領的 0.5.0-W1-286.3 再執行 claim（未遮蔽），CLI 輸出「[Warning] 0.5.0-W1-286.3 已被接手」且結束碼為 0。現行標記判定不含「[OK] 已接手」所以不誤判，但若只接分層判定第 1 層（未遮蔽即成功）就會誤判為新的 claim。parallel-claim-audit 須比照 286.2 的 is_complete_transition_success 做法：不論是否遮蔽都以 claim 驗證器確認（status 為 in_progress 且 started_at 在時間窗內；重複認領時 started_at 保持舊值）。
## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 各 hook 的判定選擇
- parallel-claim-audit：在乎狀態轉換。新增 lib/ticket_claim_verifier.py（status 為 in_progress 且 started_at 在 120 秒窗內；重複認領 started_at 保持舊值落窗外；窗常數與 VerifierUnavailable 沿用 ticket_completed_verifier）。hook 不論遮蔽先跑驗證器，明確 True/False 即為判定，票面讀不到才退回原標記判定。
- handoff-cleanup：在乎命令成功。交接檔清理冪等，重複 complete 為無害空操作，故未遮蔽即成功（第 1 層）；遮蔽時以 completed 驗證器判定，讀票失敗再退回標記。另補空 tool_response 守衛（畸形 payload 不套用未遮蔽即成功）。
- needs-context-listener：在乎命令成功。append-log 每次呼叫皆實際追加，無重複呼叫但無轉換的情形；只接第 1 層，遮蔽時退回成功回音標記，不需驗證器。
- cli-error-feedback：反向判定，只接第 1 層。未遮蔽收到 PostToolUse 即成功（argparse 錯誤結束碼非 0，走 PostToolUseFailure），輸出被吸走或引述錯誤字樣皆不回饋；遮蔽時退回 [OK] 標記，輸出含錯誤仍回饋。多陳述歸因：新增 locate_failing_statement，以輸出是否帶出該陳述子命令動詞歸因，恰一個命中才指名，否則摘要標示無法判定、不指名陳述。
### 修改檔案
parallel-claim-audit-hook.py、handoff-cleanup-hook.py、needs-context-listener-hook.py、cli-error-feedback-hook.py、lib/ticket_claim_verifier.py（新）；既有測試中「未遮蔽卻期待失敗回音」的 5 處（實際不可能到達 PostToolUse）改為遮蔽命令。
### 自檢結果
- 實作對應：AC1 四支 hook 未遮蔽且輸出重導向判成功（各有測試）；AC2 claim 遮蔽形態以票面判定；AC3 cef 成功但輸出被吸走不回饋、含錯誤輸出仍回饋（E1 對照）。
- Phase 4：重構需要 否；技術債務 無；程式碼品質 A；claim 驗證器與完成驗證器共用窗常數與例外，結構相似但判定欄位不同，不抽象。
- 295 合併：commit 前 main 上 cli-error-feedback-hook.py 最新為 607cc3733（299），295 尚未進 main，未合併。
