### 實驗執行

**(1) 產生端：兩個失敗條件是否獨立**

`_persistAndInspect(path)` 的結構：
- 持久化在 try 內。`failureReason` 於三種情況被設定：`_preferencesPort.open()` 拋例外、`handle.writeString(_pathKey, path)` 回 `false`、任一 `writeString` 拋例外。
- `_inspect(path)` 在 try/catch 之外、無條件呼叫一次（函式 dartdoc 明寫「持久化的成敗與資料夾本身是否可用是兩件事」）。
- 回傳：`failureReason == null` 回 `ChooseFolderSelected(state)`，否則回 `ChooseFolderNotRemembered(state: state, reason: failureReason)`。`state` 不經任何篩選。

`_inspect(path)` 回 `WorkspaceUnavailable` 的兩個條件：`_directoryProbe.exists(path)` 為 `false`（reason 為「資料夾不存在或所在磁碟未掛載」）；`_directoryProbe.readFirstEntry(path)` 拋 `FileSystemException`（reason 為「無法讀取資料夾內容」）。

持久化走 `WorkspacePreferencesPort`，探測走 `WorkspaceDirectoryProbePort`，兩個 port 無共用前提，函式內無任何一方失敗即跳過另一方的短路。

**(2) 呼叫端：組合到達後的處理**

`_handleChooseFolderResult` 的 `ChooseFolderNotRemembered(:final state)` 分支：先 `await _handleChosenState(...)`，再檢查 `context.mounted`，再呼叫 `AppSnackBar.show(message: l10n.workspaceNotRemembered, level: discardable, origin: userInitiated)`。此呼叫不看 `state` 是哪一種。

`_handleChosenState` 的 `WorkspaceUnavailable(:final reason)` 分支：呼叫 `AppSnackBar.show(message: l10n.folderUnavailableMessage(reason), ...)`，不收合浮層、不寫任何 provider。

兩次 `AppSnackBar.show` 皆未傳 `currentHolder`。`_resolvePreemption` 在 `holder == null` 時回 `holderUnknown`，`show` 隨即 `messenger.hideCurrentSnackBar()` 後 `showSnackBar`。兩次呼叫之間只隔一個 `await` 已完成 future 的 microtask，無畫面更新機會。

**(3) 顯示時點：`WorkspaceReady` 分支的執行順序**

`_handleChosenState` 的 `WorkspaceReady(:final path)` 分支依序：
1. 寫 `currentWorkspaceStateProvider`，重置三個旗標
2. `await gateDetectionNotifierProvider.notifier.detect(path)`
3. `await _persistRecentProjectSelection(ref, path)`
4. `_dismiss(ref)`（浮層收合）

回到 `_handleChooseFolderResult` 後才呼叫 `AppSnackBar.show(workspaceNotRemembered)`。

`detect` 內部：三個阻擋分支（`DomainNotFramework`、`DomainSchemaUnconsumable`、`DomainSchemaIncompatible`）以 `_apply` 直接寫入 `domainViewStateProvider`，**不經過 `DomainLoading`**；版本在已知範圍時 `await domainViewLoaderProvider.notifier.load(...)`，`load` 先寫 `DomainLoading`，取得掃描輪次後才寫 `DomainReady`／`DomainEmpty`／`DomainLoadFailed`／`DomainUnset`，全程被 `detect` 等待。

**(4) 範圍斷言的驗證**

**範圍驗證方法**：rg regex 法（grep -rn -E，範圍 `lib/`）
**驗證指令**：
- `grep -rn -E "hideCurrentSnackBar|clearSnackBars|removeCurrentSnackBar" lib`，排除 `lib/components/app_snack_bar.dart` 後 0 筆
- `grep -rn -E "attention_arbiter|attentionArbiter" lib`，排除 `lib/app/attention_arbiter.dart` 自身後 0 筆
- `grep -rn -E "currentHolder:" lib` 0 筆
- `grep -rn -E "NotRemembered" test integration_test`：widget 層只有 `project_switcher_test.dart` 一則（`_fakeRepositoryReady(rememberSucceeds: false)`，內層狀態為 Ready）；repository 層 G2-2／G2-3／G2-4 的探測替身皆為預設 `_FakeDirectoryProbe()`，G2-4 斷言內層狀態為 `WorkspaceReady`
**已知盲區**：經變數間接呼叫 `ScaffoldMessengerState` 的方法、以 `export` 轉出後改名引用仲裁器、`test/` 以外的測試目錄，三者不會命中。
**盲區影響評估**：`AppSnackBar` 檔頭註解自述為暫時訊息的唯一承載元件，且 `ScaffoldMessenger` 字樣在 `lib/` 的其他出現處未逐一檢視；結論「無其他清除點」「仲裁器未接線」「持有者恆未傳入」的信心為高但非窮舉證明，實作票開工時應重跑上列指令。

### 實驗發現

**已由讀碼確立的事實**

1. `ChooseFolderNotRemembered` 攜帶 `WorkspaceUnavailable` 的組合在 repository 層可產生，產生端無任何排除。
2. 該組合到達呼叫端後，連續兩次 `AppSnackBar.show`：先 `folderUnavailableMessage(reason)`，後 `workspaceNotRemembered`；第二次的 `hideCurrentSnackBar()` 清除第一則。浮層維持展開，Domain 視圖狀態不變。
3. 留下的那一則文字是「已選定，但下次啟動需重新選擇」，而此時沒有任何資料夾被選定——文字內容與事實不符，且不可用原因被清掉。
4. 第二次呼叫的 `preempted` 事件帶 `holderUnknown: true`、`preemptedShowId: null`，日誌不記錄「誰截斷了誰」。
5. `WorkspaceReady` 路徑下，「未能記住」提示的顯示晚於：該輪載入落定（含三個阻擋狀態與載入失敗）、最近專案清單寫入、浮層收合。main 上不存在「提示先於阻擋狀態」的執行順序。
6. main 上浮層收合晚於整輪載入落定。這與 §3.7〈動畫提示〉「選取專案後的重載」（浮層先收合，再由 Domain 視圖轉入載入態）及〈生命週期〉「切換專案期間」（浮層先收合再開始重載）不一致；不一致的範圍是整個收合順序，不限於這則提示。
7. 落到三個阻擋狀態的輪次不經過 `DomainLoading`：若該輪由某個阻擋狀態的出口發起，前一個阻擋狀態一直顯示到新狀態寫入為止。§2.15 跨級別表「選定成功但未能記住」列規則 3 那一格的依據「前一個阻擋狀態已因轉入 `state-domain-loading` 而被消費」，在這些輪次上於 main 不成立。
8. `lib/app/attention_arbiter.dart` 在 `lib/` 內無呼叫端；`AppSnackBar.show` 的 `currentHolder` 無任何呼叫端傳入。main 上沒有任何路徑會走到讓步或拒絕。

**最小重現條件（單元層，未執行）**

`WorkspaceRepository(preferencesPort: <open() 拋例外，或 writeString 回 false>, directoryProbe: <exists 回 false>)`，呼叫 `openPath('/任意路徑')`，預期回 `ChooseFolderNotRemembered`，其 `state` 為 `WorkspaceUnavailable`、`reason` 為「資料夾不存在或所在磁碟未掛載」。widget 層：以替身 repository 直接回傳該結果，點 `card-switcher-recent-0` 或 `action-switcher-choose-folder`。

**實際環境下的到達路徑（推論，未驗證）**

- 探測失敗一側容易成立：`_buildRecentProjectItem` 一律 `enabled: true`（展開時的可用性探測尚未接線），已刪除、已搬移或磁碟未掛載的最近專案項可被點擊；「選擇其他」則需選定後資料夾消失，或選到無讀取權限的資料夾（App Sandbox 已關閉，選擇器不授權）。
- 偏好寫入失敗一側需 `SharedPreferences.getInstance()` 拋例外或 `setString` 回 `false`。macOS 上的實際發生率未量測。
- 兩者獨立，組合的發生率為兩者之積；阻擋狀態顯示中由 `action-domain-switch-project` 展開浮層再觸發，即為 Problem Analysis 第 1 點所述情境。

**仍未驗證的假設**

- 第一則 SnackBar「未及繪出即被清除」是依 `ScaffoldMessenger` 的佇列行為推論，未以 widget 測試或實機確認是否有殘影一幀。
- 浮層展開時 SnackBar 是否被浮層遮蔽（`0.5.0-W1-167` 的 why 欄如此陳述）未驗證；若遮蔽，組合下使用者看不到任何一則。
- SPEC-001 §1 的原文未直接讀取，事實 7 對 SPEC-001 的比對只經 SPEC-003 §2.15 證據鏈的轉引。
