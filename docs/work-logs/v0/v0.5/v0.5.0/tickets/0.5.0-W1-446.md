### 問題根因（sumac 重現，PM 核對，2026-10-20）

- `.gitignore` 第 8 行排除 `pubspec.lock`，`git ls-files pubspec.lock` 為 0 筆，所以 worktree 沒有 lock。
- 主 checkout 留有一份本機 lock（2026-09-24），`shared_preferences_android` 鎖在 2.4.27，無 jni（PM 已核對 pubspec.lock 的 version 行）。
- worktree 的 `fvm flutter pub get` 因此全量重新解析，輸出 `Changed 86 dependencies`，解出 `shared_preferences_android 2.5.1`，其依賴鏈為 `jni 1.1.0 -> jni_util`。
- jni 是 FFI plugin，所以 linux／windows 的 `generated_plugins.cmake` 在 `FLUTTER_FFI_PLUGIN_LIST` 多一行 jni。
- 同一次 pub get 也讓 `lib/l10n/app_localizations_en.dart`、`app_localizations_zh.dart` 各多一個空行。這兩檔也入庫，同樣會擋合併。
- 入庫的 generated_plugins.cmake 並未過期，它反映作者當時 lock 的解析；問題在 lock 沒入庫，各 checkout 解析結果不一致。
- 只重現了 pub get 一條路徑；L19 回報的 flutter analyze 推測是同一原因，未另外重現。
## 重現實驗結果
- 方法：在乾淨的新 worktree 記錄 git status 後跑 `fvm flutter pub get`，再用 `fvm flutter pub deps` 追 jni 的來源。
- 觀察：4 個入庫檔變動（兩個 generated_plugins.cmake、兩個 l10n 產物），並生成被 gitignore 的 pubspec.lock；依賴鏈為 `shared_preferences_android 2.5.1 -> jni 1.1.0`。
- 已驗證：jni 的來源，以及 lock 未入庫造成的重新解析。未驗證：flutter analyze 路徑。
- 實驗後已 git restore 4 檔並刪除 worktree 內生成的 lock，worktree 乾淨。

### 結論

入庫的生成檔維持現狀不需要更新。要根治，須讓每個 checkout 拿到同一份 lock，修法由 0.5.0-W1-446.1 落地。

### PM 對修法候選的註記

- sumac 的首選方案是在 worktree 建立流程複製主 checkout 的 lock，但這只涵蓋 `/worktree create`。本日五個案例全是 CC runtime 以 `isolation: worktree` 建立的 agent worktree，不經 worktree_manager，首選方案涵蓋不到。
- 次選方案是把 pubspec.lock 入庫，並以入庫 lock 重生生成檔。Dart 對應用程式的建議即是把 lock 入庫，`.gitignore` 第 7 行的註解也寫明了這一點；此方案也涵蓋 CI（231.6）。PM 建議採用此方案。因為要改 .gitignore 與入庫檔，合併前須回報主控（主控指示）。

- 已重現；jni 來源為 shared_preferences_android 2.5.1；PM 已核對主 checkout lock 鎖在 2.4.27，且 lock 未入庫。
- worktree 已還原乾淨，未改任何入庫檔。
