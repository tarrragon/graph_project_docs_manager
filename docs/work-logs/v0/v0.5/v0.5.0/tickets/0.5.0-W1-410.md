### 實驗發現

已驗證的事實：
1. 閘門以寫死的路徑前綴白名單（Flutter 目錄慣例加上 `.claude/`）選擇套件，白名單外的路徑一律免跑。`__call__` 只印出一行「改動不在任何全套件範圍內，免跑」，不列出是哪些路徑。SKILL.md〈合併前全套件〉表格的最後一列把這個行為寫成契約（「其他範圍外路徑：免跑」）。
2. `tools/line-board` 自帶測試套件，但閘門從未執行它（acceptance 1 的讀碼判斷已由直接呼叫實證）。
3. **比票面更嚴重的缺口**：`assets/schema/` 被 Flutter 產品碼與 `test/unit/schema` 讀取，卻不在 Flutter 範圍內。只改內嵌副本的分支會被免跑；框架 schema 票與副本票同批合併時，套件也只有 `hooks` 與 `skill:doc`，不含 flutter。`docs/tech-decisions.md`〈2026-10-12 — 改 schema 匯出的框架票之合併閘門〉的第 2 條（合併前跑 `test/unit/schema`）目前只靠自律執行，閘門沒有補上這一層。
4. `claude plugin test` 在無 TTY 的情況下可以執行，失敗時 rc 不為 0，可以作為閘門套件。

尚未驗證的假設：
- 在快照（detached worktree）內執行 `claude plugin test` 的行為，與在 main 上執行相同。plugin 只讀自身目錄，推測成立，尚未在快照中實測。
- `tool/` 的參考實作腳本是否被測試讀取，尚未查。

## Solution
### 結論

缺口的形態不是「tools/ 被漏掉」，而是**閘門以寫死的路徑白名單選擇套件，白名單外的路徑一律靜默免跑**。tools/line-board 只是其中一例。同一機制也讓 `assets/schema/`（被產品碼與 `test/unit/schema` 讀取）在合併前不跑 flutter 測試，嚴重度比票面所記的更高。

### 三案比較（以 tools/line-board 為對象）

| 案 | 做法 | 利 | 弊 |
|---|---|---|---|
| A 閘門加 line-board 套件 | 合併前執行 `claude plugin test tools/line-board` | 已實證可在無 TTY 下執行（rc=0，6 秒），失敗時 rc=1，可攔下紅燈；測試證據寫入 `worktree-merge.log` | 對應表寫死在框架檔，直接寫入 `tools/line-board` 違反 reference-stability 規則 8，必須先有「由專案宣告套件」的載體；閘門快照環境須有 `claude` CLI |
| B 免跑時顯式警告 | 免跑訊息列出未對應的路徑，並以 WARNING 標示「這些路徑沒有任何套件覆蓋」 | 通用、改動小；未來新增的子專案或資產目錄不再無聲；不阻擋純文件合併 | 只提供訊號，不執行測試；line-board 回歸仍要靠人去跑 |
| C 維持現狀，靠派發約定 | linux 唯讀審查重跑 `claude plugin test` | 337.8–337.12 已實際執行，零開發成本 | 靠記憶執行；證據只在票面，閘門日誌看不到；不涵蓋 assets/ 這類沒有人會想到要重跑的路徑 |

**建議：B 為底線，A 建在專案宣告載體之上，C 只作過渡。** B 處理「無聲」這個通用缺陷；A 處理 line-board 實際需要的測試執行。assets/ 屬於 Flutter 目錄慣例，與 `lib/` 同性質，可以直接加入 `FLUTTER_SCOPE_PREFIXES`，不需要等宣告載體。

### 框架問題判定（兩條 AND 判準逐條套用）

| 判準 | 判定 | 依據 |
|---|---|---|
| 抽象可攜性 | 成立 | 去掉專案名後的敘述是「合併閘門以寫死的路徑白名單選擇套件，白名單外但被測試讀取、或自帶測試的路徑被靜默免跑，輸出不列出路徑」。任何 consumer 有子專案或資產目錄時同樣成立；非 Flutter 的 consumer 更嚴重，因為白名單本身就是 Flutter 目錄 |

判定為框架問題。本專案目前擔任框架主控方，修法在本專案進行。
