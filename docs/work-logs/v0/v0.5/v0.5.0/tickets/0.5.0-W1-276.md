### 補充實例（D 線，0.5.0-W1-120.7.8，2026-10-14）

- complete 被擋三次，缺「產生路徑盤點結果」。代理人做了兩項修改後才放行：(1) 補一條含該字面的 acceptance；(2) 盤點表由「路徑」兩欄改為「產生路徑、是否覆蓋、未覆蓋原因」三欄。未分別驗證是哪一項解除阻擋。
- gate 提示只寫「是否覆蓋欄只接受是或否」，未寫欄名須逐字相符：欄名也是一種未告知的字面要求。

實例（F 線，2026-10-14）：0.5.0-W1-270.3.2 只改 dispatch_skeleton.py 與 .claude/hooks/tests/ 下的測試檔，未改任何 hook 程式；where.files 觸及 .claude/hooks/tests/ 即被判為防護類 hook 票，complete（finish）時才被 gate 擋下要求實地觸發、liveness、失敗語意與盤點表，PM 於收尾時補 3 項 acceptance 與 how.strategy 表格才通過。兩個面向：(1) 必含項目到 complete 才要求（本票主題）；(2) 判定範圍把 hooks/tests/ 視同 hook 程式，對只改測試檔的票，實地觸發與失敗語意只能填「不改 hook 行為」，屬形式填寫。
實例（F 線，2026-10-14 21:27）：0.5.0-W1-281.2.1 由 incident-responder 以 ticket create 建立，where 為 .claude/hooks/tests/test_hook_dispatcher_failure_event.py（只改測試斷言）。建票時未帶入必含四項，PM finish 時被 gate 擋下（整串命令被拒，append-log 與 set-who 都沒有執行）。PM 以 set-how 補盤點表、以 set-acceptance --add 補 3 項後才通過。這是建票者為代理人、不經 ticket track dispatch 骨架的路徑，HOOK_TICKET_REMINDER 送不到。本例也屬於「只改 hooks/tests/ 即被判為 hook 票」。
### 四張卡關票盤點（saffron，2026-10-15）

證據取自 `ticket track full <id>` 與 `git log -S<句子> -- docs/work-logs`。

| 票 | 卡關原因 | 處置方式 | 是否靠補字面句子過關 |
|----|---------|---------|-------------------|

| 0.5.0-W1-120.5.1 | 建票時 acceptance 未含必含項 | complete 前以 add-acceptance 分項補上四項（commit b8d274128 等），內容對應 Solution 的〈實地觸發結果〉〈liveness 驗證方式〉〈失敗語意〉三小節，有實質證據 | 否：補的是有內容的條目，且 Solution 有對應實測 |
| 0.5.0-W1-120.7.1 | (1) 建票未含必含項；(2) 代理人在 worktree 內 complete，gate 讀到 worktree 舊副本（0 勾、無盤點表）而誤擋（根因由 264.1 修） | PM 以 add-acceptance（commit 8511b8d0a）補一條「本 session 實地觸發確認與 liveness 驗證方式記入 Solution（PM 驗收段）；失敗語意：...」；PM 補盤點表 | 是（指向句型）：該條 acceptance 不描述驗證內容，只宣告「記入 Solution」，即命中三組關鍵詞 |
| 0.5.0-W1-264.1 | 建票時 acceptance 未含必含項 | 勾選 acceptance 的同一個 commit（2b86c2ee7，訊息標 check-acceptance）把既有第 4 條「實機驗證...不列為本票驗收」尾端加上「；本 session 已實地觸發；liveness 以 hook 日誌行存在驗證；失敗語意：...」。check-acceptance CLI 不改條目文字，此為直接編輯票面後被自動提交 | 是，即 why 所述「直接 Edit 票面、在 acceptance 後補上字面句子過關」的那一例 |
