### 實驗發現

已驗證：
1. HOOK_TICKET_REMINDER 唯一送達路徑是 `ticket track dispatch`：track_dispatch 以 `_touches_hook_protection_scope(ticket)` 判定後傳 `touches_hook_scope=True` 給 `build_skeleton`，骨架才附提醒。
2. 送不到的路徑：
   | 路徑 | 送達 | 依據 |
   |------|------|------|
   | `ticket track dispatch` 骨架 | 是 | reminder_in_skeleton True |
   | 手寫 Agent prompt（不經 dispatch） | 否 | 無任何 PreToolUse Agent hook 引用提醒（使用者清單只有上列 4 檔） |
   | 代理人自行 `ticket create` | 否 | create.py 無 hook 範圍判定（0 行），acceptance 只取 `--acceptance` 參數 |
   | incident-responder 建票 | 否 | 同上，incident-responder 定義寫明以 Bash 呼叫 `ticket create`；281.2.1 為實例 |
   | 建票後 `set-where` 才補 hooks 路徑 | 否 | 同上，判定只在 dispatch 與 complete 兩處 |
3. 判定範圍含 `.claude/hooks/tests/`：只改測試檔的路徑回 True（281.2.1、270.3.2 兩例的成因）。
4. gate 前三項是子字串比對：只要 acceptance 任一處出現「session」「liveness」「fail-open」即通過，與該句是否描述實際驗證無關；指向句與無關句都回空清單。另 `_APPLICABLE_TYPES = {"IMP"}`，只檢查 IMP。

未驗證：hook-liveness 記錄（`.claude/hook-logs/_liveness/<session>.jsonl`）是否覆蓋全部已註冊 hook；若只部分 hook 寫 liveness，方案 B 的證據檢查需要退路（見 Solution）。

## Solution
### 結論

兩個缺口互相獨立：提醒只在 dispatch 送達（建票路徑全數漏接），以及 gate 前三項只比對字面（指向句即可過關）。只修其一不足：只提前帶入而 gate 仍比對字面，代理人會更早寫出字面句子；只改證據檢查而不提前帶入，代理人仍在 complete 才得知要求。選定方案 C（兩者並用，加 tests 排除）。

### 候選比較

| 方案 | 內容 | 誤擋方向 | 繞過成本 |
|------|------|---------|---------|
| A：建票時帶入 | create／set-where 判定 hook 範圍，追加四條 acceptance 模板並印提醒 | 不新增誤擋；模板若含 gate 關鍵詞反而會讓未填的模板直接通過（誤放），故模板須用不含關鍵詞的 <待填> 佔位，並由 gate 擋殘留佔位 | 低：改寫佔位為任意含關鍵詞句子即過，與現況相同 |
| B：gate 改證據檢查 | 前三項改查 Test Results／Solution 的 hook 日誌引文或 hook-liveness 輸出、fail-open/closed 宣告 | 會擋：未寫 liveness 記錄的 hook、無法在本 session 觸發的 hook（需重啟才載入，PC-BAL-033）。以過渡期 WARN 與「說明何以暫不驗證」的退路吸收 | 中：需貼出日誌行；偽造需捏造路徑與時間戳的日誌引文，屬刻意造假而非順手補句，且 PM 可用 grep hook-logs 一次驗證 |
| C：A + B + tests 排除（選定） | 建票時帶入、gate 改證據、寫入集全在 hooks/tests/ 時不視為 hook 票 | 同 B，另因排除而減少只改測試票的形式填寫 | 同 B |
| D：只改提醒送達（PreToolUse Agent hook 注入提醒） | 偵測 prompt 中的 ticket ID，查票後附提醒 | 不擋 | 不處理字面問題；且自行 create 後直接執行（不派發）的路徑仍收不到 |

### tests 排除的評估

應排除，條件為「寫入集全部落在 hooks/tests/」，有任一 hook 本體或 lib 路徑即仍命中。理由：hooks/tests/ 不會被 runtime 載入，實地觸發與 liveness 對其無對象，現況只能填「不改 hook 行為」（270.3.2、281.2.1）。誤放風險：測試被弱化使守衛失去鑑別力；這屬測試品質問題，由 Phase 4／審查與 test-assertion-design E2 管轄，不是 runtime 防護證據能攔的，故排除不降低 gate 的實際保護。
