### CAS 重試與全套件的互動（2026-10-14，F 線與 graph-project-docs-manager-bb 提出）

問題：0.5.0-W1-238.1 每次 CAS 重試都依當下的新 HEAD 產生不同的合併 commit，掛點對每次各呼叫一次。全套件需數分鐘，期間 main 幾乎必然前進（觀測：票務 CLI 的 chore commit 每分鐘數次，只改票檔），導致 CAS 失敗、重新產生 commit、再跑全套件；5 個 session 並行時可能活鎖。

| 候選 | 判定 | 理由 |
|------|------|------|
| A. 同 tree 快取 | 不採 | 並行時 HEAD 幾乎必然前進，tree 不同，快取無效 |
| B. 只比對新增變更 | 採用 | main 前進的主要來源只改票檔；差異落在豁免清單內即沿用驗證結果 |
| C. 合併期間獨占 main | 不採 | 所有 session 的票務提交在數分鐘內全部失敗或排隊 |

B 的豁免清單（保守）：`docs/work-logs/**/tickets/*.md` 與 `docs/work-logs/**/v*-main.md`。後者納入的理由：ticket track complete 的自動提交固定修改它，若排除，每次有人 complete 即觸發全套件重跑。`topic-assignments.txt` 等其他路徑一律重跑。

清單安全性證據（2026-10-14 實查）：`test/`、`integration_test/` 中提及 work-logs 的四個檔案（gap_report_test、tracking_schema_contract_test、carrier_path_lookup_test、test_copy）皆以路徑字串做比對，不讀取實際檔案；hooks 測試中組專案根路徑的兩個檔案（test_ana_ticket_metadata_validation_hook、test_agent_dispatch_validation_hook）亦不讀取票檔。
