## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 查證（2026-10-15，PM 前台）

**SYNTAX_PATTERNS 的目標輸出形態**（.claude/hooks/post-test-hook.py，常數 SYNTAX_PATTERNS）：六條樣式為 `Expected '…;})]'`、`Unexpected end of / token`、`unterminated string literal`、`unexpected end of … file`、`missing comma`、`invalid number format`，對應的是 Dart analyzer 與 JS 類編譯器的語法錯誤訊息。這批樣式隨框架在 2026-08-26 一次導入（cffdda1df），之後沒有修改紀錄，不曾針對 Python 設計。

**以 Python 3 實際訊息實測**（逐行套用上述樣式）：
- `SyntaxError: invalid syntax` → 無命中
- `SyntaxError: invalid syntax. Perhaps you forgot a comma?` → 無命中（樣式是 `missing comma`，與 Python 的措辭不同）
- `SyntaxError: unterminated string literal (detected at line 1)` → 命中 `unterminated string literal`。這是兩種語言措辭剛好相同，不是刻意涵蓋

**未命中時實際會怎樣**：_classify_errors 依 SYNTAX → COMPILATION → TEST_FAILURE → ANALYZER 的順序比對，取第一組有命中者。pytest 在收集階段遇到 SyntaxError 時，摘要會出現「N error」，落入 TEST_FAILURE 這一組。輸出端（評估訊息組裝處）的差別：
- SYNTAX_ERROR：「語法錯誤 - 簡化修復流程」「建議直接修復（無需開 Ticket）」
- 其他類型：「修復前強制評估」「必須開 Ticket 追蹤」

因此裸 Python SyntaxError 目前走的是比較嚴格的路徑，不會漏報。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論：不修

SYNTAX_PATTERNS 針對的是 Dart／JS 類編譯輸出，認不得裸的 Python SyntaxError 是因為設計範圍沒有涵蓋，並非刻意排除；但這個缺口不需要補，理由如下：
1. 未命中時會落入 TEST_FAILURE，走「必須開 Ticket」的嚴格路徑，不會漏報。
2. 補上 `SyntaxError` 樣式的方向是錯的。SYNTAX 在分類順序中排第一，任何輸出只要出現「SyntaxError」字樣，包括測試在斷言或測資裡談到 SyntaxError（本票的起因 0.5.0-W1-242.1 的測資就是這種情況），都會把真正的測試失敗降級成「直接修復、無需開票」。這是往寬鬆方向誤判，和 IMP-GPD-002 的「比對範圍過大而誤判」同一類。
3. 若要讓 Python 語法錯誤走簡化流程，須能分辨「被測程式碼的語法錯誤」與「輸出中提到 SyntaxError 的文字」，例如只比對 pytest 收集錯誤區段裡 traceback 最後一行。這屬於新需求，不是修補缺口；目前沒有實際案例要求，所以不另開票。
