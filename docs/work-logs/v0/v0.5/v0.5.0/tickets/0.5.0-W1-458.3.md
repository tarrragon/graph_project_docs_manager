## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

FlowStep 的 emits／consumes 引用不存在的 EVT id 時，目前沒有任何地方回報（459 第二項）：`lib/diagnostics/event_gap.dart` 以 EVT 節點為起點比對，引用不存在的 id 不會成為孤立事件或宣告不符；FR-10 的「flow 參照未解析」只涵蓋 `branch_from`／`return_to`／分支步 `next`（指向 step id），不涵蓋事件引用。用戶 2026-10-21 裁定：歸 Graph 的 flow 缺陷，新增一個子類（不重用「flow 參照未解析」）。

### 影響範圍

- 權威條文：主控 2026-10-21 同意以 SPEC-007 FR-09／FR-10 為權威（458 原寫「比照 443 先回寫 SPEC-003 §3.5」）。SPEC-003 §3.5、SPEC-004 §4.0.6 隨後同步
- SPEC-007 FR-09 子類表目前是 flow 四子類；規則段有三處寫死「flow 四子類」，FR-06 驗收的 graphDefects 計數式寫「FR-09 各 flow 子類的缺陷數」（不寫死數，可沿用）。新增後「四」要改，建議改為不寫死數（規則 10）
- 現況（2026-10-21，merge 09ed74ee4 後）：live 語料 11 個 EVT 節點、未解析事件引用 0 筆，事件宣告不符 0 筆。test-design 的應報案例須自造 fixture
- 實作端參照（458.4 用，本票不改）：`lib/graph/graph_built_event.dart` 的 `enum FlowDefectKind`（unresolvedReference、duplicateStepId、traversesUndeclared、traversesKeyAbsent）與 `FlowGraphDefect`{UC ID, step id, 欄位, 原始值}；`lib/graph/flow_subgraph_builder.dart`；`lib/diagnostics/graph_defect_gap.dart`；`lib/screens/gap_report/gap_report_models.dart` 的 `GapDescriptionKind`（flowRefUnresolved 等）與 `GapItemPointerType.flow`；`gap_report_descriptions.dart`；正規化行為見 `test/unit/graph/flow_events_normalization_test.dart`
- 約束：`lib/diagnostics` 不得 import `lib/schema/`（461 守衛 `test/unit/diagnostics/diagnostics_import_direction_test.dart`）

### 規格待決點（本票須寫定）

1. 判準：emits／consumes 元素（依既有正規化）不等於任何型別為 EVT 的節點 id；欄位值為 `emits` 或 `consumes`，原始值原樣
2. 同一步驟同一欄位重複引用同一不存在 id：比照 `traverses` 名稱未宣告「同一步驟內同一值重複出現只報一筆」
3. 被引用的 EVT id 本身是主圖 `duplicateId`：算存在（不報本子類），由 `duplicateId` 負責
4. 建圖不可用時不產生（FR-09 既有規則）
5. 程式識別名：FR-09 慣例是「識別名交實作票定」，458.4 命名；本票只定中文子類名與 ARB 文案（中英，L19 PM 定，114.16 前例）
6. 破洞項指向：歸 flow 小組，pointer 為 flow（選定 UC、攜帶 step id），與其他 flow 子類一致
7. 與 event_gap 的關係：本子類只管「id 不存在」；id 存在但 domain 不符仍由事件類破洞（SPEC-003 §3.5）負責，兩者不重疊

### 相關 Error Pattern

無匹配既有模式。注意 DOC-GPD-005（以替代指標寫判準）：判準直接以 EVT 節點 id 集合為準，不用 status 或檔案路徑推斷。
