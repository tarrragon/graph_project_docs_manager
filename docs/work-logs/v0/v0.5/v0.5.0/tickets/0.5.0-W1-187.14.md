### 範圍擴充：第二輪獨立審查的發現（2026-10-13）

本票原只承接「KILL 後只等一個輪詢間隔即判定」。對 0.5.0-W1-187.10 修正提交的第二輪審查（兩位審查者，皆直接呼叫 is_runner 實測）另有下列發現，併入本票並調為 P1。

誤認（實測為認定，應為不認定）：

- 首詞為絕對路徑且非已知執行檔時往後掃描：/usr/bin/vim /repo/.venv/bin/pytest、/usr/bin/less /repo/node_modules/.bin/jest、/usr/bin/git add /repo/tools/pytest、/usr/bin/grep /repo/pytest /tmp/file、/usr/bin/find /repo/node_modules/.bin/jest、/usr/bin/ssh host /usr/bin/python3 -m pytest、/usr/bin/sudo /usr/bin/python3 -m pytest、/bin/cat /x/pytest
- 直譯器後的腳本為絕對路徑且無已知副檔名時往後掃描：python3 /repo/run /data/pytest、python3 /repo/manage /srv/logs/jest、node /repo/server /var/data/vitest.ts、python /opt/app/serve /x/.venv/bin/pytest
- 路徑中目錄名以執行器名結尾且後接空白：/Users/me/pytest runs/bin/python server.py
- 選項的值被當成腳本詞：python3 -W /repo/pytest other.py、node --require /repo/node_modules/.bin/jest server.js

漏認（實測為不認定）：python3 -W ignore -m pytest、python3 -X dev /repo/.venv/bin/pytest、python3 -mpytest、node --require x.js 加 jest 路徑；jest 與 vitest 的工作程序。

成因：ps 的命令列欄位無法分辨詞界，上一輪以兩個往後掃描的迴圈猜測被空白切斷的路徑，被切斷的執行檔路徑與「普通程式後接路徑引數」在字串上同形。

裁決（主線程）：採保守案。刪除兩個往後掃描的迴圈，只看首詞；直譯器後的腳本詞本身不是執行器即不認定；帶值選項遇到即不認定。代價是執行檔路徑含空白、直譯器帶值選項時漏認，失效方向為漏認。不採改用 comm 欄位的根治案：需重寫測試替身，且審查實測某些 Python 發行版會重新執行自身使偽造的命令名消失，風險較高；若日後漏認成為實際問題再另案評估。

其他發現：

- 身份不符且 ps 查不到、或 ps 本身失敗時，回報為已終止，但本指令未送過訊號。
- TERM 後目標仍存活但身份已變時，印「身份已變」而結束碼為 0。
- 包住 terminate 的例外處理幾乎不可達。
- 測試：身份測試全數以假函式取代真實的 _same_identity，該函式恆回 True 時全檔仍綠；假環境以 raising=False 替換，函式改名後替換靜默失效；一項測試只斷言沒有 KILL，不斷言有 TERM 與回傳值；認定表的不該認案例全靠首詞非絕對路徑或選項擋下，上列誤認形態一例都沒有；測試檔區段註解寫入專案票號。

上列誤認與漏認字串皆為實測；其餘為讀碼推導。
