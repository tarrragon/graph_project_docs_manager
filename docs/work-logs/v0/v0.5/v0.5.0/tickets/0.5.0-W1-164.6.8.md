### Rationale Chain
- 0.5.0-W1-164.6.2 why: 164.6 盤點：zombie 的 branch -d／worktree remove 與兩處 git fetch 為寫入類 SIGKILL，不在 164.1 範圍；zombie is_worktree_dirty／is_branch_merged、confabulation run_command、branch-check 逾時靜默，逾時與正常完成在日誌同形（來源已完成，結論見 Solution）
- 0.5.0-W1-164.6.10 why: 164.6.2 審查發現三處測試缺口，皆不影響該票結案：(1) test_process_worktree_dead_clean_triggers_remove 沒替 get_worktree_branch 掛替身，會對執行環境跑真實的 git worktree list（唯讀，既有狀況）；(2) is_worktree_dirty 與 is_branch_merged 的 returncode 非 0 分支現在會寫一則執行失敗的 warning，但沒有測試；(3) lib 的 test_timeout_sends_sigterm_first 與 test_ignoring_sigterm_is_killed_after_grace 依賴 python 子程序在逾時前裝好訊號處理器，子程序啟動慢到秒級時前者假紅、後者照綠但沒測到 kill 路徑。後果：(1) 測試結果受執行環境的 worktree 狀態影響；(2) 新增行為無回歸保護；(3) 高負載下測試結果不反映程式行為。
- 0.5.0-W1-164.6.9 why: settings.json 給此 hook 的外層逾時為 30 秒；hook 內單一 worktree 的最壞情況為 status 10 + unlock 15 + remove 15 + log 10 + branch -d 10 秒，0.5.0-W1-164.6.2 之後三個寫入類呼叫各再加 5 秒寬限。git 真的卡住時，先到期的可能是外層逾時而非內部的溫和終止。已知 harness 逾時先送 SIGTERM，且 uv 多層啟動鏈下對外層送 SIGTERM 後 git 會成為孤兒並繼續持鎖（0.5.0-W1-164.6.3 實測 5/5）。後果：內部的溫和終止在最需要的情境可能沒機會執行，孤兒 git 之後若被 SIGKILL 仍會留下殘留鎖。此為既有結構，164.6.2 只是略為加重。
