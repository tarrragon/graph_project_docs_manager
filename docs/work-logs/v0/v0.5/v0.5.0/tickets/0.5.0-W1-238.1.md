## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
實作：worktree_manager.merge_branch_cas(branch, repo=None, base='main', pre_merge_check=None, message=None) 為合併主流程唯一入口；cmd_merge(ticket_id, pre_merge_check=None) 前置驗證後呼叫它並透傳掛點。
作法偏離 strategy 處：三方合併改用 git merge-tree --write-tree -z（git 2.38+，不使用任何 index，處理 rename，衝突 rc=1），取代手寫 read-tree + merge-file；隔離性更強，其餘護欄照 strategy。流程：解析 main/分支 -> 分支已被包含則中止 -> merge-tree -> tree 等於第一親代則中止（空合併守衛）-> commit-tree 雙親代 -> pre_merge_check -> update-ref CAS（舊值 CAS）。CAS 失敗整段以新 HEAD 重做。成功後只同步「index 與工作區皆等於舊 HEAD」的檔（diff-tree -z、ls-files -s -z、update-index --index-info -z、checkout-index -z），其餘列為未同步；共用 checkout 不在 base 分支則不同步；撞 index.lock 重試；輸出三平面核對。檔案清單全程 NUL 分隔，不經 shell。
重試預算：複製 ticket skill git_utils 的常數（退避 0.5/1/2 秒、前 3 次必做、額外重試累計等待 <=5 秒且牆鐘 <=20 秒），來源已註明於程式註解；worktree 套件無法 import ticket_system。
掛點規格（231.3 免讀碼）：簽名 (merge_commit_sha, target_ref, expected_old_sha, attempt) -> CheckResult(passed, reason)；時機 commit-tree 之後、update-ref 之前；回傳 passed=False 或拋例外 -> 不執行 update-ref、ref 不變、理由印出（[錯誤] 合併失敗：...）、exit 1；預設 None 直接 update-ref。傳 commit 而非 tree：git worktree add --detach 需 commit-ish，commit 已在物件庫無 ref 指向，可直接 worktree add --detach <path> <merge_commit_sha> 重現。重試語意：每次 CAS 嘗試依新 HEAD 產生不同合併 commit，每次嘗試都重新呼叫檢查，檢查成本隨重試次數倍增，是否快取或縮短由檢查端決定。已寫入 references/subcommands.md〈merge〉與 SKILL.md。
Phase 4：重構需要 否；技術債務 發現：worktree_manager.py 已逾 2000 行且承載多 domain（建議另票拆出 merge 模組，受本票檔案範圍限制未做）；品質 A。
