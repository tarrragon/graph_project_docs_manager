### 修法（worktree commit 28d2f5b26）

- 刪除 `_REMOVE_PATTERN`（正則 `git\s+worktree\s+remove`），改用 `lib.git_command_parse` 的 `contains_git_word` 加 `find_git_invocations(command, {"worktree"})`，接法與 worktree-branch-check 相同（0.5.0-W1-331），不另寫解析
- 只取 `args[0] == "remove"` 的呼叫。濾掉 flag 後，第一個運算元視為路徑
- 新增 `_resolve_remove_path`：路徑為相對且帶 `-C` 時，以 `inv.effective_dir` 為基準解析。`-C` 目錄含 `$VAR` 這類動態值時回傳 None，不檢查並記 warning
- 命令無法解析（例如未閉合引號）時 fail-open，記 warning
- 測試：新增 `TestGitDashCRemove`，共 6 個，全部用真實 git（tmp 內 init 加 git worktree add）

### 已知限制（另立 0.5.0-W1-386）

Guard A 的 worktree 清單查詢與 `git log main..<branch>` 仍在 hook 行程的 cwd 執行。若 `-C` 指向 cwd 以外的 repo，查不到對應分支，Guard A 會略過；Guard C 不受影響。本專案 PM 的 cwd 固定在專案根，目前不會觸發。

### 收緊分級前置盤點

見 Problem Analysis〈收緊分級前置盤點〉：文件中沒有以 `git -C … worktree remove` 移除 worktree 的範例，因此新判準不會改變任何文件範例的行為。

### 自檢結果

- [x] `git -C` 形式在修改前會被放行，修改後 Guard A／C 都能擋下（4 個紅燈轉綠）
- [x] E2：echo 與 `commit -m` 內的字樣不觸發；修改前 `commit -m` 案例會誤觸發
- [x] 主控條件：以 `git -C` 移除已合併且乾淨的 worktree 時放行
- [x] 解析失敗與動態 `-C` 目錄都 fail-open 並記日誌，與既有語意一致
- Phase 4：重構需要：否；技術債務：發現（Guard A 以 cwd 查 repo，已建 386）；程式碼品質：A；結論：以共用解析取代正則，兩支守衛的命令辨識收斂到同一入口

### 安全審查追修：無法解析時退回正則（worktree commit 305d5512d）

自動安全審查指出一處覆蓋倒退：`find_git_invocations` 回傳 None 時直接 fail-open，但舊正則對 `echo "git worktree remove <path>" | sh` 這類管線接 shell 的寫法仍會擷取路徑並檢查，改版後這類命令反而被放行。

- `_REMOVE_PATTERN` 保留，只作為無法解析時的退路，並加註說明
- 新增 `_regex_fallback_paths`：沿用舊版的取路徑邏輯，擷取到的路徑照常送 Guard A／C 檢查
- 只有在無法解析且正則也沒命中時才 fail-open；日誌記「無法解析命令（長度 N），退回正則擷取 N 個路徑」
- 通則已補進 IMP-GPD-008 解決方案（6bb8fae75）：汰換正則時，舊正則應保留作為無法解析時的退路
