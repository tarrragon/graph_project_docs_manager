## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 前置實驗：hook payload cwd（PM 執行，2026-10-08）

結論：payload cwd 反映的是代理人的基準工作目錄，可以可靠判別本票要防的失效模式。代理人隔離時，cwd 是它的 worktree；worktree 被清除、恢復後落回 main 時，cwd 是主 repo。同一個命令內的 cd 不會反映在 cwd 上。

| 探測（隔離代理人，worktree 存在時） | 命令內實際 pwd | hook payload cwd |
|------|------|------|
| echo（在 worktree） | worktree | worktree |
| 子 shell (cd main && pwd) | main | worktree |
| 裸 cd main && pwd | main | worktree |
| 下一次呼叫 pwd | worktree（裸 cd 不跨呼叫保留） | worktree |

| 失效狀態（worktree 已清除後恢復） | 證據 | hook payload cwd |
|------|------|------|
| 0.5.0-W1-105.1 恢復後的代理人（真實事件） | 主 repo hook-logs 中該 agent_id 的 6 筆 payload | 主 repo |
| 最小重現第二輪（W1-111） | 同上，4 筆 | 主 repo |

推論與設計影響：
- Bash 路徑以 payload cwd 判定「代理人基準目錄已落在主 repo」是可靠的，正好對準本票要防的失效模式
- 命令內 cd 或 git -C 指向主 repo 的情況，cwd 看不出來。但實測 runtime 在 worktree 存在時已會拒絕隔離代理人的 git -C 主 repo，以及過於複雜的 git 命令形式（探測第 7、8 步被拒），兩者互補：runtime 管 worktree 存在期間，本 hook 管 worktree 被清除之後（105.1 事件中 runtime 沒有攔下 git mv）
- 重播 fixture 可直接取自真實 payload：主 repo .claude/hook-logs/worktree-branch-check/worktree-branch-check-20261008.log 中 agent_id a8a4e24138605a3d3 的 6 筆（實作時複製到 fixture，去除 transcript_path 等與判定無關的欄位）
- 子代理人的 hook 日誌會寫到主 repo 的 hook-logs（探測代理人的紀錄在主 repo log 中可查），所以 liveness 可以從主 repo 驗證

前置實驗第 1 項完成。是否依裁決把 Edit／Write 升為 deny：本票仍以 warn 上線（裁決的「先 warn」）；實地觸發確認 warn 確實送達之後，由 PM 開承接票升級為 deny。

## Solution

### 結論

新增 `.claude/hooks/isolated-subagent-main-write-guard-hook.py`（PreToolUse，以 warn 模式運作），註冊於 settings.json 的 Bash、Edit、Write、NotebookEdit 四個 matcher。介入條件三者同時成立：payload 帶 agent_id；經 dispatch_tracker.get_active_dispatches 命中（agent_id 精確比對，或 agent_handle 正規式）branch_name == worktree 的 entry；寫入落在主 repo。寫入落點的判定：Edit／Write／NotebookEdit 看 file_path 是否在主 repo 根目錄下、且不在 .claude/worktrees/ 下；Bash 看 payload cwd 是否等於主 repo 根目錄，且命令含 git add／mv／rm／commit／restore --staged。條件成立時只輸出 additionalContext，不設 permissionDecision。ticket CLI 片段排除在外。合併 commit 75f852f8f（branch commit 846163f55）。

### 自檢結果

- 本 session 實地觸發確認（PM 執行）：以 isolation worktree 派發一個只讀的探測代理人（haiku），完成通知送達後確認它的 worktree 已被清除（14:55:27），再以 SendMessage 恢復它；pwd 為主 repo。接著它執行 `git add -- __w111_probe_nonexistent__`，該路徑不存在，git 報錯、沒有任何副作用。代理人回報收到 PreToolUse:Bash 的〈隔離失效警告〉全文；主 repo 的 working tree 無變更
- liveness 驗證方式：`.claude/hook-logs/isolated-subagent-main-write-guard-hook/` 以 info 級記錄介入（`warn: agent_id=... target=...`）與各種 fail-open 原因。本次實測該日誌出現 `[14:55:45] warn: agent_id=ab5be6f10628a9fcf target=cwd=<主 repo>`。PM 自身的呼叫沒有 agent_id，直接 return、不寫日誌，所以日誌只反映子代理人的呼叫
- 失敗語意：hook 自身拋例外時 return 0 放行，同時寫 stderr，並以 logger.critical 留下 traceback（有測試）；映射缺失、過期、狀態檔讀取失敗、缺 cwd 或缺 file_path 時，放行並記 info
- PM 審查補查兩點：(1) get_active_dispatches 不會濾掉 turn_ended_at 已設定的 entry，所以恢復情境下映射仍查得到；(2) 現行 dispatch-active.json 各 entry 的 agent_id 與子代理人 payload 的 agent_id 屬同一命名空間（實際比對 ae212a67b28ca393b 在兩邊一致），PM 派發時未給 name 也能對上
- 前置實驗與重播 fixture：見 Problem Analysis；E2 正向對照在 stub 階段為紅

### 已知缺口（不涵蓋）

1. Bash 的重導向（>、>>、tee）、sed -i、python -c 寫檔，以及不經 git 的 mkdir／cp／mv
2. git -C 指向主 repo，以及命令內 cd 到主 repo（payload cwd 不反映這兩種情況）。worktree 存在期間 runtime 已會拒絕這類命令，被清除之後就沒有防護
3. 其他 git 寫入：checkout -- <file>、reset、stash、merge、rebase、apply、cherry-pick、push，以及經 alias 的 commit
4. heredoc 中以 git add 起首的行可能誤報（只會產生警告，不會擋下）
5. 映射已被 TTL 清除（超過 24 小時），或派發時沒有記到 agent_id
6. MultiEdit 未註冊
