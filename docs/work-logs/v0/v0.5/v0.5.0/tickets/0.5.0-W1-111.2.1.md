## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 前置實驗：hook payload cwd（PM 執行，2026-10-08）

結論：payload cwd 反映的是代理人的基準工作目錄，可以可靠判別本票要防的失效模式。代理人隔離時，cwd 是它的 worktree；worktree 被清除、恢復後落回 main 時，cwd 是主 repo。同一個命令內的 cd 不會反映在 cwd 上。

| 探測（隔離代理人，worktree 存在時） | 命令內實際 pwd | hook payload cwd |
|------|------|------|
| echo（在 worktree） | worktree | worktree |
| 子 shell (cd main && pwd) | main | worktree |
| 裸 cd main && pwd | main | worktree |
| 下一次呼叫 pwd | worktree（裸 cd 不跨呼叫保留） | worktree |

| 失效狀態（worktree 已清除後恢復） | 證據 | hook payload cwd |
|------|------|------|
| 0.5.0-W1-105.1 恢復後的代理人（真實事件） | 主 repo hook-logs 中該 agent_id 的 6 筆 payload | 主 repo |
| 最小重現第二輪（W1-111） | 同上，4 筆 | 主 repo |

推論與設計影響：
- Bash 路徑以 payload cwd 判定「代理人基準目錄已落在主 repo」是可靠的，正好對準本票要防的失效模式
- 命令內 cd 或 git -C 指向主 repo 的情況，cwd 看不出來。但實測 runtime 在 worktree 存在時已會拒絕隔離代理人的 git -C 主 repo，以及過於複雜的 git 命令形式（探測第 7、8 步被拒），兩者互補：runtime 管 worktree 存在期間，本 hook 管 worktree 被清除之後（105.1 事件中 runtime 沒有攔下 git mv）
- 重播 fixture 可直接取自真實 payload：主 repo .claude/hook-logs/worktree-branch-check/worktree-branch-check-20261008.log 中 agent_id a8a4e24138605a3d3 的 6 筆（實作時複製到 fixture，去除 transcript_path 等與判定無關的欄位）
- 子代理人的 hook 日誌會寫到主 repo 的 hook-logs（探測代理人的紀錄在主 repo log 中可查），所以 liveness 可以從主 repo 驗證

前置實驗第 1 項完成。是否依裁決把 Edit／Write 升為 deny：本票仍以 warn 上線（裁決的「先 warn」）；實地觸發確認 warn 確實送達之後，由 PM 開承接票升級為 deny。
