### 實驗執行（8 格結果表）
| 格 | A 的狀態 | B 的 commit | HEAD 內容與 parent | 進行中狀態 | A 收尾結果 | 收尾他方操作 |
|---|---|---|---|---|---|---|
| 1a | cherry-pick 衝突未解決 | rc=128 "Committing is not possible because you have unmerged files" | 不變 | CHERRY_PICK_HEAD 保留 | 同樣 128 | 否（git 自己拒絕） |

| 2b | revert 衝突，A 已解決並 stage | rc=0 | 檔案 a.txt、doc.md；訊息 B-commit | REVERT_HEAD 被清 | `revert --continue` rc=128 | 是 |

| 3b | rebase 衝突，A 已解決並 stage | rc=0，輸出 `[detached HEAD ...]` | 單 parent；檔案 a.txt、doc.md；訊息 B-commit | rebase-merge 保留（rebase 仍在進行） | `rebase --continue` rc=0；最終歷史 feat2、B-commit、main、base：A 的第一個 commit（feat1）被吸收，其訊息消失，內容在 B-commit 內 | 是（內容夾帶加訊息錯置，未清狀態但 A 的 commit 被改寫） |
| 3c | `rebase -i` 的 edit 停下（無衝突，另有 amend 檔） | rc=0 | 檔案只有 doc.md，單 parent，detached | rebase-merge 保留 | `rebase --continue` rc=0 並停在下一個 edit；B-commit 成為 A 的 rebase 歷史的一部分 | 部分：未夾帶 A 的 staged 內容，但 B 的 commit 落在 A 的 detached 歷史、進入 A 的分支，B 以為提交在 main |

補充觀測：
- 1b、2a、2b 的 B-commit 皆為單 parent，沒有 MERGE_HEAD 那種兩 parent 的外觀證據，事後只能從訊息與檔案清單察覺。
- 狀態檔差異（3b 對 3c）：兩者都有 REBASE_HEAD 與 rebase-merge；edit 停下多一個 `rebase-merge/amend` 檔，衝突停下沒有。`git rev-parse -q --verify CHERRY_PICK_HEAD`、`REVERT_HEAD` 在 1b、2b 皆可解析。
- 分支：rebase 中 B 的 commit 落在 detached HEAD，rebase 結束後併入 feat；main 完全沒有 B 的 commit。

### 實驗發現
1. 已驗證：成立的格有 1b、2a、2b、3b；3c 部分成立。1a、3a 由 git 自己拒絕；1c 無進行中狀態。
2. 後果與合併相同的部分：內容夾帶（A 已 stage 的內容進 B 的 commit）、訊息錯置（B 的 -m 取代 A 的原訊息）、A 的 `--continue` 因狀態被清而失敗（cherry-pick、revert）。與合併不同：單 parent，無 MERGE_HEAD 式外觀特徵；rebase 不清狀態而是改寫 A 的歷史。
3. 守衛現況：bare-commit-guard 的 `_merge_in_progress` 只以 `rev-parse MERGE_HEAD` 判斷，上述四態全數放行（或僅依並行期 staged 範圍判定，與進行中狀態無關）。
4. 能否區分發起者與旁觀者：不能。git 狀態檔、環境與命令文字在兩者間逐項相同（沿用 0.5.0-W1-120.7〈重現實驗結果〉：ref 事件亦無法區分，僅父行程 argv 可區分 `commit` 與 `--continue`，不重測）。能區分的只有「停下原因」：衝突停下（commit 會夾帶 A 已解決的內容）與 edit 停下（rebase-merge/amend 存在）。
5. 發起者誤擋代價：衝突解決後發起者直接 `git commit` 是 git 自己的提示（"make a commit"），守衛擋下後發起者改用 `--continue`，一次重做，訊息可指路，代價低；edit 停下後新 commit 是分拆 commit 的正常用法（`--amend` 已被守衛豁免），誤擋代價較高但可改 `--amend` 或先 `reset` 再於允許路徑處理。
6. 未驗證：rebase-apply 路徑（am-based rebase）、worktree 內 rebase-merge 路徑（以 `git rev-parse --git-path` 取得可涵蓋，理論上正確）、Linux 行為。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 判定
| 格 | 成立 | 說明 |
|---|---|---|
| 1a、3a | 否 | unmerged 時 git 拒絕 commit |
| 1b、2b | 是 | 夾帶內容、訊息錯置、狀態被清、A 的 --continue 失敗 |
| 2a | 是 | 同上（REVERT_HEAD 被清） |
| 3b | 是 | 夾帶內容、A 的 commit 被吸收改寫，rebase 仍在進行 |
| 1c | 否 | -n 無進行中狀態，屬一般 staged 夾帶，由並行期 staged 範圍判定負責 |
| 3c | 部分 | 不夾帶 A 內容，但 B 的 commit 進 A 的 detached 歷史 |

### 方案比較
| 項目 | 甲：全態阻擋 | 乙：衝突態阻擋、edit 停下 WARN（推薦） | 丙：維持現狀並明列 | 丁：ref 事件層辨識（引用 0.5.0-W1-120.7） |
|---|---|---|---|---|
| 做法 | CHERRY_PICK_HEAD、REVERT_HEAD、rebase-merge 或 rebase-apply 存在即 deny | 衝突態（CHERRY_PICK_HEAD、REVERT_HEAD、rebase 無 amend 檔）deny；rebase-merge/amend 存在（edit 停下）WARN 放行 | 不改，文件列為殘留 | reference-transaction 以父行程 argv 區分 commit 與 --continue |
| 涵蓋 | 1b、2a、2b、3b、3c | 1b、2a、2b、3b 擋住；3c 提醒 | 無 | 全部（含別名、包裝），但只管掛載的 repo 事件 |
| 誤擋 | 發起者 edit 停下後的分拆 commit 被擋（需改 --amend 或繞道） | 衝突態發起者直接 commit 被擋一次，訊息指向 --continue；edit 停下不擋 | 無 | 人類終端與 IDE 一併受影響；父行程不可得時放行 |
| 誤放 | 無新增 | 3c 旁觀者 commit 放行（僅警告） | 全部 | 父行程不可得（IDE、libgit2） |
| 成本 | 低，沿用 _resolve_detect_dir | 低到中，多一次 rev-parse --git-path 與 amend 檔判斷 | 無 | 中，120.7.2 已評估，Linux 未驗證 |

推薦乙。理由：夾帶 A 已 stage 內容與改寫 A 歷史都發生在衝突態，該態發起者的正確收尾是 `--continue`，擋下代價低且與合併處置同一模式；edit 停下無法區分分拆 commit 與旁觀者 commit，而其危害只是 B 的 commit 錯置到 A 的歷史（不夾帶 A 的內容），誤擋代價高於危害，故降為 WARN。丁在 0.5.0-W1-120.7 已定位為後盾，不重測；其對 CHERRY_PICK_HEAD、REVERT_HEAD 的擴及並未驗證，不納入本次落地。
