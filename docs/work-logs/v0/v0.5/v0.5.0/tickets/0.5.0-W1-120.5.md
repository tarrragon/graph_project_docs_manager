## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 派發前補充（2026-10-14，D 線）

歸屬：協調 session 於 2026-10-14 改派 D 線；排序在 0.5.0-W1-120.4、0.5.0-W1-120.7 之後。

**建議的實驗矩陣**（how.strategy 的三種狀態再細分；「B」為旁觀者，對無關檔 doc.md add 後裸 `git commit -m`）

| 編號 | A 的進行中狀態 | 要記錄的觀測 |
|---|---|---|
| 1a | cherry-pick 遇衝突、未解決（unmerged 路徑存在） | B 的 commit rc；git 是否因 unmerged 拒絕 |
| 1b | cherry-pick 遇衝突、A 已解決並 stage | B 的 commit 是否帶走 A 的內容；CHERRY_PICK_HEAD 是否被清 |
| 1c | `cherry-pick --no-commit` 無衝突 | 同上；`-n` 時 CHERRY_PICK_HEAD 是否存在 |
| 2a | `revert --no-commit` | 同上，REVERT_HEAD |
| 2b | revert 遇衝突並解決後 stage | 同上 |
| 3a | rebase 遇衝突、未解決 | B 的 commit rc |
| 3b | rebase 遇衝突、A 已解決並 stage | B 的 commit 落在哪個分支（detached HEAD）、A 後續 `rebase --continue` 的結果與最終歷史 |
| 3c | `rebase -i` 的 edit 停下（無衝突） | 同 3b；edit 停下時裸 commit 本是 rebase 的正常用法，須判斷守衛能否區分 |

每格記：B 的 rc 與訊息首行、HEAD 的 parents 與訊息、HEAD 的檔案清單、`.git` 下 MERGE_HEAD／CHERRY_PICK_HEAD／REVERT_HEAD／rebase-merge／rebase-apply／sequencer 的存在與否、A 收尾動作的結果。

**判定「收尾他方操作」的準則**：B 的 commit 是否包含 A 的內容，或使 A 的進行中狀態消失或錯置。與合併不同，cherry-pick 與 revert 的裸 commit 產生的是單一 parent 的 commit，所以「兩個 parent」不能當判準。

**執行注意**：bash-git-protected-branch-guard 會擋 `git -C $VAR`（目標含 shell 展開無法靜態解析）。實驗寫成 scratchpad 內的腳本檔再以 `bash <腳本>` 執行，或以字面絕對路徑呼叫。

**與 0.5.0-W1-120.4 的關係**：若成立且決定擴充守衛偵測，偵測目錄沿用 120.4 落地後的解析順序（`-C` > payload cwd > project root），不另寫一套。
