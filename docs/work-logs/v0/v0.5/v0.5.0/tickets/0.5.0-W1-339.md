**(1) 錨點〈用 git 歷史量出熱點〉**：「腳本裡影響計數的設計」清單中「把子需求歸到同一個主題」之後新增一條：

- **同一功能的各輪追修另開新編號**：同一個功能經過好幾輪審查時，每一輪的追修常另開一個新需求，編號不同、彼此沒有父子關係，父子對照表也歸併不了。這些編號在排行裡各算一個，一個被反覆修改的功能看起來像好幾個需求在搶改同一個檔，這個檔因此排進前段，讀排行的人逐個 commit 歸類時，時間會先花在它身上。讀排行的人對排在前段的檔案，先用〈從修改紀錄找出職責邊界〉那條 `git log --format='%h %s'` 列出 commit 標題，把屬於同一功能的編號合併成一個主題，再用合併後的主題數與其他檔案比較；合併之後仍排在前段，才進入逐個 commit 歸類。腳本不讀標題的語意，哪些編號屬於同一功能要由人判讀。

（原文沒有絕對門檻，熱點是排行前段的相對位置，故寫「與其他檔案比較」而非「對照門檻」。）

**(2) 錨點〈拆分時與語言無關的做法：特徵測試、搬移與修改分開提交、單向依賴〉**（標題不改）：

a. 原句「做到這一點有三件事與語言無關，各語言的寫法放在各語言模組。」改為「做到這一點有三件事與語言無關，各語言的寫法放在各語言模組；要拆的邏輯在其他檔案另有副本時，還有一件事排在這三件之前。」

b. 在「**拆分前用特徵測試鎖住行為。**」段之前插入：

**拆分前先收斂散在多個檔案的重複實作。** 同一段邏輯在好幾個檔案各寫了一份時（例如讀取同一份設定的函式，在共用模組與幾支腳本裡各有一份），拆分的人先把它收斂成一份、其他檔案改為呼叫它，收斂合併之後再拆各個熱點檔。不先收斂有兩個代價：各份副本跟著需求各自被修改，同一個修正常常只落在其中一份，其餘幾份留著舊的行為；這段邏輯每改一次都要同時改好幾個檔（[散彈式修改](/design-principles/knowledge-cards/shotgun-surgery/)），這幾個檔都被推進熱點排行，各自拆完之後，每個新模組裡仍帶著一份副本，修改照樣要同時改好幾個新檔。所以收斂是這幾個拆分共同的前置：它自成一個需求、先合併，之後各熱點檔再以收斂後的版本為基準拆分，拆出的模組依賴那一份共用實作。收斂只把同一份知識合成一份；各份已經分歧時，先判斷是某一份漏修，還是兩類需求本來就要不同的行為，後者照 [DRY](/design-principles/knowledge-cards/dry-principle/) 卡片的判斷各留一份。前者在收斂時會改到漏修那幾份的行為，這個行為改動與合併副本分開提交，理由見下文〈搬移與修改分開提交〉。
