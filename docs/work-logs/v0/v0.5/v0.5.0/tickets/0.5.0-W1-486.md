#### 問題根因

讀碼版本：分支 `worktree-agent-af8d283e8e7f64264`（442896cd3，205.2.2 未合併版）。

1. **建圖不可用的產生條件**
   - `lib/graph/graph_builder.dart` 的 `buildGraph` 在 `resolveEdgeTypes(...).unavailableReason != null` 時回傳 `GraphBuildUnavailable(reason)`。
   - 原因列舉在 `lib/schema/edge_type.dart` 的 `EdgeTypeUnavailableReason`，共三類：版本超出已知範圍（`projectVersionOutOfKnownRange`）、缺正向基數（`missingForwardCardinality`）、條目被拒收且版本高於內建表。三類都由專案 `tracking_schema.json` 的內容決定。
   - 每一輪掃描（`lib/app/scan_round.dart`）都會重讀這個 JSON 再建圖。
2. **載入當下的路徑**
   - `lib/app/domain_view_loader.dart` 的 `_stateOfRound` 遇到不可用輪次，走 `_unavailableGraph`，落入 `DomainSchemaIncompatible(projectVersion: null)` 並記 level 900。
   - 所以載入當下不會進入 `DomainReady`。
3. **進入矛盾畫面的路徑**
   - `DomainReady` 建立之後，矩陣與泳道改讀 `lastCompletedRoundProvider`（`scan_round.dart`），任何一輪完成都會覆寫它。
   - 如果之後有新一輪完成（例如破洞報告重掃），而這段期間 JSON 被改成不可用，最後完成輪次就變成不可用。
   - loader 不監聽後續輪次，Domain 視圖狀態仍停在 `DomainReady`。
4. **泳道呈現**
   - `lib/screens/domain_view/domain_view_providers.dart`：`_eventOf` 遇到不可用輪次回 null，`domainSwimlaneProvider` 因此也回 null。
   - `lib/screens/domain_view/domain_view_screen.dart` 的 `_SwimlaneBody.build`：已有完成輪次，所以 `isProjectionPending` 為 false；`swimlane == null` 於是進入空泳道分支。
   - 結果顯示「需先選定 UC」（`swimlaneUcUnsetPrompt`，錨點 `state-domain-swimlane-uc-unset`），與「已選定 UC」的事實矛盾。
5. **矩陣同樣受影響（票面沒列）**
   - `domainMatrixProvider` 一樣回 null。
   - `_MatrixBody` 以 `matrix?.rows ?? const []` 渲染，畫面是零列矩陣，沒有任何提示。

**根因**：SPEC-001 §1 有兩則註記互相抵觸，而且沒有同步。
- 〈FR-13 回傳「圖不可用」時 Layout 不另處理〉的前提是「Domain 視圖不會在此狀態下進入」。這個前提只在載入時成立。
- v1.55〈矩陣與泳道同由掃描輪次衍生〉改成讀最後完成輪次之後，上述前提就失效了。
- `domainSwimlaneProvider` 的文件註解沿用了失效的前提。

#### 影響範圍

- **讀碼確認**：`domain_view_providers.dart`（`domainSwimlaneProvider`、`domainMatrixProvider`）、`domain_view_screen.dart`（`_SwimlaneBody`、`_MatrixBody`）、`domain_view_loader.dart`（`_stateOfRound`、`_unavailableGraph`）、SPEC-001 §1 的上述兩則註記。

#### 分析結論

- 建圖不可用在 Domain 視圖內只有一條出現路徑：`DomainReady` 期間有新一輪完成，且該輪建圖不可用。
- 現況：泳道誤落「泳道 · 尚未選定 UC」，矩陣靜默顯示零列。
- SPEC-001 §1 既有各列：只有「schema 不相容」描述的是同一成因；「載入失敗」處理非預期例外、「flow 未結構化」屬 UC 層，皆不適用。
- 結論：呈現方式要改規格（新增或改寫狀態轉換），**待用戶裁決**。

#### 候選（待用戶裁決）

| 候選 | 內容 | 規格依據 | 代價 |
|------|------|---------|------|
| A：退回「schema 不相容」阻擋態 | 最後完成輪次變成不可用時，`DomainReady` 轉為 `DomainSchemaIncompatible`，矩陣與泳道一起轉，行為與載入時的 `_unavailableGraph` 相同 | §1「schema 不相容」列，加上 loader 既有處置；需改寫 FR-13 那則註記，並在正常 · 矩陣、正常 · 泳道等列的退出路徑各補一條 | 狀態數不增加；轉換時丟失使用者的模式與選取；`projectVersion` 拿不到，只能顯示「型別表版本無法判讀」文案，可能與實際原因不符（載入路徑已有同樣的不精確） |
| B：在 DomainReady 內新增「圖不可用」列 | 新增「泳道 · 圖不可用」，矩陣另立一列或與泳道共用一列；保留標題與列結構，提示型別表已變更、無法建圖 | 比照 v1.55「泳道 · 投影準備中」獨立成列的論證 | 狀態數 +1 或 +2，SPEC-004 文案與錨點、§8.1、i18n 要同批更新；同一成因有兩種呈現（載入時阻擋態，執行中內嵌列） |
| C：只採可用輪次 | Domain 視圖略過不可用輪次，沿用最後一次可用的輪次 | 延伸 v1.55「輪次不是 Completed 時照常顯示上一輪」 | 違反同一則註記「兩者不會分屬不同輪次」，破洞報告與 Domain 視圖分屬不同輪次；型別表已壞卻沒有提示 |

**排除的做法**：沿用「泳道 · 投影準備中」。該列語意是「尚無完成輪次，且會自動重啟輪次」；本情境已有完成輪次、也不會自動恢復，沿用會讓提示失實。

**不論選哪一個**：FR-13 那則註記要同批改寫，`domainSwimlaneProvider` 的文件註解也要同步。
