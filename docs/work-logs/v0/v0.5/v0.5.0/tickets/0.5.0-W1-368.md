### 修法（worktree commit 9850eadf0、6a30181be）

- `worktree_manager.py`：`git worktree add` 改用常數 `WORKTREE_ADD_TIMEOUT_SECONDS = 120`，原本沿用 `run_git_command` 的預設 10 秒
- 新增 `_cleanup_failed_create(branch_name, worktree_path)`：add 失敗或逾時時依序執行 `worktree remove --force --force`、`worktree prune`，若分支存在再執行 `branch -D`；清分支失敗時寫 stderr 警告
- 清理範圍：`_cmd_create_validate_preconditions` 在 add 之前已確認分支與路徑都不存在，因此清理時存在的分支與路徑必定是本次建立的
- 錯誤訊息：輸出含 `timed out`（git_utils 逾時回傳的字面）時印「建立 worktree 逾時」，其他情況印「建立 worktree 失敗」
- 新增 `tests/test_worktree_create_failure_cleanup.py`（3 個測試，真實 git）：注入「add 真實執行並對路徑加 `lock --reason initializing` 後回報逾時」，重現實測時殘留的狀態

### 正向對照的射程

`test_preexisting_branch_not_deleted_on_failure`：分支已存在時，前置驗證在 add 之前就返回，所以這條路徑不會經過清理（斷言 `seen == []`）。只有在前置驗證保證之下，「清理不會刪掉既有分支」才成立；若日後放寬前置驗證（例如允許重用既有分支），清理必須改成只刪本次新建的分支。

### 自檢結果

- [x] 清理只作用於本次建立的 worktree 與分支（由前置驗證保證）
- [x] 雙 `--force` 有測試覆蓋：改成單一 `--force` 時測試轉紅
- [x] 逾時判定依賴 git_utils 回傳字面 `timed out`；字面若改變，只會影響訊息分類，不影響清理
- Phase 4：重構需要：否；技術債務：無；程式碼品質：A；結論：新增一個 15 行內的清理函式，職責單一

### 主控放行條件：清理每步寫入日誌（worktree commit b3fb8d267）

- 新增 `_run_cleanup_step`：worktree remove、worktree prune、branch -D 三個步驟，不論成功或失敗，每步都經 `emit_gate_line` 寫一行到 `.claude/logs/worktree-merge.log`（同一行也印到 stdout），前綴為 `[建立清理]`
  - 格式：`[建立清理]<步驟>｜target <路徑或分支>｜結果 成功/失敗`；失敗時附 `｜輸出 <git 輸出摘要，換行改空白，最多 200 字>`
  - 沿用既有機制，不另立 logging 設定。`_emit_result` 寫檔失敗只會發出警告，不中斷清理
  - 前綴與 `[合併前測試]` 不同，因此名額預估不會讀到這些行
