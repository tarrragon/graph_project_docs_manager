## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

五個後設欄位在票務 CLI 中，寫入端與消費端多數沒有接上：
- creation_accepted 的閘門註冊在 UserPromptSubmit，看不到代理人經 Bash 執行的 claim。
- tdd_phase 只在 claim 帶 --as 時推論，complete 不推進。
- who.history 沒有任何寫入端。
- Completion Info 的 Review Status 與 Executing Agent 在 complete 時保留現狀。

逐欄位的寫入端、消費端與證據見 Solution 第一、二節。

### 影響範圍

- 已驗證：v0.5.0 共 357 張票，creation_accepted 全為 false。已完成的 225 張中，tdd_phase 停在 phase1 的有 111 張，who.history 全為空。閘門日誌 8 日 1379 次檢查，真實 claim 為 0 次。
- 已處置：四張子票 0.5.0-W1-214.1.1 至 214.1.4 皆已合併並完成；本 session 之後建立的票已實測 creation_accepted 為 true、who.history 有追加、Executing Agent 與 Review Status 有寫入。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

五個欄位中，只有 tdd_phase 有部分寫入端接上；其餘四欄位的寫入端或消費端不存在、或兩端沒有接上。creation_accepted 閘門不阻擋的原因是註冊在 UserPromptSubmit：它只解析使用者輸入的文字，而 claim 是代理人經 Bash 工具執行的，從不經過這個事件。

### 一、逐欄位：寫入端、消費端、是否接上

| 欄位 | 寫入端 | 消費端 | 接上 | v0.5.0 現況（228 張已完成／已關閉） |
|------|--------|--------|------|------------------------------|
| creation_accepted | 建票固定寫 false（ticket_builder）；`track accept-creation` 改 true；遷移補 false | creation-acceptance-gate-hook（UserPromptSubmit） | 否，見第二節 | 全部 357 張皆 false |
| tdd_phase | 建票寫初始值；`claim --as` 依 registry 推論（`_apply_auto_tdd_phase`，只在帶 --as 且 agent 有對應時）；`track phase` 手動 | `_get_completed_phases_in_chain`（Phase 前置警告，讀已完成票的 tdd_phase 當作「已完成的 Phase」）；dispatch_recommender | 部分：PM 不帶 --as 的 claim 不更新，complete 也不推進 | 已完成 225 張：phase1 111、null 54、phase3b 46、phase0 8、phase2 6 |
| who.history | 建票寫 `{}`；`_apply_claim_identity` 只做 setdefault | 無 | 否：沒有任何程式碼追加內容。track_validate 的提示「claim 自動設定 current/history」與實作不符 | 已完成 225 張全為空 |
| Completion Info 的 Review Status | 建票寫 pending；`set-completion-info --review-status`；structured body | 無（complete 依 docstring「無權威資料來源」保留現狀） | 否 | 依 214 取證，pending 147 |
| Completion Info 的 Executing Agent | 建票寫當時的 who；complete 只在值為 placeholder 時填入；`set-completion-info --agent` | 無 | 否：set-who 改派不同步。本 session 為了通過身份守衛，於 complete 前把 who 改為 PM，執行者資訊即從 frontmatter 消失，只剩 body 的 Executing Agent 保留建票時的值 | 依 214 取證 |

### 二、creation_accepted 閘門未阻擋的原因與證據

- 註冊：`.claude/settings.json` 的 UserPromptSubmit 事件。程式以 regex `ticket\s+track\s+claim\s+(\S+)` 解析 `prompt`。
- 證據：`.claude/hook-logs/creation-acceptance-gate/checks-*.log`，2026-10-07 至 10-14 共 8 日 1379 次檢查。其中 1375 次為「TicketIDs: none」；另 4 次命中的都是代理人回報（agent-message hand-back）文字中提到的 claim，擷取到的 ID 帶尾隨標點（例：「0.5.0-W1-127`），exit」），查無票檔，依「檔案不存在即通過」放行。真實的 claim 一次都沒有被檢查到。
- 潛在誤擋：若代理人回報文字中出現「ticket track claim <乾淨的 pending 票 ID>」，閘門會以 exit 2 擋下那則回報，與票是否被認領無關。
- `accept-creation` 的使用者：唯一的流程引用是 pm-rules/worktree-operations.md 一列清單項；無任何 hook 或 CLI 流程會呼叫它，故全庫皆為 false。

### 三、處置候選

| 欄位 | 候選 | 建議 |
|------|------|------|
| creation_accepted | (a) 移除 UserPromptSubmit 註冊，欄位改由建票在 checklist 等硬閘門通過後直接寫 true（建立當下的驗收已由 enforce_checklist、可攜問題查重等閘門承擔）；(b) 改註冊為 PreToolUse(Bash) 並補 accept-creation 流程——一上線即擋下現存 109 張 pending 票的 claim，須先回填；(c) 移除欄位與 hook | (a)；需用戶裁決，因涉及閘門去留 |
| tdd_phase | complete 時若 `tdd_phase_source` 不是 manual，寫為 tdd_stage 的最後一個階段 | 接上，使前置警告讀到的值為真 |
| who.history | set-who、claim --as、`reassign_who_from_pm_if_takeover` 改變 current 時，追加 `{時間: 原 current}`；修正 track_validate 提示 | 接上 |
| Executing Agent | complete 時以 who.history 中最後一個非 PM 的執行者填入（不再只填 placeholder） | 與 who.history 同票 |
| Review Status | complete 時依 acceptance-gate 已計算的 Phase 4 審查證據結果寫 reviewed 或 n/a；無證據維持 pending | 接上 |
