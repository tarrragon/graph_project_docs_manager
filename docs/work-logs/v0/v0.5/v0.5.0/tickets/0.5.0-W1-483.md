### 根因（`.claude/skills/doc/doc_system/core/uc_registry.py`；hook 只是消費端）

1. kebab-case 片段被當成 UC 編號：`UC_TOKEN_RE` 的開頭是 `\b[Uu][Cc]-`。`-uc-` 中的連字號在 `u` 前面形成字詞邊界，所以複合識別符中的 `uc-unset` 會被擷取出來。
2. 豁免檢查和違規判定用的不是同一種形式：`is_violation_token` 先用原始字面 `uc-unset` 比對 `UC_PATTERN_EXEMPT_RE`（`^UC-[A-Z][a-zA-Z]`），小寫字面不會命中，所以不豁免；之後才正規化成 `UC-UNSET` 判定格式不符。如果豁免檢查也用正規化後的形式，`UC-UNSET` 就會符合 UC-Pattern 豁免（主控實測 exempt(norm) 為真）。這和函式 docstring 說的「判定一律以正規化後形式為準」互相矛盾。
3. 副檔名被當成子樹段：value 後面的 `(?:\.[A-Za-z0-9]+)*` 原本是給 `UC-01.4` 這類子樹寫法用的，但它會把 `.md` 也吃進去，於是 `UC-02.md` 被判成格式不符的偽子樹。

### 框架問題兩條判準（逐條套用）

- 抽象可攜：成立。任何 consumer 在測試或程式中用到含 `-uc-` 片段的 kebab-case 識別符，或以 `UC-xx.md` 檔名引用 UC 文件，都會觸發；把專案名與路徑換掉，敘述仍然成立。
- 根源在 `.claude/` 通用資產：成立。regex 與判定順序都在 `.claude/skills/doc/doc_system/core/uc_registry.py`，會隨 sync 傳遞。
- 結論：屬框架問題。不是 P0/P1（hook 只 WARN、不阻擋），依 2026-10-20 修補節奏，觀測進 issue 後關閉本地票。
