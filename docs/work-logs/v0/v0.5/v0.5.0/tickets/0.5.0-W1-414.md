### L14（-3e）於 411 查證時得到的相關事實（2026-10-20，Claude Code 2.1.304，從 binary 內建的 statusLine 說明文字取得）

- statusLine 命令的 stdin JSON 有 `context_window` 物件，欄位如下：
  - `total_input_tokens`：目前 context 內的輸入 token，含 cache 讀寫
  - `context_window_size`
  - `current_usage`：最近一次 API 呼叫的 input、output、cache_creation、cache_read
  - `used_percentage`、`remaining_percentage`：已算好的百分比，還沒有訊息時為 null
- 推論：狀態列可以直接讀上述欄位顯示 context 用量，不需要解析 transcript；和 411 的狀態列 wrapper 共用同一份 stdin。
- 未定案：狀態列只有用戶看得到，模型看不到。「超過 400K 時提示模型做 compact 或寫 handoff」仍需要一個模型看得到的管道，例如 hook 的 additionalContext 或 exit 2。參照 quality-baseline 規則 4「提醒類輸出須宣告受眾」。細節見 411〈重現實驗結果〉補充段。
### 問題根因（L14 填寫）

- 直接原因：context-depth-warning-hook 以 stderr 加 exit 0 輸出，Stop event 的這個管道模型看不到，所以提示從未送達（實測見〈重現實驗結果〉）。
- 次要原因：門檻 180K 的依據是舊模型在 200K window 下的 malformed 實測，不是 1M window 下累積成本的考量；去重 state 在 context 降回門檻以下時不會重設。
- 影響範圍：所有長時間執行的 session。模型不會主動提出 compact 或 handoff，context 持續累積。

### 相關 Error Pattern

quality-baseline 規則 4「提醒類輸出須宣告受眾」：exit 0 加 stderr 對模型不可見，對應案例為 IMP-GPD-004。本票是同一類問題的又一實例，不另立 error-pattern。

### 實驗發現

已驗證的事實：
- 只寫 stderr、exit 0 的 Stop hook 提示，模型看不到。同一個 Stop event 改以 additionalContext 輸出就看得到，本 session 的對話紀錄可佐證。
- cache_read 佔合計的 99% 以上。現有 hook 只取 cache_read，和合計值只差約 1 到 2K，量測口徑的差異對 400K 門檻不重要。不過合計值才和 statusLine 的 `total_input_tokens` 同一個口徑。

推論（依程式碼閱讀，未實測）：
- 現有的去重邏輯是 `tier > last_warned_tier`，state 依 session_id 保存。`/compact` 之後 context 會降回門檻以下，若 session_id 不變，state 不會重設；context 再長回原本的 tier 時不會再提示。sessionId 在 compact 後是否改變，尚未實測。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論（L14／session-naming，2026-10-20）

1. **偵測**：沿用既有的 context-depth-warning-hook（Stop event），不另寫新 hook。量測口徑改為 transcript 主線最後一則 usage 的 input + cache_creation + cache_read，與 statusLine 的 `total_input_tokens` 一致。門檻改為用戶指定的 400K，並開放以環境變數覆寫，讓 window 較小的 consumer 自訂。
2. **送達**：輸出改走 `emit_hook_output("Stop", additional_context=...)`。本 session 已實測，Stop event 的 additionalContext 會送達模型。依 quality-baseline 規則 4，受眾是模型。stderr 只保留給 hook 自身的錯誤。
3. **提示內容**：說明目前的 context 大小，並給出兩條路，讓模型主動向用戶提出：
   - 請用戶執行 `/compact`。這是內建命令，模型無法觸發。
   - 先把進度寫進票面、建 handoff，再請用戶開新 session（`claude -n <線主題>`）。這條路銜接 session-naming.md §4。
4. **去重**：保留分層（每 50K 一層），但 context 降回門檻以下時要重設該 session 的 state，否則 compact 後再長回同一層不會再提示。
5. **顯示**：用戶端不另做。cc-statusline 已經顯示 context 百分比，411.1 的 wrapper 原樣保留這一行。

### 候選方案

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 改造既有 hook：口徑、門檻、輸出管道、去重重設 | 註冊、state、測試都沿用；改完就修好「模型看不到」這個既有缺陷 | 180K 這一層原本防的是舊模型 230K 之後 malformed tool-call 的問題，改成 400K 等於放棄這一層。依據是舊模型在 200K window 下的實測，現行模型沒有對應數據 |
| B | 另寫新 hook 專管 400K，既有 hook 只把輸出改成 additionalContext | 兩個門檻各自保留 | 同一個 Stop event 有兩個深度提示，180K 到 400K 之間每 30K 提示一次，提示疲勞 |
| C | 只在狀態列加 400K 標記 | 零 hook 改動 | 狀態列只有用戶看得到，模型不會主動提 compact 或 handoff，不符合需求 |

**方案 A 的取捨**：180K 層的依據是舊模型的實測，在 1M window 的現行 session 中每回合都會觸發，但從未送達，實際效果一直是零。改成 400K 不會讓現況變差。若之後有現行模型的 malformed 數據，再以環境變數調整門檻。
