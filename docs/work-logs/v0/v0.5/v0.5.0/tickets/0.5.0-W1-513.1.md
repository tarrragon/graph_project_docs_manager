## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 衝突條文出處（L33，2026-10-31，自 513 調查移入）

- SPEC-003〈破洞報告〉狀態轉換表「無法判定破洞」列：`action-gaps-rescan` → `state-gaps-scanning`。同檔互動表「重新掃描」列：點擊後 `state-gaps-none`、`state-gaps-found` 或 `state-gaps-undeterminable` 消失。
- SPEC-001 §5「無法判定破洞」列：可用操作含「重新掃描」。
- SPEC-004 第 18 項（撰寫期決策）：重新掃描放在頁面級動作區，只涵蓋無破洞與有破洞兩態。
- 程式碼：`lib/screens/gap_report/gap_report_screen.dart` 的 `GapReportHeaderTrailing`，狀態不是 `GapReportNoGaps`／`GapReportFound` 時回傳 `SizedBox.shrink()`。
- 使用者可見後果：原因說明三選一的第三項文案為「掃描時發生非預期錯誤，無法判斷破洞；請重新掃描」（`gapsUndeterminableReasonScanFailed`），畫面上卻沒有可按的重新掃描鈕。465 H2 截圖即此狀態。

用戶裁定（AUQ，2026-10-31，主控轉達）：「無法判定破洞」狀態加上重新掃描鈕 `action-gaps-rescan`，以 SPEC-003 為準；SPEC-004 第 18 項與 GapReportHeaderTrailing 跟著改。本票依此落地為實作（改型或衍生 IMP 由 L33 決定並寫明）。記錄於 0.5.0-W1-349〈513 回報與用戶裁定〉。
