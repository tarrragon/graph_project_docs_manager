## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

守衛把登記檔中「任何一筆存在的條目」都當成有效佔用；條目的移除只有兩條路徑，而本票兩筆條目都落在兩條路徑之外。建議以「擁有者 session 已結束」為過期判準，在守衛讀取時過濾。

### 一、守衛判定佔用所讀的欄位，與不視為過期的原因

| 項目 | 現況 |
|------|------|
| 讀取 | `get_active_dispatches` 回傳 `dispatches` 全部條目；`_with_live_declared_files` 依各筆 `ticket_id` 改讀票面現行 where.files；`_staged_scope_is_safe_for_bare_commit` 以有宣告範圍者做子集／不相交判定 |
| 未讀 | `turn_ended_at`、票的狀態、`session_id` 對應的擁有者存活 |
| 不讀 `turn_ended_at` 的原因 | 守衛 docstring「五修正」刻意如此：回合結束後代理人轉入 idle 仍存活，可被 SendMessage 喚回繼續寫檔，條目存在即代表「未被確認終止」 |
| 條目移除路徑 1 | complete 時 `clear_dispatch_by_ticket_id` 清掉同票條目——只在票轉終態的那一刻觸發一次 |
| 條目移除路徑 2 | `cleanup_expired`：回合未結束者以 `dispatched_at` 起算 1 小時；回合已結束者以 `turn_ended_at` 起算 24 小時（`TURN_ENDED_MAX_AGE_HOURS`） |
| 墓碑 | 只用來銜接同步派發時 SubagentStop 早於 PostToolUse 的數秒間隔（TTL 600 秒），與佔用判定無關 |

本票兩筆條目為何落在兩條移除路徑之外：
- `0.5.0-W1-182` 的驗收稽核派發發生在該票完成之後（用戶 2026-10-13 指示補做三張已完成票的稽核與 Phase 4 審查，見 0.5.0-W1-214），complete 早已執行過，路徑 1 不會再觸發；回合結束於 10:29，24 小時 TTL 未到。
- `0.5.0-W1-164.6` 的盤點派發所屬票仍為 in_progress，路徑 1 不適用；同樣在 24 小時 TTL 內。

### 三、過期判準候選與誤放行風險

| 候選 | 本次會清掉的會擋條目 | 誤放行風險 | 判定 |
|------|---------------------|-----------|------|
| A 回合已結束（`turn_ended_at` 有值） | 11／11 | 高：idle 代理人可被喚回寫檔，與「五修正」的保守存活語意直接衝突；存活 session 的 8 筆合法佔用也會一併失效 | 不採 |
| B 所屬票已完成 | 10／11（漏 164.6） | 中：完成後的補做派發（稽核、追修）若會寫檔，即被當成無人佔用；且未完成票的殘留條目無法處理 | 不採為主判準 |
| C 擁有者 session 已結束（session_id 不在 pm-registry 的 sessions） | 11／11 | 低：背景代理人隨擁有者 session 的程序結束而結束，session 已 graceful release 後其代理人不可能再寫檔。風險僅在 registry 讀取失敗時把存活 session 誤判為已結束——既有分類已將讀取失敗獨立為 registry_unavailable，不得視為已結束 | 建議採用 |
| C' 擁有者 heartbeat 逾 30 分鐘（orphan_suspected） | — | 中：既有實測有 55 分鐘的心跳假陰性案例（pm_registry 模組 docstring），存活 session 會被誤判 | 不納入，只對 orphan_confirmed 生效 |

### 四、建議落點

守衛讀取時過濾（不採登記端清理）：
- 登記端清理須依賴 SessionEnd 觸發，而 SessionEnd 可能漏觸發；且 session-registry-start-hook 的 SessionStart 孤兒掃描依賴這批條目存活才能回報，刪除會使該掃描失去輸入。
- 讀取時過濾不改登記檔，只改守衛的佔用判定；過濾掉的條目寫 warning 日誌（含 ticket_id 與 session_id），DENY 訊息若仍出現已結束 session 的條目即為 registry 讀取失敗的訊號。
- 擁有權分類目前實作在 session-registry-start-hook 的 `_classify_ownership`，守衛若另寫一份會形成兩份判準；建議先抽到 `.claude/lib/`（dispatch_tracker 或 pm_registry）由兩者共用。
- 與 0.5.0-W1-120.4／120.7 同改 bare-commit-guard-hook.py，但函式不重疊（120.x 改 MERGE_HEAD 偵測與命令解析，本建議改派發條目過濾）；動筆前跑 `ticket track conflicts`。
