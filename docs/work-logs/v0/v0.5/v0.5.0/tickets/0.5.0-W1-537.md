### 觀測與 PM 核對（2026-10-30，L18）

- 來源：532.2 的 parsley 回報原文：「第一次用 Bash 的 python heredoc 改了 4 個測試檔，guard hook 當下沒擋，之後才擋住同類寫法。改用 Edit 完成 blocked_state 的最後一處替換和 import 移除。這個 hook 對 test/ 的 Bash 寫入攔截不一致。」
- 發生位置：隔離 worktree `.claude/worktrees/agent-a15be0e639bdadaf4`，產出 commit d5e1324ea。
- PM 核對產出無害（依規則 6 保留）：4 檔替換前後的案例宣告數、`expect(` 數、通過數都相同（empty 16/20/27、load_prompt 11/14/16、blocked 28/39/48、switcher 17/32/35）；diff 中改到的斷言行只有 3 條，都是預期的 helper 替換。
- 證據缺口：「之後擋下」是哪一支 hook、擋下時的訊息原文，以及第一次寫入的完整命令，只存在代理人 transcript（session 專屬的暫存位置，session 結束即消失），PM 沒有取得原文。分析時可以從 `.claude/hook-logs/` 中 bash-edit-guard、bash-write-boundary-guard、isolated-subagent-main-write-guard 在 2026-10-30 的紀錄還原。
- 待分析的疑點：兩次都是 Bash 寫入 test/，第一次放行、第二次擋下。可能是不同 hook 的判準差異（例如對直譯器內嵌腳本與重導向的判斷不同），也可能同一支 hook 的模式 A 只命中特定寫法。#103 記載模式 A 只認得 `sed -i` 與 `perl -pi`。

### 命令原文取證結果（2026-10-30，L18）

**第一次未被擋下的寫入**（parsley 逐字回報）：
- 呼叫方式：`python3 -I - <<'EOF'`（`-I` 隔離模式，stdin heredoc）
- 寫檔方式：自訂函式 `sub(path, pairs)`，內部用 `s=open(base+path).read()` 讀檔，用 `open(base+path,'w').write(s)` 寫回
- 目標路徑：`base='test/unit/components/'`，相對路徑。之後的回報被截斷，命令執行時的 cwd 未取得，推定為 worktree 根目錄

**未取得的原文**：之後被擋下的命令全文、擋下時的 hook 名稱與訊息、兩次的 cwd。parsley 補報時因 API 錯誤中止（`Agent terminated early due to an API error`，request id req_011CgXwqd8yHSqpJwUZBBtSC），沒有回報到這幾項。

**hook 日誌查證**（`.claude/hook-logs/bash-write-boundary-guard/bash-write-boundary-guard-20261030.log`）：
- 14:08–14:26（parsley 執行期間）共有 130 筆 `未偵測到明確的 test/lib/dart 寫入目標，允許（fail-open）`，沒有 deny 或 block 紀錄。
- fail-open 路徑只記一行判定，**不記錄命令內容**；有記 cmd 的只有 `decision=allow source=main` 這類行。所以放行的那一筆無法從日誌對應回命令，日誌也看不出這支 hook 有沒有對子代理人的命令生效。整份日誌的 source 欄只出現過 `main`（365 筆）。
- 推論（未驗證）：`open(base+path,'w')` 這種以變數拼接路徑的寫法，靜態解析抓不到「明確寫入目標」，所以走 fail-open。之後擋下的應是另一支 hook；這段期間更新過的日誌有 file-ownership-guard-hook、branch-verify、worktree-commit-before-dispatch 等，PM 沒有逐一查證。

**本次另外觀測到的缺口**：fail-open 放行時不記命令，使「放行了哪些寫入」無從事後稽核。這與 quality-baseline 規則 4（Hook 失敗必須可見）及 #103 的「命中僅警告」相關，關係判定由主控處理。
