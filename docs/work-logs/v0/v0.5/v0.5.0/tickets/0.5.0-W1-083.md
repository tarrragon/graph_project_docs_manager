# Execution Log

## Task Summary

tracking_schema.json 的 schema_generated_at_framework_version 取自重產當下的 .claude/VERSION；VERSION 由 sync-push 升版後，任何一次重產都會使 JSON 產生版本高於 App 內建 builtin_schema_version，App 依 CLAUDE.md §6 不提供內建表降級；staleness 守衛把該鍵列為 VOLATILE_KEYS 忽略，重產時沒有任何訊號提醒同步內建副本

---

## Problem Analysis
### 問題根因

`doc schema export`（`.claude/skills/doc/doc_system/commands/schema.py` 的 `_read_framework_version_at_generation`）把 `schema_generated_at_framework_version` 寫成產生當下的 `.claude/VERSION`。這個值跟 schema 內容有沒有變無關，每次 sync-push 升版之後只要重產就會升高。App 閘門（`lib/schema/schema_version.dart` 的 `classifySchemaVersion`）逐段做整數比較，產生版本高於內建版本（`assets/schema/builtin_schema_version.json`，2.60.13）就判為 `HigherThanBuiltin`，不提供內建表降級。staleness 守衛把這個鍵列在 `VOLATILE_KEYS` 並忽略它，所以這個鍵的變動完全沒有強制層。現況唯一的防線是人工改回：commit b59ffd1d9 的 diff 就是 `2.65.0` 改回 `2.60.13`，doc CHANGELOG 1.22.7／1.23.0／1.24.0 三處都寫了「刻意維持 2.60.13」。

**框架問題兩條 AND 判準（逐條套用，取代建票時 PM 的初判）**：
1. 抽象可攜：成立。把專案名換掉之後，命題仍然成立：「產生器把框架版本當成型別表版本蓋章，以該欄做相容閘門的消費端在零內容變更下判為不相容，而守衛又把該欄排除在比對之外」。初判說「其他 consumer 沒有 App 內建副本」，這點不構成反證。App 讀的是**被掃描專案**的 JSON（`lib/workspace/framework_signal_probe.dart` 讀目標專案的這個欄位），所以任何 consumer 在 VERSION 升版後重產，都會被這個 App 擋下。受害面遍及所有 consumer，不限本專案。
2. 根源在 `.claude/` 通用資產：成立。決定產生版本值的是 `.claude/skills/doc/doc_system/commands/schema.py`，忽略該鍵的是 `.claude/hooks/tracking-schema-json-staleness-guard-hook.py`，兩者都是通用資產。App 閘門的判定本身正確，它只是忠實執行該欄所宣稱的語意。

結論：屬於框架問題。

**dedup**：`section_comment.py dedup --keywords schema_generated_at_framework_version tracking_schema.json VOLATILE_KEYS 產生版本`。命中 #98、#99、#104（都是 comments 命中）；「產生版本」的 30 則命中都是無關詞。#98 的既有 observation 記錄了「刻意維持 2.60.13」這個處置，但沒有以產生器作為根因的條目。判定關係為「引用」：屬於 #98（doc skill 建立端契約）的新面向，不另開 issue。#104 是副本抄值的同型問題，在 observe 內交叉引用。

### 影響範圍

已驗證：
- 寫入點只有一處：`schema.py` 的 `build_schema_dict`，它呼叫 `_read_framework_version_at_generation`。
- 讀取點有六處：`lib/schema/schema_version.dart::schemaVersionOf`；`lib/workspace/framework_signal_probe.dart`（讀被掃描專案的 JSON）；`lib/screens/domain_view/domain_view_schema_version.dart`（讀內建資產）；`tool/spec006_reference.py`、`tool/spec007_reference.py`（快照）；`assets/schema/builtin_tracking_schema.json` 與 `builtin_schema_version.json`（兩份內建，值都是 2.60.13）。
- 現有測試都沒有比對「框架 JSON 與內建版本」：K4（`builtin_schema_version_contract_test.dart`）只比兩份內建資產；漂移測試（`domain_view_schema_drift_test.dart`）只比 `.claude/VERSION` 與內建版本，門檻 `kSchemaVersionDriftThreshold = 25` 個次版號，現況 77-60=17，仍是綠燈。

未驗證：W1-070.1 分支上的 JSON 是 2.77.0。這點來自轉述，本地 `git branch -a` 查不到名稱含 070 的分支，沒有逐字核對。

## 重現實驗結果
### 實驗方法

測試檔放在 scratchpad（`test_repro_083.py`），只在 pytest `tmp_path` 內放 fixture `.claude/VERSION`，然後直接呼叫 `doc_system.commands.schema.build_schema_dict(tmp_path)`。主 repo 的 VERSION 與 JSON 都沒有改動（執行後 `git status --porcelain` 為空）。內建版本從 `assets/schema/builtin_schema_version.json` 唯讀取得。版本比較以 Python 逐段整數比較，比照 `classifySchemaVersion` 的邏輯。

指令：`uv run --project .claude/skills/doc python -m pytest <scratchpad>/test_repro_083.py -s -q -p no:cacheprovider`

### 實驗執行

- 案例 1：VERSION 先設 2.77.0 重產一次，改成 2.77.1 再重產一次。輸出 `builtin=2.60.13 before=2.77.0 after=2.77.1`。斷言 after 高於內建版本：通過。斷言剝除 `VOLATILE_KEYS` 後兩次產出相同：通過。
- 案例 2（對照組）：VERSION 設成等於內建版本 2.60.13，重產後判為未高於內建版本：通過。
- 結果：2 passed。

### 實驗發現

已驗證：
- VERSION 升版後重產，產生版本欄就跟著升高，高於內建版本。依 App 閘門的規則會判為 `HigherThanBuiltin`。
- 兩次產出除了這個鍵以外完全相同，所以 staleness 守衛不會發出訊號。
- 只要產生版本等於內建版本，就落在已知範圍內，確認造成判定差異的變因只有 VERSION。

未驗證：App 端實機畫面確實落入不相容關卡。這是由閘門函式的邏輯推得的，沒有跑 App。

## Solution
**結論**：屬於框架問題，已 observe tarrragon/claude#98（https://github.com/tarrragon/claude/issues/98#issuecomment-6028493041）。根因修法採方向 (b)。方向 (a) 不放進框架產生器，改成本專案的 consumer 端契約測試，作為過渡期與長期的偵測層。兩者都落地，互不取代。

**範圍驗證方法**：rg 字面法，鍵名唯一且固定。
**驗證指令**：`grep -rn "schema_generated_at_framework_version" .claude/skills .claude/hooks lib assets tool test`
**已知盲區**：以動態組字串讀取該鍵的消費端（例如把鍵名拆開拼接）查不到。
**盲區影響評估**：Dart 與 Python 讀取點都以字面鍵存取，盤點表已逐一列出，盲區不影響「寫入點只有一處」這個結論。

### 方案比較

| 面向 | (a) 重產時偵測「產生版本 > 內建」並提示 | (b) 改由型別表顯式相容版本常數決定 |
|------|------|------|
| 修的層次 | 症狀：照樣升版，事後提醒 | 根因：產生版本只隨 schema 不相容變更而變 |
| 放在框架產生器的可行性 | 產生器不知道各 consumer 的副本路徑；寫進通用資產等於寫死專案路徑（違反規則 8），或須另設 consumer 設定檔 | 只改 `tracking_schema.py`／`schema.py`／守衛，路徑與專案無關 |
| 對沒有 App 內建副本的 consumer | 空操作。但他們的 JSON 被本 App 掃描時仍會被判不相容，問題沒有解決 | 重產後此欄不再隨 VERSION 跳動，被 App 掃描時不再誤判；如果有消費端把此欄當成「框架版本」讀取，語意會改變（盤點範圍內無此用途，App 讀框架版本走 `.claude/VERSION`）|
| 人工改回 | 仍然需要（提示之後要人去改） | 不再需要；守衛可以拿掉該鍵的 VOLATILE 排除，手改就會被內容比對擋下 |
| 代價 | 每次 sync-push 之後的重產都提示，雜訊高 | 鍵名中 `framework_version` 不再準確，需要用戶裁決改名或新增鍵 |
| (b') 變體：剝除波動鍵後內容相同就保留舊值 | — | 修得了零內容變更的情形；但內容一有變（即使向後相容）就會跳到當前 VERSION，人工改回仍在，所以不採用 |
