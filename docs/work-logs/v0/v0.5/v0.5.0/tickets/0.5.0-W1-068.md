### 問題根因

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 分析結論

**fail-open / fail-closed 判定：維持 fail-open（`fail_closed=False`），但非零路徑須補可觀測訊號。** 依據 technical-reference「deny 輸出失敗語意」：fail_closed 只用於放行後不可復原的守衛。本守衛的放行代價是「少一次攔截」，未放行時的 merge 本身在 index!=HEAD 下仍可能成功，且被擋的代價（重試）低但全域卡死風險由 hook bug 放大：fail_closed 會讓守衛任何 bug 變成所有 `git merge` 被擋，用戶學會繞過。守衛自身無法判定 staged 狀態時，放行是與同族 guard 一致的既定語意。缺口不在方向，在於路徑 (2) 靜默，違反 quality-baseline 規則 4。

**測試處置：** 測試本身不單獨改成 retry 或放寬；其依賴真實 git 與 10 秒逾時，屬環境敏感斷言。處置：逾時抽為模組常數後，該測試 monkeypatch 為寬鬆值降低負載敏感；另補兩個注入測試（timeout、diff 非零）斷言 rc=0 且有放行訊息，與 E2 deny 測試構成 E1 對照，使失敗時可由訊息分辨是守衛判 deny 失敗還是 fail-open。

### 候選方案

| 方案 | 利 | 弊 |
|------|----|----|
| A 維持 fail-open + 非零路徑補 log/stderr + 逾時常數化 + 注入測試（採用） | 不增全域卡死風險；補上歸因能力 | 負載下仍可能放行 |
| B 這兩條已知不確定路徑改 deny（fail-closed） | 不漏擋 | 負載下 merge 被誤擋；不符不可逆守衛條件；hook 自身 crash 仍須另議 |
| C 僅重試測試 | 改動小 | 掩蓋守衛放行，無歸因 |

框架問題判準：兩條 AND（抽象可攜 + 根源在 `.claude/` 通用資產）此處第一條未成立：缺口為單一 hook 的局部實作，且根因路徑未驗證，不 observe，不新開 issue。
