### 實驗發現

已驗證：
- 閘門環境下 macOS 確實會送出 hidden，每次都由 inactive 在 32–43ms 前導（3 次／5 輪）。lifecycle 從未回到 resumed，案例之間是由 test binding 的 resetInternalState 把 framesEnabled 重設為 true（每個案例起始行都是 `lifecycle=null framesEnabled=true`）。所以 hidden 只影響當下那個案例。
- hidden 是否造成紅燈，取決於它落在案例的哪個階段：
  - R1 app_test：hidden 落在案例開始後約 150ms，該案例正在等未受保護的 pumpWidget 送幀（`_applyViewport` 後 `_pumpAppAndCollectErrors`），之後沒有幀，卡到案例的 20 秒逾時。這就是本票的「等幀卡住」形態，與 864635939ab6 的 ITD1-A4 同型。
  - R5 app_test：hidden 落在 E2 與「多語系 zh」兩個案例之間，下一案例被重設，綠燈。
  - R1 real_font：hidden 落在「tickets @ min」執行中，仍綠燈。該案例當下等待的可能不是需要新幀的 pump，這部分未驗證。
- 負載與記憶體壓力不是必要條件：swap 與 memory_pressure 在 5 輪幾乎不變，紅燈輪的 load1 也不比綠燈輪高。
- 581.1 的 E2 案例 5/5 綠，加上閘門那次共 6/6。

仍未驗證：
- hidden 的觸發源。R1 的 hidden 緊接在 `_applyViewport`（改視窗大小）之後，推測改變視窗尺寸會讓 macOS 重算 occlusion，但 R5 的 hidden 發生在不改尺寸的 E2 之後，推測不足以解釋全部。
- R1 的紅燈訊息沒有指名步驟：煙霧測試的 pumpWidget 不經 settleGuarded 或 pumpFramesGuarded，卡住只能等 itWidgets 的 20 秒總逾時。

候選方案（供主控裁定選項 2）：
- C1（消除幀飢餓，原候選 C）：在 integration 的 binding 初始化時註冊 observer，收到 hidden 時呼叫 `scheduleForcedFrame` 或把 lifecycle 拉回 resumed，讓 framesEnabled 維持 true。可以同時消除兩種形態（等幀卡住與 581.1 的 framesEnabled=false）。代價是測試環境與真實 App 的 lifecycle 行為不同，但 integration 測的是畫面與流程，不測 lifecycle。
- C2（只讓卡住指名）：把煙霧測試等未受保護的 pumpWidget 改走帶逾時的 helper。只改善診斷，不減少紅燈。
- C1 與 C2 可以並存。C1 落地後，581.1 的 `framesEnabled=false` 字串應從已知 flaky 清單撤除，該守衛保留作為 C1 失效時的偵測。

### 處置（主控裁定 2026-10-31）

- 撤除 flaky 規則的條件：C1 合併後在 main 取樣 N>=5 全綠，回報主控，由主控撤除「framesEnabled=false」與「等幀卡住」兩類
