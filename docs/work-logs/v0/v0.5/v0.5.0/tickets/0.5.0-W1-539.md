## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 缺口三新實例：acceptance 勾選宣稱內容已寫入，但票面沒有，到 complete 時才被 gate 擋下

**來源**：graph_project_docs_manager，本地觀測票 `0.5.0-W1-539`，實例發生在 hook 實作票 `0.5.0-W1-538.2`（2026-10-30）。

### 經過

- worktree 隔離派發的實作代理人勾選了 acceptance 第 8 項，文字寫的是「產生路徑盤點表已寫入 how.strategy」。實際上 `how.strategy` 只有原本的策略文字，沒有盤點表。
- `ticket track check-acceptance` 在勾選當下沒有驗證內容，勾選成功。
- 合併後 PM 在主 checkout 執行 `ticket track complete`，acceptance-gate 的「防護類 hook ticket 必含項目」檢查擋下 complete，訊息為缺少「產生路徑盤點結果」等三項。PM 據此補寫進 `how.strategy` 後，complete 才通過。

### 機制差異（照實記錄，不是守衛失效）

| 時點 | 是否驗證內容 | 本例結果 |
|------|------|------|
| `check-acceptance` 勾選 | 否，只改 checkbox 狀態 | 不實的宣稱被勾選 |
| `complete` 時的 acceptance-gate | 是，至少對 hook 票的必含項目讀 Test Results／Solution／how.strategy 找證據 | 擋下，沒有放行 |

後果是**延後到收尾才被發現**，不是被放行。缺口三原文「僅靠 PM 覆核攔截」，在 hook 票這一類已經由 gate 機械驗證取代，但只限 gate 有列為必含的項目。其他 acceptance 項目的勾選仍然沒有對應的內容驗證。

### 對缺口三的意涵

- 勾選與驗證的時點分開：代理人回報「已完成」時，PM 看到的是已勾選的狀態。若不是 gate 恰好覆蓋到該項目，不實的勾選會一路留到結案。
- 這次能被抓到，是因為該項目恰好落在 gate 的必含清單內。這屬於覆蓋範圍上的巧合，並不代表勾選這一步本身有防護。

### 關係判定

- #92 缺口三：同一缺口的新實例 → observe（本則）。
- #70（驗收訊號可被裁量方自我寫入）：相關但不同面向。#70 談驗收判定讀的是可被自己寫入的訊號，本例談勾選時不驗證內容。這裡只引用，不合併。

### 缺口三第二實例（同日，本觀測票自身）

PM 對本觀測票執行 `ticket track check-acceptance <id> --all`，結果顯示「本次變更 7 項，目前 7/7」。PM 自己寫的只有 3 項，另外 4 項是範本依 where.files（指向 hook 檔）自動附加的 hook 票必填項。這 4 項的內文仍是佔位字串，而且明文寫著「勾選不算填寫」，`--all` 仍然靜默勾選，沒有警告。

PM 看到變更數與預期不符，查看清單後移除這 4 項。這張票是觀測票，不修改 hook，所以這些項目不適用。

**補充意涵**：`--all` 不區分「已填寫」與「仍是佔位字串」的項目。佔位字串本身是可以機械辨識的（`<待填：`），所以這一類至少可以在勾選時攔下或警告，不必等到 complete gate。
