- 既有證據：0.5.0-W1-164.5 以拋棄式 hook 設定於暫存目錄實測（claude 2.1.296，N=6），harness 逾時先送 SIGTERM；ignore 輪 hook 忽略 TERM，持鎖的 git 子程序仍 6/6 乾淨終止、無殘留鎖。該票未能區分「harness 對群組送訊號」與「git 隨父程序消失收到訊號」（probe 子程序的 trap 日誌因引號錯誤未寫出）。另 0.5.0-W1-164.6.3 實測 uv 多層啟動下只終止外層時 git 成為孤兒續持鎖。兩者合看，harness 對 hook 的行程群組送訊號的可能性不低。
- 對 0.5.0-W1-164.6.11 的影響：該票已讓 lib 版以 start_new_session 啟動 git。若 harness 確實對 hook 的群組送訊號，164.6.11 之前 git 會一併收到 TERM 並自行清鎖，之後 git 在另一個 session 收不到，hook 被終止的路徑反而會留下孤兒持鎖。故本票結論直接決定 164.6.11 是否需調整，優先處理。
- 實驗設置：沿用 164.5 的做法（暫存目錄、拋棄式 hook 設定，不動專案 settings.json），探針於 hook 本體與其子程序分別記錄 pid、pgid、sid 與收到的訊號；對照兩組子程序：同群組（現行 lib 以前的行為）與 start_new_session（現行 lib）。含直接 python 與 uv run 兩種啟動。N≥5，記 load。
- 結論須含：若對群組送訊號，對 164.6.11 的建議修法（候選：hook 自身攔截 SIGTERM 並 killpg 轉送給子群組；或不使用 start_new_session、改以其他方式在逾時時終止孫程序），以 --parent 0.5.0-W1-164.6 建實作票（本票深度已為 3）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 實驗方法

claude 2.1.299 macOS，scratchpad 拋棄式 repo 加 .claude/settings.json（UserPromptSubmit，timeout 3 秒），不動專案 settings.json。hook 本體記 pid／ppid／pgid／sid 並攔截 TERM／INT／HUP／QUIT 只記錄；hook 啟動兩個探針子程序：SAME（同群組，現行 lib 以前）與 NEWSESS（start_new_session，現行 lib），子程序同樣只記錄訊號。啟動方式 direct（python3）與 uv（uv run --no-project）。模式 ignore（hook 忽略 TERM 繼續存活）與 exit（hook 收到 TERM 立即退出）。load 1 分鐘 20-36。

### 結果（N=15）

| 啟動 / 模式 | N | NEWSESS 收到 TERM | SAME 收到 TERM | 除 TERM 外的訊號 |
|---|---|---|---|---|
| direct / ignore | 5 | 5/5 | 5/5 | 無 |
| uv / ignore | 5 | 5/5 | 5/5 | 無 |
| direct / exit | 3 | 3/3 | 3/3 | 無 |
| uv / exit | 2 | 1/2 | 2/2 | 無 |

- harness 逾時先送 SIGTERM，hook 約 2.5-3.4 秒收到（timeout 3）；hook 的子程序（含 start_new_session 的 NEWSESS，其 pgid/sid 皆異於 hook）在 hook 收到 TERM 前 0-0.1 秒先收到。故訊號對象是行程樹（hook 的後代），不只是 hook 的行程群組。
- SAME 子程序在多輪收到兩次 TERM（群組送一次、樹走訪再一次的推論，兩路徑未直接區分）。
- uv 啟動時 hook 的 pgid 是 uv 的 pid（uv 為群組領頭，hook 為其子）；hook 收到 TERM 1-3 次，不影響結論。
- 後續強制終止：ignore 模式下 NEWSESS 皆在 6 秒檢查點前消失（2 輪各有 1 個行程於 6 秒時仍在，之後再查已無），表示 hook 存活時樹走訪能到達 NEWSESS。
- exit 模式（hook 先退出）：NEWSESS 4/5 輪存活到 30 秒自然結束（ppid=1 孤兒）；其中 3 輪有收到 TERM 但探針忽略 TERM，故存活 = 後續強制終止沒有涵蓋到它；1 輪（uv exit 1）完全沒收到 TERM（hook 在 SAME 之前已退出、樹走訪找不到 NEWSESS）。SAME 在 exit 模式皆被強制終止（群組仍可達）。

### 結論

1. harness 對 hook 的後代送訊號，不限於 hook 的行程群組；start_new_session 不隔離 TERM（ignore 模式 10/10 到達）。
2. 對 0.5.0-W1-164.6.11：start_new_session 沒有使「逾時」路徑更易留孤兒——只要 git 收到 TERM 並自清鎖（git 會，前案 164.5/164.6 實測），結果與同群組相同。真正的新風險窗口：hook 在 TERM 後極快退出時，樹走訪可能找不到已被 reparent 的新 session 子程序（1/5 沒收到 TERM），其後的強制終止（群組／樹）也不涵蓋它，探針存活 4/5；若該子程序是持鎖 git，則留下孤兒續持鎖直到自然結束。同群組子程序（SAME）無此窗口（群組強制終止可達）。
3. 建議修法（採用）：hook／lib 在子群組存活期間攔截 SIGTERM，先 killpg(子群組, SIGTERM) 轉送，必要時短暫等待後 SIGKILL，再退出。已建 0.5.0-W1-164.6.14。候選：不用 start_new_session（改回同群組，但 164.6.11 當初因群組外殺等理由選用，須回看其動機）；弊：失去 lib 對子群組獨立終止的能力。

### 未驗證

- 探針忽略 TERM，真 git 收到 TERM 會自清鎖並退出，故「NEWSESS 存活」對真 git 是上界；未以真實持鎖 git 在 exit 模式重測。
- 強制終止的確切訊號與延遲、群組送訊號與樹走訪兩路徑的區分未量到。
- N 偏小（exit 模式 5 輪）；uv exit 的 TERM 漏收僅 1 例，頻率未定。
- Linux、真實 hook 載入路徑未測。
