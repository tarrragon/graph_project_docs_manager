## Problem Analysis
### 問題根因

兩端共用同一常數與同一深度計算（`constants.py` `MAX_TICKET_DEPTH = 3`；`lib/depth.py` `compute_depth`／`can_descend = depth < MAX`），但套在不同語意上：

| 端 | 位置 | 判準 | 行為 | 來源 |
|----|------|------|------|------|
| 建立端 | `ticket_id_allocator.py`（`--parent` 分支） | 新子票 depth >= 3 | warn `DEPTH_LIMIT_REACHED`，註解明寫「不硬擋，留旁路」 | 上游 W1-056.5（協議 v2 D3）；本 repo 經 `cffdda1df` 導入 |
| 派發端 | `agent-ticket-validation-hook.py` `check_depth_descend` | 被引用票 `can_descend == False`（depth >= 3） | deny Agent 派發 | 上游 W1-056.9（協議 v2 D3 強制層） |

常數註解的設計意圖：「平台 5 層 - 1 層 PM - 1 層安全邊距 = 3 層 agent 可用」——上限保護的是**agent 嵌套層數**，ticket 深度只是代理量（hook docstring：「每層 agent 從 ticket depth 推算層級」）。

根因：派發端未區分呼叫者。hook 全檔無 agent_id／主線程判別，主線程 PM 派發 depth 3 票時實際 agent 層數為 1，仍被當作「從第 3 層再往下 descend」擋下。代理量（ticket 深度 = agent 層級）的前提只在「每層 agent 以自身票的 children 往下派」時成立；PM 直接派發深的票時不成立。建立端 warn 文案「此 ticket 不應再往下派發子任務」語意正確（指 depth 3 票不該再 descend），與派發端「此票本身不可被派」實際行為不一致。

### 影響範圍

- 已驗證：PC-091（`ticket-lifecycle.md` 防護性 ANA 段、quality-baseline 規則 5）要求 ANA 落地用 `--parent`；depth 2 的 ANA 落地必產 depth 3 children，可建不可派。實例 092.1.1／096.1.1／096.1.2（ticket what 欄記錄），PM 以 migrate 改為 092.2／096.6／096.7，ANA 因此失去 children，acceptance-gate 的落地比對只剩 warning。
- 未驗證：上游 canonical 版本是否已改動兩端（本 repo 版本即 sync 後現況）。

### 相關 Error Pattern

PC-091（ANA 落地血緣）；hook 隱含前提類與 framework issue #54 主題同族。

## Solution
### 判定：何者為準

以設計意圖（限制 agent 嵌套層數）為準，兩端都不完全對：建立端 warn 語意對但未提示派發後果；派發端以 ticket 深度代理 agent 層級，對主線程派發過度阻擋。不一致的實質不在 warn／deny 的強弱，而在派發端的代理前提。

### 候選比較（不選定，由 PM 裁決）

| 候選 | 改哪一端 | 既有 depth 3 票 | 與 PC-091 相容性 |
|------|---------|----------------|-----------------|
| A 建立端硬擋，提示改掛上層 | allocator：depth >= 3 改 error，建議 `--parent` 改為祖先 | 既有票不變，仍不可派 | 衝突：depth 2 ANA 無法以 `--parent` 落地，須改 PC-091 條文 |
| B 派發端放寬：只在 subagent 呼叫時檢查 | hook：主線程（無 agent_id）派發不做深度檢查；subagent 派發維持 can_descend | 立即可由 PM 派發，免 migrate | 相容，children 血緣保留 |

### WRAP 評估（2026-10-08）

完整模式，建立在 83 的 A～D 之上，不選定方案。

#### 錨點

本票保護的是「agent 嵌套層數不超過平台上限」。ticket 深度只是代理量，候選的好壞要看它對這個保護目標的關係，不看它對 ticket 結構的關係。

#### R：查到、會改變判斷的事實

1. **派發守衛和協議定義差一層**。AGENT_PRELOAD 規則 9.2 D3 把 `can_descend(ticket)` 定義為「持有 ticket X 的 agent 能否再往下派」，判斷對象是**呼叫者自己的票**。`agent-ticket-validation-hook.py` 的 `check_depth_descend` 卻對**被派發引用的票**呼叫 `can_descend`（docstring：「ticket_id: 被派發引用的 Ticket ID」）。結果是：依協議，深度 2 的 agent `can_descend = true`，可以派深度 3 的子票；守衛卻把深度 3 子票擋下。深度 3 的票不論誰派都派不出去，「3 層 agent 可用」實際只用到 2 層。
2. **建立端門檻和派發端一致地錯在同一處**。`ticket_id_allocator.py` 在 `new_depth >= MAX_TICKET_DEPTH`（即建立深度 3）時 warn。依協議，深度 3 的票本身合法，該警告的是深度 4。
3. **agent_id 在 subagent 的 hook 輸入中可靠出現（深度 1 有實證，深度 2 無本地實證）**。本專案 `post-test-hook-20261008.log` 今天有 58 行「偵測到 subagent 環境（agent_id=…）」，來源是本 session 派出的 fork（如 a65f7f4ba849084fc、addc6f12b0e40d696）。巢狀第二層的 agent_id：本專案沒有巢狀派發紀錄可查；`parallel-dispatch.md` 引用上游 W1-056.4「hook 與 runtime 行為在嵌套層一致生效」，但該票不在本專案，無法直接核對。
4. **agent_id 只能分辨「主線程或 subagent」，不能分辨 subagent 在第幾層**。`is_subagent_environment` 只檢查欄位是否存在。它的 docstring 另外警告：本函式設計給 advisory-only hook，拿來控制 blocking 分支時，欄位缺席會讓硬擋整條失效且無訊號。B 正是把它用在 blocking 分支上。
5. **ticket 深度與實際 agent 層數不單調**。subagent 可以引用任何一張票派發，包括另一棵樹的根票（深度 1）。現行守衛、A、B、D 都無法阻止「深度 1 的 subagent 派深度 1 的另一張根票，再一路往下」。ticket 深度只在「agent 只沿自己的 children 往下派」這個慣例成立時才是準確的代理量。
6. **平台 5 層的來源未查證**。constants 註解寫「平台 5 層 - 1 層 PM - 1 層安全邊距 = 3」，本次沒有找到平台文件佐證，也無法確認 5 層是怎麼計數的。

| | 作法 | 類別 | 既有深度 3 票 | 對真實嵌套的保護 |
