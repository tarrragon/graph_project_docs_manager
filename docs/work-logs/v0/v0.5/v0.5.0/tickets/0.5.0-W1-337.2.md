## 重現實驗結果
### 實驗方法

1. 先盤點既有資料來源（W 階段的零工具類選項）：ListAgents 已能列出各 session 的 busy／idle，追查它讀的檔案
2. 用背景迴圈每秒讀一次本 session 的 `~/.claude/sessions/<pid>.json`，共 240 次；同時呼叫 AskUserQuestion，讓本 session 停下來等用戶回答
3. 只讀 `*.json`；同目錄的 `*.key` 是金鑰，不讀

### 實驗執行

- 環境：2026-10-19，CC 2.1.303，macOS
- `~/.claude/sessions/` 有每個執行中 session 的 `<pid>.json`，欄位含 `name`（也就是 ListAgents 與 SendMessage 用的名稱，例如 graph-project-docs-manager-3e）、`cwd`、`sessionId`、`status`、`statusUpdatedAt`、`messagingSocketPath`
- 取樣結果（uniq -c）：

```
  12 busy {}    
 228 waiting {'waitingFor': 'input needed'}  
```

- 取樣期間：15:39:48 至 15:44:01。AskUserQuestion 發出後約 12 秒內，`status` 從 `busy` 轉為 `waiting`，並多出 `waitingFor: 'input needed'`
- 同一時間其他 session 的檔案：其他專案的 session 是 `idle`，正在執行的線是 `busy`

### 實驗發現

**已驗證**

- CC 會在 `~/.claude/sessions/<pid>.json` 記錄每個 session 的狀態：`busy`、`idle`，以及停下來等用戶時的 `waiting`（附 `waitingFor`）。所以要知道「哪個 session 在等我回答」，不需要在各 session 內掛 hook
- 檔案有 `name` 與 `cwd`，可以依 cwd 篩出本 repo（含各 worktree）的 session；名稱與 349〈分派〉裡的 session 名稱一致

**未驗證**

- 權限確認對話框是否也顯示為 `waiting`，以及這時 `waitingFor` 的值
- session 異常結束後，檔案會不會殘留（要比對 pid 是否還活著）
- 這是 CC 的內部檔案，官方沒有文件承諾它的格式，升版後可能改變
