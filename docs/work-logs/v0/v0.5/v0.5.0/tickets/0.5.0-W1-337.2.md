## Problem Analysis
### 問題根因

337 第一階段的看板只從外部讀 repo 檔案（票檔、合併日誌），讀不到 session 內部的狀態，特別是「停下來等用戶回答」。原本的假設是，這種狀態只能在各 session 內部用 hook 觀測（337 WRAP 盲點 1）。

### 影響範圍

- 已驗證：CC 會把每個 session 的狀態寫在 `~/.claude/sessions/<pid>.json`，看板直接讀就能取得，不需要在各線 session 加任何東西（見「重現實驗結果」）。影響的檔案只有 `tools/line-board/` 的看板 mod（實作在 337.2.1）
- 未驗證：權限確認對話框的 `waitingFor` 值；pid 被重複使用時的誤判；CC 升版後格式是否改變。337.2.1 實測時另外發現 `shell` 狀態，已原樣顯示

### 相關 Error Pattern

已查（`/error-pattern query` 關鍵字 session、status、hook 觀測）：沒有直接對應的模式。本票的反轉（原以為要掛 hook，結果已有現成資料）屬於 WRAP 的「方案性質三類涵蓋」，零工具選項先列，不另立 error-pattern。

## 重現實驗結果
### 實驗方法

1. 先盤點既有資料來源（W 階段的零工具類選項）：ListAgents 已能列出各 session 的 busy／idle，追查它讀的檔案
2. 用背景迴圈每秒讀一次本 session 的 `~/.claude/sessions/<pid>.json`，共 240 次；同時呼叫 AskUserQuestion，讓本 session 停下來等用戶回答
3. 只讀 `*.json`；同目錄的 `*.key` 是金鑰，不讀

### 實驗執行

- 環境：2026-10-19，CC 2.1.303，macOS
- `~/.claude/sessions/` 有每個執行中 session 的 `<pid>.json`，欄位含 `name`（也就是 ListAgents 與 SendMessage 用的名稱，例如 graph-project-docs-manager-3e）、`cwd`、`sessionId`、`status`、`statusUpdatedAt`、`messagingSocketPath`
- 取樣結果（uniq -c）：

```
  12 busy {}    
 228 waiting {'waitingFor': 'input needed'}  
```

- 取樣期間：15:39:48 至 15:44:01。AskUserQuestion 發出後約 12 秒內，`status` 從 `busy` 轉為 `waiting`，並多出 `waitingFor: 'input needed'`
- 同一時間其他 session 的檔案：其他專案的 session 是 `idle`，正在執行的線是 `busy`

### 實驗發現

**已驗證**

- CC 會在 `~/.claude/sessions/<pid>.json` 記錄每個 session 的狀態：`busy`、`idle`，以及停下來等用戶時的 `waiting`（附 `waitingFor`）。所以要知道「哪個 session 在等我回答」，不需要在各 session 內掛 hook
- 檔案有 `name` 與 `cwd`，可以依 cwd 篩出本 repo（含各 worktree）的 session；名稱與 349〈分派〉裡的 session 名稱一致

**未驗證**

- 權限確認對話框是否也顯示為 `waiting`，以及這時 `waitingFor` 的值
- session 異常結束後，檔案會不會殘留（要比對 pid 是否還活著）
- 這是 CC 的內部檔案，官方沒有文件承諾它的格式，升版後可能改變

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論：不需要回報 mod，看板直接讀 CC 的 session 狀態檔

### 候選比較

| 候選 | 做法 | 觀測得到「在等用戶」？ | 載入與設定 | 結果 |
|------|------|----------------------|-----------|------|
| 1 讀 CC 既有狀態檔（零工具） | 看板讀 `~/.claude/sessions/<pid>.json` 的 status 與 waitingFor | 是（實測 `waiting`／`input needed`） | 各線 session 不需加任何東西，也不改設定 | 採用 |
| 2 回報 mod | 各線 session 載入 mod，以 `tool.call`（AskUserQuestion）、`turn.start`／`turn.complete` 寫共用檔 | 是 | 需要 `--plugin-dir`（每條線都要帶參數）或全域 `CLAUDE_CODE_PLUGIN_DIRS`（影響這台機器所有專案） | 不採用：觀測結果與候選 1 相同，成本較高 |
| 3 專案 settings 的 command hook | `.claude/settings.json` 掛 PreToolUse／Notification／Stop，寫共用檔 | 是 | 不改全域設定，但 `.claude/` 會隨 sync-push 帶到其他 consumer | 不採用：同上，還多了跨專案外溢 |

候選 1 的風險：狀態檔是 CC 內部格式，官方沒有文件承諾。處理方式：未知的 status 原樣顯示；CC 升版後重跑真實對照（寫入 337.2.1 acceptance）。若日後格式消失，改走候選 2，屆時觀測點已列在上表。

### acceptance 對照

2. 已比較三種方式的影響範圍：採用的候選 1 不需要改全域設定
