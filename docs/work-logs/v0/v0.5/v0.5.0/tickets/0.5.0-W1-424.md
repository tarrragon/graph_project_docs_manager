### 問題根因

設計來源：`parallel-suggestion-hook.py` 步驟 6.5 與 `.claude/lib/ask_user_question_reminders.py` 的 `WAVE_WRAP_UP_REMINDER`，對應 `.claude/pm-rules/askuserquestion-rules.md` 場景 #3「Wave/任務收尾確認」，以及該檔 hook 對照表的 parallel-suggestion-hook 列（「繼續請求但無 pending Ticket → #3 Wave 收尾」）。設計前提有兩個：(1) 用戶說「繼續」，而任務鏈內找不到可並行的票，代表一段工作做完、接近收尾；(2) 收尾單位是 Wave，而 Wave 會在數十張票內清空。

觸發條件（讀碼）：`is_continuation_request` 對整段 prompt 做子字串比對 `CONTINUATION_KEYWORDS`（繼續、下一個、接著做、接續、任務鏈、子任務、批量等）。命中後，只要步驟 4–6 沒有產出並行建議，一律進入步驟 6.5：取第一張 in_progress 票的 wave，統計同 wave 的 pending 數，再輸出提醒。pending 數只寫進狀態行，**不影響是否輸出**；提醒本文固定要求「PM 必須使用 AskUserQuestion 確認收尾動作」。

兩個前提現已不成立：

- 收尾單位：2026-09-29 的三則補記（`docs/tech-decisions.md`）改為 major 起始時定 minor 清單、minor 完成後分診定 topic patch，收尾單位改為版本與 patch。0.5.0 的票幾乎全在 W1，W1 在版本結束前不會清空。
- 「繼續」的語意：多 session 分線後，「繼續」指的是某條線的佇列（349 現行佇列行）。而且多數命中的 prompt 不是用戶輸入的文字，而是同儕訊息、技能本文、安全審查 prompt、context 續接摘要（見重現實驗）。

- transcript 分類與 hook 實際呼叫是否一一對應（hook 日誌不記錄 prompt 本文）。結論不依賴精確比例：即使只計用戶本人輸入，提醒的收尾前提也一次都沒有成立。

### 補充：同儕訊息進入 hook 的 prompt（主控轉知後驗證，2026-10-20）

- hook 讀到的 prompt 包含同儕訊息全文：同日日誌的未命中行以 prompt 開頭 50 字記錄，例：`[2026-10-20 00:23:21] DEBUG - 未識別為繼續請求: <cross-session-message from="uds:/tmp/cc-socks/569...`。當日 498 筆未命中行中，214 筆以 `<cross-session-message` 開頭、149 筆以 `<task-notification>` 開頭，其餘多為 `<agent-message`。
- 現場實例：主控傳給本 session 的訊息（內文含「等用戶裁定後再繼續」）送達時，本 session 收到 Wave 收尾提醒，該回合沒有任何用戶輸入。日誌：`[2026-10-20 17:49:39] INFO - 識別繼續請求關鍵字: 繼續`、`[2026-10-20 17:49:39] INFO - 無並行建議，輸出 Wave 收尾提醒（Wave=1, pending=109）`。主控 session 同時段也收到一次（主控轉知：觸發回合的用戶訊息不含關鍵字，同回合有 L17 訊息寫著「等用戶裁定後再繼續」）。
- 結論：同儕訊息、背景任務通知、子代理人訊息都會經 UserPromptSubmit 進入 hook，被子字串比對命中，屬誤觸發來源之一（transcript 近似量測中佔最大宗）。
## Solution
### 分析結論

採 **A：移除步驟 6.5 與 `WAVE_WRAP_UP_REMINDER`**（實作：`0.5.0-W1-424.1`）。仍需提醒的情境，改由不依賴關鍵字的載體承接（見 E2 對照）。

### 候選方案

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| A 移除（採用） | 刪除步驟 6.5、常數、測試，同步 askuserquestion-rules 場景 #3 | 誤報歸零；改動面小（hook、常數、測試，以及 pm-rules 中的一個檔案） | 單 session、不分線的 consumer 失去「繼續」時的收尾提醒；以 E2 對照確認其他載體已承接 |
| B 改以版本為單位 | active 版本 pending=0 時才提醒 | 單位與現行規劃一致 | 仍由關鍵字觸發，命中多為非用戶 prompt；版本完成要等數百張票，觸發時 `version-release check` 已涵蓋 |
| C 改讀線佇列 | 由 session 名稱對到 349 現行佇列行，佇列為（無）時提醒線收尾 | 單位與多線協調一致 | 線結束的事件發生在主控寫入佇列行時，不在「繼續」時；hook 須另設協調票路徑；只在採分線的專案有意義，對框架其他 consumer 無效 |
| D 只加來源過濾 | 排除 `<cross-session-message`、`<task-notification>` 等開頭的 prompt | 減少約 94% 的誤觸發 | 單位錯誤仍在：用戶本人說「繼續」時，W1 仍有百張以上 pending，提醒照樣不適用 |
