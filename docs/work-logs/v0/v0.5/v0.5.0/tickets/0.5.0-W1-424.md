### 問題根因

設計來源：`parallel-suggestion-hook.py` 步驟 6.5 與 `.claude/lib/ask_user_question_reminders.py` 的 `WAVE_WRAP_UP_REMINDER`，對應 `.claude/pm-rules/askuserquestion-rules.md` 場景 #3「Wave/任務收尾確認」，以及該檔 hook 對照表的 parallel-suggestion-hook 列（「繼續請求但無 pending Ticket → #3 Wave 收尾」）。設計前提有兩個：(1) 用戶說「繼續」，而任務鏈內找不到可並行的票，代表一段工作做完、接近收尾；(2) 收尾單位是 Wave，而 Wave 會在數十張票內清空。

觸發條件（讀碼）：`is_continuation_request` 對整段 prompt 做子字串比對 `CONTINUATION_KEYWORDS`（繼續、下一個、接著做、接續、任務鏈、子任務、批量等）。命中後，只要步驟 4–6 沒有產出並行建議，一律進入步驟 6.5：取第一張 in_progress 票的 wave，統計同 wave 的 pending 數，再輸出提醒。pending 數只寫進狀態行，**不影響是否輸出**；提醒本文固定要求「PM 必須使用 AskUserQuestion 確認收尾動作」。

兩個前提現已不成立：

- 收尾單位：2026-09-29 的三則補記（`docs/tech-decisions.md`）改為 major 起始時定 minor 清單、minor 完成後分診定 topic patch，收尾單位改為版本與 patch。0.5.0 的票幾乎全在 W1，W1 在版本結束前不會清空。
- 「繼續」的語意：多 session 分線後，「繼續」指的是某條線的佇列（349 現行佇列行）。而且多數命中的 prompt 不是用戶輸入的文字，而是同儕訊息、技能本文、安全審查 prompt、context 續接摘要（見重現實驗）。

### 影響範圍

- 受影響：`.claude/hooks/parallel-suggestion-hook.py`（步驟 6.5、`count_current_wave_pending`、`build_wave_wrap_up_status_line`）、`.claude/lib/ask_user_question_reminders.py`（`WAVE_WRAP_UP_REMINDER`）、`.claude/hooks/tests/test_parallel_suggestion_hook.py`（與 wave 相關的測試）、`.claude/pm-rules/askuserquestion-rules.md`（場景 #3 觸發來源欄、hook 對照表列）。
