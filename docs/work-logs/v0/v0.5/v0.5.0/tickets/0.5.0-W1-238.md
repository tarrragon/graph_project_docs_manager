## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`worktree merge <id>` 只做前置驗證，然後輸出 `git merge --no-ff <分支>` 讓呼叫端在共用主 checkout 執行。`git merge` 的提交與 HEAD 更新不是原子的：先寫 index 與工作區，最後才以 update_ref 推進 HEAD。多個 session 以隔離索引 CAS 高頻推進 HEAD 時，這一段時間窗內只要 HEAD 前進，update_ref 就失敗。

### 影響範圍（F 線 2026-10-14 實測三筆）

1. **update_ref 失敗，留下半成品合併**：主 checkout 執行 `git merge --no-ff worktree-agent-…`。git 先印出 `fatal: update_ref failed for ref 'HEAD': … is at X but expected Y`，再印 `Merge made by the 'ort' strategy.`。結果 HEAD 未前進，`.git/MERGE_HEAD` 存在，四個合併結果檔已 staged、工作區也已改寫。此狀態下，其他 session 的裸 commit 會被 bare-commit-guard 以 MERGE_HEAD 拒絕；若守衛被繞過，則會夾帶這四個檔。現行規則七只處理 `Unable to write index`，沒有這個形態的處置。
2. **手寫 CAS 合併產生空合併**：改用隔離索引 CAS 自行合併時，zsh 不會對未加引號的變數做字詞切分，多行檔案清單被當成單一路徑，`update-index` 未套入任何變更。結果是 tree 與第一親代相同、第二親代為分支的合併提交（3d66c1b）：分支被記為已合併，內容卻沒有進 main，git log 外觀正常。以補套提交（975708b）修正。屬 PC-169（空合併）同形，觸發路徑不同。
3. **CAS 成功後共用 index 同步失敗**：合併提交已成立，以 `git reset -- <檔>` 同步共用 index 時撞到 index.lock，留下「index 為舊雜湊、HEAD 為新雜湊」的過期 entry（`M ` 狀態），重試後才一致。與 0.5.0-W1-236 為同一機制。

### 相關 Error Pattern

PC-169（空合併）、IMP-V1-005（fast-forward 與過期 index 導致檔案被刪），以及 bash 規則七〈兩段式合併禁令〉。#101「保護分支守衛只擋得住已分歧的合併：worktree 交付在並行環境下無合法落地路徑」為最接近的 framework issue。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論

共用 checkout 缺少一條在 HEAD 被並行推進時仍能成立的合併路徑。`worktree merge` 應直接以隔離索引 CAS 完成合併，並內建三道防護：空合併守衛、三方合併與衝突中止、index 同步重試。規則七另補 update_ref 失敗的處置。

### 候選比較

| 案 | 作法 | 誤合併風險 |
|----|------|-----------|
| A 維持 git merge，補失敗處置 SOP | 只改文件 | 高：每次並行時都可能留下 MERGE_HEAD 與 staged 結果，處置仰賴執行者辨識訊號；手動補救本身即可能產生空合併（實測 3d66c1b） |
| B 分支先 rebase 到最新 main，再 fast-forward | worktree 內 rebase 後以 update-ref CAS 推進 | 中：rebase 會改寫分支提交；fast-forward 遇過期 index 會刪檔（IMP-V1-005） |
| C worktree merge 內建隔離索引 CAS 合併（採用） | 見子票 238.1 | 低：不碰共用 index 直到 HEAD 已成立；空合併與衝突皆中止且不寫 ref；只同步未被他人改動的檔 |
