### 問題根因

本票是實驗票。本欄記錄待驗證的假設與實驗設計，由主控於 2026-10-21 與用戶討論後寫定。

**用戶提出的假設**：UI 驗證可改成「截圖加選項，讓 Haiku 選擇」。這樣做可能比讓高階模型開放式判斷更可靠，成本也更低。

**和 464 的差別**：464 的錯誤來自前提未經查證，證據在題目之外。UI 題的全部證據都在截圖裡，不受這個問題影響。UI 題的失敗來源有兩個：

| 失敗來源 | 說明 | 實驗中的處置 |
|---|---|---|
| 視覺解析度 | Haiku 在小字、1 到 2 px 的對齊、相近顏色上的表現弱於高階模型 | 缺陷分成粗粒度（溢位、重疊、缺元件）與細粒度（對齊、顏色、小字）兩組，結論分開下 |
| 失效方向是放行 | 驗證器出錯時，輸出和「本來就沒問題」一模一樣（規則 E2） | 資料集一半是注入缺陷的截圖；主要指標是漏判率，不是一致率 |

**選項設計**：採 Set-of-Mark 做法，用 widget 樹或 semantics 的邊界在截圖上疊編號框，模型只回答編號。這樣定位交給程式，判讀交給模型。另附「無缺陷」「無法判斷」兩個選項。

**職責邊界**：「找出目標 widget」不需要視覺，finder 與 semantics 樹已能精確定位，而且不花成本。視覺只用在 widget 樹表達不出來的渲染結果：溢位、裁切、重疊、顏色、實機排版。報告必須逐項列出 finder 已能確定判斷的項目，避免把能精確驗證的東西換成機率判斷。

**成本比較的待驗證串接方案**：Haiku 取樣後，首位與次位的頻率差夠大就直接採用；頻率差小，或選了「無法判斷」，再交給 Opus 複核。實驗要量的是頻率差能不能預測 Haiku 判得對不對。比較成本時要把漏判的代價算進去，不能只比每次呼叫的價格。

### WRAP 完整模式評估（主控，2026-10-21）

**錨點**：客戶是用戶，用戶目前在實機上逐張看截圖確認（421／422／428 仍在等）。本票要回答的是：視覺選擇式驗證能不能減輕這項人工負擔，而且不漏判。

**W 反向思考（影響最大的修正）**

本票原本設想的缺陷類型中，有一部分 widget test 已經能確定性地抓到：
- **溢位**：RenderFlex overflow 在測試中會拋出 FlutterError。
- **垂直裁切**：專案已有 `expectNoVerticalClip`（`test/helpers/pump_harness.dart`）。

但這個輔助函式的註解寫明：中文字形較高的 ascender／descender 只會在實機上出現。這正是測試抓不到、只能靠人看實機截圖的缺陷。

因此，視覺驗證器的價值不在通用的渲染缺陷，而在**只有實機才出現的缺陷**：
- 實機字型下的 CJK 裁切
- 不會拋錯的元件重疊
- 主題色錯置
- 平台渲染差異

本票的資料集要以這一類為主，測試已能確定性抓到的類型只當對照。

**W 正解來源的替代方案**：除了人工注入的合成缺陷，還應該加入**歷史上實際發生過的實機缺陷**作為正向對照。來源是過去由實機驗證發現的缺陷票，例如 CJK 垂直裁切。合成缺陷由注入者設計，可能過於明顯；真實缺陷比較能代表實際會漏掉的東西。

方案三類涵蓋：
- 改造既有：widget test 的 overflow 例外與 `expectNoVerticalClip`。
- 零工具：用戶人工看截圖，也就是現況。
- 新增工具：Haiku 先判、Opus 複核。

**R 試水溫**：5 張缺陷圖（至少 2 張是歷史真實缺陷）加 5 張正常圖，Haiku 與 Opus 各取樣 5 次。先確認漏判率是否在可接受範圍內，再擴大到 20 張。

**A 悖論檢查**：如果用視覺驗證器取代用戶的實機確認，漏判就會直接流到使用者手上。因此結論只能是「減少用戶要看的張數」，例如只把有疑慮的那幾張交給用戶，不能是「取代用戶確認」。

**P 行前預想**

| 失敗原因 | 早期警訊 | 已定動作 |
|---|---|---|
| 合成缺陷太明顯 | 合成缺陷全數 5/5 被抓到，而真實缺陷漏判 | 結論只依真實缺陷計算；正式階段補細微的合成缺陷 |
| 實機才有的缺陷在送出解析度下看不見 | 真實 CJK 裁切在 Haiku 與 Opus 都漏判 | 改送局部裁切的高解析圖，作為正式階段的對照 |
| 與 widget test 重複 | 資料集多數缺陷屬於測試已能抓到的類型 | 剔除，資料集只保留實機才有的缺陷 |

**主控暫定門檻**（待多視角審查確認）

- 題級判定：5 次取樣中至少 4 次判為有缺陷，才算「判為有缺陷」。
- 串接方案的漏判定義：缺陷圖既沒有被 Haiku 抓到，也沒有被轉給 Opus（頻率差小，或選了「無法判斷」）。
- 可行條件：串接方案的漏判率為 0／5（試水溫）或不超過 1／20（正式）；正常圖被誤報的比率不超過 0.2；且每張成本低於 Opus 單獨判讀。

### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` hits an environmental
failure that persists after re-running it, or is unavailable. Scope/criteria
rejections must NOT use fallback: stop and report to PM) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.
