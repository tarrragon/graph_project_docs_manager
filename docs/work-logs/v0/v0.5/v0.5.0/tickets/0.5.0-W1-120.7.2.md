#### 1. Linux 取父行程 argv

| 平台 | 方式 | 實測 |
|---|---|---|
| macOS | `ps -o args= -p $PPID`（無 /proc） | 可用；參數以空格連接，含空白的路徑或引號參數無法還原邊界 |
| Linux | 讀 `/proc/$PPID/cmdline`（NUL 分隔） | 可用：`git commit -q -m x`、`git merge --continue`、alias 展開後 `/usr/libexec/git-core/git commit ...` 皆正確 |
| Linux busybox | `ps -o args= -p` | 不可用（`ps: unrecognized option: p`），不能只靠 ps |

退化行為：實作順序為先試 /proc，再試 ps；兩者皆取不到（無 /proc、hidepid、容器 PID 命名空間、ps 失敗）時一律放行並寫日誌。macOS 的 ps 路徑有空白參數的歧義，只取「第一個非選項 token」判子命令，選項帶值的 `-c`、`-C` 須跳過（已用 `-C <path>`、`-c k=v`、`--no-pager` 前綴驗證可正確取到 commit）。父行程 exe 為完整路徑（Xcode 版 `.../usr/bin/git`、alias 為 `git-core/git`），比對須取 basename。
未驗證：Windows（本專案目標平台僅 macOS，不處理）；macOS 是否需 sysctl KERN_PROCARGS2 取 NUL 分隔 argv（可行但需 ctypes，成本高於收益）。

#### 2. 哪些提交路徑經過 reference-transaction

| 路徑 | 經過 hook？ | 依據 |
|---|---|---|
| 人類終端 `git commit` | 是，父行程 argv 為 `git commit ...` | 實測 |
| `git merge --continue` | 是，父 argv 為 `git merge --continue`，放行 | 實測 |
| `git commit --no-verify` | 是，仍被擋 | 實測（--no-verify 只跳 pre-commit 與 commit-msg） |
| `git commit -a`、`git -C <path> commit`、alias `ci`、`sh -c 'command git commit'` | 是，全數被擋 | 實測，別名與包裝在 argv 已還原 |
| `commit-tree` 加 `update-ref`（ticket track commit 的路徑） | 是，父 argv 為 `git update-ref ...`，放行 | 實測 |
| VS Code 式呼叫（無 tty、`-c user.useConfigOnly=true commit --quiet --allow-empty-message --file -`、stdin 傳訊息） | 是，被擋 | 以同形 argv 模擬實測；VS Code 本體未啟動 |
| JetBrains、GitHub Desktop（dugite）、SourceTree、Fork、git gui | 預期是（皆 spawn git CLI） | 未實測，依據：這些工具以內建或系統 git 可執行檔 spawn 子行程，commit 為 git commit 或 commit-tree 加 update-ref；Fork.app 已安裝但未啟動 |
| libgit2 類（pygit2 實測 create_commit 帶 MERGE_HEAD 為 parent） | 否，hook 完全未執行（rt.log 0 行） | 實測：libgit2 不執行 git hooks |

結論：libgit2、JGit 路徑對本守衛不可見，與「取不到父行程時放行」同樣屬放行側，不是誤擋風險。

#### 3. 誤擋時的訊息

| 環境 | 使用者看到的內容 |
|---|---|
| 終端（實測） | hook 自己的 stderr（原型輸出 `GUARD: ...`）加 `fatal: ref updates aborted by hook`，exit 128 |
| 無 tty、stderr 被子行程捕獲（IDE 模型，以 python subprocess 模擬實測） | stdout 空，stderr 為上述兩行；rc 128。呈現位置由 IDE 決定（VS Code 為錯誤通知與 Git 輸出面板，未實測） |

追加觀察：
1. git commit 的順序是先開編輯器、使用者輸入訊息，ref 更新在最後才發生，所以被擋時訊息已輸入完畢；MERGE_HEAD 與 index 保持不變，使用者仍可改跑 `git merge --continue`，訊息留在 COMMIT_EDITMSG（依 git 流程推得，編輯器路徑未另行實測）。
2. `git commit` 是 git 文件與多數教學指示的合併收尾寫法，被擋的使用者多半不知為何。hook 訊息必須明寫替代命令與繞過方式，否則會被讀成 git 故障。

#### 4. 繞過方式

實測以下皆放行（rc=0）：`git -c core.hooksPath=/dev/null commit`；環境變數 `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.hooksPath GIT_CONFIG_VALUE_0=/dev/null`。另可刪除或改名 `.git/hooks/reference-transaction`（install hook 在下個 SessionStart 會補裝）。`--no-verify` 不能繞過（實測仍被擋）。
評估：守衛定位是防合作中的 session 無意收尾他方操作，不是對抗刻意規避（同 120.7.9 結論 4）。以上屬有意繞過，不處理；訊息中直接寫出 `git -c core.hooksPath=` 作為明示逃生口反而能避免使用者拆掉整個 hook。
