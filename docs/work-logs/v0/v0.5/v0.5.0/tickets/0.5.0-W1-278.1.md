## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 實作
- 新增 .claude/lib/session_state_key.py：session_state_key(input_data, logger) 取 hook 輸入的 session_id，非 [A-Za-z0-9_-] 字元換底線、長度上限 128（防路徑穿越）；session_state_path(template, input_data, logger) 以 {session_id} 佔位符展開。取不到 session_id 回傳 None，並記 logger.warning 與寫 stderr，不退回 ppid。
- lib/constants.py 的四個狀態檔模板由 {ppid} 改 {session_id}；五支 hook 皆經 session_state_path，repo 內 hook 與 lib 腳本已無 os.getppid()（測試 test_no_getppid_session_key_remaining_in_hooks 守住）。
- session-context-guard-hook、dispatch-count-guard-hook、handoff-prompt-reminder-hook、handoff_session_mgmt（經 handoff-auto-resume-stop-hook 傳入 input_data）改簽名接收 input_data。

### 重複計數保留哪一份
保留 session-context-guard-hook.py 的計數，移除 post-ticket-lifecycle-hook.py 的計數（含 get/read/increment_counter、警告訊息、閾值常數、update_session_counter）。理由：(1) 前者經 emit_hook_output(audience="pm_only") 過濾 subagent 觸發，後者的計數警告直接塞進 additionalContext，無受眾過濾；(2) 前者是單一職責的獨立 hook，後者是合併 hook，計數只是其被合併進來的子邏輯，lifecycle 保留 checkpoint 提醒一項職責；(3) 兩者都註冊在 PostToolUse:Bash，留任一份行為等價，移除合併 hook 內的副本改動最小。

### 失敗語意（fail-open）
- 取不到 session_id：session-context-guard 不計數、不提醒；dispatch-count-guard 不寫也不驗證；handoff-prompt-reminder 視為未提醒（提醒照常輸出，寧可重複不遺失）；handoff_session_mgmt.read_session_state 回 None（走 pending 掃描）。皆記 warning 並寫 stderr。
- 狀態檔讀寫失敗：計數寫入失敗記 warning 後繼續；讀失敗視為 0 或無狀態。
- 理由：五支皆為提醒型 hook（exit 0，不擋操作），狀態缺失的代價只是少一次或多一次提醒；fail-closed 會讓 runtime 異常時誤擋正常操作，成本高於收益。

### 舊 ppid 鍵狀態檔
不清理。理由：新鍵 session_id 與舊鍵（純數字 pid）檔名不相交，舊檔不會被讀到；舊檔位於 /tmp，由 OS 回收；主動刪除會觸及非本票建立、可能屬其他並行 session 的檔案。

### Phase 4 自評
- 重構需要：否。技術債務：發現 1 項（test_git_z_path_reading_e2 的 parallel-dispatch-verification-hook 呼叫簽名不符，與本票無關，已登記 spawn request）。程式碼品質：A。
- 附帶：handoff_session_mgmt.py 與 dispatch-count-guard-hook.py 留有不再使用的 import os，依最小變更紀律未動。

### 自檢結果
- 逐支確認 5 支 hook 的狀態檔路徑皆經 session_state_path；lifecycle 無計數；E1 對照、正向對照、缺 session_id 皆有測試。
