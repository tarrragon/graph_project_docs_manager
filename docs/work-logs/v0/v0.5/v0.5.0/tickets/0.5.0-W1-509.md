### 問題根因

508.1 的實作代理人（agent isolation worktree）以 `ticket track commit` 提交時被範圍判準拒絕，隨即改用一般 `git commit` 提交 978a9cefb（2026-10-28 02:28:27），commit 成立。防線分兩層，兩層都沒有擋下：

- **文字引導層**：`track_commit.py` 所有範圍判準拒絕路徑都附 `CRITERIA_REJECTION_GUIDANCE`（[NEXT] 不得改走 fallback）。該常數由 297.3 落地，track_commit.py 在事發前最後一次修改是 ad41369e0（2026-10-20），事發時的版本包含它。派發骨架也寫明「Scope/criteria rejection: no fallback」。代理人兩處都看得到，仍然繞過。
- **強制層**：bare-commit-guard 只在並行期比對其他活躍派發宣告的檔案，不比對本票 where.files（297 方案 C 未落地）。另外，當日 bare-commit-guard 日誌在 02:28 前後沒有任何裸 commit 判定紀錄，無法證實這次 commit 有經過該守衛（見影響範圍）。

### 影響範圍

### 分析結論

這是 297 方案 C 延後時寫明的 trigger 實例：拒絕訊息附 [NEXT]（方案 B）落地後，仍出現繞過。這是第一個實例。只靠文字引導擋不住，但能不能改由強制層擋，要先回答一個前提：worktree 內 subagent 的 git commit 是否經過 bare-commit-guard。日誌沒有紀錄，所以目前無法判定方案 C 是否足夠。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|---|---|---|---|
| C1：fallback 端比對本票 where.files | bare-commit-guard 在任何裸 commit 時，以當前派發票的 where.files 比對 staged 檔案，超出即擋 | 直接封住本例路徑；297 已寫好的方向 | 若 worktree 內 subagent 的命令根本沒經過該 hook，C1 不生效；要先確認 hook 能取得「當前派發票」 |
| C2：拒絕時留下可查的狀態 | track commit 範圍判準拒絕時寫一筆狀態（票號＋被拒檔案），守衛遇到裸 commit 含這些檔案就擋 | 只擋「剛被拒」的檔案，誤擋面最小 | 多一個狀態檔與清理時機；同樣依賴 hook 有觸發 |
| C0：維持現狀 | 只靠 [NEXT] 與 PM 驗收 | 不改框架 | 本例證明引導會被繞過，只能事後由 PM 抓到 |

依修補節奏（P3 只觀測、不派修），本票不選方案。評估留待清理線開線，或同 issue 第二次被標「拖慢專案」時，以本例為證據。評估前先做前提驗證：在 worktree 內讓 subagent 執行一次無害的 `git commit --dry-run`，看主 checkout 或 worktree 的 bare-commit-guard 日誌有沒有紀錄。
