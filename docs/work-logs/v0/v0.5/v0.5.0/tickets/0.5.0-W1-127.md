## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### PM 派發前補充（2026-10-12，框架工具組）

**根因**：`check_condition_1_unidirectional` 的「多兄弟依賴」分支只計數 `blockedBy` 中屬於兄弟的項目，計數達 2 即 BLOCK，不看前驅狀態。守衛只掛在 `ticket track claim／complete`，該檢查的防護價值在結構尚可調整時；前驅皆已終態後，結構不再影響排程，阻擋只讓票無法收尾。`--acknowledge` 只作用於條件 3、4 的 WARN，條件 1 無確認路徑。

**修法裁決**（tarrragon/claude#54 第六處實例留言列三個候選）：採「前驅皆為終態時於 claim／complete 放行」。
- 不採「只在 create／set-blocked-by 觸發」：守衛現無該觸發點，須新增掛載與命令解析，改動面大於本票要解的問題。
- 不採「為條件 1 加顯式確認旗標」：每張既成票都要人工帶旗標，且新增一條可被濫用的放行路徑。

**範圍邊界**：
- 只放寬條件 1 的「多兄弟依賴」分支。「雙向依賴」分支維持 BLOCK，不因前驅狀態改變。
- 條件 2、3、4 不動。
- 終態的定義沿用 ticket 系統既有常數（completed、closed），不在 hook 內另寫一份字面清單；若 hook 無法匯入該常數，於 NeedsContext 回報，不自行硬編碼。
- 前驅的狀態取自 `siblings_map` 既有 frontmatter，不新增檔案讀取。

**驗收條件第 2 項的讀法**：守衛不掛在 create，故「建票時多兄弟依賴仍被擋」以守衛實際觸發點驗證——同一批 fixture 下，前驅含任一非終態時 claim／complete 仍 BLOCK。

**測試要求**（`.claude/hooks/tests/test_sibling_blockedby_validator_hook.py`）：
- E1 對照：同一張有 2 個以上前驅兄弟的票，前驅全為終態時放行、任一前驅非終態時 BLOCK，兩者結果不同。
- E2 正向對照：雙向依賴在前驅為終態時仍 BLOCK。
- 既有 `test_a2_violation_multi_sibling_dep` 的 fixture 若未設定前驅狀態，須明確設為非終態，使其繼續代表「該擋」的輸入。
- 執行 `uv run --project .claude/hooks pytest`（不帶路徑），全套件通過數與失敗數記入 Test Results。

**驗收條件第 3 項**（0.5.0-W1-096.4 complete）由 PM 在合併進 main 後協調該票的持有 session 執行，不屬實作代理人的工作。

**合併**：本票在 worktree 開發，代理人不合併、不推送；PM 覆核後合併。
