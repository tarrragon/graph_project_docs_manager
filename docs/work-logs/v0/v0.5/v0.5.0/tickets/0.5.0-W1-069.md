# Execution Log

## Task Summary

subagent-stop-dispatch-cleanup 精準匹配失敗後以 mark_oldest_active_null_agent_id_entry_turn_ended 做 FIFO 後援，呼叫端僅在候選數大於 1 時停用；同步派發 Stop 先於自身記錄寫入時，若恰有一筆其他仍在執行的 null agent_id 記錄，該筆會被誤標回合結束

---

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

已重現。hook 在 mark_turn_ended_by_handle 與 mark_turn_ended_by_id 皆未命中後，若 null 且未結束的候選數不大於 1，即呼叫 mark_oldest_active_null_agent_id_entry_turn_ended。該安全條件只數候選，不問候選是否屬於本次 Stop 的代理人。同步派發順序為 Pre、Stop、Post，Stop 時自身記錄未寫入，唯一候選必然是別人的記錄。

### 影響範圍

已驗證：隔離目錄放 hook 與 lib 實檔副本，狀態檔一筆 null 運行中記錄，送入 agent_id 無匹配的 Stop，該筆被寫入 turn_ended_at，輸出「目前無代理人在執行回合中」。影響 dispatch-active.json 的並行防護計數偏低。未驗證：真實 runtime 下同步與背景並行的發生頻率；Stop 的 session_id 是否為派發者 PM 的 session（若是，session_id 約束對同一 PM 的同步與背景派發無鑑別力）。

### 相關 Error Pattern

未新增 error-pattern；框架 issue #89（同生命週期，引用關係）已 observe。

## 重現實驗結果
### 實驗方法

複製 .claude/hooks 與 .claude/lib 到 scratchpad 隔離目錄（非 git clone、未碰主 repo 的 dispatch-active.json）。以 record_dispatch 寫一筆 agent_id 為 null 的運行中記錄，再以子行程執行實際 hook，stdin 為 agent_id 無匹配的 Stop JSON。

### 實驗執行

before: [('agent-A-running', None, None)]
hook stdout: 已標記回合結束 agent_id=abc123def456 | [OK] 目前無代理人在執行回合中
after: [('agent-A-running', None, '2026-10-07T00:32:28+00:00')]
hook 日誌: SubagentStop fallback 標記回合結束（FIFO 標記最早 null entry）

### 實驗發現

已驗證重現，誤標成立。正向對照輸入（運行中 null 記錄）確實被標。未驗證項見影響範圍。
