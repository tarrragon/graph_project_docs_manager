- 已驗證：TOML 的 token 多 1.35%；長文可逐字往返；TOML 的嚴格性在規格上較強，但現行票池的 YAML 隱式型別實害為 0；部分更新與三方合併兩者打平。
- 已驗證：`find_section` 不認 code fence，除了 2 張歷史票之外，本票在評估過程中也被它損壞。這個缺陷可以留在 markdown 內修正，與格式選型無關。
- 未驗證：兩種格式的 AI 生成錯誤率差異（N=3，且沒有 MD 對照）。

## Solution
### 結論：不改（整體與 frontmatter 都維持 markdown + YAML frontmatter）

理由一句話：TOML 的優勢集中在 frontmatter 嚴格性，但現行票池的 frontmatter 由 CLI 產生，YAML 寬鬆造成的實害實測是 0 筆。TOML 要付出的代價是實際存在的：8,963 個 null 欄位無法表示、5W1H 欄位順序被打散、寫入仍需第三方函式庫、token 多 1.35%。實測到的兩個真缺陷（章節邊界不認 code fence、frontmatter 註解在寫回時遺失）在 markdown 內就能修，不需要換格式。

### AI 讀取面

| token 量 | 基準 | +1.35%（全票池）、+4.8%（短票範例） | E1、E5（o200k 代理） |

### 長文章節在 TOML 的承載方式與代價

- 承載方式：`[[sections]]` array of tables，每個章節是 `title` 加 `text`。`text` 用 multi-line literal `'''`，不跳脫反斜線；若內文含 `'''`，退回 basic `"""` 並跳脫。
- 代價一：335 張票含反斜線，只要落入 basic 字串，每個反斜線都要加倍。實測有 1 張票含 `'''`，必須走 basic 字串。
- 代價二：三個引號是硬邊界，AI 用 Edit 直接改字串時，一旦弄壞邊界，整份票解析失敗。markdown 的錯誤只影響局部。
- 代價三：章節順序靠陣列順序，章節名稱不再是可定位的標題，Marksman、GitHub 等 markdown 工具不能預覽。
- 替代形狀：用 `[sections]` table，以章節名稱當 key，可直接定址。但中文與空白 key 要加引號，也失去順序保證（TOML 1.0 沒有規範 table 內 key 的順序語意）。
