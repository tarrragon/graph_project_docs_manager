## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

閘門的 flutter 套件只跑 `fvm flutter test`（test/），integration_test 從未經閘門。實測 integration_test 全套在 macOS 穩定：6 次執行皆 36 通過、2 skip（實機探測，預設關閉）、0 失敗；冷建置 75 秒、暖執行中位數 53 秒。閘門快照每次新建，應以冷建置 75 秒估成本。

### 量測依據

| 項目 | 數值 | 來源 |
|------|------|------|
| flutter 套件耗時（非沿用） | 75～202 秒，中位數約 105 秒 | worktree-merge.log 最近 40 筆 |
| integration_test 冷建置 | 75 秒 | 本票重現實驗 |
| 近 7 天合併總數 | 331 | git log --merges --since=2026-10-14 |
| 其中觸及 flutter 套件 prefixes | 57 | 同上（docs/ 含票檔，實際觸發數略低） |
| 其中觸及 lib/、integration_test/、macos/、pubspec | 32 | 同上 |

### 候選方案

| 方案 | 做法 | 成本 | 漏網風險 |
|------|------|------|---------|
| A 全跑 | flutter 套件 command 之後追加 integration_test，或新增同 prefixes 的套件 | 每次觸發 flutter 套件 +約 75 秒（中位數 105→180 秒，約 +70%），近 7 天約 57 次；heavy 名額持有時間同比拉長，並行線排隊變長；docs/ 改動也會觸發 | 最低 |
| B 依路徑觸發 | merge-gate.yaml 新增套件 `flutter-integration`：prefixes [lib/, integration_test/, macos/]、files [pubspec.yaml, pubspec.lock]、command [fvm, flutter, test, integration_test, -d, macos] | 每次觸發 +約 75 秒，近 7 天約 32 次；純 docs／test 改動不受影響 | 只改 test/helpers 等共用前提而影響 integration_test 時漏網（integration_test 不 import test/helpers 則無此路徑，待確認） |
| C 維持現狀 | 不改閘門，改動預設狀態、外框、平台互動時由 PM 開驗證票補位 | 0 | 依賴 PM 判斷何時開驗證票；W3-003.2 即是事後才補的案例，本次未造成實際失敗 |

共同風險（A、B）：閘門會在本機啟動 macOS App 視窗（stderr 有 "Failed to foreground app"），合併期間會出現視窗；CI 落地（PR 加 CI）時需 macOS runner 才能延續。

### 推薦

B。成本只落在真正可能影響 integration_test 的合併，近 7 天約 32 次 × 75 秒；C 的補位依賴人工判斷，W3-003.2 已示範該判斷會漏。
