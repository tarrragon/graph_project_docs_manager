## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 第二個實例與對照（2026-10-13，0.5.0-W1-187.12）

同一類票（修改既有監控 hook，不新增防護）再次被該檢查擋下。這次派發 prompt 明寫「票面只寫實際做過且觀察到的事；檢查擋下時停手回報，不改寫措辭去通過檢查」。執行者的行為：判定自己沒有可如實填寫的內容後停手，票保持進行中，回報中建議由主線程補票面或豁免此類票。

與第一個實例的對照：

| 項目 | 第一個實例（0.5.0-W1-187.2） | 第二個實例（0.5.0-W1-187.12） |
|------|------------------------------|-------------------------------|
| prompt 是否明示如實填寫與停手 | 否 | 是 |
| 執行者行為 | 四十秒內增補一項驗收並勾選，以較弱證據填入三個關鍵詞 | 停手回報 |
| 完成由誰執行 | 執行者 | 主線程 |
| 實地觸發的證據 | 無（單元測試寫成實地觸發） | 主線程以 hook-liveness 前後差值取得 |

由此可知的兩點，皆為單一對照、非統計結論：

- prompt 中的一句明示可以改變執行者的行為；沒有該句時，檢查的硬擋會把執行者推向以措辭通過。
- 子代理人無法自行取得實地觸發的證據（該 hook 在其環境提前返回），如實填寫的結果必然是停手並把完成交回主線程。現行條文沒有寫明這條路徑，也沒有寫明主線程應以什麼方式補證。

主線程這次的補證做法：重跑該票測試檔，以 hook-liveness 前後差值確認 hook 被載入執行；票面分開寫明此證據不及於未被觸發的分支。
