### 判準提案（2026-10-31，L39；動手前回報主控核可）

**訊號來源**：以下三種訊號任一成立，即判定該線在等用戶。只檢查該線最後一行現行佇列行裡、狀態不是 completed 的票。

| 訊號 | 讀什麼 | 寫入方 | 解除 |
|------|--------|--------|------|
| S1 票面標記（主訊號） | 票的 `## Solution` 段中，固定格式的行 `**等用戶**：<事項>`。同一張票以最後一行為準 | 線本身：停下來等用戶時，以 append-log 寫入 | 追加一行 `**等用戶解除**：<結果>`。append-only 保留歷史，最後一行若是解除就不列出；票 completed 也不列出 |
| S2 session 等待中 | 該線存活 session 的 session 檔 `status=waiting`，附 `waitingFor` 原文 | Claude Code（AskUserQuestion、權限詢問） | session 狀態變動時自動解除 |
| S3 佇列行註記 | 現行佇列行的票註記，或文字中含字面「等用戶」，例如 `511（等用戶開 --debug）` | 主控 | 主控追加新的佇列行 |

**不採用的來源與理由**：
- 票 status：沒有「等用戶」這個狀態，in_progress 與 pending 都分辨不出來
- 票面自由文字（如「待用戶」「尚待」）：歷史行會殘留。例如 571.2 的「待用戶：在 worktree 路徑開互動式 session」在實測後仍留在票面，沒有解除記號，會誤報
- scope_blocker：語意是發版阻擋，不適用

**輸出**：與接續狀態是兩件獨立的事，另列一段「等用戶（N）」。每項一行：`L<n>（名稱）<票號>：<事項>（來源 S1／S2／S3）`；N 為 0 時寫「等用戶：無」。

**誤報邊界**：
- S1 寫了，用戶回應後卻沒補解除行，標記會一直留著，輸出照列。對策是 SKILL 寫明「用戶回應後同一步寫解除行」；票 completed 後自動不列
- S2 包含短暫的權限詢問，這也確實是在等用戶，照列
- S3 只讀每條線的最後一行，歷史行不列

**漏報邊界**：
- 線停下時沒寫 S1，session 也已 idle，也就是 571.2 原本的情況：工具偵測不到。所以 SKILL 要把「停下等用戶時寫 S1 標記並傳訊主控」定為規則。S1 是讓「忘了傳訊」仍可被偵測的那一半
- 標記寫在不在佇列裡的票，例如新衍生的票：不讀，不列
- 線在 worktree 裡改票、尚未合併：不受影響，因為 append-log 寫的是主 checkout 的票檔，工具也讀主 checkout

**E2**：
- S1、S2、S3 各準備一組有訊號的 fixture，必須列出
- 對照組不得誤報：有標記但最後一行是解除、有標記但票已 completed、自由文字「待用戶」、session 狀態是 idle、歷史佇列行含「等用戶」
