## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 補記：等待寫法本身的缺陷（2026-10-07，於認領前以 --force 寫入）

0.5.0-W1-083.2 執行者發現：PM 在多張派發 prompt 中指定的 `while pgrep -f "pytest -q" ...` 會把其他等待者的 shell 命令列（內含同一字串）也比對為正在跑的 pytest，造成等待者互相卡死；PM 本身三組 main 背景套件即因此長時間未開跑，經 TaskStop 後確認。macOS pgrep 只排除自身與祖先程序。

派發範本 `agent-dispatch-template.md` 早已載明此陷阱：「需要等待程序結束時，等已知 PID（kill -0 <pid>），不以 pgrep -f 樣式作迴圈條件」，並附 Why／Consequence（1.38.0）。PM 的 prompt 未遵循該條，屬執行端違反既有條文，非框架缺條文。

對本票分析的影響：先前記為「執行者未等待即開跑」的三例中，部分執行者是在 shell 命令列被誤判、實際沒有 pytest 在跑的情況下判斷；W1-083.2 執行者以 ps 確認無真實 pytest 後才開跑。分析時須把「真有他方套件在跑」與「被等待者 shell 誤判」分開計算，可用精確樣式 `pgrep -fl '\.venv/bin/python[^ ]* [^ ]*bin/pytest'` 只比對真正的 pytest 程序。
