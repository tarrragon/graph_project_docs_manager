## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 既有分析（incident-responder 唯讀分析，2026-10-21，研究線接手 session 轉錄）

- 閘門選套件：`.claude/skills/worktree/scripts/merge_gate.py` 的 `select_suites()` 以改動路徑比對宣告中各套件的 `prefixes`／`files`；`suite_command()` 回傳宣告命令。宣告檔 `.claude/project-integration/merge-gate.yaml` 的 flutter-integration 命令為 `[fvm, flutter, test, integration_test, -d, macos]`，對整個目錄遞迴掃 `*_test.dart`，閘門本身不篩檔。
- 466.2 之前 main 的 `integration_test/` 只有 `app_test.dart` 一個 `_test` 檔，466.2 首次讓同次執行依序啟動兩個 App。兩檔在同一 worktree 重建同一個 `build/macos/Build/Products/Debug/graph_project_docs_manager.app`，推論第二個 App 需等前一實例收尾。
- main 單跑 `python3 .claude/scripts/run-with-timeout.py 600 -- fvm flutter test integration_test/app_test.dart -d macos`：N=5，GREEN 5／RED 0，每次 `+36 ~2: All tests passed!`、約 26 秒；量測時 swap 剩 757MB（閘門失敗時 528MB）。五次通過的執行都印出 `Failed to foreground app; open returned 1`。原始 log 存於當時 session 的 scratchpad，已不可依賴，以本段數字為準。
- 失敗訊號：`Unable to start the app on the device` + `Error waiting for a debug connection: The log reader stopped unexpectedly, or never started.`
- 466.2 已以改名 `ux_capture.dart`（不帶 `_test`）避開目錄掃描，本票不阻擋 466.2。重現本票時需自建兩個最小 `_test` 檔，不要沿用 466.2 的研究檔。

### 補充：失敗摘要的雜訊行（主控，2026-10-21）

研究線回報合併閘門的失敗摘要把 `Failed to foreground app` 這類雜訊行和真正的致命行並列，通過的執行裡也每次都有這一行。主控查證後判定是專案層的設定缺口，不是框架缺陷：

- `.claude/skills/worktree/scripts/merge_gate.py` 的 `_failed_items` 支援每個套件宣告 `failure` 正規式。沒有宣告時才退回內建規則：先找 `FAILED ` 開頭與含 `[E]` 的行，都找不到就取輸出尾段。
- 本專案 `.claude/project-integration/merge-gate.yaml` 只有 line-board 宣告了 `failure`。flutter-integration 沒有宣告，App 啟動失敗時輸出又沒有 `[E]` 行，所以摘要取的是尾段。
- 框架問題的兩條判準中，第二條（根源在 `.claude/` 通用資產）不成立：框架已經提供宣告機制，是專案沒有用上。因此不開 issue，改併入本票，與「是否改成逐檔啟動」一起決定 flutter-integration 的宣告內容。

### 實驗發現
- 已驗證：同一次執行依序啟動兩個 macOS App 時，第二個確定性失敗（5/5），逐檔分開確定性通過（10/10）；swap 條件相同，記憶體壓力不是決定因子（至少在 free 約 1GB 時）。
- 已驗證：`Failed to foreground app; open returned 1` 在 GREEN 10/10 與 RED 5/5 都出現，不是失敗訊號。
- 已驗證：本次失敗輸出含 `[E]` 行（loading ... [E]），但該行只含檔名，致命原因在其前一行與後一行；內建規則取 `[E]` 行會漏掉致命字串。466.2 的失敗輸出無 `[E]` 行，兩種形態皆需被正規式涵蓋。
- 未驗證：第二個 App 失敗的底層機制（同一 .app 路徑的前一實例未收尾，屬推論）；不影響決策，因逐檔啟動已確定性避開。
