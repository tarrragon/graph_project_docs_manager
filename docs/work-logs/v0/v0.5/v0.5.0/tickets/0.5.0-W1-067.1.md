## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
`.claude/lib/hook_io.py` 新增 `get_handoff_recovery_ticket_ids(logger, project_root)`，回傳 pending handoff 指向的票集合：來源 ticket_id、target_ticket_id，以及 direction 後綴（to-sibling:<id> 等）的目標。另新增 `prompt_references_handoff_ticket`，以完整 ID 邊界比對 prompt，子票 X.1 不會命中父票 X。
- agent-ticket-validation-hook 與 task-dispatch-readiness-check 的恢復模式放行，改為「prompt 引用集合內的票」才成立；
- ticket-file-access-guard 移除本地重複解析，改用共用函式；
- `is_handoff_recovery_mode` 保留給既有測試，已無守衛呼叫。

commit 82cf6cf9e，合併 abd518714。

### 自檢結果

- 前提驗證：`ticket resume`／`handoff` 只印指示並寫 pending JSON，不會自動派發；派發 prompt 由 PM 依範本撰寫，並受 Ticket 引用守衛強制，因此恢復流程的派發會引用票（依守衛行為與範本推得，未實測真實恢復派發）。
- 執行者所提缺口的 PM 裁決：direction 為不帶後綴的 to-parent／to-child 時，集合只含來源票。程式碼確認，集合外的引用會回到一般驗證，不會直接拒絕；帶有效 Ticket 行的派發照常通過，只是不享有豁免。因此不放寬集合，避免擴大豁免範圍。
- RED：新測試 11 個，舊碼 6 紅 3 綠，direction 後綴測試先紅才補實作。GREEN：11 passed。E1（引用來源或目標票）放行，E2（缺 Ticket 行、引用無關票、子票不命中父票）攔截，兩者結果不同。
- 實地觸發（本 session 實地觸發確認）：在 `git clone --no-hardlinks` 的 clone 內放入指向不存在票的殘留 pending 檔。缺 Ticket 行的 payload 修正前 rc=0 allow、修正後 rc=2 deny；引用 handoff 票的 payload 兩版皆 rc=0。主 repo 的 pending 目錄全程未放檔。
- 規則 8：測試 ID 改為 demo-src／demo-tgt，新增行 0 命中。

### Phase 4 評估

- 重構需要：否。
- 技術債務：無新增。三支守衛改用同一個集合函式，原本的重複解析已移除。
- 程式碼品質：A。
- 結論：集合函式失敗一律回空集合（等同不豁免），比對以完整 ID 邊界避免誤命中。
