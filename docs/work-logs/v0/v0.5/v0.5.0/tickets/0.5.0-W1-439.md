### WRAP 評估：框架清理的觸發條件（2026-10-20，主控）

**錨點**：客戶是用戶本人（文件圖譜 App 的開發者），核心目標是推進 0.5.0 產品。框架修補是手段，不是產出。

**R 證據**（0.5.0 票庫，以 where.files 粗分，同一張票可能同時命中兩類）：
- 改 `.claude/` 的約 587 張，改 `lib/`／`test/` 的 99 張，框架工作約為產品的 6 倍。
- 產品 pending 32 張，其中 P1 7 張。框架 pending 73 張，全是 P2／P3。
- 修框架的線會自己生出新票：424 生出 4 張，421 生出 435，422 生出 440。所以任何「數量門檻」都會永遠成立。
- minor 週期不穩定：0.1～0.4 每版 1～4 天；0.5.0 自 10-02 起，到 10-20 仍未結束。
- canonical 約有 60 個 open issue，最舊的在 8 月。

**反向思考**：issue 累積本身不傷害專案，只有拖慢專案的問題才會。所以門檻看影響，不看數量。

**W 選項**：
- 版本邊界分診
- 拖慢次數
- 單一 issue 的觀測數
- 版本摘要由用戶挑
- 組合

觀測數門檻排除，理由是目前已有十餘個 issue 超過門檻，而且觀測數與影響無關。

**P 失敗預想與早期訊號**：
- 「拖慢專案」標得太寬，就會退回什麼都派。訊號：一週內開兩條以上清理線。
- 版本邊界久久不來，issue 擱置。訊號：已有標記第二次的 issue，卻沒有清理線可開。
- 清理線自我繁殖、做不完。護欄：開線時固定範圍。
- P0／P1 分級膨脹。護欄：PM 查證該 bug 確實阻擋專案工作。

### 用戶裁定（2026-10-20）

1. 觸發條件採組合，兩種情況可以開清理線：
   - (a) 各線碰到框架阻礙時，在該 issue 觀測並標記「拖慢專案」，同一個 issue 被標記第二次。
   - (b) 每個 minor 收尾時，主控整理一份 open issue 摘要，由用戶挑要清哪個。
2. 兩個護欄：
   - 清理線開線時把範圍固定在一個 issue（或一個叢集），途中的新發現一律回 issue，範圍做完就結束。
   - 至少有一條產品線在跑，才能開清理線。
3. 本機票觀測進 issue 後即關票，issue 為唯一權威；closed_by 寫 issue 編號，清理線開線時從 issue 區段重新建票。這樣 ANA 的子票都會是終態，不必用 `--force`。
4. 前一則裁示照舊：
   - 非 P0／P1 bug 不派修，用戶要求的例外。
   - 框架修復線不超過兩條。
   - 工作主目標放在專案進度。
