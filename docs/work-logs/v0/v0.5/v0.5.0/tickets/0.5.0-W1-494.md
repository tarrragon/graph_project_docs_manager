### 重現線索：7.1 無警告、7.2 有警告的差異（2026-10-27，主控要求補記）

依 `git reflog show --date=iso origin/main` 與合併 commit 時間：

| 情境 | 合併 commit（建立時間） | cleanup 前 origin/main 是否已含該 commit | 警告 |
|------|------------------------|----------------------------------------|------|
| 485.7.1 | 0abefd9b4（16:55:40） | 是：origin/main 於 16:56:03 update by push 至 0abefd9b4 | 無 |
| 485.7.2 | 4fe3923e1（17:08:49） | 否：origin/main 下一次更新為 17:09:40（37fba9056，PM 於 cleanup 之後 push） | LEVEL2 |

更正 why 欄：「485.7.1 以同流程（merge 後、push 前 cleanup）」不成立。7.1 cleanup 當下該 commit 已在 origin，差異即在此。16:56:03 那次 push 的執行者未查明：不是本 session（本 session 首次 push 為 16:59:47 的 e20e88b29），可能是其他並行 session 推 main 時順帶推上。

由此推定 LEVEL2 的判定與「分支 commit 是否可由某個遠端 ref 到達」相關，而非「是否可由本地 base 到達」；警告句「本地 commit 將無法恢復」把「未備份到遠端」說成「會遺失」，在 commit 已進本地 main 時與事實不符。推定待讀碼確認（acceptance 1）。

重現步驟候選：tmp repo 建 bare 遠端 → worktree 分支 commit → merge 入本地 main → (a) 不 push 即 cleanup，預期 LEVEL2；(b) push main 後 cleanup，預期無警告。
### 16:56:03 推送者（2026-10-27，主控查證後轉達，PM 以 reflog 複核）

16:56:03 把 origin/main 推到 0abefd9b4 的是 L18（畫面接真資料），不是主控、也不是本 session。reflog 複核：16:54:07 推到 02730ad38（L18 的 0.5.0-W1-479.2 合併），16:56:03 推到 0abefd9b4；L18 回報主控原文「main 已推送到 0abefd9b4」。共用本地 main 上已有本 session 16:55:40 的 485.7.1 合併，L18 推送時一併帶上——推送帶出全部本地 commit 的正常結果，非異常。主控 session 未推送。

對重現的意義：7.1 無警告是並行 session 推送的副作用，不是 cleanup 對 7.1 的判定有別；單一 session 依序執行 merge → cleanup → push 時，預期每次都會出現 LEVEL2。
對照資料點（2026-10-27）：485.7.3 合併 42fb27a65 後先 push（origin/main 至 3847e725c）再 worktree cleanup --branch worktree-agent-a7eeab728d0ceeff4，未出現 LEVEL2，與 7.2（cleanup 在 push 前）形成單一 session 內的有無對照，支持「LEVEL2 判定依 commit 是否已到遠端」的推定。
