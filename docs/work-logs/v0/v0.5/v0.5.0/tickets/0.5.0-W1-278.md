### 轉派與初步證據（2026-10-14，E 線接手，PM 前置查證）

- 轉派：派發 session 把本票由 F 線轉給 E 線，排在 277 之後、274 之前，優先度升為 P1。派發 session 另以 grep 找到 5 支用 `os.getppid()` 的 hook：`dispatch-count-guard-hook.py`（守衛）、`session-context-guard-hook.py`、ticket skill 的 `handoff-prompt-reminder-hook.py`、`handoff_session_mgmt.py`、`post-ticket-lifecycle-hook.py`
- 「這是 189.1 的回歸」這個假設與現有證據不符：
  - `session-context-guard-hook.py` 的計數檔是 `/tmp/claude-session-completed-tickets-{ppid}`。目前 /tmp 下有 155 個這種檔，最近 40 個的值幾乎都是 1（只有 4 個是 2）
  - 189.1 的分派程序是在 16:5x 合併（fce1436b6）。16:01～16:45 之間已經有大量各自只記 1 的計數檔，也就是說，分派程序上線前每次呼叫的 ppid 就已經不同
  - 機制：settings.json 以 `uv run --quiet <hook>.py` 啟動 hook，而 uv 是另外產生一個 Python 子程序，不是直接以 Python 取代自己（189 實測：uv pid 41318、Python 子程序 41400 是兩個不同的程序）。所以 hook 的 `os.getppid()` 一直是「這一次的 uv 程序」，每次呼叫都不同。分派程序上線後，ppid 變成「分派程序的 uv 程序」，同樣每次不同，性質沒有改變
- 本票待做：逐支確認這 5 支 hook 各掛在哪個事件與 matcher、是否經過分派程序、ppid 實際指向哪個程序、計數或 session 鍵從何時開始失效（附實測）；dispatch-count-guard 是守衛，優先確認。修法候選：改用 hook 輸入中的 session_id，或由啟動端透傳一個穩定的識別

## 重現實驗結果
### 實驗方法

1. 對照註冊位置：從 settings.json 與 hook-dispatch-registry.json 找出 5 支 hook 各掛在哪個事件與 matcher、是否經過分派程序
2. 讀碼：確認每支以 `os.getppid()` 組成的狀態檔路徑與用途
3. 現場狀態檔：用 Python glob 統計 /tmp 下各類狀態檔的數量、修改時間（以 189.1 合併的 16:54 為界）與內容值
4. 重現（dispatch-count-guard）：用 Write 寫好兩個 payload 檔，再以 runtime 相同的形式（`uv run --quiet <hook>.py < payload`）先後執行 PostToolUse（Agent，prompt 含「三人組」）與 UserPromptSubmit，觀察兩者是否讀寫同一個狀態檔。實驗後已刪除產生的狀態檔

### 實驗執行

| hook | 註冊位置 | 經分派程序 | ppid 鍵的狀態檔 | 用途 |
|---|---|---|---|---|
| session-context-guard-hook.py | PostToolUse:Bash | 是 | `/tmp/claude-session-completed-tickets-{ppid}` | 本 session 完成票數，達閾值提醒 |
| post-ticket-lifecycle-hook.py（含 session-context-guard 子邏輯） | PostToolUse:Bash | 是 | 同上 | 同上 |
| dispatch-count-guard-hook.py | PostToolUse:Agent、UserPromptSubmit | 否 | `/tmp/claude-dispatch-batch-{ppid}.json` | Agent 呼叫時記派發數，下次用戶輸入時比對宣稱人數 |
| handoff-prompt-reminder-hook.py | UserPromptSubmit | 否 | `/tmp/claude-handoff-reminded-{ppid}` | 每個 session 只提醒一次 |
| handoff_session_mgmt.py（由 handoff-auto-resume-stop-hook 匯入） | Stop | 否 | `/tmp/claude-handoff-state-{ppid}.json` | 每個 session 只觸發一次 Stop 處置 |

現場狀態檔：`claude-session-completed-tickets-*` 共 165 個，其中 150 個早於 189.1 合併，最早 11:54；內容 152 個為 1、13 個為 2。其他三類目前都是 0 個。

dispatch-count-guard 重現：PostToolUse 執行後寫出 `/tmp/claude-dispatch-batch-26525.json`（expected 3、actual 1、keywords 三人組與多視角）；接著 UserPromptSubmit 執行，沒有任何輸出，且該狀態檔仍在原處，未被讀取也未被清理。

### 實驗發現

已驗證：

1. 失效不是 189.1 造成的。runtime 以 `uv run` 啟動 hook，uv 另外產生 Python 子程序（189 實測兩者 pid 不同），hook 的 `os.getppid()` 一直是當次的 uv 程序，每次呼叫都不同。分派程序上線後 ppid 換成分派程序的 uv 程序，性質相同。早於 189.1 的 150 個只記 1 或 2 的計數檔就是證據
2. session-context-guard 的完成計數每次呼叫都從 0 開始，提醒閾值永遠達不到
3. dispatch-count-guard 的寫入端與讀取端是兩個不同的 uv 程序，讀取端永遠找不到寫入端的狀態檔，所以派發人數不符的警告從未發出。它本身就是 exit 0 的警告型 hook，不會擋下任何操作；失效的後果是警告消失，不是放行
4. 「每個 session 只做一次」類（handoff-prompt-reminder、handoff_session_mgmt）依同一機制，每次呼叫都會被當成新 session，可能重複提醒或重複觸發

未驗證：handoff-prompt-reminder 與 handoff_session_mgmt 在 runtime 的實際重複次數（目前沒有現場狀態檔，可能是觸發條件少見）；/tmp 下這些孤兒狀態檔是否有清理機制。

## Solution
### 分析結論

5 支以 `os.getppid()` 當 session 鍵的 hook 全部失效。原因是 runtime 以 `uv run` 啟動 hook，ppid 是每次呼叫都不同的 uv 程序，這個問題早在 189.1 之前就存在，不是分派程序造成的回歸。修法是改用 hook 輸入中的 `session_id`。

### 候選評估

| 候選 | 涵蓋 | 穩定性 | 判定 |
|---|---|---|---|
| A 改用 hook 輸入的 session_id | 5 支全涵蓋，每個事件的輸入都有 | 同一 session 內固定，與啟動方式無關 | 採用，子票 0.5.0-W1-278.1 |
| B 分派程序透傳原本的 ppid（環境變數） | 只涵蓋經分派程序的 2 支 | 原本的 ppid 也是每次不同的 uv 程序，透傳後一樣不穩定 | 不採用：前提不成立 |
| C 沿程序樹往上找 claude 主程序的 pid | 5 支 | 依賴程序樹的形狀，換啟動方式（分派程序、uv 版本）就失效 | 不採用：189.1 才剛改變過一次程序樹 |

### 同一 session 連續完成兩張票的模擬（acceptance 第 1 條）

- 做法：以本 session 的 session_id 組成 PostToolUse payload，command 為 `ticket track complete 0.5.0-W1-999 --as x`，stdout 含成功標記「已完成」；以 runtime 相同的形式 `uv run --quiet .claude/hooks/session-context-guard-hook.py < payload` 連續執行兩次。payload 中的票號是實驗用的虛擬票，沒有真的建票或 complete
- 結果：兩次各寫出一個計數檔，ppid 分別為 41524 與 41620，內容都是 1，兩次都沒有提醒（軟提醒閾值是 2）。同一 session 的第二次完成沒有累加到第一次的檔。兩個實驗檔已刪除

### 補充發現：189.1 之後同一次完成被計兩次

- /tmp 的計數檔依 189.1 合併時間（16:54）分組：合併前 150 個全是 1；合併後 15 個中 13 個是 2
- 原因：`session-context-guard-hook.py` 與 `post-ticket-lifecycle-hook.py`（後者含「子邏輯 1：Session Context Guard（來自 session-context-guard-hook）」）都註冊在 PostToolUse:Bash，對同一次 complete 各加 1。合併前兩者各是一個 uv 程序，ppid 不同，所以各寫各的檔、各記 1；合併後兩者在同一個分派程序內，ppid 相同，加到同一個檔裡變成 2
- 影響：軟提醒閾值是 2，所以 189.1 之後每次 complete 都可能立刻觸發軟提醒。這部分屬 189.1 帶來的行為變化；而重複註冊本身與 tarrragon/claude#68（改名後新舊 hook 重複執行）同類
- 落地：已在 278.1 加一條驗收，改用 session_id 前先消除重複計數，否則鍵改穩定後每次 complete 都會加 2
