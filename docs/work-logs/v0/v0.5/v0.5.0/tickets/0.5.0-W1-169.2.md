# Execution Log

## Task Summary

分析 落到三個阻擋狀態的載入輪次不經過 state-domain-loading，與 SPEC-001 §1 及 SPEC-003 §2.15 跨級別證據鏈的一致性

---

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`GateDetectionNotifier.detect` 只在 InKnownRange 分支經 `DomainViewLoader.load`（其第一個寫入是 `DomainLoading`）；三個阻擋分支以 `_apply` → `applyGateBlock` 直接寫終態。0.2.0-W1-033 建 detect 時三個阻擋判定不需掃描，故未寫載入中；0.5.0-W1-114.14 把 Ready 路徑改走共用輪次時只動了 InKnownRange 分支。

### 影響範圍

- `lib/app/gate_detection_notifier.dart`（票面 where.files 正確；169 主票〈實驗方法〉寫成 `lib/screens/domain_view/`，路徑有誤）。
- 呼叫端兩處：`lib/app/workspace_selection.dart` 的 `select`（使用者選定，含浮層與 §3.1 選擇資料夾）、`lib/assembly/shell.dart` 的啟動還原。
- 啟動還原不受影響：`domainViewStateProvider` 初值即 `DomainLoading`，阻擋分支是由載入中轉出。受影響的是 `select` 路徑。

### 相關 Error Pattern

無。屬專案層規格與實作漂移。

## 重現實驗結果
### 實驗方法

靜態讀碼（L42，2026-10-31）。讀取：SPEC-001 §1 表「未選專案」「載入中」兩列與表後註記〈載入中的退出路徑涵蓋三個阻擋狀態〉；`GateDetectionNotifier.detect`／`_apply`；`DomainViewLoader.load`／`applyGateBlock`／`cancelLoading`；`WorkspaceSelectionNotifier.select`；`_ShellState` 啟動還原段；`domainViewStateProvider` 初值。未跑測試、未實機。

### 實驗執行

SPEC-001 §1 原文：
- 「未選專案」列退出路徑：「選擇資料夾 → 載入中」。
- 「載入中」列退出路徑：「完成 → 正常／空圖／不是框架專案／無可消費的型別表／schema 不相容；載入輪次拋出非預期例外 → 載入失敗」。
- 表後註記：三個阻擋狀態「的進入條件皆發生在資料夾已選定之後……而選定資料夾一律先進入『載入中』。三者因此都是『載入中』完成後的可能落點……而非各自獨立於『載入中』之外的入口」。

`detect` 的寫入順序：

| 分支 | 先前寫入 | 本輪寫入序列 |
|------|---------|-------------|
| 皆缺 → 不是框架專案 | 無 | `applyGateBlock(DomainNotFramework)` |
| JSON 缺 → 無可消費的型別表 | 無 | `applyGateBlock(DomainSchemaUnconsumable)` |
| 超出範圍 → schema 不相容 | 無 | `applyGateBlock(DomainSchemaIncompatible)` |
| InKnownRange | 無 | `load()`：`DomainLoading` → Ready／Empty／LoadFailed／Unset |

四個分支在第一次寫入前都先 await 三到四次 probe I/O（`readVersion`、`schemaJsonExists`，後兩者另含 `builtinSchemaVersionProvider.future`、`readSchemaJsonVersion`）；這段期間畫面維持前一個狀態。

### 實驗發現

已由讀碼確立：
1. `select` 路徑下三個阻擋分支不經 `DomainLoading`，與 SPEC-001 §1 表後註記不一致。從阻擋狀態出口發起的新一輪，前一個阻擋狀態會一直顯示到新終態寫入。
2. InKnownRange 分支經過載入中，但 `DomainLoading` 晚於 probe I/O 才寫入；規格「一律先進入」以選定為起點，這段延遲同屬不一致，只是較短。
3. 競態（169.3 須處理）：`applyGateBlock` 遞增世代但不檢查呼叫者的世代；`detect` 也不記錄起始世代。若改為 detect 開頭先寫 `DomainLoading`，使用者在 probe 期間按「取消載入」→ `cancelLoading` 寫 `DomainUnset` → detect 繼續執行後仍寫入阻擋狀態或啟動 `load()`，取消被覆蓋。啟動還原路徑今天就有同一窗口（初值為 `DomainLoading`，取消鈕可按）。

未驗證：probe I/O 實際耗時（決定窗口長短）；第 3 點的競態未以測試重現。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論（L42，2026-10-31；讀碼得出）

**acceptance 1**：SPEC-001 §1 原文與 detect 寫入順序對照見〈重現實驗結果〉。

**acceptance 2：不一致。以 SPEC-001 §1 為準。** 依據：用戶 2026-10-31 對 169 Y 組裁定 Y1（以規格為準改實作），且 SPEC-003 §2.15 跨級別表的空成立論證直接引用本條。規格不改。

### 候選處置

| 候選 | 內容 | 利 | 弊 |
|------|------|----|----|
| A（建議）`detect` 開頭先寫 `DomainLoading`，並記錄起始世代 | 進入 detect 第一個動作寫載入中；之後每次寫入前檢查世代未變，被取消或被新一輪取代即放棄 | 兩個呼叫端一次對齊；InKnownRange 的 probe 延遲一併消除；修掉第 3 點競態 | `load()` 會再寫一次 `DomainLoading`（冪等）；`applyGateBlock` 簽章要帶世代或改由 detect 守門 |
| B 由 `select` 在呼叫 detect 前寫 `DomainLoading` | 只改呼叫端 | detect 不動 | 啟動還原靠初值碰巧成立，日後新增呼叫端會再漂移；競態仍在 |
| C 改規格承認阻擋狀態可不經載入中 | 不改程式 | 零實作 | 與用戶 Y1 裁定相反；§2.15 空成立論證失去依據 |
