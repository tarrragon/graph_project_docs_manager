## 重現實驗結果
### 實驗方法

在主 checkout 的 PM session（auto mode）以 heredoc 傳入含複合 git 命令形態的內容給 append-log，觀察 Claude Code runtime 是否以「names git in a form too complex to verify」拒絕。測試字串：`git -C /tmp/x add f && git -C /tmp/x commit -m y`，以及 `$(git rev-parse HEAD)` 形態。

### 實驗執行（worktree 子代理人）

測試字串：`git -C /tmp/x add f && git -C /tmp/x commit -m y`，以及 `$(git rev-parse HEAD)` 形態。若本段出現在票面，表示 worktree 子代理人情境下未被 runtime 拒絕。
### 實驗發現

- 兩種情境皆未重現：主 checkout PM session（auto mode）與 worktree 子代理人（pwd 為 .claude/worktrees/agent-a04045f6b4ed62a50）以同一 heredoc（含 `git -C … && git -C … commit` 與 `$(git rev-parse HEAD)`）呼叫 append-log，皆 rc=0；子代理人情境下 CLI 輸出「偵測到 linked worktree，票務狀態改作用於主倉庫」，寫入落在主倉庫票檔
- 已驗證：runtime 拒絕不是「heredoc 含 git 字樣」即必然觸發；原事件（341.2）的逐字拒絕訊息屬實，但觸發條件（權限模式、內容的特定形態或版本）未能定位
- 未驗證：原事件的確切觸發條件。結論不依賴找到它
## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 三個問題的結論

1. **tool-selection 規則 2「too complex to verify」例外是否足以讓 append-log 在 worktree 內通過**：否。該例外處置是「拆成原命令中的單一命令分次執行」，前提是被拒的是複合命令；append-log 加 heredoc 是單一命令，沒有可拆的部分。兩次重現（PM session、worktree 子代理人）皆未觸發拒絕，觸發條件無法定位，因此不能靠「改寫內容避開觸發」作為處置。不依賴觸發條件的解法是讓內容不出現在命令文字中：0.5.0-W1-355.2（append-log --content-file）
2. **被擋後改用 Edit 寫 worktree 內票檔是否違反 root 分離**：是。ticket SKILL〈Ticket 狀態與程式碼提交的 root 分離〉規定票面寫入一律回推主倉庫；Edit 直改 worktree 內票檔使同一張票分處兩地（worktree 分支一份、主倉庫一份），須 PM 手動合併。且依 tool-selection 規則 2，非專案來源（runtime）拒絕的語意是「不該做」而非「選錯工具」，應停手回報，不換工具繞過。dispatch 骨架現有「禁止複製或提交票面副本」未涵蓋這條退路：0.5.0-W1-355.1 於隔離派發骨架明示「CLI 被拒時不改用 Edit，內容放進回報由 PM 寫入」
3. **框架 issue 關係判定**：不新開、不附加。
   - 兩條 AND 判準：抽象可攜（任何以 worktree 派發的 consumer 皆可能遇到）成立；根源在 `.claude/` 通用資產——runtime 拒絕本身不在框架內，但票面分裂源於派發骨架未寫退路、append-log 只接受命令列內容，兩者皆在 `.claude/`，成立
   - dedup：#46（已關閉，claim 因 cwd 解析分裂寫入）與本案同屬「票面分裂」但機制不同；#43（已關閉）為 runtime 沙盒擋 complete，同屬 runtime 拒絕但不涉票面分裂。兩者皆為引用關係，不重複
   - 處置：新開 issue 依 CLAUDE.md 須逐次授權；本專案為框架主控方，修正直接落在本地 `.claude/`（355.1、355.2），隨下次 sync-push 進 canonical，不另開 issue
