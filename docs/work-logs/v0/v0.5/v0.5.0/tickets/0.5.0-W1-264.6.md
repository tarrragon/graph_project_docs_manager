## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因
`_state_cache = {"data", "mtime"}` 為模組級單槽快取。_read_state 命中條件僅為 data 非 None 且 mtime 浮點相等，鍵不含路徑，也不記錄路徑。失效時機只有兩個：_write_state 成功寫入後清空、reset_cache（測試用）。讀另一個根的檔案時只比對 mtime，相等即回傳上一個根的 data 物件。
另有別名問題：命中時回傳同一個 dict 物件（實測 is 為 True），呼叫端就地修改會污染快取，與跨根錯讀獨立。

### 影響範圍
僅 dispatch_tracker._read_state。解析度問題：st_mtime 是 float64，約 1.7e9 秒量級的精度約 2e-7 秒，所以奈秒差的兩檔也被視為相等，APFS 奈秒解析度不能阻擋碰撞。
觸發條件評估：
- 264.5 之後 get_state_file_path 對 linked worktree 解析到主倉庫，同根的 worktree 與主倉庫指向同一檔，反而不碰撞。
- 需要同一行程解析出兩個不同的實體檔：推回失敗退回傳入的根（stderr 已有降級訊息）、測試、呼叫端傳入不同根。正式 hook 每次是新行程、project_root 由單一來源決定，同行程跨根目前無已知正式路徑。
- 189.1 單一分派程序讓多支 hook 同行程依序執行，快取壽命延長；但各 hook 傳入同一個 project_root，仍是同根。若其中一支 hook 在推回失敗時退回 worktree 路徑而其他支成功，同一行程會讀到兩個不同檔，這是唯一看得到的組合，機率低。
- mtime 碰撞：不同檔 mtime 完全相同在真實運作中罕見，但浮點截斷使有效解析度約 200ns；秒級檔案系統則同一秒內的兩個檔必碰撞。
### 相關 Error Pattern
未查到同型條目；屬於快取鍵缺少身分維度。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論
成立（程式層）：單槽快取鍵不含身分，跨根錯讀已重現，含奈秒差。正式觸發條件窄（推回失敗退回不同根、測試、傳入不同根），優先級維持 P3。

### 方案比較
| 方案 | 內容 | 評估 |
|------|------|------|
| A 鍵改為路徑加 mtime | 單槽，存 (path, mtime_ns) | 修錯讀，但兩根交替讀取時互相踢出，命中率降為零；別名問題未解 |
| B 路徑為鍵的字典 | {解析後路徑: (mtime_ns, data)}，命中回 deepcopy | 修錯讀、保留各根命中、同時解別名。採用 |
| C 移除快取 | 每次重讀 | 最簡單，但回到每次 Edit/Write 重複解析，違背快取設計目的 |
共同要求：mtime 改 st_mtime_ns 比較（float 吞掉奈秒差）；_write_state 只失效該路徑項目；reset_cache 清整個字典。
採用 B。
