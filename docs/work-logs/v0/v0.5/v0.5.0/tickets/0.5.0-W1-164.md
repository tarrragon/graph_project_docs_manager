## Problem Analysis
### 問題根因

機制已實驗證實：持有 index.lock 的 git 行程被 SIGKILL 時不執行清理，留下 0 位元組鎖檔；SIGTERM、SIGINT 則 git 自行刪鎖。Python `subprocess.run(timeout=N)` 逾時時對子行程送 SIGKILL，故任何「持鎖中逾時」的 git 子程序都會留殘骸。高負載（load 50 至 140）使 git add / commit 等持鎖步驟超過 10 秒預設值，觸發面擴大。

具體嫌疑路徑：`git_ops._run_git` 預設 `_GIT_TIMEOUT=10`（多數呼叫走此預設，僅 update-ref 與 update-index 持鎖步驟已改 `timeout=None`）；`worktree-auto-commit-hook.py` 的 `git add -A`、`git commit` 以 `GIT_TIMEOUT=10` 跑 `subprocess.run`（Stop hook，harness 另有 30 秒 hook timeout）。

單一事件的最後觸及者無法定位（見重現實驗結果「定位」）。已驗證的是機制與嫌疑面，未驗證的是兩個現存證物各自由哪個呼叫造成。

### 影響範圍

- 殘骸不會自行消失：`git-index-lock-cleanup-hook.py` 寫死 `<root>/.git/index.lock`；linked worktree 的 `.git` 是檔案，`.git/worktrees/<name>/index.lock` 從未被檢查或清理（已驗證：兩個證物 worktree 的 `.git` 皆為 gitdir 指標檔）。主 repo 同型殘骸會被該 hook 清除（hook-logs 14:54:39 記錄移除了已存在 126 秒的主 repo 鎖，即同一時段另一次殘骸）。
- 後果：該 worktree 下一個 git 寫入失敗，索引過期（MM），worktree 無法非強制移除。

IMP-046（競爭與短暫重試）：不涵蓋本票，本票為無主殘骸。PC-139（外部 GUI 週期性 fork git status）：同為「鎖來源誤判」家族，但其鎖會自行消失。

## 重現實驗結果
### 實驗方法

scratch 暫存 repo（scratchpad/repro/r）。以 clean filter（`sleep 6; cat`）讓 `git add` 持有 index.lock，1.5 秒後對該 git 行程送訊號；另以 Python `subprocess.run(["git","add",...], timeout=2)` 驗證逾時路徑。腳本：scratchpad/repro/run.sh、py.py。不在任何共用 checkout 或既有 worktree 製造鎖檔。

### 實驗執行

定位：兩證物 mtime 對照 hook-logs。16:58:34 的鎖（agent-a12836...）落在同 worktree 7 個 PreToolUse hook 並行執行的窗口（16:58:33-34），所屬 Bash 命令為 grep，8 秒後（16:58:41）完成；窗口內各 hook 的 git 呼叫多已帶 `--no-optional-locks`，worktree 日誌無任何 git 逾時紀錄，無法指認持鎖者。14:52:25 的鎖（agent-a7117...）其 worktree 日誌該時段無條目；主 repo 同時段（14:52:33）另有一次殘骸，緊鄰 SubagentStop 與兩個並行 Agent 派發（14:52:20-30），但無逾時日誌。結論：兩證物無法定位到單一指令；最可能的未被日誌涵蓋的持鎖者為 harness 層（工具呼叫被中止、agent 停止時的子行程）與無逾時日誌的 SIGKILL 路徑。

### 實驗發現

已驗證：SIGKILL 是殘骸的充分條件，且 subprocess.run 逾時恰好送 SIGKILL；worktree 鎖檔不在清理 hook 涵蓋內。未驗證：證物個案的實際持鎖者；git status/diff 的機會性鎖是否為本次來源（依 git 文件為會取鎖，未實測，由 --no-optional-locks 方案降低而非消除）。

### 結論

成因為「持鎖 git 被逾時機制以 SIGKILL 終止」加上「清理 hook 不涵蓋 linked worktree」。兩個證物的個別持鎖者無法定位。

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A 逾時先 SIGTERM | 共用 helper：Popen，逾時 terminate、寬限後才 kill；套用 git_ops._run_git 與 worktree-auto-commit-hook | 直擊已驗證機制，git 自行清鎖；無誤刪活鎖風險 | 無法涵蓋 harness 層殺行程；需改兩處呼叫 |
| B 唯讀呼叫加 --no-optional-locks | 補齊 confabulation-audit(status)、tracking-schema-json-staleness-guard(diff --cached)、worktree-commit-before-dispatch(diff) | 降低取鎖面，改動小 | 非主因，僅縮小窗口；diff --cached 是否取鎖未實測 |
| C 清理 hook 涵蓋 worktree | 以 git rev-parse --git-path index.lock 解析；僅清 0 位元組、鎖齡超閾值、lsof 無持有者，留記錄 | 涵蓋 harness 層等無法預防的殘骸，自癒 | 誤刪活鎖風險，須靠鎖齡與無持有者條件控制；觸發點 PreToolUse(git add/commit) 時才清，晚於殘骸出現 |

建議 A + C 並行（A 預防、C 自癒），B 低優先。
