### 模型問題的結構（120.7.9 分析補充）

甲（命令位置判定加前綴白名單）要求 lib 預先知道「哪些程式會把後面的字串當命令執行」。這個集合沒有上界（xargs、find -exec、parallel、setsid、strace、taskset、su -c 等），每新增一個即是一個 parser-differential。四輪審查每輪新發現，與實測 19 個以上前綴命令一輪全漏，兩者同向。

乙（任意位置掃描）把問題倒過來：只須知道「哪些位置的 git 字樣不是呼叫」，這個集合小且可枚舉（輸出命令 echo、printf，查詢 command -v，引號與 heredoc，註解）。代價是 git 字樣出現在其他命令參數位置時（grep git commit、man git commit）會誤判。

### 實驗方法

原型全放 scratchpad（未改 .claude/）。models.py 以 monkeypatch 替換 lib 的 _invocations_in_statement，三案共用同一套 tokenize、heredoc 剝離、cd 追蹤、shell -c 遞迴；差別只在語句內如何找 git：

- 甲：現行 lib（命令位置判定加前綴白名單）。
- 乙：語句內逐 token 掃描，任何 token 為 git 或以 /git 結尾即進入全域選項消耗與子命令比對；掃描遇 echo、printf 即停（其後參數列例外）；shell -c 與 eval 沿用遞迴。
- 乙加（變體，僅作觀察）：例外再加 grep、rg、man、which、type 等文字檢視命令。
- 丙：阻擋型取乙的結果、提示型取甲的結果，不另有程式。
- 三案一致的簡化：_read_git_alias 固定回 None（不查 git config，避免子程序）；wanted 子命令集為 commit add merge push checkout switch reset rebase cherry-pick stash branch restore rm clean tag pull revert mv am。

### 實驗發現

已驗證：

1. 甲的漏判是開放集合：56 筆正向中 25 筆漏，且我在一輪內隨手加的 19 個以上前綴命令全數漏判；四輪安全審查每輪新發現同源。每個漏判都是「該程式接受命令作為參數」，這類程式沒有上界。
2. 乙的漏判集合是封閉的：只有字串腳本載體（su -c、script -c、sg -c 及 echo 內引號的命令替換），共 4 筆，是已知有限的 -c 家族與例外規則本身，可枚舉。
3. 乙的誤判在真實命令為 0 / 12,821，但在手寫反向壓力輸入上為 24 / 39，兩者差距說明誤判只出現在「git 與子命令字樣原樣出現在其他命令參數」的少見寫法。
4. 註解行吞語句是獨立缺陷，三案皆漏，與模型選擇無關。
5. 靜態不可決（變數、命令替換組出的 git）8 / 8 三案皆漏，任何文字辨識模型都無法處理。

未驗證：

1. 真實語料來自合作中的 PM 與代理人 session，包含的是「無意」寫法；刻意規避不在母體內，也不是守衛的定位。
2. 乙在非本專案語料（其他 consumer 專案）的誤判率未測。
3. 逐字稿語料是 tool_use 全量，包含被其他 hook 擋下而未實際執行者；對辨識模型的比較無影響。
