# Execution Log

## Task Summary

5w1h-compliance-check-hook（TodoWrite PreToolUse）以舊式 top-level decision:block 輸出並回 exit 1（非阻擋碼），輸出失敗亦落入 except 回 allow；不經 permissionDecision，block 語意是否生效未驗證

---

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

該守衛有兩層獨立失效，皆使阻擋永不生效：
1. 輸入層：make_decision 以 `"content" in tool_input` 判斷是否檢查，但 TodoWrite 真實 payload 為 `tool_input.todos[]`（content 在各項內），頂層無 content，恆走「結構無須 5W1H 檢查」allow。
2. 輸出層：命中 block 時印舊式頂層 `{"decision":"block"}` 並回 exit 1。官方 hooks 文件：PreToolUse 頂層 decision/reason 已棄用（"block" 對映 deny），但僅 exit 0 解析 stdout JSON；exit 1 屬非阻擋錯誤、動作照常執行。
結論：依官方規格，舊式輸出搭配 exit 1 在現行 Claude Code 不阻擋（規格推論，runtime 未實測）；且輸入層使其對真實輸入根本走不到 block 分支。

### 影響範圍

- 已驗證（實跑）：.claude/hooks/5w1h-compliance-check-hook.py 對真實形狀 payload 輸出 allow rc=0；對頂層 content 形狀輸出 block rc=1。
- 已驗證（讀碼）：settings.json PreToolUse matcher TodoWrite 已註冊；tests/test_5w1h_compliance_hook.py 僅呼叫 make_decision 且餵頂層 content 形狀，不覆蓋 main 與真實形狀，故全綠無鑑別力。
- 未驗證：runtime 實際是否阻擋（無法在不影響主 session 下觀測，依官方規格推論）。
- consumer：所有同步此 hook 的專案皆受影響；守衛從未保護過 5W1H 格式。

### 相關 Error Pattern

無直接對應編號。同型機制見 canonical issue #35（payload 欄位讀取正確性從未被驗證）與 #97（前提不成立與正常執行同形、fail-open 無訊號）；測試端對應 test-assertion-design-rules E2（守衛測試須含正向對照輸入）。已於 #35 附觀測。

## 重現實驗結果

### 實驗方法

以 python3 json.dumps 產生兩個違規 payload（Who: bad），經 `uv run --quiet .claude/hooks/5w1h-compliance-check-hook.py < payload` 執行，記錄 stdout 與 rc（E2 正向對照）。

### 實驗執行

- payload a（頂層 content，非真實形狀）：rc=1，stdout `{"decision":"block","reason":"Who 欄位格式錯誤：缺少執行者/分派者標記",...}`，stderr 空。
- payload b（真實形狀 todos[]）：rc=0，stdout `{"decision":"allow","reason":"工具 TodoWrite 結構無須 5W1H 檢查"}`。
- 官方文件（https://code.claude.com/docs/en/hooks.md ，PreToolUse decision control Note）：頂層 decision/reason 對 PreToolUse 已棄用，"approve"/"block" 對映 allow/deny；Exit code 節：exit 0 才解析 JSON，其他非 2 碼為非阻擋錯誤。框架內 `.claude/references/hook-architect-technical-reference.md`「deny 輸出失敗語意」一致。

### 實驗發現

已驗證：真實輸入永遠 allow；舊式輸出+exit 1 依規格非阻擋。未驗證：runtime 實機行為（依規格推論）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 結論

阻擋未生效，且為雙層失效（輸入層讀錯欄位 + 輸出層舊式 block 搭配 exit 1）。必須兩層都修。

### 候選方案（輸出層）

| 方案 | 內容 | 對既有測試 | 對 consumer | 利弊 |
|------|------|-----------|------------|------|
| A（建議） | emit_hook_output 輸出 permissionDecision deny + reason，exit 0 | make_decision 回傳形狀可保留（main 內轉換），既有測試不動；新增經 main 的 E2 | 阻擋原因以 permissionDecisionReason 顯示，格式與其他守衛一致；deny 輸出失敗由 emit_hook_output 兜底為 exit 2 | 與框架慣例一致、有兜底；需改 main |
| B | 維持印 JSON，block 時 exit 2 + stderr 寫原因 | 同上 | stderr 成為回饋給 Claude 的訊息，stdout JSON 被忽略；顯示格式與他守衛不同 | 改動最小；但 stderr 慣例被 IMP-048 視為 hook error 顯示，語意混用 |

輸入層（兩案共通）：改為遍歷 `tool_input.todos[]` 逐項檢查 content。

### 框架 issue 判準

(1) 抽象可攜：是（守衛讀錯 payload 欄位 + 非阻擋碼）；(2) 根源在 .claude/ 通用資產：是（hook 本體）。dedup 結果：#35（payload 欄位讀取）為主、#97（fail-open 無訊號）為次，關係判定為「引用」，非重複非切分。已 observe：https://github.com/tarrragon/claude/issues/35#issuecomment-6028188167

### Spawn 規劃

| 項目 | 落地 |
|------|------|
| 修復 hook（方案 A + 讀 todos[]）與 E2 測試 | 已建 0.5.0-W1-077.1（--parent） |
| 其他守衛是否同讀錯欄位 | 無需建 ticket：由 canonical #35 承接全體 hook 欄位盤點，本專案不另開 |
