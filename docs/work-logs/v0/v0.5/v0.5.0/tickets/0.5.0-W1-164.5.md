### 結論

1. hook timeout 單位為秒，兩個 hook 的 30 即 30 秒，上限在設定層面有效；#112 的毫秒誤寫不適用本專案這兩個 hook。
2. harness 逾時終止 hook 時先送 SIGTERM（6/6 輪），hook 不退出則後續被強制終止；6/6 輪持鎖的 git 子程序（add 型 4、diff 型 1、ignore 型 1）終止後皆無殘留鎖、無殘留行程。即「harness 逾時終止 hook」這條路徑在本實驗條件下不產生 0 位元組 index.lock。
3. 因此 afc6bc356／ae035706 兩個殘留鎖不能歸因於 harness 逾時終止路徑；本實驗未重現它們。仍開放的成因：SIGKILL 直接殺持鎖 git（含 hook 內 git 逾時被 SIGKILL，164.1 已處理寫入類）、唯讀呼叫點（zombie-cleanup 的 git status 逾時 10 秒 SIGKILL，未帶 --no-optional-locks）、worktree 內載入舊版 hook。
4. 與 0.5.0-W1-164.1：164.1 的 SIGTERM 再 SIGKILL 修法與 harness 本身的行為同向（先 TERM 讓 git 自行清鎖），本實驗支持該設計的前提；未驗證 164.1 的 SIGKILL 升級延遲是否足夠 git 清鎖。
