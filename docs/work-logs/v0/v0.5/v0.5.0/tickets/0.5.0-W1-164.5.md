### 新觀測（PM 88，2026-10-13 16:40 實測）：164.1 修正進 main 之後仍出現殘留鎖檔

.git/worktrees/ 下另有兩個 0 位元組 index.lock，無行程持有（pgrep 無結果），不在 0.5.0-W1-164〈現存證物〉清單內：

| 鎖檔 | mtime | 與 164.1 進 main（2026-10-13 12:10，579f47a20）的先後 | 同 worktree 最後一次 index 寫入 |
|------|-------|------|------|
| worktrees/agent-afc6bc356ffbc008e/index.lock | 2026-10-13 09:25 | 之前 | 未查 |
| worktrees/agent-ae035706bda99ac5b/index.lock | 2026-10-13 15:00 | 之後 | index 與 COMMIT_EDITMSG 皆為 12:00，reflog 於 12:00 後無任何項目 |

ae035706 一例的含意：鎖出現時該 worktree 沒有任何提交、合併或 add 留下痕跡（index 檔 mtime 未變、reflog 無新項），故持鎖者不是寫入類 git 指令，較可能是唯讀指令的機會性取鎖（git status／diff 重新整理 stat cache）在取鎖後被終止。164.1 只處理寫入子程序的逾時路徑，不涵蓋這條。該 worktree 的分支基準含 164.1（merge-base 之後），所以這不是「修正尚未到達該 worktree」的情形；但 hook 實際從哪個 checkout 載入未查。

此觀測符合 0.5.0-W1-164 Solution 所述「164.1 完成後若殘留鎖檔仍出現，即為仍有未涵蓋終止路徑的證據」。歸入本票（harness 終止 hook 時 git 子程序的鎖）與 0.5.0-W1-164.3（唯讀呼叫補 --no-optional-locks）的共同輸入，不另開票。兩個鎖檔目前未動；ae035706 屬進行中的 0.5.0-W1-114.21，該票合併後 worktree 的去留由用戶裁決。
