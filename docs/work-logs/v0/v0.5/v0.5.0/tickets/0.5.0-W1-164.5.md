## 重現實驗結果
### A 段：hook timeout 註冊值與平台單位（2026-10-13，未啟動任何 harness）

已驗證：
- .claude/settings.json 的 Stop 區：worktree-auto-commit-hook.py 與 ticket-md-auto-commit-hook.py 兩個 hook 皆為 "timeout": 30。同區的 stop-worklog-handoff-sync-check-hook.py 未設 timeout。
- 單位為秒。出處：本機 claude 2.1.296 binary（/Users/mac-eric/.local/share/claude/versions/2.1.296）內嵌的 hook schema 文字 "Timeout in seconds for this specific command/request/tool call"，且執行碼對 command 以外各 hook 型別皆為 timeout*1000 換算為毫秒（例：e.timeout?e.timeout*1000:default）。專案 .claude/references/hook-architect-technical-reference.md 亦記「timeout：handler timeout 秒數」。
- 因此 30 即 30 秒，未發生毫秒誤寫；本專案 settings.json 無任何四位數以上的 timeout 值（grep 計數 0）。canonical #112 所述「毫秒寫入」情形不適用於這兩個 hook。上限在設定層面有效。

未查明：
- command 型 hook 未設 timeout 時的預設值：binary 內 command 型分支的預設常數未能由 strings 定位（agent 型預設 60、prompt 型預設 30 已見；600000 ms 常數出現多處，無法歸屬到 command hook，不採信）。
- 「上限實際生效」僅證明設定值被讀為 30 秒，逾時當下的訊號與子程序處置留待 B 段實測。

### B 段：實驗（2026-10-13 18:47-18:49，claude 2.1.296，macOS）

方法：scratchpad 拋棄式 repo（分支 scratch）加自帶 .claude/settings.json，UserPromptSubmit 掛 hook.sh，timeout 3。hook 內 trap TERM/INT/HUP/QUIT/PIPE 並寫日誌，啟動持鎖 git 子程序後 sleep 40 秒。以 claude -p hi --model haiku --strict-mcp-config（空 MCP）--disable-slash-commands 非互動啟動，一次一個行程，每輪確認已退出再下一輪。持鎖命令：add 型 = git add 搭配 clean filter（filter 內 sleep 40，git add 先取 index.lock 再跑 filter，故鎖被長時間持有）；diff 型 = 觸碰檔案後 git diff --stat（refresh 後回寫 index）；ignore 型 = hook 自身 trap TERM 且不離開。

取樣 N=6（add 4、diff 1、ignore 1；另有首輪 add 為預備輪未計入前列則 N=7，下表列全部 6 輪日誌完整者加首輪共 6 筆有效 + 1 筆首輪）。各輪 load 1 分鐘 18.9-27.7，swap free 795-940M，皆未觸及停止條件。

| 輪 | 模式 | hook 收到 TERM 距 hook 啟動 | hook 收到其他訊號 | 逾時後 hook 與 git 子程序 | index.lock |
|----|------|------|------|------|------|
| 1 | add | 2.07s | 僅 TERM | 皆已不存在 | 無 |
| 2 | add | 2.94s | 僅 TERM | 皆已不存在 | 無 |
| 3 | add | 3.06s | 僅 TERM | 皆已不存在 | 無 |
| 4 | add | 4.26s | 僅 TERM | 皆已不存在 | 無 |
| 5 | diff | 3.18s | 僅 TERM | 皆已不存在 | 無 |
| 6 | ignore | 4.19s | 僅 TERM（被忽略） | 皆已不存在 | 無 |

（N=6，原先把首輪算兩次的敘述作廢，以此表為準。）

已驗證：
- timeout 3 的設定被讀為 3 秒（TERM 於 2.07-4.26 s 內到達，hook 啟動時間點本身有 bash 啟動與日誌延遲，未精確到亞秒）。單位為秒再獲實證。
- harness 逾時先送 SIGTERM；6/6 輪 hook 僅記錄到 TERM，未見 INT／HUP／QUIT。
- ignore 輪：hook 忽略 TERM 且不退出，輪末檢查時 hook 與 git 子程序皆已消失、日誌無 finished full loop，表示 TERM 之後仍有後續強制終止（推定為 SIGKILL 升級）。升級延遲與確切訊號未量到（本實驗只在輪末檢查）。
- 6/6 輪輪末無任何殘留行程（以 exp164 路徑、sleep 40、filter 字樣比對皆 0），6/6 輪 index.lock 不存在。
- 持鎖 git 子程序在 add 型四輪皆於持鎖狀態被終止，鎖皆被清除：git 自身的 signal 清理路徑（收到 TERM 時刪鎖）有生效，或終止涵蓋整個程序群組。

未驗證：
- 子程序是否由 harness 直接對群組送訊號，抑或僅隨父程序消失而收到 SIGHUP／TERM：probe 子程序的 trap 日誌因引號錯誤未寫出，無從區分。
- 真正的 SIGKILL 路徑下持鎖 git 是否留鎖：本實驗中 git 全數被溫和終止；未製造 hook 與 git 皆忽略 TERM 的情形（git 自己會重設 TERM 處理，ignore 輪的 git 仍乾淨消失）。以 SIGKILL 直接殺持鎖 git 必留 0 位元組鎖是已知的 git 行為，但本實驗未直接量測。
- diff 型只取樣 1 輪，且 git diff 的 index 回寫窗口極短，終止恰落在窗口內的機率低，1 輪不足以說明唯讀指令的鎖殘留機率。
- 未測 uv run 包一層的真實啟動鏈（hook 經 uv 再啟動 python 再啟動 git 時 TERM 是否逐層傳遞）；未測 Linux。
- 重現不了 ae035706／afc6bc356 的殘留鎖。
