## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`ticket track commit` 依票面 `where.files` 做範圍檢查，超出範圍就拒絕提交，這個守衛的行為正確。缺口在上游：某張票改名或搬移檔案並合併之後，其他還沒結案的票若仍在 `where.files` 寫舊路徑，沒有任何工具提醒，要等代理人提交時撞上範圍拒絕才會發現。

**同日三例**（研究線回報，2026-10-21）：

| 票 | 成因 | 可攜性 |
|---|---|---|
| 0.5.0-W1-464 | ANA 預設唯讀，where.files 沒宣告研究產出的寫入路徑 | 屬於建票者疏漏，不在本項範圍 |
| 0.5.0-W1-466.2 | 檔案改名後，舊路徑的刪除不在宣告範圍內 | 屬於本票自己的改名，不在本項範圍 |
| 0.5.0-W1-466.2.1 | 建票時寫的是改名前的路徑；改名合併後，沒有人回頭更新這張還沒派發的票 | **本項處理的形態** |

每一例都要多一輪往返：代理人停手 → PM 執行 set-where → 重新派發。

### 兩條判準（escalation-flow.md）

1. **抽象可攜**：換掉專案名稱後仍成立：「檔案改名合併之後，其他開啟中的票的範圍宣告仍指向舊路徑，直到派發後才被範圍守衛發現」。任何會改名或搬移檔案的 consumer 都適用。成立。
2. **根源在 `.claude/` 通用資產**：範圍宣告與範圍檢查都在 ticket skill，合併流程在 worktree skill，沒有專案設定參與。成立。

### 處置

- 不是 P0／P1：守衛擋得正確，沒有錯誤寫入，成本只是多一輪往返。依框架修補節奏觀測進 issue 後關閉。
- 查重：dedup 關鍵字為 where.files 改名、where.files 過期、rename where.files、範圍拒絕。#96〈文字規範的存量對帳缺口〉有一項「引用指向已不存在的物件」，範圍是文件內文裡的引用；本項是同一個軸上的新載體（開啟中的票的 where.files）與新觸發點（改名合併）。關係判定為「引用」，observe 到 #96。
- 修法方向：合併含 rename 或 delete 的分支時，掃描開啟中的票的 where.files，列出指向舊路徑的票，讓 PM 在派發前更新。這是 opinionated-default 原則說的「靠人記得」訊號。
