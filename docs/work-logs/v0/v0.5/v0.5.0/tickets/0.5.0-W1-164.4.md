## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

hook 的觸發判定函式 is_git_write_command 為命令字串子字串比對：`"git commit" in command or "git add" in command`。兩個直接後果：
1. 全域選項插在 git 與子命令之間（`git -C <path> add`、`git -c k=v commit`、`git --no-pager commit`）時，連續字串 `git add` 不存在，不觸發。
2. `ticket track commit` 的字串為 `track commit`，不含 `git commit`，不觸發。
另有別名 `git stage`、以及 add／commit 以外的取鎖命令（merge、rebase、stash、checkout、reset、restore、rm、mv、cherry-pick、update-index）全數不在判定內。反向亦有誤觸：`echo git commit` 命中（誤清方向無害，因刪除條件獨立把關）。

第二層缺口：即使觸發，目標目錄只取 payload 的 cwd。`git -C <其他 checkout> add` 的實際目標不是 cwd，鎖在別處。

### 對照表（git 2.50.1，scratch repo 實測；lock 欄=預置 0 位元組 index.lock 時命令是否失敗；回寫欄=無鎖時命令前後 .git/index 雜湊是否改變）

| # | 命令形式 | 取鎖行為（實測） | 現行觸發 | 分類 |
|---|---|---|---|---|
| 1 | git add f | lock 存在則失敗 rc=128；回寫 | 觸發 | 寫入 |
| 2 | git commit -m / -a | 失敗 rc=128；回寫 | 觸發 | 寫入 |
| 3 | git add f && git commit | 同上 | 觸發 | 寫入 |
| 4 | git -C /abs add／commit | 同 1、2 | 不觸發 | 寫入 |
| 5 | git -c k=v commit、git --no-pager commit | 同 2 | 不觸發 | 寫入 |
| 6 | git stage f（add 別名） | 同 1 | 不觸發 | 寫入 |
| 7 | /usr/bin/git add、command git commit、bash -c 'git add' | 同 1、2 | 觸發（子字串仍在） | 寫入 |
| 8 | git merge | 失敗 rc=128（-q 時無訊息）；回寫 | 不觸發 | 寫入 |
| 9 | git rebase、git cherry-pick | 失敗；回寫 | 不觸發 | 寫入 |
| 10 | git stash | 失敗（could not write index）；回寫 | 不觸發 | 寫入 |
| 11 | git checkout（切分支與 -- path）、git reset | 失敗 rc=128；回寫 | 不觸發 | 寫入 |
| 12 | git restore --staged | 失敗 rc=128；僅在有 staged 項時回寫 | 不觸發 | 寫入 |
| 13 | git rm、git mv | 失敗 rc=128；回寫 | 不觸發 | 寫入 |
| 14 | git update-index --refresh | 失敗 rc=128；回寫 | 不觸發 | 寫入 |
| 15 | ticket track commit | CLI 內部：read-tree／add／write-tree 走 GIT_INDEX_FILE 臨時 index（不取共用鎖）；update-ref 取 HEAD.lock／分支 ref 鎖；收尾 _sync_shared_index_after_commit 以 ls-files 讀、update-index --index-info 寫共用 index（取 index.lock，毫秒級，timeout=None） | 不觸發 | 寫入（僅收尾同步） |
| 16 | git status（無旗標） | lock 存在時靜默略過（rc=0）；直接探測兩次皆回寫 index | 不觸發 | 唯讀回寫 |
| 17 | git --no-optional-locks status | 不回寫 | 不觸發 | 唯讀 |
| 18 | git diff（工作樹側，無設定） | 靜默略過；stat-dirty 時回寫 | 不觸發 | 唯讀回寫 |
| 19 | git -c diff.autoRefreshIndex=false diff | 不回寫 | 不觸發 | 唯讀 |
| 20 | git diff --cached、git log、git rev-parse | 不回寫、不取鎖 | 不觸發 | 唯讀 |

解讀：唯讀回寫類（16、18）在 lock 存在時是靜默略過而非失敗，所以殘留鎖「傷害」的是寫入類（1 至 15），不是唯讀類；但唯讀回寫類「可能製造」鎖，是否為殘留成因未識別。

ticket track commit 的後果（15）：舊鎖存在時 commit 本身成功（update-ref 不需 index.lock），只有收尾同步失敗並走 _warn_sync_failed 警告，共用 index 該路徑停留在舊 HEAD 版本，即 bash-tool-usage-rules 規則七〈過期 index 快照〉的來源。hook 不觸發代表：舊鎖不被清、同步失敗、過期 entry 留給下一個裸 commit。

### 影響範圍

- 已驗證（scratch，hook 以 settings 註冊的 uv run 方式、payload cwd 為 linked worktree、worktree 鎖預置 60 秒齡 0 位元組）：`git add f1` 鎖被清；`git -C <abs> add f1`、`git -C <abs> commit`、`ticket track commit ...`、`git stage f1` 皆未清。
- 受影響情境：PM／代理人使用規則一首選的 `git -C` 與規則七預設的 `ticket track commit`；兩者恰是框架推薦寫法，故自癒目標在代理人情境的實際觸發率低。
- 未驗證：殘留鎖的實際成因（164.6 的 42 次終止留鎖 0 次），故無法斷言「補齊觸發」能讓殘留消失；本票只處理清理端的涵蓋，不假設持鎖者類型。
