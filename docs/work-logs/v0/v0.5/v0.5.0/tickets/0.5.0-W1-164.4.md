## Task Summary

分析 git-index-lock-cleanup-hook 的觸發判定不涵蓋 git -C 與 ticket track commit，框架推薦的兩種提交寫法皆不啟動清理

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

hook 的觸發判定函式 is_git_write_command 為命令字串子字串比對：`"git commit" in command or "git add" in command`。兩個直接後果：
1. 全域選項插在 git 與子命令之間（`git -C <path> add`、`git -c k=v commit`、`git --no-pager commit`）時，連續字串 `git add` 不存在，不觸發。
2. `ticket track commit` 的字串為 `track commit`，不含 `git commit`，不觸發。
另有別名 `git stage`、以及 add／commit 以外的取鎖命令（merge、rebase、stash、checkout、reset、restore、rm、mv、cherry-pick、update-index）全數不在判定內。反向亦有誤觸：`echo git commit` 命中（誤清方向無害，因刪除條件獨立把關）。

第二層缺口：即使觸發，目標目錄只取 payload 的 cwd。`git -C <其他 checkout> add` 的實際目標不是 cwd，鎖在別處。

解讀：唯讀回寫類（16、18）在 lock 存在時是靜默略過而非失敗，所以殘留鎖「傷害」的是寫入類（1 至 15），不是唯讀類；但唯讀回寫類「可能製造」鎖，是否為殘留成因未識別。

ticket track commit 的後果（15）：舊鎖存在時 commit 本身成功（update-ref 不需 index.lock），只有收尾同步失敗並走 _warn_sync_failed 警告，共用 index 該路徑停留在舊 HEAD 版本，即 bash-tool-usage-rules 規則七〈過期 index 快照〉的來源。hook 不觸發代表：舊鎖不被清、同步失敗、過期 entry 留給下一個裸 commit。

### 實驗發現

已驗證：
1. 觸發缺口如上，兩種框架推薦寫法皆不啟動清理；缺口不止兩種，另含 `git -c`、`git --no-pager`、`stage` 別名及 merge／rebase／stash／checkout／reset／restore／rm／mv／cherry-pick／update-index。
2. 預置鎖時，上述寫入類命令在批次測試中均失敗（rc=128 或 1）；merge 在 -q 下無訊息，rebase 與 stash 在我的腳本因前置步驟的訊息格式未被 grep 辨識為 BLOCKED，但 rc 非 0。
3. status 無旗標與工作樹側 diff 於 stat-dirty 時會回寫 index（status：probe.sh 直接探測兩次皆回寫，`--no-optional-locks` 後不回寫；diff：批次測試回寫，`-c diff.autoRefreshIndex=false` 後不回寫）。這與 164.6 的〈盤點分類更正〉一致。
4. 鎖路徑解析不需 git 子程序：純檔案系統上溯在兩種 checkout 都低於取樣解析度；rev-parse 子程序中位數 14 至 26 毫秒。命中路徑相對不命中路徑中位數多約 140 毫秒（389 對 250），其中含 rev-parse 與命中後的其餘處理，兩者差距未逐段拆分。
5. 現行不命中路徑本身就是每次 Bash 呼叫的固定成本（uv run 中位數 250 毫秒、最大 464）；任何方案若把「每次呼叫」的新增成本控制在毫秒內，相對此固定成本可忽略。

未驗證：
1. 批次測試中 `git status` 於 locktest.sh 顯示 index 未改寫，與 probe.sh 的直接探測（改寫）不一致；原因未查（推測與兩個腳本還原狀態的方式或 racy-git 判定有關，屬推論）。取用 status 回寫事實以 probe.sh 與 164.6 的 PM 獨立重現為準。
2. `git restore --staged n1` 批次測試中前後 index 雜湊相同，與「取鎖寫入類」的預期不符，原因未查；它在 lock 存在時確實失敗，故仍列寫入類，但「回寫」欄對它不下結論。
3. 殘留鎖的成因：本票未重現任何殘留；不假設持鎖者類型。
4. 高負載下 ticket track commit 實際 update-index 窗口長度：僅有程式碼註解「毫秒級」，未量測。
5. 純檔案系統上溯在 NFS 或權限受限路徑下的行為：未測。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

現行判定把「是否有鎖要清」綁在命令文字上，而刪除條件（0 位元組、鎖齡逾 5 秒、無行程持有、刪前複核）本身已與命令無關：滿足這四項的鎖，不論由哪條命令引起都是安全可清的。因此觸發判定的精確度只影響「何時有機會清」，不影響「清的安全性」，漏清與誤觸的代價不對稱：誤觸只多一次便宜的檢查，漏清則是 164 系列要解的問題。缺口有兩層：(1) 子命令比對漏掉全域選項、別名、其他取鎖命令與 ticket track commit；(2) 目標目錄只取 cwd，`git -C <他處>` 與 `ticket track commit --worktree <path>` 的鎖不在 cwd 的 checkout。

殘留鎖成因未識別（164.6 重現為 0 次），所以方案比較不假設持鎖者類型；所有方案的刪除條件維持不變。

### 方案比較（每次呼叫新增延遲以上方實測為依據，高負載 load 11 至 36 下取樣）

| 方案 | 內容 | 漏清方向 | 誤清方向 | 每次 Bash 呼叫新增延遲 |
|---|---|---|---|---|
