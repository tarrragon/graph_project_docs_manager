## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### Context Bundle（PM 於派發前整理，2026-10-14）

**現況實測（主 checkout，21:30）**

- `.claude/hook-logs/test-monitor/` 內有 75 個鍵檔殘留，時間從 15:33 到 21:25，內容都是 status running。
- 舊單檔 `.claude/hook-logs/test-monitor.json` 目前是 status running，start_timestamp 是很久以前的值。所以票面原本的「只採用 running」擋不住它，第 1 條驗收已改寫（見 acceptance[1]）。

**讀寫路徑**

- 鍵規則只定義在 `.claude/lib/test_monitor_path.py` 的 monitor_key：依序取 tool_use_id、session_id，兩者都沒有才回 None，改走舊單檔。
- pre（`.claude/hooks/test-timeout-pre.py`）：有鍵寫鍵檔，無鍵寫舊單檔。
- post（`.claude/hooks/post-test-hook.py` 的 check_test_timeout）：有鍵且鍵檔存在就讀鍵檔，否則退回舊單檔。收尾時鍵檔 unlink，舊單檔寫回 completed，兩者都追加到 test-duration-history.jsonl。
- 同一個 tool call 的 Pre 與 Post 輸入帶相同的 tool_use_id，所以 post 有鍵時，pre 一定是寫鍵檔。post 有鍵卻找不到鍵檔時，退回舊單檔一律是錯的。

**殘留成因（供參考，修法不必逐一對應）**

1. 281.2（20:54 合併）之前，測試失敗的命令只觸發 PostToolUseFailure，post-test-hook 不處理，所以鍵檔不會被刪。281.2 之後已註冊於 PostToolUseFailure:Bash 群組，這個成因應已消失。
2. 命令被中斷，或 post 沒有觸發。
3. 命令內含 cd：21:25 那筆的 command 以 `cd <他處>/.claude/hooks && ...` 開頭。post 觸發時 cwd 可能已改變，get_project_root 解析出不同的根，就找不到 pre 寫的鍵檔。這一點未驗證，代理人可以順手確認，但不必修，清理機制已經涵蓋。

**修法要點**

- post：有鍵時只讀鍵檔，鍵檔不存在就跳過計時（寫 debug 日誌），不退回舊單檔；無鍵時才讀舊單檔，且只採用 status 為 running 的內容。
- 清理：PM 傾向在 pre 寫入鍵檔時，順手刪除 test-monitor/ 內 mtime 超過門檻的舊鍵檔，門檻取 post-test-hook 現有的最高逾時閾值以上（例如 LIMIT 閾值的 2 倍），常數放在 test_monitor_path.py。理由是 pre 每次測試都會觸發，不依賴 SessionEnd 是否送達，也涵蓋上述三種成因。若改用 SessionEnd，要寫明理由。
- 刪除失敗時採 fail-open，寫日誌，不影響 pre 的主流程。
- 不刪舊單檔本身（無鍵的路徑仍會用到）。

**測試**

- 現有測試：`.claude/hooks/tests/test_post_test_hook.py`；另有 281.2 新增的 `tests/test_post_test_hook_failure_event.py`，不要破壞它。
- 用暫存專案根隔離（monkeypatch get_project_root 或 CLAUDE_PROJECT_DIR 加 HOOK_TEST_ISOLATION），不碰真實 hook-logs。
- 清理測試用 os.utime 設定 mtime，不要真的 sleep，也不要用 DateTime.now 比較（test-assertion-design D3）。
- E2：清理測試要包含「門檻內的新鍵檔不被刪」的對照。
- 入口：uv run --directory .claude/hooks pytest tests/test_post_test_hook.py（以及 test-timeout-pre 的測試檔，若存在）。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
- post（post-test-hook.py check_test_timeout）：有鍵時只讀鍵檔，鍵檔不存在即跳過（debug 日誌），不退回舊單檔；無鍵才讀舊單檔且只採用 status=running。
- 清理：pre 有鍵寫入時呼叫 lib/test_monitor_path.py 的 prune_stale_keyed_files，刪 test-monitor/ 內 mtime 超過 STALE_KEYFILE_SECONDS(3600=LIMIT 1800 的 2 倍) 的鍵檔；fail-open 只寫 info 日誌；不刪舊單檔；無鍵 pre 不清理。
- 選 pre 時機的理由：每次測試必觸發，不依賴 SessionEnd 送達，涵蓋中斷與 post 未觸發。門檻取最高逾時閾值 2 倍，確保仍在執行的命令不被誤刪。
- 殘留成因 3（cd）：僅讀碼，未實測驗證。get_project_root 以 cwd／worktree 偵測優先，cd 後 post 解析出不同根理論上可能；清理機制已涵蓋。

### 自檢結果
- diff 僅涉 5 檔；常數與鍵規則只在 lib/test_monitor_path.py；Python 3.9 相容（Optional）；清理失敗 fail-open；未改 test_post_test_hook_failure_event.py。
- 既有 fixture 調整：legacy 單檔補 status=running（新規則要求），並改寫原「鍵檔不存在退回舊單檔」的斷言為新行為。
