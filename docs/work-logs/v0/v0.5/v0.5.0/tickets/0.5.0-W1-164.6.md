## Task Summary

盤點 hook 內帶逾時的 git 呼叫點（唯讀未帶 --no-optional-locks、逾時即 SIGKILL、逾時不寫日誌）

## Problem Analysis
### 問題根因

0.5.0-W1-164 系列只盤點了 ticket_system 的 git_ops 與 worktree-auto-commit（164.1）以及三個唯讀呼叫檔（164.3）。本票以 AST 掃描主 checkout 的 .claude/hooks、.claude/skills/*/hooks 與其共用函式庫 .claude/lib（hook_io.py、git_utils.py），逐一確認 git 呼叫點（不以 status／diff 字面代判，字面命中多為字串常數或 frontmatter 的 status 欄位）。結論：帶 timeout 的 git 呼叫點共 101 列（42 檔），其中 subprocess 直接點 48（含 4 個 helper 實作）、經 helper 的呼叫點 53。所有 subprocess.run(timeout) 逾時均為 SIGKILL（Python 標準行為）；唯一例外是 worktree-auto-commit 的 _run_with_graceful_timeout（164.1 已改）。

結構性事實：
1. 共用 helper .claude/lib/git_utils.run_git_command 已固定帶 --no-optional-locks（34 個呼叫點因此免於唯讀取鎖缺口），但逾時只回傳字串，是否寫日誌取決於呼叫端。
2. 共用 helper .claude/lib/hook_io.run_git 不帶 --no-optional-locks（呼叫端自帶者 2 處：changelog-update、post-git-commit 的 log），逾時寫 warning 但僅在呼叫端傳入 logger 時；prompt-submit 傳 logger，其餘 hook 的 run_git 呼叫端是否傳入未逐一核對。
3. 會取 optional index lock 的子命令是 status 與工作樹側 diff（git 文件對 --no-optional-locks 的描述與用途）；log／rev-list／rev-parse／show／branch／worktree list／diff 兩 ref 之間／diff --cached 判為低風險，此分類為依 git 文件的推論，本票未逐指令實測。

## 重現實驗結果
### 實驗方法

目標：驗證 worktree-zombie-cleanup 的逾時路徑（git status 被 SIGKILL）是否留下 0 位元組 index.lock。環境：scratchpad 內拋棄式 repo（40000 檔、200 目錄），每輪先把所有檔案 mtime 設為未來值使 stat cache 全失效，量測完整 status 耗時 dur，再重置後在 dur 的 40% 處終止。未動任何 worktree、分支或專案 index.lock。量測環境：本機，load average 約 18 至 33。

### 實驗執行

| 組別 | 終止訊號 | 命令 | 終止時點 | N | 實際被終止 | 留鎖 |
|---|---|---|---|---|---|---|
| A | SIGKILL | git status --porcelain | dur 的 40% | 10 | 10 | 0 |
| B | SIGKILL | git --no-optional-locks status --porcelain | dur 的 40% | 10 | 10 | 0 |
| C | SIGTERM | git status --porcelain | dur 的 40% | 10 | 10 | 0 |
| A2 | SIGKILL | git status --porcelain | dur 的 85% 至 100% 隨機 | 15 | 12 | 0 |

### 實驗發現

已驗證：上述條件下 status 被終止 42 次，留鎖 0 次，包含 A 組。完整 status 單次耗時約 5 至 34 秒（stat 全失效加上機器負載）。
未驗證：正向對照（SIGKILL 留鎖）未建立，因此「讀取路徑不留鎖」不能由本實驗推出；較合理的解讀是鎖的持有窗口只在 stat 重新整理後寫出 index 的短暫區間，隨機時點的終止難以命中，這是推論，未以 trace 驗證。結論：無法重現，也無法排除；已建 0.5.0-W1-164.6.3 承接正向對照。取樣 N 為 10／10／10／15，分佈如上表，皆為單一結果（0 留鎖）。

### 盤點分類更正（PM 89，2026-10-13，來自 164.3／164.6.1 的合併審查，PM 獨立重現）

量測環境：git 2.50.1（Apple Git-155），scratchpad 內拋棄式 repo；對一個已追蹤檔 touch 使其 stat-dirty，比對命令前後 .git/index 的雜湊值。審查代理人與 PM 各測一次，結果逐項相同。

| 命令 | index 是否被改寫 |
|------|-----------------|
| git status --porcelain | 是 |

| git diff --name-only | 是 |
| git --no-optional-locks diff --name-only | 是 |

### 「誰送出 SIGKILL」：e1 線索的查證結果（10-14 09:56，PM）

線索（e1 的推論）：兩個實例都早於 164.1 生效，當時 ticket CLI 的 _run_git 與 worktree-auto-commit 的 git add／commit 走 subprocess.run 的 10 秒逾時（逾時即 SIGKILL），且負載長期在 70 以上。

查證：以鎖的時間（10-13 09:25 前後）比對主倉 `.claude/hook-logs` 10-13 的日誌。
- worktree-auto-commit：全日 234 次執行，234 次皆為「非 worktree 環境，跳過」；09:16～09:28 之間四筆，無逾時紀錄。
- ticket-md-auto-commit：同時段四筆皆「無未提交的 ticket md，跳過」。
- ticket-commit-retry：全日 22 筆皆為 cas_rejected，最早 10:35，無逾時。
- git-index-lock-cleanup：四筆警告都針對主倉的 index.lock（03:31、14:47、18:09、20:47），不是 worktree 的鎖。

結論：**無法證實也無法否定**。原因不在線索本身，而在證據位置——hook 日誌目錄由 worktree-aware 的 get_project_root 決定，worktree 內執行的 hook 把日誌寫在該 worktree 自己的 `.claude/hook-logs`（被 gitignore），worktree 清除時一併消失。主倉日誌因此不含 worktree 內的任何執行紀錄。

狀態：機制（SIGKILL 留鎖）已確定；164.1 之前的兩條 subprocess.run 路徑維持「首要嫌疑、未證實」。本票對已修路徑不據此收斂為「已證實」，僅記為與時序相容。

後續落點（併入 0.5.0-W1-164.4.1 的設計，不另開票）：鎖檔清理 hook 記錄線索時，日誌須寫到主倉而非 worktree 內，否則下次同樣隨 worktree 清除而消失。
