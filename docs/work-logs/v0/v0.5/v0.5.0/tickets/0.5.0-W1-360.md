### 補充：跨線實地驗收的證據須晚於變更生效（2026-10-19）

L7 的 328（閘門預檢）需以下一筆經閘門的合併作實地驗收；L9 的 356 合併在 16:19 寫入，但其 worktree merge 於 16:08:47 啟動，早於 328 合併（16:11:45），跑的是舊版程式，不能作證據（-3e 判讀）。補條文時加一列：多線同時合併時，取他線操作作實地驗收證據前，比對該操作的啟動時刻與被驗收變更進 main 的時刻，前者須晚於後者；只比對合併完成時刻會誤採舊程式的結果
### 補充素材（337 線，2026-10-19）

第四項「分派段落有程式讀者時，與讀者明文約定格式」的第二個實例：`.claude/logs/worktree-merge.log` 的 commit 欄位，語意隨行而變（-f8 經主控轉述）。
- `[合併閘門] 開始` 行：commit 是當時 main 的 HEAD
- `結束` 行：只有結果為「寫入」時才是合併 commit，其他結果仍是 main 的 HEAD

讀者若照欄位名稱直接顯示，會把它誤認為分支 commit。所以條文要寫明：約定的不只是格式，還要約定每個欄位在各種情況下的語意。
### 補充素材二（337 線，2026-10-19）

第四項的第三個實例：讀 `worktree-merge.log` 的程式不能假設 `[合併閘門] 開始`／`結束` 兩兩成對、互不重疊。不需要跑測試的合併不佔 heavy 名額，會和其他合併重疊。實例：16:19:45 a352 開始；16:21 a748 開始並結束；a352 到 16:31:50 才結束。337.5 原本假設「最後一筆開始即持有者」，這個假設不成立，修正已排入 337.4。所以約定除了寫明欄位語意，也要寫明記錄之間的時序關係（是否可能重疊）。
### 補充：行為變更依放行方向分級（2026-10-19）

主控對 L7 兩項事前回報的處置：348（新增選用旗標，不改任何放行結果）直接放行；363（修正誤判，使已合併分支不帶 --force 即可清理）雖屬誤判修正，但方向為放寬，要求進閘門前附 E2 正向對照（未合併分支修後仍擋）才放行。補條文時將「行為變更判準」細分三級：不改放行結果→主控放行；收緊→主控放行並轉知；放寬→須附正向對照，涉及用戶既有裁定或新權限時交用戶
