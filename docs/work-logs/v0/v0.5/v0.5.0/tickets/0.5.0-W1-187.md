### 問題根因

殘留測試程序有兩個獨立來源（實驗與推導見「重現實驗結果」與「Solution／結論」）：

1. 逾時包裝只對單一程序送訊號：`alarm` 加 `exec` 在逾時時只終止被 exec 的程序，測試執行器的子程序被 launchd 收養後繼續執行（實驗 A、D 已驗證）。框架範本寫的 `timeout` 在 macOS 預設環境不存在，使用者各自改寫成單一程序寫法。
2. 框架自身含全機終止：測試監控 hook 達上限時執行 `pkill -f flutter_tester`，dart-test-async-guardian 排查步驟教同一寫法；hook 在測試命令返回後才執行，終止的只會是其他 session 或其他專案的程序（讀碼推導）。

### 影響範圍

- 已驗證：`.claude/hooks/post-test-hook.py`（全機 pkill，已由子票移除）、`.claude/skills/dart-test-async-guardian/SKILL.md` 與 `.claude/templates/settings-local-template.json`（timeout 寫法，已由子票改寫）、`.claude/references/agent-dispatch-template.md`（終止後自檢不涵蓋逾時當下）。
- 已驗證：真實 flutter test 的 fvm、flutter 工具、frontend_server、flutter_tester 同屬一個程序群組，對群組送訊號可涵蓋整串。
- 未驗證：長時間存活的孤兒 flutter_tester 未在本專案重現；Linux 行為未測。
- 因果範圍更正：過載主因為記憶體換頁，孤兒為偶發放大因素（見 Solution「因果範圍的更正」）。

## 重現實驗結果
### 實驗方法

量測環境：macOS（Darwin 25.5.0，arm64，8 核），2026-10-13 14:42 至 14:52，load 約 21 至 24。

- 實驗 A 至 C 使用自毀式替身程序（改名為 orphan-exp-A／B／C／C2 的 perl 程序，600 秒後自行結束），不啟動 flutter。清理只對記下的 PID 送訊號，不以名稱比對。
- 實驗 D 使用真實的 flutter 測試（fvm flutter test --no-pub，單一測試檔 test/unit/components/divider_test.dart）。整串程序以 perl 的 setpgrp 放進新建的程序群組，清理只對該群組編號送訊號。
- 每個實驗以 ps 的 pid、ppid、pgid 三欄判定存活、父程序與群組歸屬。

### 實驗執行

| 實驗 | 做法 | 觀察 |
|------|------|------|
| A：perl alarm | perl -e 'alarm 3; exec @ARGV' 包住一個會產生子程序並等待的 sh | 3 秒後 rc=142；子程序仍存活，ppid 變為 1，pgid 維持原群組編號 |
| B1：Bash 工具逾時 | 同樣的命令交給 Bash 工具，工具逾時設為 5 秒 | 工具回報「未在逾時內完成，已移到背景」；命令與子程序都繼續執行，子程序與工具 shell 同一個 pgid |
| B2：停止背景任務 | 對 B1 的背景任務呼叫 TaskStop | 子程序一併結束，無殘留 |
| C：程序群組逾時 | perl fork 後子程序 setpgrp(0,0) 再 exec；逾時時對負的 pid 先送 TERM、2 秒後送 KILL | rc=124；直接子程序與巢狀子 shell 內的孫程序皆結束，存活數 0 |
| D：真實 flutter | 首次看到 flutter_tester 時記錄程序樹，隨即對最上層程序送 SIGALRM | 程序樹為 fvm → flutter 工具（dartvm）→ frontend_server 與 flutter_tester，四者 pgid 相同；最上層收到訊號後，flutter 工具未隨之結束，測試照常跑完並輸出 All tests passed |

另查：本機 command -v timeout、gtimeout、setsid 三者皆無輸出。

### 實驗發現

已驗證：

1. 以 alarm 加 exec 做逾時，訊號只送達被 exec 的那一個程序；其子程序存活並被 launchd 收養（實驗 A）。真實 flutter 下，最上層程序收到訊號後，底下的 flutter 工具繼續執行（實驗 D）。
2. 被留下的程序保留原本的程序群組編號（實驗 A）；真實 flutter 的四個程序同屬一個群組（實驗 D）。因此對群組送訊號可涵蓋整串。
3. 以新程序群組啟動、逾時時對群組先 TERM 後 KILL，可清除子程序與孫程序，且只用 perl 內建功能（實驗 C）。
4. Bash 工具的逾時不終止命令，只把它移到背景（實驗 B1）；之後以 TaskStop 停止時，未脫離群組的子程序會一併結束（實驗 B2）。
5. macOS 預設環境沒有 timeout、gtimeout、setsid；框架範本中的 timeout N flutter test 在此環境無法執行。

未驗證：

- 長時間存活的孤兒 flutter_tester 未在本專案重現。實驗 D 的測試檔不到一秒即跑完，程序於 3 秒內自然結束，無法區分被留下與自行結束。重現需要一個會卡住的測試。現有證據為回報方的現場觀測（17 個存活 19 至 20 小時），其來源歸因於 perl alarm 屬時間吻合的推斷，未逐 PID 查證。
- 實驗 B2 只涵蓋未脫離群組的子程序；自行建立新 session 或新群組的子程序不在涵蓋內。
- Linux 行為未測。

## Solution
### 結論

殘留有兩個獨立來源，加上一個放大因素：

1. 逾時包裝只對單一程序送訊號。alarm 加 exec 的寫法在逾時時只終止被 exec 的那個程序，測試執行器的子程序存活並被 launchd 收養。框架沒有提供可用的逾時工具：範本寫的 timeout 指令在 macOS 預設環境不存在，使用者因此各自改寫。
2. 框架自身含全機終止。測試監控 hook 在測試時長達上限時執行 pkill -f flutter_tester，dart-test-async-guardian 的排查步驟也教同一寫法。該 hook 註冊在測試命令結束之後，觸發時自己的測試已返回，被終止的只會是其他 session 或其他專案的程序。另外，計時檔每個專案只有一份，任一測試命令都會覆寫開始時間，並行時量到的時長不可靠。
3. 放大因素：沒有任何機制在跑測試前揭露機器負載或既有孤兒，殘留只能靠人注意到負載異常才被發現。

既有的終止後 pgrep 自檢約束（派發範本）處理的是代理人主動終止之後的查核，不涵蓋上述第 1、2 項：逾時包裝留下的孤兒發生時沒有任何「終止動作」可觸發自檢。

### 候選方案

逾時包裝：

| 候選 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 框架提供逾時包裝腳本：以新 session 啟動命令，逾時時對程序群組先 TERM 後 KILL，結束碼 124；包裝腳本自身收到 TERM／INT／HUP 時轉送給群組 | 寫法只有一份；群組清理經實驗 C 與 D 驗證；與 claim_verification 既有的 killpg 做法一致 | 新群組脫離 harness 的群組訊號，包裝腳本被 KILL 時無法轉送，須靠孤兒清理補位 |
| B | 文件中改列 perl 單行寫法 | 不新增檔案 | 每位寫入者各抄一份，與本次問題的成因（各自改寫）同形；無法測試 |
| C | 只加強終止後自檢條文 | 無實作 | 逾時當下沒有終止動作，自檢不會被觸發 |

框架內的全機終止：

| 候選 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 移除 hook 的 pkill，時長超過上限時只輸出警告與清理指令；排查步驟改用逾時包裝腳本 | 消除跨 session、跨專案的波及 | 失去自動終止；但該終止在測試返回後才執行，本來就終止不到自己的測試 |
| B | 把 pkill 限縮為專案路徑樣式 | 保留自動終止 | 命令列不一定含專案路徑（實驗 D 的 flutter_tester 命令列即不含），會漏；且同專案的其他 worktree 仍被波及 |

孤兒清理：

| 候選 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 清理指令以三項條件認定：父程序為 1、命令屬已知測試執行器、工作目錄位於本專案根目錄或其 worktree 之下；預設只列出，帶旗標才終止 | 範圍限於本專案；可重複執行 | 工作目錄指向已刪除 worktree 的孤兒須另行處理路徑比對 |
| B | 依命令列樣式比對 | 實作簡單 | 與全機 pkill 同一問題；且會比對到帶同字串的其他 shell（派發範本已記錄此陷阱） |

測試前的負載揭露：

| 候選 | 做法 | 利 | 弊 |
|------|------|----|----|
| A（採用） | 測試前 hook 輸出每核負載與本專案孤兒數，超過門檻時警告並附清理指令，不阻擋 | 殘留在下一次測試前即可見 | 警告可被忽略 |
| B | 超過門檻時阻擋測試 | 強制 | 高負載可能來自與測試無關的程序（觀測當下 CPU 前幾名為檔案管理員與視窗伺服器），阻擋會停下所有 session 而無從解除 |

全機 pkill／killall 守衛：採用 PreToolUse 守衛，拒絕不帶 PID 或群組範圍的 pkill 與 killall，訊息指向清理指令。不採「只寫進條文」：本次波及即發生在代理人自行決定清理方式的情況，條文在迴路內。守衛的誤擋範圍由實作票以正向與反向對照輸入界定。

### 因果範圍的更正（2026-10-13，依 0.5.0-W1-187.8 與 0.5.0-W1-188 的實測）

本票 why 欄轉述的回報把兩件事並列：測試孤兒累積（17 個存活 19 至 20 小時），以及整機 load 長期 70 至 88。讀者容易由此推得「孤兒造成過載」。後續實測不支持這個歸因：

- 符合認定條件的測試孤兒為 0 個時，load 仍在 27 至 32；回報方另行觀測到孤兒清空後 load 仍約 48 至 50。
- 同一時段交換空間 19.5G 中已用 18.4G 至 18.5G，系統態 CPU 高於使用者態。過載主因是記憶體換頁。
- 記憶體用量最大的是瀏覽器（約 15.5GB），框架工作流可控的部分約佔兩成。

更正後的定位：測試孤兒是偶發放大因素，不是過載成因。此判定來自單次取樣，取樣時沒有測試在執行，不涵蓋測試進行中的程序。

不受影響的部分：

- 「結論」一節的三點（逾時包裝只對單一程序送訊號、框架自身含全機終止、測試前無負載揭露）講的是殘留程序的來源與可見性，皆仍成立，實驗 C 與 D 的結果不變。
- 「Spawn 規劃」的六項措施皆不依賴孤兒為主因的前提，全數維持。它們防的是工具缺口與跨 session 波及，與過載佔比無關。

隨之調整的部分：

- 測試前的負載揭露（候選 A）：主訊號由「每核負載與孤兒數」改為「交換空間用量與負載」，孤兒數為輔；維持只警告不阻擋。設計輸入已寫入 0.5.0-W1-187.4。
- 優先級（用戶裁決）：0.5.0-W1-187.2 為本線唯一的 P1；0.5.0-W1-187.3 由 P1 降為 P2；0.5.0-W1-187.9 由 P2 降為 P3。
