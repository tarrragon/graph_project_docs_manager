## 重現實驗結果
### 實驗方法

量測環境：macOS（Darwin 25.5.0，arm64，8 核），2026-10-13 14:42 至 14:52，load 約 21 至 24。

- 實驗 A 至 C 使用自毀式替身程序（改名為 orphan-exp-A／B／C／C2 的 perl 程序，600 秒後自行結束），不啟動 flutter。清理只對記下的 PID 送訊號，不以名稱比對。
- 實驗 D 使用真實的 flutter 測試（fvm flutter test --no-pub，單一測試檔 test/unit/components/divider_test.dart）。整串程序以 perl 的 setpgrp 放進新建的程序群組，清理只對該群組編號送訊號。
- 每個實驗以 ps 的 pid、ppid、pgid 三欄判定存活、父程序與群組歸屬。

### 實驗執行

| 實驗 | 做法 | 觀察 |
|------|------|------|
| A：perl alarm | perl -e 'alarm 3; exec @ARGV' 包住一個會產生子程序並等待的 sh | 3 秒後 rc=142；子程序仍存活，ppid 變為 1，pgid 維持原群組編號 |
| B1：Bash 工具逾時 | 同樣的命令交給 Bash 工具，工具逾時設為 5 秒 | 工具回報「未在逾時內完成，已移到背景」；命令與子程序都繼續執行，子程序與工具 shell 同一個 pgid |
| B2：停止背景任務 | 對 B1 的背景任務呼叫 TaskStop | 子程序一併結束，無殘留 |
| C：程序群組逾時 | perl fork 後子程序 setpgrp(0,0) 再 exec；逾時時對負的 pid 先送 TERM、2 秒後送 KILL | rc=124；直接子程序與巢狀子 shell 內的孫程序皆結束，存活數 0 |
| D：真實 flutter | 首次看到 flutter_tester 時記錄程序樹，隨即對最上層程序送 SIGALRM | 程序樹為 fvm → flutter 工具（dartvm）→ frontend_server 與 flutter_tester，四者 pgid 相同；最上層收到訊號後，flutter 工具未隨之結束，測試照常跑完並輸出 All tests passed |

另查：本機 command -v timeout、gtimeout、setsid 三者皆無輸出。

### 實驗發現

已驗證：

1. 以 alarm 加 exec 做逾時，訊號只送達被 exec 的那一個程序；其子程序存活並被 launchd 收養（實驗 A）。真實 flutter 下，最上層程序收到訊號後，底下的 flutter 工具繼續執行（實驗 D）。
2. 被留下的程序保留原本的程序群組編號（實驗 A）；真實 flutter 的四個程序同屬一個群組（實驗 D）。因此對群組送訊號可涵蓋整串。
3. 以新程序群組啟動、逾時時對群組先 TERM 後 KILL，可清除子程序與孫程序，且只用 perl 內建功能（實驗 C）。
4. Bash 工具的逾時不終止命令，只把它移到背景（實驗 B1）；之後以 TaskStop 停止時，未脫離群組的子程序會一併結束（實驗 B2）。
5. macOS 預設環境沒有 timeout、gtimeout、setsid；框架範本中的 timeout N flutter test 在此環境無法執行。

未驗證：

- 長時間存活的孤兒 flutter_tester 未在本專案重現。實驗 D 的測試檔不到一秒即跑完，程序於 3 秒內自然結束，無法區分被留下與自行結束。重現需要一個會卡住的測試。現有證據為回報方的現場觀測（17 個存活 19 至 20 小時），其來源歸因於 perl alarm 屬時間吻合的推斷，未逐 PID 查證。
- 實驗 B2 只涵蓋未脫離群組的子程序；自行建立新 session 或新群組的子程序不在涵蓋內。
- Linux 行為未測。
