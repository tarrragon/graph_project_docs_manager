## 重現實驗結果
### 實驗方法

`fvm dart format --output=none --set-exit-if-changed lib test integration_test`（釘選版）與全域 SDK 的 `dart format` 同參數各跑一次，取兩組 `Changed` 清單以 `LC_ALL=C comm` 求交集與差集；再對釘選版不一致的 117 檔逐檔以 `--output=show` 與原檔 diff 計行數。

### 實驗執行

釘選 rc=1（117／337 檔），全域 rc=1（131／337 檔）；交集 110、僅釘選 7、僅全域 21；117 檔 diff 合計 5,920 行。

### 實驗發現

已驗證：漂移主因是流程沒有格式化步驟（110 檔兩版皆不一致），版本差只占 7 檔。未驗證：無。

## Solution
### 結論（待主控協調，本票停在 in_progress）

1. **成因**：主因是流程沒有格式化步驟（110／117 檔），全域與釘選版本不同只占 7 檔。只統一版本不會消除漂移
2. **建議一次性格式化**：以 `fvm dart format lib test integration_test` 單一 commit 處理全部 117 檔（約 5,920 行，純格式），commit 只含格式變更，並把該 commit 記入 `.git-blame-ignore-revs`。此步會改到所有線的檔案：依主控指示**本次不派發**，由主控協調各線暫停、合併完手上分支後再執行
3. **建議防再發**：合併閘門對「本次合併改動的 .dart 檔」跑 `fvm dart format --output=none --set-exit-if-changed <檔>`，不一致即擋。只檢查改動檔，在一次性格式化之前也能上線，不會因存量漂移全紅。閘門屬 `.claude/skills/worktree` 框架資產，依〈框架修補的節奏〉由主控決定派修或觀測進 issue
4. **過渡期約束**（一次性格式化前）：代理人只格式化自己改的檔、不對目錄跑格式化（W3-006 派發 prompt 已採此寫法）

### 候選方案比較

| 方案 | 利 | 弊 |
|------|----|----|
| A 一次性格式化 + 閘門檢查改動檔（建議） | 存量歸零；之後每次合併自動維持 | 需各線暫停一次；閘門改動屬框架 |
| B 不做一次性格式化，只加閘門檢查改動檔 | 不需暫停；漂移隨改動逐檔消失 | 每次改到舊檔都夾帶該檔的格式差異，diff 難審，持續數個版本 |
| C 維持現狀 | 零成本 | 漂移持續增加，誤跑目錄格式化的風險持續 |
