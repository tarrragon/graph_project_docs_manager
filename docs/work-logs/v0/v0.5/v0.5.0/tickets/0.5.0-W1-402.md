## 重現實驗結果
### 實驗方法

1. 讀 `create.py` 中 `--acceptance` 的 argparse 定義與後處理流程，找出拆分點
2. 直接呼叫 `ticket_system.lib.acceptance_parser.parse_acceptance_items`（唯讀，不建票），用三組輸入比對：含 `||`、不含分隔符、以 `\|\|` 跳脫
3. 比對 `references/create-command.md` 的使用說明，以及 `command_lifecycle_messages.ACCEPTANCE_PIPE_SPLIT_WARNING` 的警告文字

### 實驗執行

- 拆分點
  - `create.py` 第 1384 行 argparse 的 help 寫明「多次 --acceptance 或 | 分隔」
  - `create.py` 第 233 行呼叫 `parse_acceptance_items(args.acceptance)`
  - `acceptance_parser.parse_acceptance_items` 以 `split_unescaped(item, ACCEPTANCE_SEP)` 依未跳脫的 `|` 拆段，再去掉空白段：`cleaned = [s for s in cleaned if s]`
- 重現結果（2026-10-20）

  | 輸入 | 輸出 | 警告數 |
  |------|------|--------|
  | `兩例及其 \|\|、管線、變形寫入（E2）`（`||` 未跳脫） | `['兩例及其', '、管線、變形寫入（E2）']` | 1 |
  | `單純一條` | `['單純一條']` | 0 |
  | `shell 的 a \|\| b`（以反斜線跳脫） | `['shell 的 a \|\| b']`，保留字面 | 0 |

- 警告內容：`[WARNING] 單一 --acceptance 值含分隔符，已被拆成 {count} 條`，並提示改用反斜線跳脫。由 `create.py` 以 `print(warning, file=sys.stderr)` 輸出
- 文件：`references/create-command.md`〈多值參數格式〉已寫明分隔符、反斜線跳脫，以及「被拆成多條會印出 [WARNING]」；建立成功的訊息也會回報實際存入的驗收條數與逐條內容

### 實驗發現

已驗證：
- 拆分是設計好的功能（`|` 分隔多條，源自 W3-089 的跳脫加警告機制），不是 YAML 序列化或其他層的意外行為
- `||` 會變成兩條，原因是兩個分隔符之間的空段被丟棄
- 拆條時確實會發出警告

why 所述「無任何警告」與重現結果不符：警告輸出到 stderr，建立 365.4 時的讀法沒有留下紀錄。若以 `2>&1` 擷取後再用 grep 白名單過濾（例如只取 OK 行），警告就會被濾掉，這與 bash-tool-usage-rules 規則二所述的機制相同

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論（狀態 a）：屬功能，已有警告；補文件例子，不改程式

- 拆分位置：`ticket_system/lib/acceptance_parser.py` 的 `parse_acceptance_items`，以 `split_unescaped(item, "|")` 拆分，接著丟棄空段
- 判定為功能的依據：
  - argparse 的 help 與 `references/create-command.md` 都寫明 `|` 是分隔符
  - 有反斜線跳脫可用
  - 拆條時會印 stderr 警告，建立成功的訊息也會回報存入的條數
- 落地：在 `references/create-command.md` 補上 `||`（shell 的「或」）同樣會被拆的例子與 `\|\|` 寫法，並註明警告走 stderr、可能被 grep 白名單濾掉（43a321d6f）
- 不改程式碼：警告機制已經存在。把 `||` 特判為字面，會讓同一字元出現兩套語意，徒增規則；跳脫機制已經能表達字面
