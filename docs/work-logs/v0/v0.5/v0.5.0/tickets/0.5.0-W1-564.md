## Task Summary

評估 掃描輪次例外是否需要不改行為的取得點，讓擷取或測試能取得堆疊

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

掃描輪次的例外在兩處被捕捉後只寫 `developer.log`（`ScanRoundNotifier._runGuarded` 記錄後 rethrow；`GapReportNotifier._projectRound` 記錄後回 `GapReportUndeterminable.scanFailed()`）。`developer.log` 只送 VM service 的 Logging 串流，`flutter test` 的 stdout 看不到；`scanFailed()` 為 const 建構子、不攜帶例外。故 `ux_capture` 的 `_failIfGapsUndeterminable` 只能印出 reason／isScanFailure 等狀態欄位。

### 影響範圍

- 已驗證（讀碼）：例外的取得點只有上述兩處 catch；`_runRound` 內可覆寫的 provider 接縫有 `docsFileSystemFactoryProvider`、`builtinTrackingSchemaJsonProvider`、`degradedSchemaProvider`、`scanCorpusFnProvider`、`buildGraphFnProvider` 五個；`ux_capture.dart` 的 E2 測試已以 `extraOverrides` 覆寫 `scanCorpusFnProvider` 注入例外，證明擷取入口能把覆寫送進輪次。
- 不經接縫、無法由覆寫攔到的步驟：`resolveSchemaSource`、`typeTableFromJson`、`gapReportStateFromRound`、`ScanRoundResult` 建構、輪次排程本身。
- 未驗證：513 那次「無法判定破洞」的例外實際出自哪一步（27 次重現皆未失敗，無樣本）。

### 相關 Error Pattern

無直接對應。相鄰：`quality-baseline` 規則 1 邊界「測試綠燈不等於 Runtime 正確」（PC-165）談的是 mock 遮蔽，本票是可觀測面缺口。

---

## 重現實驗結果

### 實驗方法

讀碼（PM 前台，未執行測試）：追兩處 catch、`_runRound` 的 provider 接縫、`ux_capture.dart` 的 override 組裝與 `_failIfGapsUndeterminable`。

### 實驗執行

- `lib/app/scan_round.dart`：`_runGuarded` catch → `developer.log(error: e, stackTrace: st)` → 世代相符時 `state = ScanRoundIdle()` 並 rethrow。
- `lib/screens/gap_report/gap_report_provider.dart`：`_projectRound` catch → `developer.log` → `return const GapReportUndeterminable.scanFailed()`。
- `integration_test/research/ux_capture.dart`：`_capture` 的 overrides 依序串 `fixtureOverrides()`、`variant.overrides`、`extraOverrides`；E2 測試以 `scanCorpusFnProvider.overrideWithValue(... throw StateError(...))` 驗證紅燈。

### 實驗發現

- 已驗證：測試端可在不改 `lib/` 的前提下，把真實的 `scanCorpusFn`／`buildGraphFn`／檔案系統工廠包一層「記錄例外與堆疊後 rethrow」的裝飾器，例外語意不變，`_failIfGapsUndeterminable` 印出記錄即可。
- 未驗證：裝飾器能涵蓋 513 那次失敗的來源步驟（見影響範圍的不涵蓋清單）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 候選比較（L40，2026-10-31；讀碼得出）

| 候選 | 做法 | 改產品端 | 堆疊涵蓋 | 利 | 弊 | 可觀測性規則影響 |
|------|------|---------|---------|----|----|-----------------|
| (a) `scanFailed` 攜帶例外與堆疊 | `GapReportUndeterminable.scanFailed(error, stackTrace)`，不渲染 | 是：模型與 `_projectRound` | 兩處 catch 之後的全部步驟 | 測試直接讀 state | 失去 const 建構子，既有兩則測試的 `const ...scanFailed()` 要改；畫面層狀態攜帶 `Object`，模型為測試需求擴充 | 規則 1 已滿足（catch 有日誌），本案只為取得點而改 |
| (b) debug 用「最後一次輪次失敗」provider | catch 內另寫一個 provider，測試讀它 | 是：新增 provider 與兩處寫入 | 同 (a) | 不動既有狀態型別 | 新增產品端全域可變狀態，只服務測試；兩處 catch 多一個副作用 | 與 `developer.log` 並存，形成第二條錯誤通道，偏離規則 2「統一入口」的方向 |
| (c) 維持現狀，重現時接 VM service Logging 串流 | 下次失敗時以 `flutter test --start-paused` 接 VM service 讀 Logging | 否 | 全部步驟（凡經 `developer.log` 者） | 零改動 | 每次要人工接線；擷取是批次跑，失敗不可預期，事後接不到該次 | 無 |
| (d) 測試端裝飾既有接縫 | `ux_capture` 以 `extraOverrides` 覆寫 `scanCorpusFnProvider`、`buildGraphFnProvider`（可加檔案系統工廠），呼叫真實實作，catch 時記錄例外與堆疊並 rethrow；`_failIfGapsUndeterminable` 印出記錄 | 否（只改 `integration_test/research/ux_capture.dart`） | 經接縫的步驟：檔案讀取、掃描、建圖。不涵蓋 `resolveSchemaSource`、`typeTableFromJson`、`gapReportStateFromRound` | 例外語意不變（rethrow），產品端零改動；E2 測試已證明擷取入口能把覆寫送進輪次 | 涵蓋不完整；若失敗出在未涵蓋步驟，仍只得到 isScanFailure | 無 |

### 判定：不改產品端，採 (d)

- 理由：513 AC2 要的是「擷取失敗時留下堆疊」，屬器材需求；(a)(b) 都為測試需求改產品狀態，(d) 以既有接縫達成同一目的。(d) 的涵蓋缺口集中在純函式步驟（`resolveSchemaSource` 等），它們的輸入取自已涵蓋的檔案讀取與掃描結果，出錯時可由記錄下的輸入重放。
- (d) 仍拿不到堆疊時（失敗出在未涵蓋步驟），再評估 (a)；觸發點綁在實作票的驗收第 3 項。
- 實作以 children 建票（`0.5.0-W1-564.1`），屬 `integration_test/` 的 `*.dart`，須派代理人。
