## Problem Analysis
### 問題根因

票面敘述與 SPEC-003 現況（v1.59，§2.14 共 18 列）仍對應：列 14–17 為 0.3.2-W3-248 補登，列 18 為 0.5.0-W1-114.14.1 補登；§2.15〈可驗收形式：先分組再逐組比對〉的分組句仍寫「可棄組（列 1、3、5–10）、不可棄組（列 11–13、18）」，列 14–17 不在任何一組。

直接原因有兩層：

1. 補登列 14–17 時只同步了 §2.14 表、§2.14〈與功能需求的對應〉與 §2.17 的逐列讀出，未重跑 §2.15 自訂的「未來新增事件時比照本節程序覆核」程序。
2. §2.15 跨級別證據鏈把「時間窗」定義為事件的觸發前提（圖已建立／尚未建立），而方法論〈競爭與佔用量〉對競爭的定義是「第二個請求抵達時第一個尚未被消費」。阻擋狀態在使用者離開它之前一直未被消費，SnackBar 在停留時間到期前一直未被消費；以觸發前提互斥推不出佔用期間互斥。列 14–16 的觸發點（專案切換浮層）在任一狀態皆可用，這個落差因此由假設變成可達路徑。

### 影響範圍

已驗證（條文對讀）：

- 列 14、15 可在列 11–13、18 的阻擋狀態顯示期間到達（低級別到達時高級別正持有通道）。
- 列 16 的 SnackBar 停留期間，列 11–13、18 可到達（高級別到達時低級別正持有通道）。
- 列 17 的觸發前提與列 5–10 相同（圖已建立），可直接併入既有證據鏈第一步。
- 依賴「跨級別時序互斥」結論的句子不只在 §2.15：§2.13〈顯示位爭用時的約束與 0.1 的處置規則〉重評結果段、§2.17〈規則 2 的裁決說明〉末句與裁決表第 2 項、§2.16〈觸發事件的級別與判準原文的對應〉括號句皆引用它。
- §2.17「拒絕」本專案使用段已寫「當前者（列 11–13、18）持有通道而後者（列 5–10）到達時……仲裁層動作即為拒絕」「拒絕路徑在本專案現況即可達」，與 §2.15「列 1–10 與列 11–13、18 時序互斥」互相矛盾；列 14、15 才是該拒絕路徑的可達實例。

仍未驗證：見 Solution〈未驗證事項〉。

## 重現實驗結果
### 實驗方法

條文對讀加原始碼靜態閱讀，未執行 App、未跑測試（唯讀派發）。根因假設：「列 14–16 的觸發點在圖未建立時也可達，且可與不可棄組共存」。逐列回答兩個問題：(1) 觸發點在哪些狀態下可用；(2) 觸發後畫面狀態與提示的佔用期間。

對讀的條文：SPEC-003 §2.14 表、§2.15 全節、§2.13〈顯示位爭用時的約束與 0.1 的處置規則〉、§2.17「拒絕」本專案使用段與〈兩個觀測點的決策值對應〉、§3.1〈互動反應〉、§3.4〈帶目標跳入〉、§3.7〈互動反應〉〈生命週期〉、§2.7〈阻擋狀態的浮層可用性斷言〉、§2.8 切換專案（L2）列；SPEC-001 §1 狀態表、§4「專案未就緒」列、§7、〈返回為殼層通則〉註記、§8.2；docs/system-layer.md §3.1 通道清單；方法論〈競爭與佔用量〉〈讓步與卸載順序〉。

原始碼佐證：lib/screens/project_switcher/project_switcher_overlay.dart 的 _handleChooseFolderResult 與 _handleChosenState、lib/components/app_snack_bar.dart 的 AppSnackBar.show 與 _resolvePreemption、lib/app/attention_arbiter.dart、lib/screens/domain_view/domain_view_screen.dart、lib/tokens/motion.dart。

### 實驗執行

條文面：

1. 觸發點可用範圍。SPEC-001〈返回為殼層通則〉註記：project-switcher-entry 於 §1–§6 任一狀態皆可用；內容區 action-domain-switch-project 於三個阻擋狀態與載入失敗共四個狀態渲染。SPEC-003 §2.7〈阻擋狀態的浮層可用性斷言〉：四個狀態任一渲染時入口 enabled 為 true。§3.7〈生命週期〉展開時機列：浮層可由阻擋狀態的出口觸發。故列 14–16 的觸發點（浮層「選擇其他」與最近專案項）在阻擋狀態顯示中可達。
2. 列 14、15 觸發後。§3.7〈互動反應〉兩列皆寫「浮層維持展開；不轉狀態」並顯示 SnackBar，停留 Motion.snackBar。浮層是覆蓋層，底下的阻擋狀態不變。
3. 列 16 觸發後。§3.7〈互動反應〉該列：浮層收合並載入，另顯示 SnackBar。載入的落點依 SPEC-001 §1「載入中」列為六個分支之一，其中四個是列 11–13、18。
4. 列 17。§3.4〈帶目標跳入〉的前提是 Ticket 清單已載入或可載入；SPEC-001 §4「專案未就緒」列：Domain 處於未選專案、載入中、載入失敗或三個阻擋狀態時 Ticket 清單落「專案未就緒」，不進入清單。
5. 通道歸屬。docs/system-layer.md §3.1：通道「使用者呈現焦點」同時含暫態提示佇列與顯式關卡，兩者「持有同一種稀缺資源」、共用一個仲裁器落層。
6. 切換專案是否清除顯示中的提示。§2.8 切換專案（L2）列只寫六頁狀態重置、任務中止、returnTo 清空、切至 Domain；全文搜尋「切換專案」與 SnackBar 同現的條文為零筆。

原始碼面：

1. _handleChooseFolderResult 的 ChooseFolderUnavailable 分支與 _handleChosenState 的 WorkspaceUnavailable 分支直接呼叫 AppSnackBar.show（level 為 discardable），不檢查 Domain 當前狀態。
2. ChooseFolderNotRemembered 分支先 await _handleChosenState（其內 await gateDetectionNotifier.detect，gate 判定在此完成並套用），之後才顯示 workspaceNotRemembered。
3. AppSnackBar.show 的 currentHolder 參數全專案無呼叫端傳入；lib/app/attention_arbiter.dart 無任何檔案 import；AttentionLevel.undroppable 除型別檔與仲裁器本身外無使用點。阻擋狀態目前未登記為通道持有者。
4. Motion.snackBar 為 4 秒、Motion.snackBarWithAction 為 8 秒。
5. Domain 未選專案的 action-domain-choose-folder 仍直接把狀態設為 DomainLoading，未呼叫 chooseFolder（與 §2.14 列 14 的註記一致）。

### 實驗發現

已驗證的事實（條文可讀出）：

- 列 14、15：圖建立前後皆可發生；可在阻擋狀態（列 11–13、18）顯示期間到達。
- 列 16：SnackBar 在新專案的載入窗口內開始停留，該輪載入的落點可為列 11–13、18。
- 列 17：只在圖已建立時發生。
- 規格無「切換專案時清除顯示中 SnackBar」的條文。

原始碼與規格不一致處（分開列出）：

- 列 16 的顯示時點：規格 §3.7〈動畫提示〉「選取專案後的重載」寫浮層先收合再轉入載入態；原始碼在 gate 判定完成後才顯示 SnackBar，故原始碼下列 16 的提示可在阻擋狀態已套用之後才出現（共存不需靠停留時間跨越）。
- 仲裁：§2.17〈兩個觀測點的決策值對應〉定「等待型，被更高級別持有 → 拒絕（不顯示且留痕 + 重試訊號）」；原始碼因持有者未知而一律呈現。
