### 實作（commit bada22aed8900096f986c2084627bc6bf56ba864，分支 worktree-agent-a558d2762247d5fc2，尚未送閘門）

改動三個實作檔，lib/ 未改：integration_test/domain_view_v050.dart、app_test.dart、real_font_layout_test.dart。

C1 採方案 (2)：收到 hidden 或 paused 時，依序送 inactive、resumed，把 lifecycle 拉回 resumed。開關是全域的 `resumeWhenHidden`，預設 true。
不採方案 (1) 的理由（代理人實測）：
- flutter test 在呼叫 main() 之前就已初始化 IntegrationTestWidgetsFlutterBinding，覆寫 scheduleFrame 的子類無法建構，會撞上 `'_debugInitializedType == null': Binding is already initialized` 斷言
- observer 只呼叫一次 scheduleForcedFrame 不夠：之後每次 pump 都走 scheduleFrame，仍會被 framesEnabled 擋下

入口改為 `ensureItBinding()`，負責初始化 binding 並註冊 observer。581.1 的 framesEnabled=false 守衛保留，只加註解說明「C1 生效時不應走到此處」。

C2：新增 `pumpWidgetGuarded`。app_test 與 real_font 中原本未受保護的 pumpWidget 都改走它；real_font 那個 30 秒的 pumpAndSettle 改走 settleGuarded，步驟逾時同為 30 秒。

### 影響面（L45 查證）
lib/ 有兩處依賴 lifecycle：
- `lib/assembly/shell.dart` 的 didChangeAppLifecycleState，寫入 appLifecycleStateProvider
- `lib/screens/gap_report/scan_notification_controller.dart` 的 `_onLifecycleChange`：收到 resumed 時，若可見頁是 gaps 就撤除暫態提示，若有待顯示的拒絕通知就顯示 snackbar

C1 生效時，App 會在 hidden 之後立刻收到 inactive 與 resumed，上述邏輯可能在案例中途被觸發。未採 C1 時，同一時刻 App 會停在 hidden，該案例本來就會卡住或失去判定力。所以 C1 新增的副作用只出現在原本已經失效的案例上，但破洞報告相關案例的斷言可能因此改變。取樣時要特別觀察 gaps 類案例。
