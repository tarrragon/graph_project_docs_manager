## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 問題根因

`complete` 的收尾提交（`lifecycle._auto_commit_completion_files`）直接呼叫 `commit_files_isolated` 一次，**沒有外層重試**。`commit_files_isolated` 內部只對鎖競爭重試（最多 2 次、間隔 1 秒），`_is_cas_rejection` 明確排除 CAS 拒絕。並行 session 密集 `ticket create` 時 HEAD 每數秒前進，`rev-parse HEAD` 到 `update-ref HEAD <new> <old>` 之間的窗口被命中，update-ref 回 `is at X but expected Y`，complete 回 75，票檔留在工作區。

當次證據（git 歷史，持久平面）：complete 的窗口落在 22:20:23（本票 set 寫入）至 22:22:05（PM 手動補提交）之間；該窗口內並行 session 的四次 create 提交落在 22:20:41、22:21:22、22:21:25、22:21:31，HEAD 反覆前進。complete 沒有留下檔案日誌，故分支無法逐字確認，以 CAS 拒絕為最符合的推定（已驗證：窗口內 HEAD 確實移動；未驗證：失敗原文）。

**否定的假設**：
- index 鎖競爭：隔離索引不碰共用 index，注入共用 `index.lock` 仍 committed（rc=0），只多一則共用 index 同步 WARNING。
- bare-commit-guard：complete 走 plumbing（`commit-tree`／`update-ref`），不經 Bash 工具的 `git commit` 命令，PreToolUse 守衛對它無從攔截。

PM 當時被過濾掉的訊息是否足以判斷補提交：stderr 的 WARNING 首行即寫明「已寫入 working tree 但 auto-commit 失敗；尚未入庫，exit code 75」並附補救指令，**足以判斷**；問題在於輸出被過濾後只剩 `[OK]` 與 verify 成功行，rc 是唯一訊號。補救指令本身有缺陷（見 Solution 缺口二）。

## 重現實驗結果

### 實驗方法

pytest `tmp_path` 內建 tmp git repo（不動主 repo index 與真票，無 clone），對真實的 `lifecycle._auto_commit_completion_files` 逐一注入失敗分支，擷取 stderr 原文。腳本在 session scratchpad 的 `test_rc75.py`（8 個測試）。執行：`uv run --with pytest --with filelock --with pyyaml python -m pytest test_rc75.py -s`。

### 實驗執行

| 分支 | 注入方式 | rc | 失敗原文要點 |
|------|---------|----|------|
| A 共用 index.lock | 建 `.git/index.lock` | 0 | committed；僅 `[WARNING] 共用 index 同步失敗（update-index）：fatal: Unable to create '.../.git/index.lock': File exists.` |
| B ref 活鎖 | 建 `refs/heads/main.lock`（新） | 75 | `失敗原因：fatal: update_ref failed for ref 'HEAD': cannot lock ref 'HEAD': Unable to create '.../refs/heads/main.lock': File exists.` + 鎖檔路徑 + 鎖檔處置 |
| C ref 殘骸鎖 | 同上，mtime 300 秒前 | 75 | 同 B，加 `[殘骸診斷] 鎖已持續超過 60 秒未更新，判為崩潰殘骸而非並行活鎖，停止重試` |
| D CAS 拒絕 | `update-ref` 前並行提交一次 | 75 | `fatal: update_ref failed for ref 'HEAD': cannot lock ref 'HEAD': is at <新> but expected <舊>`；無鎖檔路徑 |
| E reference-transaction guard 拒絕 | tmp repo 的 hook 回 exit 1 | 75 | `[git-ref-transaction-content-guard] DENY: ...` + `fatal: ref updates aborted by hook` |
| F git 子步驟逾時 | `_GIT_TIMEOUT=0.0001` | 75 | `失敗原因：git rev-parse 逾時` |
| G paths 含目錄 | 傳目錄路徑 | 75 | `paths 含目錄路徑 [...]：範圍自我驗證逐檔比對...` |
| H 對照：append-log 重試路徑 | 同 D 的 CAS 競爭，走 `auto_commit_ticket_md_with_retry` | committed | `attempts=2`，第 2 次成功 |

B～G 的 WARNING 首行皆為 `[WARNING] [complete] T-1 已寫入 working tree 但 auto-commit 失敗（嘗試 1 次）；尚未入庫，exit code 75。`，工作區留 `M t.md`（D 已驗 `git status --porcelain`）。除 B、C 外，補救指令皆為 `git add <path> && git commit -m ...（或 ticket track commit 以隔離索引提交）`，標題寫「鎖排除後」。

### 實驗發現

已驗證：
1. 75 的分支共七類（B～G 加 update-ref 例外路徑），index 鎖競爭**不在其中**（A 只產生 WARNING）。
2. D 與 H 同一競爭，append-log 路徑自癒、complete 路徑失敗：缺的是外層重試，不是隔離索引機制。
3. 警告固定印「嘗試 1 次」（`_format_complete_commit_failure` 傳入寫死的 1），B 的實際為 2 次鎖重試。
4. 補救第一順位為裸 `git commit`，在 CAS／hook 分支沒有鎖可排除；並行派發期間該裸 commit 是 bare-commit-guard 的攔截對象。
5. complete 失敗不寫檔案日誌（append-log 路徑寫 `ticket-commit-retry` 日誌），事後無法還原分支。

未驗證：2026-10-06 當次的實際分支（原文已遺失，僅以窗口內 HEAD 移動推定為 D）；E 的 guard 在真實 repo 中對 ticket md 提交的實際判定（以模擬 hook 代替）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 結論

rc=75 的根因是 complete 的收尾提交無外層重試，並行 HEAD 前進（CAS 拒絕）或短暫 ref 鎖一次即失敗。補救訊息另有兩處誤導。

**與 #61 的關係：不同根，補救路徑共用互斥。**
- #61：PreToolUse 守衛攔截 Bash 命令（`git commit`），機制在命令層；complete／append-log 現已走 plumbing，不再落入該判定。
- 本票：plumbing 提交自身的 CAS／鎖／hook 失敗。
- 交集：本票的補救指令（裸 `git commit`）在並行派發期間會被 #61 的守衛擋下，兩者合成「失敗後無可用補救路徑」。關係判定為「切分＋引用」：已 observe 於 #61（https://github.com/tarrragon/claude/issues/61#issuecomment-6028458001）。

**判準與 dedup**：(1) 抽象可攜：替換專案名稱後成立，是；(2) 根源在 `.claude/` 通用資產（ticket skill），是。dedup 查 auto-commit／rc=75／complete／isolated／update-ref：最近同域為 #61 與 #55，皆未涵蓋 complete 路徑缺重試，故不另開 issue，附於 #61。

### 方案比較

| 方案 | 作法 | 利 | 弊 |
|------|------|----|----|
| A 隔離索引 CAS | 以隔離索引 CAS 取代現行提交 | 不受共用 index 與守衛影響 | **已實作**：complete 現行即 `commit_files_isolated`；A 的收益已拿到，失敗的正是它的 CAS 步驟，換 A 無增量 |
| B 維持現狀，只改訊息 | rc=75 時指示補提交步驟 | 改動小、補救路徑明確 | 每次並行建票仍失敗並需人工補提交，把可自動消除的失敗留給人 |
| C 外層重試（採用） | complete 接與 append-log 同形的鎖與 CAS 重試，並寫失敗日誌 | 消除當次現象的主因；重用既有重試預算與日誌；可觀測性補齊 | 重試預算耗盡仍會 75，需配合 B |
| D C＋B（結論） | C 後保留 B 作為預算耗盡的兜底，補救依分支 | 自癒優先、失敗時補救正確 | 兩個小改動 |

**結論**：採 D。C 為主（P2），B 為兜底（P3）。
