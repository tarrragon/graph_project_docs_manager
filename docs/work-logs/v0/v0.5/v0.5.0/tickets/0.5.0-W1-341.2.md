### Context Bundle（PM 讀碼，2026-10-19，未實測）

`.claude/hooks/bare-commit-guard-hook.py` 的 `main()` 取 `invocation = invocations[0]` 之後：

- `_has_amend_exemption(invocation.args)` 命中 → **整條命令直接 return 0**，排在 `_pending_operation_in_dirs(_resolve_detect_dirs_multi(...))` 之前
- 後續 `_has_all_exemption`、`_is_index_discarding_form`、並行期 staged 範圍檢查也只看 `invocations[0].args`

四種組合的讀碼預測（待實測）：

| 組合 | 預測 | 疑慮 |
|------|------|------|
| A. `--amend` 在前、裸 commit 在後（`;` 串接） | 放行 | 第二筆裸 commit 沒經過任何判定，連 MERGE_HEAD 偵測都被跳過。git 在合併中拒絕 amend，但 `;` 串接時第二筆照樣執行，會把合併收尾 |
| B. 裸 commit 在前、`--amend` 在後 | 依第一筆正常判定 | 預期無錯判 |
| C. 兩筆都 `--amend` | 放行 | 預期無錯判 |
| D. 兩筆都裸 commit | 依第一筆判定 | 預期無錯判 |

同根延伸（不在本票四組合內，建議一併實測一筆）：`git commit -m x; git commit -a -m y` 在並行期只依第一筆的裸 commit 規則判定，第二筆 `-a` 的內容檢查被跳過

實測要點：在真實倉庫放 MERGE_HEAD 或製造並行期，以 hook 真實輸入取得 exit code；A 組需分別測 `&&` 與 `;` 兩種串接

## 重現實驗結果

### 實驗方法

系統暫存目錄建真實臨時 repo（不在本 repo 內），每格一個全新 repo。條件 M：真實衝突合併並產生 MERGE_HEAD（無派發）。條件 P：.claude/dispatch-active.json 兩筆派發（T-1 宣告 a.txt、T-2 宣告 b.txt），staged a.txt+b.txt（跨兩派發，裸 commit 應被擋）。條件 P2：同派發，僅 staged a.txt、b.txt 為未 staged 修改（裸 commit 範圍安全，但 -a 會掃入 b.txt，應被擋）。以真實 hook 輸入（stdin JSON，cwd 為臨時 repo、行程 cwd 同、未設 CLAUDE_PROJECT_DIR）執行 bare-commit-guard-hook.py，讀臨時 repo 內 .claude/hook-logs/bare-commit-guard 判定行。腳本在 session scratchpad 的 exp.py／conseq.py，不入庫。

後果實跑（M 衝突已解決並 add，用真實 git 執行同一命令）：
- A1（&&）：rc=128，amend 被 git 拒（cannot amend during merge），後段不執行，MERGE_HEAD 仍在，無傷害。
- A2（;）：amend 同樣被拒，但第二筆裸 commit 照跑，HEAD 成為 2 parents 的 merge commit、MERGE_HEAD 消失，即收尾了他方的合併。
- E（P2）：第二筆 -a 把 b.txt（T-2 範圍）掃進 commit y；hook 對單獨 -a 會擋同樣內容（G=2）。

### 實驗發現

已驗證：
1. hook 只判定 invocations[0]；--amend 命中即 return 0，且排在 MERGE_HEAD 偵測之前，後續 invocation 完全不受檢。
2. 放行方向錯判成立三處：A2（amend ; 裸，M 條件）實際收尾合併；F（amend ; -a）同構，M 條件下 ; 串接可收尾；E（裸 ; -a，P2 條件）第二筆 -a 越權掃入他派發檔案。
3. A1 因 && 與 amend 被 git 自身拒絕而無實害，但 hook 判定仍為放行。
4. B、C、D 無錯判。

未驗證：P 條件下 A 的實害（amend 自身吸收所有 staged，屬既有 amend 豁免設計，非本票範圍）；-- pathspec／--only 置於第二筆的同型漏檢（同根，預期相同，未實測）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->

### 判定

有放行方向錯判，根因單一：main() 只取 invocations[0] 判定，--amend 豁免整條命令 return 0。實害最大者為 `amend ; 裸 commit`（分號串接）在 MERGE_HEAD 進行中：amend 被 git 拒絕後第二筆裸 commit 仍執行並收尾合併。次者為第二筆 `-a` 在並行期不受內容檢查。嚴重度中（需串接命令才觸發，但後果是靜默收尾他方合併），priority P2。

### 候選修法

| 方案 | 作法 | 利 | 弊 |
|---|---|---|---|
| 1 逐筆判定 | 對 invocations 每一筆跑完整判定鏈，任一筆 exit 2 即擋；--amend 只豁免該筆 | 根治，行為與單筆一致；B/C/D 結果不變 | main() 需把判定鏈抽成函式（現為內嵌流程），測試補多筆組合 |
| 2 amend 豁免限單筆命令 | 只有 invocations 僅一筆且含 --amend 才豁免；多筆時走完整鏈 | 改動小；amend 在 MERGE_HEAD 下本就必敗，不豁免亦安全 | 第二筆 -a／pathspec 仍只被 invocations[0] 規則涵蓋，E 類未解 |
| 3 多筆保守阻擋 | 並行期或 pending 操作下，多筆 commit 一律擋並提示拆開執行 | 實作最簡、方向安全 | 誤擋合法的 `commit -m a && commit -m b` |

建議方案 1；若要最小變更先做方案 2，並以方案 1 補 E 類。
