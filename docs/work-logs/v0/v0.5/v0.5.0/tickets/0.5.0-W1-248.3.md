## Problem Analysis
### 問題根因

gate（`GateDetectionNotifier.detect`）每次都用 `DefaultFrameworkSignalProbe.readSchemaJsonVersion` 重讀 JSON 來判斷版本範圍。建圖的 JSON 由 `ScanRoundNotifier._runRound` → `_readProjectSchemaJson` 讀入，但 `DomainViewLoader._obtainRound` 走的是 `ensureRound()`：只要已有 `ScanRoundCompleted`，就直接回傳舊輪次、不重讀。所以兩次讀取之間的間隔可能只有幾毫秒（TOCTOU），也可能長到任意時間（輪次被快取）。

確定性的生產觸發路徑（不需要 TOCTOU）：
1. 開啟一個 `tracking_schema.json` 版本高於內建表（或版本無法判讀）的專案 → gate 落 `DomainSchemaIncompatible`
2. 進入缺口報告畫面 → `gap_report_provider` 呼叫 `ensureRound()` 完成一輪，graph 為 `GraphBuildUnavailable(projectVersionOutOfKnownRange)`；缺口報告對此有合法呈現，這一輪會被保留
3. 使用者在專案內更新框架（sync-pull），JSON 版本因此落入已知範圍
4. 在專案切換浮層再選一次同一路徑 → `project_switcher_overlay` 重設 `currentWorkspaceStateProvider`，但 `ScanRoundNotifier` 的 listener 以 `_isSameWorkspace` 判為同一路徑、不 discard。`detect` 重讀 JSON 得到 `InKnownRange` → `load()` → `ensureRound()` 回傳步驟 2 的舊輪次 → `_unavailableGraph` → debug 版 assert 失敗；release 版落 `DomainUnset`

### 影響範圍

- 已驗證（靜態讀碼）：`lib/app/scan_round.dart` 的 ensureRound 與 listener、`lib/app/domain_view_loader.dart` 的 `_unavailableGraph`、`lib/screens/domain_view/gate_detection_notifier.dart`、`lib/screens/project_switcher/project_switcher_overlay.dart` 的同路徑重選分支
- 兩個讀取器的解析差異：已逐行比對，不是觸發源。兩者都是嚴格 UTF-8 加 `jsonDecode`、要求最上層為 Map、讀同一 key `schema_generated_at_framework_version`，路徑常數同值。版本欄位非 String 時 gate 回 null（Unreadable，擋下）；建圖端 `schemaVersionOf` 的 `as String?` 在同情況會 throw，但 gate 已先擋，走不到
- 同型旁支（未做 runtime 驗證）：同路徑重選會把 `degradedSchemaProvider` 重設為 false，但舊的降級輪次（isDegraded=true）仍被沿用，Ready 畫面殘留降級徽章
- 未驗證：沒有用實機或 integration_test 重現（本票限唯讀）

### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` hits an environmental
failure that persists after re-running it, or is unavailable. Scope/criteria
rejections must NOT use fallback: stop and report to PM) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.

## 重現實驗結果
### 實驗方法

靜態讀碼追蹤：gate 呼叫點（`shell.dart` 啟動還原、`project_switcher_overlay.dart` 選取）→ `detect` → `DomainViewLoader.load` → `_obtainRound` → `ScanRoundNotifier.ensureRound`；逐行比對兩個讀取器的解析程式。

### 實驗執行

- `ensureRound()`：`state is ScanRoundCompleted` 時直接回傳 result
- `ScanRoundNotifier.build` listener：`prev.path == next.path` 時 return，不 discard
- `project_switcher_overlay` WorkspaceReady 分支：寫入同值 state、重設降級旗標後直接 `detect(path)`，不呼叫 discard／rescan
- `gap_report_provider`：首次可見呼叫 `ensureRound()`，輪次被保留

### 實驗發現

- 已驗證（程式碼路徑）：四步序列可確定性觸發 `_unavailableGraph`，不依賴 TOCTOU
- 已驗證：兩讀取器解析規則等價，非觸發源
- 未驗證：實機重現（唯讀限制）


## Solution
### 分析結論

生產路徑可以觸發（依據見 Problem Analysis 四步序列），結論為改設計。`_unavailableGraph` 的不變式前提「gate 已擋下」不成立：gate 每次重讀 JSON，建圖卻沿用快取輪次。

### 候選方案

| 方案 | 內容 | 優點 | 缺點 |
|------|------|------|------|
| A | gate 通過時丟棄陳舊輪次（同路徑重選時 discard，或 gate 通過後 rescan） | 修正快取陳舊根因，並修掉降級徽章殘留 | 涵蓋不到 gate 讀與輪次讀之間的 TOCTOU |
| B | `_unavailableGraph` 依 reason 映到 SPEC-001 §1 可見阻擋態（如 `DomainSchemaIncompatible`），移除 assert | 涵蓋所有分歧來源（含 TOCTOU）；錯誤載體為畫面，符合 tech-decisions 2026-08-27 裁決 | 單獨採用時，同路徑重選仍看到過期結果 |
| C | 建圖直接使用 gate 已讀的 JSON | 單一讀取來源 | 輪次由多個消費者共用（含缺口報告），需跨 domain 改所有權，成本最高 |

採 A + B：B 為防線，A 修根因。不採 C：A+B 後只剩毫秒級 TOCTOU，B 已涵蓋。

### 自檢結果

- 範圍斷言「兩讀取器解析等價」。範圍驗證方法：列舉法（逐行比對 `readSchemaJsonVersion` 與 `_readProjectSchemaJson`）。驗證指令：`grep -rn "projectSchemaRelativePath =" -A2 lib`（確認路徑常數同值）。已知盲區：測試注入的 fake 檔案系統行為。盲區影響評估：結論只涉及生產實作，不受影響
- 依賴方向：A、B 只動 app 與 screens 層，不違反 DAG

### Phase 4 評估
