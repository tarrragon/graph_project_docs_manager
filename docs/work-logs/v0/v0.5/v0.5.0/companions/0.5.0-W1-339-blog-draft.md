你有沒有遇過這種情況：兩個人（或兩個 AI 代理人）各自在處理完全不相干的需求，卻因為要改同一個檔案而必須排隊——一個人先改、先合併，另一個人再拉最新版、解衝突、重跑測試。下一週又有第三個需求要改這個檔，於是又排一次隊。

多數人把這當成「協調問題」：排好順序、加強溝通就好。但這個現象其實在告訴你一件更根本的事：**這個檔案承載了太多種職責。**

本章教你把「修改競爭」當成量測工具：用 git 歷史找出熱點檔，判斷它是不是真的該拆，再用不改變行為的方式把它拆開。

## 為什麼修改競爭是 SRP 訊號

單一職責原則（SRP）常被解讀成「一個模組只做一件事」，但「一件事」很難判斷。Robert C. Martin 給過一個更可操作的定義：

> 一個模組應該只有一個「改變的理由」。

這句話把抽象的「職責」換成了可以觀察的東西：**改變的理由**。而改變的理由，就記錄在版本歷史裡——每一次 commit 都是一次改變，每一個需求（票、issue、PR）都是一個理由。

| 現象 | 代表什麼 |
|------|---------|
| 同一個需求的多次 commit 都改同一個檔 | 正常。同一主題的演進集中在一處，這是內聚 |
| 三、四個**不相干的需求**都要改同一個檔 | 這個檔有三、四種改變的理由，也就是三、四種職責 |

所以「不同主題的修改反覆落在同一檔」，正是 SRP 定義的直接量測。

### 行數為什麼不夠

多數團隊用行數判斷檔案是否太大，例如超過 300 行就考慮拆。行數是有用的症狀，但它會漏掉兩種情況：

| 情況 | 行數判斷 | 修改競爭判斷 |
|------|---------|-------------|
| 200 行的骨架產生器，被 6 個不同需求改過 | 不會觸發 | 會觸發 |
| 900 行的解析器，只屬於同一個需求的連續演進 | 會觸發（誤判） | 不會觸發 |

行數量的是「大不大」，修改競爭量的是「雜不雜」。後者才是 SRP 在意的。

## 用 git 歷史量出熱點

只要你的 commit 訊息帶有需求編號（票號、issue 號），就能直接算出每個檔案被幾個不同需求改過：

```python
"""依 commit 訊息中的需求編號，統計每個檔案被幾個不同需求修改。"""
import collections
import re
import subprocess

ISSUE_ID = re.compile(r"#(\d+)")  # 依你的 commit 慣例調整


def collect_changes(since: str, path: str = ".") -> dict[str, set[str]]:
    log = subprocess.run(
        ["git", "log", f"--since={since}", "--no-merges",
         "--name-only", "--format=@@%s", "--", path],
        capture_output=True, text=True, check=True,
    ).stdout

    issues_per_file: dict[str, set[str]] = collections.defaultdict(set)
    current = None
    for line in log.splitlines():
        if line.startswith("@@"):
            match = ISSUE_ID.search(line)
            current = match.group(1) if match else None
            continue
        if line and current:
            issues_per_file[line].add(current)
    return issues_per_file


def report(since: str, top: int = 20) -> None:
    changes = collect_changes(since)
    ranked = sorted(changes.items(), key=lambda kv: -len(kv[1]))
    for path, issues in ranked[:top]:
        print(f"{len(issues):3d} 個需求  {path}")


if __name__ == "__main__":
    report("2 weeks ago")
```

有兩個細節要注意：

- **`--no-merges`**：merge commit 會把整條分支的改動列進來，不排除就會重複計數。
- **把子需求歸到同一個主題**：如果你的需求有父子關係（例如 `#120` 底下的 `#120.3`），要以根需求計數，否則同一主題的連續修改會被誤算成多個理由。

## 判斷：哪些熱點該拆

跑出排行榜之後，不是每個名列前茅的檔案都該拆。用下面這張表過濾：

| 熱點類型 | 例子 | 處理 |
|---------|------|------|
| 一般程式碼，被 3 個以上不相干的需求修改 | 一支同時負責「解析命令」「判斷狀態」「產生提示訊息」的模組 | **拆分評估** |
| 同一主題的連續演進 | 一個佇列模組，被同一個「排隊機制」需求的 5 張子票陸續修改 | 不拆，這是內聚 |
| 聚合檔：設定、註冊表、CHANGELOG、索引 | `settings.json`、外掛註冊清單 | 不以職責拆分，改用「一項一檔」或「只追加」格式 |
| 只有測試檔在競爭 | 一個大測試檔被多個需求加測項 | 先看它測的產品檔；測試通常隨產品檔一起拆 |

聚合檔要特別說明。註冊表的本職就是「集中列出所有項目」，每加一個功能就要登記一次，被很多需求修改是必然的。把它拆成三份註冊表，只會讓競爭換個地方發生。這類檔案的解法是降低每次修改的衝突面，例如每個項目一個片段檔、由載入端合併。

## 拆分前：先找出職責邊界

決定要拆之後，第一步不是動手切檔，而是**回頭讀那些修改**。把近期改過這個檔案的每個需求列出來，寫下「它改的是哪一種職責」：

```text
需求 A：修正命令解析遇到引號時的錯誤        → 命令解析
需求 B：新增「並行期間」的判斷條件           → 狀態判斷
需求 C：提示訊息改成指引使用者改寫命令       → 訊息產生
需求 D：解析器支援 -C 參數                   → 命令解析
需求 E：並行期間改依工作位置過濾             → 狀態判斷
```

把職責歸類後，每一類就是一個候選模組。這個例子分出三類：命令解析、狀態判斷、訊息產生。

如果歸類後只剩一類，代表競爭來自同一主題的連續演進，或這是聚合檔，回到上一節的過濾表重新判斷。

## 拆分 Python 模組的步驟

### 第一步：先用測試鎖住行為

拆分是純粹的結構調整，不應該改變任何對外行為。在動手前，確認對外行為都有測試覆蓋，特別是**邊界與反例**：

```python
import pytest

from guard import evaluate  # 拆分前後都從這裡匯入

@pytest.mark.parametrize("command, expected", [
    ("git commit -m 'msg'", "allow"),
    ("git -C /other commit -m 'msg'", "block"),   # 應擋的寫法
    ("echo 'git commit'", "allow"),               # 字串中出現的 git
])
def test_evaluate_behavior_is_unchanged(command, expected):
    assert evaluate(command) == expected
```

注意那筆「應擋的寫法」。如果測試只驗證正常情況會放行，拆分時不小心弄壞判斷，測試依然全綠，你看不出差別。

### 第二步：依職責萃取模組，保留原本的匯入路徑

把每一類職責的函式移到新模組，原模組改為從新模組匯入（re-export）：

```text
guard.py              ← 原本 1200 行，三種職責混在一起

guard/
├── __init__.py       ← 保留 evaluate 等對外名稱，呼叫端不用改
├── command_parse.py  ← 命令解析
├── state.py          ← 狀態判斷
└── messages.py       ← 訊息產生
```

```python
# guard/__init__.py
from .command_parse import parse_command
from .messages import build_block_message
from .state import is_parallel_period


def evaluate(command: str) -> str:
    parsed = parse_command(command)
    if parsed.is_commit and is_parallel_period(parsed.target_dir):
        print(build_block_message(parsed))
        return "block"
    return "allow"
```

原本 `from guard import evaluate` 的呼叫端完全不用改。等所有呼叫端都改用新路徑之後，再決定要不要拿掉 re-export。

### 第三步：重複的判斷收斂到共用模組

拆分時常會發現，同一種判斷在好幾個檔案各寫了一份，例如三支守衛各自實作「從命令中取出 ID」。這正是它們被同一個需求一起修改的原因：規則一改，三份都要跟著改。

把它收斂成共用模組的單一函式，各處改為呼叫它。之後規則再改，只需要改一個地方，也只會產生一次修改，不再是三次競爭。

### 第四步：巨型分支改成分派表

如果一個函式的主體是長長的 `if/elif` 鏈，每個分支處理一種情況，那麼每新增一種情況都要改這個函式，它就會變成永遠的熱點。改成分派表之後，新增情況只需要加一筆登記：

```python
# 改之前：每個新需求都要改這個函式
def handle(event):
    if event.kind == "commit":
        ...
    elif event.kind == "merge":
        ...
    elif event.kind == "rebase":
        ...

# 改之後：新增情況只需要加一個處理函式並登記
HANDLERS = {}

def register(kind):
    def decorator(func):
        HANDLERS[kind] = func
        return func
    return decorator

@register("commit")
def handle_commit(event): ...

@register("merge")
def handle_merge(event): ...

def handle(event):
    handler = HANDLERS.get(event.kind)
    if handler is None:
        raise ValueError(f"未知的事件類型：{event.kind}")
    return handler(event)
```

### 第五步：避免循環匯入

拆出來的模組只能依賴更底層的模組。如果 `state.py` 和 `messages.py` 需要互相呼叫，代表它們之間還有一塊共用的東西沒有抽出來，把那塊再往下抽一層（例如 `types.py`），讓兩者都依賴它。

### 第六步：搬移和修改分開提交

純搬移的 commit 不要同時修改行為。如果搬移和修改混在同一個 commit 裡，測試一紅，你分不出是搬錯了還是改錯了。先提交一個「只搬移、測試全綠」的版本，再在之後的 commit 修改行為。

## 拆完之後：讓等待中的工作改走新檔

拆分要排在那些正在等待的需求**之前**。拆分合併後，等待中的需求改以新版本為基準，各自只改自己職責所在的新檔：

```text
拆分前：需求 A、B、C 都要改 guard.py → 只能排隊，一個接一個
拆分後：A 改 command_parse.py、B 改 state.py、C 改 messages.py → 可以同時進行
```

這就是拆分的回報：原本只能排隊做的三件事，現在可以平行處理。

過一段時間後，再跑一次熱點統計，確認這個檔案（以及拆出來的新檔）的競爭需求數確實下降。如果某個新檔很快又變成熱點，代表當初的職責分類切錯了位置。

## 文字文件也一樣

這個方法不限於程式碼。規則文件、操作手冊、範本被不同主題反覆修改，同樣代表一份文件回答了太多種問題。文字文件的拆法：

| 原則 | 做法 |
|------|------|
| 依職責切，不依長度切 | 每份新文件只回答一種問題（何時做、怎麼做、為什麼） |
| 原檔保留路由 | 原檔留一張索引表，指向各個新文件 |
| 一條規則只定義一次 | 其他文件引用它，不複製內容，避免拆完變成兩份各自修改 |
| 更新所有引用 | 用 `grep -rl` 找出所有引用原檔或舊標題的地方，逐一更新 |

## 小結

- 「改變的理由」可以從版本歷史量出來：一個檔案被幾個不相干的需求修改，就有幾種職責。
- 排除兩種反例：同一主題的連續演進（內聚），以及聚合檔（改用一項一檔或只追加的格式）。
- 拆分前先用測試鎖住行為，而且要包含「應擋」的反例；拆分時保留原匯入路徑，搬移與修改分開提交。
- 拆分要排在等待中的工作之前，拆完讓各項工作改各自的新檔，原本得排隊的事就能平行進行。

## 思考題

1. 你的專案裡，哪個檔案最常讓兩個人同時想修改？用本章的腳本跑一次，結果和你的直覺一致嗎？
2. 一個註冊表檔案被 10 個需求修改過。為什麼拆成兩個註冊表無法解決問題？你會怎麼降低它的衝突？
3. 如果拆分後，拆出來的其中一個新檔很快又變成熱點，這代表什麼？

## 實作練習

1. 修改本章的熱點統計腳本，讓它把有父子關係的需求（例如 `#120` 與 `#120.3`）歸到同一個根需求計數。
2. 挑一個你專案中被 3 個以上不相干需求修改過的模組，依「拆分前：先找出職責邊界」一節列出每次修改的職責，寫出你會拆成哪幾個模組（不必真的動手拆）。
3. 為該模組補一組行為測試，至少包含一筆「應被擋下或應回報錯誤」的反例，再思考：如果你在拆分時弄錯了，這組測試抓得到嗎？
