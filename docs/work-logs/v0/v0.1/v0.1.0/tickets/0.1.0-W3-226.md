## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

session-start 稽核連續多日對 6 張 closed 票報「closed_by 非合法 Ticket ID」。追查後確認不是單一缺陷，而是三個可分離的缺陷疊在同一則警告上。

直接原因是值域拒絕（D3）：`.claude/lib/ticket_id_pattern.py` 的 `FULL_ANCHORED_RE` 只表達本專案的 `版本-W波次-序號` 形態，`flutter_balance:W4-007` 落在其外。

但值域為何會被塞進不合法的值，答案在建立端（D2）：`lifecycle.py` 的 close 前置驗證依 reason code 分歧，`ALLOW_NONE` 側對 `resolved_by` 零驗證。寫入無阻擋、讀取必報警，兩端值域從未對接。

而操作者為何會選到 `ALLOW_NONE` 側的 reason code，答案在枚舉（D1）：6 張的實際語意是「移交另一個 consumer 執行」，`close_reason` 枚舉不涵蓋這個情境，最近似項是 `cancelled_by_user`——而它正好在 `ALLOW_NONE` 側。

三者是一條因果鏈：**枚舉缺項 → 操作者選近似項 → 該項所在分支無驗證 → 不合法值寫入 → 讀取端永久報警**。只修任一環都不完整：只放寬值域，自由文字照樣寫得進去；只補驗證，操作者仍無合法的移交表達方式可用。

### 影響範圍

本專案：6 張票（`0.1.0-W1-011` / `012` / `019` / `020` / `029` / `040`），每 session-start 固定 6 行噪音；以 `close_reason` 聚合的任何盤點會把移交算成取消。

跨 consumer：三個缺陷的載體皆為隨 sync 分發的框架資產。另一 consumer 已有 20 張票命中同一則警告（值形態不同，見 #60）。共用框架資產的跨 consumer 移交是本框架 multi-consumer 架構的結構性情境，走得越勤命中越多。

### 相關 Error Pattern

`PC-MON-002`（必填不等於有效——CLI 必填欄位無值驗證，自由文字穿透防護）。本案為其行為模式的再現而非重複：該 pattern 的修復把三層驗證加在 `resolved_by` 的 `REQUIRE_TICKET_ID` 側，堵住了自由文字通道；但「欄位語意不適用當下情境就選語意近似值」這個行為傾向未被消除，轉移到了 reason code 枚舉上。

枚舉載體比自由文字更難察覺：自由文字的違規值一眼看得出不是 ticket ID，枚舉的違規值是合法成員，任何格式驗證都會通過——不讀 note 就分不出「取消」與「移交」。該 pattern 的預防措施三問清單目前只涵蓋自由文字欄，未涵蓋「枚舉是否涵蓋全部合法情境」，此缺口已寫入 #106 的關聯節。

### 對 #60 的實質修正（本票的主要產出）

#60 body 把建立端診斷為「framework-issue/SKILL.md 從未規範 closed_by 填法」。該描述成立但不是值能寫進去的原因，照它修不會關掉洞：

- 真正的寫入路徑是 lifecycle.py 的分歧驗證。REQUIRE_TICKET_ID 側（superseded_by / duplicate）驗格式且驗存在；ALLOW_NONE 側（requirement_vanished / cancelled_by_user）對 resolved_by 零驗證
- 故 #60 的建議方向「放寬值域 + SKILL.md 補填法」若照做，洞仍在——落在新值域內的值不報警，落在外面的自由文字照樣寫得進去、照樣每 session 報警
- 正確的兩端是「guard 值域 + close 對 ALLOW_NONE 分支補值驗證」；SKILL.md 屬引導層，不構成執法

第二項修正是放寬對象有兩類、性質相反：framework issue ref 可解析可驗證，跨 consumer ticket ID 兩者皆不能。以單一字元類一併放寬，等於由值域規則主動授權一類永遠無法滿足參照完整性的引用進入 closed_by——正是 PC-MON-002 判定為缺陷的形態。已列三個方向供上游取捨（只放寬 issue ref／分層標示／移交一律轉譯為 issue ref），未主張哪個。
