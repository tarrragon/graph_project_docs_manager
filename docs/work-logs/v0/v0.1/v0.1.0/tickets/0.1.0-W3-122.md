### Task Reference
- 0.1.0-W3-096 what: 修復 破洞掃描以 microtask 完成，使掃描中骨架與系統通知觸發條件皆結構性不可達

### Rationale Chain
- 0.1.0-W3-096 why: 實機執行時，用戶按下重新掃描後**沒有授權對話框、沒有任何載入提示或動畫**，`flutter run` 的 runtime log 自 App 啟動起零輸出（`MacosScanNotifier` 的授權查詢 log 從未觸發）。

機制（PM 已讀原始碼確認）：`gap_report_provider.dart` 的 `_scheduleScan()` 是 `Future.microtask(_completeScan)`——掃描在**同一幀的 microtask 內完成**。由此推出兩件事：

1. **`state-gaps-scanning` 骨架存在時間短於一幀**，畫面上不可能看到。SPEC-003 §3.5 明訂「重新掃描時現有結果立即被骨架取代」，該骨架實際從未被繪出。
2. **系統通知的觸發條件結構性不可達**。SPEC-003 §2.2 的觸發條件是「完成當下視窗非前景，或可見頁非 `nav-page-gaps`」。完成發生在按鈕點擊的同一個 microtask 內，而按鈕點擊必然發生在視窗前景且使用者正看著破洞報告頁——**兩個條件都不可能為真**。授權因此永不請求（`notDetermined` 僅於首次觸發時請求），通知永不發送。

後果分三層：

- `0.1.0-W3-078` 要驗的四項平台事實中，至少三項（授權可用性、未簽章 build 的授權回應、撤回 API 效果）**在此實作下無法以任何操作觸達**，實機驗證無從進行。
- SPEC-003 §2.2 整節（觸發條件、不發送情境、權限 gate 三路徑、撤回三時機）與 §3.5 的骨架列，在現行實作下皆為**描述了一個不會發生的情境**的規格。
- `test/` 的 fake 直接設定狀態與 provider 值，繞過真實的完成時機，因此沒有任何測試會察覺這件事——與 `0.1.0-W3-094`（固定高度裁切）同屬「測試綠燈但實機不成立」。

**這不是說掃描應該變慢**。真實掃描（讀取檔案、解析 frontmatter）本來就需要時間；問題在於現行實作以 fixture 常數取代掃描，把耗時降為零，順帶讓所有依賴「掃描期間」的規格行為失去存在空間。
