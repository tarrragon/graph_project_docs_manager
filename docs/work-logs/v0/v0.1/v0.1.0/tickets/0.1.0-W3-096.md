### 問題根因

票面前提需修正：**通知觸發條件不是結構性不可達，而是在錯誤時機可達、在規格描述的時機不可達。**

拆成三個彼此獨立的缺陷：

| # | 缺陷 | 類別（how.strategy 的 a/b） | 本波可修？ |
|---|------|---------------------------|-----------|
| D1 | 掃描觸發點掛在 `GapReportNotifier.build()`，而 provider 的首次讀取者是 App 啟動時的 `ScanNotificationController.start()`，非「首次可見 `nav-page-gaps`」 | (a) 實作缺陷 | 是 |
| D2 | fixture 常數取代真實掃描，耗時為零，`state-gaps-scanning` 骨架存活短於一幀 | (b) 階段落差 | 否 |
| D3 | `rescan()` 路徑下 §2.2 觸發條件皆不成立 | D2 的下游 | 否（隨 D2 解） |

#### D1：掃描在 App 啟動時就跑完，不是在首次可見時

證據鏈：

1. `lib/screens/gap_report/gap_report_provider.dart` 的 `build()` 呼叫 `_scheduleScan()`。
2. `gapReportProvider` 的首次讀取者是 `lib/app/shell.dart:56-60` 的
   `ScanNotificationController(ref, () => context)..start()`，位於 `_AppShellState.initState`
   ——即 **App 啟動**，早於使用者點 `nav-item-gaps`。
   （`lib/screens/gap_report/gap_report_screen.dart:26` 的 `ref.watch` 是第二個讀取者。）
3. `lib/app/router.dart:134` 的 `firstVisibleProvider` 已建立且有單元測試
   （`test/unit/app/router_test.dart:81`），但 **`lib/` 內無任何消費者**
   （`grep -rn firstVisibleProvider lib/` 只命中 router.dart 自身與 gap_report_provider.dart
   的一句 doc comment）。SPEC-003 §2.8「不得以首次建構作為觸發訊號，須以首次可見觸發」
   的機制造好了但沒接線。

由此推導（**推導結論，未經執行驗證，見下方 NeedsContext**）：App 啟動後的第一個
microtask 內，`state` 由 `GapReportScanning` 轉為 `GapReportFound`，
`ScanNotificationController._onGapReportStateChange` 命中
`previous is GapReportScanning && completed` → `_evaluateCompletion`；
此時 `appLifecycleStateProvider` 為初值 `resumed`（`lib/app/app_lifecycle.dart`）、
`selectedDestinationProvider` 為預設 `domain`，故 `_isVisibleForeground()` 回 `false`
→ **§2.2 觸發條件 (b)「可見頁不是 nav-page-gaps」在 App 啟動當下即成立** →
`authorizationStatus()` 被呼叫，`notDetermined` 時進而 `requestAuthorization()`。

亦即現行實作不是「不發通知」，而是「使用者還沒看過破洞報告頁就先收到掃描完成通知
／授權對話框」。這與票面 why 記載的實機觀察（零 log、無對話框）不一致，落差需以
實機或測試釐清（NeedsContext 第 2 項）。

#### D2：fixture 零耗時使骨架與 cross-fade 不可觀察

`_missingFrontmatterItems` 是常數，`_completeScan` 在同一 microtask 內完成。
SPEC-003 §3.5 動畫提示表的「掃描中骨架」「掃描中 → 無破洞／有破洞 cross-fade」
「重新掃描：現有結果立即被骨架取代」三列，在 fixture 階段皆不可觀察。
此為 W2 波次既定範圍（W2-001 等票明寫「以 fixture 驅動，不串真實資料」），
屬 how.strategy 的 (b)。

#### D3：修好 D1 之後，§2.2 在 fixture 階段才真的不可達

D1 修好（改以首次可見觸發）後，兩條掃描路徑都會落在「使用者正看著 gaps 頁、視窗前景」：
首次可見觸發時使用者剛切到該頁；`rescan()` 觸發時使用者正按該頁的按鈕。
兩者完成皆在同一 microtask 內，§2.2 觸發條件 (a)(b) 皆不成立 → 不發送。
因此 §2.2 整節的可達性繫於 D2，不是獨立問題。
