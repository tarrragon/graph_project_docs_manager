## Solution
### 靜默的界定

Q5 的「靜默」= 不記日誌且不通知使用者（依據見重現實驗結果）。只談「對使用者不顯示」屬「日誌」選項，不需要本判準。

### WRAP 摘要

- W 候選（三類涵蓋）：
  1. 原草稿三條件照落（新增條文）。
  2. 純路由：Q5 補一句路由 `observability-rules.md` 規則 1 註解出口（改造既有，零新判準）。
  3. 修正草稿：三條件 AND，判定詞改為可從規格逐字觀察的形式，並強制帶規則 1 註解出口（新增條文 + 路由）。
  4. 刪除「靜默」選項與反面範例，正常路徑一律 debug 日誌（零工具）。
- R：候選 2 只回答「選了靜默怎麼合規」，不回答「何時可選」，反面範例的判定「靜默即可」仍推不出，F-28 未解。候選 1 判準詞「無副作用」「合法業務狀態」「其他機制」屬撰寫者主觀判斷，依 chained-examples 第 3 項為橋接，範例仍不合格；且未帶註解要求，與規則 1 部分衝突。候選 4 無衝突，但刪除既有選項屬變更範圍超出本票（F-28 只要求補判準），且把非異常的正常分支也拉進日誌，與 Q5 觸發條件「功能包含 catch/error handling 時必答」的範圍不符。
- AND／OR：須 AND。反例：純讀取的設定檔讀取失敗回預設值，只滿足 (a)；若 OR 成立即可靜默，操作者永遠不知設定檔損壞。(a)(b) 成立而 (c) 不成立（呼叫端未處理空結果）時，失敗轉移到下游成為無日誌的崩潰。(a) 相對 (b) 有部分冗餘，但保留作為資料遺失的保守防線。
- A：本判準只擋 W2 閘門一項，機會成本低；候選 3 改一句＋一則反例，不擴大範圍。
- P：最可能失敗——撰寫者把「規格正常流程」寫得過寬（把錯誤也列為正常結果）以取得靜默。早期警訊：規格正常流程中出現「失敗」「錯誤」「例外」字樣的結果列。防線已在條文內（(b) 以規格自身為準，審查者可逐字查）。

### 判定

採候選 3（修正草稿）：三條件 AND 成立，但須 (1) 判定詞改為可從規格與程式逐字觀察的形式，(2) 明文帶規則 1 註解出口，否則與規則 1 衝突。不採原草稿照落，也不採純路由。

### 改文草稿（`.claude/skills/tdd/references/phase1/rules.md` Q5〈行動路徑〉句後補，未落檔）

> 「靜默」指不記日誌且不通知使用者。僅在以下三項同時成立時可選靜默，任一項不成立即選日誌，catch 後回傳預設值者記 warning：(a) 該操作不寫入任何持久狀態；(b) 該結果列在本規格的正常流程中；(c) 呼叫端對該結果有處理分支。選靜默時，catch 區塊須以註解說明靜默原因（`.claude/rules/core/observability-rules.md` 規則 1「禁止，必須加日誌或在註解中說明靜默原因」）。

判定詞逐詞對照（供後續範例引用）：

| 判定詞 | 可觀察來源 |
|---|---|
| 不寫入任何持久狀態 | 功能規格的操作描述（讀／寫） |
| 列在本規格的正常流程中 | 規格正常流程段，逐字查結果名稱 |
| 有處理分支 | 呼叫端規格或程式對該回傳值的分支 |
| 註解說明靜默原因 | 規則 1 逐字 |

判「否」反例輸入（建議補入 Q5 範例）：

- 輸入：讀取使用者設定檔失敗時 catch 並回傳預設設定；規格正常流程只列「讀取成功」；呼叫端直接使用回傳值。
- 推導：(a) 成立（純讀取）；(b) 不成立（「設定檔讀取失敗」未列在正常流程）；(c) 不成立。任一項不成立 → 不可選靜默 → catch 後回傳預設值，依規則 1 記 warning 日誌。
- 對照正例：既有反面範例「純讀取操作的快取 miss」在規格正常流程列有「快取 miss 時回到來源讀取」時，(a)(b)(c) 皆成立 → 可靜默，catch 內附註解說明原因。落檔時建議把該範例補上「規格正常流程列有快取 miss 分支」的前提，否則 (b)(c) 從範例輸入無法逐字判定。

### 是否屬用戶偏好

**不屬用戶偏好**。三條件由規則 1 的註解出口與 Q5 自身觸發範圍推得，候選 3 與候選 4 的取捨屬框架條文設計（是否保留靜默選項），由 PM 裁定即可，不需上呈用戶。
