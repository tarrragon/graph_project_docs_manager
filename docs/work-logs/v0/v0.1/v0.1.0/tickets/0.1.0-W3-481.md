### 三處改寫前後對照

### 1. bdd-behavior-testing.md〈判定不拆分 Module〉條件 2

前：
> 計入 Given 設置行數的每一行替身設置，都屬於該 UseCase 某個流程步驟會呼叫的外部依賴。沒有任何流程步驟呼叫的外部依賴時：建構受測對象不需要它，其設置行先刪除、不計入行數；建構受測對象需要它，本條件不成立。

後：
> 計入 Given 設置行數的每一行替身設置，都屬於該 UseCase 某個流程步驟會呼叫的外部依賴——範圍是該 UseCase 的全部流程步驟，不是被判定的單一場景實際執行到的步驟；失敗場景提前結束而未走到的依賴，仍算「會呼叫」。判定順序：先確認該依賴是否為該 UseCase 任一流程步驟會呼叫者；判定為「否」時，才依序檢查兩分支：(1) 建構受測對象不需要它——其設置行先刪除、不計入行數；(2) 建構受測對象需要它——本條件不成立。

### 2. doc-handoff.md〈前置閘門〉「涉及 UI」判定句

前：
> 場景步驟的操作或預期結果落在第一列「圖形介面」即涉及 UI，第二、三列不觸發本檢查項；步驟未寫明呈現通道時，先回 doc 補寫通道再判定。

後：
> 場景步驟的產物（使用者最終查看或操作的對象）落在第一列「圖形介面」即涉及 UI，第二、三列不觸發本檢查項；步驟在應用程式內的觸發動作（按下按鈕、選單等）不單獨作為判定依據——否則任何有 app 內入口的步驟都會落入第一列。步驟未寫明呈現通道時，先回 doc 補寫通道再判定。

### 3. doc-handoff.md〈前置閘門判定範例〉一致性附帶修正（同段落，非票面三項之一）

同檔案第 72 行決策表「依據」欄、第 80 行檢驗問句，原文皆重複「操作或/與預期結果落在第一列」舊措辭。若不同步修改，會與上述第 2 項修正後的定義句在同一節內互相矛盾，讓讀者對照範例時看到兩種不同的判準敘述。已改為「產物」措辭，**兩處原判定結果皆維持「是／涉及 UI」不變**——該範例步驟的產物（切換後的詳情畫面）本就落在第一列，重寫前後結論同構，純屬措辭對齊，不構成第 4 項判準改變。
