## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
`dispatch-validate` 規則 4 拆為兩個子檢查：4a（既有的項數 >= 3，維持軟性）、
4b（新增樣板偵測，硬性）。4b 判準有二：(1) 條目含大括號佔位符 token（正則
`\{[A-Za-z_][A-Za-z0-9_]*\}`，只匹配單一識別字如 `{feature_name}`/`{N}`，
不匹配任意含大括號的正常內容，避免誤擋）；(2) 剝除 checkbox 前綴後與建立端
`ticket_system.lib.ticket_builder.DEFAULT_ACCEPTANCE_CRITERIA`（攤平七個
ticket 類型的預設樣板為單一 frozenset）逐字相同——補足 DOC 型第 2、3 條等
不帶大括號的樣板。驗證端未複製樣板字面，直接 import 建立端常數，無迴圈依賴。

exit code 契約更新：硬性規則由「僅規則 1」擴為「規則 1 或規則 4b」，兩者同時
違反時（未填樣板的票通常同時缺 Context Bundle）訊息列出所有命中的硬性規則

**PM 補充二：規則 4 應升為硬性（建票 session 定見，2026-09-08）**

上文把「規則 4 該不該從軟性升為硬性」列為執行者判斷項。建票 session 已表態，預設方向為**升硬性**，理由如下（執行者仍須在 Solution 獨立論證一次，此定見不取代其判斷）：

軟性規則現有三條——閾值 1 職責數、規則 2 Context Bundle 長度、規則 3 檔案存在——它們說的都是「這張票可能不好，你自己看」，判斷帶啟發式成分，誤報有實際成本，所以該軟。

但「acceptance 仍是未填的預設樣板」不是品質建議，是事實陳述：**這張票沒有可驗收的目標。** 派出去之後，代理人會對著一個沒有內容的目標宣稱達成，驗收方讀到勾選的三條也看不出異常（形態見 `PC-GPD-008`）。偵測到卻放行，等於把已知不可執行的票送出去。

且本判準幾乎沒有誤報空間：判準是「與建立端樣板逐字相同」，逐字相同就是沒填，沒有中間地帶。**啟發式規則該軟，確定性規則該硬。**

實作上須確認：升硬性後 `dispatch-validate` 的 exit code 契約（0 pass / 1 warn / 2 fail）如何反映——現行硬性只有規則 1，兩條硬性規則同時失敗時的輸出與 exit code 須有明確行為，並納入測試。

**exit code 契約的補充（建票 session 觀察）**：「兩條硬性規則同時失敗」不是邊角案例而是常態——未填樣板的票通常同時缺 Context Bundle（規則 1 硬性失敗），`0.1.0-W3-089` 與 `0.1.0-W3-087` 兩張建票當下正是如此。該測試案例不是為完備性而寫，是主要路徑。
