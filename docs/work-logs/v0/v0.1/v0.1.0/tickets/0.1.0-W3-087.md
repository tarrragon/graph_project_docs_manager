## Context Bundle

**需求摘要**: 讓 `dispatch-validate` 規則 4 除了數條數，還要辨識「未填的預設樣板」acceptance；樣板字面取自建立端，不在驗證端另建副本。

**where.files 已修正（PM 派發前查證）**

票面原列 `commands/track_dispatch.py` 與 `tests`（目錄）。規則 4 不在該檔——已改為實際實作檔與對應測試檔。原路徑存在，故規則 3 當時通過而未揭露此錯置。

**規則 4 實作現況（已驗證：`grep -rn "check_acceptance_count"`）**

- `commands/track_dispatch_validate.py` L112-120 `check_acceptance_count(acceptance, *, min_items=_MIN_ACCEPTANCE_ITEMS)`——函式體只有 `len()` 比較，無內容檢查
- 同檔 L200 為唯一呼叫點；L209 印出 `規則 4 acceptance 項數`
- 規則 1 為硬性（失敗即 exit 2），規則 2/3/4 為軟性，規則 5 fail-open。**規則 4 改為 FAIL 時，須確認它是否應升格為硬性**——票面 acceptance 第 1 條寫「使規則 4 FAIL」，但軟性 FAIL 不阻擋派發，等於偵測到了卻放行。此處需執行者判斷並在 Solution 寫明結論

**建立端權威來源（已驗證：`grep -rn "指定功能"`，唯一命中）**

`.claude/skills/ticket/ticket_system/lib/ticket_builder.py` 的模組級常數 `DEFAULT_ACCEPTANCE_CRITERIA`（約 L197 起），dict 以 ticket type 為鍵，值為字串 list，現含 IMP / TST / ADJ / RES / ANA / INV / DOC 七鍵。驗證端應 import 此常數，不得抄寫字面。

**佔位符偵測抓不全（已驗證，逐字引自建立端）**

DOC 型三條樣板中，只有第一條帶大括號：

| # | 樣板字面 | 有大括號？ |
|---|---------|-----------|
| 1 | `文件內容完整：包含標題、背景、正文、結論、附錄等 {N} 部分` | 是 |
| 2 | `格式符合規範：遵守 CLAUDE.md 的文件格式規則` | 否 |
| 3 | `內容無遺漏：所有預期的小節都已填寫（無 TODO 或空白區段）` | 否 |

RES 與 ANA 型的多數條目同樣不帶大括號。因此判準必須以「與建立端樣板逐字相同」為主，大括號偵測只是補充——票面 why 已指出這點，此表是它的實測佐證。

（同儕交付訊息把第 2 條記為「遵守入口文件的文件格式規則」，實際字面為上表所示；以建立端為準。）

**約束**

- 本專案的 ticket CLI 為多 session 共用。派發時機由 PM 控制，執行者不需考慮，但**修改後務必跑一次 `uv run pytest` 全綠再收尾**——這支 CLI 是所有並行 session 的作業工具，紅燈會立刻擴散。
- 驗證端 import 建立端常數屬正確方向（`tool-output-trust-rules` 規則 6：判定順序為 canonical 常數 > 驗證端清單 > 文件描述）。若 import 造成迴圈依賴，於 Solution 記錄並改用其他不複製字面的手段。
- acceptance 第 4 條（選填章節留樣板是否需訊號）是**評估項不是實作項**：結論寫入 Solution；若判定要做，`ticket track add-spawn-request` 上報 PM 裁決，不在本票擴大範圍。

**未知（待執行者判斷，不採信本節推論）**

票面 why 段落末尾提到的另一個做法——讓預設樣板故意只給兩條、使其必然低於門檻三條，未填就被既有條數檢查擋下——不在本票範圍。該做法改的是建立端行為，會影響所有 consumer 專案，PM 傾向另開票處理。執行者若在實作中發現偵測路徑有本質障礙，於 Solution 記錄後上報，不自行切換方案。
