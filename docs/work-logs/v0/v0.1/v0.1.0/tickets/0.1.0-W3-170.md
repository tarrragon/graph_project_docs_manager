### Task Reference
- 0.1.0-W3-167 what: 設計 提示元件的使用時機、重疊處置、類型分化，與不可見時的日誌補位
- 0.1.0-W3-169 what: 盤點 全部 SPEC 的狀態提示設計，補提示元件需求與提示訊息設計

### Rationale Chain
- 0.1.0-W3-167 why: **用戶裁示（2026-09-09）**：「也要額外評估一個問題，哪些時機要呼叫 snackbar 或者 bottoast 這類提示元件，**如果大量呼叫提示元件，反而會重疊遮蔽**，那有可能需要依照不同類型的提示需求，設計使用不同的提示元件，以及**如果提示元件看不到，我們要在哪些事件或者流程上要補 log**。」

`0.1.0-W3-166` 固化「有顯示就要有紀錄」，但不回答「何時該顯示」。兩者一起才完整：只有前者會導向「凡事都跳提示」，而提示互相遮蔽時，**資訊反而比不提示更少**——後出現的蓋掉前一則，使用者兩則都沒讀完。

**這不是假設性風險。** 本專案目前 `AppSnackBar` 有 6 個呼叫點（實查，分佈於 `shell.dart`／`gap_report_screen.dart`／`scan_notification_controller.dart`），而 `0.1.0-W3-113`（`ScanNotificationController.show` 失敗的 SnackBar fallback）與 `0.1.0-W3-165` 都會再增加觸發時機。編輯能力（`0.1.0-W3-073`）落地後還會更多。

**第三個子問題是前兩者的必然對偶**：一旦決定某些時機不顯示提示（避免遮蔽），那些事件就失去了使用者可見的回饋，此時可觀測性必須由日誌承接——否則等於用「安靜」換掉了「有紀錄」，兩頭皆空。`0.1.0-W3-078` 的實機驗證正是撞上這個：路徑走到了、程式做了對的事，但沒有任何一側留下使用者層級的證據。
- 0.1.0-W3-169 why: **用戶裁示（2026-09-09）**：「檢查所有 SPEC 當中對於狀態提示的設計，加入相關提示元件的需求以及提示訊息的設計。」

狀態提示的設計目前**散在三份 SPEC**，各自回答不同的一半：

| SPEC | 目前承載 | 缺的 |
|------|---------|------|
| SPEC-001 畫面狀態矩陣 | 有哪些狀態、各狀態的退出路徑 | 狀態**轉換**時是否需要提示、需要哪種 |
| SPEC-003 互動反應 | §2.2 三層回饋、§2.12 服務類型與等待期政策、§2.6 等待指示形式 | 提示載體的選擇判準（何時用暫態提示而非狀態轉換本身） |
| SPEC-004 元件庫 | §1 回饋通道子表、§4.26 `AppSnackBar` 條目、逐元件回饋契約 | 提示訊息的設計要求（文案結構、i18n key 命名、可讀性保障） |

**只改其中一份的後果是三者對同一件事給出不同答案。** 本專案已有先例：`0.1.0-W3-108` 補 SPEC-003 §2.12 時發現 §2.2 既有的三層表是形式軸、新增的是歸屬軸，兩軸並存而不對接會使讀者無法判斷承擔者——當時靠 PM 在 acceptance 補了一條才接上。三份 SPEC 之間的落差比一份之內更難察覺。

**「提示訊息的設計」是目前完全沒有規格的一塊。** SPEC-003 §2.2 有零星的 i18n key 清單（`scanCompleteSnackbarMessage` 等），但沒有任何條文規範提示文案本身該長什麼樣——該含哪些成分、多長、如何處理 placeholder、失敗訊息與成功訊息的措辭差異。`ux-design-evaluation` 有「關鍵回饋文字要有版面保障」（flex 寬度競爭把關鍵資訊壓成刪節號，state 正確而使用者零資訊），那是跨專案判準，本專案未落地。
