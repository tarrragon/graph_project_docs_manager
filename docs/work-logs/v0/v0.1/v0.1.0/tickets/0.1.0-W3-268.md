why: '`PC-GPD-020`（明示的意圖與明示的失敗，在可觀測面與預設或成功不可區分）歸納出七個實例。該 error-pattern 記錄的是**知識**，本票要落地的是它衍生出的**兩條可機械檢查的設計要求**——兩者載體不同，前者按需讀取、後者須進測試設計規則才會在寫測試時被想起。


  **查證結果：兩條在 `.claude/rules/`、`.claude/references/`、`.claude/methodologies/` 全域零命中。**


  **第一條，明示旗標的對照測試。** 只斷言「傳了旗標之後產物正確」的測試，在旗標完全無效時照樣全綠——因為它沒有比較對象。實例：`test_no_topic_writes_no_assignment` 以 `_make_args(no_topic=True)` 呼叫，fixture 不帶 `source_ticket`，走不到會產生差異的 S1 繼承路徑；該路徑上 `no_topic` 為真或為假結果相同，於是測試覆蓋的正好是旗標不改變任何結果的情境。修法是同批各跑一次傳與不傳，斷言**產物不同**。


  **第二條，守衛的正向對照輸入。** 守衛的失效方向是放行，而放行與「本來就沒問題」在輸出上同形。只給正常輸入的測試無法分辨守衛在工作還是守衛已死。實例：靜態守衛的註解剝除器剝過頭，使多數計數斷言變綠——守衛失效且無聲。修法是測試必須含一個**已知該紅的輸入**並斷言它確實紅。


  **為何這兩條值得從 pattern 升格為規則**：`PC-GPD-020` 的七個實例中，沒有一個是靠它自己的測試被發現的——三個靠執行者花整輪定位、兩個靠 Phase 4a 專門去查、兩個靠並行 session 實測。這不是巧合而是定義使然：失效方向為成功的機制，其自身測試若只走正向路徑就必然全綠。**要發現它只能從外部給一個已知該紅的輸入**，而這件事現在完全依賴審查者的個人警覺，沒有任何條文要求。


  **邊界**：既有規則 D1～D5 治的是「斷言結果依賴程式以外的可變因素」（機器負載、網路、時區），本二條治的是「斷言對目標功能無鑑別力」。兩者不同軸，一個斷言可以完全穩定（永不 flaky）而同時完全沒有鑑別力。'

**變更摘要**：`.claude/rules/core/test-assertion-design-rules.md`（v3.1.0 -> v3.2.0），單一檔案。

1. 新增章節「鑑別力規則（跨語言，E 系列）」，置於 Dart 規則 D4 之後、延伸路由之前。章首兩段：鑑別力定義（目標功能失效時該斷言會翻紅的能力）、與 D1～D5 的軸差異（前者治斷言受程式以外可變因素干擾，後者治斷言對目標功能無鑑別力；一個斷言可完全穩定而同時完全無鑑別力，兩軸各自檢查，通過其一不代表通過另一）。
2. 規則 E1「明示旗標必須有對照測試」：同批 fixture 各跑一次傳與不傳、斷言產物不同；只斷言「傳了旗標之後產物正確」不合格。附已發生實例 `test_no_topic_writes_no_assignment`（fixture 不帶 `source_ticket`，走不到會產生差異的繼承路徑，旗標即使完全無效測試仍全綠）。Action 補一句：構造不出差異 fixture 代表測試選錯輸入，而非該旗標不需對照。
3. 規則 E2「守衛的測試必須含正向對照輸入」：測試須含已知該紅的輸入並斷言其為紅；只斷言正常輸入通過不合格。附已發生實例（靜態守衛的註解剝除器剝過頭，把應納入計數的內容一併剝去，使多數計數斷言變綠，守衛失效且無聲）。Action 補一句：守衛判準擴充時同批補落在新判準內的該紅輸入，否則新判準零覆蓋。
4. 延伸路由增列一行指向 `PC-GPD-020`（E1／E2 的知識來源：七個實例中無一靠自身測試被發現）。
5. 檢查清單增列兩項（E1／E2）。
6. 順帶修正：延伸路由既有一行的「實驗數據」改為「實驗資料」（language-constraints 規則 2 禁用詞，屬既有內容，同檔一併修正）。
