## Context Bundle

**需求摘要**: `dispatch-validate` 新增一條規則，派發前偵測 `who` 指派的代理人是否具備該票所需工具。

**三次命中的實據（已驗證：`sed -n '1,12p' .claude/agents/saffron-system-analyst.md`）**

```
name: saffron-system-analyst
description: TDD 前置審查專家。在 TDD 開始前審查系統一致性、檢視/撰寫需求文件、...
tools: Read, Grep, Glob, LS, Bash, mcp__serena__*
```

`description` 明寫「撰寫需求文件」，`tools` 不含 Write／Edit。**兩者互相矛盾，而沒有任何機制檢查這件事**——建票者依 description 指派完全合理。

三張票分別要改寫測試設計文件、撰寫 SPEC-003 條文、撰寫 SPEC-004 條文，皆需寫檔；三次都由 PM 在派發前逐票覆核發現並改派。

**現有五條規則沒有一條看 `who`**（已驗證：`commands/track_dispatch_validate.py` 的 `check_section_present` / `check_content_length` / `check_where_files_exist` / `check_acceptance_count` / `check_acceptance_uc_alignment`，加上 087 新增的樣板偵測）。

**與 087 的關係**：087 剛把規則 4 拆為 4a／4b，其中 4b 為硬性。本票新增的規則須決定編號與嚴格度，**並與 087 建立的 exit code 契約相容**——該契約現支援多條硬性規則同時違反時列出所有命中項，新規則若為硬性須併入該機制而非另建一套。

**嚴格度的取捨（本票最需要判斷的一項）**

誤報成本高於漏報。擋下一張其實可行的票，會讓使用者學會繞過整條規則——而規則被繞過之後，它連漏報都不做了。三種邊界都可能造成誤報：

| 邊界 | 風險 |
|------|------|
| agent 定義不存在 | 讀不到 tools，不可據此判定為「缺工具」 |
| `tools` 為萬用字元或以 All tools 描述 | 部分 agent 定義如此，逐字比對會誤判為缺 |
| 唯讀型票（部分 ANA） | 確實不需寫入，要求寫入能力即為誤報 |

**判定來源的候選**（擇一或組合，須論證）：`where.files` 非空即需寫入能力／依 `type`（DOC/IMP 需寫入、ANA 未必）／兩者組合。

**約束**

- 目標檔在 `.claude/` 之下，命中派發豁免（`agent-dispatch-validation-hook.py` L20「僅主 repo `.claude/` → 不要求」），**不要加 `isolation: "worktree"`**。
- 這支 CLI 是多個 session 共用的作業工具，且執行者自己也會呼叫它（`claim` / `append-log` / `complete`）。改完立刻跑測試，不要停在半改狀態（`PC-GPD-010`）。

**未知（待執行者判斷，不採信本節推論）**

本票只加偵測。`saffron-system-analyst` 的 `description` 與 `tools` 本身矛盾——該修 description（收窄為「檢視」不含「撰寫」）或補 tools（加 Write／Edit），屬 agent 定義的範疇，不在本票。若判定該修，登記 spawn request 交 PM，不自行改 agent 定義。

**PM 補充：只比對 `tools` 是否含 Write／Edit 會漏掉來源實例（2026-09-09，實查）**

上文把判定描述為「讀 agent frontmatter 的 `tools`，與本票所需能力比對」。**那個做法會漏掉 `saffron-system-analyst`——也就是本票的來源實例。**

原因是無寫入能力有兩種形態，字面比對只認得第一種：

| 形態 | 樣態 | 字面比對的結果 |
|------|------|--------------|
| A：`tools` 不含任何寫入工具 | `oregano-data-miner`：`Grep, LS, Read` | 正確判為缺 |
| **B：`tools` 含命名空間萬用字元，字面上有寫入工具，但該工具對目標檔類型被禁用** | `saffron-system-analyst`：`... mcp__serena__*` | **誤判為有寫入能力** |

B 類的禁用來源是 `.claude/rules/core/tool-selection.md` 規則 1（已驗證，該檔 L25）：`.md` / `.txt` / `.yaml` / `.yml` / `.json` / `.toml` 的修改**禁用** `mcp__serena__replace_content` / `replace_symbol_body` / `insert_after_symbol` / `insert_before_symbol` / `safe_delete_symbol`，且有 hook 強制層（`mcp-write-tool-on-text-file-guard-hook.py`）。

**對本票設計的直接影響**：偵測必須**同時看目標檔案的副檔名**，不能只看 `tools` 清單。判定式大致是「該 agent 對 `where.files` 的這些副檔名，實際有沒有可用的寫入工具」，而非「該 agent 的 tools 有沒有寫入工具」。

**這是「誤報成本高於漏報」的另一面**：上文論證的是不要過度攔截，這裡是**漏報**——而且漏掉的正是本票的起因。兩者都要處理，不可只優化一邊。

**掃描方法本身的教訓（值得寫進 Solution）**：並行 session 第一次盤點時，把含 `*` 的 `tools` 行整條當作「萬用字元＝有寫入」排除，saffron 因此沒有出現在結果裡。**B 類在機械掃描下會偽裝成 A 類的反面**——實作偵測時若沿用同一個簡化，會複製同一個盲點。

**同型盤點的既有結果（並行 session 提供，已由 PM 逐項實查確認 `tools` 欄）**

| agent | `tools` | 與 description 的關係 |
|-------|---------|---------------------|
| `oregano-data-miner` | `Grep, LS, Read` | **矛盾且比 saffron 嚴重**——無 Write 亦無 Bash，不能寫檔、不能填 ticket body、不能建票、不能登記 spawn request，而 description 寫「為執行代理人提供詳細的實作指引」 |
| `saffron-system-analyst` | `... mcp__serena__*` | 矛盾（本票來源） |
| `sassafras-data-administrator` | `... mcp__serena__*` | 疑似（B 類） |
| `sumac-system-engineer` | `Read, Bash, Grep, Glob, LS` | 疑似——有 Bash 可安裝，但改設定檔需 Edit |
| `basil-writing-critic` | `Read, Grep, Glob, Bash, mcp__zhtw-mcp__zhtw` | **一致**——該 agent 明示「不修改文件」，無寫入工具是設計意圖 |

`basil-writing-critic` 是本票偵測必須放行的反例：**無寫入能力可以是正確的**。偵測的對象是「票的需求與 agent 能力不符」，不是「agent 沒有寫入工具」。

**歸屬邊界**：agent 定義本身該怎麼修（改 description／改 tools／維持現狀）由 `0.1.0-W3-143` 處理，不在本票。本票只加偵測。
