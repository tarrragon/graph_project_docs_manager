## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

三份框架文件各自獨立定義了「終端與非圖形呈現是否屬 UI」的判準，且三者語意不一致：

1. **version-bootstrap SKILL.md Step 2**（W3-397 E3 落地後）：呈現通道三分。「圖形介面」判 UI 類，過三項前置與 Step 4.5 地基波；「非圖形的人讀呈現」（終端、匯出版面、OS 通知）判非 UI 類，不過三項前置也不跑地基波，但須記錄通道交 foundation-design。
2. **foundation-design SKILL.md** 維度表 UI 列：適用條件「不限」，任何專案皆須回答「UI 維度的產物是什麼」。dimension-product-notes UI 維度範例明寫：終端 statusline 工具的 UI 維度產物是「改寫產物：輸出格式契約（欄位順序、色碼語意、寬度截斷規則）」，失效仍存在，不判「無」。
3. **元件庫雙向約束方法論**〈形態因素先決〉：「CLI 以鍵盤輸入與文字輸出為操作方式，依『形態由操作方式定義』原則是合法形態，通道限文字回聲與終端輸出，不因缺圖形介面而被排除在矩陣外。」回饋通道子表有完整 CLI 欄。

矛盾核心：version-bootstrap 把非圖形呈現判為「非 UI 類」後跳過地基波全部四塊，但 foundation-design 與元件庫方法論都認為非圖形呈現仍有 UI 維度的失效要防、CLI 仍是合法形態。

### 二、測例矛盾表

六個測例，分別在三份文件的判準下判定：

| 測例 | version-bootstrap Step 2 判定 | foundation-design UI 維度判定 | 元件庫方法論形態因素判定 | 矛盾？ |
|------|------|------|------|------|
| 終端進度條（stdout 百分比輸出） | 非 UI 類，跳過地基波 | 改寫產物（格式契約），失效存在 | CLI 為合法形態，回饋通道為「終端輸出：進度列或完成訊息」 | **矛盾**：VB 跳過地基波四塊但 FD 認為有產物要做 |
| CLI 互動選單（stdin/stdout 問答式） | 非 UI 類，跳過地基波 | 改寫產物（操作契約），失效存在 | CLI 合法形態，回饋含「游標行」「終端回聲」 | **矛盾**：同上 |
| 全螢幕 TUI（curses/blessed 等） | 非 UI 類（終端互動），跳過地基波 | 改寫產物（版面契約），失效存在 | CLI 合法形態（含 focus/affordance 等事件） | **矛盾**：TUI 有完整版面配置，更接近圖形介面，仍被歸為非 UI |
| 匯出文件版面（PDF/HTML 報表） | 非 UI 類，跳過地基波 | 改寫產物（版面格式契約），失效存在 | 未明確納入矩陣（非互動形態） | **矛盾**：VB 與 FD 不一致 |
| OS 通知（desktop notification） | 非 UI 類，跳過地基波 | 需判「改寫產物」或「無」 | 元件庫方法論回饋事件表 state-change 列：「不在視野時：系統通知或 badge」——OS 通知是回饋通道之一 | **部分矛盾**：OS 通知在方法論中是回饋通道，不是獨立形態 |
| GUI 彈窗（應用程式渲染的 Dialog） | UI 類，過三項前置，跑地基波 | 照預設四塊 | 桌機形態的覆蓋表面 | 無矛盾 |

六例中五例有矛盾。矛盾的共同模式：version-bootstrap 的「非 UI 類→跳過地基波」與 foundation-design 的「UI 維度不限→仍有產物」直接衝突。

### 三、矛盾的本質

三份文件的「UI」實際指涉兩個不同概念：

| 概念 | 定義 | 使用者 |
|------|------|--------|
| UI-A：圖形介面 | 由本應用程式的 GUI 框架渲染的視覺產物 | version-bootstrap Step 2 的三項前置檢查、Step 4.5 地基波四塊（i18n/design-system/UX 審查/元件庫） |
| UI-B：使用者可見的呈現一致性 | 同一概念不會在不同開發者手中長出不同樣子（不限圖形） | foundation-design 的「UI 維度要防的失效」、元件庫方法論的「形態由操作方式定義」 |

version-bootstrap Step 2 的 E3 裁決正確辨識了 UI-A（三項前置的產物確實只適用圖形介面），但 Step 4.5 地基波的跳過條件與 foundation-design 對 UI-B 的要求相衝——非圖形呈現不需要 UI-A 的四塊地基，但可能需要 UI-B 意義下的改寫產物。

### 四、統一語意選項

#### 選項 1：Step 4.5 為非圖形呈現定義改寫版地基波

**做法**：Step 4.5 的標題由「僅含 UI 提案的版本」改為適用所有有人讀呈現的版本。非圖形呈現的提案跑一個改寫版地基波，產物為：
- 輸出格式契約（取代 design-system 的 token 概念）
- 終端互動規格（取代 UX 審查的反應規格）
- i18n 與元件庫視專案而定

**影響條文**：
- version-bootstrap SKILL.md Step 2 呈現通道表第二列動作欄改為「不過三項前置；但 Step 4.5 仍跑，走改寫版地基波」
- Step 4.5 標題、Checkpoint 需改寫
- step-rationale.md〈Step 4.5〉需擴寫

**誤判代價**：
- 偽陽（高）：所有含終端輸出的提案都要編排改寫版地基波，即使只是一行 log 輸出也會被要求寫格式契約，過度工程化
- 偽陰（低）：不會漏掉任何有人讀呈現的提案

#### 選項 2：維持 E3 二分，在 foundation-design 明寫與 version-bootstrap 的分工

**做法**：承認兩份文件各司其職，不統一「UI」的語意：
- version-bootstrap Step 2 的「UI 類」= UI-A（圖形介面），專門控制三項前置與四塊地基波
- foundation-design 的「UI 維度」= UI-B（呈現一致性），專門控制產物欄的判定
- 兩者的銜接點是 Step 2 呈現通道表第二列已有的「交 foundation-design」動作

**影響條文**：
- foundation-design SKILL.md 維度表 UI 列補一行釐清：本維度覆蓋 UI-B，version-bootstrap Step 2/4.5 覆蓋 UI-A，兩者各自獨立判定
- dimension-product-notes.md UI 維度範例補一句：version-bootstrap 已判非 UI 類的提案仍須到此走 UI 維度
- version-bootstrap step-rationale.md 補一句：非圖形提案的呈現一致性由 foundation-design 承接，不在地基波處理

**誤判代價**：
- 偽陽（低）：不會無故擴大地基波範圍
- 偽陰（中）：讀者可能只讀 version-bootstrap 看到「非 UI 類」就認為 UI 維度全數跳過，不去 foundation-design 走改寫產物。Step 2 已有「交 foundation-design」的動作句，但動作句能否被遵循取決於讀者注意力

#### 選項 3：不統一，以術語區分兩種 UI

**做法**：在三份文件中引入明確術語，不改判定邏輯：
- 「GUI 類」取代 version-bootstrap 的「UI 類」，專指圖形介面
- 「呈現維度」取代 foundation-design 的「UI 維度」，涵蓋所有人讀呈現

**影響條文**：
- version-bootstrap SKILL.md 全文的「UI 類」改為「GUI 類」，含 Step 2、Step 4.5、Checkpoint
- foundation-design SKILL.md 維度表第一列「UI」改為「呈現」
- 元件庫方法論不改（它自始未使用「UI 類」做二分判定，只在回饋通道列提到 CLI）
- 所有已引用「UI 類判別」的下游文件須同步改名

**誤判代價**：
- 偽陽（低）：術語明確，不會誤擴範圍
- 偽陰（低）：讀者看到「GUI 類」與「呈現維度」自然不會混淆
- 改名成本（高）：「UI」一詞在三份文件及下游大量出現，同步改名的漏改風險高，且元件庫方法論的 L1/L2/L3 分層、流程整合點皆使用「UI 類提案」字樣

### 五、是否屬用戶程式碼風格偏好

**判定：否。** 本議題屬規劃流程判準，不涉及用戶的程式碼風格選擇。三個選項的誤判代價可客觀比較（偽陽導致過度工程 vs 偽陰導致遺漏呈現契約），不需要用戶的主觀偏好來裁決。

### 六、建議

**選項 2（維持 E3 二分，明寫分工）為最低成本、最低風險的選項**：

1. E3 裁決本身正確——三項前置與四塊地基波的產物確實只適用圖形介面，不應為非圖形呈現建立改寫版地基波（選項 1 的偽陽代價過高）
2. foundation-design 的 UI 維度「不限」也正確——非圖形呈現的一致性失效確實存在，需要改寫產物（選項 3 的改名成本過高，且改名本身不解決實質判定問題，只解決命名混淆）
3. 銜接點已存在（Step 2 第二列的「交 foundation-design」動作），缺的只是 foundation-design 端的對應說明
