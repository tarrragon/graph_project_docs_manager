## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

同 0.1.0-W3-106.1／106.2：既有回饋契約語意正確、格式落後。本票另補一項
方法論修正——106.2 覆核時 PM 指出：服務類型判定應直接依 SPEC-003 §2.12
的兩軸（使用者感知的等待長度／失敗形態）判定，不應類比外推既有實例
清單（該清單只是舉例，不是判準本身）。本票全數採兩軸判定法。

### 影響範圍

docs/spec/ui/SPEC-004-component-library.md §4.15–4.26（MatrixCell 至
AppSnackBar，本段條目數量最多）。逐條目盤點與服務類型判定：

- 4.15 MatrixCell／4.18 ExpanderIcon／4.19 RelationItem／4.23
  BlockedState：本地即時（兩軸：零等待 + 不可能失敗，純本地操作）
- 4.16 SwimlaneNode／4.17 StepNumber／4.20 DocumentBody：純顯示零互動
  層級，判定不需改動
- 4.21 EmptyState：服務類型不固定（動作按鈕依 actions 內容而定，可能
  本地即時或長時操作，仿 106.1 AppButton 的處置手法）
- 4.22 MissingSourceState：短暫非同步（兩軸：亞秒等待 + 可能失敗，
  重新整理後仍找不到檔案時經 SnackBar 通知）
- 4.24 LoadingState：長時操作類第二層本身的承載者。此類元件的掛載點
  欄拆為兩段——「為誰承載哪一層」（本元件是長時操作類第二層本體）與
  「自身互動掛在哪一層」（取消鈕的第一層由 4.4 AppButton 承載），避免
  混寫讓讀者無法判斷取消鈕本身的第一層由誰保證
- 4.25 LoadPrompt：長時操作（單一動作固定觸發 Ticket 載入，§2.12 0.1
  實例逐字命中）
- 4.26 AppSnackBar：短暫非同步（本元件即該類政策對照表訂定的第三層
  載體，自身此刻的服務類型判定不受 withAction 動作觸發的後續操作影響）

### 相關 Error Pattern

無新增；沿用父票引用的 ARCH-GPD-001 與 DOC-005。
