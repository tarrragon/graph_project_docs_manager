### 問題根因

FlowStep 型別（`tracking_schema.py`）的必填欄位為 `{id, name, next, branch_from, return_to, emits, consumes}`，無 `domain` 欄位。CLAUDE.md §6 待決清單明載：「Domain 視圖的列與格無來源：個別 domain 不是圖節點（DomainBundle 的 carrier 是整份 domain-map.md），FlowStep 亦無 domain 欄位」。

直接原因：FlowStep 設計時以拓撲（next/branch_from/return_to）與事件邊（emits/consumes）為核心，domain 歸屬未被列為必要屬性。

### 影響範圍

依賴 FlowStep domain 歸屬的規格位置（已驗證）：
- SPEC-001 §1 Domain 矩陣格（泳道「步驟置於所屬 domain 列」）
- SPEC-001 §2 步驟表 Domain 欄、事件流小表「步驟序號 · domain」
- SPEC-001 §5 / SPEC-003 §3.5 `event-declaration-mismatch` 判準
- 實作票 W3-340

### 相關 Error Pattern

無直接相關的已知錯誤模式。本議題為設計缺口而非錯誤。
## 重現實驗結果
### 實驗方法

以 Python 腳本掃描 `docs/usecases/UC-*.md` 的結構化 flow 區塊，提取全部 39 個 FlowStep 的 `emits`、`consumes`、`implements` 欄位；交叉比對 `docs/events/` 下 9 個 EVT 節點的 `producers`／`consumers` 清單與目錄歸屬。對每個候選方案計算可推導率（唯一推導出 1 個 domain 的步驟數 / 39）。

### 實驗執行

資料來源：
- 39 個 FlowStep 分布於 UC-01（7）、UC-02（7）、UC-03（6）、UC-04（6）、UC-05（7）、UC-06（6）
- 9 個 EVT 節點分布於 5 個 domain 目錄（corpus/3、schema/2、workspace/1、diagnostics/1、graph/1、layout/1）
- 28/39 個 FlowStep 的 emits 與 consumes 皆為空陣列
- 7/39 個 FlowStep 有 implements 欄位（值為 FR-02/04/05/06）

### 實驗發現（已驗證事實）

1. **28/39 步驟（71.8%）既不發射也不消費任何事件**——這些步驟是 UI 操作步驟（如 locate-domain、jump-to-node），無事件邊可供推導
2. **7/39 步驟有 implements**，但 FR → SPEC → domain 的映射鏈在上游 schema 中不存在（`tracking_schema.py` 無 `implements` 邊型別，亦無 FR 節點型別）
3. EVT producers/consumers 清單使用的是 domain 名稱（如 Corpus、Schema），與 domain-map §3 的 8 個 domain 名一致

未驗證假設：無。以上皆為資料直接讀取結果。

### 候選方案表

### 方案 (a)：FlowStep 新增 `domain` 欄位（顯式標註）

| 項目 | 內容 |
|------|------|
| 推導規則 | UC 作者在 flow 區塊內為每個步驟顯式填寫 `domain: "Workspace"` |
| 可推導率 | **39/39 = 100%**（人工填寫，定義上完整） |
| 上游需改 | tracking_schema.py：`FLOWSTEP_REQUIRED_FIELDS` 加 `domain`；doc CLI 的 UC 驗證邏輯加欄位檢查 |
| 多 domain 處置 | 不適用——每步驟恰好填一個值 |
| 零 domain 處置 | 設為必填欄位即不會有零值 |
| 失敗模式 | 人工填寫可能不一致（步驟填的 domain 與其 emits 的 EVT producers 矛盾）；39 個步驟需一次性回填 |
| 框架問題判準 | 需改 `tracking_schema.py`（`.claude/skills/doc/` 下通用資產）。(1) 抽象可攜性：FlowStep 缺 domain 欄位是 schema 設計缺口，替換專案名仍成立 → 通過。(2) 根源在 `.claude/` 通用資產 → 通過。**兩條 AND 皆通過，屬框架問題** |

### 方案 (b)：由 emits 的 EVT producers 推導

| 項目 | 內容 |
|------|------|
| 推導規則 | FlowStep.emits → EVT 節點 → EVT.producers 清單 → 取唯一 domain |
| 可推導率 | **7/39 = 17.9%**（僅 7 個步驟有 emits 且推導出唯一 domain） |
| 上游需改 | 不需改 schema；需建推導邏輯（讀 EVT frontmatter） |
| 多 domain 處置 | 本專案未命中（每個 EVT 的 producers 恰好只有 1 個 domain） |
| 零 domain 處置 | 28 個步驟 emits=[] 無法推導 |
| 失敗模式 | 71.8% 步驟無法推導——這些是 UI 操作步驟（無事件邊），此方案對它們無效 |
| 框架問題判準 | 不改 tracking_schema → 不適用 |

### 方案 (b-ext)：由 emits producers UNION consumes consumers 推導

| 項目 | 內容 |
|------|------|
| 推導規則 | 取 emits 的 EVT.producers 聯集 consumes 的 EVT.consumers |
| 可推導率 | **8/39 = 20.5%**（唯一 domain）；另 3/39 推出多 domain（multi） |
| 上游需改 | 同 (b) |
| 多 domain 處置 | 3 個步驟推出多個 domain，需額外消歧規則 |
| 零 domain 處置 | 28 個步驟仍無法推導 |
| 失敗模式 | 邊際改善（+1 唯一推導），但引入 multi-domain 消歧複雜度；根本問題未解（28 步驟無事件邊） |
| 框架問題判準 | 不改 tracking_schema → 不適用 |

### 方案 (c)：由 implements 的 FR 所屬 SPEC 推導

| 項目 | 內容 |
|------|------|
| 推導規則 | FlowStep.implements → FR → FR 所屬 SPEC → SPEC 所在 domain 目錄 |
| 可推導率 | **最多 7/39 = 17.9%**（僅 7 步驟有 implements；且 FR→SPEC 映射鏈在 schema 中不存在） |
| 上游需改 | tracking_schema.py：需新增 `implements` 邊型別與 FR 節點型別 |
| 多 domain 處置 | 本專案僅一個 SPEC（SPEC-001，ui domain），全部 FR 指向同一 domain → 無消歧問題但資訊量低 |
| 零 domain 處置 | 32 步驟無 implements 欄位 |
| 失敗模式 | 推導鏈太長（3 跳）；FR/SPEC 節點型別不存在需大量 schema 擴充；覆蓋率與 (b) 相當但成本高得多 |
| 框架問題判準 | 需改 tracking_schema（新增節點與邊型別）。(1) 抽象可攜 → 通過。(2) 根源在 `.claude/` → 通過。**屬框架問題** |

### 方案 (d)：由 domain-map.md 人工對照

| 項目 | 內容 |
|------|------|
| 推導規則 | 人工閱讀每個 FlowStep 描述，對照 domain-map §3 的 8 個 domain 界定，判定歸屬 |
| 可推導率 | **39/39 = 100%**（人工判定，定義上完整） |
| 上游需改 | 不需改 schema；結果需寫入某處（回到方案 a 的欄位問題，或維護獨立對照表） |
| 多 domain 處置 | 人工判定可選主 domain |
| 零 domain 處置 | 不會發生 |
| 失敗模式 | 結果無機器可讀載體——若不寫入 flow 區塊（= 方案 a），則對照表與步驟分離、難以驗證一致性；每次增刪步驟需人工同步 |
| 框架問題判準 | 不改 tracking_schema → 不適用 |

### 方案 (e)：Domain 視圖不以 FlowStep 為格來源（重新定義「格」）

| 項目 | 內容 |
|------|------|
| 推導規則 | 不推導。Domain 視圖矩陣的「格」改為以 EVT 邊為來源——domain A emits EVT-X、domain B consumes EVT-X → 格 = (A, B, EVT-X)。FlowStep 不出現在矩陣格中 |
| 可推導率 | 不適用（FlowStep 不參與矩陣） |
| 上游需改 | SPEC-001 §1、§2 需重新定義矩陣格語意；SPEC-003 §3.5 event-declaration-mismatch 判準需重新定義（不再以步驟 domain 比對 EVT domain） |
| 多 domain 處置 | 不適用 |
| 零 domain 處置 | 不適用 |
| 失敗模式 | 泳道「步驟置於所屬 domain 列」的規格承諾需放棄或重新定義；UC-02（assess change impact by domain）、UC-03（understand domains traversed by a flow）的「domain 貫穿」概念需重新定義——domain-map §2.5 定義「貫穿」為「一條 UC flow 經過某個 domain」，若步驟無 domain 歸屬則「經過」無法計算 |
| 框架問題判準 | 不改 tracking_schema → 不適用 |

### 給用戶的裁決題

### 裁決題 1：FlowStep domain 歸屬的資料來源

方案 (b)/(b-ext)/(c) 的可推導率皆低於 21%（28/39 步驟無事件邊，根本無法推導），無法單獨作為來源。實質可行的選項為：

**選項 A**：方案 (a)——FlowStep 新增 `domain` 必填欄位。100% 覆蓋。代價：tracking_schema.py 需改（框架問題流程）；39 個步驟需一次性回填；後續新增步驟時作者須填寫。

**選項 B**：方案 (a) + (b) 組合——新增 `domain` 欄位但允許省略；省略時由 emits 的 EVT producers 自動推導。代價：同選項 A 加推導邏輯；17.9% 步驟可自動填、82.1% 仍需人工填。推導邏輯增加複雜度但收益僅覆蓋 7 個步驟。

**選項 C**：方案 (d)——不改 schema，在 UC 文件 flow 區塊中以現有 YAML 擴充欄位（非 tracking_schema 管轄欄位）寫入 domain。代價：doc CLI 的 FlowStep 驗證不會檢查此欄位（非 FLOWSTEP_REQUIRED_FIELDS 成員）；schema 與實際資料不一致。

**選項 D**：方案 (e)——放棄 FlowStep 作為 Domain 視圖格來源。代價：SPEC-001 §1/§2 需大幅重寫；domain-map §2.5「貫穿」定義需重新解釋；UC-02/UC-03 的核心價值（「這個 domain 被幾條 flow 貫穿」）失去計算基礎。

### 裁決題 2：若選 A 或 B，框架問題的處理路徑

tracking_schema.py 變更屬框架問題（兩條 AND 判準皆通過）。需裁決：
- 走 framework issue 流程（observe → 上游修 → sync-pull）
- 或本地先改、後續 sync-push 同步上游
