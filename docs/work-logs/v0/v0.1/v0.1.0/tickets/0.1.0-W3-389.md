## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`references/typography-system.md`〈Migration Guide〉的「Common Replacements」表把「精確命中 Type Scale 離散階的值」（10/12/14/16/18/20/24/28/32）與「非精確命中、需要取整判斷的值」（11/13/15/17/19）混在同一張表，且對後者僅用表後一句散文規則（「相鄰兩階等距時，一律取較小一階」）解出唯一答案，未依「這個值從哪裡來」分流；`0.1.0-W3-336.8` G26 對 spacing-system.md 的同型表格（Non-Standard Values）已認定「就地取近似套用在既有程式碼裸值上會改變畫面」與 `foundation-design references/handoff-mode.md`〈命名與收斂分兩步〉衝突，並改採方案 D（按值來源分流：設計來源指定／畫布雜訊／既有程式碼裸值／無設計來源新寫程式碼四類分開處置，見 `0.1.0-W3-336.12` 落地後的 `spacing-system.md`〈Non-Standard Values〉）。本票評估此衝突與分流需求是否同樣存在於 typography 的取整表。

### 影響範圍

檔案：`.claude/skills/dart-style-guardian/references/typography-system.md`〈Migration Guide〉（Common Replacements 表 + 表後散文規則）。連帶：`.claude/skills/dart-style-guardian/SKILL.md` 第 49 行〈交界表〉「字級」列觸發條件目前未提及「值不在 Type Scale 離散階上」，與已修正的「間距」列（第 48 行：「需要的值不在〈Spacing Scale〉的八階上，要判斷是該取近似值還是該加一階」）不對稱。

已驗證事實（見下方重現實驗結果）：typography 表目前 5 個平手列（11/13/15/17/19）已用單一明訂規則一致解出，無 spacing 修復前「6 列給單一候選卻無理由、10/14/20/28 列給兩候選卻無 tie-break 規則」式的內部不一致；但「就地取近似套在既有程式碼裸字級上」的衝突與 spacing 完全同構——本表未區分字級值的來源，直接套用會使既有程式碼的文字大小被悄悄改變。

未驗證假設：typography-system.md 是否有其他章節依賴現行「一律取較小一階」措辭（已用 grep 排除，僅表後一句散文引用此規則，無其他引用）。

## 重現實驗結果
### 實驗方法

對 `typography-system.md`〈Migration Guide〉現行表格涵蓋的每個字級值，計算其與相鄰兩個 Type Scale 離散階（10/12/14/16/18/20/24/28/32）的距離，判斷屬「精確命中」「兩階正中間平手」或「單一候選較近」，並核對現行表格給出的答案是否與計算結果一致、平手列是否有一致的解法。

### 實驗執行

逐列距離計算（Type Scale 離散階：10/12/14/16/18/20/24/28/32）：

| 值 | 現行表格答案 | 與相鄰兩階距離 | 判定 |
|----|------------|---------------|------|
| 10 | overline(10) | 距 10 = 0 | 精確命中 |
| 11 | overline(10)（散文規則解出） | 距 10 = 1／距 12 = 1 | 正中間平手 |
| 12 | bodySmall(12) | 距 12 = 0 | 精確命中 |
| 13 | bodySmall(12)（散文規則解出） | 距 12 = 1／距 14 = 1 | 正中間平手 |
| 14 | bodyMedium(14) | 距 14 = 0 | 精確命中 |
| 15 | bodyMedium(14)（散文規則解出） | 距 14 = 1／距 16 = 1 | 正中間平手 |
| 16 | bodyLarge(16) | 距 16 = 0 | 精確命中 |
| 17 | bodyLarge(16)（散文規則解出） | 距 16 = 1／距 18 = 1 | 正中間平手 |
| 18 | titleMedium(18) | 距 18 = 0 | 精確命中 |
| 19 | titleMedium(18)（散文規則解出） | 距 18 = 1／距 20 = 1 | 正中間平手 |
| 20 | titleLarge(20) | 距 20 = 0 | 精確命中 |
| 24 | headline3(24) | 距 24 = 0 | 精確命中 |
| 28 | headline2(28) | 距 28 = 0 | 精確命中 |
| 32 | headline1(32) | 距 32 = 0 | 精確命中 |

現行散文規則原文：「上表已依『相鄰兩階等距時，一律取較小一階』規則產生（見 13／15／17／19 皆取低階：12／14／16／18），不需另外判斷方向。」11 列雖未被此句列舉，但套用同規則計算亦一致（取較小階 overline=10）。

### 實驗發現

已驗證事實：
1. 現行 5 個平手列（11/13/15/17/19）全數套用同一條散文規則、結果與規則一致，無 spacing 修復前「同屬平手卻只給單一候選又無理由」（`6→xs(8)`）式的內部不一致。
2. 現行 9 個精確命中列皆為距離 0 的精確值，不是「取近似」，無取捨可言，「單一候選是否真的較近」對此 9 列不成立疑慮。
3. 現行表格未區分「這個字級值從哪裡來」——設計稿刻意指定的字級、萃取自設計畫布的雜訊值、既有程式碼已在用的裸值、全新程式碼待選值，四者一律套同一張表給出唯一答案。就地把此表套用在**既有程式碼已在用的裸字級**（如已存在的 `fontSize: 15`）上會直接改變渲染的文字大小，此為視覺行為變更，與 `0.1.0-W3-336.8` 認定 spacing 表同款衝突完全同構（`foundation-design references/handoff-mode.md`〈命名與收斂分兩步〉：換語意名稱與改值需分兩步，不可因套用 token 名稱而連帶把值也改動）。
4. `SKILL.md`〈交界表〉「字級」列觸發條件未提及「值不在 Type Scale 離散階上」，與「間距」列（已在 `0.1.0-W3-336.12` 修正為「需要的值不在〈Spacing Scale〉的八階上，要判斷是該取近似值還是該加一階」）不對稱；若比照方案 D，此列亦應同步補上對應觸發條件以利讀者尋得〈Non-Standard Values〉節。
5. 現行「一律取較小一階」是未附理由的單向裁決（相較之下，spacing 修復前 G26 草稿的方向 A／方向 B 至少各附一句設計理由，但最終 PM 裁決仍捨棄單向裁決、改採方案 D 的「無設計來源新寫程式碼：平手時兩階並列，兩者皆合規」，理由是「無法從既有文件或程式碼推得何者為既定慣例」）。此理由對字級同樣成立：typography-system.md 全文未說明為何字級平手要偏向較小階，且此偏好會使目前所有平手列的較大候選（12/14/16/18/20）被排除在合規範圍外，卻無設計依據。

僅放寬不收窄的驗證：若將平手列由單一答案改為兩階並列，既有依現行表格採用較小階的程式碼仍合規（未被判定違規），僅新增較大階為同樣合規的選項——與 `0.1.0-W3-336.8` 對 spacing「6 列放寬為兩候選：只會放寬、不會讓現行寫法轉為不合規」的判斷同構，不需要另外的用戶簽核關卡。
