## Problem Analysis
### 補入：本專案已有一條指向回饋通道的既有路由（`0.1.0-W3-072` 審查後補）

`docs/spec/ui/SPEC-004-component-library.md` 樂觀更新政策列的重評條件段逐字寫著：

> 屆時允許類別限低風險、可逆的欄位編輯（如狀態值、標籤），回滾提示通道引用 §1 回饋通道子表 state-change 列且須能表達「操作未成功、已還原」；刪除節點、改寫邊等不可逆操作預設不樂觀

**這代表本專案早已把「操作未成功」的承載歸到回饋通道，不是 SPEC-001 的畫面狀態矩陣。** 本票裁定編輯能力五項結論的條文化承接時，該路由是既有依據而非需重新決定的事項。

**但兩者的射程不同，不可直接套用**：SPEC-004 那句管的是**樂觀更新的回滾提示**——已經樂觀顯示、隨後失敗、要還原；而 `0.1.0-W3-072` 的寫入前閘門管的是**根本沒開始寫**。兩者同屬「寫入未成功」家族，但前者有已顯示的狀態要收回，後者沒有。條文化時須分別給形態，不能以「都走回饋通道」一句帶過。

**與既有票的關係**：該列的重評條件未綁 ticket ID 且指向錯誤事件，已由 `0.1.0-W3-282` 承接（blockedBy 本票）。本票裁定承接關係後，`0.1.0-W3-282` 才知道要綁哪一張。

**判定為建議而非結論**：以上為 `0.1.0-W3-072` 多視角審查的範圍視角所提，本票 PM 已逐字查證 SPEC-004 原文屬實。該視角另提出三種阻擋條件應分別承載（有未提交變更／未被追蹤兩者屬操作回饋加破壞性確認、工作區非 git 屬常駐徽章），該三分為推得的建議，非任何現行文件的明文結論，落地決定權在本票與 `0.1.0-W3-073`。
