### FD-20a：逐句三問

句 1「照預設與改寫產物的選擇看稀缺通道的形態，不看事件流數量」
- (a) 出處：「不看事件流數量」可由 `SKILL.md`「判定的對象是產物，不是維度」＋事件流列適用條件（數量決定維度是否成立）推得；「看稀缺通道的形態」無非範例出處。
- (b) 改變讀法：是。原本改寫與否依 `SKILL.md`〈產物欄的五種合法答案〉「預設產物對本形態不適用或有害」逐案判斷，現收斂為單一軸（通道數）。
- (c) 正確性：部分。範例表「改寫產物」列原文省略的是「以多通道或多執行緒為前提的資源成本異質、分池、跨執行緒與 isolate 三節」——軸至少有兩條（通道數、執行緒數），且方法論開頭段明示「差別只在各節標明的『實例化條件』」。單軸準則會漏判「單通道但多執行緒」「多通道但請求成本同質」等形態。

句 2「預設產物…假設多個稀缺通道並存（連線池、worker pool 等）」
- (a) 出處：僅範例表「改寫產物」列。方法論本身宣稱「稀缺資源是參數，不是前提」，未宣稱其產物假設多通道。
- (b) 改變讀法：是，把範例的形態描述升為對方法論產物的定性。
- (c) 正確性：否。通道清單在單通道時為一列、九格卸載順序表以到達類別×級別為軸（方法論〈3. 級別〉「三乘三共九格」），兩者皆不以多通道為前提；且 `SKILL.md` 事件流列明示「判準在此，本 skill 不複述」，本句屬複述並改寫方法論。

句 3「即使事件流達兩條以上、維度成立，套用預設產物仍會產生恆為零的分片與跨通道欄位，此時走改寫產物」＋引號理由句
- (a) 出處：僅範例表。(b) 是。(c) 結論（該範例走改寫產物）正確，但「恆為零」理由只對範例形態成立，升為通則則過度推廣。

WRAP：
- W：保留／回退（理由句回到只在範例，閘門再度不通過）／改寫為路由至方法論實例化條件（零新判準）／改寫 `SKILL.md` 改寫產物列（範圍過大）。反向框架：若「單軸」正好是錯的——已由範例原文的「或多執行緒」反證。
- R：基本率——同 skill 6.6.12 起的補依據作業一貫以「路由至既有權威句」解題（CHANGELOG 6.6.12／6.6.13），升格範例理由句為通則在該序列中無先例。
- A：改寫成本為一段文字＋升版；不改的代價是探針依單軸準則作答，會把多執行緒單通道形態誤判為照預設。
- P：改寫後最可能失敗在「逐節查實例化條件」對讀者操作性不足；早期警訊為重建節錄檔後 FD-20a 類題探針 3/3 未達。
- 建議：改寫。

草稿 A（取代〈事件流仲裁的四種答案形態〉表前新增段）：
> 照預設與改寫產物的選擇依 `SKILL.md`〈產物欄的五種合法答案〉：預設產物對本形態成立走「照預設」，不適用或有害走「改寫產物」。事件流數量只決定維度是否成立（〈維度與產物〉事件流仲裁列適用條件），不決定產物形態。預設產物是否適用，逐節查事件流負載仲裁方法論開頭段所稱「各節標明的『實例化條件』」：有節的實例化條件在本專案不成立時，走「改寫產物」，省略該節，附改寫後的產物＋一句為什麼預設不適用（指名不成立的是哪幾節的實例化條件）。下表「改寫產物」列是單通道、單執行緒形態的一例。

### FD-20b：逐句三問

句 1（對象改寫）「事件流仲裁的對象是『多個事件流競爭同一個稀缺通道』這個競爭狀態，不是單看『有沒有事件流』或『有沒有稀缺通道』」
- (a) 出處：權威原句逐字（dimension-product-notes〈各維度要防的失效（權威出處）〉表事件流仲裁列、方法論開頭段）；範例表「無」列原文亦寫「不存在『多條事件流競爭同一通道』的情境」。非範例出處成立。
- (b) 改變讀法：只修正對象抽取的粒度；「原句的對象是原句裡會出事的那個東西」的抽取規則不變，其他五維度對象詞不受影響。
- (c) 正確性：正確。原寫法「『事件流』與『稀缺通道』」與「對象在本專案存在時不得填『無』」合讀，確實推出一條事件流不得填無，與範例「無」列相反，是真衝突。
- 判定：階段 1，保留。

句 2「單一事件流不構成此對象存在（適用條件見…『有兩條以上事件流的專案』）」＋句 3「套用於事件流仲裁：適用條件…即為上段『對象在本專案存在』的判準線——僅一條事件流時…對象不存在，填『無』」
- (a) 出處：「適用條件＝對象存在判準線」的等同無出處；範例「無」列的條件是「僅一條事件流（如單一 CLI 工具、無背景工作、無並行請求）」，比「僅一條事件流」多一個「無並行請求」。
- (b) 改變讀法：是。把 `SKILL.md` 表格的「適用條件」欄提升為〈判定「失效不存在」的理由〉的判準，其他五維度的適用條件欄無此地位。
- (c) 正確性：部分不正確。方法論〈1. 通道與仲裁器〉協調圖列：「同一個 domain 的同一條事件流，來自不同租戶的請求彼此競爭」——單一事件流但有並行請求者，競爭狀態仍存在，依新句卻會填「無」，正是 `SKILL.md` 所稱「會讓整張盤點表失效」的填法。另與同節「失效目前尚未發生不構成失效不存在」有張力，範例的重評條件可化解，但新句未交代。
- WRAP：W 保留／回退至僅改對象（「無」結論再回範例，閘門不通過）／改寫判準線為「兩個以上請求來源對同一通道發出請求」並保留重評條件。R：方法論協調圖列為直接反例。A：改寫成本一段；不改則單一事件流的多租戶服務被判「無」。P：改寫後 `SKILL.md` 適用條件「有兩條以上事件流」與新判準線字面不一致；早期警訊為探針援引適用條件答「無」。已列入衍生票評估。
- 建議：句 1 保留；句 2 後半與句 3 改寫。

草稿 B（取代「套用於事件流仲裁」段；句 1 破折號後改為「——單一事件流內來自不同請求來源的並行請求同樣構成此狀態，見下段」）：
> 套用於事件流仲裁：對象是否存在，看是否有兩個以上的請求來源會對同一個稀缺通道發出請求。事件流負載仲裁方法論〈1. 通道與仲裁器〉協調圖列寫明「同一個 domain 的同一條事件流，來自不同租戶的請求彼此競爭」，因此事件流數量不是判準線。僅一條事件流且無並行請求時，對象不存在，填「無」，附〈事件流仲裁的四種答案形態〉表「無」列的理由句與重評條件：「新增第二條事件流（背景排程、外部推送、並行請求）時重新評估」。

### TAD-03a：逐句三問

句 1（〈問題類型表〉後新增段）「識別信號『10 個以上屬性』是量的門檻，用於篩出待複判的候選，命中門檻不代表最終判定過度集中，須依聚焦性段複判」
- (a) 出處：「篩檢用途」無出處；複判依據有非範例出處——斷言品質三問後的面向計數段「同一條宣告內列舉的多項條件仍屬同一面向，斷言數依類型 9 隨條件數成比例」、類型 9 設計原則「斷言數量與被測行為的複雜度成比例，不與輸出結構大小成比例」。〈判讀範例〉「12 個斷言仍合格」只是這兩句的示範。

句 3 (2)「屬性橫跨兩條以上驗收宣告者，判過度集中，不論總數是否達門檻」
