### 第五個維度：外部驅動的事件流（用戶補充 2026-09-09）

> 而且要考慮到另一種狀況，事件流本身也可能是依賴 websocket 或者某些伺服器的輪詢動作去驅動，**這些事件發生不是透過使用者，也不能算是我們自己發起的**，這類的事件流也要加入跟其他事件流互動的考慮因素。

**本票原有的四個問題預設了每個事件都有發起者，且發起者是我們**——使用者顯式觸發，或 App 自行發起。「前台／背景」這組分界建立在該預設上：兩者都是我方決定何時開始。

外部驅動的事件不屬於任何一邊。它的到達時機不由我方決定，因此**第二問（避免同時請求使用者關注）對它直接無效**——無法排程一件不受控於何時發生的事。第四問（重要問題發生時暫停背景行為）也只能暫停我方發起的部分，暫停不了持續到達的外部事件。

**本專案目前無 websocket 或輪詢，但有結構同構的來源**：外部編輯器對原始檔的改動或刪除。SPEC-003 §3.6 明文把 `notFound` 稱為「對外部變更的第一手偵測點」——那是一個由外部造成、我方僅能偵測的狀態變更。現行設計偵測到它之後直接轉入 `state-nodeDetail-missing`，**沒有任何條文管該轉換與使用者當下互動的關係**（使用者可能正在該畫面做別的事）。編輯能力落地後，外部變更與使用者編輯的競爭會成為常態。

**因此第一問的分界須改為三分而非二分**：使用者觸發／我方自行發起／外部驅動。前兩者可排程，第三者只能接收；三者對「避免注意力競爭」與「暫停背景行為」兩條規則的適用性不同，須各自定義。

**外部驅動事件須額外回答的問題**（原四問不涵蓋）：

1. **到達時使用者正在互動中，該如何處置**——立即中斷、排入佇列待使用者空閒、或靜默記錄待使用者主動查詢。判準應依事件的重要性與時效性，不是一律。
2. **可否延後與延後的上界**——某些外部事件延後即失去意義（即時性），某些延後無損。須定義判準。
3. **是否需要合併**——高頻外部事件（如檔案系統監看）若逐一提示會淹沒使用者，合併的窗口與合併後的表達形式須定義。
4. **與我方發起事件的優先序**——兩者同時抵達時誰先，依據是什麼。

**這四項的答案會回頭約束第三問（跨 domain 協調）**：若外部事件需要「與其他 domain 確認過再執行」，而該事件不由我方發起，確認的時機只能在**接收之後、呈現之前**，不能在發起之前——這與我方發起事件的協調點位置相反，須分別定義。


### 本專案已存在的注意力競爭實例：跨路徑不對稱干擾

並行 session 讀 Flutter SDK 原始碼（`packages/flutter/lib/src/material/scaffold.dart`）查證後確認：

`ScaffoldMessengerState` 持有 `Queue<ScaffoldFeatureController<SnackBar, SnackBarClosedReason>> _snackBars`，`showSnackBar` 走 `addLast`，**只有 `_snackBars.first` 會被呈現**。因此**視覺重疊不會發生，這是 `ScaffoldMessenger` 本身的性質**——與呼叫端有沒有先 `hideCurrentSnackBar()` 無關。

`hideCurrentSnackBar()` 決定的是另一個軸：

| 路徑 | 語意 | 後果 |
|------|------|------|
| `AppSnackBar.show`（元件層，3 處） | 先 hide 再 show → **取代** | 前一則被截斷 |
| `lib/main.dart:219`（繞過元件直呼原生） | 直接 show → **排隊** | 這一則等前面播完 |

**關鍵事實**：`hideCurrentSnackBar()` 作用於 `_snackBars.first`，**不分那一則是誰放進去的**。因此任何一次 `AppSnackBar.show` 都會截斷正在顯示的 `main.dart` 那則訊息——**跨路徑干擾存在且不對稱：元件路徑殺得掉原生路徑的訊息，反之不行。**

這是本票所稱「注意力競爭」在本專案的第一個具體實例，且它**不需要兩個事件同時發生**——只需要一則正在顯示時另一則抵達。使用者的觀察是「訊息閃一下就不見了」，而被殺掉的那則目前零日誌（`main.dart:219` 不經過元件層，`0.1.0-W3-165` 的四個事件對它全不適用）。

**方法論層的一點**：先前的分析把「不重疊」歸因於「所有 show 都先 hide」，結論正確而理由錯誤。理由比結論重要——日後若加入第二個覆蓋層、或改用非 `ScaffoldMessenger` 的載體，「Material 佇列保證單一呈現」這個前提即不成立，而錯誤的理由會讓人以為「照樣先 hide 就安全」。本票在定義注意力競爭規則時，須以**載體的實際併發語意**為依據，不以呼叫端的慣例為依據。

### 更正：外部驅動在本專案目前是空類別，且其判準是「到達不受控」非「變更不受控」

上一節把「外部編輯器對原始檔的改動或刪除」列為本專案的外部驅動同構者。**該歸類錯誤**，並行 session 實查後更正，PM 採納。

**判準的精確表述**：外部驅動之所以使「避免同時請求使用者關注」失效，關鍵不是**變更**不受控，是**到達**不受控——我方無法決定何時得知，因此無法排程。

| | websocket／伺服器輪詢／推播 | 本專案的外部檔案變更 |
|---|---|---|
| 變更何時發生 | 不受控 | 不受控 |
| **我方何時得知** | **不受控（被推送）** | **受控（我方查詢時才知道）** |
| 「避免同時請求注意力」是否適用 | 否 | **是**——我方決定何時去看 |

同構關係斷在第二列。`SPEC-003:1073`（§3.6）的 `notFound` → `state-nodeDetail-missing` 雖註明「對外部變更的第一手偵測點」，但**該偵測發生在使用者點擊開啟原始檔時**——外部變更是成因，偵測時機仍由使用者觸發。故它屬第一類（使用者觸發）或第二類（我方自行發起）的「外部成因、我方觸發的偵測」，不屬第三類。

**更決定性的是本專案的既有裁定**：`SPEC-003:761` 明文「目錄消失屬外部變更，**由下一次重新載入承接，本畫面不設偵測點**」。本專案是刻意不設外部變更監看的，因此**目前沒有任何真正的外部驅動到達**——沒有任何事件會在使用者沒動作時自己冒出來。

**第三類仍應保留，但須標明為空類別並綁定生效 trigger。** 用戶提的是設計 SPEC 時的通則，該通則跨專案成立且應寫入判準；但在本專案它目前無實例。若不標明，本票會為一個尚不存在的到達形態設計處置，且讀者會誤以為本專案已有推送型來源。

**生效 trigger**：`SPEC-003:761`「本畫面不設偵測點」的裁定被推翻時（檔案系統 watcher 落地，或引入伺服器推送／輪詢），第三類出現第一個實例，屆時本票定義的外部驅動處置開始適用。此為 `decision-trigger-binding` 規則 1 狀態 (b) 的形態——有明確 trigger 的延後，不是懸空。

**對執行者的要求**：結論中涉及外部驅動的部分，須明寫是「為尚未存在的來源預留」，**不得寫成現況分析**。

`0.1.0-W3-166` 固化「有顯示就要有紀錄」，但不回答「何時該顯示」。兩者一起才完整：只有前者會導向「凡事都跳提示」，而提示互相爭用同一個顯示位時，**資訊反而比不提示更少**——後出現的取代前一則，使用者兩則都沒讀完。

**這不是假設性風險。** 本專案目前 `AppSnackBar.show(` 的呼叫點實查為 **3 處、2 個檔案**（`gap_report_screen.dart:199`、`:218`、`scan_notification_controller.dart:202`；`shell.dart` 只有註解提及，無呼叫）。而 `0.1.0-W3-113`（`ScanNotificationController.show` 失敗的 SnackBar fallback）與 `0.1.0-W3-165` 都會再增加觸發時機，編輯能力（`0.1.0-W3-073`）落地後還會更多——**呼叫點只會增加，所以此數為量測當下的值，接手者須自行複驗現值**（`reference-stability-rules` 規則 9）。

> **建票時的數字更正（2026-09-09）**：本段原寫「6 個呼叫點，分佈於三個檔案」。該值來自 `grep 'AppSnackBar.show\|AppSnackBar\.'`——第二個分支匹配任何成員存取（型別引用、列舉、註解），第一個分支的 `.` 為未跳脫的正則萬用字元，故量到的是「提及 `AppSnackBar` 的行數」而非呼叫點數。現值由兩個 session 各自以 `AppSnackBar\.show\(` 獨立實查並互相對上。另有一種口徑是「訊息結局」（同一呼叫點的分支各算一則）為 5 則，可並列參考，但 acceptance 第 2 項的對照對象是**呼叫點**。

**失效形態的更正見 Problem Analysis 的〈PM 前置實查〉第二節**：本專案的 `AppSnackBar.show` 在顯示前無條件呼叫 `hideCurrentSnackBar()`，且 `ScaffoldMessenger` 一次只呈現一則，故版面上的「重疊」不會發生，實際形態是**替換截斷**。用戶關切的後果成立且更嚴重（重疊時兩則都在畫面上，替換是後者把前者抹掉），但處置方向不同——分化元件解決的是「同時要看到兩則」，解決不了「被靜默丟棄」。

**第三個子問題是前兩者的必然對偶**：一旦決定某些時機不顯示提示，那些事件就失去了使用者可見的回饋，此時可觀測性必須由日誌承接——否則等於用「安靜」換掉了「有紀錄」，兩頭皆空。`0.1.0-W3-078` 的實機驗證正是撞上這個：路徑走到了、程式做了對的事，但沒有任何一側留下使用者層級的證據。
