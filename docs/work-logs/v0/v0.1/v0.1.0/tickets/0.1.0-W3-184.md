### 第五個維度：外部驅動的事件流（用戶補充 2026-09-09）

> 而且要考慮到另一種狀況，事件流本身也可能是依賴 websocket 或者某些伺服器的輪詢動作去驅動，**這些事件發生不是透過使用者，也不能算是我們自己發起的**，這類的事件流也要加入跟其他事件流互動的考慮因素。

**本票原有的四個問題預設了每個事件都有發起者，且發起者是我們**——使用者顯式觸發，或 App 自行發起。「前台／背景」這組分界建立在該預設上：兩者都是我方決定何時開始。

外部驅動的事件不屬於任何一邊。它的到達時機不由我方決定，因此**第二問（避免同時請求使用者關注）對它直接無效**——無法排程一件不受控於何時發生的事。第四問（重要問題發生時暫停背景行為）也只能暫停我方發起的部分，暫停不了持續到達的外部事件。

**本專案目前無 websocket 或輪詢，但有結構同構的來源**：外部編輯器對原始檔的改動或刪除。SPEC-003 §3.6 明文把 `notFound` 稱為「對外部變更的第一手偵測點」——那是一個由外部造成、我方僅能偵測的狀態變更。現行設計偵測到它之後直接轉入 `state-nodeDetail-missing`，**沒有任何條文管該轉換與使用者當下互動的關係**（使用者可能正在該畫面做別的事）。編輯能力落地後，外部變更與使用者編輯的競爭會成為常態。

**因此第一問的分界須改為三分而非二分**：使用者觸發／我方自行發起／外部驅動。前兩者可排程，第三者只能接收；三者對「避免注意力競爭」與「暫停背景行為」兩條規則的適用性不同，須各自定義。

**外部驅動事件須額外回答的問題**（原四問不涵蓋）：

1. **到達時使用者正在互動中，該如何處置**——立即中斷、排入佇列待使用者空閒、或靜默記錄待使用者主動查詢。判準應依事件的重要性與時效性，不是一律。
2. **可否延後與延後的上界**——某些外部事件延後即失去意義（即時性），某些延後無損。須定義判準。
3. **是否需要合併**——高頻外部事件（如檔案系統監看）若逐一提示會淹沒使用者，合併的窗口與合併後的表達形式須定義。
4. **與我方發起事件的優先序**——兩者同時抵達時誰先，依據是什麼。

**這四項的答案會回頭約束第三問（跨 domain 協調）**：若外部事件需要「與其他 domain 確認過再執行」，而該事件不由我方發起，確認的時機只能在**接收之後、呈現之前**，不能在發起之前——這與我方發起事件的協調點位置相反，須分別定義。


### 本專案已存在的注意力競爭實例：跨路徑不對稱干擾

並行 session 讀 Flutter SDK 原始碼（`packages/flutter/lib/src/material/scaffold.dart`）查證後確認：

`ScaffoldMessengerState` 持有 `Queue<ScaffoldFeatureController<SnackBar, SnackBarClosedReason>> _snackBars`，`showSnackBar` 走 `addLast`，**只有 `_snackBars.first` 會被呈現**。因此**視覺重疊不會發生，這是 `ScaffoldMessenger` 本身的性質**——與呼叫端有沒有先 `hideCurrentSnackBar()` 無關。

`hideCurrentSnackBar()` 決定的是另一個軸：

| 路徑 | 語意 | 後果 |
|------|------|------|
| `AppSnackBar.show`（元件層，3 處） | 先 hide 再 show → **取代** | 前一則被截斷 |
| `lib/main.dart:219`（繞過元件直呼原生） | 直接 show → **排隊** | 這一則等前面播完 |

**關鍵事實**：`hideCurrentSnackBar()` 作用於 `_snackBars.first`，**不分那一則是誰放進去的**。因此任何一次 `AppSnackBar.show` 都會截斷正在顯示的 `main.dart` 那則訊息——**跨路徑干擾存在且不對稱：元件路徑殺得掉原生路徑的訊息，反之不行。**

這是本票所稱「注意力競爭」在本專案的第一個具體實例，且它**不需要兩個事件同時發生**——只需要一則正在顯示時另一則抵達。使用者的觀察是「訊息閃一下就不見了」，而被殺掉的那則目前零日誌（`main.dart:219` 不經過元件層，`0.1.0-W3-165` 的四個事件對它全不適用）。

**方法論層的一點**：先前的分析把「不重疊」歸因於「所有 show 都先 hide」，結論正確而理由錯誤。理由比結論重要——日後若加入第二個覆蓋層、或改用非 `ScaffoldMessenger` 的載體，「Material 佇列保證單一呈現」這個前提即不成立，而錯誤的理由會讓人以為「照樣先 hide 就安全」。本票在定義注意力競爭規則時，須以**載體的實際併發語意**為依據，不以呼叫端的慣例為依據。

### 一、事件的三分判準（取代前台／背景二分）

**判準的輸入是「到達時機由誰決定」，不是實作是否非同步。** 一個 `await` 在我方選定時刻發出的呼叫屬第二類；一個由平台同步回呼推進來的事件屬第三類——非同步與否不進入判斷。

| 類別 | 單一判準問句 | 可排程性 |
|------|------------|---------|
| **一、使用者觸發** | 這個事件能否回溯到使用者當下的一個顯式操作？ | 時機已定（就是現在），不可改 |
| **二、我方自行發起** | 開始的決定點是否在我方程式碼內？ | **完全可排程** |
| **三、外部驅動** | 我方是被通知的一方，而非查詢的一方？ | 不可排程，只能於接收後處置 |

**同一個事件源會因觸發路徑不同而落在不同類別，規則隨之不同。** 破洞掃描由使用者按「重新掃描」屬第一類，由 App 啟動自動執行屬第二類——同一份程式碼、同一個產出，但第二類受注意力競爭規則約束而第一類不受。**分類的對象是「這一次的發生」，不是那段程式碼。**

第三類在本專案為空類別，見 Problem Analysis 的更正段（判準是到達不受控而非變更不受控；`SPEC-003:761` 明文不設偵測點）。生效 trigger 已綁定，此處不重述。

### 二、注意力競爭的避免規則

#### 「同時」的操作性含義

**競爭的單位不是時間點，是尚未被消費的注意力請求。**

> 兩個注意力請求構成競爭，若且唯若**第二個抵達時第一個尚未被消費**。

消費有三種、缺一不可窮盡：使用者回應（按下動作）／使用者主動關閉／載體自然過期。

**為何不以時間點定義**：本專案已存在的競爭實例（Problem Analysis 的 SnackBar 跨路徑截斷）**不需要兩個事件同時發生**——只需一則正在顯示時另一則抵達。以「同一時刻」定義會漏掉全部實際案例；以「同一畫面」定義則抓不到跨畫面的通知。以「未被消費」定義同時涵蓋兩者，且可機械判定（載體持有的佇列長度 > 1 即為競爭）。

#### 依重要性的優先序來源

級別以**使用者必須做什麼**為鍵，不以事件的技術嚴重度為鍵——技術嚴重度是產生方的視角，注意力是接收方的資源。

| 級別 | 定義 | 錯過的後果 |
|------|------|-----------|
| **L1 必須決策** | 不回應則流程無法繼續 | 流程停滯 |
| **L2 必須知悉** | 不需回應，但錯過即無其他管道得知 | 資訊永久遺失 |
| **L3 可補查** | 錯過無損，另有管道可得知 | 無 |

**截斷規則**（三條，可機械檢查）：

1. 高級別抵達時**可**截斷低級別
2. 同級別**不得**互相截斷——必須排隊或合併
3. 低級別**不得**截斷任何東西

**本專案現況違反第 3 條**：`AppSnackBar.show` 無條件 `hideCurrentSnackBar()`，因此一則 L3 完成通知會殺掉正在顯示的 L2 失敗訊息，且被殺的那則零日誌。修法是把截斷條件綁在級別上，不綁在呼叫路徑上——**現行設計讓「走哪個入口」決定生殺，而級別才是該決定它的東西**。

### 三、事件流的跨 domain 協調要求

#### 哪些事件屬「會造成互動影響」

判準兩擇一即成立：該事件會**產生一個注意力請求**，或會**改變使用者當前可見的內容**。第二項涵蓋不發提示但抽換畫面的情形（如背景重新載入導致列表重排）。

#### 確認的對象——協調圖不是依賴圖

**這是本票最容易寫錯的一點。** `docs/domain-map.md` §2 的 8 條依賴邊描述**資料方向**，單向向下；注意力競爭則發生在**任何兩個會產生注意力請求的 domain 之間，不分層級**。兩者正交。

例：`Diagnostics`（L2）與 `Workspace`（L0）之間無依賴邊，但兩者都會產生注意力請求（破洞掃描完成、資料夾不可用），因此**在注意力軸上相鄰**。依賴圖上查不到這條關係。

**推論**：若要求各 domain 互相確認，需要 N² 條協調邊，且迫使 domain 互相知道彼此存在——直接違反 §3 Bundle 界定表的公開面設計。

#### 確認的形態——單一仲裁點，不做分散式協商

各 domain 不互相確認，改為**向注意力通道的單一持有者請求**，由後者依級別規則裁決。N 條邊取代 N²，且 domain 之間維持互不知情。

該仲裁點在本專案的落點須另行指定（候選：`ScaffoldMessenger` 的包裝層、或一個新的 presentation 層元件），屬實作決策，見下方 spawn 規劃。

#### 延遲的判準與時長來源

**延遲的終點是「當前注意力請求被消費」，不是固定時長。** 若必須有時長上界，取自**載體的自然存活期**（如 SnackBar 的顯示時長），不另設常數——另設常數會產生第二個需要與載體同步的數字，即 `DOC-GPD-003` 的形態。

### 四、重要問題發生時暫停背景行為

| 面向 | 定義 |
|------|------|
| **何謂重要問題** | L1（必須決策）事件，或會使背景行為的產出失效的事件（如工作區不可用時，掃描的產出無意義） |
| **暫停範圍** | **僅第二類（我方自行發起）全部暫停**。第一類不暫停（那是使用者正在做的事，暫停它等於沒收使用者的操作）；第三類無法暫停，只能緩衝 |
| **恢復條件** | 該 L1 請求已被消費，**且**其結果不使背景行為失效（例：使用者拒絕授權後，依賴該授權的背景行為不恢復） |

**恢復條件的第二個合取項不可省略**：只看「請求已被消費」會在使用者拒絕後立刻恢復一個註定失敗的背景行為，並在下一輪再產生一次相同的請求。

### 七、外部驅動事件的四項處置判準

> **本節為尚未存在的來源預留，不是現況分析。** 第三類在本專案為空類別（Problem Analysis 更正段），生效 trigger 是 `SPEC-003:761`「本畫面不設偵測點」的裁定被推翻時。以下判準在該 trigger 觸發前不適用於任何本專案事件。

**共用第二節的 L1–L3 級別與三條截斷規則**，不另立一套——級別的鍵是「使用者必須做什麼」，與事件由誰發起無關。差別只在：外部驅動**不能提前排程**，因此規則作用在接收之後。

| 待答問題 | 判準 |
|---------|------|
| **一、到達時使用者正在互動中** | 依級別：L1 可中斷當前互動；L2 排入佇列待當前請求被消費；L3 只寫日誌待使用者主動查詢，不產生注意力請求。**不設「一律中斷」或「一律緩衝」的統一政策**——那會讓級別失去作用 |
| **二、可否延後、上界為何** | 判準是**該事件的價值是否隨時間衰減**。衰減者（有時效的即時資訊）不延後，直接依級別競爭；不衰減者延後至當前請求被消費。**上界取自事件自身的有效期，不另設常數**（另設即產生第二個需與來源同步的數字，`DOC-GPD-003` 形態） |
| **三、是否合併** | 三條件 AND：同一來源、同一級別、且**使用者對其中任一則的處置對其他則同樣適用**。第三條是關鍵——它排除了「看起來像但需要分別決策」的情形。**合併後的表達必須保留計數**，否則使用者無從判斷要不要展開 |
| **四、與我方事件的優先序** | 同級別時**外部驅動優先**。理由：我方發起的可以重排，它不行——優先給不能讓步的一方，總延遲較低。這是本票唯一一處外部驅動享有優先，其餘一律依級別 |

### 八、協調點的位置：兩類相反，且推論出實作上的實質差異

| 事件類別 | 協調點位置 | 可否選擇不接收 |
|---------|-----------|--------------|
| 第二類（我方自行發起） | **發起前**——向仲裁者問「現在可以嗎」，答否則延後或不發 | 可（不發就是了） |
| 第三類（外部驅動） | **接收後、呈現前**——事件已經到了，只能決定呈不呈現、何時呈現 | **否** |

**這個位置差異推論出一項實作要件**：外部驅動需要一個**接收緩衝**（事件已入我方邊界但尚未呈現的暫存區），我方發起不需要——不發起就不存在待處置的事件。

**因此第三類落地時必須先有緩衝，不能只加規則。** 若在沒有緩衝的情況下套用第七節的判準，「排入佇列待消費」無處可排，實作會退化為立即呈現或直接丟棄，而兩者都不是判準說的事。**這一項是第三類生效 trigger 觸發時的第一個實作前置**，須寫入承接的 DOC 票。
