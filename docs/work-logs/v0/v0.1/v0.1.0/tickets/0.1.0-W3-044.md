### 可直接實作的判定指令（由 compositional-writing 維護方提供，本側已驗證）

```bash
git log --oneline --all --diff-filter=D -- <path>
```

**有輸出＝推送方刪除過該路徑（真孤兒，可 `--clean`）；零輸出＝推送方從未擁有（他方貢獻，不可清）。**

**本側驗證（同粒度正對照）**：

| 路徑 | 命中 | 判定 | 與已知事實一致？ |
|------|------|------|----------------|
| `.claude/skills/tdd/examples/flutter-sdk-tdd-walkthrough.md` | **1** | 推送方刪過 → 真孤兒 | 是。該檔正是 `0.1.0-W3-033` 在發佈庫盤點到的唯一殘留 |
| `.claude/scripts/uv.lock` | **0** | 從未擁有 → 他方貢獻 | 是。該檔由另一 consumer 於 08-28 推上 |

**正對照必須同粒度。** 本側第一次驗證時挑的對照路徑其實從未被刪過，導致對照組與待判項同樣回零——
兩個零看起來像「指令無效」，實際是「對照挑錯」。改用 `git log --all --diff-filter=D --name-only`
先取出真正被刪過的路徑再當對照，才得到 1 vs 0 的鑑別。**以 `.claude/` 整體回傳 2 筆作為管道證明是不夠的**：
它證明管道會動，不證明它對單一路徑有鑑別力。

### 提供方對自身推導的更正（值得寫進條文）

該方先前用同一條指令查 `portability-check.sh` 得零輸出，據此推論「沒有人刪過它」——**而正確的讀法是
「不是我刪的」**。零輸出的語意限定在執行指令的那個 repo 的歷史，不涵蓋其他 repo。

**這一點直接影響本票的訊息措辭**：修好判定之後，提示文字不可寫成「此檔未曾被刪除」，
只能寫「本專案的 git 歷史無此檔的刪除記錄，它可能是其他 consumer 的貢獻」。
否則只是把一個過寬的宣稱換成另一個。

### 對照組：`skill-sync` 的同類輸出沒有這個問題

該方核對後回報：`skill-sync` 標的是 `remote-only (preserved)` 與 `PRUNE (will be deleted)`
——**描述集合，不宣稱成因**。

但其觀察值得一併記入：**誠實的標籤仍然只給一格。** 分類的動作還是得由使用者帶進來，
`remote-only` 不會告訴你這一格裡有兩種成員。所以本票的修法應同時做兩件事：
判定加上歷史查詢（把一格分成兩格），措辭改為不宣稱成因（不把分類責任推回給使用者又替他答錯）。

### 作用域有兩個會漏掉的位置（本票修法的結構）

| 位置 | 問的是 | 本票的處置 |
|------|--------|-----------|
| **判定** | 這個集合分成幾格 | 加 `--diff-filter=D` 歷史查詢，把一格分成兩格 |
| **措辭** | 每一格的宣稱有多寬 | 改為不宣稱成因、且限定於本專案的 git 歷史 |

**修好判定不會順便修好措辭**，成因是兩件事在不同的時刻被想到——**修判定的時候人在想
集合的成員，修措辭的時候才會想到讀的人站在哪裡。**

判斷標準：只改措辭是誠實但不夠（`skill-sync` 現在的狀態：`remote-only (preserved)`
不宣稱成因，但那一格裡仍有兩種成員而使用者不會知道）；只改判定則會在措辭上把修好的
判定又漏掉（寫成「此檔未曾被刪除」，而正確語意只到「不是我刪的」）。

**本票兩項 acceptance 需對應這兩個位置**，不可只驗其一。

### 零命中的兩種成因在輸出上相同而成因相反

| 成因 | 指令狀態 | 輸出 |
|------|---------|------|
| 管道壞掉（如 shell 變數展開錯誤使檔名不存在） | **沒跑起來** | 零 |
| 對照挑錯（對照路徑本身從未被刪） | **正常執行而問錯對象** | 零 |

分辨方法是問對照本身：**用來證明管道通的那一次命中，與待判項是同一個粒度嗎。**

取得合格對照的可靠做法（本票實際採用）：先以
`git log --all --diff-filter=D --name-only -- <範圍>` 撈出該 repo 實際被刪過的路徑，
從那份清單裡取一個當對照——比「想一個應該會命中的」可靠。
### 根因更正：不是「他方貢獻」，是「我方有但未追蹤」（2026-09-07，第三次修正）

前兩版分析（本票原文與 `--diff-filter=D` 判定法）都判錯了成因，動作恰好對而理由錯。

**固定值**：

| 查證 | 結果 |
|------|------|
| 本地 `.claude/scripts/uv.lock` | **存在，40004 bytes** |
| canonical 同檔 | **40004 bytes**（大小相同） |
| `git ls-files --error-unmatch` | **未追蹤**（"Did you forget to 'git add'?"） |
| `git check-ignore -v` | **被忽略**——`.gitignore:99` 的 `.claude/**/*.lock` |

**機制**：檔案被 gitignore → `git archive HEAD` 取不到 → push 不帶它 →
孤兒偵測比對「canonical 的樹 vs 推送方的 **tracked** 樹」→ 判定推送方沒有 → 建議 `--clean`。

**盲點是 `.gitignore`，不是其他 consumer。** 任何被一方忽略而另一方追蹤的檔案都會被判為孤兒。
而「不在 HEAD」與「曾在 HEAD 後被刪」在 tracked 樹的視角下同形——這正是原措辭
「本地已刪除」的來源。

**`--diff-filter=D` 判定法對此類回零**（從未追蹤故從未刪除），歸類為「他方貢獻」，
**動作正確（別清）而理由錯誤**。單靠它不足以分類。

### 修正後的三格分類

| 格 | 判定條件 | 處置 |
|----|---------|------|
| 真孤兒 | 追蹤過且有刪除記錄（`--diff-filter=D` 有輸出） | 可 `--clean` |
| 他方貢獻 | 磁碟上不存在，且無刪除記錄 | 不可清 |
| **我方有但未追蹤** | **磁碟上存在但 `git ls-files` 查無** | **不可清；另須提示 gitignore 造成分歧** |

**第三格的判別最便宜——檔案在不在磁碟上。** 它應該排在歷史查詢之前。

### 附帶：`.gitignore` 的 pattern 過度匹配

`.gitignore:99` 的 `.claude/**/*.lock` 註解寫的是「框架執行期鎖檔的類別式涵蓋」，
用意是涵蓋 `dispatch-active.lock` / `scheduled_tasks.lock` / `.allocator.lock` 這類執行期鎖檔。
**但 `uv.lock` 是 uv 的依賴鎖定檔，性質相反——它應該納入版控。** 該 pattern 以副檔名分類而
非以用途分類，於是把兩種語意相反的檔案歸為一類。

**這與 framework issue #57（「project-init 與 shim CLI 偵測路徑跨檢查器判定矛盾，
且 uv.lock 未納版控」）指的是同一件事**，本票查出了它的機制。已另立追蹤。
### 三格判別順序的結構性理由（flutter_balance 提供，優於本票原記的「便宜」）

本票原記「第三格的判別最便宜，應排在歷史查詢之前」。該側補的理由更硬：

**前兩格都以 tracked 樹為視角，第三格是唯一跳出 tracked 樹的判定。**
先跑它等於**先排除「視角本身有盲區」**，剩下的才輪到在同一視角內分真孤兒與他方貢獻。

**順序反過來的後果**：`--diff-filter=D` 回零時會被歸到「他方貢獻」——動作對、理由錯，
**且提示不出 gitignore 分歧那一句**。而那一句正是本票要給使用者的核心資訊。

**故順序不是效能考量而是正確性考量**，實作時不可為省一次磁碟查詢而調換。

### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` fails or is
unavailable) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.
