### 問題形狀

`0.1.0-W3-254` 把十三張框架資產待派票 observe 到七則既有 issue 後**停在 observe**——知識已上跨 consumer 的載體、票仍留在本地，處於中間態。另有約 30 張框架票尚未升級。合計 45 張。

中間態不是無害的暫存狀態：本地票的 pending 會讓 runqueue 與派發判定持續把它們視為可執行工作，而它們的知識住址其實已在別處；同時 issue 端只有觀測 comment 沒有區段，讀者要從 comment 流裡自行拼湊當前結論。

### 為何不能照配方直接分群

配方步驟一指定以主題中央清單分群。實測該清單已漂移，且漂移是系統性的而非零星錯誤：

- `框架 skill 撰寫` 群含 `0.1.0-W1-014`（shared_preferences key 版本化）、`0.1.0-W1-015`（Developer ID notarization）等純專案票
- `0.1 App 地基` 群含 `0.1.0-W3-162`／`163`／`164`／`212`（派發 hook 與 worktree skill）等純框架票

機制：S1 依 `source_ticket` 繼承主題而不檢查內容。任一次錯誤指派會被全部下游繼承，且**每一次繼承都不產生訊號**。唯一的人工出口 `--no-topic` 在自動推導成功時是空操作（`0.1.0-W3-266`）——本票建立過程中以三筆對照（`264` 未傳／`265` 傳 `--no-topic`／`266` 傳 `--topic`）當場驗出。

照清單分群的後果是雙向的：專案知識被寫進跨 consumer 的 issue（對其他 consumer 是雜訊），同時框架知識留在本地（正是收束要解決的問題本身）。

### 分工的不確定性

三個 graph-project-docs-manager session 同時活躍，且訊息通道間歇不可達（多次 SendMessage 回報失敗，其中部分實際送達）。配方要求派發前對齊分工，但不能循序等待回覆。

### 工具側的已知風險

`section_comment.py` 的四支寫入命令無內容長度檢查，空內容照樣 POST、exit 0、印出成功 URL，其中 `update` 空內容會清空既有區段。七個 curator 並行寫入時，一個 curator 可以建出整組空區段、通過自己的 `show`／`check` 驗收、然後回報成功。

此風險不能靠「小心一點」吸收——它的斷點在 payload 通道（heredoc 重導向次序、shell word splitting），呼叫端讀不出來。故本票在每個 curator 的 prompt 內明訂：每則寫入後必須以 `gh api --jq '.body | length'` 回讀，回讀對象必須是世界平面產物，不得採信命令自身的回音行。
