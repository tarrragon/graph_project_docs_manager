## Problem Analysis
### 問題根因

`bash-tool-usage-rules.md` 規則七的三步（精確 `git add` → `git diff --cached --name-only` 核對 → 裸 `git commit`）連同其「版本邊界（過期 index 快照）」補充，全數正確執行後仍可產出靜默回滾他人已落地變更的 commit。兩個獨立的條文缺口各自成立：

**缺口一（射程）**：共用 git index 是**全樹快照**，倉庫中每個被追蹤檔案都有一個 entry；裸 commit 提交的是整棵樹。`git diff --cached --name-only` 呈現的不是「本次提交的內容」，而是「index 相對**當下** HEAD 的差集」。與 HEAD 相同的 entry 不進差集、因此不可見。HEAD 一旦前進，所有先前與舊 HEAD 相同、而新 HEAD 已改變的 entry 立刻成為過期快照並進入該差集——這些路徑從未被任何人 `git add` 過。規則七版本邊界提供的偵測法（`git show :<path>` 對 `git show HEAD:<path>`）是**逐路徑**的，被用來防守一個**全樹範圍**的風險，而兩者的差集恰好是執行者沒有理由去檢查的部分。此項與時序無關。

**缺口二（時效）**：三步之間隱含「瞬間完成」的前提，條文未寫出此前提，也未給時效上界。本次 `git commit` 撞 `index.lock` 競爭，執行者依規則三「短暫重試為預設」加了帶 `sleep` 的重試迴圈，HEAD 在該窗口內被推進。為滿足規則三而加的等待，使規則七的核對失效——兩條規則各自正確，組合產生缺口。

**承擔者缺口（缺口一的實作面）**：現行條文把共用 index 過期 entry 的清理責任綁在「**手動** CAS 之後執行 `git restore --staged`」。但實際推進 HEAD 的主力是 ticket CLI 在幾乎每個子命令後觸發的隔離索引 auto-commit，不在該條文射程內。查證本 consumer 現行實作：

| 位置 | `GIT_INDEX_FILE` 次數 | `restore` 次數 |
|------|----------------------|---------------|
| `.claude/skills/ticket/hooks/ticket-md-auto-commit-hook.py` | 2 | 0 |
| `.claude/skills/ticket/ticket_system/lib/git_ops.py`（`commit_files_isolated`） | 7 | 0 |

隔離提交確實做到隔離，但無人負責讓共用 index 跟上。共用 index 對所有經 CAS 提交過的路徑**單調落後**，落後量隨 session 進行只增不減；任一次裸 commit 會把全部落後量一次寫進歷史。

**（二）最小重現（臨時 repo `repro2`，執行者視角）**

base commit 含 `a.txt`/`b.txt`/`c.txt`，其後無人再對 `b.txt`/`c.txt` 執行任何 `git add`。

```
步驟 1 執行者只改 a.txt 並精確 add
  git diff --cached --name-only        -> a.txt                （核對通過）
  git show :a.txt / git show HEAD:a.txt -> A1 / A0              （版本比對通過，差異恰為自己的編輯）
  git show :b.txt / git show HEAD:b.txt -> B0 / B0              （相同，故不在差集、無理由檢查）
  git ls-files | wc -l                  -> 3                    （index 是全樹快照，非「本次 staged 的清單」）

步驟 2 他方以隔離索引 CAS 推進 HEAD，改 b.txt/c.txt，全程不碰共用 index

  commit-tree -p $OLD -> update-ref <branch> $NEW $OLD           （HEAD 前進）

步驟 3 執行者的裸 commit（三步檢查皆已於步驟 1 通過）

  git show HEAD:b.txt                   -> B0                    （他方的 B1 被回滾）
  cat b.txt                             -> B1                    （僅存於工作區）

**（三）核對重跑的鑑別力（臨時 repo `repro3`）**

同樣構造，但在 HEAD 被推進**之後**重跑核對：

```
推進前  git diff --cached --name-only -> a.txt
推進後  git diff --cached --name-only -> a.txt / b.txt          （被掃入路徑現形）
推進後  git status --porcelain        -> "M  a.txt" "MM b.txt"

### 實驗發現

**已驗證的事實**

1. 票面事件屬實，時序可完整復原；推進 HEAD 的是 CLI auto-commit 而非人工操作。
2. 機制可在乾淨 repo 重現，且**重現不需任何一方違反任何規則**：執行者精確 add、核對、版本比對全數執行；他方走的是框架推薦的隔離索引 CAS。
3. **缺口一成立且射程比既有記錄更廣**：被掃入的 `b.txt`/`c.txt` 自 base commit 起無人 stage 過。其 index entry 只是全樹快照的常態成員，在核對當下與 HEAD 相同，故既不出現在 `diff --cached`，也不會被逐路徑版本比對指到。`git ls-files` 為 3 直接證實 index 是全樹而非「本次 staged 清單」。
4. **缺口二成立，且核對本身有鑑別力**：推進後重跑核對即列出 `b.txt`。失效的不是核對邏輯，而是「核對結論可跨越等待繼續有效」這個未寫出的前提。核對與 commit 是兩個命令，窗口不可能為零。
5. 回滾後工作區仍保有新內容、`git status` 顯示為未暫存修改——這是唯一的殘餘訊號，但與「他人尚未提交的正常在途編輯」同形，無鑑別力。`git log` 完全正常。
6. 承擔者缺口：`ticket-md-auto-commit-hook.py` 與 `git_ops.py` 中 `restore` 出現次數皆為 0（`GIT_INDEX_FILE` 分別 2 與 7 處），確認無任何自動清理；清理條文只綁手動 CAS 操作者。

**仍未驗證的假設**

- 三個條文候選的實際效果未實測（候選 C 需改 CLI，未實作）。
- 未量測共用 index 落後量隨 session 進行的累積速率；「單調落後」由機制推得（CAS 依設計不寫共用 index、且無清理），非由計數實測。

### 四、候選方案（三案，皆未定案，裁決在 canonical repo）

| 候選 | 內容 | 利 | 弊 |
|------|------|----|----|
| A：核對零等待 | 明寫核對結論的有效期止於下一個命令；核對與裸 commit 之間不得有任何等待；遇 `index.lock` 重跑整個三步而非只重試 commit | 改動最小，純條文；與規則三的衝突被顯式化，執行者不再需要自行發現 | 窗口只縮小不消除（兩命令間隔不可為零）；**完全不覆蓋缺口一**；仍依賴執行者記得 |
| B：有並行寫入者時 CAS 為強制而非加強選項 | 現行條文把隔離索引 CAS 定位為「高衝突路徑的並列加強選項」。改為：session 內存在活躍並行寫入者（含 ticket CLI 的 auto-commit，即幾乎所有 session）時，共用 index 路徑結構性不安全，`ticket track commit` / CAS 為唯一合法路徑；規則七三步僅適用於確認無並行寫入者的場景 | 兩個缺口同時覆蓋；CAS 以釘選的 `$OLD_HEAD` 作 `update-ref` 舊值，HEAD 於窗口內被推進時該命令**失敗**而非靜默覆蓋，是目前唯一把「時效」轉為可偵測失敗的機制 | 要求提交路徑一律有可用 CLI；CAS 不可用時的退路仍落回不安全路徑（`#55` 已載三個把執行者推回裸 commit 的 CLI 缺口）；提高條文複雜度 |
| C：清理責任移入製造端 | 隔離索引提交完成後，由提交方對本次涉及路徑執行 `git restore --staged`，使共用 index 不累積過期 entry。落點是 CLI 實作而非執行者紀律 | 消除存量，間接縮小缺口二可掃入的集合；與框架既有「工具層修法優於操作層」「預設行為優於文件規範」判準一致——執行者照條文做仍出事時，責任不在記憶力 | 需改 CLI 並評估對 worktree 與多 session 的影響；仍不保護「他方在窗口內新推進」的那一筆，故不能單獨採用 |

**傾向**（供裁決參考，非結論）：B 與 C 不互斥且覆蓋面互補——C 從製造端消除存量落後，B 使殘餘窗口從靜默覆蓋轉為可偵測失敗；A 可作為 B 不適用場景（確認無並行寫入者）下的條文補強。單採 A 不足，因其對缺口一零覆蓋。
