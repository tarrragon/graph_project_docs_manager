### 建票當下的對照實驗（PM，2026-09-09）

本票建立時刻意以 `|` 分隔六條驗收條件，CLI 的實際輸出為：

```
[WARNING] 單一 --acceptance 值含分隔符，已被拆成 6 條：
             1. create 建票成功訊息回報本次存入的驗收條數與逐條內容
             2. 逗號串接多條時呼叫者可從輸出看出實際只存入一條，有對應測試
             ...
           若分隔符屬內文（非刻意分隔多條），請改用反斜線跳脫...
```

存入 6 條（`grep -c` 於本票 acceptance 段回傳 6）。

**與 `0.1.0-W3-208` 建票時的逗號輸入對照，構成本票的核心證據**：

|------|------|---------|
| `"A|B|...|F"`（正確） | 6 條 | 警告 + 逐條 preview |
| `"A,B,...,F"`（錯誤） | 1 條 | **無任何輸出** |

### 一、回報解析結果（已實作）

`create` 建票成功訊息一律回報本次實際存入的驗收條數與逐條內容，觸發條件從
「拆條時才報」改為「一律報」——移除既有 `ACCEPTANCE_PIPE_SPLIT_WARNING`
preview 機制的觸發條件限制，不新建機制。

**修改檔案**：
- `.claude/skills/ticket/ticket_system/lib/command_lifecycle_messages.py`：
  新增 `CreateMessages.ACCEPTANCE_STORED_REPORT` 訊息模板。
- `.claude/skills/ticket/ticket_system/commands/create.py`：
  `_report_creation_success` 內於既有「已建立 Ticket / 檔案位置 / 任務類型」
  三行之後，一律印出 `[INFO] 本次存入 {count} 條驗收條件：` + 逐條 preview，
  取值來源為已落盤的 `ticket["acceptance"]`（含分隔符拆條與預設模板皆已套用
  後的最終值），故涵蓋逗號、頓號、分號等所有摺疊形態，不需針對個別分隔符
  加偵測器。
- `.claude/skills/ticket/references/create-command.md`：於「多值參數格式」
  段 `--acceptance` 範例後補充新輸出行為的說明。

**測試**：新增
`.claude/skills/ticket/ticket_system/tests/test_create_acceptance_stored_report.py`
三案例——逗號串接摺疊為 1 條、多次 `--acceptance` 各自回報、`|` 拆條後回報
拆條後的最終條數（3 案例皆對照 stdout 是否含正確條數與逐條字面）。

### 二、擴充摺疊偵測（已評估，結論：不實作）

依 ticket how.strategy 要求，對 `docs/work-logs/v0/**/tickets/*.md` 全量
1298 筆既有 acceptance 條目做量化評估，逐一計算逗號／頓號分段數：

| 偵測基準 | 命中數 | 命中率 | 判讀 |
|---------|-------|-------|------|
| 半形逗號 `,` 出現 >= 1 次 | 3 / 1298 | 0.23% | 極低，且 3 筆全數為真正的摺疊事故（`0.1.0-W3-208`、`0.1.0-W3-210` 等），非誤報 |
| 半形逗號 `,` 出現 >= 2 次 | 2 / 1298 | 0.15% | 同上，門檻更嚴仍是真陽性 |
| 全形頓號 `、` 出現 >= 2 次 | 83 / 1298 | 6.4% | 高，中文條列敘述（如「A、B、C 三者」）大量合法使用頓號，非摺疊訊號 |

**結論：不實作**，理由分兩層：

1. **頓號無法用於偵測**：how.strategy 原提案「逗號或頓號分段」的頓號分支
   命中率 6.4%——如 PM 於 Problem Analysis 所述，這類警告一旦常態化就會被
   忽略，連帶使第一段的真實訊號（一律回報）失效，risk/benefit 不成立。

2. **半形逗號分支雖低誤報，但不可移植為框架邏輯**：`acceptance_parser.py`
   是 `.claude/skills/ticket` 共用資產，會 sync 到語言慣例不同的 consumer
   專案。本專案受 `language-constraints.md` 規範一律使用全形標點
   （`，`/`、`），使半形逗號幾乎只出現在誤用場景，才造就 0.23% 的低命中率；
   但這是本專案的書寫慣例副作用，非通用訊號——若 consumer 專案以英文撰寫
   acceptance（半形逗號是英文標準標點），同一偵測邏輯會在幾乎每次呼叫觸發
   誤報，重蹈頓號覆轍。框架層程式碼不應綁定單一專案的標點慣例。

第一段「一律回報」已零誤報涵蓋全部摺疊形態（含逗號），不依賴猜測意圖，
故不需再疊加偵測器承擔上述兩層風險。

### Rationale Chain
- 0.1.0-W3-208 why: `ticket track set-acceptance --add` 的參數語意是「條目文字」，CLI 自行補 `[ ]` 前綴。
但介面沒有任何地方阻止呼叫者把 `[ ]` 也寫進文字，寫了就得到雙重前綴。

實例：`0.1.0-W3-169` 的第 8、9 兩列現為 `'[x] [ ] 0.1.0-W3-167 裁定 A ...'`
（PM 於 2026-09-09 以 `--add` 建立時帶入字面 `[ ]`）。

**後果不是排版醜。** `check-acceptance` 認前綴故判定正確，票面顯示也正常——
唯一的受害者是「以 `grep '\[ \]'` 跨票掃未完成 acceptance」這個動作，它會在一張
已完成的票上得到兩個誤命中，且該票 9/9 全勾、狀態 completed，掃描者沒有任何
線索可判斷這是假陽性。錯誤形態與 `IMP-BAL-013`（locale 使 `uniq` 靜默合併
相異 CJK 字串）同族：總數守恆、狀態正確、唯獨分組錯誤，且無警告。

**根因在工具不在使用者。** 依 `opinionated-default-design` 主張 1，文件寫「別把
`[ ]` 寫進 `--add` 的文字」不會贏過工具的預設行為——工具沉默接受就會一直有人寫。（來源已完成，結論見 Solution）
- 0.1.0-W3-142 why: `ticket track add-acceptance` 會自動為傳入的文字補上 `[ ]` checkbox 前綴，但 `--help` 只寫「驗收條件文字」，**沒有說明這件事**。

使用者若照票面既有的字面（票面存的是 `[ ] 條件內容`）複製並傳入，結果會變成 `[ ] [ ] 條件內容`。並行 session 於 2026-09-08 實際命中，自行 `remove` + `add` 修復。

**這是引導缺口而非使用者錯誤**：票面顯示的字面帶前綴，複製票面字面是最自然的操作，而 help 沒有任何訊息說明前綴會被自動加上。**使用者做了看起來最合理的事，得到錯誤結果，且該結果不會報錯**——雙前綴是合法字串，CLI 照收。

**與 `--acceptance` 的不一致同源**：`ticket create --acceptance` 不以逗號分隔（整串當一條），`--where` 則吃逗號分隔，而兩者的 help 描述看起來同構。三者合起來是同一個問題的三個實例——**help 描述參數「是什麼」，不描述參數「怎麼被處理」**。
