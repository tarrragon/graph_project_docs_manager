## 重現實驗結果
### 實驗方法

讀取三個 agent 定義檔全文（`saffron-system-analyst.md`／`sassafras-data-administrator.md`／`sumac-system-engineer.md`），比對 frontmatter `tools` 與主文三強制區塊（允許產出／禁止行為／適用情境，`agent-definition-standard` 規定的仲裁依據）的寫入承諾是否一致；用 grep 交叉驗證 tools 行是否含 Write/Edit、三區塊是否含「撰寫／調整／提交文件」等寫入承諾字樣；另讀取 `star-anise-system-designer.md`（同型 Phase 0/1 設計文件產出者）與 `basil-writing-critic.md`（明示「不修改文件」的審查型 agent）作對照組。

### 實驗執行

```
grep -E "^(name|description|tools):" .claude/agents/{saffron-system-analyst,sassafras-data-administrator,sumac-system-engineer}.md
```

## Solution
### 分析結論

裁定依據為各 agent 主文的三強制區塊（允許產出／禁止行為／適用情境，`agent-definition-standard` 規定的仲裁依據），frontmatter `description` 僅為摘要，不一致時不採信。三者的三區塊皆多處（非單一措辭疏漏）明確承諾寫入產出，與 `tools` 缺乏有效寫入能力矛盾。**三者裁定一致：(b) 改 tools，補 Write/Edit**。逐項理由與「為何不選另兩案」如下。

#### 裁定一：saffron-system-analyst → (b) 改 tools（補 `Edit, Write`）

**三區塊承諾**（三處獨立引用）：允許產出 L25「檢視/撰寫需求文件」；核心職責 L88 標題「需求文件檢視/撰寫」；明確邊界 L268「SA 負責：需求文件檢視/撰寫」。

| 候選方案 | 做法 | 利 | 弊 |
|---|---|---|---|
| (a) 改 description | 移除「撰寫」，description 與主文三處同步改為「檢視」；「補充缺失需求描述」職責移交他人 | 工具與職責一致 | 撕掉三處獨立重申的核心職責；且無明確承接方——thyme 定位是工作日誌轉方法論非系統級需求文件，star-anise 定位是 UI/UX 規範非系統級需求，改 description 製造新缺口而非消除矛盾 |
| **(b) 改 tools** | 補 `Edit, Write`，保留既有 `mcp__serena__*` 供唯讀語意搜尋 | 三區塊承諾不變、補齊工具即兌現既有設計；SA 審查對象是「ticket 與系統設計是否一致」，不是它自己撰寫的需求文件，補充 `docs/app-requirements-spec.md` 等專案共用文件不構成審查對象與審查者同一的利益衝突 | 需仰賴既有禁止行為 5（不得修改已通過審查的需求，除非被重新派回）維持流程約束——但此約束本來是流程規範非工具限制，補 Edit 不削弱它 |
| (c) 維持現狀 | 論證撰寫可用口頭建議+派發他人落地 | 零變動成本 | 與明確邊界表「SA 負責：需求文件檢視/撰寫」字面矛盾；SA 沒有等價於 basil-writing-critic「不修改文件」的身份宣告可支持維持唯讀 |

**裁定**：(b)。**不選 (a)**：職責被三處獨立重申，撤除代價是產生新缺口而非消除矛盾。**不選 (c)**：使「撰寫」在三處均為無法兌現的文字承諾。

#### 裁定二：sassafras-data-administrator → (b) 改 tools（補 `Edit, Write`）

**三區塊承諾**（比 saffron 更直接——強制性禁令而非職責描述）：禁止行為 L118「禁止只提供建議而不提交設計文件：所有資料設計必須產出正式的設計文件（ERD、儲存策略、遷移方案等），不能只提供口頭建議」。

| 候選方案 | 做法 | 利 | 弊 |
|---|---|---|---|
| (a) 改 description | description 本已不提「撰寫」，需同步弱化禁止行為第 7 條為「可用口頭建議」 | 無需改 tools | 等於刪除一條專為防止「只出一張嘴」而立的強制禁令，倒退設計品質要求 |
| **(b) 改 tools** | 補 `Edit, Write` | 直接兌現禁止行為第 7 條；同型角色 `star-anise-system-designer`（Phase 0/1 設計文件產出者）已有 `Write, Edit`，補齊後消除既有不對稱而非新增例外 | 無顯著弊端 |
| (c) 維持現狀 | 論證可經 `ticket track append-log` 等管道落地正式設計文件 | 零變動成本 | ticket log 適合記錄結論，不是「正式設計文件」的等價載體（ERD／完整遷移方案需要獨立檔案、可被後續 ticket 引用路徑），且禁止行為第 7 條原文明寫「正式的設計文件」而非附註 |

**裁定**：(b)。**不選 (a)**：等於刪掉專為避免「有建議無交付」而立的強制禁令。**不選 (c)**：ticket log 不是正式設計文件的等價載體。

#### 裁定三：sumac-system-engineer → (b) 改 tools（補 `Edit`）

**三區塊承諾**：允許產出 L147「環境配置檔案｜pubspec.yaml、build 配置、環境變數檔案等調整」；禁止行為 1 正面陳述 L178「只能修改 pubspec.yaml、build 配置、環境變數設定」——此句本身即在授權範圍內明講「可以修改」。

| 候選方案 | 做法 | 利 | 弊 |
|---|---|---|---|
| (a) 改 description | 允許產出表改為「調整建議」，禁止行為 1 正面陳述改為「只能建議修改」 | 與現有 Bash-only 能力相符 | 與五個常見問題解決方案範例（版本約束調整、`pubspec.lock` 刪除重建等，皆預設 SE 直接動手）矛盾；把「除錯」職責降級為「建議」，違反 SE 作為「跑不起來時修復」實務型角色的定位 |
| **(b) 改 tools** | 補 `Edit`（不需 `Write`——SE 產出是調整既有檔案，非新建） | 與允許產出表、禁止行為 1 正面陳述、常見問題範例三處一致；`pubspec.yaml`/build 配置屬環境範圍不涉業務邏輯，補 Edit 不擴大職責邊界（`lib/features/` 等業務邏輯路徑仍受同一份禁止行為 1 明文禁止） | 需注意授權範圍是否被誤用到業務邏輯檔案——但這由既有禁止行為 1 的路徑範圍規範，非工具本身限制，維持現有規範文字即可 |
| (c) 維持現狀 | 論證 Bash 可用 `sed`/heredoc 完成調整 | 零變動成本 | 直接違反 `tool-selection.md` 規則 1（.yaml 修改首選 Edit/Write）與規則 2（禁止以 Bash 內嵌腳本規避 Edit/Write 限制）；SE 若靠 Bash 改 `pubspec.yaml`，等同把工具選擇規則的禁令用在自己身上 |

**裁定**：(b)。**不選 (a)**：與允許產出表、禁止行為正面陳述、常見問題範例三處實作慣例矛盾，且降級 SE 核心職責。**不選 (c)**：違反本專案 `tool-selection.md` 規則 1、2 的明文禁令。
