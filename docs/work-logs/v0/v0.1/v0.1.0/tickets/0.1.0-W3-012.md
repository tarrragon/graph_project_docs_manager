### 互補接線的實際缺口

查引用現況，指向本 skill 的只有 `version-bootstrap` 與 `foundation-design`，兩者都是流程編排層。本 skill 指向 `dart-style-guardian`、`doc`、`foundation-design`、`ticket`、`ux-design-evaluation`、`version-bootstrap` 六個。

**單向的是 `ux-design-evaluation` 與 `dart-style-guardian`**：

| 缺口 | 後果 |
|------|------|
| `ux-design-evaluation` 不指回來 | 使用者做完畫面狀態矩陣後，沒有任何訊號告訴他元件層契約該由誰承接。畫面狀態填完就以為 UX 工作完成，元件契約整塊漏做 |
| `dart-style-guardian` 不指回來 | 該 skill 管 L2 框架實作規範（禁裸值、禁自製元件），執行者從它進入時看不到「這些禁令的正面對應物是元件契約」 |

這與 `foundation-design` 先前的問題同形——該 skill 自稱地基單一入口，UI 列卻零次指向契約程序，經多輪審查才補上反向路由。同一形態在相鄰 skill 上重現，說明反向路由不是個案疏漏而是新增 skill 時的系統性缺口：新 skill 會指向既有 skill（作者知道自己依賴誰），既有 skill 不會自己長出指向新 skill 的路由。

`impeccable` 與 `frontend-with-playwright` 是否需要接線待執行時評估——前者是前端介面設計，後者是框架無關的前端協議，兩者與元件契約的關係不像前兩個那樣是直接的上下游。

### 設計互補流程的擴充方向

模式 B（畫布拆解）現為三個模式中最短的 17 行，而它正是與設計端協作的那條路徑。用戶點名要補「如何跟設計互補的流程」，缺的具體是：

- 設計稿與契約的往返：契約填寫過程中發現設計稿未定義的狀態時，回問設計端還是自行補齊，判準是什麼
- 設計端缺件時的出口：設計稿只有一個形態而契約要求每形態一份時的處置
- 契約反向約束設計：契約定案後設計稿新增元件時，走哪條路徑回到契約

這三項都是模式 B 現在沒有的，且都不是規則能單獨表達的——需要範例才說得清楚，這與用戶「範例引導優於規則約束」的判斷一致。

### 現有的三個程式碼區塊不是範例

主檔有六個 code fence（三組），內容是模式 A、B、C 的編號步驟表。它們仍是規則，只是排版成等寬區塊——講的是「怎麼做」，不展示「做出來長什麼樣」。依 `skill-design-guide` 的 Body 範本，Examples 的形態是「輸入 → 動作 → 輸出 的具體案例」，三組步驟表無一符合。

現有 `## Examples` 段七行，內容是指向其他章節的路由，同樣不是案例。

### 需要的四類範例

| 類型 | 輸入 | 輸出 | 為何規則講不清 |
|------|------|------|--------------|
| 一個填好的十一欄位契約條目 | 一列畫面狀態表 | 該元件的完整契約 | 讀者最需要看到成品的樣子。十一個欄位各自的問句都有，但填出來的整體長度、詳略比例、欄位之間怎麼呼應，只有成品能示範 |
| 一個容器條目含排列不變式 | 一個畫面的佈局結構 | 容器契約與三項不變式 | 「不重疊／最小間距／空間不足策略三選一」是判準，但三項在同一條目裡怎麼並存、策略怎麼寫成可驗收的句子，需要成品 |
| 一組畫面票的 how 與 acceptance | 一個畫面的三個狀態 | 逐狀態的派發語言句型 | 派發語言章有句型模板，但一個畫面有多狀態、每狀態多容器時的完整寫法沒有示範 |
| 一組歸併與不歸併的判斷對照 | 兩個外觀相同的候選 | 歸併或拆分，附理由 | **這一類最關鍵**。規則寫「語意相同者歸併，語意不同而外觀相同者不歸併」，但判斷兩者語意是否相同正是難處。規則只能給判準，範例才能示範怎麼用判準 |

第四類對應用戶「範例引導力大於規則約束」的判斷。前三類是成品示範，第四類是判斷示範，後者無法用規則表達——規則能列出選項，不能示範怎麼選。

### 範例的可攜形態

四類範例都須去識別化才能留在 `references/`。做法是用一個虛構但完整的情境貫穿：一個假想的清單畫面，含三個狀態、四個元件候選、兩個容器。同一情境貫穿四類範例，讀者建立一次脈絡就能讀完全部，比四個互不相關的片段省。

情境的選材要避開本專案特徵——不用 domain 視圖、ticket 清單這些本專案畫面名，改用通用的資料清單場景。

各專案的真實案例另放 `references/project-integration/`，該目錄不隨同步傳遞。兩層的分工須在主檔說明，否則下一個維護者會把專案案例寫進 `references/` 而觸發可攜性閘門。

### 執行順序建議

範例先於拆分。理由是拆分的邊界取決於範例放哪裡——若範例貫穿三個模式，它可能該獨立成檔而非附在各模式後；若範例分屬各模式，則隨各模式外移。先寫範例再定邊界，比先拆再塞省一次返工。
### 接線缺口比單向更嚴重：四個 skill 零出度

查 UX 設計族六個 skill 彼此的引用（只計以名字指名同族成員者）：

| skill | 指向誰 |
|-------|--------|
| component-contract-design | dart-style-guardian、foundation-design、ux-design-evaluation |
| foundation-design | component-contract-design、ux-design-evaluation |
| ux-design-evaluation | 無 |
| impeccable | 無 |
| frontend-with-playwright | 無 |
| dart-style-guardian | 無 |

六個裡有四個是終點：使用者進入那四個之一後，沒有任何訊號指向同族其他成員。原本判斷的「ux-design-evaluation 單向」是這個現象的一個切片，實際範圍是四個。

有出度的兩個恰好是最近動過的——`component-contract-design` 是新建，`foundation-design` 的反向路由是本輪補的。

**這說明引用是單向累積的**：新 skill 會指向既有 skill，因為作者知道自己依賴誰；既有 skill 不會自己長出指向新 skill 的路由，除非有人專門去補。時間越久，早期建立的 skill 出度越低，而早期 skill 往往是使用者的入口——`ux-design-evaluation` 與 `dart-style-guardian` 都屬此類。

新增 skill 時「補既有 skill 的反向路由」若不是流程的一部分，這個偏移會持續擴大且不自我暴露：作者從新 skill 出發測試路由，看到的都是通的。

### 前次評估的三個錯誤（逐字讀完主檔後修正）

前次評估只讀了章節結構、行數與程式碼區塊，未讀各章散文內容，三項判斷因此有誤。

**錯誤一：三種模式不互斥，拆三檔會增加跳轉而非減少載入**

證據在三處：模式 B 步驟 5 為「進模式 A，自存在必要性檢視起」；模式 A 步驟 4 註明「由模式 B 進入者，本步驟以模式 B 的排列關係盤點結果代替」；模式 C 步驟 4 為「依模式 A 的同型歸併規則歸併」。

真實結構是 A 為完整流程，B 是 A 的前置替代（做完接 A 的後半），C 引用 A 的部分規則。走 B 的讀者需要 B 加 A，走 C 的需要 C 加 A 的片段。前次「三選一、讀者只走一條」的判斷不成立，據此得出的「主檔載入時另兩條無效」也不成立。

**錯誤二：〈十一欄位填寫問句〉是核心判準不是操作細節**

該節 35 行的內容遠不只問句表：空格的處置規則與待決出口（三模式共用）、兩種合法佔位值的定義與適用範圍（「待決」與「不適用」不可互代，後者只允許於六個指名欄位）、容器排列不變式三問與空間不足策略的公式形態、範本中十一欄位以外章節的來源與填寫者對照表。

主檔開頭明寫「三種模式共用〈十一欄位填寫問句〉與〈派發語言〉兩節」。把三模式共用的核心判準移出主檔，等於讓每條路徑都要多讀一個檔。

**錯誤三：「全篇規則零範例」不精確**

十一欄位問句表有「常見空格與來源」欄，逐欄列出實際會填錯的形態（變體以外觀值命名、最長測試文案空白、可放入容器填「任何地方」、操作機制沿用畫布手勢）。那是反例形態的範例——具體、可對照、示範判斷。

所以缺的不是所有範例，是**正確成品的範例**：沒有任何一處展示填好的契約條目長什麼樣。診斷應修正為「有反例無正例」，這比「零範例」精確，也改變了要補什麼。

### 修正後的拆分軸：依何時需要，不依哪個模式

主檔各段落實際的使用時機分屬四類，而現行排列把四類交錯：

| 時機 | 內容 | 現在位置 |
|------|------|---------|
| 選用（要不要用這個 skill、走哪條路） | 三種起點的判定表與仲裁規則、分工邊界、時序定位 | 三種起點、分工邊界 |
| 派發（誰能執行、前置齊了沒） | 執行者與簽核者、前置條件與缺料出口、產出檔案規範 | 執行者與簽核者、三種起點內 |
| 執行（實際做） | 三個模式的步驟、十一欄位填寫問句、多形態處置 | 模式 A/B/C、十一欄位填寫問句、三種起點內 |
| 驗收（做完了沒） | 契約齊全的定義、派發語言、Troubleshooting | 契約齊全的定義、派發語言、Troubleshooting |

**〈三種起點〉一節混了四類中的三類**：判定表屬選用，前置條件與產出檔案屬派發，多形態處置屬執行。19 行裡有 12 行與「選哪個模式」無關。

依時機拆的外移候選：多形態處置（執行期查一次）、產出檔案規範（派發時查一次）、Troubleshooting（遇到問題才查）。三個模式因彼此依賴，若拆應合為一檔而非三檔，或維持在主檔。

十一欄位填寫問句與契約齊全的定義留主檔——前者是三模式共用判準，後者是五條可機械執行的驗收，兩者是這個 skill 最常被回查的部分。

### 這次修正本身的教訓

前次評估的三個錯誤有同一個成因：**用結構代理內容**。章節標題、行數、程式碼區塊數量都是結構訊號，用它們推論內容性質在三處都推錯了——標題叫「填寫問句」的其實是核心判準，排版成 code fence 的其實是步驟表，看似互斥的三個模式其實有依賴。

結構訊號的取得成本低，所以容易被當成內容的代理指標；它與內容的對應關係卻沒有任何機制保證。這與 PC-GPD-005 的「差異規模判據」相反——那個之所以可靠正因為它量的是內容本身而非結構標籤。
### 範例設計的修正

診斷改為「有反例無正例」後，四類範例的規劃要調整。

現有的反例已覆蓋十一個欄位各自的常見錯誤，那部分不需要重寫。缺的是與它配對的正例——同一欄位填對長什麼樣。反例說「變體以外觀值命名是錯的」，讀者知道不該寫「藍色版」，但不知道寫成什麼程度才算夠：只寫 `primary` 夠嗎，還是要連行為差異一起寫？

修正後的四類：

| 類型 | 與現有反例的關係 | 為何需要 |
|------|-----------------|---------|
| 一個填好的十一欄位契約條目 | 逐欄與「常見空格與來源」欄配對 | 反例給出錯誤形態，正例給出合格門檻。兩者並置才能讓讀者判斷自己填的落在哪一側 |
| 一個容器條目含排列不變式 | 該節已有「不觸發」策略的公式形態，但無完整條目 | 公式是片段，讀者不知道三項不變式在同一條目裡怎麼並存 |
| 一組畫面票的 how 與 acceptance | 派發語言章有句型模板 | 模板是單句，一個畫面有多狀態多容器時的完整寫法無示範 |
| 一組歸併與不歸併的判斷對照 | 無對應反例 | 唯一完全缺的一類。規則寫「語意相同者歸併」，判斷兩者語意是否相同才是難處 |

第四類仍是最關鍵的一類，且是四類中唯一沒有現成反例可配對的——這反而說明它為什麼難：連常見錯誤都沒被歸納出來，因為錯的方式不只一種。

### 範例的篇幅與位置需先估

一個完整的十一欄位條目按範本格式估計四十到六十行，四類加起來可能一百五到兩百行，接近現行主檔的規模。這使「範例放哪裡」不是收尾細節而是前置決定：

- 放主檔會讓主檔翻倍，違背拆分的初衷
- 放單一 references 檔則該檔比主檔還大，讀者要為了看一個欄位的正例載入全部四類
- 依時機分散到各外移檔，則同一情境被切斷，讀者建立不了連貫脈絡

三個選項各有代價，需在執行時實際寫出第一類後才有依據判斷——一個條目實際多長、四類之間的交叉引用有多密，估計值不可靠。**執行順序因此定為：先寫第一類範例，量出實際篇幅與交叉密度，再定拆分邊界與範例位置。**

### 虛構情境的取捨

前次規劃「用一個虛構但完整的情境貫穿四類」，這個選擇有代價未評估：虛構情境可能不夠真實而失去說服力。真實案例之所以有用，正因為它帶著真實的髒亂——欄位之間的衝突、來源不可得的待決、上一版的漂移。虛構情境容易寫成每一欄都填得漂亮的樣板，而那正是讀者實際填不出來的部分。

折衷方向是虛構情境刻意保留兩到三處不完美：一欄標「待決」附決策票、一欄的來源與另一欄衝突、一個候選經存在必要性檢視被否決並記為反例。這樣正例同時示範了「不完美但合格」的樣子，而合格門檻正是讀者最需要知道的。

此取捨在執行時確認，不預先定案。

前次寫「主檔留約 74 行，接近 `ux-design-evaluation` 的 102 行形態」。查該 skill 的 references 實際規模後，這個類比誤導：

### 真正的拆分軸是角色，不是時機也不是模式

零引用的章節（三種起點、模式 A/B/C、存在必要性、容器亦為元件）有共同點：它們全屬**產出契約**的階段。高頻的三項（十一欄位、排列不變式、派發語言）全屬**消費契約**的階段。

這個 skill 實際有三種使用者，現行主檔把三者的內容交錯排列：

| 角色 | 讀什麼 | 頻率 |
|------|--------|------|
| 產出者（撰寫元件庫規格） | 三種起點、模式 A/B/C、存在必要性、容器亦為元件 | 一個版本一次 |
| 派發者（PM 寫畫面票與元件票的 how） | 派發語言、契約齊全的定義 | 每張票一次 |
| 執行者（元件票與畫面票的實作） | 十一欄位、排列不變式 | 每張票多次 |

數量級差異極大：一次規格撰寫對應四十四張實作票。**現行主檔對佔絕大多數的執行者訊噪比最差**——他要的兩節散在 245 行裡，且與他永遠用不到的三種起點、模式 A/B/C 交錯。

前次提出的「依時機拆」比「依模式拆」正確，但仍不是最佳軸——時機是角色的衍生物，同一個角色的內容在時機上本就相鄰。依角色拆能同時解決訊噪比與跳轉次數兩個問題。

那 44 張票全屬消費端（元件實作票），所以這份紀錄只回答「消費階段查什麼」。產出階段的使用頻率無樣本——本專案只寫過一次元件庫規格，且是在 skill 建立之前。
