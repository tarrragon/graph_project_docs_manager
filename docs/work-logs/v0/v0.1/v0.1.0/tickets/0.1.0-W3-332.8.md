### 實驗執行

#### 狀態 1：未載入（`state-tickets-unloaded`）

**【輸入】** SPEC-001 §4 未載入列：顯示「載入 N 張 ticket」+ 預估耗時；可用操作為開始載入、返回；首次進入此畫面。SPEC-003 §3.4 生命週期：隨 IndexedStack 建構但不觸發解析，首次可見進入此態，須使用者按 `action-tickets-start-load`。退出路徑：`action-tickets-back` → returnTo（null 時不渲染）。

**【產出】** 選件與排位（自頂向下）：
- 頂部工具列：返回按鈕（`action-tickets-back`，returnTo 為 null 時不渲染）+ 專案切換入口（`project-switcher-entry`）
- 主區：載入提示卡——標題文字含 N（票數）+ 預估耗時 + 開始載入按鈕（`action-tickets-start-load`）

| 元件 | 語意 | 關鍵契約欄 |
|------|------|-----------|
| 返回按鈕 | 返回來源畫面 | returnTo 為 null 時整個元件不渲染；非 null 時 enabled 恆 true |
| 載入提示卡 | 告知票數與耗時 | N 值來源：猜測為該專案 docs 下 ticket 檔案數的預掃描結果 |
| 開始載入按鈕 | 觸發解析 | 點擊後自身消失，進入載入中態 |

**猜測點 G1**：N 值（票數）的來源——spec 說「N 為該專案實際票數」但未說明 N 如何取得（預掃描檔名？讀 todolist.yaml？）。skill 與 spec 皆未引導。**缺口來源：spec**。

**猜測點 G2**：預估耗時的計算方式——spec 僅說「預估耗時」但未指出計算依據（每票解析時間 × N？固定公式？）。**缺口來源：spec**。

**猜測點 G3**：載入提示卡的元件形態——是獨立元件還是空狀態元件的一種變體？skill（component-contract-design）的判準問「它對使用者的語意是什麼」，語意為「引導使用者觸發載入」，與空圖/無 ticket 的「告知無資料」不同，推斷為獨立元件。**缺口來源：skill**（元件候選判準未明示此類「引導觸發」元件的歸屬）。

**【驗證】**
Given 首次進入 Ticket 清單畫面且 returnTo 非 null
When  畫面渲染完成
Then  主區顯示載入提示卡含票數 N 與預估耗時，開始載入按鈕可操作，返回按鈕可見

Given 首次進入 Ticket 清單畫面且 returnTo 為 null
When  畫面渲染完成
Then  返回按鈕不存在（不渲染），導覽列仍可用

**【產出】** 選件與排位：

| 元件 | 語意 | 關鍵契約欄 |

**猜測點 G4**：進度條是線性進度條還是圓形？spec 僅說「進度條」，未指定形態。推測為線性（與骨架版面的水平走向一致）。**缺口來源：spec**。

**【驗證】**
Given 使用者已按開始載入，10 張 ticket 中已解析 3 張
When  畫面更新
Then  進度條值為 3/10，筆數文字顯示 3

2. **「排位」推導對跨畫面一致性的依賴過度**：G5 的取消按鈕位置猜測依據「與其他畫面一致」，但 SPEC-004 實際以獨立元件內嵌。skill 的排位引導應提示「跨畫面一致性是候選假設而非判準」。

4. **組合樹與文字描述的轉換成本**：SPEC-004 以 `Panel[Toolbar, DataTable.virtual[...]]` 形式表達選件與排位，而盲推導以自然語言表。比對時需人工翻譯，後續批次可統一為組合樹形式提高比對效率。
