why: '同一工作日內，三則新寫的判準或理由各自在被第一次實際套用時才暴露缺陷，寫的當下三者都通過了作者自檢：


  一、一則錯誤模式的歸屬判準句寫成「覆核者若去查證這個手段本身，會不會得到屬實？會，就是本骨架」，缺少「已判定此處存在缺陷」這個前提，因而會吞掉全部正確的工作。

  二、一份 hook 輸出的前十列被當成母體樣本用以推論組成分佈，實際上該輸出是排序的，前十列是字典序的頭而非樣本。

  三、一則結論正確但其機制解釋錯誤的陳述，被另一方當成前提往下推一層後才暴露。


  三者的共通點不是「都寫錯了」，是**正例套用都不會攔下它們**：拿一個真的誤用去套那個判準，它判對；那十列確實都屬同一前綴；那個結論確實正確。**只有反例套用會當場產生矛盾**——拿一個完全正確的引用去套該判準，它同樣判「屬實 → 是本骨架」；問「母體若不是這個組成，樣本會長得不一樣嗎」答否即知零鑑別力；問「若這個機制不成立，結論會變嗎」答否即知理由未承重。


  現行 add 流程的步驟 5「提出預防措施」不要求任何反例，因此判準的鑑別力從未在撰寫當下被檢驗。這不適合寫成一則新的錯誤模式——錯誤模式須被 query 才會出現，而正在寫判準的人不會想到自己可能正在犯錯（opinionated-default-design 的信號判準：需要寫文件提醒使用者遵守，即代表工具預設行為還有改善空間）。正確落點是產出流程本身，使它在每一次撰寫時強制觸發。'
