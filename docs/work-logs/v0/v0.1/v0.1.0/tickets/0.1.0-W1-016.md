## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因
lib/ 內 FlutterError.onError、PlatformDispatcher.instance.onError、runZonedGuarded 三者皆 0 命中，未預期例外會讓畫面停在半渲染狀態、不崩潰不留痕跡（W1-013 裁決）。

### 影響範圍
lib/main.dart（新增三層攔截與單一出口）、lib/workspace/workspace_repository.dart（既有 1 個 `on FileSystemException catch (e)` 靜默降級，補上診斷日誌）。

### 訊息文案缺口（NeedsContext 前置說明）
單一錯誤出口的「app 級最後手段顯示」需要一段使用者可見文字。逐一核對 lib/l10n/app_zh.arb 全部 116 個既有 key，無任何一個語意適用於「未預期系統例外」（皆綁定特定情境：workspace 不可用、schema 不相容、專案非框架專案等）。依票面約束「若缺 key 停手記 NeedsContext 不自造字串」，未新增 ARB key，改以例外物件本身的 `toString()` 作為顯示內容（真實診斷文字，非虛構 UI 文案），詳見 Solution 與 NeedsContext。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 三層攔截 + 單一出口

lib/main.dart 新增：

- `installGlobalErrorHandlers()`（@visibleForTesting）：接線框架層 `FlutterError.onError`（Widget build/layout/paint 例外）與平台層 `PlatformDispatcher.instance.onError`（engine/platform channel 例外）。
- `main()`：呼叫 `installGlobalErrorHandlers()`，再以 `runZonedGuarded` 包 `runApp`，接線非同步層（未 await 的 Future/Stream 例外）。
- `reportFatalError(source, error, stack)`（@visibleForTesting）：三層共同的單一出口，先 `developer.log`（level 900，含 error/stackTrace，符合觀測性規則 2）記診斷日誌，再寫入 `fatalErrorNotifier`（`ValueNotifier<Object?>`）。
- `FatalErrorGate`（@visibleForTesting）：包住 `AppShell`，`ValueListenableBuilder` 監聽 `fatalErrorNotifier`；非空時以 `BlockedState.plain` 取代原內容，`message` 直接顯示 `error.toString()`——理由見 NeedsContext（無適用既有 ARB key，顯示真實例外文字而非虛構 UI 文案）。`onSwitchProject` 清空 notifier 供使用者「重試」。

### 既有 catch 檢視

`lib/workspace/workspace_repository.dart` 的 `on FileSystemException catch (e)` 原本靜默降級為 `WorkspaceUnavailable`，補上 `developer.log`（level 900）記錄診斷日誌，符合觀測性規則 1（catch 後 return 預設值必須記錄 warning）。`on StateError {}`（空資料夾）維持原樣，已有註解說明靜默原因，符合規則 1 空 catch 例外條款。

### 自檢結果

- `fvm dart analyze lib test`：0 issues
- `grep -rn "catch (_) {}" lib`：0 命中
- Phase 4 結論：新增程式碼量小（單一檔案接線 + 一個 gate widget），無重複邏輯、無跨 domain 混合，函式皆在 10 行內、單一職責清楚。**結論：無需重構**（品質 A）。

## NeedsContext
- **缺失項**：單一錯誤出口的 app 級最後手段顯示（acceptance 第 2 項）需要一段使用者可見文字，lib/l10n/app_zh.arb 全部既有 key 皆綁定特定情境（workspace 不可用 / schema 不相容 / 專案非框架專案等），無適用於「未預期系統例外」的通用文案。

- **影響**：目前 `message` 顯示 `error.toString()`（真實例外診斷文字），非固定 UI 文案；功能上符合「使用者看得到、非畫面靜止」，但不是票面預期的「既有 ARB key」路徑，也非精心設計的使用者導向文案。
- **建議補料**：PM 裁決是否新增 ARB key（如 `unexpectedErrorMessage`）供此情境使用；若採此路，需同步中英兩份 arb 並 `flutter gen-l10n` 重新生成 `lib/l10n/app_localizations*.dart`。
- **重派成本**：低——僅需新增一組 key + 一行程式碼改動（`message: l10n.unexpectedErrorMessage`），不影響本票已完成的三層攔截架構。
