### Rationale Chain
- 0.1.0-W3-225 why: 實證事件鏈（世界平面查證，非轉述）：
1. 219 執行者以 ticket track commit（隔離索引）提交 2cd3765a；其回報稱過程中連續遇 HEAD.lock 與 refs/heads/main.lock 競爭，經 lsof 確認無持有者後手動移除鎖檔並自行 update-ref fast-forward。
2. 222 執行者依規則七精確 add 自己的 ticket md、核對 index 後裸 commit 81517539；該 commit 除 ticket md 外帶入 domain-event-modeling.md 與 decision-record-template.md，方向為「移除 219 剛加的到達類別與級別欄」——即共用 index 中兩檔的過期 entry（219 之前的內容）被寫回 main。
3. git diff 2cd3765a 對兩檔的工作區為 0 行，證明工作區仍是 219 定稿；PM 已重新 stage 並以 794c553c 還原。

這是 bash-tool-usage-rules 規則七「版本邊界（過期 index 快照）」與「隔離索引 CAS 的時間維度要件」已描述的形態：CAS 推進 HEAD 後，共用 index 中重疊的既有 entry 全部過期，配方收尾須清理。本案的疑點是清理為何沒發生——最可能是 219 的手動鎖移除加 update-ref 路徑繞過了 ticket track commit 的收尾清理，或該命令根本沒有實作收尾清理。兩者對策不同，須查程式碼。

222 執行者另指出第二個縫隙：規則七的「核對」與「commit」之間若插入等待（鎖重試），其他代理人的 git add 可插入而不被發現；現行條文未要求核對必須緊鄰 commit。
