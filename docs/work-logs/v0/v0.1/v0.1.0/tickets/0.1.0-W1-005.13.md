### 問題根因
建立容器 ListRow（SPEC-004 4.40、5.14）。契約已齊，實作只依契約，無設計決策空缺。

### 影響範圍

### 契約差異記錄
- leading/trailing 依契約可為 ExpanderIcon/AppIcon/Badge/StepNumber 或
  Badge/AppIcon/AppText.caption/IssueMarker 多種型別，且 StepNumber、
  IssueMarker 尚未建立於 lib/components/，故以 Widget 承接（與 AppButton
  leading 已記錄的契約差異同一慣例）；primary/secondary 型別維持嚴格
  AppText，未偏離契約。
- sectionHeader 主文字需 emphasis + accentStrong，但 AppText 無
  accentStrong 顏色參數；ListRow 讀出呼叫端傳入 AppText 的 text 重繪為
  契約色 Text，primary 的型別契約（恰一個 AppText）不變，僅呈現手段不同
  （檔頭 dartdoc 已記錄）。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
實作 ListRow（lib/components/list_row.dart），五個變體對應 SPEC-004
4.40：tree / sectionHeader / item / meta / numbered，皆用私有共用建構子
+ 五個具名建構子，asserts 驗證 slot 契約（secondary 僅 item 接受）。

尺寸契約：tree/sectionHeader/meta/numbered 高固定 LayoutSize.rowHeightDense；
item 為固有高（primary+secondary 兩行 + 2×Space.sm 垂直內距）+ 頂邊框
AppColors.border。leading/trailing 與文字塊間距 Space.sm（5.14 最小間距，
Row 天然承載不重疊）。sectionHeader 用 Semantics(header: true)；tree/item
用 MergeSemantics + Semantics(button: true) 包 InkWell，leading
（ExpanderIcon 自帶 InkWell）點擊由內層 Widget 消化，不觸發列 onTap
（Flutter 巢狀可點元件慣例，測試已驗證恰一次觸發）。

Phase 4 結論：程式碼品質 A（無需重構）。五變體集中於單一 private
constructor + asserts，重複度低；尺寸/色彩全引用 token，無硬編碼；未發現
周圍技術債務。
