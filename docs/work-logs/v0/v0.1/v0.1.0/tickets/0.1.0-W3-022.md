### Round 3 Steelman 對兩個門檻的攻擊（本票最強的材料，主 session 已逐項複核數字）

**B1：「兩個門檻互補、單量一個必有一類漏網」的對稱性是假的。**

論證骨架是對稱句：行數對繁中失效 ∧ 字元數對英文失效 → 單量一個必有一類漏網。
兩個合取項的證據不同質：

| 合取項 | 引用證據 | 實際證明了什麼 |
|--------|---------|---------------|
| 行數對繁中失效 | 245 行通過 500 門檻、15,015 字元 ≈ 11.5k tokens | **指標本身失效**——每行字元數無上界，行數不攜帶 token 資訊 |
| 字元數對英文失效 | 7,584 字元 ASCII skill 依 6,500 判超標、實則約預算 38% | **常數套錯**，非指標失效。套英文欄 20,000 則 7,584 < 20,000，字元指標給出正確判定 |

換算表存在之後，字元指標零個已記載的失效案例，行數指標一個。對稱句只有一半站得住。

**500 行門檻在換算表存在後是嚴格被支配的**（窮舉讀者知識狀態）：判得出語言比例 →
能直接估 token，行數不提供額外資訊；判不出 → 行數同樣救不了（245 行 / 11.5k tokens 即
行數通過而 token 超標）。而 Action 是 OR 合併，**較嚴的那個永遠是實際生效的閘門**——對
英文內容而言，較嚴的是那個不量測任何東西的行數。

此處另有一項教訓只套用了一半：`writing-the-body`〈一則完整走查〉的結論是「兩個判準只有
一個附了動作時，生效的永遠是有動作的那個」，該次修法為第二個判準補上了動作，**但沒回頭問
合併規則對不對**——補完動作之後，失效的判準不再是沉默的，而是變成主導的。

**B2：兩個換算係數一個有實測、一個沒有；而支持沒有實測那個的「實測」是它自己的商。**

| 欄 | 依據 | 複核 |
|----|------|------|
| 繁中 1.3 | hook 的 `CHARS_PER_TOKEN`，2026-06-12 `/context` 實測 | 屬實，可重算（38.9k tokens vs 50.7k chars） |
| 英文 約 4 | 「一般 BPE 分詞的常見比值」 | **無來源、無量測、無推導** |

而支持該係數的「約 1,896 tokens」正是 **7,584 ÷ 4 = 1896.0（整除）**——證據由結論產生。

兩個實際問題：
(a) **1.3 被用在校準範圍之外**。hook 註解逐字寫「繁中為主集合」，而 `SKILL.md` 自身
    非 ASCII 佔 **38%**（主 session 實測：總 7,422 字元、ASCII 4,566、非 ASCII 2,856），
    不是「繁中為主」。條文引用了這句 caveat 卻沒有據以行動。
(b) **「混合內容取兩者之間」不可執行**，且運算形狀就是錯的——token 數是分段的和，
    不是全檔比例的內插。同一份 SKILL.md 三種方法三種結論（主 session 複核）：

| 方法 | 結果 |
|------|------|
| 繁中 6,500 | 7,422 > 6,500 → 超標 |
| 「取兩者之間」 | 落在 6,500–20,000 區間內 → **判不出來**（區間本身就是不判） |
| 分段加總 4,566/4 + 2,856/1.3 | ≈ **3,338 tokens** → 通過，離 5k 有 33% 餘裕 |

**主 session 的自我更正**：本 session 兩次回報「兩個官方門檻皆通過」，用的是**內插門檻**
（6500 + ascii_ratio × 13500），而該公式**不在文件內**，是我自己造的。文件內的方法（「取
兩者之間」）在這份檔上判不出來。結論碰巧與分段法一致，但依據是自造的，該回報應視為
「以未載明的方法得到的判定」而非「依文件判定通過」。

建議修法（合併 B1/B2）：主判準改為分段 token 估算並直接與 5k 比較，行數降為「官方合規 +
不做換算時的粗篩：超標即外移，通過不代表合格」；刪「字元數對英文失效」與由它推出的對稱句；
英文側係數若補不到來源，依據欄改寫為「無實測，取 3–4 的寬鬆側」並說明方向。

**B3：「拆分既有 skill 另有程序」預設了拆分＝搬移，重寫從未被列為選項。**
該檔「重寫」一詞零出現。把五類必查項逐一問「換成從素材重寫還會發生嗎」：節界、H1 與檔名、
跨檔指涉三類**否**（皆為搬移方法的產物）；共置關係是拆分前的內容問題、與方法無關；外部引用
兩條路徑等同。整份程序的核心賣點在重寫路徑上大部分不成立，而文件沒說它假設了搬移。
反方最強辯護（成立，且正是該寫進去的判準）：重寫會讓已審過的內容重新暴露於新錯誤——本批
修法兩輪各引入一個新缺陷即為現成證據。前提在某個範圍內成立，只是那個範圍從未被寫下來。

### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` fails or is
unavailable) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.

### 實驗執行

**(b)**：`grep -rn "一層深"` 命中 2 處（`SKILL.md` 發布前檢查清單、`writing-the-body.md` 引用規則表）。違反處：六份 reference 的檔頭「同目錄」段各列出其餘五份，另 `writing-the-body.md`／`splitting-an-existing-skill.md`／`seeing-like-an-agent.md`／`patterns-and-troubleshooting.md` 的「亦由此進入」段再指向彼此。以「禁止 A → B → C」字面判，六份全違反。以「一跳可達」判，六份檔名全部出現在 `SKILL.md` 路由表，零違反。

**(c)**：SKILL.md 的 `wc -l` 與字元量測指令，套「通用程式知識 → 移除」判為該移除；而它們正是第 2 層門檻唯一的執行手段（同檔 Consequence 段載明本層無 hook 執法、完全依賴自查），移除即等同取消該門檻。

**(d)**：對三段範例問「Claude 走錯一步會壞掉嗎」，三段都答不出來——「審查報告少一個欄位」不對應任何可觀測的壞。而同節代價段把「產物形態每次都不同」列為該低而給高的代價，若採此定義，中段的骨架與高段的目標描述都會使形態不同，三段全判為低。

**(e)**：同一份 SKILL.md（改寫前 7,773 字元、ASCII 佔 60%）三種方法三種結論：

| 方法 | 結果 |
|------|------|
| 單一 6,500 字元門檻 | 7,773 > 6,500，超標 |
| 「混合內容取兩者之間」 | 落在 6,500–20,000 區間內，判不出來 |

另量得三層表第 3 層預算欄逐字寫「無上限」，而 `writing-the-body.md` 的 TOC 條文與 W3-019 對 `patterns-and-troubleshooting.md`（6,513 字元）判「微幅超標」都是逐檔判——條文與實務對第 3 層是否有單檔判準給相反答案。

### 實驗發現

**已驗證的事實**：

1. (b) 的規則被本 skill 六份 reference 全數違反，且違反行為正是 `splitting-an-existing-skill.md`〈結構約定〉強制要求的產物——規則與規則互相衝突，不是使用者疏失。
2. (c) 的兩側不互斥：「Claude 知不知道」與「Claude 預設會不會這樣做」是兩個獨立維度，「知道但預設不會做」這一格在原判準下無位置，會被歸入「通用知識 → 移除」。
3. (d) 的「壞掉」在文件內無定義，且代價段的定義若成立，三級表塌成一格。實測三段範例在原判準下全部無法歸類。
4. (e) 的三種算法對同一份檔案給出「超標／判不出來／通過」三種結論；第 3 層「無上限」與實務逐檔判相矛盾。
5. (f) 的三個口徑單位不同、互不換算，對同一份 description 給出相反的行動建議。

**仍未驗證的假設**：

- ASCII 側換算係數 4 無實測來源（沿用票內 B2 的判定）。本次維持該值但在條文中明寫「無實測、取 3–4 的寬鬆側、誤差方向是放行」，未做新的量測。
- 第 3 層單檔門檻沿用第 2 層的 5k，理由是「整份進 context 的成本同性質」，此為推論而非實測；已在條文中以「讀取方式」而非新常數表述，降低該推論的承重。

## Solution
### 分析結論

七組中五組已重新設計並落地，(a)(g) 依派發note 暫緩、已建票承接（見下方 Spawn 落地確認）。每組的替代判準都改為**可由第三方跑出同一個答案**的形式，並各附一個本 skill 自身的邊界情境。

### 五組替代判準

| 組 | 舊判準 | 新判準 | 為何可外部驗證 |
|----|-------|-------|--------------|
| (b) | 引用只一層深，禁止 A → B → C | **一跳可達**：每份 reference 在 SKILL.md 路由表有自己的一列；禁的是「只能經由另一份 reference 才被發現的內容」 | 一行 `comm` 指令列出「在 reference 裡出現、但入口路由表沒有」的檔名，命中逐一判定 |
| (c) | Claude 真的不知道這個嗎（通用知識 → 移除） | **刪掉這段，Claude 的預設輸出會變嗎** | 刪除測試：拿掉該段，在乾淨 session 對同一任務重跑，比對兩次產出 |
| (d) | Claude 走錯一步會壞掉嗎 | 兩問依序：**1. 產物有機械消費者或動作不可逆嗎**（有 → 低）；**2. 多次執行的產物要互相比對或彙總嗎**（要 → 中；不要 → 高） | 消費者必須指得出是誰（哪支腳本、哪個 hook、哪一欄），指不出即為「沒有」 |
| (e) | 5k tokens 且 500 行；字元數依語言換算，混合內容取兩者之間；第 3 層無上限 | 主判準為**分段 token 估算直接比 5k**；行數降為官方合規項（仍須符合，但不攜帶體量資訊）；第 3 層「無上限」明確界定為**目錄總量**，單檔判準為**讀取方式**（整份執行量全檔、選段查閱量最大單節，門檻同為 5k） | 一行 python 指令算出整數，直接與 5k 比較；讀取方式由路由列措辭判定，本 skill 六份現況皆為選段查閱 |
| (f) | 三層表約 100 tokens／官方 1,024 字元／本框架 250 字元，三者並列 | **只有 250 字元是閘門**；另兩個標為官方硬上限與量級參考，並在同一張表給出換算值與各自的角色 | 換算欄可覆算；判定只用單一整數字元數 |

### 每組的邊界情境（新判準判得出來、舊判準判不出來）
