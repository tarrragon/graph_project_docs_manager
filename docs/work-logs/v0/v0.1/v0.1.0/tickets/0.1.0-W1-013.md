## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 裁決結論

產出為 `docs/tech-decisions.md` 補記段「2026-08-27：執行期 log 的裁決（W1-013）」。四項：

1. **維持 structured log 的延後**，重評條件與既有 tripwire 不變。
2. **全域錯誤處理三層立即建立**，不在延後範圍——它防無聲崩潰，與有無診斷系統無關。
3. **錯誤的載體是畫面不是檔案**：文件層問題進破洞報告，App 層失敗進 SPEC-001 既有的
   阻擋狀態／損壞標記元件。
4. **catch 不得靜默**：轉畫面錯誤態，或註解說明可靜默的原因。

### 關鍵發現：衝突有一半是轉述失真

CLAUDE.md 記「Stage 5 明示不寫」，查原文為「**延後**」且附重評條件與 tripwire 一列。
延後與拒絕在決策語意上不同——前者有觸發條件與觀察者，後者是關門。摘要把前者壓成後者，
使一個已處理好的決策在待決清單裡變成擋住整個維度的死結。

逐條比對後，`observability-rules` 五條中只有規則 4 的「啟動／關閉例行 log」落在延後範圍。
規則 1（catch 不得靜默）、規則 3（全域三層）、規則 5（平台互動）講的是「失敗時資訊不要消失」，
與「建一套 log 系統」不是同一件事，先前被當成同一件事。

實測依據：`lib/` 五檔中 `FlutterError.onError`／`PlatformDispatcher.instance.onError`／
`runZonedGuarded` 三者皆 0 命中；catch 1 個、log 0 個、print 0 個。

### 對地基盤點的影響

可觀測性維度產物由權威預設的「log 接線點、錯誤分類骨架」**改寫為「錯誤到畫面的接線」**。
此為 `foundation-design` 的「改寫產物」形態：維度成立、預設產物對本形態不適用，改的是
產出什麼而非跳過維度。推導問句的答案——可觀測性防「出事了但沒人知道」，在單機唯讀無伺服器
的桌面工具上，它長成「出事時使用者在畫面上看得到，而不是畫面卡住不動」。
