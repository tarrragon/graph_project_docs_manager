# Execution Log

## Task Summary

評估 選填章節留存未填樣板的偵測形態與掛載點

---

## Problem Analysis
### 問題根因

`check_execution_log_filled`（`acceptance_checkers/execution_log_checker.py`）只檢查 Solution AND Test Results 兩個章節（ANA 額外 OR 檢查「重現實驗結果」）。Problem Analysis 不在其檢查範圍內，且 DOC 類型直接豁免整個檢查。結果是：選填章節可以原封不動保留建票時的樣板文字（如「（選填：問題如何發現？直接原因是什麼？）」），complete 時沒有任何訊號。

樣板文字來自 `ticket_builder.py` 的 `_TYPE_PLACEHOLDERS` 字典（建立端唯一權威），以四種前綴（「必填」「選填」「免填」「待填寫」）+ 全形括號格式產生。Problem Analysis 章節另含三個 H3 子標題骨架（`### 問題根因` / `### 影響範圍` / `### 相關 Error Pattern`）與一個 HTML 註解範本。

**為何現有檢查不涵蓋**：`check_execution_log_filled` 的 AND 邏輯要求 Solution 與 Test Results **同時為空**才標記為未填。只要其中一個有實質內容，另一個的樣板殘留即被遮蔽。Problem Analysis 則完全不在迴圈內。

### 影響範圍

**已驗證事實**（以 grep 掃描 339 張 0.1.0 tickets）：

| 類型 | 已完成數 | PA 保留選填模板 | Test Results 保留模板 |
|------|---------|---------------|---------------------|
| IMP | 115 | 40（35%） | N/A（IMP TR 必填，另有檢查） |
| DOC | 120 | 67（56%） | N/A（DOC 豁免整個檢查） |
| ANA | 30 | N/A（ANA PA 必填） | 15（50%） |

120 張已完成 ticket 含至少一個選填章節的樣板殘留——約佔全部已完成票的 35%。

偵測基礎設施已可正確識別 PA 模板殘留（`_is_section_empty` 四層剝除後為空即判為空殼）。缺口不在偵測能力，在於編排層未將 PA 納入檢查。

### 相關 Error Pattern

- `PC-GPD-008`：未填樣板通過數量型檢查
- `PC-GPD-009`：驗證器驗的維度與缺陷所在維度不同軸

## 重現實驗結果
### 實驗方法

驗證兩個問題：(1) 現有偵測基礎設施 `_is_section_empty` 能否識別各類型選填章節的模板殘留；(2) 實際 complete 流程中這些殘留是否被檢查覆蓋。

驗證 (1)：以 Python 模擬 `_is_section_empty` 的四層剝除邏輯，輸入 IMP 的 Problem Analysis 完整模板文字。
驗證 (2)：以 grep 掃描所有 0.1.0 已完成 ticket，統計各類型各章節的模板殘留率。

### 實驗執行

**實驗 1：`_is_section_empty` 偵測能力**

輸入為 IMP Problem Analysis 全文模板（含三個 H3 子標題 + 三個選填佔位符 + HTML 調查過程範本）。四層剝除流程：
1. Strip HTML comments → 移除 `<!-- 調查過程記錄... -->`
2. Strip `---` separators → 無變化（PA 內無分隔符）
3. Strip H3+ headers → 移除 `### 問題根因`、`### 影響範圍`、`### 相關 Error Pattern`
4. Strip placeholder patterns `（選填：...）` → 剩餘內容為空

結果：`_is_section_empty` 回傳 True。偵測能力已具備。

**實驗 2：模板殘留率統計**

掃描 339 張 0.1.0 tickets：
- 已完成 IMP 115 張中 40 張（35%）PA 保留「（選填：問題如何發現...）」
- 已完成 DOC 120 張中 67 張（56%）PA 保留「（選填：文件變更的背景...）」
- 已完成 ANA 30 張中 15 張（50%）Test Results 保留「（選填：若有實驗輸出...）」
- 所有類型合計 120 張已完成 ticket 含選填章節模板殘留（約 35%）

**實驗 3：`check_execution_log_filled` 覆蓋範圍確認**

閱讀 `execution_log_checker.py` 原始碼：
- 檢查對象僅 Solution + Test Results（AND 邏輯）、ANA 加查重現實驗結果（OR 邏輯）
- Problem Analysis 不在任何型別的檢查範圍
- DOC 整體豁免（`_EXEMPT_TYPES = {"DOC"}`）

### 實驗發現

**已驗證事實**：
1. `_is_section_empty` 偵測能力充分——能正確識別 IMP/DOC 的 PA 模板和 ANA 的 TR 模板為空殼
2. `check_execution_log_filled` 不檢查 Problem Analysis（所有類型），且 DOC 整體豁免
3. 35% 的已完成 ticket 含至少一個選填章節的模板殘留

**未驗證假設**：
1. 尚未驗證「偵測後加 WARNING 對使用者行為的影響」——可能使 complete 變得更難通過而收益不明
2. 尚未評估「模板殘留是否真的造成讀者誤解」——35% 的比率意味著這是常態而非例外，讀者可能已學會忽略

## Solution
### 前提：偵測基礎設施已就緒

`_is_section_empty`（`execution_log_checker.py`）的四層剝除邏輯已能正確判定選填章節的模板殘留為「空殼」。缺口僅在編排層——`check_execution_log_filled` 未將 Problem Analysis 納入、DOC 整體豁免、AND 邏輯遮蔽單章節殘留。

---

### 候選方案

### 方案 A：在 acceptance-gate-hook 新增 per-section 模板殘留 WARNING

**做法**：新增一個 checker 函式（如 `check_template_residual`），在 complete 前對該 ticket type 的每個「選填」章節逐一呼叫 `_is_section_empty`，若章節在剝除前有可見內容、剝除後為空，則產出 WARNING（非阻擋）列出殘留章節名。

**涵蓋的樣板情形**（依 PC-GPD-009 要求明列）：

| 情形 | 是否涵蓋 | 判準 |
|------|---------|------|
| 章節僅含 `（選填/必填/免填/待填寫：...）` 全形括號佔位符 | 涵蓋 | `_PLACEHOLDER_PATTERN` 剝除後為空 |
| 章節僅含 H3 骨架 + 佔位符（如 IMP PA 的 `### 問題根因` + `（選填：...）`） | 涵蓋 | H3 headers + placeholders 剝除後為空 |
| 章節僅含 HTML 註解範本（如 NeedsContext/Exit Status/Spawn Requests） | 涵蓋但不必要 | 這些章節的 HTML 範本渲染後不可見，讀者不會被誤導 |
| 章節完全空白（僅 header + 可能的 `---` 分隔符） | **不涵蓋（by design）** | 這是「選擇不填」的誠實表達，不應告警 |
| 章節包含部分真實內容 + 部分殘留模板 | **不涵蓋** | 剝除佔位符後仍有內容 → 非空殼 → 不告警。此為 `_is_section_empty` 設計邊界 |
| 章節模板被改寫但語意未變（如把「問題如何發現？」改為「問題怎麼發現的？」） | **不涵蓋** | 改寫後不匹配 `_PLACEHOLDER_PATTERN`，被視為實質內容 |
| 未來新增的佔位符前綴（目前 4 種：必填/選填/免填/待填寫） | **不涵蓋** | 需同步更新 `_PLACEHOLDER_PREFIXES` |

**掛載點**：`acceptance-gate-hook.py` 步驟 6 之後，新增步驟 6b。

**Type-aware 規則**（依 `ticket-body-schema.md`）：

| 章節 | ANA 檢查？ | IMP 檢查？ | DOC 檢查？ |
|------|-----------|-----------|-----------|
| Problem Analysis | 不檢查（必填，由既有步驟覆蓋） | 檢查（選填） | 檢查（選填） |
| Solution | 不檢查（必填） | 不檢查（選填，但已由步驟 6 覆蓋） | 不檢查（免填，DOC 豁免） |
| Test Results | 檢查（選填） | 不檢查（必填） | 不檢查（免填，DOC 豁免） |

**利**：
1. 不改建票流程，對既有 ticket 和新 ticket 皆有效
2. 複用現有 `_is_section_empty` 基礎設施，實作量小
3. WARNING 級別不阻擋 complete，誤報成本低
4. 涵蓋範圍聲明明確（上表），讀者知道守衛看了什麼、沒看什麼

**弊**：
1. 35% 的已完成 ticket 含模板殘留——若追溯套用，初期 WARNING 會非常頻繁
2. 「選填但留模板」vs「選填且不填」的語意差異，WARNING 文字需謹慎措辭
3. 不涵蓋部分填寫和改寫形態，守衛仍有盲區（但已明寫，符合 PC-GPD-009 要求）

### 方案 B：建立端消除——選填章節模板從可見文字改為 HTML 註解

**做法**：修改 `_TYPE_PLACEHOLDERS` 中所有「選填」前綴的值，從 `（選填：...）` 改為 `<!-- 選填：... -->`。新建票的選填章節將只有 H3 骨架 + HTML 註解（渲染後不可見），不會產生「看起來像有內容」的視覺欺騙。

**涵蓋的樣板情形**：

| 情形 | 是否涵蓋 | 判準 |
|------|---------|------|
| **新建票**的選填章節樣板 | 涵蓋 | 模板改為 HTML 註解後渲染不可見，`_is_section_empty` 也會正確判為空 |
| **既有票**的選填章節樣板殘留 | **不涵蓋** | 已產生的模板文字不會追溯修改 |
| 必填章節的佔位符（「（必填：...）」） | **不涵蓋（by design）** | 必填佔位符的可見性是刻意的——它提醒執行者必須填寫 |
| H3 骨架留存（`### 問題根因` 等子標題無後續正文） | **不涵蓋** | 改的只是佔位符文字，H3 標題仍保留（但 H3 + 空白本身在渲染上不如 H3 + 佔位符文字那麼像「有內容」） |

**掛載點**：`ticket_builder.py` 的 `_TYPE_PLACEHOLDERS` 字典。

**利**：
1. 從源頭消除「選填模板看起來像內容」的視覺欺騙
2. 不增加 complete 流程的檢查負擔
3. 實作極簡單——改幾行字串

**弊**：
1. 不幫助 339 張既有 ticket（追溯問題完全不解決）
2. H3 骨架仍保留，「### 問題根因」下方一片空白 vs 下方有「（選填：...）」——前者可能讓不熟悉的人困惑「這裡要填什麼」
3. 對代理人的引導效果降低：代理人 Read ticket 時看不到選填章節的提示文字，可能不知道該章節「可以填什麼」（Schema 註解仍在但沒有具體提示）

---

### 結論：值得做，建議方案 A 優先、方案 B 作後續改善

**值得做的理由**：
1. 35% 的已完成 ticket 有模板殘留——這不是理論風險而是現狀。PC-GPD-008 實證的形態（「看起來像真的內容，只有大括號洩漏」）在選填章節完全成立，且更隱蔽——「（選填：...）」的括號比大括號更容易被讀者忽略。
2. 偵測基礎設施已就緒（`_is_section_empty` 四層剝除通過實測），實作成本低。
3. WARNING 級別的誤報成本極低——不阻擋 complete，最壞只是多一行提示。

**建議執行順序**：
1. **方案 A**（IMP ticket）：新增 `check_template_residual` checker，掛在 acceptance-gate-hook 步驟 6b，WARNING 級別。初期僅對 IMP PA + ANA TR 生效（最高價值子集），DOC 視 A 的 WARNING 頻率再決定是否開啟。
2. **方案 B**（後續 DOC ticket）：方案 A 上線後，評估選填章節模板是否仍有引導價值；若 WARNING 頻率穩定下降（代理人學會填或清空），再將選填佔位符改為 HTML 註解。
