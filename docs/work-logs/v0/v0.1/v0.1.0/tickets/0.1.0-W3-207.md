#### 1. Purpose

**背景**：`0.1.0-W3-184` 第三節裁定跨 domain 的注意力協調形態為單一仲裁點而非分散式協商。`docs/domain-map.md` §2.6.1 已指定仲裁器落層（L4 畫面狀態層或其下的 presentation 包裝，不得落入任一涉及 domain 內部）；SPEC-003 §2.14 已逐則指定每一則提示的到達類別、級別、標定點；§2.15／§2.16 已把讓步規則與暫停恢復寫成可驗收形態。三者都是規則，沒有任何一處程式碼在執行它們：現行三處 `AppSnackBar.show` 呼叫點（`gap_report_screen.dart:199`、`:218`、`scan_notification_controller.dart:202`）與 `main.dart:219` 的原生呼叫各自直達載體，「現在是不是請求使用者注意的適當時機」沒有任何地方在回答。

**目標**：建立一個仲裁器。各 domain 的事件在其標定點只表達「我要發出這個級別、這個到達類別的請求」，仲裁器依 SPEC-003 §2.15 的讓步規則與持有者狀態回覆一個決策（接受、跳過、拒絕、延後），並在持有者被消費時廣播「已消費」訊號，供被延後的自發型工作重驗前提後再請求。可觀察的改善：每一則進入或離開通道的請求都留下攜帶七項欄位的決策事件；跨級別的截斷只在仲裁器一處讀取持有者級別。

**非目標**：

- 不實作第三類（推送型）接收緩衝，範疇歸屬與 trigger 見第 7 節。
- 不修改任何載體的截斷行為（`AppSnackBar` 的 `hideCurrentSnackBar` 屬 `0.1.0-W3-205`）。
- 不選擇載體。載體由 SPEC-003 §2.13〈判準 T〉與 §2.14 指派表決定，發生在請求方；仲裁器不知道載體是什麼。
- 不引入提示佇列（`0.1.0-W3-239` 裁定），仲裁器不持有任何等待中的請求。
- 不暫停任何背景工作。仲裁器只裁決不做工（方法論〈核心概念〉），暫停與恢復由工作擁有者依 SPEC-003 §2.16 執行，仲裁器只提供「已消費」訊號。

```dart
/// 級別（SPEC-003 §2.14 主名；L1–L3 僅慣用名）。列舉順序即優先序，index 越大越高。
enum AttentionLevel {
  discardable,     // 可棄（L3 可補查）
  mustLeaveTrace,  // 須留痕（L2 必須知悉）；0.1 無實例，仍為合法值
  undroppable,     // 不可棄（L1 必須決策）
}

/// 到達類別（SPEC-003 §2.14 到達類別欄）。
/// 推送型刻意不存在：0.1 無接收緩衝，該類別在型別層即不可表達（第 7 節）。
enum AttentionArrival {
  waiting,      // 等待型：能回溯到一個正在等待我方回覆的外部發起者
  spontaneous,  // 自發型：開始的決定點在我方程式碼內
}

/// 來源 domain。僅列 docs/domain-map.md §2.6.2 判「是」的三者；
/// 新增來源須先在該表改判，不得在此擴充。
enum AttentionSource { workspace, schema, diagnostics }

/// 一次請求。全部欄位在標定點（SPEC-003 §2.14「標定點」欄）由請求方填妥，
/// 仲裁器只讀取、不推導。
final class AttentionRequest {
  const AttentionRequest({
    required this.id,
    required this.level,
    required this.arrival,
    required this.source,
    this.parentLevel,
    this.deadline,
  });

  /// 請求識別。與 0.1.0-W3-176 的 shown／closed 配對識別同源，
  /// 使仲裁事件與載體事件可跨層配對。
  final String id;
  final AttentionLevel level;
  final AttentionArrival arrival;
  final AttentionSource source;

  /// 子呼叫時填父請求的級別（SPEC-003 §2.14「傳播規則」欄非空的列）。
  final AttentionLevel? parentLevel;

  /// 等待型由發起者攜帶的剩餘預算；自發型為下一次排程時刻前的餘量。
  /// 缺席時仲裁器不代填，只在事件記「指派」（見 2.5）。
  final Duration? deadline;
}

/// 接受後交給請求方與載體的持有憑證；載體以它回報 presented／release。
final class AttentionHandle {
  final String requestId;
  final AttentionLevel level;
  final AttentionArrival arrival;
  final AttentionSource source;
  final DateTime acceptedAt;
}

/// 仲裁決策。動作集取自方法論〈讓步與卸載順序〉卸載順序表，本專案只用到四種。
sealed class AttentionDecision {}

/// 接受：立即呈現。preempted 非空時載體必須先截斷該持有者再呈現。
final class AttentionAccepted extends AttentionDecision {
  final AttentionHandle handle;
  final AttentionHandle? preempted;
  /// 同級別取代（0.1.0-W3-239 具名例外）時為 true，載體依 SPEC-003 §2.13
  /// 〈截斷事件的日誌等級〉留痕；跨級別搶佔時為 false。
  final bool sameLevelReplace;
}

/// 跳過：自發型／可棄在通道被高級別持有時的動作（「跳過，不補跑」）。
final class AttentionSkipped extends AttentionDecision {
  final AttentionHandle blockedBy;
}

/// 拒絕：等待型在通道被高級別持有時的動作，附可重試資訊。
final class AttentionRejected extends AttentionDecision {
  final AttentionHandle blockedBy;
  /// 可重試資訊：訂閱後於持有者被消費時收到一次通知。
  final Stream<AttentionConsumed> retryAfter;
}

/// 延後：自發型／須留痕在通道被更高級別持有時的動作。
/// 仲裁器不保存此請求；請求方訂閱 signal，收到後重驗前提再重新 request。
final class AttentionDeferred extends AttentionDecision {
  final AttentionHandle blockedBy;
  final Stream<AttentionConsumed> signal;
}

/// 持有者離開通道的原因（消費三形態 + 非消費的三種離開）。
enum AttentionReleaseReason {
  responded,     // 使用者回應（按下動作、關卡決策、授權對話框回答）
  dismissed,     // 使用者主動關閉
  expired,       // 載體自然過期（SnackBar timeout）；或仲裁器懶檢查判定逾期
  preempted,     // 被高級別搶佔、或同級別取代而截斷（由仲裁器於接受當下記錄）
  notPresented,  // 接受後載體未呈現（如 context 已卸載）
  withdrawn,     // 我方撤回（ScanNotifier.withdraw）
}

/// 「已消費」訊號的內容。
final class AttentionConsumed {
  final AttentionHandle handle;
  final AttentionReleaseReason reason;
  final DateTime at;
}

/// 目前持有者的快照（讀取用）。
final class AttentionHolder {
  final AttentionHandle handle;
  final DateTime? presentedAt;      // presented 尚未回報時為 null
  final Duration? naturalLifespan;  // 載體回報；關卡類為 null（無自然存活期）
  Duration ageAt(DateTime now);      // 最老未消費請求年齡（本專案恆等於持有者年齡）
}
```

**2.3 仲裁器介面**

```dart
abstract class AttentionArbiter {
  /// 請求佔用通道。同步、常數時間、不阻塞、不保存請求。
  AttentionDecision request(AttentionRequest request);

  /// 載體開始呈現時回報；naturalLifespan 為該載體的自然存活期
  /// （SnackBar 取 Motion.snackBar／Motion.snackBarWithAction；關卡與授權對話框傳 null）。
  void presented(AttentionHandle handle, {required Duration? naturalLifespan});

  /// 持有者離開通道。非當前持有者的 handle 只留痕不改狀態。
  void release(AttentionHandle handle, AttentionReleaseReason reason);

  /// 目前持有者；空通道為 null。
  AttentionHolder? get holder;

  /// 「已消費」廣播。每次當前持有者離開即發出一則；無訂閱者時不緩衝。
  Stream<AttentionConsumed> get consumed;
}
```

| 成員 | 輸入約束 | 回傳／副作用 |
|------|---------|-------------|
| `request` | `request.id` 非空；`parentLevel` 非空時 `level` 不得高於它 | 回傳四種決策之一；`AttentionAccepted` 時持有者記錄立即改為本請求（不等 `presented`）；`preempted` 非空時舊持有者記錄已被移除並已發出 `consumed(reason: preempted)` |
| `presented` | `handle` 為當前持有者；`naturalLifespan` 為零或負值視同 `null` 並留痕原值 | 記錄 `presentedAt` 與 `naturalLifespan`；非當前持有者時只留痕 |
| `release` | 任意 handle | 當前持有者：清空記錄、發出 `consumed`；其他：留痕 `releasedNonHolder`，狀態不變 |
| `holder` | 無 | 快照；讀取不觸發懶檢查 |
| `consumed` | 無 | 廣播 stream；`AttentionRejected.retryAfter` 與 `AttentionDeferred.signal` 皆為同一 stream 過濾為 `blockedBy` 那一筆的視圖 |

**2.4 決策規則（唯一的裁決表）**

判準引用方法論〈讓步與卸載順序〉三條讓步規則（回答「高負載時先停哪些請求？」）與卸載順序表（到達類別 × 級別）；級別比較鍵引用〈級別〉「級別是請求的屬性，不是端點的屬性」（回答「級別是靜態標註還是動態推導？」）。本表不另立判準，只把兩者對本專案「恰一筆持有者」的狀態機實例化。

先做懶檢查：持有者已 `presented` 且 `naturalLifespan` 非空且 `now - presentedAt > naturalLifespan` → 先以 `expired` 釋放並留痕，再依空通道處理。

| 持有者 H | 請求 R 的級別與類別 | 決策 | 依據 |
|----------|-------------------|------|------|
| 空 | 任意 | `Accepted(preempted: null)` | 無競爭（184 §二「競爭 = 第二個抵達時第一個尚未被消費」） |
| 級別 < R | 任意 | `Accepted(preempted: H, sameLevelReplace: false)` | 讓步規則 1「高級別抵達時可搶佔低級別」 |
| 級別 == R | 任意 | `Accepted(preempted: H, sameLevelReplace: true)` | `0.1.0-W3-239` 具名例外：規則 2 在本通道以截斷並留痕取代排隊或合併；跨載體時載體無法截斷，`preempted` 仍記為舊持有者以維持恰一筆記錄，留痕由仲裁事件承接 |
| 級別 > R | 自發型／可棄 | `Skipped(blockedBy: H)` | 卸載順序表自發型／可棄格「跳過，不補跑」；規則 3「低級別不得搶佔任何請求」 |
| 級別 > R | 自發型／須留痕 | `Deferred(blockedBy: H)` | 卸載順序表自發型／須留痕格「延後至離開卸載狀態」。本專案「離開卸載狀態」= 持有者被消費（184 §三「延遲的終點是當前注意力請求被消費」） |
| 級別 > R | 自發型／不可棄 | 不可達 | 不可棄已是最高級別，不存在更高的 H |
| 級別 > R | 等待型／可棄 | `Rejected(blockedBy: H)` | 卸載順序表等待型／可棄格「拒絕＋可重試資訊」 |
| 級別 > R | 等待型／須留痕 | `Rejected(blockedBy: H)` 且仲裁事件逐筆留痕 | 等待型／須留痕格「拒絕＋可重試資訊＋留痕」 |
| 級別 > R | 等待型／不可棄 | 不可達 | 同上；卸載順序表明寫等待型／不可棄「不由仲裁器卸載」，本表以型別層不可達滿足 |
| `H.requestId == R.id`（持有者再請求） | 任意 | `Rejected(blockedBy: H)` 並留痕 `heldAndRequested` | 方法論〈通道與仲裁器〉「禁止的是並行持有：持有一份的同時申請第二份」（回答「一個請求可不可以在持有通道時再要一份？」）。序列重借（先 `release` 再 `request`）不受此限 |

**級別傳播單調不升**：`parentLevel` 非空且 `level > parentLevel` 時，仲裁器以 `parentLevel` 裁決並留痕 `levelClamped`。這是執行既有標定而非推導級別——方法論〈級別〉「呼叫方可為子呼叫指派不高於自身的級別，不可升」（回答「一個不可棄請求發出的子呼叫算什麼級別？」）。

**與 SPEC-003 §2.13〈判準 T〉的先後**：T1–T4 在請求方執行，決定要不要暫態提示、用哪個載體、是否延後至 `resumed`；仲裁在「即將呈現」的那一刻執行，決定此刻能不能。順序為 T → 仲裁 → 載體；(b2) 延後顯示的項目在 `resumed` 當下才 `request`。

**與 `0.1.0-W3-122` 的分工**：122 把掃描觸發改為消費 `firstVisibleProvider`，解的是「掃描為何在錯誤時機啟動」；本票解的是「掃描完成後的注意力請求此刻能否呈現」。兩者正交，122 落地與否不改變本表。

**2.5 可觀測事件**

不變式引用方法論〈可觀測性〉「每一個請求離開通道都是一個可觀測事件」（回答「被丟棄的請求怎麼追溯？」）。以與 `AppSnackBarLogSink` 同形的接縫實作：

```dart
enum AttentionArbiterLogEvent {
  accepted, preempted, sameLevelReplaced, skipped, rejected, deferred,
  released, expired, releasedNonHolder, heldAndRequested, levelClamped,
}

typedef AttentionArbiterLogSink = void Function(
  AttentionArbiterLogEvent event,
  Map<String, Object?> fields, {
  int? level,
});
```

每則事件的 `fields` 至少含七項：`requestId`、`arrival`、`level`、`channel`（0.1 固定為 `userFocus`）、`decision` 或 `reason`、`occupancy`（`{inFlight: 0|1, queueDepth: 0, oldestAge: Duration?}`，三項分列不相加）、`deadlineRemaining`（為 `null` 時另附 `deadlineAssigned: true`）。

留痕粒度：0.1 三個級別皆逐筆記錄。方法論〈可觀測性〉「可棄只計數加取樣樣本」的前提是留痕本身可能成為負載；本通道的請求率受人類互動速率上界（單一使用者桌面應用），逐筆記錄不構成負載，計數退化形態不啟用。留痕載體為 `developer.log`（`name: 'AttentionArbiter'`），與被保護的通道（畫面）不共用。方法論〈旁路的存在與可靠性〉「允許有損者降級為同進程的計數」（回答「沒有旁路的系統怎麼辦？」）——本專案無 structured log 基礎設施，此為退化形態，明列不隱藏。

日誌等級：`skipped`／`rejected`／`deferred`／`expired` 對背景發起者取 warning（900），對使用者發起者取 info，鍵為發起者而非級別，沿用 SPEC-003 §2.13〈截斷事件的日誌等級以「事件的發起者」為鍵〉（發起者由 `arrival` 判定：`spontaneous` 為背景發起）；`heldAndRequested`、`levelClamped`、`releasedNonHolder` 恆為 warning（呼叫方契約違反）。

#### 3. GWT Scenarios

級別縮寫：可棄＝D、須留痕＝T、不可棄＝U。持有者以「載體／級別／類別」描述，皆為 SPEC-003 §2.14 的列。

正常流程：

- **場景 1：空通道接受等待型**。Given `holder == null`；When Diagnostics 以 `waiting`／D 請求（§2.14 列 5）；Then 回傳 `Accepted(preempted: null)`，`holder.handle.requestId` 等於請求 id，發出 `accepted` 事件含七欄位。
- **場景 2：空通道接受自發型**。Given `holder == null`；When Diagnostics 以 `spontaneous`／D 請求（列 3，於 `resumed` 當下）；Then 回傳 `Accepted`，`holder` 為該請求。
- **場景 3：呈現、消費、訊號**。Given 場景 1 的持有者已 `presented(naturalLifespan: Motion.snackBar)`；When 載體 `release(handle, expired)`；Then `holder == null`，`consumed` 發出一則 `(handle, expired)`，發出 `released` 事件。
- **場景 4：序列重借合法**。Given 授權對話框請求（列 4，`spontaneous`／D）已被接受並以 `responded` 釋放；When 同一流程以新 id 請求系統通知（列 2，`parentLevel: D`）；Then 回傳 `Accepted`，無 `heldAndRequested` 事件。

讓步規則：

- **場景 5：高級別搶佔低級別**。Given 持有者為 SnackBar／D／`waiting`；When Schema 以 `spontaneous`／U 請求（列 11）；Then 回傳 `Accepted(preempted: <SnackBar handle>, sameLevelReplace: false)`，`holder` 為關卡請求，發出 `preempted` 事件（`requestId` 為被搶佔者），`consumed` 發出 `(舊 handle, preempted)`。
- **場景 6：同級別取代（具名例外）**。Given 持有者為 SnackBar／D／`waiting`（列 6）；When Diagnostics 以 `spontaneous`／D 請求（列 3）；Then 回傳 `Accepted(preempted: <舊 handle>, sameLevelReplace: true)`，發出 `sameLevelReplaced` 事件，`holder` 為新請求。
- **場景 7：低級別自發型遇高級別持有者被跳過**。Given 持有者為關卡／U／`spontaneous`；When Diagnostics 以 `spontaneous`／D 請求；Then 回傳 `Skipped(blockedBy: <關卡 handle>)`，`holder` 不變，發出 `skipped` 事件（level 900）。
- **場景 8：低級別等待型遇高級別持有者被拒絕並可重試**。Given 持有者為關卡／U；When Workspace 以 `waiting`／D 請求；Then 回傳 `Rejected(blockedBy, retryAfter)`，`holder` 不變；關卡以 `responded` 釋放時 `retryAfter` 發出一則且 `handle` 為關卡 handle。
- **場景 9：須留痕自發型被延後、訊號後重新請求**。Given 持有者為關卡／U，請求方為測試替身的 `spontaneous`／T；When 請求得 `Deferred(signal)`，訂閱 `signal`，關卡釋放，請求方重驗前提為真後再次 `request`；Then 第一次回傳 `Deferred`，訊號恰發出一則，第二次回傳 `Accepted`，釋放後再請求前 `holder == null`（仲裁器未持有該請求）。

邊界條件：

- **場景 10：持有者再請求被拒（禁止持有並等待）**。Given 持有者 `requestId == 'r1'` 尚未釋放；When 以 `id: 'r1'` 再次 `request`；Then 回傳 `Rejected`，發出 `heldAndRequested`（level 900），`holder` 不變。
- **場景 11：逾期懶檢查**。Given 持有者已 `presented(naturalLifespan: 4s)`，注入時鐘前進 4.001s，載體未回報；When 任意新請求到達；Then 先發出 `expired` 事件並 `consumed(expired)`，再依空通道接受新請求。
- **場景 12：非持有者的 release 不改狀態**。Given 持有者為 `r2`；When `release(<r1 handle>, dismissed)`；Then `holder` 仍為 `r2`，發出 `releasedNonHolder`，`consumed` 不發出。
- **場景 13：子呼叫級別高於父級別被夾住**。Given `holder == null`；When 請求 `level: U, parentLevel: D`；Then 回傳 `Accepted` 且 `handle.level == D`，發出 `levelClamped`。
- **場景 14：無 deadline 的請求標「指派」**。When 請求 `deadline: null`；Then 對應事件 `fields['deadlineRemaining'] == null` 且 `fields['deadlineAssigned'] == true`。
- **場景 15：關卡無自然存活期不逾期**。Given 持有者為關卡／U，`presented(naturalLifespan: null)`，時鐘前進任意長；When 新請求到達；Then 不發出 `expired`，依 2.4 以關卡為持有者裁決。
- **場景 16：`naturalLifespan` 為零或負值**。When `presented(handle, naturalLifespan: Duration.zero)`；Then 視同 `null`，`presented` 事件 `fields` 附原值；之後不觸發懶檢查逾期。

異常流程：

- **場景 17：接受後未呈現**。Given 請求已被接受，載體因 `context` 已卸載未呈現；When `release(handle, notPresented)`；Then `holder == null`，發出 `released`（`reason == notPresented`），`consumed` 發出一則。
- **場景 18：推送型不可表達**。靜態檢查：`AttentionArrival` 恰有 `waiting`、`spontaneous` 兩值，無第三值。

#### 4. Error Handling

| 錯誤情境 | 處理策略 | 回傳／拋出 | 需要回滾？ |
|---------|---------|-----------|-----------|
| `request.id` 為空字串 | 拒絕進入裁決 | 開發期 `assert`；生產期回傳 `Rejected` 並留痕 `heldAndRequested` 以外的獨立欄位 `reason: emptyId` | 否 |
| 持有者再請求 | 拒絕，不改狀態 | `Rejected` + `heldAndRequested` warning | 否 |
| `level > parentLevel` | 夾至 `parentLevel` 後照常裁決 | 對應決策 + `levelClamped` warning | 否 |
| `presented` 的 handle 非當前持有者 | 忽略，留痕 | `releasedNonHolder` warning（`fields['op'] = 'presented'`） | 否 |
| `release` 的 handle 非當前持有者 | 忽略，留痕 | `releasedNonHolder` | 否 |
| 載體從未回報 `release`（契約違反） | 有自然存活期者由懶檢查以 `expired` 清除；無自然存活期者（關卡）無法自癒 | `expired` warning；關卡類停留為持有者直到狀態機退出回報 | 否 |
| `consumed` 無訂閱者時發出 | 不緩衝、不重播 | 無 | 否 |
| 請求方在 `Deferred` 後未重新請求 | 不屬仲裁器責任；自發型 deadline 為「下一次排程時刻」，於下一輪自行再請求 | 無 | 否 |
| 同一 tick 內兩次 `request` | `oldestAge` 由注入時鐘計算得零；裁決不用年齡，無影響 | 無 | 否 |

方法論〈跨執行緒與 isolate〉「仲裁器佇列深度是它自身的佔用量指標；溢出時對等待型的申請回覆拒絕」（回答「仲裁器溢出時的預設是什麼？」）：本專案無佇列，溢出分支不存在，此處明列避免讀者以為遺漏。

#### 8. 可用性單點的明寫

方法論〈通道與仲裁器〉「仲裁器與通道處於同一 failure domain 時，仲裁器不新增單點；仲裁器若是通道之外的獨立行程，它就是新增的可用性單點」回答「仲裁器會不會成為新的單點？」。

本仲裁器與通道同在 UI isolate，非獨立行程；但它是通道之外的獨立物件——持有者記錄與 `ScaffoldMessenger` 內部佇列、系統通知送達狀態、關卡狀態機三者皆不共享記憶體。因此存在「仲裁器狀態壞而通道還能動」的失效路徑，票面要求明寫：

| 失效模式 | 表現 | 防線 |
|---------|------|------|
| 持有者記錄未釋放（載體漏回報） | 之後所有低級別請求被跳過或拒絕，畫面本身正常 | 有自然存活期者：懶檢查逾期（場景 11）；`releasedNonHolder`／`expired` warning 使漏回報可被日誌發現 |
| 關卡類持有者記錄未釋放 | 同上且無法自癒 | 無上界。消費機制：Phase 3b acceptance 須含「關卡狀態機每一條退出路徑皆有 `release`」的靜態檢查（方法論〈登記類條款的消費要件〉「登記只有在連接消費機制時才算完成」回答「寫下待量測之後呢？」） |
| 訊號無人訂閱時發出 | 被延後者永不重新請求 | 第 4 節：自發型工作於下一次排程時刻自行再請求，訊號只縮短等待、不是唯一恢復路徑 |
| 對等待型 fail-closed | 使用者操作的回饋被拒 | 只在持有者為更高級別時拒絕，且拒絕附 `retryAfter`；空通道與同級別一律接受 |
