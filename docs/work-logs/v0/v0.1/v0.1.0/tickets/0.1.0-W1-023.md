## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因
0.1.0-W1-003 選項 B（版本切片）已定案為 Ticket 節點檔的規模處置方向，但因 acceptance 明確排除 work-logs 而未落地，需獨立子任務決定「切哪個版本」並落地。

### 切片標準決策
以框架自身 `doc_system.core.frontmatter_parser.parse_frontmatter_text`（逐行語意，非天真 `str.split("---")`，理由見 `docs/tech-decisions.md`「130 個 YAML 錯誤不存在」段）對來源專案 `book_overview_app` 的 `docs/work-logs/v0/` 逐版本目錄分類統計 status 值分佈、四型語意邊（spawned_tickets/children/blockedBy/relatedTo）出現數、缺 frontmatter carrier 數。單一版本目錄無法同時滿足「status 多值 + 四型邊皆有 + 缺 frontmatter 樣本 + 體積可控」，故取 v0.25（pending/in_progress 來源）與 v0.31（closed/accepted/四型邊/缺 frontmatter 樣本來源）聯集，共 773 個檔案、約 5.4 MB。

### 已知落差（描述 vs 實測）
本票原描述期待涵蓋「YAML 解析失敗（how.strategy 斷行）」型損壞樣本。實測後 book_overview_app 全部 773 個切片檔案中無此類樣本——依 `docs/tech-decisions.md`「2026-08-27：撤回——『130 個 YAML 錯誤』不存在，是量測 artifact」，此形態源於天真 parser 誤判 frontmatter 內 markdown 表格分隔線為區塊邊界，框架自身逐行語意解析對本專案全量 ticket 的真實錯誤數為 0。本切片實際涵蓋的損壞形態是「缺 frontmatter carrier」（parse_frontmatter_text 回傳 None），與同語料目錄下 PROP/SPEC/UC 三型別的處置一致，屬同一失敗模式，判定為草稿描述與實測落差，已依 claim 檢查清單獨立驗證並如實記錄。

## Solution

### 抽取方式
以 `rsync -a --prune-empty-dirs --include='*/' --include='tickets/*.md' --exclude='*'` 從 `~/project/book_overview_app/docs/work-logs/v0/v0.25/` 與 `v0/v0.31/` 只抽取 `tickets/*.md`（不含 `acceptance-reports/` 等同版本目錄下其他子目錄），保留原目錄結構落地至 `test/fixtures/corpus/book_overview_app/docs/work-logs/`。逐檔 `cmp`／`diff -rq` 對照來源，773 個檔案位元組相同。

### 統計結果
以 `parse_frontmatter_text` 對 773 個檔案分類：759 個可解析（`status`: pending 31 / completed 715 / in_progress 2 / accepted 1 / closed 6 / 其他 4；`spawned_tickets` 非空 37 / `children` 非空 56 / `blockedBy` 非空 142 / `relatedTo` 非空 40），14 個回傳 `None`（缺 frontmatter carrier，皆為同版本目錄下伴隨文件如設計決策記錄、完成摘要）。

### 產出

- `test/fixtures/corpus/book_overview_app/docs/work-logs/README.md`：切片標準、來源、缺 frontmatter 樣本清單、status/邊分佈統計
