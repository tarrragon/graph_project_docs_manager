### PM 驗收 0.1.0-W3-204 時發現的一個硬案例（本票須處理，非另開票）

`SPEC-003` §2.14 列 4「通知授權請求」標為 **自發型／可棄**，其推導正確——傳播單調不升，父列（列 1–3 破洞掃描完成）為可棄，子呼叫不得高於它；票面亦附了獨立理由（fallback 齊全、拒絕不造成不可回復後果）。

但它的**載體是 macOS 原生權限對話框**，該表已註明「不落於 §2.2／§2.12／§2.13 既定的三種載體形式內，仍佔用使用者呈現焦點」。這使它成為讓步規則第三條（**低級別不得搶佔任何請求**）的一個難以機械驗證的案例：對話框的呈現時機由作業系統決定，不由我方的仲裁點決定——若此時畫面上正有一個不可棄的阻擋關卡（列 11–13），我方無法阻止該對話框覆蓋它。

**本票撰寫第三條的可驗收形態時須回答**（不預設答案，三種都可能成立）：

1. 兩者在時序上互斥嗎？阻擋關卡（列 11–13）發生在 Domain 視圖載入的 gate 判定；權限請求發生在破洞掃描完成處置。若進入掃描的前提本就要求已通過 gate，則兩者不可能並存，第三條在此列**空成立**——但這需要實查 `SPEC-001` 的進入條件確認，不能假設。
2. 不互斥，則第三條對本列**不可機械驗證**，須在條文中明確標為「載體不受我方仲裁點控制」的例外，並寫明例外的邊界（哪些載體屬此類），而非略過不提。
3. 也可能結論是列 4 的級別標定應改——但改標定屬 `0.1.0-W3-204` 的產出範圍，本票若得此結論須回報 PM，不自行改該表。

**為何不另開票**：這正是「三條讓步規則寫成可機械判定的驗收形態」在本專案的第一個硬案例，屬本票 acceptance 第一條的範圍；另開票會讓條文與其唯一的困難案例分處兩張票。
