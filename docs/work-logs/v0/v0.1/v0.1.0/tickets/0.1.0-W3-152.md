### Task Reference
- 0.1.0-W3-144 what: 裁定 oregano-data-miner 在現行 ticket 流程中不可用：補工具或退役

### Rationale Chain
- 0.1.0-W3-144 why: `oregano-data-miner` 的 `tools` 為 `Grep, LS, Read`——無 Write／Edit，**亦無 Bash**。它不能寫檔、不能填 ticket body、不能建票、不能登記 spawn request。依 `quality-baseline` 規則 5 情境表，工具清單不含 Bash 的 agent 在派發階段即不應被指派 ANA 型 ticket；而「資料提取策略規劃者」這個定位本質上就是 ANA 型工作。**沒有任何一種派發方式能讓它完成一張票。**

原列於 `0.1.0-W3-143` 與其餘四個 agent 一併裁定。PM 讀其主文三區塊後判定不同質，三項理由皆為結構性：

**一、矛盾在三區塊內部，143 的仲裁方法對它失效。** 143 規定「三區塊與 frontmatter description 不一致時以三區塊為準」。但 oregano 的「允許產出」同一區塊內即自相矛盾：

| 欄 | 內容 |
|----|------|
| 檔案類別 | 資料提取策略文件（`.md`）、DOM 選擇器規劃、驗證/轉換規則文件、外部研究報告 |
| 操作類型 | Grep / LS / Read（純唯讀工具） |
| 路徑範圍 | 僅產出策略性文件至 ticket context 或 `docs/`；禁止 Write/Edit 任何程式碼或資料模型 |

第一列與第三列前半承諾產出 `.md` 至 `docs/`，第二列否定其手段。第三列後半的禁令只涵蓋「程式碼或資料模型」，反面即默示 `docs/` 下的寫入是被允許的——但工具清單不提供。仲裁者本身不一致時，143 的方法無法收斂。

**二、一項強制義務無任何可用工具能履行。** 「禁止行為」第 6 條：「外部資源研究任務**必須記錄在 Ticket 執行日誌**中，包括查詢過程、資訊來源、分析步驟。」寫入執行日誌需 Edit（直接改 ticket md）或 Bash（`ticket track append-log`），兩者皆無。這不是措辭與能力不符，是規範要求了一件結構上做不到的事。

**三、可能的結論不在 143 的選單內。** 143 要求逐項裁定為「改 description／改 tools／維持現狀」三選一。oregano 的合理結論包含第四項——**退役此 agent**：本專案零指派紀錄（`docs/work-logs/` 全量搜尋僅命中討論它的兩張票本身），且其定位（網頁抓取、DOM 操作）與本專案（Flutter 桌面文件管理）無交集。三選一的 acceptance 無法乾淨承載一個需要第四選項的決定。

**擴散範圍**：`.claude/agents/` 經 sync 擴散至全部 consumer 專案。本專案零指派使本地風險低，但選單上的壞選項隨框架送到每個 consumer——且選單本身看不出這件事。
