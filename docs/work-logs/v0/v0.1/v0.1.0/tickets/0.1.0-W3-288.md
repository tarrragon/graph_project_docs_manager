## Problem Analysis
### 問題根因

`lib/hook_logging.py` 的日誌 root 與呼叫端的狀態 root 由兩個彼此獨立、優先序相反的解析器各自決定；對齊手段是呼叫端逐點顯式傳一個**預設即舊行為**的 kwarg。漏接無任何訊號：日誌照樣寫、內容照樣正確，只是落在查詢者不讀的路徑上。

本票不是重新判定該形態（`0.1.0-W3-285` 已判定升級成立並 observe 至 `tarrragon/claude#97`），而是**在派任何實作之前先統整修法**。

### 影響範圍

已驗證的事實（本票實測，`.claude/` 全樹、排除測試檔與定義處）：

- 日誌入口呼叫行 320（`setup_hook_logging` 165 + `run_hook_safely` 153 + `mark_hook_entry` 2），分佈 159 檔（`hooks/` 118、`skills/ticket/` 23、其他 skills 16、其餘 2）。
- 顯式傳 `project_root` 者 **4 行 / 3 檔**（更正 `0.1.0-W3-285` 記錄的「1」，成因見下節）。
- `save_check_log` 與 `get_hook_log_dir` **完全沒有 root 參數**，非測試呼叫點 11 處——契約本身有洞，這 11 處連「記得傳」都做不到。
- 錯配不只一類：類一（狀態走 `get_ticket_state_root`）真陽 6 檔（2 已修 / 4 未修）；類二（狀態走 `lib/git_utils.py::get_project_root`，環境變數優先，與日誌走的 `hook_base` worktree 優先方向相反）12 檔，既有討論未涵蓋。

仍未驗證的假設：159 檔中 66 檔的 root 來源未判定；是否存在刻意要日誌留在 worktree 的呼叫端；`CLAUDE_PROJECT_DIR` 在 linked worktree 內實際指向何處。

**已驗證的事實**：

### 選定判準

四條依序套用，完整對照表在 #97 該則觀測的第六節：

1. 是否改變**下一個新增呼叫點**的預設結果——B 不改變，故單獨採 B 等於接受同一問題持續複製。
2. 失敗時是否有訊號——A 的失敗模式落在 #97 形態 1 的無訊號區，D 的反向錯配同樣無訊號。一個修形態 4 的方案不應以製造形態 1 為代價。
3. 對其他 consumer 的破壞面——A 全體立即失效，D 日誌落點全體遷移，E 無（舊入口保留）。
4. 要求呼叫端回答的問題，呼叫端答得出來——E 讓答案由 import 語句表達，而非由記憶表達。

### 本結論的承重點

**每個會寫狀態的呼叫端，其 state root 來源是模組級的選擇，而非執行期才決定的值。** 此一事實不成立（例如某類呼叫端依 payload 決定操作哪個 root），import 綁定就表達不出那個選擇，候選 E 對該類退化為只剩守衛，整個選擇崩。

該承重點**部分未驗證**：159 檔中 root 來源可指名者 93 檔，其餘 66 檔未判定。已建 `0.1.0-W3-292`（ANA，P1）逐檔判類，該票是實作的真正第一步。

候選 D 的承重點則已實測**不成立**（92/159），故 D 的否決依據是數字不是偏好；此結論同時回答 #97「方案評估」中「觀測面與作用面的對齊」方向 (a) 與 worktree 隔離意圖的衝突問題——衝突確實存在，面為 92/159。
