## Problem Analysis

### 缺口的規模：不是個案

掃全部 59 個 skill 的 `## Examples` 段，**幾乎全數沒有該段**。有的少數幾個裡，`component-contract-design` 的該段是七行的路由文字而非案例。

但「沒有 Examples 段」不等於「沒有範例」——本專案的範例實際以兩種形態存在：程式碼區塊與正反對照表。以 UX 設計族六個 skill 為樣本：

| skill | 行數 | code fence | 正反對照 | references |
|-------|------|-----------|---------|-----------|
| component-contract-design | 245 | 6 | 5 | 0 |
| ux-design-evaluation | 102 | 2 | 6 | 6 |
| impeccable | 181 | 2 | 0 | 0 |
| frontend-with-playwright | 170 | 2 | 2 | 8 |
| dart-style-guardian | 335 | 18 | 0 | 4 |
| foundation-design | 220 | 4 | 9 | 0 |

兩個極端說明現行檢查的失效方式：`dart-style-guardian` 有 18 個 code fence 但零正反對照——程式碼多不等於有判斷示範；`impeccable` 兩者皆近乎零，181 行純規則。兩者都通過現行的「含至少 1 個範例」檢查，因為該判準只計數不看形態。

`component-contract-design` 的六個 code fence 經檢視全為編號步驟表，是規則的另一種排版，不是案例。這說明計數式判準連「這個區塊是不是範例」都判別不了。

### 判準要能區分的三件事

修訂後的檢查清單條目須能判別：

| 對象 | 是不是範例 | 判別依據 |
|------|-----------|---------|
| 編號步驟表 | 否 | 講的是怎麼做，無具體輸入與輸出 |
| 正反對照表 | 是（判斷示範） | 給出兩個具體對象與選擇結果 |
| 完整成品 | 是（成品示範） | 有具體輸入，有可對照的輸出 |
| 指向他處的路由段 | 否 | 內容不在本地，讀者需再跳一次 |

兩類範例的用途不同：成品示範回答「做出來長什麼樣」，判斷示範回答「在多個合法選項間怎麼選」。規則能列出選項不能示範怎麼選，所以判斷示範是規則無法替代的那一類。修訂時應要求兩類至少各有其一，而非籠統的「至少一個範例」。

### 本票範圍的邊界

全體 skill 補範例不在本票範圍——那是 59 個檔案的工作量，且多數 skill 的範例需求由其領域決定，不是一次能定案的。本票只改 `skill-design-guide` 這一份規範，使**後續新建或修訂的 skill** 被要求思考範例。既有 skill 的補範例依需要逐一建票，`component-contract-design` 是第一張（W3-012）。

### 上游追蹤

本票所修的規範缺口已上報框架 canonical repo 為 `tarrragon/claude#79`（缺口一：範例要求只計數不看形態）。該 issue 的建議修法即本票的三處改動，兩者內容一致。

**本票的修訂結果須補充回 issue #79**。特別是判準的可用性——issue 內列的四種對象判別表是從現況反推的，本票會是第一次拿它去改實際規範，改的過程若發現判準有無法判定的邊界（例如既是步驟表又含具體輸入輸出的混合形態），那個發現比判準本身更值得回報。
