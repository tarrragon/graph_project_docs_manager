## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### 缺口的規模：不是個案

掃全部 59 個 skill 的 `## Examples` 段，**幾乎全數沒有該段**。有的少數幾個裡，`component-contract-design` 的該段是七行的路由文字而非案例。

但「沒有 Examples 段」不等於「沒有範例」——本專案的範例實際以兩種形態存在：程式碼區塊與正反對照表。以 UX 設計族六個 skill 為樣本：

| skill | 行數 | code fence | 正反對照 | references |
|-------|------|-----------|---------|-----------|
| component-contract-design | 245 | 6 | 5 | 0 |
| ux-design-evaluation | 102 | 2 | 6 | 6 |
| impeccable | 181 | 2 | 0 | 0 |
| frontend-with-playwright | 170 | 2 | 2 | 8 |
| dart-style-guardian | 335 | 18 | 0 | 4 |
| foundation-design | 220 | 4 | 9 | 0 |

兩個極端說明現行檢查的失效方式：`dart-style-guardian` 有 18 個 code fence 但零正反對照——程式碼多不等於有判斷示範；`impeccable` 兩者皆近乎零，181 行純規則。兩者都通過現行的「含至少 1 個範例」檢查，因為該判準只計數不看形態。

`component-contract-design` 的六個 code fence 經檢視全為編號步驟表，是規則的另一種排版，不是案例。這說明計數式判準連「這個區塊是不是範例」都判別不了。

### 判準要能區分的三件事

修訂後的檢查清單條目須能判別：

| 對象 | 是不是範例 | 判別依據 |
|------|-----------|---------|
| 編號步驟表 | 否 | 講的是怎麼做，無具體輸入與輸出 |
| 正反對照表 | 是（判斷示範） | 給出兩個具體對象與選擇結果 |
| 完整成品 | 是（成品示範） | 有具體輸入，有可對照的輸出 |
| 指向他處的路由段 | 否 | 內容不在本地，讀者需再跳一次 |

兩類範例的用途不同：成品示範回答「做出來長什麼樣」，判斷示範回答「在多個合法選項間怎麼選」。規則能列出選項不能示範怎麼選，所以判斷示範是規則無法替代的那一類。修訂時應要求兩類至少各有其一，而非籠統的「至少一個範例」。

### 本票範圍的邊界

全體 skill 補範例不在本票範圍——那是 59 個檔案的工作量，且多數 skill 的範例需求由其領域決定，不是一次能定案的。本票只改 `skill-design-guide` 這一份規範，使**後續新建或修訂的 skill** 被要求思考範例。既有 skill 的補範例依需要逐一建票，`component-contract-design` 是第一張（W3-012）。

### 上游追蹤

本票所修的規範缺口已上報框架 canonical repo 為 `tarrragon/claude#79`（缺口一：範例要求只計數不看形態）。該 issue 的建議修法即本票的三處改動，兩者內容一致。

**本票的修訂結果須補充回 issue #79**。特別是判準的可用性——issue 內列的四種對象判別表是從現況反推的，本票會是第一次拿它去改實際規範，改的過程若發現判準有無法判定的邊界（例如既是步驟表又含具體輸入輸出的混合形態），那個發現比判準本身更值得回報。
### 追加的第四處修法：讀者角色欄

W3-012 的回溯結果顯示，拆分軸選錯的根因不在拆分技巧，在於現行範本沒有任何欄位要求作者說明「本 skill 的讀者是誰、各讀哪些章節」。作者因此不會問自己這個問題，拆分邊界只好從章節結構推論，而結構與內容的對應沒有機制保證。

實證：該 skill 的三種讀者（產出者、派發者、執行者）使用頻率差一比四十四，而現行主檔把三者的內容交錯排列，對佔絕大多數的執行者訊噪比最差。這個失衡在建立時不可見，因為當時還沒有使用紀錄。

**建議在 Body 範本新增讀者角色欄**，要求列出各角色與其對應章節。有使用紀錄時以紀錄校準，沒有時至少留下作者當時的假設，供後續比對。

配套的檢查清單條目：寫完後問「訊噪比最差的那個讀者是誰」，若答案是使用頻率最高的那群，拆分軸選錯。

此修法與原三處（Examples 必填、實質判準、規則與範例分工論證）的關係：前三處管「有沒有範例」，本處管「內容給誰看」。兩者獨立——一份有完整範例但角色交錯的文件，範例本身也會被錯誤的讀者載入。

已一併補進框架 issue #79 的評論。
### 第五處修法：判準的第一條應是可執行性

另一 consumer 提供的實證改變了判準的結構。原先規劃的四種對象判別表是**分類**（這是不是範例），它判別不了**驗證**（這個範例有沒有用）。

實證：某 skill 的 SKILL.md 範例 `ticket create --parent "<id>" --action "實作" --target "事件融合層"` 逐字執行得到 `CHECKLIST_VALIDATION_FAILED`，缺四個必填欄位。該範例形態正確、有輸入有輸出，符合「完整成品」的分類定義，只是不能用。

一個通過分類判準卻執行即失敗的範例有害而非中性：讀者照抄後撞牆，且撞牆時會先懷疑自己而非文件。

**判準第一條**：範例必須可逐字執行且通過該 skill 自己的檢查。可機械驗證（對 SKILL.md 每個 code block 的命令行做 dry-run），不依賴審查者記得檢查。

此條與原四處修法的關係：Examples 必填管「有沒有」、分類判準管「是不是」、可執行性管「能不能用」，三層依序。前兩層通過而第三層失敗是最糟情形——文件看起來完備而讀者用不了。

### 上位形態：示範性內容未經它所示範的系統驗證

該實證是三個切面之一：

| 切面 | 示範性內容 | 未經誰驗證 |
|------|-----------|-----------|
| ARCH-BAL-013（本專案語料庫已有，復發四次） | guard 訊息給的處置指令 | 其他 guard |
| 另一 consumer 的驗收發現 | hook 錯誤訊息內嵌的 yaml 範例 | 該 hook 自己的解析要求 |
| 本次實證 | SKILL.md 的範例 | 該 skill 的 checklist |

共同結構：示範性內容以字串常數形式存在，型別上合法，而它作為「使用者會照抄的產物」這一層沒有型別可檢查。測試驗程式行為，範例是資料，不會有測試去執行它。

### 附帶：引導有效但只在失敗路徑上

同一實證的第二項：該 CLI 的錯誤訊息帶 hint 與具體建議，引導品質不差，但要先失敗一次才拿得到；而 `--help` 有兩層必填（argparse 層與 checklist 層）只顯示一層。

引導存在、有效、寫得好，但在失敗路徑上；文件與 `--help` 這兩條成功路徑上的引導反而不完整。

對本票的意涵：檢查「有沒有引導」會通過，要檢查的是「引導在哪條路徑上」。此觀察應納入檢查清單的設計。

已同步至框架 issue #79。
### 附帶觀察：從單一案例歸納條款時，案例的偶然特徵會被寫成必要條件

本觀察與本票主題（範例引導）相鄰但不同，記於此待第二個實例出現後再決定載體。

`bash-tool-usage-rules` 3.8.0 的「截斷方向」條款描述的機制正確：CLI 錯誤前綴在頭、回吐內容在尾，`tail` 會截掉判別依據。但該條款的語境隱含「輸出很長所以取不到頭」——實測顯示問題與長度無關，那次拒絕的輸出**只有三行**，而 `tail -2`、`tail -3` 是最常用的值，正好命中。

條款是從一個 argparse 長輸出的案例歸納的，「長」是那個案例的偶然特徵，被寫進了條款的語境。實際的失效分布不是這樣：錯誤輸出通常反而短，短輸出更危險，因為使用者會覺得「才幾行，取幾行應該夠」。

**窄的方向剛好是使用者最常用的值**，這不是隨機的窄。

### 為何不另建載體

三項理由：

| 理由 | 說明 |
|------|------|
| 只有一個實例 | 依「先驗證問題規模再決定機制」，單一實例不足以支撐專屬載體 |
| 上位形態已有涵蓋 | 另一 consumer 的 PC-BAL-064 收「取樣落在單一維度而結論被讀為全域」，本觀察是其變體——差別在對象是規則條款而非驗證判準 |
| 現有 issue 主題不合 | 該 consumer 建議記在協定 issue，但那張收的是 issue 協作協定；本觀察屬規則撰寫品質，主題不符。硬塞會使該張範圍模糊 |

待第二個實例出現時再判斷：若同屬「條款從案例歸納而偶然特徵入條件」，可與 PC-BAL-064 合併為同一筆的第二個對象；若形態不同，屆時另建。

### 對本票的間接意義

本票要為 `skill-design-guide` 補範例判準。此觀察提示一個相鄰風險：**判準本身也是從案例歸納的**。四種對象判別表源自本專案幾個 skill 的現況，可執行性判準源自另一 consumer 的一次實證。若那些案例有偶然特徵被寫進判準，會重演同一形態。

具體的防護是撰寫判準時明寫「本判準的歸納來源是什麼案例」，讓後續讀者能判斷自己的情況是否落在來源範圍內。此項已納入本票的檢查清單設計。
