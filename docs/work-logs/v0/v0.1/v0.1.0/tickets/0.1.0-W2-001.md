### 實作前分析

SPEC-001 §1 現行版本（v1.16）共 11 個狀態列（含「已選格」疊加態）。依照票面
how 段逐狀態組合句型檢查，發現兩類缺口需先確認再實作：

1. 矩陣格與泳道節點的資料來源需要單一權威——採用單一 `FlowStep` fixture
   清單（`_uc02Steps`／`_uc04Steps`）同時驅動矩陣格詳情、關係符號（direct 由
   `traverses` 包含推導）、列小計、泳道節點四者，避免四處各自維護不一致的假資料。
2. 「正常 · 矩陣／已選格／正常 · 泳道／泳道 · 尚未選定 UC／泳道 · flow 未結構化」
   五列共用同一份底層資料（矩陣／泳道模式 + 選中格 + 選中 domain + 降級旗標），
   將其收斂為單一 `DomainReady` 狀態類別，由 `mode` 欄位與 App 層共用值
   `selectedUcProvider` 計算實際渲染的子列，而非各自獨立的五個 sealed 子類別。

### 頁面層佈局原語限制的發現

acceptance 第一項「頁面層不以原生佈局原語直接包兩個以上元件庫元件」與
SPEC-004 §3.6「`SplitRow.header`[`PageTitle`, `SegmentedControl`]」的字面組合
要求衝突——`lib/app/shell.dart` 現行對六個目的地共用同一份無 `trailing` 的
`SplitRow.header`。既有 `gap_report_screen.dart` 遇到同型缺口時選擇在內容區
頂端插入按鈕列並回報後續票（`0.1.0-W2-008`，尚為 pending）。

本票改採不同解法：由於 `AppDestination.domain` 是唯一需要頁首右格的目的地，
在 `shell.dart` 的 `pages` 迴圈為 `SplitRow.header` 補一行條件式 `trailing`
（`item == AppDestination.domain ? const DomainHeaderTrailing() : null`），
其餘五個目的地 `trailing` 仍為 `null`、渲染不受影響，符合「一行接線，不改其他
目的地」的派發要點，且讓 `SegmentedControl` 真正落在 SPEC-004 要求的頁首右格
（而非頁面內容頂端），不需要在頁面層另組合排版容器。
