### 階段 2 草稿（A-28「共用狀態 → 合併」判準，未改檔，交 WRAP）

**現況**：`cognitive-load.md` 的拆分閾值（功能職責數 > 2、修改檔案數 > 5）只回答「要不要拆」，不回答「哪些 FR 該合併成同一張功能模組票」。全專案（含 `domain-bundle-mapping-methodology.md`）查無任何條文以「共用狀態」作為 GREEN 票合併判準——此判準目前僅存在於範例，屬本輪盤點認定的真缺口，非僅缺路由。

**草稿判準**：同一 spec 內的多個 FR，若同時滿足 (a) 共用同一狀態或同一元件樹、(b) 合併後功能職責數與修改檔案數未超過 `cognitive-load.md` 拆分閾值，得依「功能模組」粒度合併為一張 GREEN 票；不滿足 (a) 或 (b) 任一者，依「spec FR」粒度各自成票。

**會改變哪些判定**：目前 SKILL.md「每個 spec FR 或功能模組 1 張」的「或」在共用狀態但未觸及閾值的邊界情況下無成文判準，PM 只能各自解讀；此草稿一旦收斂為條文，會把「兩個 FR 職責緊密但各自看都不超閾值」的情況從「PM 自由裁量」改為「強制合併」，可能推翻先前依直覺分票的既有 ticket 拆分慣例。此為新判準、非用戶程式碼風格偏好，依 W3-417 用戶裁示不上呈用戶，交 WRAP 收斂。

### 階段 2 WRAP 評估：A-28「共用狀態 → 合併」（獨立評估者，依 wrap-decision skill）

**合併判準 G1（本組權威指定）**：A-28（version-bootstrap）與 C-11a（foundation-design，0.1.0-W3-420）同屬「票粒度：何時合併、何時拆」。兩者合併為一條：**共用檔案者合併、合併後超閾值者拆**。權威為既有條文，不新增：`.claude/pm-rules/task-splitting.md`〈拆分後檢查清單〉B「共用檔案的問題已合併到同一 ticket」＋ `.claude/rules/core/cognitive-load.md`〈速查三閾值〉。version-bootstrap 與 foundation-design（皆框架綁定、不宣告 portable）路由至此。A-12（component-contract-design，portable）不路由，其目錄單位規則與 G1 一致（不同目錄 → 檔案不交集），見 0.1.0-W3-418。

**反向框架結果**：thyme 草稿以「共用狀態」為合併依據，與既有條文衝突——`task-splitting.md`〈拆分策略速查〉策略 7 核心原則「測試群組間有依賴時，透過序列派發解決，不以依賴為由合併」。共用狀態是依賴，不是合併理由；共用**檔案**才是（檔案所有權）。另：現行 SKILL.md 補句「「或」由〈速查三閾值〉決定」只能判「要不要拆」，兩種分法都未超閾值時判不出取哪一個（範例正是此情形），故該補句本身也是半依據。
