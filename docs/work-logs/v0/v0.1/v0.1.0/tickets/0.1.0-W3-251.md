## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 世界平面查證：過濾能力不在該呼叫路徑上（修正一項轉述）

回報方稱「`get_active_dispatches()` 那層已經有 `_is_dispatch_expired()`，所以修法可能只是加一個條件」。**實際讀碼後不成立**，該方亦自陳未讀完全部分支。

`get_active_dispatches()` 的全文是讀檔後 `return state["dispatches"]`——**不做任何過濾**，`_is_dispatch_expired()` 只被 `cleanup_expired()` 呼叫。所以 `is_file_under_dispatch()` 拿到的必然是全部 entry，過濾能力存在於模組內但不在這條路徑上。

**這使問題比回報的更大一層：函式名在說謊。** 名為 `get_active_dispatches` 卻回傳全部 entry（含已結束回合者），每一個呼叫端都得自己知道要再過濾一次。查證各呼叫端：

| 呼叫端 | 是否自行過濾 |
|--------|------------|
| `session-registry-start-hook` | 有（篩 `turn_ended_at` 已設定者） |
| `subagent-stop-dispatch-cleanup-hook` | 有 |
| `bare-commit-guard-hook` | 刻意不過濾，且寫了理由 |
| `workspace-wipe-guard-hook` | 刻意不過濾，且寫了理由 |
| `agent-commit-verification-hook` | **未查證，列為驗收項** |
| `is_file_under_dispatch`（同模組內） | 不過濾，且無理由 |

**修法因此不只是加一個條件**，要先裁決命名：維持現名而在每個呼叫端過濾（現況，靠每個呼叫端各自知情），或改名為 `get_all_dispatches()` 並另立一個真正只回傳進行中 entry 的函式。後者讓「忘記過濾」在讀碼時可見；前者不會。這是 Solution 要記的裁決。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 裁決：採改名，不採「維持現名 + 每個呼叫端各自過濾」

`get_active_dispatches()` 改名為 `get_all_dispatches()`（語意誠實：回傳全部 entry），另立一個只回傳 `turn_ended_at is None` 之 entry 的函式；`is_file_under_dispatch()` 改呼叫後者。

**裁決依據不是「哪個比較乾淨」，是錯誤有沒有觀測面。** 呼叫端忘記過濾時，程式照常運作、結果照常回傳，只是多涵蓋已結束的 entry——沒有例外、沒有紅燈、沒有任何一刻會有人發現。現況六個呼叫端的分佈（四個各自過濾、一個未查證、一個漏掉且無理由）不是紀律問題，是這個名字已經失效的證據：四個記得的人不能證明名字有效，一個漏掉的人足以證明它無效。

改名後，「呼叫 `get_all_*` 而其後沒有過濾」在**讀碼當下**可見；維持現名則要求每個呼叫端**記得**一件名字沒說的事。**把判斷移出迴路，而不是要求判斷更可靠。**

**執行注意（框架資產的改名邊界）**：`.claude/` 會同步至其他 consumer 專案，改名須在同一次提交內涵蓋全部呼叫端與測試，不可分批；查證所得呼叫端為六處（見 Problem Analysis 表）加測試檔，全數位於 `.claude/` 內，單一提交可涵蓋。

**兩個刻意不過濾的 hook 不因改名而改變行為**：`bare-commit-guard` 與 `workspace-wipe-guard` 各自寫了「陣列非空即視為 active」的理由，它們應改呼叫 `get_all_dispatches()`（語意正是要全部），註解保留。改名讓它們的刻意變成顯性，而非被迫調整。

### 修復前的實測樣本（before）

`main-thread-edit-restriction-hook` 對一筆 `turn_ended_at` 已設定於數小時前的 entry，仍持續發出「此檔案正在被背景代理人處理」警告。可驗證的 before 樣本：另一 session 於 `2b07f0ae`、`7302dceb` 兩次成功編輯 `.claude/references/bash-tool-usage-details.md` 與 `.claude/rules/core/bash-tool-usage-rules.md` 時，兩次皆收到該警告；該兩檔屬本專案 `0.1.0-W3-225` 的派發檔案清單，而 `225` 當時已 completed 逾七小時。
