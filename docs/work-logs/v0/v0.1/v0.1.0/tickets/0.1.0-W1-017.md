## Task Summary

## Problem Analysis
### 問題根因

`core.ignorecase=true` 下，寫入 `SKILL.md` 會落進既有的 dirent `skill.md`——內容通過，檔名被吞。該吞噬雙向對稱，push 與 pull 都無法傳遞純大小寫改名，兩端各自須自行修正。

三個 skill 的入口檔因此在 git tree 中停留為小寫，與其餘 54 個不一致。平台以檔名辨識 skill 入口，小寫者不被載入。

### 阻塞原因（已解除）

`commit-stage-guard-gate-hook.py` 對 staged rename 的 `pre_text` 由**新路徑**解析（`git show HEAD:<new_path>`），新路徑在 HEAD 中不存在因而得空字串，整個檔案 19037 bytes 被判為新增內容（220 行），觸發多個 guard 的誤判。

判斷基準被本次操作本身移動了——「既有內容」的參照點正是那個剛被改掉的東西。

上游修復（框架 2.42.11，`_get_staged_rename_map`）到位後阻塞解除。

### 影響範圍

`.claude/skills/{continuous-learning,error-pattern,strategic-compact}/SKILL.md` 三檔的 git tree 檔名。內容不受影響。

## Solution
重做配方（僅在 index 遺失時需要；正常情況三筆 rename 已在 index 中，等 hook 修好後裸 commit 即可）

單段式 rename 在 core.ignorecase=true 下被 git 視為無變更，必須經中介檔名：

    R=<專案根目錄>
    for s in continuous-learning error-pattern strategic-compact; do
      git -C "$R" mv ".claude/skills/$s/skill.md" ".claude/skills/$s/skill.md.tmp"
      git -C "$R" mv ".claude/skills/$s/skill.md.tmp" ".claude/skills/$s/SKILL.md"
    done

執行時可能撞 index.lock（本次撞了兩次），重試即過。

驗證（兩個 grep 皆不加 -i——-i 對大小寫問題零鑑別力，flag 語意本身就是忽略待驗維度）：

    git ls-files | grep -E '/SKILL\.md$' | wc -l    # 應為 57
    git ls-files | grep -cE '/skill\.md$'           # 應為 0
    git diff --cached -M --numstat                   # 三筆皆 0 增 0 刪

上游對應票：balance 的 0.2.1-W3-1139（P0），修 commit-stage-guard-gate-hook
對純 rename 以新路徑取 pre_text 的問題，採「保留 R + 解析舊路徑」方案。

行前預想：12 小時後最可能的失敗原因是 index 被其他 session 或 hook 清掉，
三筆 rename 消失而無人察覺（本 session 開頭才剛清掉兩個卡住的陳舊 index blob，
先例存在）。防護即上方配方——重做成本三行，且驗證是固定值不是判斷。


### 狀態更新（sync-pull 之後）

**index 已還原至 HEAD，三筆 rename 不在暫存區。** 這是刻意的，非遺失：

上游修復（balance 的 `0.2.1-W3-1139`）要經 sync-pull 才到本地，而
sync-pull 的前置檢查是 `git diff --cached --name-only -- .claude` 非空即中止——
staged rename 會擋住它自己的解方。故先還原 index 讓 `.claude` 乾淨、跑 pull，
不重新 stage，保留下一次 pull 的通道。

檔案系統的 dirent 仍是大寫（`ls -1` 逐目錄確認）；`core.ignorecase=true` 使
git 將 tracked 的 `skill.md` 對上 dirent `SKILL.md` 而回報乾淨。

**實測：本次 pull 未帶來修復。**

    grep -c '_get_staged_rename_map' .claude/hooks/commit-stage-guard-gate-hook.py  -> 0
    git ls-remote https://github.com/tarrragon/claude.git HEAD  -> 116bfa560ac6…
    .sync-state.json last_synced_base_sha                        -> 116bfa560ac6…

框架 repo HEAD 未移動——修復 commit 在上游的專案 repo，尚未推至框架 repo。
此為「兩個同步目標被混為一談」的又一實例：修好、複驗、測試全數完成，
唯獨未執行讓修復離開來源 repo 的那個動作。

**正確順序**：上游 push 框架 repo → 本專案 sync-pull → 重做 rename → 裸 commit。

### 附帶發現：pull 的提示會建議抵銷本修復

本次 pull 輸出「3 個上游檔案本地缺漏：skills/*/skill.md，可能需要手動補齊」。
三個檔的 blob 經比對與 HEAD 相同，未被上游覆蓋，故該提醒屬「以大小寫敏感方式
找小寫檔找不到」，非同步失敗。但照其字面「手動補齊」操作會把小寫檔補回來，
正好抵銷本票的修復——**修好之後，工具會建議把它改回去**。

### 阻塞解除的實際經過與一項未預期的損壞

上游修復（框架 2.42.11）到位後執行 sync-pull。三項修復逐一以 grep 計數確認到位，`settings.json` 維持 193 登記 / 0 重複組，未再被灌入重複。

**但該次 pull 把三個 skill 的入口檔從工作區刪除**——磁碟上完全消失（`ls` 三個目錄皆無任何 `skill.md` / `SKILL.md`），git 仍追蹤小寫版本。pull 輸出中有兩處訊號，當下都不像損壞：

- `[Skill 變更摘要] 移除: continuous-learning, error-pattern, strategic-compact` —— 讀起來像 skill 清單的統計差異
- `提醒: 3 個上游檔案本地缺漏` —— 上游併行 session 已預告此則為誤報（其 `1142`），並明確建議忽略

**該建議在本次執行中不成立**：這一則不是誤報，檔案是真的沒了。誤報的判定來自對方在自己環境的量測，我照套會保留一個三個 skill 都沒有入口檔的工作區。

處置：自 HEAD 還原三檔，並逐一比對 sha256——還原內容、pull 前備份（`claude-backup-907_jj2z`）、上游現行內容三者相同，無內容遺失。三檔確認完好後才做兩段式 rename。
