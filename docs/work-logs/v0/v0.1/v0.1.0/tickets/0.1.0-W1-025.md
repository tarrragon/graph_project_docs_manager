## Task Summary

使下一次 sync-pull 產生零衝突，讓 base 推進至上游 HEAD，終止純大小寫改名 delta 的每次重放 .claude/.sync-conflicts 的未解衝突與 .sync-state.json 的 base SHA

## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`sync-claude-pull.py` 的三方合併把上游的**純大小寫改名**拆成兩個獨立 delta 項：刪 `skill.md` ＋ 加 `SKILL.md`。套用刪除半邊時（L1796-1799）以路徑字串構造 `local_file`：

    if merged is None:
        if local_exists:
            _atomic_remove(local_file, rollback_log)

在大小寫不敏感檔案系統上，`skill.md` 解析到實際存在的 `SKILL.md`，`local_exists` 為真，直接 unlink。

**判定發生在路徑字串層，不在檔案系統狀態層**——這是為什麼本地 index 與磁碟完全對齊（皆為 `SKILL.md`）卻毫無保護作用。

### 與上游 1144 的關係：不同路徑，故其防護不適用

上游 `1144` 修的是 `cleanup_stale_files` 的安全網 `_is_git_tracked`。本案不經過該函式，實測三項：

| 驗證 | 結果 |
|------|------|
| `git ls-files --error-unmatch .claude/skills/*/SKILL.md` | TRACKED |
| 直接呼叫修復後的 `_is_git_tracked(...)` | `True`（安全網是好的） |
| 三檔是否在 `.sync-conflicts/` | 否——若走該路徑且回 True 會 `shutil.move` 至該處 |

三項一致指向：`cleanup_stale_files` 未參與。

上游據此建立的大小寫自檢（比對 index 與 disk）對本路徑**零鑑別力**——它測的變數是 index vs disk，本路徑的變數是 **base vs upstream 之間有無純大小寫改名**，兩者不相干。該自檢在本次拉取前跑過並回報乾淨，隨後仍刪檔。

### 重放迴圈

有未解衝突時 base 不推進（L2136-2145，對齊 git merge 語意）。base 停在 `116bfa56`（改名之前）使同一份 rename delta 每次 pull 重算並重放：

    pull 套用 delta → 刪檔 → 留下衝突 → base 不推進 → 下次 pull 同一份 delta

已實測連續兩次拉取各刪一次。**清衝突才能推進 base，而每次 pull 都製造新衝突**——兩件事互卡，須人工介入打破。

### 相關 Error Pattern

`PC-GPD-002`（共享方法使交叉驗證退化為共振）的邊界延伸：本案的防護與缺陷**不是共享來源，是根本不在同一條路徑上**。防護本身正確、實測有效，錯的是把它的結論用出適用範圍。上游已自陳此點。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 執行結果

**迴圈已終止。** 第三次拉取的決定性測試：

    已套用 0 個 delta 變更
    無衝突
    已記錄 base SHA: 15d14be8ce0c
    三個 SKILL.md：皆存在（無刪除、無警示）

### 逐步實測

| 步驟 | 動作 | 結果 |
|------|------|------|
| 1 | 三個入口檔備份至 repo 外 | sha256 記錄：`4df2e2ea…` / `efcfbb9c…` / `180f1eb7…` |
| 2 | 四個衝突分類 | `VERSION` 與 `CHANGELOG` 本地已等於上游（sha256 比對），下次合併 no-op；餘三個取上游 |
| 3 | 提交後第二次 pull | **無衝突**，base 自 `116bfa56` 推進至 `15d14be8` |
| 4 | 該次仍刪三檔（改名 delta 的最後一次重放） | 自 HEAD 還原，三方 sha256 與備份逐一 MATCH |
| 5 | `readme_index.sync` 重生索引 | `PC-GPD-001` / `PC-GPD-002` 兩列補回（`grep -c` = 2） |
| 6 | 第三次 pull | 0 delta、無衝突、無刪除、base 不變 |

`settings.json` 全程維持 193 登記 / 0 重複組（`1141` 的修復有效）。

### 順帶完成：孤兒分支清理

16 個分支逐一以 `rev-list --count main..<branch>` 驗證 `ahead=0` 後刪除（12 個人工命名的舊 docs/feat 分支 + 4 個本輪 worktree 分支）。使用 `git branch -d` 而非 `-D`——前者對未合併分支會拒絕，是與「已驗證 ahead=0」互相獨立的第二道確認。剩餘分支：僅 `main`。

### 對其他 consumer 的意義

本次處置**不依賴上游 `1155` 修好**。根因是 base 停在改名之前使 delta 每次重放；一旦 base 推進越過改名點，該 delta 被消費，之後不再產生。任何 base 早於改名的專案都可用同一路徑脫困：清衝突 → pull（會刪一次）→ 還原 → 之後乾淨。

**代價是必然被刪一次**，故備份到 repo 外是前置條件而非保險。
