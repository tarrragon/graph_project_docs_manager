### Rationale Chain
- 0.1.0-W3-213 why: **用戶裁示（2026-09-09）**：跨 SPEC 的事件流管控需要比 `0.1.0-W3-184` 更複雜的分析與規劃，範圍延伸至三個本專案目前不涵蓋的面向——

> 我們現在雖然是用在單線程的 flutter，但是 flutter 其實也有 isolate 的功能可以跑多線程，而更延伸的說，我們相關的 skill 規劃設計也會用到後端服務的設計上，那伺服器需求的功能在處理這種大量事件流同時啟動需要有更詳細的規劃跟管理，無論是本地排程，或者是大量的外部請求，或者各種本地腳本，或者高負載的查詢或者解碼，都會對整體造成影響。
>
> 那高負載的情況下如何維持服務，如何判斷要停止哪些請求，以及維持可觀測性讓工程師做管控跟除錯。

該需求已交由另一 session（fable model）規劃設計，**本專案的 SPEC 設計待其產出後再回頭檢視**。

**為何需要本票**：`0.1.0-W3-202`（事件排程與注意力仲裁方法論）與該產出**處理同一層**——`184` 定義的三分判準、L1–L3 級別、競爭的操作性定義、仲裁模型，全部是「大量事件同時發生時如何取捨」的一個切面（稀缺資源為使用者注意力）；該產出的稀缺資源是 CPU、記憶體、連線數，但取捨結構同源。

**先做 `202` 則後果**：產生兩份涵蓋重疊的權威定義，一份在方法論、一份在該產出，而兩者沒有任何同步機制——**這正是本專案今日花費最多力氣處理的那類漂移**（`framework issue #104` 的主題）。

`202` 是 `203`／`204`／`205`／`207` 的上游，故整條鏈一併等待。**這是 `decision-trigger-binding` 規則 1 狀態 (b)（明確 trigger 延後），不是懸空**——本票即該 trigger 的承載者。
- 0.1.0-W3-184 why: **用戶更正（2026-09-09）**，起因是 PM 把提示密度問題框成「先問這些提示時刻是否都必要」：

> 這樣也不完全正確。如果需要提示使用者的訊息，表示有他的重要性，那**有重要性的動作，不應該同時大量執行**，或者真正有重要問題發生的時候，**應該要暫停背景的行為**，所以我才提到有的提示訊息要擋住使用者的操作。
>
> 那重點是當我們設計 spec 的時候，也要評估**有哪些行為會在背景執行，哪些動作會在前台跟使用者互動**，是不是有些動作要**避免同時請求使用者的關注或者指令**，或者會造成互動影響的 SPEC 在設計的時候，**整個事件流就應該包含跟其他 domain 確認過再執行，或者應該加入延遲的動作**。

**PM 原本的框架把提示當成雜訊，這是錯的。** 提示需求本身是重要性訊號——需要提示使用者，表示該事件有重要性。因此提示密度過高不是「提示太多」，是**同時執行了太多重要的事**。

**這使 `0.1.0-W3-167` 的處置範圍必須收窄。** 在提示層做排隊、優先級或載體分化，是幫一個排程問題做視覺化緩衝——症狀被吸收，成因原封不動，而且緩衝做得越好，成因越不可能被發現。167 處理「留下來的提示怎麼呈現」，本票處理「為什麼會有這麼多同時發生的重要事件」。

**本專案已有具體實例。** 破洞掃描掛在 `GapReportNotifier.build()`，首讀者是 App 啟動時的 `ScanNotificationController.start()`（`0.1.0-W3-122` 的主題）——使用者尚未看過破洞報告頁，掃描就已在背景完成並試圖請求通知授權。這正是「背景行為在前台注意力尚未就緒時請求使用者關注」，而現行 SPEC-003 §2.2 的觸發條件只判斷「可見頁是不是 gaps」，不判斷「現在是不是請求使用者注意的適當時機」。

編輯能力（`0.1.0-W3-073`）落地後前台互動會大幅增加，此時若背景仍有掃描、載入、git 操作各自獨立觸發，注意力競爭會從偶發變成常態。**現在定義比事後補容易。**（來源已完成，結論見 Solution）
