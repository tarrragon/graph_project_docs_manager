### Task Reference

把 `reference-stability-rule8-guard-hook.py` 的偵測面由「ticket ID」擴至規則 8 條文涵蓋的「專案層級識別符」，至少納入專案檔案路徑；先量既有命中數再決定該層級是 WARNING 或阻擋。

### Rationale Chain

實查三處（接手者請依 PC-162 獨立重驗）：

| 位置 | 內容 |
|------|------|
| `reference-stability-rule8-guard-hook.py:313` | 掃描迴圈 `for pattern in (VERSIONED_TICKET_PATTERN, BARE_TICKET_PATTERN)`——只有這兩個樣式 |
| `reference-stability-rules.md:61` | 規則 8 條文：「禁止引用專案特定的 ticket ID、**worklog 路徑等專案層級識別符**」 |

條文以「等」開放列舉，且指名的失效形態對路徑類與 ID 類完全相同；守衛只實作其中一類。

**實證**：`.claude/methodologies/component-library-bidirectional-constraint-methodology.md` v1.18.0 三處寫入 `docs/spec/ui/SPEC-003-interaction-response.md`，全數通過。修正見 `0.1.0-W3-175`。

### 本票的核心不是覆蓋率，是覆蓋率被誤讀

同一次編輯中，守衛**確實命中了**該檔 changelog 段落的 ticket ID，執行者依提示改寫後通過，並在完成回報中把此事記為「框架層小插曲，無需處理」。守衛動作過、被滿足了，於是「符合規則 8」在執行者與驗收者雙方心中同時結案。

**沉默與命中的可解讀性不對稱**：

| 守衛狀態 | 讀者的合理推論 | 是否仍會自查 |
|---------|--------------|------------|
| 沉默 | 未檢查，或檢查了沒事 | 可能會 |
| 命中並被滿足 | 已檢查，且問題已解決 | 幾乎不會 |

因此**部分覆蓋而會命中的守衛，對未覆蓋的那一類比不存在的守衛更不利**——它為漏網的部分提供了合規的外觀。這是本票列 P1 的理由。

- 本檔為框架資產，經 sync 擴散至全部 consumer 專案，且為 PreToolUse 即時生效的 hook——**改壞會當場擋住全部人的編輯**。修改時機依 `PC-GPD-010` 排序，判準是當下有沒有人在呼叫它。
