### 一、五個 Driven Port 的三回饋點覆蓋表

**圖例**：Y = 已覆蓋、N = 未覆蓋（gap）、N/A = 不適用（附理由）、spec = spec 定義但未實作

**監控追蹤欄統一說明**：五個 port 均為 N/A。CLAUDE.md §6「structured log 維持延後（重評條件與 tripwire 不變）」，0.1 無 APM 系統。此為設計期決定非疏漏，重評 tripwire 已記錄。以下表格省略此欄，僅列呼叫端與日誌兩消費者。

#### Port 1: DirectoryPathPicker（typedef 形態，file_selector）

| 時刻 | 呼叫端 | 日誌 | 備註 |
|------|--------|------|------|
| 呼叫發出 | Y（:198 呼叫 `_pickDirectoryPath()`） | Y（:195 `開啟資料夾選取面板`） | |
| 受理 | N/A | N/A | fire-and-wait，G4-3 鎖定 |
| 結果 | Y（null/例外/path → 三個 ChooseFolderResult variant） | Y（:200/:204/:207 全分支） | |

**接縫形態特殊性**：typedef 無 adapter 類別，三時刻全由呼叫端（`chooseFolder()`）承擔。與 abstract interface class 形態的差異：方法論承擔者表的「adapter 實作」在此形態中回落為呼叫端自身——0.1.0-W3-133 Q1 已裁定方法論不要求 adapter 為獨立類別，此處是同一判準的 typedef 延伸。

#### Port 2: WorkspacePreferencesPort + Handle（abstract interface class，兩步 API）

| 時刻 | 呼叫端 | 日誌 | 備註 |
|------|--------|------|------|
| 呼叫發出 | Y（:224 / :252 呼叫 `_preferencesPort.open()`） | Y（:219-221 / :249） | |
| 受理 | Y（`open()` 回傳 Handle = 管道可用） | Y（:225 / :263 `偏好設定儲存已就緒`） | G4-1 正向、G4-2 負向 |
| 結果 | Y（bool + 例外 → Selected/NotRemembered） | Y（:228-234 / :237 全分支） | |

#### Port 3: WorkspaceDirectoryProbePort（abstract interface class，單步 API）

| 時刻 | 呼叫端 | 日誌 | 備註 |
|------|--------|------|------|
| 呼叫發出 | Y（:281 / :289 呼叫 probe 方法） | Y（:280 / :287） | |
| 受理 | N/A | N/A | fire-and-wait（dart:io 直接 I/O） |
| 結果（exists=false） | Y（回傳 WorkspaceUnavailable） | **N**（:281-286 直接 return，無日誌） | minor gap |
| 結果（readFirstEntry 失敗） | Y（回傳 WorkspaceUnavailable） | Y（:295-298 level 900） | |
| 結果（readFirstEntry StateError） | Y（回傳 WorkspaceReady） | N/A（空資料夾不是失敗） | 設計選擇 |

**Gap**：`exists()` 回 false 時日誌缺失。呼叫端有回傳值（`WorkspaceUnavailable`），但日誌消費者無法區分「探測了但不存在」與「未探測」。建議由 0.1.0-W3-135（例外契約補齊票）一併處理，加一行 `_log('資料夾不存在：$path')` 即可。

#### Port 4: ScanNotifier / MacosScanNotifier（abstract class + MethodChannel）

| 方法 | 呼叫發出 呼叫端 | 呼叫發出 日誌 | 受理 | 結果 呼叫端 | 結果 日誌 |
|------|----------------|-------------|------|-----------|----------|
| authorizationStatus | Y | Y（:79） | N/A | Y（enum） | Y（:85/:88-92/:94-100） |
| requestAuthorization | Y | Y（:106） | N/A | Y（enum） | Y（:112/:115-120/:122-128） |
| show | Y | Y（:134-136） | N/A | **void**（注 1） | Y（:147-158） |
| withdraw | Y | Y（:163） | N/A | **void**（注 1） | Y（:167-178） |

**注 1**：`show()` 和 `withdraw()` 回傳 `Future<void>`，例外被吞——呼叫端無法區分成敗。但 SPEC-003 §2.2 明示「發送與撤回期間不顯示任何等待指示」「撤回失敗不阻擋、不轉狀態，只記 log」。此為 spec 規定的 fire-and-forget 設計：發送失敗不影響畫面狀態轉換，畫面已完成掃描中→結果的 cross-fade。方法論的「不互相抵扣」適用前提是呼叫端需要結果來做決策——此處呼叫端不做決策。**判定為 spec 規定的 design choice，非 gap**。

#### Port 5: ExternalOpener（SPEC-003 §2.2 定義，未實作）

| 時刻 | 呼叫端 | 日誌 | 備註 |
|------|--------|------|------|
| 呼叫發出 | spec（方法呼叫即事件） | **spec 未明述**（臨時實作 :233 有，但非契約義務） | 建議 W1-068 實作時補入契約 |
| 受理 | N/A | N/A | Process.run fire-and-wait |
| 結果 | Y（enum ExternalOpenResult 三值） | spec 部分（「失敗可觀測」列有 warning log，成功未述） | |

**對 W1-068 的建議**：實作時確保呼叫發出日誌為契約義務（SPEC-003 §2.2 的「可觀測性」列宜補一句「入口時以 developer.log 記錄 path」），結果成功分支亦宜有 info 日誌。

### 二、Spec 落點裁定

#### Domain 歸屬

| Port | 所屬 Domain | 理由 |
|------|------------|------|
| DirectoryPathPicker | Workspace | 資料夾選取是 workspace 的公開面 |
| WorkspacePreferencesPort/Handle | Workspace | 路徑持久化是 workspace 的內部面 |
| WorkspaceDirectoryProbePort | Workspace | 可用性探測是 workspace 的內部面 |
| ScanNotifier | 跨 domain（Diagnostics 產出 → 通知遞送） | SPEC-003 §2.2 已定義契約，服務 UI 層 |
| ExternalOpener | 跨 domain（任何畫面可觸發） | SPEC-003 §2.2 已定義契約，服務 UI 層 |

#### 裁定：雙落點

**Workspace 三個 port → 新建 `docs/spec/workspace/SPEC-005-workspace-driven-ports.md`**

理由：
1. Workspace domain 在 `docs/spec/` 下零 spec——domain-map §3 界定其公開面（目前路徑、可用性狀態、開啟原始檔）與內部面（路徑持久化、可用性探測），但專案 spec 層無對應文件
2. 三個 port 的變更理由相同（「資料夾存取方式改變」），歸同一份 spec 符合 SRP
3. 內容：三個 port 的回饋點覆蓋表（本 ANA 產出的表格轉化為規範形式）、兩步/單步 API 的設計理由引用（回指 W3-133 裁定）、測試義務（回指方法論但列出本專案的 fixture 紀律）

**ScanNotifier + ExternalOpener → 修訂 SPEC-003 §2.2 既有契約表**

理由：
1. SPEC-003 §2.2 已有兩者的完整契約表（介面、可觀測性、測試斷言、i18n），不需要搬遷
2. 缺的是三時刻 x 兩消費者的顯式覆蓋表——追加為§2.2 各契約表的子節即可
3. ScanNotifier 和 ExternalOpener 服務的是 UI 互動（通知使用者、開啟檔案），留在 UI domain spec 是 domain-correct

### Rationale Chain
- 0.1.0-W3-107 why: 用戶裁示（2026-09-08）：回饋契約的三層結構要應用到 Clean Architecture 的六角結構，**不只輸入端**——服務本身往外呼叫（開檔案、開資料庫、打 API）也適用同一設計原則，也都應該被列入測試。

差別在**回饋的消費者**，不在結構：

| | 輸入端（driving port） | 輸出端（driven port） |
|---|---|---|
| 觸發者 | 使用者 | 應用層／領域層 |
| 回饋消費者 | 使用者（視覺／觸覺／聲音） | 呼叫端執行緒、log、APM（如 sentry） |
| 三層對應 | 按下確認／服務受理／event 效果 | 呼叫發出／外部系統受理／結果 |

用戶另指出一個時序約束：「**都是需要先設定好這個回饋點機制，才做得到**」——log 與 APM 追蹤不是事後可以補上的能力，它們消費的是設計期就要決定的回饋點。沒有預先定義回饋點，追蹤工具能拿到的只有例外堆疊，拿不到「呼叫發出了、外部系統收到了、結果是什麼」這三個時刻。

1. **回饋契約目前只長在元件庫方法論裡**（`component-library-bidirectional-constraint-methodology.md`），那是 UI 層的載體。架構層原則長在 UI 方法論下，其他層的實作者不會讀到。
