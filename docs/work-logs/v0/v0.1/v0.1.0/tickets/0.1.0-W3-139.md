### Rationale Chain
- 0.1.0-W3-107 why: 用戶裁示（2026-09-08）：回饋契約的三層結構要應用到 Clean Architecture 的六角結構，**不只輸入端**——服務本身往外呼叫（開檔案、開資料庫、打 API）也適用同一設計原則，也都應該被列入測試。

差別在**回饋的消費者**，不在結構：

| | 輸入端（driving port） | 輸出端（driven port） |
|---|---|---|
| 觸發者 | 使用者 | 應用層／領域層 |
| 回饋消費者 | 使用者（視覺／觸覺／聲音） | 呼叫端執行緒、log、APM（如 sentry） |
| 三層對應 | 按下確認／服務受理／event 效果 | 呼叫發出／外部系統受理／結果 |

用戶另指出一個時序約束：「**都是需要先設定好這個回饋點機制，才做得到**」——log 與 APM 追蹤不是事後可以補上的能力，它們消費的是設計期就要決定的回饋點。沒有預先定義回饋點，追蹤工具能拿到的只有例外堆疊，拿不到「呼叫發出了、外部系統收到了、結果是什麼」這三個時刻。

現況三項缺口：

1. **回饋契約目前只長在元件庫方法論裡**（`component-library-bidirectional-constraint-methodology.md`），那是 UI 層的載體。架構層原則長在 UI 方法論下，其他層的實作者不會讀到。
2. **`clean-architecture-implementation-methodology.md` 完全沒有回饋相關內容**（實查：「回饋」「adapter」「port」三詞零命中）。它有依賴方向、介面契約、業務邏輯位置的檢查清單，但沒有「這個 port 的呼叫有沒有可觀測的三個時刻」。
3. **`observability-rules` 是從日誌側寫的**（catch 要有日誌、統一日誌工具、全域錯誤處理、關鍵流程三階段），回答「發生了要記下來」；不回答「哪些時刻**必須**是可觀測的回饋點」。兩者互補但目前沒有接線——`ARCH-GPD-001` 已寫明日誌與使用者回饋是獨立義務，但沒說輸出端的「執行緒回饋」與「日誌」是什麼關係。（來源已完成，結論見 Solution）
- 0.1.0-W3-133 why: Phase 4a 兩個視角對同一問題給出方向相反的意見，需要裁定。

**linux（Acceptable 偏低）主張補 adapter 層**：`WorkspaceRepository` 同時是 repository 又是三個 adapter。方法論〈Port 回饋契約〉自己寫了承擔者分工——呼叫發出歸呼叫端，受理與結果歸 **adapter**——但本專案沒有 adapter 層，repository 直接寫 `SharedPreferences.getInstance()`、`Directory(path).list()`。於是要讓 adapter 內部的「受理」時刻可觀測，唯一手段是往 repository 身上鑿洞：`WorkspacePreferencesHandle` 的存在理由只是 `getInstance()` 是兩段式 API，那是 SharedPreferences 的實作細節，卻被提升成 repository 的公開介面。它主張三個真 adapter 類別（各自獨立檔案）可讓接縫從 5 降到 3，可觀測性一條不減。
