## NeedsContext
### 階段 2 草稿：9 項需新判準（未落檔，待 PM／WRAP 裁決）

以下條文風險與 DOC-14b 經查證後皆無非範例的既有依據，屬新判準需求，依步驟 3 停手，草稿如下：

#### 風險 3：樂觀更新「低風險」定義的時點模糊
- **問題**：`component-library-spec-template.md`〈2. 狀態綁定模式〉「低風險＝伺服器拒絕並還原畫面後，不留下還原提示無法抵銷的外部後果」——「拒絕並還原後」為時點，但金流／庫存扣減等例示的外部後果通常發生於伺服器**受理**當下而非拒絕之後，讀者無法判定「受理前已產生、拒絕後才顯現」的後果算不算數。
- **選項**：A 不動（本批已用「可逆」分支避開，未阻塞現行探針）；B 補一句「後果判定不分先後，凡該操作曾使伺服器產生外部效果（無論拒絕前後）即不得樂觀」；C 改用「操作送出後、結果確認前，是否已對外部系統產生不可逆效果」取代「拒絕並還原後」的時點敘述。
- **建議**：B 或 C 需驗證是否與現行「AND：低風險且可逆」判準衝突，建 WRAP 評估後裁定。

#### 風險 5：design token 消費者範圍表與強制規則直接衝突（真衝突）
- **問題**：`design-system-spec-template.md`〈10〉消費者範圍表「僅 1 個 domain 使用 → `{domain}/constants/`（範例：某 feature 專屬的 badge 大小）」與強制規則「所有 design token…必須集中於 design system 目錄」「禁止 design token 散落在各 feature 目錄」及決策表第一題（視覺 token → 集中目錄）直接矛盾：badge 大小屬視覺 token（間距／尺寸），依強制規則應集中，消費者範圍表卻允許留在 domain。
- **選項**：A 刪除消費者範圍表第一列（視覺 token 一律集中，不論消費者數）；B 消費者範圍表改標「僅適用純業務常數」，與強制規則的視覺 token 範圍分流；C 反向修正強制規則，允許單一 domain 使用的視覺 token 留在 domain。
- **建議**：A 或 B（與風險 6 一併裁決，兩者皆涉及「消費者範圍表」的適用範圍是否限縮為純業務常數），需 WRAP 評估。

#### 風險 6：純業務常數例外與決策表第二題直接衝突（真衝突）
- **問題**：強制規則「純業務常數（如預設標籤名稱）不在本規則範圍，可留在所屬 domain」對純業務常數給予無條件豁免；決策表第二題「此常數是否被 2+ domain 使用？是→放 `core/`，否→放所屬 `domain/constants/`」卻對純業務常數也套用消費者數量判準。兩者對「跨 domain 使用的純業務常數」給出不同位置。
- **選項**：A 決策表第二題明訂僅適用純業務常數（強制規則的「不在本規則範圍」改為「不受第一題視覺 token 判準拘束，但仍受第二題消費者數量判準」）；B 強制規則的豁免改為絕對豁免，決策表第二題加註「僅適用非純業務常數」；C 拆表——視覺 token 一張決策表，純業務常數另一張。
- **建議**：需與風險 5 一併決定「消費者範圍表」與「強制規則」的分工邊界，建 WRAP 評估。

#### 風險 8／DOC-14b：降級後表現「不得無感、須標示已降級」只在已刪除範例 E-14
- **問題**：`E-14`【驗證】段「降級後的可見表現是否可以完全等同原本即時同步的畫面（讓使用者無感）？預期：否，必須明確標記已降級」，此結論在範本〈回饋契約〉「降級不解除回饋義務」段與方法論同名節皆無明文（兩處只要求「可見表現須寫明」與「前提不成立時的替代表現」，未要求表現須與正常態有別或須標記）。本批 DOC-14b 之判定不依賴此句（見附記「不影響判定」），但作為條文本身仍有缺口。
- **選項**：A 不補（現行兩處要求已足夠約束「須有表現」，「是否要求視覺上明顯有別」留待實例累積後再定）；B 於方法論〈降級不解除回饋義務〉Action 補一句「該表現不得與正常狀態的表現無法區分，須有可辨識降級已發生的標記」；C 只在範本補（不動方法論），視為 L3 專案層級加嚴。
- **建議**：B（提升為 L1 通用判準，理由與方法論 Why 段「收斂到沒有表現的狀態等同銷毀證據」一致——若表現與正常無異，效果與零表現相同），需 WRAP 評估後決定措辭。

#### 風險 10：播報替代填入回饋通道子表哪一格未交代
- **問題**：〈回饋通道子表〉引言「播報替代不因該形態非觸控裝置而豁免」，但子表列＝六類事件、欄＝形態，未指明播報替代該填入哪個事件列（如僅 state-change，或任一因通道限制需要替代的事件皆可）。
- **選項**：A 補一句「播報替代填入該事件在對應形態欄的格內，與其他替代通道同格併列，不限於單一事件」（即：非固定列，依需要替代的事件而定）；B 限定僅 state-change 與 affordance 兩列適用播報替代；C 另立獨立列「播報（跨事件）」。
- **建議**：A（與現行「格內容三選一」的填表邏輯一致，播報只是等價替代的一種形式，不需要另立特例列），需 WRAP 確認不與無障礙子節「狀態變化播報」重複定義。

#### 風險 11：測試點／組合規則的規則內容置於佔位符大括號內，易誤讀為待填範例
- **問題**：`組合規則`表「作為表格或列表的一欄時 | {欄比例 / 固定寬（引用 token）；內距（引用 token）}」與`測試點` checklist「{回饋契約每個已定義事件各自一則測試…}」的規則本身寫在 `{…}` 內，`{…}` 慣例上代表「待填空」，讀者可能誤判為範例而非規則（惟本批答案鍵已直接引用這些大括號內文字作判準依據，顯示目前仍可正確解讀，非阻斷性缺口）。
- **選項**：A 不動（現行已可正確解讀，risk 屬觀察）；B 將這兩處規則移出大括號，改寫為固定規則文字，大括號僅保留真正待填部分；C 全文加一句通用說明「表格與 checklist 內的 `{…}` 若描述的是可選項清單或固定規則（非留白提示），視為規則本身」。
- **建議**：B（結構性消除歧義，且不改變任何判準內容，屬格式重構非新判準——但因涉及範本多處格式改寫，範圍不小，仍列草稿待 PM 排入 Wave）。

#### 風險 12：操作機制範本佔位例示與範例 E-16 產出逐字重複（觀察，非缺口）
- **問題**：`操作機制`表佔位例示「整數 1 步（0-100 共 101 值）」「滑桿軌道 240px，約每 2px 一個值 → 足夠」與範例 E-16 產出逐字相同，未來若再用滑桿類輸入出題，可能誤把範本佔位例示當成獨立於範例之外的依據，實際上兩者同源。
- **建議**：不需 WRAP，僅供出題與後續維護者知悉：後續操作機制類題目與範例應避免重複沿用滑桿 240px 這組數字，改用其他輸入裝置（如本批已用座位圖點選）以避免同構污染。

#### 風險 13：範例輸出表格式與範本實際欄位結構不一致
- **問題**：E-16 產出把「足夠／不足」獨立成欄，範本〈操作機制〉合併為「具體值 → 足夠 / 不足」一欄；E-18 產出列為三欄（文字｜key｜是），範本〈i18n〉表只有兩欄（文字｜i18n key）。範例示範的輸出格式與範本實際要求的表格結構不一致，可能誤導讀者以為範例格式才是正確格式。
- **選項**：A 修正範例輸出表，改為與範本欄位結構一致；B 不動，於範例前加註「輸出表格式僅供示意判準，實際填寫以範本欄位結構為準」。
- **建議**：A（範例本應示範正確格式），但屬範例檔內容修改而非新增判準句，且會變動既有已驗證範例內容，故仍列草稿待 PM 確認影響範圍後排入 Wave，不在本票逕行修改。

#### 風險 14：豁免清單條件 1「套件提供但頁面直用之元件」封裝失敗後屬何類未定
- **問題**：`豁免清單`引言允許「套件提供而由頁面直接使用的元件」在先以元件庫元件封裝、失敗並記錄路徑後主張豁免，但此類已被明文排除於「第三方套件類」（限套件內部生成、呼叫端無法替換子件者），應歸方法論〈豁免三條件〉條件 1 列舉的哪一類（測試斷言／效能豁免／非視覺輔助結構件／一次性刻意破格）未交代；範例 E-24 產出第一列判「可豁免」也未指類別。
- **選項**：A 新增第五個子類別「套件提供但頁面直用、封裝失敗」，獨立於既有四類；B 依失敗原因逐案歸入既有四類最接近者（多數情況為效能豁免，需附 profiler 證據）；C 要求此類一律先建元件票，不接受直接豁免（收緊現行允許）。
- **建議**：B 或 C 需先盤點過去豁免清單實際案例的失敗原因分布，建 WRAP 評估或 ANA 查證後裁定。
