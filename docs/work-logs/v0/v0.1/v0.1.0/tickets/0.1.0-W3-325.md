## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

**機制不是 argparse 原生的 nargs="+" 貪婪收值**，而是本檔自建的兩道加固共同作用的結果。純 argparse 對未註冊的 `-` 開頭 token 會回 `unrecognized arguments` 並 exit 2（同檔其他子命令實測即如此）；靜默吸收需要以下兩者同時成立：

| 環節 | 位置 | 作用 |
|------|------|------|
| 前處理器 `_escape_dash_prefixed_keyword_values` | `section_comment.py`（`main()` 開頭、`parse_args` 之前） | 收值階段中凡 `-` 開頭且不在停止白名單內的 token，一律加不可見前綴，argparse 因此看不出它是旗標，收為關鍵字值 |
| gh 呼叫的 `--` 分隔符 | `search_issues_by_keyword` | 關鍵字排在全部旗標之後、以 `--` 分隔，使被吸收的 `--all` 成為合法 gh 搜尋詞而非 unknown flag，查詢不失敗，`skipped=0` |

兩道加固各自的目的正當（讓「commit -a」「--force」這類含 `-` 的**字面**查重關鍵字可用），合起來的副作用是把「未知旗標」從硬錯誤變成靜默吸收。

**停止白名單已實際漂移**（非假設）：`_KEYWORD_VALUE_STOP_FLAGS` 的註解自述「集合僅列本檔實際註冊的旗標」，但實測本檔註冊 21 個 option string，白名單只列 12 個，缺 7 個——`--all`／`--consumer`／`--issue`／`--json`／`--priority`／`--stage`／`--status`，**全數為 `todo` 子命令的旗標**（該子命令後加，白名單未同步）。`--all` 正落在此缺口內。白名單無反向多餘項（STOP 減 REGISTERED 為空）。

由此分出兩個性質不同的層次：

1. **實作偏離已明示的契約**：白名單應等於本檔註冊旗標集合（扣除兩個 multi-value 旗標本身），現缺 7 項。predicate 機械可判，補齊後 `dedup --keywords x --all` 會與 `--owner`／`--force` 一樣 exit 2。
2. **未註冊 token 的意圖歧義**：即使補齊白名單，任意拼錯（`--forc`／`--keywrods`）與真正的字面值仍不可區分。此為現行契約**明文允許且已被測試固定**的行為（見「相關 Error Pattern」），改動即改契約。

### 實驗發現

**已驗證的事實**

1. 靜默吸收面**限 2 處**（`init --dedup-keywords`、`dedup --keywords`），其餘 7 子命令與其他 `.claude/` CLI 皆 exit 2。「不只 dedup 一處」的假設成立，但規模是 2 不是全檔。
2. 觸發條件是**白名單缺項**，非 nargs 本身：白名單內的旗標照樣被拒。白名單現缺 7 項且全為 `todo` 子命令旗標，漂移已實現。
3. 拼錯字串（`--forc`／`--keywrods`）與短旗標（`-x`）同樣被吸收——此類**無法靠補白名單消除**，與缺項是兩個不同層級的問題。
4. `--all` 作為搜尋詞實際命中 8 則 issue，且末行涵蓋缺口宣告為 0，報告在每一個機械訊號上都與正確執行同形或更「成功」。

**仍未驗證的假設**

- 歷史上是否真發生過範圍失真的 dedup：查無痕跡，且記錄形式使其原則上難以留痕，據實記為未知（推理見 Problem Analysis）。
