## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 範圍與前提修正（flutter_balance 交叉核對 + 本側查證，2026-09-07）

**一、範圍是三檔不是兩檔。** 同一個發佈庫 commit `563e9fc` 一併刪除的還有
`scripts/portability-check.sh`。本側查證：該檔存在（8/27 建立），**未進 settings**——
與另兩個 hook 的狀態不同，故三檔可能需要分別裁決而非一次定案。

| 檔 | 本地 | settings 註冊 | hook-logs |
|----|------|--------------|----------|
| `hooks/comment-qa-hook.py` | 在，可執行 | 4 處（與另一 hook 合計） | 有 09-03／09-04 |
| `hooks/worklog-format-check.py` | 在，可執行 | 同上 | 有 |
| `scripts/portability-check.sh` | 在 | **0 處** | 不適用（非 hook） |

**二、廢除的前提被證偽。** 發佈庫 `563e9fc`（v0.92.0）的 CHANGELOG 條目逐字寫
「兩者在 0.17.0 就宣告移除（職責已由其他機制覆蓋），而檔案留在原地……**任何 settings
都沒有註冊它們**」。

該前提對廢除方成立，對至少兩個 consumer 不成立：本專案 4 處註冊、flutter_balance
4 處註冊（該側行號 L681／L690／L745／L759）且該檔於 09-02 還被其票修改過。

**三、本專案的 CHANGELOG 與檔案系統自相矛盾。** 本地
`compositional-writing/CHANGELOG.md` 第 53 行已含該 0.92.0 條目——它是隨
`skill-sync pull`（1.5.2 → 1.7.1）進來的，而 pull 的 local-only 保留機制把三個檔留下了。
**於是本專案同時持有「宣告刪除的紀錄」與「未被刪除的檔案」，兩者互相否證而無人察覺。**

該條目自己也寫了機制：「刪除靠 `skill-sync push --prune` 傳播，否則本地刪掉而其他
消費端繼續 pull 到它」——作者知道傳播需要 `--prune`，但 pull 不刪 local-only 檔，
所以已安裝的 consumer 一律留著。

**四、對應票與約束。** flutter_balance 側對應票為 `0.2.1-W3-1250`（三方定案）。
**定案前雙方皆不對 `compositional-writing` 執行 `skill-sync push`**——任一方 push
都會把三檔送回發佈庫，覆蓋廢除方的決定。

**五、裁決的關鍵未知**：「職責已由其他機制覆蓋」中的「其他機制」是什麼。
該側在自己專案查不到。已向廢除方（`compositional-writing` 的維護專案）詢問，
回覆到手後轉該側一份，其票面要引用。

定案方向二擇一：全體廢除並解除註冊，或發佈庫恢復三檔並更正 0.92.0 條目。
