**缺失項**：「無提案」狀態錨點命名不一致（SPEC-003 §3.3／§4 #14 為 `state-traceability-empty`，
`lib/screens/trace/trace_screen.dart` 與 `test/unit/screens/traceability_test.dart` 為
`state-traceability-no-proposal`）。Problem Analysis 指示「以 SPEC-001／SPEC-004 為佐證判定，
兩者一致時改 SPEC-003；不一致或需改產品碼時停手寫 NeedsContext」。

**觸發位置**：`docs/spec/ui/SPEC-003-interaction-response.md` §3.3〈互動反應〉「跳轉破洞報告」列、
§4 #14；`lib/screens/trace/trace_screen.dart:42`；`test/unit/screens/traceability_test.dart:6,117,124,146`。

**已 grep 佐證**：SPEC-001 v1.15、SPEC-004 v1.41 全文皆不含 `state-traceability-empty` 或
`state-traceability-no-proposal` 字面（兩者對此狀態皆只用中文狀態名「無提案」，不落地機械
anchor 字面）。但本 App 既有 anchor 命名慣例可交叉比對：「無 X」狀態在其餘畫面一律採
`-empty` 後綴（UC Flow「無 UC」→`state-ucFlow-empty`；Ticket「無 ticket」→`state-tickets-empty`），
與 SPEC-003 現行的 `state-traceability-empty` 一致；產品碼的 `state-traceability-no-proposal`
偏離此既有命名慣例，屬命名例外或歷史遺留。

**影響**：若依「SPEC 兩份佐證與產品碼一致才改 SPEC-003」的判準，SPEC-001／SPEC-004 兩份文件
皆未直接佐證任一寫法，僅能以既有 anchor 命名慣例間接支持 SPEC-003 現行寫法；產品碼與此慣例
不一致，修正需要**改動產品碼**（`trace_screen.dart` 與對應測試），超出本票 where.files
（僅 `docs/spec/ui/SPEC-003-interaction-response.md`）與唯讀稽核範圍。本票依指示不動 SPEC-003
此處，亦不改產品碼。

**建議補料**：另立 IMP/DOC 票，二選一：(a) 改產品碼 anchor 為 `state-traceability-empty`
以符合既有 `-empty` 命名慣例（連動測試檔字面與任何其他引用）；(b) 若判定
`no-proposal` 為刻意的語意精確化例外，改 SPEC-003 對應處為 `state-traceability-no-proposal`
並於命名慣例段落註記此例外理由。兩案皆需 PM 或 SA 裁決優先方向。

**重派成本**：低——grep 佐證已完成，候選方案已列出，只待裁決優先方向後執行單一改動點
（SPEC-003 兩處或產品碼一處 + 對應測試）。
