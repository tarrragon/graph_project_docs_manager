### 由 `0.1.0-W3-176` Phase 4a 轉來的兩項觀察（PM 路由，2026-09-10）

兩項皆經審查判定**當前不可達、不建票**，但本票要改寫的正是那條路徑，改寫時須各看一眼。

**觀察 A：`reason == hide` 是承重前提，但無守衛。**
現行實作以 `SnackBarClosedReason.hide` 判定「這則是被後續一次 `show` 截斷的」。該等價關係成立的前提是 `hideCurrentSnackBar()` 全 repo **恰 2 處**（審查實測：`app_snack_bar.dart:173` 預設 `hide`、`:220` 明確 `action`；無 `removeCurrentSnackBar` / `clearSnackBars`）。若日後新增第三個呼叫點，`hide` 不再恆等於「被截斷」，warning 會開始標到另一類事件上，而 T-1～T-9 沒有任何一個會紅燈。本票既然重寫截斷條件，**須重新確立或以斷言鎖住這個前提**，不可預設它繼續成立。

**觀察 B：動作回呼的順序在理論上可產生未稽核的截斷。**
`app_snack_bar.dart:214-223` 的順序為 `log(actionPressed)` → `onAction()` → `hideCurrentSnackBar(reason: action)`。若某個 `onAction` **同步**呼叫 `AppSnackBar.show`，新的一則會先取代舊的（記 `hide`），隨後那句 `hideCurrentSnackBar(reason: action)` 會把**新的那一則**以 `action` 關掉——新訊息使用者一眼未見，日誌記為 `closed{reason=action, level=null}`，**正好是這條線要消滅的那種不可稽核截斷**。

當前不可達：唯一的 `withAction` 呼叫點（`gap_report_screen.dart:199`）其 `onAction` 回傳 Future 且未 await，同步段不顯示任何 SnackBar。且此順序繼承自 `0.1.0-W3-165`，非新引入。本票改寫該段時一併確認新設計是否仍有此形態。

#### 1. Purpose

**問題**：`AppSnackBar.show` 在顯示前無條件 `hideCurrentSnackBar()`，截斷的唯一依據
是「這次呼叫發生了」——即 SPEC-003〈鑑別「綁級別」與「綁呼叫路徑」兩種實作〉判為
「綁呼叫路徑」的那一種。同時 `lib/main.dart` 的 `ChooseFolderUnavailable` 分支直接
呼叫 `ScaffoldMessenger.showSnackBar` 繞過元件層，使干擾不對稱（元件路徑殺得掉原生
路徑的訊息、反之不行）且被殺的那則零日誌。

**目標**：兩件事，順序不可調換。

1. 收斂入口：全部提示經 `AppSnackBar`，使「哪些訊息在競爭同一個顯示位」是一個可以
   被完整回答的問題。
2. 把截斷條件綁在級別上：`show` 接受級別參數，截斷與否的唯一輸入是「新請求的級別」
   與「當前持有者的級別」，判定落在單一純函式內，靜態可讀出。

**可觀察的改善**：截斷發生時，日誌能回答被截斷的是哪一則（`0.1.0-W3-176` 的
`showId` 已使被截斷者自報身分，本票再補「誰截斷了誰」的關聯）；讓步發生時（低級別
遇高級別持有者），被丟棄的那一則不再無聲——它從未呈現，但留下一筆帶級別與訊息的
事件。

**非目標**：

- 不引入任何形式的提示佇列（`0.1.0-W3-239`），含 Material 內建 FIFO。讓步的處置是
  **不呈現**，不是排隊等待。
- 不在元件內持有「當前顯示者」狀態（見第 0 節步驟 3）。
- 不改 SPEC-003 任一條文；不改 `0.1.0-W3-176` 已落地四個事件值的語意（本票只新增
  兩個事件值）。
- 不實作仲裁器（`0.1.0-W3-207`）。本票只實作載體側，且介面形狀對齊該票 Solution
  第 2.6 節的 C1／C3／C5／C6 四項載體側契約。
- G2（實際可見時長）／G3（未顯示的決定）不在本票（`0.1.0-W3-241`／`242`）。

| 由 `origin`（`AppSnackBarOrigin`）推導 | **否決** | 兩者不同軸且非單射。`origin` 的值域是 {使用者發起, 背景發起}，它回答「截斷這一則要不要記 warning」（SPEC-003〈截斷事件的日誌等級〉明訂以發起者為鍵）；級別回答「誰能截斷誰」。實查 §2.14 指派表：13 列中可棄組（列 1、3、5–10）橫跨自發型與等待型、亦橫跨背景發起（列 3）與使用者發起（列 5–10），不可棄組（列 11–13）全為自發型且不走 SnackBar。以 `origin` 推導在 0.1 只能得到常數函式（全部映射到可棄）；一旦 §2.14 新增一則背景發起的須留痕 SnackBar，其 `origin` 與列 3 完全相同而級別不同，推導函式無從區分。更根本的後果是耦合：合併後任一條規則的修改會污染另一條 |
| 由 `variant`（`plain` / `withAction`）推導 | **否決** | SPEC-003〈截斷事件的日誌等級〉已明寫「以變體為鍵會同時誤判兩邊」，該論證對級別同樣成立且更強——變體是版面決策（T4 的產物），與級別無因果 |
| 由呼叫端查 §2.14 指派表後以顯式參數傳入 | **採用** | 級別是請求的屬性、在標定點標定（SPEC-003 §2.14〈級別的標定依據〉，回答「級別是靜態標註還是動態推導？」——答案是靜態標註）。呼叫端即標定點所在處，是唯一持有該資訊的位置。參數**必填**（不給預設值）：預設值會使「確實是可棄」與「呼叫端忘了查表」在型別與日誌上都不可區分，而後者正是本票要消除的那一類無聲降級 |

##### 2.1 級別型別的落點

| 項目 | 規格 |
|------|------|
| 型別 | `enum AttentionLevel { discardable, mustLeaveTrace, undroppable }`，列舉順序即優先序，`index` 越大級別越高 |
| 對應 | 與 SPEC-003 §2.14 級別欄主名一一對應：可棄／須留痕／不可棄。0.1 無須留痕實例，仍為合法值（`0.1.0-W3-207` Phase 1 同此裁決） |
| 檔案 | **`lib/app/attention_level.dart`（新增，僅型別無行為）** |
| 為何不放元件內 | 票面 acceptance 第三項要求「元件內未另立一套級別定義」。若定義在 `app_snack_bar.dart`，`0.1.0-W3-207` 的仲裁器需要同一組值，而該票 acceptance 明訂仲裁器不得 import `AppSnackBar`——結果必然是兩份平行定義，即 §2.15 警告的兩份同一事實。放 L4 的獨立型別檔，兩者各自 import 同一份 |
| 與 `0.1.0-W3-207` 的關係 | 該票 Phase 1 的 2.2 節把此列舉寫在 `lib/app/attention_arbiter.dart` 內。名稱、值、順序完全相同，差別只在檔案。本票先落地，故由本票建立該檔；207 落地時改為 import。已登記為 spawn request 請 PM 對齊（第 10 節） |

##### 2.2 `show()` 簽名（粗體為本票新增）

```dart
static void show(
  BuildContext context, {
  required String message,
  required AttentionLevel level,            // 新增，必填
  AppSnackBarVariant variant = AppSnackBarVariant.plain,
  String? actionLabel,
  VoidCallback? onAction,
  Key? actionTestKey,
  AppSnackBarOrigin origin = AppSnackBarOrigin.background,
  AttentionHolderHint? currentHolder,       // 新增，過渡形態（見 2.7）
});
```

```dart
/// 呼叫端已知的當前通道持有者快照。
///
/// 過渡形態：`0.1.0-W3-207` 的仲裁器合併後，本型別與 `currentHolder` 參數一併
/// 由 `AttentionAccepted.preempted` 取代（收斂由該票承擔，見 2.7）。
final class AttentionHolderHint {
  const AttentionHolderHint({required this.showId, required this.level});
  final int showId;          // 被截斷者的識別（與 0.1.0-W3-176 的 showId 同一空間）
  final AttentionLevel level;
}
```

`currentHolder == null` 的語意是**未知**，不是「通道為空」。過渡期呼叫端無資訊來源，
一律傳 null；此時行為與現況一致（截斷後呈現），但事件必帶 `holderUnknown: true`，
使「這個判斷還沒有輸入」本身可被搜尋、可稽核，而非靜默退化為舊行為。

##### 2.3 截斷裁決（唯一的裁決表）

判定落在單一私有純函式，輸入恰為兩項，不接受 `variant`／`origin`／`message`／
`context`——函式體因此**不可能**引用它們（結構性可讀出，形態沿用
`0.1.0-W3-176` 的 `_resolveClosedLevel`）：

```dart
enum _Preemption { holderUnknown, preemptLower, replaceSameLevel, yieldToHolder }

static _Preemption _resolvePreemption(
  AttentionLevel incoming,
  AttentionHolderHint? holder,
);
```

| 持有者 | 新請求級別 | 結果 | 行為 | 依據 |
|--------|-----------|------|------|------|
| `null`（未知） | 任意 | `holderUnknown` | `hideCurrentSnackBar()` 後呈現；`preempted` 事件帶 `holderUnknown: true`、`preemptedShowId: null` | 過渡形態（2.7）。不得改為「不 hide 直接 show」——那會落入 Material 內建 FIFO，即 `0.1.0-W3-239` 禁止的佇列 |
| 級別 < 新請求 | 任意 | `preemptLower` | 截斷後呈現；`preempted` 事件 `sameLevelReplace: false` | 讓步規則 1「高級別抵達時可搶佔低級別」 |
| 級別 == 新請求 | 任意 | `replaceSameLevel` | 截斷後呈現；`preempted` 事件 `sameLevelReplace: true`（留痕） | `0.1.0-W3-239` 具名例外：規則 2 在本通道以截斷並留痕取代排隊或合併。**實作不得改回排隊** |
| 級別 > 新請求 | 任意 | `yieldToHolder` | **不呼叫 `hideCurrentSnackBar`、不呼叫 `showSnackBar`**，記 `yielded` 事件後返回 | 讓步規則 3「低級別不得搶佔任何請求」。規則 3 字面為「排隊等待」，但 `0.1.0-W3-239` 裁定不引入佇列，故本專案的形態是不呈現並留痕——與 SPEC-003〈顯示位爭用時的約束與 0.1 的處置規則〉「留痕是唯一不吸收症狀的滿足方式」同一理由，且對應 `0.1.0-W3-207` 裁決表的 `Skipped`／`Rejected` 兩格 |

比較鍵恆為 `AttentionLevel.index`；元件內無以載體型別、變體或呼叫路徑為鍵的分支。

**不變式 INV-SNACKBAR-NOQUEUE**：`ScaffoldMessengerState.showSnackBar` 的呼叫在
`AppSnackBar` 內恰一處，且該處必然緊接於同一函式的 `hideCurrentSnackBar()` 之後。
任何「不 hide 就 show」的路徑都會使 Material 內建 FIFO 生效，構成 `0.1.0-W3-239`
禁止的提示佇列，並使 SPEC-003 §2.16／§2.17「佔用量恆為 0 或 1」的既有結論失效。

##### 2.4 日誌事件（新增兩值，既有四值語意不變）

```dart
enum AppSnackBarLogEvent { shown, skippedUnmounted, actionPressed, closed,
                           preempted, yielded }
```

| 事件 | 何時 | `fields`（於 `baseFields` 之外） | 等級 |
|------|------|--------------------------------|------|
| `preempted` | 截斷發生的當下，由**截斷者**記 | `level`、`preemptedShowId`（`int?`）、`preemptedLevel`（`AttentionLevel?`）、`sameLevelReplace`（`bool`）、`holderUnknown`（`bool`） | 無（info）。**被截斷那一則的嚴重度不由本事件承擔**——SPEC-003〈截斷事件的日誌等級〉的鍵是被截斷者的發起者，截斷者不知道它，該判定仍由被截斷者自己的 `closed{reason: hide}` 經 `_resolveClosedLevel` 承擔，本票不改該路徑 |
| `yielded` | 低級別讓步、決定不呈現時 | `level`、`holderShowId`、`holderLevel`、`variant`、`message` | 依 `origin`：背景發起 warning（900）、使用者發起 info。**鍵與 §2.13 一致**——此處被丟棄的告知就是新來的這一則，其發起者即 `origin` |

`preempted` 與被截斷者的 `closed{showId, reason: hide}` 兩筆合起來回答票面 acceptance
第二項：前者給出「誰截斷了誰」的關聯，後者給出被截斷者的身分與嚴重度。過渡期
`preemptedShowId` 為 null 時，關聯由 `closed{reason: hide}` 單獨承擔（即 `0.1.0-W3-176`
的現況能力），且 `holderUnknown: true` 明記關聯缺口的成因。

##### 2.5 動作回呼的順序（處置轉來的觀察 B）

現行順序 `log(actionPressed) → onAction() → hideCurrentSnackBar(reason: action)` 改為：

```text
log(actionPressed) → hideCurrentSnackBar(reason: action) → onAction()
```

**為何不用 `controller.close()`**：`ScaffoldFeatureController.close()` 在 Flutter 內部
`assert(_snackBars.first == controller)` 且以預設 `reason: hide` 關閉——既會在被取代後
觸發 assert，又會把使用者按下動作的結局錯記為 `hide`（`_resolveClosedLevel` 據此判
warning），兩者都比現況差。改順序是最小且語意正確的修法：使用者按下動作，這一則就
結束了，`onAction` 的後續效果屬另一次事件。

##### 2.7 過渡形態與收斂路徑

`0.1.0-W3-207`（仲裁器）現為進行中、實作尚未合併（實查 `lib/` 無仲裁器檔案），
故本票依票面 `how` 的過渡條款實作，並在此明記形態與收斂 trigger：

| 期別 | `currentHolder` 的來源 | `hide` 條件 | 級別比較發生在 |
|------|----------------------|------------|--------------|
| 過渡（本票落地後至 `0.1.0-W3-207` 合併前） | 呼叫端傳入；0.1 呼叫端無來源，一律 null（未知） | `_resolvePreemption` 回傳非 `yieldToHolder` | 元件內單一純函式 `_resolvePreemption`。**元件不持有任何持有者狀態**——資訊逐次由參數帶入，呼叫結束即消失 |
| 收斂（`0.1.0-W3-207` 合併後，由該票執行） | 仲裁決策 `AttentionAccepted.preempted`（該票 Solution 2.6 C1） | `preempted` 非空 | 仲裁器（L4），元件不再比較。`AttentionHolderHint` 與 `currentHolder` 參數一併刪除 |

**收斂 trigger**：`0.1.0-W3-207` 合併（狀態 (b) 明確 trigger 延後，
`decision-trigger-binding` 規則 2 合法形式）。過渡期的可稽核標記為每筆 `preempted`
事件的 `holderUnknown: true`——收斂完成時該欄位應在正式路徑上不再出現，可作為
收斂是否落地的機械判據。

**過渡期為何仍要建立完整的三條裁決路徑**：SPEC-003〈鑑別「綁級別」與「綁呼叫路徑」
兩種實作〉明訂「驗收形態必須為未來新增事件預先準備鑑別能力，而非只驗證現況」，且
其行為測試要求「注入一個目前佔用者為高級別的測試替身狀態」——`currentHolder` 參數
即該注入點。過渡期正式路徑恆走 `holderUnknown`，另三條路徑由元件層單元測試以直接
傳入快照驗證，這正是該節指定的驗收方式。

**過渡期的誠實邊界**：正式路徑上跨級別的讓步規則 1／3 不會被執行到（`holderUnknown`
無條件截斷）。這不構成規格違反——SPEC-003〈跨級別：規則 1／3 對列 1–10 與列 11–13
的驗收〉已以時序互斥證明兩規則對本專案**空成立**，且 0.1 經 `AppSnackBar` 的訊息
全為可棄一級（2.6 表逐列），跨級別情形在正式路徑上不存在。

#### 3. GWT Scenarios

級別縮寫：可棄＝D、須留痕＝T、不可棄＝U。「持有者」一律指 `currentHolder` 參數。

正常流程：

- **場景 1（過渡期正式路徑）**：Given `currentHolder == null`；When 以 `level: D` 呼叫
  `show`；Then 呼叫 `hideCurrentSnackBar()` 後呈現，發出 `preempted` 事件且
  `holderUnknown == true`、`preemptedShowId == null`，隨後發出 `shown`。
- **場景 2（高級別搶佔低級別）**：Given `currentHolder = (showId: 7, level: D)`；When 以
  `level: U` 呼叫；Then 截斷後呈現，`preempted` 事件 `preemptedShowId == 7`、
  `preemptedLevel == D`、`sameLevelReplace == false`、`holderUnknown == false`。
- **場景 3（同級別截斷並留痕）**：Given `currentHolder = (showId: 7, level: D)`；When 以
  `level: D` 呼叫；Then 截斷後呈現，`preempted` 事件 `sameLevelReplace == true`。
- **場景 4（低級別讓步）**：Given `currentHolder = (showId: 7, level: U)`；When 以
  `level: D`、`origin: background` 呼叫；Then **不發出 `shown`**、畫面上原持有者未被
  清除，發出 `yielded` 事件（`holderShowId == 7`、`holderLevel == U`、`level == D`、
  帶 `message`），等級為 900。
- **場景 5（讓步的等級鍵）**：同場景 4 但 `origin: userInitiated`；Then `yielded` 事件
  等級為 info（無 900）。
- **場景 6（動作按下的順序）**：Given `withAction` 已呈現；When 按下動作；Then 事件序為
  `actionPressed` 在前，`closed{reason: action}` 隨後，且 `onAction` 於 `hide` 之後被
  呼叫恰一次。
- **場景 7（`main.dart` 收斂）**：Given `chooseFolder` 回傳 `ChooseFolderUnavailable`；
  When 分支執行；Then 經 `AppSnackBar.show`（`plain`、`origin: userInitiated`、
  `level: D`）呈現 `chooseFolderUnavailableMessage`，且 `main.dart` 內
  `ScaffoldMessenger.of(context).showSnackBar` 零命中。

邊界條件：

- **場景 8（讓步不排隊）**：Given 場景 4 的讓步已發生；When 等待超過
  `Motion.snackBarWithAction`；Then 被讓步的那一則**不會**在稍後自行出現（無延遲呈現、
  無佇列），全程只有一筆 `yielded`。
- **場景 9（動作回呼同步再顯示，觀察 B）**：Given `withAction` 已呈現，其 `onAction`
  同步呼叫 `AppSnackBar.show`；When 按下動作；Then 新的一則不被 `reason: action` 關閉
  ——新 `showId` 的 `closed` 事件不得帶 `reason: action`；使用者可見到新的一則。
- **場景 10（`hideCurrentSnackBar` 呼叫點守衛，觀察 A）**：靜態掃描
  `lib/components/app_snack_bar.dart` 原始碼：`hideCurrentSnackBar` 恰 2 處（一處預設
  `hide`、一處明確 `reason: action`），`removeCurrentSnackBar` 與 `clearSnackBars` 皆 0；
  全 `lib/` 範圍內該三個識別符在本元件之外零命中。
- **場景 11（裁決函式不接受無關輸入）**：靜態檢查 `_resolvePreemption` 的參數恰為
  `(AttentionLevel, AttentionHolderHint?)`，其函式體不含 `variant`／`origin`／
  `message`／`context`／`Type` 判斷（SPEC-003〈鑑別「綁級別」與「綁呼叫路徑」〉靜態
  檢查列）。
- **場景 12（級別定義唯一）**：靜態檢查 `AttentionLevel` 在 `lib/` 內恰一處宣告，且
  三個值與 SPEC-003 §2.14 級別欄主名一一對應；`app_snack_bar.dart` 內無第二套級別
  列舉或級別常數。
- **場景 13（`showSnackBar` 呼叫點唯一且必接於 hide 之後）**：靜態檢查
  INV-SNACKBAR-NOQUEUE（2.3）。

異常流程：

- **場景 14（context 已卸載）**：Given `context.mounted == false`；When 呼叫 `show`；
  Then 行為與現況一致——發出 `skippedUnmounted`（warning）後返回，且**不呼叫**
  `hideCurrentSnackBar`（不得因為新增裁決而在早退前先截斷）。
- **場景 15（`withAction` 缺 slot）**：Given `variant: withAction` 而 `actionLabel` 或
  `onAction` 為 null；When 呼叫；Then 觸發既有 assert（行為不變）。
- **場景 16（持有者快照已失效）**：Given `currentHolder` 指向一則已自然過期消失的
  SnackBar；When 以較低級別呼叫；Then 元件仍依級別讓步（不驗證快照新鮮度）。**理由**：
  快照新鮮度屬持有者狀態，元件不持有亦不查詢；收斂後由 `0.1.0-W3-207` 的逾期懶檢查
  （該票場景 11）承擔。過渡期呼叫端一律傳 null，此路徑不會在正式路徑發生。

#### 4. Error Handling

| 錯誤情境 | 處理策略 | 回傳／拋出 | 需要回滾？ |
|---------|---------|-----------|-----------|
| `context` 已卸載 | 早退，不觸碰 messenger | `skippedUnmounted`（warning），無截斷 | 否 |
| `withAction` 缺 `actionLabel` / `onAction` | 開發期 assert（既有） | assert 訊息不變 | 否 |
| 呼叫端未傳 `level` | 編譯失敗 | 必填參數，無執行期分支 | 否 |
| `currentHolder` 為 null（資訊缺席） | 不猜測、不代填，退回無條件截斷並標記 | `preempted{holderUnknown: true}` | 否 |
