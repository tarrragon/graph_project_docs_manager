### 由 `0.1.0-W3-176` Phase 4a 轉來的兩項觀察（PM 路由，2026-09-10）

兩項皆經審查判定**當前不可達、不建票**，但本票要改寫的正是那條路徑，改寫時須各看一眼。

**觀察 A：`reason == hide` 是承重前提，但無守衛。**
現行實作以 `SnackBarClosedReason.hide` 判定「這則是被後續一次 `show` 截斷的」。該等價關係成立的前提是 `hideCurrentSnackBar()` 全 repo **恰 2 處**（審查實測：`app_snack_bar.dart:173` 預設 `hide`、`:220` 明確 `action`；無 `removeCurrentSnackBar` / `clearSnackBars`）。若日後新增第三個呼叫點，`hide` 不再恆等於「被截斷」，warning 會開始標到另一類事件上，而 T-1～T-9 沒有任何一個會紅燈。本票既然重寫截斷條件，**須重新確立或以斷言鎖住這個前提**，不可預設它繼續成立。

**觀察 B：動作回呼的順序在理論上可產生未稽核的截斷。**
`app_snack_bar.dart:214-223` 的順序為 `log(actionPressed)` → `onAction()` → `hideCurrentSnackBar(reason: action)`。若某個 `onAction` **同步**呼叫 `AppSnackBar.show`，新的一則會先取代舊的（記 `hide`），隨後那句 `hideCurrentSnackBar(reason: action)` 會把**新的那一則**以 `action` 關掉——新訊息使用者一眼未見，日誌記為 `closed{reason=action, level=null}`，**正好是這條線要消滅的那種不可稽核截斷**。

當前不可達：唯一的 `withAction` 呼叫點（`gap_report_screen.dart:199`）其 `onAction` 回傳 Future 且未 await，同步段不顯示任何 SnackBar。且此順序繼承自 `0.1.0-W3-165`，非新引入。本票改寫該段時一併確認新設計是否仍有此形態。

### Rationale Chain
- 0.1.0-W3-184 why: **用戶更正（2026-09-09）**，起因是 PM 把提示密度問題框成「先問這些提示時刻是否都必要」：

> 這樣也不完全正確。如果需要提示使用者的訊息，表示有他的重要性，那**有重要性的動作，不應該同時大量執行**，或者真正有重要問題發生的時候，**應該要暫停背景的行為**，所以我才提到有的提示訊息要擋住使用者的操作。
>
> 那重點是當我們設計 spec 的時候，也要評估**有哪些行為會在背景執行，哪些動作會在前台跟使用者互動**，是不是有些動作要**避免同時請求使用者的關注或者指令**，或者會造成互動影響的 SPEC 在設計的時候，**整個事件流就應該包含跟其他 domain 確認過再執行，或者應該加入延遲的動作**。

**PM 原本的框架把提示當成雜訊，這是錯的。** 提示需求本身是重要性訊號——需要提示使用者，表示該事件有重要性。因此提示密度過高不是「提示太多」，是**同時執行了太多重要的事**。

**這使 `0.1.0-W3-167` 的處置範圍必須收窄。** 在提示層做排隊、優先級或載體分化，是幫一個排程問題做視覺化緩衝——症狀被吸收，成因原封不動，而且緩衝做得越好，成因越不可能被發現。167 處理「留下來的提示怎麼呈現」，本票處理「為什麼會有這麼多同時發生的重要事件」。

**本專案已有具體實例。** 破洞掃描掛在 `GapReportNotifier.build()`，首讀者是 App 啟動時的 `ScanNotificationController.start()`（`0.1.0-W3-122` 的主題）——使用者尚未看過破洞報告頁，掃描就已在背景完成並試圖請求通知授權。這正是「背景行為在前台注意力尚未就緒時請求使用者關注」，而現行 SPEC-003 §2.2 的觸發條件只判斷「可見頁是不是 gaps」，不判斷「現在是不是請求使用者注意的適當時機」。

編輯能力（`0.1.0-W3-073`）落地後前台互動會大幅增加，此時若背景仍有掃描、載入、git 操作各自獨立觸發，注意力競爭會從偶發變成常態。**現在定義比事後補容易。**
- 0.1.0-W3-204 why: `0.1.0-W3-184` 定義了級別與規則，但**沒有指定本專案的每一種提示走哪個級別、哪個載體**。規格層不指定，實作只能各自判斷，而各自判斷的結果不會一致——這是 `0.1.0-W3-168` 為元件契約解決過的同型問題。

**已知須被規格涵蓋的一項現況違規**：`AppSnackBar.show` 無條件 `hideCurrentSnackBar()`，使 L3 完成通知可截斷正在顯示的 L2 失敗訊息（違反截斷規則第三條）。修法屬實作，但**「哪個級別可截斷哪個級別」必須先是規格**，否則實作票沒有可依循的判準。

**不寫則後果**：`0.1.0-W3-184` 的規則停在方法論層，本專案無任何可驗收的落點——規則存在但沒有任何測試會因違反它而變紅。
