## Problem Analysis

### 追加成因：push 的兩步不是原子的

原始症狀（push 後方向報告仍回報推送前狀態）在本票建立時歸因為遠端 manifest 的讀取快取。同日稍晚出現第二個成因，兩者症狀相同但性質不同：

`push` 先寫 skill 內容並提交，再更新 `versions.json` 並提交。這兩步之間若失敗（實測為本機磁碟寫滿，`OSError: [Errno 28]` 落在寫 `versions.json` 那行），內容已落地而 manifest 停在舊 hash，遠端進入內容與 manifest 不一致的狀態。

此時的錯誤方向不是暫時的：無名稱 `pull` 讀 manifest 得到舊 hash，與本地實際內容比對後判為分歧，方向指向錯誤的一側，且不會隨時間自行恢復。實測手動修正 `versions.json` 的 hash 後，該 skill 立即從分歧清單消失。

修法評估時兩個成因要一起看——只處理快取不涵蓋這一種，只處理原子性不涵蓋另一種。原子性這一側的可行方向：把內容與 manifest 併為單一 commit，或在 push 結尾復驗 manifest 與內容一致、不一致時明確報錯而非靜默留下不一致狀態。

### 根因已查明（W3-025 實測，2026-09-07）

本票原記徵狀與繞道方式（重新 clone 遠端逐檔 diff），未記機制。W3-025 執行六支
skill 的 push 時再次命中並定位到成因：

**`fetch_remote_manifest` 讀 `raw.githubusercontent.com`，該端點回應帶
`cache-control: max-age=300`。** push 後 5 分鐘內重跑分歧報告，遠端側讀到的是
push 前的快照。

**本次實測的形態**：五支 push 全部成功（遠端 `versions.json` 已含新 hash、commit
也在），緊接著重跑兩次分歧報告，該五支仍以舊遠端 hash 被歸類為 `SHOULD PULL`。

**這個訊號為何難擋**：報告分類明確、零警告，且**最早 push 的那一支因落在上一份快取
快照內而顯示正確**——部分正確的輸出看起來像整體正確。使用者若逐支核對前幾筆並發現
無誤，會更相信後面幾筆。

**修法方向（W3-025 SR-4 的建議，經 PM 併入本票）**：判定是否已同步應改讀 repo 的
`versions.json`（`git clone` 或 GitHub API，兩者皆不走該 CDN 快取），或等快取過期；
最低限度是在 push 成功訊息或 SKILL.md 加一行說明此 5 分鐘窗口。

**與本票原範圍的關係**：同一缺陷，本則補的是機制與可行修法，不改變本票的標的。
