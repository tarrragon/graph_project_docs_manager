### 二、SPEC-004 回饋契約子節與程式碼一致性

### 2.1 系統性結論（一致）

SPEC-004 §4 的回饋契約（已由 W3-060.2-060.5 填寫完成、42 條目全數落成）：
- **press-ack 列**：所有可互動元件均寫「Material 內建 ripple」或「Material 內建」，與程式碼一致（均使用 InkWell / TextButton）。掛載點為互動事件本身，不掛在服務回應路徑上。
- **等待與結果列**：均寫「本元件承載三層中的點擊確認層（pressed 態）；等待指示為畫面級 / 結果通知為狀態轉換本身」，正確地將服務相關回饋委派給呼叫端/畫面。
- **state-change 列**：均寫「觸發者：呼叫端（§2 過渡提示觸發點）」，確認狀態變更回饋由持有新舊值的呼叫端觸發，與程式碼一致。

**未發現規格對實作錯、實作對規格未寫、或兩者皆未涵蓋的不一致。**

### 2.2 W3-098 新增條款的影響

W3-098 已完成，在方法論〈回饋契約〉節新增了三項條款：
1. 掛載點條款：press-ack 與等待指示的掛載點須獨立於服務回應
2. 失敗路徑覆蓋：成功/失敗/逾時/服務不可用列在同一張表
3. 降級不解除回饋義務

對 SPEC-004 §4 既有 42 條目的影響：
- 條款 1（掛載點）：既有契約已隱式滿足——press-ack 均寫「Material 內建」即掛在互動事件上。但格式上未含顯式「掛載點」欄位（W3-098 新增的欄位格式），此為格式差異而非語意差異。
- 條款 2（失敗路徑）：既有「等待與結果」列的描述聚焦在成功路徑（「結果通知為狀態轉換本身」），未明列失敗、逾時、服務不可用時的行為。0.1 為唯讀展示殼，多數互動不涉及可失敗的服務（本地狀態操作），但以下 callback 背後的呼叫端邏輯涉及可失敗操作：`load_prompt.onStart`（載入）、`loading_state.onCancel`（取消）、`missing_source_state.onRefresh`（檔案檢查）、`recent_project_item.onTap`（專案切換觸發掃描）。這些元件自身的 press-ack 不受影響（A 類判定不變），但呼叫端的接線是否在失敗路徑仍提供回饋，屬頁面/畫面層的責任，超出本票（元件層盤點）的範圍。
- 條款 3（降級不解除義務）：同理屬呼叫端層面。

### Rationale Chain
- 0.1.0-W3-078 why: W3-064 acceptance 2、3 承接，平台事實只有實機能驗
- 0.1.0-W3-098 why: 實機驗證時使用者按下重新掃描按鈕，**畫面完全沒有反應**——沒有按下的視覺、沒有等待指示、沒有失敗訊息。背後同時有三件事失敗（平台 handler 未註冊、完成邏輯落在同一 microtask 使骨架不可見、例外被降級收斂為某個狀態值），但使用者側的觀察只有一件事：按了沒反應。

用戶據此下的裁示（2026-09-08）：**提示效果應該掛在互動元件上，跟背後服務能不能運作不相關。**

現行〈回饋契約〉節的六類事件表定義了觸發者與回答範圍，但**沒有規定回饋的掛載點**。實作者自然會把回饋寫在服務回應的處理路徑上——那是「有東西可以顯示」的地方——於是產生一條反向相關：服務正常時回饋齊全，服務不可用時回饋為零。使用者最需要知道發生什麼事的那一刻，系統最沉默。

第二個缺口：六類事件表只列了事件，**沒有要求回答涵蓋失敗路徑**。「等待與結果」列指向三層回饋模型，而該模型的「結果通知」在實務上被讀成成功結果。失敗、逾時、服務不可用不在同一張表上，因此沒有人為它們填欄位。

第三個缺口：**降級與靜默沒有被區分**。把例外收斂為已知狀態值是行為確定性的手段，但收斂後的狀態若無可見表現（或其表現另有前提條件而前提不成立），收斂等於銷毀證據。現行條文沒有要求指出降級目標狀態的可見表現。

完整分析見 `ARCH-GPD-001`（互動回饋掛在服務的成功路徑上，服務越不可用回饋越少）。
