#### 一、可直接沿用的判準（各附「為何這樣定」，理由比結論重要）

| 判準 | 為何這樣定 |
|------|-----------|
| **事件三分，鍵是「到達時機由誰決定」**：使用者觸發／我方自行發起／外部驅動 | 只有這個鍵能決定**可否排程**，而可否排程決定了能用哪些手段。**實作是否非同步與此無關**——一個在我方選定時刻發出的 `await` 屬第二類，一個被推進來的同步回呼屬第三類。這是最容易誤判的一處 |
| **級別的鍵是「接收方必須做什麼」，不是產生方的技術嚴重度** | 稀缺資源屬於接收方。以產生方視角分級會讓「很嚴重但接收方無事可做」的事件搶到高優先序 |
| **競爭 = 未被消費的請求**，不是「同一時刻」也不是到達率 | 本專案的實際案例**不需要兩件事同時發生**——只需一則正在顯示時另一則抵達。後端對應：**依佔用量卸載，不依到達率** |
| **三條截斷規則**：高可截低、同級不互截（排隊或合併）、低不得截任何 | 第三條是實際被違反的那一條。本專案的提示元件無條件覆蓋前一則，使低級別訊息殺得掉高級別 |
| **協調圖不是依賴圖** | 互不呼叫的兩個 domain 仍會搶同一個通道；依賴圖上查起來是「無關係」，**看起來像已確認過** |
| **單一仲裁點，不做分散式協商** | N 條邊取代 N²，且元件之間維持互不知情。互相確認會迫使每個元件知道其他元件存在 |

#### 二、明確不足之處（本專案沒有、後端需要）

| 缺口 | 為何本專案沒有 |
|------|--------------|
| **backpressure** | UI 推不回給使用者；後端必須推得回去 |
| **資源成本異質** | 上述判準假設每個請求成本相同，只分級不分量 |
| **deadline / timeout 傳播** | 「延後至當前請求被消費」沒有上界 |
| **部分降級** | 注意力不可分割（只有一則能被看見），CPU 可以切分。「只有 first 被呈現」沒有後端對應 |
| **跨執行緒的狀態一致性** | 本專案單線程，isolate 未使用 |
| **可觀測性只到元件層日誌** | 後端需要佔用量、卸載計數、分級延遲、以及**被丟棄請求的可追溯性** |

#### 三、本專案的現地約束（避免設計出用不上的東西）

- Flutter macOS 桌面 App，**單機、無伺服器**；`0.1` 目標平台僅 macOS
- App Sandbox **關閉**（需執行專案內 doc CLI）
- 8 個 domain，依賴單向向下，完整依賴邊 8 條（`docs/domain-map.md` §2）
- **目前無 websocket 與輪詢**，外部驅動為空類別；且 `SPEC-003` 明文裁定「目錄消失屬外部變更，由下一次重新載入承接，本畫面不設偵測點」——本專案是刻意不設外部變更監看的
- **structured log 在 `0.1` 維持延後**（`docs/tech-decisions.md` 有裁定與重評條件）。可觀測性方案若以 structured log 為前提，須知道本專案目前不具備該基礎

#### 四、今日實測的三個坑（與可觀測性設計直接相關）

1. **測試綠燈驗到的是「程式做了對的事」，不是「使用者收到了對的資訊」。** 本專案曾出現診斷測試通過、實機上卻無任何紀錄能回答使用者看到什麼的情形——日誌上與靜默失敗完全同形。結論是回饋的最末端載體本身必須自帶日誌，那是資訊鏈唯一可留存的證據。**後端對應**：請求被卸載時，若只有服務端指標而無該請求的可追溯記錄，卸載與靜默失敗同形。

2. **恆真警告等於沒有警告，且比沒有偵測更糟。** 本專案有兩個實例——一個檢查器每個 session 報 81 組未收斂項、一個對已完成任務仍報「檔案使用中」。**輸出恆非空且增量不可見時，資訊量趨近零**，而背景雜訊會讓真正的新事件更難被看見。解法是把當前狀態凍結為 baseline、只報增量。**這對高負載監控直接適用**：一個在高負載時必然亮起的告警，在高負載時沒有資訊量。

3. **正確的結論配上錯誤的理由，當下完全無症狀。** 本專案今日兩度發生：結論成立、驗證通過、但支撐它的機制解釋是錯的；失效發生在有人依那個理由推導下一步時。**對設計文件的要求**：判準要寫出「它回答的是什麼問題」，不只寫結論。

#### 五、我認為值得優先回答的四個問題

1. **卸載的判準是佔用量還是到達率？** 上述「競爭 = 未被消費的請求」指向佔用量，但那是單通道場景的推論，多核心下未必成立。
2. **被卸載的請求如何留痕？** 沒有留痕則卸載與靜默失敗同形（見坑 1）；全部留痕則高負載時留痕本身成為負載。
3. **級別是靜態標註還是動態推導？** 本專案是靜態（每則提示在規格層指定級別）。後端的同一個 API 在不同情境下重要性可能不同。
4. **仲裁點自身的過載怎麼辦？** 單一仲裁點是本專案的結論，但它在後端會成為單點。
