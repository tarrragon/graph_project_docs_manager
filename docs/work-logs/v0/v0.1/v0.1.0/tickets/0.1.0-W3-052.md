## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`dispatch-identity-bind-hook.py`（PostToolUse:Agent）在派發成功後將
`who.current` 由「無主態」（`pending` / `待派發` / `?` / 空字串）改綁為
實際派發的 subagent_type，但 `UNBOUND_WHO_VALUES` 未把 PM 身份字面值
（`rosemary-project-manager`）視為可覆蓋——PM 依 pm-role 流程先 `claim`
再派發時，`who.current` 若寫成 PM 名稱（例如 `claim --as
rosemary-project-manager`），此狀態不被視為「無主」，派發時不會重新
綁定給實際執行者。此為根因：不是 identity-guard 或 `--as` 必填規則本身
有誤（兩者各自正確），而是「PM 暫代管」與「已指派給 PM 本人執行」兩種
語意在 `UNBOUND_WHO_VALUES` 判準上被誤判為同一種狀態。

### 影響範圍

- `.claude/hooks/dispatch-identity-bind-hook.py`（源頭修復：擴大可覆蓋範圍）
- `.claude/skills/ticket/ticket_system/commands/lifecycle.py`（新增
  `reassign_who_from_pm_if_takeover`：complete/finish 前置保底，涵蓋
  worktree 隔離派發等 hook 未觸發的場景）
- `.claude/skills/ticket/ticket_system/commands/track.py`（`_execute_complete`
  接線：在 identity 對照前呼叫上述保底函式）
- `.claude/skills/ticket/ticket_system/lib/identity_guard.py`（情境 4 deny
  訊息補上具體出口指令，對稱於情境 1a 既有的補救提示）
- `.claude/skills/ticket/SKILL.md`（新增「PM 先 claim 再派發時的身份死結
  （已修復）」小節，依 skill-cli-sync-check 規則同步）

### 相關 Error Pattern

PC-V1-002（identity-guard 的原始威脅模型與防護鏈）——本次修復不改變其
核心防護（代理人之間的誤指派仍全數 deny），僅針對「PM 暫代管」這一種
被誤判為「已指派」的狀態擴大可覆蓋範圍。

### 本 session 新增事實（票面建立後發生，供後續讀者判斷是否落在同一形態）

1. **本 session 後續又有三個代理人撞上同一狀態**（另一批被派發者，非
   Problem Analysis 中列的原三例）：全數改由 PM 以
   `--as rosemary-project-manager` 代跑 `complete`。累計六次，非偶發。
2. **繞過方式已知可行但不採用**：`ticket track set-who --current <agent>`
   能解，曾有一個代理人自行用過。但那是改權責歸屬欄位，不該由執行者
   自行決定——本次修法給的是不需要碰 `who` 的出口（見上方兩道防線），
   不是把 `set-who` 變成正式的自助繞過路徑。
3. **對照組（同一 session 內）**：`bare-commit-guard-hook.py` 兩次擋下
   裸 commit，每次都印出完整的拆分指令（`git restore --staged` +
   分批 add/commit），被擋的成本只是多跑幾次命令。同樣是擋，差別在
   有沒有給出口——本次識別到的兩道防線與情境 4 deny 訊息的具體指令化，
   即是把本問題對齊到同一形狀。
