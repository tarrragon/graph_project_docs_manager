## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

實測復現（uv run --directory .claude/skills/doc python3 -c ...）確認：
`find_uc_tokens_in_text("...action-ucFlow-select-uc-UC-01...")` 只回傳一個
token `('uc-UC', 1)`，normalize 後為 `UC-UC`；真正的 `UC-01` 完全未被獨立
偵測到（不是「被誤判為違規」，而是被前一個假匹配的 value 群組吞掉，
regex 引擎的搜尋游標已越過它）。

根因在 `UC_TOKEN_RE`（`.claude/skills/doc/doc_system/core/uc_registry.py`
:45-48）：value 群組 `[A-Za-z0-9...]+` 是貪婪字元類，遇到
`select-uc-UC-01` 時，先在 `-uc-` 處（`-` 為 word boundary）比對到
prefix+hyphen，接著 value 群組貪婪吃進緊接的 `UC`（因為 `U`/`C` 也落在
`[A-Za-z0-9...]` 範圍內），直到遇到下一個 `-` 才停止，產出偽匹配
`uc-UC`。搜尋游標推進到此匹配結束處（`UC` 之後），使真正的 `UC-01`
永遠不會被當作獨立 token 掃到。

### 影響範圍與範疇修正

Ticket where.files 僅列 `.claude/hooks/uc-reference-validation-hook.py`，
但該檔本身不含 UC token regex，只是呼叫
`doc_system.core.uc_registry.find_uc_tokens_in_text()`（模組 docstring
明載「本模組是該規則的唯一實作（單一來源），PreToolUse 寫入驗證 hook
須複用本模組，避免各自實作導致規則漂移」）。regex 實體
（`UC_TOKEN_RE`）定義於 `.claude/skills/doc/doc_system/core/uc_registry.py`
，該模組同時被 `doc uc verify/trace/context` CLI 共用。

故實際修改對象調整為 `uc_registry.py`（+ 其既有測試
`.claude/skills/doc/tests/test_uc_registry.py`），而非 hook 檔本身；
hook 檔不需改動（它只是消費端）。此為 ticket 認領檢查清單「已獨立
驗證 Ticket 描述的數量/範圍」項下的修正，範疇仍是同一顆 bug、同一個
acceptance，僅落點檔案更正為正確的單一實作來源，不算越界。

### 相關 Error Pattern

未查得直接對應既有 error-pattern；本案屬 regex 貪婪匹配吞併相鄰合法
token 的典型案例，暫不另建 error-pattern（單一模組內的區域性 bug，非
跨專案可重現的結構性錯誤）。
