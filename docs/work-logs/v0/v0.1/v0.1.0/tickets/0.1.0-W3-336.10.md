若要對「其他跨版本共用契約檔案」寫檢驗問句（設計產出物形態，依 chained-examples.md〈各段允許
與禁止內容〉判定），該問句必須能指回條文中一句界定「契約檔案」範圍的定義句。

逐一查證結果（`grep -rn "契約檔案\|契約 SOT\|SOT 檔案\|契約級" .claude/skills/version-bootstrap/
.claude/skills/foundation-design/`）：

- `version-shift-sop.md` 第 15 行：僅列舉兩個具名項（`schema/*.schema.json`、DDL 章節）與一個
  開放第三類「其他跨版本共用契約檔案」，未界定第三類的邊界。
- 第 9 行（動機段）：「契約 SOT 檔案（如 schema 定義）」——僅舉例，非定義句。
- 第 24-29 行（判斷準則表）：分級對象是「已被步驟 1 判定觸及」的項目，處理的是「觸及項算不算硬
  耦合」，不是「什麼算契約檔案」，無法回頭充當步驟 1 的邊界定義。
- 專案內唯一另一處「契約」相關模板 `.claude/skills/doc/templates/data-contract-template.md`
  定義的是「資料契約文件」這個 SPEC 文件類型本身（A/B 兩區結構），與本處「契約檔案＝觸及即需
  盤點的物件」是不同概念，不能借用。
- SKILL.md 第 92 行僅重複「schema／DDL／契約級的殘留耦合」，同樣未界定第三類開放項邊界。

**結論**：條文中「其他跨版本共用契約檔案」查無任何定義句可作為檢驗問句依據，依
〈「缺範例」與「缺引導」的分界〉判定順序（先問「這個決策點有沒有文字約束存在」）——本處雖有

  變更會影響雙方消費邏輯的資料定義檔案，範圍限資料層（如 ORM model 定義、遷移腳本引用的

  草稿 B（寬範圍，含介面層）：
  「其他跨版本共用契約檔案，指任兩個以上模組或版本依賴其定義的欄位、路徑或 key 集合作為
  讀寫依據的檔案，改變其集合會破壞既有消費方，範圍包含資料定義檔、API 路由表、i18n key
  清單；是否列入以本專案當下是否已有該類消費方為準——若本專案尚無 API 層或未把 i18n key
  集合當作跨模組契約，該類檔案不屬本步驟盤點範圍（現況：本專案為 macOS 桌面應用，多語系採
  Flutter 官方 ARB，尚無 API 層，若採此草稿現階段等同窄範圍）。

  兩草稿差異僅在「是否把非資料結構的介面清單（API 路由表、i18n key）預先納入範圍」；草稿 B
  多一句「以本專案當下是否已有該類消費方為準」的判準，避免未來若新增 API 層時需再次修文。
