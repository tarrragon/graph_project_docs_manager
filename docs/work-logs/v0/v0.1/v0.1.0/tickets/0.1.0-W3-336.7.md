### C04：錯誤訊息 i18n 呼叫層級（需裁決）

**矛盾位置**：`references/i18n-guidelines.md`〈Violation 2: Hardcoded Error Messages〉vs `SKILL.md`〈Violation 6: ViewModel Hardcoded User Messages〉

**兩方原文**：
- i18n-guidelines.md Violation 2 Fix：
  ```dart
  throw Exception(context.l10n!.genericError);
  showError(context.l10n!.loadError);
  ```
  在拋出例外處直接呼叫 `context.l10n!`，未區分該處是否持有 `BuildContext`。
- SKILL.md Violation 6 Fix（Scope 為 `lib/presentation/**/viewmodel.dart` 等 ViewModel 層）：
  ```dart
  state = state.copyWith(errorMessage: context.l10n!.invalidFileFormat);
  state = state.copyWith(errorMessage: ErrorHandler.getUserMessage(exception));
  ```
  同時並列 `context.l10n!` 直接呼叫與 `ErrorHandler.getUserMessage` 兩種寫法作為對等 Fix，未說明何時該用哪一種。

**建議以哪方為準**：thyme 不片面選邊，提出兩個候選方向供裁決：
- 方向 A（翻譯移到呈現層）：ViewModel／非 widget 層一律不得使用 `context.l10n!`（通常不持有 BuildContext），改丟未翻譯的錯誤碼／enum，由呈現層以 `ErrorHandler.getUserMessage` 對應成 l10n 訊息。i18n-guidelines.md Violation 2 的 Fix 需同步改為錯誤碼＋ErrorHandler 形式。
- 方向 B（維持直接呼叫）：專案若已有其他機制讓非 widget 層取得可用的 localization（例如透過 DI 注入的 localization service，而非 BuildContext），則兩處可以統一為直接呼叫寫法；SKILL.md Violation 6 的 `ErrorHandler.getUserMessage` 選項應移除或降級為次要案例並註明適用時機。

**理由**：i18n-guidelines.md 的寫法把 `context.l10n!` 直接放進 `throw Exception(...)`，隱含拋出處持有 BuildContext；這在常見 Flutter 分層（ViewModel／UseCase／Repository 不持有 widget context）下不成立。但本專案是否已有其他方式讓非 widget 層合法取得 l10n（例如注入的 localization 服務），thyme 未讀到本專案實際的錯誤處理層架構決定，無法片面判定何者為現況、何者需修正。

**是否屬用戶程式碼風格偏好**：是——「錯誤訊息該在哪一層翻譯、用哪種呼叫寫法」屬母票裁示明文列出的「i18n 呼叫形式」個人取捨範圍。

**改後文字草稿**：待方向確定後才能寫定。
- 若選 A：i18n-guidelines.md Violation 2 Fix 改為丟錯誤碼／enum，範例 `throw AppException(AppErrorCode.generic);`、`showError(ErrorHandler.getUserMessage(AppErrorCode.loadFailed));`（實際型別／API 名稱依本專案既有 ErrorHandler 慣例定，此處僅示意）。
- 若選 B：SKILL.md Violation 6 Fix 拿掉 `ErrorHandler.getUserMessage` 該行，只留 `context.l10n!` 寫法；i18n-guidelines.md Violation 2 補一句「僅限持有 BuildContext（或等價 localization 存取）的層級適用」。

### C07：垂直間距命名慣例（需裁決）

**矛盾位置**：`references/spacing-system.md`〈UISpacing Constants〉vs 同檔〈SizedBox Usage〉/〈EdgeInsets Usage〉/〈Common Patterns〉vs `SKILL.md`〈SizedBox Spacing〉

**兩方原文**（實際為三種寫法並存，非僅兩種）：
1. spacing-system.md〈UISpacing Constants〉：定義兩組獨立命名——水平不加字首＋`.w`（`UISpacing.xs // 8.w`、`UISpacing.md // 16.w` 等），垂直另立 `vertical` 字首常數＋`.h`（`UISpacing.verticalXs // 4.h`、`UISpacing.verticalMd // 16.h` 等）。
2. spacing-system.md〈SizedBox Usage〉〈EdgeInsets Usage〉〈Common Patterns〉：範例一律用「不加字首、不加尾綴」的 `UISpacing.xs/sm/md/lg` 同時涵蓋 width 與 height（例：`SizedBox(height: UISpacing.md)`、`SizedBox(width: UISpacing.xs)`），既非 `verticalXx`，也未見 `.h`/`.w` 尾綴。
3. SKILL.md〈SizedBox Spacing〉：表格對 `SizedBox(height: ...)` 一律標「Responsive: `.h` suffix」，暗示寫法應為 `UISpacing.xxs.h`（僅表格文字註記，範例程式碼未寫出尾綴）。

三種寫法互斥：同一個「16dp 垂直間距」在三處分別寫成 `UISpacing.verticalMd`、`UISpacing.md`、`UISpacing.md.h`；且 `verticalSm`（8）與 `xs`（8）兩組常數值重疊，讀者無法判斷類別實際成員為何。

**建議以哪方為準**：thyme 已 grep 專案 `lib/` 與全 repo，確認**本專案目前沒有任何 `UISpacing` 類別實作**（`grep -rn "class UISpacing"` 零命中），且 `.claude/config/dart-style-guardian.json` 記載的實際 token 類別名是 `AppSpacing`（非 `UISpacing`，此為另一已知獨立缺口 G25，不在本票範圍）。故沒有既成程式碼可供 thyme 逕行核對「哪一組寫法才是實際 API」，三個候選方向供裁決：
- 方向 A：採〈UISpacing Constants〉雙命名組（水平不加字首＋`.w`、垂直 `verticalXx`＋`.h`）；修正〈SizedBox Usage〉〈EdgeInsets Usage〉〈Common Patterns〉範例與 SKILL.md 表格全部改用此組。
- 方向 B：採〈SizedBox Usage〉單一命名組（`UISpacing.xs/sm/md/lg` 不加字首不加尾綴，getter 內部依用途已回傳縮放後的值）；修正〈UISpacing Constants〉節與 SKILL.md 表格改為此組，刪除 `verticalXx` 與外部尾綴寫法。
- 方向 C：採 SKILL.md 的「基礎常數＋外部尾綴」組（`UISpacing.xs.h` / `UISpacing.xs.w`）；修正兩份 reference 檔改為此組，刪除 `verticalXx` 常數與「getter 已內建尾綴」的說明。

**理由**：三組寫法看不出何者為既定慣例；本專案尚未實作對應類別，無法以程式碼反查。若後續地基波實際建立間距 token 類別時已定案某一種寫法，應直接以該實作回頭校正三份文件，不需要走風格裁決；若屆時仍未定案，才需要使用者對「間距常數命名慣例」表態。

**是否屬用戶程式碼風格偏好**：是（條件性）——目前無實作可查證，屬命名慣例的個人取捨，交用戶或留待地基波建立 `AppSpacing` 實作時一併定案；若定案時發現已有既存實作，則改判為「文件與程式碼不符」的字面不一致，屆時可由後續票逕行依實作修正，不需裁決。

**改後文字草稿**：待方向或實作確認後才能寫定。
