## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 前置實查（2026-09-09）：本專案已有一個現成的量測點，母體下界遠大於預期

`tarrragon/claude#104` 正文說「母體尚未盤點」，故第一步是盤點不是實作。**本專案有一個已經在跑的檢查器可直接給出母體的一個下界**，不需另做盤點工具。

`.claude/hooks/error-patterns-index-consistency-check-hook.py`（SessionStart 觸發）除索引一致性外，還檢查 error-pattern 之間的**雙向回指**——A 引用 B 時 B 是否回指 A。實跑輸出節錄：

```
  ARCH-BAL-005 -> ARCH-BAL-003（... 未被 ARCH-BAL-003 回指）
  ARCH-BAL-006 -> ARCH-BAL-002（... 未被 ARCH-BAL-002 回指）
  ARCH-BAL-007 -> ARCH-BAL-006（... 未被 ARCH-BAL-006 回指）
  ...另有 71 組未列出
```

**單一目錄內即有 81 組以上的單向引用。** 三項後果：

#### 一、「不做」這個結論變得難以成立，但這個數字可能是高估

issue 正文寫「母體若只有個位數且集中在少數目錄，維護 registry 的成本可能高於漂移的成本」。81 組以上顯然超出該門檻。

**但取用前須先判定定義是否涵蓋**：這 81 組是同類型文件之間的引用，與正文描述的「兩份互相引用且需同步的文件對」不完全同義——error-pattern 之間的引用是知識關聯，未必每一則都構成「一側改了另一側必須跟著改」的同步義務。**母體盤點的第一步是先定義什麼算一對**，否則這個數字會被當成母體規模直接用。

#### 二、偵測手段的先例比 issue 正文所列的更近

正文以「程式碼 → 文件單向」的 CLI 同步檢查為先例，並指出方向不同。**本專案這個 hook 是文件 ↔ 文件、雙向、且已實作**——既不需 registry 也不需 marker，配對來源是**文件內文的引用本身**（掃描引用關係，反查對側是否回指）。

這是正文三個選項（registry ／ marker ／不做）之外的**第四種手段**。成立條件是引用關係可由內文機械辨識（此處是 ID 格式固定），不適用於以自然語言指涉對方的引用。

#### 三、它同時是反例：偵測存在不等於漂移被修

該 hook 每個 session 都在報，81 組以上長期未收斂。若 issue 的結論只到「加一個偵測」，很可能複製出同一個結果：**每次都報、每次都被略過的警告**。

選手段時應一併決定**未收斂項的處置路徑**（阻擋、建票、或明文接受為已知狀態並記錄基準），否則偵測產出的只是背景雜訊——**而背景雜訊會讓真正的新漂移更難被看見，比沒有偵測更糟**。

#### 四、一組乾淨的正例，可作為「什麼算一對」的定義起點（另一 session 於同日補入）

第一點指出 81 這個數字可能高估，因為 error-pattern 之間的引用是知識關聯、未必構成同步義務，故**母體盤點的第一步是先定義什麼算一對**。以下這組符合最嚴格的定義，可作該定義的正例：

| 面向 | 內容 |
|------|------|
| 兩側 | `docs/spec/ui/SPEC-003-interaction-response.md` §2.12 的 `INV-FEEDBACK-001` 節 ↔ 元件庫雙向約束方法論〈元件層回饋日誌（觀測對偶）〉節 |
| 關係 | 方法論為定義正本（節內明寫）；SPEC-003 為**逐字引文**並標明歸屬 |
| 同步義務 | 明確——正本改了引文就是錯的，不是「關聯性變弱」 |
| 比對成本 | 機械可判定，不需語意判斷——但**需要雙方都明示引文邊界**，見下方更正 |
| 目前的漂移訊號 | 無 |

來源：`0.1.0-W3-175` 把該不變式定義升格進方法論，`0.1.0-W3-173` 將 SPEC-003 降為實例化並保留附歸屬的引文（使讀者不必跳檔）。兩處於本補充寫入當下經實測逐字一致。

**它對本票的用處有兩層**：一是給「一對」一個無爭議的正例，讓 81 組可以逐一對照篩選，而非整批當母體或整批棄用；二是它把偵測成本壓到下界——**若連字串相等比對都判定不值得，結論不能再援引成本，須另行說明理由**。反過來若結論為實作，這組是成本最低的首個覆蓋對象。

**不預設結論**。接手者請依 PC-162 獨立重驗兩處是否仍逐字一致——本補充寫入當下一致，而那正是本票要處理的性質。

##### 更正（同日稍後）：比對成本不是「字串相等」，是「字串相等 + 明示的引文邊界」

上表原寫比對成本為「字串相等」，依據是 PM 以 `grep -o "<該句>"` 在兩個檔案各抓一次、結果相同。**該測試的邊界就是 pattern 自身**——同一個 pattern 在兩邊各切一段，切出來必然相等，因此它證明不了兩處文字相同。

實測兩處的完整字串在邊界處不同：

| 位置 | 實際文字形態 |
|------|------------|
| 方法論 | 粗體包夾、**無句尾句號**、由前後 em-dash 界定 |
| SPEC-003 | 無粗體、**有句尾句號**、由「定義見方法論〈…〉節：」引入 |

核心敘述本身逐字相同，差異只在強調標記與句尾標點。但這使**天真的位元組相等比對會立即回報不一致**，而那是誤報。

**這對本票的意義比原本的宣稱更具體**：最低成本的偵測仍需要一件目前不存在的基礎設施——**兩側都能被機械辨識的引文起訖邊界**。沒有它，實作者只剩兩條路：把該句硬編進檢查程式（正本一改，檢查程式也得改，等於多一處要同步），或做模糊比對（把「什麼程度的差異算漂移」變回語意判斷，本組相對其他 81 組的成本優勢即消失）。

因此若本票結論為實作，**第一個要決定的不是比對演算法，是引文邊界的標記形式**（HTML 註解、特定 markdown 慣例、或其他），且該形式須能套用到其他候選對。此問題與母體大小無關，母體為 1 時同樣存在。

**PM 註**：本更正本身即本票所處理現象的一個實例——一段引文（原表格）與其依據（一次量測）不一致，且沒有任何機制會指出來，是靠另一個執行者在別的工作中順帶發現的。
