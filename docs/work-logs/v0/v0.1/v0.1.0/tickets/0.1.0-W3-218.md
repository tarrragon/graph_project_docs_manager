### 範例材料：三場景套用（取自方法論定稿前的高負載工程視角審查，2026-09-09）

以下為審查者以方法論**初稿**套用三個場景的結果。「卡住的判準」多數已在定稿修入方法論（見各條括號），worked-examples 應改寫為「套用結果／當時卡住處／方法論現行對應判準」三段，去除審查語氣，且以定稿的類別名（等待型／自發型／推送型）與級別名（不可棄／須留痕／可棄）重述。

#### (a) HTTP API 共用 DB 連線池，另有 cron 對帳與 webhook 消費

能套用：連線池是通道、持有層是資料存取基礎層，仲裁器掛在取用連線之前。到達類別三者分別落等待型／自發型／（webhook 送達跳等待型、確認後處理自發型）。佔用量以「已借出連線數＋等待者數＋最老等待者年齡」實例化，進入／離開閾值分開。全表掃描與主鍵查詢成本跨數量級，觸發依成本分池。

當時卡住處與現行對應：
1. webhook 送方等待 ack 並在非 2xx 時重送，初稿歸第三類會放棄回 503 這個推回手段 →〈到達類別〉逐跳分類：送達跳等待型、確認後處理自發型。
2. cron 對帳屬窗口驅動，初稿「逾期跳過不補跑」會遺漏當日窗口 →〈Deadline 傳播〉自發型分狀態驅動（跳過）與窗口驅動（留痕併入下一窗口）。
3. HTTP、cron、webhook 各為獨立行程各持一池時，真持有者是 DB；分片等於靜態配額，cron 閒置時配額不流回 HTTP →〈通道與仲裁器〉分片前提為真持有者、靜態配額為代價。
4. handler 在交易中巢狀取第二條連線：已持有一條、正在等另一條，三參數模型計為 in-flight，是連線池死鎖路徑 →〈通道與仲裁器〉一次申請、禁止持有並等待。

#### (b) Flutter 桌面 App：worker isolate 解析大檔，主 isolate 處理操作與提示

能套用：三個通道（主 isolate 事件迴圈、worker isolate、提示載體）各一仲裁器；worker 回傳結果與主 isolate 派工在接收方依「有無人等回覆」分類（request/reply 為等待型、fire-and-forget 為推送型）。解析進度提示（自發型、可棄）與使用者觸發的對話框（等待型、不可棄）以三條讓步規則裁決。

當時卡住處與現行對應：
1. 主 isolate 事件迴圈的佇列深度不可讀，只有 frame 逾時與迴圈 lag →〈競爭與佔用量〉以最老年齡的代理量作輸入並標明是三項中的第三項。
2. isolate 內計算無法被外部中斷，只有 kill 或協作式檢查點；kill 等於重算 →〈讓步與卸載順序〉CPU 搶佔以可中斷點為實例化條件。
3. 記憶體通道的消費是 GC 回收，不在三種消費形態內；跨 isolate 傳遞會複製、佔用量瞬間翻倍 → 未修入，另票承接（記憶體通道實例化條件）。worked-examples 須標明此為已知缺口。

#### (c) 訊息消費者：付款完成事件與心跳混流

能套用：拉取式消費在拉取決策屬自發型，拉進來的批次是接收緩衝；付款完成為不可棄落持久佇列，心跳為可棄可合併，合併三條件成立且保留計數。持久佇列即 broker、記憶體緩衝即 prefetch 視窗、不可棄的 ack 只在處理完成後發出。

當時卡住處與現行對應：
1. 同一 partition 的 FIFO 加 ack 上，級別搶佔在拉取批次之外不可能成立 →〈讓步與卸載順序〉有序通道上級別搶佔只在批次內成立，跨批次依級別分池。
2. 心跳是最新值語意事件，全丟會讓下游存活偵測誤報 → 九格表推送型×可棄改為先合併再丟棄、最新值語意保留最新一則加計數。
3. prefetch 視窗被不可棄事件填滿且下游 DB 慢時，消費者唯一手段是停止拉取 → 九格表推送型×不可棄「延後至接收視窗填滿即為容量失敗訊號」。

#### 其他可入範例的裁定

- 佔用量不依到達率在 CoDel 與 adaptive concurrency limit 下成立：CoDel 的 sojourn time 即最老年齡；adaptive limit 的准入仍比較 in-flight 數。成立條件：佔用量含最老年齡、閾值可由延遲訊號推導、服務時間可量測。
- 常數時間有界仲裁與分級延遲可同時成立：級別為固定小枚舉、每（類別×級別）一條 FIFO、deadline 出隊懶檢查、延遲用固定桶直方圖。
- 高負載除錯必問而初稿指標集漏掉的兩問：「通道有沒有在推進」（完成計數）、「誰把通道佔滿」（佔用量按類別×級別分解）。
