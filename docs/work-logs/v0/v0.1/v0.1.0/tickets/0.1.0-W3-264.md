why: '`section_comment.py` 的四個寫入命令（`init`／`add`／`update`／`observe`）都是 `Path(content_file).read_text(encoding="utf-8")` 之後直接送出，**沒有任何長度檢查**。內容為空時照樣 POST、照樣 `return 0`、照樣印出一則可解析的成功 URL。


  **已實際命中一次**：`0.1.0-W3-254` 執行 observe 時，heredoc 因 `2>&1` 位置錯誤而未接上 `/dev/stdin`，貼出一則只有工具首行標記的 138 字元空殼 comment，而命令回傳看起來完全正常。是事後以 `gh api --jq ''.body | length''` 回讀才發現，不是靠任何回報訊號。


  **`update` 這一支的後果不是貼一則空 comment，是清空一則既有區段**——它是 PATCH，空內容會把該區段原本的全部內容覆蓋掉，而回傳一樣是成功。區段是跨 consumer 的知識載體，被清空後除了 GitHub 的編輯歷史沒有本地副本。


  **為何 exit code 擋不住**：工具回報的每一項都是真的——POST 真的成功、comment 真的存在、URL 真的解得開。假的是那個沒被陳述的關係：「貼上去的內容等於操作者給的內容」。payload 走的是另一條通道（檔案／stdin），那條通道斷掉時斷點不會出現在 exit code 裡。這是 `PC-GPD-019`（形狀相符終止查證：觀測是真的、關係是假的）在寫入側的實例。


  **放大條件**：收束流程會派多個 curator 並行執行 `init`／`add`，每個 curator 自行判斷成敗。工具不拒絕空內容時，一個 curator 可以建出一整組空區段、通過自己的 `show`／`check` 驗收（索引一致、區段存在，只是沒有內容）、然後回報成功。


  **修法方向是工具而非文件**（`opinionated-default-design` 原則 1：預設行為勝過文件規範）。空內容不存在任何合法用途，四支一律拒絕即可，不需要旗標豁免。'
