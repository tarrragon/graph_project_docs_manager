### 問題根因

**回饋契約回答「怎麼告知使用者」，不回答「等待期間怎麼保護使用者和系統」。** 三個缺口：

1. **回饋形式無分類規則**：不同服務類型（立即完成 vs 數分鐘操作）的回饋形式不同，但規格沒有依服務類型的對照表。
2. **輸入阻擋無規則**：SPEC-003「阻擋」一詞只用於阻擋狀態元件（畫面狀態的一種），與「等待期間阻擋輸入」不是同一件事。
3. **重複觸發防護無歸屬**：`Motion.searchDebounce` 存在但未規定實作層級；按鈕類防抖無條文。

### 第一步：服務類型分類

### 分類軸

依「使用者感知的等待長度」與「失敗形態」兩軸切分。同步/非同步是實作細節（使用者感知不到），不作為分類軸。

### 四類服務類型

| 類型 | 使用者感知的等待 | 失敗形態 | 0.1 實例 |
|------|----------------|---------|---------|
| I. 本地即時 | 零（同一幀內完成） | 不可能失敗（純本地狀態操作） | 導覽切換、模式切換、樹展開收合、篩選選取、返回、Esc 收合 |
| II. 延遲觸發 | 使用者持續輸入中，停頓後才觸發；等待感知為「輸入→結果更新」的延遲 | 不可能失敗（本地過濾運算） | 搜尋輸入防抖後觸發過濾（`input-tickets-search`） |
| III. 短暫非同步 | 亞秒（使用者可能感知到短暫等待，但不需要進度指示） | 可能失敗（外部程序不存在、執行失敗、平台 API 拒絕） | 外部開啟（open file/dir）、系統通知發送/撤回、授權查詢/請求 |
| IV. 長時操作 | 秒至分鐘（使用者明確感知等待，需要進度指示與取消能力） | 可能失敗（解析錯誤、平台錯誤、資料損壞） | Domain 載入、Ticket 載入、破洞掃描 |

### 各類切分理由（「它的政策哪裡與別類不同」）

**I vs II**：類型 I 不經過任何服務呼叫（純本地狀態變更），三項政策全為「無」。類型 II 雖然結果也是本地運算，但有防抖延遲——使用者輸入與結果之間有一段可感知的等待（300ms），且需要防抖機制防止逐字元觸發，這兩點在類型 I 不存在。

**II vs III**：類型 II 的結果必然成功（本地過濾不可能失敗），無需結果回饋元件；類型 III 可能失敗（外部程序不存在、平台拒絕），需要 Layer 3 結果回饋（SnackBar）。類型 II 的防護是防抖（延遲觸發），類型 III 的防護是冪等（重複呼叫 open 同一檔案為合法操作）。

**III vs IV**：類型 III 等待時間亞秒（使用者不需要進度指示，點擊確認的 pressed 態即足夠），不阻擋輸入。類型 IV 等待秒至分鐘，需要 Layer 2 受理回饋（LoadingState 進度指示），需要阻擋頁面內容，且需要取消能力。

### 第二步：逐類型三項政策

### 政策對照表

| 政策 | I. 本地即時 | II. 延遲觸發 | III. 短暫非同步 | IV. 長時操作 |
|------|-----------|-------------|---------------|-------------|
| **Layer 2 回饋（服務受理）** | 不適用（無服務呼叫） | 不適用（本地運算，無受理階段） | 不提供（亞秒完成，pressed 態已足夠覆蓋等待感知；SPEC-003 Section 2.6「0.1 無非狀態級短暫等待」） | `LoadingState`（骨架或進度條 + 計數文字，SPEC-003 Section 2.6） |
| **Layer 3 回饋（event 效果）** | 狀態轉換本身（使用者直接看到結果） | 清單筆數更新（狀態轉換本身） | `AppSnackBar`（成功/失敗各有對應文案，SPEC-003 Section 2.2） | 狀態轉換本身（載入完成 cross-fade）；頁面不可見時升級為系統通知或 SnackBar（僅破洞掃描，SPEC-003 Section 2.2「系統層通知」） |
| **輸入阻擋** | 不阻擋 | 不阻擋 | 不阻擋 | 阻擋頁面內容（整頁被 `LoadingState` 取代）+ 取消按鈕 |
| **重複觸發防護** | 無需（本地狀態操作天然冪等） | 防抖（`Motion.searchDebounce`），承擔者＝服務 | 冪等（重複觸發為合法操作，如多次 open 同一檔案）；授權請求有系統級防護（`notDetermined` 只首次彈框） | 禁用觸發來源（`LoadingState` 取代頁面後觸發入口不存在） |

### 各項政策說明

#### 回饋提示形式

**類型 III（短暫非同步）的 Layer 2 不提供的理由**：SPEC-003 Section 2.6 已定案「0.1 無非狀態級短暫等待需要延遲顯示的情境」，且「外部開啟契約」明訂不顯示等待指示（實測 200-550ms，由 pressed 態覆蓋）。如果未來 0.1 後出現需要等待指示的短暫非同步（如 0.5-2 秒的 API 呼叫），須新增時間 token 並評估延遲顯示策略（SPEC-003 Section 2.6 末段），屆時可能需要拆分類型 III。

**類型 IV 的 Layer 3 回饋路徑依結果可見性分岔**：
- 使用者仍在觸發頁面 → 狀態轉換本身為結果（載入態 cross-fade 至正常態）
- 使用者已離開觸發頁面（僅破洞掃描，SPEC-003 Section 2.8 L1）→ 系統通知（granted）或 AppSnackBar.withAction（denied fallback）

**回饋形式皆對應既有元件**：
- `LoadingState`：SPEC-004 Section 3.1 第 14 項（骨架/進度條 + 取消）
- `AppSnackBar`：SPEC-004 Section 3.1 第 16 項（plain / withAction）
- Material pressed 態：SPEC-004 Section 4.0.1
- 系統通知：SPEC-003 Section 2.2（ScanNotifier 介面）
- **無缺件**：四類服務類型的回饋形式皆可由既有元件承載

#### 輸入阻擋範圍

三選一判準：

| 選項 | 判準 | 適用類型 |
|------|------|---------|
| 不阻擋 | 操作亞秒內完成，或使用者正在進行中的互動（輸入文字）不應被打斷 | I, II, III |
| 禁用觸發來源 | 防止同一來源重複觸發，但使用者可操作其他元素 | 0.1 無此類型（類型 IV 天然由 LoadingState 替代整頁） |
| 阻擋頁面內容 | 操作秒至分鐘，中間結果無法顯示於正常態版面，整頁被載入態取代 | IV |

**類型 IV 的「阻擋」是頁面內容被 LoadingState 取代**：`LoadingState` 佔據 SPEC-001 的整個內容區，正常態元素不可見亦不可互動。但**導覽列（rail）不被阻擋**——SPEC-003 Section 2.8 L1 定案切換導覽項不取消任務，因此使用者可離開但任務繼續。此非「整個畫面凍結」，而是「頁面內容區被替代」。

**阻擋頁面內容時必須同時提供取消**：`LoadingState` 已含取消按鈕，取消契約 C1-C8（SPEC-003 Section 2.5）確保取消在 `Motion.cancelDeadline`（500ms）內抵達目標態。此約束已被既有規格滿足。

#### 重複觸發防護

**承擔者一律是服務**（用戶裁示）。元件在每一次互動都發出 Layer 1 回饋（不變式，見第三步），防抖/節流/冪等決策由服務做。

| 防護機制 | 服務層行為 | 元件層行為 |
|---------|-----------|-----------|
| 防抖（debounce） | 服務在收到事件後啟動計時器，窗口內再次收到相同事件則重設計時器，窗口結束才執行 | 元件每次輸入都更新自身顯示（Layer 1），無條件呼叫服務回調 |
| 節流（throttle） | 服務在固定間隔內至多執行一次（0.1 無此類型） | 同上 |
| 冪等（idempotent） | 服務接受重複呼叫，相同輸入產生相同效果，不阻擋不排隊 | 元件每次點擊都有 pressed 態（Layer 1），無條件呼叫服務回調 |
| 禁用觸發來源 | 服務開始長時操作時，通知 UI 層進入載入態 | LoadingState 取代頁面內容，觸發入口物理上不存在 |

---

### 第三步：不變式

**INV-FEEDBACK-001：元件在每一次互動都必須發出第一層回饋，即使服務因防抖、節流或冪等而丟棄該次呼叫。**

展開：
- 使用者按下按鈕 → pressed 視覺（ripple / 變色 / 變形）必須在 `Motion.feedback`（100ms）內出現，**不受服務是否執行該次呼叫影響**。
- 使用者在搜尋框輸入字元 → 字元必須立即出現在輸入框中，**不受防抖計時器是否已到期影響**。
- 使用者在防抖窗口內多次按下同一按鈕 → 每一次按下都有 pressed 視覺，即使服務只執行最後一次。

**Why**：防抖若做在元件層，窗口內的按下會沒有 ripple——使用者看到一個沒反應的按鈕，正是 ARCH-GPD-001 的形態（回饋掛在服務的成功路徑上），只是成因從「服務不可用」換成「服務刻意不執行」。元件永遠回饋、服務決定是否真的執行，兩者的責任分離對應三層歸屬的第一層（元件自身）與第二層（服務）。

**Consequence**：違反此不變式時，使用者無從區分「按鈕壞了」與「服務正在防抖」。且自動化測試無法發現——測試替身不做防抖，元件在測試中恆有回饋，只有真實環境下快速連按才暴露缺陷。

**機械檢查方式**：
1. 搜尋所有 `Timer`（dart:async）用法，確認沒有在計時器回調之外的路徑抑制 Layer 1 回饋（如在 debounce 窗口內把按鈕設為 disabled 或跳過 onPressed 呼叫）。
2. 搜尋所有 `enabled: false` 的設定路徑，確認沒有以「防抖中」為 disabled 的理由——disabled 的合法理由是「操作不可用」（如取消進行中），不是「操作被防抖暫緩」。

### 現況盤點：Motion.searchDebounce 違例

### 調查結果

`Motion.searchDebounce` 的防抖實作在**元件層**（`lib/components/search_field.dart:116`）：

```dart
_debounceTimer = Timer(Motion.searchDebounce, () {
  widget.onChanged(text);
});
```

`SearchField` widget 的 `_handleTextChanged` 方法持有 `Timer? _debounceTimer`，由元件決定何時呼叫 `onChanged` 回調。服務/provider 層無任何防抖邏輯。

### 是否違反裁示

**是，在歸屬層面違反「防抖由服務提供，不是元件提供」的裁示。** 元件是防抖的決策者與執行者。

**但不變式 INV-FEEDBACK-001 未被違反**：每一次鍵盤輸入，字元都立即出現在輸入框中（Layer 1 回饋存在）。防抖只延遲 `onChanged` 回調（相當於延遲服務呼叫），不抑制輸入框的視覺更新。

### 需要的修正方向

將防抖從 `SearchField._handleTextChanged` 移至消費 `onChanged` 的 provider/service 層。修正後 `SearchField` 在每次非組字輸入都無條件呼叫 `onChanged`，provider 做 debounce 決策。

**不在本票範圍**：修正涉及元件與 provider 的接線改動，應由 IMP ticket 執行。以 spawn request 登記。

### Task Reference
- 0.1.0-W3-102 what: 修正 回饋責任的三層歸屬：服務受理層的承擔者是服務不是元件

### Rationale Chain
- 0.1.0-W3-102 why: `0.1.0-W3-098` 落地的〈掛載點〉條文寫「按下確認與等待指示的觸發點是互動事件本身與『已送出、尚未回應』這個狀態」——把**兩層都歸給元件**。用戶隨後的裁示（2026-09-08）給出三層，且中間那層的承擔者是服務不是元件：

| 層 | 內容 | 承擔者 |
|----|------|--------|
| 一、互動元件層 | 互動當下的回饋：震動／音效／變形／變色／光環 | **元件自身**，與背後是否掛服務無關 |
| 二、服務受理層 | command 發送 event 給服務後，服務自己的處理回饋：toast、loading 動畫 | **服務** |
| 三、event 效果層 | 服務處理完之後才觸發 event 應該觸發的效果，無論成功失敗或其他 | 事件處理路徑 |

現行條文與此的差距有兩處：

1. **歸屬錯置**：「等待指示」（第二層）被寫成元件的義務。實際上 command 送出之後，是**服務**要對「我收到了、正在處理」負責。把它歸給元件，會讓服務側完全沒有回饋義務——服務可以什麼都不做而條文仍被滿足。

2. **第一層的無條件性未寫明**：條文的判準問句「把服務拔掉還看得到反應嗎」隱含了第一層必須存在，但沒有明說**每個可互動元件都必須有互動當下的回饋，沒有例外**。PM 在派發存量盤點票時因此把「互動不觸發跨層呼叫」誤讀為「判準自動成立」——純本地狀態切換的元件若按下時無任何表現，只有狀態改變後的結果，一樣是缺陷，而該誤讀在現行條文下讀得通。

`ARCH-GPD-001` 同樣只寫了兩層（回饋 vs 服務回應），未涵蓋服務受理層的獨立歸屬，須一併補。
