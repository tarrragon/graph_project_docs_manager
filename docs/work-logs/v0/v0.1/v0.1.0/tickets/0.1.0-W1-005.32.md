## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 實作概述

`FilterDropdown`（StatefulWidget）+ `FilterOption`（純值類）。觸發器顯示
`{label}：{currentValue}`，寬度取「全部」與各選項文字（含 label 前綴）的最寬者，
以 `LayoutBuilder` 取可用寬度做上限（避免超長測試文案撐破版面，同時滿足
「選取不同值時寬不變」）。選單以 `OverlayEntry` + `CompositedTransformFollower`
呈現（頂緣貼觸發器底緣、左緣貼觸發器左緣，全數選項展開不捲動，SPEC-003 F4）；
展開／走選項（↑↓Home/End）／收合皆不呼叫 `onChanged`，唯一呼叫點是選取且值改變
（F5）；選單根 `Semantics.role = menu`，選項 `role = menuItem` 並帶 `selected`
（F6）；模態遮罩（`GestureDetector` + `HitTestBehavior.opaque` 全螢幕覆蓋）吸收
選單展開期間的外部點擊，不傳遞至下層（F7）。

### 修改檔案

- `lib/components/filter_dropdown.dart`（新增）
- `test/unit/components/filter_dropdown_test.dart`（新增，25 個測試）
- `lib/components/components.dart`（追加一行 export）

### 自檢結果

**框架層陷阱（排查過程記錄）**：
1. 觸發器同時把同一 `FocusNode` 交給外層 `Focus` widget 與內層 `InkWell`，
   觸發 `child != this` 斷言（自己成為自己的 parent）。改為只交給 `InkWell`，
   鍵盤啟用改用 `Shortcuts`/`Actions`（`ExpanderIcon` 既有慣例）。
2. `dispose()` 內經 `_closeMenu()` 呼叫 `setState()`，在 unmount 路徑上觸發
   `_lifecycleState != _ElementLifecycle.defunct` 斷言。加 `_isDisposing` 旗標，
   `dispose()` 只清理資源（overlay 移除、FocusNode dispose）不觸發重建。

**契約值**：SPEC-004 4.13 契約值未變動，無需修改 SPEC-004（4.13 本文「待決」標記
本身留待後續 DOC 票去標，非本票範圍）。

**Phase 4 結論**：程式碼品質 A（單檔案、單一職責、無外部依賴新增）。技術債務：
F7 模態遮罩目前對整個視窗吸收點擊（含觸發器自身所在區域）——再次點擊觸發器座標
時實際命中遮罩而非 InkWell 本身，最終行為與直接點觸發器一致（皆收合選單），
但非透過觸發器 `onTap` 路徑觸發，測試中以 `warnIfMissed: false` 明確標註此為
預期的吸收路徑。不影響本票驗收，若未來需要精確依 SPEC-003「再點觸發器：焦點
停在觸發器」逐字實作，需改用 `TapRegion`（group 內點擊視為內部）取代目前的
全螢幕 barrier，留待有實際需求時再處理。無需另開 Ticket：此為已知且不影響
功能正確性的實作細節，非缺陷。
