    **一、新增要件：基準必須釘選為變數，禁止在配方任一步驟寫 `HEAD` 符號**


    失效機制：`read-tree` 與 `commit-tree` 之間若 HEAD 被並行推進，tree 與 parent 分屬不同基準，差集即成靜默回滾。跨 Bash 呼叫執行時窗口尤其大（Bash 工具的 shell 變數不跨呼叫存活，基準須以檔案或明確重述傳遞）。


    為何三要件擋不住：要件 2（`GIT_INDEX_FILE`）保護寫入端、不保護基準新鮮度；要件 3 以舊基準自檢時必然通過（tree 相對它就是只有預期檔案）。


    CAS 舊值是唯一偵測點：`update-ref` 舊值寫 `HEAD` 會自我解析而恆相等；寫釘選的變數則在 HEAD 被推進時**失敗而非覆蓋**。這是配方裡唯一能察覺本情形的環節。


    實證：commit `4bd0e2ac` 靜默回滾了並行 session 對某 ticket md 的 `blockedBy` 設定；由對方以正向 commit 修復。


    **二、新增收尾步驟：CAS 成功後清理共用 index 的過期 entry**


    隔離索引的設計目的是不觸碰共用 index，但那也意味著——CAS 推進 HEAD 之後，**共用 index 中任何既有 entry 都相對新 HEAD 變舊**。此後任何一次裸 commit 都會把這些檔案回滾，且 `git diff --cached --name-only` 的檔名核對對此無鑑別力（規則七「版本邊界」的同一機制，但成因是自己剛才的 CAS）。


    配方須補收尾步驟與可執行的偵測／處置：


    - 偵測：`git status --porcelain` 出現 `MM` 的檔案，或逐檔比對 `git show :<path>` 與 `git show HEAD:<path>`

    - 判定：index 版本若不含新 HEAD 已有的內容，即為過期

    - 處置：`git restore --staged <path>` 重設回 HEAD；**先確認 index 中無他方獨有內容**再重設（有則屬他人在途工作，改為通知對方而非逕自重設）


    實證：一次 CAS 提交後，共用 index 留下六個檔案的過期 entry（皆為該次提交剛推進的內容），在被裸 commit 觸發前偵測並清除。


    `bash-tool-usage-rules.md` 規則七後既有的「版本邊界（過期 index 快照）」邊界段補一句交叉引用，指出隔離索引路徑不僅有同型風險、且**會主動製造**這種過期快照，其防線分別是 CAS 舊值釘選與收尾清理。'
