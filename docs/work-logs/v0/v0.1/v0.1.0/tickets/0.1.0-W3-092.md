## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填 -->

### 問題根因

traceability.yaml 的頂層鍵由 TRACEABILITY_SCHEMA（tracking_schema.py）定義為封閉集合（四軸：mappings / domain_bundle_tests / data_contract_tests / runtime_tests），有 pytest conformance 測試強制。測試對象目錄（test-object-catalogue.md）定義六個來源類別。兩者形狀不同構——六類中「畫面狀態轉換」「互動規則」「元件契約」三類在四軸中無對應位置。

問題不是「怎麼對齊」，而是「該不該對齊」。

### 影響範圍

已驗證事實：
1. test-map 命令（W3-090 後）只消費 mappings 軸
2. domain_bundle_tests / data_contract_tests / runtime_tests 三軸無任何工具讀取消費者（batch_init 僅生成骨架）
3. 六類來源類別的單位是「規格條目」（細粒度），四軸的單位是粗粒度——粒度不同

### 相關 Error Pattern

無。本議題屬設計決策而非錯誤修復。

## Solution
<!-- Schema[ANA/Solution]: 必填 -->

### 三候選結論論證

#### A：本就不同構，明訂分工

兩者回答不同問題：

| 維度 | traceability.yaml（四軸） | 測試對象目錄（六類） |
|------|--------------------------|-------------------|
| 問什麼 | 已存在的測試對應到哪條規格？ | 從規格推導該測哪些對象？ |
| 用途 | 審計（事後追溯，資料型） | 設計（事前推導，方法論型） |
| 單位 | UC-SPEC 映射 / domain bundle / 資料契約 / runtime 場景 | 規格條目（細粒度） |
| 消費者 | test-map CLI（mappings 軸）；人工查閱 | 測試設計者（Phase 1/2） |
| 生命週期 | 隨測試實作持續更新 | 測試設計期產出，實作後穩定 |

利：schema 不動，無 conformance 測試影響，無跨專案影響。
弊：三類無對應的來源類別需另找載體。

#### B：應同構，擴充 schema

為三類新增頂層軸（screen_state_tests / interaction_rule_tests / component_contract_tests）。

弊：
1. 頂層鍵封閉集合擴充影響所有 consumer 專案的既有 traceability.yaml
2. 既有三軸（domain_bundle_tests / data_contract_tests / runtime_tests）已無工具讀取，再加三軸等於六軸中五軸無消費者
3. 新軸粒度（規格條目）與既有軸粒度（domain bundle / 資料契約）不一致，混在同一檔案造成認知負擔
4. 元件契約在元件庫規格已有載體（SPEC-004 逐元件測試契約欄位），進 yaml 形成雙份 SSOT

#### C：部分同構

判準（AND）：有工具消費場景、粒度與既有軸一致、無其他權威載體。

逐類檢查：

| 來源類別 | 工具消費？ | 粒度一致？ | 無其他載體？ | 結論 |
|---------|----------|----------|------------|------|
| 畫面狀態轉換 | 無 | 否 | 是 | 不進 |
| 使用案例行為場景 | 有（mappings 已覆蓋） | 是 | 是 | 已在 |
| 互動規則 | 無 | 否 | 是 | 不進 |
| 元件契約 | 無 | 否 | 否（SPEC-004） | 不進 |
| Token 不變式 | 有（data_contract_tests 已覆蓋） | 是 | 是 | 已在 |
| 平台契約 | 有（runtime_tests 已覆蓋） | 是 | 是 | 已在 |

三類無對應的來源類別全數不滿足進入判準，結論與 A 相同。

### 擇定結論：A（本就不同構，明訂分工）

理由：
1. 候選 C 過濾後結果與 A 完全相同——三類都不該進 schema
2. 候選 B 產生五軸無消費者的空欄位，違反「沒有消費者就不擴充」原則
3. 兩份文件回答的問題、粒度、消費者、生命週期皆不同，不同構是正確的設計狀態

### 三類無對應的來源類別的載體

| 來源類別 | 建議載體 | 理由 |
|---------|---------|------|
| 畫面狀態轉換 | 規格文件 docs/spec/ 下對應 SPEC 的狀態矩陣章節 | 規格本身即定義狀態轉換，測試對象從該規格推導 |
| 互動規則 | 規格文件 docs/spec/ 下對應 SPEC 的互動規則章節 | 同上 |
| 元件契約 | 元件庫規格 SPEC-004 逐元件測試契約欄位 | 已有載體，不需重複 |

三者權威來源都是規格文件。traceability.yaml 的角色是實作後審計記錄；三類屬設計期推導，留在規格文件是正確位置。

### Spawn 落地確認

結論為 A，不擴充 schema。無需登記 spawn request。兩份文件補界線說明與互指路由是否建 DOC 票，由 PM 裁決。
