### Rationale Chain
- 0.1.0-W3-072 why: tech-decisions L830 記載 tripwire「加入編輯能力」的規定 action 為備份／衝突／還原／PII 全部重評、等同新的架構決策，觸發條件於 0.0.3-W1-002 定案時成立而四項皆未執行。0.2 將決定 workspace 存取與資料來源範圍，該決策會引用「App 是否擁有／改寫使用者資料」的前提；四項未重評即代表 0.2 在未定的安全前提上做範圍決策。
- 0.1.0-W3-281 why: `0.1.0-W3-072` 的五項結論反覆指名 `0.1.0-W3-073` 為條文化載體。多視角審查的證據視角查證後發現兩個問題。

**一、載體未指名**：`0.1.0-W3-073` 的 `where.files` 只列 SPEC-004（元件庫規格）與 PROP-005（提案），沒有任何一份是「編輯能力規格」本身；其 acceptance 第一條要求「編輯能力規格建立」，但該新文件要建在哪個路徑，票面未指名。任何承接安排在路徑未定之前都無法驗收。

**二、承接關係在票面無痕跡**：`0.1.0-W3-073` 與 `0.1.0-W3-072` 的關係是 `blockedBy`（073 等 072），**不是 spawn**——072 的 `spawned_tickets` 不含 073。因此 072 加給 073 的五項條文化責任，在 073 票面上沒有留下任何痕跡：該票執行者依其 what／why／how／acceptance 逐條執行，不會知道要寫這五條，也不會因漏寫而被 acceptance-gate 擋下。

**三、範疇部分不符**：073 的重心是樂觀更新政策的解鎖（四條 acceptance 中兩條專講樂觀更新）。五項結論對其範疇的落點為：還原的變更記錄落在範疇內；備份與衝突部分落在「失敗與衝突的畫面態」但其判定邏輯屬 Corpus／History domain 而該票 layer 為 Presentation；PII 與寫入範圍界限兩項完全落在其外（不在四項產出、不在 where.files、acceptance 零提及）。

本票不預設採哪一路。審查提供三條候選（改指／另開條文化票／擴充 073 票面）及各自需同步改動處與風險，見 `0.1.0-W3-072` 的 Solution。
