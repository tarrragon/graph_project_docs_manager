### Rationale Chain
- 0.1.0-W3-142 why: `ticket track add-acceptance` 會自動為傳入的文字補上 `[ ]` checkbox 前綴，但 `--help` 只寫「驗收條件文字」，**沒有說明這件事**。

使用者若照票面既有的字面（票面存的是 `[ ] 條件內容`）複製並傳入，結果會變成 `[ ] [ ] 條件內容`。並行 session 於 2026-09-08 實際命中，自行 `remove` + `add` 修復。

**這是引導缺口而非使用者錯誤**：票面顯示的字面帶前綴，複製票面字面是最自然的操作，而 help 沒有任何訊息說明前綴會被自動加上。**使用者做了看起來最合理的事，得到錯誤結果，且該結果不會報錯**——雙前綴是合法字串，CLI 照收。

**與 `--acceptance` 的不一致同源**：`ticket create --acceptance` 不以逗號分隔（整串當一條），`--where` 則吃逗號分隔，而兩者的 help 描述看起來同構。三者合起來是同一個問題的三個實例——**help 描述參數「是什麼」，不描述參數「怎麼被處理」**。（來源已完成，結論見 Solution）
- 0.1.0-W3-214 why: **同一個 `ticket create --help` 輸出裡，四個多值參數用兩種分隔符**：

| 參數 | help 寫的分隔符 |
|------|---------------|
| `--where` / `--where-files` | 逗號，如 `'file1.py,file2.py'` |
| `--blocked-by` | 逗號，如 `'ID1,ID2'` |
| `--related-to` | 逗號，如 `'ID1,ID2'` |
| `--acceptance` | **`|`**，如 `'條件A|條件B'` |

三比一。**呼叫者在同一次呼叫中先用三次逗號，第四次沿用逗號是這個介面自己教出來的**，
而它是唯一失敗的那個——逗號不是分隔符，六條判準被當成一條字串收下。

**失敗完全無聲**：不報錯、不警告、票面顯示正常、`check-acceptance` 判定正常。
唯一的損失是驗收粒度——六條當一條勾，任何一條沒做到都不會被單獨標示出來。

**實例**：`0.1.0-W3-208` 建立時 PM 以逗號串接六條判準，實際存入 1 條
（`grep -c '^- '` 於該票 acceptance 段回傳 1）。

**這不是文件缺口。** `references/create-command.md:87-89` 的範例正確且完整
（`--acceptance "條件A" --acceptance "條件B"` 與 `"條件A|條件B|條件C"` 兩種都有），
`--help` 也寫對了。**問題在於正確的說明擋不住錯誤的習慣**，而那個習慣是同一支
CLI 的其他三個參數建立的——依 `opinionated-default-design` 主張 1，工具的預設
行為會贏過文件。

**本專案已認得這個危害類別。** `acceptance_parser.detect_numbered_list_collapse`
的存在就是為了「使用者把 N 條塞進一個值裡」這件事，但它只偵測**換行的編號列表**
（`1. ` / `2、`），單行逗號串接是同一危害的另一種表面形態，未被涵蓋。（來源已完成，結論見 Solution）
