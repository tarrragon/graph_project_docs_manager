## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 定位判定（先於修法）

`oregano-data-miner` **在框架中仍有定位**，但定位錯置——現行三區塊要求它獨立擁有並完成 ANA/DOC 型 ticket，這在其工具集（`Grep, LS, Read`）下結構性不可行；框架已有相容的既存分類可承接它：`TICKET_EXEMPT_AGENT_TYPES`（純唯讀、免 Ticket ID 的諮詢型 agent，與 `basil-writing-critic`／`linux` 同類）。`agent-ticket-validation-hook.py` 的判準原文（「工具僅含唯讀...不會產生持久化副作用者可豁免」）已涵蓋 oregano，只是尚未列入名單——此為 `ARCH-BAL-003` 已追蹤的同型脫節，非本票新發現的獨立問題。

支持「定位仍存在」的實證：book_overview_app 的 0.10 版 master plan 大量規劃性指派 oregano；其唯一一張 `status: completed` 的 ticket 明確將工作拆為「研究」與「撰寫」兩個角色——這個分工模式本身被驗證有效（研究者不必自己產文件，由另一個 agent 轉錄/撰寫），只是「研究者」選錯了 agent（該研究實際用了 oregano 不具備的 WebSearch/WebFetch，經 general-purpose 完成）。這正是「純諮詢型」定位的雛形，只需把 oregano 的三區塊改寫到與這個已被驗證的實務模式一致。

### 四選一裁定：(c) 改為純諮詢型

**不選 (a) 補 Bash+Edit**：補寫入工具會使 oregano 具備持久化副作用能力，直接抵觸 `TICKET_EXEMPT_AGENT_TYPES` 判準的「不產生持久化副作用」要件——一旦補上，它就從「可豁免 Ticket 驗證」變成必須引用 Ticket ID、承擔完整 ticket 生命週期義務的一般實作型 agent。這會把它併入「策略規劃者被要求兼具寫入權」的模式，架空其核心身份宣言「你設計藍圖，其他代理人執行實作」，也不符合 `basil-writing-critic`「產出審查報告，不修改文件」這一同型 agent 的既有設計慣例。

**不選 (b) 只補 Bash**：`Bash` 可呼叫 `ticket track append-log` 寫入 ticket md，此動作本身即是持久化副作用（git commit），同樣使它脫離唯讀豁免資格、被迫回到「需要 Ticket ID + 承擔 ticket 生命週期義務」的一般模式。且它仍無 Write/Edit，仍無法履行「允許產出」欄承諾的獨立 `.md` 策略文件產出——只解決「能記錄」，未解決「能完整正常運作於 ANA/DOC ticket 的其餘義務」（例如無法自行建立 spawn ticket、無法完整落實 quality-baseline 規則 5）。是半套修法，且仍與唯讀豁免設計衝突。

**不選 (d) 退役**：實證顯示定位仍有需求（見上「定位判定」段的 book_overview_app 分工模式）；框架另有多個同型純唯讀 agent 已用「不擁有 ticket、僅供諮詢」模式運作良好，證明這個角色類別本身站得住腳。缺陷在於 oregano 被錯誤地要求扮演「ticket 擁有者」而非「被諮詢者」——這是可修的錯置，不是角色本身不成立。退役會捨棄一個已在其他 consumer 專案被驗證過、只需重新收斂範疇即可修好的分工模式。

### 允許產出三欄矛盾的修正方向（獨立缺陷，隨 c 一併修正，不因選 c 而略過）

| 欄 | 現行內容（矛盾） | 修正方向 |
|----|----------------|---------|
| 檔案類別 | 資料提取策略文件（`.md`）、DOM 選擇器規劃、驗證/轉換規則文件、外部研究報告 | 無獨立檔案產出；研究/策略內容以口頭回報（inline 文字回覆）形式交付給派遣者 |
| 操作類型 | Grep / LS / Read（純唯讀工具） | 不變（Grep / LS / Read） |
| 路徑範圍 | 僅產出策略性文件至 ticket context 或 `docs/`；禁止 Write/Edit 任何程式碼或資料模型 | 不適用（無寫入路徑）；讀取範圍依派遣者提供的上下文，不主動寫入任何檔案。移除「僅產出策略性文件至...」這句與操作類型矛盾的敘述 |
