## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`0.1.0-W3-181` 以全量掃描存量 1990 個相異路徑值（394 檔）論證路徑軌不轉阻擋。但 `diff_new_hits`（`:498`）比對 `pre_text` 與 `post_text` 的集合差，只報編輯後新增的命中——既有內容（存量）永不觸發。因此「1990 規模過大」描述的是存量，而轉阻擋的影響面是流量，**兩者是不同的軸**。以存量數論證阻擋成本會高估實際代價。

此外，路徑軌 WARNING-only（exit 0）與 ticket ID 軌阻擋（exit 2）並列，exit code 完全由 ticket ID 軌決定（`main()` 第 779-811 行），路徑軌對 exit code 無影響。只含路徑違規的編輯以 exit 0 通過整個守衛，可能複製了 PC-GPD-009 所修正的「部分覆蓋被讀為全合規」缺陷結構。

### 影響範圍

**已驗證事實**：
- `.claude/hooks/reference-stability-rule8-guard-hook.py` 第 772-777 行路徑 WARNING 輸出與第 779-811 行 ticket ID 阻擋判斷——exit code 完全由後者決定（讀碼確認）
- `diff_new_hits` 對兩軌皆以集合差運算，存量永不觸發（`tarrragon/claude#84` 已實證）
- Sync-pull 走 git 操作不經 PreToolUse hook，sync-pull 命中不受升級影響

### 相關 Error Pattern

- PC-GPD-009：部分覆蓋而會命中的守衛，其命中被讀成全規則合規
- `tarrragon/claude#84`：`diff_new_hits` 的 `added_text` 只取 staged diff 新增行機制記錄

## 重現實驗結果
### 實驗方法

**量測的是什麼**：git commit 粒度的路徑軌新增命中頻率。一個 commit 可能包含多次 Edit 操作，故 per-commit 計數是 per-Edit 的下界。

**代表性邊界**：樣本期間為 W3 wave 後段，有密集的方法論/error-pattern/skill 撰寫活動——這是路徑引用最密集的活動型態（大量引用 `docs/spec/`、`docs/tech-decisions.md` 等）。日常 IMP 實作（主要改 `lib/`、`test/`）產生的路徑引用流量會更低。**本量測偏向高估流量**。

**系統性盲區**：
1. 被 ticket ID 軌阻擋而未成功 commit 的編輯不在樣本中——這些編輯可能同時有路徑命中，但因被阻擋而不可見。低估量與高估量交叉方向相反，無法事前判定淨偏差。
2. 經 Bash 寫入的 `.claude/` 編輯雖在 git 歷史中，但 hook 不會對其觸發（PreToolUse 僅 Edit/Write/MultiEdit）。本量測對此類計入了命中但實際不會產生阻擋——偏向高估。
3. Sync-pull 的 merge commit 中手動解衝突的部分可能經 Edit 操作，本量測已將 sync-pull 整體排除——可能遺漏少量 merge 解衝突的本地編輯。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 事實澄清

**「1990/394」是存量而非流量**。`diff_new_hits` 使存量永不觸發（`#84` 已實證），轉阻擋的實際影響面只有新引入流量。後續討論不可再以此數字論證阻擋成本。

### 問題一：流量量測

實際流量：每 11-12 個 commit 遇到約 1 次路徑命中（僅計本地編輯，排除 sync-pull 回流），其中真實違規僅佔 6%（1/188 commits），50% 可 30 秒以 marker 解除。

量測偏向高估（樣本期為方法論/error-pattern 密集撰寫期），日常 IMP 實作的流量更低。

### 問題二：WARNING 層是否複製了缺陷結構

**是的，WARNING 層複製了 PC-GPD-009 所述缺陷結構的核心機制。**

機制路徑：
1. 一次編輯只引入專案路徑引用、無新增 ticket ID
2. 路徑軌命中，stderr 寫 WARNING（第 773-777 行）
3. ticket ID 軌 `diff_new_hits` 回傳空（第 779 行 `new_hits` 為空列表）
4. `main()` 回傳 `EXIT_ALLOW`（第 790 行，exit 0）
5. **下游讀到的是「通過 rule8 守衛」——路徑違規在 exit code 中不可見**

結構對照：

| PC-GPD-009 原始形態 | 路徑軌 WARNING 形態 |
|---|---|
| 守衛只認 ticket ID 不認路徑：路徑違規靜默通過 | 守衛認路徑但只 WARNING：路徑違規以 exit 0 通過 |
| 守衛命中 ticket ID 並被滿足時規則在讀者心中結案 | WARNING 被印但 exit 0，「通過守衛」被讀為全規則合規 |
| 沉默時讀者仍可能自查 | WARNING 時操作者可能注意但下游只看 exit code |

**唯一改善**：WARNING 對當前操作者可見（stderr 瞬時輸出）。但此可見性不持久化：hook 日誌僅除錯用、ticket body 不記守衛 WARNING、commit 不記載——下游消費者（PM 驗收、code review、其他 consumer sync-pull）看不到。

### 問題三：1990 個存量的處置

依 `#84` 機制，存量永不觸發且會隨 sync-push 原樣 overlay 回 canonical。

**處置建議**：明文記錄 1990/394 為已知存量基準（量測時點 2026-09-08，W3-181 實作當下），不在本 consumer 獨立清理。理由：
1. 清理成果會被下次 sync-pull 的上游 overlay 覆蓋
2. `#84` 已有 canonical 層清理計畫（flutter-balance 14 張票），分級清單做一次即全體適用（兩端分布幾乎相同）
3. 本 consumer 獨立清理會與上游方案分歧，產生二次返工

### 候選方案

**方案 A：升級路徑軌為阻擋（exit 2）**

修改 `main()` 使路徑軌命中參與 exit code 判斷（與 ticket ID 軌相同機制）。

| 面向 | 評估 |
|------|------|
| 阻擋頻率 | 每 11-12 個 commit 約 1 次（偏高估） |
| 解除成本 | 50% 可 30 秒 marker 解除；43% 需個案判斷（1-3 分鐘） |
| 真實攔截率 | 6%（約每 188 commits 攔 1 次真實違規） |
| 消除缺陷結構 | 是——路徑違規不再以 exit 0 通過 |
| 對 sync-pull | 無影響——sync-pull 走 git 不經 PreToolUse hook |
| 與 #84 關係 | 不衝突——本地升級只改 exit code 行為，不改 diff_new_hits 機制 |
| 風險 | 功能性引用（3 hits）目前三個 marker category 都不精確適用，升級前需先設計豁免通道，否則逼出不精確 marker |

利：完全消除缺陷結構複製。
弊：每 11 個 commit 約 1 次中斷，其中約一半需超過 30 秒處理；功能性引用需新 marker category。

**方案 B：維持 WARNING，以流量數據替代存量數據作為理由**

不改程式碼。在票面明載：維持 WARNING 的理由從「存量 1990 規模過大」改為「流量中真實違規率 6%，阻擋的邊際收益低於邊際摩擦，且功能性引用（19%）無現有豁免通道」。

| 面向 | 評估 |
|------|------|
| 維持理由 | 真實違規率 6%，94% 為合法或半合法引用 |
| 缺陷結構 | 仍存在——路徑違規以 exit 0 通過 |
| 與 #84 關係 | 最大相容——不預設本地修法方向 |
| 對當前操作者 | WARNING 可見（stderr），較零偵測已有改善 |

利：零開發成本；與上游保持最大相容。
弊：缺陷結構持續存在；「等真實損失」作為重評觸發意味被動。

**重評條件**（均為可觀測事件，非無限延後）：
1. `#84` 上游完成判定方式修改
2. 本 consumer 出現因路徑違規通過守衛導致的跨 consumer 後果
3. 新增第四個 marker category（如 `functional_ref`）使功能性引用有正式豁免通道——此時阻擋的無效攔截率從 94% 降至約 75%，成本效益值得重評

### 建議

**建議方案 B（維持 WARNING）**，理由：
1. 真實違規率 6% 不支持阻擋的成本效益——每 188 commits 才攔 1 次真實違規
2. 功能性引用（19%）無現有豁免通道，升級前需先解決豁免設計
3. `#84` 可能改變判定方式，先升級可能需二次返工
4. WARNING 對當前操作者可見已是從零到有的改善

**但維持理由必須更正**：依據是「流量中真實違規率 6%」而非「存量 1990 規模過大」。

- 0.1.0-W3-181 why: `reference-stability-rule8-guard-hook.py` 的掃描（`:313`）只迭代 `VERSIONED_TICKET_PATTERN` 與 `BARE_TICKET_PATTERN` 兩個樣式，**只認 ticket ID**。而規則 8 的條文（`reference-stability-rules.md:61`）是「禁止引用專案特定的 ticket ID、**worklog 路徑等專案層級識別符**」，並明寫失效形態為「sync 到其他專案後會變成死連結和誤導性資訊」。專案文件路徑正屬此類。

**實證**：`0.1.0-W3-166` 在 `.claude/methodologies/component-library-bidirectional-constraint-methodology.md` 寫入三處 `docs/spec/ui/SPEC-003-interaction-response.md`，全部通過守衛。該路徑在其他 consumer 專案不存在，且方法論新增條款的整個前提掛在該引用上（詳見 `0.1.0-W3-175`）。

**守衛的部分覆蓋是缺陷通過的直接成因，不只是沒攔到**：同一次編輯中，守衛**確實命中了**該檔 changelog 段落的 ticket ID，執行者依提示改寫後通過。於是「通過 rule8 守衛」被執行者與驗收者雙方讀成「符合規則 8」。

**沉默與命中的可解讀性不對稱**：守衛沉默時，讀者仍可能自行查驗；守衛命中並被滿足時，該規則在讀者心中已結案。因此**部分覆蓋而會命中的守衛，比不存在的守衛更容易讓漏網的那一類通過**——它為未覆蓋的部分提供了合規的外觀。這是本票優先級為 P1 而非 P2 的理由：缺陷不在覆蓋率，在覆蓋率被誤讀為完整。（來源已完成，結論見 Solution）
