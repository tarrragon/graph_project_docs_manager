why: '`agent-dispatch-validation-hook.py` 的廣域 staging 偵測以字串比對 prompt 內容，**無法區分「指示使用」與「明文禁止」**。


  **實測**（2026-09-10，`0.1.0-W3-176` Phase 3a 派發）：prompt 中的字樣為


  > 不帶 pathspec（禁 `git add .` / `git add -A`）


  即**禁令**，而 hook 回報「偵測到廣域 git staging（git add . / -A / --all）」並建議「改用精準路徑 staging」——prompt 本來就在要求精準路徑 staging。


  **後果不是誤擋（本檢查為警告不阻擋），而是訓練派發者移除正確的禁令**：要消除這則警告，最直接的做法是把禁令句刪掉；刪掉之後 prompt 對廣域 staging 就真的沒有防線了。**一個檢查若使遵守它的最省力路徑等於拆掉真正的防護，它在製造它要防的東西。**


  **同型**：本專案本日已記錄兩個同族缺陷——`0.1.0-W3-237` 第一項（檢核器把「找不到通道節」報成「FR 缺標定」）與第二項（引導訊息以節號指路而指向錯誤章節）。三者共同形態是**檢查器的輸出把讀者導向錯誤的下一步**。'
how:
  task_type: Implementation
  strategy: '使該偵測能區分指示與禁令。**不採「加白名單關鍵字」**（如見到「禁」就放行）——那只是把字串比對換一組字串，中文的否定表述形式眾多（禁／不得／不可／勿／避免／禁用），漏一個就恢復誤判，且會製造新的反向漏洞（真正的廣域 staging 指示只要在句中出現「禁」字就能繞過）。


    方向：偵測命中時**不逕自回報違規，改為要求輸出足以自我否證的證據**——印出命中的整行原文，讓讀者自行判斷該行是指示還是禁令；並把訊息措辭由斷言（「偵測到廣域 git staging」）改為條件式（「prompt 含廣域 staging 字樣，若為禁令可忽略，若為指示請改精準路徑」）。此方向與 `0.1.0-W3-237` 一致：檢查器不確定時應輸出可判讀的原始證據，不是輸出一個確定的錯誤結論。


    補迴歸測試兩筆：含禁令句的 prompt 不應產生斷言式違規回報；含指示句的 prompt 應產生回報。
