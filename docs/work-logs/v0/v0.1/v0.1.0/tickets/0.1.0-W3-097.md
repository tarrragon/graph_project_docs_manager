## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

**票面假設（guard 失敗）與實測不符：`applicationDidFinishLaunching` 從未被呼叫，
guard 那一行根本沒有執行機會。**

驗證方式（macOS 26.x / Flutter 3.47.1，App 以 `open -n --stdout` 經 LaunchServices
啟動，NSLog 走 stderr）：

1. 在 `applicationDidFinishLaunching` 入口與 guard 兩側各插一行 NSLog —— 兩行都沒印，
   `MainFlutterWindow.awakeFromNib` 的探針則有印。故問題不在 guard 判斷，在整段方法。
2. 排除量測管道失真：先以直接執行 bundle 內執行檔的方式量測，再改以 `open`
   經 LaunchServices 啟動重測，兩種啟動路徑結果一致，非「命令列啟動不觸發啟動事件」的假象。
3. 排除 delegate 未接線：`applicationWillFinishLaunching` 的探針證實
   `NSApp.delegate` 就是本 AppDelegate 實例，且
   `responds(to: applicationDidFinishLaunching:)` 為 `true`。
4. 定位到通知層：以 `NotificationCenter.addObserver(forName: nil)` 錄下整段啟動期間所有
   `NSApplication*` 通知，實測序列為
   `WillFinishLaunching` -> `WillUpdate/DidUpdate` -> `DidFinishRestoringWindows`
   -> `WillBecomeActive` -> `DidBecomeActive` -> 之後只剩 update 迴圈。
   **`NSApplicationDidFinishLaunchingNotification` 一次都沒有發出**，因此 AppKit 也就
   不會呼叫對應的 delegate 方法。

AppKit 為何不發這則通知，未進一步定位（屬 AppKit 啟動序列內部行為，本票不宣稱結論）。
可確定且足以支撐修復的是：**這個 callback 在本 app 不可靠，不能拿它當接線點**。
`applicationWillFinishLaunching` 則實測必定執行，且 `FlutterAppDelegate` 自己也在該時點
讀 `mainFlutterWindow` 設定視窗標題。

### 影響範圍

`0.1.0-W3-064` 實作的整套系統通知在實機零可用：`authorizationStatus`、
`requestAuthorization`、`show`、`withdraw` 四個方法全部 `MissingPluginException`，
`onActivated` 回傳因 channel 為 nil 而無效。Dart 端依 SPEC-003 §2.2 收斂為 `denied`，
所以不崩潰、畫面正常，只是通知永不出現。

### 相關 Error Pattern

- PC-BAL-010（驗證管道對目標現象不敏感）：`test/` 以 `FakeScanNotifier` 替換整個
  `ScanNotifier`，不經過真實 `MethodChannel`，1159 個測試對本缺陷零敏感度。這正是
  `0.1.0-W3-074` 所指缺口的第一個實例。
- 本票診斷過程中亦主動防範同類偏誤：先懷疑「直接執行 bundle 執行檔」這個量測管道本身
  會抑制啟動事件，改用 LaunchServices 重測後才採信結論（見上「驗證方式」第 2 點）。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修改內容

**`macos/Runner/AppDelegate.swift`**

1. 註冊時機從 `applicationDidFinishLaunching`（實測不執行）移到
   `applicationWillFinishLaunching`（實測必定執行）。此時 nib 已載入完畢
   （`MainFlutterWindow.awakeFromNib` 的時間戳早於本 callback），
   `mainFlutterWindow` 與其 `contentViewController` 皆已就緒，
   因此**不需要**改成強制解包，guard 原樣保留。
2. 註冊邏輯抽為 `registerScanNotifierChannel()`，並補上雙向可見訊號：
   - 成功：`NSLog("[AppDelegate] ... channel 已註冊")`
   - 失敗：`NSLog` 明說「channel 未註冊；系統通知將全面失效」，取代原本的靜默 return
     （quality-baseline 規則 4）。NSLog 走 stderr，`flutter run` console 直接看得到，
     不像 Dart 端的 `developer.log` 只進 VM service 的 Logging stream。
3. 方法上的註解寫明「不可改回 `applicationDidFinishLaunching`」與實測依據，
   避免下一位維護者依 Flutter 官方樣板的直覺改回去。

**`integration_test/app_test.dart`**：新增 `group('scan_notifier 原生端接線')`，
以裸 `MethodChannel(scanNotifierChannelName)` 直接呼叫 `withdraw` 與
`authorizationStatus`，斷言不是 `MissingPluginException`、且授權查詢回傳三個合法值之一。

**未修改 `lib/services/macos_scan_notifier.dart`**：降級為 `denied` 的設計正確，照派工要求不動。

### 為什麼測試放在既有檔案而不是新開一個檔

實測：macOS 上一次 `flutter test` 呼叫只能啟動一次 app。`integration_test/` 放兩個檔案時，
後跑的那個必定以 `Unable to start the app on the device` 收場——兩種順序（app_test 先／
scan_notifier 先）皆重現，與檔案內容無關。若另開檔案，README 記載的
`fvm flutter test integration_test/ -d macos` 會變紅，且紅燈原因與被測功能無關，最容易被誤診。
故併入 `app_test.dart`，並在 `main()` 上方留註解說明「新增測試請加在這裡而不是新增檔案」。

### 接線錯誤與規格要求的 denied 降級如何區分

SPEC-003 §2.2 要求「其他結果視為 `denied`」是為了**畫面層的行為確定性**，不等於
「接線錯誤也該靜默」。兩者在畫面上同形，因此區分機制不能放在畫面層，本票放兩處：

| 機制 | 位置 | 區分方式 |
|------|------|---------|
| 啟動期正向訊號 | 原生端 NSLog | 接線正常必有「channel 已註冊」；缺這行即為接線錯誤，不必等任何 Dart 呼叫 |
| 可執行的驗收 | `integration_test/app_test.dart` | 降級時 channel 有回應並回傳 `denied`；接線錯誤時 channel 完全無回應（`MissingPluginException`）。斷言鎖在「有無回應」，不鎖授權結果——授權結果取決於使用者與系統設定，不是程式碼的性質 |

原本缺的不是「runtime 分不出來」（Dart 端 log 文字本來就寫了「原生端未註冊 handler」），
而是**沒有任何機制會因為接線斷掉而變紅**。新測試補的是這一點。

### 測試有效性驗證（非空測試）

把註冊時機改回 `applicationDidFinishLaunching` 重跑，兩條測試皆紅，且錯誤訊息與 W3-078
實機觀測逐字相同：
`MissingPluginException(No implementation found for method authorizationStatus on channel graph_project_docs_manager/scan_notifier)`。
改回修復版即全綠。
