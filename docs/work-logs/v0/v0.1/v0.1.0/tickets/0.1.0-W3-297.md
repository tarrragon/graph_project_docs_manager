## Problem Analysis
### 問題根因

本票測的是 `0.1.0-W3-293` 於 commit `51662bb2` 落地的新條文（`.claude/skills/framework-issue/references/escalation-flow.md`〈修法時點分離：發現票何時能寫定修法〉），標的為 `tarrragon/claude#97`。#97 是三組標的中唯一已被統整過一輪者（觀測 comment 5629167716），因此可問「新條文能不能讓下一輪更省」而非只問「讀起來合不合理」。

受測條文的結構：原則一（時點分離單位是欄位不是票）、原則二（豁免軸是證據狀態不是規模）＋三問（消費端已觀測／反例已試／範圍已量）、兩檔擴散面處置表、三個檢驗案例、與規則 5 的銜接。

### 影響範圍

**已驗證的事實**：

- #97 現況：body 索引 6 筆區段、觀測流 4 則，`check` 三項警訊皆未觸發（RC=0）；6 個區段的 owner 全為 `flutter-balance-77`。
- 本端無 owner 識別（派發票未提供），依協定只能 `observe`。此條件與 288 那一輪相同——該輪的統整 comment 自己寫明「本則不建立區段（派發未提供 owner 識別，依協定不得以代理人名替代）」。

### 實驗發現

**已驗證的事實**：

1. 條文對「本端不是區段擁有者」這一步沒有說法：兩檔處置表第二檔的動作是「修法形狀移至 framework issue 區段決定」，而本端在 #97 上不能寫任何區段。這不是假設——288 那一輪已在同一條件下發生，統整內容落在觀測流（不進 body 索引）。
2. 條文對「issue 區段內的修法需要什麼證據狀態」零條文：修法被推到 issue 之後即離開條文射程，候選 E 的承重點 66/159 未判定這件事，沒有任何一端的機制會擋下它。
3. 第三問「範圍已量」在本 issue 的輸入下給出錯誤的通過（`163/164` 與 `15 個呼叫端` 都是量到的數字，仍漏一整類與跨行 3 處）。
4. 第一問「消費端已觀測」在本 issue 是連續量（93 指名／66 未判定），條文為二值問，門檻由執行者自訂。
5. 第二問「反例已試」在候選 D 上給出了正確且非顯然的答案（見 Solution 類別 2）。
6. `check` 主警訊以「距最新觀測的時間差」為代理指標，對「觀測已推翻區段內容」無鑑別力（實測本 issue 三項全綠）。

**仍未驗證的假設**：F5 所述「第一檔（限本 consumer 且可逆）在 `.claude/` 下是否接近空集合」，本票只以 #97 涉及的四個資產（經 288 的 `should_exclude()` 實測皆 False）為據，未對 `.claude/` 全樹量測 sync 排除比例。
