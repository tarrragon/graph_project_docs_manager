why: '編輯一個一天多前被派發過的檔案時收到警告「此檔案正在被背景代理人處理（ticket `0.1.0-W3-101`）」，而該票早已完成。實查後根因與第一直覺不同。


  **一、過期機制存在，該筆記錄早該被濾掉。** `dispatch_tracker.py` 定義 `TURN_ENDED_MAX_AGE_HOURS = 24` 與 `_is_dispatch_expired`，而該筆記錄的 `turn_ended_at` 為 `2026-09-08T07:57:45`，命中當下已逾 30 小時。**問題不是登記從未過期，也不是 TTL 設太長**，`turn_ended_at` 有被正確寫入。


  **二、`is_file_under_dispatch` 拿到的是未過濾的全量清單。** `get_active_dispatches` 的實作為 `state = _read_state(project_root); return state["dispatches"]`，不呼叫 `_is_dispatch_expired`。`is_file_under_dispatch` 迭代該清單比對檔名，因此命中歷來每一筆曾宣告過該檔案的記錄。實測該檔現有 37 筆。


  **三、關鍵：兩個不相容的「active」定義共存，且兩者都是刻意的。** 這一點推翻了「函式取錯名字」的初判——實查三個消費端，它們要的是兩種不同的東西：


  | 消費端 | 需要的語意 | 依據 |

  |--------|-----------|------|

  | `workspace-wipe-guard-hook.py` 的 `_get_active_dispatch_count` | **全量** | 該函式 docstring 明文寫死：「計入陣列中所有 entry，不檢視個別 entry 的 `turn_ended_at`⋯entry 存在本身即代表『未被確認終止』，**是刻意保守的判斷**」 |

  | `session-registry-start-hook.py` 的 idle 代理人掃描 | **全量** | 候選集合定義為「`turn_ended_at` 已設定」；過濾逾期等於濾掉最舊的那批，而那批正是最該被回報的（實測 SessionStart 候選含「started 6d ago」） |

  | `is_file_under_dispatch` → `main-thread-edit-restriction` / `agent-commit-verification` | **濾過期** | 問的是「現在有人正在編這個檔嗎」，37 筆歷史記錄對這個問題零鑑別力 |


  **所以 `get_active_dispatches` 沒有取錯名字**——在 wipe-guard 已寫死的定義下（active = 未確認終止），它的名與實一致。真正的缺陷是 **`is_file_under_dispatch` 需要另一個「active」的定義，卻借用了這一個**。


  > **分類更正**：本則原歸 `PC-GPD-009`（驗證器量錯軸）。該分類不成立——wipe-guard 量的軸是對的、結論也對。形態更接近**同一個詞在兩個消費端各自成立但互不相容**。分類不影響修法，記錄於此供日後歸檔。


  **後果**：該警告對已派發過的檔案恆真。恆真警告的代價不是吵，是它會在真正發生碰撞時發出**完全相同的訊號**，而讀者此時已學會忽略它——真碰撞因此靜默通過。'

  strategy: '**修法是拆成兩個入口，各自的名稱表達實情。不是「過濾」也不是「改名」二選一——那個二分預設了只有一個正確語意，而實查證明有兩個。**


    | 入口 | 語意 | 消費端 |

    |------|------|--------|

    | 保守存活（存在即未確認終止） | 回傳全部 entry，行為與現行 `get_active_dispatches` 完全相同 | `workspace-wipe-guard-hook.py`、`session-registry-start-hook.py` |

    | 未過期 | 套用 `_is_dispatch_expired` | `is_file_under_dispatch` 與其下游（`main-thread-edit-restriction`、`agent-commit-verification`） |


    命名由執行者決定，但兩個名稱都須讓呼叫端不必讀實作就知道拿到的是哪一種；沿用 `active` 一詞於其中任一者須說明理由，因為該詞正是本缺陷的來源。


    **兩條被否決的修法與理由（須記錄，否則會被下一個人重新提出）**：


    **一、把 `get_active_dispatches` 直接改成過濾。** `workspace-wipe-guard` 是防資料遺失的守衛，改成過濾會使它**靜默變弱**——而它自己的 docstring 正好警告過同型失敗（「讀檔失敗即靜默降級為不設防，與本守衛防止資料遺失的目的相悖」）。從另一個入口製造出它明文防的那件事，且無任何訊號。`session-registry-start-hook` 的 idle 掃描同樣會被削弱：過濾掉的正是最舊、最該被回報的那批。


    **二、只改名不改行為。** 解決誤讀，不解決 `is_file_under_dispatch` 仍拿錯清單。缺陷會從「名字騙人」變成「名字誠實但用錯」，恆真警告照舊。


    **三、在 ticket 完成時清登記。** 只覆蓋 ticket 生命週期這一個來源；被中斷的、跨 session 的、未完成的記錄仍會累積。


    **四、把當前 37 筆凍結為 accepted baseline。** baseline 適用於「真實存在但已知可接受的落差」；此處的記錄不是可接受的狀態而是應被回收的過期資料，凍結它等於讓警告永久靜音，真碰撞一併消音。


    **驗證要點**：改動後必須確認 `workspace-wipe-guard` 的計數行為**完全不變**、其 docstring 的保守語意宣告仍成立，以及 `session-registry-start-hook` 的候選集合大小不變。這三項是本次改動最容易被順手破壞的東西——修過濾的人很容易把它們一起改掉。'

### 路由判定（2026-09-09）：本票依判準屬框架問題，不應在本地當下修

`escalation-flow.md`〈介入判斷〉為兩條 AND，本票兩條皆符合：

| 判準 | 判定 |
|------|------|
| 抽象可攜性 | 符合——「共用讀取 API 的兩個消費端各自需要不相容的 active 定義，其中一個因此收到恆真警告」，替換專案名與路徑後完全成立 |
| 資產範圍 | 符合——`.claude/lib/dispatch_tracker.py` 與三個 `.claude/hooks/`，皆為通用資產 |

**在本地修的下場**（該節 Consequence 原文）：修復困在本地 commit 歷史不會傳播；下次 `sync-pull` 可能以上游未修的舊版覆蓋本地修復，且無 canonical 記錄可查。**此缺陷現存於每一個 consumer**——它們的 `is_file_under_dispatch` 都在拿全量清單。

#### 查重結果：屬既有 issue 的問題領域，不宜另建

已跑 `dedup`（關鍵字 `dispatch_tracker is_file_under_dispatch 派發記錄 過期`，38 則命中）。兩則相關，關係不同：

| issue | 關係 | 依據 |
|-------|------|------|
| `tarrragon/claude#54`〈hook 判定邏輯的隱含前提未驗證：誤報、誤清與 WARNING 不入 session context〉 | **同領域，本票為其新實例** | 該 issue 正文列的既有實例含「`dispatch_tracker` 清理鍵造成跨條目誤清」（刪除鍵值問題），本票是**讀取路徑**的同族缺陷；其正文明寫「這些 hook 在所有 consumer 的每個 session 執行。誤報消耗每個使用者的注意力」，本票正是一則誤報，成因正是一個未驗證的隱含前提（「`get_active_dispatches` 回傳的是 active 的」） |
| `tarrragon/claude#89`〈SubagentStop 於代理人轉入 idle 時即清空 dispatch-active.json〉 | **同檔案，方向相反，屬引用** | #89 是 entry 被清得太早；本票是 entry 在讀取時從不被過濾。兩者對同一份資料的存活期有相反的訴求，修任一方前須確認不會使另一方惡化 |

**依增長語意（同領域裂成多張才是失效），正確動作是對 `#54` 附加 observe，不是另建 issue。**

#### 現況：卡在授權，非卡在判斷

`observe` 屬外顯動作。本專案先前的用戶授權範圍限於建立 `#102`／`#103`／`#104` 三張，**不自動延伸至後續 observe**。因此本票停在此處等授權裁示，路徑已判定完成：

1. 對 `#54` observe，內容為本票 Problem Analysis 全文（三節根因 + 三消費端對照 + 四條被否決修法）
2. 依路徑 A close 本票，reason-note 指向 `#54`
3. 當下建驗證票，trigger 為「`sync-pull` 帶回含 fix-version 的版本後」

**授權未到之前不得改為在本地修**——那正是本節第一段所述的錯誤路徑。

#### 與 `0.1.0-W3-188` 的一致性

同一判準套用於 `188` 亦兩條皆符合（守衛涵蓋範圍窄於實際下游數，可攜；根源在 `.claude/hooks/` 與 `.claude/references/`）。**188 先前判定為「即時可修的下游同步」不走升級，該判定與本節判準不一致**——當時的依據是 `tool-output-trust-rules` 規則 6 的判定順序（建立端優先於驗證端），但那條規則回答的是「誰是權威」，不是「該在哪裡修」。**兩張票的路由應一併裁示**，不宜一張升級一張不升級。
