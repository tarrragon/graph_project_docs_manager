why: '編輯一個一天多前被派發過的檔案時收到警告「此檔案正在被背景代理人處理（ticket 0.1.0-W3-101）」，而該票早已完成。實查根因後發現三層事實，與第一直覺不同：


  第一，過期機制存在且該筆記錄早該被濾掉。dispatch_tracker.py 定義 TURN_ENDED_MAX_AGE_HOURS = 24 與 _is_dispatch_expired，而該筆記錄的 turn_ended_at 為 2026-09-08T07:57:45，命中當下已逾 30 小時。所以問題不是「登記從未過期」，也不是 TTL 設得太長。


  第二，過濾根本沒有被套用在這條讀取路徑上。get_active_dispatches 的實作是 state = _read_state(project_root); return state["dispatches"]——直接回傳全部記錄，不呼叫 _is_dispatch_expired。is_file_under_dispatch 迭代該清單比對檔名，因此會命中歷來每一筆曾宣告過該檔案的記錄。實測該檔現有 37 筆記錄。


  第三，函式名稱宣告了實作未提供的性質。名為 get_active_dispatches 卻回傳全部 dispatches；過期回收由獨立的 cleanup_expired 承擔，需呼叫端主動呼叫。實查消費端：worktree-auto-commit-hook.py 同時 import 兩者（有補償），main-thread-edit-restriction-hook.py 與 agent-commit-verification-hook.py 只讀不清（無補償）。這是驗證器量測維度與宣稱性質不同軸的形態（PC-GPD-009），發生在讀取 API 而非檢查器。


  後果是該警告對已派發過的檔案恆真。恆真警告的代價不是吵，是它會在真正發生碰撞時發出完全相同的訊號，而讀者此時已學會忽略它——真碰撞因此靜默通過。'

    判定 get_active_dispatches 該過濾還是改名：若過濾，其全部消費端的行為都會改變，須逐一確認沒有消費端依賴「拿到全部記錄」（session-registry-start-hook.py 的殘留代理人掃描很可能就是，該掃描的目的正是回報逾時未回收者）；若該掃描確實需要全量，則正確修法是保留 get_active_dispatches 的語意但改名為表達實情的名稱，另提供一個真正過濾的入口供警告類消費端使用。二擇一並記錄理由。


    無論走哪條，is_file_under_dispatch 都必須只比對未過期的記錄——它的用途是「這個檔案現在有人在動嗎」，過期記錄對該問題沒有資訊。
