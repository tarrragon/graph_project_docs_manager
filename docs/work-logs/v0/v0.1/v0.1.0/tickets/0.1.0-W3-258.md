### 兩例的可機械化程度差距，須分開下結論（並行 session 指出，PM 覆核成立）

原 how 第 2 問把兩例並列問「可機械判定的部分有多少」。**兩例的答案差距比原文暗示的大，合併下結論會讓難的那例拖住容易的那例。**

| 實例 | 觸發源 | 可機械化程度 |
|------|-------|------------|
| `0.1.0-W3-176` acceptance 因拆票失效 | **本票內部**（自己的拆分動作） | **高**——偵測點可綁在拆票這個動作上：拆票時把母票 acceptance 逐條標為待重評。不是「只能靠人」 |
| `0.1.0-W3-207` §2.2 因前置票合併失效 | **外部票**（他人的票合併） | **低**——原 how 提的比對法（`blockedBy` 票的 `where.files` 與本票 Solution 提及的識別符）**會漏掉此例**：`205` 的產出是**新建**一個檔案，`207` §2.2 是**內嵌宣告**同名列舉，識別符相同（`AttentionLevel`）但檔案路徑不同，`where.files` 交集為空。要抓到它得比對**識別符**而非路徑，而識別符須從 Solution 的程式碼區塊裡抽——已非 grep 層級 |

**因此本票的結論須分開下**：拆票路徑可綁動作、機械可行；前置票合併路徑先只落為派發前的人工檢查點，機械化另議。

### 第三個載體：同一張票內的欄位之間（2026-09-10 追加）

`0.1.0-W3-236` 的 `why` 寫「本票做裁定」，而今日追加的 Problem Analysis 寫「本票只產出證據、裁決歸 `210`」——**同一份票面並存兩套相反的分工敘述**。成因是 PM 收窄範疇時只追加了說明段，沒回頭改 `why` 與 `how`。

由下游讀者（`graph-project-docs-manager-86` 讀票準備調整 `210`）發現並直接來問，**不是任何檢查發現的**。

此例使本票的載體清單成為三種：**型別定義段**（跨票）、**驗收條件**（跨階段）、**同票欄位之間**（票內）。第三種的偵測條件與前兩種不同——它不需要跨票比對，兩段相反的文字就在同一個檔案裡。
