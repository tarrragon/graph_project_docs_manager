## Task Summary

complete/finish 被 identity-guard 擋下時（情境 1a 缺 --as、情境 4 身份不符），錯誤訊息需直接印出當前 who.current 的具體值，讓執行者不需額外查詢即可判斷下一步；並評估「--as 缺席時直接以 who.current 身份執行」的自動填補方案是否安全

## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### WRAP 三問

**W（Widen）候選方案**：
1.（採用）僅改訊息：情境 1a/4 直接印出 who.current 具體值與可複製指令，不改變任何放行/攔截邏輯。
2.（拒絕）--as 缺席時自動以 who.current 身份執行：會架空 ENFORCED_COMMANDS 要求明示宣告身份的初始設計（telemetry 顯示 96% 呼叫端已守規則，該規則本身不是問題）。
3.（拒絕，較弱）僅修 PM 派發 prompt 流程，要求派發前先查 who.current：無法防止人為疏漏重演（本次事件正是「沿用經驗寫死」的人為疏漏），訊息層的修復不依賴流程紀律。

**A（Attain distance）機會成本**：改動範圍侵限於 identity_guard.py 訊息字串與對應測試，不影響其他 ticket 排程；預估工作量小。

**P（Prepare to be wrong）**：最可能失敗點是訊息查值（_resolve_who_current）在極端情境（ticket 不存在、YAML 損毀）拋例外導致 deny 路徑本身失敗；對策：沿用既有 `_resolve_who_current` 的既有防禦（無法解析回 None），訊息組裝時對 None 走原有 fallback 文案，不新增例外面。
