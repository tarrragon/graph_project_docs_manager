### Rationale Chain
- 0.1.0-W3-226 why: 本專案 6 張 closed 票的 closed_by 為 `flutter_balance:W4-007` 形態（5 張裸形、1 張含版本號），每次 session-start 皆被 version-tracking-consistency-guard 判為非合法 Ticket ID，產出固定噪音。

實際語意（讀 6 張票的 close_reason_note 確認，非推論）：全部為「用戶裁示移交 flutter_balance 執行。標的 .claude/... 為共用框架資產，兩專案各自修改會造成 sync 衝突，故集中單一 session 處理」。即移交另一個 consumer 執行，不是取消。

三個可分離的缺陷：

D1 reason code 枚舉缺「移交」項：6 張全用 cancelled_by_user 記錄移交。需求沒有被取消，只是換執行者。日後盤點「哪些需求被放棄」會把這 6 項仍在進行的工作算進去。這是 PC-MON-002 行為模式的再現——但這次穿透的不是自由文字欄，是 reason code 枚舉：PC-MON-002 的修復把自由文字堵在 resolved_by，卻沒發現同一個「欄位語意不適用當下情境就選語意近似值」的逼迫會轉移到 reason code 上。

D2 建立端對 ALLOW_NONE 分支零驗證：lifecycle.py 的 elif reason_code in self._CLOSE_REASONS_ALLOW_NONE 分支只檢查 reason_note 非空，完全不驗 resolved_by 的格式。故 cancelled_by_user / requirement_vanished 下任意字串今天仍寫得進去（非存量問題，是現行可重現的洞）；而 guard 不分 reason code 一律要求 FULL_ANCHORED 或 none。兩端值域不一致且無阻擋時機。

D3 跨 consumer 票號不可解析：flutter_balance:W4-007 對本 repo 讀者無法導航，且跨 repo 無法驗存在性。這與 framework issue ref（owner/repo#N，可解析可驗證）性質不同，兩者不該以同一條放寬規則一併納入值域。

框架問題兩條 AND 判準（逐條套用，非憑印象）：
1. 抽象可攜——把本專案與 flutter_balance 換成任兩個 consumer，上述三項論述完全成立。共用框架資產的移交是本框架 multi-consumer 架構的結構性情境，非本專案特例。成立。
2. 根源在 .claude/ 通用資產——D1/D2 在 .claude/skills/ticket/ticket_system/commands/lifecycle.py，D3 在 .claude/lib/ticket_id_pattern.py 與 .claude/hooks/version-tracking-consistency-guard-hook.py。三者皆隨 sync 分發。成立。
