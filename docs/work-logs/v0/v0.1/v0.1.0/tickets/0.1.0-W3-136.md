## Context Bundle

**需求摘要**: 消解「框架建議的合併指令」與「框架守衛」的互斥，並讓被擋下的合併不再留下 `MERGE_HEAD` 殘局。

**兩端的精確位置（已驗證：`grep -rn "checkout main && git merge" .claude/` 與 `sed -n '165,205p'`）**

守衛端 —— `.claude/lib/commit_content_guards.py` 的 `_check_branch_verify`。關鍵三行的語意：

```python
project_root = get_project_root()
current_branch = get_current_branch(cwd=str(project_root))   # 判定依據：工作區在哪個分支
...
return [Finding("deny", "branch-verify", ...)]                # 保護分支上的非豁免路徑一律 deny
```

該函式轉呼 `branch-verify-hook.py` 的 `is_protected_branch` / `is_allowed_branch` / `is_exempt_path_on_protected_branch`，本身不看「這次要寫哪個 ref」，也不看是否處於 merge 中。

建議端 —— `git checkout main && git merge {branch} --no-edit` 的三個出處（`grep` 排除 `hook-logs/` 與 worktree 副本後）：

| 檔案 | 位置 |
|------|------|
| `.claude/hooks/agent-commit-verification-hook.py` | 兩處輸出，約 L501 與 L534 |
| `.claude/error-patterns/process-compliance/PC-039-worktree-unmerged-invisible-output.md` | 約 L46 |

`PC-039` 存在的目的正是防止 worktree 產出遺失——**它建議的復原指令本身被守衛擋著**，這一層矛盾要一併處理。

**本次事故的完整時序（已驗證，可作為測試案例的來源）**

1. 發起 session 在主 repo（HEAD=main）跑 `git merge --no-ff <worktree 分支>`
2. git 完成合併計算，寫入 index、建立 `MERGE_HEAD`（`1924d05d`）
3. 守衛在 ref 寫入階段回 deny，終端顯示 `fatal: ref updates aborted by hook`
4. 發起者依終端訊息判斷「合併沒發生」，轉去分析守衛，未回頭清理
5. `MERGE_HEAD` 與 10 個 staged 檔案（1107 insertions，含兩個新增檔）滯留主 repo
6. 三方 session 察覺後全數停手約一小時；期間票面自動提交（隔離索引路徑）仍推進 HEAD 三個 commit
7. 發起者確認來源 commit 仍被分支持有後執行 `git merge --abort`

**第 4 步是本票要消除的認知落差**：終端只顯示 ref 寫入失敗，沒有任何訊息指出 index 與 `MERGE_HEAD` 已被寫入。方案 (c)（改在合併前攔截）能根除此落差；方案 (a)(b) 則須確保 deny 訊息明確告知殘局存在與清理指令。

**約束**

- **不得放寬保護分支的原有意圖**：守衛要擋的是「在 main 上逐檔直接提交非豁免內容」，那個行為仍須被擋。acceptance 第 5 條的第二項即此回歸測試。
- **兩端必須同時改**。只修守衛會讓三處建議變成過期文件；只修建議會讓使用者失去唯一記載的合併路徑。
- `PC-039` 是 error-pattern，屬按需讀取層，修改時三明示可完整展開；`commit_content_guards.py` 的行為變更須依 `.claude/rules/core/skill-cli-sync-check.md` 檢查是否有下游文件描述其行為需同步。
- 本專案的 `.claude/` 為框架資產，變更會隨 sync 擴散至其他 consumer 專案——守衛行為的改動請以「其他專案的 main 分支保護不被削弱」為前提設計。

**未知（待執行者判斷，不採信本節推論）**

agent 命名 worktree（Agent 工具的 worktree 隔離模式產生，如 `worktree-agent-<hash>`）無法使用 `worktree merge <ticket-id>`，因該命令以票號解析 worktree。這是否屬本票範圍、或應另開票讓 `worktree` skill 支援 agent 命名，由執行者評估後於 Solution 記錄結論或登記 spawn request（acceptance 第 4 條）。

**PM 補充：守衛的實際涵蓋面比 why 段描述的更窄（2026-09-08，實查）**

why 段寫「同一份守衛換執行位置換答案」。實查後可以講得更精確——**這道守衛只擋得住已分歧的合併，而 fast-forward 完全不觸發它**。

**實證**：`ef1d18de`（`lib/screens/trace/trace_screen.dart` + `test/widget/app/shell_test.dart` 的變更）就在同一天直接落在 main 上，未被守衛擋下。`git rev-list --parents -n 1 ef1d18de` 只回一個 parent——它不是 merge commit，是 fast-forward。

| | fast-forward | 已分歧的合併 |
|---|---|---|
| 分支基準 | 就是當時的 main 頂端 | main 已前進 |
| 產生新 commit | **否**——只前移 ref | 是（merge commit） |
| 守衛執行時機 | **不存在**——沒有 commit 可檢查 | 有，且必然 deny |

**這對方案選擇的意義**：三個候選方案都要面對一個問題——守衛目前的實際效果不是「保護 main 不被非豁免內容污染」（FF 早就可以把 `lib/` 送進 main），而是「**擋下慢了一步的合併**」。基準沒動就 FF 過去、守衛看不到；基準一動就必須產生 merge commit、守衛必然擋下。而已分歧正是並行環境下無法避免的那一種。

換言之，守衛在**保護意圖**上已經有一個既存的大洞（FF），而它擋住的恰好是無害且必要的那類操作。方案設計時請把這一點納入：若只是讓 merge 通過，等於承認保護意圖本來就沒有透過這條路徑達成；若要真正保護 main，缺的是 ref 層而非 commit 層的檢查（FF 不產生 commit，只有 ref 更新）。**此判斷屬 PM 觀察，執行者應獨立驗證後再據以設計。**

**旁證：繞道的代價**（供評估「不修守衛而要求大家 rebase」是否可行）——本次事故中，來源分支在停手期間已與 main 分歧 28 個 commit。要走 FF 就得先 rebase，而 rebase 改寫 commit hash（既有引用失效），且 rebase 到 FF 之間的窗口一旦被其他 session 推進 main 就要重來。**繞道的成本隨並行度上升，不是常數。**

**PM 補充二：本票的派發路徑不受本票要修的 bug 影響（2026-09-08，實查）**

初看有循環依賴的疑慮——本票要修合併路徑，而執行者 `thyme-python-developer` 在 `agent-dispatch-validation-hook.py` 的 `IMPLEMENTATION_AGENTS` 清單內，被強制要求 `isolation: "worktree"`；worktree 交付又要靠本票要修的合併路徑才能落地。**實查後確認不成立。**

| Prompt 路徑分類 | isolation=worktree | Hook 行為 |
|---------------|--------------------|----------|
| **僅主 repo `.claude/`** | **不要求** | **放行（豁免 worktree）** |
| 主 repo `.claude/` + 非 `.claude/` | 無 | 阻擋（強制 worktree） |
| 僅非 `.claude/` | 無 | 阻擋（強制 worktree） |

本票的 `where.files` 全數在 `.claude/` 之下，命中第一列——**不需要 worktree，直接在主 repo 派發，沒有合併步驟，因此不觸及本票要修的路徑**。

**執行者請注意兩件事**：

1. **不要主動加 `isolation: "worktree"`**。加了反而會把交付放進一個需要合併才能落地的分支，而合併正是壞的那條路。
