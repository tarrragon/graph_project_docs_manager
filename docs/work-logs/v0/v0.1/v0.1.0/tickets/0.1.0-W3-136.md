  **互斥的兩端（皆已實查）**


  一端是建議。`git checkout main && git merge {branch} --no-edit` 出現在三處：`.claude/hooks/agent-commit-verification-hook.py` 的兩處輸出（約 L501、L534），以及 `.claude/error-patterns/process-compliance/PC-039-worktree-unmerged-invisible-output.md`（約 L46）——後者存在的目的正是防止 worktree 產出遺失。


  另一端是守衛。`.claude/lib/commit_content_guards.py` 的 `_check_branch_verify`（約 L173-199）取 `get_current_branch(cwd=str(project_root))` 判定分支，隨後對保護分支上的非豁免路徑一律回 `deny`。`git merge` 在 main 上會 stage `lib/` 等非豁免檔案，因此必然命中。


  **判定依據錯位**：守衛判的是「執行 hook 的工作區在哪個分支」，不是「這次要寫哪個 ref」。同一份守衛換執行位置換答案——代理人在自己的 worktree 內提交時，它看到的是非保護的 worktree 分支，直接放行；同樣內容在主 repo 上就被擋。


  **時機造成殘局**：守衛擋在 ref 寫入階段（`fatal: ref updates aborted by hook`），但 git 早已把合併結果寫進 index 並建立 `MERGE_HEAD`——被擋下的是 ref 寫入，不是合併過程。發起者看到 fatal 會以為合併沒發生，實際上 merge 狀態留在原地。


  **實測後果**：`MERGE_HEAD` 卡住期間，主 repo 上任何裸 commit 都會把該次合併的 staged 檔案一併送出（本次為 10 個、1107 insertions）。三方 session 全數停手等待，期間票面自動提交仍推進了 HEAD 三個 commit（該路徑走隔離索引、不檢查 `MERGE_HEAD`，另案處理）。


  **繞道不普遍可用**：票號命名的 worktree 可走 `worktree merge <ticket-id>`；Agent 工具的 worktree 隔離模式產生的是 agent 命名 worktree，該命令回報找不到對應 worktree，無替代路徑。'
