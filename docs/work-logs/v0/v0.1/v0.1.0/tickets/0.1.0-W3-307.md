## Problem Analysis
### 問題根因

第一輪三張測試皆為正向使用 frame（拿條文處理真實 issue，記錄它答不出的地方）。本票測的是相反的東西：**條文答得出、而答案可被構造成錯的**。

直接原因：改版條文（`escalation-flow.md`〈修法時點分離〉）的豁免閘門由四問 + 一條合成規則 + 一張二軸擴散面表構成。四問中有三問的字面允許作答者選擇「以什麼為證據」，而條文沒有限定所選證據必須與該問所問的對象同軌。

影響範圍：條文以「已測過」身分隨 sync 擴散至全部 consumer；通過閘門的票在票面上與嚴謹判定完全不可分辨。

### 影響範圍

受影響檔案：`.claude/skills/framework-issue/references/escalation-flow.md`〈修法時點分離：發現票何時能寫定修法〉全節。

**已驗證的事實**（本票實際執行的觀測）：

| 事實 | 觀測手段 | 結果 |
|------|---------|------|
| `should_exclude()` 對 hooks／rules／skills 定義本體皆為 False | `python3` 直接呼叫 `lib.sync_exclude_manifest.should_exclude` 於 5 個代表路徑 | 5/5 皆 False（與 `0.1.0-W3-301` 量測一致） |
| 本 consumer 的 `.claude/hooks/` 有機械訊號 | `ls .claude/hooks/tests` | `test_bare_commit_guard_hook.py` 存在 |
| `bare-commit-guard-hook.py` 未偵測 `-i`／`--include` | `grep -n` 該檔，第 298 行 `any(tok in ("--", "--only", "-o") ...)` | 確認遺漏；而 `bash-tool-usage-rules` 規則七明列 `--include`／`-i` 為禁用 |

**仍未驗證的假設**：本票構造的三張票皆為「可寫出」而非「已送出」——未實際建票、未實際送 issue。構造的有效性在於票面逐條對照條文字面成立，不在於它被誰接受過。

### 相關 Error Pattern

與 PC-165（測試綠燈不等於 runtime 正確）同型：本票揭露的是「判準綠燈不等於判定正確」——同一結構，載體由測試換成條文。另與 `escalation-flow.md` 自身引述的 `163/164 → 316/320` 案例同型（構造二即其可複製版）。

## 重現實驗結果
### 實驗方法

本票的「實驗」是對抗構造：以條文字面為規則書，嘗試產出一張**逐條合規、四問全綠、二軸表落在第一檔、而修法實質未驗證**的票。判定標準不是觀感，而是能否對每一問給出一個字面成立的答案，以及該答案的鑑別力是否涵蓋該問所問的對象。

三個指定攻擊面各獨立嘗試：(a) 消費端拆分後的合成規則；(b) 二軸表的非機械軸；(c)「反例已試」的最低標準。

### 實驗執行

**共用前提（三個構造都用到，已實測）**：

```
should_exclude('.claude/hooks/bare-commit-guard-hook.py')            -> False
should_exclude('.claude/rules/core/quality-baseline.md')             -> False
should_exclude('.claude/skills/framework-issue/references/escalation-flow.md') -> False
ls .claude/hooks/tests/test_bare_commit_guard_hook.py                -> 存在
ls -d .claude/skills/framework-issue/tests                           -> 存在
```

即：這些位置一律落在「隨 sync 擴散」一側（二軸表第 1 列不可達），但本 consumer 內**都有機械訊號**，故一律由第 2 列判為**第一檔**。第一檔一旦成立，「使用者群已觀測」即可合法填「不適用」，合成規則放行。**跨 consumer 這一維在此被完全移出檢查範圍，而移除它的依據（本地有測試）與它所問的事（別人是否在用）無關。**

#### 構造一（攻擊面 a + b）：正交事實升格為免答券

**可寫成的真實票**

- **action**：擴充 `bare-commit-guard-hook.py` 的 index-discarding 形式偵測，納入 `-i`／`--include`
- **target**：`.claude/hooks/bare-commit-guard-hook.py:298`（`_is_index_discarding_form`）
- **why 要點**：`bash-tool-usage-rules` 規則七明列四項禁用形式（`-- pathspec`／`--only`／`-o`／`-i`），強制層只實作前三項；`-i` 會把 index 中他人已 staged 的檔案一併送出，並行環境下與 `--only` 同等危險。

**四問作答（逐條字面成立）**

| 問 | 答 | 依據 |
|----|----|------|
| 執行條件已觀測 | 是 | 實跑該 hook，餵 `git commit -i <path>` 的 PreToolUse payload，實測放行（exit 0），非推定 |
| 使用者群已觀測 | **不適用** | 擴散面第一檔。判定依據：`should_exclude()`＝False，但本 consumer 內有機械訊號（`.claude/hooks/tests/test_bare_commit_guard_hook.py`，修法錯誤時紅燈）→ 二軸表第 2 列。依據與擴散面判準同址可查，符合條文對「不適用」的全部要求 |
| 反例已試 | 是 | 修法前餵 `-i` payload 得 exit 0、修法後得 exit 2；前提為錯（regex 未生效）輸出即不同。非沉默、非與「本來就沒問題」同形 |
| 範圍已量 | 是 | 1 檔、1 條判斷式、既有測試案例數由 `grep -c` 量到 |

合成規則：執行條件＝是 ∧ 使用者群＝不適用 → 消費端已觀測＝是。**四問全綠 → 豁免 → 發現當下寫定修法。票面完全合規。**

**未驗證之處**：`-i` 在其他 consumer 的用法零觀測。若任一 consumer 的票務／提交腳本正以 `git commit -i` 實作限縮提交（本專案沒有，但條文沒要求去看），此修法一旦 sync-push 即硬擋該 consumer 的全部提交路徑。**「使用者群已觀測」問的正是這件事，而豁免它的事實是「本地有測試」——本地測試對其他 consumer 的呼叫端鑑別力為零。**

**次生缺陷（順序循環）**：擴散面表的入口句是「三問任一為否時，**先依下表判定擴散面歸檔**」，即擴散面應在出現「否」之後判定；但「使用者群已觀測」列又說「擴散面判定為第一檔時填不適用」，要求擴散面在作答之前判定。兩種讀法都成立：先判擴散面則永遠不出現「否」，第二檔處置（issue 待裁列）成為不可達分支。這正是條文自己所寫「一個兩種讀法都成立的判準比沒有判準更糟」的實例。

### 實驗發現

**已驗證的事實**：三個攻擊面各構造出一個通行證案例，皆逐條對照條文字面成立，皆可直接寫成一張真實的票。條文在這三處**沒有失效——它正確地放行了三個未驗證的修法**。

**根因收斂為兩句**：

1. **二軸表第 2 列把一個與「使用者群」正交的事實（本地有機械訊號）升格為該問的免答券。** 這一列不是疏漏，是刻意加的——條文明寫「單靠 `should_exclude()` 會使第一檔恆空，須與機械訊號軸並用」。為了讓第一檔非空而引入的軸，恰好吃掉了跨 consumer 這一維。**第一檔從「恆空」直接翻到「幾乎恆滿」**（凡本 consumer 有測試／hook／CI 覆蓋的位置皆入第一檔）。
2. **「反例已試」只要求觀測有輸出差異，未要求該差異與修法的承重前提相關。** 加上「修法**或**其前提」的選言，作答者可自選最容易證偽的那一個。

**仍未驗證的假設**：本票未實際建票送審，故未驗證「這樣的票在人工複核下是否會被擋」。但條文的作用點正是取代人工複核——若結論依賴複核者眼力，該條文即未提供條文所承諾的判準。

## Solution
### 分析結論

條文的閘門可被完全合規地穿過。三個構造各自成立，且彼此獨立（封掉其中一個不影響另兩個）。**不能以「條文大致穩健」收尾**——本票的產出是三張可以真的寫出來的票。

缺陷集中在兩處，各有一個最小修補位置。

**方案 A：四處字面修補（如上表）**
