分離 framework-issue 升級流程中的發現時點與修法決定時點

---

## Problem Analysis
### 問題根因

發現問題的時點與決定修法的時點在同一個動作裡完成。`ticket create` 要求 `--action`（動詞）與 `--target` 必填、`--type` 預設 IMP，因此「發現即建立」在預設路徑上等於「發現即講出一個修法動詞」；`quality-baseline.md` 規則 5 的優先級對應表把「高」直接映到 IMP Ticket，再加一層推力；`escalation-flow.md` 規範何時升級、怎麼判、寫到哪，未規範修法在哪個時點定案。三者疊加的後果是：修法寫進 `title` 與 `how` 之後，被每個下游讀者當成已定案的前提讀，不再被當成待驗證的判斷——它從未被證明錯，也從未被檢查，而在票面上與一個已驗證的決定不可分辨。

**由實驗直接得到的一項設計輸入（非事先預設）**：既然健康形態的成本是一個欄位而非一張票，時點分離的單位應定在欄位層，不在票層——這使「小型發現被逼進完整分析流程」的成本反對意見在多數情形下不成立。

### 條文形狀：適用與豁免的判準

**一、時點分離的單位是欄位，不是票。** 實驗已顯示健康形態（修法寫成待驗證＋停手條件）在本專案已有 12 張票自發採用，成本是一個句子。故條文不要求「發現時多開一張分析票」，要求的是發現票寫入修法時同時寫下該修法的證據狀態。

**二、豁免軸是證據狀態，不是問題規模。** 「修法看似顯然」不構成豁免依據。可在發現當下寫定修法的條件是三問皆為「是」：

1. **消費端已觀測**：修法要改的東西，誰讀它、在什麼條件下執行，是已觀測而非推定？
2. **反例已試**：是否做過一個「修法若錯就會失敗」的觀測，而不只是「修法看起來能解掉徵狀」？

- **若判準直接豁免它，「修法看似顯然」為什麼不是可信的豁免依據？** 因為此處的「顯然」正是未觀測消費端的產物。把 `Spawn Requests` 加進清單看似顯然，但若該清單從未被任何自檢實際消費，修法的效益為零；若消費端對未列項的處置本來就是忽略，修法同樣無效；若該清單是刻意排除「代理人不該自行寫入的章節」，修法還是錯的。三種情形在發現當下的證據下不可區分，而它們都通不過第一問。**「顯然」是一個關於消費端的斷言，不是關於問題規模的斷言**——這正是把豁免軸定在證據狀態而非規模的理由。該票實際上已以此形態建立（why 明寫「兩種情形在票面現有證據下不可區分」），可作為判準與既有正確實務一致的旁證。
