## Task Summary

依 0.1.0-W3-311 的證據裁決 owner 驗證器的修法方向，並處置 ticket-intake owner 識別行的失效範例

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`section_comment.py` 的 `validate_owner`（`OWNER_FORMAT_RE`，`init`／`add`／`transfer-owner` 共用）要求 owner 尾碼為純數字，而 owner 值的供應端是 session 短名，尾碼實測為兩碼十六進位。**但這只是三個獨立缺陷之一**——本票的核心發現是票面「三方向互斥、擇一」的框定不成立：

| 票面方向 | 實際治的是什麼 | 是否被其他方向涵蓋 |
|---|---|---|
| A 驗證器（regex） | 逐 session 命中率 | 否，B 與 C 皆不治 |
| B 取值管道 | 子代理人取不到任何 owner 值 | 否，A 完全不觸及 |
| C 範本失效範例 | 照範本填必然 exit 3 | C 的內容由 A 決定，不是 A 的替代方案 |

三者的交集只在症狀（都降級為 `observe`），成因互不重疊。

### 影響範圍

**已驗證的事實**（承接 `0.1.0-W3-311`，本票另行複核）：

1. owner 的三個讀取端全為 `startswith(f"{prefix}-")`，無解析無排序——`section_comment.py` 的 `_discover_owned_issue_numbers_by_prefix`、`todo --consumer` 的列篩選、`session-start-issue-check-hook.py` 的擁有檢查。本票以 grep 獨立複核，與派發者提供的證據一致。
2. `validate_owner` 的三個呼叫點為 `cmd_init`／`cmd_add`／`cmd_transfer_owner`；`cmd_update` 不驗證 owner（沿用既有 comment 的 owner）。
3. `_project_owner_prefix()` 在 `section_comment.py` 與 `session-start-issue-check-hook.py` 各有一份同 heuristic 實作（git common dir 目錄名 kebab 化），推導失敗時回退 `Path.cwd().name`。
4. 失效範例不只 `ticket-intake.md` 一處：`comment-as-section-protocol.md` 的 owner 識別格式段與 `validate_owner` 的錯誤訊息，皆以某一個 consumer 的字面值作範例。

**仍未驗證的假設**：

- session 短名尾碼的產生規則無任何本機可讀來源，「兩碼十六進位」為觀測歸納。本票的修法選擇刻意不依賴此規則（見 Solution 對「收成十六進位」的否決理由）。
- 各 consumer 的 git checkout 目錄名是否皆等於其慣用 owner 前綴，無管道判定。此為錨定變體的主要風險，已列入實作票的要件。

### 相關 Error Pattern

`ARCH-BAL-023`（識別欄位無共用契約，消費端靜默漏檢）：寫入端與讀取端各自自洽、兩者之間缺約定，與本現象同構。本票的修法選擇正是消除該形態——令寫入端改用讀取端已在用的同一個判準函式。

### 實驗發現

**已驗證的事實**：

1. 錨定候選**保住了現行純數字尾碼兼任的過濾能力**：代理人角色名、存量代理人型別名、含底線值、裸 uuid 片段全數維持被擋。原先「放寬 regex 會連代理人角色名一併放行」的顧慮，對錨定形態不成立——該顧慮成立於單純放寬尾碼字元集的形態（`framework-issue-curator` 會通過）。
2. 錨定候選**新增一項現行沒有的阻擋**：他 consumer 的 owner 值在本專案下執行時被擋（第 13 列）。這阻斷了冒名，同時也阻斷了跨 consumer 的 `transfer-owner` 移交，須有逃生口。
3. 錨定候選**使 uuid 前綴形態一併通過**（第 6 列）。該形態子代理人可從 scratchpad 路徑自行推得，且觀測流中已出現過。這是本票判定「A 與 B 不可分開出貨」的直接依據——錨定若先於取值管道定案落地，同一前綴下會並存兩個尾碼命名空間。
4. 存量 `thyme-python-developer-e2e` 在錨定下仍不合法（單純放寬則會自動合法）。因驗證只在寫入端，存量讀取不受影響。

**仍未驗證的假設**：各 consumer 的 checkout 目錄名是否等於其慣用 owner 前綴。本探針中他 consumer 的推導前綴是依其 owner 值反推填入的，非實測該機器上的 `git rev-parse` 輸出——無管道取得他 consumer 的目錄名。此為錨定的唯一回歸風險，已寫入實作票的要件（推導失敗或不符時降級為格式檢查，不得硬擋）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 裁決一：修法方向為「錨定本專案前綴」，不是單純放寬尾碼

`OWNER_FORMAT_RE` 改為「前綴須等於 `_project_owner_prefix()` 推導值，尾碼為非空 `[a-z0-9]+`」，即 `^<推導前綴>-[a-z0-9]+$`。

**選它的理由**：owner 的三個讀取端全為前綴比對，尾碼從未被任何讀取端解讀；錨定使寫入端與這三個讀取端共用同一個判準函式，而非另立一套只有寫入端執行的規則（`ARCH-BAL-023` 形態的解消）。實測顯示它同時保住現行過濾能力（代理人角色名、含底線值、裸 uuid 片段仍被擋），且把過濾判準從「尾碼字元集」升級為「必須是自己這個 consumer」。

**不選其他兩種放寬法**：

| 候選 | 否決理由（實測依據） |
|---|---|
| 尾碼放寬為 `[a-z0-9]+`（不錨定前綴） | `framework-issue-curator`、`thyme-python-developer-e2e` 會通過，現行兼任的代理人角色名過濾器消失。此即票面顧慮「放寬 regex 會連代理人角色名一併放行」的成立場合 |
| 尾碼收成兩碼十六進位 | session 短名的產生規則在任何本機可讀來源皆查無記載，「兩碼十六進位」是 13 個觀測值的歸納而非規格。以未經證實的產生規則作驗證判準，規則一變即再次全面失效；且 `blog-cd` 這類非兩碼形態仍被擋 |

**平行 session 提案的複核結論**：該提案（錨定前綴）未經本票複核不得當前提，本票已以 14 值探針實跑複核，判定**採用**，但附三項它未涵蓋的後果（見裁決三）。

### 裁決二：票面「三方向互斥、擇一」的框定不成立

據實記錄，不為符合票面而硬選：

| 方向 | 與其他方向的實際關係 |
|---|---|
| A 驗證器 | 承重項。治逐 session 命中率 |
| B 取值管道 | **獨立缺陷，A 完全不觸及**。子代理人無任何管道取得 owner：`ListAgents` 不可得、`pm-registry.json` 無序號欄。本次派發即為實例 |
| C 範本失效範例 | **不是替代方案，是 A 的附屬後果**。C 的內容由 A 決定，且 C 單獨執行不可行——現行驗證器下不存在「既合法又對應真實 session 名」的值可寫進範例，照 C 改只能在謊報與占位符之間二選一 |

**A 與 B 不可分開出貨**：錨定會使 uuid 前綴形態（`<前綴>-dcead428`）一併通過，而該形態與 PM 用的短名尾碼（`-5d` 形態）屬兩個不同命名空間，觀測流中已出現過該形態的 owner 值。A 若在 B 定案前單獨落地，等於主動製造一個新的不一致，而不只是沒治好舊的。故實作票 `0.1.0-W3-320` 設 `blockedBy 0.1.0-W3-319`。

### 裁決三：`ticket-intake.md` 失效範例的處置（定案）

owner 識別行的範例值改為占位形態（本專案 kebab 前綴 + session 序號 + 前綴須等於 CLI 推導值 + 序號取 `ListAgents` 首行名稱），**不寫任何具體 consumer 的字面值**。

理由有二，第二項比第一項射程更廣：該值現在會 exit 3；且範本是跨 consumer 同步的資產，錨定後寫死的字面值在其餘每一個 consumer 都會被主動拒絕。同一處置適用 `comment-as-section-protocol.md` 的 owner 識別格式段與 `validate_owner` 的錯誤訊息（後者改印當下推導出的前綴）。

**過渡期文字**（A 落地前）須明寫「尾碼含字母的 session 會被 exit 3 擋下，此時降級 `observe`」，否則過渡期又是一次照範本填、照樣失敗。

### 實作端待處理項（已寫入 `0.1.0-W3-320` 的 how.strategy 與 acceptance）

1. `_project_owner_prefix()` 推導失敗時回退 `Path.cwd().name`。該函式現行只用於讀取路徑，推錯僅漏篩；移到寫入路徑後推錯會**拒絕合法 owner**。要求：推導失敗時降級為格式檢查，不得硬擋。
2. 跨 consumer 的 `transfer-owner` 會被擋，需顯式逃生口或該子命令不套用錨定。
3. 錯誤訊息與兩份 references 的範例值須去除具體 consumer 名。
4. 存量 owner `thyme-python-developer-e2e` 在錨定下仍不合法（單純放寬則自動合法）。驗證只在寫入端，存量讀取不受影響，不在實作票範圍，亦不另建票——是否遷移取決於 `0.1.0-W3-319` 的命名空間結論。
