### Task Reference
- 0.1.0-W3-138 what: 修正 hook 完整性檢查把非 settings.json 註冊的 hook 誤報為未註冊

### Rationale Chain
- 0.1.0-W3-138 why: SessionStart 的 hook 完整性檢查把 `git-ref-transaction-content-guard.py` 報成「未註冊」，**而它的註冊是完整的**。三個 session 在同一天被這一行誤導。

**註冊鏈實查**：

```
$ grep -c "git-ref-transaction-content-guard" .claude/settings.json
0
$ cat .git/hooks/reference-transaction
#!/bin/sh
# git-ref-transaction-content-guard shim -- 由 .claude/hooks/git-ref-transaction-guard-install-hook.py 產生，勿手動修改。
```

`settings.json` 註冊 installer → installer 產生 `.git/hooks/reference-transaction` shim → shim 呼叫 guard。**整條鏈自洽，且 installer 本身在 settings.json 裡、SessionStart 時回報 `[OK]`。**

**檢查器量的是「檔名在不在 settings.json」，宣稱的是「有沒有被註冊」。**更難看的是：**宣稱的答案就在它自己讀的那個檔案裡**——鏈的起點（installer）正是它唯一的資料來源。它不是資訊不足，是沒有沿著手上的資料往下走一步。

**三個獨立受害者（同日）**：一個 session 整個工作期間據此預設該 guard 未生效，並因此提出一個已被反證的曝險擔憂；另一個 session 讀過該行、歸類為背景雜訊，事後自陳「沒有踩到只是因為我沒往下推，不是因為我判斷正確」；第三個同樣未質疑。

**實際風險**：該 guard 是隔離索引提交（`commit-tree` + `update-ref`）唯一的內容檢查點——傳統 `pre-commit` 對該路徑零命中，其檔頭有 git 2.50.1 實測表為證。若有人據「未註冊」推論「隔離索引提交未經檢查」，會誤判所有走 `ticket track commit` 的框架資產提交為未受檢，進而可能繞開或重複建置防護。

**檔名同樣在說太大的話**：`hook-completeness-check` 宣稱檢查「完整性」，實際量的是 settings.json 涵蓋率。只改訊息不改檔名，等於把不實陳述從輸出搬到檔名——而檔名的血緣更廣（settings.json 註冊項、`.claude/hook-logs/` 同名產物目錄、引用它的文件）。
