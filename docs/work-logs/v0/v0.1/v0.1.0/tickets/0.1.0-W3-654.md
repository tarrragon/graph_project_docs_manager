## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
改寫 `check_worklog_completed` 內的 pending/in_progress 掃描邏輯：新增
`collect_ticket_scope_groups(tickets_dir, version)`，依 status 與 frontmatter
`scope_blocker` 欄位分三組——`in_progress` 一律阻擋；`pending` 且非空
`scope_blocker` 阻擋；`pending` 且無 `scope_blocker` 進 `overflow`（前移清單，
不阻擋），並用新函式 `compute_overflow_target_version` 計算目標版本（IMP +
`what` 欄位首詞屬新功能動詞「實作/新增/建立/開發」→ minor+1，其餘 → patch+1，
鏡射 ticket skill 內部溢出版本判斷函式的分類規則）。`what` 首詞取代原本的
`--action` 參數——ticket frontmatter 不持久化 create 時的 `--action` 原始值，
僅能以 `what` 欄位（預設值「動詞 + 目標」）近似推斷，已知簡化並於程式
docstring 註明。

新增 `finish` 子命令：先呼叫 `migrate_overflow_tickets`，對前移清單逐張
呼叫 `ticket migrate <source_id> <target_id> --version <target_version>`
（獨立 subprocess，經 `_run_ticket_migrate` 包一層供測試 mock）；目標版本
須已在 `docs/todolist.yaml` 登記（讀取 `versions[].version` 清單比對），
未登記時整批阻擋且不自動登記；任一張失敗即中止不留半搬狀態。`finish` 與
`release` 共用主體流程（`elif args.command in ("release", "finish")`），
`finish` 僅多一道 Step 0 前移步驟，其餘 preflight/文件更新/git 操作邏輯不變。

未跨 skill import ticket skill 內部 `lib/version.py`（版本溢出計算另行在
version-release skill 內以 `compute_overflow_target_version` 鏡射實作），
理由：version-release 為獨立 uv single-file script，安裝版走
`uv tool install` 進 site-packages，跨 skill import 會引入路徑不相容風險，
兩個函式邏輯簡單（純算術 + 分類），維護成本低於 import 耦合成本。

文件同步：SKILL.md 新增 `finish` 子命令說明、〈發版判準：blocker 阻擋、
其餘前移〉章節（含範例輸出）；references/release-workflow-details.md 的
Step 1 pre-flight 偽程式碼與檢查項清單同步改寫；CHANGELOG.md 記錄
2.2.0；metadata.version 同步升版。
