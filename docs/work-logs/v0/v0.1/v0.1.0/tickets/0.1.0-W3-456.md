### 用戶原話與派發 context（PM 寫入，2026-09-16）

**用戶原話**
> 我設想可能遇到的狀況是，當我跟別人協作或者接手舊專案時，我需要做專案分析盤點，但是我不可能開 ticket 系統，這種協作專案或者已經上線的專案應該有他自己的任務分派系統比如 asana 或者使用 slack ，那我應該需要一個報告或者一個 todo 清單或者一個 excel 表去列出來或者可以盤點修復進度，我們需要設計這個替代性的系統，這應該是剛好找到我們目前框架中缺失的一部分功能

**發現脈絡**
- 0.1.0-W3-452.1 WRAP 複核 foundation-design FD-13a 時，判定「缺 ticket 系統時，應建票內容記入降級記錄」是新判準。
- PM 以 AUQ 詢問落點偏好，用戶回覆上段。
- 草稿見 0.1.0-W3-452.1 Solution；待落檔票為 0.1.0-W3-455。

**要回答的問題**
1. 框架內哪些地方假設 ticket 系統存在，且在「對方有自己的任務系統」時不成立？請盤點（至少含 foundation-design、version-bootstrap 的建票步驟、component-contract-design step-5）。
2. 替代產物的形態：報告、todo 清單、表格或匯出格式。需求條件：
   - 讓對方系統能匯入或照抄；
   - 能追蹤修復進度；
   - 能表達先後順序（取代 blockedBy）。
   用 WRAP 評估。
3. 替代產物與本框架 ticket 的對應關係：哪些欄位必留，哪些可省。
4. 框架問題判準：依 `.claude/skills/framework-issue/references/escalation-flow.md` 的兩條 AND 判準逐條套用並記錄，再跑 dedup，記錄關係判定（重複／切分／引用）。

**約束**
- 本票只做分析與設計建議，不改 skill 檔。
- 屬用戶偏好的欄位或形態選項，明標後交 PM 以 AUQ 詢問。

## 重現實驗結果
### 實驗方法

本題不是 bug，「重現」是量測建票假設的實際分布，確認缺口不是個案。三組唯讀命令，皆於 2026-09-16 main 工作樹執行：

1. `git grep -l -E "建票|ticket create|blockedBy" -- .claude/skills/`（排除 `ticket` skill 本身）列出命中檔案。
2. 同 pattern 加 `':!*CHANGELOG.md' ':!*.py' ':!*.json'`，列出正文命中行並逐行分類。
3. 補掃 `開票|補票|前置票|決策票|Ticket ID`，抓第 2 組 pattern 漏掉的同義寫法。

另讀三份宣告前置條件或接手流程的正文：`foundation-design/SKILL.md`〈移植前置條件〉、`version-sequencing/SKILL.md`〈移植前置條件〉、`doc/references/legacy-code-workflow.md`〈前置步驟〉。

### 實驗執行

| 組 | 觀察 |
|----|------|
| 1 | 65 個檔案命中（含 CHANGELOG、程式碼、測試） |
| 2 | 正文 140 行命中；逐行歸為甲（交付給被操作 repo 的工作項）、乙（本框架執行者自身的派發與編排）、丙（欄位設計範例或已抽象化） |
| 3 | 補出 7 處同義寫法：`component-contract-design` 三處（前置票、決策票、UX 審查補票）、`dart-style-guardian` 兩處（前置票、另開票）、`foundation-design/references/handoff-mode.md`（另開票）、`parallel-evaluation`（報告表 Ticket 欄強制） |

正文三份的實際寫法：

- `foundation-design`：前置條件第二項要求「被盤點的 repo 有具 `blockedBy` 語意的 ticket 系統」，降級段把應建票內容「直接記入降級記錄本身」，沒有欄位、順序與進度的規格。
- `version-sequencing`：前置條件同上；降級段寫「建一張補齊該基礎設施的票」，缺的正是 ticket 系統，這個處置在結構上無法執行。
- `doc/references/legacy-code-workflow.md`：接手舊專案流程把「`/ticket create` 可正常建立 ticket」列為步驟 0 之前的必要前置；`.claude/references/multi-system-tracking-sync.md` 將「只在核心文件記錄，不建立 Ticket」列為禁止行為。

### 實驗發現

**已驗證的事實**

1. 甲類建票點共 33 處（清單見 Solution〈受影響建票點清單〉），分布在 9 個 skill 與 1 份 reference。
2. 宣告前置條件的只有 `foundation-design` 與 `version-sequencing` 兩處。`component-contract-design` 有 11 處建票指令（step-5），卻沒有 ticket 系統前置條件；它唯一的降級條款處理「執行者沒有 Bash」，不處理「repo 沒有 ticket 系統」。
3. 框架裡專為「接手他人程式碼」寫的流程（`legacy-code-workflow`）把安裝本框架 ticket 系統列為強制前置，和用戶描述的情境直接衝突。
4. `.claude/skills/doc/templates/legacy-assessment-report-template.md` 已有進度欄（每步驟的狀態、完成日期、commit）和「後續行動」表，但表的追蹤方式欄只接受 Ticket 或 Proposal ID，沒有外部系統編號、順序或對帳欄。
5. `tdd/references/portable-design-boundary.md`〈可攜式約束規則〉已經把 `/ticket` CLI 抽象成「任務系統」。概念層的抽象有先例，只是沒有產物規格。
6. 規則層有兩處把合法載體限定為 ticket：`decision-trigger-binding` 規則 2（合法 trigger 限 ticket ID）與品質基線規則 5（發現即建票）。

**仍未驗證的假設**

- Asana、Jira 的 CSV 匯入是否支援依賴欄：未對照官方文件。因此下方設計不依賴匯入工具保留依賴，順序改用整數欄表達。
- 接手或協作情境的實際發生頻率：無樣本，只有用戶的描述。
