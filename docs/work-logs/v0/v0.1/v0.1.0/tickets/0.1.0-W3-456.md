### 實驗發現

**已驗證的事實**

1. 甲類建票點共 33 處（清單見 Solution〈受影響建票點清單〉），分布在 10 個 skill 與 1 份 reference。
2. 宣告前置條件的只有 `foundation-design` 與 `version-sequencing` 兩處。`component-contract-design` 有 11 處建票指令（step-5），卻沒有 ticket 系統前置條件；它唯一的降級條款處理「執行者沒有 Bash」，不處理「repo 沒有 ticket 系統」。
3. 框架裡專為「接手他人程式碼」寫的流程（`legacy-code-workflow`）把安裝本框架 ticket 系統列為強制前置，和用戶描述的情境直接衝突。
4. `.claude/skills/doc/templates/legacy-assessment-report-template.md` 已有進度欄（每步驟的狀態、完成日期、commit）和「後續行動」表，但表的追蹤方式欄只接受 Ticket 或 Proposal ID，沒有外部系統編號、順序或對帳欄。
5. `tdd/references/portable-design-boundary.md`〈可攜式約束規則〉已經把 `/ticket` CLI 抽象成「任務系統」。概念層的抽象有先例，只是沒有產物規格。
6. 規則層有兩處把合法載體限定為 ticket：`decision-trigger-binding` 規則 2（合法 trigger 限 ticket ID）與品質基線規則 5（發現即建票）。

**仍未驗證的假設**

- Asana、Jira 的 CSV 匯入是否支援依賴欄：未對照官方文件。因此下方設計不依賴匯入工具保留依賴，順序改用整數欄表達。
- 接手或協作情境的實際發生頻率：無樣本，只有用戶的描述。

## Solution
### 結論摘要

建議形態：新增一份**盤點工作項表**（worklist）規格與範本，形態是一行一項的扁平表，順序用整數「順序層」表達，另設「外部編號」與「對帳紀錄」追蹤進度。這屬零工具加改造既有：不寫 CLI，也不串接對方系統的 API。

各 skill 不逐點改寫。做法是在各自的前置條件或降級段加**一條讀法映射**：「無 ticket 系統時，本 skill 的建票讀作『在工作項表新增一列』，`blockedBy` 讀作『前置項與順序層』」。這樣 33 處建票點大多不必個別改文。

### 錨點

客戶是做盤點的人，以及接收盤點結果的對方團隊；對方已經有自己的任務系統。產物要同時滿足三件事：

1. 能匯入或照抄進任何任務系統，包括只有文字的 Slack；
2. 交出去之後仍能對帳修復進度；
3. 不要求對方安裝本框架的任何東西。

不做的代價：盤點結果沒有落點，只好寫進降級記錄的自由文字，或違規建立本框架 ticket。前者的缺口在盤點表上看起來和已完成一樣。

### W：選項（三類涵蓋）

| 選項 | 內容 | 類別 |

| B 盤點工作項表規格 | 獨立規格與範本：扁平表、固定欄位、整數順序層、外部編號、對帳紀錄；各 skill 以讀法映射指向它 | 零工具（加少量改造既有） |
| C 純 todo 清單 | markdown `- [ ]` 清單，依順序排列 | 零工具 |

**反向思考**：假設「根本不需要替代產物，交一份報告就好」。報告只能回答「發現了什麼」，回答不了「修到哪了、先修哪個」，而後兩者正是用戶原話要求的（「可以盤點修復進度」）。反向論述不成立。

**假選項檢查**：A 與 B 可退化為同一方案，差別只在載體位置，B 的欄位規格可以直接套進 A 的報告。因此 A 併入 B，改稱「B 的範本由接手評估報告引用」。實質選項剩 B、C、D、E、F 五個。

### 產物形態建議（B）

**檔案組成**（單一文件，放在被盤點 repo 的決策文件旁；對方不收進版控時，另存為交付檔）：

1. **摘要**：盤點範圍、日期、項目總數、依順序層統計的件數。
2. **工作項表**：一行一項，每格單行，欄位見下表。這張表就是可直接貼入試算表或轉 CSV 的區塊。
3. **項目詳情**：每項一小節，放多行內容（驗收條件逐條列、證據、影響檔案）。表格中只放摘要。
4. **對帳紀錄**：一次對帳一列，記日期、對帳者、各狀態件數、未對應件數、狀態有變的項目編號。

**匯入與照抄**：

| 對方系統 | 做法 |
|---------|------|
| 試算表（Excel、Google Sheets） | 工作項表直接貼上或轉 CSV；依順序層排序、依狀態篩選 |
| 支援 CSV 匯入的任務系統（Asana、Jira 等） | 工作項表轉 CSV 匯入。依賴欄的匯入支援未驗證，所以前置項放進描述首行「前置：INV-003、INV-007」，順序層對應到 section 或 label |
| GitHub Issues | 逐項手動建立，或由對方自行用 `gh issue create` 批次建立；標題帶項目編號 |
| Slack 或只有文字的管道 | 依順序層分段貼文，每段一則訊息，每項一行「編號 標題（前置：…）」；進度由分析者在產物中對帳 |

**進度追蹤**：分兩個階段，主檔會轉移。

- 交付前：產物是主檔，所有項目為「待辦」。
- 交付匯入後：狀態主檔改為對方系統。產物回填「外部編號」，對帳時把對方系統的狀態抄回「狀態」欄與「最後對帳日」，並在對帳紀錄新增一列。
- 進度讀法：依順序層統計完成比例。順序層 n 的項目全部完成（或標記不做）之前，順序層 n+1 的項目視為有阻擋，但不另設 blocked 狀態欄，改由前置項推導。

**順序表達**：「前置項」列出本表項目編號；「順序層」= 沒有前置項時為 1，否則為所有前置項順序層的最大值加 1。兩欄並存的理由：前置項保留精確依賴，順序層讓不支援依賴的工具也能排出正確先後。
