### Context Bundle

**審查對象（六檔，全部唯讀）**

`.claude/skills/component-contract-design/SKILL.md` 與同目錄 `references/` 下五檔：
`modes-a-b.md`、`mode-c.md`、`field-questions.md`、`dispatch-language.md`、`examples-troubleshooting.md`。

**這次改動是什麼**

原為單一 SKILL.md（245 行、15,015 字元，為 skill body 預算 6,500 字元的 2.31 倍）。拆分為純位元搬移：每一行不是留在 SKILL.md 就是原封搬入某個 reference，已驗證 245/245 行覆蓋無重複無遺漏、五份 reference 正文與原檔對應區間位元相同。SKILL.md 現為 3,985 字元。

**本次唯一新寫的內容（其餘一字未改）**

1. SKILL.md 的〈按需讀取〉章節：標題、一句說明、五列路由表
2. 五個 reference 各自的檔頭三行：`# 標題`、`> 自 SKILL.md〈X〉逐字搬移…`、`> 同目錄：…`

因此 finding 請分兩組回報：**A 組**為本次新寫內容的問題（可立即修）、**B 組**為搬移前既有內容的問題（屬原檔既有品質，另行評估，仍須報）。

**切分依據**

「一次工作會不會同時用到」。三種模式互斥，判定起點後只走一條，故 `modes-a-b.md`（模式 B 末步驟接回模式 A）與 `mode-c.md` 分立；`field-questions.md` 為三模式共用的查表；`dispatch-language.md` 在契約齊全後寫票才用；`examples-troubleshooting.md` 為卡住時查詢。SKILL.md 留路由與判準：三種起點判定表、〈契約齊全的定義〉、〈分工邊界〉。

**已知的風險面**

拆分前這些章節同處一檔，互相以〈章節名〉指涉（如模式 A 步驟 6 寫「依〈十一欄位填寫問句〉逐欄填」）。現在那些章節分散在不同檔案，「本節」「見上」「見下」這類位置性指涉在搬移後可能失效。

**定位（frame 判斷標準的輸入）**

這是 **agent 指令 / 規範**，不是人類教材。讀者是照著執行的執行者（PM 或設計類代理人），讀完之後的動作落在世界上：複製 spec 範本、逐元件填十一欄位、建立元件票與畫面票。體例應為操作手冊——步驟編號是執行的位置，判錯代價要寫出來。

**共通產出契約（所有 reviewer 適用）**

- 每個 finding 欄位：位置（檔名 + 段落語意標題，不用行號）/ 問題 / 組別（A 新寫 / B 既有）/ 嚴重度（嚴重必修 / 建議可改）/ 建議修法
- 每個 finding 須註明**它那一類的全部命中位置**；抽樣者寫明抽了幾處、怎麼選的
- 某一維零命中須明寫「這一維跑過、零命中」，不可省略
- 報告 1500 字內，最後給整體評估分級
- 不修改任何檔案；不再往下派 agent
- 完成後以 `SendMessage({to: "main"})` 主動送出報告本體——任務結束通知不會把報告帶回主線程；預期超長時按維度切分並標號 1/N

### Round 4 翻譯探針（r4-translate-a／b，Haiku，逐字相同指令）

對象：〈契約齊全的定義〉全節（本次改動最大、且為全套唯一機械閘門）。判斷標準是份與份之間的分歧，不看任一份譯文的品質。

**一、譯文並排的分歧（不在任何一份決策清單中——即不自覺的決定）**

| 原文 | 譯者 A | 譯者 B | 判定 |
|------|--------|--------|------|
| 該制**不裁**排列不變式 | does **not require** | does **not cut** | **語意相反** |
| 每種**尺寸** | each size | each **dimension** | 詞義分歧 |
| 特徵測試**補不起** | cannot supplement | unable to cover | 兩者皆非原意（原意為「規模大到補不起來」） |
| **落成值** | delivered values | finalized values | 詞義分歧 |

「不裁」最嚴重。原文在 field-questions 為「十一欄位縮至…三欄，**排列不變式不裁**」，意為排列不變式**仍須填**。譯者 A 讀成「不要求」，正好相反——而該句位於替代判準表，照 A 的讀法小型專案可跳過排列不變式，那正是齊全第 3 條要擋的。**兩份決策清單皆未列入此項**，重現了 skill 記載的形態。

**二、決策清單交叉比對（自覺的決定）**

| 項目 | A | B | 判定 |
|------|---|---|------|
| 「對應到**一個**容器元件」的基數 | 未列為決定（譯為 one） | 明列，選 exactly one，替代 at least one | **分歧**：B 決定了 1:1，A 未察覺這是個決定。而此為齊全第 2 條，宣稱可機械執行——機械檢查需知是「至少一個」還是「恰好一個」（兩個排列關係能否共用同一容器） |
| 「子件數量**無上限者**」修飾誰 | 明列「修飾語依附點不清」 | 明列，選修飾「子件數量」並註明另一讀法「文法可行但語意錯誤」 | 兩份最終讀法相同，但皆判為原文不清。低嚴重 |
| 第 6 條六個括號的語意關係 | 明列「括號內是屬性還是獨立定義」 | **逐項列出六個，且六項的判讀各不相同**——#11 解釋、#12 定義、#13 解釋、#14 驗證方法、#15 紀錄內容、#16 度量 | **嚴重**：見下 |

**三、最嚴重的一項（主 session 判定，B 的 #12 直接示範損害）**

Round 3 新寫的第 6 條寫作「每個關機判定各有一條依據紀錄：起點判定（命中的訊號＋另兩起點的排除理由）、形態數（簽核人與日期）、…」。六個括號在原文中**都是「該紀錄須含什麼」**，但寫法未使該關係顯性。

B 對 #12 的判讀是「**定義：『形態數』就是指簽核人與日期**」——把紀錄內容讀成了術語定義。形態數是「支援幾個形態」這個數字，括號說的是紀錄要含簽核人與日期。B 讀錯了，而它讀錯的原因在我的句子：六個括號各自承擔不同的語意關係（有的是內容、有的看起來像定義），冒號又同時可讀作「即以下六種」或「該紀錄須含以下六項」。

**修法**：把冒號結構改為顯性對映——「各有一條依據紀錄，紀錄內容如下：起點判定 → 命中的訊號與另兩起點的排除理由；形態數 → 簽核人與日期；…」

**四、其餘可修項**：「文案放不放得下不在此判定」的「此」指六條全體還是第 6 條（B #28）；「除落成值與附舉證的『不適用』外」的「落成值」無定義（兩譯者給不同英文）。

**主 session 的補充判讀（reviewer 未指出）**：這不是單純的表頭不一致。Examples 例 1 示範的是**步驟 3**（存在必要性），而欄位表定義的是**步驟 2** 的產出物——「判定」與「理由」是步驟 3 才追加的欄。同一張表在不同步驟有不同欄位集，而欄位表未宣告它會長欄。
