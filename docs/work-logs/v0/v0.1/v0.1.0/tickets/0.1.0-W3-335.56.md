### E6 落檔前置：WRAP 快速模式定案「不是框架專案」判定條件

**矛盾**：SPEC-001 §1「不是框架專案」列進入條件「資料夾可讀但無 `docs/` 目錄」，
與同檔 FR-07 驗收「`.claude/VERSION` 與 JSON 皆缺時進入『不是框架專案』狀態」、
〈Gate 三問對照〉「不確定」欄「兩者皆缺 → 視為非框架專案」不一致；且〈Gate 三問
對照〉下方粗體註記明寫「schema gate 的三路判定只用兩個訊號：`.claude/VERSION`
的值，與 `tracking_schema.json` 檔案是否存在」「這兩個訊號足以正確分出三類，
無需第三個訊號」。

**候選（W，含反向框架）**：
- O1 採兩訊號版本為準：改寫 §1 該列進入條件與顯示文字，刪 docs/ 判準
- O2 採 docs/ 判準為準：改寫 FR-07 與 Gate 三問對照
- O3 兩訊號都需要（合取：VERSION 與 JSON 皆缺 且 無 docs/）
- O4（反向框架）：不再區分「不是框架專案」狀態，合併判準

**事證（R）**：
- Gate 三問對照粗體註記明寫「只用兩個訊號」「無需第三個訊號」「不讀 `.py`」，
  且引 PROP-002 已否決 Dart 側解析 `.py`（`ast.literal_eval` 失敗），此為刻意
  設計約束非疏漏
- SPEC-003 §2.7「是否顯示版本值」列（v1.34 已落檔）：「不是框架專案：否（無
  `.claude/VERSION` 可讀）」——SPEC-003 起草時已採兩訊號判準定性此狀態，非 docs/
- FR-07 理由段「四個個案指向同一個缺席變數（被觀察專案的框架版本）」，frame 3-H
  個案觀察對象為 `.claude/` 缺席，非 `docs/` 缺席
- UC-01〈例外場景〉完全未涵蓋「不是框架專案」（範圍外發現項 2，本輪不修，但
  佐證 docs/ 判準缺乏 UC 出處）
- O2 使 docs/ 判準與 schema gate「只用兩個訊號」既定約束衝突，且 docs/（UC 節點
  原始檔目錄）與 `.claude/`（型別表）分屬不同判斷維度，改用 docs/ 未解決兩者
  可能不同一專案的問題
- O3 增加判準複雜度，直接違反 Gate 註記「只用兩個訊號」，未見任何實際案例
  需要區分「有 docs/ 但兩訊號缺」與「無 docs/ 且兩訊號缺」
- O4 使狀態數改變，牽動 SPEC-001〈狀態總數〉、SPEC-003 §4、SPEC-004 §3.6 三處
  連動；「不是框架專案」訊息內容（FR-07「說明本 App 需要什麼」）與其餘兩阻擋
  態不同，合併會使訊息失去針對性，且無 UC 或 frame 3-H 事證支持合併

**裁決**：O1。「不是框架專案」進入條件改為「`.claude/VERSION` 與
`tracking_schema.json` 皆缺」；顯示文字移除 docs/ 字面，改用兩訊號判準措辭。

**被放棄選項優點**：O2 對使用者最直覺（沒有 docs/ 即非框架專案，語意貼近框架
輸出物存放位置）；O3 涵蓋最廣，能同時處理兩種訊號都缺的邊界情況；O4 狀態數
最少、實作最簡單。

**選定方案缺點**：(1) 有 `docs/` 但無 `.claude/`（或反之）的專案，本裁決未特別
區分，此類邊界個案仍依兩訊號判準落入既有三分支之一，docs/ 存在性不再影響判定；
(2) UC-01 尚無此例外場景（範圍外發現 2，本票不新增回寫），讀者仍需從 FR-07
理由段才知道判準來源；(3) 顯示文字改寫涉及 UI 文案精確措辞，此票只定 SPEC-001
語意层級文字，逐字文案由 SPEC-004（`0.1.0-W3-335.57`）承接。

**P 失敗訊號**：若後續實測發現有 docs/ 但無 `.claude/` 的專案，且該專案應被
判為「不是框架專案」以外的更精確分類，則需重評並加入 O3 合取判準。
