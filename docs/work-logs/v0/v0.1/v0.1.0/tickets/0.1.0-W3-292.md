## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`0.1.0-W3-288` 選定的修法有一個單一承重點：**每個會寫狀態的呼叫端，其 state root 來源是模組級的選擇，而非執行期才決定的值**。該承重點在 288 當下只對 159 個日誌呼叫檔中的 93 檔驗證過，其餘 66 檔未判定。本票是對那個未判定集合的逐檔判類。

判類前先重現 288 的掃描條件，確認兩邊談的是同一個集合，再逐檔判定。判準本身不先寫死——288 與 273 兩次失敗皆是「判準先於查證」，本票的判準在讀碼過程中兩度收窄（見〈實驗執行〉的判準演進段）。

### 影響範圍

掃描範圍：`.claude/` 全樹 `*.py`，排除 `/tests/`、`test_*`、`conftest` 與定義檔自身（`lib/hook_logging.py`、`lib/hook_base.py`、`lib/__init__.py`）。

實際受影響者為未判定集合中**有狀態寫入**的 18 檔；其餘 47 檔無狀態寫入，僅有經 `hook_logging` 預設路徑產生的日誌。

**已驗證**：159 檔集合可重現；未判定集合的四類分佈；各寫入者的 root 運算式（逐檔讀碼）。
**未驗證**：本票不涉及 `CLAUDE_PROJECT_DIR` 在 linked worktree 內的實際指向（288 已標明須實測，本票同樣未測，且本票結論不依賴它）。

### 相關 Error Pattern

同族形態為「判準先於查證，且錯誤在輸出上與正確同形」——`0.1.0-W3-273`（直接 import 判準漏 4）、`0.1.0-W3-288`（提及模組判準偽陽 8/14）。本票對此的防護寫在〈實驗執行〉的判準演進段：對「無狀態寫入」這一類做了**兩層** import 追查（第一層 helper、第二層 helper 的 helper），因為單層判準正是前兩次失敗的形狀。

### 實驗發現

**已驗證的事實**：

1. **承重點成立（依其字面射程）**：159 個日誌呼叫檔中，無任何**會寫狀態**的呼叫端依 payload 內容決定其 state root。65 檔判類為 (a) 47／(b) 18／(c) **0**／(d) 0。
2. **承重點成立，但它不足以支撐選定方案**。這是本票最重要的發現，理由見下。18 個寫入者的 root 來源實測為**六種互異的解析器**：`hook_base.get_project_root()`（`hook_logging` 的隱含預設）、`git_utils.get_project_root()`、`framework-rule-edit-skill-trigger-hook` 自建的 `_get_project_dir()`、兩個 auto-commit hook 各自自建的 `find_project_root()`、`pm_registry` 的 `git rev-parse --git-common-dir`、以及 `Path(__file__)` 相對路徑。**其中三種是呼叫檔自己重新實作的**，既不 import 任何共用解析器，也不經 `hook_logging`。
3. **選定方案「把 root 綁進日誌入口、使 import 語句表達選擇」對這 18 檔的涵蓋為零**。它們的**日誌** root 確實來自 `hook_logging` 預設，會被方案改到；但它們的**狀態** root 走的是上述自建或 helper 內部解析器，與日誌入口無交集。改日誌入口不改狀態根，兩者在這 18 檔中本來就是分離的。
4. **承重點問的是錯的問題**。它把風險設定為「root 是否執行期才決定」，實測風險不在時點而在**來源分歧**：六種解析器的優先序互異（`hook_base` 有 worktree 感知與 CLAUDE.md marker 搜尋，`git_utils` 無 worktree 感知，`_get_project_dir()` 連 marker 搜尋都沒有，`find_project_root()` 只認 cwd），同一次執行在不同 hook 中可解析到不同目錄。承重點成立這件事，對此毫無保護力。
5. **兩個非專案根的狀態根**：`worklog-format-check.py` 的抽樣計數寫在 `skills/doc-flow/hook-logs/`（skill 目錄相對），四個 `/tmp/...{ppid}` 計數檔完全不在專案樹內。任何以「專案根」為單位的方案對這些檔無定義。
6. **一個日誌根與判定根蓄意分離的實例**：`branch-verify-hook.py` 判定對象是 payload `file_path` 所屬的 repo（跨 repo），日誌卻寫在本專案根。把兩者綁在一起會改變它的行為。

**仍未驗證的假設**：

- 是否有呼叫端刻意要日誌留在所在 worktree（288 已列，本票未測，需實機而非讀碼）。
- `CLAUDE_PROJECT_DIR` 在 linked worktree 內的實際指向（288 已標明須實測不可推論；本票的六解析器差異分析在該值已知後才能排出實際錯配矩陣）。
- 六種解析器在同一次執行中實際解析到的目錄是否真的分歧（本票由讀碼推得優先序互異，**未實測**；這是把發現 4 從「機制上可能」升級為「實際發生」所需的下一步）。
