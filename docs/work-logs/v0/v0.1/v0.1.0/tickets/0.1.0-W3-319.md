## Problem Analysis
### 問題根因

兩個缺陷疊加，`0.1.0-W3-315` 的裁決 A（驗證器錨定本專案前綴、尾碼放寬為非空 `[a-z0-9]+`）只觸及其一：

1. **尾碼有兩個命名空間**：PM 用的 ListAgents 短名尾碼（`-66`／`-59` 形態）與 session uuid 前綴（`-dcead428` 形態）。A 的尾碼判準 `[a-z0-9]+` 對命名空間無任何約束力，兩者會一併通過，任意字串亦然（實跑：`<前綴>-zzzzzzzz` 在 A 下通過）。同一前綴下並存使「哪一次 session 寫的」語意失效。
2. **子代理人取值管道**：票面與 `0.1.0-W3-311` 記為「無合法管道、需新供應端」。本票實測推翻此歸因——管道存在且是既有基礎設施（見重現實驗結果）。

### 實驗發現

**已驗證**：

1. 子代理人有合法取值管道，且該管道是既有基礎設施（`CLAUDE_CODE_SESSION_ID` + `resolve_session_id`），不需新供應端。票面與 `0.1.0-W3-311` 的「需新供應端」代價據此不成立。
2. 兩種執行體取到同一值：本執行體的環境變數值 = PM 的 SessionStart hook 寫入 registry 的鍵。
3. 短名命名空間在三個狀態檔中零落地點；uuid 命名空間有兩個既有落地點。
4. `0.1.0-W3-315` 的 A 對命名空間無約束力（`-zzzzzzzz` 通過）。
5. 推導值在現行驗證器下仍 exit 3，故本票仍須降級 `observe`——成因由「無管道」換成「驗證器未改」。

**仍未驗證**：他 consumer 的 checkout 目錄名是否等於其慣用 owner 前綴（沿用自 `0.1.0-W3-315`，該欄為反推填入）；`CLAUDE_CODE_SESSION_ID` 跨平台版本存在性（單一版本觀測）。

## Solution
### 裁決一：尾碼命名空間採 session uuid 前 8 碼

寫入端判準定為 `^<推導前綴>-[0-9a-f]{8}$`。前綴錨定沿用 `0.1.0-W3-315` 裁決一；本票收窄的是尾碼——由該票的 `[a-z0-9]+` 改為 uuid 第一段。

**選它的理由**：唯一能被兩種執行體從同一來源一致取得、且該來源已是既有基礎設施的值。子代理人實測可讀 `CLAUDE_CODE_SESSION_ID`，其值與 `pm-registry.json` 的 sessions 鍵逐字相同，而該鍵由 PM 的 SessionStart hook 寫入——「兩個執行體取到同一值」因此是可交叉驗證的事實而非推論。uuid 是平台對 session 的主鍵，尾碼自此真能回答「哪一次 session 寫的」（可 join 回 registry heartbeat 與 `dispatch-active.json` 的 `session_id`）。

**不選 ListAgents 短名**：三個既有狀態檔中零落地點（實讀見重現實驗結果）。要讓它可用須新造供應端與一套漏填偵測，而其產生規則在任何本機可讀來源查無記載——`0.1.0-W3-315` 已據同一理由否決「兩碼十六進位」判準，理由在此仍成立。

**不選兩者並存**：即 `0.1.0-W3-315` 判定 A 不可單獨出貨的那個新不一致。

**不選 `CLAUDE_CODE_BRIDGE_SESSION_ID`（`session_014d49...`）**：大小寫混用，與三個讀取端共用的 kebab 前綴比對形態不同，且不對應 registry 任何鍵。

**相對 A 的鑑別力差異**（實跑）：`<前綴>-zzzzzzzz` 在 A 下通過、本裁決擋下。A 的尾碼字元集對命名空間無約束力，這是本票必須收窄而非沿用的原因。

### 裁決二：取值管道為 CLI 自行推導，漏填模式就地消滅

`init`／`add` 改為預設自行推導 owner，`--owner` 降為覆寫用。推導來源 `CLAUDE_CODE_SESSION_ID`，與 `.claude/lib/hook_logging.py` 的 `resolve_session_id` 同一供應端（5 支 hook 在用；`section_comment.py` 引用數實測 0）。

**這是消滅失效模式而非補訊號**：派發者不再需要提供 owner，「漏填」不存在。`0.1.0-W3-311` 記的「B 需新供應端」代價據本次實測不成立。

**殘餘失效模式與其當下訊號**（acceptance 第 2 項的硬要求）：

| 情形 | 要求行為 |
|---|---|
| 推導失敗（環境變數缺失，如平台版本不提供） | `init`／`add` exit 3，印三項診斷：環境變數是否存在、推導出的前綴、該 uuid 是否在 `pm-registry.json` 中 |
| 顯式 `--owner` 與推導值不符 | exit 3，除非顯式覆寫旗標（跨 consumer `transfer-owner` 逃生口見 `0.1.0-W3-315` 實作端待處理項 2） |
| 確需降級 `observe` | 改為顯式旗標並要求寫入降級原因，禁止靜默選擇 |

**Why**：現況是靜默降級為 `observe`，結論落進不受 `check` 主警訊涵蓋的觀測流；這整串問題今天才被發現即是該無訊號的後果。訊號必須落在寫入嘗試的當下，不得延後到人工閱讀觀測流時。

### 裁決三：存量不遷移

本機 20 筆 owner 全屬短名命名空間（`<前綴>-66` 14、`<前綴>-59` 5、`flutter-balance-77` 1）。判準只掛寫入端，存量讀取為前綴比對不受影響，故不遷移、不改寫既有區段首行；需要時以 `transfer-owner` 個案遷移。兩個命名空間不會混淆——8 碼十六進位與短名尾碼在字面上互斥可判。

此即 `0.1.0-W3-311` 待處置項 2 與 `0.1.0-W3-315` 實作端待處理項 4（存量 `thyme-python-developer-e2e`）的定案：不處置。

### 候選方案比較

| 候選 | 利 | 弊 | 採否 |
|---|---|---|---|
| uuid 前 8 碼 + CLI 自行推導 | 兩執行體同源、零新供應端、可 join registry、命名空間唯一 | 存量短名在寫入端失效；繫於環境變數存在性 | 採 |

| 沿用 `0.1.0-W3-315` 的 A 尾碼 `[a-z0-9]+` 不再收窄 | 實作最小 | 對命名空間零約束力，兩空間並存即 A 不可單獨出貨的成因本身 | 不採 |
