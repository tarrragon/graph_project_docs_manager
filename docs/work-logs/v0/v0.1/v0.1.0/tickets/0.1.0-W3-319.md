## Problem Analysis
### 問題根因

兩個缺陷疊加，`0.1.0-W3-315` 的裁決 A（驗證器錨定本專案前綴、尾碼放寬為非空 `[a-z0-9]+`）只觸及其一：

1. **尾碼有兩個命名空間**：PM 用的 ListAgents 短名尾碼（`-66`／`-59` 形態）與 session uuid 前綴（`-dcead428` 形態）。A 的尾碼判準 `[a-z0-9]+` 對命名空間無任何約束力，兩者會一併通過，任意字串亦然（實跑：`<前綴>-zzzzzzzz` 在 A 下通過）。同一前綴下並存使「哪一次 session 寫的」語意失效。
2. **子代理人取值管道**：票面與 `0.1.0-W3-311` 記為「無合法管道、需新供應端」。本票實測推翻此歸因——管道存在且是既有基礎設施（見重現實驗結果）。

### 影響範圍

| 對象 | 影響 |
|---|---|
| `.claude/skills/framework-issue/scripts/section_comment.py` | 寫入端判準（`OWNER_FORMAT_RE`／`validate_owner`）與 owner 取得路徑（`init`／`add` 的 `--owner`） |
| `references/ticket-intake.md`、`references/comment-as-section-protocol.md` | owner 識別格式段的占位形態，處置沿用 `0.1.0-W3-315` 裁決三 |
| 本地 `framework-issue-owned.json` 20 筆存量 owner | 只影響寫入端，讀取為前綴比對不受影響（裁決三定不遷移） |

**已驗證事實**：子代理人 Bash 程序可讀 `CLAUDE_CODE_SESSION_ID`；該值與 `pm-registry.json` 的 sessions 鍵逐字相同；三個 owner 讀取端全為 `startswith` 前綴比對；短名在 `pm-registry.json`／`dispatch-active.json`／`framework-issue-owned.json` 三處皆無落地點。

**仍未驗證的假設**：他 consumer 的 git checkout 目錄名是否等於其慣用 owner 前綴（`0.1.0-W3-315` 探針該欄為反推填入，本票未補驗，不當已證）；`CLAUDE_CODE_SESSION_ID` 跨平台版本的存在性（本次環境 `AI_AGENT=claude-code_2-1-267_agent`）。

### 相關 Error Pattern

`PC-BAL-001`（驗證端與建立端各自維護判準而漂移）為同型：owner 判準只掛寫入端，與三個讀取端不共用同一來源。本票裁決使寫入端改用與讀取端同源的推導值，收斂該形態。
