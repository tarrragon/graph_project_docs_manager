**PM 補充（新落地的方法論條文，2026-09-08）**

本票的兩項核心對象都是 driven port，而今天新落地的條文**直接管轄它們**——票面成文時該條文尚不存在，`how.strategy` 引用的兩份來源（`ux-design-evaluation` 的錯誤恢復與 gate、SPEC-004 §1 回饋通道子表）都是**輸入端**（使用者互動）的規範，不涵蓋輸出端。

| 本票的對象 | port 類型 |
|-----------|----------|
| 本 App 直接改檔 | driven port——檔案系統 |
| CLI 僅作驗證器 | driven port——外部程序 |

**新權威來源**：`.claude/methodologies/clean-architecture-implementation-methodology.md` 的〈Port 回饋契約〉（已驗證存在，commit `8db1f6d4`）。以標題文字引用，不寫 URL fragment。其下五個子節與本票的對應：

| 子節 | 對本票的意義 |
|------|------------|
| 輸出端回饋層級與判準 | 「寫入流程與 CLI 驗證的接線」須交代三個可觀測時刻：呼叫發出／外部系統受理／結果。消費者是呼叫端程式碼、日誌、監控追蹤，不是使用者 |
| 不變式：INV-PORT-OBSERVE-001 | 規格須明寫此不變式對編輯寫入路徑成立 |
| 回饋消費者與投影關係（含不互相抵扣規則） | **日誌不抵扣呼叫端回饋**。典型違反正是本票的形態：寫檔失敗只記日誌並回傳預設值，呼叫端無法區分「寫成功」與「失敗被降級」，而樂觀更新的回滾判斷正依賴這個區分 |
| 時序約束 | 回饋點須在設計期定義，不是事後補得回來的——本票是設計期，錯過就補不回 |
| 測試義務 | 規格須指明各時刻如何驗，含「呼叫發出」時刻不需外部系統替身、只需記錄器 |

**與樂觀更新政策的直接關聯**：acceptance 第 2 條要定案樂觀更新政策。樂觀更新的前提是「呼叫端能可靠得知寫入最終成功或失敗」——若 port 的結果時刻沒有可區分的回傳（例如失敗被 catch 收斂為靜默回傳），回滾邏輯就沒有觸發依據，樂觀更新在規格上不成立。**這一項請在規格中明寫因果，不要只寫政策結論。**

**約束**：本補充不改變票面既有的四項規格內容要求（可編輯範圍／寫入流程與 CLI 驗證接線／失敗與衝突畫面態／樂觀更新政策），是為第二項與第四項補上輸出端的權威依據。若判定〈Port 回饋契約〉與 SPEC-004 §1 回饋通道子表有衝突，停手記入 Solution 交 PM，不自行選邊。
