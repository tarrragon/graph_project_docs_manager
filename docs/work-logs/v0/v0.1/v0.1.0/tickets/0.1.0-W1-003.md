### 影響範圍

### 實測落差（描述 vs 實機）

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 節點檔抽取
自四個語料專案 ~/project/{book_overview_app,book_overview_v1,monitor,screen_clock} 的 docs/proposals、docs/spec（含各 domain 的 domain-map.md）、docs/usecases、docs/proposals-tracking.yaml，逐檔案 cp -r 抽取至 test/fixtures/corpus/{project}/docs/，明確不含 docs/work-logs/。抽取結果與來源 diff -rq 逐檔位元組相同（無轉碼、無截斷）。另建 test/fixtures/corpus/empty_state/ 為現造的空狀態邊界樣本。每個專案目錄下附 meta.yaml 記錄 snapshot_date、claude_framework_version（各專案 .claude/VERSION：app=2.27.8、v1=2.27.8、monitor=2.22.1、screen_clock=2.24.0）與極端案例說明。tool/snapshot_corpus.dart 提供可重現抽取邏輯（單一來源專案路徑 → 目的目錄名），供後續補充或更新語料時使用。

### 四種極端驗證
真實規模：screen_clock（乾淨、規模適中）。空狀態：empty_state（現造）。異常長內容：book_overview_v1 的 docs/spec/extraction/e2e-contract.md（1673 行）。損壞資料：book_overview_app 4 個、book_overview_v1 8 個缺 frontmatter carrier（parse_frontmatter 回傳 None）。舊框架版本：monitor（2.22.1，tracking_schema.py 僅 78 行無型別表）、screen_clock（2.24.0，中間取樣點）。

### acceptance 第 4 項驗證方式
以框架 frontmatter_parser.parse_frontmatter + tracking_schema.GRAPH_NODE_TYPES 的 id_pattern，對四個專案的原始 docs/ 與抽取後的 fixture 逐檔案分類（node id + 型別），比對兩者結果，四個專案 mismatches 皆為 0（screen_clock 24 檔、monitor 38 檔、book_overview_app 62 檔、book_overview_v1 58 檔），證明抽取未改變逐行 frontmatter 語意解析分類。

### ticket 規模項處置（三選項權衡）
選項 A：整份入庫（17 MB 量級，以 flutter_balance 專案的 ticket 量體為參照估算）。優點：語料最完整、CI 環境一致無額外設定。缺點：單一語料來源即讓 fixture repo 體積暴增，且 ticket carrier 的真實損壞形態集中在極少數檔案（如本票已定位的單一 YAML 壞檔），為此付出全量體積代價不划算。
選項 B：取版本切片（僅抽該來源專案 1-2 個版本目錄的 tickets，如僅取含已知壞 YAML 樣本的那個版本）。優點：體積可控（估計數百 KB 至數 MB）、仍是真實資料、可鎖定已知的損壞樣本。缺點：版本切片的選取標準需要人工判斷維護，未來新增 ticket 損壞形態需要重新篩選。
選項 C：本機路徑而 CI 跳過（fixture 只留一個指向本機 ~/project/ 的路徑設定，測試在偵測不到該路徑時自動 skip）。優點：零額外體積。缺點：CI 環境與貢獻者本機環境行為不一致，永遠無法在 CI 驗證 Ticket 節點的 parser 行為，且該路徑高度環境相依（僅本機開發者持有語料），不具可移植性，違反 fixture 應可重現的基本要求。

**選擇：選項 B（版本切片）**，但範圍限縮為本票不落地——理由：本票 acceptance 明確排除 work-logs（'不含 work-logs'），Ticket 節點檔的抽取屬另一個獨立子任務（需要先决定切哪個版本、如何標註來源版本區間等細節，屬功能職責且與本票的 PROP/SPEC/UC 三型別抽取無直接依賴）。已建 spawn request 追蹤，留待後續 wave 依選項 B 執行。
