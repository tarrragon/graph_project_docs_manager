## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 死局實測（PM，2026-09-21）

三條路同時封死，逐一實跑確認：

```
ticket track release 0.1.0-W3-648
  → [enum-gate:deny] 'closed' -> 'pending' 非法（closed 合法出邊：無（終態））
ticket track claim 0.1.0-W3-648
  → [enum-gate:deny] 'closed' -> 'in_progress' 非法（同上）
ticket track append-log 0.1.0-W3-648
  → 當前 status=closed，需要 status=in_progress
```

ticket md 另有 read guard，PM 無法直接編輯票面。

### 事故經過

`0.1.0-W3-649` 清倉以「`where.files` 全數落在 `.claude/` 下」為判準關掉 49 張可攜票。該判準只說明**問題可攜**，不說明**票的內容是知識還是程式碼變更**——`framework-issue` 的模型是「ticket 記執行，issue 記問題」。14 張 `type: IMP` 的執行票被誤標為 `not_executable_knowledge_captured`，其中 `0.1.0-W3-648` 被關當下手上已有 4054 個通過的測試。

判準缺這一層是 PM 的錯，不是執行者的。

### 要還原的 11 張（W3-649 判定為確定誤關）

`0.1.0-W3-648`、`0.1.0-W3-275`、`0.1.0-W3-507`、`0.1.0-W3-509`、`0.1.0-W3-274`、`0.1.0-W3-327`、`0.1.0-W3-330`、`0.1.0-W3-276`、`0.1.0-W3-357`、`0.1.0-W3-334`、`0.1.0-W3-633`

另 3 張（`0.1.0-W3-178`／`0.1.0-W3-180`／`0.1.0-W3-197`，內容為「驗證 issue 修復是否抵達」）**先不還原**，其性質介於知識與執行之間，待 PM 另裁。

### 設計要點

- 必填還原理由；落地清除 `close_reason`／`close_reason_note`／`closed_by`／`completed_at` 四欄
- 票面留下還原記錄（何時、誰、為何），不可靜默改狀態
- `state_machine` 合法出邊表同步新增該轉移，且**只能由還原命令觸發**——`release` 與 `claim` 對 closed 票仍須被擋（acceptance 第 2 項的兩個該紅輸入）

### 基底注意

`.claude/skills/ticket/` 剛由 `0.1.0-W3-648` 改過（新增 `--dedup-checked` 可攜問題分流閘門，CHANGELOG 已到 2.36.0，全套件 baseline 4054 passed）。動手前先 `git log --oneline -3` 確認基底，不要回退其變更。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 命令設計
新增 `ticket track restore <id> --reason <text> [--as <agent>]`（`ticket_system/commands/track_restore.py`），仿 `set-closed-by` 的檔案/測試骨架。僅允許 `status=closed`；`--reason` 必填（禁止靜默還原）；落地清除 `close_reason`/`close_reason_note`/`closed_by`/`closed_at`/`completed_at` 五欄（ticket how 欄列四欄，另加 `closed_at`——`close()` 實際寫入的欄位是 `closed_at` 而非 how 欄誤植的 `completed_at`，`completed_at` 在 close 時通常已是 null，兩者皆清除以求完整對稱），並寫入 `restored_at`/`restored_by`/`restore_reason` 三個還原記錄欄位，走 auto-commit。

### 轉移矩陣與該紅輸入
`constants.py` 的 `STATUS_TRANSITIONS[STATUS_CLOSED]` 由 `frozenset()` 改為 `frozenset({STATUS_PENDING})`，只開放 `pending` 這一個出邊。驗證只能由 restore 觸發（acceptance 第 2 項）：
- `release()` 新增明確 app-level guard：`status == STATUS_CLOSED` 時直接拒絕（因 release 的目標狀態可能是 pending，若不擋，closed 票會透過 release 「順路」拿到新開放的 pending 出邊）
- `claim()` 未特別加 guard：其恆將狀態導向 `in_progress`，`in_progress` 不在新開放的出邊集合內，`_enforce_enum_gate`（deny 模式）自然攔截並拋 `EnumGateViolation`
測試 `TestClosedTerminalStillEnforced` 各給一個該紅輸入驗證兩者。

### 測試骨架陷阱（自檢過程記錄）
初版 `test_claim_rejected_by_enum_gate` 誤判通過：fake `load_ticket` 未寫入 `ENUM_SNAPSHOT_FIELD`，導致 `_collect_transition_violations` 因 `snapshot is None` 提前放行，claim 靜默成功卻無測試訊號。修正：fake loader 補 `fm[ENUM_SNAPSHOT_FIELD] = _snapshot_enum_fields(fm)`，重跑後正確驗證 `EnumGateViolation` 被拋出。

### 11 張確定誤關票已還原
逐張以 `ticket track restore <id> --reason "0.1.0-W3-649 判定確定誤關（W3-650 執行）" --as thyme-python-developer` 還原：0.1.0-W3-648／275／507／509／274／327／330／276／357／334／633。全數 status=pending、四個 close 欄位已清除、票面已有 restored_at/restored_by/restore_reason 記錄，逐張以 auto-commit 落於主 repo（worktree 下 ticket CLI 依 git-common-dir 解析寫入主檢出，非本 worktree 分支，屬既有設計，見主 repo `git log` 對應 11 個 `chore(<id>): restore status` commit）。另 3 張（W3-178/180/197）依裁決不還原。

### 文件同步（skill-cli-sync-check）
`references/track-command.md` 新增 `restore` 子命令表列項、專節說明、CLI 可修改欄位表 `status` 列補充；`CHANGELOG.md` 新增 2.37.0；`SKILL.md` frontmatter 版號同步至 2.37.0。
