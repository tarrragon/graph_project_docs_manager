## Problem Analysis
### 問題根因

**直接原因：待裁列的資料本身沒有時間軸，而唯一的讀取入口是一個需要人主動呼叫的唯讀子命令。** `todo` 聚合出的每一列只有六個欄位（`來源票`／`型別`／`做什麼`／`acceptance 條數`／`優先級`／`階段`／`狀態`，加上聚合端補的 `issue`／`owner`），**沒有任何日期欄位**。這決定了兩件事：

1. 任何「以時間為訊號」的推送形態（逾期、落後 N 天）在待裁列上**沒有逐列的資料可依據**，只能退回區段層的 `updated_at`，粒度比 `check` 的主警訊更粗。
2. 任何「只印新增」的形態必須由**本地快照**製造出時間軸，資料端不提供。

**規模是第二個根因**：本票實測 `todo` 預設範圍輸出 109 列，其中 101 列狀態為 `待裁票`（93%）；本 consumer 擁有的 43 列**全部**為 `待裁票`（43/43）。因此 `--status 待裁票` 這個既有篩選旗標**對推送量沒有鑑別力**——它篩掉的是 8 列。這與 `0.1.0-W3-318` 對 `check` 的 `--stale-days` 判定同形：**參數化這條路已走完，缺的是訊號定義**。

**方向相反但同一個病**：`check` 主警訊七天窗實測六張 issue 全未觸發（恆偽）；待裁列若「把清單印出來」則每次 session 都觸發（恆真）。兩者皆命中 `PC-BAL-010`（驗證／觀察管道對待驗現象不敏感，恆真與恆偽雙向），共同判準是同一句：**這個推送條件的結果，會隨待裁列的實際狀態改變嗎？**

## 重現實驗結果
### 實驗方法

本票要裁的是推送形態，故「實驗」的對象不是待裁列的內容，而是**每個候選形態的「不該印」條件在真實資料上是否非空**。方法：

1. 先寫下判準（下稱 **N 測**），再對每個候選形態套用，避免以形態的直覺吸引力代替判準。
2. 凡判準依賴的數字，一律實跑取得，不引用前票（`0.1.0-W3-306`／`318`）的數字。
3. 全程唯讀：不改 CLI、不改 hook、不對 canonical issue 寫入。

**N 測（三問，全部成立才算可採）**：

| 問 | 內容 | 不成立的後果 |
|----|------|-------------|
| N1 | 「什麼情況下不該印」可寫成一個句子 | 推送條件恆真，命中 `PC-BAL-010` 恆真向 |
| N2 | 該句子**在今日真實資料上為真**（即今天確實不會印） | 條件存在但永不成立，等於無條件 |
| N3 | 該句子的反面（會印的情況）在真實資料上**也能成立**（即該通道並非永久沉默） | 命中 `PC-BAL-010` 恆偽向，即 `check` 七天窗的失效方向 |

N2 與 N3 必須分開問：`check` 的七天窗**通得過 N1**（「距最新觀測 <= 7 天即不印」是一個完整句子），也通得過 N2（今天確實不印），敗在 N3——累積期內觀測持續刷新使該條件結構性恆成立。**只問 N1 會把七天窗判為可採**，這是本票把驗收第一條當門檻而非形式的具體理由。

### 實驗發現

**已驗證的事實**

1. **`--status 待裁票` 對推送量沒有鑑別力**（實驗 2）：全體 109 列中 101 列是 `待裁票`；本 consumer 43 列中 43 列是 `待裁票`。以狀態為推送條件，等於印出整份清單。
2. **待裁列的資料端沒有時間軸**（實驗 3）：逐列無日期欄位。時間軸只能由本地快照製造，或退回區段層 `updated_at`（粒度為整個區段，非逐列）。
3. **逐列身分可機械計算**（實驗 3）：`(issue, owner, 來源票)` 在 109 列上唯一且零碰撞，故「本次與上次快照的差集」是一個有 predicate 的運算（`0.1.0-W3-318` 的 L2 性質成立）。唯一需處理的雜訊是 `來源票` 欄反引號包法不一致（同一份資料內兩種寫法並存），屬正規化而非判定。
4. **「不印」在今日真實資料上成立**（實驗 7）：若採「只印自上次以來的新增列」，本 consumer 在 2026-09-10 06:19 之後的每一次 session 都不會印任何東西；若採「印全列」，同一期間每次 session 印 101 列。**這是兩種形態在同一組資料上的可觀測差異，不是偏好差異。**
5. **成本非零且落在最擁擠的事件上**（實驗 4／5）：預設範圍聚合實測 13.63 秒，而 SessionStart 已有 44 支 hook。前例 hook 之所以便宜，是因為它走登記檔快速路徑且對每張 issue 設 12 秒上限；待裁列聚合若照現況原樣掛上，單支 hook 即可能成為 SessionStart 最慢的一支。
6. **條文已指名觸發器而執行層為零**（實驗 6）：這一項是機械可查的（grep 零命中），與「有沒有人在處理待裁列」是兩個不同命題——本票只宣稱前者（`PC-BAL-067` 射程限制）。

**仍未驗證的假設**

- 待裁列的長期寫入頻率分佈未取得，本票只有兩天的直接觀測（實驗 7）。N2／N3 的判定只用到「今日不印」與「寫入事件確實發生過」兩件事，不依賴頻率分佈。
- 本票未實測任何候選形態的實際推送效果（那需要先實作，本票範圍排除）。
- 實驗 4 的 13.63 秒未拆解為 gh 往返與本地處理各自佔比，本票不以其成因為任何判定依據。
