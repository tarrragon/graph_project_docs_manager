## Problem Analysis
### 問題根因

**直接原因：待裁列的資料本身沒有時間軸，而唯一的讀取入口是一個需要人主動呼叫的唯讀子命令。** `todo` 聚合出的每一列只有六個欄位（`來源票`／`型別`／`做什麼`／`acceptance 條數`／`優先級`／`階段`／`狀態`，加上聚合端補的 `issue`／`owner`），**沒有任何日期欄位**。這決定了兩件事：

1. 任何「以時間為訊號」的推送形態（逾期、落後 N 天）在待裁列上**沒有逐列的資料可依據**，只能退回區段層的 `updated_at`，粒度比 `check` 的主警訊更粗。
2. 任何「只印新增」的形態必須由**本地快照**製造出時間軸，資料端不提供。

**規模是第二個根因**：本票實測 `todo` 預設範圍輸出 109 列，其中 101 列狀態為 `待裁票`（93%）；本 consumer 擁有的 43 列**全部**為 `待裁票`（43/43）。因此 `--status 待裁票` 這個既有篩選旗標**對推送量沒有鑑別力**——它篩掉的是 8 列。這與 `0.1.0-W3-318` 對 `check` 的 `--stale-days` 判定同形：**參數化這條路已走完，缺的是訊號定義**。

**方向相反但同一個病**：`check` 主警訊七天窗實測六張 issue 全未觸發（恆偽）；待裁列若「把清單印出來」則每次 session 都觸發（恆真）。兩者皆命中 `PC-BAL-010`（驗證／觀察管道對待驗現象不敏感，恆真與恆偽雙向），共同判準是同一句：**這個推送條件的結果，會隨待裁列的實際狀態改變嗎？**

### 實驗方法

本票要裁的是推送形態，故「實驗」的對象不是待裁列的內容，而是**每個候選形態的「不該印」條件在真實資料上是否非空**。方法：

1. 先寫下判準（下稱 **N 測**），再對每個候選形態套用，避免以形態的直覺吸引力代替判準。
2. 凡判準依賴的數字，一律實跑取得，不引用前票（`0.1.0-W3-306`／`318`）的數字。
3. 全程唯讀：不改 CLI、不改 hook、不對 canonical issue 寫入。

**N 測（三問，全部成立才算可採）**：

| 問 | 內容 | 不成立的後果 |
|----|------|-------------|
| N1 | 「什麼情況下不該印」可寫成一個句子 | 推送條件恆真，命中 `PC-BAL-010` 恆真向 |
| N2 | 該句子**在今日真實資料上為真**（即今天確實不會印） | 條件存在但永不成立，等於無條件 |
| N3 | 該句子的反面（會印的情況）在真實資料上**也能成立**（即該通道並非永久沉默） | 命中 `PC-BAL-010` 恆偽向，即 `check` 七天窗的失效方向 |

### 實驗發現

**已驗證的事實**

1. **`--status 待裁票` 對推送量沒有鑑別力**（實驗 2）：全體 109 列中 101 列是 `待裁票`；本 consumer 43 列中 43 列是 `待裁票`。以狀態為推送條件，等於印出整份清單。
2. **待裁列的資料端沒有時間軸**（實驗 3）：逐列無日期欄位。時間軸只能由本地快照製造，或退回區段層 `updated_at`（粒度為整個區段，非逐列）。
3. **逐列身分可機械計算**（實驗 3）：`(issue, owner, 來源票)` 在 109 列上唯一且零碰撞，故「本次與上次快照的差集」是一個有 predicate 的運算（`0.1.0-W3-318` 的 L2 性質成立）。唯一需處理的雜訊是 `來源票` 欄反引號包法不一致（同一份資料內兩種寫法並存），屬正規化而非判定。
4. **「不印」在今日真實資料上成立**（實驗 7）：若採「只印自上次以來的新增列」，本 consumer 在 2026-09-10 06:19 之後的每一次 session 都不會印任何東西；若採「印全列」，同一期間每次 session 印 101 列。**這是兩種形態在同一組資料上的可觀測差異，不是偏好差異。**
5. **成本非零且落在最擁擠的事件上**（實驗 4／5）：預設範圍聚合實測 13.63 秒，而 SessionStart 已有 44 支 hook。前例 hook 之所以便宜，是因為它走登記檔快速路徑且對每張 issue 設 12 秒上限；待裁列聚合若照現況原樣掛上，單支 hook 即可能成為 SessionStart 最慢的一支。
6. **條文已指名觸發器而執行層為零**（實驗 6）：這一項是機械可查的（grep 零命中），與「有沒有人在處理待裁列」是兩個不同命題——本票只宣稱前者（`PC-BAL-067` 射程限制）。

**仍未驗證的假設**

- 待裁列的長期寫入頻率分佈未取得，本票只有兩天的直接觀測（實驗 7）。N2／N3 的判定只用到「今日不印」與「寫入事件確實發生過」兩件事，不依賴頻率分佈。
- 本票未實測任何候選形態的實際推送效果（那需要先實作，本票範圍排除）。

## Solution
### WRAP 三問（claim Checkpoint）

**W（Widen）**：候選形態不只「印或不印」二選一——本票列了五種（全列／本 consumer 清單／時間門檻／claim 時點／未讀取的新增列），並把「承擔者」與「訊號定義」拆成兩個獨立問題，否則會在「該不該掛 hook」上爭論而不觸及「掛上去印什麼」。
**R（Reality Test）**：先問「今天這個形態會不會印」，用實跑的 109 列與區段時間戳回答，不用推想。兩個數字決定了大半結論：101/109 是 `待裁票`，本 consumer 待裁列自 2026-09-10 起零變化。
**A（Assume the opposite）**：反面假設是「待裁列就該每次全印，因為它本來就該被清掉」。本票不以噪音為理由駁回它，而以載體分工駁回：存量的讀取入口已存在（`todo`），推送若負責存量就必然恆真；**存量靠一次性裁票 session，推送只負責讓新寫入被知道**。
**P（Prepare to be wrong）**：最可能失敗的原因是「新增列被印過一次、當次沒處理、之後永久沉默」（at-most-once 通知）。防護是把通報集合定為 ack-based 而非 seen-based——這一點寫進本票的形態定義，不留給實作票自行決定。

### 結論（四句）

1. **可採的形態是「未讀取的新增列」，不是「待裁票清單」。** 不該印的條件寫成一句：**自上次通報後沒有新增列，或新增列已被讀取過**。該條件今日在真實資料上成立（本 consumer 待裁列自 2026-09-10 06:19 起零變化，實驗 7），其反面也確實發生過（09-10 的五則區段寫入），故同時通過 N2 與 N3。
2. **承擔者裁定為 SessionStart hook（主通道）＋ 寫入端即時回印（輔通道）；條文層不作為承擔者。** 理由是讀者身分：待裁列的**寫入者**是 curator、**裁決者**是 PM，而 PM 的固定入口只有 session 啟動。條文層已被 `0.1.0-W3-318` 的補料實測反證（owner 條文的讀者即其作者，仍連漏兩次）。
3. **前例部分適用：基礎設施可沿用，訊號模型不可沿用。** `check` 的主警訊以時間差為訊號，而待裁列逐列沒有日期欄位（實驗 3）；且兩者失效方向相反——`check` 恆偽（七天窗不觸發），待裁列的自然形態恆真（每次印 101 列）。兩者同屬 `PC-BAL-010`，用同一道判準檢查，但不能用同一個訊號。
4. **`0.1.0-W3-318` 標為 M2 的其餘四項不共用此通道，但共用此門檻。** 其餘四項的缺口是「操作者已在看輸出，而輸出少說了一件事」；待裁列的缺口是「沒有任何呼叫時點」。前者的承擔者必然是子命令自身或 PreToolUse 攔截，與 SessionStart 無關；**但 N 測三問對四項全部適用**（例如 `dedup` 收斂若做成「一律印全部命中」，即落入與「印全列」相同的恆真形態）。

### 一、五個候選形態逐一套 N 測

| 形態 | 「不該印」的條件 | N1 可寫成句子 | N2 今日為真 | N3 反面可成立 | 判定 |
|------|----------------|--------------|------------|--------------|------|
| A 全列每次印 | 待裁列為空 | 是 | **否**（實測 109 列非空，本 consumer 43 列全為待裁票） | 是 | **不可採**：條件存在但在可預見期間永不成立，等於無條件（恆真向） |
| B 只印本 consumer 的 `待裁票` | 本 consumer 無待裁列 | 是 | **否**（43/43 全為待裁票；C1 十五項寫入後為 58） | 是 | **不可採**：`--status` 篩掉的是 8 列，對推送量無鑑別力；與 A 同形，只是量少 |
| C 逾期／落後 N 天 | 未逾期 | 是 | 是 | **否** | **不可採**：逐列無日期欄位，只能退回區段 `updated_at`，而寫入行為本身即刷新它——累積期結構性不觸發，即 `check` 七天窗已被實測的失效方向（恆偽向） |
| D 有人 claim 相關票時印 | 本次 claim 的票不在待裁列的來源票集合 | 是 | 是 | **近乎否** | **不可採為主通道**：本 consumer 43 列來自 43 張**已完成的收束來源票**（實驗 3），再被 claim 的機率近零；列內無檔案欄位，改以檔案重疊為條件則無 predicate。可作為日後輔助，不承擔主通道 |
| **E 未讀取的新增列（ack-based delta）** | **自上次通報後無新增列，或新增列已被讀取** | 是 | **是**（自 2026-09-10 06:19 起零變化） | **是**（09-10 發生過五則區段寫入） | **可採** |
| E' 同上但 seen-based（印過即消） | 同上 | 是 | 是 | 是 | **不足**：at-most-once 通知——印過一次而當次未處理即永久沉默，失效方向與 `check` 同向。故本票把 ack-based 寫進形態定義，不留給實作票選 |

**E 的 predicate 已被驗證存在**（實驗 3）：`(issue, owner, 正規化後的來源票)` 在 109 列上唯一且零碰撞，差集為機械運算，符合 `0.1.0-W3-318` 的 L2 判準。唯一的資料雜訊是 `來源票` 欄反引號包法不一致，屬正規化不屬判定。

**為何 A／B 不能用「反正就該清掉存量」翻案**：存量的讀取入口已經存在且條文已指名（`todo --status 待裁票`，`escalation-flow.md` 第二檔）。**把存量也押在推送上，推送條件就必然恆真**；存量的正確處置是一次性的裁票 session（其觸發可由 delta 累積量構成），推送的職責只是讓新寫入被知道。這是載體分工，不是噪音偏好。

### 二、`session-start-issue-check-hook.py` 作為前例的適用性判定

**判定：部分適用——基礎設施可沿用，訊號模型不可沿用。** 逐項對照：

| 面向 | `check` 前例 | 待裁列 | 同類？ |
|------|-------------|-------|-------|
| 訊號性質 | 兩個時間戳的差（當前結論 vs 最新觀測） | 一份清單的成員變化 | **否** |
| 資料端是否有時間軸 | 有（comment `updated_at`） | **無**（逐列零日期欄位，實驗 3） | **否** |
| 失效方向 | 恆偽（七天窗六張 issue 全未觸發） | 自然形態恆真（每次 101 列） | **相反** |
| 推送頻率的決定者 | 觀測流的到達速率（他方寫入） | 本方與他方的收束／裁票事件（離散、稀疏，實驗 7） | **否** |
| 觸發時機 | SessionStart（startup／resume） | 同（見第三節裁定） | **是** |
| 可沿用的基礎設施 | 登記檔快速路徑、`SOURCES_TO_RUN`、subagent 略過、fail-open、per-issue 逾時 | 同樣需要這五項，且**成本壓力更大**（實驗 4：預設範圍聚合 13.63 秒；實驗 5：SessionStart 已 44 支 hook） | **是** |

**因此「有前例所以照掛」不成立，而「有前例所以不必重造 fail-open 與範圍解析」成立。** 兩者是不同層次：前者是訊號設計，後者是工程複用。

### 三、推送承擔者的三個候選與各自的漏讀失效方向

| 候選 | 漏讀失效方向（沒被讀到時，長什麼樣） | 可否偵測 |
|------|--------------------------------|---------|
| **SessionStart hook** | **靜默**：gh 不可用、登記檔缺失、逾時、fail-open 任一命中即完全不輸出，而讀者無從分辨「沒有新增」與「hook 沒跑成功」——兩者輸出皆為空。另一向是被 44 支既有 hook 的輸出淹沒（讀得到但看不見） | 可（hook-logs 有紀錄），但需有人去看 |
| `todo` 子命令自身輸出 | **對象錯位**：看到的人是主動呼叫者，而主動呼叫者已經在讀待裁列了；真正需要被通知的裁決者不會呼叫它。失效樣態是「功能完好而通知量為零」，即今日現況 | 不可（沒有「應該印卻沒印」的事件） |
| curator 派發時的必經步驟（條文層） | **作者自身亦漏**：`0.1.0-W3-318` 補料已實測同型——owner 識別的條文其讀者即作者本人，落地後兩次派發仍漏填。失效樣態是條文存在且正確、執行率不明 | 不可（無機械訊號；`0.1.0-W3-308` 已判定此類效果零觀測） |

**裁定：主通道為 SessionStart hook，輔通道為寫入端（`init`／`add`／`update` 寫入含待辦表的區段成功後）即時回印本次新增列數。條文層不作為承擔者。**

三項理由：

1. **讀者身分決定通道**：待裁列的寫入者與裁決者不是同一人。子命令輸出只觸及寫入者，只有 session 啟動觸及裁決者。
2. **輔通道補的是主通道唯一不可偵測的缺口**：主通道的失效是「靜默」，而寫入端回印讓寫入者當場知道自己寫進去了幾列——**寫入端的回印不是為了提醒裁決者，是為了讓「寫了幾列」這個數字在兩個通道上可比對**。成本為零（該次呼叫已在跑 gh）。
3. **條文層已被反證，不重複投資**：不是「條文無效」，而是「條文不能作為送達保證」。相關條文（`escalation-flow.md` 第二檔已指名觸發器）維持原狀即可，不因本票而加強。

### 四、`0.1.0-W3-318` 標為 M2 的其餘四項是否共用同一推送通道

**判定：全部不共用。** 逐項：

| M2 項 | 缺口的位置 | 承擔者 | 與待裁列共用通道？ |
|-------|-----------|-------|-----------------|
| `dedup` 命中規模無收斂手段 | 操作者**正在看**輸出，而 20 筆命中無從逐一判定 | `dedup` 自身的輸出（排序／分組／過濾） | 否 |
| `dedup` 靜默吞多餘旗標 | 參數解析期，rc=0 且無警告 | `dedup` 自身的參數檢查 | 否 |
| `show` 未提示 body 非權威 | 操作者正在看 `show` 輸出 | `show` 自身輸出加一行（無條件，不需判斷 body 內容） | 否 |
| SR-4（`bare-commit-guard-hook.py` 未偵測 `-i`／`--include`） | Bash `git commit` 發出時 | PreToolUse guard hook | 否（事件與輸入皆不同） |

**共用與不共用的分界是一句話**：其餘四項的缺口是「**已經有呼叫時點，而該時點的輸出少說了一件事**」；待裁列的缺口是「**沒有呼叫時點**」。前者不需要新通道，後者需要的正是新通道。故形態不一次定。

**但有一件事一次定**：N 測三問對五項全部適用。具體地，`dedup` 收斂若實作為「一律印出全部命中並加標記」，其「什麼情況下不該印」答不出來，即與本票判為不可採的形態 A 同形；`show` 的 body 提示屬**無條件一行**，它不進 N 測——因為它不是推送而是輸出常駐內容，兩者不可混為一談（混談會導出「既然 show 可以無條件加一行，待裁列也可以無條件印」的錯誤類推）。

### 五、候選方案

**方案甲：ack-based delta ＋ SessionStart 主通道 ＋ 寫入端回印（建議）**

- 內容：如第一節 E 與第三節裁定。範圍界定（第六節）交後續票實作。
- 利：唯一同時通過 N1／N2／N3 的形態；主通道觸及裁決者；輔通道零成本且使兩個通道的數字可比對；`check` 前例的基礎設施可直接複用。
- 弊：需要一份本地狀態（per-worktree、不入版控），其遺失會使下一次推送把全部待裁列當成新增印出一次——**這是已知的退化方向，實作票須明寫其處置**；且主通道的靜默失效不可由讀者側察覺。

**方案乙：只做寫入端回印，不掛 SessionStart（不採）**

- 內容：`init`／`add`／`update` 成功後回印本次新增列數，不建立任何 session 啟動通道。
- 利：零成本、零狀態、零誤報，且完全不增加 SessionStart 的 44 支 hook 負擔。
- 弊：**通知對象錯位**——只有寫入者看到，而寫入者本來就知道自己寫了什麼；裁決者的送達率仍為零。這正是今日現況的一個更小版本，不解決本票的問題。
- 不採理由：它使「待裁列會被讀到」這件事在觀測上無法區別於現況。

**方案丙：全列（或本 consumer 全待裁票列）每次 SessionStart 印出（不採）**

- 內容：把既有 `todo --consumer <本 consumer> --status 待裁票` 的輸出掛上 SessionStart。
- 利：實作最小（一支包裝 hook）、零狀態、零誤報定義問題。
- 弊：實測即 101 列（本 consumer 43 列，C1 十五項寫入後 58 列）於每次 session 啟動輸出，且「什麼情況下不該印」答不出來。
- 不採理由：命中 `PC-BAL-010` 恆真向。**這正是本票驗收第一條要擋下的形態**，且它與 `check` 七天窗是同一個病的兩個方向——後者已有六張 issue 的實測作為反面基準。

**建議**：甲。乙作為甲的輔通道被併入，不作為獨立方案；丙不採。

### 六、範圍界定（交後續票）

**本票已定死、後續票不得重議的三項**：

1. 推送的訊號是**未讀取的新增列**（delta），不是狀態清單、不是時間門檻。
2. delta 集合是 **ack-based**（未被讀取前持續通報），不是 seen-based。
3. 主通道為 **SessionStart**，輔通道為**寫入端回印**；條文層不作為承擔者。

**後續票須決定、本票刻意不決定的四項**（皆屬實作形態，寫在此處只為界定範圍）：

1. ack 訊號的取得方式與其載體落點。
2. 成本控制手段——實測預設範圍聚合 13.63 秒、SessionStart 已 44 支 hook，此值不可原樣帶入。
3. 推送範圍（是否限本 consumer 擁有的列、他方 consumer 新增列是否通報）。
4. 狀態遺失後的退化行為（首次執行與狀態檔缺失時的處置），以及誤報的可觀測定義。

**本票不產出任何實作細節**：上列四項只寫「要決定什麼」，不寫 schema、欄位、檔名或演算法。

### 七、規則 5 落地宣告（逐項）

本票為裁決票，產出為形態裁定與範圍界定；執行由 PM 依第五、六節派發。逐項宣告：

- **推送形態的實作（`todo` delta 推送 hook ＋ 寫入端回印）** — **無需建 ticket**：標的為 `.claude/skills/framework-issue` 與 `.claude/hooks/` 的框架通用資產，屬跨 consumer 問題，其載體為 canonical issue 的待辦列；而本票明示不對 canonical issue 寫入，故由 PM 決定落點（待裁列一列或本地實作票）後派發。在此建票會使同一決定有兩個入口。
- **`0.1.0-W3-318` 的 C1 十五項寫入待裁列** — **無需建 ticket**：本票只裁推送形態，該項為 `0.1.0-W3-318` 第八節方案甲的既有處置，已在 PM 手上，非本票新發現。
- **M2 其餘四項（`dedup` 收斂／`dedup` 旗標靜默／`show` body 提示／SR-4）** — **無需建 ticket**：本票僅判定其是否共用通道（第四節），未產生新的處置需求；SR-4 已於 `0.1.0-W3-307` 登記為 spawn request 待 PM resolve。
- **N 測作為跨項門檻的固化（是否寫入框架條文或方法論）** — **無需建 ticket**：本票不落條文；此判準是否值得固化屬 PM 對第四節結尾一段的裁決，不由本票預先建立。

本章節不含 spawn 規劃表格；上列每一項皆為明示的豁免宣告。
