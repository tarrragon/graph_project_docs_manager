# Execution Log

## Task Summary

修復 頁首標題「Domain 視圖」左側缺內距，文字貼齊內容區左緣

---

## Problem Analysis
### 問題根因

`SplitRow` 完全沒有實作水平內距，而頁首正是由它承載。

`page_column.dart:57` 的 `padding: EdgeInsets.all(Space.xl)` 只包住 `Expanded` 那一格（內容 slot 與其 `AnimatedSwitcher`）；頁首那一格是同層 `Column` 的另一個 child，寫法為 `SizedBox(height: LayoutSize.headerHeight, child: header)`，不在 `Padding` 之內。所以 ticket why 段的假設成立：內距在 `PageColumn` 存在，但標題不在那個容器內。

`SplitRow.build` 修復前為 `Row` → 直接 `SizedBox`/`DecoratedBox`，中間沒有任何 `Padding`。`PageTitle` 置於 `Expanded(child: leading)`，左緣即列的左緣。

**渲染樹實查證據**（非推論，`test/widget/app/shell_test.dart` 修復前紅燈輸出）：

```
Expected: <20.0>
  Actual: <0.0>
畫面「Domain 視圖」的頁首標題內距不符
```

`test/unit/components/split_row_test.dart` 四項水平內距斷言同時紅燈，四項的 `Actual` 皆為 `0.0`。

**規格契約**：SPEC-004 §4.29「使用 design token」間距列明訂「水平內距 `Space.xl`（頁首）/ `Space.sm`（底列、詳情卡）；左右格最小間距 `Space.md`」。三項中只有 `Space.md` 有實作，兩項水平內距從未落地。§4.28 `PageColumn` 的 token 表則只列「內容區內距 `Space.xl`」，未涵蓋頁首——規格對責任歸屬本身沒有歧義，是實作漏了。

### 影響範圍

`SplitRow` 的三種形態全部受影響，非只有頁首：

| 形態 | 規格值 | 修復前實測 | 使用點 |
|------|--------|-----------|--------|
| `header`（頁首） | `Space.xl` | 0 | `lib/app/shell.dart:120`，六個畫面共用 |
| `header` + `compactHeader`（詳情卡標題列） | `Space.sm` | 0 | 元件庫，畫面票尚未接線 |
| `footer`（Ticket 清單摘要底列） | `Space.sm` | 0 | 元件庫，畫面票尚未接線 |

六個畫面的頁首由 `lib/app/shell.dart:118-125` 的單一迴圈產生，共用同一份 `SplitRow.header`，故修 `SplitRow` 一處六畫面全修。

### 相關 Error Pattern

與 `0.1.0-W3-094` 同源：內距缺失不拋例外、不觸發溢位，既有的 `expectNoOverflow` 類斷言對它零鑑別力。`split_row_test.dart` 修復前已有 12 項測試全綠（含四項不溢位、兩項固定高、一項最小間距 `Space.md`），沒有任何一項會因水平內距為 0 而紅燈。

## Solution
### 修在 slot 而非畫面

ticket how 段要求論證「該修 `SplitRow.header` slot 本身（影響全部使用者）或該畫面（僅一處）」。選 slot，三個理由：

1. **規格已指名承擔者**。SPEC-004 §4.29 的 token 表把水平內距寫在 `SplitRow` 條目下，§4.28 `PageColumn` 的 token 表只列內容區內距。規格已經決定由誰承載，實作照做即可，不需重新裁量。
2. **改畫面修不完**。頁首雖由 `shell.dart` 單點渲染，但 `footer` 與 `compactHeader` 兩個變體的水平內距同樣缺失，且規格值不同（`Space.sm`）。修畫面只解一個變體，另兩個留給未來的畫面票各自踩一次。
3. **呼叫端不得覆寫**。§5.3 排列不變式對間距的措辭是「呼叫端不得覆寫」，把內距下放給呼叫端與該條文相斥。

### 改動

`lib/components/split_row.dart`：

- 新增 `_horizontalPadding` getter，與既有的 `_fixedHeight` / `_border` / `_background` 同一組變體衍生屬性，回傳 `Space.xl`（`header` 且非 `compactHeader`）或 `Space.sm`（其餘）。值取自 `Space` token，無硬編數字。
- `build` 的 `row` 外包一層 `Padding(padding: EdgeInsets.symmetric(horizontal: _horizontalPadding))`。**只設水平方向**：兩個固定高變體的高由 `_fixedHeight` 鎖定，垂直內距會壓縮子件可用高，且規格 token 表只講水平內距。
- 檔頭 dartdoc 補一句水平內距歸屬，並點名「父容器 `PageColumn` 的 `Space.xl` 只包內容 slot，不及於頁首 slot」——這正是本次的誤判點，寫在檔頭讓下一個讀者不必重查一次。

`test/unit/components/page_column_test.dart`：既有測試「間距使用 Space.xl token（非硬編碼）」原以 `find.descendant(of: PageColumn, matching: Padding)` 取唯一 `Padding`，`SplitRow` 加內距後該 finder 命中兩個而拋 `Bad state`。改為 `find.ancestor(of: AnimatedSwitcher, matching: Padding).first` 精確指向內容區那一個。**收窄而非放寬**：原斷言驗的是內容區內距，改後仍驗同一件事，只是不再依賴「樹裡只有一個 Padding」這個與斷言無關的巧合。

### 新增斷言

`test/unit/components/split_row_test.dart` 新增群組「水平內距（§4.29「使用 design token」間距列）」四項，量的是文字 `RenderBox` 左緣（或 trailing 右緣）與 `SplitRow` 自身 `RenderBox` 邊緣的距離，比對 token 值：

| 測試 | 斷言 |
|------|------|
| header：標題文字左緣與容器左緣的距離為 Space.xl | `titleRect.left - rowRect.left == Space.xl` |
| header：trailing 右緣與容器右緣的距離為 Space.xl | `rowRect.right - trailingRect.right == Space.xl` |
| compactHeader（詳情卡標題列）：水平內距為 Space.sm | `titleRect.left - rowRect.left == Space.sm` |
| footer（摘要底列）：左右水平內距皆為 Space.sm | 左右兩側各一 |

`test/widget/app/shell_test.dart` 新增「六個畫面的頁首標題左緣與頁面容器左緣距離皆為 Space.xl」，對應 acceptance 的「六個畫面一致」：起真實 `AppShell`，逐頁量標題文字左緣到該頁 `PageColumn` 左緣的距離。

三個測試設計決定：

- **取 `AppShell.pages` 的實例而非按型別搜尋**。`find.byType(PageColumn)` 在 `AppShell` 下命中 7 個而非 6 個——`TraceabilityScreen` 自建了一個巢狀 `PageColumn`（已建 `0.1.0-W3-127`）。改用 `find.byWidget(page)` / `find.byWidget(page.header)` 以身分定位，斷言不會因該缺陷修復與否而擺盪。
- **各處 `skipOffstage: false`**。`IndexedStack` 只繪製目前頁，其餘五頁預設會被 finder 跳過（實測：不加時第 2 頁「UC Flow」即找不到 `PageTitle`）；五頁皆已完成佈局，量測有效。
- **先 `expect(titleFinder, findsOneWidget)` 再取 widget**。直接 `tester.widget<PageTitle>` 在找不到時只拋 `Bad state: No element`，不說是哪個畫面；多一道斷言把失敗訊息換成畫面名。
