## Problem Analysis

### 派發前登記：skill-design-guide SKILL.md 的作者意圖清單（十項，B 批差集的分母）

1. 本檔整合官方 spec 與本專案慣例，聚焦「為什麼這樣設計」與「怎麼做」，不重述官方全文
2. Concise is Key：每段文字要過兩問（刪掉輸出會變嗎／值得 token 成本嗎），第一問問的是行為差異不是知識空缺
3. 三層載入的預算：第 1 層 description 250 字元、第 2 層 SKILL.md 全檔小於 5k tokens 且小於 500 行、第 3 層目錄總量無上限而單檔判準是讀取方式
4. 三個預算的適用對象各不相同，先認對象再量
5. token 估算要分段加總（非 ASCII 取 1.3、ASCII 取 4），不是全檔比例內插
6. 行數是官方合規項不是體量判準；兩個都量、取較嚴者
7. 第 2 層無 hook 執法，完全依賴撰寫者自查
8. 超標時外移什麼的判準在 splitting reference；分界是「讀者在選路之前還是之後用到它」，不是互斥性
9. 按需讀取六份 references 各有觸發條件；路由表的「涵蓋章節」欄要與目標檔的 `##` 標題逐字相同且雙向齊全
10. 發布前檢查清單分四組，其中觸發測試那一組目前無可執行程序、不是閘門

## Solution
<!-- Schema[DOC/Solution]: 免填（DOC 類型以變更摘要取代）（.claude/pm-rules/ticket-body-schema.md） -->
### 落地內容

`SKILL.md` 三處新增（〈正文是操作手冊，references 是它的依據〉、〈超標了怎麼辦——不是刪，也不是硬搬〉、檢查清單〈讀者可用性〉組）、四處壓縮、兩處前移；`splitting-an-existing-skill.md` 四處（路由表最小定義與四問語意、三類必查項、〈兩種驗證〉表修正、〈走完之後〉節）。逐項對照探針量測見 Test Results，此處不重述。

### 用戶追加的兩點都已落為條文

**「正文太長不是為了塞進容量而刪減或搬到 references」**——寫成〈超標了怎麼辦〉的四格診斷表，第四格明訂三項成因都不成立時「超標是設計問題，不是編輯問題」，不得為達標而刪判斷條件或搬進 references。

**「以 SRP 考慮把 skill 做拆分以及互相引用，而不是過度拆解到難以閱讀」**——寫成三段獨立條文：SRP 的單位是 skill 不只是檔案（把兩件事的細節各自外移，職責數量沒變）；兩種拆法的判別在讀者要不要換任務，並列出兩邊判錯各自的代價；過度拆解與超標是同一判準的兩端，預算只是其中一端的代理指標。元件庫的類比一併寫入：一個元件一份契約、組合由容器承載，而不是把所有元件塞進同一份條目靠參數分岔。

### 自檢結果

- **acceptance 1（正文與 references 的分工）**：`SKILL.md` 核心心法首節，含放正文／放 references 對照表六列與單一判準；探針量到的 2/3「文件沒說」即為此節的動因。
- **acceptance 2（檢查清單含探針審查、涵蓋改寫）**：〈讀者可用性〉組五項，標題即寫「新寫與**改寫**皆須」，末句說明改寫者為何是最讀不出缺口的讀者。
- **acceptance 3（三類必查項各附查法）**：兄弟檔互指矩陣不對稱（附 grep）、層級混疊（附並排比對法）、用詞定義與使用分居（附受管詞盤點法，並註明檔頭總括式不算數）。
- **acceptance 4（兩種驗證表已修正）**：欄名由「可機械執行」改為「誰能判」，拆分可用性由「否」改為「外部可量，作者不可判」，並補派發方式與「入口檔要單獨跑一批」。
- **acceptance 5（探針回報完成歸因，處置與不處置各有記錄）**：處置八項、不處置三項各附理由，見 Test Results 兩張表。
- **未做而應說明者**：
  1. **本次改動未經複驗。** 本版自己新增的〈讀者可用性〉第五項正是「修完再跑一次」，而該項對本次改動尚未執行——與前一票（`0.1.0-W3-302`）留下的缺口同型。已建子票承接。
  2. **本 skill 的 SKILL.md 現為 4608 tokens，距門檻餘 392。** 下次再加條文極可能再度撞線，屆時應重跑四格診斷而非直接壓縮；本次已示範一次，成因一（論證未壓）仍是最先該查的。
  3. **`splitting-an-existing-skill.md` 全檔 5669 tokens。** 依第 3 層判準（選段查閱看最大單節）合格，最大單節 1439；但全檔已超過整份執行者的門檻，若日後該檔的讀取方式改為整份執行即不合格。
