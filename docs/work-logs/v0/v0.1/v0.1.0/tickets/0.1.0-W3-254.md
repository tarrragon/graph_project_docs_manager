### 問題根因

十三張待派票積壓，成因不是排程，是它們全為 `.claude/` 框架資產而尚未過升級流程。用戶 09-08 的流程指正來自一次實際損失：一張本地票在未查重的情況下修了上游已知缺陷的第二條軌，本地修完會被 sync-pull 以上游舊版覆蓋，canonical 端無記錄。

十三張若照原樣派發，同一損失可能重演十三次。

### 影響範圍

十三張的標的分佈：ticket CLI（`ticket_system/` 五張）、hook 層（三張）、agent 定義（兩張）、框架 references（一張）、framework-issue 腳本（一張）、佔位符形態評估（一張）。全數隨 sync 分發至所有 consumer。

### 相關 Error Pattern

`PC-GPD-019`（形狀相符終止查證）。本票的方法設計直接受其約束：標題層比對顯示十三張各有候選承接 issue，但標題相符只證明主題相鄰。本票因此把「讀候選 issue 的 body 驗證涵蓋範圍」列為不可省的步驟，而該步驟當場推翻了一組候選（見 Solution 的 `#15` 段）。

### 驗證步驟推翻的一組候選：#15 不是 190 的承接者

標題層比對把 `#15`（`test_save_ticket_race` 的 gitignore 斷言以文字層 regex 對 monorepo consumer 造成 `*.lock` 誤傷）配給 `190`（create lock 檔名與 git 原生 ref lock 不可區分）。兩者共用 `*.lock` 這個字串。

讀 body 後不成立：`#15` 談的是**測試斷言把政策手段當政策目標**，`190` 談的是**檔名承載兩套相反語意**。主題相鄰、機制無關。190 改配 `#55`。

這一組是本票驗證步驟的唯一產出，也是它不可省的證明——若照標題層結果執行，該觀測會落在一個與它無關的 issue 上，且因為主題看起來相符，錯誤不會被任何人察覺。

### 兩項對上游裁決順序有影響的發現

**一、`#73` gate 住 150 與 152。** `#73` 若裁定除冊 `oregano`，152 整張作廢。觀測中另提一點供其裁決：**零派發可能是「用不到」，也可能是「派過一次、因定義缺陷失敗、之後沒人再派」**，兩者在 dispatch log 上同形；而 150 揭露的正是「主文承諾寫檔、frontmatter 無 `Edit`／`Write`」這類定義缺陷。單看派發計數不足以支撐除冊。

**二、`#33` 的驗收方向第 2 條射程未定。** 該條寫「HTML comment 形式的 Schema 標註維持不變」，意圖應是保護既有 `<!-- Schema[...] -->` 標註，但字面也可讀成「佔位符不得改成 HTML 註解」——後者會讓 195 的源頭修法在驗收階段出局，只剩 194 的偵測層。兩種讀法導向不同的最終形態，差別只在一句話的射程。
