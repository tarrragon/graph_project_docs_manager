### Phase 4 重構評估（補記，事後執行）

**背景**：本票走 Implementation 直接實作（無 TDD Phase 1-3b 循環），依 quality-baseline.md 規則 2「適用範圍不限 TDD 流程」，complete 前應執行等價多視角審查並記錄結論；當時漏執行，本節為 PM 要求後補記，不回退既成 commit（規則 6）。

**評估依據**：針對三個實際可能出問題的面向逐一分析（PM 指定範圍），非泛用重構檢查清單。

**1. `_TRACK_COMPLETE_PATTERN` 的誤報面**

`_has_track_complete` 是裸 regex（`track\s+complete\b`，大小寫不敏感）對整段自由文字 prompt 掃描，無白名單過濾。會誤觸的合法情境至少兩類：
- 否定句：「不要用 `ticket track complete`」「請勿使用 complete，改用 finish」
- Meta 引用：說明/討論這個機制本身時提及「track complete」（例如本票自己的派發 prompt、或未來討論此 hook 行為的 ticket）

比對同檔案內 `_has_wide_staging`（`_WIDE_STAGING_PATTERN`，PC-092 廣域 staging 偵測）：同樣是裸 regex 掃描、同樣無白名單，PM 舉的「不要用 `git add -A`」誤觸案例即發生在該處——兩者是同一種既有設計慣例（warn-only 偵測器一律不做否定句過濾），非本票新增的獨有缺陷。

`_detect_keyword_conflicts`（W5-045/W11-004.1.3）另有一套完整的 PER_MATCH_WHITELIST_RULES（引號/否定前綴/路徑上下文/meta-task），其中 `_has_negation_prefix` 簽名已是通用形式 `(prompt, start, end=None) -> (bool, str)`，理論上可直接復用於 `_has_track_complete`。

**判斷**：接受現狀，不在本票修正。理由：(a) 本檢查為 WARNING 不阻擋，成本僅一則可忽略的提示，非誤判即誤擋；(b) 警告文案已內嵌「若為合法引用可忽略」的免責句，緩解使用者困惑；(c) 與既有 `_has_wide_staging` 的既定慣例一致，非破壞既有一致性標準。已登記 SR-5（P3）追蹤，供後續視實際誤報頻率決定是否復用白名單。

**2. 呼叫點只在分支 (3)**

複查 main()：isolation="worktree" 可經四個路徑放行——(1.5) 審查模式關鍵字豁免、(1.6) `Dispatch-Mode: readonly` 首行宣告豁免、(2) 僅主 repo `.claude/` 的 ARCH-015 豁免、(3) 一般 worktree 放行（本票唯一有實作提示的分支）。isolation 參數由 PM 在 Agent 呼叫層宣告，CC runtime 是否實際建立 worktree（因而觸發 `complete` 誤判風險）取決於這個參數本身，與本 hook 走哪條分支放行無關。

**判斷**：這是覆蓋缺口，不是純粹刻意收窄的設計決策——當初選擇只覆蓋分支 (3) 是為了精準對應 0.1.0-W3-147 的實際樣態（非 `.claude/` 路徑 + worktree）與 acceptance 明列的測試情境，屬「先滿足已知需求」的範圍限縮，但未主動評估其餘三個分支的殘留風險。其中 (2)「僅主 repo `.claude/`」是較常見的落差：`.claude/` 類 ticket 收尾同樣要下 `track complete`/`finish`，若 PM 誤以為需要 worktree 而多宣告 isolation="worktree"，目前不會收到提示。(1.5)/(1.6) 語意上屬唯讀模式，實務搭配 track complete 的機率低，風險相對小。已登記 SR-6（P2）追蹤，修法明確（呼叫點上移至 isolation 讀取後即可，無需改動判斷邏輯本身），不在本票擴大修改範圍。

**3. `print` JSON 到 stdout 的碰撞風險**

複查全檔案僅一處呼叫 `_emit_worktree_complete_warning`（分支 (3) 內），函式內部以 `_has_track_complete` 短路、命中時才印一次 JSON，印完後該分支立即 `return 0`，故單次 hook 執行內最多印一次 JSON，無自我碰撞可能。跨 hook 碰撞方面：`.claude/settings.json` 的 `PreToolUse`/`Agent` matcher 下註冊多個 hook（`worktree-commit-before-dispatch-hook.py`、`agent-prompt-length-guard-hook.py` 等），但 CC runtime 對同一 matcher 下的多個 hook 是分別起獨立子行程執行，各自的 stdout 各自被 harness 解析為獨立 JSON envelope，非同一串流串接——與 `askuserquestion-reminder-hook.py` 等既有印 JSON 的 hook 共存的既有模式一致。`run_hook_safely` 包裝層本身不額外印 stdout（只在錯誤路徑寫 log 檔），不構成第二個輸出來源。

**判斷**：無實質碰撞風險，不需處理，SR-4（`_WIDE_STAGING_WARNING` 通道問題）性質不同——那裡是「stderr 在 exit 0 時不被注入」的可見性問題，不是本項評估的「多段 JSON 互相覆寫」問題，兩者判定對象不同，此處確認不追加同類 spawn request。

**最小產出四項**：

- 重構需要：否
