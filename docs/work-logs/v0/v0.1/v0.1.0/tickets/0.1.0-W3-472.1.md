### 實驗發現

**已驗證事實**

1. 分界的兩個前提在非範例條文中都有出處：容器管的是兩個元件之間（S1、S2），內距無排列關係且歸子件組合規則或容器格位（S4、S5）。
2. 沒有任何一處把這兩個前提合寫成「內距 vs 鄰件間距」的分界句；唯一合寫的位置是範例檔（S8）。
3. DOC-19a 那一題的具體失敗結構（允許句只在佔位符內）已於 W3-469 消除：現行引言 S7 直接允許欄內距，探針只讀現行引言即可答 (a) 可。
4. W3-472 NeedsContext 的「已刪範例」為誤述，S8 於 HEAD 仍在。
5. S4 的句子主詞是「單一子件的包裝」，位在容器候選盤點步驟內；讀者為了填組合規則而翻方法論或範本時，不會走到該句。分界可推得，但推得它的前提散在三份檔案的三個不同用途段落。

**仍未驗證的假設**

- 改文後探針是否 3/3 通過——本票未重跑探針。
- 除表格欄外的其他內距情形（元件與容器邊緣、元件內部兩處內容之間）在實際填寫時的出現頻率，無資料。

## Solution
### 一、判定：不是新判準

分界所需的前提在既有**非範例**條文中都有出處（見〈重現實驗結果〉S1、S2、S4、S5），可逐詞推得；缺的是「沒有任何一處把前提合寫成一句分界」，而唯一合寫的載體是範例檔（S8）。這正是 W3-417 既有的風險類別「依據只在範例內」，不是判準本身不存在。

附帶結論：DOC-19a 那一題的具體失敗已由 W3-469（72f56cc0b）消除——現行範本〈組合規則〉引言已含 S7「作為表格或列表的一欄時，本列填欄比例或固定寬與欄內距，皆引用 token」，只讀現行條文即可答 (a) 可。**剩餘缺口不是那一題，是那一題以外的情形**（見下方兩則判否反例）。

### 二、分界條文草案

> 「不得另定間距」的射程依該段距離的**兩端各是什麼**判定：

| 距離的兩端 | 管轄 | 依據 |
|---|---|---|
| 一個元件 ↔ 另一個元件 | 容器的排列不變式「最小間距」；子件的組合規則不得另定 | S1、S2、S3 |
| 本元件的內容 ↔ 本元件自身的邊界（內距） | 本元件的組合規則；作為表格或列表一欄時填在該列 | S4 前半、S6、S7 |
| 本元件的邊界 ↔ 容器或格位的邊界 | 所屬容器的契約（格位），不填在本元件的組合規則 | S4 後半 |
| 本元件的內容 ↔ 本元件的另一處內容 | 本元件自身實作，登記於 design token 依賴表的「間距」列，不進組合規則 | **本次新增**（由 S6 射程全為對外關係、加範本 design token 依賴表既有「間距」列推得，無直接出處） |

> 兩端皆非上列四種組合者（如兩個容器之間），對兩者的共同上層重問一次同一問句，由該層承載。

**逐詞可推的檢查**：讀者只需回答一個問句「這段距離的兩端各是什麼」，即落入唯一一列；四列的鍵互斥，兜底句處理未列組合。不需要知道 padding／margin 的框架語彙，也不需要知道元件的視覺外觀。

**判否反例（兩則，皆非探針題的同構）**

1. **容器內縮被誤判為內距**：某「提示橫幅」元件固定用在設定頁的對話框內，撰寫者想在它的組合規則寫「與對話框內緣保留 `spacing-md`」。**判否**——兩端是本元件的邊界與容器的邊界，落第三列，屬對話框容器的格位。照填的後果是同一元件放進第二個容器時該值失效，而元件自己的測試不會紅（與方法論〈容器亦為元件〉Consequence 段的事故形態同源）。
2. **元件內部兩處內容被誤判為內距**：某「同步狀態列」元件由狀態圖示與其右側說明文字組成，撰寫者想把兩者之間的距離填進組合規則。**判否**——兩端都是本元件的內容，落第四列，屬本元件自身實作，登記於 design token 依賴表的「間距」列；組合規則整欄問的是本元件**對外**的關係（可放進哪些容器、禁放區、對齊基準、作為一欄時佔多寬與內距，S6）。

> 正向情形（表格欄內距可填）不另造例示：現行範本引言 S7 已是逐字條文，另造例示會與 W3-417 探針題 DOC-19a 同構。

**理由**

1. 被界定的禁令句（S3）本身在方法論該節，射程說明與禁令同處，讀者不需跳檔就取得完整規則。
2. 兩個消費端本來就明文指向該節——範本引言括號逐字寫「（方法論〈容器亦為元件〉）」、`step-2-path-a-spec-derivation.md` 步驟 4 逐字寫「判準是元件庫雙向約束方法論〈容器亦為元件〉的判別問句」。主文放在**已被引用的位置**，兩端各補一句路由即可，不產生第三份副本，避開「同一判準多處分叉」。
3. 分界的兩個前提 S1（判別問句）、S2（最小間距列）同在該節；主文落別處會把前提與結論拆到兩份檔案。

**不落 doc 範本的理由**：範本會被複製進每個專案，既有取向是「維持範本精簡可複製」（4aec4afc5 commit message 逐字，屬 doc skill 既有取向，非本次用戶偏好）；且範本已有 S7 涵蓋最常見情形，再放整張四列表等於把方法論搬進範本。
**不落 component-contract-design 的理由**：S4、S5 分別長在「判容器候選」與「掃原生佈局」兩個不同用途的步驟裡，主文落那裡，填 doc 規格的讀者不會走到。
