**PM 補充（其中一條 tripwire 的條件形態今日改變，2026-09-08）**

本票要為 tripwire 總表中無偵測承擔者的條目指名觸發條件。其中一條在票面成文後**條件形態被新落地的方法論改動了**，指名時須一併處理。

**受影響的條目**（已驗證：`docs/tech-decisions.md` L576）：

> 出現無法由破洞報告解釋的故障 → 重評 structured log 的延後決定 → 承接者：**待指名**（`0.1.0-W1-013` 裁定維持延後並保留本條，但該票已完成，未指派偵測者）

**新落地的條文**：`.claude/methodologies/clean-architecture-implementation-methodology.md` 的〈Port 回饋契約〉，子節〈時序約束〉（commit `8db1f6d4`）。以標題文字引用，不寫 URL fragment。該子節主張：log 與 APM 追蹤**不是事後可補的能力**——它們消費的是設計期就要決定的回饋點；設計期沒把回饋點寫進 port 契約，事後補記錄只能拿到例外堆疊，拿不到「呼叫發出了、外部系統收到了、結果是什麼」這三個時刻。

**這對本條 tripwire 的意義**：原條件是**事後偵測型**——等「出現無法由破洞報告解釋的故障」才重評。但若回饋點未在設計期定義，故障出現時能拿到的資訊已經被限制住了，重評的時點正好是最無從判斷的時點。換句話說，**這條 tripwire 的觸發條件與它要保護的東西之間有時序落差**，而該落差是本票要指名條件時應該處理的。

**不是要求本票推翻延後決策**：`docs/tech-decisions.md` L951 已明確區分——可觀測性規則 1／3／5 講的是「失敗發生時資訊不要消失」，延後的是「建一套 structured log 系統」，兩者不同層次。〈時序約束〉落在前者（設計期定義回饋點，成本近乎為零），不觸及後者。本票指名條件時請維持這個區分，不要把它讀成「該實作 structured log 了」。

**可能的處理方向（供參，非結論）**：本條的偵測承擔者或許不該是「等故障發生的人」，而是「新增 driven port 時的設計審查」——即把事後偵測改為設計期關卡。若採此方向，須確認該關卡有實際載體（會紅燈的測試、會被執行的 ticket、會擋下操作的 hook），不能只是散文複述——`docs/tech-decisions.md` L580 附近已明訂 tripwire 需有實際載體，散文複述與本表原本的問題同型。

**其餘條目不受影響**：本補充只涉及 structured log 這一條，其他條目的指名工作照票面進行。
