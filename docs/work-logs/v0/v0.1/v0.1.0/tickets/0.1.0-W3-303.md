## Problem Analysis
### 問題根因

**`add` 與 `observe` 的分界在協定裡是三處各自局部定義、且互相不引用的結果，票面指定的射程處對它完全沒有說法。**

票面把 `comment-as-section-protocol.md`〈增長語意與 close 語意〉指為此判斷的射程所在。實讀該節全文（該檔 `## 增長語意與 close 語意` 到 `## 已知限制` 之間）：內容為兩段，一段講 open issue 數增長不是失效訊號（單位是 issue 張數），一段講 close 代表當前結論暫時穩定，另加一行與 fix-matrix close 的層次區隔。**全節無 `add`、無 `observe`、無區段數量的任何字樣**。

因此第一項結論為據實記錄：**〈增長語意與 close 語意〉對 add／observe 分界未定義**，本票不替它決定。該節射程是「issue 張數」與「close 動作語意」，不是「一張 issue 內的區段配置」。

分界實際可推導的來源有三處，分散在兩份檔案與一份代理人定義：

| 來源 | 條文 | 給出的軸 |
|------|------|---------|
| `comment-as-section-protocol.md`〈操作一覽〉 | `add`＝任何 session 建自有區段並成為 owner；`observe`＝附加實測／反證／疑慮，不需 owner、不需協商 | 產出形態（結論／狀態 對 觀測） |
| `comment-as-section-protocol.md`〈init 前查重：三種關係處置〉 | 重複→「併入既有 issue，以區段或觀測附加」；切分→建新 issue；引用→「單向指向即可」 | 與既有 issue 的關係 |
| `ticket-intake.md`〈前提與分工〉2、〈步驟二：查重與落點〉 | 對方認領的主題本方只加 `observe`；主題已有 open issue 且已被他方 `init`→`add --owner <本方識別>` | 認領歸屬 + 收束場景落點 |

### 實驗發現

**已驗證的事實**：

1. 〈增長語意與 close 語意〉全節無 `add`／`observe`／區段數量字樣——分界在該節未定義（acceptance 1 的據實記錄部分）。
2. 一張 issue 內有多則「當前結論*」是既成的 canonical 現況，非假想：`#92` 三則（三個 owner）、`#97` 兩則（同一 owner、不同主題）。後綴的分割單位是**主題**，不是 consumer，也不是 issue。

4. 但 `check` 的觀測流不分流：N 則當前結論全部與同一條觀測流比對，故 `add` 使每一則新觀測同時對 N 個 owner 計時，跨射程誤報隨區段數線性增加。這是 `add` 的實際代價，且與「兩個結論入口」是不同的一件事。
5. 索引表只有名稱與連結兩欄，無射程與權威標示；讀者側唯一的射程資訊是區段名的後綴，而後綴是 `ticket-intake.md` 的命名慣例，`comment-as-section-protocol.md`〈已知限制〉自承工具不檢查名稱重複。
6. `#54` 上那三則累積中的觀測屬**本 consumer 的前代 session**，不是他方——`ticket-intake.md`〈前提與分工〉2「對方認領的主題本方只加 `observe`」對該情形不適用。`0.1.0-W3-298` 選 `observe` 的實際依據與它所引的依據不是同一件事（見 Solution 二）。
7. 協定檔〈已知限制〉指向的〈以 add 加進他方已 init 的 issue 時〉**不在該檔內**，實際位於 `ticket-intake.md`；跨檔錨點斷裂，而該處正是後綴慣例（第 5 項所述唯一的射程機制）的權威所在。

**仍未驗證的假設**：本票未新增任何區段，第 4 項的跨射程誤報為原始碼推導 + 現況佐證，未以新製造的觀測直接觸發一次警訊 B 命中。

## Solution
### 一、分界判定（acceptance 1）

**票面指定的射程處未定義**：`comment-as-section-protocol.md`〈增長語意與 close 語意〉對 `add` 與 `observe` 無任何說法，其射程是 issue 張數與 close 動作語意。本票據實記錄並停在此結論，不替該節決定。

**分界可從協定其他既有語意推導，但有一格明文留白**。推導出的判準為二維查表（軸皆取自協定既有條文，未新造）：

| 關係判定（〈三種關係處置〉） | 產出形態 | 協定既有條文給出的載體 | 依據 |
|------|---------|------------------|------|
| 引用（僅提及、領域不同） | 任何 | `observe` | 「單向指向即可，不需互標」——單向指向且不改對方內容，唯一相符的操作是 `observe` |
| 切分（同領域、不同層級） | 任何 | 新 issue 後 `init` | 〈步驟二〉落點表第四列 |
| 重複（同領域、同層級） | 實測／反證／疑慮 | `observe` | 〈操作一覽〉`observe` 的用途逐字為「實測、反證、疑慮」；`SKILL.md` 決策表「對既有 issue 補實測、反證、疑慮→`observe`」 |
| 重複（同領域、同層級） | 一群本地票的收束結論與待辦 | `add --owner <本方識別>` | 〈步驟二〉落點表第二列「主題已有 open issue 且已被他方 `init`→`add --owner <本方識別>`」 |
| 上兩列的交集或難分時 | — | **協定未給判準** | 〈三種關係處置〉「重複」格逐字為「以區段或觀測附加」，兩個選項並列、無擇一條件 |

**覆寫條款一條**（優先於上表）：主題已被同機器活躍的他方 session 認領時，本方一律只 `observe`（`ticket-intake.md`〈前提與分工〉2「對方認領的主題，本方只加 `observe`，不 init、不 close 對方列出的票」）。此條以「認領」為判準，與 owner 是誰無關。

**缺口的精確位置**：不是整個分界沒定義，而是「重複」格的兩個選項之間沒有擇一條件，而收束落地的多數情形正落在該格。第二檔處置若要指名載體，要補的是這一格，不是整張表。
