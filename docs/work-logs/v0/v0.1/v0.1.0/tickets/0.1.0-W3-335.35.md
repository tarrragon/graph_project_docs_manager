- **W**：(1) 草稿：只列「When 或 Then 會實際讀取」的狀態；(2) .27：「未被讀取者不列」（禁止）；(3) 反向框架：維持全部前序狀態（與範例檢驗問句相反）；(4) 以「依賴」界定下限，上限不設（本評估採用）。
- **R 事證**：原條文目的是「不可假設各 GWT 場景獨立」，即防止漏列必要前提——這是下限問題。草稿的「會實際讀取」在種子階段不可判定：種子由 UC 文字產出，尚無實作，無從得知系統內部讀取哪些狀態（例：原舉例的 session，Then 不提及但步驟無 session 即無法執行）。可判定的判準是「缺少該狀態時，本步驟的 When 無法執行或 Then 結果會不同」。原條文舉例保留並加條件，會讓舉例變成條件句，讀者仍先讀到「涵蓋全部」，應改寫舉例。
- **A 被放棄選項的代價**：採草稿「會實際讀取」→ 種子作者以猜測實作為判準，session 類隱性前提被漏列，下游測試假綠；採 .27「不列」→ 把可讀性取捨升格為禁令（見下方交用戶項）；維持原條文 → 範例檢驗問句持續無依據句。
- **P**：失敗原因＝作者把「依賴」理解成「文字上被提及」。可觀測訊號：Given 未含登入／session 類前提，但 When 為需驗證身分的操作。
- **定稿條文**（取代〈轉換注意事項〉跨步驟狀態累積一條）：

  > **跨步驟狀態累積**：UC 步驟有序，後續步驟的 Given 必須包含本步驟所依賴的前序累積狀態，不可假設各 GWT 場景獨立。「依賴」的判準：缺少該狀態時，本步驟的 When 無法執行，或 Then 的結果會不同。不符合此判準的前序狀態不必列入 Given。例：步驟 3 為「使用者查詢自己送出的事件」時，其 Given 須含步驟 1 建立的 session（無 session 無法查詢）與步驟 2 送出的事件（無事件則 Then 不同）。

  連帶：範例一第二則檢驗問句的「只列 When 會讀到的前序狀態」改為「只須列本步驟所依賴的前序狀態（判準見跨步驟狀態累積一條）」。
- **風格偏好，交用戶**：未被依賴的前序狀態「可以列入」（寬鬆，定稿採此）還是「不得列入」（.27 建議）。寫法差異：寬鬆＝Given 可順帶描述完整情境，閱讀時較接近 UC 敘事，但種子較長、依賴與非依賴混在一起；禁止＝Given 只剩必要前提，一眼看出步驟依賴什麼，但讀者要回頭讀前序步驟才知道完整情境。兩者都不影響測試正確性。

#### W39（起點 B 步驟 B3 粒度）

- **裁決**：修改後採用；混合測試的拆法為風格偏好，交用戶。
- **W**：(1) 草稿：任一斷言追溯不到 → 整則標無規格來源；(2) 反向框架：任一斷言可追溯即算有來源；(3) 斷言級標記、測試不標；(4) 整則標記，但後續判定作用在追溯不到的斷言上（本評估採用）。
- **R 事證**：B1、B2 已是斷言級（逐檔記錄斷言對象、反向追溯每個斷言），B3 突然改為測試級，粒度斷裂。支持整則標記的事證：`layered-test-strategy.md`〈分層之外的補位形態〉characterization test 段「與正確性測試混用會讓紅燈無法歸因」——混合測試不能當作乾淨的有來源測試。草稿的缺口在後續：整則測試進入「characterization 或應刪除」判定時，刪除會一併移除可追溯的斷言，B4 隨即把該規格條目報為缺口，形成刪了再補。
- **A 被放棄選項的代價**：反向框架 → 混合測試計入有來源，紅燈歸因失效；純斷言級 → 目錄上看不出哪則測試是混合的，混用問題不現形；草稿原文 → 刪除判定可能帶走有來源斷言。
- **P**：失敗原因＝判定「應刪除」時整則刪除。可觀測訊號：B3 判定刪除的測試，在 B4 掃描時其可追溯斷言對應的規格條目出現為新缺口。
- **定稿條文**（B3 動作欄改寫）：

  > 追溯不到的測試標記「無規格來源」：一則測試只要有任一斷言追溯不到規格條目，整則即標記（混用會使紅燈無法歸因，見 `references/layered-test-strategy.md`「分層之外的補位形態」節）。後續判定作用在追溯不到的斷言上：判定是否為 characterization test 或應刪除；可追溯的斷言保留為有規格來源的測試，不隨判定一併刪除。
- **風格偏好，交用戶**：混合測試處置後的寫法。寫法 A：拆為兩則測試（一則只含可追溯斷言、一則為 characterization 或刪除），每則測試單一性質、紅燈即可歸因，代價是測試數增加、共用的 setup 要重複或抽出。寫法 B：同一則測試內移除或改寫追溯不到的斷言，測試數不變，代價是 characterization 斷言若保留須另立一則，否則等於刪除。定稿條文只規定「可追溯斷言不得隨之刪除」，拆法不代定。

#### W40（起點 C 步驟 C2「公開介面」）

- **裁決**：(a)(b) 兩種解讀皆否決，採第三解讀：以可呼叫的公開進入點為單位。
- **W**：(a) 公開介面＝公開方法；(b) 公開介面含屬性、事件等非方法成員，各自一條；(c) 可呼叫的公開進入點（公開方法、模組層級公開函式、以函式實作的存取子），事件等輸出記入觸發它的進入點條目（本評估採用）；反向框架：以公開類別為單位（範例已明文否定）。
- **R 事證**：C2 的來源欄格式為 `code: {檔案}:{函式}`，要求條目有函式識別子；characterization test 的定義是「對現有程式跑一次、把實際輸出記錄成預期值」（layered-test-strategy.md 同節），要求條目可被執行。(a) 的「方法」字面排除模組層級公開函式（無類別的函式在多數語言是常見公開介面），這類程式碼走 C2 會漏條目且 C1 覆蓋性檢查無從發現。(b) 的事件、屬性沒有 `{函式}` 可填、無法獨立「跑一次」，其行為須經某個方法觸發才能觀察，另立條目會與觸發它的方法條目重複觀察同一次輸出。
- **兩種解讀的結論**：(a) 否決——措辭精確化過頭，改變了模組層級函式的判定（原「公開介面」字面包含它們），不是無判定變更；(b) 否決——與來源欄格式及 characterization test 的執行前提不相容。
- **A 被放棄選項的代價**：(a) 模組層級公開函式漏登；(b) 條目數膨脹且產生無 `{函式}` 可填的列，C2 欄位完整判準下必然不合格。
- **P**：失敗原因＝存取子是否算進入點的邊界爭議。可觀測訊號：目錄中出現來源欄為屬性名而非函式名的列。
- **是否改變既有判定**：以類別方法為主的程式碼，與現行範例結果相同；對模組層級函式，與「公開介面」字面一致，不改變；僅相對 (a) 的讀法有差異。
- **定稿條文**（C2 動作欄改寫）：

  > 若無規格 / 使用案例 → 以程式碼為來源建 characterization test 目錄，每個可呼叫的公開進入點一條（公開方法、模組層級的公開函式、以函式實作的公開存取子）；事件、串流等由進入點觸發的輸出，記入觸發它的進入點條目，不另立條目。來源欄標 `code: {檔案}:{函式}`，同時建議補撰規格。

  連帶：〈characterization 條目粒度範例〉開頭句改為「以可呼叫的公開進入點（此例為公開方法）為單位，而非以公開類別為單位」；第二則檢驗問句預期改為「隨公開進入點數量增加，此例為公開方法」。

#### W41（UC 步驟→GWT 拆分規則）

- **裁決**：修改後採用；同一 When 下多個獨立結果是否拆種子為風格偏好，交用戶。
- **W**：(1) 草稿：凡可獨立驗證的預期結果各拆一種子；(2) 反向框架：一步驟一種子，多結果寫多條 Then；(3) 依 Given／When 是否不同分流（本評估採用）。
- **R 事證**：〈轉換範例〉的 5a、5b 兩個結果對應不同 When（未帶／帶篩選條件）與不同 Given——一個 GWT 只有一個 When，這一類必須拆，屬正確性。但草稿判準「各自可獨立斷言」同樣涵蓋「同一 When 產生兩個結果」（例：送出後資料已儲存且畫面顯示成功提示），這一類拆成兩個種子或寫一個種子兩條 Then，測試都正確，差別是一則測試一個斷言還是多個斷言——屬測試寫法取捨。另草稿未處理檔頭句「每個 UC 場景步驟轉換為 GWT 格式的行為場景種子」，字面仍是一對一，與新規則並存會矛盾。`doc-handoff.md`〈追溯矩陣建立範例〉的「步驟 1 拆為 1a、1b」未說明屬哪一類，不受影響。
- **A 被放棄選項的代價**：草稿原文 → 替用戶決定「一則測試一個斷言」風格；反向框架 → 不同 When 被塞進同一種子，GWT 結構失效。
- **P**：失敗原因＝作者把不同輸入分支誤當成同一 When 的多個 Then。可觀測訊號：種子的 When 欄含「或」「若…則」等條件分支字眼。
- **定稿條文**：檔頭句改為「每個 UC 場景步驟轉換為一個或多個 GWT 格式的行為場景種子（拆分規則見〈轉換方法〉）」；〈轉換方法〉表後補：

  > **一步驟多結果的拆分**：一個場景步驟宣告多個預期結果，且各結果對應不同的 Given 或 When（不同輸入分支、不同觸發條件）時，每組 Given／When 各拆為一個種子（例：5a、5b），因為一個 GWT 只有一個 When。同一組 Given／When 產生多個預期結果時，{用戶裁決後填入：拆為多個種子／寫為一個種子的多條 Then}。

  連帶：〈轉換範例〉第二則檢驗問句補「兩個結果的 When 不同（未帶／帶篩選條件）」作為拆分理由，引用上段。
- **風格偏好，交用戶**：同一組 Given／When 的多個獨立結果。寫法 A：拆多個種子，每個測試一個斷言，紅燈直接指出哪個結果壞，代價是同一次操作的 setup 與 When 重複、測試數增加。寫法 B：一個種子多條 Then，一個測試多個斷言，貼近 UC 敘事且 setup 不重複，代價是第一個斷言失敗時後續斷言不執行（多數測試框架），一次紅燈只看到一個問題。

#### W43（UC 成功保證→驗收標準）

  連帶：〈驗收標準轉換範例〉第二列轉換結果改為「原文照抄，標〔不可量化〕」，檢驗問句引用本列。
