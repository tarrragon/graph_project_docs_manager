## Solution
### 結論

改版對第一輪缺口的實際效果，**不是整體消失，也不是整體未變**：22 項既有缺口中 6 項消失、2 項位移、8 項換形態、6 項未變。消失的集中在「條文沒說」這一類（落地形態、issue 端載體、路由、區段操作指引）——這類缺口靠寫字即可關掉。未變的集中在「需要改機械層或改結構」這一類（章節順序、`check` 觸發器、`dedup` 命中規模、部分觀測門檻、觀測型工作無類別）——這類缺口在純條文層的改版中結構性不會動。

**最值得注意的一項**：改版為了修 F1（owner 識別未提供使 curator 只能 observe）而在〈派發 curator〉範本寫入 owner 識別行與填寫紀律段，但該段給的範例值 `graph-project-docs-manager-5d`（也正是本次派發給本 session 的識別值）**經 CLI `validate_owner()` 實跑為不合法**（序號段限純數字）。照著範本填的人會在 `add`／`init` 被 exit 3 擋下，降級為 `observe`——與 F1 的後果逐字相同，只是成因從「漏填」換成「照範本填」。缺口沒有消失，它換了一個形態留在原處。

### 三、重點必測其二：「消費端」拆分後是否仍讀得出兩義

**對條文自訂 fallback 條件的判定：不成立於原處（消費端），成立於新處（擴散面判準第二列）。**

拆分後以 `#103` 四項探針（`0.1.0-W3-299` 失效點 1-2 的同一輸入）重走：

| 列 | 本次答案 | 是否還讀得出第二義 |
|----|---------|------------------|
| 執行條件已觀測 | 是 | 否。「在什麼情況下被執行、執行時讀到什麼」只指向探針實測，正向對照 `sed -i` 已證明 hook 掛載中且警告管道通暢 |

| 合成 | 否（任一為否即為否） | 合成規則為明文，無自由心證空間 |

### 四、改版引入的新缺口（與既有缺口分開列）

**N1（最高）：〈派發 curator〉範本給的 owner 識別範例值不合法，且與 CLI 的實際規則相斥。**

`ticket-intake.md` L160 的範本寫「owner 識別：<專案 kebab>-<session 序號>（範例格式：`graph-project-docs-manager-5d`；換成本次派發的實際值，不得留占位符）」，L171 另以整段「填寫紀律」強調漏填的後果。實跑 `validate_owner()`：regex 為 `^[a-z0-9]+(-[a-z0-9]+)*-[0-9]+$`，序號段限純數字，`graph-project-docs-manager-5d` FAIL。本次派發給本 session 的識別即為該值（與範例逐字相同），因此本 session 在 `add`／`init` 上被結構性阻斷。**這正是這段文字要治的那個後果**（curator 降級為 observe、結論落在觀測流、不受 `check` 主警訊涵蓋），成因從「PM 漏填」換成「PM 照範本填」。修這一項有兩個互斥方向（範本改用純數字序號範例，或 CLI 放寬序號段），本票不選定。

**N2：兩義由「消費端」位移至擴散面判準第二列的「機械訊號」，且該列與守衛類修法的失效方向相斥。**

條文原句：「為 False（隨 sync 擴散）且本 consumer 內有機械訊號（測試紅燈／hook 阻擋／CI）**會在修法錯誤時顯示**」。守衛類修法的錯誤有兩個方向：誤擋（有訊號）與漏放（沉默）。條文未加方向限定詞，同一修法可判第一檔或第二檔。與 `test-assertion-design-rules` 規則 E2 同型（「守衛的失效方向是放行，放行與輸入本來就沒問題在輸出上同形」），而兩份文件互指仍為 0。

**N3：合成規則與擴散面判準互為前置，有次序循環。**

「使用者群已觀測」一列的填法（L58）要求「擴散面判定為第一檔時填『不適用』」，即擴散面是回答四問的輸入；而同節 Action（L68）寫「三問任一為否時，**先依下表判定擴散面歸檔**」，即擴散面是四問的輸出。執行者無從得知先算哪一個。此循環在第一輪不存在（原條文的擴散面純為後置分流），屬改版引入。
