why: '建票 CLI 的兩處介面行為與使用者的合理預期不符，且**兩者都無法從 `--help` 看出來**。


  **其一：Context Bundle 的自動抽取只認 `--source-ticket`。** `--discovered-during` 不觸發抽取——兩個旗標在這件事上不等價，而 `--help` 只說明語意差別（發現衍生 vs 規劃衍生、是否繼承主題），沒說其中一個會決定 Context Bundle 是否存在。


  後果：只給 `--discovered-during` 建出的票沒有 Context Bundle，`dispatch-validate` 規則 1 硬性失敗，而失敗訊息說「Context Bundle section 不存在」——**不指向真正成因**（建票時選了哪個旗標）。


  **其二：`--acceptance` 不以逗號分隔**，整串當一條收下。而同一支 CLI 的 `--where` 吃逗號分隔。兩者的 `--help` 描述看起來同構，**使用者從介面上得不到區分的依據**。


  後果：以逗號傳入多條驗收條件時只會得到一條。若該票恰好只需三條以上才過門檻，會被規則 4 擋下（有訊號）；若不足門檻的檢查未觸發，則靜默少條（無訊號）。


  **三個實例，其中一個是決定性的**：


  1. PM 於 2026-09-08 建的 `0.1.0-W3-089` 與 `0.1.0-W3-087` 皆只給 `--discovered-during`，兩張都缺 Context Bundle，由並行 session 於派發前查證發現。

  3. **並行 session 在同一 session 內完整診斷了問題其一、把診斷寫成訊息送出，兩小時後照樣以 `--discovered-during` 建了兩張缺 Context Bundle 的票。**


  第三個實例是本票方案選擇的決定性依據：**文件化不足以擋住它**。建票當下人在想票的內容，不在想 CLI 的參數語意——連剛寫下診斷的人都擋不住。因此「改錯誤訊息」或「補文件說明」都不夠：訊息只在失敗之後出現，而失敗發生在建票之後。要擋住必須在**建票當下**。

### Rationale Chain
- 0.1.0-W3-089 why: `bash-tool-usage-details.md` 的隔離索引 CAS 配方寫得對——步驟 1 明訂 `OLD_HEAD=$(git rev-parse HEAD)` 釘選基準，步驟 3 `read-tree "$OLD_HEAD"`、步驟 6 `commit-tree -p "$OLD_HEAD"`、步驟 8 `update-ref HEAD "$COMMIT_SHA" "$OLD_HEAD"` 全部用該變數。但配方沒有說明**不釘選會怎樣**，而「把 `$OLD_HEAD` 換成 `HEAD`」是一個看起來完全等價的替換。

實測命中（commit `4bd0e2ac`，PM 執行）：`read-tree HEAD` 與 `commit-tree -p HEAD` 分屬兩次 Bash 呼叫，其間並行 session 提交了 `eab601b2`。結果是 tree 取自舊 HEAD、parent 指向新 HEAD——**該 commit 靜默回滾了 `eab601b2` 對 `0.1.0-W3-088.md` 的變更**（`blockedBy` 被清回 `[]`）。

三層防護同時失效，而每一層單看都「通過」：

| 防護 | 為何沒擋住 |
|------|-----------|
| 要件 2（`GIT_INDEX_FILE`） | 確實生效——共用 index 全程未被觸碰。它保護的是寫入端，不保護基準的新鮮度 |
| 要件 3（tree 層級自檢） | 用 `$OLD_HEAD` 比對時必然通過：tree 相對它就是只有預期的檔案。要察覺得比對**新** HEAD |
| 步驟 8 的 CAS | 舊值寫 `HEAD` 時自我解析為當前 ref，比較必然相等——CAS 的全部保護力來自釘選舊值，不釘選等於沒有 |

現有的「完整性三要件」章節涵蓋不到這個模式：三要件談的是清單來源、寫入隔離、範圍自檢，全都是**空間維度**（提交了哪些檔案）；本案是**時間維度**（基準有多新），與規則七既有的「版本邊界（過期 index 快照）」同源，但發生在隔離索引路徑上——而該路徑正是被推薦用來取代共用 index 的做法，讀者不會預期它有同型風險。
