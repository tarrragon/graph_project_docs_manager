## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`section_comment.py` 的 `validate_owner`（`OWNER_FORMAT_RE = ^[a-z0-9]+(-[a-z0-9]+)*-[0-9]+$`，`init`／`add`／`transfer-owner` 共用）要求 owner 尾碼為純數字；而 owner 值的唯一供應端是 session 短名（`ListAgents` 首行名稱，等同跨 session 訊息的 `from-name`），其尾碼實測為兩碼十六進位，字元集含 a-f。寫入端（純數字尾碼）與讀取端（三個消費點皆為 `startswith(f"{prefix}-")` 前綴比對）採兩套判準，尾碼寫入後從未被任何讀取端解讀——此為候選根因表述。

### 影響範圍

**已驗證的事實**：

1. 受影響檔案：`.claude/skills/framework-issue/scripts/section_comment.py`（`OWNER_FORMAT_RE`／`validate_owner`）、`references/comment-as-section-protocol.md` 的 owner 識別格式段、`references/ticket-intake.md` 的 owner 識別行段。
2. 不是本專案特有：13 個真實 session 名跨三個 consumer，4 個被擋，其中 `blog-cd` 屬第三個 consumer（非本專案、非 flutter-balance）。
3. 不是本專案結構性不可用：`#92` 有 4 則、`#95` 有 3 則區段的 owner 為本專案 session（`-59`／`-66`），為世界平面查證（`show 92`／`show 95`）。**票面 why 段「本專案至今無任何 session 可通過該驗證」「歷次 curator 派發全數降級 observe」兩句與此矛盾，以本節實測為準**。
4. 影響形態為逐 session 擲骰：能否擁有區段取決於該次 session 尾碼是否恰為兩碼數字。若尾碼為均勻兩碼十六進位，不通過比例為 156/256。
5. 降級為 `observe` 有兩個獨立成因：(a) 尾碼含字母被 exit 3 擋；(b) 子代理人無取值管道（`ListAgents` 對 subagent 不可得；`pm-registry.json` 的 session 條目欄位為 `name`／`project`／`registered_at`／`heartbeat_ts`／`tickets`／`files`，無 session 序號欄，且 `name` 為底線形式專案名，本身亦不通過驗證）。本次派發即為 (b) 的實例。

**仍未驗證的假設**：

- session 短名尾碼的產生規則未見於任何本機可讀來源；「兩碼十六進位」為 13 個觀測值的歸納，非規格。本 session 的 uuid 前綴與其短名尾碼無可見對應關係。
- `flutter-balance` 本次抽到 4 個全通過。無管道判定該 consumer 的尾碼字元集是否與本專案同形，據實記為未知，不推測。

### 相關 Error Pattern

`ARCH-BAL-023`（識別欄位無共用契約，消費端靜默漏檢）——與本現象同批由上游帶入（見 `.claude` sync 至 framework-issue 2.0.0 的 commit 訊息），描述的正是寫入端與消費端各自自洽而兩者之間缺約定的形態，與本票候選根因表述同構。
