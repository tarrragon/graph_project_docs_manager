## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論（WRAP 快速模式）

**定案：降級，不拒絕；降級是顯式關卡後的使用者動作，不自動發生。**

- W（擴選項）：A 拒絕（現況）／B 純檔案模式（只列檔案）／C 以 App 內建型別表檢視／D 讀該專案 `.py`。
- R（現實檢驗）：見重現實驗結果——三個缺檔語料可用內建表還原 5 型節點 + A 層 10～11 條邊；B 比可還原的少；D 為 PROP-002 已否決且 2.2x 的 `.py` 無型別表。
- A（拉開距離）：若這是一年後回看，「App 對 94% 的語料零服務」比「降級模式下某條邊解讀有偏差」代價高得多；後者有徽章與破洞報告可觀察，前者無從觀察。
- P（預想失敗）：舊語料同名欄位值型別不同 → 破洞報告成批「不合法值」。tripwire 與處置已寫入 tech-decisions 補記段。

### 候選方案比較

| 方案 | 可還原 | 判定 |
|------|------|------|
| A 拒絕 | 0 | 否決：丟掉實測可還原的整個 A 層圖 |
| B 純檔案模式 | 檔案清單 | 否決：少於實測可還原量 |
| **C 以 App 內建型別表檢視** | 7 型節點 + A 層 12 條邊 | **採納**，必須顯式標示為降級（PROP-002「版本永遠正確」承諾在此不成立） |
| D 讀專案 `.py` | — | 否決：PROP-002 已否決，且舊版無型別表 |

### 降級的可見範圍（已回填規格）

1. 進入：「無可消費的型別表」保留為顯式關卡，`action-domain-degraded-view` 僅在 `VERSION` 不高於內建表 `schema_generated_at_framework_version` 時渲染；高於時不渲染，只剩切換專案。
2. 畫面：六畫面皆可進入，無畫面級白名單。
3. 邊層級：只渲染 established 12 條；proposed 4 條不渲染。
4. 破洞報告：「舊框架版本缺欄位」不列破洞；斷邊與不合法 ID 照報。
5. 標示：每畫面 header 常駐 `badge-<screen>-degraded-schema`（含兩個版本值），切換浮層該項同標；切換專案時重置。「降級型別表」為疊加旗標，狀態總數維持 31。
6. gate 判定訊號不變（`VERSION` 值 + JSON 存在性），不讀 `.py`。
