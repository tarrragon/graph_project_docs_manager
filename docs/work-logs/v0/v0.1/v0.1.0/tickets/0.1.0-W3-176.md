`withAction` 但屬使用者發起（不需 warning）；日後若有背景發起的 `plain` 提示，

輸入須為**事件發起者**而非 `variant`。發起者可機械取得——呼叫來自使用者互動回呼
（`onTap` / `onPressed` 路徑）或背景 listener（`ref.listenManual` 路徑）。
本票若無法在元件內判定發起者，改由呼叫端以參數傳入，並於 Solution 記錄該選擇；
**不得以 `variant` 近似替代**。

### Phase 1 功能規格（lavender-interface-designer，2026-09-09）

範圍：G1 關聯識別 + 截斷日誌等級判別。G2（`0.1.0-W3-241`）與 G3（`0.1.0-W3-242`）不在本節。

#### 0. 前置驗證：框架內建機制（ARCH-010 防護）

設計自建方案前先驗證框架內建機制是否已足夠：

| 步驟 | 問題 | 實查結果 |
|------|------|---------|
| 1 | Flutter 內建機制是否已提供 SnackBar 的關聯識別？ | 否。`ScaffoldMessengerState.showSnackBar` 回傳的 `ScaffoldFeatureController` 每次呼叫皆為新物件，但它不進入日誌欄位（無穩定可讀值），且 `skippedUnmounted` 路徑根本不會產生 controller |
| 2 | Dart 標準庫是否已有解？ | `identityHashCode(controller)` 可取值，但不保證唯一（物件回收後可重用）、無序、且同樣不覆蓋 `skippedUnmounted` |
| 3 | 本地狀態是否足夠？ | 是。單一 `static int` 遞增計數器即滿足「同一次 `show` 的全部事件共享一個值、跨呼叫不重複」，不需 Riverpod、不需新依賴 |
| 4 | 需要外部狀態管理或新抽象嗎？ | 否 |

結論：採步驟 3 的本地靜態計數器。**發起者（origin）同樣先驗證**：Flutter 未提供任何受支援的公開 API 可回答「目前呼叫堆疊是否位於指標事件派送中」（`GestureBinding` 不暴露此狀態查詢）；依賴內部狀態會隨 SDK 升級失效。故發起者由呼叫端傳參，與 acceptance 第 3 項「元件內判定不到時由呼叫端傳參」一致。

#### 1. Purpose

讓 `AppSnackBar` 的截斷日誌能回答兩個問題——**被截斷的是哪一則**（關聯識別），以及**這次截斷有多嚴重**（等級）。前者的既有替代手段是 `shown` / `closed` 的 FIFO 順序推斷，與其他 tag 的日誌交錯時不可靠；後者現況不存在（`closed` 一律不帶 level）。

#### 2. API 介面定義

##### 2.1 新增列舉（`lib/components/app_snack_bar.dart`）

    /// 一次 [AppSnackBar.show] 的發起者（SPEC-003〈截斷事件的日誌等級〉）。
    ///
    /// 截斷日誌的等級以本列舉為鍵，不以 [AppSnackBarVariant] 為鍵——變體會
    /// 同時誤判兩邊（`withAction` 亦可能是使用者發起；背景發起亦可能是 `plain`）。
    enum AppSnackBarOrigin {
      /// 呼叫來自使用者互動回呼（`onTap` / `onPressed` 路徑）。截斷時使用者
      /// 剛做過動作、沒反應會注意到，故為 info。
      userInitiated,

      /// 呼叫來自背景 listener（如掃描完成）。截斷後使用者無任何線索指出
      /// 曾發生過什麼，故為 warning。
      background,
    }

##### 2.2 `show` 簽名（唯一變更為末位新增一個具名選填參數）

    static void show(
      BuildContext context, {
      required String message,
      AppSnackBarVariant variant = AppSnackBarVariant.plain,
      String? actionLabel,
      VoidCallback? onAction,
      Key? actionTestKey,
      AppSnackBarOrigin origin = AppSnackBarOrigin.background,
    })

`AppSnackBarLogEvent` 四個列舉值、`AppSnackBarLogSink` typedef、`logSink` 注入點皆不變。

##### 2.3 日誌欄位（`fields`）

新增兩個 key，既有 key 一律不改名、不移除、不改值：

| key | 型別 | 出現於 | 語意 |
|-----|------|-------|------|
| `showId` | `int` | 四個事件全部 | 本次 `show` 呼叫的關聯識別。同一次呼叫發出的每一個事件攜帶同一值；跨呼叫嚴格遞增且不重複 |
| `origin` | `AppSnackBarOrigin` | 四個事件全部 | 本次 `show` 的發起者。等級判定的唯一輸入（見 2.4） |

既有欄位維持原樣：`shown` 的 `variant` / `message` / `duration` / `actionLabel`（僅 `withAction`）、`skippedUnmounted` 的 `variant` / `message`、`actionPressed` 的 `actionLabel`、`closed` 的 `reason`。

**兩個新 key 在四個事件全部出現（而非只出現於 `closed`）的理由**：單一規則的實作分支數為零，逐事件例外則需在四處各判一次；且 `shown` 帶 `showId` 是配對的另一半，`shown` 帶 `origin` 使「這一則被判為哪一類」在顯示當下即可稽核，不必等它被截斷才知道。

##### 2.4 日誌等級規則

    截斷判別式：event == closed AND fields['reason'] == SnackBarClosedReason.hide
      （F3：全 repo 只有兩處呼叫 hideCurrentSnackBar，:121 取預設 reason=hide、
        :166 明確 reason=action，故 hide 恆等於「被後續一次 show 截斷」）

| 事件 | 條件 | level | 相對既有行為 |
|------|------|-------|------------|
| `closed` | `reason == hide` AND `origin == background` | `900`（warning） | 新增（既有恆不帶 level） |
| `closed` | `reason == hide` AND `origin == userInitiated` | `800`（info） | 新增 |
| `closed` | `reason != hide`（`timeout` / `action` / `dismiss` / `swipe` / `remove`） | 不傳（維持 `null`） | 不變 |
| `shown` | 全部 | 不傳 | 不變 |
| `actionPressed` | 全部 | 不傳 | 不變 |
| `skippedUnmounted` | 全部 | `900` | 不變（不受 `origin` 影響） |

`800` / `900` 沿用 `dart:developer` 承自 `package:logging` 的 `Level` 值（INFO=800、WARNING=900）；專案既有 warning 皆為 `900`（`macos_scan_notifier.dart`、`workspace_repository.dart` 等），本節只新增 `800` 一個值。

**info 分支顯式傳 `800`、不沿用「不傳」的理由**：不傳 level 的語意是「未指定」（`developer.log` 取 0），與「判定結果為 info」不是同一件事。兩個分支都顯式傳值，日誌讀者才能分辨「這則截斷被判為使用者發起」與「這則根本沒經過等級判定」；靜態讀碼時兩分支對稱，也較容易確認判定輸入不含 `variant`（SPEC-003 FR-17 的靜態可驗形態）。

#### 3. 設計決策

##### D1：關聯識別採 process 內單調遞增整數

| 面向 | 決定 | 理由 |
|------|------|------|
| 型別 | `int` | 無新依賴；日誌可讀且隱含先後順序；比對為精確相等 |
| 產生點 | `show()` 進入點的第一件事，**在 `context.mounted` 檢查之前** | 使 `skippedUnmounted` 也有識別；否則「未顯示」這條路徑仍不可配對 |
| 產生方式 | `static int _lastShowId = 0;` → `final showId = ++_lastShowId;` | Dart 單執行緒事件迴圈、遞增之間無 `await`，無競態 |
| 重置 | 不重置，不提供重置 API | 測試斷言「兩事件的 `showId` 相等」而非絕對值，故不需重置；不加 `@visibleForTesting` 重置點可少一個公開面 |
| 溢位 | 不處理 | 64 位元整數在單一 process 生命週期內不可能耗盡 |

**否決的替代**：UUID（引入依賴、日誌不可讀、無順序）；`identityHashCode(controller)`（不保證唯一、不覆蓋 `skippedUnmounted`）；沿用 `message` 字面（同一則訊息可重複顯示，不唯一，且與 `0.1.0-W3-132` 改事件識別碼的方向衝突）。

##### D2：`origin` 的形態與預設值（本票必答問題）

**形態**：具名選填參數 + 列舉，預設 `AppSnackBarOrigin.background`。

**為何選填而非必填**：必填可徹底消滅預設值猜測，但會使三個既有呼叫點（`gap_report_screen.dart:199`、`:218`、`scan_notification_controller.dart:202`）與測試 harness 立即無法編譯，而這三個檔案皆不在本票 `where.files`（只有元件與其測試）。故 0.1 定為選填；改必填的評估併入呼叫端標註的後續票（見第 8 節 SR-1），本節不留無 trigger 的延後。

**預設值選 `background` 的依據是誤判後果不對稱**：

| 若預設取 | 呼叫端漏傳時的實際誤判 | 後果 | 誤判會不會被發現 |
|---------|---------------------|------|----------------|
| `background`（採用） | 使用者發起被記為背景發起 | 截斷記為 warning，等級偏高 | **會**——warning 量異常是可見訊號，會被追查並修正 |
| `userInitiated` | 背景發起被記為使用者發起 | 截斷記為 info，淹沒在 info 流中 | **不會**——沒有任何訊號指出它被漏標 |

背景發起正是 SPEC-003〈顯示位爭用時的約束與 0.1 的處置規則〉要保護的那一類（「使用者不知道事件已發生，且他不會知道自己錯過了什麼」）。取 `userInitiated` 為預設時，漏標會把最需要被看見的一類降級為 info——那是本票要修的「不可稽核」缺口的同構複製。取 `background` 的代價是偏高等級的噪音，而**偏高的誤判會自我揭露，偏低的誤判會自我隱藏**，故取偏高側。

**已知的過渡期代價（刻意接受）**：三個既有呼叫點中兩個為使用者發起（`gap_report_screen` 的兩處皆在 `onTap` 路徑內），一個為背景發起（`scan_notification_controller._showDeniedSnackbar`，走 `denied` fallback）。本票不改呼叫端，故在標註完成前，那兩處若被截斷會記為 warning。方向與上表一致（可自我揭露），承接見 SR-1。

**殘留風險（無機械偵測手段）**：呼叫端傳入與事實相反的值時，元件無法察覺。本票不虛構偵測機制；核對落在 SR-1 的呼叫端標註逐點檢查。

##### D3：等級判定的輸入不含 `variant`

判定輸入恰為兩項：`fields['reason'] == hide`（是否為截斷）與 `origin`（誰發起）。實作中不得出現 `variant` 參與等級決策的分支——SPEC-003 明寫以變體為鍵會同時誤判兩邊（`sourceFileNotFoundSnackbarMessage` 是 `withAction` 但屬使用者發起；日後背景發起的 `plain` 會被漏記）。此為靜態可讀出的驗收項（第 7 節 A6）。

#### 2. 測試基礎設施（新群組專用）

**記錄替身**：記錄三元組（事件、欄位快照、等級），取代既有群組只記事件與等級的替身。

    records: List<({AppSnackBarLogEvent event, Map<String, Object?> fields, int? level})>
    sink = (event, fields, {level}) =>
        records.add((event: event, fields: Map.of(fields), level: level));

`Map.of(fields)` 取快照而非持有參考的理由：斷言在事件發生後才執行；若實作日後改為重用同一個 map 實例，持有參考會使先前記錄被回填，斷言讀到的是最後一次的值而非當下值——該失效不會紅燈，只會靜默給出錯誤結論。

**查詢輔助**（測試檔內私有，不進 `lib/`）：以述詞查找而非索引取值。

| 輔助 | 用途 |
|------|------|
| `showIdOf(record)` | `record.fields['showId'] as int` |
| `originOf(record)` | `record.fields['origin']` |
| `closedWithReason(reason)` | 在 `records` 中以 `event == closed && fields['reason'] == reason` 查找 |
| `shownAt(index)` | 僅供 T-3 的結構斷言使用（見該測試的限定條件） |

**索引使用的硬性限制（A3 的核心）**：`records` 的索引位置**不得**用於決定「哪一個 `closed` 對應哪一個 `shown`」。配對一律經 `showId` 相等判定。索引僅可用於斷言「事件出現順序」這件事本身（T-3）。

**時間推進**：沿用既有 `_pumpBy`（100ms 步距）與 `materialTransition` 常數，不新增推進工具。

#### 3. 行為鏈推演與四維度分支

行為鏈：`show 進入` → `showId 產生` → `mounted 判定` →（未掛載：`skippedUnmounted` 終止）／（已掛載：`hideCurrentSnackBar` → `shown` → `showSnackBar` → `closed.then`）。

四個維度的分支窮舉：

| 維度 | 分支 | 承接測試 |
|------|------|---------|
| 正常 | 顯示後自然逾時；動作被按下 | T-1、T-7 |
| 異常 | `context` 已卸載（唯一無 SnackBar 產生的路徑） | T-8 |
| 邊界 | 同一同步區塊內零幀截斷；`origin` 漏傳取預設；事件列舉集合本身 | T-2、T-3、T-6、T-9 |
| 中斷 | 顯示中途被後續 `show` 截斷；截斷的等級隨發起者變動 | T-4、T-5 |

**前置條件驗證強制表**（每個 When 之前必須先斷言 Given 成立）：

| 測試 | Given | 前置斷言 |
|------|-------|---------|
| T-1 | 無 SnackBar 顯示、日誌記錄為空 | `expect(records, isEmpty)` + `expect(find.byType(SnackBar), findsNothing)` |
| T-2 / T-3 | 同上，且錨點 Element 已掛載 | 同上 + `expect(anchor.mounted, isTrue)` |
| T-4 | 第一則已跑滿進場動畫 | 推進 `materialTransition` 後 `expect(find.byType(SnackBar), findsOneWidget)` 且 `records` 僅一筆 `shown` |
| T-5 各列 | 第一則以指定 `(variant, origin)` 顯示中 | `expect(find.byType(SnackBar), findsOneWidget)` |
| T-6 | 同 T-5，但呼叫時未傳 `origin` | 同上 |
| T-7 | `withAction` 已顯示且動作 label 可命中 | `expect(find.byKey(_snackBarActionKey), findsOneWidget)` |
| T-8 | `context` 所屬 Element 已卸載 | `expect(capturedContext.mounted, isFalse)` |
| T-9 | 無執行前提（純結構斷言） | — |

無前置斷言的 When 會使紅燈語意不明：測不到事件時，分不出「行為錯」與「情境根本沒建立起來」。

#### 4. 測試規格（Given-When-Then）

**T-1 基準線：plain 自然逾時**（S1；A1、A7）

    Given: records 為空、無 SnackBar 顯示（前置斷言如上表）
    When:  以 variant=plain、origin=background 呼叫一次 show，
           推進 materialTransition，再推進
           Motion.snackBar + materialTransition + materialTransition
    Then:  records 的事件序為 [shown, closed]
           兩者的 showId 相等
           closed 的 fields['reason'] 為 SnackBarClosedReason.timeout
           closed 的 level 為 null，shown 的 level 為 null

`origin` 取 `background`（而非 `userInitiated`）的理由：`background` 是唯一會產生 900 的組合，若實作誤把等級規則套到非 `hide` 的 `closed`，本測試才會紅燈。取 `userInitiated` 則 A7 的鑑別力減半。

**T-2 同步區塊內連續兩次 show 的配對**（S2；A2、A3）

    Given: records 為空、無 SnackBar 顯示、錨點 Element 已掛載
    When:  同一同步區塊內連續呼叫 show(FIRST) 與 show(SECOND)
           （皆 plain、origin=background、訊息不同），
           隨後推進至兩則都結束
    Then:  兩筆 shown 的 showId 相異，且 SECOND 的大於 FIRST 的
           reason == hide 的 closed 恰一筆，其 showId 等於 FIRST 的 shown 的 showId
           reason == timeout 的 closed 恰一筆，其 showId 等於 SECOND 的 shown 的 showId

配對一律以 `showId` 查得。**禁止斷言 `showId` 的絕對值**——計數器為 process 內靜態且不重置（Phase 1 D1），絕對值取決於同檔先前跑過幾個測試，寫死即為隨測試順序而變的假斷言。

**T-3 配對不依賴出現順序的佐證**（S2 的同一情境；A3）

    Given: 同 T-2
    When:  同 T-2
    Then:  reason == hide 的 closed 在 records 中的索引大於 SECOND 的 shown 的索引

意義：`closed` 並非緊接其對應的 `shown`，故「相鄰配對」與「第 n 個 shown 對第 n 個 closed」這類順序法在本元件上不成立，配對必須依 `showId`。

序的推導依據（`fvm` 釘選的 Flutter 3.47.1 SDK 原始碼實查）：`ScaffoldMessengerState.hideCurrentSnackBar` 在非 `accessibleNavigation` 路徑下走 `_snackBarController.reverse().then(...)`，completer 於反向動畫結束後才完成；而本元件在記錄 `shown` **之前**就已呼叫 `hideCurrentSnackBar`，故 `closed(FIRST)` 必晚於 `shown(SECOND)`。測試 harness 的 `MediaQuery` 只覆寫 `disableAnimations`，未動 `accessibleNavigation`（預設 false），故走的是該路徑。

**Phase 3b 若實測序與此推導不符**：以實測為準、回報 PM，並改以其他不依賴順序的形態表達本項；T-2 的 `showId` 配對斷言為 A3 的主斷言，不受本項影響。獨立成一個 `testWidgets`（而非併入 T-2）的理由：兩者紅燈語意不同——T-2 紅燈表示配對錯，T-3 紅燈表示序的推導過期。

**T-4 顯示中途被截斷的配對**（S3；A3）

    Given: 第一則已跑滿進場動畫（前置斷言：SnackBar findsOneWidget、records 僅一筆 shown）
    When:  呼叫第二次 show，推進至兩則都結束
    Then:  配對結果與 T-2 同形（reason == hide 的 closed 其 showId 等於第一則）

範疇註記：T-2 與 T-4 兩組情境**之間**的可區分性需要「實際可見時長」，屬 `0.1.0-W3-241`，本票不承諾（Phase 1 第 10 節與 PM 裁示採讀法 (i)）。

**T-5 截斷等級矩陣：variant × origin**（S4、S5、S6；A4、A5、A6）

表格驅動，四列各為一個獨立 `testWidgets`（測試名含組合，紅燈直指哪一格）：

| 列 | 第一則的 variant | 第一則的 origin | 期望 closed(hide) 的 level |
|----|-----------------|----------------|--------------------------|
| 1 | `plain` | `background` | `900` |
| 2 | `plain` | `userInitiated` | `800` |
| 3 | `withAction` | `background` | `900` |
| 4 | `withAction` | `userInitiated` | `800` |

    Given: 第一則以該列的 (variant, origin) 顯示中（前置斷言：SnackBar findsOneWidget）
    When:  後續一次 show 截斷它
    Then:  該 closed 的 reason 為 hide、origin 為該列的 origin、level 為該列的期望值

矩陣（而非只測兩格）的理由：`variant` 的值域恰為兩個，四格即為「level 對 variant 不敏感」在觀測層面的窮舉。與「`withAction` 較嚴重」的直覺相反的兩格（列 3 得 900、列 4 得 800）正是要鎖住的性質。

**行為測試不取代靜態檢查**：行為測試無法區分「實作中沒有 `variant` 分支」與「有分支但兩支結果恰好相同」。A6 的靜態部分見第 7 節 V-2。

**T-6 origin 預設值**（S9；A4）

    Given: 第一則以未傳 origin 的方式顯示中
    When:  後續一次 show 截斷它
    Then:  該 closed 的 origin 為 AppSnackBarOrigin.background、level 為 900

本測試鎖住的是 Phase 1 D2 的誤判方向選擇（偏高側可自我揭露）。若日後有人把預設改為 `userInitiated`，此測試紅燈。

**T-7 withAction 按下動作**（S7；A1、A7）

    Given: withAction 已顯示且動作 label 可命中
    When:  按下動作標籤，推進至結束
    Then:  records 的事件序為 [shown, actionPressed, closed]
           三者的 showId 相等
           closed 的 reason 為 action、level 為 null

`actionPressed` 也帶 `showId` 是 A1「同一次 show 的每個事件共享同值」的第三個證據點（前兩者為 `shown` 與 `closed`）。

**T-8 context 已卸載**（S8；A10、A1）

    Given: 取得的 context 所屬 Element 已卸載（前置斷言：capturedContext.mounted 為 false）
    When:  呼叫 show（不傳 origin）
    Then:  records 恰一筆，事件為 skippedUnmounted、level 為 900
           其 fields 含 showId 與 origin 兩個 key，origin 為 background
           find.byType(SnackBar) findsNothing
           再推進 Motion.snackBar + 兩段 materialTransition 後，records 仍恰一筆
           （該 showId 無任何後續事件）

最後一項對應 Phase 1 第 5 節「`skippedUnmounted` 之後該 `showId` 不再有任何事件」，是「識別涵蓋未顯示路徑」（D1 的產生點在 mounted 檢查之前）的驗證。

**T-9 事件列舉結構**（A9）

    Given: 無執行前提
    When:  讀取 AppSnackBarLogEvent.values
    Then:  逐項等於 [shown, skippedUnmounted, actionPressed, closed]

不是 widget test（用 `test` 而非 `testWidgets`）。以逐項相等（而非只比長度）同時鎖住四值的名稱與順序。

#### 5. 刻意不覆蓋的項目與理由

| 項目 | 不覆蓋的理由 |
|------|------------|
| `reason` 為 `swipe` / `dismiss` / `remove` 的 `closed` | 等級規則的判定分支恰為 `reason == hide`，其否定支已由 `timeout`（T-1）與 `action`（T-7）兩條實際可達路徑覆蓋。再加第三個否定支不增加鑑別力，且 `swipe` 須以拖曳手勢構造，成本高於所得 |
| 實際可見時長、T-2 與 T-4 之間的可區分性 | `0.1.0-W3-241` |
| 「因判準而未顯示」事件 | `0.1.0-W3-242` |
| 呼叫端傳入的 `origin` 是否與事實相符 | 元件無從察覺（Phase 1 D2 殘留風險）。核對落在 `0.1.0-W3-245`（呼叫端標註） |
| `logSink` 拋例外 | Phase 1 第 5 節定為維持既有行為，不新增 try/catch；為不存在的行為寫測試會把範疇外的決定鎖死 |
| `showId` 溢位 | 64 位元整數在單一 process 生命週期內不可達 |
| 併發產生重複 `showId` | Dart 單執行緒事件迴圈，遞增之間無 `await`，無競態可構造 |

### Phase 3a 實作策略（pepper-test-implementer，2026-09-10）

範圍：G1 關聯識別 + 截斷日誌等級判別。輸入為 Phase 1 第 0–11 節與 Phase 2 第 1–11 節。本節只產出語言無關策略與虛擬碼，不含實作程式碼。

#### 1. 策略總覽：三個機制

| 機制 | 解決 | 對應驗收 |
|------|------|---------|
| M1 呼叫級識別號 | 「被截斷的是哪一則」——每次 `show` 進入時取一個單調遞增號 | A1、A2、A3 |
| M2 呼叫級欄位基底 | 同一次 `show` 的四個事件共享同一組 `{showId, origin}`，由單一處組成後併入各事件的欄位 | A1、A10 |
| M3 等級判定純函式 | 輸入恰為 `(reason, origin)` 的無副作用對映 | A4、A5、A6、A7 |

三者互相獨立：M1 決定值、M2 決定該值出現在哪些事件、M3 決定 level。實作分歧點只有一處（M3 的兩層條件），其餘皆為資料搬運。

#### 2. 核心虛擬碼

##### 2.1 模組級狀態與識別號產生

    模組級可變狀態：lastShowId ← 0            // 單一執行緒事件迴圈，遞增之間無讓步點
    模組級常數：      LEVEL_INFO ← 800, LEVEL_WARNING ← 900

    程序 nextShowId():
        lastShowId ← lastShowId + 1
        回傳 lastShowId
        // 不記錄任何日誌事件（C-1）；不提供重置入口（Phase 1 D1）

##### 2.2 等級判定純函式（M3）

    純函式 resolveClosedLevel(reason, origin) -> 等級或「不指定」:
        若 reason ≠ CLOSED_REASON_HIDE:
            回傳 「不指定」                    // A7：timeout / action / dismiss / swipe / remove
        若 origin = ORIGIN_BACKGROUND:
            回傳 LEVEL_WARNING                 // A4
        否則:
            回傳 LEVEL_INFO                    // A5：origin = ORIGIN_USER_INITIATED

    形式性質（A6 的靜態部分）：
      - 形式參數恰為 reason 與 origin 兩項；不接受 variant，故其函式體不可能引用 variant
      - 無外部讀取、無外部寫入、對相同輸入恆給相同輸出

##### 2.3 顯示入口的控制流程

    程序 show(context, message, variant, actionLabel, onAction, actionTestKey,
              origin ← ORIGIN_BACKGROUND):        // 選填，預設見 Phase 1 D2

        斷言(variant ≠ WITH_ACTION 或 (actionLabel 與 onAction 皆已提供))

        showId ← nextShowId()                     // ← 在 mounted 判定之前（A10）
        baseFields ← { showId: showId, origin: origin }   // M2：本次呼叫的欄位基底

        若 context 未掛載:
            log(SKIPPED_UNMOUNTED,
                baseFields ∪ { variant, message },
                level = LEVEL_WARNING)            // 既有行為不變，不受 origin 影響
            返回                                   // 該 showId 不再產生任何事件

        messenger ← 取得訊息呈現器(context)
        messenger.hideCurrent()                   // 截斷前一則；其 closed 由前一次呼叫的閉包處理

        isWithAction ← (variant = WITH_ACTION)
        log(SHOWN,
            baseFields ∪ { variant, message, duration,
                           若 isWithAction 則 actionLabel },
            不傳 level)                            // C-2

        controller ← messenger.show(
            以 message／variant 組出的內容，
            動作被按下時的回呼 ← 程序():
                log(ACTION_PRESSED,
                    baseFields ∪ { actionLabel },
                    不傳 level)                    // C-2
                onAction()
                messenger.hideCurrent(reason = CLOSED_REASON_ACTION)
        )

        當 controller 的結束通知完成(reason) 時:
            log(CLOSED,
                baseFields ∪ { reason },
                level = resolveClosedLevel(reason, origin))
            // baseFields 與 origin 皆為本次呼叫的區域繫結，
            // 由閉包持有；不讀取模組級狀態

##### 2.4 關鍵不變量

| 不變量 | 由什麼保證 |
|-------|-----------|
| 同一次 `show` 的所有事件 `showId` 相同 | 四個 log 點的欄位皆由同一個 `baseFields` 展開，無第二處產生 `showId` |
| 截斷者的等級取自「被截斷那一則」的 `origin` | `closed` 的回呼是**該則自己**那次 `show` 的閉包；後續 `show` 呼叫 `hideCurrent()` 不改寫任何前一則的繫結 |
| 跨呼叫 `showId` 嚴格遞增 | 唯一寫入點 `nextShowId`，遞增與讀取之間無讓步點 |
| 等級判定不含 `variant` | `resolveClosedLevel` 的形式參數表 |

#### 4. 控制流程的分歧點清單（實作分歧數的上界）

| # | 分歧 | 位置 | 說明 |
|---|------|------|------|
| 1 | `context` 是否掛載 | show 入口 | 既有，語意不變 |

| 3 | `reason` 是否為 `hide` | `resolveClosedLevel` | 新增 |
| 4 | `origin` 是否為 `background` | `resolveClosedLevel` | 新增 |

#### 5. Phase 2 移交項的正面處置

##### 5.1 C-1：`show` 進入點不得新增日誌事件

`nextShowId()` 只做遞增與回傳，無日誌副作用（2.1 已寫入虛擬碼註記）。**識別號的可稽核性由既有四個事件各自攜帶 `showId` 達成，不需要一筆「show 被呼叫」事件**——那筆事件能提供的資訊（本次呼叫存在、其識別號）已完整落在 `SHOWN` 或 `SKIPPED_UNMOUNTED` 之一，兩者對每次呼叫恰有其一必然發出。故 C-1 不是取捨，是冗餘消除。

Phase 3b 自檢：`show` 由入口到 `mounted` 判定之間的 log 呼叫數為 0。

##### 5.2 C-2：`shown` 與 `actionPressed` 不得攜帶 level

策略為**只在需要 level 的呼叫點傳 level**：四個 log 點中只有 `SKIPPED_UNMOUNTED`（既有的 900）與 `CLOSED`（`resolveClosedLevel` 的結果）傳值，另兩點連該具名引數都不出現。

反面做法（統一在所有 log 點呼叫某個「求等級」函式、非截斷時回傳「不指定」）雖然對稱，但會使 `shown` 的 level 由一個規則決定而非結構上不可能有值，日後改動該規則會靜默影響 `shown`。**不採用**。

##### 5.3 V-2：A6 靜態部分的可測性接縫——採納，且限定為私有

**決定：採納接縫，抽為私有純函式 `resolveClosedLevel(reason, origin)`，不加對外可見標註。**

| 面向 | 採納私有純函式 | 不抽（判定內嵌於 `closed` 回呼） | 抽並對外可見 |
|------|--------------|------------------------------|------------|
| A6 靜態驗證形態 | 讀一個兩參數的簽名即可判定「輸入不含 variant」 | 須人工逐行讀回呼區塊，確認其詞法範圍內未引用 `variant` | 同左欄 |
| 公開面 | 不增（Phase 1 D1 取向不受損） | 不增 | +1，與 D1 相反 |
| 額外測試 | 無（仍由 T-5 四列間接驗證） | 無 | 可加純函式表格測試 |

**取捨說明**：三者對 A6 的**行為**驗證力相同（皆為 T-5 四列）。差異只在 V-2 這項人工核對的可靠度——內嵌時，回呼的詞法範圍涵蓋整個 `show` 的區域繫結（含 `variant`、`isWithAction`），核對者須證明「範圍內可見但未被引用」；抽為純函式後，`variant` 根本不在其詞法範圍內，核對降為讀簽名。這是把一項「須逐行查證的否定命題」換成「一眼可讀的結構事實」，成本為零。

不取「對外可見」的理由：多出的公開面換來的是純函式表格測試，而該測試與 T-5 四列的覆蓋完全重疊（同樣的 `(reason, origin)` 組合），是重複覆蓋而非新增鑑別力；付出一個永久的公開面換零增益不成立。

**V-2 的執行形態（交 Phase 3b 與 Phase 4）**：核對對象為 `resolveClosedLevel` 的簽名與函式體；判定依據為「其形式參數不含 variant，且函式體只引用形式參數與模組級等級常數」。`grep` 僅作輔助列位置用，不作判定依據（沿用 Phase 2 第 7 節措辭）。

##### 5.4 T-3 的事件出現序：實測不符時的處置

Phase 2 由 SDK 原始碼推導出 `closed(FIRST)` 晚於 `shown(SECOND)`（`hideCurrentSnackBar` 於反向動畫結束後才完成結束通知，而本元件在記錄 `shown` 之前已呼叫 `hideCurrent()`）。

**此推導不進入實作決策**：本策略的配對機制（M1／M2）對事件出現序完全不敏感——`showId` 由呼叫級閉包攜帶，無論 `closed(FIRST)` 落在 `shown(SECOND)` 之前或之後，配對結果相同。故 T-3 實測與推導不符時**不需要改任何實作**。

處置順序（Phase 3b）：

1. 先確認 T-2 是否綠燈。T-2 綠燈即表示 A3 的主斷言成立，配對機制正確
2. T-2 綠燈而 T-3 紅燈 → 判定為 Phase 2 對 SDK 行為的推導過期（該測試的紅燈語意即為此，見 Phase 2 T-3 段），**不改實作、不改配對策略**
3. 記錄實測到的實際序（含推進步距），回報 PM；由 PM 決定 T-3 改為以實測序表達、或改以其他不依賴順序的形態表達後重跑
4. T-2 與 T-3 同時紅燈 → 屬配對機制問題，回到實作

**禁止**以調整推進步距、增減 `pump` 次數的方式讓 T-3 轉綠而不查明實際序——那會把一個過期的推導固定成看似通過的斷言。
