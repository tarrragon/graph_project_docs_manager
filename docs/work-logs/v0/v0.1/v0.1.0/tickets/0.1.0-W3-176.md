### 來自 0.1.0-W3-167 的更正：G3 事件的日誌等級不得以 variant 為鍵

`0.1.0-W3-167` 補記四第三節的更正，直接影響本票 G3 的實作。

**原本的判別依據已失效**。167 的 C1–C8 表曾把「`withAction` 被截斷」定為 warning，
理由是「損失的是操作能力（唯一入口消滅）」。PM 覆核實查後該理由不成立——
`rescanAction` 有 `action-gaps-rescan` 按鈕（`gap_report_screen.dart:87-92`，呼叫

`viewGapsAction` 的目的地在導覽列（`router.dart:42`）。**動作入口皆有替代。**

**正確的判別依據是事件的發起者**：

| 發起者 | 損失可否被使用者自行察覺 | 等級 |
|-------|----------------------|------|
| 使用者發起（點破洞項 → `sourceFileNotFound` / `openedExternally` / `externalOpenFailed`） | 可——他剛做了動作，沒反應會注意到 | info |
| 背景發起（掃描完成 → `scanComplete*`） | 否——他沒做任何動作，截斷後無任何線索指出曾發生過什麼 | **warning** |

**以 `variant` 為鍵會同時誤判兩邊**：`sourceFileNotFoundSnackbarMessage` 是
`withAction` 但屬使用者發起（不需 warning）；日後若有背景發起的 `plain` 提示，
以 `variant` 為鍵會漏記。

**對本票的具體要求**：G3（「因判準而未顯示」事件）與截斷相關日誌的等級決策，
輸入須為**事件發起者**而非 `variant`。發起者可機械取得——呼叫來自使用者互動回呼
（`onTap` / `onPressed` 路徑）或背景 listener（`ref.listenManual` 路徑）。
本票若無法在元件內判定發起者，改由呼叫端以參數傳入，並於 Solution 記錄該選擇；
**不得以 `variant` 近似替代**。

G3 的觸發條件仍屬 `0.1.0-W3-169` 規格層（本票只提供載體），此更正只約束等級的
判別輸入，不改變該分工。

### Phase 1 功能規格（lavender-interface-designer，2026-09-09）

#### 0. 前置驗證：框架內建機制（ARCH-010 防護）

設計自建方案前先驗證框架內建機制是否已足夠：

| 步驟 | 問題 | 實查結果 |
|------|------|---------|
| 1 | Flutter 內建機制是否已提供 SnackBar 的關聯識別？ | 否。`ScaffoldMessengerState.showSnackBar` 回傳的 `ScaffoldFeatureController` 每次呼叫皆為新物件，但它不進入日誌欄位（無穩定可讀值），且 `skippedUnmounted` 路徑根本不會產生 controller |
| 2 | Dart 標準庫是否已有解？ | `identityHashCode(controller)` 可取值，但不保證唯一（物件回收後可重用）、無序、且同樣不覆蓋 `skippedUnmounted` |
| 3 | 本地狀態是否足夠？ | 是。單一 `static int` 遞增計數器即滿足「同一次 `show` 的全部事件共享一個值、跨呼叫不重複」，不需 Riverpod、不需新依賴 |
| 4 | 需要外部狀態管理或新抽象嗎？ | 否 |

結論：採步驟 3 的本地靜態計數器。**發起者（origin）同樣先驗證**：Flutter 未提供任何受支援的公開 API 可回答「目前呼叫堆疊是否位於指標事件派送中」（`GestureBinding` 不暴露此狀態查詢）；依賴內部狀態會隨 SDK 升級失效。故發起者由呼叫端傳參，與 acceptance 第 3 項「元件內判定不到時由呼叫端傳參」一致。

#### 1. Purpose

讓 `AppSnackBar` 的截斷日誌能回答兩個問題——**被截斷的是哪一則**（關聯識別），以及**這次截斷有多嚴重**（等級）。前者的既有替代手段是 `shown` / `closed` 的 FIFO 順序推斷，與其他 tag 的日誌交錯時不可靠；後者現況不存在（`closed` 一律不帶 level）。

#### 2. API 介面定義

##### 2.1 新增列舉（`lib/components/app_snack_bar.dart`）

    /// 一次 [AppSnackBar.show] 的發起者（SPEC-003〈截斷事件的日誌等級〉）。
    ///
    /// 截斷日誌的等級以本列舉為鍵，不以 [AppSnackBarVariant] 為鍵——變體會
    /// 同時誤判兩邊（`withAction` 亦可能是使用者發起；背景發起亦可能是 `plain`）。
    enum AppSnackBarOrigin {
      /// 呼叫來自使用者互動回呼（`onTap` / `onPressed` 路徑）。截斷時使用者
      /// 剛做過動作、沒反應會注意到，故為 info。
      userInitiated,

      /// 呼叫來自背景 listener（如掃描完成）。截斷後使用者無任何線索指出
      /// 曾發生過什麼，故為 warning。
      background,
    }

##### 2.2 `show` 簽名（唯一變更為末位新增一個具名選填參數）

    static void show(
      BuildContext context, {
      required String message,
      AppSnackBarVariant variant = AppSnackBarVariant.plain,
      String? actionLabel,
      VoidCallback? onAction,
      Key? actionTestKey,
      AppSnackBarOrigin origin = AppSnackBarOrigin.background,
    })

`AppSnackBarLogEvent` 四個列舉值、`AppSnackBarLogSink` typedef、`logSink` 注入點皆不變。

##### 2.3 日誌欄位（`fields`）

新增兩個 key，既有 key 一律不改名、不移除、不改值：

| key | 型別 | 出現於 | 語意 |
|-----|------|-------|------|
| `showId` | `int` | 四個事件全部 | 本次 `show` 呼叫的關聯識別。同一次呼叫發出的每一個事件攜帶同一值；跨呼叫嚴格遞增且不重複 |
| `origin` | `AppSnackBarOrigin` | 四個事件全部 | 本次 `show` 的發起者。等級判定的唯一輸入（見 2.4） |

既有欄位維持原樣：`shown` 的 `variant` / `message` / `duration` / `actionLabel`（僅 `withAction`）、`skippedUnmounted` 的 `variant` / `message`、`actionPressed` 的 `actionLabel`、`closed` 的 `reason`。

**兩個新 key 在四個事件全部出現（而非只出現於 `closed`）的理由**：單一規則的實作分支數為零，逐事件例外則需在四處各判一次；且 `shown` 帶 `showId` 是配對的另一半，`shown` 帶 `origin` 使「這一則被判為哪一類」在顯示當下即可稽核，不必等它被截斷才知道。

##### 2.4 日誌等級規則

    截斷判別式：event == closed AND fields['reason'] == SnackBarClosedReason.hide
      （F3：全 repo 只有兩處呼叫 hideCurrentSnackBar，:121 取預設 reason=hide、
        :166 明確 reason=action，故 hide 恆等於「被後續一次 show 截斷」）

| 事件 | 條件 | level | 相對既有行為 |
|------|------|-------|------------|
| `closed` | `reason == hide` AND `origin == background` | `900`（warning） | 新增（既有恆不帶 level） |
| `closed` | `reason == hide` AND `origin == userInitiated` | `800`（info） | 新增 |
| `closed` | `reason != hide`（`timeout` / `action` / `dismiss` / `swipe` / `remove`） | 不傳（維持 `null`） | 不變 |
| `shown` | 全部 | 不傳 | 不變 |
| `actionPressed` | 全部 | 不傳 | 不變 |
| `skippedUnmounted` | 全部 | `900` | 不變（不受 `origin` 影響） |

`800` / `900` 沿用 `dart:developer` 承自 `package:logging` 的 `Level` 值（INFO=800、WARNING=900）；專案既有 warning 皆為 `900`（`macos_scan_notifier.dart`、`workspace_repository.dart` 等），本節只新增 `800` 一個值。

**info 分支顯式傳 `800`、不沿用「不傳」的理由**：不傳 level 的語意是「未指定」（`developer.log` 取 0），與「判定結果為 info」不是同一件事。兩個分支都顯式傳值，日誌讀者才能分辨「這則截斷被判為使用者發起」與「這則根本沒經過等級判定」；靜態讀碼時兩分支對稱，也較容易確認判定輸入不含 `variant`（SPEC-003 FR-17 的靜態可驗形態）。

#### 3. 設計決策

##### D1：關聯識別採 process 內單調遞增整數

| 面向 | 決定 | 理由 |
|------|------|------|
| 型別 | `int` | 無新依賴；日誌可讀且隱含先後順序；比對為精確相等 |
| 產生點 | `show()` 進入點的第一件事，**在 `context.mounted` 檢查之前** | 使 `skippedUnmounted` 也有識別；否則「未顯示」這條路徑仍不可配對 |
| 產生方式 | `static int _lastShowId = 0;` → `final showId = ++_lastShowId;` | Dart 單執行緒事件迴圈、遞增之間無 `await`，無競態 |
| 重置 | 不重置，不提供重置 API | 測試斷言「兩事件的 `showId` 相等」而非絕對值，故不需重置；不加 `@visibleForTesting` 重置點可少一個公開面 |
| 溢位 | 不處理 | 64 位元整數在單一 process 生命週期內不可能耗盡 |

**否決的替代**：UUID（引入依賴、日誌不可讀、無順序）；`identityHashCode(controller)`（不保證唯一、不覆蓋 `skippedUnmounted`）；沿用 `message` 字面（同一則訊息可重複顯示，不唯一，且與 `0.1.0-W3-132` 改事件識別碼的方向衝突）。

##### D2：`origin` 的形態與預設值（本票必答問題）

**形態**：具名選填參數 + 列舉，預設 `AppSnackBarOrigin.background`。

**為何選填而非必填**：必填可徹底消滅預設值猜測，但會使三個既有呼叫點（`gap_report_screen.dart:199`、`:218`、`scan_notification_controller.dart:202`）與測試 harness 立即無法編譯，而這三個檔案皆不在本票 `where.files`（只有元件與其測試）。故 0.1 定為選填；改必填的評估併入呼叫端標註的後續票（見第 8 節 SR-1），本節不留無 trigger 的延後。

**預設值選 `background` 的依據是誤判後果不對稱**：

| 若預設取 | 呼叫端漏傳時的實際誤判 | 後果 | 誤判會不會被發現 |
|---------|---------------------|------|----------------|
| `background`（採用） | 使用者發起被記為背景發起 | 截斷記為 warning，等級偏高 | **會**——warning 量異常是可見訊號，會被追查並修正 |
| `userInitiated` | 背景發起被記為使用者發起 | 截斷記為 info，淹沒在 info 流中 | **不會**——沒有任何訊號指出它被漏標 |

背景發起正是 SPEC-003〈顯示位爭用時的約束與 0.1 的處置規則〉要保護的那一類（「使用者不知道事件已發生，且他不會知道自己錯過了什麼」）。取 `userInitiated` 為預設時，漏標會把最需要被看見的一類降級為 info——那是本票要修的「不可稽核」缺口的同構複製。取 `background` 的代價是偏高等級的噪音，而**偏高的誤判會自我揭露，偏低的誤判會自我隱藏**，故取偏高側。

**已知的過渡期代價（刻意接受）**：三個既有呼叫點中兩個為使用者發起（`gap_report_screen` 的兩處皆在 `onTap` 路徑內），一個為背景發起（`scan_notification_controller._showDeniedSnackbar`，走 `denied` fallback）。本票不改呼叫端，故在標註完成前，那兩處若被截斷會記為 warning。方向與上表一致（可自我揭露），承接見 SR-1。

**殘留風險（無機械偵測手段）**：呼叫端傳入與事實相反的值時，元件無法察覺。本票不虛構偵測機制；核對落在 SR-1 的呼叫端標註逐點檢查。

##### D3：等級判定的輸入不含 `variant`

判定輸入恰為兩項：`fields['reason'] == hide`（是否為截斷）與 `origin`（誰發起）。實作中不得出現 `variant` 參與等級決策的分支——SPEC-003 明寫以變體為鍵會同時誤判兩邊（`sourceFileNotFoundSnackbarMessage` 是 `withAction` 但屬使用者發起；日後背景發起的 `plain` 會被漏記）。此為靜態可讀出的驗收項（第 7 節 A6）。

**失效形態的更正見 Problem Analysis 的〈PM 前置實查〉第二節**：本專案的 `AppSnackBar.show` 在顯示前無條件呼叫 `hideCurrentSnackBar()`，且 `ScaffoldMessenger` 一次只呈現一則，故版面上的「重疊」不會發生，實際形態是**替換截斷**。用戶關切的後果成立且更嚴重（重疊時兩則都在畫面上，替換是後者把前者抹掉），但處置方向不同——分化元件解決的是「同時要看到兩則」，解決不了「被靜默丟棄」。
