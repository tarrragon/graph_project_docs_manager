### Task Reference
- 0.1.0-W3-167 what: 設計 提示元件的使用時機、重疊處置、類型分化，與不可見時的日誌補位
- 0.1.0-W3-168 what: 補寫 component-contract-design skill 的提示元件設計引導

### Rationale Chain
- 0.1.0-W3-167 why: **用戶裁示（2026-09-09）**：「也要額外評估一個問題，哪些時機要呼叫 snackbar 或者 bottoast 這類提示元件，**如果大量呼叫提示元件，反而會重疊遮蔽**，那有可能需要依照不同類型的提示需求，設計使用不同的提示元件，以及**如果提示元件看不到，我們要在哪些事件或者流程上要補 log**。」

`0.1.0-W3-166` 固化「有顯示就要有紀錄」，但不回答「何時該顯示」。兩者一起才完整：只有前者會導向「凡事都跳提示」，而提示互相遮蔽時，**資訊反而比不提示更少**——後出現的蓋掉前一則，使用者兩則都沒讀完。

**這不是假設性風險。** 本專案目前 `AppSnackBar` 有 6 個呼叫點（實查，分佈於 `shell.dart`／`gap_report_screen.dart`／`scan_notification_controller.dart`），而 `0.1.0-W3-113`（`ScanNotificationController.show` 失敗的 SnackBar fallback）與 `0.1.0-W3-165` 都會再增加觸發時機。編輯能力（`0.1.0-W3-073`）落地後還會更多。

**第三個子問題是前兩者的必然對偶**：一旦決定某些時機不顯示提示（避免遮蔽），那些事件就失去了使用者可見的回饋，此時可觀測性必須由日誌承接——否則等於用「安靜」換掉了「有紀錄」，兩頭皆空。`0.1.0-W3-078` 的實機驗證正是撞上這個：路徑走到了、程式做了對的事，但沒有任何一側留下使用者層級的證據。
- 0.1.0-W3-168 why: `0.1.0-W3-167` 會定案三件事：何時該用暫態提示元件、重疊遮蔽如何處置（含是否需要類型分化）、不顯示時由誰承接可觀測性。這些是**設計決策**，而 `component-contract-design` 是元件契約的產生器——引導流程不問這些問題時，後續每個新元件都要重新論證一次，且各自論證的結果不會一致。

前一輪回饋契約的落地順序是方法論 → skill → 範本 → SPEC → 測試策略（`0.1.0-W3-056` / `101` / `057` / `105` → `108` / `106` / `100` / `104` / `111`）。**用戶指示本輪照同一順序**：先改元件庫 skill，再改 SPEC，再補測試，實機最後。

該 skill 已有〈回饋契約〉的填寫引導與判準問句「把這個元件背後的服務整個拔掉，使用者按下去還看得到反應嗎」（`0.1.0-W3-058`／`101`）。本票補的是另一個維度：**這個元件的回饋該不該用暫態提示載體，若是，用哪一種**——前者問回饋存不存在，後者問回饋走哪個通道。
