### 二、發現（列出交 PM，本票未自行調和）

**發現一：`openedExternallyMessage` 的既有條文與判準 T 結論相反。**
SPEC-003 §2.2 外部開啟契約與 §3.5 互動反應表明訂 `opened` → SnackBar
`openedExternallyMessage`；SPEC-004 §4.26 slot 契約與 i18n 子節引用該 key；
§2.12 短暫非同步列亦要求「成功與失敗各有對應 i18n key」。
而判準 T1 判它不該顯示——`/usr/bin/open` 成功即代表外部應用程式已到前景，
我方視窗因此非前景，SnackBar 停留 `Motion.snackBar` 後自行消失，使用者切回來
時已無。`0.1.0-W3-167`〈不符者與處置〉已判定不符並交本票裁決（SR-3）。
**本票未改 §2.2、§3.5、§4.26 任一條文**，改在新增的 §2.13 內以對照表把該項標為
「判準判否、現行條文判是」並綁定待裁決狀態。
理由：移除一則既有的成功回饋屬行為變更，牽動三份 SPEC 四處條文與 `0.1.0-W1-068`
的測試斷言，超出「補提示元件需求與提示訊息設計」的範圍。
**PM 可採的兩條路**：(a) 裁定移除，另開 DOC 票同步四處條文與實作票；
(b) 裁定保留，則需在 §2.13 對照表寫明保留理由（判準的例外須有具名理由，
否則下一個事件會照抄這個例外）。

**發現二（非不一致，複驗結果為一致）**：SPEC-003 §3.5 與 §3.6 對同一個
`ExternalOpenResult.notFound` 給出不同回饋——§3.5（破洞報告）走 SnackBar

狀態轉換 `state-nodeDetail-missing` 且明寫「不出現 SnackBar」。
表面上是同一事件兩種處置，實則**兩者皆符合判準 T2**：節點詳情有可見的狀態轉換
（T2 判是 → 不提示），破洞報告沒有（破洞項點擊不改變畫面狀態，T2 判否 → 提示）。
記於此是因為它是判準 T 目前唯一的跨畫面驗證點——若日後有人「統一」這兩處，
即為判準的違反。已寫入 §2.13 的對照表。

本票獨立複驗（PC-162）：`grep -rn "showDialog\|AlertDialog\|showModalBottomSheet\|Drawer("
lib/` → **0 命中**。所指的程式碼已不存在，該列是整改記錄而非現存衝突。
`0.1.0-W3-167` SR-9 併入本票。**本票已就地改為「整改完成」措辭**——此為文字與現況
脫節的更正，不含設計決策，與發現一的性質不同。

#### 4.2 裁定：顯示位爭用的三者取捨（本票裁定，票面 how 未列）

`0.1.0-W3-167` 前段〈第二問〉把「排隊／延後／拒絕新的 `plain`」的取捨交本票；
該票〈補記一〉隨後收窄——機制層撤回為待裁定，其前提由 `0.1.0-W3-184` 裁定，
且明寫「最低成本的滿足方式是留痕，不是重排」。**本票的裁定與該收窄一致**：

**三者皆不採用。0.1 的規則是「不重排，但必須留痕」。** 這是一項裁定（不是延後）——
三個候選都被評估並附代價後否決，見 §2.13〈顯示位爭用時的約束與 0.1 的處置規則〉的
四列處置表。否決的共同理由：三者都在提示層為排程問題做視覺化緩衝，症狀被吸收而
「同時發生了兩件都需要告知使用者的事」這個成因原封不動。

**重評 trigger 綁 `0.1.0-W3-184`**（ticket ID，符合 `decision-trigger-binding` 規則 2），
非時間、非事件。該票裁定「兩則本就不應同時到達」時重排機制連需求都不成立。

**約束層的保護對象依 `0.1.0-W3-167`〈補記四〉第二節校正後寫入**：保護的是
**事件已發生的告知本身**，不是動作入口——0.1 兩個動作入口皆有替代路徑
（`rescanAction` 與 `action-gaps-rescan` 呼叫同一個 `rescan()`；`viewGapsAction`
的目的地可由 `nav-item-gaps` 自行前往），無替代的是「掃描已完成」這個訊號。
**截斷日誌等級以事件的發起者為鍵，不以提示變體為鍵**（同補記四第三節），
理由與誤判形態一併寫入 §2.13。

#### 4.4 T1 判否的承接由兩項細分為三項

`0.1.0-W3-167` 的 C1／C2 分類是「有升級通道」與「無升級通道」兩分支。
本票落規格時發現需要第三分支：**Domain 載入與 Ticket 載入完成時使用者若已離開，
T1 判否且無升級通道（§2.2〈適用範圍〉明訂不升級），依 167 的兩分支會落入 C2 需補
日誌——但實際上結果是持久狀態，使用者回來即見，沒有任何資訊損失。**
故承接寫為 (a) 升級通道 / (b1) 狀態承載 / (b2) 延後顯示 / (c) 日誌承接四者依序，
其中 (b1)(b2) 合稱「延後至該畫面再度可見」。

**這不是新設計**：`0.1.0-W3-168` 落地於 `field-questions.md` 的問句原文即為
「改走升級通道或**延後至該畫面再度可見時處理**，兩者皆不可行時進入…日誌承接」，
本票只是把該中間分支在專案規格內實例化並給出可機械判定的可行條件。

#### 4.5 提示訊息設計要求的可否證形態（SPEC-004 §4.0.12）

票面要求「不寫『訊息應清楚』這類無法否證的敘述」。五項的否證方式：

| 項 | 內容 | 如何否證 |
|----|------|---------|
| M1 成分 | 五列成分表，其中「操作指引置於 `message`」「技術細節」「檔案路徑與明細」三列為禁止項 | 讀 ARB 值逐項比對；命中禁止項即違反，缺結果陳述即違反 |
| M2 長度與版面保障 | 全部語系最長值 × 兩種測試尺寸下 2 行內不截斷；觸發截斷時改寫文案不放寬上限；`withAction` 下動作 label 先讓步 | 渲染後量測；斷言併入 4.26 既有測試點，不另立測試 |
