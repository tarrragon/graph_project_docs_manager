### 一、三份 SPEC 的既有狀態提示條文盤點（補件之前）

盤點單位為「條文」，不是章節——同一節內可能一半回答形式、一半回答歸屬。
「回答了哪一半」的兩半定義為：**何時提示**（一個事件要不要顯示、用哪種載體）

### 二、發現（列出交 PM，本票未自行調和）

**發現一：`openedExternallyMessage` 的既有條文與判準 T 結論相反。**
SPEC-003 §2.2 外部開啟契約與 §3.5 互動反應表明訂 `opened` → SnackBar
`openedExternallyMessage`；SPEC-004 §4.26 slot 契約與 i18n 子節引用該 key；
§2.12 短暫非同步列亦要求「成功與失敗各有對應 i18n key」。
而判準 T1 判它不該顯示——`/usr/bin/open` 成功即代表外部應用程式已到前景，
我方視窗因此非前景，SnackBar 停留 `Motion.snackBar` 後自行消失，使用者切回來
時已無。`0.1.0-W3-167`〈不符者與處置〉已判定不符並交本票裁決（SR-3）。
**本票未改 §2.2、§3.5、§4.26 任一條文**，改在新增的 §2.13 內以對照表把該項標為
「判準判否、現行條文判是」並綁定待裁決狀態。
理由：移除一則既有的成功回饋屬行為變更，牽動三份 SPEC 四處條文與 `0.1.0-W1-068`
的測試斷言，超出「補提示元件需求與提示訊息設計」的範圍。
**PM 可採的兩條路**：(a) 裁定移除，另開 DOC 票同步四處條文與實作票；
(b) 裁定保留，則需在 §2.13 對照表寫明保留理由（判準的例外須有具名理由，
否則下一個事件會照抄這個例外）。

**發現二（非不一致，複驗結果為一致）**：SPEC-003 §3.5 與 §3.6 對同一個
`ExternalOpenResult.notFound` 給出不同回饋——§3.5（破洞報告）走 SnackBar
`sourceFileNotFoundSnackbarMessage` 帶 `rescanAction`，§3.6（節點詳情）走
狀態轉換 `state-nodeDetail-missing` 且明寫「不出現 SnackBar」。
表面上是同一事件兩種處置，實則**兩者皆符合判準 T2**：節點詳情有可見的狀態轉換
（T2 判是 → 不提示），破洞報告沒有（破洞項點擊不改變畫面狀態，T2 判否 → 提示）。
記於此是因為它是判準 T 目前唯一的跨畫面驗證點——若日後有人「統一」這兩處，
即為判準的違反。已寫入 §2.13 的對照表。

**發現三：SPEC-004 §1〈回饋通道子表〉標題掛「（提案）」，本票補件不解除。**
該子表的 state-change 列已寫入系統通知升級整段（用戶簽核 2026-09-08），
但標題仍為提案。本票在 §4.0.12 與 4.26 的補件會引用該子表。
**維持提案標記**——解除條件（PM 於本規格票驗收核定）不在本票 acceptance 內，
逕自拿掉等於代替他票裁定。

**發現四：SPEC-004 §4.42 `SwitcherOverlay` 反例列的「既有」二字已 stale。**
`SPEC-004:5784` 寫「以 `showDialog` / `AlertDialog` 呈現（**既有** `shell.dart` 空殼）」。
本票獨立複驗（PC-162）：`grep -rn "showDialog\|AlertDialog\|showModalBottomSheet\|Drawer("
lib/` → **0 命中**。所指的程式碼已不存在，該列是整改記錄而非現存衝突。
`0.1.0-W3-167` SR-9 併入本票。**本票已就地改為「整改完成」措辭**——此為文字與現況
脫節的更正，不含設計決策，與發現一的性質不同。
