## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
在 lib/app/router.dart 新增 NavIntent 列舉（rail/jump）、returnToProvider（單槽，AppDestination?）、
navigateTo(ref, target, intent) 與 consumeReturnTo(ref) 兩個入口函式，落實 SPEC-003 §2.3 四條規則：
rail 清空 returnTo、jump 記錄跳轉前畫面、連續 jump 只保留最近一次、返回時切至 returnTo 並隨即清空。
shell.dart 的 nav-item onTap 改呼叫 navigateTo(ref, item, NavIntent.rail)，取代原本直寫 provider。

首次可見訊號：visitedDestinationsProvider（Set<AppDestination>，初始空集合）+ firstVisibleProvider
（Provider.family<bool, AppDestination>），判斷「目前選取項 == destination 且不在 visited 集合」，
副作用（寫入 visited）延後至 Future.microtask 執行，避免在其他 provider 的 build 過程中同步改寫。
純 provider 層依賴 selectedDestinationProvider，不依賴 widget 生命週期，滿足 IndexedStack 一次建構
六頁但只在首次成為 index 時觸發訊號的要求。本票未接線任何畫面消費 firstVisibleProvider（無實際
惰性載入邏輯可接），只交出訊號本身，供後續畫面票使用。

返回鍵渲染：AppShell 新增 _ReturnToHeader（ConsumerWidget），watch returnToProvider，非 null 時
在內容區頂端渲染 TextButton.icon，key 為 action-<destination.name>-back，onPressed 呼叫
consumeReturnTo(ref)。SPEC-003 §2.4 要求的正式位置（PageColumn 根堆疊 SplitRow.header 右側
ButtonRow）待元件庫元件到位後替換渲染實作，本票的 _ReturnToHeader 只承接「AppShell 單一渲染、
六個畫面不各自定義返回錨點」這一份對外行為，錨點命名已依 §2.9 就位，之後替換渲染實作不影響
測試錨點。

既有 nav-item-/nav-page- 錨點未變更；action-ucFlow-back-to-domain（UC Flow 畫面既有的內容區
返回動作）不受影響，留在內容區內，未接觸 AppShell 層的 returnTo 機制。

### 自檢結果（Phase 4）
- 重構需要：否（新增 4 個 provider/函式 + 1 個 widget，各自單一職責，無重複邏輯）
- 技術債務：有（記錄如下，非本票範圍）
  1. _ReturnToHeader 是暫時渲染形式，待元件庫 PageColumn/SplitRow/ButtonRow 到位後需替換
  2. firstVisibleProvider 尚無任何畫面消費，需後續畫面票接線驗證
- 程式碼品質：A（dart analyze 0 issues；函式皆在 10 行內；provider 職責單一；有需求編號註解對應 SPEC-003 章節）
- 結論：不需立即重構，兩項技術債務已標記待後續票處理

補記：navigateTo / consumeReturnTo 的第一參數簽章改為 ProviderReader（T Function<T>(ProviderListenable<T>)）
而非 WidgetRef，因 WidgetRef 不是 Ref 的子型別、無法在純 ProviderContainer 測試中復用。
WidgetRef.read 與 ProviderContainer.read 皆符合此簽章，shell.dart 呼叫處改為 navigateTo(ref.read, ...) /
consumeReturnTo(ref.read)，測試直接傳 container.read，兩邊呼叫的是同一份實作，不重複邏輯。
