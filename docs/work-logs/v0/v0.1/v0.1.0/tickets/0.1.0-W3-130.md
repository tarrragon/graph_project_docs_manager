  **更根本的發現來自 `0.1.0-W3-110`：全套件結果在共用工作區下不是單票的觀測。** 同一 base 的兩次全套件執行得到不同的失敗集合（-13 vs -1），成因是他方未提交的工作區編輯在測試執行期間可見且持續變動。測試套件讀的是工作區，而工作區是共用且瞬時的（`tool-output-trust-rules` 規則 5 延伸）。


  後果分兩面，兩面都會出事：


  - **偽陽性**：他人在製品的紅燈被算進本票，執行者花時間排查與己無關的失敗，或誤判自己破壞了東西

  - **偽陰性**：他人尚未提交的**修復**讓本票的缺陷暫時不顯形，本票因此以「全綠」收尾，而該修復可能永遠不會提交


  `0.1.0-W3-095` 的情形使偽陽性這一面更難判讀：它的紅燈是 PM 明令「新斷言在修復前先紅燈」的產物——**刻意的紅燈與缺陷的紅燈在測試輸出上完全同形**，只有派發方知道差別。`0.1.0-W3-112` 因此只能標為瞬時觀測交回 PM，那是它當下能做的最強處置。'

    條文須回答三件事：


    1. **全套件結果的定位**：在共用工作區下它是共用狀態的觀測，不是單票的觀測。可作為「整體健康度」的參考，**不可作為單票驗收證據**。單票驗收須以能排除他方影響的方法取得。

    2. **三種方法的強度階梯**：變更集歸屬（最弱，只證明非自己造成）→ 還原重測（證明與自己無關）→ 子集雙向比對加建構點查證（另證明因果路徑不存在）。成本反向遞增，選擇依紅燈的嚴重度與排查成本。

    3. **刻意紅燈的存在**：新斷言在修復前先紅燈是正確做法（今日多張票明令要求），因此**共用環境中的紅燈不必然是缺陷**。執行者無法從輸出分辨，正確處置是標為瞬時觀測並交回派發方，不自行推斷性質。
