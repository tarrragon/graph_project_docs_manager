## Task Summary

分析 W3-336.3、.6、.9 撰寫者自檢表宣稱範例驗證段皆可溯，但獨立判定者在 W3-395 至 397 找到無依據句的檢查；判定是否應把 chained-examples 驗證段機械檢查改為獨立審查者執行，或補可機械執行的檢查步驟

## Problem Analysis
### 問題根因

`chained-examples.md`〈驗證段機械檢查：依據句可溯性〉的 Action 只寫「能不能在條文中找到對應的依據句」，未定義四件事：依據句須逐字到什麼程度、每個檢驗問句是否都要列入、依據句是否須支撐預期答案、範例本身的文字能否充當依據句。三位撰寫者（W3-336.3／.6／.9，皆 thyme-documentation-integrator）各自在這些未定義處判為合格，而撰寫者與檢查者是同一人。

### 影響範圍

- 已驗證：W3-336.3（foundation-design）、.6（version-bootstrap）、.9（dart-style-guardian）三份自檢皆宣稱合格，其中 13 處檢驗問句、推導列或段落位置實際不合格（分類見 Solution）。
- 已驗證：W3-397 的新自檢表與 W3-395 修正表仍是撰寫者自檢，未經獨立判定。
- 未驗證：本批以外、其他 skill 依同一檢查步驟自檢過的範例，漏判率未知。

### 相關 Error Pattern

同型機制：`test-assertion-design-rules.md` E2（守衛只給正常輸入，失效與合格同形）；framework issue #70（驗收訊號由裁量方自我寫入）。

## 重現實驗結果
### 實驗方法

以 `git show 47ef759b:<path>` 讀修正前的範例原文，逐問句比對三張票自檢表宣稱的依據句；再用 `git grep` 查該依據句在範例區塊以外的條文中有沒有出現。

### 實驗執行

- `git grep` 查「出事了但沒人知道」「同一概念長出多種樣子」「部署後才發現壞掉」：命中位置全在範例的【產出】或【驗證】段（dimension-product-notes.md 兩處範例、examples.md 兩處範例），條文命中為零。
- version-bootstrap SKILL.md 查「版面配置／可操作元件」：零命中。範例一 Q1、Q2 的預期答案靠這兩項判準得出；自檢表列的依據句是五詞關鍵字句，那句話推不出「彈窗屬 UI 類」。
- i18n-guidelines.md 範例：Q2 題文含 `'ISBN: $isbn'`；Q3 預期答案出現「貨幣、日期、格式化 API」。W3-336.9 的自檢表每則範例只列一個依據，#10 列的是標籤「參數化翻譯規則」而非引文，Q3 沒有列入。
- color-system.md 範例：Q1 含 `ColorScheme／TextTheme`；Q2 用了「掃描器 pattern 群組」；【產出】與【驗證】之間夾著 Dart 區塊。自檢表 #8 只列 Key Files 的 Theme 列。

### 實驗發現

已驗證：13 處漏判中 10 處落在 Action 未定義的四個地方；另 3 處違反的是〈【驗證】段〉寫得清楚的技術語法禁令，漏判原因是可溯性自檢表沒有這一欄，撰寫者只核對了依據句。未驗證：換成獨立審查者、但檢查步驟不變時，能攔下多少。W3-336.13 的探針（haiku，被問到時）對 V3-D2 b 是 0/3，這顯示光換人、步驟不變時鑑別力也低，但探針的角色是作答者而非審查者，不能直接等同。

### 1. 漏判型態分類表

| B 以標籤或同義改寫冒充逐字 | 1 | .9 i18n #10 列「參數化翻譯規則」 | 表尾「四項皆逐字」 |
| C 依據句存在但推不出預期答案 | 2 | .6 version-bootstrap 範例一 Q1、Q2（五詞句推不出「彈窗屬 UI 類」，需要「版面配置／可操作元件」） | 列五詞句，標「逐字」 |

| 合計 | 13 | | |

### 2. 歸因：步驟不可機械執行，且撰寫者與檢查者同一人，兩者都成立

- **步驟不可機械執行（主因，10／13）**：Action 只寫「能不能找到對應的依據句」。沒有規定逐問列表，所以出現 E；沒有規定逐字引文，所以出現 B，以及 .3 的「近似逐字」；沒有排除範例文字，所以出現 A；沒有要求引文推得出預期答案，所以出現 C、D。四個未定義處都讓「合格」可由撰寫者自己宣告。
- **同一人（放大因子，13／13）**：三張票都由撰寫範例的代理人自檢。A、C 型的判準是撰寫者自己在範例裡寫出的，撰寫者讀起來會覺得那本來就是條文。F 型的禁令本身寫得清楚（〈【驗證】段〉），但它不在可溯性表的檢查欄內，自檢時只看了表上有的欄。
- **反證**：光換人不夠。W3-336.13 的探針被直接問到時，V3-D2 b 是 0/3；獨立判定者之所以攔得下，是因為他對每題先從條文寫出正確答案與依據句，這一步本身就是機械化的逐問比對。

### 3. 候選改動

| 候選 | 做法 | 攔得住的型態 | 機會成本 |
|------|------|------------|---------|
| 甲 零工具：把檢查步驟改寫為可機械執行 | 見草稿甲 | A、B、D、E、F；C 攔得住一部分（多了支撐欄，但仍由人判讀） | 每則範例的自檢表變長，約每問一列；仍是撰寫者自檢，C 的語意判讀仍可能放水 |
| 乙 改造既有：支撐欄交獨立審查者 | 新增範例的 DOC 票完成前，由非撰寫者（basil-writing-critic，接 basil-writing-critic 既有的強制觸發條件「規則／Skill／方法論檔案變更後」）只複核甲表的「支撐」欄與 A 型欄；接入點是 skill-design-guide〈發布前檢查清單〉加一列 | C、A 的殘餘 | 每張補範例票多一次派發；審查者若沒有甲的表可核，會退回探針的 0/3 水準，因此乙依賴甲 |
| 丙 新增工具：逐字引文比對腳本 | 驗證段每問改附行內出處標記 `〔依據：<檔>〈<錨點>〉「<引文>」〕`；腳本對引文 `grep -F` 條文檔，排除範例的程式碼圍欄與【輸入】【產出】【驗證】段後才算命中；另對驗證段做啟發式掃描（`$`、`.of(`、`()`、CamelCase 識別符） | A、B、E（標記缺漏即紅）、F 的大部分 | 既有範例全數要補標記（遷移成本）；腳本本身要有對照測試（E2：至少一個已知該紅的輸入，例如本表 A 型原文）；C、D 屬語意，腳本攔不住 |

建議：先採甲（本身就有效，且是乙、丙的前提），同一批接乙的支撐欄複核；丙等甲的行內標記格式定下來後再評估。只採丙會把標記格式與遷移成本壓在尚未穩定的步驟上。

### 4. 草稿甲（取代〈驗證段機械檢查：依據句可溯性〉的 Action 段；本票不落檔）

> **Action**：撰寫或審查【驗證】段時，逐問填下表，每個檢驗問句或 Then 句一列，不得合併、不得省略：
>
> | 問句 | 引文（逐字複製） | 出處（檔〈錨點〉） | 引文位置在範例之外？ | 引文推得出預期答案？ | 驗證段無程式語法／框架名？ |
>
> 1. 引文必須逐字複製，且在出處檔 `grep -F` 能命中；改寫、摘要、標籤（如「參數化翻譯規則」）一律判不合格。
> 2. 命中位置落在任何範例的【輸入】【產出】【驗證】段或程式碼圍欄內，判「條文查無依據句」。
> 3. 「推得出」欄：只讀引文、不讀範例，能否得出預期答案的每一個判定詞；預期答案出現引文沒有的判準詞（如「版面配置」），判否。
> 4. 問句本身在問「是否可追溯到條文」時，不算檢驗問句，刪除。
> 5. 第六欄依〈【驗證】段〉禁止內容表判定，問句與預期答案都要查。
> 6. 任一欄為否，依下方檢查結果表處置；不得以「近似逐字」或總括句宣告合格。
