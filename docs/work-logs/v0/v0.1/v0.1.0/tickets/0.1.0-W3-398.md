# Execution Log

## Task Summary

分析 W3-336.3、.6、.9 撰寫者自檢表宣稱範例驗證段皆可溯，但獨立判定者在 W3-395 至 397 找到無依據句的檢查；判定是否應把 chained-examples 驗證段機械檢查改為獨立審查者執行，或補可機械執行的檢查步驟

## Problem Analysis
### 問題根因

`chained-examples.md`〈驗證段機械檢查：依據句可溯性〉的 Action 只寫「能不能在條文中找到對應的依據句」，未定義四件事：依據句須逐字到什麼程度、每個檢驗問句是否都要列入、依據句是否須支撐預期答案、範例本身的文字能否充當依據句。三位撰寫者（W3-336.3／.6／.9，皆 thyme-documentation-integrator）各自在這些未定義處判為合格，而撰寫者與檢查者是同一人。

### 影響範圍

- 已驗證：W3-336.3（foundation-design）、.6（version-bootstrap）、.9（dart-style-guardian）三份自檢皆宣稱合格，其中 11 個檢驗問句或推導列實際不合格（分類見 Solution）。
- 已驗證：W3-397 的新自檢表與 W3-395 修正表仍是撰寫者自檢，未經獨立判定。
- 未驗證：本批以外、其他 skill 依同一檢查步驟自檢過的範例，漏判率未知。

### 相關 Error Pattern

同型機制：`test-assertion-design-rules.md` E2（守衛只給正常輸入，失效與合格同形）；framework issue #70（驗收訊號由裁量方自我寫入）。

## 重現實驗結果
### 實驗方法

以 `git show 47ef759b:<path>` 讀修正前的範例原文，逐問句比對三張票自檢表宣稱的依據句；再用 `git grep` 查該依據句在範例區塊以外的條文中有沒有出現。

### 實驗執行

- `git grep` 查「出事了但沒人知道」「同一概念長出多種樣子」「部署後才發現壞掉」：命中位置全在範例的【產出】或【驗證】段（dimension-product-notes.md 兩處範例、examples.md 兩處範例），條文命中為零。
- version-bootstrap SKILL.md 查「版面配置／可操作元件」：零命中。範例一 Q1、Q2 的預期答案靠這兩項判準得出；自檢表列的依據句是五詞關鍵字句，那句話推不出「彈窗屬 UI 類」。
- i18n-guidelines.md 範例：Q2 題文含 `'ISBN: $isbn'`；Q3 預期答案出現「貨幣、日期、格式化 API」。W3-336.9 的自檢表每則範例只列一個依據，#10 列的是標籤「參數化翻譯規則」而非引文，Q3 沒有列入。
- color-system.md 範例：Q1 含 `ColorScheme／TextTheme`；Q2 用了「掃描器 pattern 群組」；【產出】與【驗證】之間夾著 Dart 區塊。自檢表 #8 只列 Key Files 的 Theme 列。

### 實驗發現

已驗證：三張自檢表的漏判都落在 Action 未定義的四個地方；沒有任何一例是依據句寫得清楚卻被檢查者看漏。未驗證：換成獨立審查者、但檢查步驟不變時，能攔下多少。W3-336.13 的探針（haiku，被問到時）對 V3-D2 b 是 0/3，這顯示光換人、步驟不變時鑑別力也低，但探針的角色是作答者而非審查者，不能直接等同。
