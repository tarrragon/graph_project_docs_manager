  兩種修法的差別是結構性的，不是工作量：


  | 修法 | 涵蓋範圍 | 漏掉的可能性 |

  |------|---------|-------------|

  | 各呼叫點加 log | 實查為 6 個呼叫點、3 個檔案（`shell.dart`／`gap_report_screen.dart`／`scan_notification_controller.dart`） | 每新增一個呼叫點就可能漏，**而漏掉的那個正好不會被發現**——它沒有 log |

  | 元件內部加 log | 全部呼叫點，含未來新增的 | 結構上不可能漏 |


  **元件是回饋的終端，因此也該是觀測的終端。** 這與 `INV-FEEDBACK-001` 是同一件事的兩面：該不變式要求元件在每一次互動都發出第一層回饋；把日誌掛在元件內部，等於讓該不變式自己留下可稽核的痕跡。與 `ARCH-GPD-001`「日誌不抵扣使用者回饋」互為反面——該則講日誌有記不代表使用者收到回饋，本案是使用者回饋不留日誌，故它失效時無人知道。

    2. **靜默早退**：元件內若有 `context.mounted` 之類的守衛而不顯示，**必須記錄**（warning 等級）——那是目前唯一完全無痕跡的失敗路徑

    3. **動作被按下**：使用者按了動作按鈕（如「檢視」），該互動本身是第三層回饋的消費點

    4. **自動消失或被取代**：若元件可判定，記錄結束原因；不可判定則於註解說明為何不記
