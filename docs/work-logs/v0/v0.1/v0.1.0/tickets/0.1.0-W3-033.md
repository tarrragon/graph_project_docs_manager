## Solution
### 分析結論

以 canonical 為基準的全庫盤點結果：**58 個共同 skill 的發佈庫獨有檔案為 0**，
**發佈庫獨有的整個 skill 目錄 9 個（61 檔）**。W3-025 找到的那一筆（tdd/examples/
flutter-sdk-tdd-walkthrough.md）已於同日被發佈庫 commit 5828ec3 刪除，是目前全庫唯一一筆
確認過的此類殘留；陽性對照證實同一管線在該檔存在時會報出它，故 0 是真陰性。

票面預設「發佈庫獨有即繞過 canonical 寫入的分叉」，此前提在 skill 目錄層級不成立。
canonical 的 skill 名稱集合與本專案本地 .claude/skills 完全一致，它是本專案 .claude 的快照，
不是全 consumer 的聯集；另一 consumer 用 skill-sync push 送進發佈庫的 skill，本來就不會經過
canonical。因此二選一的判定框架（回收 / prune）對這 9 個都不適用，需要第三種結論。

### 逐筆判定

發佈庫獨有的 9 個 skill 目錄，判定一致為**不動**（既不回收也不 prune）。共同依據三條，
逐筆的個別證據列於表內：

- canonical 的 git log --all --diff-filter=ADR 對這 9 個路徑全部為空——從未進過 canonical，
  不是刪除後未傳播的殘留
- 各自有獨立的多版本演進歷史，且全部被 2026-09-02 的全庫 CHANGELOG 重構覆蓋到，屬在維護狀態
- 領域為內容生產（教學模組、知識卡、migration playbook、商業研究、團隊評估），
  與本框架專案（Flutter 桌面應用的文件流工具）不重疊

### 候選方案

| 方案 | 內容 | 利 | 弊 |
|------|------|----|----|
| A：全數 prune | 對 9 個目錄執行帶 --prune 的清除 | 讓發佈庫與 canonical 對齊，之後的盤點差集恆為空 | 刪掉另一 consumer 正在維護的 61 個檔案（最近一次改動距今 3 天）。skill-sync 預設保留 remote-only 檔案正是為了防這件事，本方案是刻意繞過該保護 |
| B：全數回收進 canonical | 把 9 個目錄併入 canonical 的 skills/ | 差集同樣歸零，且無資料損失 | canonical 是本專案 .claude 的快照，回收等同在本專案安裝 9 個用不到的 skill，膨脹每次 session 的 skill 索引。且下次本專案 sync-push 會把它們固化進 canonical，讓「canonical 是誰的快照」這件事再也說不清 |
| C：不動，改為記錄拓樸（採用） | 9 個維持現狀，把 canonical 非超集這件事寫進 skill-sync 文件 | 無資料損失、無索引膨脹；把「下一個人會重犯同一個誤判」這個真正的風險關掉 | 差集不會歸零，日後每次盤點都要重新認出這 9 個屬正常存量——這正是要靠文件消化的部分 |

採 C。A 與 B 都是為了讓一個數字歸零而動內容，而該數字本身出自錯誤前提。真正需要修的是前提
沒有被記錄下來：本票差一步就照票面把這 9 個判成殘留。
