### 問題根因
父票 039 十四項審查發現中的第 5、6、10 項：linux 指出 §2.4 只承認三類導航反應但「返回」實為未承認的第四類；§2.3 規則 1（rail 切換一律清空 returnTo）表面上看似與部分畫面（Domain 視圖、追溯視圖、破洞報告正常態）不消費 returnTo 產生矛盾；「採單槽而非堆疊」的理由用「堆疊會產生回到哪一層的歧義」，但規則 3（A→B→C 場景下單槽返回目標明確定義）已示範堆疊/連續跳轉語意可以是明確的，該論證自相矛盾。

### 影響範圍
docs/spec/ui/SPEC-003-interaction-response.md §2.3、§2.4、變更歷史。範圍依團隊主管指示限定於這三處，未觸碰 §3.x 逐畫面表格（039.4 或既有 SPEC-001 定案範圍）。

### 調查發現（範圍邊界說明）
本票驗收條件中「破洞報告正常態的 returnTo 有消費者」原可能被讀為需在 §3.5 新增返回按鈕，但查證 SPEC-001 §5 破洞報告正常態（無破洞／有破洞）的退出路徑欄本就只列「導覽、切換專案」，並未定義「返回」為合法退出路徑；在 §3.5 新增返回按鈕會逾越 SPEC-001 授權範圍。改採 §2.3 澄清：規則 1（任一畫面下一次 rail 切換皆清空 returnTo）本身即是這些畫面的合法通用消費者，與規則 4 的專屬返回錨點是同一變數的兩種消費路徑，非互斥矛盾。此判讀完全落在指示範圍（§2.3）內，未修改 §3.5。
