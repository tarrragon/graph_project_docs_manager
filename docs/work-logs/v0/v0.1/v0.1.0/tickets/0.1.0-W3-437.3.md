- 問題：元件外觀隨元件自身資料態改變（如封存卡片變暗），要建模為狀態集的一個狀態，還是變體參數。

  - (B) 變體參數：改 step-3 狀態集來源刪資料態；正例一改變體寫法；〈共用規則一〉原文不動。

## 重現實驗結果
### 實驗方法

本票為建模慣例評估，「重現」指取得兩類事實：(1) 本專案既有元件規格實際把資料態驅動的外觀放在哪一欄；(2) 業界設計系統對「狀態」與「變體」的分界基本率。

- 專案：`grep -c "| 資料態" docs/spec/ui/SPEC-004-component-library.md`；逐列讀命中的狀態矩陣列；`grep -n "tone\|修飾參數"` 同檔；`grep -rn "修飾參數\|tone" .claude/skills/component-contract-design`。
- 方法論：`component-library-bidirectional-constraint-methodology.md`〈元件契約判準〉欄位順序段。
- 業界：WebFetch Adobe Spectrum Design Data states registry、Primer StateLabel 文件；WebSearch Material Design states。

### 實驗執行

### 實驗發現

已驗證的事實：
1. 業界基本率：「狀態」除互動瞬態外，普遍納入由應用資料決定、執行期可切換的二元旗標（disabled、selected、pending）。「變體」保留給呼叫端依設計意圖選定的樣式族或尺寸；三個來源皆未見把執行期可切換的資料旗標建模為 variant。
2. 業界另有第三種形態：分類資料值直接映射外觀（Primer `status`、SPEC-004 Badge `tone`）——既非狀態也非變體，是值對映參數。
3. 本專案 SPEC-004 已隱含採用選項 A（42 列資料態狀態列），並已實際使用第三種形態（tone／修飾參數），但 skill 條文未收錄第三種形態。
4. 方法論把狀態集定為回饋契約的節點；資料態若降為變體，其轉場（例：封存變暗的過渡）在回饋契約中沒有節點可掛。

仍未驗證的假設：archived 的「可操作性」是否改變（封存卡能否點入詳情）屬正例情境的設計決定，本評估不定；草稿沿用 437.1「可操作：同 default」。

## Solution
multi_view_status: skipped

### 評估框架

wrap-decision 完整模式：錨點（W2 開工閘門：skill 範例與條文不得教出相反判定；F-16 修補方向取決於本慣例）→ Step 0（非個人化諮詢；所需事實為專案規格與業界慣例，已於重現實驗取得，充足）→ W → R → A → P。

### 判定

**資料態驅動的外觀，依「資料在元件上的形狀」分流，不是二選一**：執行期可切換、有進有出的元件旗標（封存、選中、停用、展開）歸狀態集；分類資料值直接映射外觀（狀態徽章依狀態值取色）是值對映參數，不開狀態列也不立變體；變體只留給呼叫端依設計意圖選定、元件生命期內不變的形態。封存卡變暗屬第一類，歸狀態集——即選項 A。

### W：選項

假設根因層先寫明：本問題的根因假設是「skill 缺一條判準區分外觀的驅動者」，而非「條文字面寫錯」。

| 選項 | 做法 | 假設 |
|------|------|------|
| A 歸狀態集 | 437.1 草稿六處（規則一與 path-b 步驟 3 補射程子句；正例一補 archived 狀態、測試契約與輸入段） | 資料態旗標與互動瞬態同屬元件自身狀態 |
| B 變體參數 | step-3 狀態集來源刪資料態；正例一改 `archived` 變體；規則一不動 | 凡非互動的外觀差皆為呼叫端選定形態 |
| C 三分流（A + 值對映） | A 全部，另於 step-3 變體列補一句：分類資料值映射外觀者為值對映參數，不進狀態集、不立變體 | 資料態有「旗標」與「分類值」兩種形狀，後者現行條文無落點 |
| D 呼叫端承載 | 封存變暗由清單容器以不透明度包覆，卡片不知封存 | 封存是畫面級呈現決定 |
| E 刪範例語句 | 正例一不提封存（437.1 選項 D） | 範例不必示範此邊界 |

品質檢查：
- 框架測試：五項無法一句話概括（落點分別為狀態集／變體／分流判準／容器／不處理）。
- 三類涵蓋：改造既有（A、B、C）、零工具（E）、搬移責任（D）；新增工具不適用。
- 關聯性：C 是 A 的超集，實質差異只在第三類的落點；D 與 B 在「元件不持封存狀態」上同向。
- 反向思考：若 B 正確——變體是建構時選定，執行期資料旗標翻轉時等於元件在變體間跳轉；狀態矩陣的來源、同步策略、進入、退出四欄在變體表中沒有對應欄，封存的退出路徑與「等確認才顯示」的同步策略會無處可寫，死胡同檢查失去覆蓋。反向論述不成立。若 D 正確——封存若同時改變可操作性（例如封存卡不可觸發動作），容器無法改卡片內部行為，只能靠參數分岔，回到 B；D 只在「純外觀、行為完全不變」時成立，射程窄於問題。

### R：現實檢驗

| 證據 | 支持 |
|------|------|
| 業界：Spectrum states registry 含 disabled／pending／selected；Material states 含 disabled／selected／activated 並可與互動瞬態疊加 | A（資料旗標是狀態） |
| 業界：Primer StateLabel 以 `status` prop 承載議題狀態值；`variant` 原管尺寸且已棄用 | C 的第三類存在；三來源皆未把執行期資料旗標建為 variant，B 無基本率支撐 |
| 本專案 SPEC-004：42 列狀態矩陣列來源為資料態（NavItem selected、AppButton disabled、ProjectSwitcherEntry expanded、IssueMarker） | A（已隱含採用） |
| 本專案 SPEC-004：Badge `tone`、AppText 修飾參數明標「非變體」，且不為各狀態值開狀態列 | C（第三類已在用，skill 未收錄） |
| 方法論〈元件契約判準〉：回饋契約是邊、狀態集是節點 | A（封存過渡需節點） |

基本率結論：B 在業界與本專案皆無先例；A 是主流；C 補的第三類在業界（Primer）與本專案（Badge）皆有實例，不是新發明。

Steelman B：變體寫法讓元件 API 單一軸、呼叫端一眼可見全部外觀組合，測試矩陣「變體 × 狀態」較小。C 的三個缺點：(1) 讀者要多學一個類別；(2) 「旗標 vs 分類值」邊界在多值旗標（例：active／archived／deleted 三態生命週期）上可能模糊；(3) 條文增一句，skill 體量增加。缺點 (2) 的處置：判別問句用「每個值是否有各自的可操作性或進出路徑」——有則狀態集，只有取色則值對映。

### A：拉開距離

| 選項 | 機會成本 | 風險 | 不選其他的代價 |
|------|---------|------|--------------|
| A | 437.1 草稿六處照落檔，零新增成本 | 第三類（分類值取色）讀者仍可能照正例一的寫法把每個狀態值開成狀態列，與 SPEC-004 Badge 做法相反 | 不選 C：skill 與本專案既有規格留一處未收錄的慣例 |
| B | 需反向改 step-3 並重寫 SPEC-004 42 列，擠壓 W2 開工 | 失去進出與同步策略欄的死胡同覆蓋 | 不選 A：與業界基本率和既有規格雙重背離 |
| C | A 的成本 + step-3 一句 | 新增子句措辭若不準，會把旗標誤導向值對映 | — |
| D | 零條文改動 | 行為變動時失效 | 不選 A：封存行為變更時無契約可寫 |
| E | 零連動 | 失去唯一邊界示範，下個範例重撞 | — |
