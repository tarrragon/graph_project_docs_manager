### Rationale Chain
- 0.1.0-W3-166 why: **用戶裁示（2026-09-09）**：「元件層內建回饋日誌應成為元件庫的通用契約條款。這些元件庫的回饋可以成為測試的判定依據，尤其這是最終使用者真正看到的資訊，**如果我們只驗邏輯，整個資訊鏈還是有可能中斷**。」

該裁示有一個當日的實證。`0.1.0-W3-078` 第二次實機驗證中，`0.1.0-W3-096` 附帶的診斷測試綠燈（`authorizationStatusCalls == 1`，程式邏輯正確），但實機上**沒有任何紀錄能回答「使用者看到了什麼」**——`denied` fallback 的 SnackBar 是否顯示，日誌上與靜默失敗完全同形，唯一分辨手段是人眼即時觀察，而 SnackBar 會自動消失。該項因此未取得。

**測試驗到了「程式做了對的事」，沒驗到「使用者收到了對的資訊」，而兩者之間還有一整段。** 元件層日誌記的不是「呼叫了顯示」，是「這個字串被顯示出來了」——這是資訊鏈最末端唯一可留存的證據。

**為何是條款而非個案**：`0.1.0-W3-165` 修的是 `AppSnackBar` 一個元件。條款層級的固化使後續新增的任何終端回饋元件自動受同一約束，不需要每次重新論證；同時讓元件層日誌取得**驗收依據**的正式地位，而非僅是除錯便利。

**與既有條文的關係**：`INV-FEEDBACK-001` 要求元件在每一次互動都發出第一層回饋，但該不變式**沒有觀測面**——違反時沒有任何東西會叫。本條款是它的觀測對偶：規範加上它自己的觀測面，才是完整的一組。（來源已完成，結論見 Solution）
- 0.1.0-W3-175 why: `0.1.0-W3-166` 落地的方法論 v1.18.0 有三處以絕對路徑引用 `docs/spec/ui/SPEC-003-interaction-response.md`（`L224`／`L397`／`L404`，實查）。`.claude/` 經 sync 擴散至全部 consumer 專案，**其他專案沒有該檔**——它們讀到的是指向空處的「定義正本」，而該方法論新增條款的整個前提（本節是該不變式的觀測對偶）就掛在那個引用上。與 `reference-stability-rules` 規則 8 同族，識別符由 ticket ID 換成專案檔案路徑。

**為何是升格而非改寫引用形態**：保留 `INV-FEEDBACK-001` 這個 ID 當跨專案共同錨點、卻讓定義留在專案檔，是不融貫的——ID 若要當共同錨點，定義必須在框架層，否則該 ID 在別的 consumer 不存在或指向別的東西。故只有兩條路：升格定義，或棄用 ID。該不變式的內容（元件在每一次互動都必須發出第一層回饋，即使服務因防抖、節流或冪等而丟棄該次呼叫）不含任何專案特定成分，且已被方法論／`layered-test-strategy`／SPEC-003／SPEC-004 當共同錨點在用，故升格。

**為何拆成框架側與專案側兩票**：框架自足是純加法，不需動 SPEC-003。升格後、`0.1.0-W3-173` 完成前，兩處是兩份相同敘述（重複）；而現況是懸空指標。**重複可以慢慢收，懸空不行**，故兩步互不阻擋且中間狀態嚴格較優。

**本票存在的原因是時序**：修正指示於 `0.1.0-W3-166` complete 之後才送達執行代理人，該票已終態，不重開。原代理人 transcript 尚在，重新派發可沿用其既有 context。（來源已完成，結論見 Solution）
