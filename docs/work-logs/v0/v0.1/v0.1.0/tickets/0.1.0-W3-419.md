**B-03b + B-04b（input-mechanism.md〈四個決策維度〉Keyboard type 小節，同一缺口，兩則範例共用）**
草稿：「決策表填入的值須為可跨框架轉譯的中性描述（如「隱碼型鍵盤」「email 型鍵盤」），不得直接寫特定 UI 框架的鍵盤型別列舉名稱；框架對應可另立旁註欄，不進決策表本體。」
會改變哪些判定：目前條文完全未限制決策表用詞形式；補上後，不限 Keyboard type，Submit model／IME policy 等其他維度的決策表寫法都會被要求比照辦理，屬新增的通用書寫規範。

**B-05（input-mechanism.md〈場景一：表單〉驗證時機段落）**
草稿：「判準是規則能否在使用者裝置本地、不需伺服器參與就算出結果：能→格式驗證（on blur）；需要查詢或核對伺服器狀態→業務驗證（on submit）。」
會改變哪些判定：目前條文僅以「格式明確／格式不明確」的例子帶過，沒有可機械執行的測試；補上「能否本地算出」後，格式正確但仍須查重複（如 email 唯一性）等邊界案例的既有分類需要重新核對是否仍落在原本歸類。

**B-12b（screen-state-matrix.md〈四欄定義〉或檢查清單「error 類狀態」項）**
草稿：「error 類狀態涵蓋所有代表『功能因失敗或中斷而無法正常使用』的狀態，包含連線類流程的 disconnected；兩者都須同時提供『重試』與『返回』兩個選項。」
會改變哪些判定：「error 類狀態」一詞目前外延未定義，只在範例中把 disconnected 一併處理；明文定義後，timeout／expired／revoked 等語意相近的既有狀態是否也算 error 類會被連帶追問，可能牽動其他規格已寫定的狀態分類。

**B-13（interaction-feedback.md〈按鈕級回饋〉timeout 兜底句）**
草稿：「緩衝量沒有固定公式，由規格撰寫者依該操作的重要性與使用者等待耐性決定，只要求『略大於後端逾時值』。」
會改變哪些判定：目前條文只給「略大於」的方向，沒交代決定權與依據；補上後等於明文承認本節不再提供精確公式，未來若要追加「重要操作應如何量化緩衝秒數」的細則，須先修改本句。

**B-14c（screen-state-matrix.md〈填寫步驟〉步驟 2 或步驟 3；目前規則僅存在於〈填寫範例〉步驟 3 的敘述中，屬範例內文字不算條文）**

**B-15（screen-state-matrix.md〈容易漏列的狀態：initializing〉段落）**
草稿：「一般的單次請求（發出、等待、回應到達即結束）不算獨立生命週期——其存續完全依附本次畫面互動，不需要 initializing 狀態；只有查詢對象在本次互動之外仍持續存在（常駐服務、另一 process）才需要。」
會改變哪些判定：目前條文只 positive 定義「有生命週期時」要加 initializing，沒有排除「單次請求」；補上後，既有規格中把「等待中」誤標為 initializing 的畫面會被要求改判為一般 loading。

**B-16（screen-state-matrix.md〈反模式〉「進入條件不可逆」段落）**
草稿：「判斷可逆性只看是否存在能讓狀態轉回進入前那一刻的操作；單純的畫面導覽返回（不改變狀態本身）不算反向操作。」
會改變哪些判定：目前條文只舉一個「連線成功／斷開連線」的例子，沒有「導覽返回不算」的排除規則；補上後，既有規格中把「返回上一頁」當成已滿足〈檢查清單〉「反向操作」要求的既有判定都要重新檢查。

**B-19b（error-recovery.md〈重試機制〉間隔策略段落）**
草稿：「固定間隔場景（前景瞬斷）與指數退避場景一致，都須提供『立即重試』按鈕，讓使用者可以跳過等待；重試中的 UI 三要件（正在重試／已重試次數／下次時間）兩種間隔策略皆適用。」
會改變哪些判定：目前「立即重試按鈕」只明確綁定在「伺服器過載訊號…指數退避」子句，固定間隔子句沒有這個要求；補上後，只為指數退避場景設計立即重試按鈕、固定間隔場景略過的既有畫面會被判定為缺口。

**B-24（navigation-patterns.md〈iOS HIG vs Material Design 慣例差異〉選擇策略表後）**

**B-29（gate-fallback.md〈破壞性操作確認 gate〉段落）**
