## Problem Analysis
### 問題根因

dart-style-guardian 寫的是「不該怎麼做」。每一類約束的正面寫法都分給 foundation-design（token 階）與 component-contract-design（契約欄位、豁免、baseline）處理。所以分歧最容易出在兩種位置：(1) 需要讀者判斷「該歸哪一階／哪一類」的位置；(2) 兩個 skill 對同一件事（豁免、原生元件直用、baseline、token 名）各自表述的交界。除此之外，正文與 references 的所有對照表都以 UIColors／UISpacing／UIFontSizes／`context.l10n!` 為名，校準檔卻是 AppPalette／AppSpacing／AppTypography／`AppLocalizations.of(context)`。〈起手〉明文禁止讀者「自己編一組類別名」，正文本身卻示範了一組不存在的類別名。

### 影響範圍

已驗證（Read 全文 + grep）：SKILL.md 與 references 共 4 份（color-system／spacing-system／typography-system／i18n-guidelines），另含 component-contract-design 的 SKILL.md〈與相鄰資產的交界〉、addresses.md、step-3〈逐元件欄位來源〉、step-5 遷移票。scripts/style_checker.py 只讀了 pattern 群組，用來核對文字宣稱與掃描器實際行為是否一致。
未驗證：`.claude/methodologies/component-library-bidirectional-constraint-methodology.md` 的豁免三條件、〈元件文字歸屬〉全文沒有讀，交界列中引用這兩處的部分標為「術語定義在別處」，細節由修補票核對。

### 相關 Error Pattern

同型：PC-166 家族以外沒有直接對應。「文件宣稱與工具行為脫節」和 language-constraints 規則 5 的 OpenCC 案例屬同一機制（規則文字與實作脫節、無人察覺），本票不另建 error-pattern。
