## Problem Analysis
### 問題根因

`add-acceptance` 的 `value` 參數語意是「條目文字」，CLI 自行補正規 `[ ]` 前綴；
但 `--help` 只寫「驗收條件文字」，未說明這個自動處理。使用者複製票面既有字面
（已含 `[ ] `）貼入時得到雙前綴，且該結果是合法字串，CLI 不報錯。

`set-acceptance --add`/`--edit` 屬同一根因但範圍更廣：0.1.0-W3-208 已修好
底層剝除邏輯（`_strip_checkbox_prefix`），但只改了 `track_set_acceptance.py`
的實作，未回頭補 `track.py` 內這兩個旗標的 `--help` 文字——行為已修正但
介面未告知使用者「這裡也會自動處理」，是文件與行為不同步的殘留缺口。

### 影響範圍

- `.claude/skills/ticket/ticket_system/commands/track.py`：`add-acceptance`
  的 `value` 位置參數、`set-acceptance` 的 `--add`/`--edit` 旗標，三處 help
  文字缺漏同一類說明。
- `.claude/skills/ticket/ticket_system/commands/fields.py`：`add-acceptance`
  的實作（`execute_add_acceptance`）原本完全不剝除誤帶的前綴，是三處中
  唯一連底層行為都未修正的（`set-acceptance` 側已在 0.1.0-W3-208 修好）。
- `docs/work-logs/v0/v0.1/v0.1.0/tickets/0.1.0-W3-012.md`：frontmatter
  acceptance 第 1 列因舊行為產生雙前綴殘留資料，屬 0.1.0-W3-208 掃描時
  已列出但未授權修正的已知缺陷。

### 相關 Error Pattern

與 `IMP-BAL-013`（locale 使 `uniq` 靜默合併相異 CJK 字串）同族：總數守恆、
狀態正確、唯獨內容或分組有多餘/錯誤字面，且無警告——雙前綴不影響
`check-acceptance`/`complete` 的驗收判定，唯一受害者是依字面掃描的動作
（如 `grep '\[ \]'`）。

## Context Bundle

**需求摘要**: 讓 `add-acceptance` 的 help 說出它會對輸入做什麼，而不只說輸入是什麼。

**現況（已驗證：`ticket track add-acceptance --help`）**

```
positional arguments:
  ticket_id          Ticket ID
  value              驗收條件文字
```

`value` 的描述是「驗收條件文字」——沒有任何訊息說明 `[ ]` 前綴會被自動補上。而票面存的字面是 `- '[ ] 條件內容'`，複製票面字面是最自然的操作。

**PM 未受影響的原因（供執行者理解影響面）**：本 session 今日全部使用 `set-acceptance --add`（可一次傳多條）而非 `add-acceptance`，且傳入時未自帶前綴，故無雙前綴產生。實查全部 ticket md，`[ ] [ ]` 零命中。**這代表問題的觸發需要「用 `add-acceptance` 且自帶前綴」兩個條件同時成立**，不是普遍發生——但一旦發生不會報錯。

**這是一類問題的第三個實例，本票的價值在此**

| 參數 | help 描述 | 實際處理 |
|------|----------|---------|
| `add-acceptance` 的 `value` | 「驗收條件文字」 | 自動補 `[ ]` 前綴 |
| `create --acceptance` | 「驗收條件」 | **不**以逗號分隔，整串當一條 |
| `create --where` | 「影響檔案（逗號分隔）」 | 以逗號分隔 |

前兩者的 help 描述看起來同構，實際處理相反——使用者從介面上得不到區分依據。**共同形態是 help 描述參數「是什麼」，不描述參數「怎麼被處理」。**

acceptance 第 3 條要求檢視同一 CLI 內其他自動處理輸入的參數，即為此——**只修一個等於承認前兩個實例不算數**。

**約束**

- 目標檔在 `.claude/` 之下，命中派發豁免，**不要加 `isolation: "worktree"`**。
- 這支 CLI 是多個 session 共用且執行者自己會呼叫，改完立刻跑測試（`PC-GPD-010`）。
- 第二步（冪等處理）是評估項不是必做項。**不做也是合法結論**，但須說明理由——冪等看似更安全，仍須先確認沒有人刻意需要字面的方括號開頭內容。

**PM 補充：第四個實例是分隔符不一致，不是 help 缺漏（2026-09-09，實查）**

並行 session 回報 `set-related-to` 與 `append-log --section` 為新實例。**實查後兩者的 help 都有寫**，本票不應把它們列為 help 缺漏：

- `ticket track set-related-to --help` 的 epilog 明寫：「value 是單一位置參數：多個 ID 須引號包成一個字串，字串內以空格分隔；不加引號會被 shell 拆成多個參數，argparse 報 unrecognized arguments。」並附兩則範例。
- `ticket track append-log --help` 的 usage 行為 `[-h] --section SECTION ...`——`--section` 未加方括號，argparse 慣例即表示必填。

**但真實的問題還在，只是位置不同：同一支 CLI 內兩個清單型參數用相反的分隔符。**

| 參數 | 分隔符 | 是否有 help 說明 |
|------|--------|----------------|
| `create --where` | **逗號** | 有（「逗號分隔」） |
| `set-related-to` 的 value | **空格**（且須引號包成單一字串） | 有（epilog） |

兩者都有文件，**問題在於使用者不會為每個參數重讀 help**——剛用完 `create --where` 的逗號，下一個命令換成空格，慣性會直接沿用。這與本票原本三個實例的機制**不同**：那三個是 help 沒說，這個是 help 說了但介面本身違反一致性預期。

**對本票範圍的意義**：兩類問題的處方不同。help 缺漏補文字即可；分隔符不一致補文字**不夠**——因為文件已經存在而人仍會踩。要嘛統一分隔符（破壞性變更，須評估既有呼叫端），要嘛讓兩者都接受兩種分隔符（相容性做法）。

執行者請於 Solution 明確區分這兩類，並就分隔符不一致給出結論：**統一／雙向相容／維持現狀並僅記錄**三選一，附不選另兩者的理由。若判定屬破壞性變更超出本票（ADJ／P3）範圍，登記 spawn request 交 PM，不自行擴大。

**一項方法教訓（並行 session 提供，值得寫進 Solution）**：回報缺陷前先實查該處的 help 全文——包含 argparse 的 epilog 段，它不在 `--help` 輸出的前幾行。本次兩則回報都是在踩到錯誤後憑印象歸類為「help 沒說」，而實際上錯誤訊息與 epilog 都寫了。**踩到與沒有文件是兩件事。**

### Rationale Chain
- 0.1.0-W3-208 why: `ticket track set-acceptance --add` 的參數語意是「條目文字」，CLI 自行補 `[ ]` 前綴。
但介面沒有任何地方阻止呼叫者把 `[ ]` 也寫進文字，寫了就得到雙重前綴。

實例：`0.1.0-W3-169` 的第 8、9 兩列現為 `'[x] [ ] 0.1.0-W3-167 裁定 A ...'`
（PM 於 2026-09-09 以 `--add` 建立時帶入字面 `[ ]`）。

**後果不是排版醜。** `check-acceptance` 認前綴故判定正確，票面顯示也正常——
唯一的受害者是「以 `grep '\[ \]'` 跨票掃未完成 acceptance」這個動作，它會在一張
已完成的票上得到兩個誤命中，且該票 9/9 全勾、狀態 completed，掃描者沒有任何
線索可判斷這是假陽性。錯誤形態與 `IMP-BAL-013`（locale 使 `uniq` 靜默合併
相異 CJK 字串）同族：總數守恆、狀態正確、唯獨分組錯誤，且無警告。

**根因在工具不在使用者。** 依 `opinionated-default-design` 主張 1，文件寫「別把
`[ ]` 寫進 `--add` 的文字」不會贏過工具的預設行為——工具沉默接受就會一直有人寫。（來源已完成，結論見 Solution）
- 0.1.0-W3-214 why: **同一個 `ticket create --help` 輸出裡，四個多值參數用兩種分隔符**：

| 參數 | help 寫的分隔符 |
|------|---------------|
| `--where` / `--where-files` | 逗號，如 `'file1.py,file2.py'` |
| `--blocked-by` | 逗號，如 `'ID1,ID2'` |
| `--related-to` | 逗號，如 `'ID1,ID2'` |
| `--acceptance` | **`|`**，如 `'條件A|條件B'` |

三比一。**呼叫者在同一次呼叫中先用三次逗號，第四次沿用逗號是這個介面自己教出來的**，
而它是唯一失敗的那個——逗號不是分隔符，六條判準被當成一條字串收下。

**失敗完全無聲**：不報錯、不警告、票面顯示正常、`check-acceptance` 判定正常。
唯一的損失是驗收粒度——六條當一條勾，任何一條沒做到都不會被單獨標示出來。

**實例**：`0.1.0-W3-208` 建立時 PM 以逗號串接六條判準，實際存入 1 條
（`grep -c '^- '` 於該票 acceptance 段回傳 1）。

**這不是文件缺口。** `references/create-command.md:87-89` 的範例正確且完整
（`--acceptance "條件A" --acceptance "條件B"` 與 `"條件A|條件B|條件C"` 兩種都有），
`--help` 也寫對了。**問題在於正確的說明擋不住錯誤的習慣**，而那個習慣是同一支
CLI 的其他三個參數建立的——依 `opinionated-default-design` 主張 1，工具的預設
行為會贏過文件。

**本專案已認得這個危害類別。** `acceptance_parser.detect_numbered_list_collapse`
的存在就是為了「使用者把 N 條塞進一個值裡」這件事，但它只偵測**換行的編號列表**
（`1. ` / `2、`），單行逗號串接是同一危害的另一種表面形態，未被涵蓋。（來源已完成，結論見 Solution）
