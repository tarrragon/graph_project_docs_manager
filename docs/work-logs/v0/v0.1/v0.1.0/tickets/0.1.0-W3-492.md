## Task Summary

## Problem Analysis
### 問題根因

框架把「spec／UC 文件的位置」與「程式碼的位置」綁成同一個根。`doc` CLI 的
`FileLocator.__init__` 以 `<project_root>/docs/{proposals,spec,usecases,events}` 推導全部
文件路徑，而 `get_project_root()` 的三層解析（`CLAUDE_PROJECT_DIR` → `git rev-parse
--show-toplevel` → 往上找含 `docs/` 的目錄）其中兩層直接以「文件在被操作 repo 的版控內」
為前提。issue #109 的 U5 把 spec 與 UC 移到專案外的外接資料夾後，這個單根假設不成立。

單根之所以能撐到現在，是因為既有專案的文件與程式碼確實同根。外接模式把兩者拆開，凡是
同時觸及文件與程式碼的命令（`doc test-map`、`doc uc verify`、`doc uc trace`、
`uc-reference-validation-hook`）就失去一個可解析的根，而它們的失敗形態是靜默通過，不是
報錯（見「重現實驗結果」實驗 6、7）。

### 影響範圍

盤點方式與命中位置見「重現實驗結果」。共 38 個讀寫點，分布於 6 類載體：doc CLI 根解析
（2）、doc CLI 命令（11）、`uc_registry` 與 `tracking_schema`（4）、hook（6）、
ticket／spec／tdd skill（5）、文件敘述型（10）。

已驗證的事實：

- 以 `CLAUDE_PROJECT_DIR` 指向外接資料夾時，純文件命令（`doc domain`、`doc uc list`、
  `doc create`）全數正常，寫入落點正確（實驗 2、3、8）
- 雙根命令在外接模式下產出假陰性而非錯誤（實驗 6、7）
- `doc` shim 以 cwd 的 git root 是否含 `.claude/skills/doc` 決定能否啟動；外接模式下
  cwd 若在被操作 repo 則 CLI 完全不可用（實驗 1）

仍未驗證的假設：

- 12 個判定為「需改寫」的點，其改寫成本尚未逐點估算（本票只做判定，不做設計）
- 外接資料夾內是否保留 `docs/` 中間層，兩案的下游影響已在 Solution 對比，但未經實際
  協作案驗證

## 重現實驗結果
### 實驗方法

兩段。第一段用 grep 盤點讀寫點；第二段實際搭一組「外接資料夾 + 被操作 repo」佈局，
跑 `doc` CLI 觀察各命令在雙根下的實際行為。

盤點指令（在 repo 根執行）：

```
git grep -ln -E "docs/spec|docs/usecases|docs/use-cases|docs/proposals|traceability\.yaml|app-use-cases|domain-map" -- .claude/
grep -rn -E "project_root|get_project_root|FileLocator\(|/ \"docs\"|os\.path\.join" --include="*.py" .claude/skills/doc/doc_system/
```

第二段佈局（建於 scratchpad，實驗後刪除）：

```
w3492/
  operated-repo/        （git init 的被操作 repo，無 .claude/）
    lib/main.dart       （含 UC-01 引用）
    lib/bogus.dart      （含未定義的 UC-99，正向對照輸入）
  external/             （外接資料夾，非 git repo）
    docs/app-use-cases.md      （SSOT，含 UC-01）
    docs/spec/ui/SPEC-001-x.md
    docs/usecases/
```

### 實驗執行

| # | 指令 | 觀察到的實際行為 |
|---|------|-----------------|
| 1 | cwd=`operated-repo`，`doc domain` | `doc: 找不到當前專案的 .claude/skills/doc（cwd 不在已配置專案內，或非 git 倉庫）`。shim 以 cwd 的 git root 是否含 `.claude/skills/doc` 為啟動條件 |
| 2 | `CLAUDE_PROJECT_DIR=external doc domain` | 正常列出 `ui` |
| 3 | `CLAUDE_PROJECT_DIR=external doc uc list` | 正常列出 `UC-01 掃描工作區` |
| 4 | `CLAUDE_PROJECT_DIR=external doc uc verify` | 「驗證通過，無違規 token」 |
| 5 | `CLAUDE_PROJECT_DIR=external doc uc verify <operated-repo>` | 「驗證通過，無違規 token」 |
| 6 | 加入 `bogus.dart`（UC-99）後重跑 4、5 | 4 仍「驗證通過」（假陰性）；5 抓到 `發現 1 處違規 UC 編號: ../operated-repo/lib/bogus.dart:1:UC-99` |
| 7 | `CLAUDE_PROJECT_DIR=external doc test-map` | 「沒有找到任何 UC 文件」——掃描目標為 `external/test`、`external/integration_test`，被操作 repo 的測試完全不在範圍內 |
| 8 | `CLAUDE_PROJECT_DIR=external doc create usecase --title 測試` | 正確寫入 `external/docs/usecases/UC-001-測試.md` |

實驗 6 是本盤點的鑑別力來源：4 與 5 在無違規輸入下輸出完全相同（實驗 4、5），單看那組
結果無法分辨預設掃描範圍是否涵蓋被操作 repo。放入一個已知該被攔下的 UC-99 之後，兩者
才分開。

### 實驗發現

已驗證的事實：

1. **單根參數化已部分可用**：`CLAUDE_PROJECT_DIR` 指向外接資料夾即可讓純文件命令
   （query／list／nav／domain／create／validate／uc list）全數運作，前提是外接資料夾內
   保留 `docs/` 中間層。這是 22 個「可參數化」判定的實證基礎，不是推論。
2. **雙根命令的失效是靜默的**：`doc uc verify`（無 path）與 `doc test-map` 在外接模式下
   把被操作 repo 整個排除在掃描範圍外，輸出分別是「驗證通過」與「沒有找到任何 UC 文件」
   ——兩者都是成功語氣。錯誤不會被使用者看見。
3. **`uc verify` 已有部分出口**：其位置參數可指定掃描路徑，但輸出的檔案定位是相對 doc
   root 的相對路徑（`../operated-repo/lib/bogus.dart`），跨出資料夾邊界後對讀者不可用。
   `doc uc trace` 與 `doc test-map` 沒有對應參數。
4. **shim 是最外層的前提**：外接模式下 CLI 必須從分析者端（有 `.claude/skills/doc` 的
   repo）啟動，不能從被操作 repo 啟動。這條約束須寫進 SR-1 規格，否則使用者的第一個
   動作就會失敗。

仍未驗證的假設：

- 文件敘述型讀寫點（F 群 10 點）的「可參數化」判定屬人工判讀，無自動化驗證手段
- hook 群（D 群）未實際在外接佈局下觸發驗證，判定依程式碼路徑解析方式推導

## Solution
### 1. 讀寫點清單（38 點）

判定三類：**可參數化**＝把根換成外接資料夾即生效，不改邏輯；**需改寫**＝根換掉之後語意
仍然不對，須改成位置無關契約或拆雙根；**不適用**＝外接模式下這個讀寫點本身不成立。

「本框架自身專案的讀寫點」（讀 `.claude/` 自有資產者）依票面 how.strategy 第 4 步排除在
判定之外，僅在表中標明並說明排除理由。

### 工作項表與 spec／UC 的相對位置

工作項表（`inventory.md`）放在外接資料夾**根層**而非 `docs/` 之下。理由是它不是 doc CLI
的節點型別，放進 `docs/` 會被 `doc validate` 的檔名規範檢查（B8）與 `uc verify` 的全量
掃描（B6）掃到，產生非目標的違規回報。放根層則兩者都不觸及。

工作項表的「影響範圍」欄填被操作 repo 的相對路徑（如 `lib/foo.dart`），「來源」欄填外接
資料夾內的相對路徑（如 `docs/spec/ui/SPEC-001-x.md`）。兩種路徑的基準不同，規格須明寫，
否則交付後對方無從判斷某條路徑該從哪裡起算。
