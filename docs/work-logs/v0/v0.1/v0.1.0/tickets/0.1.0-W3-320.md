## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 判準取自 0.1.0-W3-319（收窄版），非 315 原定寬鬆版

`validate_owner` 改為：前綴須等於 `_project_owner_prefix()` 推導值、尾碼須為 session uuid 前 8 碼十六進位（`^<prefix>-[0-9a-f]{8}$`），取代 315 原定的寬鬆 `[a-z0-9]+`。實測 `_project_owner_prefix()` 在本 worktree（`.claude/worktrees/agent-*`）內仍正確推導為 `graph-project-docs-manager`——`git rev-parse --git-common-dir` 回傳主 repo 的 `.git`，worktree 隔離不影響此推導。

### 前綴推導失敗時的降級（acceptance 2）

`validate_owner` 內 `_project_owner_prefix()` 呼叫包 `try/except Exception`；推導拋例外時降級為 `GENERIC_OWNER_FORMAT_RE`（不錨定前綴，僅檢查 `<kebab 前綴>-<8 碼十六進位>` 形狀），不因推導失敗硬擋合法 owner。現行 `_project_owner_prefix()` 實作本身已對 `git` 失敗內部 fallback 為 `Path.cwd().name`（不拋例外），故此降級路徑目前僅由測試以 monkeypatch 觸發驗證；真實環境要進入此路徑需該函式本身改為會拋例外（超出本票範圍，函式簽名未變）。

### transfer-owner 逃生口（acceptance 3）

新增 `validate_owner_for_transfer`，只檢查通用形狀不錨定本專案前綴，`cmd_transfer_owner` 改呼叫它。跨 consumer 移交（如把 owner 轉給另一專案的 session 識別）因此不受本專案前綴限制；仍拒絕代理人角色名與底線值等不符通用形狀的值。

### 候選方案評估：uuid 尾碼是否應退化為顯示用（未採用）

Prompt 提出的候選——前綴只作顯示、判定只吃 uuid 段——與 320 acceptance 5「須拒絕他 consumer 值」直接衝突：若判定不比對前綴，`blog-cd-af3d9b12` 這類他 consumer 值會通過，正是 0.1.0-W3-315 裁決一要保住的過濾能力（讀取端三處皆前綴比對）。已用 `test_validate_owner_rejects_other_consumer_prefix` 實測驗證錨定路徑正確擋下此值。故維持前綴錨定為主要判準，僅在推導失敗（例外）時退化為通用格式檢查——此路徑不影響對「其他專案前綴但推導正常」的值的過濾能力，因為推導正常時仍走錨定分支。

「該函式現行回退是 `Path.cwd().name`，讀取路徑推錯只是漏篩，寫入路徑推錯會拒絕合法 owner」——此為 315 提出、319 沿用的既有風險，本票未變更 `_project_owner_prefix()` 本身的 fallback 邏輯（僅在其拋例外時降級，非其回傳「可能錯誤但不拋例外」的值時降級），故該風險本票不解、亦不新增。是否須改造 `_project_owner_prefix()` 使其對「使用 fallback 分支」可觀測（如回傳 tuple 或旗標）超出本票範圍，未展開處理，理由：本票 acceptance 未要求此項，且無法在本地驗證他 consumer 目錄名與其前綴慣例是否一致（315／319 皆標為「未驗證假設」）。
