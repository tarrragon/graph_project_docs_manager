## Solution
<!-- Schema[DOC/Solution]: 免填（DOC 類型以變更摘要取代）（.claude/pm-rules/ticket-body-schema.md） -->
四項缺陷逐一查證與修法（執行者：thyme-documentation-integrator，實際落於 `references/` 四檔）：

1. **模式 B 步驟 5 跳過步驟 2（仍存在，照票面修）**：`modes-a-b.md:61` 原「進模式 A 自存在必要性檢視起」改為「專案另有狀態表者，先補跑模式 A 步驟 2 的『顯示』欄與『可用操作』欄兩處候選來源（避免漏掉只在單一狀態出現、畫布未畫出的元件），再自存在必要性檢視起；無狀態表者直接自存在必要性檢視起」。

2. **模式 C 步驟 5 事故清單無輸入通道（仍存在，照票面修）**：`mode-c.md:26-27` 補「來源三選一：issue tracker 既有紀錄、ticket 描述提及的缺陷、用戶口述提供的清單，逐一標明取自何處」與「三者皆查無時視同零事故」的分支條件。

3. **統一匯出入口無定位作法（重新查證後：仍存在，非拆分順帶解決）**：`addresses.md:19` 該列「地址」欄查證時仍寫「定位作法尚未給，見待補票」——拆分只是把定義搬進地址表，未補作法。已補「先找元件目錄根層的 barrel／index 檔或套件匯出宣告（舉例：`index.dart`、`components.ts`、`pubspec.yaml`／`package.json` 的 `exports`）；找不到時退路為模式 C 步驟 1 的元件盤點結果反推事實上的範圍，並建工具票補齊匯出宣告」。票面 `where.files` 未列此檔（票寫於單檔時期），但地址表是統一匯出入口唯一的定義落點，於此修正屬正確位置。

4. **多形態專案節為整節散文（重新查證後：仍存在，非拆分順帶解決）**：CHANGELOG 記載的節界修復只還原 `##` 標題，未動內文體例。`field-questions.md` 該節原單一段落已改寫為兩張表——「十一欄位跨形態的共用範圍」（跨形態共用 6 欄 vs 每形態各一份 6 欄+容器條目）與「形態因素矩陣的每形態填一次維度」（覆蓋表面對映／回饋通道／最小命中區 token／禁放區與安全區），剩餘判準句（同一語意落在不同容器與操作機制、設定項與斷點的差異）留散文，體例與同檔其餘節（如十一欄位問句表）一致。

**版號處置（與票面指示衝突，已擇一執行並記錄）**：票面 Problem Analysis 同時要求「不要改 SKILL.md」與「frontmatter metadata.version 要改」，兩者矛盾；且查證時 `SKILL.md` frontmatter 已被同期 agent 併行改為 1.5.4（`dispatch-language.md` 的不相關修法），驗證票面預警屬實。依「不要改它」的明確指示，本次未觸碰 `SKILL.md`；改於 `CHANGELOG.md` 新增 1.6.0 條目記錄四項修法，並於條目內註明 frontmatter 版號待併行工作結束後再同步，避免與進行中的併行編輯衝突。CHANGELOG 新增內容原含票號引用，遭 `reference-stability-rule8-guard-hook` 阻擋（框架 skill 禁引用專案層級識別符），已改為指向 CHANGELOG 自身 v1.3.0 條目的描述性引用，不含 ticket ID。
