## Problem Analysis
### 問題根因

`_openItem`（`lib/screens/gap_report/gap_report_screen.dart`）對外部開啟只寫了成功路徑：

```dart
await Process.run('open', [item.filePath]);
if (!context.mounted) return;
AppSnackBar.show(context, message: l10n.openedExternallyMessage);
```

`ProcessResult` 被整個丟棄，`exitCode` 從未讀取，因此**任何**開啟結果都顯示「已在外部開啟」。
這比靜默失敗更糟：靜默失敗使人重試，假成功使人相信檔案已經打開然後往下走。

同一條接線上的另一半不對稱：`Process.run` 拋例外（`ProcessException`，例如可執行檔不存在）時
無人接住，例外傳到 `FatalErrorGate` 被收斂為 `BlockedState`——開一個檔案失敗把整個畫面變成
阻擋狀態。兩種失敗一種太輕（假成功）一種太重（全畫面阻擋），中間正確的刻度（一則失敗
SnackBar）反而缺席。

判準（`ARCH-GPD-001` 解決方案 3）：收斂之後的狀態必須有可見表現，且該表現要與事件成比例。

### 影響範圍

`lib/screens/gap_report/gap_report_screen.dart::_openItem`，SPEC-003 §3.5「破洞項」三列。
四處外部開啟（§3.1／§3.2／§3.5／§3.6）中只有 §3.5 已接線，其餘三處尚未實作，故本票只動這一處。

### 相關 Error Pattern

`ARCH-GPD-001`（互動回饋掛在服務的成功路徑上）。本案是該則的一個變形：回饋不只是「失敗時消失」，
而是「失敗時回報成功」——`await` 之後無條件顯示成功訊息，等於把成功路徑的回饋掛在了所有路徑上。

## Solution
### 修改內容

| 檔案 | 變更 |
|------|------|
| `lib/screens/gap_report/gap_report_screen.dart` | `_openItem` 拆出 `_runOpen`：檢查 `exitCode`、`try`/`catch` 收斂例外，回傳診斷字串或 `null`；依結果二選一顯示 SnackBar；失敗時 `developer.log` level 900 記路徑與 stderr。新增 `gapItemProcessRunnerProvider` 測試接縫 |
| `lib/l10n/app_zh.arb`、`app_en.arb`、`app_localizations*.dart` | 新增 key `externalOpenFailedMessage`（見下方「跨票影響」） |
| `test/unit/screens/gap_report_test.dart` | 新增 group「破洞項外部開啟」三則：exitCode 0／exitCode 非零／呼叫拋例外 |

三個結局各有一則回饋，缺任一則即為靜默失敗或假成功：檔案不存在 → `sourceFileNotFoundSnackbarMessage`
＋重新掃描動作（既有，不動）；`exitCode == 0` → `openedExternallyMessage`；其餘（非零 exitCode 或
例外）→ `externalOpenFailedMessage`。日誌與使用者回饋兩項義務分別滿足，不互相抵扣（`ARCH-GPD-001`
解決方案 5）。

### 與 `0.1.0-W1-036` 三結果契約、`0.1.0-W1-068` 的關係（acceptance 3）

**本票是 `0.1.0-W1-068` 的前置，不是與它競爭的暫時修補。** 三點論證：

1. **語意同構，非另立一套。** 本票落地的三個結局與 SPEC-003 §2.2 的 `opened` / `notFound` / `failed`
   一一對應，連 SnackBar 文案都取 §3.5 兩列與 §2.2 指定的同一組 key。本票沒有發明第四種結局，
   也沒有把任何一種結局併掉。
2. **本票不建立抽象。** `gapItemProcessRunnerProvider` 的型別就是 `Process.run` 本身
   （`Future<ProcessResult> Function(String, List<String>)`），不含結果列舉、不含存在檢查、
   不含 `/usr/bin/open` 路徑決策——它是替身掛點，不是 `ExternalOpener` 的第二實作，因此不觸犯
   `ARCH-BAL-012`（第二實作重新發明已迴避的假設）。`0.1.0-W1-068` 落地時的動作是替換而非重寫：
   `_runOpen` 整個刪除，`_openItem` 改讀注入的 `ExternalOpener.open(path)` 的三分支，本 provider
   一併刪除。程式碼註解已寫明這條退場路徑。
3. **不做本票的代價是假成功存活到 `0.1.0-W1-068` 排上為止。** 該票的驗收含實機項（簽章 .app 內對
   檔案與目錄各測一次 exitCode），成本高於本票且尚未排程；而假成功是使用者已經撞到的缺陷
   （`0.1.0-W3-103` 接線盤點），兩者不宜綁在同一個排程上。
