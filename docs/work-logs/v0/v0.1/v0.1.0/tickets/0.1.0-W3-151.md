## Problem Analysis
### 問題根因

依票面 how 段指示，先查證 `specs:` / `usecases:` 兩鍵是否被任何程式路徑讀取，範圍涵蓋 `.claude/skills/doc/doc_system/` 全域，發現與初步結論不一致的兩層事實：

1. **`doc_system/` 內部零消費**（`grep -rn '\.get("specs"\|\["specs"\]\|\.get("usecases"\|\["usecases"\]' .claude/skills/doc/doc_system/` 零命中）：`status.py` 只讀 `proposals` 鍵；`create.py` 的 `_add_tracking_entry` 只在 `doc_type == "proposal"` 呼叫，`doc create spec` 從未寫入 `specs:` 段；`batch_init.py` 只讀 `proposals` 鍵；`list_cmd.py` 的 `list_specs`/`list_usecases` 呼叫 `FileLocator`，其實作掃描 `docs/spec/`／`docs/usecases/` 檔案系統，不讀 yaml。此層與票面觀察（`doc status` 只輸出提案總數）一致。

2. **擴大搜尋範圍至 `.claude/skills/ticket/` 後找到真實消費者**：`.claude/skills/ticket/ticket_system/lib/spec_reference_checker.py` 的 `_collect_spec_ids()` 遞迴走訪整份 `proposals-tracking.yaml` 的所有字串值擷取 `SPEC-NNN`（不限定 `specs:` 鍵路徑），`load_registered_spec_ids()` 讀取 `docs/traceability.yaml` + `docs/proposals-tracking.yaml` 聯集作為「SPEC 登錄簿」，供 `ticket create` 建票時經 `create_reporter.py` 呼叫 `detect_unregistered_spec_references()` 警告未登錄的 SPEC 引用。**結論：`specs:` 段非死資料，是 `ticket create` 建票時的真實輸入。**

**實測證據**（比照 `0.1.0-W3-140` 手法，直接呼叫函式而非猜測）：
- backfill 前（`git show HEAD:docs/proposals-tracking.yaml`）：`_load_yaml_spec_ids()` 回傳 `{SPEC-001, SPEC-004}`。
- backfill 後：`load_registered_spec_ids()` 回傳 `{SPEC-001, SPEC-002, SPEC-003, SPEC-004, SPEC-005}`；`detect_unregistered_spec_references({'what': '涉及 SPEC-002 SPEC-003 SPEC-005', ...})` 由「會產生警告」變為 `[]`。
- 即 SPEC-002/003/005 漏登會使建票時引用這些規格的新票收到假的 `UNREGISTERED_SPEC_REFERENCE_WARNING`，警告文字會誤導讀者「確認編號是否誤植」，而正確反應應是補登錄簿（同 `0.1.0-W3-140` 對 SPEC-004 的診斷）。

**usecases 段同型漏登檢查**：`.claude/skills/ticket/` 全域搜尋未見類似 `spec_reference_checker.py` 的 UC 版本消費者——`context_bundle_extractor.py` 的 `_detect_uc_references` 雖會擷取 ticket 文字中的 `UC-\d{2}` 引用，但改呼叫 `doc uc summary --json` 讀 `docs/usecases/` 檔案系統，不讀本 yaml，非聯集登錄簿消費者。`doc_system/` 內部同樣零消費（同上）。逐筆核對 `docs/proposals-tracking.yaml` 的 `usecases:` 段：UC-01 至 UC-06 共 6 筆，與 `docs/usecases/` 目錄下 6 份檔案、CLAUDE.md 記載的 UC-01~06 完全一致，**無漏登**。

usecases 段目前確認為零消費、零漏登，與本票 acceptance 限定範圍（校準 specs 段漏登）無關，本票不處置。其「零消費本身即與 SPEC-004 引用的清單不雙份維護原則相悖」一事已另開 `0.1.0-W3-174`（P3 DOC，source_ticket 本票）追蹤，不以口頭延後帶過。
