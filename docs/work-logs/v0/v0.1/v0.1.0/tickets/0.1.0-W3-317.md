### 問題根因

`component-contract-design` 這次修好的是「內容拆分造成的閱讀割裂」：正文跳躍、references 無閱讀引導、讀某一節時不知道還有另一節。它的〈與相鄰資產的交界〉表指名四個相鄰 skill——若只修一端，讀者被導過去之後落回同一形態，等於在交界處重新製造它。

### 影響範圍（派發探針前的靜態量測）

**互指矩陣**（各 SKILL.md 內指名對方的次數）：

| 從＼到 | component | foundation | ux-design | dart-style | version-boot |
|--------|-----------|-----------|-----------|-----------|-------------|
| component-contract-design | — | 3 | 3 | 1 | 2 |
| foundation-design | 1 | — | 1 | **0** | 5 |
| ux-design-evaluation | 1 | **0** | — | **0** | **0** |
| dart-style-guardian | 1 | **0** | **0** | — | **0** |
| version-bootstrap | 1 | **0** | **0** | **0** | — |

兩處是明確的單向斷裂，不是「剛好沒提到」：

- `foundation-design` 五處寫「交回 `version-bootstrap`」「本 skill 的產物交給 `version-sequencing` 排版本」，`version-bootstrap` 零處提及 `foundation-design`。下游不知道有上游會把東西交過來。
- `foundation-design` 的載體表列「執法工具」一類、工作流第 5 步要求「機械檢查接入執法載體」、Common Issues 有一列專講「執法載體裝了卻從沒擋下違規」——全程未指名 `dart-style-guardian`。讀者被要求接一個沒有名字的東西。

### 更正：description 超標不是「未被發現」，是已凍結的既有債

上文把兩處 description 超標列為硬違規，語氣暗示它們未被察覺。查證後更正：

`.claude/hooks/skill-description-baseline.json`（產生於 2026-09-08）已凍結 **22 個 skill** 的 description 超標值，`ux-design-evaluation: 989` 與 `dart-style-guardian: 260` 都在其中。`skill-description-length-check-hook.py` 的 `WARNING_THRESHOLD = 250` 只對 baseline 以外的新增違規告警——這正是 `foundation-design` 自己工作流第 5 步寫的做法（「首次接入執法載體必然大量失敗：設 baseline 凍結既有違規、只擋新增，再逐批收斂」）。

**這改變兩件事**：

1. **事實層**：這兩項是 22 項待收斂清單中的兩項，不是漏網。原本的寫法會讓讀者以為執法層失效，實際上執法層正照設計運作。
2. **處置層**：本票只收斂這兩項（它們落在本次審查範圍內），**修完必須同步移除 baseline 中的對應條目**，否則 baseline 留著一個比實際值大的凍結值，等於替未來的回退預先簽名。其餘 20 項不在本票射程，不順手改。

`i18n-guidelines.md` 零入站連結與 `version-bootstrap` 超標零 references 兩項未在任何 baseline 內，仍為未被任何機制發現的缺口。
## 重現實驗結果
### 實驗方法

**本節於派發探針之前寫定，內容不得於探針回報後修改。** 事後訂門檻會被「這次寫得更清楚了」蓋過去；事後補作者意圖清單會使分母被回溯填補、重點涵蓋度差集塌成空集。

**批次形態（2-B⁗）**：每個 skill 一批、每批 3 個低階 model 實例，同批內指令逐字相同，不含任何審查框架（不告訴它們這是在找問題），明令禁止臆測填補（不知道就寫不知道）。判準取分歧的分布，不取任一份報告。

**共同提問（五問，逐字相同）**：

1. 照這份文件工作，我的第一個具體動作是什麼？
2. 這份文件要我產出什麼？
3. 有哪些情況這份文件叫我去別的地方？各是哪裡？
4. 讀完之後，我還不知道但需要知道的是什麼？
5. 這份文件與哪些其他 skill 有分工關係？各自的界線在哪？

第 1 問對應規則類文件的「第一個具體動作」要求；第 5 問是本票特有，直接量測互指斷裂在讀者端的後果。

| 排除項無轉介地址 | ux-1、ux-3 各自主動指出：文件說不涵蓋「視覺風格設計（品牌色、字型、間距美學）與使用者研究方法」，**但沒說誰負責** | **2/3，處置** |

**排除項無轉介地址是一個獨立於互指矩陣的發現**：矩陣只量「有沒有指名對方」，量不到「明示排除卻不給去向」。而品牌色、字型、間距正是 `foundation-design` 的 UI 維度與 `dart-style-guardian` 的 token 體系所管——排除句寫對了，缺的是後半句。兩個讀者在無提示下各自指出同一處，是這一項最強的證據。

**本 skill 是四者中結構最健康的**：它有〈觸發路由〉表，而該表在三個讀者身上全部生效。這反過來替處置方向作證——四個 skill 缺的不是內容，是路由表這個裝置。

## 方法限制的補記：3/3 不是三個獨立確認

本票兩輪皆以「同批 3 個實例、同一 model、指令逐字相同」為形態，並以分歧的分布為判準。**這個設計本身共用取樣面**——三個實例讀同一份檔、用同一個 model、拿同一組提問，它們一致時，排除的是「單一實例的隨機波動」，**不排除「這個 model 對這種寫法一致地讀錯」**。

因此本票的計數該這樣讀：

| 觀測 | 能推出 | 不能推出 |
|------|--------|---------|
| 3/3 答不出 | 這份文件對這類讀者穩定失效 | 無（此向可靠——失敗是穩定的就是缺陷） |
| 3/3 答對 | 這份文件對這類讀者穩定有效 | **不能推出對其他讀者有效**。三個一致可能只是同一個盲點的三份副本 |

**兩個方向的證據強度不對稱**：失敗方向上，一致性是壞消息的加強；成功方向上，一致性不構成獨立確認。本票的處置全部基於失敗方向（3/3 或 0/3 命中），這一側不受影響；但**複驗判「已解決」時，依據的是成功方向**，該側的證據強度低於計數的表面值。

**降低此限制的做法（本票未做，記為方法缺口）**：換一個 model 家族跑一批對照，或改用不同措辭但同義的提問。兩者本票皆未做——換 model 會使兩輪不可比，換措辭會構成新批次。這是「維持可比性」與「取樣獨立性」之間的實際取捨，本票選了前者，代價寫在此處。

本項與並行 session 同日判定的一個框架問題同構：兩個 session 各自查證同一份輸出、各自漏掉同一半（欄位以外的鍵），兩人的結論互相佐證而缺陷完好。**「各自查證」不等於「獨立查證」——共用取樣面時，一致性不增加資訊。**
## 實驗發現

### 已驗證的事實

1. **Q5「與其他 skill 的分工」在四批全部命中**，且與派發前的互指矩陣量測獨立吻合。矩陣量的是文字有沒有出現，探針量的是讀者有沒有帶走——兩種方法在同一組結論上重合，排除任一方的量測誤差。
2. **路由表這個裝置有效，缺它就失效**。`ux-design-evaluation` 有〈觸發路由〉表，Q3 三份全數正確；`dart-style-guardian` 的連結列在第 8 節〈Related Documentation〉之下且不完整，Q1 三份三答案、孤兒 reference 0/3。同一份文件的其他條件相近，差別在裝置的有無與位置。

4. **同一個詞在同一份文件內指兩件事，會被讀者當成缺陷回報**。`version-bootstrap` 的「全自動」相隔六行兩義，2/3 主動提問。
5. **明示的排除若不附轉介地址，讀者會停在那裡**。`ux-design-evaluation` 排除視覺風格設計，2/3 指出不知道該找誰。

### 本輪方法的已知限制（誠實記錄，不修飾）

五個共同提問**沒有直接探測部分作者意圖項**——例如 `ux-design-evaluation` 的「四個核心支柱」與 `dart-style-guardian` 的「六種常見違規」，讀者未被問到，因此它們的重點涵蓋度差集**本輪不可量**，不得因為「沒人提」就判為漏。這是提問設計的缺口，非文件缺陷。複驗時若要覆蓋這幾項，須另加一問（例如「這份文件有哪幾條你必須遵守的硬規則」），且該問一旦加入即構成新的批次，不與本輪合併計數。
