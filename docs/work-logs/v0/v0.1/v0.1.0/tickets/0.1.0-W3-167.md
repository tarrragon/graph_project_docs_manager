#### 二、失效形態是「替換截斷」，不是「視覺重疊」

`AppSnackBar.show` 在 `messenger.showSnackBar(...)` 之前**無條件**呼叫 `messenger.hideCurrentSnackBar()`（`lib/components/app_snack_bar.dart`，元件內註解標為「新的 SnackBar 取代 → dismissed（SPEC-004 §4.26 狀態矩陣退出路徑）」）。加上 `ScaffoldMessenger` 本身一次只呈現一則、其餘排隊，**兩則提示在版面上同時可見在本專案的結構下不會發生**。

實際的失效是前一則被提前關閉，使用者可能一個字都沒讀到。更尖銳的是 `hideCurrentSnackBar()` 作用於佇列最前端的項目：若第二次 `show` 發生在第一則被呈現的 frame 之前，該則會**一 frame 都未顯示就消失**，且目前全程無痕跡。

這一項對第三個子問題有直接後果：它正是票面所稱「程式主動決定不告知使用者」的實例，而且是**可由原始碼判定**的，不需要執行 App。

#### 三、共時可達性（可達性事實，非推測）

兩個觸發源彼此獨立，可落在同一時窗：

- 使用者操作驅動：`_openItem`（點選破洞項）
- 背景掃描驅動：`_showDeniedSnackbar`，含 `_pendingDeniedNotification` 於 `resumed` 時的延後 flush

因此「兩則提示在同一顯示時窗內爭用」不是假設，是既有控制流即可達的狀態。**尚未取得的是頻率**，見下節。

**機制解釋**（層一，對應 A 的 `命中次數=0`）：`showSnackBar` 只在
`_snackBars.isEmpty` 時呼叫 `_snackBarController.forward()`；`hideCurrentSnackBar`
在 `_snackBars.isEmpty` 時直接 return。故同步區塊內兩次 `show` 的實際序列是——
第一次：hide 為 no-op，佇列空故 `forward()`，加入 A；第二次：佇列非空且 controller
未 dismissed，故 `reverse()`（此時動畫值仍約為 0，反轉瞬間完成），加入 B，且因佇列
非空**不再** `forward()`。A 的 `dismissed` 狀態回呼把 A 移出佇列並為 B 啟動
`forward()`。A 因此從未推進到可見的動畫值。

### 實驗發現

**已驗證的事實**（五項）：

| # | 事實 | 依據 |
|---|------|------|
| F1 | 同一同步區塊內的第二次 `show` 使第一則**一幀都不被渲染** | A 組逐幀命中次數 0 |
| F2 | 已顯示中的提示被後續 `show` 立即截斷，不等自身停留時間 | B 組 `FIRST=1` → `FIRST=0` |
| F3 | `closed{reason=hide}` 是截斷的唯一判別式；未被截斷者為 `timeout`／`action` | C 組對照 + 複驗二的呼叫點唯一性實查 |
| F4 | **A 與 B 的日誌完全同形**——「一幀未顯示」與「顯示 1 秒後被截斷」在日誌上不可區分 | A/B events 逐字相同 |
| F5 | `withAction` 被截斷時，動作按鈕隨之消失且從未被呼叫；該則訊息的**唯一操作入口就此消滅** | D 組 `動作標籤存在=1 → 0`、`actionCalled=0` |

**F5 是本票最重要的一項**。被截斷的若是 plain，使用者損失的是一則可從其他管道
重建的資訊（狀態仍在畫面上）；被截斷的若是 withAction，損失的是**該功能在 0.1
的唯一入口**——`viewGapsAction`（`denied` fallback 下唯一告知掃描完成的通道，

（找不到檔案後重新掃描的唯一入口）。這使「截斷是否可接受」不再是頻率問題，
而是後果分級問題：**低頻不足以使 F5 可接受，因為單次發生即造成使用者永遠不知道
掃描已完成**。

| 假設 | 為何未驗證 | 取得條件 |
