#### 二、失效形態是「替換截斷」，不是「視覺重疊」

`AppSnackBar.show` 在 `messenger.showSnackBar(...)` 之前**無條件**呼叫 `messenger.hideCurrentSnackBar()`（`lib/components/app_snack_bar.dart`，元件內註解標為「新的 SnackBar 取代 → dismissed（SPEC-004 §4.26 狀態矩陣退出路徑）」）。加上 `ScaffoldMessenger` 本身一次只呈現一則、其餘排隊，**兩則提示在版面上同時可見在本專案的結構下不會發生**。

實際的失效是前一則被提前關閉，使用者可能一個字都沒讀到。更尖銳的是 `hideCurrentSnackBar()` 作用於佇列最前端的項目：若第二次 `show` 發生在第一則被呈現的 frame 之前，該則會**一 frame 都未顯示就消失**，且目前全程無痕跡。

這一項對第三個子問題有直接後果：它正是票面所稱「程式主動決定不告知使用者」的實例，而且是**可由原始碼判定**的，不需要執行 App。

#### 三、共時可達性（可達性事實，非推測）

兩個觸發源彼此獨立，可落在同一時窗：

- 使用者操作驅動：`_openItem`（點選破洞項）

#### 複驗三：失效形態確認為替換截斷，且規格已預先允許它

前置實查稱「兩則同時可見在本專案結構下不會發生」——複驗成立，且再加一層：
`AppSnackBar.show` 的無條件 `hideCurrentSnackBar()` 使 `ScaffoldMessenger` 內建的
**佇列語意實質失效**（佇列仍在，但前一則永遠等不到自己的停留時間）。

更重要的是，**這個行為是規格明文允許的**，不是實作偏離：

- SPEC-004 §4.26 狀態矩陣 shown 列退出路徑：「新的 SnackBar 取代 → dismissed」
- SPEC-004 §4.26 回饋契約〈等待與結果〉列重複觸發防護：「冪等——**新的 `show` 取代前一則**，重複觸發為合法操作」

規格寫下「取代」時，回答的是「重複觸發要不要排隊」（答：不排隊，冪等），
**沒有回答「被取代的那一則發生了什麼」**。本票要補的正是後者：當被取代者是

### PM 前置實查第二節的理由更正（結論不變，理由變了）

原文寫「視覺重疊不會發生，因為 `AppSnackBar.show` 先呼叫 `hideCurrentSnackBar()`」。**理由錯誤。** 實查 Flutter SDK（`$HOME/fvm/versions/3.47.1/packages/flutter/lib/src/material/scaffold.dart`）：

- `ScaffoldMessengerState` 持有 `Queue<ScaffoldFeatureController<SnackBar, SnackBarClosedReason>> _snackBars`；`showSnackBar` 走 `_snackBars.addLast(controller)`，只有 `_snackBars.first` 被呈現。
- **不重疊是 `ScaffoldMessenger` 本身的性質**，與是否先 hide 無關。

`hideCurrentSnackBar()` 決定的是取代 vs 排隊：

| 路徑 | 語意 | 後果 |
|------|------|------|
| `AppSnackBar.show` | 先 hide 再 show → 取代 | 前一則被截斷 |
| `lib/main.dart:219`（繞過元件的原生呼叫） | 直接 show → 排隊 | 這一則等前面播完 |

`hideCurrentSnackBar` 作用於 `_snackBars.first`，**不分是誰放進去的**——任何一次 `AppSnackBar.show` 都會截斷正在顯示的 `main.dart` 那則。**跨路徑干擾存在且不對稱**：元件路徑會殺掉原生路徑的訊息，反之不會。

**為何理由比結論重要**：若日後加入第二個覆蓋層或改用非 SnackBar 載體，「Material 佇列保證單一呈現」這個前提即不再成立；而「先 hide 所以安全」那個錯誤理由會讓人以為照樣先 hide 就沒事。

### `0.1.0-W3-165` 核心論證的前提補正

該票主張「元件內部加 log 涵蓋全部呼叫點含未來新增的，結構上不可能漏」。`main.dart:219` 不經過元件，因此零日誌。正確表述是「**在所有呼叫都經過元件的前提下**不可能漏」，而該前提本身需要被強制（例如禁用原生 API 直呼），否則它只是假設。該處的處置歸 `0.1.0-W3-177`，本票只列進盤點。

### 量測對象更正與外部驅動維度（2026-09-09，第三次轉入）

#### 一、量測對象由「同時幾則」改為「顯示窗口內是否有第二則抵達」

前文要求量測提示密度／同時最多幾則。**那不是正確的量測對象**——跨路徑干擾不需要兩個事件同時發生，只需要一則正在顯示時另一則抵達。窗口長度為 `Motion.snackBar` / `Motion.snackBarWithAction`。此判準比「同時發生」寬得多，命中機會也高得多。

#### 二、跨路徑干擾發生時兩側皆無紀錄

`lib/main.dart:219` 不經過元件層，`0.1.0-W3-165` 的四個事件對它全不適用；元件那則的 `closed(reason: hide)` 記的是**它自己被誰關掉，不是它關掉了誰**。因此「元件路徑截斷原生路徑」發生時兩邊日誌都無痕跡——**現有元件層日誌無法承接跨路徑干擾的可觀測性**，此為第三個子問題的直接材料。

#### 三、外部驅動維度，及其對本專案的適用邊界

`0.1.0-W3-184` 將事件來源由前台／背景二分改為三分（使用者觸發／我方自行發起／外部驅動）。外部驅動（websocket／伺服器輪詢）的特徵是到達時機不由我方決定，故「避免同時請求注意力」對其直接無效。

**但本專案目前沒有真正的外部驅動到達，此點經 PM 實查：**

| 引用 | 內容 |
|------|------|
| `SPEC-003:1073`（§3.6 節點詳情） | `notFound` → `state-nodeDetail-missing`，「此為對外部變更的第一手偵測點；不出現 SnackBar，狀態轉換即回饋」——但該偵測發生於**使用者點擊開啟原始檔時** |
| `SPEC-003:761` | 「目錄消失屬外部變更，**由下一次重新載入承接，本畫面不設偵測點**」 |

外部變更是**成因**，偵測時機仍是**我方或使用者觸發**。差別在下表第二列：

| | websocket／輪詢 | 本專案的外部變更 |
|---|---|---|
| 變更何時發生 | 不受控 | 不受控 |
| **我方何時得知** | **不受控（被推送）** | **受控（我方查詢時才知道）** |
| 「避免同時請求注意力」是否適用 | 否 | **是** |

**不得把本專案的外部變更當成外部驅動的實例分析**，否則會為尚不存在的到達形態設計處置。它歸「我方自行發起」——外部成因、我方觸發的偵測。真正的外部驅動要等推送型來源（檔案系統 watcher、伺服器推送）落地才出現，屆時 §3.6「不設偵測點」的裁定會先被推翻。結論若需涵蓋未來形態，須明寫「為尚未存在的來源預留」，不得寫成現況分析。

### 第一問：何時該用暫態提示元件

### 判準 T：四問依序，先命中先決定

輸入一律為**事件的性質**，不是呼叫點的身分。四個輸入都可由呼叫端在觸發當下讀到，
不需人工判斷。

| 序 | 問題 | 輸入（可機械取得） | 命中時的結論 |
|----|------|------------------|------------|
| T1 | 事件抵達時，**使用者當前可見的畫面**是否即觸發它的畫面，且視窗在前景？ | `AppLifecycleState == resumed` AND 可見頁 == 觸發頁 | **否 → 不用暫態提示**。改走升級通道（系統通知）或延後至可見；兩者皆不可行時落入第三問的日誌承接 |
| T2 | 事件是否在**使用者當前可見的畫面上**產生可見的狀態轉換？ | 是否有對應的 `state-*` 錨點變更，且該錨點在可見頁上 | **是 → 不用暫態提示**（狀態轉換本身即結果） |
| T3 | 訊息內容是否需要使用者保留、抄錄或逐項閱讀？ | 是否含路徑、明細、需比對的清單 | **是 → 不用 SnackBar**（自動消失使資訊喪失），改由畫面承載 |
| T4 | 是否附帶使用者必須執行才能取得結果的操作？ | 是否有非空的動作回呼 | **是 → `withAction`，且列不可截斷級**（見第二問）；**否 → `plain`，可截斷級** |

**T1 置於 T2 之前是刻意的。** 反過來會得出錯誤結論：掃描完成確實產生了
`state-gaps-scanning → state-gaps-found` 的狀態轉換（T2 為「是」），但若使用者不在
`nav-page-gaps`，那個轉換不在他的視線內——這正是 SPEC-003 §2.2〈系統層通知〉存在的

### 第二問：重疊遮蔽的處置與是否需要類型分化

### 現況：不是重疊，是替換截斷

實測（〈重現實驗結果〉F1／F2）確認失效形態為替換截斷，非視覺重疊。
`AppSnackBar.show` 的無條件 `hideCurrentSnackBar()` 使 `ScaffoldMessenger` 內建的
佇列語意實質失效：佇列仍在，但前一則永遠等不到自己的停留時間。
**此行為是 SPEC-004 §4.26 明文允許的**（狀態矩陣退出路徑「新的 SnackBar 取代」、
回饋契約重複觸發防護「冪等——新的 `show` 取代前一則」），規格回答的是「重複觸發要
不要排隊」，沒有回答「被取代的那一則發生了什麼」。

### 四個處置方向逐一評估

| 方向 | 做法 | 代價 | 判定 |
|------|------|------|------|
| 佇列排隊 | 移除無條件 `hideCurrentSnackBar`，讓原生佇列生效 | 最後一則可能延後 4–8 秒才出現，屆時已與觸發脈絡脫節，使用者不知道它在講哪一次操作；且直接與 SPEC-004 §4.26「冪等取代」條文衝突 | **部分採用**（僅用於不可截斷級被壓住時） |
| 優先級搶佔 | 依變體分級：`withAction` 不得被後續 `show` 靜默截斷；`plain` 可被任何後續截斷 | 元件從「無狀態靜態入口」變為持有分級策略，需在元件內加入判斷 | **採用** |
| 合併為單則 | 同時窗內多則合併為摘要 | 0.1 的六個訊息結局語意互不相干（外部開啟 vs 掃描完成 vs 資料夾不可用），無合理摘要形式；強行合併會產生語意不成立的句子 | **不採用** |
| 依類型分流至不同載體 | 新增 Banner／Toast 等元件承接不同類型 | 新元件。`0.1.0-W3-063` SR-2 已由 PM 裁決 0.1 不新增（維持選項 c），重評綁 `0.1.0-W3-062` | **待量測，且不在本票翻案** |

### 裁定（兩項，分別標明是否依賴頻率）

**裁定 A（可裁定，不依賴頻率）：`withAction` 不得被後續 `show` 靜默截斷。**

依據是實驗 F5 而非頻率：被截斷時動作按鈕隨之消失且從未被呼叫（`actionCalled=0`），
等同銷毀該則訊息的唯一操作入口。在 0.1 這兩個入口是——`viewGapsAction`
（`denied` fallback 下唯一告知掃描完成的通道，SPEC-003 §2.2 已定 0.1 不提供 Banner
與 NavItem 徽章）與 `rescanAction`（找不到檔案後重新掃描的唯一入口）。

**低頻不足以使此後果可接受**：單次發生即造成使用者永遠不知道掃描已完成，
而他不會知道自己錯過了什麼。這是後果分級問題，不是頻率問題——故本裁定不等量測。

具體規則（排隊或延後或拒絕新的 plain，三者的取捨）屬規格層，交 `0.1.0-W3-169`。
本票只定「不得靜默截斷」這條約束與其理由。

**裁定 B（依賴頻率，停在待量測）：是否需要分化提示元件，不由本票決定。**

若實測顯示爭用極少發生，裁定 A 的優先級規則即足夠，新增元件為過度設計。
本票**不由可達性推導頻率**（前置實查第四節的紀律照守）。已建 `0.1.0-W3-179`
承接量測，含判別式、三項指標、取樣要求與實機協調約束；依
`decision-trigger-binding` 規則 2，本延後的 trigger 為該 ticket ID 而非時間或事件。

**量測不需人眼觀察**：判別式 `closed{reason=hide}` 的唯一性已實查（見複驗二）。
但指標二（被截斷者是否為 `withAction`）與指標三（實際可見時長）需先補
`0.1.0-W3-176` 的 G1／G2 欄位，故 `0.1.0-W3-179` 標 `blockedBy 0.1.0-W3-176`。

### WRAP 決策框架（完整模式）

觸發判定：本票命中〈二元處置取捨〉——票面 `how` 已預先列出四個處置方向，屬「選項
由直覺產生、未經 W 擴增即封閉解空間」；且涉及規格層不可逆變更（裁定 A 會寫入 SPEC）。
故跑完整模式而非快速模式。

### 錨點確認

**核心目標**：本專案是文件因果鏈的視覺化工具（CLAUDE.md §1），提示元件是支撐設施
不是主線。**這個錨點對第二問有直接後果**：不宜為提示爭用新增元件，除非量測證實
既有載體確實承載不了。

### Step 0 資料充足度閘門

| 檢查 | 答案 |
|------|------|
| 決策所需資料是否齊備 | **部分**——「發生時會怎樣」齊備（F1–F5 實測），「多常發生」缺席 |
| 是否用假設替代資料 | 已隔離：裁定 A 不用頻率，裁定 B 明標待量測 |
| 假設錯誤的後果 | 裁定 A 若錯：規格條文需回退，尚未寫入實作，成本低。裁定 B 若強行推定：可能新增一個不需要的元件，或漏掉一個需要的 |

**閘門判定**：不足 + 中風險 → 拆為「可依現有資料裁定」與「須補資料」兩部分，
前者裁定、後者綁 ticket trigger。這正是第二問裁定 A／B 的分法。

### W — 擴增選項（爬梯子法）

票面給了四個方向。爬梯子後**多出兩個**，且其中一個來自本專案既有慣例：

| 層 | 搜尋範圍 | 找到 |
|----|---------|------|
| 0 身邊 | 本專案既有程式碼 | **選項 E**：把「待顯示的提示」提升為 provider 狀態，由頁面層消費後清空。此模式在本專案**已有兩個實例**——`ScanNotificationController._pendingDeniedNotification`（延後至 `resumed`）與 `pendingLocateGapItemProvider`（消費後清空）。截斷因此變成「延後」，且待處理狀態可被讀取 |
| 0 身邊 | 同上 | **選項 F**：不改行為，只補日誌（零行為變更，純觀測） |
| 1 同層 | 本專案其他模組 | SPEC-003 §2.2 系統層通知——升級至 App 外通道（已被 `0.1.0-W3-063` SR-2 裁決 0.1 不擴充） |
| 2 同領域 | Material | `ScaffoldMessenger` 原生佇列（即票面的「佇列排隊」，本專案主動以 `hideCurrentSnackBar` 停用之） |

**三類涵蓋檢查**：改造既有（佇列／優先級／選項 E）、零工具（選項 F）、新增工具
（分化元件）——三類皆有代表，通過。

**品質檢查**：

| 檢查 | 結果 |
|------|------|
| 選項消失測試（票面四個全移除還能怎麼做） | 還有 E 與 F → **原本四個確實不足**，W 階段有實質產出 |
| 假選項偵測 | 佇列／優先級／E 皆屬「調整顯示順序」，分化屬「換載體」，F 屬「不處置」——三個不同途徑，非季辛吉陷阱 |
| 框架測試（能否一句話概括） | 前五個可概括為「怎麼處理爭用」，**F 不可**——它拒絕了「必須處理」這個前提。F 的加入即是框架鬆綁 |

**選項 E 的評估**（W 新增，票面未列）：與專案既有慣例一致是其最大優點，但它把
「哪一則該先顯示」的決策從元件推到頁面層，而爭用的兩個觸發源分屬兩個不同的頁面層
物件（`_openItem` 在 `GapReportScreen`、`_showDeniedSnackbar` 在
`ScanNotificationController`），沒有共同的仲裁點——除非再新增一個。**列入
`0.1.0-W3-169` 的候選，不在本票排除**：它是否優於裁定 A 的元件內分級，取決於規格
要不要引入一個提示仲裁者，屬規格層決策。

### R — 現實檢驗

**基本率**：Material `SnackBar` 的預設語意是**佇列**，不是取代。本專案的無條件
`hideCurrentSnackBar()` 是主動偏離平台預設。偏離通常有理由，此處的理由是 SPEC-004
§4.26 的「冪等——新的 `show` 取代前一則」；但冪等成立於「**重複觸發同一操作**」，
而實際被套用到「不同事件的不同訊息」——這是**適用範圍的外推**，不是原條文的意思。
基本率因此不支持現行做法。

**反向驗證**（假設「截斷根本無害」）：

| 若截斷無害 | 反證 |
|-----------|------|
| 使用者總能從別處得知 | 對 `plain` 成立（狀態仍在畫面上）；對 `withAction` **不成立**——F5 實測動作按鈕消失且從未被呼叫，`viewGapsAction` 與 `rescanAction` 在 0.1 無替代入口 |
| 爭用罕見到可忽略 | 頻率未知，不可用於支持任一方向；但即使罕見，F5 的後果不隨頻率縮小 |

**反向驗證的產出是精確化，不是推翻**：「無害」只在 `plain` 上成立。這**正是**裁定 A
採「依變體分級」而非「一律排隊」的依據——若無此檢驗，容易過度反應為全面排隊，

### A — 拉開距離

**10/10/10**：

| 時距 | 後果 |
|------|------|

### 一、先接受範圍收窄

`0.1.0-W3-184` 的用戶更正：提示需求本身是重要性訊號，提示密度過高不是「提示太多」，
是**同時執行了太多重要的事**；在提示層做排隊、優先級或載體分化，是幫排程問題做
視覺化緩衝——症狀被吸收，成因原封不動，而且緩衝做得越好，成因越不可能被發現。

**這對前段裁定 A 有直接後果。** 裁定 A 須拆為兩層，兩層的去留不同：

| 層 | 內容 | 去留 |
|----|------|------|
| 約束層 | `withAction` 的動作入口不得被**無痕跡**銷毀（實驗 F5 的後果認定） | **留**——這是後果陳述，不是排程處置 |
| 機制層 | 以佇列／優先級搶佔／provider 仲裁**實現**該約束 | **撤回為待裁定**——屬提示層緩衝，其前提由 `0.1.0-W3-184` 裁定 |

**最低成本的滿足方式是留痕，不是重排。** 第三問已定的 C5 warning 日誌即滿足約束層，
且完全不觸及排程：程式仍然截斷，但截斷這件事不再無聲。若 `0.1.0-W3-184` 裁定同時
到達本就不該發生，重排機制連需求都不成立；若裁定確實會同時到達，機制選擇再由
`0.1.0-W3-169` 依該結論定。

**收窄不改變的部分**：判準 T（第一問）、六個訊息結局的對照、日誌缺口 G1–G3
（第三問）皆不依賴排程前提，不受影響。實驗 F1–F5 是對現行程式碼的觀測，亦不受影響。

### 二、四類提示的逐類約束（不先統一分類再套用）

四類的約束來源不同、承擔者不同，故逐類處理。**「不先統一分類再套用」的具體意思**：
若先把四類統一為「提示」再套判準 T，會把輸入阻擋類誤導向 SnackBar——而 SPEC-003
§2.12 已明訂該類的第三層是狀態轉換本身，第二層是 `LoadingState`，根本不經提示元件。

| 類 | 0.1 實例 | 約束來源（既有，非本票新訂） | 本票的處置 |
|----|---------|---------------------------|-----------|
| **內部失敗** | `externalOpenFailedMessage`、`chooseFolderUnavailableMessage`、`ScanNotifier.show` 失敗（`0.1.0-W3-113`，目前**無** fallback） | `ARCH-GPD-001`〈降級不解除回饋義務〉；SPEC-003 §2.2 外部開啟契約〈失敗可觀測〉列 | 判準 T 全程適用。**額外約束**：失敗類被爭用丟棄時不得無痕跡——此類是四類中唯一「使用者不主動採取行動就不會知道出錯」者，其餘三類的事實都還在畫面上 |
| **背景完成** | `scanCompleteSnackbarMessage` / `scanCompleteNoGapsSnackbarMessage` | SPEC-003 §2.2〈系統層通知〉（觸發條件、不重複發送、權限 gate 三路徑） | 判準 T1 已由既有條文保證（顯示時機明訂為前景且非 gaps 頁，或延後至 `resumed`）。**成因層歸 `0.1.0-W3-184`**——背景掃描在使用者注意力尚未就緒時完成，正是該票所指的實例 |
| **必須確認** | **0.1 無實例，亦無載體** | 無——SPEC-004 §6 明禁 `showDialog` / `AlertDialog` / `showModalBottomSheet` / `Drawer` | 見下節。**不在本票裁定** |
| **輸入阻擋** | Domain 載入、Ticket 載入、破洞掃描 | **SPEC-003 §2.12 既有政策**：三選一判準（不阻擋／禁用觸發來源／阻擋頁面內容）+「阻擋頁面內容者必須同時提供取消」（由 §2.5 C1／C4 承擔，驗收落在 FR-02） | **接上既有政策，不另起一套**。此類不經 SnackBar——阻擋由 `LoadingState` 取代頁面內容承載，判準 T 在 T1 之前即已分流 |

**第四類與判準 T 的關係須明寫**：判準 T 的輸入是「一則要不要顯示為暫態提示」，
而輸入阻擋類的問題是「等待期間怎麼保護使用者」，兩者不是同一個問題。§2.12 已完整
回答後者（含重複觸發防護的承擔者一律是服務、不變式 INV-FEEDBACK-001），本票不
複述亦不修改——`DOC-005` 跨文件原則失步：同一條約束在兩處各寫一份會各自演進。

### 三、必須確認的載體：0.1 無載體，新增即推翻既有裁定

用戶原話「有的提示訊息要擋住使用者的操作」指向此類。三項事實：

1. SPEC-004 §6 原生元件禁用對照表明列 `showDialog` / `AlertDialog` /
   `showModalBottomSheet` / `Drawer` 皆禁用，改用 `SwitcherOverlay`，並稱其為
   **「0.1 唯一覆蓋層」**，理由「§1 覆蓋表面對映無 dialog / sheet / drawer」。
2. `SwitcherOverlay` 是專案切換浮層，語意上不承載確認；挪用會使同一元件既是導覽
   入口又是確認載體。
3. 故新增「必須確認」載體**推翻既有規格裁定**，屬提案層級，不可由本票或實作票就地決定。

**且順序不可顛倒**：`0.1.0-W3-184` 若裁定「有重要性的動作不應同時大量執行、真正有
重要問題時應暫停背景行為」，需要擋住使用者的場合會大幅減少——那些場合多半正是
幾件重要的事同時發生的場合。**先建載體再問成因，會建出一個只為緩衝而存在的元件，
而成因原封不動**，這正是本節第一段所接受的那個錯誤形態。

**承接**：已建 `0.1.0-W3-185`（DOC P2，blockedBy `0.1.0-W3-184`），SR-5 resolved
processed。該票 acceptance 第 1 項明訂：若 184 的結論使需求消失，「0.1 不需要此類
載體」是合法且優先的結論，不是任務失敗。

兩種修法的差別是結構性的，不是工作量：

| 修法 | 涵蓋範圍 | 漏掉的可能性 |
