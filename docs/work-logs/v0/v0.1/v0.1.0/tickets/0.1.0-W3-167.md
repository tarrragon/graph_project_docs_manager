#### 一、呼叫點數量與票面敘述不符

| 計數方式 | 實查值 | 位置 |

| 訊息結局（同一呼叫點的分支各算一則） | 5 | 找不到檔案／已開啟／開啟失敗／掃描完成無破洞／掃描完成 N 個破洞 |

本票 `why` 與 acceptance 第 2 項寫「6 個呼叫點，分佈於三個檔案」。實查 `shell.dart` 只有第 93 行的註解提及 `AppSnackBar.show`，**無實際呼叫**。分析請以實查值為準，並在 Solution 記錄此差異與採用的計數口徑；不要為湊合票面數字而虛列。

#### 二、失效形態是「替換截斷」，不是「視覺重疊」

`AppSnackBar.show` 在 `messenger.showSnackBar(...)` 之前**無條件**呼叫 `messenger.hideCurrentSnackBar()`（`lib/components/app_snack_bar.dart`，元件內註解標為「新的 SnackBar 取代 → dismissed（SPEC-004 §4.26 狀態矩陣退出路徑）」）。加上 `ScaffoldMessenger` 本身一次只呈現一則、其餘排隊，**兩則提示在版面上同時可見在本專案的結構下不會發生**。

實際的失效是前一則被提前關閉，使用者可能一個字都沒讀到。更尖銳的是 `hideCurrentSnackBar()` 作用於佇列最前端的項目：若第二次 `show` 發生在第一則被呈現的 frame 之前，該則會**一 frame 都未顯示就消失**，且目前全程無痕跡。

這一項對第三個子問題有直接後果：它正是票面所稱「程式主動決定不告知使用者」的實例，而且是**可由原始碼判定**的，不需要執行 App。

#### 三、共時可達性（可達性事實，非推測）

兩個觸發源彼此獨立，可落在同一時窗：

- 使用者操作驅動：`_openItem`（點選破洞項）
- 背景掃描驅動：`_showDeniedSnackbar`，含 `_pendingDeniedNotification` 於 `resumed` 時的延後 flush

因此「兩則提示在同一顯示時窗內爭用」不是假設，是既有控制流即可達的狀態。**尚未取得的是頻率**，見下節。

#### 四、本票期間取不到的量測，與其邊界

acceptance 第 3 項要求以 `0.1.0-W3-165` 的元件層日誌實測。派發時 165 為 in_progress，且本 session 受並行約束**不得啟動 App**（`0.1.0-W3-078` 的通知授權狀態具一次性量測價值，實機由該票持有者在受控條件下進行）。

因此本票可取得與不可取得的分別是：

| 問題 | 可否在本票內判定 | 依據 |
|------|----------------|------|
| 爭用是否**可能**發生 | 可 | 上節可達性 + 元件的 `hideCurrentSnackBar` 語意 |
| 爭用**實際發生的頻率** | 否 | 需 165 落地後的執行期日誌，且需啟動 App |

「不要憑推測決定是否分化元件」的紀律照守：可達性判定是原始碼證據而非推測，**但頻率資料缺席這件事必須在 Solution 明寫**，不得以可達性推導出頻率結論。若分化與否的裁定確實取決於頻率，則該項應停在「待量測」並登記 spawn request，不得以推測補足。
