## Problem Analysis
### 問題根因

0.1 的整合測試斷言對象包含四類互動行為——PROP-004 §首個整合測試的契約 要求「應可捲動處能捲動、應可換頁處能換頁、應可拖拉處能拖拉」，SPEC-001 FR-02 要求「取消操作恆可用」。這四句話沒有可驗對象：

- 「應可捲動處」沒有外延。測試無從知道要斷言幾個地方、哪幾個地方
- 「取消恆可用」沒有時間界線。按下之後多久內要抵達什麼狀態、期間畫面呈現什麼，皆未定義
- SPEC-001 的退出路徑欄用的是自然語言（「返回」「導覽至其他畫面」），沒有對應到具體的觸發元素與可觀察結果

反應規格未定則斷言無可驗對象，元件庫亦不知要實作什麼互動行為。

### 影響範圍

| 對象 | 影響 |
|------|------|
| `0.1.0-W1-005` 元件庫 | 八類元件的互動行為無依據；載入態元件是否承擔取消契約未定 |
| 0.1 整合測試 | 三類互動的斷言無枚舉清單；FR-02 無時間基準 |
| 七張畫面票 | 各自的退出路徑無具名錨點，會長出七套不一致的返回行為 |
| `lib/app/router.dart` / `shell.dart` | 現行殼無來源記錄、無首次可見訊號，四個「回到來源」退出路徑無承接處 |

### 相關 Error Pattern

審查產出屬規格文件，與程式碼修改類 error-pattern 無直接對應。本票執行過程本身命中一項既有模式：`PC-167`（分析代理人 worktree 內無寫入能力，PM 須 transcribe）——本票執行者 `star-anise-system-designer` 的 tools 清單不含 Write 與 Bash，SPEC-003 全文經對話分七則轉送後由 PM 逐字落檔。該工具清單缺陷已建 `0.1.0-W1-029` 追蹤。

## Solution
### 分析結論

產出 `docs/spec/ui/SPEC-003-interaction-response.md`（840 行），涵蓋七畫面各自的四類行為，並將 SPEC-001 的自然語言退出路徑轉為可斷言的具名錨點。

四項核心契約：

| 契約 | 內容 | 解決的問題 |
|------|------|-----------|
| 全域互動盤點（§1） | 10 個捲動處、3 類換頁處、1 個拖拉處，明寫「清單之外沒有第四處」 | PROP-004 三個「處」原無外延，測試無從知道要斷言幾處 |
| 取消契約（§2.5） | C1–C11 十一條，三處載入態共用，附三處目標態對照與強制斷言方式 | FR-02「取消恆可用」原無時間界線與期間呈現定義 |
| 單槽來源記錄（§2.3） | `returnTo` 單槽 + 四條規則，非堆疊 | SPEC-001 四個「回到來源」退出路徑原無目標定義 |
| 逐狀態對照表（§4） | 29 列，每列的導航反應欄皆非空且皆指向具名錨點 | 退出路徑原為自然語言，無可驗對象 |

### 候選方案與取捨

**方案一：導航來源以堆疊記錄（未採）**

以完整 history stack 記錄跳轉序列，返回時 pop。優點是語意與瀏覽器一致、支援多層返回。缺點是六項導覽是平行關係而非層級關係——A→B→C→A 之後按返回應回哪裡沒有唯一答案；堆疊在平行導覽下會累積出使用者無法預測的深度，且測試難以斷言「應該回到哪」。

**方案二：單槽來源記錄（採用）**

只記錄「最近一次跳轉從哪來」。缺點是不支援多層返回。優點是語意單一、可斷言（`ref.read(returnToProvider)` 是一個值不是一個序列）、且與現行 `IndexedStack` 平行殼相容。連續 jump 的行為明確定義（A→B→C 時 `returnTo` 為 B）而非未定義。

已於 SPEC-003 §設計約束記錄重評條件：日後導入 deep link 或多視窗時此決策須重新評估，§2.3 的四條規則是重評起點。

**取消契約的歸屬：三畫面各自實作 vs 元件單一承擔（採後者）**

三處載入態的差異只有「目標態」與「進度型別」兩個參數，其餘 11 條行為完全相同。由 SPEC-002 的載入態元件單一承擔，三個畫面以參數差異化。分開實作會產生三套各自漂移的取消行為，而 FR-02 的驗收是對三處同時成立。
