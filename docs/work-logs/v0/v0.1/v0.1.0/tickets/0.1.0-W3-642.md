# Execution Log

## Task Summary

分析 acceptance 項的射程超出票的範圍邊界時執行者仍勾滿的重複模式，定出可偵測的判準

---

## Problem Analysis
### 問題根因

acceptance 項的射程跨層（元件層加畫面層）但票的範圍邊界只涵蓋一層時，執行者在自身範圍內做完後勾滿全部 acceptance——勾滿與真的達成在票面同形。根因不是欺瞞，而是 acceptance 撰寫時未將跨層射程拆到對應層的票。

### 影響範圍

本版 165 張已完成 IMP 票中，含跨層語意的 acceptance 項共 8 項（分佈於 8 張票）。

漂移項：2 項（W2-001 AC2、W1-074 AC3）。漂移率：2/8 = 25%。以票為單位：2/165 = 1.2%。
正確反例：1 項（W1-075 AC3，PM 收窄射程後正確收尾）。
正常項：5 項（W2-003 至 W2-007，畫面層票，退出路徑在自身範圍內）。

漂移只發生在元件層票承載了畫面層才能驗證的 acceptance。

### 相關 Error Pattern

無已知 error-pattern 直接對應。最接近的是 PC-055（AC 漂移偵測），但不涵蓋 AC 撰寫時射程超出票範圍邊界的形態。

範圍驗證方法：rg regex 法，六個跨層語意 pattern 掃描 165 張已完成 IMP 票的 acceptance 欄位。
已知盲區：跨層語意可能以其他措辭表達，但本版 AC 撰寫風格高度一致（均由同一 PM 撰寫），六個 pattern 覆蓋主要句型。

## Solution
### 判準候選評估

### 候選 A：NeedsContext 散文與 acceptance 勾選矛盾偵測（hook 側）

機制：掃描同票 NeedsContext 是否含「不可操作」「未做」「超出範圍」等否定語意，若有且對應 acceptance 項為 [x]，報 WARNING。

已知該紅的輸入驗證：W2-001——NeedsContext 含「第二條退出路徑不可操作」，AC2 為 [x]。該輸入確實命中。

評估：
- 優點：直接偵測矛盾，兩次漂移案例均可捕獲
- 缺點：散文語意匹配 false positive 高（NeedsContext 記載的缺口不一定與被勾的 AC 項對應），且 NeedsContext 的措辭無 schema 約束
- 裁定：**不採納**。散文匹配的精度不夠，false positive 會使偵測成為噪音而被忽略

### 候選 B：acceptance 項引用的檔案路徑或畫面名超出 where.files（hook 側）

機制：解析 acceptance 項中的 lib/ 路徑或 screen 名稱，比對 where.files，超出則報 WARNING。

已知該紅的輸入驗證：W1-074 AC3 提及「Domain 視圖」（screen 概念），where.files 只有 lib/components/blocked_state.dart。然而 AC3 的措辭是「Domain 視圖 state-domain-schema-unconsumable 的降級檢視退出路徑可實際操作走通」——未含具體 lib/ 路徑，只有語意概念名。

評估：
- 優點：可機械化
- 缺點：本版兩次漂移案例的 AC 均未含具體檔案路徑，只有語意概念名（「Domain 視圖」「退出路徑」），hook 無法可靠匹配概念名到 where.files
- 裁定：**不採納**。本版的 AC 撰寫風格不含具體路徑，該判準對真實母體鑑別力為零

### 候選 C：AC 撰寫規範——跨層項在撰寫時即拆分（PM 側）

機制：PM 撰寫 acceptance 時，若某項的驗證需要觸及 where.files 以外的檔案或 where.layer 以外的層，該項必須拆到對應層的票。元件層票的 AC 只斷言元件層可觀測的事實；若元件的效果須在畫面層才能驗證，AC 改為「畫面層接線的承接票已建立並掛雙向血緣」。

已知該紅的輸入驗證：W1-074 原 AC3「Domain 視圖的降級檢視退出路徑可實際操作走通」——在此規範下應改為「畫面層接線的承接票已建立並掛雙向血緣」（W1-075 AC3 實際採用的措辭）。W1-075 已實證此規範可行且正確收尾。

評估：
- 優點：源頭治理，從撰寫時即消除跨層射程；W1-075 已實證可行
- 缺點：依賴 PM 撰寫時的判斷，非機械強制
- 裁定：**採納為主要措施**

### 候選 D：acceptance-gate-hook 增加 where.files 覆蓋率 WARNING（hook 側輔助）

機制：finish 時掃描每個 [x] 的 acceptance 項，若該項提及的 testKey（action-*、state-*）不在 where.files 所列路徑的原始碼中出現，報 INFO（非阻擋）。

已知該紅的輸入驗證：W1-074 AC3 提及「state-domain-schema-unconsumable 的降級檢視退出路徑」——但 AC 文字中的 testKey 是語意描述而非精確的 testKey 字面值，匹配精度不可靠。

評估：
- 缺點同候選 B——AC 措辭無 schema 約束，testKey 提取不可靠
- 裁定：**不採納**。與候選 B 同因

### 落點裁定

**採納候選 C：AC 撰寫規範（PM 側源頭治理）**

規範內容：元件層票（where.layer = Presentation 但 where.files 限於 lib/components/）的 acceptance 項，若其驗證需觸及 lib/screens/ 或 lib/app/ 或其他層的檔案，該項須改寫為「畫面層接線的承接票已建立並掛雙向血緣」（或等價的元件層可觀測斷言）。

此規範可一般化：**任何 IMP 票的 acceptance 項，其驗證射程不得超出 where.files 的涵蓋範圍；若效果須在票範圍以外才能觀測，AC 改為「承接票已建立並掛雙向血緣」。**

未採納候選的理由摘要：
- 候選 A（NeedsContext 矛盾偵測）：散文語意匹配精度不夠，false positive 高
- 候選 B（AC 引用路徑超出 where.files）：本版 AC 不含具體路徑，鑑別力為零
- 候選 D（testKey 覆蓋率）：AC 措辭無 schema 約束，testKey 提取不可靠

### Spawn 落地確認

需要建立一張 DOC 票將此撰寫規範落地為 pm-rules 或 references 文件。
