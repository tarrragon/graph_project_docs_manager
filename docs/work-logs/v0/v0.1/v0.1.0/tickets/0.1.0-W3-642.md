## Problem Analysis
### 問題根因

acceptance 項的射程跨層（元件層加畫面層）但票的範圍邊界只涵蓋一層時，執行者在自身範圍內做完後勾滿全部 acceptance——勾滿與真的達成在票面同形。根因不是欺瞞，而是 acceptance 撰寫時未將跨層射程拆到對應層的票。

### 影響範圍

本版 146 張已完成 IMP 票（口徑：type=IMP 且 status=completed，不含 closed）中，含跨層語意的 acceptance 項共 8 項（分佈於 8 張票）。

漂移項：2 項（W2-001 AC2、W1-074 AC3）。漂移率：2/8 = 25%（以跨層 AC 項為分母），2/146 = 1.4%（以票為分母）。
正確反例：1 項（W1-075 AC3，PM 收窄射程後正確收尾）。
正常項：5 項（W2-003 至 W2-007，畫面層票，退出路徑在自身範圍內）。

漂移只發生在元件層票承載了畫面層才能驗證的 acceptance。

### 相關 Error Pattern

無已知 error-pattern 直接對應。最接近的是 PC-055（AC 漂移偵測），但不涵蓋 AC 撰寫時射程超出票範圍邊界的形態。

範圍驗證方法：rg regex 法，六個跨層語意 pattern 掃描 146 張已完成 IMP 票的 acceptance 欄位。
計數指令：遍歷 docs/work-logs/v0/v0.1/v0.1.0/tickets/*.md，以 frontmatter 正則 ^type: IMP$ 且 ^status: completed$ 篩選。
已知盲區：跨層語意可能以其他措辭表達，但本版 AC 撰寫風格高度一致（均由同一 PM 撰寫），六個 pattern 覆蓋主要句型。

## Solution
### 判準候選評估

### 候選 A：NeedsContext 散文與 acceptance 勾選矛盾偵測（hook 側）

機制：掃描同票 NeedsContext 是否含「不可操作」「未做」「超出範圍」等否定語意，若有且對應 acceptance 項為 [x]，報 WARNING。

已知該紅的輸入驗證：W2-001——NeedsContext 含「第二條退出路徑不可操作」，AC2 為 [x]。確實命中。

裁定：**不採納**。散文語意匹配精度不夠，NeedsContext 措辭無 schema 約束，false positive 會使偵測成為噪音而被忽略。

### 候選 B：acceptance 項引用的檔案路徑或語意超出 where.files（hook 側）

機制：解析 acceptance 項中的路徑或承接票引用，比對 where.files，超出則報 WARNING。

初評（C 生效前）：本版兩次漂移案例的 AC 均未含具體檔案路徑，只有語意概念名（「Domain 視圖」「退出路徑」），hook 無法可靠匹配。鑑別力為零。

重評（C 生效後）：**C 改變了 AC 的形狀**。C 要求跨層 AC 改寫為「承接票 <ticket-id> 已建立並掛雙向血緣」。這使 B 有了可機械判定的輸入——hook 可以 (1) 偵測 AC 項是否含承接票 pattern，(2) 驗證引用的 ticket ID 存在且 source_ticket 指向本票。

已知該紅的輸入驗證（C 生效後的形態）：若 W1-074 AC3 已依 C 改寫為「承接票 0.1.0-W2-011 已建立並掛雙向血緣」，B 可驗證 0.1.0-W2-011 存在且 source_ticket = 0.1.0-W1-074。若 AC 仍為原文「退出路徑可實際操作走通」（即 PM 忘了遵守 C），B 不會偵測到——但此時 B 的角色不是偵測漂移，而是驗證 C 的形狀合規。

裁定：**採納，作為 C 的強制層**。B 單獨無效（C 生效前 AC 無結構化形狀），但 C+B 組合形成「C 改形狀、B 偵測形狀」的雙層防護。

### 候選 C：AC 撰寫規範——跨層項在撰寫時即拆分（PM 側）

機制：PM 撰寫 acceptance 時，若某項的驗證需觸及 where.files 以外的檔案或 where.layer 以外的層，該項必須改寫為「承接票 <ticket-id> 已建立並掛雙向血緣」。

已知該紅的輸入驗證：W1-074 原 AC3 在此規範下應改寫為承接票形態（W1-075 AC3 實際採用的措辭）。W1-075 已實證此規範可行且正確收尾。

C 單獨落地的弱點：**沒有機制在 PM 寫出跨層 AC 的當下攔下它**。C 是一條撰寫規範，執行全靠 PM 自律。依 opinionated-default-design 第一條「預設行為 > 文件規範」，每一條要求使用者記得遵守的規範本身就是信號——工具的預設行為還有改善空間。C 單獨 = 信號本身，不是解法。

裁定：**採納，但必須與 B 組合**。C 定義正確的 AC 形狀，B 在 finish 時偵測形狀是否合規。

### 候選 D：acceptance-gate-hook 增加 where.files 覆蓋率 WARNING（hook 側輔助）

機制：finish 時掃描每個 [x] 的 acceptance 項，若提及的 testKey 不在 where.files 所列路徑的原始碼中出現，報 INFO。

裁定：**不採納**。AC 措辭無 schema 約束，testKey 提取不可靠；且 C+B 已覆蓋此需求。

### 落點裁定

**採納 C + B 組合（撰寫規範 + hook 偵測）**

| 層 | 內容 |
|---|---|
| C（PM 側規範） | acceptance 項的驗證射程不得超出 where.files；若效果須在票範圍以外才能觀測，AC 改寫為「承接票 <ticket-id> 已建立並掛雙向血緣」 |
| B（hook 側偵測） | acceptance-gate-hook 在 finish 時偵測含承接票 pattern 的 AC 項，驗證引用的 ticket ID 存在且 source_ticket/spawned_tickets 雙向血緣完整；AC 項含「退出路徑可實際操作走通」等跨層語意但 where.files 只列元件層路徑時，報 WARNING 提示 PM 檢查射程 |

C 單獨落地時無強制機制——PM 寫出跨層 AC 不會被攔下，全靠自律。C+B 的防護模型是：C 改變 AC 的形狀使其可機械判定，B 在 finish 時驗證形狀合規。PM 忘了遵守 C 時，B 不會直接偵測到（因為 AC 仍為自然語言，B 無法判定其射程），但 B 會驗證「含承接票 pattern 的 AC 引用是否有效」，使正確遵守 C 的票獲得額外保障。

未採納候選的理由摘要：
- 候選 A（NeedsContext 矛盾偵測）：散文語意匹配精度不夠，false positive 高
- 候選 D（testKey 覆蓋率）：AC 措辭無 schema 約束，testKey 提取不可靠；C+B 已覆蓋
