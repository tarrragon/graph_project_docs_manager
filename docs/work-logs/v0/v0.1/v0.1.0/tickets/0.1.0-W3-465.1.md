## 重現實驗結果
### 實驗方法

1. 出處重查：以 `git grep -F`（範圍 `.claude`）查同義字與同型表，關鍵字包括：「列索引」「{編號}」「有沒有」「對不對」「結構驗證」「非功能性需求測試對照表」「未被禁用」「前置條件類型」「將每個前置條件轉換」。
2. 逐詞推導：分別把草稿和建議改文放回節錄檔語境，對 4 題題幹（probes/q）重新推判定，再和答錯答案（probes/a r2／r3）的讀歪路徑比對，看改文能否擋下。
3. 判否反例：每則各構造一個依改文應判「否」的輸入，確認改文有鑑別力。

### 實驗執行

出處重查命中（非範例）：
- 20b：`doc-handoff.md` 種子包範本資料列 `| {編號} | {前置條件} | {操作} | {預期} | ... |`。「場景」欄的佔位符是 {編號}，也就是列索引的內容依據。同檔 `phase2/rules.md`〈GWT 格式〉寫「場景 {編號}：{業務行為描述}」，兩處對「場景」的內容寫法不一致。
- 36a：`cases/printer-test-coverage-depth-failure.md` 標題「坑 3：斷言只檢查「有沒有」，沒檢查「對不對」」，下一行寫「對應 Decision Question Q_new3（值驗證 vs 存在性驗證）」。`phase2-test-design.md` 有同名標題。`test-assertion-design/SKILL.md`〈確定性斷言的基礎形態〉列「結構驗證｜驗證欄位存在、型別正確、陣列長度」「功能正確性｜輸出值直接比對固定預期值」。W3-465 原查詢未命中這三處。
- 37b：`phase2/rules.md`〈產出（Layer 1）〉寫「Phase 2 完成後，必須產出：…非功能性需求測試對照表（Q10/Q_new4 的答案）」，未附「有空格才產出」的條件。
- 39a：同檔〈行為鏈推演執行步驟〉步驟 2「列出完整前置清單」、步驟 3「將每個前置條件轉換為可執行的測試斷言」；表中「類型」與「驗證方式」逐列一一對應。正面案例把「存在至少一筆記錄項目」「可點擊（未被禁用）」拆成兩條前置驗證，但這是範例，不能當出處。bdd-testing-methodology 的正確模式寫「「送出」按鈕存在且可互動」，合成一條，與上述拆法相反。

逐詞推導（答錯路徑是否被擋）：
- 20b 草稿：「只用來標示列序」與題幹「只用來標示這是第幾列」幾乎同字，會形成字面比對，無法證明讀者懂判準；「不承載 Given/When/Then/來源以外任何內容」會讓承載 Given 內容的欄也符合列索引定義，有歧義。
- 36a 草稿：例示「長度是否大於零」與題幹 `length` greaterThan(0) 同構，換題後照抄即可答對。
- 37b 草稿：可擋 r3，但理由句（「建表是逐項核對的手段，不是診斷動作」）沒有出處。
- 39a 草稿：寫「四類型不互斥，按鈕同時屬 UI 元素存在與操作可執行」。用這句推 39a(b)「驗證下載按鈕未被禁用屬哪一類」會得到「兩類皆可」，推不出唯一答案「操作可執行」；例示「按鈕」也與題幹同構。

### 實驗發現

- 已驗證：20b、36a、37b 的判準在既有條文有出處，只缺路由或改寫。39a 的「依驗證方式欄歸類」可從表結構推出，「類型不依斷言作用的元素決定」這半句屬新判準。
- 已驗證：四則草稿都有至少一項不宜直接落檔（同構例示、推不出唯一判定、理由無出處）。
