### 逐則評估

#### TDD-20b

- **出處**：`doc-handoff.md`〈TDD 輸入種子包格式〉範本資料列 `| {編號} | {前置條件} | {操作} | {預期} | ... |`。「場景」欄只填 {編號}，這就是它屬列索引的依據。現行括號句「場景為列索引，非欄位本身」只說了結論，沒有說依據。
- **建議改文**（`doc-handoff-uc-to-gwt-conversion.md`〈GWT 種子與行為單元的分工邊界〉，替換括號句）：「（依範本，場景欄只填 {編號}，因此是列索引，不是欄位；是否為列索引，看欄內填的是不是只有編號，不看欄名。只填編號的欄不計入四欄；填了編號以外內容的欄，不論欄名為何，都不是列索引）」
- **逐詞推導**：20b 的「序號」欄只填列序，符合「只填編號」，屬列索引；其餘四欄為 Given／When／Then／來源，判「符合」。r2 讀歪（「多了序號欄位」）被「不看欄名」一句擋下。r3 讀歪（「實際欄位仍為場景」）被「場景欄因此是列索引，不是欄位」擋下。
- **判否反例**：表頭仍是「| 場景 | Given | When | Then | 來源 |」，但場景欄填「匯出報表時略過停用帳號」這類業務描述。依改文，這欄填了編號以外內容，不是列索引，計入欄位，超出四欄，判「不符合」。這個反例的方向與兩題相反（欄名同為「場景」，結果卻不是列索引），不同構。
- **用戶偏好**：`phase2/rules.md`〈GWT 格式〉寫「場景 {編號}：{業務行為描述}」，允許場景附帶描述；種子包範本只填 {編號}。場景欄能否附帶業務描述由用戶裁決，裁決結果決定上述反例判「不符合」是否成立。若允許附帶描述，改文要改成「只填編號，或編號加場景名稱」，判準的範圍也隨之放寬。

#### TDD-36a

- **出處**：(1) `cases/printer-test-coverage-depth-failure.md` 標題「坑 3：斷言只檢查「有沒有」，沒檢查「對不對」」，並標明「對應 Decision Question Q_new3（值驗證 vs 存在性驗證）」；`phase2-test-design.md` 有同名標題。(2) `test-assertion-design/SKILL.md`〈確定性斷言的基礎形態〉：「結構驗證｜驗證欄位存在、型別正確、陣列長度」「功能正確性｜輸出值直接比對固定預期值」。
- **建議改文**（`phase2/rules.md` Q_new3〈行動路徑〉，接在「標記「值驗證」或「存在性驗證」。」之後）：「分類看斷言檢查的語意，不看 API 名稱：只檢查『有沒有』的屬存在性驗證，對應 `.claude/skills/test-assertion-design/SKILL.md`〈確定性斷言的基礎形態〉的『結構驗證』（驗證欄位存在、型別正確、陣列長度）；檢查『對不對』的屬值驗證，對應同表的『功能正確性』（輸出值直接比對固定預期值）。」
- **逐詞推導**：36a 的 `length` greaterThan(0) 只檢查有沒有內容，屬「陣列長度」一類的結構驗證，判存在性驗證。r2 因「字面是數值比較」歸為值驗證，被「不看 API 名稱」與「輸出值直接比對固定預期值」擋下，因為 0 不是預期值。36b 的 `isA<String>()` 屬「型別正確」，判存在性驗證，與題幹前提一致。
- **判否反例**：`expect(invoice.total, equals(1200))` 是輸出值直接比對固定預期值，屬功能正確性，判值驗證，不是存在性驗證。
- **同構風險**：改文引用出處原字「陣列長度」「型別正確」，這是判準字面，不是例示；但下一輪出 Q_new3 題若再用長度或型別斷言，讀者可能靠字面比對答對。建議出題改用出處未列名的形態（例如「集合非空」的其他寫法，或檔案存在檢查）。
- **用戶偏好**：(1) 範圍斷言（如 greaterThan(100)，非零門檻）與〈確定性斷言的基礎形態〉的「邏輯不變式」列，歸值驗證、存在性驗證，還是在二分之外另立一類。(2) 長度等於固定值（如長度等於 3）屬「陣列長度」（存在性），還是「比對固定預期值」（值）。改文對這兩類邊界沒有唯一判定，由用戶決定。

#### TDD-37b

- **出處**：`phase2/rules.md`〈產出（Layer 1）〉：「Phase 2 完成後，必須產出：…非功能性需求測試對照表（Q10/Q_new4 的答案）」，條件中沒有「有空格才產出」。
- **建議改文**（Q_new4〈行動路徑〉，接在「空格代表測試盲點。」之後）：「此表即〈產出（Layer 1）〉所列『非功能性需求測試對照表（Q10/Q_new4 的答案）』，組 2 觸發時必須產出，是否產出不看表中有無空格。」
- **逐詞推導**：37b 三條都已覆蓋，(a) 沒有空格；(b) 依「是否產出不看表中有無空格」，仍須建表。r3 以「無識別需求」反推不建表，被這句擋下。W3-465 草稿的理由句（「建表是逐項核對的手段…」）沒有出處，改用路由句取代。
- **判否反例**：Phase 1 規格只有 schema 版本遷移（欄位改名），沒有日誌、可觀測性或錯誤處理路徑需求。依改文，組 2 未觸發，不產出此表，判「否」。注意：這個反例與 TDD-35b 同樣走「組 2 未觸發」的判定軸，只是輸入不同。此判準唯一的「否」分支就是未觸發，無法避開這條軸；這個反例只用於本票驗證，不寫入條文。
- **用戶偏好**：〈產出（Layer 1）〉的清單本身沒寫觸發條件，組 2 則有觸發條件。組 2 未觸發時，是完全不產出此表，還是產出一份標註「不適用」的表，由用戶決定。

#### TDD-39a

- **出處**：表中「類型」與「驗證方式」逐列一一對應（表結構）；〈行為鏈推演執行步驟〉步驟 2「列出完整前置清單」、步驟 3「將每個前置條件轉換為可執行的測試斷言」。「類型不依斷言作用的元素決定」這半句找不到非範例出處，屬新判準（正面案例拆成兩條前置驗證只是範例支持）。
- **草稿問題**：草稿寫「四類型不互斥，同一元素可能同時符合多列」，把「元素」和「前置條件」混為一談。以此推 39a(b) 會得出「兩類皆可」，推不出唯一答案「操作可執行」。例示「按鈕同時屬兩類」也與題幹同構。
- **建議改文**（`phase2/rules.md`〈前置條件驗證強制規則〉表後）：「歸類時，拿該條前置條件要檢查的內容對照〈驗證方式〉欄，不看它作用在哪個元素上。同一元素的『存在』與『可操作』是兩條前置條件，依步驟 3 各自轉成一條斷言，分別歸入對應類型。」
- **逐詞推導**：39a(b)「驗證下載按鈕未被禁用」對照驗證方式欄「驗證按鈕未被禁用」，歸「操作可執行」。r3 把「存在且已啟用」合成一條、再依對象歸入 UI 元素存在，被「兩條前置條件」與「不看它作用在哪個元素上」擋下。39a(a) 仍依表前強制句作答，不受影響。
- **判否反例**：搜尋輸入框的前置條件 `expect(find.byType(SearchField), findsOneWidget)`，對照驗證方式屬「UI 元素存在」，不屬「操作可執行」，判「否」。反例用的是輸入框加存在性，與題幹的按鈕加禁用狀態不同構。
- **殘餘風險**：「資料已載入」的驗證方式「驗證清單長度或特定項目存在」與「UI 元素存在」的 findsOneWidget 可能重疊（清單中的特定項目本身也是 UI 元素），改文沒有消解這一點，已併入 0.1.0-W3-470 追蹤。
- **用戶偏好**：(1) 是否採「同一元素的存在與可操作是兩條前置條件」。bdd-testing-methodology 的正確模式寫「「送出」按鈕存在且可互動」，是合成一條，兩者方向相反，需用戶裁決以哪邊為準。(2) 表中類型名是否統一為同一分類軸（例如都改成狀態命名）。這屬較大的改動，本票不建議，列為選項。
