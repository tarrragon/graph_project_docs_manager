# Execution Log

## Task Summary

裁決 規則層是否承認盤點工作項表的項目編號為合法 trigger 與追蹤載體

---

## Problem Analysis
### 問題根因

`decision-trigger-binding` 規則 2 寫「合法 trigger 限 ticket ID」，`quality-baseline` 規則 5 寫「發現即建立 Ticket」。兩條都把追蹤載體的**身分**（是不是本框架 ticket）當判準。協作或接手他人專案時，被操作 repo 沒有本框架 ticket 系統，替代產物是外接資料夾內的盤點工作項表，其項目編號不是 ticket ID。

根因不是兩條規則寫錯，是**射程未寫明**。兩條規則成文時，「專案」與「裝有本框架 ticket 系統的專案」是同一件事，無須區分；協作情境把這兩者拆開後，條文字面延伸到了一個它沒有設想過的情境。

### 影響範圍

已驗證的事實：

- 受影響建票點 33 處，分布 10 個 skill 與 1 份 reference（framework issue #109 R1 實證，量測於 2026-09-16）。
- 規則 2 的立論基礎不是「必須是本框架 ticket」。`decision-trigger-binding-details.md` 規則 2.5 的 Why 明文寫：「規則 2 的實質關切是『無人執行』而非『無 ticket』。ticket 被指定為唯一合法 trigger，理由是它是專案內唯一能被 scheduler 推進的單位」。
- 規則 2.5 的兩軸四格表已承認一個非 ticket-ID 的追蹤錨點：「需跨 consumer 追蹤時另以 framework issue（`claude#NN`）為錨點」。故「限 ticket ID」在框架自身實作中已非絕對。
- 強制層 `ana_spawn_consistency_checker.py` 的 `_EXEMPTION_MARKERS` 為字面字串清單（含「無需建 ticket」），逐行扣抵一項 spawn 規劃。

仍未驗證的假設：

- 協作或接手情境的實際發生頻率沒有樣本（issue #109 自陳）。本裁決因此只處理合法性，不處理成本效益。

### 相關 Error Pattern

- PC-093（無 trigger 延後累積為死議題）：規則 2 的來源。本裁決不得削弱其可驗證邊界——這是防架空條件的設計約束來源。
- PC-GPD-006（自建目錄跨 consumer 攜帶外來識別符）：本裁決落為條文時，條文內不得寫入本專案 ticket ID；工作項編號格式若需舉例，須以 `rule8-exempt: illustration` 標記或改用佔位符。

### 實驗發現

已驗證的事實：

- **F1**：規則 2 的立論基礎是「可被推進的追蹤單位」，ticket 只是**本專案內**該性質的唯一實例。載體身分不是第一原則，是該原則在有 ticket 系統的專案內的唯一解。
- **F2**：框架已承認過一個非 ticket-ID 的追蹤錨點（framework issue 編號），理由是它具備穩定識別與可查狀態。本裁決若承認工作項編號，是把同一道理擴到第二種情境，不是開新原則。
- **F3**：強制層以字面字串逐行扣抵。在本框架 ANA 票的 Solution 內逐項寫「無需建 ticket：已落為工作項表 <編號>」即可扣抵，**不需修改任何 hook**。此為讀實作確認，非推測。

仍未驗證的假設：

- **A1**：工作項表在實際協作案中能否維持「唯一主檔」。零樣本，只能以規格與絆腳索防護，不能以實證支持。
- **A2**：規則條文落在自動載入層後，skill 執行者是否真的據以行動。`decision-trigger-binding-details.md` 規則 2.5 自陳的邊界「指名不等於會被執行」同樣適用於本裁決。

### 本案不落在規則 2.5 同一類豁免

規則 2.5 的判別問題是「此刻是否還有做不做 / 做 A 還是 B 未回答」。工作項表的一列是尚未執行、有前置項、待排序的待辦，決策未下完，落在該表的「決策未下完」列——該格既有處置是「框架檔案不是合法載體，改寫入專案 ticket；需跨 consumer 追蹤時另以 framework issue（`claude#NN`）為錨點」。故**不能套用規則 2.5 的豁免**，須另立射程條文。

但該格同時是本裁決最強的內部依據（實驗發現 F2）：框架已承認過一個非 ticket-ID 的追蹤錨點，判準是該錨點具備穩定識別與可查狀態，不是它叫什麼名字。本裁決把同一判準擴到第二種情境。

### 工作項表欄位與 ticket 欄位的語意比對

規則 2 的可驗證邊界之所以有效，是因為 ticket ID 背後有五項保證。逐項比對工作項表（欄位規格取自 issue #109「方案評估」區段）：

| # | ticket 提供的保證 | 工作項表對應欄位 | 對應程度 | 缺口 |
|---|------------------|----------------|---------|------|
| 1 | 唯一識別、不重用（`id`） | 項目編號 | 對應 | 唯一性僅及於該外接資料夾，無全域命名空間。跨案引用時須連同資料夾識別 |
| 2 | 終態可判定（`status`） | 狀態（待辦／進行中／完成／不做） | 對應 | 「不做」須在詳情寫理由，語意等同 `dismissed` 附理由 |
| 3 | 完成定義可勾選（`acceptance`） | 驗收條件（表內摘要 + 詳情全文） | 對應 | 無 |
| 4 | 依賴關係可查（`blockedBy`） | 前置項 + 順序層 | 部分對應 | `blockedBy` 有反向索引（`ticket track deps`），前置項是單向文字，查「誰擋著我」可以，查「我擋著誰」須全表掃描 |
| 5 | 可被推進（scheduler runqueue、派發機制） | 對帳紀錄 + 最後對帳日 + U2 對帳責任人 | **不對應** | 人工對帳非自動推進。此為唯一實質缺口，由閘門 G4 補 |
| — | 出處可溯（`source_ticket`） | 來源（盤點出處：維度、步驟） | 對應 | 無 |
| — | 分派與編排（`who`／`type`／`priority`／`parent_id`） | 同名可選欄 | 對應（可選） | 對方有自己慣例時省略，不影響前五項 |
| — | 框架內部編排（`tdd_phase`／`decision_tree_path`／`version`） | 一律省略 | 不適用 | 這些欄位服務本框架的流程，不服務追蹤可驗證性 |

**判定**：第 1–4、6 項對應，第 5 項不對應。規則 2 的實質關切正是第 5 項（實驗發現 F1：「實質關切是無人執行」），故承認結論的成立條件，就是把第 5 項補起來——這是閘門 G4 存在的理由，不是附加要求。

### 五道防架空閘門（G1–G5）

承認的是「符合這五道閘門的編號」，不是「任何自訂編號」。五道全部通過才承認；缺任一道，該編號等同無 trigger 延後，規則 2 與規則 5 原條文照常適用。

| 閘門 | 內容 | 判準性質 |
|------|------|---------|
| **G1 射程閘門** | 僅在**被操作 repo 無本框架 ticket 系統**時適用。判準是客觀事實（該 repo 有無 `docs/work-logs/` 票庫且 ticket CLI 可用），不是便利性宣稱。同一專案內 ticket 系統可用而改用工作項編號，視為違反規則 2 | 可執行查核 |
| **G2 載體閘門** | 編號必須來自符合欄位規格的工作項表主檔，該表須同時具備四個與可驗證性直接相關的必留欄位：項目編號、狀態、驗收條件、前置項（含順序層）。缺任一欄，該編號不是合法載體 | 查欄位，非判語意 |
| **G3 唯一主檔閘門** | 一個交付案只有一份工作項表主檔（U1、U3）。存在第二份追蹤主檔（含分析者端逐項對應的影子票）時，兩份的編號皆不合法 | 數主檔份數 |
| **G4 推進閘門** | 分析者端必須有**一張本框架 ticket** 作為該交付案的對帳載體，其 acceptance 記載對帳觸發條件與承擔者，工作項表為其產出。缺此票時，工作項編號退回不合法 | 查票是否存在 |
| **G5 收件方閘門** | 射程由**發現的收件方**決定，不由手邊有無 ticket 系統決定。本框架自身的發現（框架缺陷、本專案技術債）不適用射程切換，仍須建 ticket 或走 framework issue | 問收件方是誰 |

五道都是機械可查的（查事實、查欄位、查份數、查票、查收件方），沒有一道要求判斷「這個載體夠不夠等效」。這是刻意的設計約束：規則 2 的價值在判準機械化，若改寫成「合法 trigger 限 ticket ID 或等效追蹤載體」，守衛即退回逐句判斷，與 `decision-trigger-binding-details.md` 規則 2.5 拒絕「規則 8 增列語意型豁免」的理由同型。

### 由誰保證不漂移

須區分兩件被混談的事——**指涉穩定**與**狀態權威**：

| 保證 | 交付前 | 交付後 |
|------|-------|-------|
| 指涉穩定（編號不重用、不重編） | 分析者。工作項表是唯一主檔（G3） | 分析者。編號在全時段是穩定識別 |
| 狀態權威（哪一份說了算） | 工作項表 | **轉移至對方系統**。工作項表降為對照表，狀態由對帳回抄，並新增一列對帳紀錄 |

因此精確說法是：**工作項編號在全時段是合法的 trigger 識別，但狀態判定權威隨交付切換**。此點必須寫入條文——不寫則會出現「工作項表寫完成、對方系統還沒做」的雙主檔，而那正是 U3 排除影子票所要避免的形態。交付後首次對帳前未回填外部編號者，該列計為「未對應」，不得據以宣告終態。

### 規則 5 的三種終態對應

規則 5 的實質是「發現不得只停在敘事」，其三種落地終態在工作項表上逐一有對應：

| 規則 5 的落地形式 | 工作項表對應 |
|------------------|------------|
| 建票並記入 `spawned_tickets` / `children` | 工作項表新增一列，來源欄記出處 |
| spawn request resolve 為 `processed` 附 ticket ID | 新增一列並於交付後回填外部編號 |
| resolve 為 `dismissed` 附理由 | 狀態填「不做」，詳情寫理由 |
| 逐項標註「無需建 ticket：[理由]」 | 同上 |

**強制層缺口與零改動接法**：`acceptance-gate-hook` Step 2.5.2 只計 `spawned_tickets` + `children` + 已判定 spawn request，工作項表列不計數。實驗發現 F3 已確認 `ana_spawn_consistency_checker.py` 的 `_EXEMPTION_MARKERS` 以字面逐行扣抵，故在本框架 ANA 票的 Solution 內逐項寫「無需建 ticket：已落為工作項表 <編號>（主檔：<外接資料夾路徑>）」即可扣抵。**不需修改任何 hook**——這是本裁決的落地成本為零的關鍵。

### WRAP 完整分析

**W（Widen options）** — 四個候選，兩個採用：

| 方案 | 內容 | 判定 | 依據 |
|------|------|------|------|
