## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`ticket track` 對 `spawned_tickets` 只有 `add-spawned`，無對稱的移除子命令；
`acceptance` 欄位則 add/remove 兩者俱全，介面不對稱。實際後果已發生：
`0.1.0-W1-075` 的執行者誤把已存在且無關的既有票（source_ticket 指向他處）
寫入自己的 `spawned_tickets`。ticket md 受 hook 禁止直讀直編，該欄位一旦
寫錯即無合法更正路徑。

進一步追根因：`resolve-spawn-request --status processed --spawned-ticket`
與 `add-spawned` 皆接受任意既有 ticket ID 寫入 `spawned_tickets`，兩者都
不驗證該 ID 是否已宣稱歸屬另一張票（`source_ticket` 衝突）——這是本次
污染案例的實際源頭，不只是「缺移除子命令」。

### 影響範圍

  argparse 定義）

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修復方式

**Acceptance 1（介面比照 remove-acceptance）**：新增 `remove-spawned` 子
命令，介面比照 `add-spawned`（`nargs='+'`，可一次傳多個 ID，對齊 Unix
`rm a b c` 慣例，非按索引——索引語意對 `spawned_tickets` 不穩定，
`add-spawned` 允許任意順序追加，索引會隨其他寫入者的追加而漂移）。

行為：
- 已找到的 ID 正常移除並寫入；找不到的 ID 於 stderr 回報（非靜默）
- 全數找不到時 rc=1；至少一項成功移除時 rc=0（部分成功不整批拒絕）
- 移除成功時，若目標票的 `source_ticket` 恰回指本票，同步清除該反向
  欄位（`_clear_reverse_source_if_matches`），保持雙向血緣一致；
  target 不存在／版本無法解析／`source_ticket` 指向他處，一律視為
  「無需清除」不中斷主流程

**Acceptance 2（清除 W1-075 的錯誤血緣）**：以新命令執行
`ticket track remove-spawned 0.1.0-W1-075 0.1.0-W4-001`，已驗證：
- `ticket track full 0.1.0-W1-075` 的 `spawned_tickets` 僅剩
  `0.1.0-W1-078`、`0.1.0-W3-644`（本票，因 `source_ticket` 指向
  W1-075 而自動雙向關聯，非污染）
- `ticket track tree` / `deps` 視圖不再顯示 W1-075 與 W4-001 的衍生關係
- W4-001 自身 `source_ticket` 維持 `0.1.0-W3-045.1`（污染本為單向，
  未動它）

**Acceptance 3（裁定血緣一致性檢查）**：**裁定為「加，但僅 WARNING 不
硬擋」**。

裁定理由：
1. 根因確認發生在寫入端——`add-spawned` 與
   `resolve-spawn-request --status processed --spawned-ticket` 皆接受
   任意既有 ticket ID，不驗證其 `source_ticket` 是否已指向他處。這正
   是本次污染的實際源頭（remove-spawned 只是修復管道，不是防止管道）
2. 不採「硬擋」：`spawned_tickets` 存在「刻意關聯一張已有主的既有票」
   的合法情境（如 PM 事後補記一個獨立完成、未走 `--source-ticket`
   流程的既有票），硬擋會誤傷這類合法用法
3. 採「WARNING」：對齊 opinionated-default-design 原則——預設路徑應
   引導正確做法而非僅靠文件規範；寫入當下即時提示屬第一層防範，
   `remove-spawned` 屬第二層 fallback（寫錯後的更正路徑），兩者互補

落地：新增共用函式 `ticket_ops.check_reverse_source_conflict`，
`add-spawned` 與 `resolve-spawn-request`（processed 分支）皆於成功寫入
後、對每個新增的 spawned ID 呼叫；衝突時印 WARNING 到 stderr，不影響
rc 與寫入結果。

### 驗證方式

- 單元測試覆蓋 `execute_remove_spawned`（含反向欄位清理／不清理兩種
  情境）、`check_reverse_source_conflict`（4 種判定情境）、
  `add-spawned`／`resolve-spawn-request` 的 WARNING 整合（發出／不發出
  各一）
- 實際對 `0.1.0-W1-075` 執行 `remove-spawned` 並以 `full`／`tree`／
  `deps` 三個唯讀命令交叉驗證結果
- `ticket_system/tests/` 全量套件重跑確認無回歸（見 Test Results）

### 自檢結果

- [x] 無新增未使用 import（`test_remove_spawned.py` 移除未使用的

  （符合規則 4 可觀測性：找不到/版本無法解析時回傳 None/False 而非

### Phase 4 結論

**重構需要**：否。**技術債務**：無新增。**程式碼品質**：A。

- `execute_remove_spawned` 與 `execute_add_spawned` 結構高度對稱（符合
  既有 codebase 慣例，未見額外抽 helper 的必要——兩者僅有「add vs
  remove + not_found 回報」的差異，抽共用 helper 的複雜度增量大於重複
  的兩個 10 行迴圈本身）
- `check_reverse_source_conflict` 抽為 `ticket_ops.py` 共用函式（而非
  各自 inline），符合 DRY——`add-spawned` 與 `resolve-spawn-request` 兩
  呼叫點共用同一判定邏輯
- 認知負擔：`execute_remove_spawned` 主體約 25 行（含 file_lock 區塊），
  巢狀深度 2，符合 cognitive-load 規則的可接受範圍
