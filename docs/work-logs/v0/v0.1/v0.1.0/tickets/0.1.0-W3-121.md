### 1. 三項裁決

#### 裁決 A：`chooseFolder()` 回傳型別 —— 新增獨立結果型別，不擴充 `WorkspaceState`

**裁決**：新增 `sealed class ChooseFolderResult`（4 個 variant），`WorkspaceState` 維持現狀不動。

```dart
/// `chooseFolder()` 的結局。與 `WorkspaceState` 正交：
/// `WorkspaceState` 描述「資料夾現在能不能用」，本型別描述「這次選取這個動作的結局」。
sealed class ChooseFolderResult {
  const ChooseFolderResult();
}

/// 使用者關閉面板未選取。對應現行 `null` 回傳。
class ChooseFolderCancelled extends ChooseFolderResult {
  const ChooseFolderCancelled();
}

/// 選取面板本身開不起來（MissingPluginException、PlatformException）。
/// 現行行為是裸傳播例外，呼叫端拿到未分類例外。
class ChooseFolderUnavailable extends ChooseFolderResult {
  const ChooseFolderUnavailable(this.reason);
  final String reason;
}

/// 已選定且已持久化：下次啟動 `restore()` 讀得回來。
class ChooseFolderSelected extends ChooseFolderResult {
  const ChooseFolderSelected(this.state);
  final WorkspaceState state;
}

/// 已選定但未能記住：本次可用，下次啟動會回到 `WorkspaceUnset`，使用者需重選。
class ChooseFolderNotRemembered extends ChooseFolderResult {
  const ChooseFolderNotRemembered({required this.state, required this.reason});
  final WorkspaceState state;
  final String reason;
}
```

**理由（為何不擴充 `WorkspaceState`）**：

1. **兩者是正交軸，合併會產生笛卡兒積**。「資料夾可用性」（Unset / Ready / Unavailable）與「是否已持久化」互相獨立——使用者可能選到一個路徑，寫入失敗（未記住），而該資料夾同時是 `Ready` 或 `Unavailable`。若把「未記住」做成第四個 `WorkspaceState` variant，這兩軸就被壓成一維，必然丟失其中一軸的資訊。
2. **`restore()` 永遠不會產生「未記住」**。該語意只存在於寫入路徑。把它塞進 `WorkspaceState` 會讓 `restore()` 的回傳型別出現一個永不發生的分支，`_WorkspaceBanner` 的 exhaustive switch 被迫處理死分支。
3. **保護 W1-014 的型別空間**。`WorkspaceState` 是 UI 直接消費的展示狀態；把持久化機制的失敗語意塞進去，等於讓 SharedPreferences 的實作細節洩漏到 UI 型別，違反「Ports 不洩漏技術細節」。
4. **`ChooseFolderNotRemembered` 攜帶 `state` 而非取代它**：呼叫端仍然拿得到可用的 `WorkspaceState`，本次工作階段不被降級；只是額外知道「這個選擇沒被記住」。這正是「不互相抵扣」的落地——寫入失敗必須同時有日誌（診斷投影）與呼叫端可消費的回傳（程式決策投影），兩者分別存在。

**呼叫端義務（不可只記 log）**：`main.dart` 的 `_chooseFolder()` 收到 `ChooseFolderNotRemembered` 時，必須對使用者顯示「已選定，但下次啟動需重新選擇」的提示（SnackBar 或 banner 附註）。這是 UI 層的「日誌不抵扣使用者回饋」（ARCH-GPD-001）投影，Phase 3b 需新增對應 l10n key（zh-TW 樣板 + en）。

#### 裁決 B：`restore()` 的「讀取失敗」vs「從未設定過」—— 需要區分，且大部分情況可區分

**裁決**：需要區分。兩者在 SharedPreferences 上「同為 null」的前提並不成立——真正同為 null，只發生在 `getInstance()` 成功之後。

| 情境 | 可觀測差異 | 回傳 |
|------|-----------|------|
| 從未設定過 | `getInstance()` 成功，`getString()` 回 null | `WorkspaceUnset()` |
| 儲存層不可用（平台通道失效、plist 無法載入） | `getInstance()` 拋例外 | `WorkspaceUnavailable(lastKnownPath: null, reason: '無法讀取已儲存的工作資料夾設定')` |
| 殘餘不可區分：`getInstance()` 成功但 plist 內容毀損被平台當空值載入 | 無 | `WorkspaceUnset()`（見下方預設行為） |

**理由**：`SharedPreferences.getString()` 是純記憶體查表（`getInstance()` 已把整份 plist 載入快取），它本身沒有 I/O 失敗路徑；真正的讀取失敗集中在 `getInstance()`，而那是一個會拋例外的 async 呼叫，語意上與 null 完全可分。現行程式碼把 `getInstance()` 的例外裸傳播，才使兩者在呼叫端看起來同形。加上 try/catch 後即分離，**不需要新增型別**：`WorkspaceUnavailable` 的 `lastKnownPath` 本就是 `String?`，`null` 表示「知道有問題但不知道是哪個資料夾」，恰好承載此語意。

**殘餘不可區分情況的預設行為與風險**：

- **預設行為**：視為 `WorkspaceUnset`，App 正常啟動，使用者被要求重選。**不阻擋 App**——與 main.dart:195 既有註解的決策一致（還原失敗不阻擋使用）。
- **風險**：使用者曾設定過資料夾，卻看到「請選擇資料夾」，會誤以為設定遺失且無從得知原因。這是靜默失效，正是 W1-014 why 所指的失效形態。
- **緩解一（本票內）**：`restore()` 的結果時刻無論走哪個分支都留 log，事後從日誌可判讀是「讀到 null」還是「例外」。
- **緩解二（跨 W1-014）**：W1-014 引入 schema 版號 key 後，可用交叉判據收窄——**版號 key 存在但 path key 不存在**，代表這個安裝曾經寫過設定，屬異常，應判為 `WorkspaceUnavailable` 而非 `WorkspaceUnset`。此判據要求 W1-014 在「首次寫入 path 的同一次操作」內寫入版號 key（見第 4 節相容性）。

#### 裁決 C：受理時刻的適用性 —— 對 SharedPreferences 適用，對 file_selector 不適用

本票 how 段的預設是「受理時刻對 SharedPreferences 與 file_selector 無對應概念」。逐一驗證後，**SharedPreferences 部分推翻該預設**，理由如下（差異已回報 PM，見第 6 節）。

| 外部系統 | 受理時刻是否適用 | 理由 |
|---------|----------------|------|
| SharedPreferences | **適用**，載體為 `getInstance()` 成功回傳 | 方法論定義受理為「連線建立、檔案控制碼取得、請求被接收」。`getInstance()` 正是「取得儲存管道」的動作：它成功回傳代表底層 plist 已載入、後續 `setString`/`getString` 有對象可操作。相對於 `setString` 這個真正的寫入請求，`getInstance()` 完成即為「管道已建立、尚未知寫入結局」，三時刻齊備。故三時刻各自記錄，不合併 |
| file_selector `getDirectoryPath()` | **不適用**（缺載體，非略過） | API 只回傳單一 `Future<String?>`，該 Future 在使用者關閉面板時才 complete。面板「已開啟」這個受理事實沒有任何回傳值、callback 或狀態可供觀測。App 端無法從中取得受理訊號，故此時刻在 App 端不可觀測 |

**file_selector 受理缺失的後果與歸屬**：無法區分「面板開啟中、使用者思考」與「面板根本沒開起來、Future 永遠不 complete」。此為 App 端邏輯軌無法覆蓋的缺口，屬平台端事實軌，由 `0.1.0-W3-088` 的實機驗證承接，本票不擴張範圍。

**`getString()` 的受理時刻**：`getInstance()` 之後 `getString()` 是純記憶體查表，受理與結果同一瞬間，不另設事件（否則產生無資訊量的重複日誌）。

### 2. 三個呼叫點的三時刻落點與承擔者

共同約定：所有日誌走 `developer.log(..., name: 'WorkspaceRepository')`；失敗分支 `level: 900`，其餘不指定 level（沿用檔案既有寫法，符合 observability-rules 規則 2）。日誌字面加 `// i18n-exempt: 開發者 debug log` 註解，與 workspace_repository.dart:82 一致。
