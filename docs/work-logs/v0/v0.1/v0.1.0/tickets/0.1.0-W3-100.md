## Problem Analysis
### 問題根因

**回饋契約是新確立的測試義務，測試側無承載位置、替身無對應角色、斷言形態未設計。**

1. `test-object-catalogue.md` 的六個來源類別中，「元件契約」類指向 SPEC-004 的「測試點」子節，內容為渲染正確性。回饋契約是同一元件條目下的另一子節，但在測試對象目錄中沒有對應的測試對象行——欄位表多了一欄，測試側沒有登記位置。
2. `test/` 目錄唯一的服務替身 `FakeScanNotifier` 只模擬「服務可用且回傳假資料」，不拋例外、不逾時、不永不回應。其餘元件測試使用 `ProviderScope.overrides` 狀態注入，完全不經過服務層。
3. `pumpContract` 已建立假時鐘推進慣例，但回饋契約還需要「服務尚未回應時回饋已存在」的狀態順序斷言。

## Solution
### 三題分析

### 題一：回饋契約在測試對象目錄中的位置

**結論：既有「元件契約」來源類別下的新測試對象行，不新增來源類別。**

#### 論證

判準是「與既有類別的斷言來源是否同源」。

**現行「元件契約」類別的結構**：
- 來源規格：SPEC-004 逐元件條目
- 斷言來源：元件契約欄位表→「測試點（widget test）」子節
- 測的維度：渲染正確性（全變體全狀態渲染不溢位、最長文案截斷）

**回饋契約測試對象的結構**：
- 來源規格：SPEC-004 逐元件條目（同一文件、同一元件條目下的不同子節）
- 斷言來源：元件契約欄位表→「回饋契約」子節
- 測的維度：回饋正確性（按下確認可見、等待指示獨立於服務、失敗路徑有表現）

兩者的斷言來源屬同一元件條目下的不同子節。類比：「變體」與「狀態矩陣」也是同一元件條目下的不同子節，但同屬「元件契約」類別。**元件契約作為來源類別的邊界是 SPEC-004 的元件條目層級，不是子節層級**。

不新增來源類別的理由：
1. test-object-catalogue 的來源類別以「規格權威的型別」劃分（畫面狀態規格、使用案例文件、互動行為規格、元件庫規格、設計 token 規格、技術決策記錄）。回饋契約的權威仍是元件庫規格（SPEC-004），與渲染測試同型別。
2. 新增類別會讓同一元件的測試對象散落在兩個類別（渲染在「元件契約」、回饋在「回饋契約」），讀者須跨類別才能看到一個元件的全部測試義務——破壞目錄的查找效率。
3. 契約欄位表八個欄位無需新增欄位。新增的是**行**：每個可互動元件的每個需測試的回饋事件成為一行，`來源規格條目` 格式為 `SPEC-004 §4.N 回饋契約 {事件名}`，`來源類別` 填「元件契約」。

**落地方式**：`test-object-catalogue.md` 的來源類別表「元件契約」列補一句：「含回饋契約（六類事件的通道/門檻/token/狀態邊正確性）」。不改表結構，只補說明。

**條件式相依**：本結論依賴 W3-098 定案的回饋契約四段格式（通道/門檻/token/狀態邊）。若後續 W3-101 改變格式結構（如加欄或分表），測試對象行的 `斷言來源` 格式需同步調整，但「屬元件契約類別、不新增來源類別」的結論不受影響——因為這取決於規格權威型別（恆為 SPEC-004），不取決於欄位格式。

### 題二：替身的角色集合

**結論：定義五個角色，為既有「stub 盲區與語意級假後端」形態的元件級特化延伸。**

#### 角色集合

| 角色 | 行為定義 | 命名慣例 | 對應的回饋契約驗證目標 |
|------|---------|---------|---------------------|
| available | 方法以 `async` 直接回傳預設值 | `Fake{Service}()` 或 `Fake{Service}.available()` | 成功路徑回饋齊全（既有測試已覆蓋） |
| throws | 方法拋出指定例外（`PlatformException` / `MissingPluginException` / 自訂） | `Fake{Service}.throws(exception)` | 例外被降級後，降級目標狀態有可見表現 |
| timeout | 方法以 `Future.delayed(duration)` 延遲回應，或以永不完成的 `Completer` + 外部 timeout 機制觸發 | `Fake{Service}.timeout(duration)` | 逾時路徑觸發的回饋正確（等待指示持續直到逾時判定） |
| neverResponds | 方法回傳永不完成的 `Completer<T>.future`；呼叫端無 timeout 時即永遠不回應 | `Fake{Service}.neverResponds()` | 服務未回應時，互動回饋已存在（按下確認、等待指示皆獨立於服務），驗證 ARCH-GPD-001 掛載點條款 |
| returnsFailure | 方法回傳業務層級失敗結果（非例外；如枚舉 `denied` / `error` 狀態值） | `Fake{Service}.returnsFailure(result)` 或以建構子參數控制回傳值（與既有 `FakeScanNotifier(authorization: denied)` 同形） | 失敗結果路徑的回饋正確（與 throws 不同，此為非例外的失敗） |

#### 判準

**何時需要哪個角色**：取決於元件的回饋契約「等待與結果」列的四段（成功/失敗/逾時/服務不可用）。

| 回饋契約段 | 需要的角色 | 斷言目標 |
|-----------|-----------|---------|
| 成功 | available | 成功回饋出現 |
| 失敗 | returnsFailure | 失敗回饋出現 |
| 逾時 | timeout | 逾時回饋出現；等待指示在逾時判定前持續顯示 |
| 服務不可用 | throws + neverResponds | throws：降級狀態有表現；neverResponds：按下確認與等待指示獨立於服務回應 |

**五角色中 `neverResponds` 的特殊地位**：它是 ARCH-GPD-001 判準問句的機械化實現——「把服務整個拔掉，使用者按下去還看得到反應嗎？」。在測試中表現為：注入 `neverResponds` 替身 → 觸發互動 → `tester.pump()` 一幀 → 斷言按下確認的 pressed 視覺與等待指示皆存在。服務永不回應等同「拔掉」，而回饋仍存在等同判準問句答「是」。

#### 命名慣例

沿用既有 `Fake{Service}` 前綴（與 `FakeScanNotifier` 一致），以具名建構子區分角色：

```dart
// 既有形態（available，預設）
final fake = FakeScanNotifier();

// 新增角色
final fake = FakeScanNotifier.throws(MissingPluginException('test'));
final fake = FakeScanNotifier.timeout(Duration(seconds: 5));
final fake = FakeScanNotifier.neverResponds();
final fake = FakeScanNotifier.returnsFailure(NotificationAuthorization.denied);
```

角色由建構子選定，不在方法呼叫時動態切換——簡化生命週期管理，且每個測試案例只需驗證一個角色下的行為。

#### 與「stub 盲區與語意級假後端」的關係

**是該形態的元件級特化延伸，不是另一件事。**

`layered-test-strategy.md` 的「stub 盲區」分析指出：stub 回放的是我們的假設，假設與斷言出自同一人之手，測試必然綠。補位是「語意級假後端」——有狀態、跑完整互動鏈。

本票的五角色替身與該分析同根但尺度不同：

| 維度 | 語意級假後端 | 五角色替身 |
|------|------------|-----------|
| 尺度 | 整合測試層（多元件跨完整互動鏈） | 元件測試層（單一元件的回饋行為） |
| 覆蓋 | 外部服務行為假設是否正確 | 服務可用性各種狀態下回饋是否存在 |
| 驗證對象 | 互動鏈的端到端正確性 | 元件回饋契約的獨立於服務性 |
| 替身複雜度 | 有狀態、持有狀態機 | 無狀態、建構時決定角色 |

共同的根因洞察：**只扮演「可用」的替身，結構上無法驗證「不可用」時的行為。** 語意級假後端解決整合層的此問題（以有狀態假後端取代回放級 stub），五角色替身解決元件層的此問題（以角色化建構子取代只有「可用」的 fake）。

兩者不互相取代：元件層的五角色替身確保每個元件的回饋契約被逐一驗證；整合層的語意級假後端確保多元件串接時回饋鏈端到端正確。五角色替身是語意級假後端在元件測試尺度的投影。

**落地方式**：`layered-test-strategy.md`「分層之外的補位形態」節的「stub 盲區與語意級假後端」段後，補一段說明元件層的角色化替身形態，引用本票結論。

### 題三：時間門檻的斷言形態

**結論：既有 `pumpContract` 假時鐘慣例足以覆蓋時間門檻，不違反 D1；補充一個「未完成 Future + pump」形態覆蓋掛載點判準。**

#### 確認 pumpContract 覆蓋回饋門檻

`pump_harness.dart:116` 的 `pumpContract` 等價於 `tester.pump(contract)`——推進 Flutter 測試框架的假時鐘 `contract` 這麼久，然後斷言期望狀態。

回饋契約的時間門檻（如「pressed 視覺 `Motion.feedback`（100ms）內出現」）在此形態下的斷言：

```dart
await tester.tap(find.byKey(buttonKey));
await pumpContract(tester, Motion.feedback); // 推進假時鐘 100ms
expect(find.byType(PressedVisual), findsOneWidget);
```

**為何不違反 D1**：`test-assertion-design-rules` 規則 D1 禁止的是「`Stopwatch.elapsed*` + `lessThan(N)` 作 pass-fail」——量測真實耗時然後斷言耗時小於門檻。`pumpContract` 做的是推進假時鐘然後斷言狀態存在，不量測真實耗時。兩者的區別：

| 維度 | Stopwatch 斷言（D1 禁止） | pumpContract 斷言（合規） |
|------|-------------------------|-------------------------|
| 時鐘 | 真實系統時鐘 | Flutter 測試框架假時鐘 |
| 斷言對象 | 真實耗時毫秒數 | 推進後的 widget 狀態 |
| 環境依賴 | 機器負載影響 | 假時鐘確定性推進，零環境依賴 |
| 紅燈含義 | 「機器太慢」（可能非程式缺陷） | 「時間 token 接線錯誤或動畫未觸發」（程式缺陷） |

`pumpContract` 的斷言紅燈含義是「元件未在 `Motion.feedback` 的假時鐘推進後達到預期狀態」——這是對 token 接線的正確性斷言，不是效能斷言。結論：**完全合規，不需修改 `test-assertion-design-rules.md`。**

#### 補充形態：未完成 Future + pump（掛載點判準的機械化）

`pumpContract` 覆蓋「在門檻時間後狀態正確」；但 ARCH-GPD-001 的核心測試義務是「**服務尚未回應時回饋已存在**」——這不是時間斷言，而是狀態順序斷言。形態：

```dart
// Arrange: 注入 neverResponds 替身，服務永不完成
final fake = FakeScanNotifier.neverResponds();
// ...（注入 fake 到 ProviderScope）

// Act: 觸發互動
await tester.tap(find.byKey(scanButton));
await tester.pump(); // 一幀，足夠元件 rebuild

// Assert: 服務尚未回應，但回饋已存在
expect(find.byType(PressedVisual), findsOneWidget);     // 按下確認
expect(find.byType(WaitingIndicator), findsOneWidget);  // 等待指示

// （後續步驟：可選擇完成或不完成 fake 的 Future，驗證結果回饋）
```

此形態的特徵：
- 不量測時間，不使用 `pumpContract`
- 斷言的是「互動事件觸發後一幀內，回饋已存在，且此時服務尚未回應」
- 直接對應 ARCH-GPD-001 判準問句「拔掉服務還看得到反應嗎」
- 與 `neverResponds` 角色配對使用

**為何 pumpContract 不能取代此形態**：`pumpContract(tester, Motion.feedback)` 推進 100ms 假時鐘。若元件的實作恰好在服務回應後才觸發回饋，而替身恰好在 100ms 假時鐘內回應（available 替身的 `async` 回傳在一個 microtask 後完成），則 pumpContract 推進後回饋存在——但這是因為替身已回應，不是因為回饋獨立於服務。只有 `neverResponds` + 一幀 pump 才能驗證回饋的觸發不依賴服務回應。

**落地方式**：此形態不需修改 `test-assertion-design-rules.md`（它不是時間斷言規則，而是替身角色的使用慣例），適合記載在 `layered-test-strategy.md` 或 `test-object-catalogue.md` 的驗證形態說明中。

- 0.1.0-W3-098 why: 實機驗證時使用者按下重新掃描按鈕，**畫面完全沒有反應**——沒有按下的視覺、沒有等待指示、沒有失敗訊息。背後同時有三件事失敗（平台 handler 未註冊、完成邏輯落在同一 microtask 使骨架不可見、例外被降級收斂為某個狀態值），但使用者側的觀察只有一件事：按了沒反應。

用戶據此下的裁示（2026-09-08）：**提示效果應該掛在互動元件上，跟背後服務能不能運作不相關。**

現行〈回饋契約〉節的六類事件表定義了觸發者與回答範圍，但**沒有規定回饋的掛載點**。實作者自然會把回饋寫在服務回應的處理路徑上——那是「有東西可以顯示」的地方——於是產生一條反向相關：服務正常時回饋齊全，服務不可用時回饋為零。使用者最需要知道發生什麼事的那一刻，系統最沉默。

第二個缺口：六類事件表只列了事件，**沒有要求回答涵蓋失敗路徑**。「等待與結果」列指向三層回饋模型，而該模型的「結果通知」在實務上被讀成成功結果。失敗、逾時、服務不可用不在同一張表上，因此沒有人為它們填欄位。

第三個缺口：**降級與靜默沒有被區分**。把例外收斂為已知狀態值是行為確定性的手段，但收斂後的狀態若無可見表現（或其表現另有前提條件而前提不成立），收斂等於銷毀證據。現行條文沒有要求指出降級目標狀態的可見表現。
