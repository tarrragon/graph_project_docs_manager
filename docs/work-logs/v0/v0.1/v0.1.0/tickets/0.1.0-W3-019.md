### Context Bundle

**審查對象（四檔，全部唯讀）**

`.claude/skills/skill-design-guide/SKILL.md` 與 `references/` 下三檔：`patterns-and-troubleshooting.md`、`seeing-like-an-agent.md`、`splitting-an-existing-skill.md`。

**定位（frame 判斷標準的輸入）**

這是**查閱型參考文件**，不是照著跑的操作手冊——與本專案前一次審查的對象（component-contract-design，操作手冊）定位不同。讀者有兩種：(a) 正在建立或修改一個 skill 的人／agent，帶著具體問題來查一節；(b) 審查別人寫的 skill 的人，把 §12 檢查清單當閘門走一遍。讀完之後的動作落在世界上（改一個 skill 的 frontmatter、拆一份檔案、重寫一段 description），但**不是照第 1 節走到第 13 節**。體例應為查表 + 判準，不是編號流程。

**結構判讀（拆分方案的關鍵輸入）**

本檔有**兩個 hub 章節**：§8 建立流程指向四節、§6 Body 寫作指向五節。兩者的性質是「走一遍全文的路線」，價值恰恰來自能指向全文。

這與前一次審查的對象（component-contract-design）結構不同：那份的三種模式**互斥**，切分點天然存在——判定起點後只走一條，不會同時用到另兩條。本檔的節之間是**索引與被索引**的關係，切在哪裡都會把索引與被索引物分開：外移 §8／§12 則路線變跨檔，外移被指涉的節則路線的目的地變跨檔。

因此本次拆分方案須先回答一個前次未遇的問題：**索引型章節該跟著內容走，還是留在入口檔？** 兩個候選答案各有代價——留在入口則入口檔保有全部索引但體量壓力集中於此；跟著內容走則索引被分散、讀者不知該查哪一份。第三種可能是把索引改為不帶 §編號的形態（指向檔名而非節號），使外移不影響其有效性。此判斷交由拆分方案 reviewer，本段僅提供結構事實。

**量測 artifact 記為 finding 候選**：§6.1 的推薦骨架在程式碼區塊內使用 `## ` 標題共 5 處（L259／263／267／271／430）。主 session 兩次量測皆中招（第一次章節統計、第二次互指歸屬），修正後才得正確數字。任何以 `^## ` 解析章節的工具都會誤讀本檔——包括本檔自己在 §12 建議的機械檢查。

### Round 1-A/B 報告（s1ab-writing）+ 主 session 複驗

字句層十七類全跑，11 類零命中，無 emoji、無地區用語、無廢話前綴、無誇飾。扣分集中在**規範文件自身違反自訂條文**。

**三項嚴重，主 session 全部複驗屬實**：

| 項 | 複驗 |
|---|---|
| description 382 字元 vs §5.1 自訂「< 250 字＝禁止」 | **屬實**。實測 382；`skill-description-length-check-hook.py` 的 `WARNING_THRESHOLD = 250`，本檔會被自己專案的 hook 告警。附帶：§5.1／§12 寫「字」而 §4.1 寫「字元」，英文 description 下兩讀差 7 倍，單位須統一 |
| §6.4 列「三類例外」而 §12 檢查清單寫「須屬 §6.4 的**兩類**例外之一」 | **屬實**。§6.4 L319 起實列三類 |
| §3.1 禁止 `CHANGELOG.md`，而本檔有之，且 SKILL.md 末行主動指路 | **屬實，但規模超出 reviewer 所見** |

**CHANGELOG 一項的規模與性質修正**：主 session 全庫量測——**59 個 skill 中 58 個帶 `CHANGELOG.md`**。這不是「本檔違規」而是**規則與全專案慣例正面衝突**，且慣例那邊有支撐：每份 CHANGELOG 開頭皆載「版號規則與兩個住址（本檔與 frontmatter 的 `metadata.version`）見專案的 skill 同步規範」，即本專案的 skill 走 git 同步、有版號協定。

§3.1 該列的理由寫「給人看的版本紀錄 → 放專案根目錄或 git log」，此理由對**打包上傳的 skill**成立（官方 spec 的情境），對**走 git 同步且有跨 consumer 版號協定的 skill** 不成立。修法不是刪 58 個檔，而是判：該條是否需要「本專案例外」，或本專案的版號協定是否該改用其他載體。此項超出本次審查的裁決範圍，須另行決定。

**範例充足度（用戶指定評估項一）的結論**：範例密度呈明顯偏態。§5（Description）與 §6.4 範例充足；**§1.3 自由度、§1.4 Opinionated Defaults、§6.5 拆分三節為純判準零樣本**，而這三節恰是全檔判斷難度最高、後果最不可逆的三處（自由度選錯→ skill 行為漂移；預設值選錯→ agent 全程走錯路徑；拆分做錯→ 缺陷在讀者使用時才暴露且已無對照基準）。reviewer 建議若只補三節就補這三節，主 session 認同。

**範例品質**：全檔五處「實證」標記逐一核對，無杜撰。兩處經直接查證屬實（`CHARS_PER_TOKEN = 1.3`、`SCAN_CONFIG` 三列與 `WARNING_THRESHOLD = 250`）、一處內部自洽、兩處因未具名而不可複驗（非造假，是可驗證性缺口——建議依 §6.4 自身條文以身分指名）。

**三明示**：完整明示 3 節（§1.2、§6.4、§6.5），表格內承載 5 節，零論證 15 節。補法優先序為 §1.3／§6.2／§6.3／§11——這四節的 Why 缺失最影響套用正確性，讀者不知判準邊界就會照字面套。

**references 的兩處規範自違**：`patterns-and-troubleshooting.md` 與 `seeing-like-an-agent.md` 各有一處第二人稱（「你想要什麼工具」「了解你的使用案例」），直接違反 SKILL.md §8 Step 4 自訂的「不用『我』『你』」。
