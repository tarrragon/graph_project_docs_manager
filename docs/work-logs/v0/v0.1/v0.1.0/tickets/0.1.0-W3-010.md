### 探針結論的兩項誤估（同一檔案內的互斥）

`bash-commit-guard-hook.py` 的檔頭在相隔約十五行的兩處給出互斥的判斷：

| 位置 | 內容 |
|------|------|
| 三設計題裁決第 2 條 | 「WARN 對 AI agent 無約束力**已四次實證**，並行期改 DENY 才有效防護」 |
| 探針結論第 1 條 | 條目提早消失「僅可能在極端時序下低估真並行度而降級為 WARN（**安全方向**，符合 ANA 本已接受的約 20% 精確率設計）」 |

兩者不能同時成立。DENY 機制存在的唯一理由就是 WARN 沒有約束力；既然如此，「降級為 WARN」不是安全方向而是防護關閉。探針只檢視了一個風險軸——會不會誤 DENY 打斷合法操作——把另一個方向逕自標為安全，而同一份檔案在十五行前已否定那個標籤。

第二項誤估在頻率。探針寫「極端時序下」，但另一 consumer 的實測顯示記錄是在每個代理人回合結束轉入 idle 時被清除，屬每次派發的預設流程而非邊角時序。發生頻率不是偶發而是必然。

兩項誤估同向，一起把嚴重度壓到可接受，使該現象被記錄下來卻不觸發追問。對方據此把其修復票升為 P0。

### 消費端語意的反方向風險

框架側若只改清理時機而消費端仍讀「陣列非空」，語意會從「有代理人存活」漂移為「有代理人處於某個狀態」，兩者在 idle 這一格分岔，且失準方向相反——保留 entry 後，已交付但尚未終止的代理人會被計為活躍，使並行防護在不需要時持續 DENY。本票驗收須涵蓋兩個方向，不只確認 DENY 恢復。

### 驗收可行性的限制：觀測與回收都是 session-scoped

另一 consumer 實測兩項限制，本票驗收設計受其約束：

| 動作 | 本 session 自有代理人 | 他 session 所屬 |
|------|---------------------|---------------|
| `ListAgents` 列出 | 是（帶 running / idle 狀態） | 否 |
| `TaskStop` 停止 | 是 | 否（回報找不到該 task，即使名稱取自其 idle 通知） |

本票的驗收步驟派發本 session 自有的具名代理人，不受此限，仍可執行。但推論出的一個風險須記下：擁有者 session 結束後，其殘留代理人可能無任何 session 有權停止，而它仍存活並週期性發通知。本 session 目前有二十個處於 idle 的 teammate，若該推論成立，session 結束時它們的歸屬即成問題。此風險不在本票範圍，記於此供後續評估。

### 拉取後的一項對外回報（另一 consumer 請求）

該 consumer 的 idle agent 回收掃描（歸屬三分：自有／他 session 存活／孤兒）驗證時只有兩個候選，且全落在「自有」這一格。本 session 目前有 19 個自有代理人，加上跨 session 可見的其他 session，樣本可能同時涵蓋兩到三格。

拉取含該功能的框架版本後，SessionStart 會輸出 idle agent 候選與歸屬分類。該輸出應回報給 `flutter-balance-99`，作為多代理人情境（N=19）的取樣補充。

此為對外協作事項，不影響本票的驗收條件。

### 附帶發現：append-log 失敗但 PostToolUse 宣告成功

本段原本要寫入 NeedsContext 章節，`append-log` 因該票為 pending 而拒絕寫入（提示 claim 或 `--force`），但同一次呼叫的 PostToolUse hook 仍輸出「[NeedsContext] 已更新於 0.1.0-W3-010」。

`grep` 票面確認該段落未寫入（命中 0），工作區無變更。也就是**寫入失敗而 hook 宣告成功**。

發現它是因為兩個訊號矛盾——CLI 的拒絕訊息與 hook 的成功宣告同時出現才觸發查證。若 CLI 錯誤被輸出截斷或 hook 先於錯誤顯示，只會看到「已更新」。

此形態與本輪已記錄的幾筆同族：失效時外觀訊號正常。差別在這筆的訊號不只是「沒有異常」而是「主動宣告成功」，比靜默失敗更強——靜默失敗至少不阻止查證，主動宣告會終止查證動機。

屬框架缺陷，應上報 canonical。
### 該附帶發現的後續：已上報並取得更強證據

上報為 `tarrragon/claude#80`。建立該 issue 的命令本身又觸發了同一個 hook，取得比原推測更明確的證據：

該命令是 `framework-issue` 的 `create_issue.py`，與 append-log 無關、與任何 ticket 無關，PostToolUse 仍輸出「[NeedsContext] 已更新於 `<ticket-id>`」，且 `<ticket-id>` 是**字面的佔位符**而非解析失敗的空值。

所以觸發條件比推測的更寬：命令字面含 `NeedsContext` 即可，本次命中的是 issue body 描述問題時寫的那個字串。該 hook 在那次呼叫中不知道有沒有票、不知道是哪張票、不知道有沒有寫入，仍宣告已更新。

修法優先序因此改變，已補進 issue：先收窄觸發條件（命令確實是 append-log 且解析得出 ticket ID），再依 exit code 決定宣告內容。只做後者不夠——與 ticket 無關的呼叫沒有 exit code 可讀。

另記一項：佔位符原樣輸出表示模板取不到值仍繼續，這條路徑即使觸發條件修對，遇解析失敗仍會產出無意義宣告。
