## Solution
### 題一：輸出端的三層對應

### 三層對照表

| 層 | 輸入端（driving port） | 輸出端（driven port） | 結構差異 |
|----|----------------------|---------------------|---------|
| 一 | 按下確認：pressed 視覺／觸覺／聲音，承擔者＝元件自身 | 呼叫發出：方法被調用、Future 被建立、呼叫事件被記錄，承擔者＝呼叫端程式碼 | 輸入端的消費者是使用者（視覺通道），輸出端的消費者是呼叫端執行緒（程式控制流）+ log（持久記錄）+ APM（統計追蹤） |
| 二 | 服務受理：已送出、正在處理（loading 動畫/toast），承擔者＝服務 | 外部系統受理：連線建立／檔案控制碼取得／請求被接收（acknowledged 狀態或 progress callback），承擔者＝ adapter 實作 | 輸入端由 UI 元件表現，輸出端由 adapter 的回傳型別或 callback 介面表現 |
| 三 | event 效果：服務處理完的結局（成功/失敗/逾時/服務不可用），承擔者＝事件處理路徑 | 結果：外部操作的結局（成功/失敗/逾時/不可達），承擔者＝ adapter 實作的回傳值或例外 | 結局集合同構（成功/失敗/逾時/不可達），差別在呈現介面（輸入端是 SnackBar/狀態轉換，輸出端是回傳型別/例外型別） |

### 輸入端不變式在輸出端的對應形式

輸入端 INV-FEEDBACK-001：元件在每一次互動都必須發出第一層回饋，即使服務因防抖而丟棄。

輸出端對應不變式 **INV-PORT-OBSERVE-001**：**每一次 driven port 呼叫都必須產生第一層可觀測事件（呼叫已發出），即使呼叫最終失敗、被防抖丟棄或立即拋出例外。**

展開：
- 呼叫端調用 port 方法的那一刻即為第一層事件。此事件不依賴外部系統是否回應、是否可達、是否逾時。
- 第一層的可觀測證據可以是 log 記錄（「呼叫 X.method(params) 於 timestamp」）或 APM span 開始。
- 如果第一層不存在，外部系統無回應時 log/APM 只能在第三層（結果）產生記錄；而逾時之前沒有任何記錄——形成可觀測性空窗，正如輸入端缺第一層時使用者「按了沒反應」。

**判準問句**（平行於輸入端「拔掉服務還看得到反應嗎」）：把外部系統整個拔掉（模擬不可達），呼叫端能否得知「呼叫已發出但無回應」？Log 能否記錄「何時發出、對誰發出、至今無回應」？答案為否，即第一層缺失。

### 時序約束（用戶裁示）

log 與 APM 追蹤不是事後可補的能力，它們消費的是設計期就要決定的回饋點。具體含義：

- Port 介面的簽章決定呼叫端能拿到什麼——回傳型別是 `Result<T,E>` 還是 bare `T`？有 progress callback 嗎？有 acknowledged 狀態嗎？這些決定第二層是否可被消費。
- Adapter 實作中的 log/APM call 位置決定三個時刻是否被記錄——呼叫前一行（第一層）、收到受理回應時（第二層）、操作完成時（第三層）。
- 設計期沒有把這些回饋點寫進 port 契約，事後補 log 只能拿到例外堆疊（第三層的失敗分支），拿不到第一層和第二層——因為那兩個時刻的記錄需要程式碼在那個位置主動發出 log call，那些位置不在例外路徑上。

### 題二：回饋消費者與其介面

### 三個消費者的投影

| 消費者 | 消費形式 | 消費目的 | 對應層（典型） |
|--------|---------|---------|--------------|
| 呼叫端執行緒 | 回傳值／例外／Future 狀態／progress callback | 程式決策（重試、降級、傳播錯誤、更新 UI 狀態） | 三層皆有：回傳值（三）、acknowledged（二）、呼叫成功發出（一） |
| Log | 結構化日誌記錄（時間戳 + context + 層級 + stack trace） | 開發者診斷（事後除錯、稽核軌跡、incident 根因分析） | 三層皆有：呼叫記錄（一）、受理記錄（二）、結果記錄（三） |
| APM | trace span（start/end）/ 計時追蹤 / 錯誤率 / 告警 | 營運監控（延遲分佈 p50/p99、錯誤率趨勢、告警觸發） | 三層皆有：span start（一）、checkpoint（二）、span end（三） |

### 三者拿到的是同一份資訊還是不同視角？

不同視角。三者是同一組事件的三種投影：

- 呼叫端拿到的是**同步即時投影**——方法回傳值、thrown exception、Future.then/catchError。語意是「我現在能拿這個結果做什麼決策」。
- Log 拿到的是**持久化投影**——寫入磁碟的文字記錄。語意是「事後有人來查，能看到什麼」。
- APM 拿到的是**統計投影**——延遲分佈、錯誤率。語意是「這個 port 長期的健康度如何」。

三種投影各自不可替代——log 記了不代表呼叫端知道、呼叫端處理了不代表 log 有留紀錄、兩者都有不代表 APM 有追蹤延遲分佈。

### 日誌與呼叫端回饋在輸出端是否同構於「不互相抵扣」？

**是，且理由同構。**

ARCH-GPD-001 第 5 點：「日誌不抵扣使用者回饋——兩者是獨立義務，審查時分別確認。」

輸出端的同構規則：**日誌不抵扣呼叫端回饋，呼叫端回饋不抵扣日誌——兩者是獨立義務，審查時分別確認。**

具體形態：

| 違反情境 | 輸入端等價物 | 結果 |
|---------|------------|------|
| Adapter 的 catch 只記 log + return default → 呼叫端拿到 default，無法區分「成功且值恰為 default」與「失敗被降級」 | ARCH-GPD-001 降級等於銷毀證據 | 呼叫端做出基於虛假前提的決策（以為成功，實際失敗） |
| Adapter 吞掉例外只記 warning → 呼叫端 Future 永不 complete 或拿到 null | 服務不可用時回饋為零 | 呼叫端永遠等待或 NPE，開發者可在 log 中看到但呼叫端無從得知 |
| Adapter 回傳 Result.failure + 不記 log → 呼叫端知道失敗但 log 中無記錄 | 使用者看到錯誤但開發者 log 中找不到 | incident 分析時無從溯源 |

### 不互相抵扣規則在輸出端的完整形式

| 義務 | 消費者 | 不可被以下抵扣 |
|------|--------|--------------|
| 呼叫端回饋 | 呼叫端執行緒 | Log 已記錄不代表呼叫端已知；回傳 default/null 不代表成功 |
| 可觀測性 | Log + APM | 呼叫端已處理（重試/降級）不代表 log/APM 可省略 |

兩套義務獨立，審查時分別確認——結構上平行於 ARCH-GPD-001 第 5 點。

### 「執行緒回饋」與「日誌」在輸出端是否合一？

**不合一。** 輸入端的三層回饋消費者是使用者一人（三層都是給同一個人看的不同時刻）。輸出端的三個消費者是三個不同實體，各自有不同介面：
- 呼叫端透過程式語言的型別系統消費（回傳型別、例外型別、Future 泛型）
- Log 透過結構化日誌 API 消費（`developer.log` 等）
- APM 透過 trace/span API 消費

**Pro**：
- 非 UI 層實作者在設計 port/adapter 時會讀這份方法論，回饋契約在正確時機被讀到——**正中判準**。
- clean-architecture 方法論目前只有 75 行（四層架構 + 依賴方向 + 介面契約），port 的可觀測性是顯然的空白，加入回饋契約正是補上這個空白。
- 不需搬移元件庫方法論的任何內容；〈掛載點〉〈失敗路徑覆蓋〉〈降級不解除回饋義務〉三個 `#####` 子節標題原樣保留，只在〈掛載點〉開頭加一行引用指向架構層定義。
- 三層結構本身不依賴任何特定技術棧，是通用架構原則，適合放在通用方法論中。

**Con**：
- clean-architecture 方法論目前是通用的，加入 feedback 使其體量增加。但回饋三層不綁任何框架，仍屬通用。

### 候選 (b)：新建架構層方法論（如 `port-feedback-contract-methodology.md`）

**Pro**：乾淨分離，不改既有方法論。

**Con**：
- 元件庫方法論的〈回饋契約〉節剛由多張票落定（W3-098/101/102），三個 `#####` 子節標題已被 skill 與範本逐字引用為跨檔錨點——如果要從元件庫搬原則到新方法論，下游引用全部要更新。

- 兩份方法論（元件庫 + port-feedback）各自定義三層結構，修改時要保持同步——正是 W3-107 why 段「兩套互不相容的分類是最壞的產出」所警告的。

**Con**：完全不解決問題。票面 why 已點出「架構層原則長在 UI 方法論下，其他層的實作者不會讀到」——加一段「本節只適用 UI」等於承認問題但不解決。

### 題四：測試義務

### 輸出端三層的驗收方式

| 層 | 驗證目標 | 斷言形態 | 需要替身嗎？ |
|----|---------|---------|------------|
| 一、呼叫發出 | port 方法被調用、呼叫事件被記錄 | `verify(mockPort.method(), called: 1)` 或 spy 確認方法被呼叫；log 斷言含「呼叫 X.method 於 timestamp」 | **不需要外部系統替身**——驗的是呼叫端確實發出了呼叫，用 mock/spy 記錄呼叫事實即可 |
| 二、外部系統受理 | adapter 正確處理 acknowledged/processing 狀態 | 注入角色化替身 → 觸發呼叫 → 斷言 adapter 狀態轉移或 progress callback 呼叫次數 | **需要替身**：W3-100 的 acknowledged / processing 角色 |
| 三、結果 | adapter 正確處理四種結局 | 注入角色化替身 → 斷言回傳值型別或例外型別 | **需要替身**：W3-100 的 succeeds / fails / timesOut / throwsPlatformError 四角色 |

### 第一層是否如輸入端一樣不需替身？

**是，但有一個結構差異。**

輸入端第一層（按下確認）：不需要任何替身。純 widget test，不注入服務依賴，只建構元件本身。驗的是元件自身的 pressed 視覺——與服務完全無關。

輸出端第一層（呼叫發出）：**不需要外部系統替身**，但 port 本身是介面，測試中需要一個 mock/spy 來記錄呼叫事實。這個 mock/spy 不模擬任何行為（不回傳特定值、不拋例外），只記錄「method 被呼叫了、參數是什麼」。

精神一致——兩者都不依賴外部系統的行為。差異在載體：
- 輸入端第一層的載體是 widget tree（build 就有），不需任何注入
- 輸出端第一層的載體是 port interface（dependency injection），需要一個記錄器（spy）

spy 不是行為替身——它不屬於 W3-100 的 acknowledged/processing/fails 等行為角色。它只是一個「呼叫記錄器」，與輸入端第一層測試中 `tester.tap` + `pump` 確認 pressed 態的角色同構。

### INV-PORT-OBSERVE-001 的驗收

| 測試 | 斷言形態 | 替身角色 |
|------|---------|---------|
| 外部系統無回應時第一層仍存在 | 注入 `neverAcknowledges` → 呼叫 port method → 斷言 log 含呼叫記錄（不等待回應） | Layer 2 neverAcknowledges（外部系統無回應），但第一層斷言不依賴它回應 |
| 呼叫立即拋例外時第一層仍存在 | 注入 `throwsPlatformError` → 呼叫 port method → 斷言 log 含呼叫記錄（在例外之前已記錄） | Layer 3 throwsPlatformError |
| 防抖窗口內重複呼叫皆有第一層記錄 | 連續呼叫 N 次 → 斷言 log 含 N 筆呼叫記錄（即使服務只執行最後一次） | 無替身（Layer 1 驗證） |

### W3-105 替身角色是否同一組？

**可共用。** W3-105 定義的替身角色從輸入端視角設計，但角色語意（行為模式）在輸出端同構：

| W3-100/105 角色 | 輸入端用途（使用者視角） | 輸出端用途（呼叫端視角） |
|----------------|----------------------|---------------------|
| acknowledged | 服務受理（loading 觸發） | 外部系統受理（連線建立/控制碼取得） |
| processing | 服務處理中（進度更新） | 外部系統處理中（progress callback） |
| neverAcknowledges | 服務無回應（驗 INV-FEEDBACK-001） | 外部系統無回應（驗 INV-PORT-OBSERVE-001） |
| succeeds | 服務成功 | 外部操作成功 |
| fails | 服務失敗 | 外部操作失敗 |
| timesOut | 服務逾時 | 外部操作逾時 |
| throwsPlatformError | 平台錯誤 | 平台錯誤（輸出端亦跨平台邊界） |

角色定義不變，消費者不同。**不需要各自建一套分類**——同一組角色適用於兩端。

### W3-105 服務類型分類是否可共用？

**可共用同一套分類框架**（以感知者等待長度 x 失敗形態兩軸切分），但感知者不同且適用範圍有差異：

| W3-105 類型 | 輸入端（使用者感知） | 輸出端（呼叫端感知） | 差異 |
|------------|-------------------|-------------------|------|
| I. 本地即時 | 零等待，純本地操作 | **不存在**——純本地操作不跨 port 邊界，不存在 driven port | 輸出端自然排除 |
| II. 延遲觸發 | 防抖後才觸發，本地運算 | 0.1 無實例（搜尋防抖的結果是本地過濾，不呼叫外部系統）；未來若有 API 搜尋則適用 | 輸出端在 0.1 無實例 |
| III. 短暫非同步 | 亞秒，可能失敗 | **直接適用**——file open、permission check、short API call 皆為 driven port 呼叫 | 消費者從使用者改為呼叫端+log+APM |
| IV. 長時操作 | 秒至分鐘，需進度與取消 | **直接適用**——domain 載入、大檔解析、網路下載 | 同上 |

結論：**分類框架共用，輸出端在 0.1 實際適用 III 和 IV 兩類**。不另建一套分類。

### Rationale Chain
- 0.1.0-W3-102 why: `0.1.0-W3-098` 落地的〈掛載點〉條文寫「按下確認與等待指示的觸發點是互動事件本身與『已送出、尚未回應』這個狀態」——把**兩層都歸給元件**。用戶隨後的裁示（2026-09-08）給出三層，且中間那層的承擔者是服務不是元件：

| 層 | 內容 | 承擔者 |
|----|------|--------|
| 一、互動元件層 | 互動當下的回饋：震動／音效／變形／變色／光環 | **元件自身**，與背後是否掛服務無關 |
| 二、服務受理層 | command 發送 event 給服務後，服務自己的處理回饋：toast、loading 動畫 | **服務** |
| 三、event 效果層 | 服務處理完之後才觸發 event 應該觸發的效果，無論成功失敗或其他 | 事件處理路徑 |

現行條文與此的差距有兩處：

1. **歸屬錯置**：「等待指示」（第二層）被寫成元件的義務。實際上 command 送出之後，是**服務**要對「我收到了、正在處理」負責。把它歸給元件，會讓服務側完全沒有回饋義務——服務可以什麼都不做而條文仍被滿足。

2. **第一層的無條件性未寫明**：條文的判準問句「把服務拔掉還看得到反應嗎」隱含了第一層必須存在，但沒有明說**每個可互動元件都必須有互動當下的回饋，沒有例外**。PM 在派發存量盤點票時因此把「互動不觸發跨層呼叫」誤讀為「判準自動成立」——純本地狀態切換的元件若按下時無任何表現，只有狀態改變後的結果，一樣是缺陷，而該誤讀在現行條文下讀得通。

`ARCH-GPD-001` 同樣只寫了兩層（回饋 vs 服務回應），未涵蓋服務受理層的獨立歸屬，須一併補。（來源已完成，結論見 Solution）
- 0.1.0-W3-105 why: 現行回饋契約回答的是「怎麼告知使用者」，不回答「按下之後到結果之前這段時間，系統怎麼保護自己與使用者」。用戶於三層歸屬裁示後補充三項（2026-09-08），三項都以**服務類型**為自變數：

1. **不同類型的服務應提供哪些回饋提示** —— 並明指這是**測試驗收的一個指標**，故須可機械檢查，不能只是敘述性建議。
2. **等待期間是否需要阻擋使用者的其他操作、屏蔽畫面輸入** —— 這與提示是兩件事：提示是「告知」，阻擋是「防止」。目前規格兩者都沒有依服務類型的規則。
3. **按鈕類互動元件的防抖** —— 且明確裁示**防抖由服務提供，不是元件提供**。

第 3 點的歸屬與三層模型一致，且推出一條重要不變式：**元件在每一次按下都必須發出第一層回饋，即使服務因防抖而丟棄該次呼叫**。若防抖做在元件層，防抖窗口內的按下會沒有 ripple，使用者看到的是一個沒反應的按鈕——正是 `ARCH-GPD-001` 的形態，只是成因從「服務不可用」換成「服務刻意不執行」。元件永遠回饋，服務決定要不要真的執行。

現況：SPEC-003 §2.1 只有 `Motion.searchDebounce`（300 ms，搜尋輸入用），沒有按鈕類的防抖規則，也沒有規定它實作在哪一層；「阻擋」一詞在 SPEC-003 全文只用於「阻擋狀態元件」（畫面狀態的一種），與「等待期阻擋輸入」不是同一件事，目前後者無任何條文。（來源已完成，結論見 Solution）
