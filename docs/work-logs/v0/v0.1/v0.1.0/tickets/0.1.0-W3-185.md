### 前提重評（2026-09-10，因方法論與 spec 設計更新）

**本票的問句由「是否需要」降為「形態為何」——方法論已經要求它存在。**

「必須確認」類提示的定義是：接收方不做決策就不能繼續。依方法論〈級別〉，級別的鍵是**丟棄後果由誰承擔、可否回復**——這類提示丟棄後接收方無從補救，落在**不可棄**。而方法論〈讓步與卸載順序〉對不可棄格的處置是固定的、不由個案裁量：等待型 × 不可棄「不由仲裁器卸載，無法服務即觸發容量 tripwire」；推送型 × 不可棄「**不得只存在於記憶體緩衝**，必須落持久佇列」。

`AppSnackBar` 是會自動消失的記憶體內載體。承載不可棄級別的提示違反上述條款。**所以「0.1 需不需要必須確認類載體」不再是開放問題**——只要本專案存在不可棄級別的提示，載體就是必需的；本票要決的是它的形態，以及 SPEC-004 §6 的原生元件禁用對照表要怎麼開這個口。

**這也改變了與 SPEC-004 的衝突性質**：原本是「新增載體會推翻既有規格裁定」（兩個對等主張相衝），現在是「既有裁定與方法論的不可棄條款不相容」（規格層需依方法論調整）。後者的處置路徑不同——不是權衡，是把 §6 的理由（「§1 覆蓋表面對映無 dialog／sheet／drawer」）拿去對照級別要求，若對映確實沒有，則缺的是對映而不是載體。

**仍未決的部分**：本專案 0.1 是否真的存在不可棄級別的提示。若逐條標定後全部落在須留痕或可棄，本票可判為 0.1 不需要。**這一項應由 SPEC-003 §2.14 的到達類別與級別指派表逐列判定，不另行推測。**
