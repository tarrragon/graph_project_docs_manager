### 實驗發現

**已驗證的事實**：

1. 四條路徑中，argparse 拒絕（含任何形式：缺必填/未知旗標）從未進入
   `create_id_allocation_lock`，不產生也不刷新鎖檔——與 PM 原始觀測一致。
2. 其餘三條路徑（Step1 內部拒絕、checklist 拒絕、`--dry-run`）皆會取鎖，
   且皆透過 try/finally 正確釋放 OS 層 flock（`lsof` 事後皆為空、無任何
   一次殘留持有者）——鎖機制本身沒有「未釋放」的缺陷。
3. 鎖檔在 release 後**不會被刪除**，是 `filelock` 函式庫（及一般 flock-based
   lock）的刻意設計：`create_id_allocation_lock` docstring 已明文
   「crash 後 OS 自動回收 fd 釋鎖，殘留檔不影響 reuse」。刪除鎖檔屬另一種
   設計（如 git 的 ref lock：存在即鎖定、操作完成即刪除），兩種設計不可
   混用——對 flock-based 鎖在 release 後刪除檔案會重新引入 TOCTOU 競爭
   （process A 刪除時 process B 可能已對舊 inode 取得 flock，隨後
   process C 建立同名新檔案，B 的鎖已脫離任何人會再檢查的 inode）。
4. 全域搜尋確認**不存在任何程式碼消費端**會讀取此鎖檔的存在性或內容
   作為判斷依據；`reap_stale_locks` 明確排除它。唯一「讀取」它的是人類
   在事故排查時執行 `ls`/`find` 觀察到它與 git 原生鎖同時出現。

**結論（回答 acceptance 第 2 條的分岔點）**：此缺陷的形態是**「產生但無人
檢查的假訊號」**，不是「未釋放的互斥鎖」。鎖機制運作正確；問題出在它
遺留的檔案在視覺特徵（位置 `ticket-create-locks/`、副檔名 `.lock`、
0 bytes、無持有者）上與 git 原生 ref lock/index lock 無法區分，導致排查
者以同一套判準誤判並移除，見 `PC-GPD-013`。

**仍未驗證的假設**：例外路徑（Step 1-3 內部丟出非預期例外，如磁碟寫入
中途拋錯）與並行呼叫（兩個 process 同時取鎖競爭）未在本次重驗範圍內
重現；但兩者皆不影響上述結論——try/finally 對任何例外路徑皆保證釋放，
並行競爭本就是 flock 語意本身要處理的情境（`FileLock.acquire()` 為
blocking，會等待而非產生殘留）。此二項留待修法票（見 Solution spawn
規劃）驗收時視需要補測，不影響本票的假訊號判定。

## Solution
### 判定結論

見「重現實驗結果」：本缺陷是**產生但無人檢查的假訊號**，不是未釋放的
互斥鎖。修法方向因此是「降低視覺誤判機率」與「消除不必要的鎖動作」，
不是「讓鎖檔消失」——後者若照 acceptance 第 3 條字面實作為「release 後
刪除檔案」會重新引入 TOCTOU 競爭（見重現實驗結果第 3 點），是倒退而非
修正。以下方案皆維持 flock 語意與跨 worktree 共用位置不變。

**acceptance 第 3、4 條的達成方式說明**（供修法票承接者與 PM 對照）：
第 3 條「不殘留鎖」以方案 A-1（副檔名去除歧義）達成其精神——鎖檔不再
出現在 `find .git -name "*.lock"` 這類全域鎖盤點指令中，不再與 git 原生
`main.lock`/`HEAD.lock` 混為一談；檔案本身仍會存在（flock 語意要求），
但不再具備「看起來是殘留鎖」的視覺特徵。第 4 條「dry-run 不取得或刷新
任何鎖」以方案 A-2（dry-run 跳過鎖）字面達成。

### 候選方案

**方案 A（建議採用）：兩項獨立低風險修正，分別對應第 3、4 條**

- **A-1 檔名去除歧義**：`CREATE_LOCK_FILENAME`（`file_lock.py:150`）由
  `.ticket-create.lock` 改為不匹配 `*.lock` glob 的命名（如
  `.ticket-create.rendezvous`），位置與跨 worktree 共用機制
  （`_resolve_shared_lock_path`）不變。
  - 優點：改動範圍小（單一常數 + 同步更新 `test_create_id_allocation_race.py`／
    `test_create_id_sibling_worktree_scan.py`／`test_reap_stale_locks.py` 三個
    測試檔的常數引用）；不改變任何鎖行為與正確性；直接命中
    `PC-GPD-013` 記載的混淆成因（同時出現、同為 0 bytes、同無持有者、
    同在鎖盤點指令的比對範圍內）。
  - 缺點：既有安裝已產生的舊 `.ticket-create.lock` 殘留檔不會自動消失
    （為害仍是零，但目錄下會同時存在新舊兩種命名，需一次性文件說明
    或清理腳本）；`.lock` 副檔名是常見慣例，改名需確認 `.gitignore`
    規則（`*.lock`）仍涵蓋新副檔名，否則新鎖檔會被意外納入版本控制。
- **A-2 dry-run 不取鎖**：將 `--dry-run` 分支判斷（現於
  `_persist_and_report` 內、`create.py:610-614`）提前到
  `create_id_allocation_lock`（`create.py:874`）之前，dry-run 預覽改為
  在鎖外唯讀計算 would-be ticket_id。
  - 優點：精準對應第 4 條；預覽路徑完全不再取得/刷新任何鎖狀態；風險低
    （純粹搬移既有唯讀計算的執行位置，不改變計算邏輯）。
  - 缺點：並行下 dry-run 顯示的預覽 ID 有極小機率與稍後真正建立時分配
    到的 ID 不同（dry-run 語意本就是「不落地的預覽」，此為可接受的
    既有限制，非本修法引入的新風險）；需重新梳理
    `resolve_ticket_id_and_wave` 與 `_persist_and_report` 的呼叫順序，
    測試需覆蓋「dry-run 與真實 create 並行時彼此不受影響」。

**方案 B：維持機制不變，僅補強文件/觸發時的可見提示**

於 `PC-GPD-013` 或 `bash-tool-usage-rules.md` 補一條「已知非阻塞鎖清單」，
明列 `*.ticket-create.lock`（或未來改名後的副檔名）屬 flock-based 常駐
rendezvous 檔案、非阻塞信號；`.ticket-create.lock` 錯誤訊息
（`CHECKLIST_VALIDATION_FAILED` 等）中補一行提示「本次操作已取得又釋放
序列化鎖，殘留檔不影響後續建票」。
- 優點：零程式碼風險，可立即落地，且與方案 A 不衝突可並行採用。
- 缺點：治標不治本——`create_id_allocation_lock` docstring 現在就寫著
  「殘留檔不影響 reuse」，本次排查證明**文件已存在仍被誤判**（事故當下
  排查者查的是鎖檔本身的視覺特徵，不是原始碼註解）；且完全不處理
  第 4 條（dry-run 仍會不必要地刷新鎖狀態）。單獨採用不足以達成 acceptance，
  僅適合作為方案 A 的補充。

**方案 C：把鎖檔移出 `.git` common dir，物理脫離 git 原生鎖目錄**

另尋跨 worktree 共用的非 `.git` 位置存放鎖檔，徹底不出現在
`find .git -name "*.lock"` 的搜尋範圍內。
- 優點：比 A-1 更徹底地與 git 原生鎖切割。
- 缺點：工程成本明顯高於 A-1，卻換來相同的「不再被同一份盤點指令掃到」
  效果——A-1 用改副檔名已達成同一目的、成本低很多；且需要重新驗證
  `.claude/` 下是否存在等效於 git-common-dir 的跨 worktree 共用位置，
  若找不到會被迫退回本地互斥、重新引入 `IMP-072` 的原始撞號問題

### Task Reference

查明 `ticket create` 的 create lock 在四條退出路徑上的取得與釋放行為，並判定其形態是「未釋放的互斥鎖」還是「產生但無人檢查的假訊號」。兩者修法相反，故本票不預設修法。

### Rationale Chain

本票源於 2026-09-09 的並行殘留鎖排查，不是源於任何既有 ticket。當日在同一 repo 內三個 session 共用工作區，先後出現多把殘留鎖，排查過程中發現 create lock 是其中唯一一把「持續產生卻不阻擋任何操作」的——其餘（`index.lock` / `main.lock` / `HEAD.lock`）皆確實擋住對應操作。

**這個差異是本票的核心**：其餘鎖擋住操作，因此排查者移除它們之後管道確實恢復，因果成立；create lock 不擋任何操作，但它與其餘鎖同時出現、同樣是 0 bytes、同樣無持有者，於是被同一套判準處理，且移除後管道恰好也恢復（因為真正的阻因同時被移除了）。**至少兩個 session 各自把管道恢復歸因於移除這把鎖。** 錯誤歸因未造成損害，但它會在下一次事故中重演，且下一次未必無害。

背景機制已記錄於 `PC-GPD-013`（繞道路徑成功，使共用資源的故障失去唯一的診斷訊號），本票是該則在單一工具上的具體修正標的。
