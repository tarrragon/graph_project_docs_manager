### PM 建票前實測（原始觀測，供接手者對照；仍請依 PC-162 獨立重驗）

以 `ticket create` 本身作為實驗載體，同一環境連續四次觀測，每次前後以 `ls -l .git/ticket-create-locks/` 讀取鎖狀態：

| # | 觸發 | 命令結果 | 鎖狀態變化 |
|---|------|---------|-----------|
| 1 | 缺 `--action` / `--target` | argparse `error: the following arguments are required` | **無鎖產生** |
| 2 | 缺 `acceptance` / `when` / `how_strategy` | `CHECKLIST_VALIDATION_FAILED` | **產生新鎖**（0 bytes） |
| 3 | 欄位齊備 | `[OK] 已建立 Ticket`（即本票） | **產生新鎖**（0 bytes） |
| 4 | `--dry-run`，且執行前既有一把鎖 | `[DRY-RUN] 將建立 Ticket ...（不落地，未寫入任何檔案）` | **既有鎖 mtime 被刷新** |

第 4 次同時證實兩件事：`--dry-run` 會動到鎖狀態；以及**鎖存在時建票管道並未被擋住**（命令一路推進到產出 dry-run 預覽）。

每次觀測皆確認 `lsof <鎖檔>` 零持有者、`ps` 無 ticket 行程殘留。

**接手者請注意**：以上為建票當下的單一環境觀測，未涵蓋例外路徑（如寫入中途拋錯）、未涵蓋並行呼叫，也未查明是否有任何程式碼讀取該鎖——最後一項是 acceptance 第 2 條的核心，也是決定修法方向的分岔點。

### Task Reference

查明 `ticket create` 的 create lock 在四條退出路徑上的取得與釋放行為，並判定其形態是「未釋放的互斥鎖」還是「產生但無人檢查的假訊號」。兩者修法相反，故本票不預設修法。

### Rationale Chain

本票源於 2026-09-09 的並行殘留鎖排查，不是源於任何既有 ticket。當日在同一 repo 內三個 session 共用工作區，先後出現多把殘留鎖，排查過程中發現 create lock 是其中唯一一把「持續產生卻不阻擋任何操作」的——其餘（`index.lock` / `main.lock` / `HEAD.lock`）皆確實擋住對應操作。

**這個差異是本票的核心**：其餘鎖擋住操作，因此排查者移除它們之後管道確實恢復，因果成立；create lock 不擋任何操作，但它與其餘鎖同時出現、同樣是 0 bytes、同樣無持有者，於是被同一套判準處理，且移除後管道恰好也恢復（因為真正的阻因同時被移除了）。**至少兩個 session 各自把管道恢復歸因於移除這把鎖。** 錯誤歸因未造成損害，但它會在下一次事故中重演，且下一次未必無害。

背景機制已記錄於 `PC-GPD-013`（繞道路徑成功，使共用資源的故障失去唯一的診斷訊號），本票是該則在單一工具上的具體修正標的。
