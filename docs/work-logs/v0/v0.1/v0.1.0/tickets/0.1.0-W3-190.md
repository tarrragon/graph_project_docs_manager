### Rationale Chain
- 0.1.0-W3-155 why: `.claude/skills/ticket/ticket_system` 的 create 流程取得 `.git/ticket-create-locks/<版本目錄>.ticket-create.lock` 之後，四條退出路徑中有三條未釋放它。鎖為 0 bytes、無持有行程，且**不會擋住任何後續建票**——它的代價不在阻擋，而在事故排查中作為假訊號。

**四條路徑皆為實測，非推論**：

- argparse 層拒絕（缺 `--action` / `--target`）：**不留鎖**
- checklist 層拒絕（`CHECKLIST_VALIDATION_FAILED`，缺 `acceptance` / `when` / `how_strategy`）：**留鎖**
- 建票成功：**留鎖**
- `--dry-run`（明示不寫入任何檔案）：**留鎖，且刷新既有鎖的 mtime**

由此可定位兩件事：鎖的取得在 argparse 之後、checklist 之前；且早於「是否真的要寫入」的判斷——否則 `--dry-run` 不該動到它。

**為何這條路徑經常被走到**：漏填必填欄是建票的高頻首次錯誤（本次排查中同一人連續命中兩次）。而錯誤訊息完整列出缺失欄位與修正建議，**完全未提及鎖已被取得且未釋放**。

**實際損害是誤導，不是阻擋**（建票後補測，修正建票當下的錯誤推論）：實驗確認鎖存在時 `ticket create` 照常執行、未被擋住。因此本日約 9 分鐘的建票不可用**不是這把鎖造成的**——同時間另有 `main.lock`（41 bytes）與 `HEAD.lock` 擋住 commit 步驟，那才是阻因。建票當下把兩者歸為同一原因，屬未經實測的推論，已於此更正。

真正的代價是它在事故排查中的形態：它看起來是一把鎖、位在 `ticket-create-locks/` 目錄下、命名指向建票，於是被當成阻因處理。本日至少兩個 session 各自移除它並將管道恢復歸因於該移除，而管道從未被它擋住。**一個持續產生卻不被檢查的鎖檔，在並行事故中會穩定地把排查者導向錯誤的根因。**
