## Problem Analysis
### 問題根因

F-16：〈共用規則一〉「外觀不同：降為變體」與 path-b 步驟 3「外觀差異降為變體」只寫給「歸併候選之間」的外觀差異，條文未標此範圍；正例一把「由元件自身資料態驅動的外觀差異（封存變暗）」歸狀態集，依據是 step-3〈元件契約欄位填寫問句〉的變體列（行為不同的形態）與狀態集列（來源含資料態）。字面牴觸，實質是規則一的處置語句射程過寬。另正例一內部不自洽：變體列說交由「狀態集的對應狀態」，但狀態集列只列 default／focused，無封存狀態，測試契約列與狀態集備註「兩狀態皆本地互動瞬態」同樣未含。

F-18：正例三的待決落在畫面票傳入的 slot 值（阻擋提示的訊息文案 key），不是元件契約欄位；輸入段明寫七項元件契約「已填滿」。step-4 第 1 條與 Troubleshooting 第 3 列管的是元件契約欄位待決（元件不得被引用），兩者對象不同，前提未寫出。另 Q 的「不阻擋本畫面票通過」中「通過」語意未定（寫法合格 vs 可派發），與同段 how「設為本畫面票 blockedBy」字面相反。step-5〈畫面票〉對「slot 值待決」無條文，是前提缺口。

### 影響範圍

已驗證（逐字讀）：appendix-examples.md〈正例〉一 變體／狀態集／測試契約三列、〈正例〉三 how 阻擋列、「刻意保留的不完美」段、第三則 Q；step-2-extract-components.md〈共用規則一〉表外觀不同列；step-2-path-b-canvas-decomposition.md 流程區塊步驟 3；step-3-fill-contract.md 變體列與狀態集列；step-4-verify-completeness.md〈契約齊全的定義：六條〉第 1、4 條；step-5-write-tickets.md〈畫面票〉how 列與〈決策票與分析票〉；appendix Troubleshooting「最長測試文案填不出來」列。
未驗證：方法論檔〈派發語言〉是否另有 slot 值待決條文（未讀，落檔票須補查）。

### 實驗方法

文件牴觸判讀，無程式執行。逐字讀雙方條文與範例（清單見 Problem Analysis〈影響範圍〉），以 grep 查旁證：`grep -rn "封存\|archived" references/`（僅正例一變體列 1 處命中，狀態集／測試契約無封存狀態）；`grep` 方法論 component-library-bidirectional-constraint-methodology.md〈派發語言〉段的「待決／i18n／blockedBy」。

### 實驗執行

- F-16：比對〈共用規則一〉表頭語境（存在必要性檢視：先假設能併，找併不進去的理由）→「外觀不同」列的處置射程是歸併候選；step-3 狀態集列「此狀態的來源是互動瞬態、資料態、還是無」→ 資料態驅動的外觀屬狀態集有條文依據。
- F-18：比對正例三輸入段「已填滿契約的七項元件」→ 待決不在元件契約；step-4 第 1 條主語為「元件契約欄位表」；Troubleshooting 第 3 列主語為「最長測試文案」（元件內容政策欄）；方法論〈派發語言〉段只有「發現缺件時 → 建元件票、設 blockedBy」，無 slot 值待決條文。

### 實驗發現

- 已驗證：F-16 為「條文射程未標 + 範例內部缺狀態」雙缺陷，非單純範例錯；F-18 為「前提未寫 + 『通過』語意未定」，條文與範例在補前提後可並存。
- 已驗證：step-5 與方法論皆無「畫面票 slot 值待決」條文。
- 未驗證：阻擋提示元件的最長測試文案實際來源（正例未填阻擋提示契約表），補前提時須以明文假設寫入。
