### 草稿 A（A-11，需新增判準，未落地）

**位置**：`step-5-write-tickets.md`，接在新增的「非狀態進入情境」段之後（或緊接疊加態段，補為第五條）。

**草稿條文**：

> **巢狀容器**：容器的子件本身為容器時，how 須逐層展開到最深層的葉元件——每一層容器的每個格位都指名到最終落地的葉元件與變體，不得停在中繼容器層即止。資料驅動、筆數不固定的格位以固定寫法「數量依資料筆數」標明，不窮舉逐筆重複結構。

**會改變哪些判定**：現行 how 句型表（〈畫面票〉句型表 how 列）只描述單層寫法「容器 Z 第 N 格放元件 A」，未言明巢狀容器情形；目前唯一的行為依據是範例本身。補上本條後，任何巢狀容器的畫面票 how 若只寫到中繼容器層即明文判定不合格（現況只能靠讀者自行類推範例，條文層面沒有禁止）；「資料驅動格數用固定寫法」也從範例展示的慣例，變成正式禁止窮舉逐筆結構的規則。兩者皆是把既有範例的隱含判準顯性化，不影響目前已存在的落成值，但會讓「只寫到中繼容器層」這種先前條文未禁止、僅範例未鼓勵的寫法，第一次被條文明確排除。

**WRAP 三問**：
- W（候選）：(a) 僅補上述最小陳述；(b) 額外規定巢狀多層時每層是否都要各自標記容器類型。採 (a)，(b) 超出本判定範圍。
- A（機會成本）：低，草稿範圍限於本判定，不擴及其餘判定列。
- P（最可能失敗原因）：「最深層的葉元件」定義在多層巢狀（三層以上）時可能與讀者對「葉」的直覺不一致；已在措辭中明寫「不得停在中繼容器層即止」以降低歧義，但未經第二輪覆核前不視為定案。

### 草稿 B（A-12，需新增判準，未落地）

**位置**：`step-5-write-tickets.md`〈遷移票〉「按 feature 目錄拆票」句後。

**草稿條文**：

> **拆票單位是葉目錄**——該 feature 樹狀結構下不再往下分的最深層目錄，不是頂層目錄；同一頂層目錄下有多個葉目錄時，各葉目錄各自成票，不因共享頂層而合併。目錄本身無子目錄者，該目錄即為葉目錄，一票即可涵蓋。

**會改變哪些判定**：現行「按 feature 目錄拆票」一句未指定層級，可能被讀成「以頂層 feature 目錄為單位」；本票的來源盤點顯示，實際期望行為（葉目錄為單位）目前只在範例的判定表與檢驗問句中出現，條文本身留有歧義空間。補上本條後，任何依頂層目錄拆票（將巢狀多個葉目錄的變更併入同一張票）的既往或未來做法會被明文判定不合格；「無子目錄的目錄本身即為葉目錄」這點若不一併寫入，單層 feature 目錄（如範例中的 `features/settings/`）的判定會有疑義，故草稿一併納入。

**WRAP 三問**：
- W（候選）：(a) 僅補葉目錄定義句（如上）；(b) 另訂巢狀深度上限或遷移票粒度的量化閾值。採 (a)，(b) 沒有既有觸發需求，不無中生有規定閾值。
- A（機會成本）：低。
- P（最可能失敗原因）：與 `foundation-design` skill 或其他處理目錄拆分的 skill 若存在同名但不同定義的「拆票單位」規則，會產生跨 skill 衝突；已用 `git grep` 掃描 `.claude/` 未發現「最深層目錄」「不再往下分」等詞出現在本 skill 與其 CHANGELOG 之外的任何檔案，判定無衝突風險。
