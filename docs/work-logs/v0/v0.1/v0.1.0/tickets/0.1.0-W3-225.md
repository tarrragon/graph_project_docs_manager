## Problem Analysis
### 問題根因

`.claude/skills/ticket/ticket_system/lib/git_ops.py` 的 `_run_git_with_lock_retry`（89-105 行）遇 git 命令失敗時，只在錯誤字串含 `"index.lock"` 才重試（101 行：`while not ok and "index.lock" in err`）。`commit_files_isolated` 的 CAS 步驟（267-269 行）`git update-ref HEAD "$commit_sha" "$old_head"` 在鎖競爭下產生的錯誤文字是 `cannot lock ref 'HEAD': Unable to create '.../refs/heads/main.lock'`（或 `HEAD.lock`），不含子字串 `index.lock`。已用真實 git（非轉述）與正式產出碼各驗證一次（見「重現實驗結果」），確認此條件恆為假：`update-ref` 撞鎖時**一次都不重試**即回傳 `status: failed`，且 `commit_sha` 被丟棄（274 行 `"commit_sha": None`），呼叫端拿不到剛才已建好的 commit-tree 物件 SHA。

219 執行者回報「連續遇 HEAD.lock 與 refs/heads/main.lock 競爭，經 lsof 確認無持有者後手動移除鎖檔並自行 update-ref」，與此程式碼行為完全吻合：工具在第一次撞鎖即失敗，無法重試也無法回報物件 SHA，執行者只能繞出工具外自行完成 CAS。手動 `update-ref` 繞過 `commit_files_isolated` 函式本體，該函式收尾用的 `_sync_shared_index_after_commit`（277 行）只在函式內部成功分支被呼叫——外部手動 `update-ref` 不會、也無法觸發它。共用 index 因此對 `domain-event-modeling.md`／`decision-record-template.md` 兩檔停留在 219 之前的舊內容。

10 分鐘後（17:52:23），222 執行者依規則七流程（精確 `git add` 自己的 ticket md → `git diff --cached --name-only` 核對 → 裸 `git commit`）完成收尾。`bare-commit-guard-hook.py` 的 PreToolUse 記錄顯示，其核對時間點（17:52:16）staged 檔案數確實只有 1 個——此刻 219 尚未手動落地（219 的 HEAD 移動時間是 17:52:22，見 reflog），共用 index 的舊 entry 與當時 HEAD（8ea5e931）一致，核對合法通過。219 的手動 `update-ref` 在核對之後、裸 commit 執行之前的 6 秒窗口內把 HEAD 推進到 `2cd3765a`，222 的裸 `git commit`（committer 時間 17:52:23）沿用未重新整理的共用 index，把兩檔的舊 entry 一併提交，形成 `81517539` 對 219 內容的靜默回滾。

## 重現實驗結果
### 實驗方法

三段式重現，全部在 scratchpad 臨時 repo 執行（不動本專案 working tree）：

1. **原始碼層**：用 raw git 在臨時 repo 對 `refs/heads/main.lock` 與 `.git/HEAD.lock` 分別造鎖，觀察 `git update-ref` 的真實 stderr 文字是否含子字串 `index.lock`。
2. **生產程式碼層**：直接 `import ticket_system.lib.git_ops.commit_files_isolated`（正式模組，非改寫版），在背景執行緒持有 `refs/heads/main.lock` 3 秒（> 工具重試上限的實際等待時間），呼叫真實函式提交一個檔案變更，量測是否重試、結果狀態、耗時。
3. **完整因果鏈層**：模擬「工具因鎖競爭失敗 → 執行者以 `git fsck --unreachable` 找回孤兒 commit-tree 物件並手動 `update-ref` → 共用 index 對該檔停留舊內容 → 另一操作精確 add 別的檔案後裸 commit」全流程，驗證舊內容是否隨裸 commit 回滾。

### 實驗執行

**段 1（原始碼層）**：

```bash
touch .git/refs/heads/main.lock
git update-ref HEAD "$NEWSHA" "$OLD_HEAD"
```

實得 stderr：
```
fatal: update_ref failed for ref 'HEAD': cannot lock ref 'HEAD': Unable to create
'.../repo/.git/refs/heads/main.lock': File exists.
```
`.git/HEAD.lock` 造鎖情境同構，訊息主體相同（皆以 `.../HEAD.lock` 或 `.../refs/heads/main.lock` 結尾）。兩種訊息皆**不含**子字串 `index.lock`。

**段 2（生產程式碼層）**：背景執行緒 `touch refs/heads/main.lock`，等待 0.3 秒後在主執行緒修改 `a.txt` 並呼叫 `commit_files_isolated(["a.txt"], "test: modify a.txt", cwd=REPO)`；背景執行緒於呼叫後 3 秒才移除鎖檔。

實得回傳：
```python
{'status': 'failed', 'commit_sha': None,
 'error': "fatal: update_ref failed for ref 'HEAD': cannot lock ref 'HEAD': "
          "Unable to create '.../refs/heads/main.lock': File exists. ..."}
elapsed = 0.64 s
```
0.64 秒即失敗（鎖檔 3 秒後才釋放），證實 `_run_git_with_lock_retry`（`_MAX_RETRIES=2`、`_RETRY_WAIT_SECONDS=1`）**完全未觸發重試**——若重試邏輯生效，理論上限也僅 1 次額外嘗試、等待 1 秒，仍遠不足以撐過 3 秒鎖，但實得耗時遠低於連 1 秒等待都沒發生，確認重試迴圈的 `while` 條件在第一次失敗即判為 False（`"index.lock" in err` 為 False）而直接返回。

`git fsck --no-reflog --unreachable` 隨後確認函式內部已建好但未被引用的 commit-tree 物件確實存在：
```
unreachable commit e3698facc7a024de8a2b7d2f96933c004df2e67e
```

**段 3（完整因果鏈層）**：
```bash
git update-ref HEAD "$ORPHAN" "$OLD_HEAD"      # 模擬人工繞過，跳過 _sync_shared_index_after_commit
git show :a.txt                                 # → orig-a（共用 index 未同步，停留舊內容）

printf 'new-b\n' > b.txt; git add b.txt
git diff --cached --name-only                   # → a.txt 與 b.txt 皆列出（因 HEAD 已推進，此刻核對「本應」能發現異常）
git commit -qm "chore: modify b.txt only (222-style)"

git show HEAD:a.txt                              # 實得：orig-a（應為 new-a）
```

### 實驗發現

**已驗證的事實**：
1. `update-ref` 的 ref lock 錯誤文字不含子字串 `index.lock`，`_run_git_with_lock_retry` 的重試條件對此類錯誤恆為 False（段 1 + 段 2，原始碼與正式模組雙重驗證）。
2. `commit_files_isolated` 在此條件下於撞鎖瞬間即放棄，不重試、`commit_sha` 遺失，但底層 commit-tree 物件確實已建立且可用 `git fsck --unreachable` 尋回（段 2）。
3. 繞過該函式手動完成 `update-ref` 後，共用 index 對受影響檔案永久停留舊內容，直到被其他操作觸發（無論是否為過期快照）才會浮現；後續一次無關的精確 add + 核對 + 裸 commit 會把該舊內容一併提交，靜默回滾（段 3，端到端重現與正式事件 81517539 的機制一致）。
4. 段 3 的核對步驟（`git diff --cached --name-only`）在本次重現中恰好「抓到」了 a.txt（因為模擬時 HEAD 已先於核對推進）；但在正式事件中，核對發生於 HEAD 推進**之前**（17:52:16 核對，17:52:22 HEAD 才推進），核對當下舊 entry 與當時 HEAD 一致、合法通過——兩者對照證實同一機制在不同時序下，核對步驟有時能攔截、有時不能，取決於核對與 HEAD 推進的相對順序，純屬競態，不是核對邏輯本身有誤。

**仍未驗證的假設**：219 執行者的確切人工操作序列（見 Problem Analysis）。本實驗只驗證「工具行為 + 機制可行性」，不代表 219 執行者的實際操作與本重現逐步相同，但已驗證的機制足以解釋觀測到的全部事實（時間戳落差、staged 檔案數快照、最終回滾內容）。

## Solution
### 結論

三類候選缺陷（工具／路徑／條文）並非互斥的單一根因，而是一條因果鏈：**工具缺陷是根因，路徑缺陷是其必然後果，條文缺陷（含 TOCTOU 縫隙）是在鏈條末端把已產生的過期狀態放行進歷史的最後一環**。裁定如下：

- **工具缺陷（根因，已附程式碼證據）**：`git_ops.py:101` 的 `_run_git_with_lock_retry` 重試條件 `"index.lock" in err` 不匹配 `update-ref` 產生的 ref lock 錯誤文字（`cannot lock ref 'HEAD': ... refs/heads/main.lock` 或 `HEAD.lock`）。已用真實 git（段 1）與正式產出碼 `commit_files_isolated`（段 2）雙重重現：撞鎖瞬間即失敗（0.64 秒），完全未觸發設計中的重試。這不是「重試不夠久」的調校問題，而是重試邏輯對此步驟**從未生效過**。
- **路徑缺陷（直接後果，已附程式碼證據）**：`commit_files_isolated` 失敗分支（270-275 行）丟棄 `commit_sha`，且收尾同步 `_sync_shared_index_after_commit`（277 行）只存在於函式內部成功分支之後——這意味著任何形式的「繞出工具外完成 CAS」（不論是本次的手動 update-ref，或未來任何替代做法）結構上都不可能觸發該同步。219 執行者的應急操作（確認鎖檔無持有者、手動完成 update-ref）在當下是合理反應，問題在工具沒有提供不遺留過期 entry 的正確恢復路徑。
- **條文缺陷／TOCTOU 縫隙（末端環節，已附時間戳證據）**：`bare-commit-guard-hook.py` 於 17:52:16 核對 222 的 staged 範圍，當下共用 index 的過期 entry 與彼時 HEAD（8ea5e931）一致，核對合法通過；219 的手動 `update-ref` 於 17:52:22 才把 HEAD 推進到 `2cd3765a`；222 的裸 commit 於 17:52:23 執行，沿用已核對但未重新驗證的共用 index，把過期 entry 一併提交。這正是 `bash-tool-usage-details.md`「規則七核對步驟的版本邊界」路徑 B 的一次真實命中，該節已有 Action 建議（核對後、commit 前加一道版本比對）,但此建議：(a) 只存在於按需讀取的 details 文件，未反映在自動載入的規則七主文三步驟 checklist；(b) 未涵蓋「若核對與 commit 之間發生等待（含鎖重試），必須重新核對」這個更精確的觸發條件。若無工具缺陷造成的 9 分 47 秒延遲，核對與 commit 的正常間隔應在次秒級，此縫隙命中機率會大幅降低——但縫隙本身的存在與工具缺陷無關，值得獨立補述。

**兩個候選方案（已依此結論收斂，非平行選項）**：

| 方案 | 內容 | 利 | 弊 | 裁定 |
|------|------|-----|-----|------|
| A：只修工具（縮小重試字串比對範圍不足） | 僅擴充 `_run_git_with_lock_retry` 的重試判定 | 修復成本低，直接命中根因 | 不處理「工具重試仍可能耗盡」的殘餘情境（極端高並行度下仍可能撞鎖超過重試上限），屆時仍會走回人工繞過老路，路徑缺陷與 TOCTOU 縫隙仍會復發 | 不採用（單獨） |
| B：工具修復 + 條文補述人工繞過的收尾義務 + 並行期重新核對規則（本票採用） | 修 `_run_git_with_lock_retry` 之外，同時（1）失敗時回報 commit_sha 降低人工尋回成本、(2) 條文明訂繞過後必須執行收尾清理、(3) 條文明訂並行期核對後有等待須重新核對 | 根因與殘餘風險（工具仍可能失敗）皆有對策；不需新增 hook 強制層即可縮小視窗 | 條文類補述仍依賴執行者記憶遵守，非機制強制；若未來證實仍高頻復發，需再評估 hook 強制層（非本票範圍，留待復發時另開票） | 採用 |

**TOCTOU 縫隙裁定**：**補條文，不新增 hook 強制層**。理由：(1) 視窗大小主要由工具缺陷造成的延遲決定，工具修復後視窗預期回到次秒級，剩餘風險的成本效益不足以支撐新增 hook 機制的複雜度；(2) `bare-commit-guard-hook.py` 自身文件已明示其防護標的是「範圍過寬」而非「內容過舊」，擴大其職責範圍會模糊既有 hook 的設計邊界；(3) 現有「版本邊界」小節的 Action 建議已提供正確的人工核對手法，缺口是「未被主文 checklist 收錄」與「未明確要求重新核對的觸發條件」，補條文即可彌補，不需疊加新機制。
