## Problem Analysis
### 問題根因

`.claude/skills/ticket/ticket_system/lib/git_ops.py` 的 `_run_git_with_lock_retry`（89-105 行）遇 git 命令失敗時，只在錯誤字串含 `"index.lock"` 才重試（101 行：`while not ok and "index.lock" in err`）。`commit_files_isolated` 的 CAS 步驟（267-269 行）`git update-ref HEAD "$commit_sha" "$old_head"` 在鎖競爭下產生的錯誤文字是 `cannot lock ref 'HEAD': Unable to create '.../refs/heads/main.lock'`（或 `HEAD.lock`），不含子字串 `index.lock`。已用真實 git（非轉述）與正式產出碼各驗證一次（見「重現實驗結果」），確認此條件恆為假：`update-ref` 撞鎖時**一次都不重試**即回傳 `status: failed`，且 `commit_sha` 被丟棄（274 行 `"commit_sha": None`），呼叫端拿不到剛才已建好的 commit-tree 物件 SHA。

219 執行者回報「連續遇 HEAD.lock 與 refs/heads/main.lock 競爭，經 lsof 確認無持有者後手動移除鎖檔並自行 update-ref」，與此程式碼行為完全吻合：工具在第一次撞鎖即失敗，無法重試也無法回報物件 SHA，執行者只能繞出工具外自行完成 CAS。手動 `update-ref` 繞過 `commit_files_isolated` 函式本體，該函式收尾用的 `_sync_shared_index_after_commit`（277 行）只在函式內部成功分支被呼叫——外部手動 `update-ref` 不會、也無法觸發它。共用 index 因此對 `domain-event-modeling.md`／`decision-record-template.md` 兩檔停留在 219 之前的舊內容。

10 分鐘後（17:52:23），222 執行者依規則七流程（精確 `git add` 自己的 ticket md → `git diff --cached --name-only` 核對 → 裸 `git commit`）完成收尾。`bare-commit-guard-hook.py` 的 PreToolUse 記錄顯示，其核對時間點（17:52:16）staged 檔案數確實只有 1 個——此刻 219 尚未手動落地（219 的 HEAD 移動時間是 17:52:22，見 reflog），共用 index 的舊 entry 與當時 HEAD（8ea5e931）一致，核對合法通過。219 的手動 `update-ref` 在核對之後、裸 commit 執行之前的 6 秒窗口內把 HEAD 推進到 `2cd3765a`，222 的裸 `git commit`（committer 時間 17:52:23）沿用未重新整理的共用 index，把兩檔的舊 entry 一併提交，形成 `81517539` 對 219 內容的靜默回滾。

### 影響範圍

**已驗證的事實**：
- `git_ops.py:101` 的 `"index.lock" in err` 條件不匹配 `update-ref` 產生的 ref lock 錯誤文字（regel七詳細與程式碼皆已用真實 git 重現，見下節）。
- `commit_files_isolated` 於 update-ref 失敗分支（270-275 行）不重試、不回報 `commit_sha`、不呼叫收尾同步（277 行僅存在於成功分支之後）。
- 2cd3765a 的 author/committer 時間戳為 17:42:35（`git cat-file -p` 已驗證），但依 `git log -g` reflog，HEAD 實際指向該 commit 的時間是 17:52:22——中間 9 分 47 秒的落差，與「commit-tree 物件已建好、update-ref 失敗、稍後才手動補上」的機制一致。
- `bare-commit-guard-hook.py` 的 `.claude/hook-logs/bare-commit-guard/bare-commit-guard-20260909.log` 第 6375-6377 行顯示 17:52:16 該次核對 staged 檔案數=1，放行；81517539 實際變更 3 檔（含回滾 2 檔），committer 時間 17:52:23——與 219 手動 HEAD 推進時間（17:52:22）僅差 1 秒，構成規則七詳細已記載的「核對步驟的版本邊界：過期 index 快照」路徑 B 的一次真實命中。

**仍未驗證的假設**：
- 219 執行者「lsof 確認無持有者後手動移除鎖檔」的確切操作序列（本票僅能從其回報文字與物件時間戳交叉驗證機制吻合，無法取得該 session 的逐字操作記錄）。
- 是否有其他 4 名並行代理人的提交也撞上同一批鎖競爭但未觸發後續回滾（無反例證據，但也未逐一排查其 commit 內容）。

**受影響檔案（.claude/ 框架資產，非本專案專屬）**：
