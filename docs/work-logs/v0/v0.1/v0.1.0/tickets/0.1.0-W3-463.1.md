## Problem Analysis
### 問題根因

W3-463 將 TDD-21b、TDD-29b 兩項歸為「條文全域查無優先序，需新判準」。本票複核後，兩項的直接原因都不是判準缺席，是**既有權威句與消費句之間缺一條路由**：

| 項 | 既有權威（非範例，`git grep -F` 命中） | 缺的是什麼 |
|---|---|---|
| TDD-21b | 〈版本號分配規則〉引言句「確保依賴關係正確」；〈架構層級執行順序〉表說明欄逐列寫明該層的依賴（「依賴 Domain」「依賴 Application」等）；〈並行判斷〉表「有 blockedBy / 否」 | 未寫明架構層級表是分配原則在說明欄依賴成立時的結果，說明欄不符時回到分配原則 |
| TDD-29b | `.claude/rules/core/observability-rules.md` 規則 1 表首句「每個 catch 區塊必須滿足以下至少一項，否則需附註說明原因」；`quality-baseline.md` 規則 4 擴充「只做 `return`/`pass` 時在註解說明」 | Q5 句中「catch 後回傳預設值者記 warning」射程未限定在「任一項不成立」分支；Q5 引用的是規則 1 的空 catch 列，回傳預設值的 catch 不是空 catch，引錯列 |

## 重現實驗結果
### 實驗方法

條文推導實驗（本票為條文判準分析，無可執行程式）：以 HEAD c87672098 的條文為唯一依據，把 W3-463 草稿各方向代入三類輸入推導，檢查是否與同節其他正文矛盾。三類輸入：(1) 探針題目的結構；(2) 與探針不同構的輸入；(3) 反向輸入（草稿方向的失效情境）。引文皆以 `git grep -F` 確認非範例。

### 實驗執行

**TDD-21b**

| 輸入 | 方向 B（架構層級表優先） | 草稿方向 A（依賴優先、取較晚者） | 一律依分配原則 |
|---|---|---|---|
| 探針結構：Infrastructure 任務直接依賴另一個第二批任務 | 兩者同為第二批 -> 〈並行判斷〉「同一批次 / 是」與「有 blockedBy / 否」同時命中，**同節自相矛盾** | 第三批，無矛盾 | 第三批，無矛盾 |
| 不同構：Presentation 元件只直接依賴 Domain 值物件，未依賴任何 Application 任務 | 第三批 | 取較晚者 -> 第三批；但分配原則「依賴前一批 / 下一個批次」逐字推出第二批，「較晚者」是分配原則沒有的 max 規則 | 第二批；與〈並行判斷〉「不同架構層但無依賴 / 是」一致 |
| 依賴與說明欄一致：UseCase 只直接依賴 Domain 任務 | 第二批 | 第二批 | 第二批（兩表同解，無需偏離） |

**TDD-29b**

| 讀法 | 對探針情境（三項成立、catch 回傳預設值）的結論 | 與權威句比對 |
|---|---|---|
| 讀法 1：「catch 後回傳預設值者記 warning」無條件 | 不可靜默 | 比規則 1 表首句「否則需附註說明原因」與 quality-baseline 規則 4「只做 `return`/`pass` 時在註解說明」更嚴，且條文未寫加嚴理由 |
| 讀法 2：該子句只屬「任一項不成立即選日誌」分支 | 可靜默，附註解 | 與規則 1 表首句一致；與 tdd CHANGELOG 2.10.1 所記意圖「消解與該規則的潛在衝突」一致 |

另查：Q5 句尾路由引的是規則 1「空 catch」列（「禁止，必須加日誌或在註解中說明靜默原因」），而探針情境的 catch 有回傳值、不是空 catch，讀者依引文找到的列與情境不符，須自行跳到表首句才能消解。

### 實驗發現

已驗證的事實：
- 21b 方向 B 使〈並行判斷〉表同節矛盾，被既有正文排除；只剩依賴優先一種自洽讀法，故屬路由而非新判準。
- 21b 草稿方向 A 的「以較晚者為準」在反向輸入下偏離分配原則逐字結果，本身是新判準，應刪去。
- 29b 規則 1 表首句已提供「附註說明原因」的出口，兩份規則在交集情境不衝突；衝突感來自 Q5 的子句射程與引錯列。

仍未驗證的假設：
- 修補後探針重跑能通過（待落檔後依 W3-417 處置重跑）。
- 「Presentation 元件可早於 Application 批次」是否符合用戶的派發習慣（見 Solution 用戶偏好標註）。
