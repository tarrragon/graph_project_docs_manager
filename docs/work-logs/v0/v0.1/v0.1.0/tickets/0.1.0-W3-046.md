### 現成修法（flutter_balance 提供，該側已在用且經固定值驗證）

該側 `.gitignore` 的對應三行：

```gitignore
*.lock
!uv.lock
!**/uv.lock
```

**採 blanket `*.lock` 後白名單合法 lock**，其註解逐字為「避免誤傷各 skill 的
uv.lock ／ pubspec.lock ／ Podfile.lock」。

**該側固定值**：`git ls-files` 對 `.claude/scripts/uv.lock` 與各 skill 的 uv.lock
共 9 個皆追蹤；`git check-ignore -v .claude/scripts/uv.lock` 不命中。

**與本專案寫法的差別**：本側是 `.claude/**/*.lock`（以路徑範圍 + 副檔名分類），
該側是全域 `*.lock` + 白名單（以副檔名分類但用白名單救回用途）。**後者的分類軸仍是
副檔名，但白名單使「用途」這個維度顯性化**，且新增合法 lock 時只需加一行白名單，
不需重新設計 pattern。

**本專案另須注意**：本側除 `.claude/scripts/uv.lock` 外，各 skill 目錄下也可能有 uv.lock，
且本專案為 Flutter，另有 `pubspec.lock`／`Podfile.lock` 需納入白名單——後兩者目前由
`.gitignore` 第 7-8、58-60 行逐檔列舉處理，改用白名單形式後那幾行可一併收斂。

**此修法可直接作為 framework issue #57 的修法建議**（該 issue 記「uv.lock 未納版控」而
未給機制與修法）。

### 修法與驗證（PM 前台執行，commit `05a5180a`）

**執行者為 PM 而非代理人**：`.gitignore` 是 `pm-role.md` 明列的 PM 可寫路徑；派發路徑被兩道
hook 連續擋下（實作代理人須 worktree 隔離 → worktree 須先 `git push origin main`），而本地
main 領先 origin/main **353 個 commit**，該推送屬使用者未授權的對外動作。改由 PM 直接執行，
非繞過守衛。

**修法**（形式取自 flutter_balance 已在用且經固定值驗證的寫法）：

```gitignore
.claude/**/*.lock
!.claude/**/uv.lock
```

**驗證以 `git check-ignore` 的行為為準，不驗 pattern 字面**：

| acceptance | 驗法 | 結果 |
|-----------|------|------|
| 1 uv.lock 納版控 | `git check-ignore -q` 對 `scripts/uv.lock`、`skills/ticket/uv.lock` | 兩者**未忽略**，PASS |
| 2 執行期鎖檔仍忽略 | 同上，對 `dispatch-active.lock`／`scheduled_tasks.lock`／`.allocator.lock`／巢狀 `a/b/c.lock` | 四者**仍忽略**，PASS |
| 3 行為測試通過 | `pytest test_save_ticket_race.py` | **7 passed** |

### 附帶查明：這顆地雷為何能潛伏

全庫 10 個 `uv.lock` 中，**只有 `.claude/scripts/uv.lock` 先前未追蹤**，其餘 9 個早已在
index 裡——**gitignore 不影響已追蹤檔案**，故那條規則只咬到唯一一個在規則之後才新增的檔
（08-28 由另一 consumer 推上）。9/10 正常運作，因此無人察覺。

**一條錯的忽略規則，命中率取決於它寫下的時間點**——寫得越晚，被它咬到的既有檔案越少，
也就越不容易被發現。這使「規則寫下時全庫掃一次」成為必要動作而非可選。

### 本票重新推導了一個已存在的 error-pattern

`PC-APP-006`（`.gitignore` 排除測試 fixture 導致新環境測試失敗）與本票**機制完全相同**：

| 項目 | PC-APP-006 | 本票 |
|------|-----------|------|
| 症狀 | `sync-push --clean` 報告孤兒檔（本地存在但遠端已刪除） | 同 |
| 診斷指令 | `git check-ignore -v`＋`git ls-files --error-unmatch` | **同兩條** |
| 核心區分 | **靜態 fixture（需追蹤）vs runtime 產物（應排除）** | **依賴鎖定檔（需追蹤）vs 執行期鎖檔（應排除）** |

**該 pattern 早已存在，而本 session 花了三個根因版本才推導出同一件事。**

**它沒被找到的原因是 scoping**：標題與辨識訊號都限定在測試 fixture
（訊號表逐字寫「`sync-push` 報告孤兒檔在 `tests/fixtures/`」），而機制本身與 fixture 無關。
查 `uv.lock`／孤兒／`--clean` 都不會撞到一個叫「測試 fixture」的 pattern。

**`error-pattern 衝突檢查` hook 確實列出了它**——但那個檢查在 `complete` 時觸發（工作已做完），
且一次列出 44 個 pattern 未排序。它證實 pattern 在庫裡，不證實它在需要時找得到。

**處置**：另立票將 `PC-APP-006` 泛化——標題與辨識訊號由「測試 fixture」擴為
「被忽略卻需要被追蹤的檔案」，並把本票的鎖檔案例與 `--clean` 誤刪的後果補為第二實例。
