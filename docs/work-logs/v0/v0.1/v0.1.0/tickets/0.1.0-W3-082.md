### 問題根因（更正票面 why 段描述）

實測確認：真實機制不是「靜默濾除該項」，而是 `_parse_where_path_entries` 的
`all(_looks_like_path(item) for item in entries)` 全有全無判定——只要清單中有
一項不符合路徑判定，整份清單就整體回傳 None、僅寫入 layer 描述、files 完全
不同步（不是逐項濾除單一項，是整批退回）。這與 PM 派發前定位的候選假設一致。

根本原因在 `_looks_like_path`：舊實作要求每個項目必須「含 `/`」才可能被判為
路徑，`CLAUDE.md` 這類無目錄前綴的根層檔名因此無論副檔名為何都直接判 False，
導致整份清單（若含此類根層檔名）判定失敗、files 不更新。

最小重現（`uv run --directory .claude/skills/ticket python3 -c "..."`）：
- `_looks_like_path('CLAUDE.md')` → False（修復前）
- `_parse_where_path_entries('a/b.py,CLAUDE.md,c/d.py')` → None（修復前，整批退回）
- `_parse_where_path_entries('CLAUDE.md,a/b.py,c/d.py')` → None（修復前，位置不影響結果）

### 修復方式

`_looks_like_path`（`ticket_system/commands/fields.py`）新增無斜線分支：
無 `/` 的根層項目改用「副檔名 AND repo 內實際存在」雙條件（而非有斜線分支
的 or 邏輯），兩者皆須成立才判為路徑——單看副檔名不足以判定（`v1.0`、`N/A`
之類的描述文字也可能含句點），額外要求存在性可避免描述型輸入重新落入
files（延續既有 docstring 記載的反向事故防線）。

`_exists_in_repo` 補上呼叫 `file_conflict.parse_file_intent` 剝離
`::read`/`::write` 讀寫意圖後綴後才查詢檔案系統，否則 `CLAUDE.md::read`
這類帶標記的根層項目會因為 repo 內不存在字面上帶 `::read` 的檔案而誤判
不存在。

`execute_set_field` 的 CLI 回顯：非路徑型輸入（`synced_files is None`）且
欄位為 `where` 時，額外印出 `existing.get("files", [])` 的實際值與筆數，
使「files 完全未同步」這件事對呼叫者可見，不再需要另跑 `ticket track where`
才能發現差異（acceptance 第 2 項）。

### Task Reference

修復 `ticket track set-where` 的路徑判定，使專案根層的無斜線檔名能進入 `where.files`，
並讓判定失敗對呼叫者可見。

### Rationale Chain

`dispatch-readiness` 的檢查 6（acceptance 提及路徑涵蓋性）是**強制 fail** 項，比對的是
`where.files`。當 acceptance 提及一個根層檔名、而該檔名進不了 `files` 時，合法票被硬擋，
且擋下的理由（「請把該路徑加進 where.files」）指向一個做不到的動作——使用者照做仍失敗，
因為 `set-where` 收下字串卻不寫入。

失敗是靜默的：`set-where` 的回顯取自 `where.layer`（保存完整傳入字串），使用者看到的是
「已更新」加上完整路徑清單，而 `files` 可能一項未變。要發現差異必須另跑 `ticket track where`
逐項比對——沒有理由這麼做的人不會做。

### Related Files

- `.claude/skills/ticket/ticket_system/commands/fields.py` — `_parse_where_path_entries`
  與 `_looks_like_path` 的判定所在；`_sync_where_files` 為呼叫點
- `.claude/skills/ticket/ticket_system/tests/test_fields_set_where.py` — 既有測試

### 既有設計約束（修復不得破壞）

`fields.py` 的 docstring 記載一次反向事故：舊判定只看「含 `/`」，導致架構層級描述
（`Presentation/UI`、`Domain/Application layer`、`N/A`、`framework/.claude`）被誤判為路徑，
結果 `layer` 寫不進去、描述文字進了 `files`，污染 dispatch hook 的 scope 判定。
現行三條件（不含空白、含 `/`、看起來像檔案系統路徑）是該事故的修補。

**放寬根層檔名時必須同時保住這個性質**：不能讓 `N/A` 之類的描述重新落入 `files`。
驗收要求的三種組合測試（根層檔名／`::read` 標記／目錄路徑）之外，建議補一組
「描述型輸入仍被正確判為非路徑」的迴歸測試，證明修補未回退。
