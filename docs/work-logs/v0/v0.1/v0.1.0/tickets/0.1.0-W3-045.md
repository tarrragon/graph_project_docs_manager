### 形態與命名定案（2026-09-07）

**形態：兩支各自成家，不合併。** 採納 flutter_balance 的理由——「兩支各一個 hook 顯得零碎」
不是成本，**零碎正是那個不變式的形狀**（發佈庫七支帶 hooks 的 skill，每支的 hook 都只服務
自己的主題）。合成一支「專案規範 skill」會再造一個承載兩個主題的 skill，與被刪的那支同構。

| 檔 | 落點 | 依據 |
|----|------|------|
| `worklog-format-check.py` | **併入既有 `doc-flow`**，成為其 `hooks/` 的第一支 | 本側查證：`doc-flow` 的 description 明寫管 worklog 與 documentation consistency checks，正文提及 work-log 四次，且目前**無 `hooks/` 目錄**。主題相符，滿足七比零不變式 |
| `comment-qa-hook.py` | **獨立成家，命名 `dart-comment-traceability`** | 依既有 `dart-style-guardian`／`dart-test-async-guardian` 的 `dart-` 前綴慣例 |

**不選 `doc` skill**：該 skill 的主題是需求追蹤文件（PROP／SPEC／UC），與 worklog 格式無關。
本側同時存在 `doc` 與 `doc-flow` 兩支，前者管需求文件、後者管專案文件系統（CHANGELOG／
worklog／ticket／error-pattern／todolist），worklog 屬後者。

### 遷移時發現的既有 bug（兩個 consumer 皆有）

`comment-qa-hook.py` 的 `save_report()` 呼叫 `log_message(msg)` 單引數，而
`log_message(logger, message)` 要求兩個必要參數——**每一次報告生成路徑都拋 `TypeError`**。
同一呼叫慣例出現在六個從未持有 logger 參照的輔助函式。

**它只在「沒有東西要報告」時看起來正常。** 本專案的修法為 `log_message()` 相容兩種
呼叫慣例，已隨 canonical 上去；flutter_balance 的副本超出本專案寫入範圍，已通知。

**這回頭改變了廢除方正式意見的一個前提。** 該意見稱「兩支都沒有已知缺陷，你們還在跑
不是問題」——那句在其環境為真，因為 `comment-qa-hook` 對他們**目標集合為空**，永遠走不到
報告生成路徑，也就永遠碰不到該 `TypeError`。**「無已知缺陷」與「在我的環境不會觸發」
在那句話裡是同一個表述。**

推論：三選一規則的第三項（寫出缺陷）有一個前置——**寫得出缺陷的前提是跑得到那條路徑**。
已回饋該側評估是否為該項加限定語。
