### 候選方案與裁定

五項結論的完整內容見 `docs/tech-decisions.md`〈2026-09-10：加入編輯能力 tripwire 的重評——四項規定重評與一項補列〉，此處只記兩項經 WRAP 框架裁定的方案比較（用戶明示這兩項以 WRAP 決策，第三項另立票）。

**一、備份形態**

| 候選 | 取捨 | 裁定 |
|---|---|---|
| 帶未提交編輯與非 git 工作區一律阻擋寫入（首版） | 保證使用者知道有東西可能遺失；但把「不用 git 的使用者能否編輯」定為不能，且該產品決定被藏在一條安全規則下 | 不採 |
| `git hash-object -w` 快照後放行 + 非 git 工作區改工作區能力層唯讀降級 | 持有者仍為使用者自己的 git，App 只留 SHA；實測不動 index／HEAD／refs／stash／reflog | **採** |
| 只收一半（非 git 改降級，未提交編輯仍阻擋） | 機制數最低 | 不採 |

裁定依據三項，前兩項為首版未做的功課：(1) 基本率——同類桌面編輯器保護未提交資料的常見形態是 local history 或 autosave 版本，「阻擋寫入直到使用者提交」幾乎無人採用，而首版的阻擋不是比較後選出的；(2) 快照不違反總約束，且 SHA 是識別符不是內容，與「只記識別」同形；(3) 悖論檢查——阻擋違反了更上位的目的（本 App 的存在是讓使用者更容易維護文件），用下位原則的字面壓過上位目的。

P 階段的三項失敗預想已寫入結論本身而非留在票內：兩週 gc 窗口須明寫且禁用「備份」一詞、快照須有可見回饋與取回說明路徑否則是裝飾、`hash-object` 失敗即退回阻擋不得靜默放行。

**二、變更記錄載體**

W 階段的反向思考觸發重跑：相反論述「記錄應該落地」有力（最需要記錄的時刻是崩潰時，正是 session 內畫面必然消失的時刻），依品質檢查須重新定義問題。重新定義後發現二元為假——「即時確認」與「事後追溯」是兩個不同情境，需求不同。**裁定兩者皆做**：即時確認走 session 內回饋，事後追溯走 App 提供（非自動執行）的提交動作。

**三、組織方式**

首版宣稱五項皆由單一原則推得，該宣稱被同節下方五個 Why 段落中的三個直接否證。改以作用時點分軸（寫入前閘門／寫入後義務／橫切約束），並指名總約束的實際射程。此項非措辭修正——錯誤的分組軸會使下一次 tripwire 觸發時的重估範圍算錯，且會讓一條假的推論鏈擋住正當的窄修改。
