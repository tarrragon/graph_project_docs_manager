## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### how 欄與 SPEC 比對結果

比對 SPEC-001 §1「無可消費的型別表」列與 SPEC-003 §3.1：措辭為「以 App
內建型別表檢視（僅在 .claude/VERSION 值不高於 App 內建型別表的產生版本時
提供；高於時不渲染該動作，只剩切換專案）」。原 how 欄描述與此一致，未發現
落後規格之處，故無須調整實作方向。

### 問題根因

`domain_view_screen.dart` 的 `_builtinSchemaVersion = '2.40.3'` 為寫死
常數，未對應任何實際內嵌資產；本 repo 自身 `.claude/VERSION`（2.60.1）
已高於該常數，但既有測試僅用 '0.0.3'／'9.99.9' 兩個遠離門檻的 fixture
值，未覆蓋「以真實 VERSION 驅動」的情境，掩蓋了降級出口在 HEAD 已不可達
的事實。

### 影響範圍

- lib/screens/domain_view/domain_view_schema_version.dart（新增：資產讀取
  provider + 版本比較 + 漂移偵測純函式）
- assets/schema/builtin_schema_version.json（新增：內嵌資產，欄位複製自
  .claude/skills/doc/doc_system/core/tracking_schema.json 的
  schema_generated_at_framework_version）
- pubspec.yaml（新增 flutter.assets 宣告）
- test/unit/screens/domain_view_test.dart（新增以真實 .claude/VERSION
  驅動的案例）
- test/unit/screens/domain_view_schema_drift_test.dart（新增：漂移偵測）

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修復方式

兩段落地：

1. 建立內嵌資產 `assets/schema/builtin_schema_version.json`（欄位
   `schema_generated_at_framework_version` 複製自
   `.claude/skills/doc/doc_system/core/tracking_schema.json` 同名欄位，
   現值 2.40.3，與原寫死常數一致，證實原常數並非隨意杜撰，而是漏了
   把它固化為可驗證資產），透過 `pubspec.yaml` 的 `flutter.assets`
   宣告內嵌進 build。新增
   `lib/screens/domain_view/domain_view_schema_version.dart`：
   - `builtinSchemaVersionProvider`（`FutureProvider<String>`）於執行期
     以 `rootBundle.loadString(..., cache: false)` 讀取該資產。
   - `isHigherThanBuiltinSchemaVersion`：由 `domain_view_screen.dart`
     搬出的既有比較邏輯（逐段整數比較，語意不變）。
   - `domain_view_screen.dart` 的 `_SchemaUnconsumableView` 改為
     `ref.watch(builtinSchemaVersionProvider)`，資產載入中或失敗時安全
     預設 `canDegrade = false`（呼應既有「不確定時不自動降級」精神）。

2. 漂移偵測：新增純函式 `schemaVersionMinorDrift`／
   `isBuiltinSchemaVersionDrifted`（比較 `.claude/VERSION` 與資產版本的
   次版號差距），門檻 `kSchemaVersionDriftThreshold = 25`（現行實際漂移
   為 20，留 5 版餘裕）。承擔者：下一位執行涉及
   `domain_view_schema_version.dart` 或
   `assets/schema/builtin_schema_version.json` 的 IMP ticket 之
   parsley-flutter-developer；偵測機制為
   `test/unit/screens/domain_view_schema_drift_test.dart` 內以真實
   `.claude/VERSION` 驅動的門檻測試，超過門檻時該測試轉紅、CI 卡關，
   非無 trigger 的待觀察（decision-trigger-binding 規則 1／2.5）。

### 實作過程中的技術障礙與修正

`rootBundle.loadString` 預設 `cache: true` 時，在 `flutter test` 環境下
第一個測試觸發的 Future 若未被完整等待（多數 widget 測試不需要該值即可
通過），其快取的 Future 物件會被同進程後續測試重用，但該 Future 可能
永久卡在未完成狀態（實測重現：第二個測試 `AsyncLoading` 永不轉
`AsyncData`，`await provider.future` 掛起不回）。改用
`rootBundle.loadString(path, cache: false)` 讓每次呼叫各自獨立完成，
解決此問題；成本可忽略（本機小型資產檔）。

### 自檢結果

- Package 導入：新檔均用 `package:` 完整路徑（測試檔）或相對路徑（lib 內
  同目錄，符合既有慣例）。
- 函式行數：新增純函式均在 10 行內，單一職責。
- 需求註解：`domain_view_schema_version.dart` 檔頭含 SPEC 引用與承擔者／
  門檻說明。
- 錯誤處理：資產載入失敗或進行中皆走安全預設（`canDegrade = false`），
  不拋出未攔截例外。
- 未修改 `lib/components/`、`lib/app/`，符合派發約束。

### Phase 4 結論

品質：A。重構需要：否。技術債務：無新增（原常數缺乏資產背書的技術債務
已由本票清償；`kSchemaVersionDriftThreshold` 門檻本身是新增的維護點，
但已依 decision-trigger-binding 規則 2.5 指名承擔者與偵測機制，非隱性
債務）。結論：現行實作已達成本票 acceptance，不需進一步重構。
