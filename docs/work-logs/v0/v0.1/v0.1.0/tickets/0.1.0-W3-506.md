# Execution Log

## Task Summary

分析 release 後狀態由 blockedBy 欄位非空決定而非由 blocker 是否完成決定，使票從 runqueue 靜默消失

---

## Problem Analysis
### 問題根因

`release` 把「衍生狀態」寫成持久欄位，而它計算該狀態時只讀 `blockedBy` 的**字面非空性**，不查 blocker 的實際狀態。

寫入點：`.claude/skills/ticket/ticket_system/commands/lifecycle.py` 的 `TicketLifecycle.release()`，註記為 W3-082 的三行——`blocked_by = ticket.get("blockedBy") or []` 後 `target_status = STATUS_BLOCKED if blocked_by else STATUS_PENDING`，隨即 `ticket["status"] = target_status` 落盤。同一檔案在 import 區已引入共用 predicate `is_fully_unblocked`，並在 `_can_cascade_unblock`、`_reverse_unblock_blockedby` 與 dispatch 判定三處呼叫它；`release()` 是唯一一處在同檔內放著該 predicate 不用、改以字面判定的地方。

讀取端：`.claude/skills/ticket/ticket_system/commands/track_runqueue.py` 的 `_is_unblocked_pending`。它對兩個軸的信任度不對稱——

| 軸 | 判定方式 |
|----|---------|
| `status` | 字面比對 `!= "pending"` 即排除（守衛在最前，先於任何重算） |
| `blockedBy` | 呼叫 `is_fully_unblocked(..., include_closed_as_resolved=True)` 動態重算 |

W1-020 為 `blockedBy` 軸補的重算，被 `status` 軸的字面守衛擋在門外：一張 `status=blocked` 的票在重算發生前就已被排除，blocker 是否已解除完全不被查詢。

兩端合起來即本案的失效鏈：`release` 用過期字面寫出一個錯的 `status`，`runqueue` 對 `status` 不重算，於是這個錯值成為唯一權威。

### 與 framework issue #30 既有裁決的關係（本案的判準來源）

`tarrragon/claude#30` 於 2026-08-04 關閉時明文裁定：**維持讀取端動態判定，不做寫入端 blockedBy 清除**；理由是「`blockedBy` 欄位語意為靜態依賴宣告，有效性由查詢時動態判定，此為設計而非缺口」，並保留依賴歷史的 audit 價值。

該裁決成立的前提是「所有消費端都在讀取時重算」。`release()` 違反這個前提：它是一個**寫入端**消費者，把靜態宣告直接固化成持久狀態欄位。固化之後，該值就不再是任何人會重算的東西——`status` 恰恰是全系統唯一被當作字面真相消費的欄位。

本案因此不是 #30 的重複，而是 #30 裁決的反例：裁決本身在讀取端仍成立，缺的是「靜態宣告不得被寫入端固化」這條配套約束。

### PM 實測（列為既有事實，來源為 PM，本票未重跑）

1. `blockedBy=[0.1.0-W3-494]` 且該 blocker 已 completed 時，`release` 後 status 為 `blocked`，runqueue grep 命中 0
2. 全量掃描 0.1.0 全部票：status=blocked 共 2 張，其中 blocker 已全部完成者 1 張（標本 `0.1.0-W3-495`）
3. `set-blocked-by ... --remove` 清空 blockedBy 後，status 仍為 blocked、runqueue 仍不列——status 是持久欄位，`set-blocked-by` 不重算
4. `ticket track` 子命令清單無 `set-status`；直接 Read／Edit ticket md 被 hook 硬擋

本票對第 1、3 兩項以隔離實驗獨立複現（見下一章節），對第 2、4 項沿用 PM 結果未重跑。

### 標本時序（本票以 git 歷史重建，修正派發時的假設）

派發時的時序假設為「標本在 blocker 完成當下正處 in_progress」。git 歷史顯示**不是**：

| 時刻 | 事件 | 標本 status |
|------|------|------------|
| 12:19 | 標本建立，`blockedBy: [0.1.0-W3-494]` | pending |
| 12:41:53 | blocker `0.1.0-W3-494` completed | pending |
| 13:04:31 | 標本 claim | in_progress |
| ~13:15 | 標本 release | blocked |

blocker 完成當下標本是 **pending**，不是 in_progress。差別是實質的：`_classify_child` 對 pending 與 in_progress 都回傳 `in_progress_warning`（只警告、不改動、不清 `blockedBy`），`_reverse_unblock_blockedby` 對兩者都因 `status != blocked` 而跳過。也就是說，無論當時是 pending 還是 in_progress，cascade 都不會處理它——問題不在「錯過了一個時間窗」，而在 cascade 的射程從設計上就不含非 blocked 的下游，因此那個過期的 `blockedBy` 條目必然留存，成為往後任何一次 `release` 的地雷。

### 現有測試對本案無鑑別力

`tests/test_release_status_semantics.py::test_nonempty_blocked_by_returns_blocked` 斷言「`blockedBy=["0.0.0-W0-DEP"]` → blocked」，但 fixture 從未建立 `0.0.0-W0-DEP` 這張票。缺席的 blocker 在 `is_fully_unblocked` 下本就判為未解除，因此該測試在「blocker 已解除」與「blocker 未解除」兩種情形下輸出相同——對本案這一軸完全沒有翻紅能力。這正是 `test-assertion-design-rules` E1（明示旗標必須有對照測試）所述形態：只有單邊斷言，沒有會產生差異的對照 fixture。

同一事實的另一面是：修法不會被這個測試擋住——把 `release` 改為呼叫 `is_fully_unblocked` 後，該測試仍會通過。

### 相關 Error Pattern

執行 `grep` 掃描 `.claude/error-patterns/` 後，最接近的是 `architecture/ARCH-BAL-018-snapshot-correctness-inverts-when-source-reaches-terminal-state.md`（快照／衍生欄位的正確性定義隨消費端生命週期改變）。

**同**：都是「來源資料被反正規化為衍生欄位後，欄位與來源脫節」。
**異**：ARCH-BAL-018 的核心是兩種正確性定義互斥（終態端應保留存證、待執行端應同步現值），因此不存在單一正確的同步策略。本案沒有這個互斥——`status` 在任何時刻都只有一個正確值，缺口單純是一個寫入端用過期字面算出它，而所有讀取端都假定它已被正確算出。

本案尚無完全對應的既有 pattern。是否新增 error-pattern 列入下方 Spawn 規劃交 PM 裁決。

### 實驗發現

**已驗證的事實**

1. `release` 在 blocker 已 completed 時仍寫 `blocked`（A1）。PM 實測第 1 項於隔離環境獨立複現，排除現場資料特殊性。
2. `status=blocked` **有**合法離開路徑：`claim` 接受 blocked 態並轉為 `in_progress`（A3）。`validate_claimable_status` 的 docstring 明寫「blocked: 可認領（需要重新開始）」，guard clause 只擋 in_progress 與 completed。無任何 hook 攔截此路徑。
3. 該離開路徑會被同一缺陷再次吸收：`claim` 之後若再 `release`，因 `blockedBy` 字面未變而回到 `blocked`（A4）。離開路徑只有一條且單向——必須一路走到 `complete`。
4. `release` 對已是 blocked 的票直接拒絕（A2），而 `lib/precondition.py` 對 blocked 態的建議動作正是 `release`。這條建議指向一個會拒絕它的命令，形成封閉迴圈。
5. runqueue 的 `status` 軸為字面比對，先於 `blockedBy` 軸的動態重算（A5）：同一組 `blockedBy`，status 為 `blocked` 判 `False`、為 `pending` 判 `True`。差別只在 status 欄位本身。
6. `complete` 的下游重算射程只含 `status=blocked` 的下游（B1／B2／B4，對照組 B3／B5）。pending 與 in_progress 下游一律只發警告。
7. **兩條 cascade 都不清 `blockedBy`**，連被成功解鎖的 blocked 下游也不清（B5）。此為 #30 裁決的明文設計，非缺口；但它意味著每張曾有 blocker 的票都永久帶著一個字面條目，而 `release` 會把這個條目讀成「仍被擋著」。
8. 預設導航面（runqueue list／dashboard／board）皆不列標本；唯二指名它的是 `runqueue --format dag` 與 `list --status blocked`，兩者都需要讀者**已經懷疑**有 blocked 票才會去跑。`validate` 與 `audit` 皆不報「status=blocked 但 blocker 全解除」。

**仍未驗證的假設**

- 本案在其他 consumer 的實際發生率（本票未跨 consumer 量測）。
- `release` 三行的上游引入時間與 #30 裁決（2026-08-04）的先後（本 repo 歷史起點為 2026-08-26 框架導入，該行導入時已成形；先後關係無法由本 repo 判定）。
