### 問題根因

三項紅燈**同源**（同一個 `project_root` 未接線的根解析分裂），逐項判定如下：

**判定方式**：實跑一次後到檔案系統找日誌實際落點（非只看 stderr/logger caplog）。

1. `test_dashboard_auto_gc_logging.py` 兩項：`track_dashboard.py::_get_handoff_gc_logger()`
   呼叫 `hook_logging.setup_hook_logging("handoff-gc")` 時**未傳 `project_root`**。
   `setup_hook_logging` 未傳此參數時委派 `.claude/lib/hook_base.py` 自身的
   `get_project_root()`；而 `_auto_gc_stale_handoffs` 的實際歸檔動作已改用
   `ticket_system.lib.paths.get_ticket_state_root()`。兩函式在 linked worktree
   內解析方向相反（`get_project_root()` 回傳 worktree 自身根目錄；
   `get_ticket_state_root()` 回推主倉庫），造成歸檔寫入正確位置、但日誌檔落在
   worktree 自己的 `.claude/hook-logs/`，測試斷言的 `CLAUDE_PROJECT_DIR` 下找不到檔案。
   **實測驗證**：修復前執行測試套件後，`find` 該 worktree 的
   `.claude/hook-logs/handoff-gc/` 確實出現 `handoff-gc-20260910.log`
   （日誌憑空多出現在 worktree，而非測試預期的 tmp 隔離目錄）。

2. `test_track_dispatch_check.py::TestPruneFlag::test_prune_writes_hook_log_via_real_logger`：
   `track_dispatch_check.py::_get_prune_logger()` 同樣呼叫
   `hook_logging.setup_hook_logging(_PRUNE_HOOK_NAME)` 未傳 `project_root`，
   與本模組已用於 `dispatch-active.json` 讀寫的 `get_ticket_state_root()`
   同一分裂。實測日誌同樣落在 worktree 的
   `.claude/hook-logs/dispatch-check-prune/dispatch-check-prune-20260910.log`。

**同源證據**：兩處呼叫點的程式碼形狀完全一致——皆為 `_get_*_logger()` 這類
lazy-load `.claude/lib/hook_logging.py` 的輔助函式，皆呼叫
`hook_logging.setup_hook_logging(<hook_name>)` 且未帶 `project_root`，皆與
同模組內已改用 `get_ticket_state_root()` 的狀態寫入路徑（歸檔 / prune）
分處不同 root。此為「同一個未接線的參數」造成的同一種分裂，非「徵狀相同
但成因各異」的巧合——`setup_hook_logging` 的 `project_root` 參數本身即為此
場景設計（docstring 已明載：「hook 若以 __file__ 導向 root 讀寫狀態檔，但
日誌另呼叫不帶參數的 get_project_root()，兩者在 worktree 內執行時會解析出
不同 root」），只是這兩個呼叫點建立時未接上。

**非測試假設錯誤，亦非功能未寫**：`_auto_gc_stale_handoffs` 與 `--prune`
的實際業務邏輯（歸檔 / 清理）皆正確執行且寫對位置；問題僅發生在「同一次
操作的日誌記錄」與「該操作的實際效果」使用了兩套不同的 root 解析函式。
判定為**功能側日誌路徑漂移**（三種可能成因中的第二種），修功能。

**第三項例外**：`test_track_dispatch_check.py::test_prune_writes_hook_log_via_real_logger`
本身在完成上述功能修復後仍紅一次，成因與前兩項不同層次——該測試的
`_run()` 已將 `mod.get_ticket_state_root` monkeypatch 為 `lambda: tmp_path`
（供 `dispatch-active.json` 讀寫），但測試斷言卻讀 `CLAUDE_PROJECT_DIR`。
功能修復後 `_get_prune_logger()` 呼叫的正是這個被 monkeypatch 覆寫的
`get_ticket_state_root`，日誌因此正確地落在 `tmp_path`（與 dispatch 狀態
同根，達成本票修復目標），但測試斷言仍寫著修復前的（錯誤）預期位置
`CLAUDE_PROJECT_DIR`。此為**測試假設錯誤**（斷言的 root 與該測試自己
monkeypatch 的 root 本就不一致），已改測試斷言為 `tmp_path` 並在測試內
註明依據。

### Rationale Chain
- 0.1.0-W3-271 why: 知識住址：`tarrragon/claude#55`，區段「當前結論（graph-project-docs-manager：ticket CLI 契約與提交路徑）」與「待辦與來源（同後綴）」的 `0.1.0-W3-229` 列；原票 `0.1.0-W3-229` 已 closed（`not_executable_knowledge_captured`）。

**原缺陷**：`_run_git_with_lock_retry` 僅在錯誤字串含 `index.lock` 才重試，而 `commit_files_isolated` 的 CAS 步驟 `update-ref` 撞鎖時的錯誤文字是 `cannot lock ref 'HEAD': ... refs/heads/main.lock`（或 `HEAD.lock`），不含該子字串，**重試條件恆為 False**。撞鎖瞬間即失敗且 `commit_sha` 遺失，逼迫執行者手動繞出工具外完成 CAS，進而跳過收尾同步，造成共用 index 過期 entry 並被後續裸 commit 靜默回滾他票內容。

**2026-09-10 實地命中，且暴露了原票未記錄的兩項後果**：

一、**CAS 失敗會同時留下兩個鎖**——`refs/heads/main.lock`（41 bytes，內含已寫好的新 ref 值）與 `HEAD.lock`（0 bytes），而 ref 從未更新。commit 物件與鎖殘骸同時存在，全部 session 的全部提交路徑（工具路徑與手動 CAS）撞同一把鎖，換命令不繞過。實測全域停擺 39 分鐘、`HEAD` 一次都沒推進。

二、**工具無鎖齡判讀，故即使修好重試條件仍會對殘骸無限重試**。殘骸與並行活鎖的錯誤輸出**完全同形**，而兩者的正確處置相反：活鎖約十秒自行消失（判別是消失的同時 HEAD 前進到新 commit），重試即可、不得移除；殘骸不會自行消失（判別是內容可溯源為某次已知崩潰操作的產物且 mtime 停在該時刻），須由原執行者移除。修好重試而不加鎖齡判讀，等於把「立刻失敗」換成「永遠重試」。

三、**`update-ref` 失敗時應一併指出自己是否留下鎖殘骸**（群 A 由群 F 的溯源判準推得）。否則清理責任無法歸屬——合法的移除判準是「可溯源為自己崩潰操作的殘骸」，而執行者若不知道自己留下了什麼，就沒有人有資格清理。「舊鎖就刪」不是合法判準：它在多數情況結論正確，但對「這個鎖是誰留下的」零回答，結論若錯也無從發現錯在哪一步。

**實測數據**（群 G 單一觀測者橫跨兩種鎖，`#55` observe `5614476090`）：第 1 次 `HEAD.lock` 17 分鐘 0 bytes 期間零 commit（殘骸）；第 2 次 `HEAD.lock` 失敗後立即 `stat` 已不存在（活鎖）；第 3 次 `main.lock` 41 bytes 時間戳同為 14:01:39（殘骸的另一半）。該則另記錄一條誤判路徑：**剛清完同名鎖的人看到它再現，會傾向推論「有東西在重建它」而去查工具，而正確動作只是重試**——誤判的觸發條件不是鎖的屬性，是觀測者剛做過什麼。（來源已完成，結論見 Solution）
