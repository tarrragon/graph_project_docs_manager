### 實驗發現

**已驗證的事實**：

- CAS 失敗（update-ref 因 HEAD 被搶先移動）在目前實作中**不自動整體重試**，
  失敗訊息與復原路徑（commit-tree SHA 可手動接續）只回傳給呼叫端文字，
  無結構化重試協定，復原完全依賴呼叫端（代理人）自行判斷（`git_ops.py`
  程式碼與 docstring 直接驗證，非推論）。
- 鎖殘骸的清理判準（`_stale_lock_diagnosis`）刻意設計為「工具不移除任何鎖，
  需由留下該鎖的執行者依內容溯源後自行處置」，但在多代理人各自獨立執行、
  彼此不共享執行內文的並行環境下，**沒有任何一個角色天然具備「這是不是我
  留下的」判斷所需資訊**，此為（a）「CAS 失敗為何留鎖」的根因，且是
  設計已知取捨（non-deletion by design）與並行落檔場景（多執行體無共享
  內文）疊加後才顯性化的缺口，非單純程式錯誤。
- `bare-commit-guard-hook.py` 的並行期 DENY 依賴 `dispatch-active.json`
  存在活躍記錄，而 `tarrragon/claude#89` 已記載該檔在代理人轉入 idle
  時即被清空，此為（b）「代理人為何退回裸 commit 夾帶他票 staged」的
  高度可能機制（防護在應仍生效時已提前降級為 WARN）。
- 六個以上文件落檔代理人（W3-418/419/420/421/422/423/424/426）同時
  共用主 repo working tree 與 git index，超出 `PC-137` 已驗證的並行
  上限（5），落在其明文標示為未測的並行 6+ 區間。

**仍未驗證的假設**：

- 「代理人自行移除 HEAD.lock 並以 `git update-ref` 替他人完成 CAS」
  這項行為本身的觸發動機——是代理人依循某條既有規則的合理推論（例如
  誤讀「不移除任何鎖」為「僅限工具不移除，代理人可以」），或是任務
  受阻下的即興應急，git 物件歷史本身無法佐證，屬本票已知的證據缺口，
  留待 PM 或事件回報方補充第一手代理人推理過程（若可得）。
- 裸 commit 事件當下 `dispatch-active.json` 是否確實已清空（#89 機制
  是否為本次事件的實際觸發，或另有其他成因）：本票未取得該時刻的
  `dispatch-active.json` 快照，僅能建立機制上高度吻合的候選鏈，不列
  為已驗證事實。
