## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

六個以上文件落檔代理人（thyme-documentation-integrator）並行共用主 repo working tree 與 git index，超出 `PC-137` 已驗證的並行上限（5，未測門檻 6+）。在此並行度下，隔離索引 CAS（`ticket_system/lib/git_ops.py::commit_files_isolated`）暴露兩個既有設計取捨的疊加缺口：(1) update-ref 因 HEAD 被搶先移動而失敗時不自動整體重試，只回傳文字提示；(2) 鎖殘骸清理刻意設計為工具不自動移除、需執行者依內容溯源自行處置，但多代理人互不共享執行內文，無人能安全判斷鎖是否為自己所留。疊加 `bare-commit-guard-hook.py` 依賴 `dispatch-active.json` 判斷並行期（該檔依 `tarrragon/claude#89` 會在代理人轉入 idle 時提前清空），三者共同構成本票 what 欄位所述三起事件的機制基礎。

### 影響範圍

已驗證影響：`.claude/skills/ticket/ticket_system/lib/git_ops.py`（CAS 重試與失敗處置邏輯）、`.claude/hooks/bare-commit-guard-hook.py`（並行期 DENY 依賴的存活判定）、`.claude/pm-rules/parallel-dispatch.md` 與 `parallel-dispatch-worktree-details.md`（低風險代理人並行上限未明訂）。三者皆為 `.claude/` 通用資產，影響所有 consumer 專案的高並行文件落檔場景，非本專案專屬。仍未驗證：(a) 代理人自行清鎖並代他人完成 update-ref 的第一手觸發動機；(b) 裸 commit 事件當下 dispatch-active.json 是否確實已清空（機制高度吻合但無時間點快照佐證）。

### 相關 Error Pattern

已執行 `framework-issue dedup`，命中 `tarrragon/claude#89`（SubagentStop 提前清空 dispatch-active.json 使並行防護降級為 WARN）與 `tarrragon/claude#101` 附帶缺口二（隔離索引 CAS 繼續推進 HEAD 而不檢查外部危險狀態），兩者判定為引用關係（機制相關但情境不同，非重複）。本地 `PC-137`（並行 subagent .claude 目錄編輯 deny）提供並行上限 5／未測 6+ 的實證基準，直接支撐本票「並行度超出已驗證範圍」的判定。

### 實驗發現

**已驗證的事實**：

- CAS 失敗（update-ref 因 HEAD 被搶先移動）在目前實作中**不自動整體重試**，
  失敗訊息與復原路徑（commit-tree SHA 可手動接續）只回傳給呼叫端文字，
  無結構化重試協定，復原完全依賴呼叫端（代理人）自行判斷（`git_ops.py`
  程式碼與 docstring 直接驗證，非推論）。
- 鎖殘骸的清理判準（`_stale_lock_diagnosis`）刻意設計為「工具不移除任何鎖，
  需由留下該鎖的執行者依內容溯源後自行處置」，但在多代理人各自獨立執行、
  彼此不共享執行內文的並行環境下，**沒有任何一個角色天然具備「這是不是我
  留下的」判斷所需資訊**，此為（a）「CAS 失敗為何留鎖」的根因，且是
  設計已知取捨（non-deletion by design）與並行落檔場景（多執行體無共享
  內文）疊加後才顯性化的缺口，非單純程式錯誤。
- `bare-commit-guard-hook.py` 的並行期 DENY 依賴 `dispatch-active.json`
  存在活躍記錄，而 `tarrragon/claude#89` 已記載該檔在代理人轉入 idle
  時即被清空，此為（b）「代理人為何退回裸 commit 夾帶他票 staged」的
  高度可能機制（防護在應仍生效時已提前降級為 WARN）。
- 六個以上文件落檔代理人（W3-418/419/420/421/422/423/424/426）同時
  共用主 repo working tree 與 git index，超出 `PC-137` 已驗證的並行
  上限（5），落在其明文標示為未測的並行 6+ 區間。

**仍未驗證的假設**：

- 「代理人自行移除 HEAD.lock 並以 `git update-ref` 替他人完成 CAS」
  這項行為本身的觸發動機——是代理人依循某條既有規則的合理推論（例如
  誤讀「不移除任何鎖」為「僅限工具不移除，代理人可以」），或是任務
  受阻下的即興應急，git 物件歷史本身無法佐證，屬本票已知的證據缺口，
  留待 PM 或事件回報方補充第一手代理人推理過程（若可得）。
- 裸 commit 事件當下 `dispatch-active.json` 是否確實已清空（#89 機制
  是否為本次事件的實際觸發，或另有其他成因）：本票未取得該時刻的
  `dispatch-active.json` 快照，僅能建立機制上高度吻合的候選鏈，不列
  為已驗證事實。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 分析結論

三起事件對應三個各自獨立、可分開處置的缺口，皆座落於 `.claude/` 通用資產（ticket CLI plumbing、派發規則、hook），非本專案專屬：

| 事件 | 缺口定位 | 判定 |
|------|---------|------|
| (a) CAS 失敗留 ref lock 殘骸 | `ticket CLI`（`git_ops.py` 的失敗處置：不重試 + 不移除鎖 + 清理判準要求「可溯源為自己產物」，但並行多執行體互不共享內文） | 設計已知取捨在新場景（多代理人低內文共享並行落檔）下顯性化為缺口 |
| (b) 代理人退回裸 commit 夾帶他票 staged | `hook`（`bare-commit-guard-hook.py` 依賴 `dispatch-active.json`，而該檔案依 `tarrragon/claude#89` 會在代理人轉入 idle 時提前清空，防護降級為 WARN） | 已有框架 issue 追蹤（#89），本票為其提供一個新的具體命中場景 |
| (c) 代理人自行清鎖並代他人完成 CAS | `派發規則`（`parallel-dispatch.md`／`parallel-dispatch-worktree-details.md` 未明文禁止此行為；且低風險文件落檔代理人被歸類為免 worktree、共用 index，本波次 6+ 並行超出 `PC-137` 已驗證上限） | 規則缺口 + 已知容量上限被突破的複合結果 |

三者共同的深層成因：**低風險文件落檔代理人的免 worktree 假設，是在「並行數 ≤ 5」的已驗證範圍內建立的；本次波次以 6+ 並行同時寫入共用 working tree，直接跑出該假設的驗證邊界**，CAS 重試次數過少（`_MAX_RETRIES=2`）與鎖殘骸不可自動歸屬清理，在低並行下發生機率低、後果可忽略，在 6+ 並行下相同機制被放大成連續三起需要人工/代理人自行介入的事件。

### 候選方案

**候選 1：派發規則層——文件落檔代理人並行上限與批次化**

在 `parallel-dispatch.md`／`parallel-dispatch-worktree-details.md` 明訂：低風險文件落檔代理人（如 `thyme-documentation-integrator`）同時並行數 ≤ 5（對齊 `PC-137` 已驗證上限），超過 5 張待落檔票時拆批次序列派發（批次間仍可並行，批次內序列，或以 worktree 化取代批次拆分）。

- 利：改動範圍最小（只改規則文件），立即可用，不需碰 CLI/hook 程式碼；直接對齊已有實證數據（PC-137），無需新實驗。
- 弊：治標不治本——CAS 重試不足、鎖殘骸不可自動歸屬清理的機制缺陷仍在，只是把觸發機率壓回「低並行下少發生」的舊狀態，未來若容量需求成長（例如落檔波次天然產生 8+ 張票）仍會撞上同一問題；且「≤5」上限本身只有一次 session 的實證（尚待更多樣本鞏固）。

**候選 2：CLI 層——強化 CAS 重試與失敗訊息的結構化復原路徑**

修改 `commit_files_isolated`：(1) 對 `update-ref` 因 HEAD 移動而失敗（非撞鎖）的情形，增加「從新 HEAD 重跑整個週期」的自動重試（與撞鎖重試分開計數，避免無限迴圈需設上限，例如 3-5 次整體重試）；(2) 失敗訊息中若已產生 commit-tree SHA，除文字提示外，額外提供可直接執行的 `git update-ref` 手動接續指令範本，降低代理人自行發明危險操作（如手動刪鎖）的誘因。

- 利：從根源降低 CAS 失敗率與人工介入需求，效益不受限於特定並行數上限，long-term 對所有 consumer 專案受益（`.claude/` 通用資產）。
- 弊：改動核心 plumbing 程式碼，需完整測試覆蓋（含撞鎖 vs HEAD 前進兩種失敗路徑的區分、重試上限的邊界測試）；仍不解決「多代理人互不共享內文導致無人能安全判斷鎖殘骸歸屬」的協調問題（重試次數提高只降低觸發機率，不消除該機制）。

**候選 3：Hook 層——bare-commit-guard 補強派發存活判定，禁止跨代理人清鎖**

依 `tarrragon/claude#89` 的方向修復 `dispatch-active.json` 清理時機（idle 不等於終止），並在 `bare-commit-guard-hook.py` 補一條規則：偵測 Bash 命令字面含 `rm` 目標為 `*.lock`／`HEAD.lock` 或 `update-ref` 時，若當前並行注意力不屬於留鎖者本人（無法核實時保守 DENY），阻擋此類操作並提示走 `ticket track commit` 重試而非手動介入。

- 利：直接針對 (b)(c) 兩事件的行為模式建立機制層防線，不依賴代理人自律；與既有 #89 修復同批次可望一次解決兩個問題。
- 弊：範圍最大、風險最高——需要準確識別「鎖是否為自己所留」這件事本身在多執行體環境下就沒有可靠的機制化判準（此為 (a) 的根因之一），Hook 若一律 DENY 清鎖操作，會讓真正需要人工介入的崩潰殘骸清理（`_stale_lock_diagnosis` 設計上就預期會發生）完全卡死、無合法解法；需要先解決「如何機制化證明鎖的歸屬」這個更難的子問題，可行性尚待進一步設計。
