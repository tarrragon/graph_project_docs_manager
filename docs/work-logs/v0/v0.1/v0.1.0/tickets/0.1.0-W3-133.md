## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 第一問：方法論的「adapter」是否要求獨立類別？

**結論：否。方法論不要求 adapter 為獨立於 repository 檔案的類別。**

方法論〈Port 回饋契約〉承擔者表使用「adapter 實作」標註受理與結果時刻的承擔者。「adapter 實作」在方法論中是角色標籤——指「實作 port 介面並與外部系統交互的程式碼」——非組織結構指令。方法論全文無以下任何一項：

- adapter 必須是獨立於 repository 的頂層類別
- adapter 必須在獨立檔案中
- adapter 必須有特定的目錄結構（如 `ports/` + `adapters/`）

方法論四層架構表將 "Repository 介面" 置於 Interface Adapters 層，"DB、Web、UI 具體實作" 置於 Frameworks & Drivers 層。在 Clean Architecture 語境中，concrete implementation（即 `_Default*` 類別）本身就是 adapter——它 adapt 外部框架到 port 介面。現有的 `_Default*` 類別完全符合此角色定位。

**對 linux 批評的重新定位**：linux 的前提「WorkspaceRepository 同時是 repository 又是三個 adapter」與現有程式碼不符——Repository 透過 DI 委派給 `_Default*` adapter 類別，不直接呼叫外部 SDK（實查：Repository 方法中無 `SharedPreferences.getInstance()` 或 `Directory(path).exists()` 呼叫，這些僅出現在 `_Default*` 內部）。linux 的批評因此從「違反方法論」降為「檔案組織偏好」（將 private adapter 移至獨立檔案），兩者處置成本完全不同。

### 第二問：WorkspacePreferencesHandle 兩層形態的歸屬

**結論：WorkspacePreferencesHandle 是受理時刻的必要載體，非 SharedPreferences 實作細節的洩漏。**

論證四點：

1. **架構動機**：`WorkspacePreferencesPort.open()` 捕捉受理時刻（儲存管道可用），`WorkspacePreferencesHandle.readString/writeString` 捕捉結果時刻。這是方法論〈Port 回饋契約〉三時刻模型（呼叫發出→受理→結果）的直接映射。

2. **測試支撐**：G4-1 驗證受理事件存在且順序正確（正向），G4-2 驗證 `open()` 失敗時無受理事件（負向鑑別力），G4-3 驗證 file_selector 無受理事件（確認這不是機械套用而是架構選擇——fire-and-wait 模式無 acknowledge 步驟）。

3. **不可合併性**：Redundancy 視角已查證「沒有任何一個介面可以合併而不損失一條現存的綠燈測試」。若把 `open()` + `readString/writeString` 合併為單一方法，G4-1 和 G4-2 的語意基礎將消失——受理時刻與結果時刻無法分別觀測。

4. **型別不洩漏**：Coupling 視角實查確認 `SharedPreferences` 的型別未出現在任何介面簽章或呼叫端具體型別比對中。`WorkspacePreferencesHandle` 的形狀恰好與 SharedPreferences 的兩段式 API 平行，但抽象層級不同——呼叫端看到 `open()` + `readString/writeString`，不是 `getInstance()` + `getString/setString`。

### 第三問：是否建立 `lib/<domain>/ports/` + `adapters/` 目錄約定

**結論：不建立目錄約定。補一份接縫形態約定（寫入 `docs/tech-decisions.md`），標準化另外三個 port 的實作形態。**

理由：

1. **架構分離已存在**：port 介面與 default adapter 已是獨立類別，只是共處一個檔案。將它們移至獨立目錄改變的是檔案組織，不是架構品質。

2. **規模不符**：本專案目前有 1 個 domain（workspace），計畫中最多 4 個 driven port。若建目錄約定，4 port × `ports/` + `adapters/` = 8 個新目錄對一個小型桌面工具過度組織。

3. **不解決核心問題**：linux 關注的是「各自發明接縫形態」。解法是約定文件標準化形態（命名規範、兩步/單步判準、default adapter 封裝方式），而非目錄結構。

4. **封裝代價**：建 `adapters/` 目錄需將 `_Default*` 從 private 改為 public（Dart 的 `_` 前綴 = 檔案級 private），破壞現有封裝——呼叫端目前無法繞過 port 介面直接使用 default adapter，這是刻意設計。

### 候選結論與裁定

| 候選 | 描述 | 利 | 弊 | 裁定 |
|------|------|------|------|------|
| **A** | 維持現狀 + 接縫約定文件 | 零遷移成本；已有架構分離；約定文件防各自發明；保留 private 封裝 | 單檔 309 行接近閾值（下文處置）；閱讀者需理解 private adapter 角色 | **擇定** |
| B | 建立 `ports/` + `adapters/` 目錄 + 遷移 | 目錄結構顯性化角色 | 規模不符（8 新目錄）；private adapter 須改 public（破壞封裝）；遷移成本擴散至下游 4 票 | 否決 |
| C | 部分——大 port 獨立 adapter，小 port 內嵌 | 靈活 | 需給「多大算大」判準（新認知負擔）；目前 4 個 port 體量差異不大（均 10-20 行） | 否決 |

### 309 行的處置（AC 第 4 條）

`cognitive-load.md` 閾值：「> 300 行 → 分析 domain 邊界，考慮拆分檔案」。此為「考慮」級非「必須」級（「必須」級是「> 2 個 domain」，本檔僅 1 個）。

分析結果：
- Value types（`WorkspaceState` 及其子類、`ChooseFolderResult` 及其子類，第 7-76 行）佔 70 行，為純資料類別，無外部依賴
- 提取至 `workspace_types.dart` 可將主檔降至 ~239 行（遠低於閾值），不破壞 private adapter 封裝
- 提取後主檔僅剩 port 介面 + default adapter + repository = 單一責任（外部系統互動），value types = 另一責任（狀態建模）
- 此操作不影響任何既有 import（`workspace_types.dart` 可由 `workspace_repository.dart` re-export）

**裁定**：建議提取 value types 至 `workspace_types.dart`。登記 spawn request 交 PM 裁決是否建票。

3. `restore()` 的 `getInstance()` / `getString()`：無失敗路徑。Phase 1 已修正本條的初始描述——`getString()` 是純記憶體查表無 I/O 失敗路徑，真正的讀取失敗集中在會拋例外的 `getInstance()`，兩者不可混為一談，詳見 Solution 裁決 B。
