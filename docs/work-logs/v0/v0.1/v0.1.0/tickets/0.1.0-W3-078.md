### 實機觀測記錄（2026-09-08，PM 執行）

**量測環境**：macOS 25.5.0（arm64）、Flutter 3.47.1（FVM 釘選）、debug build 未簽章、
App Sandbox 關閉（PROP-001）。觀測管道為 Dart VM Service 的 DevTools Logging 分頁
（`developer.log` 不進 `flutter run` console，見下方「觀測管道」）。

#### 事實三（已測得）：macOS 的 AppLifecycleState 對應

實測轉換序列（時間為當次 session 的實際時戳）：

| 時間 | 轉換 | 對應操作 |
|------|------|---------|
| 15:12:51.371 | `resumed -> resumed` | App 啟動（自轉換） |
| 15:14:56.889 | `resumed -> inactive` | 視窗離開前景 |
| 15:14:57.420 | `inactive -> hidden` | （531 ms 後） |
| 15:18:13.031 | `hidden -> inactive` | 視窗返回 |
| 15:18:13.037 | `inactive -> resumed` | （6 ms 後） |
| 15:18:15.732 | `resumed -> inactive` | 再次離開 |
| 15:18:15.739 | `inactive -> hidden` | （7 ms 後） |
| 15:18:17.556 | `hidden -> inactive` | 返回 |
| 15:18:17.556 | `inactive -> resumed` | （同毫秒） |
| 15:18:23.648 | `resumed -> inactive` | 再次離開 |
| 15:18:24.167 | `inactive -> hidden` | （519 ms 後） |

**結論**：macOS 上 `inactive` **不是可停留狀態，而是過渡態**。離開前景（失焦或最小化）
一律走 `resumed -> inactive -> hidden`，返回一律走 `hidden -> inactive -> resumed`；
兩段間隔在 6 ms 到 531 ms 之間，取決於系統當下負載，不具語意。

**對 SPEC-003 §2.2 的影響**：觸發條件 (a) 寫「完成當下視窗非前景（`AppLifecycleState`
非 `resumed`）」。依本次實測：

1. 條件本身成立且可用——`hidden` 確實表示非前景。
2. 但**任何以 `inactive` 為判斷分支的邏輯在 macOS 上是死碼**，因為它從不停留於該值。
3. **失焦與最小化在此列上不可區分**——兩者終態皆為 `hidden`。若後續需要區分
   「視窗可見但失焦」與「已最小化」，`AppLifecycleState` 不提供該資訊，須另尋來源。

#### 事實一（測得的結果與預期不同）：授權查詢在平台邊界就失敗

原待驗項為「`UNUserNotificationCenter` 在沙盒關閉與 Developer ID 簽章下的可用性」。
實測顯示這一層**根本沒被觸達**——`MethodChannel` 原生端未註冊：

    15:12:51.441 [MacosScanNotifier] Level.WARNING (900)
    查詢授權狀態失敗，原生端未註冊 handler（視為 denied）：
    MissingPluginException(No implementation found for method authorizationStatus
    on channel graph_project_docs_manager/scan_notifier)

因此本次**未能**測得 `UNUserNotificationCenter` 的可用性，也未能測得未簽章 debug build
的授權請求回應——兩者都在 channel 修好之後才有意義。承接票 `0.1.0-W3-097`（P0）。

#### 事實二（部分可答）：Flutter 端載體

載體選擇為原生 `MethodChannel`（`macos/Runner/AppDelegate.swift` +
`lib/services/macos_scan_notifier.dart`），`pubspec.yaml` 無任何第三方通知套件。
此為原始碼事實，不需實機。但「該選擇是否可行」的實測依據仍待 `0.1.0-W3-097` 修復後補。

#### 事實四（未測得）：撤回 API 的效果

需先有已送達的通知才能測撤回，因此同樣阻擋於 `0.1.0-W3-097` 與 `0.1.0-W3-096`。

#### 觀測管道（本次驗證的方法學發現）

`flutter run` 的 console **不顯示 `developer.log` 的輸出**——該 API 寫入的是 Dart VM
Service 的 Logging stream，`flutter run` 只轉送 `print` / `debugPrint`。本專案的可觀測性
策略全面採用 `developer.log`（CLAUDE.md §6），因此**專案的全部 log 在標準開發迴圈中不可見**，
必須開 DevTools 的 Logging 分頁才看得到（本次實測共 244 個 event）。

PM 曾據 `flutter run` console 零輸出推論「通知路徑從未執行」，該推論錯誤：實際上啟動時
即已執行授權查詢並失敗。**以某一管道的輸出缺席推論世界狀態，前提是該管道確實承載該訊號**，
本次未先驗證此前提。此教訓應併入驗證配方（`.claude/skills/verify/` 尚未建立，
session 啟動每次警告「驗證環境未就緒」）。
