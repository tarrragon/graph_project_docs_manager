### 本票前提為誤（W3-019 Round 2 查出，2026-09-04）

Disclosure〉在該輪新增了語言換算表，並明寫「**不可把 6,500 無條件套用於 ASCII 為主的
skill**」。本票在該修法落地之後、於同一 session 內立案時再犯一次。

**但本票不逕行關閉**，因為 W3-019 Round 2 另揭露兩件本票範圍內、且與字元數無關的實質問題：

**教訓**：修法落地不等於修法生效於後續決策。本次的修法寫在 SKILL.md 條文裡，而立案動作
不讀該條文——條文與使用它的決策點之間沒有強制連結。判別問句：

### 更正上表的算式，並註銷第 2 項（2026-09-07，v1.7.3 重測）

### 外部實跑提供的決定性案例（blog 專案，2026-09-07）

本票的核心未決項是「第 3 層門檻的適用對象未定義」——三層表逐字寫 references「無上限」，
而同節又給了單檔判準（讀取方式：整份執行量全檔／選段查閱量最大單節）。**兩處說法並存

該專案以本 skill v1.9.0 實跑一次 **30,101 tokens / 392 行**的拆分（6 倍門檻），

**`round-2-cadence.md` 的 8,172 tokens 正落在本票的歧義區**：照「整份執行」量全檔它超過 5k，
照「無上限」它合規。該專案因此**未再拆並記為已知問題，明文等本票定案**。

**這使本票從「條文有歧義」升級為「有下游被它擋住」**。定案時建議一併答三件事：

1. 「無上限」的作用域是目錄總量還是單檔（本側判斷是前者，但條文沒寫）
2. 整份執行 vs 選段查閱的判別由誰決定——入口檔的路由詞（「讀這一份再繼續」）還是該檔自身有無 TOC
3. 超過 5k 的選段查閱型 reference 是否需要再拆，或只需最大單節合規即可

**附帶**：該專案量 description 時算的是欄位本身不含引號，與本側閘門若寫「含引號」會差 2 字元。
本票若一併定案 description 的量法，須明示是否含引號。
