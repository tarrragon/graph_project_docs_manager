## Context Bundle

**需求摘要**: 建立 error-pattern——編輯一支正在被使用的工具時，危險窗口是「還沒改完」而非「改壞了」；排程依據應為「有無執行體正在呼叫」而非「有無他人正在編輯」。

**查重候選（已驗證：`ls .claude/error-patterns/process-compliance/` 篩並行／共用資源相關）**

acceptance 第 5 條要求建立前查重。以下為 PM 初篩的候選，執行者須逐一開檔確認，不得僅依檔名判斷：

- `PC-029-parallel-agents-shared-file-conflict.md`
- `PC-092-parallel-agents-git-index-race.md`
- `PC-076-cross-session-uncommitted-legacy.md`
- `PC-078-parallel-session-ticket-state-misjudgment.md`
- `IMP-034-init-py-transitive-import-breakage.md`（import 失效相關，機制可能有交集）
- `IMP-069-pep723-dependencies-not-transitive.md`（同上）

以 `grep -rln "SyntaxError\|使用中的工具\|部署窗口"` 掃全 error-patterns 目錄無直接命中，但**無命中不等於無涵蓋**——既有 PC 可能以其他措辭描述同一機制。查重結論寫入 Solution。

**本則的核心論證（兩種失效的性質對照）**

| 維度 | 改壞了 | 還沒改完 |
|------|--------|---------|
| 持續時間 | 一直壞到修好 | 只有寫入到寫入完成之間的幾百毫秒 |
| 失效方式 | 邏輯錯誤，與改動內容相關 | `SyntaxError` / `ImportError`，與改動內容**無關** |
| 被發現機率 | 高——穩定重現 | 低——不重現，下次跑就好了 |
| 事後歸因 | 可行——症狀指向改動 | 幾乎不可行——症狀與改動內容無關聯 |

機制：Python 在每次 CLI 呼叫時 import 原始碼，所以「有人正在編輯 CLI 原始檔」與「有人正在呼叫該 CLI」是同一份資源的讀寫競爭。

**代價不對稱是本則的重點，不是機率。**窗口短、機率低——若只論機率，結論會是「可以忽略」。真正的理由是落點：呼叫失敗可能發生在代理人的收尾階段（`complete` / `set-exit-status`），那是整條路徑上最難重來的位置——工作已全部做完、卡在最後一步，而失敗原因與它做的事完全無關。撰寫時若把論證寫成「並行環境要小心」，就丟失了本則唯一有價值的部分。

**實例（已驗證）**

`0.1.0-W3-087` 修改 `.claude/skills/ticket/ticket_system/commands/track_dispatch_validate.py`（`ticket track dispatch-validate` 的實作）。當時三個 session 共用該 CLI，另兩個 session 有代理人正在跑 `claim` / `append-log` / `complete`。PM 據此把 087 的派發排到那些代理人收工之後——而非僅依「同儕 session 是否也在用 CLI」判斷。兩個 session 交換後皆認定此判準具一般性。

**適用邊界（須寫進 error-pattern，否則會被過度套用）**

本則管的是**被多個執行體即時呼叫的工具**（本框架的 `ticket` / `doc` / `worktree` 等 CLI、hook 腳本）。一般產品程式碼的編輯不適用——它們不會在編輯當下被別的 session import 執行。判準是「這個檔案會不會在我編輯的這一刻被別的行程載入執行」。

**約束**

- 本檔屬按需讀取層，三明示可完整展開。
- 類別傾向 `process-compliance`（PM 傾向，非結論）；若查重後判定屬 `implementation` 更貼切，於 Solution 說明。
- 建立後須依既有慣例更新 error-patterns 索引（`error-patterns-index-consistency-check-hook.py` 於 SessionStart 檢查一致性）。
