why: '多 session 共用一支 CLI（本框架的 `ticket` / `doc` / `worktree` 等）時，修改該 CLI 原始碼的風險被普遍理解為「改壞了會影響別人」。這個理解漏掉了危險性更高的另一半。


  **兩種失效的性質對比**：


  | | 改壞了 | 還沒改完 |

  |---|--------|---------|

  | 持續時間 | 一直壞到修好 | 只有寫入到寫入完成之間的幾百毫秒 |

  | 失效方式 | 邏輯錯誤，與改動內容相關 | `SyntaxError` / `ImportError`，與改動內容**無關** |

  | 被發現機率 | 高——穩定重現 | 低——不重現，且下次跑就好了 |

  | 事後歸因 | 可行——症狀指向改動 | 幾乎不可行——症狀與改動內容無關聯 |


  Python 在每次 CLI 呼叫時 import 原始碼，所以「有人正在編輯 CLI 原始檔」與「有人正在呼叫該 CLI」是同一份資源的讀寫競爭。編輯到一半的檔案會讓任何一次呼叫拿到 SyntaxError。


  **代價的不對稱是本則的重點**：窗口短、機率低，但落點可能是代理人的收尾階段（`complete` / `set-exit-status`）——那是整條路徑上最難重來的位置，工作已全部做完、卡在最後一步，而且失敗原因與它做的事完全無關。低機率乘高代價，值得為它排序而非忽略。


  **實例**：`0.1.0-W3-087` 修改 `track_dispatch_validate.py`（`ticket track dispatch-validate` 的實作）。當時三個 session 共用該 CLI，其中兩個 session 有代理人正在跑 `claim` / `append-log` / `complete`。PM 據此把 087 的派發排到那些代理人收工之後，而非僅依「同儕是否也在用」判斷。'
