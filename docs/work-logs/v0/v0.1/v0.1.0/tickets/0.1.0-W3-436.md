## Problem Analysis
### 問題根因

`references/i18n-guidelines.md` 兩處條文都提到「錯誤碼」，但各自沒有寫明所指的對象，也沒有互相引用：

- 〈Exceptions〉第 1 項原文：「Some strings may NOT need i18n: 1. **Technical identifiers** - Error codes, keys」。指的是**錯誤碼識別字串本身**（程式內部值，例如 enum 值或常數字串），它不進 ARB。
- 〈Violation 2: Hardcoded Error Messages〉原文：「拋出例外或回傳錯誤的位置（Repository／UseCase／ViewModel 等非 widget 層）……改丟未翻譯的錯誤碼或例外型別，交由呈現層以 `ErrorHandler` 轉譯」，Fix 為 `Text(ErrorHandler.getUserMessage(context, errorCode))`。指的是**使用者可見的錯誤訊息**：錯誤碼只是在層與層之間傳遞的載體，顯示前要先轉成翻譯後的文案。

兩處對錯誤碼的處置方向一致：〈Violation 2〉要求「未翻譯的錯誤碼」，正好依賴〈Exceptions〉的豁免。兩者沒有對同一對象給出相反處置。缺的是交界：錯誤碼直接顯示給使用者時（DSG-04b 題幹：只顯示錯誤碼，沒有標籤），讀者分不出這算〈Exceptions〉的「識別符值豁免」，還是〈Violation 2〉的「使用者可見錯誤訊息須經呈現層轉譯」。〈Exceptions〉現有的標籤＋識別符段只處理「有標籤」的情況，沒有處理「錯誤碼取代訊息」。

### 影響範圍

- 已驗證：只影響 `references/i18n-guidelines.md`〈Exceptions〉與〈Violation 2〉。`SKILL.md`〈Violation 6〉的 Allowed Exceptions 只列 `e.toString()`（僅供記錄，不對使用者顯示），沒有提到錯誤碼豁免，不在衝突範圍內。
- 已驗證：C04 裁示原文（`0.1.0-W3-336.7` Solution）：「非 widget 層（ViewModel／UseCase／Repository）不使用 l10n，丟錯誤碼或 enum，由呈現層對應為文案」。
- 未驗證：`style_checker.py` 與 PostEdit hook 如何處理只顯示錯誤碼的程式碼行。本票只讀文件，沒有跑掃描器。這一點不影響文字判定。

### 相關 Error Pattern

沒有直接對應的 error-pattern。性質上屬於同一 skill 內兩處條文沒有交代交界，與 W3-417 讀者探針暴露「依據只在範例內」的同一類問題。

## 重現實驗結果
### 實驗方法

用文字推演重現：把 DSG-04b 情境（呈現層只顯示錯誤碼，沒有標籤）分別套用兩條條文，逐字引依據句，看兩條給出的判定是否不同。只讀檔，不改 skill。

### 實驗執行

情境代碼（示意）：`Text(state.errorCode.name)`，畫面顯示 `LOAD_FAILED`。

| 套用條文 | 依據句（逐字） | 判定 |
|---------|--------------|------|
| 〈Exceptions〉 | 「Technical identifiers - Error codes, keys」＋「僅數值本身列入本豁免」 | 錯誤碼是技術識別符，沒有標籤 → 豁免，不需要 i18n |
| 〈Violation 2〉 | 「改丟未翻譯的錯誤碼……交由呈現層以 `ErrorHandler` 轉譯」＋Fix `Text(ErrorHandler.getUserMessage(context, errorCode))` | 呈現層應先轉譯再顯示 → 直接顯示錯誤碼屬違規 |

對照：非 widget 層 `throw AppException(AppErrorCode.loadFailed)`，兩條判定一致（錯誤碼不翻譯），沒有分歧。

### 實驗發現

- 已驗證：分歧只出現在「呈現層把錯誤碼當成使用者可見文字輸出」這個情況。在層間傳遞錯誤碼時，兩條一致。
- 已驗證：兩條的對象不同（識別符值 vs 使用者可見訊息），條文沒有寫明這一點，也沒有互相引用 → 判定為**缺交界**，不是矛盾。
- 已驗證：錯誤碼直接顯示時，哪條優先無法從條文推出。C04 裁示「由呈現層對應為文案」可以作為推導依據，但 i18n-guidelines 條文內沒有寫出來。

## Solution
### 判定

**缺交界，不是矛盾。**

| 條文 | 對象 | 處置 |
|------|------|------|
| 〈Exceptions〉第 1 項「Technical identifiers - Error codes, keys」 | 錯誤碼識別字串本身（程式內部值） | 不進 ARB |
| 〈Violation 2〉「改丟未翻譯的錯誤碼……交由呈現層以 `ErrorHandler` 轉譯」 | 使用者可見的錯誤訊息 | 呈現層轉譯後才顯示 |

兩條處置方向一致：〈Violation 2〉的「未翻譯的錯誤碼」本身就依賴〈Exceptions〉的豁免。缺口在於兩條都沒寫明各自的對象，也沒有互相引用。結果是「呈現層直接把錯誤碼顯示給使用者」這個情況（DSG-04b）套兩條會得到相反判定，而條文本身推不出哪條優先。

### 候選處置

| 候選 | 內容 | 利 | 弊 | 與 C04 的關係 |
|------|------|----|----|--------------|
| A（建議） | 寫明錯誤碼豁免只到識別符值本身；錯誤碼不得取代訊息單獨顯示；要附參考編號時，訊息轉譯、編號以參數帶入 | DSG-04b 可從條文判定；判準寫在條文句內，不只存在範例裡 | 新增一個判準小節，檔案增加約 25 行 | 由 C04「由呈現層對應為文案」推導而來，不改變裁示 |
| B | 兩處各補一句互相引用，只寫明對象不同，不處理錯誤碼直接顯示的情況 | 改動最小 | DSG-04b 仍無法判定，W2 閘門「零無依據句」過不了 | 不改變 |
| C（不建議） | 把只顯示錯誤碼比照 ISBN 數值，列為豁免 | 與現有標籤＋識別符判準形式對稱 | 允許呈現層不轉譯就顯示錯誤，與 C04「由呈現層對應為文案」衝突 | **會改變用戶裁示**，須用戶另行裁決，不能由落地票自行採用 |

### 候選 A 改後文字草稿

**1. 〈Exceptions〉清單第 1 項改為：**

```markdown
1. **Technical identifiers** - Error codes, keys（僅指識別符值本身：層間傳遞、寫入日誌、作為查表鍵；錯誤碼要讓使用者看到時，見〈判準：錯誤碼與使用者可見錯誤訊息的交界〉）
```

**2. 〈判準：標籤＋識別符組合時如何分割〉之後新增小節：**

````markdown
### 判準：錯誤碼與使用者可見錯誤訊息的交界

錯誤碼豁免的對象是識別符值本身：在層間傳遞（`throw AppException(AppErrorCode.loadFailed)`）、寫入日誌、作為 `ErrorHandler` 查表的鍵，都不進 ARB。使用者可見的錯誤訊息不在豁免範圍內，依〈Violation 2〉由呈現層轉譯後顯示。**錯誤碼不得取代訊息單獨顯示**，因為呈現層跳過轉譯就等於把未翻譯的內部值交給使用者。需要讓使用者看到錯誤碼（例如回報問題用的參考編號）時，錯誤碼必須跟在轉譯後的訊息旁，組合方式依上一節走參數化翻譯，只有錯誤碼值本身豁免。

```dart
// Violation（呈現層把錯誤碼當訊息直接顯示）
Text(state.errorCode.name)

// Fix（呈現層轉譯後顯示）
Text(ErrorHandler.getUserMessage(context, state.errorCode))

// Fix（需附參考編號：訊息轉譯，錯誤碼值以參數帶入）
Text(context.l10n!.errorWithReference(
  ErrorHandler.getUserMessage(context, state.errorCode),
  state.errorCode.name,
))
// ARB: "errorWithReference": "{message}（錯誤代碼：{code}）"
```

片段                         | 是否豁免 | 理由
-----------------------------|----------|------------------------------------------
層間傳遞的錯誤碼             | 是       | 技術識別符值，不對使用者顯示
呈現層只顯示錯誤碼、沒有訊息 | 否       | 使用者可見錯誤訊息被錯誤碼取代，違反〈Violation 2〉的呈現層轉譯
訊息旁附帶的錯誤碼值         | 是       | 識別符值本身；外圍文字走參數化翻譯
````

**3. 〈Violation 2〉說明段末尾補一句：**

```markdown
此處丟出的錯誤碼本身屬〈Exceptions〉的技術識別符，不進 ARB；豁免只到錯誤碼值為止，顯示給使用者的訊息仍須轉譯（交界見〈判準：錯誤碼與使用者可見錯誤訊息的交界〉）。
```

草稿中的型別與 API 名稱（`AppErrorCode`、`ErrorHandler.getUserMessage`、`errorWithReference`）沿用現有範例的示意寫法，不綁定本專案識別符（符合規則 8）。
