### Commit 規範

Recommended: commit via isolated index (files must be a subset of this
ticket's where.files; never touches the shared index):
  ticket track commit <ticket-id> -m "..." -- {exact files}
In a linked worktree (files changed under a worktree dir, not the main repo):
add `--worktree <abs-worktree-path>` to the command above.
Fallback (not recommended; only if `ticket track commit` fails or is
unavailable) — use precise staging + verified bare commit only (no pathspec):
  git add {exact files}
  git diff --cached --name-only   # confirm index contains ONLY {exact files}
  git commit -m "..."             # bare commit; no -- <paths> / --only / -o / -a
Forbidden: git add . / git add -A; git commit -- <paths> / --only / -o / -a
  (pathspec-style commit discards the index and rebuilds it from working-tree
   content for the given paths — it silently absorbs unstaged edits other
   sessions may have on the same path, not just already-staged ones)
Before fallback commit: git diff --cached --name-only to check staged scope; git restore --staged <path> for any non-owned file
If bare `git commit` fallback is DENYed by bare-commit-guard-hook (another
dispatch active), stop and escalate to PM; never switch to pathspec /
--only / -o / -a to get around it.
If a commit is later found to have swept in out-of-scope content (e.g. a
peer session's staged changes):
Forbidden recovery actions: git revert; git reset --soft; git commit
--amend; any "reverse apply"/reapply of the diff. None of these may be
used to undo or rewrite the commit.
The ONLY permitted actions are: stop, record the commit SHA and file
list in the ticket, report to PM.
Reason: swept-in content is diff-indistinguishable from a peer's
legitimate concurrent write in the same window, so any of the forbidden
actions above would also undo the peer's legitimate work.

#### C01：退出路徑「完成後自動轉場」是否算有效退出路徑

**矛盾位置**：
- 甲：`SKILL.md`〈Core Pillars〉"Every state has an exit" 列
- 乙：`references/screen-state-matrix.md`〈四欄定義〉退出路徑欄「常見遺漏」旁的內容說明
- 丙：`references/screen-state-matrix.md`〈檢查清單〉第 3 項
- 丁：`references/screen-state-matrix.md`〈退出路徑的例外邊界〉

**兩方原文**：
- 甲：「畫面的每個狀態至少一條使用者可自行觸發的離開路徑；退出路徑為空 = UX 死胡同」
- 乙（四欄定義表，退出路徑欄「內容」）：「使用者如何離開：返回、導航他處、取消、完成後自動轉場」——把「完成後自動轉場」與其他三種使用者主動操作並列，未加條件
- 丙：「每個狀態至少一條使用者可自行觸發的退出路徑？」
- 丁：「退出路徑是預設要求。可豁免的唯一情況：該狀態持續時間極短（< 1 秒）且有保證的自動轉場——即使如此仍建議保留取消」

甲／丙／丁三處一致：退出路徑預設須「使用者可自行觸發」，自動轉場只在「極短 + 有保證」的條件下才是可豁免的例外，且仍建議保留取消。乙把「完成後自動轉場」直接列為退出路徑欄可填內容之一、不附任何條件，等於告訴填表人「自動轉場本身就是一種退出路徑」，與甲／丙／丁的「例外需條件、且仍非首選」相牴觸。

**建議以哪方為準**：以甲／丙／丁（3 處一致）為準，修正乙。

**理由**：甲／丙／丁三處相互印證構成一致政策（自動轉場是受限例外、非預設選項），乙是唯一的孤立說法；乙若不改，agent 逐格填表時會把任何「完成後自動跳轉」的狀態直接判定「退出路徑已填」而跳過使用者可觸發性檢查，實質架空丁的例外邊界（因為丁的豁免條件本應該是少數，乙卻讓它變成表格明文允許的常態選項）。

**改後文字草稿**（`references/screen-state-matrix.md`〈四欄定義〉表格「退出路徑」列「內容」欄）：

原文：
> 使用者如何離開：返回、導航他處、取消、完成後自動轉場

改為：
> 使用者如何離開：返回、導航他處、取消（使用者主動操作）。「完成後自動轉場」不計入本欄的預設內容——僅在〈退出路徑的例外邊界〉條件成立時，該狀態才可用自動轉場替代使用者觸發的退出路徑

#### C02：100–400ms 帶該用 spinner 還是動畫過渡

**矛盾位置**：
- 甲：`references/interaction-feedback.md`〈三層回饋模型〉表格第 2 層「等待指示」列
- 乙：`references/interaction-feedback.md`〈時間門檻與回饋策略〉表格「100-400ms」列

**兩方原文**：
- 甲：「2. 等待指示 | 100ms-10s | 「正在處理」 | spinner / loading 狀態 / 進度條」
- 乙：「100-400ms | 幾乎即時 | 動畫過渡掩蓋等待 | 快速搜尋、本地查詢」（同表下一列「400ms-1s」才是「Spinner / 按鈕 loading 狀態」）

甲把「等待指示」層的時間範圍訂為 100ms-10s、實作直接寫 spinner；乙把同一段時間切成兩帶，100-400ms 明文禁用 spinner（只用動畫過渡），400ms 以後才允許 spinner。同檔〈延遲是分布、不是常數〉的延遲顯示（delayed spinner）機制（「發請求後等 300-400ms 才掛 spinner」）與乙一致、與甲不一致。

**建議以哪方為準**：以乙（時間門檻表）與〈延遲顯示〉條文為準，修正甲。

**理由**：乙與〈延遲顯示〉機制彼此印證（都把 spinner 的出現延後到 300-400ms 之後），是同檔內部更細緻、更晚寫成的規則；甲是高層三段式概覽，若逐字採用會讓 agent 在 100ms 就掛 spinner，與〈延遲顯示〉「快的請求不該閃 spinner」的設計初衷牴觸。acceptance 明文要求「C02 時間門檻與同檔延遲 spinner 條文一致」，即以延遲 spinner 條文（乙側）為準。

**改後文字草稿**（`references/interaction-feedback.md`〈三層回饋模型〉表格「2. 等待指示」列「實作」欄）：

原文：
> spinner / loading 狀態 / 進度條

改為：
> 依〈時間門檻與回饋策略〉分帶決定：100-400ms 用動畫過渡、400ms 以上才用 spinner / loading 狀態 / 進度條（含延遲顯示機制）

#### C03：輕微錯誤是否可以只有一個行動

**矛盾位置**：
- 甲：`references/error-recovery.md`〈核心概念〉最後一句（底線敘述）
- 乙：`references/error-recovery.md`〈錯誤訊息的兩個職責〉行動面第 3 點
- 丙：`references/error-recovery.md`〈錯誤訊息的兩個職責〉〈三層結構〉段落末句
- 丁：`references/error-recovery.md`〈Error loop 的逃生口〉第 1 點

**兩方原文**：
- 甲：「使用者在任何錯誤狀態下都有至少兩條路（繼續嘗試、或離開）」
- 乙：「行動選項中至少一個是退出路徑（返回 / 關閉 / 取消）— 使用者可能不想重試、只想離開」
- 丙：「輕微錯誤只需標題 + 一個行動；嚴重錯誤三層都要」
- 丁：「每個 error 畫面至少兩個選項 —「重試」+「返回」是最小組合」

甲／乙／丁三處一致要求錯誤狀態至少有兩個選項（或至少一個退出路徑外加其他行動），丙的「輕微錯誤只需...一個行動」若照字面（一個行動＝一個按鈕）執行，會與甲／丁的「至少兩條路／兩個選項」直接衝突。

**建議以哪方為準**：以甲／乙／丁（3 處一致，且甲是全篇開宗明義的底線敘述）為準，修正丙。

**理由**：甲是〈核心概念〉開頭明訂的底線（三個組成共同遵守），丁是專門處理「使用者被困住」情境的具體規則，兩者立場一致且更貼近本 skill「防止使用者被困住」的核心目的；丙若保留字面「一個行動」，會讓「輕微錯誤」變成唯一被允許只給單一出口的例外類別，且丙本身未定義「輕微」的判準，agent 會傾向把多數錯誤判為「輕微」以省事，實質架空甲／丁的底線。丙原意應是「可省略『說明』這一層」而非「只能有一個按鈕」，故修正時保留其「可簡化三層結構」的合理部分。

**改後文字草稿**（`references/error-recovery.md`〈錯誤訊息的兩個職責〉〈三層結構〉段落末句）：

原文：
> 輕微錯誤只需標題 + 一個行動；嚴重錯誤三層都要。

改為：
> 輕微錯誤可省略「說明」層、只需標題 + 行動；行動仍須符合底線——至少一個是退出路徑，且與其他行動合計仍達〈Error loop 的逃生口〉要求的至少兩個選項。嚴重錯誤三層都要。

#### C12：screen-state-matrix E2 與 interaction-feedback E12 同情境範例欄位值不一致

**矛盾位置**：
- 甲：`references/screen-state-matrix.md`〈填寫範例〉修復後矩陣（E2）
- 乙：`references/interaction-feedback.md`〈畫面級回饋〉「以連線流程為例的狀態回饋」表（E12）

兩表描述同一情境（遠端終端機 app 連線流程的 idle / connecting / connected / error / disconnected 五狀態），但退出路徑目標不一致：

| 狀態 | 甲（E2）退出路徑 | 乙（E12）退出路徑 |
|------|----------------|----------------|
| idle | 取消 → 返回首頁 | 返回上一頁 |
| connecting | back → 返回首頁 | 取消 → idle |
| connected | back / disconnect → 首頁 | 斷開 → idle / 返回 |
| error | back → 返回首頁 | 重連 → connecting / 返回 → idle |
| disconnected | back → 返回首頁 | 重連 → connecting / 返回 → idle |

甲全數導向「返回首頁」（離開整個連線流程），乙的多數退出導向「idle」（留在流程內、回到起始狀態）。兩檔皆聲明「自包含」（不需先讀其他 reference），但只讀其中一檔的讀者會產出結構不同的狀態機。

**建議以哪方為準**：以甲（screen-state-matrix E2）為準，修正乙（E12）。

**理由**：`interaction-feedback.md`〈不適用〉段自陳「狀態的枚舉與退出路徑歸狀態矩陣」——乙檔本身已承認退出路徑的權威定義權不在自己；`SKILL.md`〈與相鄰資產的交界〉亦未把退出路徑劃給 interaction-feedback。故 E12 的退出路徑欄應是「引用甲的定義」而非「自行另訂一套」，兩表不一致時以甲為準。

**改後文字草稿**（`references/interaction-feedback.md`〈畫面級回饋〉表格與其後說明句）：

原表格退出路徑欄改為與甲一致（同時「可用操作」與「UI 呈現」欄配合甲的狀態機調整，例如 idle 的可用操作由「點擊連線」改為甲的「取消」、進入方式改為甲的「自動連線」，避免同表內其他欄與新退出路徑欄矛盾）：

| 狀態 | UI 呈現 | 可用操作 | 退出路徑 |
|------|--------|---------|---------|
| idle | 空白（自動連線） | 取消 | 取消 → 返回首頁 |
| connecting | 全頁 spinner +「連線中」+ back | 取消連線 | back → 返回首頁 |
| connected | 功能畫面 + back | 使用 / 斷開 | back / disconnect → 首頁 |
| error | 錯誤訊息 + 重連 + back | 重新連線、返回 | back → 返回首頁 |
| disconnected | 「連線中斷」+ 重連 + back | 重新連線、返回 | back → 返回首頁 |

並將表格後的說明句：

原文：
> 關鍵設計：error 和 disconnected 必須同時提供「重連」和「返回」— 只有重連會把使用者鎖在錯誤迴圈。timeout 是 connecting 的隱形退出路徑：取消靠使用者主動、timeout 是系統兜底（取值略大於 client / 後端逾時、讓真正的失敗先回來），逾時後轉入 error。

改為（移除「重連 → connecting」「返回 → idle」這類與新表不符的內部狀態指涉，改用甲一致的「首頁」終點）：
> 關鍵設計：error 和 disconnected 必須同時提供「重新連線」和「返回」（見上表可用操作欄）— 只有重新連線會把使用者鎖在錯誤迴圈，返回導向首頁的退出路徑見上表。timeout 是 connecting 的隱形退出路徑：取消靠使用者主動、timeout 是系統兜底（取值略大於 client / 後端逾時、讓真正的失敗先回來），逾時後轉入 error。

**備註（供裁決參考）**：另一可行方案是移除 E12 表格的「退出路徑」欄，改為文字引用「退出路徑欄定義與本情境完整值見 `screen-state-matrix.md`〈填寫範例〉」，避免兩處日後各自演進再度分歧。本提案採「同步值」而非「移除欄位＋引用」，因 E12 表格緊鄰段落強調「連線類多步驟流程的畫面級回饋」教學情境、拿掉退出路徑欄會降低範例的可讀完整性；若用戶認為「引用替代同步」更能防止未來drift，可改採備註方案，不影響其餘三則矛盾的處置。
