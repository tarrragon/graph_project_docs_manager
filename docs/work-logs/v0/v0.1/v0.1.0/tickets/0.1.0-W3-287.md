### Task Reference
- 0.1.0-W3-286 what: 收窄 規則七精準 staging 的適用條件：核對與提交之間存在等待時失效

### Rationale Chain
- 0.1.0-W3-286 why: **本 session 的實測事件，非推想**。PM 依規則七三步提交一行 `topic-assignments.txt` 的主題歸屬：精確 `git add` 單一路徑 → `git diff --cached --name-only` 核對（輸出只有該檔）→ 另加規則七版本邊界的過期快照比對（`git show :<path>` vs `git show HEAD:<path>`，確認只差我加的那行）→ 裸 `git commit`。三步全數執行且全數通過。

**產出的 commit 含三個檔案**：`topic-assignments.txt`（正確）、`0.1.0-W3-263.md`（回滾其 `status`／`completed_at`）、`v0.1.0-main.md`（刪除該票的工作日誌完成行）。後者無人修復，僅存於未提交的工作區，直到 PM 事後查證才前推補回。

**兩個條文缺口，各自獨立**：

**缺口一：偵測法是逐路徑的，掃入的卻是未被檢視的路徑。** 規則七版本邊界給的偵測法是對「該路徑」比對 index 與 HEAD。但被掃入的兩個檔案在 `git add` 當下與 HEAD 相同——正因如此它們不出現在 `diff --cached`，也不會有人想到去對它們跑過期比對。**核對的射程是執行者已經懷疑的路徑，而風險來自執行者沒有懷疑的路徑。**

**缺口二：核對有時效，條文未說。** 三步之間隱含「瞬間完成」的假設。本次 `git commit` 遭遇 `index.lock` 競爭，PM 依規則三「短暫重試為預設」加了帶 `sleep 5` 的重試迴圈；HEAD 在該窗口內被並行代理人推進，使核對結果失效。**為滿足規則三而加的重試，使規則七的核對失效**——兩條規則各自正確，組合起來產生缺口。

**為何 P1**：規則七是所有 consumer 專案的並行提交紀律主線，且本次失效路徑不需任何一方違規即可重現。
