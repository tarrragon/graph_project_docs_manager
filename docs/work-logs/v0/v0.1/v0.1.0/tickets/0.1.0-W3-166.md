### Task Reference
- 0.1.0-W3-165 what: 在 AppSnackBar 元件內部加入顯示日誌，使全部呼叫點的使用者可見回饋自動可觀測

### Rationale Chain
- 0.1.0-W3-165 why: `0.1.0-W3-078` 第二次實機驗證需觀測 `denied` fallback 的 SnackBar 是否出現，發現該路徑零日誌——SnackBar 出現與靜默失敗在日誌上完全同形，唯一分辨手段是人眼即時觀察，而 SnackBar 會自動消失、事後無法回溯。該次驗證因此未取得此項。

**用戶裁示（2026-09-09）把修法從呼叫點提升到元件層**：「snackbar 或者 bottoast 這類的提示元件，都可以在元件上加掛 log，更方便除錯，因為那是使用者會看到的終端。」

兩種修法的差別是結構性的，不是工作量：

| 修法 | 涵蓋範圍 | 漏掉的可能性 |
|------|---------|-------------|
| 各呼叫點加 log | 實查為 6 個呼叫點、3 個檔案（`shell.dart`／`gap_report_screen.dart`／`scan_notification_controller.dart`） | 每新增一個呼叫點就可能漏，**而漏掉的那個正好不會被發現**——它沒有 log |
| 元件內部加 log | 全部呼叫點，含未來新增的 | 結構上不可能漏 |

**元件是回饋的終端，因此也該是觀測的終端。** 這與 `INV-FEEDBACK-001` 是同一件事的兩面：該不變式要求元件在每一次互動都發出第一層回饋；把日誌掛在元件內部，等於讓該不變式自己留下可稽核的痕跡。與 `ARCH-GPD-001`「日誌不抵扣使用者回饋」互為反面——該則講日誌有記不代表使用者收到回饋，本案是使用者回饋不留日誌，故它失效時無人知道。

`lib/components/app_snack_bar.dart` 目前 `developer.log` 為 0 行（實查）。
