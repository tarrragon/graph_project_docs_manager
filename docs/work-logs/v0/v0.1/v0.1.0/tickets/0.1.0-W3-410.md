### 逐處查證（三處「本則推導無條文依據句」）

搜尋範圍：`.claude/skills/` 全文 grep 相關關鍵字（排除本三處範例自身），另通讀 `saas-tech-selection` observability.md／reliability.md 全文與元件庫雙向約束方法論〈多形態的契約結構〉〈形態因素先決〉。

| 位置 | 判定 | 理由 |
|---|---|---|
| `dimension-product-notes.md`〈可觀測性維度〉【驗證】 | 階段 2（維持標註） | grep「背景執行緒」「非同步任務」「每次輸出」「輸出時的失敗」於 `.claude/skills/` 範例外零命中；observability.md 通讀無相關句。條文「系統壞了怎麼知道、知道了怎麼定位」只定義失效本身，不含「甲把失效窄化為背景/非同步任務、乙的同步輸出當下失敗屬條文涵蓋範圍」這個判準，無可引原句 |
| `dimension-product-notes.md`〈UI 維度〉【驗證】（SR-1） | 階段 2（維持標註） | 新查得候選條文兩句（皆非本票判定基準所用，記錄供後續參考）：元件庫雙向約束方法論〈多形態的契約結構〉「同一語意可落在不同容器：導覽項這個元件跨形態共用，承載它的容器在手機是收合的抽屜……在平板與桌機是常駐展開的側欄；數值調整這個語意在桌機是可拖動的滑桿，在手機是步進按鈕或輸入彈窗」；〈形態因素先決〉回饋通道列「CLI 以鍵盤輸入與文字輸出為操作方式，依「形態由操作方式定義」原則是合法形態……不因缺圖形介面而被排除在矩陣外」。此二句主詞是「語意」而非「產物」，較 6.6.8 輪引用的〈改寫產物是主路徑〉更貼近本例判定對象，但描述的是「同一語意跨裝置形態（手機/平板/桌機）各自具體化」，本例要判定的是「同一語意在單一 CLI 形態內，樣式數量唯一是否等於失效不存在」，兩者軸不同（跨形態具體化 vs 單一形態內的樣式計數／維護漂移風險），仍推不出本例判定詞，若引用即屬橋接，故不構成階段 1 可引依據 |
| `examples.md`〈拆兩問〉步驟 1 | 階段 2（維持標註） | 通讀 reliability.md，Day one 最小集「CI gate：測試+lint 通過才能 merge」不以有無獨立部署動作為前提，純函式庫同樣需要合併前品質關卡；此發現方向與本例結論「本專案沒有獨立部署動作，該失效在本專案不存在」相反，屬新查得的反向訊號而非支撐句，不構成階段 1 可引依據 |

**候選方向與會使哪類判定改變**：

1. 可觀測性維度：候選新增句——明示可觀測性失效不限於背景/非同步錯誤，同步輸出路徑的錯誤（使用者看到不完整或錯亂結果卻不知原因）亦屬本維度範圍。一旦成立，「甲的推導錯在哪一步」可重新寫回並判合格：甲把失效範圍窄化為背景執行緒/非同步任務、乙的「同步輸出當下的失敗」屬條文涵蓋範圍內。
2. UI 維度：候選新增句——連結「同一語意在單一形態內，即使目前樣式唯一，仍可能因後續各自修改而長出不一致」，或「形態成立即需盤點語意在該形態下的具體樣子清單，不因清單目前長度為 1 而略過」。一旦成立，「輸出樣式唯一是否等於失效不存在」可改判合格，且 examples.md〈UI 維度適用條件不限〉已刪除的 Q1（甲：無是否合格）可望同批一併解決（同一缺口，與 SR-1 為同一根源）。
3. DevOps 拆兩問步驟 1：本項發現的修法路徑與前兩處不同——不是「補一句連結失效定義與判定」，而是可能需要重新檢視步驟 1／2 的結論本身是否成立（CI gate 對純函式庫可能仍是「已存在」或「照預設」而非「無」）。此為內容正確性層級的問題，超出本票「補依據句」範圍，建議另開 ANA 票由 PM 決定是否重新設計本例；若確認 CI gate 對純函式庫同樣適用，本例〈拆兩問〉整體結論需要重新設計，而不只是補一條驗證問句。

**本票結論**：三處皆判定需新判準或需重新檢視內容正確性，無一可於本票階段 1 直接落檔；三處標註「本則推導無條文依據句」與 `examples.md`〈拆兩問〉的可引條文註記維持不變，`dimension-product-notes.md`／`examples.md` 本票未變更任何文字。候選方向已如上記錄，供後續補條文或 ANA 票採用。
