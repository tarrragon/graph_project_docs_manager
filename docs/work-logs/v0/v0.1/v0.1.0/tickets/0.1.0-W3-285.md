## Task Summary

判定 hook_logging 的 project_root 漏接形態是否升級為 framework issue

## Problem Analysis
### 問題根因

`.claude/lib/hook_logging.py` 的 `setup_hook_logging(hook_name, project_root=None)` 提供一個可選 kwarg 用以對齊「日誌落點」與「呼叫端的狀態檔落點」，其 docstring 逐字寫明失效模式。但該 kwarg 預設為 `None`，未傳時回退到 `get_project_root()`（worktree 感知，優先回傳呼叫端所在 worktree）。呼叫端若以 `get_ticket_state_root()`（反向回推主倉庫）讀寫狀態，兩者在 linked worktree 內解析出不同 root，日誌落在無人查閱的 worktree 副本。

直接原因不是「某個呼叫點寫錯」，而是修正手段本身是 opt-in 且預設即舊行為：漏接與正確傳參在型別、回傳值、退出碼、日誌內容上全部相同，只在 worktree 內落點分歧，無任何靜態或執行期守衛。

## 重現實驗結果
### 實驗方法

本票為升級判定，不重現原始 bug（原始 bug 已由 `0.1.0-W3-273` 以三個紅燈重現並修復）。本票要驗證的是三件可被否證的事：(1) 漏接的規模；(2) 錯配呼叫端是否今日仍存在；(3) 涉及資產是否確在 sync 範圍內——第三項是判準二成立與否的唯一機械依據，不可憑印象。

### 實驗執行

1. **漏接規模**：對全 `.claude/` 掃描 `setup_hook_logging(` 與 `init_hook_logging(`，排除 `/tests/` 與定義處，得 164 個呼叫點；同一集合再篩含 `project_root` 者，得 1 個（`hooks/subagent-stop-dispatch-cleanup-hook.py`）。

4. **查重**：`section_comment.py dedup` 跑兩組關鍵字（`project_root` / `hook_logging` / `worktree`），關係判定見 Solution。
