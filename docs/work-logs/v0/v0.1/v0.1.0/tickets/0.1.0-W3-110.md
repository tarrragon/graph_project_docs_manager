## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修改內容

**`lib/components/search_field.dart`**（單向移除，不搬移）

- 刪 `Timer? _debounceTimer` 欄位、`dispose()` 內的 `_debounceTimer?.cancel()`、
  `dart:async` import。
- `_handleTextChanged` 的尾段由「空字串立即呼叫／非空排程 `Timer`」兩分支
  收斂為單一 `widget.onChanged(text)`。無防抖後空字串與非空字串行為相同，
  該分支失去存在理由。
- 組字（IME composing）判斷與 `_lastKnownText` 去重判斷**原樣保留**：前者是
  輸入法正確性、後者濾掉純選取／焦點觸發的同步更新，兩者都不是防抖。
- 四處 dartdoc（檔頭 library doc、slot 表 onChanged 列、onChanged 欄位、
  `_handleTextChanged`）改述為「每次非組字的文字變更即呼叫一次，防抖歸屬
  服務層」。

**`test/unit/components/search_field_test.dart`**

group 更名「互動反應：防抖動與清除」→「互動反應：輸入即通知與清除」，四則
測試處置如下：

| 原測試 | 處置 | 理由 |
|--------|------|------|
| 輸入後 pump 前 onChanged 零次；pump(searchDebounce) 後恰一次 | 改寫為「輸入後 pump 即呼叫一次」 | 原斷言驗的是元件內 Timer 的延遲排程，該行為已不存在 |
| 連續輸入只在防抖動結束後呼叫一次 | 改寫為「連續輸入逐次呼叫，不合併」，斷言收到 a／ab／abc 三次 | 同上；改寫後驗的是「不合併」這個新契約，比刪除保留更多鑑別力 |
| 清除鈕立即呼叫 onChanged 空字串 | 保留，僅刪標題的「不等待防抖動」後綴 | 行為未變 |
| 刪至空立即呼叫 onChanged 空字串 | 同上 | 行為未變 |

**無測試被刪除**。原兩則改寫後仍各自驗得到東西（即時觸發、逐次不合併），
不構成 how.strategy 所述「改寫後失去意義（純測 Timer）」的情形。group 內留
一段註解記錄改寫緣由與原測試驗的是什麼，避免後人把「逐次呼叫」誤讀為回歸。

### Motion.searchDebounce 保留：移除歸屬不等於取消時間契約

token 未刪（`lib/tokens/motion.dart:58` 原樣，`test/unit/tokens/motion_test.dart`
的兩則 300 ms 斷言未動）。兩者是不同層級的決定：

| 決定 | 內容 | 本票是否變更 |
|------|------|-------------|
| 時間契約 | 搜尋輸入停止後 300 ms 才實際過濾（SPEC-003 §2.1 契約類 token） | 否 |
| 歸屬 | 由誰持有那 300 ms 的計時器 | 是：元件層 → 服務層 |

本票換的是**消費者**不是**存廢**。300 ms 這個承諾仍然有效，只是暫時沒有
消費者——直到 `0.1.0-W2-003` 的 provider 接手（見 Spawn Requests SR-1）。
若連 token 一併刪除，等於把「歸屬修正」誤執行成「取消契約」，之後畫面票
將無據可依，且 SPEC-003 §2.1 的條文會指向不存在的常數。

### 不變式 INV-FEEDBACK-001 確認

不受影響。該不變式要求的第一層回饋是「鍵入字元立即出現在輸入框」，由
`TextEditingController` 與 `TextField` 的內建回顯承載，原本就不經
`onChanged` 與 `_debounceTimer` 路徑。移除防抖只影響第二層（過濾結果何時
更新）的觸發時機，且該層在本票後由服務層承擔。

機械佐證：`search_field_test.dart` 中「TestCopy.longToken 輸入後無溢位錯誤」
與 filled 態清除鈕出現的斷言，皆在 `await tester.pump()` 後（不推進假時鐘）
成立，代表回顯與清除鈕顯示不依賴任何延遲。

### Rationale Chain
- 0.1.0-W3-105 why: 現行回饋契約回答的是「怎麼告知使用者」，不回答「按下之後到結果之前這段時間，系統怎麼保護自己與使用者」。用戶於三層歸屬裁示後補充三項（2026-09-08），三項都以**服務類型**為自變數：

1. **不同類型的服務應提供哪些回饋提示** —— 並明指這是**測試驗收的一個指標**，故須可機械檢查，不能只是敘述性建議。
2. **等待期間是否需要阻擋使用者的其他操作、屏蔽畫面輸入** —— 這與提示是兩件事：提示是「告知」，阻擋是「防止」。目前規格兩者都沒有依服務類型的規則。
3. **按鈕類互動元件的防抖** —— 且明確裁示**防抖由服務提供，不是元件提供**。

第 3 點的歸屬與三層模型一致，且推出一條重要不變式：**元件在每一次按下都必須發出第一層回饋，即使服務因防抖而丟棄該次呼叫**。若防抖做在元件層，防抖窗口內的按下會沒有 ripple，使用者看到的是一個沒反應的按鈕——正是 `ARCH-GPD-001` 的形態，只是成因從「服務不可用」換成「服務刻意不執行」。元件永遠回饋，服務決定要不要真的執行。

現況：SPEC-003 §2.1 只有 `Motion.searchDebounce`（300 ms，搜尋輸入用），沒有按鈕類的防抖規則，也沒有規定它實作在哪一層；「阻擋」一詞在 SPEC-003 全文只用於「阻擋狀態元件」（畫面狀態的一種），與「等待期阻擋輸入」不是同一件事，目前後者無任何條文。（來源已完成，結論見 Solution）
