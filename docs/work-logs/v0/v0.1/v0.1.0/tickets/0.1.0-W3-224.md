## Problem Analysis
<!-- Schema[DOC/Problem Analysis]: 選填（若 DOC 起因於缺陷或盤點結論可填）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

Layer 2 維度 5「資源競爭」（`0.1.0-W3-223`，同批次進行中）靠 AI 語意判讀，成本高、
非秒級。Layer 1 需要一個機械檢核在無思考成本下先篩：spec 的 FR 段落是否提及事件流
但 domain-map 的通道表無對應標定。既有 `check_domain_coverage.py` 已做「FR 對
domain-map §7 覆蓋表」的同形比對，改造它新增第二種比對（通道表）而非新增工具。

### 設計決策

1. **章節定位以標題文字、不依編號**：實查本專案 `docs/domain-map.md` 發現既有
   `## 2.5 三個易混淆詞的定義` 已佔用「2.5」編號，證實範本注記「不佔用既有 §3-§7
   編號」不足以保證專案層無衝突——`_extract_section_by_title` 用正則比對標題文字
   （「通道與協調圖」「到達類別與級別」），以標題階層（`#` 數）決定章節邊界，不比對
   數字編號。
2. **訊號詞單一常數**：`EVENT_FLOW_SIGNAL_WORDS` 定義於 `check_domain_coverage.py`，
   逐字對齊 `0.1.0-W3-223` 寫入 SKILL.md 維度 5 掃描說明的清單（事件、通知、提示、
   背景、排程、佇列、推送、webhook、isolate），SKILL.md 新增段落引用「與 Layer 2
   維度 5 共用同一份清單」，程式碼常數為權威來源。
3. **FR 段落切分重用 `check_api_surface.split_fr_sections`**：避免第三份切段邏輯，
   同目錄 sibling import（scripts 目錄本身已在 sys.path，直接執行與測試皆可解析）。
4. **命中判定**：FR 段落文字（含標題）命中任一訊號詞（不分大小寫）即列入待查集合；
   在 domain-map「通道與協調圖」節之「到達類別與級別實例」子表（用同一 title-based
   定位）用既有 `extract_fr_ids`（token 展開）找該 FR 是否被引用；未被引用者列為
   提醒，exit code 沿用既有慣例（0=通過、1=有缺口，非阻擋性質同 API surface 檢核）。
