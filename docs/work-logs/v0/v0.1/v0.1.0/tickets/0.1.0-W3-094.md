## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因

`nav_item.dart` 與 `project_switcher_entry.dart` 皆以 `SizedBox(height: LayoutSize.hitTargetMin)`
（token 值 28）包住內容。兩者內容的固有高度都是 33：圖示 `LayoutSize.iconLg`（17）加上下內距
2 × `Space.sm`（8 + 8）。`SizedBox` 給子項的是緊約束，`Padding` 只能把 28 − 16 = 12 傳給內層
`Row`，圖示與文字被壓進 12 邏輯像素內，超出的 5 個像素靜默裁切。

實測數字（本票新斷言的紅燈訊息）：內容固有高度 17.0，實得 12.0，兩元件 × zh/en × 兩視窗尺寸
共 8 個斷言一致。

`LayoutSize.hitTargetMin` 的 dartdoc 與 SPEC-004 §1 皆定義它為「可點元件最小尺寸不得小於之」
——命中區**下界**。以它當固定高度等於把無障礙下限反過來當排版上限用。

### 測試為何全綠

`expectNoOverflow`（`test/helpers/pump_harness.dart`）的實作是 `expect(tester.takeException(), isNull)`，
只攔得到會拋 `FlutterError` 的 `RenderFlex` overflow。`SizedBox` 對超出的子項是靜默裁切、不拋例外，
故 `nav_item_test.dart` 原有的八個以上「不溢位」測試（zh/en 六個 key × 兩種視窗尺寸）對本形態零鑑別力。

兩檔原有的高度斷言同樣無鑑別力：`nav_item_test.dart` 的「高不小於 hitTargetMin」與
`project_switcher_entry_test.dart` 的 `greaterThanOrEqualTo(hitTargetMin)`，在高度被釘死為 28 時恰好
邊界成立。

另一層遮蔽：widget test 的測試字型每個字符高度恰等於 `fontSize`，中文字形較高的 ascender／descender
只在實機出現。因此任何以文字實際高度為對象的斷言在測試環境都驗不出來——本票的斷言改驗造成裁切的
**結構**（容器高度小於內容固有高度），與字型無關，故在測試環境同樣紅燈。

### 影響範圍

側欄是六個畫面的常駐入口，兩元件的裁切在每一個畫面都可見。同形態在 `lib/` 內至少還有四處未驗證
（`search_field.dart:133`、`segmented_control.dart:146`、`filter_dropdown.dart:297`、`toolbar.dart:81`），
已建 0.1.0-W3-123 追蹤。

### 相關 Error Pattern

`PC-BAL-010-verification-channel-insensitive-to-target-phenomenon`（驗證通道對目標現象不敏感）為同族：
測試通道（`takeException`）量的軸與缺陷所在的軸（容器對內容的約束）不同，故恆為綠。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### 修復

| 檔案 | 改動 |
|------|------|
| `lib/components/nav_item.dart` | `SizedBox(height: LayoutSize.hitTargetMin)` → `ConstrainedBox(constraints: BoxConstraints(minHeight: LayoutSize.hitTargetMin))` |
| `lib/components/project_switcher_entry.dart` | 同上（同形態） |

改為下界約束後，高度隨內容固有值增長至 33，命中區下界仍被保證，SPEC-004 4.7／4.8 尺寸契約的
「尺寸模式：高固有」與「最小命中區」同時成立。兩處各加註解說明「`hitTargetMin` 是命中區下界而非
高度上界」，避免後續再被改回固定高度。

### 新增斷言

`test/helpers/pump_harness.dart` 新增 `expectNoVerticalClip(tester, content)`：取 `content` 節點的
`getMaxIntrinsicHeight(box.size.width)` 與其實得高度比較，實得較小即代表被祖先壓縮而靜默裁切。

設計要點：

- **`content` 必須落在固定高度容器之內**（本票用最內層 `Row`）。對容器本身求固有高度會被它自己的
  `additionalConstraints` 夾回同一個值，斷言恆成立而沒有鑑別力——這是本斷言唯一的誤用方式，已寫入
  dartdoc。
- **驗結構而非驗字型**。文字裁切在 widget test 裡不會自行顯形（測試字型字符高度恰等於 `fontSize`），
  故不以文字高度為斷言對象。
- 容差 `_kLayoutEpsilon = 0.01` 邏輯像素，遠小於任何可見裁切（最小可見量為 1 邏輯像素）。

未採用「再加一個 `expectNoOverflow`」：那正是漏掉本缺陷的斷言。

### 斷言先紅燈驗證

修元件**之前**單獨執行新斷言，兩檔皆紅：

- `nav_item_test.dart --plain-name 內容不被固定高度裁切` → 4 紅（zh/en × min/design）
- `project_switcher_entry_test.dart --plain-name 內容不被固定高度裁切` → 4 紅（zh/en × min/design）
- 紅燈訊息一致：`內容固有高度 17.0，實得 12.0`

修元件之後同樣命令全綠。
