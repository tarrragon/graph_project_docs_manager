## Solution
<!-- Schema[DOC/Solution]: 免填（DOC 類型以變更摘要取代）（.claude/pm-rules/ticket-body-schema.md） -->
兩份文件各補一段界線說明，並互指對方為路由目標。內容取自 `0.1.0-W3-092` 結論 A（本就不同構，明訂分工），非重新裁定。

**一、`.claude/skills/tdd/references/test-object-catalogue.md`（v1.1.0 -> v1.2.0）**

於「三、契約欄位表」新增子節〈與追溯矩陣的界線〉，與既有的〈與元件契約欄位表的結構性差異〉並列（同為「本目錄與另一份看似重疊的產出如何分工」）。內容：五維度對照表（問什麼／用途／單位／消費者／生命週期）、三條 AND 進入判準、三類不進的來源類別及其真正的權威載體、以及不寫此界線會發生的兩種相反誤讀。

路由寫法遵循規則 8：主路由指向框架權威 `.claude/skills/doc/doc_system/core/tracking_schema.py` 的 `TRACEABILITY_SCHEMA`，`docs/traceability.yaml` 以「該 schema 所定義形狀的專案檔案」形式提及，不以專案路徑作為唯一定位。單位欄不寫死軸數，改述「該 schema 各軸各自定義」（規則 10）。

**二、`docs/traceability.yaml` 頭部註解**

原第二段只說「兩者是不同形狀的兩份產出」並把落差指向某張票的 Solution，讀者從註解本身讀不到分工內容，仍須另開一份 ticket 才知道界線在哪。改寫為自足的界線說明：兩者各自的問題／消費者／生命週期、三條 AND 判準、三類不進者的權威載體，末句明寫「本檔缺某個測試對象類別不是缺口，是分工」，並回指測試對象目錄。schema 權威段落未動。

**順帶修正（規則 10）**：原註解寫「六來源類別、九欄契約」，該目錄 v1.1.0 已追加第七個來源類別，此計數在寫下後即靜默失效——正是規則 10 所治的形態。改為不帶數字的描述（「以規格條目為單位、按來源類別展開」）。

**驗證**：`yaml.safe_load` 解析通過，頂層鍵仍為 `version` / `mappings` / `domain_bundle_tests` / `data_contract_tests` / `runtime_tests` / `last_updated`，未因註解改寫而變動。雙向路由各存在一處。
