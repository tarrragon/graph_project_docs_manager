### 一、測試對象的單位判定

### 候選方案

| 方案 | 單位 | 優點 | 缺點 |
|------|------|------|------|
| (a) UC 場景 | 每個 UC 場景（主成功＋替代＋例外） | 與 doc-handoff GWT 映射直接對接 | UC 只有 6 個、39 個 FlowStep；元件層、token 層、平台契約無法以 UC 場景為單位 |
| (b) 元件 | SPEC-004 的每個元件 | 已有完整目錄（SPEC-004 §4） | 與 SPEC-004 的測試契約欄**完全重複**——SPEC-004 每個元件的「測試點」子節就是逐元件測試契約 |
| (c) 規格條目 | 每個可驗證的規格宣告（FR、UC 步驟、狀態轉換、互動規則、token 不變式、平台契約） | 覆蓋全部規格層級；每個測試對象有唯一的規格來源；與既有 SPEC-004 測試契約不重複 | 粒度較細，需聚合機制 |

### 結論：方案 (c) 規格條目

**與既有 spec 不重複的論證**：

SPEC-004 的測試契約欄回答的是「這個元件要怎麼測」（全變體全狀態渲染、每種尺寸不溢位、最長文案截斷）。本目錄回答的是「從規格推導，整個專案要測哪些東西」——涵蓋六個來源類別，SPEC-004 元件測試只是其中之一，且本目錄對元件的記載粒度是「規格來源 + 驗證形態 + 是否已有測試」，不重複 SPEC-004 的逐欄契約。

**六個來源類別**：

| 來源類別 | 規格權威 | 測試對象舉例 | 既有測試側目錄？ |
|---------|---------|-------------|----------------|
| 1. 畫面狀態轉換 | SPEC-001 每行 | 「載入中 → 正常」轉換的進入條件與退出路徑 | 無 |
| 2. UC 行為場景 | UC-01~06 FlowStep + 替代/例外 | 「UC-01 步驟 3：選擇資料夾後進入載入」 | 無 |
| 3. 互動規則 | SPEC-003 各節 | 「Esc 收合浮層，焦點回到入口」 | 無 |
| 4. 元件契約 | SPEC-004 §4 逐元件 | 「AppButton 全變體全狀態渲染不溢位」 | **有**（SPEC-004 測試契約欄） |
| 5. Token 不變式 | SPEC-002 + `lib/tokens/` | 「AppColors.accent 值 = token 定義值」 | 部分有（3 個 token 測試） |
| 6. 平台契約 | CLAUDE.md §6 + tech-decisions | 「App Sandbox 關閉」「minSize 960x640」 | 部分有（2 個契約測試） |

本目錄承載**全部六類**的測試對象索引。第 4 類不重複 SPEC-004 的契約欄位——本目錄只記「來源 → 測試」的映射行，不記逐欄契約值。

### 二、契約欄位表

每個測試對象的記載欄位：

| 欄位 | 問句 | 缺失後果 |
|------|------|---------|
| **對象** | 這個測試對象是什麼？用唯一識別名標記 | 無識別名 → 測試票無法引用規格來源 |
| **來源規格條目** | 規格中哪一條宣告了這個對象的行為？格式：`{SPEC-ID} §{章節}` 或 `{UC-ID} 步驟 {N}` | 無來源 → 測試與專案需求脫鉤，「設計出與專案無關的測試」的結構成因 |
| **來源類別** | 六類之一（畫面狀態 / UC 行為 / 互動規則 / 元件契約 / token 不變式 / 平台契約） | 無類別 → 不知該從 layered-test-strategy 五層的哪一層選測試方法 |
| **測試形態** | 該對象的測試方法：unit / widget / integration / 實機驗證 / golden / 組合（多種以逗號分隔） | 無形態 → 預設全部 unit test，跨元件串接與平台行為漏測 |
| **驗證形態** | fake / 實機 / 兩者（W3-074 A3 定義的正交屬性） | 無驗證形態 → 跨邊界功能的平台端事實漏驗（W3-074 暴露的根因） |
| **斷言來源** | 斷言的預期值從哪裡來？格式：`{SPEC-ID} §{章節} {具體條文}` | 無斷言來源 → 斷言值為測試設計者自行判斷，與規格脫鉤 |
| **fixture 需求** | 該測試需要什麼前置條件？格式：假資料集名 / pump harness / 特定視窗尺寸 / ProviderScope override | 無 fixture → 每個測試自行建立 fixture，不一致且難維護 |
| **跳過條件與理由** | 何時不測？依 layered-test-strategy 跳過條件 + SPEC-004 豁免清單。非空值代表合法跳過 | 無跳過條件 → 無法區分「還沒測」與「不需要測」 |
| **反例** | 什麼情境會有人誤把這個測試對象歸入此類？ | 無反例 → 來源類別邊界模糊時，重複測試或漏測 |

### 三、齊全定義

### 可機械檢查的完成判準

一份測試對象目錄可被視為「齊全」，須同時滿足四條：

| 條件 | 機械檢查方式 | 來源 |
|------|------------|------|
| C1：覆蓋性 | SPEC-001 每個狀態的每條退出路徑在目錄有對應行；UC-01~06 每個 FlowStep 有對應行；SPEC-003 每個編號互動規則有對應行 | 計數比對：目錄行數 >= 各 SPEC/UC 的可驗證條目數之和（扣除合法跳過） |
| C2：欄位完整 | 目錄每行的每個欄位非空（跳過條件可為空，代表必測） | 逐行逐欄非空檢查 |
| C3：來源唯一 | 每行的「來源規格條目」不重複（同一條規格條目不被兩行引用） | distinct 檢查 |
| C4：跳過合法 | 每個「跳過條件與理由」非空的行，其理由引用 layered-test-strategy 跳過條件表或 SPEC-004 豁免清單的具體條款 | 理由引用存在性檢查 |

### 與既有覆蓋率判準的關係

| 既有判準 | 來自 | 測的東西 | 關係 |
|---------|------|---------|------|
| 行為場景覆蓋率 100% | layered-test-strategy UseCase 層 | 所有業務場景都有測試 | **補充**——行為場景 100% 回答「量」（是否全部有測試），本齊全定義回答「質」（每個測試的規格來源、斷言來源、形態是否填寫完整） |
| 分支覆蓋率 100% | layered-test-strategy Domain 層 | 每個分支代表一個業務決策 | **測不同的東西**——分支覆蓋率是程式碼層級指標（code coverage），本齊全定義是規格層級指標（spec-to-test traceability） |
| 整體新增程式碼 80% | layered-test-strategy | 扣除跳過層後的基線 | **不衝突**——程式碼覆蓋率仍然適用，本齊全定義在其之上增加規格追溯維度 |

**結論**：本齊全定義**補充**既有覆蓋率判準。既有判準回答「測了多少」（量化），本齊全定義回答「每個測試是否對應到規格、對應是否完整」（質化追溯）。不取代。

### 五、派發語言：測試票 how 的目標句型
