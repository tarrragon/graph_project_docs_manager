## Solution
### 修復方式

- `hooks-test-gate-hook.py` 把驗證階段抽成 `_verify_touched_hooks`，範圍從 `_resolve_test_paths` 到 `emit_hook_output`，原有邏輯不變。
- `main()` 在確認本次 commit 觸及 hook 檔之後，用單一的 `try/except Exception` 呼叫 `_verify_touched_hooks`。捕到例外時：
  - 寫 `logger.critical` 與 stderr。
  - 輸出 deny，reason 由 `_build_verification_error_message` 產生，內容包含例外型別與訊息、「無法驗證等同未通過」，以及逃生路徑：gate 只攔 Claude 的 Bash 工具，需要時改在使用者終端機執行該 commit。
- 偵測階段（從 payload 解析到判定 touched）沒有改，維持 fail-open。
- 新增 `_log_segment_timing_safely`：計時日誌出錯時只寫 warning 與 stderr，不改變判定。
- 沒有新增任何環境變數 bypass。hook 檔沒有版本標記，所以沒有升版。
- 實作 commit 770078b30（basil-hook-architect，在 worktree 完成），由 PM 合併。

### 自檢結果

PM 審查 diff：
- 邊界只有一個，偵測與驗證的分界寫在註解裡。
- deny 之後 return 0，符合 PreToolUse 以 stdout 的 JSON 傳達 deny 的契約。

已知限制（PM 更正執行者的描述）：deny 路徑上的 `emit_hook_output` 如果自己拋出例外（例如 stdout 管線中斷），例外會往上傳到 `run_hook_safely`，以 exit 1 結束。在 PreToolUse 裡，exit 1 等於放行，不是阻擋。這種情況屬於 stdout 失效的極端邊界，盤點表也已列出。本票不處理。

### 實地觸發（PM，main d0dac9873）

- 在主 repo 用 synthetic PreToolUse payload（`git add .claude/hooks/uv-tool-ownership-guard-hook.py && git commit -m x`）觸發 gate。
- 結果：rc=0、stdout 0 bytes，屬於綠燈放行。gate 日誌記錄「目標測試結果: returncode=0」與「所有觸及的 hook 檔對應測試皆通過，允許」，執行 15.96 秒。
- `_liveness` 在 14:14:35 有一筆 hooks-test-gate 紀錄，代表 runtime 確實載入並執行了這個 hook。
- 合併本票時，gate 也對自己的修改跑了測試並放行。

### Phase 4 評估

- 重構需要：否
- 技術債務：偵測階段的輸入防禦由 W1-036.3 承接；`git diff --cached` 失敗時沒有可見訊息，由 W1-036.2 承接。
- 程式碼品質：A
- 結論：把驗證階段抽成一個函式，讓單一邊界成立，main 的可讀性也變好。不需要重構。
