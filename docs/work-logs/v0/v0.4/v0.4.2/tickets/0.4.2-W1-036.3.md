## Solution
### 修復方式

- `main` 在偵測階段對三個輸入加型別守衛：input_data 必須是 dict、tool_input 必須是 dict、command 必須是 str。不符合時寫一行 `logger.info`（含實際型別），然後 return 0。
- `_is_host_repo_commit` 的 except 從只接 OSError，擴大為 `(OSError, RuntimeError, ValueError)`，遇到時回傳 False。RuntimeError 對應符號連結迴圈，ValueError 對應路徑含 NUL。
- 偵測階段維持 fail-open。驗證階段的 fail-closed 邊界（W1-036.1）與 diff 失敗提醒（W1-036.2）都沒有更動。
- 實作 commit f7cc02e6c（basil-hook-architect，在 worktree），由 PM 合併。

### 自檢結果

- PM 審查 diff：改動只有三個型別守衛和擴大的 except，沒有碰到驗證階段。新增行經規則 8 grep 檢查，0 命中。
- 執行者回報的基線數字有誤，已核對：它寫的是 5347，但 main 在 W1-057 合併後的預設套件是 5350 passed，再加上本票新增的 6 項，正好是 5356。

### 實地觸發（PM，main，合併後）

用 synthetic PreToolUse payload 送入兩次：
- 正常 payload（git add uv-tool-ownership-guard-hook.py && git commit）：rc=0，stdout 為空，沒有 CRITICAL。日誌記錄「所有觸及的 hook 檔對應測試皆通過，允許」。
- 異常 payload（tool_input 是字串）：rc=0，沒有 CRITICAL。日誌記錄「tool_input 型別非 dict（str），偵測階段 fail-open 放行」。修前同樣的輸入是 exit 1，且有 CRITICAL。

兩次觸發都在 `_liveness` 留下 hooks-test-gate 紀錄（共 2 筆）。可執行位為 -rwxr-xr-x（W1-036.1 已確認）。

### Phase 4 評估
