## Problem Analysis

### 問題根因

測試的日誌根目錄在被測程式內才解析，而現行隔離只改其中一種解析點。三種繞過路徑，各有已驗證的來源：

| 路徑類型 | 機制 | 受影響範圍 |
|---------|------|-----------|
| P1 subprocess hook 繼承環境 | `isolate_hook_logs` 只 monkeypatch 同一程序內 `lib.hook_logging.get_project_root`；測試以 `subprocess.run` 啟動 hook 時，子程序重新解析根目錄（繼承的 `CLAUDE_PROJECT_DIR` 或 cwd 的 `git rev-parse`），落在真實 repo。同型機制見 IMP-BAL-015 | hooks 套件 19 個目錄加 `_liveness` |
| P2 被測模組自行解析且不讀 `CLAUDE_PROJECT_DIR` | `ticket_system/lib/identity_guard.py` 的 `_resolve_identity_log_path` 只認 `HOOK_LOGS_DIR`，否則 `git rev-parse --show-toplevel`；`ticket_system/tests/conftest.py` 的 autouse 設了 `HOOK_LOGS_DIR`，但 `tests/` 樹沒有 | ticket 套件 `identity-guard` |
| P3 worktree 偵測優先於環境變數 | `lib.hook_base.get_project_root` 的 linked worktree 偵測排在 `CLAUDE_PROJECT_DIR` 之前；ticket skill 根 conftest 只設 `TICKET_SYSTEM_TEST_ISOLATION`（ticket 路徑旗標），未設 hook 側的 `HOOK_TEST_ISOLATION`，in-process 載入的 hook 在 worktree 內寫進 worktree 根 | 僅 linked worktree 內跑 ticket 套件：`agent-ticket-validation`、`needs-context-listener-hook`、`ticket-md-auto-commit`、`test` 四目錄（另有 `acceptance-gate`，與 hooks 套件重疊） |

另有 `markdown-formatter`（只含 `.cleanup_trigger` 的空目錄）：`lib/tests/test_w2010_import_normalization.py` 以 script 模式 import `lib/markdown_formatter.py`，模組載入時即建立日誌目錄，屬 P1 變體。

**liveness 的特殊性**：`mark_hook_entry` 以 `CLAUDE_CODE_SESSION_ID` 命名索引檔。測試繼承呼叫者的 session id，所以測試記錄併入呼叫者那個真實 session 的 `_liveness/<session_id>.jsonl`，而非獨立檔。

### 2. `_liveness` 的 E2 結論（歷史索引檔是否混有測試記錄）

| 特徵 | 實測的測試特徵 | 歷史檔中的對應 |

### 3. 隔離方案比較

評估軸：洩漏覆蓋、對既有路徑斷言測試的誤傷、consumer 可攜性、產品碼改動、既有實測依據。

| 方案 | 做法 | 覆蓋 | 誤傷既有路徑斷言測試 | consumer 可攜性 | 結論 |
|------|------|------|-------------------|---------------|------|
| A lib 單一解析點 | `lib/hook_logging` 新增 `resolve_hook_logs_dir()` 讀測試專用環境變數，僅當解析根等於 lib 自身所在 repo 時重導；各處改呼叫 | 只涵蓋走該 API 的路徑；29 支 hook 腳本、`git_utils`、`common_functions`、ticket 的 `git_ops` 等各自拼 `hook-logs`，需逐一遷移，遷移前仍洩漏 | 低（守衛限定真實根）；遷移每一處都是產品碼改動，各有回歸面 | 需同步 lib 改動，conftest 與產品碼兩端要同版 | 覆蓋靠遷移完成度，工作量最大，風險在產品碼 |
| B conftest session 級專案根重導 | session 級 fixture 設 `CLAUDE_PROJECT_DIR` 指向含 `CLAUDE.md` 的 tmp，並設 `HOOK_TEST_ISOLATION=1`（略過 worktree 偵測）。子程序與 in-process 皆繼承 | **實測 hooks 套件零洩漏**，含自行拼路徑的 hook | **實測 5 項 / 5326**，皆為斷言解析行為本身；以 `real_project_root` opt-out fixture 處理 | 只動 conftest，`sync` 後 consumer 直接得到；不依賴 lib 版本 | **採用** |
| C 哨兵（事後偵測） | 套件結束時比對 hook-logs 前後清單並使套件失敗 | 只偵測不預防 | 無 | 可攜，但在 PM session 內並行的真實 hook 也在寫 hook-logs，全目錄比對會誤報 | 單獨不可行；以 `pytest-` 前綴 session id 縮窄為「前綴檔存在與否」後可作為 B 的棘輪（子票 3） |
| D 逐呼叫點注入 | 每個 `_run_hook` 類 helper 注入環境 | 57 檔、111 處 `subprocess` 呼叫、23 個自訂 helper，漏一處即洩漏 | 低 | 每個新測試都要記得，PC 型重複 | 維護面大於收益，淘汰 |
| E 符號連結換出 hook-logs | session 期間把真實 `hook-logs` 換成 tmp 符號連結 | 全覆蓋 | 低 | 可攜 | 淘汰：同時段真實 session 的 hook 日誌被吞（違反 quality-baseline 規則 4），測試被 kill 時符號連結殘留 |
