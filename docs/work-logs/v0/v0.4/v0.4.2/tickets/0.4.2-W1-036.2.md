## Solution
### 修復方式

- `_touched_hook_filenames` 新增選用參數 `diff_failures`，舊有的 3 參數呼叫不受影響。`git diff --cached` 失敗時，除了原本的 `logger.warning`，另外寫 stderr，並把失敗原因記進 `diff_failures`。
- 新增 `_build_diff_failure_reminder`，提醒內容說明三點：staged 清單沒有驗證過、可能有 hook 檔被漏判、這次放行不阻擋。
- `main` 依情況處理：
  - 沒有任何觸及檔：輸出提醒後放行。
  - 有從命令字面推導出的觸及檔：提醒併入 `_verify_touched_hooks` 的 reminders，維持單一輸出。測試真的紅燈時照樣 deny。
- 0.4.2-W1-036.1 的驗證階段邊界沒有更動。
- 實作 commit d3db3caa5（basil-hook-architect，在 worktree 完成），PM 合併為 e895dab05。第一次合併遇到短暫的 index 寫入失敗，當時沒有 MERGE_HEAD、也沒有暫存內容，重試後成功。

### 自檢結果

PM 審查 diff：
- 失敗時維持 fail-open，但提醒對使用者可見，同時寫 stderr、日誌與 additional_context，符合 quality-baseline 規則 4。
- 新參數是選用的，不影響既有呼叫端。
- 新增行做過規則 8 grep，0 命中。

### 實地觸發（PM，main e895dab05）

- 在主 repo 用 synthetic PreToolUse payload（`git add .claude/hooks/uv-tool-ownership-guard-hook.py && git commit -m x`）觸發。
- 結果：rc=0、stdout 0 bytes，屬正常路徑的綠燈放行，git diff 成功時不會出現提醒。gate 日誌記錄「所有觸及的 hook 檔對應測試皆通過，允許」，耗時 4.54s。
- `_liveness` 在 14:57:51 有一筆 hooks-test-gate 紀錄，可執行位為 -rwxr-xr-x。
- git diff 失敗的路徑，已由執行者在 clone 中用必然失敗的 git shim 重現（見 Test Results）。

### Phase 4 評估

- 重構需要：否
- 技術債務：無新增。偵測階段的輸入防禦由 W1-036.3 承接。
- 程式碼品質：A
- 結論：提醒沿用既有的 reminders 管道合併輸出，沒有另開輸出路徑，不需要重構。
