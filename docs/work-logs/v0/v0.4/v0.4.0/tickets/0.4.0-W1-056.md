# Execution Log

## Task Summary

GRAPH_EDGE_TYPES 每個邊型新增正向基數欄位（值域 one／many），表示節點的 forward_field 可宣告一個或多個終點；JSON 匯出（edge_types）同步帶出。provenance（source_proposal）設為 many：source_proposal 可寫清單，寫純量時視為一項清單。spawn（source_ticket）、blood（parent_id）、discovery（discovered_during）為 one；其餘清單型欄位為 many。

---

## Problem Analysis
### 問題根因

`GRAPH_EDGE_TYPES` 只宣告邊的方向與欄位名稱，沒有宣告正向欄位可以有幾個終點，所以「單值／多值」只能從 frontmatter 的寫法或讀取端的程式去猜。依用戶的 WRAP 裁決（tech-decisions 最後一則補記），provenance（source_proposal）必須允許多值，例如 UC-01 同時來自 PROP-003 與 PROP-002。

### 影響範圍（PM 讀碼確認，2026-09-30）

- 框架端讀取 `source_proposal` 的位置只有兩處，都不涉及形狀：`doc_system/core/constants.py` 的欄位常數，以及 `tracking_schema.py` 邊型表的 forward_field。
- 本專案 App 端：`lib/schema/type_table_json_codec.dart` 只讀 node_types，沒有讀 edge_types，所以新增欄位不會影響目前的 App 解析。App 內建副本 `assets/schema/builtin_tracking_schema.json` 的契約測試（`builtin_schema_version_contract_test.dart`）只比對 App 內兩份資產的產生版本是否一致，不和框架 JSON 比對，本票不需要同步副本。App 端要消費這個欄位，是 SPEC-007 FR-01／FR-04 實作票的範圍，不在本票。
- `tracking-schema-json-staleness-guard` 會要求 schema.py 變更時同批重新產生 JSON，執行者需照做。

### 框架問題判準（兩條 AND）

1. 抽象可攜：是。邊型表的形狀宣告是所有 consumer 共用的 schema；「一個節點可有多個來源提案」與專案無關。
2. 根源在 `.claude/` 通用資產：是，根源在 `.claude/skills/doc/doc_system/core/tracking_schema.py`。

### 查重

由 e1 指定在 #98（doc skill 建立端與驗證端各自實作契約）附觀測，公告 `source_proposal` 形狀變更。這屬於契約宣告權威化，是 #98 所在家族的延伸，關係判定為引用加附加觀測。本專案是 doc skill 上游，實作在本專案進行。
