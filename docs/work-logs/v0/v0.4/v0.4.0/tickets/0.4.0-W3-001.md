- 0.4.0-W1-049 what: 依 0.4.0-W1-048 三項裁決改寫路徑 C 步驟 3〈原生佈局掃描〉與其框架對應段：(1) 頁面層任何多子件佈局都計為一個排列關係，不論子件是元件庫元件或原生葉節點；(2) 多子件佈局以結構定義——接受子件清單的節點（Flutter：帶 children 參數或以 builder 產生多子件者），列舉降為例示並補疊層（Stack／IndexedStack）與捲動列表（ListView／GridView／CustomScrollView／Sliver）、Table；(3) 頁面層的單子件佈局輔助一律計入，依屬性歸屬轉置：填滿／空間分配（Expanded／Flexible）→ 容器具名 slot，間距／對齊／畫面邊距（Padding／Align／Center／當間隔的 SizedBox）→ 容器負責或容器參數，單一元件固定尺寸 → 元件尺寸變體（記為元件契約缺口）。另寫明與方法論『原生元件禁用對照表』的分工：原生葉節點本身屬元件層違規，其所在排列屬容器層。

### Rationale Chain
- 0.4.0-W1-048 why: 本專案是 component-contract-design 的開發上游（CLAUDE.md §1）。判準缺口使 consumer 的發版守衛無法定義：缺口 1 會把合理的單子件伸縮提示誤判為違規或整批放過，缺口 2、3 使計數系統性偏低（守衛失效方向是放行，E2 同型）。方法論〈禁自製元件〉已把『頁面以原生佈局原語排列元件』定為違規，掃描判準是它的偵測面，偵測面比判準窄即為漏報。
- 0.4.0-W1-049 why: 0.4.0-W1-048 用戶裁決（缺口 1 經 WRAP）。佈局輔助留在呼叫端有兩個結構問題：容器不變式（如 Panel『恰一個子件填滿剩餘高』）無法由容器驗證；Expanded 等 ParentDataWidget 須為 Flex 直接子件，頁面因而依賴容器內部是 Flex 且不再包層，容器改內部結構時頁面於執行期拋 Incorrect use of ParentDataWidget、編譯期無訊號。
