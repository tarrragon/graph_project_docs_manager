# Execution Log

## Task Summary

W1-052 的 _stage_appended_blob 以「HEAD 版本 + 本次追加行」提交 append-only 檔。兩個寫入者交錯追加且各自提交時，HEAD 行序為 A、B，工作區行序可能為 B、A，檔案在 git status 持續顯示為已修改，直到有人整檔提交

---

## Problem Analysis
### 問題根因

`git_ops._stage_appended_blob` 以「old_head 版本 + 本次 text」組出提交內容，行序由**提交順序**決定；工作區檔案由寫入端 `_append_line`／`append_topic` 以 `'a'` 模式追加，行序由**追加順序**決定。`get_ticket_state_root()` 使所有寫入者（含 linked worktree 內的 session）寫同一個主倉庫工作區檔，因此兩個寫入者的「追加順序」與「提交順序」一旦相反，HEAD 與工作區即成為同一行集合的不同排列，`git status` 持續顯示 ` M`。

發生條件（實驗 E1 已窮舉兩寫入者 6 種合法交錯驗證）：兩個寫入者**都在任一方提交前完成追加**，且**先追加者後提交**。create 流程中追加發生在 rc==0 之後、提交發生在 Context Bundle 抽取之後，兩者之間有一段可被並行 create 插入的窗口。

漂移不會自癒：之後任何乾淨的 append 提交都以 HEAD 為基底延續錯位（E2），只有整檔提交能消除。

### 影響範圍

已驗證的事實：
- 受影響檔：`docs/work-logs/topic-assignments.txt`、`docs/work-logs/topics-registry.txt`（唯二經 `append_lines` 提交的檔，呼叫端僅 `commands/create.py`）。
- 內容無損：漂移時工作區與 HEAD 的行集合（multiset）相同，只有順序不同；沒有行被吸入或遺失。
- 讀取端對漂移行的順序不敏感（判定見下節「讀取端語意」）。
- 可見後果只有流程層：持續的 ` M` 狀態，與 W1-052 要消除的「未提交主題行」外觀相同，會被誤認為他人遺留；整檔提交時 diff 呈現「刪一行、加同一行」的搬移。
- 實際頻率：W1-052（b2898346b）之後觸及這兩個檔的提交共 49 筆，沒有任何一筆含刪除行（即沒有發生過漂移後的整檔修正）；主 repo 目前這兩個檔 status 乾淨。觀測期約 10 小時，屬低頻邊界。
- W1-067（同步改讀當下 HEAD）只作用於 index 平面：它消除「同步順序顛倒時 index 比 HEAD 舊」造成的 `MM`，工作區對 HEAD 的漂移不受影響，仍為 ` M`（實驗 E4）。

仍未驗證的假設：
- 持續 ` M` 是否會擋下其他流程（例如 worktree 合併守衛對主工作區髒檔的檢查）未實測；本結論不依賴此假設。

### 讀取端語意

全部讀取端都經兩個函式讀檔，沒有其他程式直接開這兩個檔（grep `.claude/` 非測試、非 worktree 副本）：

| 讀取函式 | 順序語意 | 對漂移的敏感度 |
|---------|---------|---------------|
| `topic_assignments.list_assignments()` | 同一 ticket_id 多筆時取最後一筆（改派） | 不敏感：漂移的兩行來自兩次 create，ticket_id 必不同（`append_assignment` 拒絕已存在的 id）；改派行由 `topic_backfill --reassign` 寫入，不經 `append_lines` 提交，不會成為漂移的一方 |
| `topic_assignments.list_assignment_history()` | 同一 ticket_id 依寫入順序 | 同上，不敏感 |
| `topic_registry.list_topics()` | 正規化去重、保留首次出現的原始寫法、維持檔案順序 | 僅在兩個並行 create 同時新增「正規化後相同」的主題名時，首次出現的寫法會不同（前提是 `append_topic` 的讀後寫 TOCTOU 先發生，屬另一個問題）；其餘情況不敏感 |

下游消費端：`track_topics` 以 `sorted()` 排主題、`track_board` 以 `_topic_sort_key` 排序、`track_runqueue` 只做 dict 查詢、`topic_inference.build_topic_file_clusters` 做集合聯集；檔案順序只影響 `--topic` 錯誤提示「既有主題：」的列舉順序（顯示用）。

結論：行序對讀取結果沒有語意；漂移的代價只在 `git status` 的持續 ` M`。

**E3：CAS 競態（A 讀 old_head 之後 B 先完成提交）**

- A 第 1 次提交：`failed`，錯誤為 `cannot lock ref 'HEAD': is at <B 的提交> but expected <舊 HEAD>`；`_is_lock_contention(error)` 回傳 True，因此 `auto_commit_ticket_md_with_retry` 外層會重試。

### 實驗發現

已驗證的事實：
1. 持續 ` M` 會發生，條件是「兩寫入者都在任一方提交前完成追加，且提交順序與追加順序相反」（E1-3、E1-4）。其餘 4 種交錯終態乾淨。CAS 競態會被重試吸收成同一種情形（E3）。
2. 漂移只有行序差，行集合相同；後續乾淨提交不會修復漂移，只有整檔提交能消除（E2）。
3. W1-067 只影響 index 平面：它把同步順序顛倒時的 `MM` 降為 ` M`，對工作區與 HEAD 的行序漂移沒有影響（E4）。
4. 「提交端依工作區順序投影」在原型中消除全部 6 種交錯的漂移，並且不吸入他人未提交的行（P1、P2）。
5. 主 repo 現況：W1-052 之後 49 筆觸及這兩個檔的提交沒有任何刪除行，目前 status 乾淨，觀測期內尚未發生。

仍未驗證的假設：
- 三個以上寫入者的交錯只以推論涵蓋（漂移條件推廣為「提交順序不是追加順序」），未逐一窮舉。
- 投影原型未涵蓋同一行重複出現（例如改派來回後出現兩行相同內容）時的 multiset 配對位置；實作票須補此測試。

## Solution
### 分析結論

1. 行序漂移會發生，發生時 `git status` 持續顯示 ` M`，直到有人整檔提交；條件是「兩寫入者都在任一方提交前完成追加，且提交順序與追加順序相反」（重現實驗 E1-3、E1-4、E3）。
2. 漂移不影響任何讀取結果：兩個讀取函式對漂移涉及的行都不敏感，下游顯示端各自排序（Problem Analysis「讀取端語意」）。代價只在流程層：外觀與 W1-052 要消除的「未提交主題行」相同，會被誤認為他人遺留。
3. W1-067 對本問題沒有影響：它只修 index 平面（`MM` 降為 ` M`），工作區對 HEAD 的漂移不變（E4）。
4. 觀測頻率低：W1-052 之後 49 筆相關提交沒有發生過。

### 候選方案評估

| 候選 | 做法 | 利 | 弊 | 判定 |
|------|------|----|----|------|
