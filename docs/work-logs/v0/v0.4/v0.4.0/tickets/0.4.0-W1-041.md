### 試行結果：失效訊號逐項（0.3.2～0.4.0，2026-10-01 量測）

| 失效 | 訊號 | 實測 | 判定 |
|---|---|---|---|
| 停放區成墳場 | major 規劃未引用停放文件 | `docs/major-planning-inbox.md` 從未建立。同日廢除「不預先登記未來版本」後，延後項直接落到已登記的後續版本：0.5.0 5 張、0.6.0 9 張、1.0.0 34 張 | 訊號不適用；停放的實際載體是「已登記的後續版本」。風險轉為這些版本的票池在其規劃波未被逐張裁決 |
| topic patch 被塞爆 | patch 票數超出分診清單 | 0.3.2 分診 topic 14 張，最終 21 張；0.3.3 共 60 張；0.4.0（minor）66 張。依 where.files 是否含 `.claude/` 分類，框架票佔比：0.3.2 7/21、0.3.3 19/60、0.4.0 39/66（59%） | 觸發。增量主要不是 topic 收件，而是「流程工具缺陷屬前置」路徑：框架票依規則進入當期版本，不經分診、不受數量上限。0.4.0 finish 因此等待框架票結案（用戶裁決 2026-10-01） |
| 例外閥成後門 | 例外閥進票比例上升 | `scope_blocker` 只在 0.3.1 用過 7 次；0.3.2、0.3.3、0.4.0 皆 0 次。被同日補充的「執行期新發現依 topic 契合度進 patch」取代，每筆收件在該版 notes 寫明判定依據 | 未觸發 |
| 工具自動路由繞過規劃 | patch 內出現無分診紀錄的票 | 試行期版本登記與遷移皆手動（0.4.1 登記、W4 延後九項 migrate）。但 `ticket create` 未給 `--version` 時預設進 active 版本，框架票多經此路徑進入 | 部分觸發：未見自動路由進 patch，但「預設 active」使框架票無分診進入當期版本；與 canonical #55 的 W1-088 觀測同源 |

### 推框架的修改方案

1. `version-progression.md`〈版本生命週期〉：minor 完成後分診一次，依 topic 定 patch 數量；執行期新發現依 topic 契合度進尚未開工的 patch，都不契合才延後；例外閥限契約行為或資料錯誤，票面寫判定依據。
2. 〈版本登記規則〉：允許預先登記版本；延後進入後續版本須附「經討論後決定放在此處」的記錄；後續版本的票池在其規劃波必須逐張裁決（取代獨立停放文件）。
3. 前移路由：不再一律送最近開放後繼，由分診指定。
4. 框架票與專案版本脫鉤（本輪新發現）：上游資產票不應以「前置」名義無上限進入專案版本並阻擋其 finish。方向候選：由分診指定收件版本並受數量上限；或另設不計入專案版本契約的框架軌，以 canonical issue 為知識載體（與 #81「問題 context 應由專案 ticket 遷至 framework issue」相關）。
5. 帶入版本契約模板（todolist 檔頭〈版本契約〉五欄：topic 清單、預期變更、驗證方式分類、人工實測時段與前置檢查、結果值日誌事件）。

canonical 登記：dedup 命中 #55（自動選版）、#81（ticket 池與 framework issue）皆為相關而非重複；版本生命週期規則本身無既有 issue，需新開 issue（`create_issue.py`，待用戶逐次授權）。

canonical 登記：#114（用戶授權新開，2026-10-01）。落地承接：0.4.1-W1-013（方案 1～3、5 直接落地；方案 4 先經用戶 WRAP 裁決）。
