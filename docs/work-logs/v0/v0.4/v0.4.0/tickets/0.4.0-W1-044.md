## Solution
### 查證結果

- **平台單位是秒**。出處：code.claude.com/docs/en/hooks —— "Seconds before canceling."；預設值 "600 for command, http, and mcp_tool"（UserPromptSubmit 降為 30）；"A timed-out command, http, or mcp_tool hook doesn't block the tool call."
- **錯誤來源**：`.claude/hook-specs/claude-code-hooks-official-standards.md` 以毫秒示範，原文 `"timeout": 60000  // 可選，預設 60 秒`、`"timeout": 120000  // 2 分鐘`。settings.json 的數值是照這份文件寫的。`.claude/references/hook-architect-technical-reference.md` 記為秒數，與官方一致，兩份框架文件互相矛盾。

### settings.json timeout 盤點（2026-09-30 實測）

以程式解析 settings.json：`timeout` ≥ 1000 的註冊共 77 筆，對應 63 支不重複的 hook；值為 5000、10000、15000、20000、30000，實際等於 83 分鐘到 8.3 小時。唯一正確的是 W1-043 新增的 hooks-test-gate 120。

### 直接換算的風險

以 `.claude/hook-logs/*/` 的 `Hook execution time`（程序內計時，不含 uv 啟動）比對原意的秒數（原值 / 1000）：

- 26 支 hook 的實測最大值超過原意的一半，另有 5 支無 log 資料。
- 其中已超過原意的例子：
  - auq-option-pattern-detector：原意 5s，最大 9.63s
  - confabulation-audit：原意 15s，最大 19.27s
  - hook-dependency-isolation-check：原意 10s，最大 24.55s
  - session-start-issue-check：原意 20s，p99 47.42s，有 5 次超過
  - tracking-schema-json-staleness-guard：原意 30s，最大 394.17s
- 直接除以 1000 會讓這些 hook 在負載下被平台終止。PreToolUse 逾時不阻擋工具呼叫，等於把守衛改成會靜默失效，比現狀更差。

### 判定

1. 屬實：單位誤用，現有值形同未設上限。影響是 hook 卡住時沒有有效的逾時上限；目前沒有觀察到實害。
2. 修法不能直接換算，要依實測分佈逐支設定。已開 0.4.0-W1-047（IMP，P2）承接，同時更正 hook-specs 文件的單位。狀態為 (b)：由 W1-047 承接。
3. 框架問題兩條判準：
   - 抽象可攜：是。settings.json 經 sync 散佈（sync-claude-pull 只排除 settings.local.json），錯誤示範文件也隨框架散佈，任何 consumer 照文件寫都會得到錯誤單位。
   - 根源在 `.claude/` 通用資產：是。根源是 `.claude/hook-specs/` 的文件與 `.claude/settings.json`。
4. 查重：以 settings.json、timeout 查詢，命中的 issue（#11、#53、#68、#97 等）主題皆非 timeout 單位，判定未命中。依流程回報 e1，不新開 issue。
