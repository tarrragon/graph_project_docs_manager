## Problem Analysis
### 問題根因

鎖死由三個獨立缺口疊加而成，缺一即不會形成「無路可結」：

1. **逃生閥契約斷裂（CLI 與 hook 不一致）**：CLI 在 complete 的 Step 3.7 提供 `--force` 旁路 children 阻擋，阻擋訊息主動印出 `用法: ticket track complete <id> --force`，`.claude/skills/ticket/references/track-command.md` 的 complete 前置清單「子任務完成度」列與其後說明段同樣記載此旁路。但 PreToolUse 的 acceptance-gate-hook 在 CLI 執行前就以同一條件（children 非終態）deny，且整支 hook 不解析命令中的 `--force`。在裝有該 hook 的環境，CLI 的 `--force` 分支不可達；hook 的 deny 訊息只寫「請先完成所有子任務」與「ANA 落地請用 --parent 建 children」，後者指向的正是造成鎖死的路徑。
2. **children 同時承載血緣與完成門檻**：PC-091 與 ticket-lifecycle.md〈防護性 ANA〉刻意把兩者合併（防護性 ANA 要等落地完成才 complete，防止「只診斷不開藥」）。副作用是 blockedBy 該 ANA 的下游票所等待的 ANA 終態，從「分析結論可用」位移為「全部落地完成」。flutter_balance 案例中 20 多張元件票卡住屬此機制：它們依賴的是 UX 補審的結論，卻被量測、評估、文件一致性等非前置 children 間接卡住。
3. **規則文字三層不一致**：
   - `quality-baseline.md` 規則 5〈ANA Solution 內 spawn 規劃〉（自動載入）情境表首列寫 `ticket create --source-ticket <本票 ID>`，`--parent` 只列為「子任務形態」。
   - `ticket-body-schema.md`〈Solution 章節：Spawn 落地確認〉的「部分未建」列把 `--source-ticket` 與 `--parent` 並列為等價選項。
   - PC-091 v1.2.0、`field-semantics.md`〈用戶情境對照表〉、`ticket-lifecycle.md`〈ANA Ticket 落地下游血緣選擇（強制）〉定 children 為唯一選項，並明文禁止用「spawned + --yes-spawned」表達 ANA 落地以繞過 gate。
   - 以上各層都沒說明選 children 的後果：ANA 會維持 in_progress 直到 children 終態，blockedBy 此 ANA 的票也一起等。

flutter_balance 的繞過路徑（migrate → set-parent --clear → add-spawned → complete --yes-spawned）正是 PC-091 列為禁止的反模式，代表現行權威在這個情境給不出合規的結案路徑。

## 重現實驗結果
### 實驗方法

所有實驗都在 session scratchpad 內進行，未觸碰本專案票庫：

1. **hook 層**：在 scratchpad 建立假專案 `w1068/proj`，放一張 ANA 父票 `9.9.9-W1-001`（`children: [9.9.9-W1-001.1]`）與一張 pending 子票。以 `CLAUDE_PROJECT_DIR=<假專案>`、cwd 為假專案（非 git），把 PreToolUse JSON 從 stdin 餵給 `uv run --quiet .claude/skills/ticket/hooks/acceptance-gate-hook.py`，比較兩個命令：`ticket track complete 9.9.9-W1-001`，以及同一命令加 `--force`。
2. **hook 對照組**（E2 正向對照）：把子票改為 completed，重跑帶 `--force` 的命令，確認閘門能分辨兩種狀態，不是一律 deny。
3. **CLI 層**：在 ticket skill 的 uv 環境 import `ticket_system.commands.lifecycle`，以 monkeypatch 替換 `list_tickets`，直接呼叫 `_handle_pending_children_block(ticket, version, force)`，比較 force=False、force=True，以及子票 completed 三種情況。
4. **其他 hook 排查**：`grep -rln force` 掃 `.claude/hooks/*.py`、`.claude/skills/*/hooks/*.py`，再交集 `track complete` 字面。

### 實驗執行

| 情境 | 觀察 |
|------|------|
| hook，無 --force，子票 pending | `permissionDecision=deny`，rc=2，訊息 `[ERROR] Acceptance Gate: 子任務未全部完成` |
| hook，有 --force，子票 pending | `permissionDecision=deny`，rc=2，訊息與上列逐字相同；hook-logs 記錄「識別到 ticket track complete 命令: ... --force」，之後不存在任何 force 分支 |
| hook，有 --force，子票 completed | `permissionDecision=allow`，rc=0 |
| CLI，force=False，子票 pending | 回傳 1；stderr 印出 `建議：先完成上述 children，或使用 --force 旁路` 與 `用法: ticket track complete 9.9.9-W1-001 --force` |
| CLI，force=True，子票 pending | 回傳 None（放行），stderr 印 `[Warning] ... --force 旁路強制完成` |
| CLI，force=False，子票 completed | 回傳 None |
| 其他 hook 排查 | 命中的 `commit-stage-guard-gate-hook.py`、`phase4-decision-enforcement-hook.py`、`git-ref-transaction-content-guard.py` 都是 "enforcement" 等字面的 force 子字串，沒有任何一支對 `complete --force` 做判定 |

附帶觀察：hook deny 輸出的 checklist 第 5 項對 ANA 父票顯示「非 ANA，不適用」，原因是步驟 1 提早 return 時 `task_type` 帶空字串。屬顯示瑕疵，不影響判定。

### 實驗發現

已驗證的事實：
- 攔下 `complete --force` 的是 acceptance-gate-hook 本身的步驟 1（children_checker），沒有另一支 hook 參與。回報中「complete 被擋」與「--force 被擋」是同一個判定點。
- CLI 的 `--force` 旁路本身正確，但在 hook 存在時永遠跑不到；CLI 的錯誤訊息把使用者導向一個必然被 deny 的命令。
- 閘門有鑑別力：children 終態時放行。問題在於它不承認旁路，並非誤判。

仍未驗證的假設：
- flutter_balance 的 W1-008 資料（4 張 children 與 20 多張 blockedBy 票）取自回報內容，本專案未取得對方票庫。
- `acceptance_auditor.validate_children_completed` 在 complete 路徑上是否構成第三道 children 判定。

本實驗不涵蓋：hook 在 git linked worktree 下以 worktree 根定位票檔的路徑；`batch-complete` 命令對 children 的判定；孫層 children（`_collect_incomplete_descendants` 遞迴）在 --force 情境下的行為；`require_in_progress` 與 children 共用同一個 `--force` 旗標時的交互作用；互動環境（isatty）下的 CLI 行為。
