# Execution Log

## Task Summary

update-ref 持有 HEAD.lock 與分支鎖期間，.git/hooks/reference-transaction shim 以 uv run 啟動 git-ref-transaction-content-guard.py。負載約 90 時，實測 18:00:17 開始、18:00:27 才放行。W1-064 已讓 update-ref 不再因逾時被殺，但持鎖時間仍隨負載拉長，會放大其他 git 行程的鎖競爭。需量測冷啟動與判定各自的耗時，並評估縮短持鎖窗口的做法（例如 shim 改用已安裝環境的 python、快取、或只在 prepared 階段做必要檢查）。

## Problem Analysis
### 問題根因

持鎖窗口 = `update-ref` 取得 HEAD.lock／分支鎖後呼叫 `reference-transaction prepared`，到 hook 返回為止。實測拆段（真實 hook 情境，GIT_TRACE 時間戳，見〈重現實驗結果〉）顯示主因不是 uv 冷啟動，而是 guard 判定階段**串行派生的 git 子程序數量**：

- 子程序數 = `8 + 5F`（F = 新 commit 相對 first-parent 的變更檔數；實測 F=1 為 13、F=6 為 38、F=21 為 113，與公式完全吻合）。
  - 固定 8 次：`get_project_root` 解析（`rev-parse --git-dir --git-common-dir`、`--show-toplevel` ×2）、`rev-list <new> --not --all`、`rev-parse MERGE_HEAD`、`rev-parse <sha>^`、`diff --name-only`、`diff -M --name-status`（後兩者取同一份資訊）。
  - 每檔 5 次：`show <pre>:<path>`、`show <new>:<path>`、`diff <pre> <new> -- <path>`，以及 `_check_branch_verify` 每檔重跑一次的 `get_project_root`（`rev-parse --show-toplevel`）與 `get_current_branch`（`branch --show-current`）。後兩者內容與檔案無關，卻在每檔迴圈內重複；`is_merge_commit` 豁免判斷排在這兩次呼叫之後，merge 也照付。
- 每個子程序的 CPU 時間極小（`/usr/bin/time` user+sys 約 0.3 s，牆鐘時間 1 s），牆鐘時間主要花在排程等待上，所以每個子程序的延遲隨負載放大：負載 14–19 時約 11–21 ms，負載 21–31 時約 51–113 ms（程序內 profile）。18:00:17→27 那次事件在負載約 90 下耗時 10 s，若以約 16 個程序估算（shim 1 + uv 1 + python 1 + guard 13），每個程序約 0.6 s，與上述趨勢一致（屬外推，未在該負載下實測）。
- uv 段（解析與環境建立）在快取暖時只佔 30–90 ms（成對差值中位數），不是主因。快取冷時為一次性的 1.46 s。

### 影響範圍

- 已驗證：`.claude/hooks/git-ref-transaction-content-guard.py`（判定階段的子程序鏈）、`.claude/lib/commit_content_guards.py` 的 `_check_branch_verify`（每檔 2 次與檔案無關的 git 呼叫）。持鎖時間隨 F 線性成長。F=21 在負載約 15 時持鎖 1.4–2.5 s；merge 的 F 等於該分支帶入的檔案數，所以 merge 是最壞情境。
- 已驗證（附帶發現，與延遲無關）：shim `exec uv run --quiet` 在 uv 無法解析依賴時（離線且快取冷）以 rc=1 結束，在 uv 不存在時以 rc=127 結束。兩者都是 `prepared` 非零，會直接中止所有 ref 寫入（實測 `fatal: ref updates aborted by hook`，update-ref rc=128）。這與 guard 檔頭宣告的 fail-open 語意相反。guard 的 deny 也用 rc=1（`EXIT_BLOCK`），shim 目前無法靠離開碼分辨「guard 判定阻擋」與「uv 啟動失敗」。
- 未驗證（觀察）：`_check_branch_verify` 以「目前 checkout 的分支」判定保護分支，不是以 stdin 中實際被寫入的 ref 判定。在某分支上對另一個 ref 做 `update-ref` 時，判定對象可能錯位。本票未實測。
- 真實紀錄（低信度，僅作參考）：比對 2026-09-30 本專案 guard 日誌與 commit 時間（秒級、以最近時間配對，merge／rebase 的舊 committer date 會造成錯配），從 commit-tree 到放行的間隔中位數約 1 s、p90 約 4 s，≥10 s 的有 57 筆。

### 相關 Error Pattern

以 `reference-transaction`、`持鎖`、`fail-closed`、`index.lock` 查 `.claude/error-patterns/`，沒有直接對應 hook 持鎖延遲的條目。最接近的是 IMP-046（git index.lock 競爭）：本票的持鎖窗口正是放大該類競爭的上游因素。
