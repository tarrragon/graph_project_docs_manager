### 自檢結果

- **本 session 實地觸發**：合併後，在主 repo 以 `GIT_TRACE` 對一筆真實的票務提交（append-log，F=1）取 trace。當時 load average 為 107.79、87.29、50.97（1、5、15 分鐘）。
  - reference-transaction 從 prepared（00:11:21.562）到 committed（00:11:26.062），持鎖 4.5 s。
  - 持鎖期間 git 子程序共 12 個：rev-parse 7、diff 2、rev-list 1、cat-file 1、branch 1。扣除 shim 自己的 rev-parse 為 11，與代理人量到的常數一致。
- **如實判讀**：F=1 時子程序只從 14 減到 12，所以本次 4.5 s 和 W1-064 事件的 10 s 以上（load 約 90）之間的差距，大部分來自兩次量測的負載不同，不能歸功於本票。本票的效果集中在多檔提交：代理人實測 F=21 時子程序由 134 降到 11，持鎖由 1.924 s 降到 0.250 s（約 -87%），而且與 F 無關。
- **liveness**：guard 日誌在 00:10:06 與 00:11:26 都記錄「新 commit 內容無發現，放行：new_commits=1」，新版本在主 repo 正常運作。
- **等價性**：新增 5 種情境（違規、無違規、merge、根 commit、多檔），新舊路徑產生的 StagedFile 與 findings 逐項相等；另有防空轉測試，以及「patch 區段不符時退回舊路徑」的測試。代理人另外用封存的舊版 guard 做端到端對照，exit code 與 stderr 逐字相同。
- **失敗語意**：guard 自身例外時的語意沒有動。
