### PM 合併後實測發現兩個缺陷（2026-09-30 19:31 至 19:35，83）

**缺陷 1：他方保護規則把自己的歷史版本誤判為他方 stage，過期 entry 因此永久卡住。**
- 19:31:09：append-log 提交 3ab1cf86c，接著同步共用 index 時撞上 index.lock（路徑 A），entry 停在 3ab1cf86c 的 blob。
- 之後的 5 次寫入（append-log 1 次、check-acceptance 4 次）同步時，都判定該 entry「既非本次 commit 的 parent 版本、也非本次 tree 或當下 HEAD 版本」，當成他方 stage 而不覆寫。
- 結果：`git status` 顯示 `MM`，index 為 138e26052（3ab1cf86c 的版本），HEAD 與工作區為 ee5e0cb53。這正是本票要修的過期 entry，而且修正後的邏輯反而把它鎖死。
- 修法：entry 的 blob 若出現在該路徑的提交歷史中（HEAD 可達、限定最近 N 次），就是過期的己方版本，可以覆寫成 HEAD；只有從未提交過的 blob 才視為他方 stage。

**缺陷 2：共用 index 同步的 update-index 沿用 10 秒 timeout，同樣有「持鎖中被殺」的風險。**
- 19:34:15 出現 `.git/index.lock`：0 bytes，沒有任何行程持有（lsof 為空），期間所有 index 操作都失敗。PM 於 19:35 確認無持有者後刪除。
- 建立者無法直接證明。時間落在 PM 連續執行 check-acceptance 的期間，當時機器處於高負載。W1-064 判定「共用 index 同步為毫秒級」，這在高負載下不成立。
- 修法：共用 index 同步中持有 index.lock 的步驟，比照 update-ref 不設會殺行程的 timeout；或先證明這些步驟不可能超時，並附量測。

**處置**：PM 已執行 `git restore --staged` 把 entry 重設回 HEAD。本票暫不結案，重新派發修正。
