## Problem Analysis
<!-- Schema[IMP/Problem Analysis]: 選填（小型 IMP 可留 placeholder；大型 IMP 建議填寫）（.claude/pm-rules/ticket-body-schema.md） -->
### 產生版本號維持原值的理由（PM，2026-09-30，依 e1 更正）

結論：`schema_generated_at_framework_version` 維持原值。派發時寫的理由「App 目前不讀 edge_types」不成立，App 自 0.4.0-W2-002 起已經以 `resolveEdgeTypes` 讀取 edge_types，不可再引用這個說法。正確理由如下：

1. 0.4 不讀方向性欄位，多出的欄位在解碼時被忽略。
2. 0.5 開始讀取時，依 SPEC-007 FR-01：專案 JSON 缺這個欄位、且版本在已知範圍內時，由內建表補值。因此同一版本號下，JSON 有沒有這個欄位都能正確處理。前提是 0.5 的內建表已經帶有這個欄位，這一點須列入 0.5.0-W1-001 的驗收。

另外，W1-056（`forward_cardinality`）當時也用了同一個錯誤說法，它的正確理由同上。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 複核與合併（2026-09-30，83）

- **欄位**：合併 d43f30d02，doc skill 升為 1.24.0。欄位為 `direction`（directed／undirected）。選用字串列舉，是為了與既有的 class、layer、forward_cardinality 等具名值域保持一致。
- **判定表**：只有 association 為 undirected。spec／uc／proposal_association 雖同為 see-also，但上游未宣告對稱，因此判為 directed。完整表格見代理人回報。
- **消費點盤點**：`.claude/` 內沒有 hook 或其他 skill 讀取 edge_types 的欄位清單。`commands/schema.py` 整體匯出，不必修改。
- **產生版本號**：維持 2.60.13，理由依 e1 更正後的版本，見 Problem Analysis。CHANGELOG 1.24.0 同時更正了 1.23.0 條目的錯誤理由。
- **通知**：已在 #98 附觀測（comment 5911849804）。0.5.0-W1-001 已透過 e1 通知，要點是 0.5 的內建表必須帶 direction 欄位，FR-01 的補值才能成立。

### 自檢結果

- **live 驗證**：直接讀取合併後 main 上的 tracking_schema.json，16 個邊型都有 direction，只有 association 為 undirected；schema_generated_at_framework_version 為 2.60.13。
- **全套件**：合併後在 main 執行 `uv run --directory .claude/skills/doc --extra test pytest -q`，403 passed、1 skipped。
- **紅燈證據**：新測試引入時 ImportError（驗證函式尚不存在），修正後 TestEdgeDirection 全綠，含 E2 正向對照（缺欄位、值域外的 "both"）。
