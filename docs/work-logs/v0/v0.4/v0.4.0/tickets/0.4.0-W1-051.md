SessionStart hook session-start-issue-check 的 p99 為 49.6 秒（20 個樣本），遠高於同類 hook。W1-047 依公式給 152 秒上限，未處理成因

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 問題根因
hook 走 owned-issues 登記檔快速路徑（.claude/state/framework-issue-owned.json，25 張 issue），對每張 issue 以 subprocess 串行呼叫 section_comment.py check（每次內部 2 次以上 gh API，含 --paginate 全量讀 comments）。耗時 = 25 x 單張 check 耗時，無快取、無並行。

### 各階段耗時（實測，正式啟動方式 uv run + SessionStart JSON source=startup，N=6）
| 階段 | 耗時 |
|------|------|
| 整體牆鐘 N=6 | 91.9 / 88.9 / 97.9 / 83.9 / 88.4 / 71.5 秒（中位約 88s） |
| gh auth status（3 次） | 0.62 / 0.96 / 0.63 秒 |
| gh api 單張 issue comments --paginate | 0.84 秒 |
| section_comment.py check 單張（3 張） | 2.08 / 3.39 / 2.58 秒 |
| 登記檔讀取、模組載入、無登記檔時 hook 空跑 | 約 2.2 秒（含 uv 啟動） |
| 25 張串行 check 推算 | 約 52-85 秒，與整體牆鐘吻合 |
註：量測期間有另一段量測同時進行，數值含輕度網路/CPU 競爭；整體牆鐘高於 W1-047 的 p99 49.6s，因當時 owned 數量較少或網路較佳。

### 影響範圍
- 耗時隨 owned issue 數量線性增長（目前 25 張，約 3.5 秒/張）；與 GitHub 上全部 issue 數無關。
- 登記檔只增不減（updated_at 起自 2026-09-07），已關閉 issue 是否移出未驗證（假設）。
- 已驗證：設定 timeout 152 秒，25 張約 88 秒；超過約 43 張將被外層強制終止。
- 成因信心：高（原始碼結構 + 分段實測 + 推算吻合）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論（已決策）
成因為「owned issue 逐張串行 subprocess check，無快取」，耗時 O(N)。建議修法，依收益排序：
1. 並行：ThreadPoolExecutor 同時跑各張 check（gh 為 IO 等待），預期降至約 max(單張) x ceil(N/worker)，約 5-10 秒。
2. 略過已關閉 issue：登記檔中 closed 者不查（或寫入端關閉時移除），直接減少 N。
3. 快取/節流：同一 issue 距上次成功 check 未滿數小時即跳過（state 檔記 last_checked）。
4. 背景化：hook 立即返回，結果留待下次 session 注入（改變語意，最後考慮）。
建議實作票：0.4.0-W1-052 已存在（spawned），請 PM 確認其範疇涵蓋 1+2；3 視需要另議。
