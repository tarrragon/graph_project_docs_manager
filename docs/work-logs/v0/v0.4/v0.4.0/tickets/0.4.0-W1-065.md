# Execution Log

## Task Summary

lib/git_command_parse 的切詞把 ')' 或 ');' 黏入前一 token，子 shell 閉合後的語句併入前一語句，find_git_invocations 因此漏抓括號後的 git 呼叫。PM 實測 find_git_invocations 對 '(cd /tmp/x && git status); git merge foo'、'(… ); git commit -m x'、'(true); git reset --hard' 皆回傳空清單；無括號的 'git status; git merge foo' 正常。修法：在共用切詞層處理引號外的括號（拆為獨立 token 並作語句邊界），移除 W1-061 在 workspace-wipe-guard 內的局部 _space_parens，改用共用層。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
### PM 複核與合併（2026-09-30，83）

- 合併 64d07314e，已在 origin/main。改動：`.claude/lib/git_command_parse.py` 新增 `space_shell_parens`／`_tokenize_command` 管線；wipe-guard 移除局部 `_space_parens`，保留單一子 shell 的 cd 作用域規則；merge-guard 的 deny 標題改為「目標 repo 的 index 有 staged 變更」。
- **括號不配對的語意**：代理人維持照常切分並寫 debug 日誌，不回傳 None；未閉合引號仍回 None。PM 同意這個做法：括號不配對時照常切分仍能抓到其中的 git 呼叫，比回 None（部分守衛因此放行）更保守。
- **PM 以合併後的 main 探測**：下列寫法都能正確抓到目標命令，括號內文字也不會被誤切：
  - 子 shell 後以分號接 git、子 shell 後以空白加分號接 git
  - 大括號群組 `{ git status; }; git reset --hard`
  - 引號內括號 `echo "(x)"; git commit -m "a (b) c"`
  - 命令替換後接 git、`--format="%h (%s)"` 後接 git
  - `true && (git reset --hard)`

### 自檢結果

- **本 session 實地觸發**：
  - `(true); git -C <scratch> merge --no-edit br`（scratch 的 index 有 staged 檔）：被 merge-guard deny，標題為新措辭。修正前，這個寫法會繞過所有 git 守衛。
  - `(true); git -C <scratch> status --short`：放行，rc=0。
- **liveness**：merge-staged-index-guard 日誌於 19:10:39 記錄 `git merge 被阻擋（staged=1）: (true); git -C …`。
