### 分析範圍與「過長」的判準（代理人，2026-10-01）

- 持鎖窗口：`commit_files_isolated` 的 `git update-ref HEAD <new> <old>` 取得 `HEAD.lock` 與 `refs/heads/<branch>.lock` 之後呼叫 `reference-transaction prepared`，到 hook 返回、ref 寫入為止。S1（0.4.0-W1-070.1）已把 guard 判定段的 git 子程序數由 `8+5F` 降為常數，本票量測 S1 之後還剩多少、剩下的花在哪裡。
- 「過長」以並行寫入者的容忍預算衡量，不另訂主觀門檻。三層預算如下：
  - git 本身：`core.filesRefLockTimeout` 本專案未設定，預設 100 ms，撞 ref 鎖等 100 ms 即失敗。
  - `git_ops._run_git_with_lock_retry`：同一命令最多 2 次，間隔 1 s。
  - `git_utils.auto_commit_ticket_md_with_retry`：整筆提交重建後重試，退避 0.5／1／2 s，總等待預算 5 s，耗盡後 exit 75，需人工補救。
  - 因此持鎖約 1.1 s 以上，並行的另一筆提交第一輪必失敗並進入退避；持鎖 5 s 以上，有機會耗盡對方的預算。
- 相關 Error Pattern：IMP-046（index.lock 競爭）與 IMP-GPD-001（update-ref 鎖重試子字串）屬同一競爭面，本票只量持鎖長度，沒有新的錯誤模式。
