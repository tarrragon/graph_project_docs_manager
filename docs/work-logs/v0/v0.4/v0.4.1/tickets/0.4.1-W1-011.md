### S2-sh 的一致性與繞過風險

- **sha 與內容的綁定**：commit sha 是 tree、parents 與 message 的雜湊，所以 new 的內容與「相對 first-parent 的 diff」都完全由 sha 決定。快取以 new sha 為鍵，這個綁定是強的。
- **新 commit 集合的綁定**：guard 掃描的是 `rev-list <new> --not --all`。快取項記錄預驗證時的 parent sha。shim 只在以下條件全部成立時才判定命中：
  - stdin 恰為 1 行；
  - ref 位於 `refs/heads/` 之下；
  - old 不是全零；
  - 快取項內記錄的 parent 與 stdin 的 old 字串相等。
  - 理由：實測 CAS 在進入 `prepared` 前已驗證 old 等於 ref 現值；new 唯一的 parent 等於 old，old 被既有 ref 涵蓋，所以新 commit 集合恰為 {new}。這個判斷只靠字串比對，不需要任何 git 呼叫。
  - 不符合以上形態的寫入（merge、多 ref、多 commit、force 寫入）一律未命中，走現行完整掃描。
- **規則版本的綁定**：快取項須記錄預驗證當時的 guard 版本識別。shim 以字串比對一份由安裝 hook 維護的版本檔，不相等即視為未命中。快取項只能使用一次：`committed`／`aborted` 狀態時由 shim 刪除（此時鎖已釋放，刪除不計入持鎖時間），另設依年齡清掃，處理寫入後未被使用的殘留項。
- **情境的綁定（主要風險）**：branch-verify 依賴 repo root、目前分支與合併狀態。預驗證在 ticket CLI 行程內執行，該行程帶有 `CLAUDE_PROJECT_DIR`（指向主專案），而 `get_project_root` 會優先採用它。若 worktree 內的提交照此解析，就會以主專案的分支判定，產生錯誤的放行。因此預驗證必須使用 `commit_files_isolated` 已解析的 repo_root，不得經過 `CLAUDE_PROJECT_DIR`，並需以 worktree 情境的等價性測試覆蓋。
- **失效方向**：快取缺席、版本不符、形態不符、預驗證模組無法載入或預驗證自身例外，一律不寫快取或判為未命中，退回鎖內完整掃描。唯一的危險方向是錯誤命中，必須以 E2 正向對照輸入測試守住：含違規內容的 commit 在預驗證端不得寫入快取，在 hook 端仍須以 rc=87 阻擋。
- **繞過風險**：能寫入 `.git/` 的行程，原本就能刪除 shim 或以 `-c core.hooksPath` 繞過 guard。guard 自身是 fail-open，不是安全邊界，所以快取檔沒有新增「蓄意繞過」的類別。新增的是「意外錯誤命中」的類別，由前四項綁定處理。
- **行為差異**：命中時 hook 不輸出 WARN 級訊息，所以預驗證端須把 WARN 照原格式輸出到 stderr；deny 時不寫快取，由 hook 照常阻擋並輸出訊息，deny 的訊息來源維持單一。
