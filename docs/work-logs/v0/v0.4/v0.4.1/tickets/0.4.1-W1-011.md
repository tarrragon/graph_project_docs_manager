### 分析範圍與「過長」的判準（代理人，2026-10-01）

- 持鎖窗口：`commit_files_isolated` 的 `git update-ref HEAD <new> <old>` 取得 `HEAD.lock` 與 `refs/heads/<branch>.lock` 之後呼叫 `reference-transaction prepared`，到 hook 返回、ref 寫入為止。S1（0.4.0-W1-070.1）已把 guard 判定段的 git 子程序數由 `8+5F` 降為常數，本票量測 S1 之後還剩多少、剩下的花在哪裡。
- 「過長」以並行寫入者的容忍預算衡量，不另訂主觀門檻。三層預算如下：
  - git 本身：`core.filesRefLockTimeout` 本專案未設定，預設 100 ms，撞 ref 鎖等 100 ms 即失敗。
  - `git_ops._run_git_with_lock_retry`：同一命令最多 2 次，間隔 1 s。
  - `git_utils.auto_commit_ticket_md_with_retry`：整筆提交重建後重試，退避 0.5／1／2 s，總等待預算 5 s，耗盡後 exit 75，需人工補救。
  - 因此持鎖約 1.1 s 以上，並行的另一筆提交第一輪必失敗並進入退避；持鎖 5 s 以上，有機會耗盡對方的預算。
- 相關 Error Pattern：IMP-046（index.lock 競爭）與 IMP-GPD-001（update-ref 鎖重試子字串）屬同一競爭面，本票只量持鎖長度，沒有新的錯誤模式。

### 實驗方法

- 器材：在 scratchpad 以 `git clone --local` 建立主 repo 的副本（HEAD 77e061427，guard 與 `commit_content_guards.py` 皆與主 repo 逐字相同，已含 S1 4160fb7a1）。`.git/hooks/reference-transaction` 是主 repo shim（shim-version 3）的逐字複本，以 `cmp` 確認。shim 以相對路徑解析 guard，所以執行的是副本內同版的 guard。量測時移除 `CLAUDE_PROJECT_DIR` 與 `GIT_*`。
- 提交形態：比照 `commit_files_isolated`。先對副本內一張 ticket md 追加一行（F=1），以臨時 `GIT_INDEX_FILE` 執行 read-tree、add、write-tree，再 commit-tree，最後計時 `git update-ref HEAD <new> <old>`。
- 持鎖時間的兩種量法互相對照：
  - (a) `GIT_TRACE` 中 `run_command ... prepared` 到 `... committed` 的間隔。
  - (b) 0.5 ms 輪詢 `HEAD.lock`／`refs/heads/main.lock` 存在的時長。
  - 兩者差距小於 15 ms。
- 分段（依 trace 時間戳）：
  - shim 段：prepared 到 shim 內第一個 git。
  - uv+python 起動段：到 guard 的第一個 git。
  - 判定段：到 committed。
- 4 種變體每輪隨機排序：
  - `S1_current`：逐字 shim，即現況。
  - `S2_sh_hit`：shim 以 sh 讀 stdin，執行 1 次 `rev-parse --git-common-dir`，查快取檔，命中即放行，不啟動 python。
  - `S2_py_hit`：shim 照常 `uv run`，進入一支 stub 腳本，script 依賴與 guard 相同，同樣 import lib 並呼叫 `get_project_root`，查快取命中即放行，用來近似 guard 入口命中的路徑。
  - `no_hook`：無 hook。
- 負載：每筆記錄 `sysctl vm.loadavg` 的 1 分鐘值（前／後）。量測期間沒有自行製造負載。共 4 批（b1–b4），每批每個變體 N=8，每個變體合計 N=32。
