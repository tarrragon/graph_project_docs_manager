# Execution Log

## Task Summary

flutter_balance v2.71.0 取樣：gate 總耗時與 pytest 自報差距最多約 20 秒；W1-035 在本機兩組取樣（load 14～60）差距僅 0.2～2.9 秒，uv 啟動 0.03～0.24 秒，無法重現。待驗證假設：consumer 依賴較大致 sync 慢、pytest 自報不含匯入與 collection、高負載下子程序排程延遲。

## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 本機首筆 gate 內分段資料（PM，W1-035.2 合併 4b7061c62 時的實地觸發）

`分段計時: file=test_hooks_test_gate_hook.py status=pass total=17.44s pytest_self_reported=5.56s uv_and_startup_gap=11.88s load1=17.52`

- 0.4.1-W1-035 以手動命令量測時，差距只有 0.2～2.9 秒；gate 內實際觸發這一筆是 11.88 秒。代表手動重現與 gate 內呼叫的差距不在同一個量級，歸因時不能只靠手動命令的量測。
- 待區分的可能來源：gate 本身已在 uv 管理的 python 程序內執行，再啟動一層 uv；合併當下其他程序並行（W1-037 代理人正在跑 ticket 測試）；pytest 自報時間不含外掛與 conftest 匯入。
- 依本票驗收，取樣仍以 consumer 端 N>=10 為準；本機資料只作對照組。

### 本機第二筆 gate 內分段資料（PM，W1-038.1 合併 04e96605e，2026-10-01 21:58）

`分段計時: file=test_testpaths_coverage_warning.py status=pass total=2.67s pytest_self_reported=2.31s uv_and_startup_gap=0.36s load1=14.26`

- 與第一筆（gap 11.88 s，load1 17.52）相比，兩筆的 load 相近，gap 卻差了 30 倍以上。差距不能只用 load 解釋；可能的來源包括同時段其他程序造成的 I/O 或快取冷熱，以及兩次執行的測試檔不同（匯入量不同）。
- 目前本機僅 2 筆，不足以歸因（PC-168）。依本票驗收，取樣仍以 consumer 端 N>=10 為準。
### consumer 第 1 筆（flutter_balance-53，e1 轉達）與取樣方法裁定（PM）

- 樣本：提交 e38992c0d（sync-pull v2.73.0，冷快取，load 31.01）。content guard 測試 total 25.50 s、pytest 17.08 s、gap 8.42 s；同一次 gate 內，其後三個測試檔的 gap 都在 1 s 以下。
- 與本機 gap 11.88 s 那一筆（單檔、同為該次 gate 第一個 uv run）方向一致。暫定歸因方向：gate 每次執行時「第一個 uv run」的冷啟動或環境同步成本，而不是每個測試檔各付一次。這仍待樣本驗證。
- 取樣方法裁定：接受合成樣本，但與真實樣本分組記錄、不可合併計算（見驗收）。
  - 理由：gate 判定觸及檔的來源之一，是命令字面中 git add 的路徑（`_touched_hook_filenames` 來源 2），所以直接餵 payload 執行的程式碼路徑與真實提交相同，連 hook 外層那一次 uv run 也相同。
  - 合成組缺少一項因素：真實提交時，harness 並行啟動的其他 PreToolUse hook 會與 gate 競爭 uv 快取。兩組分布若有落差，這個落差本身就是歸因證據。
