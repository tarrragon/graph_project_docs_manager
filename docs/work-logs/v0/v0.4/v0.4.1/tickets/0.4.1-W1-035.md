### 量測結論（已驗證 vs 未驗證）
- 已驗證：warm 環境下 uv 啟動開銷中位約 0.04s、最大 0.24s；gate 與 pytest 自報差 0.2~0.5s 常態、最壞 2.9s（load>40）。冷 venv 額外約 0.8s。直接用 .venv/bin/python 與 uv 的總耗時無系統性差異（組 A 直用甚至較慢，屬雜訊）。
- 未能重現：flutter_balance 觀測的「gate 與 pytest 自報差 ~20s」。本 repo 量不到，故 20s 差距不能歸因於 uv 啟動。未驗證假設：(a) consumer 的 hooks 依賴較大，uv sync 在 pyproject/uv.lock 變動後重裝或需網路；(b) pytest 自報不含解譯器啟動、conftest/匯入、collection，高負載下這段被拉長；(c) load 20~30 下 uv 子程序排程延遲。需在 flutter_balance 以相同方法對 gap 分段量測才能定論。
- 限制：自然負載期間無 pytest 全套件並行；組 B 的負載來自非 pytest 來源，且最高 load 60 時樣本只有 1 筆。

### 三方案比較
| 方案 | 作法 | 預期效益（依量測） | 對鑑別力 | fail-closed |
|---|---|---|---|---|
| 1 預熱 | SessionStart 背景跑 `uv sync --project hooks`（或首檔前 gate 自行 sync） | 僅消除冷 venv 的 ~0.8s；warm 時無效 | 無影響，測試仍同 interpreter/依賴 | 保留：gate 命令不變；預熱失敗不影響 gate（gate 仍 uv run，解析失敗 rc=1 -> red，實測 unresolvable dep 為 rc=1） |
| 2 重用環境 | 直接 `.venv/bin/python -m pytest`，或 `uv run --no-sync` | 省 uv 啟動 0.03~0.24s，相對 60s 上限可忽略 | 風險：.venv 過期（pyproject/uv.lock 變動未同步）時以舊依賴跑測試，鑑別力下降 | 風險：.venv 不存在時 `subprocess.run` 拋 FileNotFoundError；`_run_pytest` 僅 catch TimeoutExpired，gate 以預設 `run_hook_safely(fail_closed=False)` 回 exit 1，非 2，等於放行。`--no-sync` 缺 venv 實測 rc=2 且 stderr 'Failed to spawn'，但 .venv 缺 pytest 實測 rc=1（red）。須補 OSError->red 才算 fail-closed |
| 3 逾時只計 pytest | 以 pytest 自身時間（`--durations` 或 pytest-timeout，或 gate 計 uv 前後差）為判準，uv 階段另設較寬上限 | 消除 uv/sync 變異對正常測試的誤擋；對 20s gap 若來自 uv/sync 則有效，若來自 pytest 啟動/collection 則無效 | 無影響（測試內容不變）；但 pytest-timeout 屬新依賴 | 須保留 uv 階段獨立上限，否則 uv 卡死（網路/鎖）無上界；`TOTAL_BUDGET=100`、平台 timeout 120 的不變式需保留（現有測試 `test_settings_timeout_exceeds_worst_case`）。解析失敗 rc!=0 照舊 red |

### 建議
量測顯示 uv 啟動不是瓶頸，方案 2 與 1 的效益 <1s，不值得改動且方案 2 有 fail-open 風險；方案 3 只有在證實 gap 來自 uv/sync 階段時才有價值。建議先補診斷再決定，不先動上限。
