## Problem Analysis

### 再現實例（2026-10-01 約 21:29～21:30，PM 記錄）

- 經過：0.4.1-W1-035.2 的執行者在 worktree 內執行 `append-log --section Solution`，回傳 exit 75。CLI 依 cwd 解析到主 checkout 並寫入票檔，但 CAS 的 update-ref 被拒，因為主 repo HEAD 已經前進。
- 當時並行狀況：21:27～21:30 間，主 repo 每 1～20 秒就有一個新提交，來源有 PM、e1，以及 W1-037、W1-038、W1-035.2 三個代理人的 ticket CLI。
- 後果：這次沒有遺失資料。約 20 秒後同一張票的 append-log Test Results（268ad4314）以整檔方式提交，把 Solution 一併帶入。但這是巧合：如果之後沒有對同一檔案再提交，修改會一直留在工作區。
- 與本票的關係：這是單一路徑提交在 HEAD 競爭下失敗且沒有重試的實例。單一路徑淨變更為零的情況在 W1-034 已排除，所以失敗原因是 CAS 競爭，與範圍自檢無關。本票的重試與檔案日誌可以直接涵蓋這個情境。執行者回報 commit-tree 物件 057bfd255 沒有任何 ref 指向。

### 現有機制查證（實作前）

- 三層重試：(1) git_ops._run_git_with_lock_retry（單一 git 呼叫，最多 2 次、固定等 1 秒）；(2) git_utils.auto_commit_ticket_md_with_retry（整個 commit_files_isolated 重做，退避 0.5/1/2 秒，總預算 5 秒，條件 _is_lock_contention 且無殘骸診斷標記）；(3) commit_ticket_md_reporting 失敗時 stderr 輸出原因、鎖路徑、git add + git commit 補救指令，exit 75。
- HEAD 前進的處理：update-ref 的錯誤文字 `cannot lock ref 'HEAD': is at X but expected Y` 含 `cannot lock ref`，被 _is_lock_contention 判為鎖競爭。結果有兩個缺陷：(a) 內層 (1) 以同一個 old_head 重試，CAS 必定再失敗，白等 1 秒；(b) 外層 (2) 整個重做，這部分是對的，但 5 秒預算在「每 1~20 秒一個提交」的競爭下用盡即放棄（再現實例的 exit 75）。另外 old_head 為空以外的「HEAD 並行移動」fallback 文字不含鎖字樣，不被視為可重試。
- 檔案日誌：重試與 exit 75 路徑只寫 stderr，無任何檔案日誌（唯一的日誌檔是 prevalidate 失敗，路徑 .claude/hook-logs/git-ops-prevalidate/）。
- IMP-GPD-001 教訓：判斷錯誤類型不可只比對單一子字串；本次新增 CAS 拒絕判定同時涵蓋 `but expected` 與 fallback 文字，並以 E1 對照測試固定。
- 設計：新增 _is_cas_rejection（git_ops）；內層遇 CAS 拒絕立即返回不睡；外層對 CAS 拒絕與鎖競爭皆重試；每次重試與最終失敗寫 .claude/hook-logs/ticket-commit-retry/retry-YYYYMMDD.log（欄位 reason、waited_s、attempt、ticket、結果）；日誌寫入失敗僅 stderr。總等待上限維持 5 秒，遠小於 PreToolUse timeout。
### 合併後發現：新測試在高負載下不穩定（PM，2026-10-01 約 22:50）

- PM 在 main dabbafc08 對 `ticket_system/tests/test_commit_cas_retry.py` 連跑三次：
  - load1 70.6：1 failed
  - load1 61.1：2 failed
  - load1 57.5：10 passed
- 另外兩處也出現失敗：PM 的 scratchpad 排查（HEAD 1138e83b6）有 1 failed；W1-039 執行者的 worktree 有 2 failed。
- 失敗的兩個測試是 `test_head_advanced_retries_and_commit_content_correct` 與 `test_log_write_failure_goes_to_stderr_and_keeps_commit_result`，都回傳 git_failed，預期為 committed。W1-026 執行者當時在較低負載下跑是全綠。
- PM 初判（待 incident 驗證）：`_COMMIT_RETRY_BUDGET_SECONDS` 總等待預算 5 秒，另外加上每次 git 呼叫本身的耗時。高負載下 git 子程序變慢，預算因此用盡。若初判成立，問題有兩層：
  - 測試斷言依賴機器負載（test-assertion-design D 系列）；
  - 產品端預算在高負載的真實環境下同樣不夠，而這正是 W1-026 要處理的情境。

### Phase 4 更正（PM，incident 結論後）

- 技術債：有，由 0.4.1-W1-042（P1）承接。內容包括測試與負載隔離、保證最少重試次數，以及產品預算依實測重新設定。
- 本票的日誌與 CAS 分類兩部分仍然有效。重試能否在高負載下生效，以 W1-042 合併後的驗證為準。
