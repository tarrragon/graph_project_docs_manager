### 合併後發現：新測試 test_wall_cap_limits_retries_beyond_min 不穩定（PM，2026-10-01 23:46～23:55）

- main 7089f06f2 的 finish 驗證全套件全綠：ticket 4402/4402、hooks 5374/5374。但 `ticket_system/tests/test_commit_cas_retry.py` 整檔連跑 11 次，失敗 5 次，load1 介於 10.7～34.7，失敗與負載高低無關。
- 失敗的都是同一項 `test_wall_cap_limits_retries_beyond_min`。單獨以 `-k` 執行 3 次皆通過，只有整檔執行時才會失敗。
- 失敗輸出：`assert capped < relaxed`，實際為 `E assert 3 < 3`。牆鐘上限從 5.5 放寬到 9.5 後，重試次數沒有增加。依假時鐘推算（per_attempt=1.0、backoff 1.0），放寬後應有 4 次以上。
- PM 初判（待 incident 驗證）：每次嘗試推進假時鐘的量不固定。可能原因：`_advance_head_times` 搭配真實 git 時，單次嘗試內讀取時鐘的次數會變動；或某條路徑沒有經過 `_clock`；或兩次 `_run` 之間有狀態殘留。
- 實地觸發佐證：主 repo 真實 retry 日誌第 5 行 `[2026-10-01 23:04:12] retry ticket=0.4.1-W1-042 attempt=1 waited_s=0.50 reason=cas_rejected`，是本票執行者在主 checkout 寫票時，遇到真實 HEAD 競爭而觸發的重試。

## Solution
<!-- Schema[IMP/Solution]: 選填（.claude/pm-rules/ticket-body-schema.md） -->
修法：預算改三層：前 3 次重試必做（_COMMIT_MIN_RETRIES=3，不受牆鐘限制）；額外重試須累計 sleep <= 5.0s（只計 sleep，不含嘗試耗時）且自首次嘗試起牆鐘 <= 20.0s（_COMMIT_RETRY_WALL_CAP_SECONDS）；新增時鐘接縫 _clock。commit 2b8cd80b0。

量測（單次提交嘗試=commit+guard+update-ref，N=24，3 輪各 8 次，load1 30.2-37.7）：min 0.37s、median 約 0.69s、max 3.01s；各輪 median 0.68/0.74/0.51、max 1.37/3.01/1.46。先前記載的 load1 39-62 未能再現，取 max 3.0s 並以約 2 倍餘裕（6s）計算。
預算依據：最少重試 3 次=閒置機器本來就會做的 3 次（退避 0.5/1/2 共 3.5s，5s 預算下第 4 次 2s 超出）。保證路徑最壞耗時=4 次嘗試 x 單次耗時+3.5s：量測 max 3.0s 計 15.5s；2 倍餘裕 6s 計 27.5s。呼叫端 timeout：auto-commit hook 30s（settings.json）、CLI 經 Bash 工具預設 120s。額外重試牆鐘 20s < 30s；保證路徑 15.5s < 30s；單次嘗試容忍上限約 (30-3.5)/4=6.6s。已知上界：最少重試不受牆鐘限制，單次嘗試持續超過 6.6s 時保證路徑會超出 hook timeout。Phase 4：重構需要否；技術債務無；品質 A。
### 驗收第 3 項的兩層依據（PM，依 e1 條件整理）

**測試層：判定與負載隔離**
- 預算判定改用可注入的 `git_utils._clock`（假時鐘），測試結果不再隨機器負載變動。這一層以假時鐘證明。
- 新增測試 `test_wall_cap_limits_retries_beyond_min` 本身另有非決定性問題，由 incident 開立的修復票處理。這不影響本節結論。

**產品層：真實高負載下的行為**
- 由「可重試的失敗至少重試一次」這項保證承擔，與預算數值無關。
- 程式依據：`may_retry = attempts <= _COMMIT_MIN_RETRIES or within_extra_budget`。前 `_COMMIT_MIN_RETRIES`（3）次重試透過 `or` 短路，不受牆鐘上限與 sleep 預算約束；即使第一次嘗試已超過預算，仍至少重試。
- 斷言此保證的測試：
  - `test_slow_first_attempt_still_retries_once`：第一次嘗試極慢，仍會重試並 committed。
  - `test_min_retries_guaranteed_then_wall_cap_stops`：最少重試次數必定執行，之後才由牆鐘上限停止。

**預算數值的量測依據（照實記錄）**
- 單次提交嘗試的耗時分布在 load1 30.2～37.7 下量測，N=24，max 3.0 s。N>=5 連跑時 load1 只有 9～16，不屬於高負載。
- 高負載情境由最少重試保證涵蓋；預算數值（sleep 5 s、牆鐘 20 s）只影響最少次數之外的額外重試。本票不宣稱已在高負載下驗證預算數值。

**實地觸發**
- 主 repo 真實 retry 日誌有一筆 `[2026-10-01 23:04:12] retry ticket=0.4.1-W1-042 attempt=1 waited_s=0.50 reason=cas_rejected`。下一秒 23:04:13，commit dcf8a7eac（claim status）落地，日誌中沒有對應的 final_failure，表示真實 HEAD 競爭後重試一次即提交成功。
- 這筆記錄是在 W1-026 版本的重試邏輯下觸發的；本票合併時間為 23:2x，晚於這筆記錄。因此它同時是 W1-026 日誌與 CAS 判定的實地觸發證據。
