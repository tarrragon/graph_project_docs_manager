## Problem Analysis
<!-- Schema[ANA/Problem Analysis]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
反方向實例（2026-10-01，主 repo）：ticket migrate 0.4.1-W1-010.6.1 0.4.1-W1-010.7 時，新 ID 的階層對應的父票從 W1-010.6 變成 W1-010。migrate 依新 ID 把 W1-010.7 的 parent_id 改為 W1-010，但引用改寫只做 ID 替換：W1-010.6 的 children 被換成 W1-010.7，W1-010 的 children 卻沒有加入，形成雙向不一致；PM 以 add-child 與 set-parent 往返手動修正（330d1cb93、c3fce27db）。本票分析時應一併涵蓋：遷移造成父票改變時，舊父 children 移除、新父 children 加入。

重現環境：tmp 專案目錄（非 git，auto-commit 為 skipped 非致命；提交範圍由程式碼推導，見 Solution）。以 TICKET_SYSTEM_TEST_ISOLATION=1 與 CLAUDE_PROJECT_DIR 指向 tmp 目錄，執行本 worktree 的 ticket migrate。樹：010(children 010.1, 010.6)；010.1(child 010.1.1)；010.6(child 010.6.1)。程式碼位置：migrate.py 的 _migrate_ticket_files 與 _update_cross_references_collecting，皆只做舊 ID 到新 ID 的逐欄位字串替換，不走訪子孫、不同步 children。

案例 A：migrate 010.6 到 010.8（同層改號，被遷移票有子票）
- 子票 010.6.1：id 不變，parent_id 與 chain.parent 改為 010.8，chain.root 不變。ID 前綴（010.6）與 parent_id（010.8）不一致，010.6 這個 ID 已不存在。
- 新票 010.8：previous_ids=[010.6]，chain 重算為 depth 1，children=[010.6.1]（舊 children 保留）。
- 父票 010：children 內 010.6 被替換為 010.8。此案例父票未變，children 無誤。
結論：parent_id 與 children 欄位自洽，唯一斷裂處是 ID 階層前綴。

案例 B：migrate 010.6.1 到 010.7（新 ID 階層對應的父票由 010.6 變成 010，即 W1-010.6.1 事件）
- 新票 010.7：parent_id 與 chain.parent 重算為 010，正確。
- 舊父 010.6：children 內 010.6.1 被替換為 010.7（應移除）。
- 新父 010：children 維持 [010.1, 010.6]，未加入 010.7（應加入）。
- 結果：010.7.parent_id=010，但 010 的 children 不含 010.7，而 010.6 的 children 含 010.7，雙向不一致；與主 repo 事件一致。根因：替換邏輯只認舊 ID 字串，沒有「舊父移除、新父加入」的結構性同步步驟。

案例 C：migrate 010.1 到 030（中間層提升為根）
- 新票 030：chain 重算為 root/depth 0/parent None，但 parent_id 仍為 010（migrate.py 只在 chain_info.parent 非空時覆寫 parent_id，沒有清除分支），id 階層為根而 parent_id 指向 010；父票 010 的 children 因字串替換含 030。額外缺陷，歸入子票 1。
- 子票 010.1.1：id 不變，parent_id 與 chain.parent 改為 030，chain.root 仍為 010（chain.root 只在 old_id 等於 root 時才被改寫）。

共通事實：子票永遠不隨父票遷移；引用改寫涵蓋 blockedBy/relatedTo/children/source_ticket/parent_id/spawned_tickets/discovered_during/closed_by/chain.root/chain.parent，但「ID 前綴即階層」這個不變式沒有任何程式碼維護。已驗證事實：以上三案的欄位值皆為實測；未驗證：真實 git 下單一隔離提交的實際路徑集合（tmp 目錄非 git，僅由 _commit_migrations 程式碼推導）。

## Solution
<!-- Schema[ANA/Solution]: 必填（.claude/pm-rules/ticket-body-schema.md） -->
### 結論：採「連帶遷移」，附 preflight 全有或全無；preflight 失敗時退化為拒絕

三案比較（評估軸為任務指定三點）：

| 評估軸 | 連帶遷移 | 拒絕遷移（有子票即拒） | 保持現狀 |
|--------|---------|----------------------|---------|
| previous_ids / chain / topic | 每個子孫各追加 previous_ids、重算 chain、追加一行 topic（inherit_assignment 對每個新 ID 各一行，append-only，舊行保留）；ID 前綴不變式成立 | 全不動，但封死合法流程 | 子孫 ID 前綴懸空（案例 A、C），previous_ids 無法回溯子孫為何掛在不存在的前綴下 |
| 單一隔離提交範圍 | _commit_migrations 已接受 records 清單並一次提交（批次路徑 _batch_migrate 同機制）；範圍 = 子樹每票新檔 + 舊檔刪除 + 全部引用者 + topic 追加行，隨子樹大小線性成長但仍單一 commit | 零 | 同現狀：被遷移票 + 引用者 |
| MAX_TICKET_DEPTH=3 | 子樹整體平移，最深子孫深度 = 新父深度 + 1 + 子樹內相對深度，可能超限；須 preflight 阻擋（深度上限現為 warn 不硬擋，見 ticket_id_allocator，migrate 路徑應硬擋，因為連帶改號不可回頭） | 不涉及 | 不涉及，但遷移後 ID 字串深度與 parent_id 鏈深度可分歧（案例 C） |

選連帶遷移的理由：
1. 發版前撞號改號機制（_resolve_available_target_id）會遷移任意票，含有子票者；拒絕會讓該流程在父票撞號時卡死。
2. 現況的斷裂是「ID 前綴即階層」不變式未被維護；連帶遷移是唯一讓不變式成立的方案，拒絕只是不讓它被破壞，保持現狀則持續破壞。
3. 基礎設施已就緒：records 清單 + 單一 commit + 逐票 topic 追加皆已存在，缺的是子樹展開與 preflight。

設計要點（交實作票）：
- 子樹以 ID 前綴 + parent_id 雙重判定收集，old 到 new 映射一次建完，引用改寫用同一個映射單趟套用（逐對序列改寫在 010.1 到 010.2 與 010.2 到 010.3 這類重疊映射下會二次改寫，需避免）。
- preflight 全數通過才寫檔：所有新 ID 無碰撞（或比照現行改號）、最深新 ID 深度不超過 MAX_TICKET_DEPTH、目標版本已註冊。任一失敗則整體拒絕、零寫入並輸出原因。
- 原子性：目前 _migrate_ticket_files 先寫檔後提交，中途失敗無回滾；連帶遷移擴大此窗口，實作票需定義失敗時的處置（至少列出已寫入集合）。
- 與 parent 變更同步（驗收第 3 項）獨立成票且先做：不依賴連帶遷移，對單票遷移同樣成立。
