## Problem Analysis
### 問題根因

version-shift 與 migrate 是兩套各自維護的「改票號＋改引用」實作，前者自 2026-08-26 框架導入後未再演進（git log 只有導入與 sync 兩筆），後者經 W1-010.1～.5 已補齊自動提交、previous_ids、topic 承接、hierarchical 掃描與 discovered_during／closed_by／chain 改寫。version-shift 的缺陷都來自「沒有跟上框架不變式」：

- 路徑：`_validate_versions` 等七處寫死扁平 `docs/work-logs/v{version}`，不經 `paths.get_tickets_dir_under_root`。框架不變式 W14-052 規定新版本一律三層，故 version-shift 對任何依預設建立的版本都在前置驗證 exit 1（X1 重現）；即使在扁平舊結構下能跑，產出的目標目錄也是扁平，違反同一不變式。
- todolist：`yaml.safe_dump` 整檔重寫；只改 `current_version`／`previous_version`／`tech_debt` 三鍵，`versions[]` 不動。
- 引用：以「版本前綴替換」改 6 個欄位，與 migrate 的「精確 ID 比對」語意不同，且漏 discovered_during、closed_by；跨版本掃描只看 `v*/tickets`（扁平）。
- 其餘缺口：不記 previous_ids、不承接 topic、不改 worklog 主檔名、不提交；所有 except 皆靜默（`_shift_single_ticket`、`_process_ticket_for_cross_refs`、`_rename_worklog_dir`、`_update_todolist_yaml`、`execute` 的 RuntimeError），這正是 IMP-025 收錄的案例本身；`_find_auxiliary_files` 在檔案改名之後才執行，計數恆為 0。
- 測試未發現的原因：test_version_shift.py 的 22 個案例全部使用扁平 fixture，沒有一個案例落在框架預設的三層結構上。

## Solution
### 結論摘要（待用戶 WRAP 裁決）

建議 C：把 version-shift 改為 migrate 的批次包裝。保留命令名與參數（`ticket version-shift <from> <to> [--dry-run]`），票面的改號、改引用、topic、previous_ids、提交全部交給 migrate；version-shift 只負責 migrate 不處理的三件事：列舉來源版本的票、todolist 版本條目原位改寫、worklog 主檔改名，並把這三者併入同一筆提交。

理由：
- 單一實作：version-shift 的缺陷全部來自「自己另寫一套改號邏輯而沒跟上框架不變式」。A 會保留兩套實作，下次 migrate 再補欄位時又會分歧；B 與 C 都消除分歧，C 另外保留命令介面。
- 實驗支撐：X3 證明 migrate --config 已完成整版搬移的票面部分且符合 W1-010 (1) 的提交語意，C 的新增範圍收斂到三件事。
- 預設行為優先（opinionated-default 主張 1、4）：B 留給使用者的是一份四步人工程序（登記版本、產生設定檔、執行 migrate、手改 todolist 與 worklog 主檔），漏做最後一步不會報錯，只會讓之後每次 complete 靜默缺進度行（見實驗發現）。C 把這些步驟收進工具。
- consumer 影響：C 不改 CLI 介面，在 canonical 端不是破壞性變更；B 會讓仍在扁平舊結構使用此命令的 consumer 失去命令，而本 repo 無法驗證是否有這類 consumer。

選 B 的條件：若用戶判定「整版改號」不是框架要支援的操作（本 repo 無使用紀錄，也沒有任何流程依賴它；發版前移走逐張 migrate），B 的維護面最小。此時 B 的人工程序須寫進 SKILL.md，且應附 worklog 主檔處理步驟，否則會出現上述靜默缺行。

不建議 A：修復需要的五項（階層路徑、保留註解的 todolist、versions[]、worklog 主檔、topic）加上 previous_ids、discovered_during／closed_by、提交、五處靜默 except，幾乎是重寫 migrate 已具備的能力，且留下兩套實作。
