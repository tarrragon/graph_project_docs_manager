## Solution
### 根因（實驗佐證，執行者回報、PM 覆核）

等待來源是測試啟動的 git 子程序數，乘上主機高負載下每個子程序的啟動延遲；不是 sleep、uv 或 shim。
- 排除：兩支 hook 程式內沒有 sleep、backoff、retry；install 測試用假的 uv 腳本；guard 以 sys.executable 執行；全域 git config 沒有 templateDir 或 hooksPath，tmp repo 不含 shim。
- 子程序計數（subprocess spy）：TestBatchedEquivalence 12 案共 227 次 `git --no-optional-locks -c ...`，另有每案重複的 init、config ×2、add、commit，約 60 次。
- 量測期間 load average 40～79，CPU 約 10%（程序在排隊）；同一份未改動的測試，在不同時段量到 28～52 秒。

### 修正（實作 30661c2a7，合併 6abc4873f）

只改兩個測試檔，hook 產品碼與 gate 上限都未動。
- 兩檔各加 module 級模板 repo fixture，每個測試以 shutil.copytree 取副本，取代每次重跑 init、config、add、commit。content_guard 的模板分支固定為 main。
- content_guard 的 5 個情境（violation、clean、multi_file、root_commit、merge）整檔只建一次，副本連 commit SHA 一併帶走；TestSubprocessCountConstant 改用模板副本。
- 斷言本身未改，只改 repo 的取得方式。

### 鑑別力正向對照（執行者實測後還原）

| 改壞的產品碼 | 結果 |
|---|---|
| `_build_scan_files_batched` 的 post_text 加後綴 | test_staged_files_identical_to_legacy 5 個情境全紅 |
| 批次路徑每檔多一次 rev-parse | test_count_independent_of_changed_file_count 紅（F=1 為 12 個程序、F=21 為 32 個） |

test_scenarios_cover_both_verdicts 的 violation 與 clean 各取獨立副本，deny 與放行兩種判定都保留。

### 自檢結果（PM）

- commit 位於正確分支，worktree 乾淨，只動兩個測試檔，無殘留鎖。
- 代理人回報的 hooks 總數（5019 passed 加 48 skipped）與基線 5277 有落差。查核結果：基線是 hooks 與 `.claude/lib/tests` 合計，PM 實跑 lib 為 258 passed，5019 加 258 等於 5277。本票沒有新增案例。
- 放寬 gate 上限沒有被採用。

### Phase 4 重構評估

- 重構需要：否
- 技術債務：無新增
- 程式碼品質：A
- 結論：模板副本 fixture 是測試基礎設施層的收斂，把每個測試的建 repo 成本降為每個檔案一次。子程序數斷言與等價性斷言的語意不變，鑑別力已由上方正向對照驗證。

### 第二輪（實作 e07470896，合併 953d707dd）

**做法**：只拆測試檔，不改 hook 本體與 gate。gate 只執行名稱完全符合 hook 的 `test_<stem>.py`，所以搬到 `test_git_ref_transaction_content_guard_batched.py` 的測試不在 gate 執行範圍內，改由全套件執行。所有斷言一字未改；共用 fixture 由 _batched 檔以相對匯入從原檔取用，沒有複製。

| 範圍 | 驗證的測試 |
|---|---|
| gate（原檔，18 項） | hook 主路徑測試，加上 TestBatchedEquivalence 的 violation 代表案例（staged 與 findings 各 1）。e1 裁定：批次化是正式路徑，原檔至少保留一個等價性案例 |
| 只有全套件會跑（_batched 檔，11 項） | 等價性的 clean、multi_file、root_commit、merge 四個情境；deny 與放行對照；fallback；TestSubprocessCountConstant |

**剩餘風險**：改 hook 時，重量級變體（multi_file、root_commit、merge、fallback、子程序數）的問題，要到全套件才會被發現，gate 看不到。

**鑑別力正向對照**（執行者實測後還原）：
- 改壞批次路徑的輸出：原檔的 violation 代表案例翻紅。
- 每個檔多一次 git 子程序：_batched 檔的子程序數測試翻紅。

**原因量測**：拆檔前，TestBatchedEquivalence 合計約 70 秒，約佔整檔一半；其中最慢的是 root_commit 情境 15.8 秒（load 57～120）。
