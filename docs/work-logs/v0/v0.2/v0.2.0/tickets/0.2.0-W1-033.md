### 判定順序實作要點（與 W1-024／W1-038 定案對齊）

範圍判定恆以 JSON 的 `schema_generated_at_framework_version`（非 `.claude/VERSION`）與 App 內建版本比較（`!isHigherThanBuiltinSchemaVersion(jsonVersion, builtinVersion)`，`0.2.0-W1-024` 定案）；`.claude/VERSION` 是否存在只決定「顯示版本是否為推定值」，不參與範圍比較——W1-032 manifest 中 flutter_balance／graph_project_docs_manager 兩列 VERSION（2.59.9／2.60.3）遠高於 builtin（2.40.3）但仍正常載入，因為 JSON 版本等於 builtin，正是此設計的直接驗證（17 列整合測試逐列覆蓋）。

### 與 how.strategy 的一處偏離：domainViewStateProvider 未改為 NotifierProvider

策略文字寫「domainViewStateProvider 由 StateProvider 改為 notifier 供應」。實測 `test/unit/screens/domain_view_test.dart` 有 20+ 處 `domainViewStateProvider.overrideWith((ref) => const DomainXxx())`（StateProvider 的 `overrideWith` 簽章為 `(ref) => T`），若改為 `NotifierProvider`，`overrideWith` 簽章需改為 `() => Notifier<T>`，會使該檔全數 override 呼叫編譯失敗——該檔不在本票 `where.files`，屬越界大改。

改採維持 `domainViewStateProvider` 為 `StateProvider` 不變，`GateDetectionNotifier`（獨立 `Notifier<void>`）以 `ref.read(domainViewStateProvider.notifier).state = ...` 寫入——這已滿足「由 gate 偵測 notifier 供應狀態」的實質語意（gate 偵測邏輯以 notifier 形式存在、負責計算並寫入狀態），只是不改變 `domainViewStateProvider` 本身的宣告型別。此為避免大範圍越界破壞而做的判斷，不是忽略策略——`test/integration/gate_manifest_test.dart` 直接驗證此寫入路徑的正確性。
