### 6. 整合測試形態建議

### 候選方案

**方案 A：凍結 fixture 快照**

測資在 `test/integration/` 以 Dart 常數定義 17 列 manifest（專案名、VERSION 值、JSON 存在、預期分支、降級可否），測試以 mock filesystem port 驅動 gate 偵測邏輯，斷言每列的最終 DomainViewState 與預期分支一致。

| 優點 | 缺點 |
|------|------|
| CI 可執行（無 ~/project 依賴） | 測資可能與現實漂移 |
| 斷言逐專案（非僅三個計數） | 新增專案需手動更新 fixture |
| 可涵蓋邊界案例（VERSION 缺 + JSON 有） | 不驗證真實路徑 |

**方案 B：真實路徑即時掃描**

integration_test/ 直接掃描 ~/project/ 並斷言每個目錄的 gate 分支。

| 優點 | 缺點 |
|------|------|
| 驗證真實環境 | CI 無 ~/project |
| 自動涵蓋新增專案 | 環境不同結果不同（fragile） |
| 無手動 fixture 維護 | 專案增刪測試紅燈 |

**方案 C：凍結 fixture + 開發機 live overlay**

主測試為方案 A（CI 用）；`test/integration/` 另有一支 `@Tags(['live'])` 的 live test 掃描 ~/project/ 比對 fixture manifest，若有差異報 warning（非 fail）。

| 優點 | 缺點 |
|------|------|
| CI 安全 + 開發機額外驗證 | 兩條路徑維護 |
| live test 警示 fixture 漂移 | live test 為 advisory 非 blocking |

### 建議

**採方案 A（凍結 fixture）**。理由：

1. PROP-005 §0.2 的整合測試定義為「本機 17 個有 .claude/ 的專案，各自進入正確的 gate 分支」——斷言粒度已明確為逐專案，而非僅三個計數。方案 A 的 fixture manifest 直接承載此粒度。
2. CI 環境無 ~/project，方案 B 不可行。方案 C 的 live overlay 增加維護成本但收益有限（fixture 漂移由 SPEC-001 變更驅動而非環境驅動）。
3. 測資來源為本票 §1 manifest 表，凍結時間點已知，漂移可追蹤。

**斷言粒度**：每列一個 test case，斷言 `gate(versionValue, jsonExists) == expectedBranch`。不以三個計數斷言（6/9/2）為唯一斷言——計數正確但個別專案分支錯誤時計數恰巧守恆。

**CI 環境無 ~/project 的處置**：fixture manifest 是 Dart 常數，不依賴檔案系統。mock filesystem port 回傳 fixture 定義的訊號。若未來需要真實路徑驗證，另建 `@Tags(['live'])` 測試。
