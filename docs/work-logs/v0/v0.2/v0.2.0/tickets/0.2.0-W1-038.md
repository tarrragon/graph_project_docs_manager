定案 VERSION 缺加 JSON 有路徑的 state 處理

## Problem Analysis
### 問題根因

SPEC-001〈Gate 三問對照〉schema gate「不確定」欄定義了「`.claude/VERSION` 缺失但 JSON 存在 → 以 JSON 內的產生版本推定並標示」的行為，但：
1. §1 狀態表無對應列——判定順序 step 3（JSON 存在 → 依版本範圍分正常／schema 不相容）的隱含前提是 VERSION 存在，但 step 1 只攔截「兩者皆缺」，VERSION 單獨缺失而 JSON 存在的路徑直接落入 step 3 卻無載體
2. `DomainViewState` sealed class 的七個子類別皆不承載「版本來自推定」的語意：`DomainReady` 無版本欄位、`DomainSchemaIncompatible` 的 `projectVersion` 語意為 `.claude/VERSION` 真實值而非推定值
3. Gate 偵測 notifier 尚未建置（W1-033 核心缺口），但即使建置，路由至 state 的映射也缺此分支

### 影響範圍

**已驗證的事實**：
- W1-032 manifest 的 17 個真實專案中 **0 個**命中此路徑（6 個兩訊號皆缺、9 個只有 VERSION、2 個兩者皆有）
- `DomainSchemaUnconsumable` 的 `version` 欄位為 required String（domain_view_state.dart），語意綁定 `.claude/VERSION` 真實值
- `DomainSchemaIncompatible` 的 `projectVersion` 同樣語意綁定 `.claude/VERSION`
- `isDegraded` 旗標已在 `DomainReady` 與 `DomainEmpty` 上實作，為正交疊加旗標的先例
- 降級徽章由 `degradedSchemaProvider` + `degradedSchemaVersionsProvider` 兩個獨立 provider 承載，`AppShell` 於返回列常駐渲染

**仍未驗證的假設**：
- 「App 已知範圍」判準（W1-024 pending）未定，推定版本落入 in-range 或 out-of-range 的邊界未完全確定

3. `isDegraded` 旗標是「正交疊加旗標」的既有先例：不新增 state 子類別、以 bool 欄位疊加於 `DomainReady`／`DomainEmpty`、搭配獨立 provider 承載徽章文字
4. 降級徽章渲染位置為「頁面框架於返回列常駐」（SPEC-001 §1 降級註記 (4)），推定版本標示可比照同一位置

**仍未驗證的假設**：
- Gate 偵測 notifier（W1-033）尚未建置，推定邏輯與 state 路由的整合行為無法端到端驗證

## Solution
### WRAP 快速模式

#### W（Widen）— 三個候選方案

**方案 A：既有 state 加 `inferredVersion` 疊加旗標**

在 `DomainReady`、`DomainEmpty`、`DomainSchemaIncompatible` 三個子類別加 `String? inferredVersion` 欄位（或 `bool isVersionInferred`），null／false 為預設（VERSION 真實值）、non-null／true 為推定值。畫面層據此渲染標示徽章。

| 利 | 弊 |
|----|-----|
| 沿用 `isDegraded` 旗標先例，模式一致 | 觸及三個既有 state class（`DomainReady`、`DomainEmpty`、`DomainSchemaIncompatible`），各加一個 nullable 欄位 |
| 不新增 sealed 子類別，switch 分支不增加 | 「推定」是正交關注點散佈於三個類別，語意不如獨立類別集中 |
| W1-033 gate notifier 路由邏輯最簡單：檢測到 VERSION 缺 + JSON 有 → 用 JSON 版本當 version → 走正常流程 → 在結果 state 上設 inferredVersion | `DomainSchemaIncompatible` 已有 `projectVersion`（語意為 VERSION 真值），加 `isVersionInferred` 後需同時改語意說明 |
| 標示徽章可比照降級徽章位置（返回列常駐） | — |

**方案 B：新增 sealed 子類別 `DomainVersionInferred`**

新增一個包裝式 state class：

```dart
class DomainVersionInferred extends DomainViewState {
  const DomainVersionInferred({
    required this.inferredVersion,
    required this.inner, // DomainReady / DomainEmpty / DomainSchemaIncompatible
  });
  final String inferredVersion;
  final DomainViewState inner;
}
```

| 利 | 弊 |
|----|-----|
| 「推定」語意集中於一個類別 | 包裝模式破壞 sealed class 的扁平 switch 慣例——畫面層需先匹配 `DomainVersionInferred` 再解包 `inner`，分支數從 7 變 8 且 inner 的類型需二次 switch |
| 不動既有子類別欄位 | SPEC-001 §1 需新增一列狀態（影響狀態總數，與 §8.1 逐狀態標註表均需同步） |
| — | `DomainVersionInferred(inner: DomainReady(...))` 與 `DomainReady(inferredVersion: ...)` 語意等價但結構更深，測試 fixture 撰寫成本更高 |
| — | 0/17 真實專案命中此路徑，為一個零命中的邊界案例新增 sealed 子類別結構開銷過大 |

**方案 C：併入「無可消費的型別表」（`DomainSchemaUnconsumable`）**

將「VERSION 缺 + JSON 有」視為「schema 狀態未知」，路由至 `DomainSchemaUnconsumable`，使用者需手動「以 App 內建型別表檢視」才能進入。

| 利 | 弊 |
|----|-----|
| 不新增欄位也不新增子類別 | **語意錯誤**：JSON 存在且版本可能在範圍內，使用者可以正常檢視圖譜，卻被阻擋在需手動操作的關卡——違反 Gate 三問「推定並標示」（允許進入但標示）的設計意圖 |
| — | `DomainSchemaUnconsumable` 的顯示文字「此專案的框架版本早於圖譜型別表的機器可讀匯出」在 JSON 存在時**事實錯誤** |
| — | `DomainSchemaUnconsumable.version` 為 `.claude/VERSION` 真實值，VERSION 缺失時無值可傳——需改為 nullable 或傳空字串，破壞既有 required 語意 |
| — | 降級出口判定依賴 `.claude/VERSION` 值（「不高於 App 內建版本」），VERSION 缺失時無從比較 |

#### R（Reality Test）

見「重現實驗結果」章節。核心事實：

1. 0/17 真實專案命中此路徑 → 結構開銷應最小化
2. Gate 三問定義行為為「推定並標示」→ 使用者應能直接進入正常畫面，不被阻擋
3. `isDegraded` 旗標模式已建立先例 → 方案 A 模式一致

#### A（Attain distance）

本票為 P2 ANA，不擠壓其他工作。方案 A 的修改量最小（三個類別各加一個 nullable 欄位 + copyWith 擴充 + 徽章渲染），W1-033 實作端可直接消費。

#### P（Prepare to be wrong）

最可能失敗的原因：方案 A 的 `inferredVersion` 欄位在三個類別上散佈，未來若推定版本的標示語意進化（例如需區分「推定自 JSON」與「推定自其他來源」），散佈的欄位需同步改動。防護措施：三個類別的欄位名稱與語意完全相同（`String? inferredVersion`），日後若需集中化可一次提取為 mixin 或共用介面，不需先行過度設計。

### 定案結論

**採方案 A：既有 state 加 `inferredVersion` 疊加旗標。**

理由排序：
1. **語意正確性**：Gate 三問「推定並標示」的行為是「允許進入 + 標示推定來源」，方案 A 精確承載此語意（進入正常流程 + 旗標標示）；方案 C 阻擋使用者，違反設計意圖
2. **先例一致性**：`isDegraded` 旗標模式完全匹配——不新增 sealed 子類別、以 nullable 欄位疊加正交關注點、搭配獨立 provider 承載徽章文字
3. **結構開銷比例**：0/17 真實專案命中、方案 B 新增 sealed 子類別 + SPEC-001 新增狀態列 + §8.1 同步 + 包裝式 switch 二次解包——結構開銷與命中機率嚴重不成比例

#### DomainViewState 載體形狀

三個受影響子類別的變更：

**`DomainReady`**：新增 `String? inferredVersion` 欄位（預設 null）。null 時為正常（VERSION 真實值驅動），non-null 時值為 JSON 的 `schema_generated_at_framework_version`，畫面標示「版本推定自型別表」。`copyWith` 同步擴充。

**`DomainEmpty`**：新增 `String? inferredVersion` 欄位（同語意）。空圖也可能發生在推定版本路徑上（JSON 存在且版本在範圍 → 載入 → 節點為零）。

**`DomainSchemaIncompatible`**：新增 `bool isVersionInferred`（預設 false）。此類別已有 `projectVersion` 欄位承載版本值——推定版本落入此欄（語意從「`.claude/VERSION` 真實值」擴展為「專案版本（真實或推定）」），`isVersionInferred` 標記來源。不新增 `String? inferredVersion` 避免與 `projectVersion` 語意重疊。

不觸及的子類別：`DomainUnset`（未選專案）、`DomainLoading`（載入中）、`DomainNotFramework`（兩訊號皆缺）、`DomainSchemaUnconsumable`（VERSION 有 + JSON 無）——此四類在判定順序上不可能經歷「VERSION 缺 + JSON 有」路徑。

#### 畫面標示位置

比照降級徽章先例（SPEC-001 §1 降級註記 (4)），推定版本徽章由 `AppShell` 於返回列同一列常駐渲染，六畫面任一狀態皆顯示（前提：gate 偵測結果為 inferredVersion 非 null）。徽章文字建議：「版本推定自型別表 (v{inferredVersion})」。

承載方式比照降級徽章的 `degradedSchemaProvider` + `degradedSchemaVersionsProvider` 模式：新增 `inferredVersionProvider`（`StateProvider<String?>`），gate 偵測 notifier 於偵測到 VERSION 缺 + JSON 有時寫入 JSON 版本值，切換專案時重置為 null。`AppShell` 讀取此 provider，non-null 時渲染徽章。

**與降級徽章的共存**：推定版本 + 降級在邏輯上互斥（推定版本路徑必然走 step 3 即 JSON 存在，降級路徑的進入條件是「無可消費的型別表」即 JSON 不存在），兩個徽章不會同時出現。

#### Gate 偵測 notifier 對本定案的消費方式（供 W1-033 參考）

```
偵測流程 step 3（JSON 存在）：
  讀取 JSON 的 schema_generated_at_framework_version → jsonVersion
  if (VERSION 存在):
    version = VERSION 真實值
    isInferred = false
  else:
    version = jsonVersion
    isInferred = true
  
  版本範圍判定(version, builtinVersion):
    在範圍 → DomainReady(inferredVersion: isInferred ? jsonVersion : null)
             或 DomainEmpty(inferredVersion: isInferred ? jsonVersion : null)
    超出範圍 → DomainSchemaIncompatible(
                 appVersion: builtinVersion,
                 projectVersion: version,
                 isVersionInferred: isInferred)
  
  寫入 inferredVersionProvider（isInferred ? jsonVersion : null）
```
