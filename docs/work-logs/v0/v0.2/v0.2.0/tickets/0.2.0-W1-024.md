## Problem Analysis
### 問題根因

SPEC-001 §1「schema 不相容」進入條件使用「框架版本超出 App 已知範圍」作為判準，但「App 已知範圍」一詞從未被定義。CLAUDE.md §6 將其列為五項空殼判準之一。

判定對象是被觀察專案 `tracking_schema.json` 內的 `schema_generated_at_framework_version` 欄位，對照 App 內建資產 `assets/schema/builtin_schema_version.json` 的同名欄位。非 `.claude/VERSION`（後者用於「無可消費的型別表」的降級出口判定，見 `domain_view_schema_version.dart` 的 `isHigherThanBuiltinSchemaVersion`）。

### 影響範圍

**已驗證的事實**：

- SPEC-001 §1、Gate 三問對照、FR-04 三處引用「App 已知範圍」但未定義
- SPEC-001 §1 L67-68 註記：「App 已知範圍」判準定案時以面板改放本體沒有的資訊重評（trigger：`0.1.0-W3-364`，已遷移至本票）
- W3-335.37 R4 P 失敗訊號亦依賴本判準定案
- SPEC-003 §2.7 阻擋狀態比較表引用「App 支援版本與專案版本兩值」——兩值的語意依賴本定義
- 現有 `isHigherThanBuiltinSchemaVersion` 函式的比較邏輯（逐段整數比較）可直接重用，僅需改變第一運算元（JSON 版本取代 `.claude/VERSION`）
- App builtin 版本為 `"2.40.3"`，W1-032 manifest 中兩個「可載入」候選的 JSON 版本皆為 `"2.40.3"`

**仍未驗證的假設**：

- `schema_generated_at_framework_version` 僅在 schema 內容變更時才更新（目前兩個有 JSON 的專案框架版本 2.59.9 與 2.60.3，但 JSON 版本皆停在 2.40.3，暗示如此，但非契約保證）

### 相關 Error Pattern

無直接對應的 error-pattern。最近似者為 PC-055（AC 漂移偵測）——判準引用散佈但定義缺席導致各處獨立假設。

### 實驗發現

**已驗證的事實**：
1. 「App 已知範圍」被 SPEC-001 三處、SPEC-003 一處、CLAUDE.md 一處、W3-335.37 一處引用，共七處，無一定義
2. 所有引用皆使用「超出」一詞，語意為方向性上界（非雙向範圍）
3. 判定對象一致：JSON `schema_generated_at_framework_version` 對 App builtin 同名欄位
4. 現有比較函式 `isHigherThanBuiltinSchemaVersion` 的邏輯可直接重用（取反即為「在範圍內」）
5. W1-032 manifest 中兩個「可載入」候選 JSON 版本皆 = builtin（2.40.3），三個候選定義在現有資料上結果一致
6. `schema_generated_at_framework_version` 在框架 VERSION 從 2.40.3 進至 2.60.3 期間未改變，暗示此欄位僅在 schema 內容變更時更新

**仍未驗證的假設**：
- 上述第 6 點為觀測推斷，非契約保證。若框架在不改 schema 的情況下重新匯出 JSON，版本欄位會跟著框架 VERSION 上升，此時 Candidate A 會產生 false positive（不影響安全，僅影響便利性）
