## Problem Analysis
### 問題根因

SPEC-001 §1「schema 不相容」進入條件使用「框架版本超出 App 已知範圍」作為判準，但「App 已知範圍」一詞從未被定義。CLAUDE.md §6 將其列為五項空殼判準之一。

判定對象是被觀察專案 `tracking_schema.json` 內的 `schema_generated_at_framework_version` 欄位，對照 App 內建資產 `assets/schema/builtin_schema_version.json` 的同名欄位。非 `.claude/VERSION`（後者用於「無可消費的型別表」的降級出口判定，見 `domain_view_schema_version.dart` 的 `isHigherThanBuiltinSchemaVersion`）。

## Solution
### 1. WRAP 評估

#### W（Widen）：三個候選定義

**Candidate A：json_version <= builtin_version（向後相容，拒絕較新）**

判定式：`schema_generated_at_framework_version`（JSON）<= `schema_generated_at_framework_version`（builtin）

| 面向 | 評估 |
|------|------|
| 語意 | App 內建版本為上界；JSON 版本等於或低於 builtin → App 認識該 schema → 正常；JSON 版本高於 builtin → App 不認識 → schema 不相容 |
| 實作 | `!isHigherThanBuiltinSchemaVersion(jsonSchemaVersion, builtinSchemaVersion)` ——重用既有函式，僅第一運算元從 `.claude/VERSION` 改為 JSON 的 `schema_generated_at_framework_version` |
| 安全預設 | 版本字串無法解析時 `isHigherThan` 回傳 `true` → 取反為 `false` → schema 不相容（拒絕不確定格式，與 SPEC-001「無可消費的型別表」精神一致） |
| 優點 | 與 SPEC-001 所有「超出」用語方向一致；App 升級後自然接納舊 JSON（App parser 較新，可處理舊 schema 子集，缺欄位由 damage marking 處理）；無額外資產維護 |
| 缺點 | 若框架在不改 schema 的情況下重新匯出 JSON，JSON 版本會跟著框架 VERSION 上升，超過 App builtin → false positive（不影響安全，僅影響便利性） |

**Candidate B：json_version == builtin_version（精確比對）**

判定式：`schema_generated_at_framework_version`（JSON）== `schema_generated_at_framework_version`（builtin）

| 面向 | 評估 |
|------|------|
| 語意 | 僅接受與 App 內建版本完全一致的 JSON |
| 優點 | 零風險、零模糊 |
| 缺點 | App 升級後（builtin 跟著上升）舊 JSON 立即被拒——即使 schema 內容不變、App parser 完全相容。假設情境：schema 在 2.40.3 至 2.50.0 之間未改變，App 以 2.50.0 重建後 builtin = 2.50.0，原 JSON 2.40.3 != 2.50.0 → 被判 schema 不相容，使用者被不必要地阻擋 |

**Candidate C：\[min_known, builtin_version\] 顯式管理範圍**

判定式：`min_known_version` <= JSON version <= `builtin_version`，其中 `min_known_version` 為額外維護的下界資產

| 面向 | 評估 |
|------|------|
| 語意 | 有明確的上下界，可精確控制相容範圍 |
| 優點 | 可精確排除已知不相容的舊版 |
| 缺點 | 需額外資產（`min_known_version` JSON 或常數）；初始 min = builtin → 等同 Candidate B，無額外收益；維護負擔與回報不成比例——目前只有一個 schema 版本，尚無「需排除的舊版」 |

#### 反向思考

- **若 A 錯**：舊 JSON 有結構性破壞變更（非欄位缺少，而是語意改變）→ App 嘗試解析 → damage marking 大量觸發 → 使用者看到大部分「損壞」的專案。此情境需要 schema 有結構性破壞同時 `schema_generated_at_framework_version` 未跟著更新——依設計不應發生（版本欄位記錄產生時點，schema 變更必然產生新版本）。即使發生，damage marking 比完全阻擋（schema 不相容）提供更多資訊。
- **若 B 錯**：App 升級後所有舊 JSON 專案被不必要地阻擋 → 使用者被迫等待所有專案重新匯出 JSON。這是更差的使用者體驗，且與 SPEC-001 FR-04「版本不符時拒絕渲染」的精神不符——這裡是「版本相符但數字不同」。
- **若 C 錯**：與 A 同風險方向，但增加一個必須維護的資產。

#### 基本率

- 現存 JSON 版本數：1（`"2.40.3"`）
- 可載入候選數：2（flutter_balance、graph_project_docs_manager）
- 三個候選在現有資料上結果完全一致（2.40.3 == 2.40.3 且 <= 2.40.3）
- 差異僅在 App 或專案框架版本演進後才顯現

### 2. 定案結論

**採 Candidate A：`json_version <= builtin_version`**

**「App 已知範圍」定義**：

> `tracking_schema.json` 的 `schema_generated_at_framework_version` 值
> 不高於 App 內建資產 `builtin_schema_version.json` 的同名欄位值時，
> 該 JSON 在 App 已知範圍內（版本在範圍內）；高於時超出已知範圍
> （schema 不相容）。

**判定式**（偽碼）：
```
isInAppKnownRange(jsonVersion, builtinVersion) =
    !isHigherThanBuiltinSchemaVersion(jsonVersion, builtinVersion)
```

**理由**：
1. 與 SPEC-001 所有「超出」用語的方向一致——「超出」即「高於」，上界為 App builtin
2. 向後相容：App 升級後自然接納舊 JSON，舊 schema 子集由既有 damage marking（SPEC-001 FR-05）處理
3. 安全預設：版本字串無法解析時拒絕，與「不確定時不自動降級」精神一致
4. 零額外資產：重用 `isHigherThanBuiltinSchemaVersion` 函式，僅改第一運算元
5. 現有資料驗證：W1-032 manifest 中兩個「可載入」候選 JSON 版本 2.40.3 = builtin 2.40.3 → `!isHigher(2.40.3, 2.40.3)` = `true` → 在範圍內 → 正常，符合預期
